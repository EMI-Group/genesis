# SystemLive Support Modules

## Intent

Support modules extracted from `EvoDashWeb.SystemLive` to keep the main LiveView module focused on lifecycle callbacks and event handlers.

## Routing Table

None — leaf directory (five module files: `status.ex`, `charts.ex`, `update_card.ex`, `source_card.ex`, `runtime_controls.ex`).

## API Surface

### Modules

| Module | Purpose |
|--------|---------|
| `Status` | Status-checking pure functions that derive overall status (`:ok`/`:error`/`:info`/`:warning`/`:loading`) from system-check result maps, plus backend name and config item label formatting. Includes `overall_health/1` — the merged system-health derivation for the self-check health banner: takes the per-check maps plus `sandbox_shown`/`nix_shown` flags and returns `%{status: :ok \| :warning \| :error \| :loading, reasons: [String.t()]}` with gettext-wrapped, human-readable failure reasons (`:loading` while any critical assign is nil; sandbox/nix only count when their cells are actually rendered) |
| `Charts` | Pure SVG/ring-buffer helpers + chart-card components for the SystemLive scheduler-status charts (hand-rolled server-rendered SVG — no JS plotting lib; see the "System page charts (SVG, zero JS)" section in this file for full data semantics). Consumes the PRE-AGGREGATED sample maps broadcast by the evo_git system sampler DIRECTLY — the aggregation logic lives in the evo_git sampler. Sample maps carry the per-model `llm_slots` map (`%{model_id => %{used:, waiting:, capacity:}}` — the ONLY source for the LLM chart, read defensively, missing ⇒ 0) plus the 12 legacy aggregate keys (`llm_used, llm_waiting, llm_capacity, tool_used, tool_waiting, tool_capacity, agents_total, agents_running, agents_blocked, agents_waiting, agents_pending, scheduler_alive` — still consumed by the tool/agents series builders; the legacy `llm_*` keys NO LONGER drive the LLM chart). Pure functions: `push/2,3` (ring buffer, cap 60), `llm_series/2` (per-model, from each sample's `llm_slots[model_id]`), `llm_model_ids/1` (sorted unique model ids across samples), `tool_series/1`/`agents_series/1` (series builders with gettext names), `y_max/1` (max×1.2 headroom, floor 4), `y_for/2`, `path_for/2` + `pad_to_capacity/2` (SVG `d` strings, zero left-pad). Components (`use Phoenix.Component` + gettext + CoreComponents `icon`): `charts_section/1` (full section: header + paused badge + 3-card grid; takes a `selected_llm_model` attr — resolution rule keep-if-present-else-first-id) and `chart_card/1` (legend + SVG sparkline, "Collecting data…" placeholder while `samples == []`; optional `model_ids`/`selected_model` attrs render the in-card model selector) |
| `UpdateCard` | Software update card (auto-update UI, desktop+local-only): `active_task_ids/1` — the ONLY `EvoDash.NodeContext.list_task_ids/2` consumer in the dashboard (always LOCAL `node()`, `@active_statuses = [:running, :pending, :cancelling, :finalizing]`, id-only). See the `## Auto-Update card flows` section below |
| `SourceCard` | Genesis Source **card** (clone/update UI for the `EvoGit.SelfReflectiveSource` managed checkout, **local-only** — `visible?/1` = `node in [nil, node()]`; a remote `genesis_remote` daemon's self-reflective agent reads the REMOTE host's filesystem, so clone/update must never act remotely). Markup: `source_section/1` component (`source_card.ex`) — renders the Genesis Source as a PEER CARD of the System Self-Check check grid (`id="genesis-source-card"`, a direct grid child inside `<div id="system-self-check">` alongside the Configuration / Required Tools / Sandbox / Nix / LLM Connection cells; same `rounded-lg border border-base-300 bg-base-100` container, tinted icon box (`p-2 rounded-md bg-info/10`) + `font-semibold text-sm` title), showing only the minimal useful info: the checkout directory (`dir`), commit + version when cloned — plus the clone/update buttons in a bottom-right action row of the card. Branch (`main`) and Remote URL (the repo path) displays are NOT rendered (always-constant values), and there is NO reference line (the Directory row already shows the checkout path); the "in use" badge (`status.is_reference`) sits next to the title, and when `override_in_effect?/1` holds the muted note "An explicit override is in effect" carries the actual reference path. Public spawn functions `spawn_status_load/3`, `spawn_clone/3`, `spawn_update/3` run on `EvoDash.TaskSupervisor` and self-message the LiveView (`{:source_status_loaded, seq, node, result}` / `{:source_clone_result, ...}` / `{:source_update_result, ...}`). Runners resolve from app-env seams AT SPAWN TIME: `:source_status_runner` (raw status map or `{:unavailable, reason}`), `:source_clone_runner` / `:source_update_runner` (`{:ok, status} | {:error, reason} | {:unavailable, reason}`). Default runners guard the backend with `Code.ensure_loaded?(EvoGit.SelfReflectiveSource)` and call it via `apply/3` (a direct call to the missing module would emit an "undefined function" compile warning) — absent backend → `{:unavailable, :module_missing}`; async-boundary rescue → `{:unavailable, :runner_error}`. Also hosts the small render helper `override_in_effect?/1` (moved here from `system_live.ex` when the markup was extracted) — no `reference_path/1` helper exists (the reference line it fed is gone). Events `clone_source` / `update_source` + assigns `source_card_visible`, `source_status`, `source_status_loading`, `source_busy`, `source_status_seq` stay in `system_live.ex` |
| `RuntimeControls` | The grouped **System Controls** section — the LAST content section of the System page (`controls_section/1` in `runtime_controls.ex`, wrapper `id="system-controls"`): light section header + the three system-control-related cards — **System Dashboard** (`.link navigate` to `/dashboard`, path passed as the `dashboard_path` assign), **Scheduler Control** (pause/resume) and **System Control** (VM restart/stop) — rendered as three VERTICAL cards (`flex flex-col`, title+description top, actions bottom) in a responsive grid (`id="runtime-controls"`, `grid grid-cols-1 md:grid-cols-2 lg:grid-cols-3 gap-3`) so all three sit on one line on wide screens and stack on narrow ones. There is no standalone System Dashboard link card and no separate two-column runtime-controls row — the section is the single bottom container for all three. Pure markup — all behavior stays in the LiveView event handlers (`toggle_pause`, `request_restart`, `request_stop` + the confirmation modals rendered by `system_live.ex`). Assigns consumed: `scheduler_paused`, `dashboard_path` (computed in `system_live.ex` via `with_node_param/2` — the component holds no `~p`/`with_node_param` imports) |

## Constraints

- The module contains pure functions — no I/O, no socket, no process calls. (`UpdateCard`/`SourceCard` are the exceptions: async spawn helpers that run on `EvoDash.TaskSupervisor`.)
- Follows the project-wide `try/rescue` anti-pattern policy — the ONLY rescue is at the async boundary in the `SourceCard` spawn functions (a crashing runner must not wedge the card's loading/busy state).
- The Genesis Source card is **local-only** by design: `SourceCard.visible?/1` returns `node in [nil, node()]`, so clone/update never act on a remote node (a remote daemon's self-reflective agent reads the remote host's filesystem).

## System page section order (top → bottom)

The System page (`EvoDashWeb.SystemLive`, inline `render/1` in `system_live.ex`) renders, in order:

1. **Software Update card** — `id="software-update-card"`, first section, gated `@update_card_visible` (desktop+local only).
2. **System Self-Check** — `id="system-self-check"`: merged health banner + responsive check grid (Configuration / Required Tools / Sandbox gated / Nix gated / LLM Connection cells) with the **Genesis Source card** (`SourceCard.source_section/1`, `id="genesis-source-card"`) as a PEER grid cell when `@source_card_visible` (local only). The whole grid area collapses to a spinner during a re-check (`system_checks_status == :checking`), so the source card hides then too.
3. **Scheduler status charts** — `Charts.charts_section/1` (SVG, zero JS).
4. **System Controls** (LAST content section) — `RuntimeControls.controls_section/1` (`id="system-controls"`): ONE grouped section holding the three system-control cards — **System Dashboard** (`.link navigate` to `/dashboard`), **Scheduler Control** (pause/resume), **System Control** (restart/stop) — as three VERTICAL cards in a responsive grid (`id="runtime-controls"`, `grid grid-cols-1 md:grid-cols-2 lg:grid-cols-3 gap-3`) so all three sit on one line on wide screens and stack on narrow ones. The System Dashboard link is one of the three cards here; there is no separate standalone System Dashboard item and no two-column runtime-controls row elsewhere.
5. **Bottom modals** (fixed overlays) — restart/stop confirm modals, the Software Update apply modals (busy wind-down + force-kill), and the update **changelog modal** (gated on `@changelog_open`, see "Auto-Update card flows").

## Notes for Agents — System self-check design (health banner + check grid)

The self-check section (System page) is a merged health banner + responsive 2D grid of check-term cells:

- **Overall health banner** (full-width, top of the self-check section, ALWAYS rendered — including during `:checking`, where it shows a neutral spinning "Checking system health..." state): derived by `Status.overall_health/1` from `health_checks/1` (private in `system_live.ex`) — a map of the five check assigns plus `sandbox_shown`/`nix_shown` flags mirroring the cell gating in the template. Returns `%{status: :ok | :warning | :error | :loading, reasons: [String.t()]}`:
  - `:loading` when any ALWAYS-critical assign (supervisor/config/tools) is nil — nil checks render neutral, never as errors.
  - `:error` when any critical check fails: process tree (`Status.supervisor_healthy?/1`), configuration (`Status.config_ok?/1`), tools (`Status.tools_status/1 != :ok`), or sandbox (`Status.sandbox_status/1 != :ok` **only when `sandbox_shown`**).
  - `:warning` when only non-critical issues exist: nix enabled-but-not-built (`Status.nix_status/1 != :ok`, **only when `nix_shown`**) — deliberately NOT a hard failure (nix is optional).
  - `reasons` are gettext-wrapped human-readable strings ("Required settings are missing or invalid", "A required tool (git or ripgrep) is missing", "Sandbox is unavailable", …) rendered as a bullet list under the banner headline ("System running correctly" / "System needs attention" / "System running, but needs attention").
  - `@config_status` carries the remote config status on a remote node, so the banner needs no extra RPC.
- **Check grid**: `div.grid.grid-cols-1.sm:grid-cols-2.lg:grid-cols-3.gap-3` with one `check_cell/1` per term: Configuration, Required Tools, Sandbox (gated `EvoDashWeb.PlatformInfo.show_sandbox?(@platform_os)`), Nix Environment (gated `@nix_check != nil and enabled and available`), LLM Connection (info status, `~p"/settings?category=llm&node=…"` link) — plus the **Genesis Source card** (`SourceCard.source_section/1`, `id="genesis-source-card"`) as the last grid cell when `@source_card_visible` (local only; it hides with the rest of the grid during a re-check spinner).
- **DOM contract (AUTHORITATIVE — do not deviate)**: check cells do NOT emit `<details>`/`<summary>` — the header is a plain `<div class="flex items-center gap-3 p-4">`, and the detail + `:fix` slot are always rendered (fix gated `@status not in [:ok, :info] and @fix != []`). Do NOT re-add a disclosure.
- **Test markers**: title spans render exactly as `<span class="font-semibold text-sm">{title}</span>` so `>Sandbox</span>` / `>Nix Environment</span>` markers match; "flake.nix"/"Flake valid"/"hero-lock-closed"/"sandbox-exec (macOS)"/"bwrap (Linux)" detail strings are unchanged. `Status.format_backend/1` maps `:bwrap` → "bwrap (Linux)" (badge `badge-success` in the check grid); `Status.sandbox_status/1` treats bwrap with `capabilities.filesystem_isolation` as `:ok`.
- **Supervisor health feeds ONLY the merged banner**: there is no "Genesis Process Tree" row and no `supervisor_status/1` component.
- **`~p` gotcha**: interpolating into the PATH portion of a static route (`~p"/settings#{…}"`) emits a compile-time "no route path" warning (test_path materializes the interpolation as `"1"` → `/settings1`); use `with_node_param/2` (appends `?node=` — only safe for query-less URLs) or interpolate in the query portion only.

## System page charts (SVG, zero JS)

- Hand-rolled server-rendered SVG — ZERO JS dependencies (the vendored asset set is fixed; do not add JS/CSS for charts).
- `EvoDashWeb.SystemLive.Charts`: `push/2,3` (ring buffer, cap 60), `llm_series/2` (ONE model profile — per-sample values from each sample's `llm_slots[model_id]` via a defensive `Map.get` chain: a sample missing `:llm_slots`, a missing model key, or a missing inner key ⇒ 0 for that sample, so sparklines stay continuous during rollout; `model_id` nil/absent ⇒ all-zero series, no crash), `llm_model_ids/1` (sorted unique model ids = union of per-sample `llm_slots` keys; `[]` for empty buffer/dead scheduler/legacy sampler without the key), `tool_series/1`/`agents_series/1` (series builders with gettext names — still Map.fetch!-based on the 12 aggregate keys), `y_max/1` (max×1.2 headroom, floor 4), `y_for/2`, `path_for/2` + `pad_to_capacity/2` (SVG `d` strings, zero left-pad). Components (`use Phoenix.Component` + gettext + CoreComponents `icon`): `charts_section/1` (header + paused badge + 3-card grid; optional `selected_llm_model` attr) and `chart_card/1` (legend + SVG sparkline, "Collecting data…" placeholder while `samples == []`; optional `model_ids`/`selected_model` attrs). Markup: `<svg viewBox="0 0 300 100" preserveAspectRatio="none">` + `vector-effect="non-scaling-stroke"`; the Capacity series renders as a `static: true` dashed horizontal line at the LATEST per-sample capacity (per-model, so past peak/off-peak transitions gain y_max headroom automatically).
- **Per-model LLM plot + in-card selector**: the LLM Slots card plots ONE model profile, chosen by the deterministic clamp rule — keep `selected_llm_model` if it is present in the samples' model ids, else `List.first(llm_model_ids(samples))` (nil when none ⇒ all-zero series). When `chart_card`'s `model_ids` is non-empty the card renders the compact control between the description and the chart body: a static muted single-model label when exactly one id is known, else a compact dropdown (DaisyUI `select select-sm select-bordered rounded-md w-full`, `name="model"`, `phx-change="select_llm_model"`, `aria-label="Model"` — every id an `<option>`, the current `selected_model` preselected; the select sits in a minimal inert `<form>` because LiveView change events only fire from inputs inside a form, and the input-level binding serializes only its own field → params `%{"model" => id}`). No control when `model_ids == []` (no samples / legacy sampler without `llm_slots`) — the all-zero LLM series chart still renders when samples exist. Model ids are user-config strings — never gettext-ed, never atomized.
- **Consumes the PRE-AGGREGATED sample maps broadcast by the evo_git system sampler DIRECTLY** — the aggregation logic lives in the evo_git sampler, NOT here. Each sample now carries the per-model `llm_slots` map (config-profile id STRING keys → `%{used:, waiting:, capacity:}`; every configured profile present; `%{}` when the scheduler is dead) AND the 12 legacy aggregate keys (`llm_used, llm_waiting, llm_capacity, tool_used, tool_waiting, tool_capacity, agents_total, agents_running, agents_blocked, agents_waiting, agents_pending, scheduler_alive`) — the tool/agents charts still read those; the legacy `llm_*` keys NO LONGER drive the LLM chart.
- **Selection state (dashboard-side)**: `SystemLive` holds a `selected_llm_model` assign (`nil` on mount and on node switch — resolution re-defaults to the first id once the new node's samples arrive). Every samples-change path (live `{:system_sample, ...}` push and the seed-fill success arm) recomputes it via `resolve_selected_llm_model/2` with the NEW samples list + the OLD selection (one assign); the `select_llm_model` event handler stores the chosen id clamped by the SAME rule (an id no longer in the buffer falls back to the first available id). The per-model data itself lives in the evo_git sampler; only SELECTION is dashboard-side.
- **Push contract**: `{:system_sample, node, seq, sample}` every 3s from a node-side sampler. **Seed**: on mount/node-switch ONE async `EvoDash.NodeContext.get_recent_system_samples(current_node)` runs via `EvoDash.TaskSupervisor` + self-message `{:system_samples_seeded, seq, node, result}` + stale-guard (monotonic `chart_seed_seq` + node); on error ONE retry after 3s (one-shot, gated by `chart_seed_retried` — NOT periodic); on node switch the buffer is cleared + re-seeded. The `:system_samples_runner` app-env test seam is resolved AT SPAWN TIME. `{:scheduler_config_updated, node}` → `spawn_paused_load/1`. Remote nodes: pure PubSub (samples arrive via the cluster).

## Async node-aware loads on System page

- `spawn_node_loads/1` spawns TWO `EvoDash.TaskSupervisor` tasks: `spawn_paused_load/1` → `{:paused_state, node, paused}` (gated by `scheduler_alive?/1`) and `PlatformInfo.os_for_node(node)` → `{:platform_os_result, node, os}`.
- Both `handle_info` clauses are stale-guarded on `socket.assigns.current_node == node`.
- Mount defaults: `scheduler_paused: false`; `platform_os` takes the local fast-path only (`current_node in [nil, node()]` → synchronous `os_for_node` call, preserving the `:platform_os_override` test seam).
- Test idiom: `await_view_assign(view, key, value)`.

## Genesis Source card (peer of the System Self-Check grid)

The Genesis Source UI renders as a CARD (`source_section/1` in `source_card.ex`, outer wrapper `id="genesis-source-card"`) that is a PEER CELL of the System Self-Check check grid inside `<div id="system-self-check">`, gated on `@source_card_visible` (local nodes only). It is the grid's last child, alongside Configuration / Required Tools / Sandbox / Nix / LLM Connection, with the same `rounded-lg border border-base-300 bg-base-100` container, a tinted icon box (`p-2 rounded-md bg-info/10` + `hero-code-bracket-square` `size-4 text-info`), and a `font-semibold text-sm` title — it reads as a proper card "alongside the others", not a full-width line. Because it lives inside the grid, it hides together with the grid area while a re-check is running (`system_checks_status == :checking` collapses the grid to a spinner) — acceptable/consistent; its own `source_status_loading` states (loading spinner / unavailable message / map status) still work as cell content. Layout/design decisions:

- **Simplified info**: only the checkout directory (`status.dir`), the commit + version when cloned, and the "not cloned yet" explanation ("The Genesis source has not been cloned yet."). Branch (`status.branch` — always `main`) and Remote URL (`status.remote_url` — always the repo path) displays are NOT rendered (useless constants). There is NO reference line — the old "The self-reflective agent reads: %{path}" text is gone (the Directory row already shows the checkout path), and no `reference_path/1` helper exists. The "in use" badge (`status.is_reference`, `badge badge-info badge-sm`) sits NEXT TO THE TITLE in the card header. When `override_in_effect?/1` holds (reference != managed dir), the muted note "An explicit override is in effect" carries the actual reference path in a `font-mono` span (info preservation — an explicit override can differ from the managed dir in the Directory row; no plain path is duplicated in the non-override case).
- **Subtitle + bottom-right action row**: the card is a flex column (`flex flex-col`); the header is `flex items-center gap-3 p-4` holding only the icon box + title + badge; the info body is `px-4 pb-4 text-sm flex-1 flex flex-col` and starts with the subtitle "Genesis source checkout used by the self-reflective agent.", then renders the loading / unavailable / map-status states. Clone (`id="clone-source"`, `phx-click="clone_source"`) vs Update (`id="update-source"`, `phx-click="update_source"`) buttons are chosen by `status.exists` and render at the END of the body in a bottom-right action row (`mt-auto pt-3 flex justify-end gap-2`) only when `not @source_status_loading and is_map(@source_status)` (loading/nil/`{:unavailable, _}` states show no buttons — matching the old standalone card). Busy-state labels ("Cloning…"/"Updating…" with spin icon) + `disabled={@source_busy != nil}` logic unchanged. Events `clone_source` / `update_source` + assigns `source_card_visible`, `source_status`, `source_status_loading`, `source_busy`, `source_status_seq` stay in `system_live.ex`; flashes ("Genesis source cloned." etc.) unchanged.
- Local-only (`SourceCard.visible?/1` = `node in [nil, node()]`); a remote daemon's self-reflective agent reads the REMOTE host's filesystem, so clone/update must never act remotely.
- Guarded backend: `Code.ensure_loaded?(EvoGit.SelfReflectiveSource)` + `apply/3` (a direct call to the missing module emits an "undefined function" compile warning) — absent backend → `{:unavailable, :module_missing}`; async-boundary rescue → `{:unavailable, :runner_error}`.
- Seams resolved at spawn: `:source_status_runner` (raw status map or `{:unavailable, reason}`), `:source_clone_runner` / `:source_update_runner` (`{:ok, status} | {:error, reason} | {:unavailable, reason}`).
- Status map contract (UNCHANGED, backend-owned): `%{dir:, exists:, is_git_repo:, valid:, commit:, branch:, version:, remote_url:, reference:, is_reference:}`.

## SystemLive platform gating (EvoDashWeb.PlatformInfo)

- Sandbox self-check **cell** wrapped in `if PlatformInfo.show_sandbox?(@platform_os)` (no "Not Available"/"Disabled" messaging on Windows/unknown); Nix Environment **cell** wrapped in `if @nix_check != nil and @nix_check.enabled and @nix_check.available` (nix hidden when disabled in config OR binary not found — `EvoGit.Nix.enabled?/0` + `EvoGit.Platform.nix_available?/0`).
- `platform_os` assigned in mount + handle_params (after `assign_node/2`). `safe_system_checks/1` — checks run on the LOCAL VM; only the config status is fetched remotely. The same gating predicates drive the health-banner aggregation via `health_checks/1`.

## Auto-Update card flows

Software Update card (FIRST section of the page — `system_live.ex` render, after the remote gate) — gated on `@update_card_visible` = `UpdateStatus.visible?(@current_node)` (computed in `handle_params/3` after `assign_node`; hidden on the `mix` dev server and on remote `genesis_remote` nodes). State hub = `EvoDash.UpdateStatus` (see `apps/evo_dash/lib/evo_dash/CONTEXT.md` — state machine, `"updates"` broadcast contract, once-per-version `request_download?/0` guard). Architecture: three layers (state hub / global on-mount hook `EvoDashWeb.LiveHooks.UpdateStatus` / JS hook in `assets/js/app.js` ~L753) connected ONLY by the event-name protocol — no module cross-references between the card and the global hook. The Rust `check_update`/`download_update`/`begin_update` commands are a separate workstream (`desktop/src-tauri/CONTEXT.md`); JS invokes them defensively (missing keys tolerated → hub normalizes to `:error`).

**Card states** (per `docs/auto-update.md` §11.2): `:checking` (spinner), `:up_to_date` ("Genesis <current> is up to date" + last-checked), `:available` (compact "Version <latest> is available" line + amber dot + a "View changelog" link + Download button; **notify-only mode** — Linux non-AppImage deb/rpm/portable — shows "update via your package manager" instead, NO self-download), `:ready` ("Update ready" + Restart & Update + blue `animate-ping` dot, plus the same small changelog link), `:error` ("Check failed" + Retry — with two sentinel arms: `error == "not_configured"` → friendly pre-key message (update_status.ex:319-326); `error == "not_available"` → "Latest version <v> — no auto-update for this platform" when the feed's `latest_version` is known else "No auto update on this platform" (update_status.ex:303-317); ANY other error renders the raw backend `error` string in small muted text below the label so real failures are diagnosable), `:applying` (buttons disabled), `:idle` (Check now). Release notes are NEVER dumped inline in the card — the `:available`/`:ready` states stay compact, each rendering a "View changelog" link only when the feed carried notes (`@update_status.notes` present and non-empty); the notes body opens in the changelog modal below. Mount-triggered check fires in `handle_params/3` when visible && connected && hub `:idle`.

**Changelog modal**: opened via the "View changelog" link in the `:available`/`:ready` states (`changelog_link/1` component, `id="view-changelog"`, `phx-click="open_changelog"`; renders nothing unless `changelog_notes?/1` — `@update_status.notes` is a non-empty string). State: `changelog_open` boolean (mount default `false`; reset in `handle_params/3` together with the restart/stop confirmation flags on node change). Events: `open_changelog` / `close_changelog` (no-ops unless the card is visible, like the other Software Update card events). Rendered at the bottom of `render/1` with the page's other fixed-overlay modals (`fixed inset-0 z-50` backdrop `phx-click="close_changelog"` + centered `bg-base-100` panel), but wider (`max-w-2xl`), titled "Update changelog", with a scrollable body (`max-h-[70vh] overflow-y-auto`) showing `@update_status.notes` as ESCAPED plain text with `whitespace-pre-wrap` (`{...}` HEEx interpolation — never `raw/1` or `MarkdownRender`: the feed body is remote-supplied) and a Close button (`phx-click="close_changelog"`).

**Flows**:
- **Check** (safe anytime): `check_for_updates` (or mount trigger) → `UpdateStatus.check_started()` + `push_event(socket, "update_check_requested", %{})` + `spawn_check_watchdog/1` on `EvoDash.TaskSupervisor`. Watchdog runs the `:update_check_runner` seam (default: sleep `:update_check_timeout` (30s) then `check_failed("timeout")` if still `:checking`) in try/rescue — `:checking` can NEVER stick. When a runner seam is injected the timeout watchdog ALSO runs in parallel (belt-and-braces for tests). Results arrive via hub broadcasts (real path) or `send(view.pid, {:update_check_result, payload})` (test seam).
- **Auto-download**: after an `"available"` check result, the global hook's interceptor pushes `"update_download_requested"` once per version (`request_download?()` guard); a download failure keeps `:available` with the manual Download button (`download_update` handler pushes the same event). Download is inert/verified (Phase 1).
- **Apply** (gated — the only dangerous step): "Restart & Update" → `active_task_ids(:gate)` = `:update_active_task_ids` seam (list OR one-arg fun `(ctx)`, ctx ∈ `:gate | :winddown_poll`) or node-aware `EvoDash.NodeContext.list_task_ids(node(), [:running, :pending, :cancelling, :finalizing])`. **Idle** → `proceed_apply/1` (`UpdateStatus.applying()` + push `"update_apply_requested"`; JS `begin_update` → `update_apply_confirmed` → `stop_backend/0` via the `:desktop_quit_stop_fun` seam — NEVER `bin/genesis_desktop stop`, broken under `RELEASE_DISTRIBUTION=none`). **Busy** → modal "N task(s) still running" with Defer or "Apply & gracefully stop tasks" → `start_winddown/1`: loops cancelling ALL active tasks (`TaskRegistry.cancel_task/1` — graceful, results preserved `:cancelled` and reviewable) until empty (`{:update_winddown_complete}` → apply) or `:update_winddown_timeout` passes (default ~35 min; poll `:update_winddown_poll_ms` default 5s; keeps cancelling newly-appearing tasks so nothing starts mid-wind-down) → user-warned force-kill modal → `confirm_force_kill_update` → `force_kill_all/0` (`TaskRegistry.force_kill_task/1`) → apply. Wind-down crashes → `{:update_winddown_error, _}` → error flash (never wedge).

**Sidebar notification dot** (`components/layouts.ex`): `sidebar_nav_link/1` has a `notification` attr; the System nav link passes `notification={update_status_notification(@update_status)}` — amber dot (`bg-amber-500`) on `:available`, blue `animate-ping` (`bg-blue-500`) on `:ready`. `@update_status` comes from the global on-mount hook, so the dot appears on every page and updates from `"updates"` broadcasts. All 9 `Layouts.app` call sites pass `update_status={@update_status}`; JS hook mount point: `<div id="update-status-hook" phx-hook="UpdateStatus" />` inside the app layout.

**Exhaustive "Check failed" enumeration** — the card renders "Check failed" (`system_live.ex:275`) exactly when `phase == :error` AND `error` is neither `"not_configured"` nor `"not_available"` — the two sentinels are the ONLY check-status values that bypass it. Every path into non-sentinel `:error`:
1. **Check-result payload → `:error`** (`apply_check_result/2`, update_status.ex:266-347): non-map payload → `"check_failed"`; `"status" => "error"` → `payload["error"] || "check_failed"` PLUS `latest_version: payload["version"] || state.latest_version` (an error payload carrying the feed's version still shows it); `"not_available"` → sentinel while KEEPING the payload's `latest_version`/`notes`/`date`; any OTHER/absent/non-string status → `payload["error"] || "check_failed"` (unknown statuses imply a stale/mismatched Rust build or a seam).
2. **Watchdog timeout** (`default_watchdog/1`, update_card.ex:136-143): `check_failed("timeout")` if still `:checking` after 30s. Spawned on every SystemLive check trigger (`system_live.ex:859` mount-trigger, `:1087` Check-now click). Real-world causes: JS result never arrives (hook unmounted mid-navigation → `pushUpdateEvent` guard no-ops app.js:789-799), or Rust check >30s (its plugin timeout is also 30s — a slow fetch can transiently show "Check failed" then be overridden by the late JS result, a legal transition). JS timer-driven checks (30s startup / 6h periodic, app.js:772-773) spawn NO watchdog and never call `check_started/0` — only SystemLive-triggered checks enter `:checking`.
3. **Crashing check runner** — `spawn_check_watchdog/1` try/rescue (update_card.ex:67-73) → `check_failed("check_failed")` (production-irrelevant; only fires with the runner seam).
4. **Download-result errors** (`apply_download_result/2`, update_status.ex:350-376; JS `invokeUpdateDownload` app.js:811-819): non-map payload → `"check_failed"`; `"status" => "error"` while phase NOT in `[:available, :checking, :ready]` → `:error` with `payload["error"]` (can be nil); unknown download status → `"check_failed"`. From `:available` (normal download state) an error returns to `:available` — card does NOT show "Check failed". Note Rust download `not_configured` returns the LONG message string as `error` (main.rs:178-181), NOT the sentinel — so a download error from an unexpected phase renders "Check failed" even pre-key.
5. **Apply failures** (`apply_failed/1`, update_status.ex:221-223; hook `handle_event("update_apply_failed")` → `apply_failed(payload["error"] or "apply_failed")`): `:applying` → `:error` → "Check failed" (shared `:error` branch). From JS `invokeUpdateApply` (app.js:824-836): `begin_update` resolving without `{ok: true}` or throwing.

**Broadcast/subscription notes**: `mount/3` subscribes to `"updates"` (system_live.ex:742) AND the on-mount hook subscribes the same pid (update_status.ex:162) — Phoenix PubSub dedupes identical {pid, topic} subscriptions, exactly one copy delivered. The on-mount `:handle_info` interceptor consumes `{:update_status, state}` with `{:halt, ...}` BEFORE SystemLive's own clause (system_live.ex:1215-1220, dead code in the merged system) — both assign the same state, no divergence. `mount/3`'s `update_status: UpdateStatus.get()` snapshot (line 780) is taken before handle_params triggers `check_started/0` — first paint shows `:idle` then `:checking` via broadcast (no gap). Late-arriving results always override earlier `:error`/`:checking` states; the timeout watchdog no-ops once phase leaves `:checking` — the UI can never permanently wedge on "Checking for updates…".

## Known Issues — markup/theme gotchas (Adwaita restyle)

- **`*-content` tokens must never sit on translucent tints** — the semantic `-content` pairs are tuned for the SOLID semantic fill and are polarity-swapped per theme (light `success-content`/`error-content`/`info-content` = `#ffffff`, dark = `#1e1e1e` near-black, GNOME-style). `text-success-content` on `bg-success/20` renders white-on-pale-mint in light AND near-black-on-dark-green in dark — invisible in both themes (same for `text-warning-content` on `bg-warning/20` in dark). Correct grammar on tints (used everywhere else, e.g. `check_cell`, task-status tints): full `text-<semantic>` token on `bg-<semantic>/10..20`. `-content` is only for text sitting ON the solid fill (solid `btn-success`, `badge-warning`, etc.). This directory's support-module markup (`runtime_controls.ex`, `charts.ex`, `source_card.ex`) follows the correct grammar; keep it that way when adding markup.
- **Card/page separation is a hairline**: cards must read as cards against the `bg-base-100` main view (`layouts.ex` `main#main-content`) — app.css comments designate `base-300` as the "borders" tone; `base-200` is "chrome/hover". This directory's card containers (`charts.ex` chart-card, `source_card.ex` genesis-source-card, `runtime_controls.ex` Scheduler/Dashboard cards) use `border-base-300`; the model-selector dropdown inside the chart card uses the standard DaisyUI `select-bordered` grammar (the same bordered-select token used by the other in-card/app selects). If cards elsewhere must read as cards (esp. dark), prefer `border-base-300` or add a subtle shadow — this is app-wide grammar, so change it centrally, not per card.
