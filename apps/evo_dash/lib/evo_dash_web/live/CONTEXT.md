# LiveView Pages

## Intent
Phoenix LiveView modules and templates for the EvoDash interactive UI — real-time task management, agent inspection, runtime configuration, and user help.

### HomeLive operational UX and current gotchas

`home_live.ex` presents "Genesis Assistant" with the shared provider/model/reasoning picker in its own `#chat-llm-selection-form`, separate from the composer, so native input change events reach the existing selection handlers.
The page retains idle-only New chat, a separately scrolling transcript, pinned approval cards and the "Message Genesis Assistant…" composer.
Every nonblank idle send starts a NEW `:reflect` task with `mode: "reflect"`, bounded textual conversation preamble and no `:path`; the current message itself has no page-level length limit and cannot be sent while a task is running or cancelling.
Enter submits through a server-maintained Shift latch, Shift+Enter keeps the newline, and model selection stays available during a run but affects later tasks only.
Stop gracefully cancels only the chat's own task, not a task discussed in the answer; after success the page enters cancelling, hides Stop and leaves disabled Send visible until a terminal event.
Node switches reset chat state without cancelling the previous task, reset model selection across target/node scopes, and keep older chats in the local dashboard's in-memory ChatHistory with a ten-chat prune cap but no chat-switching UI.
The page has no full remote connection gate, but pending-target model loads and sends are blocked so a disconnected remote selection cannot launch a local reflect task; the source gate still keys visibility to the resolved BEAM node.
Connected mount subscribes to tasks, agents and approvals, then ApprovalWorkflow recovers the core's live pending requests off-process after chat restoration and whenever usable chat/node/root-agent scope changes, with explicit recovery retry and no polling.
Approval ownership requires a nonblank request id, matching task OR normalized agent id, and matching source node; evaluator requests require a source-node stamp, and pending remote contexts never recover or respond against the local service.
Pending approval cards occupy a pinned, internally scrolling area between transcript and composer capped at `min(11rem,25dvh)`.
Evaluator cards preserve exact original code and target runtime, distinguish one-time write consent from unrestricted sudo evaluation, and retain legacy command-level approval presentation.
Decisions route by chat/source node through ApprovalWorkflow, never by evaluator target node; busy cards remain visible with both decisions disabled until a matching result arrives.
Response failures retain cards and show translated retry guidance; success, backend not-found or resolution broadcasts remove them, while scope/token guards and recovery tombstones reject late results and prevent snapshot resurrection.
Approval state remains ephemeral and outside ChatState; remount/reconnect recovery rebuilds it from the actual core `EvoGit.CommandApproval.pending/0` via `NodeContext.call_remote/4`.
Agent lookup fetches the node's agent roster and history refreshes fetch the WHOLE chat-agent history on each message-count event, without page-level debounce, incremental offset, pagination or payload cap; seq guards discard stale responses rather than cancelling outstanding work.
Completed/cancelled events fetch a lite task row and finalize from its result, but a live failed broadcast immediately displays generic "The task failed." and clears refs without fetching its structured error; structured failure detail is available only through fetched-task reconciliation.
A failed terminal task read degrades to nil and is displayed as "The conversation was deleted.", conflating RPC/store failure with a genuinely missing task.
Chat lookup/history share `chat_fetch_seq`, terminal reads use a separate `chat_task_fetch_seq`, and model/source loads have separate counters; `reset_chat/1` resets both chat counters to zero while model/source counters survive.
Local-only persistence stores full transcript and thought history at lifecycle updates, not every draft keystroke, and neither transcript nor thought history has a per-chat byte/count bound in this page.
Support modules own exact suggestion wording, answer rendering, transcript preamble limits and approval styling; see `home_live/CONTEXT.md` rather than duplicating those details here.

### Example-task teaching content (onboarding)

- `EvoDashWeb.ExampleTask` (`example_task.ex`) — shared module holding the demo objective text (`example_objective/0`, verbatim string, NOT gettext-wrapped). Single source of truth for the "example task" teaching sections: the onboarding completion page (`WelcomeCompleteLive` at `/welcome/complete` — `welcome_live.ex` does not render the example card) and the projects-page no-project empty-state panel (`projects_live.ex`, gated by `is_nil(@active_project)` — disappears once a project is open; contains a collapsible `<details>` panel with Copy + prefill buttons).
- Copy-to-clipboard reuses the global `ClipboardCopy` hook (`data-content` + `phx-hook="ClipboardCopy"`, pushes a `"copied"` event); each page rendering example content defines its own `handle_event("copied", ...)` flash handler (pattern: `welcome_complete_live.ex`, `review_live.ex:338`).
- Dashboard prefill ("Use this example") uses a hidden `<textarea id="example-task-objective" class="hidden" readonly>` RCDATA holder + inline onclick JS: `p.value = h.value; p.dispatchEvent(new Event('input', {bubbles: true}))`. The dispatched input drives the AdaptiveInput hook — autogrow AND the client-side layout switch (the example — 1554 chars — crosses the layout thresholds (char count and the compact height cap), so the hook flips `data-layout` to expanded; the flip can also be height-driven). No server event is involved — there is no `phx-change` on the prompt textarea (`phx-update="ignore"` keeps the DOM value stable); `@task_prompt` is only updated by `restore_state` / `task_submit`. NEVER set this via innerHTML — the example text contains literal `<link>`/`<script>` strings; always use the `.value` property.

### Node-Aware Integration
All LiveViews register the `EvoDashWeb.LiveHooks.NodeAware` on-mount hook (via the `live_view/0` macro in `evo_dash_web.ex`). As part of the node-aware pattern, each LiveView:
- Calls `assign_node/2` in `handle_params/3` (reads the `?node=<id>` query param, resolving it to a saved+connected target or falling back to local).
- Passes `current_node_id` / `current_node_name` (and `remote_targets` / `connection_statuses`) to the `Layouts.app/1` call.
- Handles `{:node_selected, _}` (delegated to `NodeAware.handle_node_selected/2`) and `{:remote_connection_status, _, _}` messages (delegated to `NodeAware.handle_connection_status/2`).

### Canonical LLM selection and configuration boundaries
`llm_selection.ex` (`EvoDashWeb.LLMSelection`) is the shared Projects/Assistant task-picker boundary over canonical `llm.providers` and `llm.default_provider_profile`; legacy profile ids are migration input only, never parsed by splitting their strings.
Its fixed APIs are `from_config/2`, `reconcile/2`, `task_opts/3` (with a default third argument), `select_provider/3`, `select_model/3` and `select_reasoning_effort/3`, backed by `EvoGit.Config.Schema.provider_profiles/1`, `model_selections/1` and `resolve_model_spec/2`.
The server-only bundle contains `config`, `provider_profiles`, `model_selections` and `model_selection_enabled`; config may contain credentials and must never enter browser state or ChatHistory.
Picker state contains only STRING keys `provider_profile_id`, `model` and optional `reasoning_effort`; `%{}` or a legacy empty string means explicit Auto, while nil means uninitialized and resolves the configured default even when selection rules exist.
`reconcile/2` restores stale display selections to the configured default, whereas `task_opts/3` rejects invalid explicit selections and removes old `model_spec`/`model_id`/`model_id_locked` options before emitting `model_spec: spec, model_id_locked: true` or no model options for Auto.
Provider/model changes reset downstream defaults; the shared component's native slider submits a ZERO-BASED index into the exact model's ordered effort inventory, normalized through `LLMSelectionComponents.resolve_reasoning_effort/3` before persistence or launch.
The reasoning helper also accepts a resolved effort string; an advertised inventory with no default starts at its first entry, and a model without an inventory omits the task-level override.
Both Projects task forms render the canonical projections and `selected_model_spec`, and normal submissions plus GitHub issue fixes use `ProjectsLive.LaunchOptions.apply/2` for identical strict model locks, nonblank custom-agent ids and nondefault `fast`/`high_quality` options.
Quality level remains an independent speed/quality policy, not reasoning effort; invalid selections return an error before either path starts a task.
`LLMSelection.canonical_spec/1` deliberately projects `resolved.provider_profile_id`, `resolved.model`, `resolved.reasoning_efforts` and `resolved.reasoning_effort`; `resolved.model_spec` is the ReqLLM-ready model argument used by connection tests, not the canonical picker map.
Projects seeds picker scope/readiness/error state and uses `ProjectsLive.ModelSelectionScope.bundle/1` to enforce `{target_id, beam_node}` ownership for changes, launch and persistence, including same-target reconnects.
Async picker loads guard generation, target id, BEAM node and project path, preserve newer choices and pending restores on failure, and expose a retry rather than silently selecting Auto.
Normal submissions and GitHub fixes share the same readiness/restore gate, while GitHub request envelopes additionally bind unique request tokens to reject stale or unscoped results.
Browser restoration waits for the owned ready bundle and migrates legacy ids through the shared resolver; model-only `persist_model_selection` updates merge canonical fields into the same node's saved state without replacing DOM-owned drafts.
Full-form persistence remains separate from draft-safe partial updates; helper state-machine and retry details belong in `projects_live/CONTEXT.md` and browser consumption in `apps/evo_dash/assets/CONTEXT.md`.
Assistant uses `HomeLive.ModelSelect.load/1` for a tagged `%{node:, config:, model_selection_enabled:}` snapshot, local synchronously or remote via supervised SafeCall with `model_select_seq` and node guards.
A failed loader startup immediately clears `model_select_loading` and records a load error because no result message will arrive.
`HomeLive.ModelSelect.task_opts/4` (defaulting opts) requires the snapshot and selection scope `{current_node_id, current_node || node()}` to match before preparing a repo-less reflect launch, and errors before adding a user bubble or clearing its draft.
`HomeLive.ChatState` persists only the three canonical picker keys, a scope and shape-error marker, with `selected_model_id` retained only as legacy migration input; New chat can retain a same-scope choice, different scopes reset to the new node's default and unscoped legacy ids migrate locally only.
Pending remote targets never load a local model snapshot or submit locally, and load failures remain errors instead of silently changing a pin to Auto; support details belong in `home_live/CONTEXT.md`.
Welcome creates multi-model provider profiles through `welcome_live/Setup`, not legacy shadow model rows; onboarding persistence, OAuth and test-scoping details are documented below and in `welcome_live/CONTEXT.md`.

### Settings canonical configuration and connection tests
Settings renders canonical provider profiles outside the generic category form, delegates editor transformations/events to its helpers, and uses `ConfigIO.canonicalize_file_config/1` across save paths to preserve unrelated config while removing legacy shadow keys.
The core Schema facade supplies canonical projections/resolution and provider-profile validation during normal boot; dashboard code must not introduce facade shims or bypass validation.
Connection tests reconcile the persisted selection after config loads/saves, bind `test_config_scope` to `{target_id, beam_node}`, and reject pending targets or configuration from another scope.
Tests resolve the selected provider/model on the viewed node and pass its ReqLLM-ready model argument plus full core-composed authentication, reasoning and generation options, never local credentials for a remote test.
`SafeCall.start/4` delivers `{{:llm_test_result, seq, scope}, result}` with scope `{target_id, beam_node, selection_value}`; config, selection or node changes invalidate the sequence, unscoped legacy results are ignored, and startup failures settle immediately.
`persist_file_config/3,4` delegates local and remote writes to `ConfigSave.start/4`, and the full nested `{{:settings_config_saved, token, scope}, result}` message passes to `ConfigSave.complete/2` before the page applies any config or success feedback.
Only a matching save receipt updates file config, runtime profiles, persisted test selection, health and OAuth status; failed writes retain the previous config and correction draft, while successful writes with failed refreshes show warnings.
Provider creation uses atom `:new` (a saved string id `"new"` is ordinary), and the page passes raw nested submissions and `profile_form_errors` through to the editor helpers/components.
Editor/save ownership uses `{target_id, beam_node}` plus request tokens, and switches or reconnect phase changes invalidate saves before replacing identity, clear drafts/errors and invalidate old config-load generations.
An invalidated writer retains its live-worker guard until termination, and the page monitors that worker to defer a fresh scope snapshot until its write is finished.
Generic category/search saves filter through `ConfigIO.generic_schema?/1`, and resets use the protected `parse_key_path/2` boundary rather than touching dedicated provider/default paths.
Editor, OAuth, persistence and test-runner details belong in `settings_live/CONTEXT.md`.

### Shared Conventions
- All LiveViews use `use EvoDashWeb, :live_view` and import `CoreComponents` and `Layouts`.
- All pages use `EvoDashWeb.Layouts.app/1` layout with `current_page` for nav highlighting.
- Every page also carries `@accent_color` (the shell-wide config accent, `data-accent-color` on `#app-layout`), seeded by `EvoDashWeb.LiveHooks.Appearance` (registered in `live_view/0` after `NodeAware`) from a per-node accent cache (`EvoDash.AccentCache`). On a LOCAL node it resolves `EvoGit.Config.resolve([:appearance, :accent_color])` synchronously inside a `:handle_params` interceptor; on a REMOTE (`?node=`) target the cache is read synchronously first (a warm remote accent paints from the first paint — no interim local/default color), and a connected socket additionally spawns an async `EvoDash.TaskSupervisor` fetch via `NodeContext.get_resolved_config/1` that lands through a stale-guarded `:handle_info` interceptor and writes the cache on success — never an RPC on the render path. Detail: `../live_hooks/CONTEXT.md`.
- Styled with DaisyUI/Tailwind CSS; business logic delegated to context modules.

### UI Patterns (modals, forms, events)
These patterns are used consistently across the LiveViews. Follow them when adding new interactive features.

- **Modal pattern:** A modal is conditionally rendered with `<%= if @some_assign do %>` wrapping a `<div class="modal modal-open bg-black/50" id="...">` containing a `<div class="modal-box ...">`. Open/close state is driven by a `nil`/value socket assign: opening via `phx-click="open_modal"` (optionally carrying `phx-value-id`), closing via `phx-click="close_modal"` resetting to nil; the backdrop `<div class="modal-backdrop" phx-click="close_modal">` also closes. See `AgentsLive`'s `view_full_message`/`close_message_modal` and `EvoDashWeb.Helpers`'s reusable modal component.
- **Inline editor pattern:** List editors use a `<form phx-submit="save_..." >` with a hidden `<input type="hidden" name="id" value=...>` + visible inputs, submitted by a `<button type="submit">`; edit state is toggled by an `@editing_...` assign. See `SettingsComponents.ModelProfilesEditor.model_profile_edit_form/1` (`phx-submit="save_model_profile"`).
- **Event naming:** Events use `phx-click` (buttons) and `phx-submit` (forms); values passed via `phx-value-<key>="<value>"` (received in the handler's params map as string keys). Integer ids arrive as strings — `String.to_integer/1` is used to convert.
- **Task cancellation UX** (TasksLive): two two-step server-side confirmation-modal flows follow the SystemLive warning-modal pattern (fixed overlay + backdrop with `phx-click` close + centered panel with warning icon/text + dismiss/confirm buttons; NO custom JS — the assigns `@confirm_cancel_task_id` / `@confirm_force_kill_task_id` drive visibility, mutually exclusive, cleared on node switch). **Graceful cancel** (card's inline Cancel button, `[:pending, :running]`): `confirm_cancel_task` → `EvoDash.NodeContext.cancel_task/2` (agents save + exit, result preserved; `:pending` → immediate `:cancelled`); confirm `btn-warning` "Cancel Task", dismiss "Keep Running". **Force kill** (three-dot dropdown, `[:running, :cancelling]`): `confirm_force_kill_task` → `EvoDash.NodeContext.force_kill_task/2` (kills all agents → `:failed`, result nil'd); confirm `btn-error`. Success → collapse expanded card + `reload_current_page/1`; `{:error, reason}` → error flash. The status filter includes "Cancelling" (`value="cancelling"`) — a pure SQL string comparison (the store's private SQL WHERE builder `EvoGit.Store.Operations.Tasks.where_filters/2`), so `:cancelling` round-trips with no evo_dash-side atom whitelist. Details: `tasks_live/CONTEXT.md`.

## Notes for Agents — "tasks" topic broadcast handlers

## Notes for Agents — async data-load & exit-safety contract (these pages)

**Current rule: no LiveView process ever blocks on a store / registry / cross-node RPC call, and no page renders unbounded task blobs.**
Every read that can cost an `:erpc` round-trip or a `GenServer.call` into the task store runs in a supervised `EvoDash.TaskSupervisor` child (each call inside `EvoDash.SafeCall.run/1`) and lands as a self-message guarded by a monotonic seq/generation counter PLUS a node match (and usually a project-path / task-id match too).
Every per-click MUTATION is either a guarded `EvoDash.SafeCall.run/1` in the handler or a supervised `EvoDash.SafeCall.start/4` task whose result message is ALWAYS sent, so a loading flag can never stick.
The exit-safety is load-bearing, not defensive: a `GenServer.call` timeout, a dead store, or an unreachable remote node EXITS the caller (which `rescue` alone cannot catch) — an unwrapped call in a handler kills the LiveView, and an unwrapped call in a loader wedges the page's loading state forever.
`EvoDash.SafeCall` (`../../evo_dash/safe_call.ex`, detail in `../../evo_dash/CONTEXT.md`) is the ONLY sanctioned boundary: `run/1` → `{:ok, v} | {:error, {:exit, reason} | {:exception, e} | {kind, reason}}`, `run/2` → the value or a caller-supplied fallback, `start/4` → a supervised task that always reports `{tag, result}`.
**Message-shape rule (gotcha): `start/4` sends the tag VERBATIM as the message's first element — a multi-element tuple tag stays ONE nested tuple and is NEVER flattened into the message.** A `{:foo, seq, node}` tag arrives as `{{:foo, seq, node}, result}`; handlers MUST pattern-match that nested shape (a flattened `{:foo, seq, node, result}` clause silently never matches, so the outcome is lost — e.g. an approval-response error would never flash). Terms differ for tasks spawned directly with `Task.Supervisor.start_child` + a manual `send/2`, whose tags ARE flat (`{:chat_history_loaded, node, seq, agent_id, result}`).

### Projects parent resume and target-identity gotchas
`ProjectsLive.handle_params/3` derives `remote?` only from BEAM-node inequality, while project activation selects the remote path by non-nil target id, so a connected target aliasing the local BEAM follows inconsistent branches.
The remote-activation continuation sets `resume_foreign_repos_guard` from the pending resume id; the parent clears that flag only on target-id switches and otherwise relies on the AsyncLoad remote-extras continuation to consume it.
A same-BEAM connected target can therefore leave the resume guard set if helper remote-extras loading follows the parent's false `remote?` assign.
The URL `resume_from` handling also unconditionally starts `start_foreign_repos_restore/2`, whose lookup is the LOCAL `TaskRegistry.get_task_lite/1` even in a remote-target context; remote activation already restores the task's repos separately.
That local restore's result guard checks only task id and BEAM node, not target id or request generation, and can overwrite the remote activation's restored list or survive a same-BEAM target switch.

## Constraints
- Each LiveView uses either an inline `render/1` or a companion `.html.heex` template — not both. (Three render inline; `AgentsLive` uses a separate template.)
- Auto-refresh intervals must be gated behind `connected?/1` to avoid leaking timers.
- Naming: `<name>_live.ex` for modules, `<name>_live.html.heex` for companion templates.
- **No `try/rescue` around config/core-value loading.** LiveViews must NOT wrap `EvoGit.Config.*`, `EvoGit.AgentScheduler.*`, or `EvoGit.SystemCheck.*` calls in `try/rescue`. If these crash, the LiveView SHOULD crash truthfully — displaying a wrong default value (e.g. `false`, `%{}`, `100_000`) is worse than a visible crash, and the supervision tree handles recovery. Defensive `rescue _ -> default` around these functions is an anti-pattern and must be removed.
- **`try/rescue` for external boundaries requires a justification comment.** The only accepted use is around genuinely untrusted external execution (e.g. `System.cmd` running project-config-defined shell commands in `ProjectsLive`'s `run_command`), where a user-friendly error flash is better UX than a LiveView crash. Every retained `try/rescue` must carry a comment explaining why it is justified.
- **Atom conversion from untrusted input uses whitelist lookups, not `try/rescue`.** For converting user-supplied strings (URL params, form POST data) to atoms, use explicit `Map` lookups (`Map.get/2`, `Map.fetch/2`) or `case` against a known whitelist — never `String.to_existing_atom/1` wrapped in `try/rescue`, and never `String.to_atom/1` (atom-table exhaustion DoS risk).
