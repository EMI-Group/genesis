# LiveView Pages

## Intent
Phoenix LiveView modules and templates for the EvoDash interactive UI — real-time task management, agent inspection, runtime configuration, and user help.

### Example-task teaching content (onboarding)

- `EvoDashWeb.ExampleTask` (`example_task.ex`) — shared module holding the demo objective text (`example_objective/0`, verbatim string, NOT gettext-wrapped). Single source of truth for the "example task" teaching sections: the onboarding completion page (`WelcomeCompleteLive` at `/welcome/complete` — `welcome_live.ex` does not render the example card) and the projects-page no-project empty-state panel (`projects_live.ex`, gated by `is_nil(@active_project)` — disappears once a project is open; contains a collapsible `<details>` panel with Copy + prefill buttons).
- Copy-to-clipboard reuses the global `ClipboardCopy` hook (`data-content` + `phx-hook="ClipboardCopy"`, pushes a `"copied"` event); each page rendering example content defines its own `handle_event("copied", ...)` flash handler (pattern: `welcome_complete_live.ex`, `review_live.ex:338`).
- Dashboard prefill ("Use this example") uses a hidden `<textarea id="example-task-objective" class="hidden" readonly>` RCDATA holder + inline onclick JS: `p.value = h.value; p.dispatchEvent(new Event('input', {bubbles: true}))`. The dispatched input drives the AdaptiveInput hook — autogrow AND the client-side layout switch (the example exceeds the 600-grapheme threshold, so the hook flips `data-layout` to expanded). No server event is involved — there is no `phx-change` on the prompt textarea (`phx-update="ignore"` keeps the DOM value stable); `@task_prompt` is only updated by `restore_state` / `task_submit`. NEVER set this via innerHTML — the example text contains literal `<link>`/`<script>` strings; always use the `.value` property.

### Node-Aware Integration
All LiveViews register the `EvoDashWeb.LiveHooks.NodeAware` on-mount hook (via the `live_view/0` macro in `evo_dash_web.ex`). As part of the node-aware pattern, each LiveView:
- Calls `assign_node/2` in `handle_params/3` (reads the `?node=<id>` query param, resolving it to a saved+connected target or falling back to local).
- Passes `current_node_id` / `current_node_name` (and `remote_targets` / `connection_statuses`) to the `Layouts.app/1` call.
- Handles `{:node_selected, _}` (delegated to `NodeAware.handle_node_selected/2`) and `{:remote_connection_status, _, _}` messages (delegated to `NodeAware.handle_connection_status/2`).

### Shared Conventions
- All LiveViews use `use EvoDashWeb, :live_view` and import `CoreComponents` and `Layouts`.
- All pages use `EvoDashWeb.Layouts.app/1` layout with `current_page` for nav highlighting.
- Styled with DaisyUI/Tailwind CSS; business logic delegated to context modules.

### UI Patterns (modals, forms, events)
These patterns are used consistently across the LiveViews. Follow them when adding new interactive features.

- **Modal pattern:** A modal is conditionally rendered with `<%= if @some_assign do %>` wrapping a `<div class="modal modal-open bg-black/50" id="...">` containing a `<div class="modal-box ...">`. Open/close state is driven by a `nil`/value socket assign: opening via `phx-click="open_modal"` (optionally carrying `phx-value-id`), closing via `phx-click="close_modal"` resetting to nil; the backdrop `<div class="modal-backdrop" phx-click="close_modal">` also closes. See `AgentsLive`'s `view_full_message`/`close_message_modal` and `EvoDashWeb.Helpers`'s reusable modal component.
- **Inline editor pattern:** List editors use a `<form phx-submit="save_..." >` with a hidden `<input type="hidden" name="id" value=...>` + visible inputs, submitted by a `<button type="submit">`; edit state is toggled by an `@editing_...` assign. See `SettingsComponents.ModelProfilesEditor.model_profile_edit_form/1` (`phx-submit="save_model_profile"`).
- **Event naming:** Events use `phx-click` (buttons) and `phx-submit` (forms); values passed via `phx-value-<key>="<value>"` (received in the handler's params map as string keys). Integer ids arrive as strings — `String.to_integer/1` is used to convert.
- **Task cancellation UX** (TasksLive): two two-step server-side confirmation-modal flows follow the SystemLive warning-modal pattern (fixed overlay + backdrop with `phx-click` close + centered panel with warning icon/text + dismiss/confirm buttons; NO custom JS — the assigns `@confirm_cancel_task_id` / `@confirm_force_kill_task_id` drive visibility, mutually exclusive, cleared on node switch). **Graceful cancel** (card's inline Cancel button, `[:pending, :running]`): `confirm_cancel_task` → `EvoDash.NodeContext.cancel_task/2` (agents save + exit, result preserved; `:pending` → immediate `:cancelled`); confirm `btn-warning` "Cancel Task", dismiss "Keep Running". **Force kill** (three-dot dropdown, `[:running, :cancelling]`): `confirm_force_kill_task` → `EvoDash.NodeContext.force_kill_task/2` (kills all agents → `:failed`, result nil'd); confirm `btn-error`. Success → collapse expanded card + `reload_current_page/1`; `{:error, reason}` → error flash. The status filter includes "Cancelling" (`value="cancelling"`) — a pure SQL string comparison (`EvoGit.Store.Queries.build_where`), so `:cancelling` round-trips with no evo_dash-side atom whitelist. Details: `tasks_live/CONTEXT.md`.
- **LiveComponent event routing:** Inside a `use EvoDashWeb, :live_component`, events use `JS.push("event", target: @myself, value: %{...})` (targets the component itself) or plain `phx-click` (targets the parent LiveView). `NodeSelectorComponent`'s `select_node` targets `@myself`, then `send(self(), {:node_selected, id})` to the parent. See `components/CONTEXT.md`.

## Notes for Agents — Platform-specific Settings/System gating (`EvoDashWeb.PlatformInfo`)

`live/platform_info.ex` — platform detection for LiveViews with remote-node support. API:

- `os_for_node(current_node)` → `:linux | :macos | :windows | :unknown`. **Testability override FIRST**: `Application.get_env(:evo_dash, :platform_os_override, nil)` — when set to a known OS atom it is returned directly (the injection seam; `:os.type/0` is not injectable). Local node (nil/`node()`) → `EvoGit.Platform.os()`. Remote node → `EvoDash.NodeContext.call_remote(node, :os, :type, [])` mapped (`{:unix,:darwin}`→`:macos`, `{:unix,_}`→`:linux`, `{:win32,_}`→`:windows`, else `:unknown`). **Total — never raises** (justified `try/catch` at the cross-node RPC boundary, precedent `NodeContext.call_remote/4`).
- Pure predicates: `windows?/1`, `macos?/1`, `linux?/1`, `show_sandbox?/1` (→ `os in [:linux, :macos]`; conservative false for `:windows`/`:unknown`), `sandbox_backend_for/1` (`:linux→:systemd_run`, `:macos→:sandbox_exec`, `_→:none`).
- `filter_schemas_by_category(schemas_by_category, os)`: `:windows`/`:unknown` → `Map.delete(:sandbox)`; `:macos` → keep only `sub_category == nil` sandbox schemas (mode + write_paths; drops `:resources`/`:process`/`:linux` — consumed ONLY by the Linux/systemd-run machinery); `:linux` → unchanged. Other categories untouched (`Map.get(schema, :sub_category)` — absent key = nil).

**SettingsLive**: `schemas_by_category` filtered per node OS in `mount/3` AND re-filtered in `handle_params/3` (BEFORE `category_str_to_atom` so `?category=sandbox` resolves nil on Windows → falls back to `:llm`). **Data-safety**: filtering is BOTH the display mechanism AND the save round-trip protection — `save_category` only processes schemas present in the filtered list and `params_to_category_config` deep-deletes params absent from the form, so hidden sandbox fields (e.g. `[:sandbox,:resources]`, `[:sandbox,:linux]` on macOS) are never clobbered on save. `sandbox_backend(assigns)`: local → `@scheduler_config[:sandbox_backend]` (accurate, reflects binary availability); remote → `PlatformInfo.sandbox_backend_for(@platform_os)`. Details: `settings_live/CONTEXT.md`.

**SystemLive**: Sandbox self-check **cell** wrapped in `if PlatformInfo.show_sandbox?(@platform_os)` (no "Not Available"/"Disabled" messaging on Windows/unknown); Nix Environment **cell** wrapped in `if @nix_check != nil and @nix_check.enabled and @nix_check.available`. Details: `system_live/CONTEXT.md`.

**Tests**: platform-gating coverage lives in `test/evo_dash_web/live/platform_info_test.exs` via the `:platform_os_override` seam; `settings_live_test.exs` and `system_live_test.exs` are `async: false` (safe for `Application.put_env` + `on_exit` cleanup).

## Notes for Agents — Welcome page stepwise quick setup (welcome_live.ex)

The quick setup is a **stepwise flow** (provider → variant → model → credentials):

- **Events**: `select_welcome_provider` (sets `selected_provider_id` + defaults `selected_variant_id` to the provider's FIRST variant; fully resets `selected_entry`/`api_key_input`/`base_url_input`/`search_query`/`llm_test_status`), `select_welcome_variant` (whitelist against the provider's variants; same resets), `base_url_changed` (mirrors `api_key_changed`), `select_welcome_model` (also resets `base_url_input`), `save_welcome_setup` (accepts `base_url`). Assigns: `selected_provider_id`, `selected_variant_id`, `base_url_input`. Model entries come from `flat_models` (built by `flatten_models`/`build_flat_entry` — keys `provider_id, provider_display_name, variant_id, variant_display_name, credential_key, model_id, model_display_name, resolved_atom, model_string`); per-provider filtering via `provider_models/3` + `filtered_provider_models/2`.
- **Credentials gating**: the api_key input, merged save button, and connection test render ONLY when `@selected_entry != nil`. The Base URL input renders only when `EvoGit.Config.LLMCatalog.requires_base_url?(@selected_entry.provider_id)` is true (currently no preset provider requires it); a hidden `base_url` input always carries the typed value so the save/test params shape is stable. `resolve_welcome_model_value/4` threads the typed base_url.
- **Custom-model providers excluded**: the provider grid skips `custom_model: true` entries (OpenRouter/OpenAI-Compatible API) — they have no preset models; the end-of-list guidance card directs users to Settings.
- **LLM connection test** (`test_llm` event + `{:llm_test_result, result}` handle_info + `llm_test_status` assign, `:idle` default): a compact inline port of the Settings page connection test, rendered as a sibling div BELOW the `phx-submit="save_welcome_setup"` form (MUST stay outside that form — nested forms are invalid HTML). The typed API key (if non-empty) is saved via `EvoGit.Config.save_credentials/1` BEFORE spawning (`EvoGit.SystemCheck.llm_test/1` reads credentials from the saved file). Success row renders `@selected_entry.model_display_name` (NOT `data.model` — avoids the map-render crash class). `select_welcome_model` AND `select_welcome_provider`/`select_welcome_variant` reset `llm_test_status` to `:idle` so stale results never show for a different model.
- **Back button**: page-body row above the header (visible in both setup/all-set states), pure client-side: `onclick="if (window.history.length > 1) { history.back(); } else { window.location.href = '/'; }"` — no phx event. The page passes `simple_nav={false}`.
- **Test strategy**: `test/evo_dash_web/live/welcome_live_test.exs` derives ALL model ids/display names dynamically from `EvoGit.Config.LLMCatalog.providers()` (helpers `provider/1`, `model_string/2`) — never hardcode model ids there; the catalog changes frequently. Connection-test LiveView tests inject `:testing` via `:sys.replace_state` + `Phoenix.LiveView.Utils.force_assign` (the async task is racy); ok/error via `send(view.pid, {:llm_test_result, ...})` + `render(view)`. A typed API key in a `test_llm` test makes the spawned task attempt a REAL provider request (fails fast with the bogus key); the unit-style handler test uses NO typed key so it fails fast without network.

## Notes for Agents — "tasks" topic broadcast handlers

`EvoDashWeb.LiveHooks.NodeAware.on_mount/4` subscribes EVERY LiveView (`use EvoDashWeb, :live_view` in `evo_dash_web.ex`) to `EvoGit.PubSub` topic `"tasks"` — so every connected LiveView process receives the raw `{:task_updated, task_id, status, node}` / `{:task_deleted, task_id, node}` broadcasts in ITS OWN `handle_info` and MUST have matching clauses (or a catch-all). NodeAware's attached `:handle_info` hook passes everything except `{:node_aware_active_tasks, ...}` through with `{:cont, socket}` — it does NOT intercept task broadcasts. The failure mode is a FunctionClauseError that kills the LiveView on the next task broadcast. The status is matched with a wildcard (`_status`), so ALL statuses are covered (`:pending`, `:running`, `:cancelling`, `:finalizing`, `:completed`, `:cancelled`, `:failed`, `nil` for review-only mutations) plus `{:task_deleted, _, _}`.

**New LiveViews added via `use EvoDashWeb, :live_view` MUST add three clauses**: `{:task_updated, ...}` + `{:task_deleted, ...}` forwarding to `NodeAware.handle_task_info/2` (which applies `event_from_current_node?/2` BEFORE the 300ms trailing-edge debounce; returns `{:noreply, socket}` — do NOT re-wrap in an extra `{:noreply, ...}`), plus `handle_info(:node_aware_reload_tasks, socket)` → `{:noreply, NodeAware.reload_tasks(socket)}` (the debounce self-message crashes without it — welcome pages need it too once they forward). Mirror `settings_live.ex:850-867`. The actual reload runs the page-specific refresh (tasks_live: `reload_current_page`; projects_live: project-config refresh + browser notifications + sidebar; review_live: broadcast-guarded async review-data reload — only the reviewed task's own broadcasts re-fetch) and ends with `NodeAware.clear_task_reload_pending(socket)`. Test idioms: `tasks_live_test.exs` `":task_updated broadcast handling"` (real `Phoenix.PubSub.broadcast(EvoGit.PubSub, "tasks", ...)` + render) and `node_aware_test.exs` (direct `NodeAware.handle_task_info/2` unit tests).

## Constraints
- Each LiveView uses either an inline `render/1` or a companion `.html.heex` template — not both. (Three render inline; `AgentsLive` uses a separate template.)
- Auto-refresh intervals must be gated behind `connected?/1` to avoid leaking timers.
- Naming: `<name>_live.ex` for modules, `<name>_live.html.heex` for companion templates.
- **No `try/rescue` around config/core-value loading.** LiveViews must NOT wrap `EvoGit.Config.*`, `EvoGit.AgentScheduler.*`, or `EvoGit.SystemCheck.*` calls in `try/rescue`. If these crash, the LiveView SHOULD crash truthfully — displaying a wrong default value (e.g. `false`, `%{}`, `100_000`) is worse than a visible crash, and the supervision tree handles recovery. Defensive `rescue _ -> default` around these functions is an anti-pattern and must be removed.
- **`try/rescue` for external boundaries requires a justification comment.** The only accepted use is around genuinely untrusted external execution (e.g. `System.cmd` running project-config-defined shell commands in `ProjectsLive`'s `run_command`), where a user-friendly error flash is better UX than a LiveView crash. Every retained `try/rescue` must carry a comment explaining why it is justified.
- **Atom conversion from untrusted input uses whitelist lookups, not `try/rescue`.** For converting user-supplied strings (URL params, form POST data) to atoms, use explicit `Map` lookups (`Map.get/2`, `Map.fetch/2`) or `case` against a known whitelist — never `String.to_existing_atom/1` wrapped in `try/rescue`, and never `String.to_atom/1` (atom-table exhaustion DoS risk).
