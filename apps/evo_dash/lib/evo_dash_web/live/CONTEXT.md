# LiveView Pages

## Intent
Phoenix LiveView modules and templates for the EvoDash interactive UI — real-time task management, agent inspection, runtime configuration, and the Genesis Assistant operator chat.

### AgentsLive selected-agent streaming

`agents_live.ex` attaches the selected connected inspector through `agents_live/StreamWatch`, forwarding `:inspector_stream_ready`, `:inspector_stream_reconciled`, `:agent_delta`, `{:agent_stream_closed, agent_id, snapshot, seq}` and worker `:DOWN` in the LiveView consumer process, projecting newly admitted checkpoint messages and authoritative terminal status in the SAME callback.
Selection close, node/target changes and termination detach the watch; a selected owned watch survives agent removal and keeps its retained ended detail outside the live tree; the serial worker fields and monotonic watch/history counters survive scope resets.
A sealed snapshot's explicit status outranks late summary/status updates; a status-less snapshot lets the first terminal summary settle both live and retained detail and then rejects stale overwrites; `phase: :done` alone never implies success; a late terminal summary can settle an already-removed agent without reintroducing its tree row.
Core snapshots atomically capture checkpoint messages, nested `activity: %{phase:, current_call: nil | %{id:, turn:, attempt:, text:, thinking:}}` and an authoritative sequence, including accumulated current-call content even without watchers.
StreamWatch freezes retirement/replacement batches, coalesces atomic snapshot requests and replays only newer buffered deltas; `StreamWatch.reconciled/6` guards scope, request identity and the sequence watermark.
Watched checkpoint history belongs exclusively to the stream (snapshot-pending/reconciling/FAILED watches keep their last coherent checkpoint/live pair); independent history results cannot overwrite owned rows and message-count updates cannot start history RPCs while ownership holds.
Watched-history Retry and empty-history full-message refresh use `StreamWatch.reconcile/1`; transport failures require explicit reattachment, never fallback history reads or polling.
Unwatchable agents keep the independent history fallback (`{:agent_history_loaded, agent_id, node, history_seq, watch_token, result, modal_index}`, guarded by selection/node/sequence/watch token; unscoped five-element results ignored).
`StreamPanel.stream_panel/1` renders an assistant-style live current-call row at the memory tail with inline activity/animation outside checkpoint loading/empty/error; checkpoint memory stays unsuppressed with no message-identity guessing.
The stable `agent-history-<id>` root uses `InspectorMessages`, `data-inspector-scope` binds node/target/selection/watch/snapshot scope, and checkpoint rows expose `data-inspector-message` markers; raw history, tool details, modals and DOM ids stay intact; activity interpretation stays in `StreamPresentation`/`StreamPanel`.

### ProcessesLive (managed OS processes)

`ProcessesLive` (`GET /processes`, sidebar **Processes**) lists the executions `EvoGit.ProcessManager` tracks on the viewed node — agent tool calls (in-BEAM built-in ones included) and background jobs — with node-filtered, PUSH-driven liveness off the `"processes"` topic (`{:process_started, execution, node}`, `{:process_updated, id, changes, node}`, `{:process_exited, execution, node}`, `{:process_sample, node, seq, entries}`, `{:process_control, id, entry, node}`) and NO polling.
The initial snapshot and any `agent_id`/`task_id`/node change load asynchronously through `ProcessesLive.Load` (`{:processes_loaded, seq, node, result}`, `load_seq` + node stale guards); the status tab / kind / text filters are pure render-time state (`Format.filter/2`, tab counts over the other dimensions); stream mechanics are in the Routing Table row above.
Filters are URL state — `?status=live|finished|all`, `?kind=tool_call|background_job`, `?q=`, `?agent_id=`, `?task_id=` — with `node` appended by `&` (never `Helpers.with_node_param/2`, which appends `?`); pause/resume are one-click with default reasons, while terminate/kill require a non-empty reason in the confirm modal and run through `ProcessesLive.Actions` (`:processes_control_runner`, 4-arity).
A `:builtin` call has no OS process (Target/Uptime/CPU/Memory render `—`, no control cluster); terminal facts (`exit_code` plus a `reason` of `:exited`, `:timeout`, `:invalid_arguments`, `:owner_died`, `{:killed_by, actor}`, `{:crashed, detail}` or `:no_os_process`) are recorded for foreground shell calls too.
A genuinely new row (the list is newest-first, so it joins at the head) enters with the `process-row-enter` class from the `:entering` MapSet, cleared after the call-time seam `:processes_entering_ttl_ms` (default 1500 ms) and never on the initial load. Detail: `processes_live/CONTEXT.md`.

### HomeLive interactive-session UX (conversation list, send path, queue/interrupt, approvals)

A conversation is ONE long-lived interactive agent session addressed as `/assistant?session=<agent_id>` (node param appended by `&`); navigation is always `push_patch`, and the legacy `/help` route 302s to `/assistant` with the raw query string preserved (`RedirectController.assistant/2`).
`session` is authoritative in `handle_params/3` (same-id changes short-circuit; a MISSING param means the local draft / new-chat state); `SessionActions.url/2` is the only URL builder and `parse_session/1` parses with `Integer.parse/1` plus a positive guard, never an atom conversion.
`session_mode` is `:interactive`, `:one_shot` (legacy `:reflect` fallback) or nil; a session agent id is a positive integer and doubles as the `EvoDash.ChatHistory` chat id.
Composer: `home_live/Composer.composer/1` renders the textarea above a control bar carrying the shared provider/model/reasoning capsule on the left and Send/Stop/Interrupt on the right inside `#chat-form`; the page header renders no picker, and the transcript scrolls independently above the approval strip and composer.
The page renders no conversation rail: the list is the shared app-layout sidebar's **Conversations** section (`#chat-session-list`, body `SessionList.session_list/1`), rendered below Active Tasks on EVERY dashboard page by `Layouts.app/1`.
The list UNIONs live core sessions (`SessionActions.list/1` → `NodeContext.list_agents/1` + `list_awaiting_input/1`, read defensively) with locally cached chats lacking a live session, ordered awaiting-input → running → ended (newest id first within each live group, cached order for ended).
Each row is `#chat-session-<id>` with a marker (violet "Waiting for you" for `:awaiting_input`, running dot, muted "Ended"), a title from the cached first user message (80 graphemes) → core objective → "Session <id>", and `aria-current` for the current session; a row PATCHES on the Assistant page and NAVIGATES to the same URL elsewhere (a cross-LiveView patch is illegal), so exactly one of `patch`/`navigate` is set.
The list loads ASYNC (no archive, no per-row history) through `LiveHooks.NodeAware` (`session_list`, `session_list_loading`, `session_list_error`, `session_list_seq`): on the connected LOCAL mount, on every `assign_node/2` node-context change (a remote page shows the REMOTE node's sessions) and on every `:node_aware_reload_tasks` debounce — never on a timer.
Send with NO session starts one: `NodeContext.start_session/2` with `SessionActions.session_opts/2` (repo-less `EvoGit.Agents.SelfReflective`, `objective` = the message text with NO preamble, canonical `model_spec` omitted for Auto, pending attachments); on `{:ok, agent_id}` the page adopts it (chat id = agent id, `session_mode: :interactive`, `chat_agent_id`, `chat_status: :running`) and `push_patch`es.
Send WITH a session calls `send_session_message(node, agent_id, %{text:, attachments:}, :queue)` — no new task or chat; `{:session, :finished | :not_found}` marks it `:ended` (cached transcript kept, New chat offered) while `{:session, {:bad_state, phase}}` and other failures only flash a retry-able error.
The one-shot fallback fires ONLY when interactive sessions are unavailable — `function_exported?/3` false, `:llm_not_configured`, or a refusal (`{:interactive_root_only, _}`, `{:invalid_session_opts, _}`, `{:unsupported_session_mode, _}`, also inside `{:start_session_failed, _}`) — starting the legacy `:reflect` task (`mode: "reflect"`, no `:path`, `Transcript.build_preamble/2 <> "New message: " <> text`, `session_mode: :one_shot`); transport errors (`:timeout`, `:noconnection`) are NOT fallback triggers.
Both branches keep the source gate, `ModelSelect.task_opts/4` validation before any send (invalid → "Choose a valid model before sending a message." and nothing sent), the pending-remote refusal and the attachment caps.
The composer stays usable while `:running`; only `:cancelling`, `:ended`, the source gate, a pending remote target or an unready model snapshot disable it.
Queue and interrupt are separate affordances with IDENTICAL behaviour: Send posts `:queue`, `#chat-interrupt-button` posts `:interrupt`, both applied at the next turn boundary — no copy may promise a chunk-level halt.
A send while `:running` appends a transient queued echo (`queued_echoes`, capped at 20) after the last entry, disappearing when `message_count` grows or on stop/close; Stop is a graceful `NodeContext.cancel_task/2` on the session's task id (fallback `SessionActions.close/3`) leaving the page `:cancelling`.
`AssistantComposer` submits on Enter (Shift+Enter newlines); a model selection made during a run applies to the NEXT session only; New chat works while `:idle`/`:ended` and clears draft, per-chat refs, echoes and attachments.
Reattach (`?session=<id>`) restores the cache from `ChatHistory.get_state(session_id)`, spawns ONE supervised attach loader (`list_agents` + `list_awaiting_input` + `get_agent_history`) and attaches the push-only delta watch (`home_live/Watch.attach/1`: PubSub subscription inline in the LiveView, watcher registration + snapshot in a supervised task with the LiveView pid) whose snapshot seeds the transcript via `Messages.transcript/1`.
A non-empty independent attach history replaces the cache only while no watch owns the surface; watched snapshots hydrate checkpoint history and current-call prefixes atomically; `:awaiting_input` maps to `:idle` while running/cancelling phases carry through.
A session with no summary, not awaiting and an empty cache shows "This session has ended." with a disabled composer and New chat (only when no pending/failed watch owns its phase); a gone session WITH a cache renders read-only.
Node switches reset chat state (incl. `session_id`, echoes, attachments) without cancelling the previous session; older conversations stay reachable via the list and the in-memory `ChatHistory` (ten-chat prune cap).
Approvals are scoped to the session: chat id = agent id, `chat_agent_id` is the session agent, `chat_task_id` is the summary `task_id` (set on adoption AND reattach), and `ApprovalWorkflow.init/1` + re-recovery run on every session switch so a previous session's requests never render.
Each assistant entry owns its reasoning (rebuilt by `Messages.transcript/1`, preserved by delta reduction and persistence); the global `thought_process` is a reducer output, not the presentation authority.
Caps: 200 transcript entries (newest kept), 8 000 rendered characters per entry, 40 live thought-buffer entries.
Layout stability: an assistant entry's action footer ALWAYS renders (buttons appear once finalized), the interrupt affordance sits in a constant `h-7` row, `#chat-messages` is a `flex-1 min-h-0` scroller, and the approval strip reserves its height.
`#chat-messages` scroll is the `AgentHistoryAutoScroll` hook — instant, coalesced (ONE `requestAnimationFrame` setting `scrollTop = scrollHeight`, no animation), pinned within a 56 px threshold only user input re-evaluates, following growth via `ResizeObserver` (+ `MutationObserver` re-syncing the observed set); CSS contract `overflow-anchor: none`, `overscroll-behavior: contain`, `scroll-behavior: auto`, `min-height: 0`.
Attachments are local-filesystem-only (picker ids `"chat_file"`, `"chat_file_image"`, `"chat_file_audio"`): a text file appends `"\n\n---\n## Attached file: <basename>\n\n" <> content`, image/audio stage `%{"type" => "image"|"audio", "name" => …, "media_type" => IANA, "data" => raw}` with base64 only at submit; at most 4 per message of at most 15 MiB each, removable chips cleared on a successful send, and a remote/pending target sets `attach_unavailable: true` with a manual-path fallback reading on the LOCAL node.
The page has no remote connection gate, but pending-target model loads and sends are blocked; the source gate keys visibility to the resolved BEAM node.
Connected mount subscribes to tasks, agents and approvals, then ApprovalWorkflow recovers pending requests off-process after chat restoration and whenever usable chat/node/root-agent scope changes, with explicit retry (`retry_approvals`) and no polling; ownership requires a nonblank request id, matching task OR normalized agent id and matching source node (evaluator requests need a source-node stamp), and pending remote contexts never recover or respond locally.
Approvals render in TWO surfaces from `home_live/approval_dialog.ex`: a fixed-height `#approval-status-bar` strip (`approval_bar/1`, `h-10`, reserved even when empty) above the composer with the count badge + Review button (`open_approval_dialog`) and the preserved `#approval-recovery-error` / "Retry approvals" / `#approval-response-error` line, and a single-request `<dialog id="approval-dialog" class="modal" phx-hook="DialogModal">` (`approval_dialog/1`) with `prev_approval`/`next_approval` stepping and a Deny / Allow-once pair.
`approval_dialog_open`/`approval_dialog_index` are LOCAL VIEW state (never persisted; reset by `reset_chat/1` and when nothing remains pending); events are `open_approval_dialog`, `dialog_closed`, `prev_approval`, `next_approval`, `retry_approvals`, `approval_response`.
`ApprovalWorkflow.requested_with_notification/2` admits live arrivals returning `{socket, payload_or_nil}`: only a novel owned pending live request auto-opens the dialog and pushes a privacy-safe `task_notification` (`%{title:, body:, request_id:, scope:, tag:}`, request-scoped tag).

### Draft scope identity (`EvoDashWeb.DraftScope`)
`draft_scope.ex` is the ONE place the browser-draft scope identity is defined; the `StatePersistence` hook and every page that persists a draft consume it instead of building keys themselves.
A scope is `{node, token}`; the token is the selected project's VCT point (`vct:///projects/<name>`, or `vct:///workspaces/<slug>` for a workspace), read from `:point`, `"point"` or `:vct_path` and returned VERBATIM, else the raw absolute OS path also returned verbatim (never `Path.expand/1`ed, trimmed or OS-mangled, because a remote node's path must round-trip).
Its fixed API is `token/1`, `project/1`, `workspace/1`, `point?/1`, `path/1`, `store_key/2` and `legacy_store_key/2`, all pure and total for a mount struct, a string- or atom-keyed map, a bare binary or garbage.
`store_key/2` is the `sessionStorage` shape — `"dashboard_state:" <> Jason.encode!([node, token])`, byte-identical to the legacy path-keyed entry, and the bare `"dashboard_state"` for a nil token — while `legacy_store_key/2` is the path-keyed entry a VCT-scoped draft may be adopted from.
A token is a STORAGE/SCOPE identity only: task admission, `mount_project` and interactive-session start always take the absolute OS path from `path/1`, which answers nil for a `vct:`-only selection (a workspace has no path at all), so a workspace token can never reach `start_task`; `project/1` answers nil for a workspace and `workspace/1` nil for anything else.

### UI Patterns (modals, forms, events)
These patterns are used consistently across the LiveViews. Follow them when adding new interactive features.

- **Modal pattern:** A modal is conditionally rendered with `<%= if @some_assign do %>` wrapping a `<div class="modal modal-open bg-black/50" id="...">` containing a `<div class="modal-box ...">`. Open/close state is driven by a `nil`/value socket assign: opening via `phx-click="open_modal"` (optionally carrying `phx-value-id`), closing via `phx-click="close_modal"` resetting to nil; the backdrop `<div class="modal-backdrop" phx-click="close_modal">` also closes. See `AgentsLive`'s `view_full_objective`/`close_objective_modal` and `EvoDashWeb.Helpers`'s reusable modal component.
- **Inline editor pattern:** editors use a `<form phx-submit="save_...">` with a hidden `<input type="hidden" name="id" value=...>` (the provider editor's hidden `profile_id`) plus visible inputs, submitted by a `<button type="submit">`; edit state is toggled by an `@editing_...`/`@expanded_id` assign, and the form id stays constant because at most one row is edited at a time. See `SettingsComponents.ProviderProfiles.Detail.profile_detail/1`.
- **Event naming:** Events use `phx-click` (buttons) and `phx-submit` (forms); values pass via `phx-value-<key>="<value>"` (string keys in the handler's params map). Integer ids arrive as strings — `String.to_integer/1` converts.
- **Task cancellation / pause UX** (TasksLive): two-step server-side confirmation modals follow the SystemLive warning-modal pattern (fixed overlay + backdrop `phx-click` close + centered panel + dismiss/confirm; NO custom JS — `@confirm_cancel_task_id` / `@confirm_force_kill_task_id` assign visibility, mutually exclusive, cleared on node switch). **Graceful cancel** (inline Cancel button, `[:pending, :running, :awaiting_input]`): `confirm_cancel_task` → `EvoDash.NodeContext.cancel_task/2` (agents save + exit, result preserved; `:pending` → immediate `:cancelled`), confirm `btn-warning` "Cancel Task". **Force kill** (three-dot dropdown, `[:running, :awaiting_input, :cancelling, :pausing, :paused]`): `confirm_force_kill_task` → `EvoDash.NodeContext.force_kill_task/2` (kills all agents → `:failed`, result nil'd), confirm `btn-error`. Both mutations (and close-session) run OFF-PROCESS through `EvoDash.SafeCall.start/3,4`, tagged `{{:cancel_result | :force_kill_result | :close_session_result, task_id}, result}`, guarded by the per-task `action_busy` map cleared on EVERY outcome; success collapses the card, drops the row from the stream where the action removed it and refreshes through the async `PageLoad.start/3`; `{:error, reason}` → error flash. The status filter includes "Cancelling" plus "Pausing"/"Paused" — a pure SQL string comparison (`EvoGit.Store.Operations.Filters.where_filters/2`), so those statuses round-trip as exact stored TEXT with no evo_dash-side atom whitelist. **Pause / resume** ride the same modal idiom off-process (`{{:pause_result, task_id}, result}` / `{{:resume_result, task_id}, result}`) with `action_busy` disabling the pair per task: Pause (`[:running, :pausing]`) opens a `Pause task?` confirmation modal, Resume (`:paused`) posts directly (direct for a `:clean` pause, `phx-confirm`-gated for a `:dirty` one). Details: `tasks_live/CONTEXT.md`.
- **Interactive sessions (`:awaiting_input`)**: a NON-terminal status — the task's root agent is a live interactive session that finished a turn and waits for the user (no worker, no LLM/tool slot, no timer). It is admitted wherever a task counts as ACTIVE but never as busy work: the task card renders a violet badge/label with a reply box and a Close-session action, the sidebar lists it in its own Sessions group, TasksLive renders/filters it server-side and wires `session_send_message` → `EvoDash.NodeContext.send_session_message/4` (`:queue`) and `confirm_close_session` → `EvoDash.NodeContext.close_session/3` (`:normal`), and `/server/status` deliberately excludes it from the busy count. A session has no reviewable `genesis/agent_*` branch until it closes (`show_review_button?/1` still keys on `:completed`); closing it finalizes the task into its normal terminal status. Detail: `tasks_live/CONTEXT.md`, `../components/task_card_components/CONTEXT.md`, `../live_hooks/CONTEXT.md`.
- **LiveComponent event routing:** Inside a `use EvoDashWeb, :live_component`, events use `JS.push("event", target: @myself, value: %{...})` (targets the component itself) or plain `phx-click` (targets the parent LiveView). `NodeSelectorComponent`'s `select_node` targets `@myself`, then `send(self(), {:node_selected, id})` to the parent. See `components/CONTEXT.md`.

## Notes for Agents — "tasks" topic broadcast handlers

`EvoDashWeb.LiveHooks.NodeAware.on_mount/4` subscribes EVERY LiveView (`use EvoDashWeb, :live_view` in `evo_dash_web.ex`) to `EvoGit.PubSub` topic `"tasks"` — so every connected LiveView process receives the raw `{:task_updated, task_id, status, node}` / `{:task_deleted, task_id, node}` broadcasts in ITS OWN `handle_info` and MUST have matching clauses (or a catch-all). NodeAware's attached `:handle_info` hook passes everything except `{:node_aware_active_tasks, ...}` through with `{:cont, socket}` — it does NOT intercept task broadcasts. The failure mode is a FunctionClauseError that kills the LiveView on the next broadcast; the status is matched with a wildcard (`_status`), covering all statuses (`:pending`, `:running`, `:awaiting_input`, `:cancelling`, `:pausing`, `:paused`, `:finalizing`, `:completed`, `:cancelled`, `:failed`, `nil` for review-only mutations) plus `{:task_deleted, _, _}`.

**New LiveViews MUST add three clauses**: `{:task_updated, ...}` + `{:task_deleted, ...}` forwarding to `NodeAware.handle_task_info/2` (which applies `event_from_current_node?/2` BEFORE the 300 ms trailing-edge debounce; returns `{:noreply, socket}` — do NOT re-wrap), plus `handle_info(:node_aware_reload_tasks, socket)` → `{:noreply, NodeAware.reload_tasks(socket)}` (the debounce self-message crashes without it — welcome pages need it too once they forward). The actual reload runs the page-specific refresh (tasks_live: async page load via `TasksLive.PageLoad.start/3`; projects_live: project-config refresh + browser notifications + sidebar; review_live: broadcast-guarded async review-data reload — only the reviewed task's own broadcasts re-fetch) and ends with `NodeAware.clear_task_reload_pending(socket)`. Test idioms: `tasks_live_test.exs` `":task_updated broadcast handling"` (real `Phoenix.PubSub.broadcast(EvoGit.PubSub, "tasks", ...)` + render) and `node_aware_test.exs` (direct `NodeAware.handle_task_info/2` unit tests).

## Notes for Agents — async data-load & exit-safety contract (these pages)

**Current rule: no LiveView process ever blocks on a store / registry / cross-node RPC call, and no page renders unbounded task blobs.**
Every read that can cost an `:erpc` round-trip or a `GenServer.call` into the task store runs in a supervised `EvoDash.TaskSupervisor` child (each call inside `EvoDash.SafeCall.run/1`) and lands as a self-message guarded by a monotonic seq/generation counter PLUS a node match (usually with a project-path / task-id match too).
Every per-click MUTATION is either a guarded `EvoDash.SafeCall.run/1` in the handler or a supervised `EvoDash.SafeCall.start/3,4` task whose result message is ALWAYS sent, so a loading flag can never stick.
The exit-safety is load-bearing, not defensive: a `GenServer.call` timeout, a dead store, or an unreachable remote node EXITS the caller (which `rescue` alone cannot catch) — an unwrapped call in a handler kills the LiveView, and an unwrapped call in a loader wedges the page's loading state forever.
`EvoDash.SafeCall` (`../../evo_dash/safe_call.ex`, detail in `../../evo_dash/CONTEXT.md`) is the ONLY sanctioned boundary: `run/1` → `{:ok, v} | {:error, {:exit, reason} | {:exception, e} | {kind, reason}}`, `run/2` → the value or a caller-supplied fallback, `start/3,4` → a supervised task that always reports `{tag, result}`.
**Message-shape rule (gotcha): `start/3,4` sends the tag VERBATIM as the message's first element — a multi-element tuple tag stays ONE nested tuple and is NEVER flattened.** A `{:foo, seq, node}` tag arrives as `{{:foo, seq, node}, result}`; handlers MUST match that nested shape (a flattened clause silently never matches, so the outcome is lost). Tasks spawned directly with `Task.Supervisor.start_child` + a manual `send/2` have FLAT tags.

### Projects parent resume and target-identity gotchas
`ProjectsLive.handle_params/3` derives `remote?` only from BEAM-node inequality, while project activation selects the remote path by non-nil target id, so a connected target aliasing the local BEAM follows inconsistent branches.
The remote-activation continuation sets `resume_foreign_repos_guard` from the pending resume id; the parent clears it only on target-id switches, and a same-BEAM connected target can therefore leave the guard set.
The URL `resume_from` handling also unconditionally starts `start_foreign_repos_restore/2`, whose lookup is the LOCAL `TaskRegistry.get_task_lite/1` even in a remote-target context; its result guard checks only task id and BEAM node, not target id or request generation, and can overwrite the remote activation's restored list or survive a same-BEAM target switch.

### Task read shapes — the lightweight reads
- A page load is ONE `list_tasks_page/2` returning 18-key SUMMARY rows (`limit: 25`) plus `total` — no `result`/`usage`/`logs`/`archive_metadata`; the store clamps an out-of-range offset itself.
- Heavy per-card data is LAZY: `get_task_lite/2` on expand (full struct, `archive_metadata: nil`, no `:archive_records`; cached per task id and invalidated on a node-matching task event) and, ONLY on an explicit archive disclosure, bounded archive pages (`list_task_archives/3` — 100 entries, no results) with one agent's full entry per "Show result" (`get_agent_archive/3`).
- Search matches `id` / `opts` / `project_path` / `branch_name` only — a task's `result` is NOT searchable; the summary page row is orders of magnitude smaller than the same row through the full-row read, so a page's cost is independent of the `result` blob size.
- `ReviewLive.LoadData` reads the reviewed task with `get_task_lite/2` inside its supervised loader; the Archive tab is rendered and fetched ONLY when the persisted task opts opted into archiving (`EvoDashWeb.ArchiveHelpers.archive_opt?/1`; otherwise `switch_tab` refuses it and `ArchiveLoad` never fetches, showing an explicit "not collected" state) and pages on demand (first page cached per `{task_id, node}`, "Load more" appends by cumulative FETCHED offset, the retained window bounded at `ArchiveHelpers.max_retained/0`).
- `HomeLive.async_fetch_task/2` (terminal event / mount reconciliation), the ProjectsLive notification scan and the resume-restore paths all use lite rows — the terminal path reads only `:status`/`:result`/`:error`.
- On the core side `list_tasks_page`, `get_task_lite`, `list_task_archives` and `get_agent_archive` are all offloaded by the registry, while `get_unique_paths/1` blocks the core TaskRegistry for the duration of its read.
- No dashboard page issues a FULL-row task read: `list_tasks_paginated` and `get_task/2` are unissued (the export controller reads the lite row plus archive pages).

## Constraints
- Each LiveView uses either an inline `render/1` or a companion `.html.heex` template — not both. (Every page except `AgentsLive`, which uses its companion template, renders inline.)
- Auto-refresh intervals must be gated behind `connected?/1` to avoid leaking timers.
- Naming: `<name>_live.ex` for modules, `<name>_live.html.heex` for companion templates.
- **No `try/rescue` around config/core-value loading.** LiveViews must NOT wrap `EvoGit.Config.*`, `EvoGit.AgentScheduler.*`, or `EvoGit.SystemCheck.*` calls in `try/rescue`. If these crash, the LiveView SHOULD crash truthfully — a wrong default value (`false`, `%{}`, `100_000`) is worse than a visible crash, and the supervision tree handles recovery.
- **`try/rescue` for external boundaries requires a justification comment.** The only accepted use is around genuinely untrusted external execution (e.g. `System.cmd` running project-config-defined shell commands in `ProjectsLive`'s `run_command`), where a user-friendly error flash is better UX than a LiveView crash.
- **Atom conversion from untrusted input uses whitelist lookups, not `try/rescue`.** For user-supplied strings (URL params, form POST data), use explicit `Map` lookups (`Map.get/2`, `Map.fetch/2`) or `case` against a known whitelist — never `String.to_existing_atom/1` wrapped in `try/rescue`, and never `String.to_atom/1` (atom-table exhaustion DoS risk).
