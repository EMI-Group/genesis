# LiveView Pages

## Intent
Phoenix LiveView modules and templates for the EvoDash interactive UI — real-time task management, agent inspection, runtime configuration, and user help.

## Routing Table
- `components/` → LiveComponents (`use EvoDashWeb, :live_component`) — `NodeSelectorComponent` for the SSH Remote Development node selector
- `agents_live/` → Support modules extracted from `AgentsLive`: `ToolCallDisplay` (tool-call rendering contract — structured subagent/shell rows + one-line others, constrained height)
- `projects_live/` → Support modules extracted from `ProjectsLive`: `StatePersistence`, `Project`, `Assigns`. Note: `projects_live.ex` is ~1846 lines — a future split of more event handlers into this support directory may be warranted (the recent prompt-sync change was only ~7 lines).
- `settings_live/` → Support modules extracted from `SettingsLive`: `ModelProfileHelpers` (pure data-transformation for `[[llm.models]]` CRUD), `ConfigIO` (config loading, runtime updates, atom whitelists)
- `system_live/` → Support modules extracted from `SystemLive`: `Content` (static guides/references), `Status` (health-check status helpers)
- `tasks_live/` → Support modules extracted from `TasksLive`: `DirtyTracker` (pure dirty-check state machine gating the remote-node `:remote_poll` full-page reloads)

### Example-task teaching content (onboarding)

- `EvoDashWeb.ExampleTask` (`example_task.ex`) — shared module holding the demo objective text (`example_objective/0`, verbatim string, NOT gettext-wrapped). Single source of truth for the "example task" teaching sections on the onboarding surfaces: the onboarding completion page (`WelcomeCompleteLive` at `/welcome/complete` — the example card moved here from the Welcome page; `welcome_live.ex` no longer renders it) and the projects-page no-project empty-state panel (`projects_live.ex`, gated by `is_nil(@active_project)` — disappears once a project is open; contains a collapsible `<details>` panel with Copy + prefill buttons).
- Copy-to-clipboard reuses the global `ClipboardCopy` hook (`data-content` + `phx-hook="ClipboardCopy"`, pushes a `"copied"` event); the pages that render example content each define their own `handle_event("copied", ...)` flash handler (pattern: `welcome_complete_live.ex`, `review_live.ex:312`).
- Dashboard prefill ("Use this example") uses a hidden `<textarea id="example-task-objective" class="hidden" readonly>` RCDATA holder + inline onclick JS: `p.value = h.value; p.dispatchEvent(new Event('input', {bubbles: true}))`. The dispatched input drives the AdaptiveInput hook — autogrow AND the client-side layout switch (the example exceeds the 600-grapheme threshold, so the hook flips `data-layout` to expanded). The hook also re-asserts the layout after any server re-seed of `data-layout` from the possibly-stale `@task_prompt` (MutationObserver on `.input-layout`, e.g. after toggling mode/model). No server event is involved — there is no `phx-change` on the prompt textarea; `@task_prompt` is only updated by `restore_state` / `task_submit`. `phx-update="ignore"` on the prompt textarea keeps the DOM value stable. Never set this via innerHTML — the example text contains literal `<link>`/`<script>` strings; always use the `.value` property.

### ReviewLive merge-target branch selector

The review page (`ReviewLive`, `GET /review/:task_id`) has a merge-target branch selector: the merge action merges into a user-selectable branch instead of always the repo's default. `load_task_data/2` loads `merge_targets` and `default_merge_target` (assigns, defaulted to `[]`/`nil` in `mount/3`) via `EvoGit.Review.list_branches/1` and `EvoGit.Review.default_merge_target/1` when `repo_path` exists (plain `case` on tuple returns, no try/rescue; degrades gracefully to `[]`/`nil`). The `merge` event handler reads `params["target_branch"]` (trimmed; non-member targets fall back to the default when a known list was loaded) and calls `EvoGit.Review.merge_branch/3`, falling back to `merge_branch/2` (legacy default-resolving path) when no target is given. The success flash mentions the effective target branch. UI lives in `ReviewComponents.Actions.action_buttons/1` (see `components/review_components/CONTEXT.md`).

### Notes for Agents — Tool-call display contract (`agents_live/tool_call_display.ex`)

The Agents page chat history viewer renders tool-call messages (both the inline detail panel and the full-message modal) through `EvoDashWeb.AgentsLive.ToolCallDisplay.display/1` (aliased as `ToolCallDisplay` in `agents_live.ex`). The module is a pure rendering contract — see `agents_live/CONTEXT.md` for the full API. Durable facts:

- **Return contract**: `display/1` returns `%{label: String.t(), kind: :structured, rows: [{String.t(), String.t()}]}` (subagent + shell calls) or `%{label: String.t(), kind: :inline, summary: String.t()}` (all other calls). The template branches on `display.kind == :structured`.
- **Structured calls**: `subagent_*`-prefixed names (core `subagent_tool_name/0` family — `subagent_manager`, `subagent_executor`, `subagent_codebase_investigator`, `subagent_task_scheduler`, `subagent_genesis_planner`, `subagent_codebase_lead`, `subagent_context_extractor`; prefix detection covers future variants) show rows `Path` (first of `"path"`/`"file_path"`) + `Objective` (truncated to 200 chars with `…`); `run_bash`/`run_powershell` shell calls show a single `Command` row (truncated to 200 chars, `"command"` from decoded args with raw-args-collapsed fallback). Raw arguments JSON is NEVER dumped for these.
- **One-line calls**: every other tool (read_file, write_file, edit_file, rg, glob, list_dir, make_dir, create_files, read_context, write_context, search_context, skill_*, complete_task, unknown, …) renders a single-line summary: path-like field (`"path"`/`"file_path"`/`"dir_path"`/`"paths"`, list values joined with `" "`) if present, else compact single-line `Jason.encode/1` of the decoded args, else whitespace-collapsed raw arguments, else `""` — truncated to 160 chars with `…`.
- **Height-constrained everywhere**: structured blocks render inside `max-h-12` (inline panel, ~2 lines) / `max-h-60` (modal) `overflow-y-auto` containers; the nested `bg-base-100/40` box layer was removed — structured rows now render flat inside the parent container (no separate box/background layer), only the parent "Tool Calls" box keeps its background. Inline summaries are one line (`whitespace-nowrap overflow-hidden text-ellipsis`). No new CSS in `app.css` — stock Tailwind 4 / DaisyUI utilities only.
- **Label/rows layout contract (both render sites)**: the tool-call label ("Shell call" / "subagent_manager" / etc.) is INLINE beside the rows — a flex row (`flex items-start gap-2`) with the label as a `shrink-0` span and the rows container as `min-w-0 flex-1`, so the label and the first structured row key ("Command" / "Path") sit on the SAME line, top-aligned. This applies in BOTH the inline detail panel and the full-message modal (the modal's label was previously its own block line with `mb-1`; it now mirrors the inline panel's flex row). The key column is `w-20 shrink-0` with 10px uppercase text; NO padding offsets remain (`p-1.5` on the inline rows container, `pt-0.5` on the key span, and `p-2` on the modal rows container were removed along with the box layer). The inline-summary else-branch is a `min-w-0` span (not a div) in both sites.
- **`EvoDashWeb.Helpers.tool_call_display/1` is NO LONGER used by the Agents page** — it remains a public, test-pinned helper in `helpers.ex` (do not remove it). The new module reuses Helpers' defensive extractors (`tool_call_name/1`, `tool_call_arguments/1`, `tool_call_is_shell?/1`) and adds its own non-crashing `Jason` handling via pattern-matched `case` — no `try/rescue` (project policy).
- **New gettext strings** (`Path`, `Objective`, `Command`) will not appear in the POT/PO until release-time extraction — expected, do NOT run `mix gettext.extract`/`merge`/`translate` during development.

### Node-Aware Integration (SSH Remote Development, Phase 2)
All LiveViews register the `EvoDashWeb.LiveHooks.NodeAware` on-mount hook (via the `live_view/0` macro in `evo_dash_web.ex`). As part of the node-aware pattern, each LiveView:
- Calls `assign_node/2` in `handle_params/3` (reads the `?node=<id>` query param, resolving it to a saved+connected target or falling back to local).
- Passes `current_node_id` / `current_node_name` (and `remote_targets` / `connection_statuses`) to the `Layouts.app/1` call.
- Handles `{:node_selected, _}` (delegated to `NodeAware.handle_node_selected/2`) and `{:remote_connection_status, _, _}` messages (delegated to `NodeAware.handle_connection_status/2`).

### UI Patterns (modals, forms, events)
These patterns are used consistently across the LiveViews. Follow them when adding new interactive features.

- **Modal pattern (rendered in the LiveView's own template/component):** A modal is conditionally rendered with `<%= if @some_assign do %>` wrapping a `<div class="modal modal-open bg-black/50" id="...">` containing a `<div class="modal-box ...">`. The open/close state is driven by a `nil`/value socket assign. Opening: a `phx-click="open_modal"` handler sets the assign (optionally carrying an `phx-value-id`). Closing: a `phx-click="close_modal"` handler resets the assign to `nil`. The backdrop `<div class="modal-backdrop" phx-click="close_modal">` also closes. See `AgentsLive`'s `view_full_message`/`close_message_modal` and `view_full_objective`/`close_objective_modal` (in `agents_live.html.heex` + `agents_live.ex`), and `EvoDashWeb.Helpers`'s reusable modal component.
- **Inline form submission (inline editor pattern):** Instead of a full modal, list editors use a `<form phx-submit="save_..." >` with hidden `<input type="hidden" name="id" value=...>` + visible inputs, submitted by a `<button type="submit">`. The edit state is toggled by an `@editing_...` assign. See `SettingsComponents.ModelProfilesEditor.model_profile_edit_form/1` (`phx-submit="save_model_profile"`).
- **Event naming:** Events use `phx-click` (buttons) and `phx-submit` (forms). Values passed via `phx-value-<key>="<value>"` (received in the handler's params map as string keys). IDs that are integers arrive as strings — `String.to_integer/1` is used to convert (e.g. `select_agent` → `%{"id" => id}`).
- **`ModalHelpers` (`live/modal_helpers.ex`):** A `__using__` macro injecting shared modal event handlers (`view_full_result/2`, `close_result_modal/1`, `view_full_options/2`, `close_options_modal/1`) into a host LiveView. **Only `TasksLive` `use EvoDashWeb.ModalHelpers`** — ProjectsLive's `use` + its `view_full_result`/`view_full_options`/`toggle_task_details` handlers were removed in the Tasks A-D minimal-projection rework. (The injected helpers read `socket.assigns.tasks`, which on TasksLive is the full TaskInfo page list.)

- **Task cancellation UX (graceful cancel + force kill)** (TasksLive, commit `c2c4de9b`): the old `handle_event("cancel_task", ...)` (which called `NodeContext.cancel_task` directly) is replaced by TWO two-step server-side confirmation-modal flows following the SystemLive warning-modal pattern (fixed overlay + backdrop with `phx-click` close + centered panel with warning icon/text + dismiss/confirm buttons; NO custom JS — the assigns `@confirm_cancel_task_id` / `@confirm_force_kill_task_id` drive visibility):
  - **Graceful cancel** (card's inline Cancel button, `phx-click="open_cancel_modal"`): `open_cancel_modal` → assign `:confirm_cancel_task_id`; `close_cancel_modal` → nil; `confirm_cancel_task` → `EvoDash.NodeContext.cancel_task(current_node, task_id)` (GRACEFUL — agents save + exit, result preserved; `:pending` → immediate `:cancelled`); `:ok` → collapse expanded card (`MapSet.delete(expanded_task_ids, task_id)`) + `reload_current_page/1`; `{:error, reason}` → flash `gettext("Failed to cancel task: %{reason}", reason: inspect(reason))`. Modal: title `gettext("Cancel Task?")`, confirm `gettext("Cancel Task")` (`btn-warning`), dismiss `gettext("Keep Running")` (distinct label so there are not two "Cancel" buttons).
  - **Force kill** (card's three-dot dropdown, `phx-click="open_force_kill_modal"`): `open_force_kill_modal` → assign `:confirm_force_kill_task_id`; `close_force_kill_modal` → nil; `confirm_force_kill_task` → `EvoDash.NodeContext.force_kill_task(current_node, task_id)` (BRUTAL — kills all agents, result nil'd; escalation from `:cancelling`); same `:ok` collapse+reload / error-flash handling. Modal: title `gettext("Force Kill Task?")`, confirm `gettext("Force Kill")` (`btn-error`).
  - **Modal state lifecycle**: both assigns seeded `nil` in `mount/3`, MUTUALLY EXCLUSIVE (opening one modal clears the other), and cleared on node switch in `handle_params/3` (NOT on same-node pagination/filter push_patches — node change detected by comparing the `:tasks_node_loaded` context tuple before/after `assign_node/2`).
  - **Status filter**: dropdown gained `gettext("Cancelling")` (`value="cancelling"`). The filter is a pure SQL string comparison (`build_filters_from_assigns` → `EvoGit.Store.Queries.build_where`, status column string `"cancelling"`), so `:cancelling` round-trips — no evo_dash-side atom whitelist / `String.to_existing_atom` path exists for the status filter.
- **LiveComponent event routing:** Inside a `use EvoDashWeb, :live_component`, events use `JS.push("event", target: @myself, value: %{...})` (targets the component itself) or plain `phx-click` (targets the parent LiveView). See `NodeSelectorComponent` (`select_node` targets `@myself`, then `send(self(), {:node_selected, id})` to the parent).
- **Task-form layout — server-seeded + client-driven (no per-keystroke round trip):** The task form's layout (compact vs expanded) is seeded server-side at render from the prompt length via `TaskFormComponents.layout_for/1` (threshold > 600 graphemes OR > 16 lines) and updated client-side while typing by the AdaptiveInput JS hook (mirrors the same thresholds). The hook also re-asserts the client-computed layout whenever the server re-seeds `data-layout` from its possibly-stale `@task_prompt` — a MutationObserver on `.input-layout` (attributeFilter: ['data-layout']) re-runs the computation on any server re-render (e.g. toggling mode/model), so the layout can never snap back to compact while a long prompt remains in the box; it converges immediately (the hook only writes the attribute when the computed value differs) with zero network events. `@task_prompt` is NEVER updated per keystroke — the textarea has no `phx-change`; it is set only by `restore_state` and `task_submit`. Prompt draft persistence is purely client-side (the StatePersistence input watcher in app.js). After a successful `task_submit`, `@task_prompt` is reset to `""` by `assign_form_defaults/1` and the handler pushes a `"clear_prompt"` event; the AdaptiveInput hook empties the visible textarea (morphdom skips it under `phx-update="ignore"`), re-asserts autogrow + layout, and clears the draft prompt from the persisted `dashboard_state` sessionStorage blob — the submitted prompt no longer survives reloads.

### Design Notes — Dashboard Top Bar & Command Palette Keyboard

- **Palette keyboard binding must live on the focused element:** LiveView `phx-keydown` bindings do NOT bubble to ancestor elements — the handler only fires when the focused element itself carries the binding. The command palette's `phx-keydown="palette_keydown"` must therefore be on the search input (project_components.ex), NOT on the overlay div. Since `handle_palette_key/3` (`projects_live.ex`) only acts on special keys — `"Escape"` (closes, any mode), `"ArrowDown"`/`"ArrowUp"` (menu index nav), `"Enter"` (menu selection) — and has a catch-all clause returning the socket unchanged for everything else, printable characters typed into the search input are no-ops server-side: typing + `palette_search` filtering (a separate `phx-change` event) coexist without interference. Event path: input `phx-keydown` → `handle_event("palette_keydown", %{"key" => key}, socket)` → `handle_palette_key/3` (clauses at `projects_live.ex:1381-1447`, catch-all `:1447`). Palette close event name: `close_project_palette` (`handle_event` at `projects_live.ex:649`; the backdrop uses `phx-click="close_project_palette"` and click-away uses the same name).

The omnibox trigger (left side) lives in project_components.ex and is unchanged. All strings remain gettext-wrapped — no .pot/.po edits.
- **No-project hint + page dim (commit `8f652ec7`):** when no project is open (`is_nil(@active_project)`) and the hint is not dismissed, the LOCAL top bar (only — gated `!@remote and !@hide_palette`) carries `data-no-project="true"`, renders a clickable `.no-project-hint` pill ("Open or create a project", `phx-click="open_project_palette"` + dismiss X with `phx-click="dismiss_no_project_hint"` + `phx-stop-propagation`), and the page body renders `<div class="no-project-overlay" aria-hidden="true">` (fixed, `pointer-events: none`, z-20 — pure visual dim below the top bar's z-30). ### Design Notes — Remote-Connection Bootstrap Progress & Form (`settings_live.ex`)

- **Bootstrap progress steps must stay in sync with the core** (`EvoGit.RemoteConnection` bootstrap stages, `apps/evo_git/lib/evo_git/remote_connection.ex`). `settings_live.ex` renders a daisyUI `<ul class="steps steps-horizontal text-xs w-full">` in the Settings page target card, driven by a `stage_idx` case on the `bootstrap_stage` atom from `@bootstrap_progress[target.id].stage`. The mapping is a single linear sequence (monotonic in BOTH real bootstrap paths — do not reorder without checking the core):
  `:probing_platform`(0) → `:downloading`(1) → `:downloading_locally`(2) → `:uploading`(3) → `:extracting`(4) → `:setting_permissions`(5) → `:detecting_os`(6) → `:copying_config`(7) → `:generating_cookie`(8) → `:starting_daemon`(9); `_ -> -1` fallback.
  Note: `:downloading_locally` is a distinct core-broadcast stage (auto-download path fallback when the remote download — curl, then wget — fails) with its OWN sequential step (index 2). `:detecting_os` fires ONLY in the local-tarball upload path (between `:setting_permissions` and `:copying_config`); the auto-download path never broadcasts it (OS comes from the probe). Any new core stage added in `remote_connection.ex` must be added to BOTH the `stage_idx` case and the `<li>` list here.
- **Remote-connection form fields** (Settings page): `local_binary_path` is now OPTIONAL — blank means the runtime auto-downloads the `genesis_remote` release tarball on the remote (help text under the input). An optional `platform` text input (`"linux_x64"` / `"darwin_arm64"` / `"windows_x64"`, blank = auto-probe remote OS/arch) was added and is persisted via `build_remote_target_from_params/1` (`platform: params["platform"] || ""`) into the target map; `EvoGit.RemoteConnections.get_target` already carries the `platform` key (nil when unset). New-target defaults in `add_remote_target` include `platform: nil`.
- **New gettext strings** added for this feature (`Probing platform`, `Downloading`, `Downloading locally`, `Extracting`, `Copying config`, `Generating cookie`, `Leave blank to auto-download the release on the remote`, `Platform (optional)`, `Blank = auto-probe the remote OS/arch`) will NOT appear in the POT/PO until the next release-time extraction — expected, do NOT run `mix gettext.extract`/`merge` during development.

## Notes for Agents — Platform-specific Settings/System gating (`EvoDashWeb.PlatformInfo`)

`live/platform_info.ex` (new, commit `c41594d9`) — platform detection for LiveViews with remote-node support. API:

- `os_for_node(current_node)` → `:linux | :macos | :windows | :unknown`. **Testability override FIRST**: `Application.get_env(:evo_dash, :platform_os_override, nil)` — when set to a known OS atom it is returned directly (the injection seam; `:os.type/0` is not injectable). Local node (nil/`node()`) → `EvoGit.Platform.os()`. Remote node → `EvoDash.NodeContext.call_remote(node, :os, :type, [])` mapped (`{:unix,:darwin}`→`:macos`, `{:unix,_}`→`:linux`, `{:win32,_}`→`:windows`, else `:unknown`). **Total — never raises** (justified `try/catch` at the cross-node RPC boundary, precedent `NodeContext.call_remote/4`).
- Pure predicates: `windows?/1`, `macos?/1`, `linux?/1`, `show_sandbox?/1` (→ `os in [:linux, :macos]`; conservative false for `:windows`/`:unknown`), `sandbox_backend_for/1` (`:linux→:systemd_run`, `:macos→:sandbox_exec`, `_→:none`).
- `filter_schemas_by_category(schemas_by_category, os)`: `:windows`/`:unknown` → `Map.delete(:sandbox)`; `:macos` → keep only `sub_category == nil` sandbox schemas (mode + write_paths; drops `:resources`/`:process`/`:linux` — consumed ONLY by the Linux/systemd-run machinery, see `sandbox/macos.ex`); `:linux` → unchanged. Other categories untouched (`Map.get(schema, :sub_category)` — absent key = nil).

**SettingsLive**: `schemas_by_category` filtered per node OS in `mount/3` AND re-filtered in `handle_params/3` (BEFORE `category_str_to_atom` so `?category=sandbox` resolves nil on Windows → falls back; if resolved/persisted active category is `:sandbox` but filtered map lacks it → falls back to `:llm`). **Data-safety**: filtering is BOTH the display mechanism AND the save round-trip protection — `save_category` (`settings_live.ex:~711`) only processes schemas present in the filtered list, and `params_to_category_config` (`config_io.ex:102+`) deep-deletes params absent from the form, so hidden sandbox fields (e.g. `[:sandbox,:resources]`, `[:sandbox,:linux]` on macOS) are never clobbered on save. `sandbox_backend(assigns)` private helper: local → `@scheduler_config[:sandbox_backend]` (accurate, reflects binary availability); remote → `PlatformInfo.sandbox_backend_for(@platform_os)` (`scheduler_config` is loaded from the LOCAL scheduler only — `ConfigIO.load_scheduler_config()` in mount).

| Projection | Store fn | Keys | Decodes result? |
|---|---|---|---|
| Summary | `Store.select_tasks_summary/3` (apps/evo_git store.ex:308-310) | 16 keys: id, status, review_status, **result**, started_at, finished_at, type, project_path, **opts**, branch_name, model_id, agent_count, base_sha, commit_sha, lease_expires_at, updated_at | **YES** — `decode_summary_row` (store.ex:1031-1067) runs `Codec.decode_result` per row (heaviest blob: archive_records + usage) |
| Id-only | `Store.select_task_ids/1` (store.ex:182, handler 618-637) | id, status, updated_at | No |
| Full | `safe_select_paginated_tasks/2` | all TaskInfo columns incl. logs/usage/archive_metadata | Yes (full struct) |

RPC chain for all three: LiveView → `EvoDash.NodeContext` (node_context.ex:353/370/382/395) → `EvoGit.RemoteNode` (remote_node.ex:358/381/314/423) → local direct or `:erpc` → `AgentScheduler.RemoteAPI` (remote_api.ex:323/336/296/359) → `TaskRegistry` (task_registry.ex:116-152) → Store. Summary handlers are Task-offloaded (task_registry.ex:416-457) but decode still runs INLINE on the Store GenServer heap; `list_task_ids` replies inline by design (cheap).

**Every LiveView** gets the sidebar Active Tasks via `EvoDashWeb.LiveHooks.NodeAware` on_mount (applied in `evo_dash_web.ex:53`): `on_mount` → `load_running_and_pending_tasks/1` (node_aware.ex — delegating entry, now backed by the UNIFIED loader `fetch_active_tasks/1` → `partition_active_tasks/1` → `assign_active_tasks/1`, see "Unified sidebar Active Tasks loader" below) → statuses-filtered summary `@active_statuses = [:running,:pending,:finalizing,:completed]` (local TaskRegistry / remote NodeContext RPC; empty lists in pending-remote contexts, `fetch_active_tasks/1`). **The on_mount load is gated behind `connected?/1` (dead-render skip)** — the dead HTTP render keeps the empty-list `assign_new` assigns and fires NO query; the connected mount reload (or the first `handle_params` → `assign_node/2`) fetches the sidebar. `handle_params` → `assign_node/2` (node_aware.ex:130-184) reloads only when the `:tasks_node_loaded` context changed (dedup guard). Broadcasts → 300ms trailing debounce (`debounce_task_reload/1` node_aware.ex:362-370) → each page's `handle_info(:node_aware_reload_tasks)` → `NodeAware.reload_tasks/1` (or page-specific reload + `clear_task_reload_pending`).

**Field needs per consumer:** sidebar + pending-candidate derivation need ONLY id, status, opts (label), started_at, finished_at, project_path, branch_name (via the single public `show_review_button?/1`), review_status. **NO consumer of the summary maps reads `result`** — the sidebar's `show_review_button?/1` is now COLUMN-BASED (single public implementation in `EvoDashWeb.LiveHooks.NodeAware`, node_aware.ex — matches `branch_name` presence, never `result`), and `branch_name` is a denormalized summary column populated at write time (`codec.ex:95` `task.branch_name || extract_branch_name(task.result)`, extract at codec.ex:107-116). TasksLive's full-result modal reads result from the paginated FULL TaskInfo path, not the summary. `list_tasks_changed_since` consumers (DirtyTracker) only read updated_at. **So `result` is being dropped from the summary projection** (parallel evo_git work; that decode was the ~25 MB LiveView retention driver). `opts` must STAY in `@summary_columns` — task_label needs it (the earlier "drop result/opts" proposal in store/CONTEXT.md Known Issues was half-right).

**Unified sidebar Active Tasks loader (DONE — single implementation):**

- **Home**: `EvoDashWeb.LiveHooks.NodeAware` (node_aware.ex) — already the shared node-aware sidebar loader applied to all LiveViews.
- `@active_statuses [:running, :pending, :finalizing, :completed]` (module attribute).
- `fetch_active_tasks/1` (node_aware.ex) — node-aware fetch returning `{running, pending}`. SOCKET-based shape (reads `socket.assigns[:current_node] || node()` and `[:current_node_id]` — this is what preserves the pending-remote guard): local → `TaskRegistry.list_tasks_summary(@active_statuses)`, remote → `EvoDash.NodeContext.list_tasks_summary(current_node, @active_statuses)`. Pending-remote guard: `current_node_id != nil and current_node == node()` → `{[], []}` (local tasks never appear in a pending remote context).
- `partition_active_tasks/1` (node_aware.ex) — PURE (no I/O): `{running, pending}` where running = status in `[:running,:pending,:finalizing]`; pending = completed + `review_status` nil + `show_review_button?/1`, sorted `{:desc, DateTime}` by `finished_at || started_at`.
- `assign_active_tasks/1` (node_aware.ex) — ARITY CHOSEN: `/1` socket-based (fetches via `fetch_active_tasks/1`, assigns `:running_tasks`/`:pending_tasks`). Consistent with `fetch_active_tasks/1`'s socket shape and the ProjectsLive event-handler call sites (they run on connected sockets).
- `load_running_and_pending_tasks/1` (node_aware.ex) — public delegating entry point (`assign_active_tasks/1`), used by on_mount, assign_node, reload_tasks, and projects_live.ex:1525's `:node_aware_reload_tasks` handler.
- `show_review_button?/1` (node_aware.ex) — PUBLIC, column-based: `%{status: :completed, branch_name: branch}` with `is_binary(branch) and branch != ""` → true. NEVER reads `result` from summary maps. The duplicate private copies in `Assigns` (assigns.ex) were DELETED.
- **Dead-render skip**: `on_mount/4` calls the loader ONLY when `Phoenix.LiveView.connected?(socket)`; the dead render keeps the empty-list `assign_new` assigns (no query). `:tasks_node_loaded` is seeded on BOTH paths so the first `handle_params` → `assign_node/2` never double-fetches. `load_running_and_pending_tasks/1` itself is NOT gated (tests call it on non-connected sockets).
- **Removed duplicates**: `Assigns.assign_running_and_pending_tasks/1` + `Assigns.show_review_button?/1` (assigns.ex) DELETED; `EvoDash.NodeContext.list_tasks/1` (node_context.ex, full TaskInfo, zero web-layer callers) DELETED.
- **ProjectsLive call sites**: deleted (redundant — covered by NodeAware on_mount/assign_node dedup + broadcast-driven debounced reloads) mount:520, handle_params fallbacks 635/665/674, activate_project:1846; rerouted through `NodeAware.assign_active_tasks/1` (immediate UX on connected sockets) task_submit, cancel_task, clear_task_history, delete_task.

`pending_tasks` derivation is `branch_name`-column-based (NO `result` matching) so the evo_git `@summary_columns` can drop `result` (store.ex:58 — "drop result" has been a Known-Issues fix direction since round 1, implemented in parallel evo_git work).

## Constraints
- Each LiveView uses either an inline `render/1` or a companion `.html.heex` template — not both. (Three render inline; `AgentsLive` uses a separate template.)
- Auto-refresh intervals must be gated behind `connected?/1` to avoid leaking timers.
- Naming: `<name>_live.ex` for modules, `<name>_live.html.heex` for companion templates.
- **No `try/rescue` around config/core-value loading.** LiveViews must NOT wrap `EvoGit.Config.*`, `EvoGit.AgentScheduler.*`, or `EvoGit.SystemCheck.*` calls in `try/rescue`. If these crash, the LiveView SHOULD crash truthfully — displaying a wrong default value (e.g. `false`, `%{}`, `100_000`) is worse than a visible crash, and the supervision tree handles recovery. Defensive `rescue _ -> default` around these functions is an anti-pattern and must be removed.
- **`try/rescue` for external boundaries requires a justification comment.** The only accepted use is around genuinely untrusted external execution (e.g. `System.cmd` running project-config-defined shell commands in `ProjectsLive`'s `run_command`), where a user-friendly error flash is better UX than a LiveView crash. Every retained `try/rescue` must carry a comment explaining why it is justified.
- **Atom conversion from untrusted input uses whitelist lookups, not `try/rescue`.** For converting user-supplied strings (URL params, form POST data) to atoms, use explicit `Map` lookups (`Map.get/2`, `Map.fetch/2`) or `case` against a known whitelist — never `String.to_existing_atom/1` wrapped in `try/rescue`, and never `String.to_atom/1` (atom-table exhaustion DoS risk).
