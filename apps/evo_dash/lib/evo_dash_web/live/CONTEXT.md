## Intent
Phoenix LiveView modules and templates for the EvoDash interactive UI — real-time task management, agent inspection, runtime configuration, and user help.

### ProcessesLive (managed OS processes)

`ProcessesLive` (`GET /processes`, sidebar **Processes**) lists the executions `EvoGit.ProcessManager` tracks on the viewed node — agent tool calls (in-BEAM built-in ones included) and background jobs — with node-filtered, PUSH-driven liveness off the `"processes"` topic (`{:process_started, execution, node}`, `{:process_updated, id, changes, node}`, `{:process_exited, execution, node}`, `{:process_sample, node, seq, entries}`, `{:process_control, id, entry, node}`) and NO polling; the initial snapshot and any `agent_id`/`task_id`/node change load asynchronously through `ProcessesLive.Load` (`{:processes_loaded, seq, node, result}`, `load_seq` + node stale guards), while the status tab / kind / text filters are pure render-time state (`Format.filter/2`, tab counts over the other dimensions). Filters are URL state — `?status=live|finished|all`, `?kind=tool_call|background_job`, `?q=`, `?agent_id=`, `?task_id=` — with `node` appended by `&` (never `Helpers.with_node_param/2`, which appends `?`); pause/resume are one-click with default reasons, while terminate/kill require a non-empty reason in the confirm modal and run through `ProcessesLive.Actions` (`:processes_control_runner`, 4-arity). Runtime is `:foreground | :background` and backend is `:builtin | :systemd | :bwrap | :sandbox_exec | :none`; a `:builtin` call has no OS process, so Target/Uptime/CPU/Memory render `—` and no pause/resume/terminate/kill controls exist for it, and terminal facts (`exit_code` plus a `reason` of `:exited`, `:timeout`, `:invalid_arguments`, `:owner_died`, `{:killed_by, actor}`, `{:crashed, detail}` or `:no_os_process`) are recorded for foreground shell calls too. A genuinely new row (the list is newest-first, so it joins at the head) enters with the `process-row-enter` class from the `:entering` MapSet, cleared after the call-time seam `:processes_entering_ttl_ms` (default 1500 ms) and never on the initial load. Detail: `processes_live/CONTEXT.md`.

### HomeLive interactive-session UX (conversation list, send path, queue/interrupt, approvals)

A conversation is ONE long-lived interactive agent session, addressed in the URL as `/help?session=<agent_id>` with the node param appended by `&`; navigation is always `push_patch`.
`session` is authoritative in `handle_params/3` — every param change re-resolves it (a same-id change short-circuits) and a MISSING `session` param means the local draft / new-chat state.
`SessionActions.url/2` is the only URL builder and `SessionActions.parse_session/1` parses the param with `Integer.parse/1` plus a positive guard, never an atom conversion.
`session_mode` is `:interactive` (live session) or `:one_shot` (the legacy `:reflect` fallback), and `nil` for a fresh draft; a session agent id is a positive integer and therefore doubles as the `EvoDash.ChatHistory` chat id.
`home_live.ex` presents "Genesis Assistant" with the shared provider/model/reasoning picker in the composer card's control bar (inside the `#chat-form` composer form, capsule left and Send/Stop/Interrupt right, below the textarea), where the capsule's provider/model/reasoning buttons emit `phx-click` selection events; the page header renders no picker.
The page renders a left-rail conversation list (`#chat-session-list`, `SessionList`) above a separately scrolling transcript, plus pinned approval cards and the "Message Genesis Assistant…" composer.
The list UNIONs live core sessions (`list_awaiting_input/1` plus root self-reflective `list_agents/1` rows in `:awaiting_input`/`:running` with no `parent_id`, read defensively) with locally cached chats that have no live session, ordered idle-first, then running, then ended.
Each row is a `push_patch` link to `?session=<agent_id>` carrying a marker (violet "Waiting for you" for `:awaiting_input`, a running dot for `:running`, muted "Ended" otherwise) and a title from the cached transcript's first user message (80 graphemes), else the core row's objective, else "Session <id>".
The list loads ASYNC with no archive and no per-row history, and refreshes on the node-filtered `"tasks"` debounce plus after a session is adopted or closed — never on a timer.
Send with NO session starts one: `NodeContext.start_session/2` with `SessionActions.session_opts/2` (`EvoGit.Agents.SelfReflective`, `repo_less: true`, `objective` = the message text with NO preamble, canonical `model_spec` omitted for Auto, pending attachments), and on `{:ok, agent_id}` the page adopts it — chat id = agent id, `session_mode: :interactive`, `chat_agent_id`, `chat_status: :running`, the first user message kept in the transcript — then `push_patch`es to `?session=<agent_id>`.
Send WITH a session calls `send_session_message(node, agent_id, %{text: text, attachments: atts}, :queue)`: no new task, no new chat, and a `{:session, :finished | :not_found | {:bad_state, _}}` answer marks the conversation `:ended` while keeping the cached transcript and offering New chat.
The one-shot fallback fires only when interactive sessions are unavailable — `function_exported?/3` false, `:llm_not_configured`, or a refusal (`{:interactive_root_only, _}`, `{:invalid_session_opts, _}`, `{:unsupported_session_mode, _}`, also inside a `{:start_session_failed, _}` wrapper) — and starts the legacy `:reflect` task (`mode: "reflect"`, no `:path`, `Transcript.build_preamble/2 <> "New message: " <> text`) with `session_mode: :one_shot` plus a gettext notice; transport errors such as `:timeout`/`:noconnection` are not fallback triggers.
Both branches keep every existing guard: the source gate, canonical `ModelSelect.task_opts/4` validation before any send (an invalid selection flashes "Choose a valid model before sending a message." and sends nothing), the pending-remote refusal and the attachment caps.
The composer stays usable while the session is `:running`; only `:cancelling`, `:ended`, the source gate, a pending remote target or an unready model snapshot disable it.
Queue and interrupt are separate affordances with IDENTICAL behaviour today: Send posts `:queue` and `#chat-interrupt-button` ("Send now (interrupt turn)") posts `:interrupt`, and both are applied at the next turn boundary, so no copy may promise a chunk-level halt.
A send while `:running` appends a transient queued echo (`queued_echoes`: `%{id:, text:, at:}`, capped at 20) after the last transcript entry with "Queued — sent at the next turn boundary"; it is not a fake assistant message and disappears when the agent's `message_count` grows or on stop/close.
Stop is distinct from Interrupt: a graceful `NodeContext.cancel_task/2` on the session's task id, falling back to `SessionActions.close/3` when no task id is known, leaving the page in `:cancelling` until the terminal event.
Enter submits through a server-maintained Shift latch, Shift+Enter keeps the newline, and model selection stays usable during a run but applies to the NEXT session only.
New chat is enabled while `:idle` or `:ended` and clears the draft, per-chat refs, echoes and pending attachments.
Reattach (`?session=<id>`) restores the cached transcript from `ChatHistory.get_state(session_id)`, clears per-chat refs, then spawns ONE supervised attach loader gathering `list_agents` + `list_awaiting_input` + `get_agent_history`.
A non-empty history REPLACES the cached transcript through `Messages.to_entries/1`; `:awaiting_input` maps to `:idle` while `:running`/`:cancelling` carry through, and a session with no summary, not awaiting and an empty cache shows the "This session has ended." empty state with a disabled composer and a New chat affordance, whereas a gone session WITH a cached transcript renders it read-only.
Node switches reset chat state (including `session_id`, echoes and attachments) without cancelling the previous session and reset model selection across target/node scopes; older conversations stay reachable through the conversation list and the local in-memory `ChatHistory` with its ten-chat prune cap.
Approval cards are scoped to the session: the chat id IS the agent id, `chat_agent_id` is the session agent, `chat_task_id` is the summary's `task_id` (set on adoption AND on reattach), and `ApprovalWorkflow.init/1` plus re-recovery runs on every session switch so a previous session's cards never render.
Per-message reasoning lives on each transcript entry (a `reasoning` field derived from the history read through the existing `Messages` funnel) rather than one global last-turn buffer, so scrolling back shows each turn's own thoughts.
Transcript caps: 200 entries (newest kept), 8_000 rendered characters per entry and 40 reasoning entries per assistant message, persisted bounded through `ChatState`.
Attachments stay local-filesystem-only: picker ids `"chat_file"`, `"chat_file_image"` and `"chat_file_audio"`; a text file appends `"\n\n---\n## Attached file: <basename>\n\n" <> content` to the message text, while image/audio files stage `%{"type" => "image"|"audio", "name" => basename, "media_type" => IANA, "data" => raw_bytes}` with base64 applied only at submit.
At most 4 attachments per message of at most 15 MiB each, rendered as removable pending chips and cleared on a successful send; a remote or pending target sets `attach_unavailable: true` and offers the manual-path fallback, whose reads run on the LOCAL node's filesystem.
The page has no full remote connection gate, but pending-target model loads and sends are blocked so a disconnected remote selection cannot start a local session or one-shot reflect task; the source gate still keys visibility to the resolved BEAM node.
Connected mount subscribes to tasks, agents and approvals, then ApprovalWorkflow recovers the core's live pending requests off-process after chat restoration and whenever usable chat/node/root-agent scope changes, with explicit recovery retry and no polling.
Approval ownership requires a nonblank request id, matching task OR normalized agent id, and matching source node; evaluator requests require a source-node stamp, and pending remote contexts never recover or respond against the local service.
Pending approval cards occupy a pinned, internally scrolling area between transcript and composer capped at `min(11rem,25dvh)`.
Evaluator cards preserve exact original code and target runtime, distinguish one-time write consent from unrestricted sudo evaluation, and retain legacy command-level approval presentation.
Decisions route by chat/source node through ApprovalWorkflow, never by evaluator target node; busy cards remain visible with both decisions disabled until a matching result arrives.
Response failures retain cards and show translated retry guidance; success, backend not-found or resolution broadcasts remove them, while scope/token guards and recovery tombstones reject late results and prevent snapshot resurrection.
Approval state remains ephemeral and outside ChatState; remount/reconnect recovery rebuilds it from the actual core `EvoGit.CommandApproval.pending/0` via `NodeContext.call_remote/4`.
Agent lookup fetches the node's agent roster and history refreshes fetch the WHOLE chat-agent history on each message-count event, without page-level debounce, incremental offset, pagination or payload cap; seq guards discard stale responses rather than cancelling outstanding work.
Completed/cancelled events fetch a lite task row and finalize from its result, but a live failed broadcast immediately displays generic "The task failed." and clears refs without fetching its structured error; structured failure detail is available only through fetched-task reconciliation.
A failed terminal task read degrades to nil and is displayed as "The conversation was deleted.", conflating RPC/store failure with a genuinely missing task.
Chat lookup/history share `chat_fetch_seq`, terminal reads use a separate `chat_task_fetch_seq`, and model/source loads have separate counters; `reset_chat/1` resets both chat counters to zero while model/source counters survive.
Local-only persistence stores the bounded transcript and per-entry reasoning at lifecycle updates, not every draft keystroke, so the persisted chat state stays within the 200-entry / 8_000-character / 40-reasoning-entry caps.
Support modules own exact suggestion wording, answer rendering, transcript preamble limits and approval styling; see `home_live/CONTEXT.md` rather than duplicating those details here.

### Node-Aware Integration
All LiveViews register the `EvoDashWeb.LiveHooks.NodeAware` on-mount hook (via the `live_view/0` macro in `evo_dash_web.ex`). As part of the node-aware pattern, each LiveView:
- Calls `assign_node/2` in `handle_params/3` (reads the `?node=<id>` query param, resolving it to a saved+connected target or falling back to local).
- Passes `current_node_id` / `current_node_name` (and `remote_targets` / `connection_statuses`) to the `Layouts.app/1` call.

### UI Patterns (modals, forms, events)
These patterns are used consistently across the LiveViews. Follow them when adding new interactive features.

- **Modal pattern:** A modal is conditionally rendered with `<%= if @some_assign do %>` wrapping a `<div class="modal modal-open bg-black/50" id="...">` containing a `<div class="modal-box ...">`. Open/close state is driven by a `nil`/value socket assign: opening via `phx-click="open_modal"` (optionally carrying `phx-value-id`), closing via `phx-click="close_modal"` resetting to nil; the backdrop `<div class="modal-backdrop" phx-click="close_modal">` also closes. See `AgentsLive`'s `view_full_objective`/`close_objective_modal` and `EvoDashWeb.Helpers`'s reusable modal component.
- **Inline editor pattern:** List editors use a `<form phx-submit="save_..." >` with a hidden `<input type="hidden" name="id" value=...>` + visible inputs, submitted by a `<button type="submit">`; edit state is toggled by an `@editing_...` assign. See `SettingsComponents.ModelProfilesEditor.model_profile_edit_form/1` (`phx-submit="save_model_profile"`).
- **Event naming:** Events use `phx-click` (buttons) and `phx-submit` (forms); values passed via `phx-value-<key>="<value>"` (received in the handler's params map as string keys). Integer ids arrive as strings — `String.to_integer/1` is used to convert.
- **Task cancellation UX** (TasksLive): two two-step server-side confirmation-modal flows follow the SystemLive warning-modal pattern (fixed overlay + backdrop with `phx-click` close + centered panel with warning icon/text + dismiss/confirm buttons; NO custom JS — the assigns `@confirm_cancel_task_id` / `@confirm_force_kill_task_id` drive visibility, mutually exclusive, cleared on node switch). **Graceful cancel** (card's inline Cancel button, `[:pending, :running, :awaiting_input]`): `confirm_cancel_task` → `EvoDash.NodeContext.cancel_task/2` (agents save + exit, result preserved; `:pending` → immediate `:cancelled`); confirm `btn-warning` "Cancel Task", dismiss "Keep Running". **Force kill** (three-dot dropdown, `[:running, :awaiting_input, :cancelling]`): `confirm_force_kill_task` → `EvoDash.NodeContext.force_kill_task/2` (kills all agents → `:failed`, result nil'd); confirm `btn-error`. Success → collapse expanded card + `reload_current_page/1`; `{:error, reason}` → error flash. The status filter includes "Cancelling" (`value="cancelling"`) — a pure SQL string comparison (the store's private SQL WHERE builder `EvoGit.Store.Operations.Tasks.where_filters/2`), so `:cancelling` round-trips with no evo_dash-side atom whitelist. Details: `tasks_live/CONTEXT.md`.
- **Interactive sessions (`:awaiting_input`)**: a NON-terminal status — the task's root agent is a live interactive session that finished a turn and waits for the user (no worker, no LLM/tool slot, no timer). It is admitted wherever a task counts as ACTIVE but never as busy work: the task card renders a violet badge/label with a reply box and a Close-session action, the sidebar lists it in its own Sessions group, TasksLive renders and filters it server-side and wires `session_send_message` to `EvoDash.NodeContext.send_session_message/4` (`:queue`) and `confirm_close_session` to `EvoDash.NodeContext.close_session/3` (`:normal`), and `/server/status` deliberately excludes it from the busy count. A session has no reviewable `genesis/agent_*` branch until it closes (`show_review_button?/1` still keys on `:completed`); closing it finalizes the task into its normal terminal status. Detail: `tasks_live/CONTEXT.md`, `../components/task_card_components/CONTEXT.md`, `../live_hooks/CONTEXT.md`.
- **LiveComponent event routing:** Inside a `use EvoDashWeb, :live_component`, events use `JS.push("event", target: @myself, value: %{...})` (targets the component itself) or plain `phx-click` (targets the parent LiveView). `NodeSelectorComponent`'s `select_node` targets `@myself`, then `send(self(), {:node_selected, id})` to the parent. See `components/CONTEXT.md`.

## Notes for Agents — "tasks" topic broadcast handlers

`EvoDashWeb.LiveHooks.NodeAware.on_mount/4` subscribes EVERY LiveView (`use EvoDashWeb, :live_view` in `evo_dash_web.ex`) to `EvoGit.PubSub` topic `"tasks"` — so every connected LiveView process receives the raw `{:task_updated, task_id, status, node}` / `{:task_deleted, task_id, node}` broadcasts in ITS OWN `handle_info` and MUST have matching clauses (or a catch-all). The failure mode is a FunctionClauseError that kills the LiveView on the next task broadcast. The status is matched with a wildcard (`_status`), so ALL statuses are covered (`:pending`, `:running`, `:cancelling`, `:finalizing`, `:completed`, `:cancelled`, `:failed`, `nil` for review-only mutations) plus `{:task_deleted, _, _}`.

Mirror `settings_live.ex:850-867`. The actual reload runs the page-specific refresh (tasks_live: async page load (`TasksLive.PageLoad.start/3`); projects_live: project-config refresh + browser notifications + sidebar; review_live: broadcast-guarded async review-data reload — only the reviewed task's own broadcasts re-fetch) and ends with `NodeAware.clear_task_reload_pending(socket)`. ## Notes for Agents — async data-load & exit-safety contract (these pages)

**Current rule: no LiveView process ever blocks on a store / registry / cross-node RPC call, and no page renders unbounded task blobs.**
Every read that can cost an `:erpc` round-trip or a `GenServer.call` into the task store runs in a supervised `EvoDash.TaskSupervisor` child (each call inside `EvoDash.SafeCall.run/1`) and lands as a self-message guarded by a monotonic seq/generation counter PLUS a node match (and usually a project-path / task-id match too).
Every per-click MUTATION is either a guarded `EvoDash.SafeCall.run/1` in the handler or a supervised `EvoDash.SafeCall.start/4` task whose result message is ALWAYS sent, so a loading flag can never stick.
The exit-safety is load-bearing, not defensive: a `GenServer.call` timeout, a dead store, or an unreachable remote node EXITS the caller (which `rescue` alone cannot catch) — an unwrapped call in a handler kills the LiveView, and an unwrapped call in a loader wedges the page's loading state forever.
`EvoDash.SafeCall` (`../../evo_dash/safe_call.ex`, detail in `../../evo_dash/CONTEXT.md`) is the ONLY sanctioned boundary: `run/1` → `{:ok, v} | {:error, {:exit, reason} | {:exception, e} | {kind, reason}}`, `run/2` → the value or a caller-supplied fallback, `start/4` → a supervised task that always reports `{tag, result}`.
**Message-shape rule (gotcha): `start/4` sends the tag VERBATIM as the message's first element — a multi-element tuple tag stays ONE nested tuple and is NEVER flattened into the message.** A `{:foo, seq, node}` tag arrives as `{{:foo, seq, node}, result}`; handlers MUST pattern-match that nested shape (a flattened `{:foo, seq, node, result}` clause silently never matches, so the outcome is lost — e.g. an approval-response error would never flash). Terms differ for tasks spawned directly with `Task.Supervisor.start_child` + a manual `send/2`, whose tags ARE flat (`{:chat_history_loaded, node, seq, agent_id, result}`).

- **Review in-progress UI is part of that contract**: `ReviewComponents.RepoCards.repo_cards/1` takes `review_action={@review_action}` + `busy_repos={@busy_repos}` — while ANY action is in flight it disables `#merge-all-repositories` (spinner + "Merging…"), and a busy repo (or any in-flight action) disables that card's `merge` submit + `reject` button with a spinner + "Merging…"/"Rejecting…". `busy_repos` is read TOTALLY (`MapSet.member?` only for a `MapSet`, anything else = not busy), so a nil/legacy shape never raises. `ReviewComponents.Actions.task_actions/1` disables every task-level action (`disabled={@loading}` from `@action_loading`; anchors get `pointer-events-none opacity-50`).

### Projects parent resume and target-identity gotchas
`ProjectsLive.handle_params/3` derives `remote?` only from BEAM-node inequality, while project activation selects the remote path by non-nil target id, so a connected target aliasing the local BEAM follows inconsistent branches.
The remote-activation continuation sets `resume_foreign_repos_guard` from the pending resume id; the parent clears that flag only on target-id switches and otherwise relies on the AsyncLoad remote-extras continuation to consume it.
A same-BEAM connected target can therefore leave the resume guard set if helper remote-extras loading follows the parent's false `remote?` assign.
The URL `resume_from` handling also unconditionally starts `start_foreign_repos_restore/2`, whose lookup is the LOCAL `TaskRegistry.get_task_lite/1` even in a remote-target context; remote activation already restores the task's repos separately.
That local restore's result guard checks only task id and BEAM node, not target id or request generation, and can overwrite the remote activation's restored list or survive a same-BEAM target switch.
### Test seams for the async loaders (resolved AT SPAWN TIME)

- **`:tasks_page_load_runner`** — 4-arity `(node, page, page_size, filters)` page-load function, default `&EvoDashWeb.TasksLive.PageLoad.load/4`, resolved inside `PageLoad.run/6` (so every caller gets the injected runner). Called inside `EvoDash.SafeCall.run/1`, and `{:tasks_page_loaded, seq, node, result}` is ALWAYS sent (with `{:error, ...}` on failure), so injecting `fn _, _, _, _ -> exit(:boom) end` proves the LiveView survives with `:tasks_loading` cleared. Companion counting seam: **`:tasks_page_load_hook`** (1-arity, wraps the spawn; default identity).
- **`:tasks_task_detail_runner`** / **`:tasks_task_archive_runner`** / **`:tasks_task_archive_agent_runner`** — all three resolve AT SPAWN TIME inside `TasksLive.TaskDetail`'s spawned child: the detail runner is 2-arity `(node, task_id)` defaulting to `&EvoDash.NodeContext.get_task_lite/2`, while both archive runners are 3-arity — `(node, task_id, opts)` defaulting to `&EvoDash.NodeContext.list_task_archives/3` and `(node, task_id, agent_id)` defaulting to `&EvoDash.NodeContext.get_agent_archive/3`. Each runs inside `EvoDash.SafeCall.run/1` and ALWAYS sends its result tag, so an injected exiting runner proves the LiveView survives with the card in its retry-able `:error` state.
- **`:review_archive_runner`** / **`:review_archive_agent_runner`** — the same two 3-arity archive shapes for `ReviewLive.ArchiveLoad`, resolved AT CALL TIME inside the spawned child: `fn node, task_id, opts -> %{entries: [map()], total: non_neg_integer()} end` (default `&EvoDash.NodeContext.list_task_archives/3`) and `fn node, task_id, agent_id -> map() | nil end` (default `&EvoDash.NodeContext.get_agent_archive/3`).
- **`:projects_async_load_runner`** — a 0-arity batch runner resolved in `AsyncLoad.maybe_spawn/2`, defaulting to `AsyncLoad.default_batch/6`.
The guarded loader always delivers the scoped `{:async_project_load, node, prev_node_id, path, results}` result, including runner errors, invalid shapes and supervisor startup failure.
A matching failure invalidates picker bundle ownership/readiness, preserves explicit and pending selections without partial persistence, and exposes `retry_model_selection`; it does not run successful-load continuations.
Detailed result envelopes and helper seams belong in `projects_live/CONTEXT.md`.

### Task read shapes — the lightweight reads

- A page load is ONE `list_tasks_page/2` returning 16-key SUMMARY rows (`limit: 25`) plus `total` — no `result`/`usage`/`logs`/`archive_metadata`; the store clamps an out-of-range offset itself, so an out-of-range page needs no second refetch.
- Heavy per-card data is LAZY: `get_task_lite/2` on expand (full struct, `archive_metadata: nil`, no `:archive_records`; cached per task id and invalidated on a node-matching task event) and, ONLY on an explicit archive disclosure, bounded archive pages (`list_task_archives/3` — 100 entries, no results) with one agent's full entry per "Show result" (`get_agent_archive/3`).
- Search matches `id` / `opts` / `project_path` / `branch_name` only — a task's `result` is NOT searchable (it is compressed at rest and is not even loaded until a card is expanded).
- Measured payload (one fixture with a 2,380,000-byte result): the summary page row is 984 B vs 2,381,183 B for the same row through the full-row read — ≈2420× smaller; the page's cost is independent of how large a task's `result` blob is.
- `ReviewLive.LoadData` reads the reviewed task with `get_task_lite/2` (result/opts/SHAs/usage, no archive) inside its supervised loader; the Archive tab is rendered and fetched ONLY when the persisted task opts opted into archiving (`EvoDashWeb.ArchiveHelpers.archive_opt?/1`; otherwise `switch_tab` refuses it and `ArchiveLoad` never fetches, showing an explicit "not collected" state) and pages its archive on demand (`ReviewLive.ArchiveLoad` — first page cached per `{task_id, node}`, "Load more" appends by cumulative FETCHED offset, the retained window is bounded at `ArchiveHelpers.max_retained/0`, per-agent results fetched individually).
- `HomeLive.async_fetch_task/2` (terminal event / mount reconciliation), the ProjectsLive notification scan and the resume-restore paths all use lite rows — the terminal path reads only `:status`/`:result`/`:error`.
- On the core side `list_tasks_page`, `get_task_lite`, `list_task_archives` and `get_agent_archive` are all offloaded by the registry (no long inline SELECT), while `get_unique_paths/1` blocks the core TaskRegistry for the duration of its read.
- No dashboard page issues a FULL-row task read: `list_tasks_paginated` and `get_task/2` are unissued (the export controller reads the lite row plus archive pages).

### Direct (non-spawned) calls — the sanctioned leftovers

- **Handler-local mutations are `EvoDash.SafeCall.run/1`-guarded rather than spawned** (the click needs the outcome to flash/navigate): ProjectsLive `do_task_submit` (`TaskRegistry.start_task/2` local / `NodeContext.start_task/3` remote) + `ProjectsLive.GitHub.start_fix_task`, the ProjectsLive foreign-repo validation (`NodeContext.dir?/2` → fallback `false`, `NodeContext.list_branches/2` → fallback `{:error, :unavailable}` so an unreachable node yields a validation error), `ProjectsLive.ProjectFlow`'s VCT mount (`NodeContext.mount_project(node(), path, Path.basename(path))` + a `NodeContext.projects/1` reload, both `SafeCall`-guarded) and the ProjectsLive `forget_project` event (`NodeContext.forget_project/2` + async reload), SettingsLive remote-target `get_target`/`save_target`/`delete_target`/`disconnect`, `LiveHooks.Appearance.resolve_mode/1` (`get_target` + `connection_status`), HomeLive send/stop, AgentsLive `send_user_message`, TasksLive cancel/force-kill/delete (each guarded, then an async `PageLoad.start/3` reload).
- **LOCAL config-file / ETS reads stay synchronous by design** (they never cross a node and cannot hang): `EvoGit.Config.*` / `ConfigIO` / `EvoGit.AgentScheduler.get_config` in mount and local save paths, `LiveHooks.Appearance`'s local accent resolve, `PlatformInfo` local OS detection (`RemoteNode.call_remote/4` is total), `EvoDash.ChatHistory` + `EvoDash.ActiveTasks` ETS reads, and anything already inside a `Task.Supervisor.start_child` body.
- **Remote-node reads in the same flows are `SafeCall`-guarded or spawned** (SettingsLive remote saves run in ONE `SafeCall.start/4` task; the accent and model-profile fetches spawn). Rule for new code: a click that must report an outcome → `SafeCall.run/1` inline; anything a render depends on → supervised task + seq/node guard. Never a bare `NodeContext`/`TaskRegistry` call on the LiveView process.

## Constraints
- Each LiveView uses either an inline `render/1` or a companion `.html.heex` template — not both. (Three render inline; `AgentsLive` uses a separate template.)
- Auto-refresh intervals must be gated behind `connected?/1` to avoid leaking timers.
- Naming: `<name>_live.ex` for modules, `<name>_live.html.heex` for companion templates.
- **No `try/rescue` around config/core-value loading.** LiveViews must NOT wrap `EvoGit.Config.*`, `EvoGit.AgentScheduler.*`, or `EvoGit.SystemCheck.*` calls in `try/rescue`. If these crash, the LiveView SHOULD crash truthfully — displaying a wrong default value (e.g. `false`, `%{}`, `100_000`) is worse than a visible crash, and the supervision tree handles recovery. Defensive `rescue _ -> default` around these functions is an anti-pattern and must be removed.
- **`try/rescue` for external boundaries requires a justification comment.** The only accepted use is around genuinely untrusted external execution (e.g. `System.cmd` running project-config-defined shell commands in `ProjectsLive`'s `run_command`), where a user-friendly error flash is better UX than a LiveView crash. Every retained `try/rescue` must carry a comment explaining why it is justified.
- **Atom conversion from untrusted input uses whitelist lookups, not `try/rescue`.** For converting user-supplied strings (URL params, form POST data) to atoms, use explicit `Map` lookups (`Map.get/2`, `Map.fetch/2`) or `case` against a known whitelist — never `String.to_existing_atom/1` wrapped in `try/rescue`, and never `String.to_atom/1` (atom-table exhaustion DoS risk).
