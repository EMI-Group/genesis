# LiveView Pages

## Intent
Phoenix LiveView modules and templates for the EvoDash interactive UI — real-time task management, agent inspection, runtime configuration, and user help.

## Routing Table
- `components/` → LiveComponents (`use EvoDashWeb, :live_component`) — `NodeSelectorComponent` for the SSH Remote Development node selector
- `agents_live/` → Support modules extracted from `AgentsLive`: `ToolCallDisplay` (tool-call rendering contract — structured subagent/shell rows + one-line others, constrained height)
- `projects_live/` → Support modules extracted from `ProjectsLive`: `StatePersistence`, `Project`, `Assigns`. Note: `projects_live.ex` is ~1846 lines — a future split of more event handlers into this support directory may be warranted.
- `settings_live/` → Support modules extracted from `SettingsLive`: `ModelProfileHelpers` (pure data-transformation for `[[llm.models]]` CRUD), `ConfigIO` (config loading, runtime updates, atom whitelists)
- `system_live/` → Support modules extracted from `SystemLive`: `Content` (static guides/references), `Status` (health-check status helpers)
- `tasks_live/` → Support modules extracted from `TasksLive`: `DirtyTracker` (pure dirty-check state machine gating the remote-node `:remote_poll` full-page reloads)

### Example-task teaching content (onboarding)

- `EvoDashWeb.ExampleTask` (`example_task.ex`) — shared module holding the demo objective text (`example_objective/0`, verbatim string, NOT gettext-wrapped). Single source of truth for the "example task" teaching sections on the onboarding surfaces: the onboarding completion page (`WelcomeCompleteLive` at `/welcome/complete` — `welcome_live.ex` does not render the example card) and the projects-page no-project empty-state panel (`projects_live.ex`, gated by `is_nil(@active_project)` — disappears once a project is open; contains a collapsible `<details>` panel with Copy + prefill buttons).
- Copy-to-clipboard reuses the global `ClipboardCopy` hook (`data-content` + `phx-hook="ClipboardCopy"`, pushes a `"copied"` event); the pages that render example content each define their own `handle_event("copied", ...)` flash handler (pattern: `welcome_complete_live.ex`, `review_live.ex:312`).
- Dashboard prefill ("Use this example") uses a hidden `<textarea id="example-task-objective" class="hidden" readonly>` RCDATA holder + inline onclick JS: `p.value = h.value; p.dispatchEvent(new Event('input', {bubbles: true}))`. The dispatched input drives the AdaptiveInput hook — autogrow AND the client-side layout switch (the example exceeds the 600-grapheme threshold, so the hook flips `data-layout` to expanded). The hook also re-asserts the layout after any server re-seed of `data-layout` from the possibly-stale `@task_prompt` (MutationObserver on `.input-layout`, e.g. after toggling mode/model). No server event is involved — there is no `phx-change` on the prompt textarea; `@task_prompt` is only updated by `restore_state` / `task_submit`. `phx-update="ignore"` on the prompt textarea keeps the DOM value stable. Never set this via innerHTML — the example text contains literal `<link>`/`<script>` strings; always use the `.value` property.

### ReviewLive merge-target branch selector

The review page (`ReviewLive`, `GET /review/:task_id`) has a merge-target branch selector: the merge action merges into a user-selectable branch instead of always the repo's default. `load_task_data/2` loads `merge_targets` and `default_merge_target` (assigns, defaulted to `[]`/`nil` in `mount/3`) via `EvoGit.Review.list_branches/1` and `EvoGit.Review.default_merge_target/1` when `repo_path` exists (plain `case` on tuple returns, no try/rescue; degrades gracefully to `[]`/`nil`). The `merge` event handler reads `params["target_branch"]` (trimmed; non-member targets fall back to the default when a known list was loaded) and calls `EvoGit.Review.merge_branch/3`, falling back to `merge_branch/2` (default-resolving path) when no target is given. The success flash mentions the effective target branch. UI lives in `ReviewComponents.Actions.action_buttons/1` (see `components/review_components/CONTEXT.md`).

### Review page RPC inventory (load_task_data vs lazy per-event) — remote-SSH payload analysis

`ReviewLive.load_task_data/2` (`review_live.ex:754-936`) runs from `handle_params/3` (page load + node change; dedup guard `tasks_loaded_for == current_node` at `:287-294`) and from the debounced `:node_aware_reload_tasks` handler (`:720-727`). Each run issues 6 synchronous node-aware RPCs in sequence: `get_task/2` → `list_branches/2` + `default_merge_target/2` → `branch_exists?/3` (only when branch_name + repo available) → `load_review_metadata/3` (branch path) or `load_review_metadata_from_shas/4` (post-merge/reject path) → `list_commits/3` or `list_commits_from_shas/4`; plus a fire-and-forget `set_review_metadata/4` write when SHAs were just persisted (`:873-875`). `MergeCheck.maybe_start/1` (`merge_check.ex:42-69`, called from `:293` and `:724`) then spawns ONE async `check_merge/4` in `EvoDash.TaskSupervisor` (dedup-guarded on `merge_status.state == :checking` for the same target). All of these return the verbatim underlying value (only transport failures add `{:error, {kind, reason}}`).

**Diffs are LAZY — never eager.** `load_review_metadata*`/`load_commit_files` return per-file `%EvoGit.Review.FileInfo{}` with `diff: nil` (numstat/shortstat metadata only); per-file `load_file_diff/5,/6` (or `load_commit_file_diff/4` on the commit view) runs only on the `select_file` (`:353-365`), `toggle_file_expansion` (`:368-380`), `load_file_diff` (`:383-385`), and `expand_context` (`:393-418`, larger `:context` opt) phx events. `load_review_data/3` (the eager full-diff variant) is NEVER called anywhere in evo_dash — dead path for the dashboard (only the passthrough definition exists at `node_context.ex:703`). Tab switches are pure assigns, no RPC.

Consumed-vs-transferred (per function):
- `get_task/2` (`:761`): consumed = `opts[:path]`/`opts[:prompt]||opts[:objective]`, `result` (keys commit_sha/branch_name/result/pr_url/pr_title), `review_status`, `status`, `base_sha`, `commit_sha`, `archive_metadata`, `usage`, `agent_count`, `model_id`, `started_at`, `finished_at`. `logs` (and ref/lease_expires_at) are transferred by the full TaskInfo but never read by this page.
- `load_review_metadata*` (8-key map: commit_sha, base_sha, diff_stat, diff, files, changed_files_count, total_additions, total_deletions): consumed = `base_sha` (`:870`), `changed_files_count` (`:96,:119`), `total_additions`/`total_deletions` (`:120-121`), `files` (per-file `path`/`status`/`additions`/`deletions`/`language`/`diff` in the components). **Transferred but never read: top-level `commit_sha`, the raw `diff_stat` string, and `diff` (nil)** — the diff stats bar renders from the counts, not `diff_stat`.
- `list_commits*` (6-field `%CommitInfo{}`): consumed = sha, short_sha, message, author_name, date (`commits_list` + `format_commit_history` `:959-965` + commit_header lookup `:1086`). `author_email` is transferred but unused.
- `check_merge/4`: result → `merge_status` `%{state: :checking|:clean|:conflict|:error, target:, files: []|paths}` (`merge_check.ex:162-192`); components read only `state` (spinner/clean banner/conflict block) and `files` (count + first-4 paths, actions.ex:198-241); `target` is server-side only (staleness + merge call).
- One-shot event RPCs (`merge_branch/3,4` `:466-468`, `reject_branch/3` `:530`, `create_github_pr/5` `:612`, `start_task/3` `:684` + auto-resolve `merge_check.ex:128`, `set_review_status/3` `:473,:532,:559,:597`, `set_review_metadata/4` `:874`): only the ok/error tag and flash-relevant values consumed (merged sha never rendered; `start_task`'s returned `%TaskInfo{}` discarded; set_review_status/metadata are fire-and-forget GenServer casts returning `:ok`).
- Gotcha: `default_merge_target` actually returns `{:ok, name}` — the @specs in RemoteAPI/RemoteNode/NodeContext claiming bare `String.t()` are wrong; ReviewLive matches `{:ok, name}` (`:794-797`). Field-consumption details per component: `components/review_components/CONTEXT.md` → "Field-consumption audit".

### Notes for Agents — Agents page layout & legend tooltip (`agents_live.html.heex` + app.css)

The Agents page uses a fixed-viewport layout (`xl+` only): `.agents-page-layout` (grid, `overflow: hidden`), `.agents-left-col` (column flex, `overflow: hidden`), `.agents-tree-panel` (card, `flex: 1 1 0`), with the tree content scrolling inside `.agents-tree-panel .card-body` (`overflow-y: auto`) and the legend (`.agents-legend`) as a SIBLING of card-body at the panel's bottom. On mobile (<xl) it's normal flow under `#main-scroll` (`overflow: auto`) inside `#app-layout` (`overflow: hidden`).

**Legend tooltips use the `LegendTooltip` JS hook (`assets/js/hooks/legend_tooltip.js`) — NOT DaisyUI `.tooltip`.** DaisyUI's tooltip pseudo-element is absolutely positioned and horizontally CENTERED on the chip, so the long `data-tip` texts (max-width 20rem) on the right-aligned legend chips extend past the panel's right edge and get clipped by the page-level overflow containers (`#app-layout`, `#main-scroll`, `.agents-page-layout`, `.agents-left-col`). CSS-only anchoring can't fix this (the panel is ~480px wide at xl, so any single anchor overflows on some chip). The hook renders the tip as a `position: fixed` element appended to **`document.body`** — mandatory because `.agents-page-layout`'s `animate-fade-in-up` uses `animation-fill-mode: both`, so `transform: translateY(0)` PERSISTS on the layout and would trap even `position: fixed` descendants inside its `overflow: hidden`. The chips carry `data-tip` (gettext) + `phx-hook="LegendTooltip"` + unique ids (LiveView requires `id` for phx-hook); the `tooltip` class was REMOVED so DaisyUI's clipped tooltip doesn't double-render. The "Send Message" button tooltip (`tooltip` class, short text near the card edge) stays inside its container and is NOT affected — do not convert it.

### Notes for Agents — Tool-call display contract (`agents_live/tool_call_display.ex`)

The Agents page chat history viewer renders tool-call messages (both the inline detail panel and the full-message modal) through `EvoDashWeb.AgentsLive.ToolCallDisplay.display/1` (aliased as `ToolCallDisplay` in `agents_live.ex`). The module is a pure rendering contract — see `agents_live/CONTEXT.md` for the full API. Durable facts:

- **Return contract**: `display/1` returns `%{label: String.t(), kind: :structured, rows: [{String.t(), String.t()}]}` (subagent + shell calls) or `%{label: String.t(), kind: :inline, summary: String.t()}` (all other calls). The template branches on `display.kind == :structured`.
- **Structured calls**: `subagent_*`-prefixed names (core `subagent_tool_name/0` family — `subagent_manager`, `subagent_executor`, `subagent_investigator`, `subagent_task_scheduler`, `subagent_genesis_planner`, `subagent_architect`, `subagent_context_extractor`; prefix detection covers future variants) show rows `Path` (first of `"path"`/`"file_path"`) + `Objective` (truncated to 200 chars with `…`); `run_bash`/`run_powershell` shell calls show a single `Command` row (truncated to 200 chars, `"command"` from decoded args with raw-args-collapsed fallback). Raw arguments JSON is NEVER dumped for these.
- **One-line calls**: every other tool (read_file, write_file, edit_file, rg, glob, list_dir, make_dir, create_files, read_context, write_context, search_context, skill_*, complete_task, unknown, …) renders a single-line summary: path-like field (`"path"`/`"file_path"`/`"dir_path"`/`"paths"`, list values joined with `" "`) if present, else compact single-line `Jason.encode/1` of the decoded args, else whitespace-collapsed raw arguments, else `""` — truncated to 160 chars with `…`.
- **Height-constrained everywhere**: structured blocks render inside `max-h-12` (inline panel, ~2 lines) / `max-h-60` (modal) `overflow-y-auto` containers; structured rows render flat inside the parent container (no separate box/background layer) — only the parent "Tool Calls" box keeps its background. Inline summaries are one line (`whitespace-nowrap overflow-hidden text-ellipsis`). No new CSS in `app.css` — stock Tailwind 4 / DaisyUI utilities only.
- **Label/rows layout contract (both render sites)**: the tool-call label ("Shell call" / "subagent_manager" / etc.) is INLINE beside the rows — a flex row (`flex items-start gap-2`) with the label as a `shrink-0` span and the rows container as `min-w-0 flex-1`, so the label and the first structured row key ("Command" / "Path") sit on the SAME line, top-aligned. This applies in BOTH the inline detail panel and the full-message modal (the modal's label mirrors the inline panel's flex row). The key column is `w-20 shrink-0` with 10px uppercase text; the rows containers carry NO padding offsets (`p-1.5`/`pt-0.5`/`p-2` are absent). The inline-summary else-branch is a `min-w-0` span (not a div) in both sites.
- **`EvoDashWeb.Helpers.tool_call_display/1` is not used by the Agents page** — it remains a public, test-pinned helper in `helpers.ex` (do not remove it). `ToolCallDisplay` reuses Helpers' defensive extractors (`tool_call_name/1`, `tool_call_arguments/1`, `tool_call_is_shell?/1`) and adds its own non-crashing `Jason` handling via pattern-matched `case` — no `try/rescue` (project policy).
- **New gettext strings** (`Path`, `Objective`, `Command`) will not appear in the POT/PO until release-time extraction — expected, do NOT run `mix gettext.extract`/`merge`/`translate` during development.

### Node-Aware Integration (SSH Remote Development, Phase 2)
All LiveViews register the `EvoDashWeb.LiveHooks.NodeAware` on-mount hook (via the `live_view/0` macro in `evo_dash_web.ex`). As part of the node-aware pattern, each LiveView:
- Calls `assign_node/2` in `handle_params/3` (reads the `?node=<id>` query param, resolving it to a saved+connected target or falling back to local).
- Passes `current_node_id` / `current_node_name` (and `remote_targets` / `connection_statuses`) to the `Layouts.app/1` call.
- Handles `{:node_selected, _}` (delegated to `NodeAware.handle_node_selected/2`) and `{:remote_connection_status, _, _}` messages (delegated to `NodeAware.handle_connection_status/2`).

### UI Patterns (modals, forms, events)
These patterns are used consistently across the LiveViews. Follow them when adding new interactive features.

- **Modal pattern (rendered in the LiveView's own template/component):** A modal is conditionally rendered with `<%= if @some_assign do %>` wrapping a `<div class="modal modal-open bg-black/50" id="...">` containing a `<div class="modal-box ...">`. The open/close state is driven by a `nil`/value socket assign. Opening: a `phx-click="open_modal"` handler sets the assign (optionally carrying an `phx-value-id`). Closing: a `phx-click="close_modal"` handler resets the assign to `nil`. The backdrop `<div class="modal-backdrop" phx-click="close_modal">` also closes. See `AgentsLive`'s `view_full_message`/`close_message_modal` and `view_full_objective`/`close_objective_modal` (in `agents_live.html.heex` + `agents_live.ex`), and `EvoDashWeb.Helpers`'s reusable modal component.
- **Inline form submission (inline editor pattern):** Instead of a full modal, list editors use a `<form phx-submit="save_..." >` with hidden `<input type="hidden" name="id" value=...>` + visible inputs, submitted by a `<button type="submit">`. The edit state is toggled by an `@editing_...` assign. See `SettingsComponents.ModelProfilesEditor.model_profile_edit_form/1` (`phx-submit="save_model_profile"`).
- **Event naming:** Events use `phx-click` (buttons) and `phx-submit` (forms). Values passed via `phx-value-<key>="<value>"` (received in the handler's params map as string keys). IDs that are integers arrive as strings — `String.to_integer/1` is used to convert (e.g. `select_agent` → `%{"id" => id}`).
- **`ModalHelpers` (`live/modal_helpers.ex`):** A `__using__` macro injecting shared modal event handlers (`view_full_result/2`, `close_result_modal/1`, `view_full_options/2`, `close_options_modal/1`) into a host LiveView. **Only `TasksLive` uses `EvoDashWeb.ModalHelpers`** (ProjectsLive does not). The injected helpers read `socket.assigns.tasks`, which on TasksLive is the full TaskInfo page list.

- **Task cancellation UX (graceful cancel + force kill)** (TasksLive): TWO two-step server-side confirmation-modal flows follow the SystemLive warning-modal pattern (fixed overlay + backdrop with `phx-click` close + centered panel with warning icon/text + dismiss/confirm buttons; NO custom JS — the assigns `@confirm_cancel_task_id` / `@confirm_force_kill_task_id` drive visibility):
  - **Graceful cancel** (card's inline Cancel button, `phx-click="open_cancel_modal"`): `open_cancel_modal` → assign `:confirm_cancel_task_id`; `close_cancel_modal` → nil; `confirm_cancel_task` → `EvoDash.NodeContext.cancel_task(current_node, task_id)` (GRACEFUL — agents save + exit, result preserved; `:pending` → immediate `:cancelled`); `:ok` → collapse expanded card (`MapSet.delete(expanded_task_ids, task_id)`) + `reload_current_page/1`; `{:error, reason}` → flash `gettext("Failed to cancel task: %{reason}", reason: inspect(reason))`. Modal: title `gettext("Cancel Task?")`, confirm `gettext("Cancel Task")` (`btn-warning`), dismiss `gettext("Keep Running")` (distinct label so there are not two "Cancel" buttons).
  - **Force kill** (card's three-dot dropdown, `phx-click="open_force_kill_modal"`): `open_force_kill_modal` → assign `:confirm_force_kill_task_id`; `close_force_kill_modal` → nil; `confirm_force_kill_task` → `EvoDash.NodeContext.force_kill_task(current_node, task_id)` (BRUTAL — kills all agents, result nil'd; escalation from `:cancelling`); same `:ok` collapse+reload / error-flash handling. Modal: title `gettext("Force Kill Task?")`, confirm `gettext("Force Kill")` (`btn-error`).
  - **Modal state lifecycle**: both assigns seeded `nil` in `mount/3`, MUTUALLY EXCLUSIVE (opening one modal clears the other), and cleared on node switch in `handle_params/3` (NOT on same-node pagination/filter push_patches — node change detected by comparing the `:tasks_node_loaded` context tuple before/after `assign_node/2`).
  - **Status filter**: the dropdown includes `gettext("Cancelling")` (`value="cancelling"`). The filter is a pure SQL string comparison (`build_filters_from_assigns` → `EvoGit.Store.Queries.build_where`, status column string `"cancelling"`), so `:cancelling` round-trips — no evo_dash-side atom whitelist / `String.to_existing_atom` path exists for the status filter.
- **LiveComponent event routing:** Inside a `use EvoDashWeb, :live_component`, events use `JS.push("event", target: @myself, value: %{...})` (targets the component itself) or plain `phx-click` (targets the parent LiveView). See `NodeSelectorComponent` (`select_node` targets `@myself`, then `send(self(), {:node_selected, id})` to the parent).
- **Task-form layout — server-seeded + client-driven (no per-keystroke round trip):** The task form's layout (compact vs expanded) is seeded server-side at render from the prompt length via `TaskFormComponents.layout_for/1` (threshold > 600 graphemes OR > 16 lines) and updated client-side while typing by the AdaptiveInput JS hook (mirrors the same thresholds). The hook also re-asserts the client-computed layout whenever the server re-seeds `data-layout` from its possibly-stale `@task_prompt` — a MutationObserver on `.input-layout` (attributeFilter: ['data-layout']) re-runs the computation on any server re-render (e.g. toggling mode/model), so the layout can never snap back to compact while a long prompt remains in the box; it converges immediately (the hook only writes the attribute when the computed value differs) with zero network events. `@task_prompt` is NEVER updated per keystroke — the textarea has no `phx-change`; it is set only by `restore_state` and `task_submit`. Prompt draft persistence is purely client-side (the StatePersistence input watcher in app.js). After a successful `task_submit`, `@task_prompt` is reset to `""` by `assign_form_defaults/1` and the handler pushes a `"clear_prompt"` event; the AdaptiveInput hook empties the visible textarea (morphdom skips it under `phx-update="ignore"`), re-asserts autogrow + layout, and clears the draft prompt from the persisted `dashboard_state` sessionStorage blob — the submitted prompt does not survive reloads.

### Design Notes — Dashboard Top Bar & Command Palette Keyboard

- **Palette keyboard binding must live on the focused element:** LiveView `phx-keydown` bindings do NOT bubble to ancestor elements — the handler only fires when the focused element itself carries the binding. The command palette's `phx-keydown="palette_keydown"` must therefore be on the search input (project_components.ex), NOT on the overlay div. Since `handle_palette_key/3` (`projects_live.ex`) only acts on special keys — `"Escape"` (closes, any mode), `"ArrowDown"`/`"ArrowUp"` (menu index nav), `"Enter"` (menu selection) — and has a catch-all clause returning the socket unchanged for everything else, printable characters typed into the search input are no-ops server-side: typing + `palette_search` filtering (a separate `phx-change` event) coexist without interference. Event path: input `phx-keydown` → `handle_event("palette_keydown", %{"key" => key}, socket)` → `handle_palette_key/3` (clauses at `projects_live.ex:1381-1447`, catch-all `:1447`). Palette close event name: `close_project_palette` (`handle_event` at `projects_live.ex:649`; the backdrop uses `phx-click="close_project_palette"` and click-away uses the same name).
- **Top bar spacing (`ProjectsLive.top_bar/1`):** container `dashboard-topbar` uses `gap-3 px-4 py-3`; the Configure button is `btn btn-md btn-ghost gap-2`; dropdown section headers ("Task Options" / "Project Settings") use `text-xs`. The omnibox trigger (left side) lives in project_components.ex. All strings remain gettext-wrapped — no .pot/.po edits.
- **No-project hint + page dim:** when no project is open (`is_nil(@active_project)`) and the hint is not dismissed, the LOCAL top bar (only — gated `!@remote and !@hide_palette`) carries `data-no-project="true"`, renders a clickable `.no-project-hint` pill ("Open or create a project", `phx-click="open_project_palette"` + dismiss X with `phx-click="dismiss_no_project_hint"` + `phx-stop-propagation`), and the page body renders `<div class="no-project-overlay" aria-hidden="true">` (fixed, `pointer-events: none`, z-20 — pure visual dim below the top bar's z-30). Events/assigns: `dismiss_no_project_hint` sets `@no_project_hint_dismissed` (mount default `false`; reset to `false` in `activate_project/2` so the hint returns for a future no-project session). The hint/overlay naturally disappear once a project activates. CSS lives in `assets/css/app.css` ("No-Project Hint" section: `.no-project-overlay`, `.dashboard-topbar[data-no-project="true"]` taller padding + box-shadow pulse — NO backdrop-filter/filter/transform on the topbar, containing-block trap, see assets/CONTEXT.md Known Issue (ii); `.no-project-hint`). New gettext strings ("Open or create a project", "Dismiss", "Project path") land in the .pot at release time — do NOT run extract.
- **New-project form is a SINGLE full-path input:** `palette_new_project/1` submits `phx-submit="create_project"` with one `name="path"` field (`id="new-project-path-input"`, `phx-change="new_project_path_input"`, debounce 150, `list="new-project-path-suggestions"`). ## Notes for Agents — System self-check design (health banner + check grid, system_live.ex)

The self-check section (System page) is a **merged health banner + responsive 2D grid of check-term cells**. Durable facts:

- **Overall health banner** (full-width, top of the self-check section, ALWAYS rendered — including during `:checking`, where it shows a neutral spinning "Checking system health..." state): derived by `Status.overall_health/1` (`system_live/status.ex`) from `health_checks/1` (private in `system_live.ex`) — a map of the five check assigns plus `sandbox_shown`/`nix_shown` flags mirroring the cell gating in the template. Returns `%{status: :ok | :warning | :error | :loading, reasons: [String.t()]}`:
  - `:loading` when any ALWAYS-critical assign (supervisor/config/tools) is nil — nil checks render neutral, never as errors.
  - `:error` when any critical check fails: process tree (`Status.supervisor_healthy?/1`), configuration (`Status.config_ok?/1`), tools (`Status.tools_status/1 != :ok`), or sandbox (`Status.sandbox_status/1 != :ok` **only when `sandbox_shown`**).

  - `reasons` are gettext-wrapped human-readable strings ("Required settings are missing or invalid", "A required tool (git or ripgrep) is missing", "Sandbox is unavailable", …) rendered as a bullet list under the banner headline ("System running correctly" / "System needs attention" / "System running, but needs attention").
  - `@config_status` carries the remote config status on a remote node (via `safe_system_checks/1`), so the banner needs no extra RPC.
- **Check grid**: `div.grid.grid-cols-1.md:grid-cols-2.gap-3` with one `check_cell/1` per term: Configuration, Required Tools, Sandbox (gated `EvoDashWeb.PlatformInfo.show_sandbox?(@platform_os)`), Nix Environment (gated `@nix_check != nil and enabled and available`), LLM Connection (info status, `~p"/settings?category=llm&node=…"` link). `check_cell/1` is a `rounded-lg border` card whose `<details>/<summary>` disclosure expands to show (a) a gettext "what was checked" description line, (b) the detected values (rendered verbatim: config missing badges + validation-warning count, tool badges with version/error, sandbox backend + Enabled/Disabled + isolation/limits, nix Binary/flake.nix/Flake valid + error), and (c) a `:fix` slot hint rendered only when the status is not `:ok`/`:info` ("Install ripgrep…", "Fix the missing or invalid settings in Settings." + Open Settings link via `with_node_param(~p"/settings", …)`, per-backend sandbox hints, nix fix hint).
- **Supervisor health feeds ONLY the merged banner**: there is no "Genesis Process Tree" row and no `supervisor_status/1` component. The `supervisor_check` assign and `Status.supervisor_healthy?/1` exist and feed the banner's process-tree check.
- **Test markers**: title spans render exactly as `<span class="font-semibold text-sm">{title}</span>` so `>Sandbox</span>` / `>Nix Environment</span>` markers match; "flake.nix"/"Flake valid"/"hero-lock-closed"/"sandbox-exec (macOS)"/"bwrap (Linux)" detail strings are unchanged. - `~p` gotcha: interpolating into the PATH portion of a static route (`~p"/settings#{…}"`) emits a compile-time "no route path" warning (test_path materializes the interpolation as `"1"` → `/settings1`); use `with_node_param/2` (appends `?node=` — only safe for query-less URLs) or interpolate in the query portion only.

## Notes for Agents — System page charts (scheduler status over time)

The System page (`system_live.ex`) renders three status charts below the self-check section: **LLM Slots**, **Tool Slots**, and **Agents**, sampled every 3 seconds over a 60-sample ring buffer (~3 minutes).

- **Charting approach — hand-rolled server-rendered SVG, zero JS deps**: there is NO plotting library in the bundle (no package.json/npm workflow; the vendored asset set is fixed — do not add JS/CSS). All geometry and markup live in the pure support module `EvoDashWeb.SystemLive.Charts` (`system_live/charts.ex`): ring-buffer `push/3` (default capacity 60), `build_sample/2` + `status_counts/1` (agent-list → sample map), `config_totals/1` (config → capacity map), series builders `llm_series/1`/`tool_series/1`/`agents_series/1`, `y_max/1` (max(capacity, observed) × 1.2, floor 4 — never zero, no div-by-zero), `y_for/2` (value → y coordinate within the fixed chart height, clamped at `y_max`), `path_for/2` (polyline + filled area as SVG `d` strings; values left-zero-padded via `pad_to_capacity/2` so fresh charts grow left-to-right), and the `charts_section/1` + `chart_card/1` components (`use Phoenix.Component`; card = legend row with last values + `<svg viewBox="0 0 300 100" preserveAspectRatio="none">` with `vector-effect="non-scaling-stroke"` strokes so lines stay crisp at any width). The LLM/Tool **Capacity** series is marked `static: true` and is rendered as a single dashed horizontal `<line>` reference line at the current config level (via `y_for/2`), not as a per-sample polyline/area — so it does not move when the cached config totals refresh. The LiveView is thin: mount assigns (`chart_samples`/`chart_node`/`chart_config_cache`/`chart_tick_count`/`chart_tick_seq`), a `connected?`-gated `Process.send_after(self(), :system_chart_tick, 3000)` scheduled in mount, and one `<Charts.charts_section samples={@chart_samples} paused={@scheduler_paused} />` call in `render/1`. **The tick itself is ASYNC — see "Async sampling" below.**
- **Data-source semantics + limitation (must stay truthful)**: live "used slot" holder counts are NOT observable from the dashboard — slot holders live only in the `EvoGit.AgentScheduler` GenServer loop state, are not mirrored to `:evogit_sched_meta` ETS, and are not exposed via `RemoteAPI`. "In use" is therefore a clearly-labeled proxy: the count of agents in `:running` status (the agents that acquire/hold slots); `:blocked` (agents waiting for a slot) is the "Waiting" series — a saturation signal. Capacities come from the resolved config: LLM = Σ `concurrency` over `model_profiles`, tool = `max_tool_concurrency` (via `config_totals/1`, `%{}`/unknown → zeros). The same `:running`/`:blocked` counts feed both the LLM and tool charts — only the capacity lines differ. Chart card descriptions state this proxy explicitly ("slot-use proxy — slot holders are not exposed").
- **Sampling & lifecycle**: 3s tick, ring buffer of 60 samples ≈ 3 min (cap memory). `handle_params/3` resets the buffer + config cache when `current_node` differs from `chart_node` (charts never mix nodes). Config totals are cached per node (`chart_config_cache` = `{node, totals}`) and re-fetched every 10th tick ≈ 30s (config changes rarely; avoids an :erpc round-trip per tick for remote nodes). The paused state is reused from the existing `@scheduler_paused` assign — shown as a "Scheduler Paused" badge in the charts section header.
- **Async sampling (no per-tick freeze)**: `handle_info(:system_chart_tick, socket)` reschedules `Process.send_after(self(), :system_chart_tick, 3000)` IMMEDIATELY (steady 3s cadence even while a sampling task is in flight) and calls `spawn_chart_tick/1` instead of the old synchronous `do_chart_tick/1`. `spawn_chart_tick/1` increments TWO counters at spawn time — `chart_tick_count` (per-node tick number, reset to 0 in handle_params on node change; drives the `rem(tick, 10) != 1` config-refresh rule) and `chart_tick_seq` (monotonic across the LiveView's lifetime, NEVER reset — the result-application guard) — then spawns a task via `Task.Supervisor.start_child(EvoDash.TaskSupervisor, ...)` that runs `sample_chart/3` OUTSIDE the LiveView process: `scheduler_alive?/1` liveness gate → `NodeContext.list_agents/1` + the every-10th-tick `chart_totals/3` (cache snapshot passed in at spawn), sending `{:chart_tick_result, seq, node, agents, totals}` to the captured `parent`. The handle_info clause applies the sample (`Charts.build_sample` + `Charts.push`) only when `seq >= chart_tick_seq` (drops older in-flight results) AND `node == current_node` (drops results from a previously-viewed node — the buffer was reset on the node switch); the config cache is stored only when `totals != nil` (the dead-scheduler branch sends `nil` so zero capacities never suppress the next 10th-tick refresh — the old code never cached in the dead branch either). NodeContext degradation is unchanged (`list_agents` → `[]`, `get_remote_config` → `%{}` on failure), so the task is total and can never crash the LiveView. Overlapping task spawns are allowed (the timer never waits); only result application is sequence-guarded. Edge case: a dropped stale result delays that tick's config-totals refresh by up to ~9 ticks (the cache keeps the older totals; the next ≡1-mod-10 tick refetches) — harmless, the sampled data itself is never lost.
- **Remote nodes**: everything goes through `EvoDash.NodeContext` (`list_agents/1` → `[]` on failure, `get_remote_config/1` → `%{}` on failure) — RPC failure / missing scheduler / missing config records a zero/empty sample for that tick, never crashes. **Local-node liveness gate**: `scheduler_alive?/1` (private in system_live.ex) returns `true` for remote nodes (RPC degrades gracefully) and for the local node checks `Process.whereis(EvoGit.AgentScheduler) != nil or :ets.info(:evogit_sched_meta) != :undefined` BEFORE any GenServer-backed config call — a fresh system with no scheduler records zero samples instead of raising `:noproc`. The gate now runs INSIDE the spawned sampling task (`sample_chart/3`), keeping the task total. No try/rescue anywhere (project policy).
- **DOM contract — check cards**: the self-check `check_cell/1` component does NOT wrap its content in a `<details>`/`<summary>` disclosure. The header row is a plain `<div class="flex items-center gap-3 p-4">` (icon box + title + status icon), there is no chevron icon, and the details + `:fix` hint content is always rendered (the `:fix` block is gated on `@status not in [:ok, :info] and @fix != []`). ⚠️ The test `system_live_test.exs:544` ("check terms are expandable details cards…") passes vacuously because `Layouts.app`'s sidebar user-menu dropdown (`layouts.ex:367`) renders `<details>`/`<summary>` — the assertion matches the layout, not the check cells. The check cells themselves emit no `<details>`; do not "fix" the test by re-adding a disclosure.
- **Extension note**: if a future `:evo_git` change exposes real slot counters (e.g. mirrors slot-holder counts into `:evogit_sched_meta` or adds a `RemoteAPI` call), swap the status-derived proxy in `Charts.build_sample/2` for the real values — the sample map keys (`llm_used`/`tool_used`/`llm_waiting`/`tool_waiting`) and the card descriptions are the only places that need updating.

## Notes for Agents — Async node-aware loads on the System page

The System page's node-dependent data loading is fully async (remote-SSH UX workstream #5) — the LiveView never blocks on cross-node RPCs in `handle_params/3` or the 3s chart tick. Local + remote share ONE code path (`EvoDash.NodeContext` already unifies them — never fork).

- **`handle_params/3` spawns the paused-state + platform-OS loads** via `spawn_node_loads/1` (system_live.ex) instead of the old synchronous `NodeContext.paused?/1` + `PlatformInfo.os_for_node/1` calls (each up to 30s of RPC on a remote node). Two tasks are spawned per handle_params run through `Task.Supervisor.start_child(EvoDash.TaskSupervisor, ...)` (the fn runs in the task — `self()` is captured before spawning): `spawn_paused_load/1` calls `EvoDash.NodeContext.paused?(node)` (gated by the `scheduler_alive?/1` liveness check so it can never raise `:noproc` on a fresh boot; remote RPC failure → false) and sends `{:paused_state, node, paused}`; the second task in `spawn_node_loads/1` calls `EvoDashWeb.PlatformInfo.os_for_node(node)` (total, never raises — do NOT edit platform_info.ex) and sends `{:platform_os_result, node, os}`. Both handle_info clauses are stale-guarded: the result is applied ONLY when `socket.assigns.current_node == node` (the node captured at spawn), so a slow remote RPC can never overwrite the current node's values after a node switch.
- **Mount defaults**: `scheduler_paused: false`; `platform_os` uses a LOCAL fast-path only (`current_node in [nil, node()]` → synchronous `os_for_node`, preserving the `:platform_os_override` test seam for tests that set it before `live()`; remote → `:unknown` until the async result arrives). The template gates the Sandbox check cell on `PlatformInfo.show_sandbox?(@platform_os)` — `:unknown` renders it hidden until the async fill-in (identical to the old remote behavior, where RPC failure also produced `:unknown`).
- **`{:scheduler_config_updated}` handler is node-aware** (correctness fix): it calls `spawn_paused_load/1` (async, node-aware) instead of the old `load_paused_state/0`, which read the LOCAL scheduler's `AgentScheduler.get_config()` even when viewing a remote node — the broadcast fires from the node's scheduler, so the local-only read showed the WRONG paused state remotely. Local behavior is unchanged apart from being async.
- **Test strategy**: tests asserting paused/platform-gated content right after `live()` may need `render_async(view)` or the file's `await_view_assign(view, key, value)` helper (the async results arrive via `{:paused_state, node, paused}` / `{:platform_os_result, node, os}` — injectable by `send(view.pid, ...)` with the expected node). The three `:platform_os_override` platform tests pass unchanged (mount fast-path). Chart tests inject `{:chart_tick_result, seq, node(), agents, totals}` with `seq >= assigns(view)[:chart_tick_seq]` (or send `:system_chart_tick` and await `chart_tick_count == 1` / a non-empty `chart_samples`); stale-drop tests send an older `seq` and assert the samples did not change.

## Constraints
- Each LiveView uses either an inline `render/1` or a companion `.html.heex` template — not both. (Three render inline; `AgentsLive` uses a separate template.)
- Auto-refresh intervals must be gated behind `connected?/1` to avoid leaking timers.
- Naming: `<name>_live.ex` for modules, `<name>_live.html.heex` for companion templates.
- **No `try/rescue` around config/core-value loading.** LiveViews must NOT wrap `EvoGit.Config.*`, `EvoGit.AgentScheduler.*`, or `EvoGit.SystemCheck.*` calls in `try/rescue`. If these crash, the LiveView SHOULD crash truthfully — displaying a wrong default value (e.g. `false`, `%{}`, `100_000`) is worse than a visible crash, and the supervision tree handles recovery. Defensive `rescue _ -> default` around these functions is an anti-pattern and must be removed.
- **`try/rescue` for external boundaries requires a justification comment.** The only accepted use is around genuinely untrusted external execution (e.g. `System.cmd` running project-config-defined shell commands in `ProjectsLive`'s `run_command`), where a user-friendly error flash is better UX than a LiveView crash. Every retained `try/rescue` must carry a comment explaining why it is justified.
- **Atom conversion from untrusted input uses whitelist lookups, not `try/rescue`.** For converting user-supplied strings (URL params, form POST data) to atoms, use explicit `Map` lookups (`Map.get/2`, `Map.fetch/2`) or `case` against a known whitelist — never `String.to_existing_atom/1` wrapped in `try/rescue`, and never `String.to_atom/1` (atom-table exhaustion DoS risk).
