# SettingsLive Support Modules

## Intent

Support modules extracted from `EvoDashWeb.SettingsLive` to keep the main LiveView module focused on lifecycle callbacks and event handlers.

## Routing Table

None — leaf directory (six module files: `node_data.ex`, `model_profile_helpers.ex`, `model_profile_events.ex`, `config_io.ex`, `search_events.ex`, `custom_agent_events.ex`).

## API Surface

### `EvoDashWeb.SettingsLive.NodeData` (`node_data.ex`)

Async node-aware data loading for the Settings page (remote-SSH UX optimization #4). `handle_params/3` must never block the LiveView render loop on cross-node RPCs — `EvoDash.NodeContext.get_resolved_config/1` (a FULL merged config map) can take up to 30s on a slow or unreachable remote node, and every navigation used to run it (plus config status, platform info, and the custom-agents list) synchronously in the LiveView process. The async task computes the PLATFORM gating (OS detection + schema filtering + nix gating) too — those calls (`PlatformInfo.os_for_node/1`, `filter_schemas_by_category/2`, `filter_nix_category/2`) are pure and total and short-circuit on the `:platform_os_override`/`:nix_available_override` test seams, so they run inside the task with zero render-loop blocking.

| Function | Purpose |
|----------|---------|
| `start/3` | Spawns the supervised load task (`Task.Supervisor.start_child(EvoDash.TaskSupervisor, ...)`) for the socket's current node, capturing `parent` + `node` + the `?category=` URL param (`params["category"]`, passed from `handle_params/3`) BEFORE spawning. Reads the UNFILTERED schemas snapshot from `socket.assigns.all_schemas_by_category`. Returns `:ok` (fire-and-forget). The task sends `{tag, node, category_param, results}` back; a `try/rescue` (justified: RPC boundary + user config files; expected failure = unreachable node) funnels ANY failure — erpc exit, config-parse raise — into error results so the LiveView renders the error banner instead of silently keeping mount's stale data. |

Results map: `%{platform_os: :linux | :macos | :windows | :unknown, filtered_schemas_by_category: map(), file_config: map(), config_status: map(), remote_config_error: nil | term(), custom_agents: %{agents: [map()], model_selection_script: String.t(), script_status: :ok | {:error, {:compile_error, String.t()}}}}` — `platform_os`/`filtered_schemas_by_category` are computed inside the task via the existing pure `PlatformInfo` functions (`filter_nix_category(filter_schemas_by_category(all_schemas, os), node)`); the error funnel degrades conservatively (`:unknown` OS → `:sandbox` dropped, nix hidden when undeterminable) and ALWAYS includes `custom_agents` so `apply_node_data_results/3` never KeyErrors.

Local and remote share ONE code path (`EvoDash.NodeContext` unifies local-direct with `:erpc`): local → `ConfigIO.load_file_config()` + `EvoGit.Config.config_status()`; remote → `get_resolved_config/1` (failure → `%{}` file_config + `remote_config_error: reason` — never a silently-empty config that would trigger a spurious "No LLM Model Configured" box) + `get_remote_config_status/1` (safe degraded map). `fetch_custom_agents/1` is TOLERANT (any non-matching result shape → empty defaults) — the LiveView's synchronous `load_custom_agents_data/1` keeps its strict match for the save flows.

### `EvoDashWeb.SettingsLive.ModelProfileHelpers` (`model_profile_helpers.ex`)

Pure data-transformation functions for model profile CRUD operations on the `[[llm.models]]` configuration list.

| Function | Purpose |
|----------|---------|
| `add_model_profile/2` | Adds a new model profile with a unique ID and default concurrency (3). **IDs are named after the model**: `generate_profile_id(models, base_name)` produces `<base>`, `<base>-2`, `<base>-3`, ... (suffix from 2, skipping existing ids); base is derived from `model_value` (string `"provider:model_id"` → part after first `:`; plain string → itself; map spec → `:id`; slugified downcase + non-alphanumeric runs → `-`); nil/empty/unusable base falls back to the `profile-N` scheme (draft flow — `add_model_profile(file_config, nil)` — keeps `profile-N` ids). `generate_profile_id/1` kept as a wrapper delegating to `/2` with nil base. |
| `update_model_profile/3` | Updates an existing profile's fields. |
| `replace_model_profiles/2` | Replaces all profiles in a category. |
| `mirror_model_profiles_by_provider/2` | Copies profiles from one provider to another. |
| `parse_model_profile_params/2` | Parses form params, composing ReqLLM-native map model specs (provider, id, base_url, extra). Also parses the OPTIONAL peak/off-peak fields: `peak_concurrency` (string number) and `peak_hours` (Phoenix-nested map keyed by string index, list, or absent). Both keys stay ABSENT from the profile when disabled/empty so TOML omits them (never `nil`/`[]`). UI-side UX validation surfaces one of `"peak_concurrency_invalid"`, `"peak_hours_invalid_time"`, `"peak_hours_start_equals_end"`, `"peak_hours_overlap"` (strict overlap `startA < endB && startB < endA` in minutes-since-midnight; touching boundaries allowed). Error precedence: spec → provider_options → peak. See "Peak/Off-Peak Hour Concurrency (model profiles)" below. |
| `parse_peak_fields/1` | Public — parses `params["peak_concurrency"]` + `params["peak_hours"]` + `params["off_peak_days"]` (+ per-window `days`) into `{:ok, %{}}` (disabled), `{:ok, %{peak_concurrency: non_neg_int, peak_hours: [...], timezone: "IANA", off_peak_days: [...]}}` (absent keys omitted), or `{:error, reason}`. |
| `normalize_days/1`, `normalize_peak_hours_draft/1` | Public pure normalizers for the day-chip fields: `normalize_days/1` → canonical 9-value day list from ANY shape (bare string / list with `""` seed entries / absent / odd → `[]`); `normalize_peak_hours_draft/1` → numerically-sorted atom-keyed window list for draft re-renders (keeps `:days` only when non-empty). |
| `valid_clock_time?/1`, `clock_to_minutes/1` | Public pure helpers: `valid_clock_time?` matches strict 24h `HH:MM` (regex `\A(?:[01]\d|2[0-3]):[0-5]\d\z` — `"9:00"`, `"24:00"`, `"12:60"`, `"12:0"` all false); `clock_to_minutes` → minutes-since-midnight (`nil` for non-conforming strings). |
| `model_profile_collision?/3` | Checks for duplicate provider+model combos. |

All functions are pure — no I/O, no socket, no process calls.

### `EvoDashWeb.SettingsLive.ModelProfileEvents` (`model_profile_events.ex`)

Event handlers for the model-profiles editor (delegated from `settings_live.ex`). `save_model_profile/2` maps `parse_model_profile_params/2`'s four peak error strings to gettext flashes ("Peak concurrency must be a non-negative integer.", "Peak hours must use HH:MM 24-hour format.", "Peak hour window start and end must differ.", "Peak hour windows must not overlap." — zh_CN comments anchor the release-time translator).

**Peak-hours row editor (in-memory only — nothing persisted until the enclosing save form submits)**: `add_peak_hours_row/2` appends `%{start: "", end: ""}` to the editing profile's `peak_hours` (creating the key if absent); `remove_peak_hours_row/2` parses the `phx-value-index` via `Integer.parse` (malformed → -1, out-of-bounds → no-op) and `List.delete_at/2`; removing the LAST row deletes the `peak_hours` key entirely (absent = disabled). Both target the profile whose id == `socket.assigns.editing_profile_id` (via `ModelProfileHelpers.profile_id/1`, atom-or-string key safe), read existing rows atom-or-string defensively, write atom keys, keep `editing_profile_id` set, and no-op (`{:noreply, socket}`) when no editing profile matches. **Wiring note**: `settings_live.ex` must route `"add_peak_hours_row"` / `"remove_peak_hours_row"` phx events to these functions (guarded on `editing_profile_id` non-nil).

### `EvoDashWeb.SettingsLive.CustomAgentEvents` (`custom_agent_events.ex`)
Event handlers for the Settings `:agents` category (custom agents + model-selection script — the per-node `agents.toml` file, NOT config.toml). All functions take a socket (+ params) and return a socket; all persistence goes through `EvoDash.NodeContext` (local node calls `EvoGit.CustomAgents` directly, remote routes `:erpc` via `EvoGit.RemoteNode`), and atom conversions use whitelist lookups (no try/rescue).
| Function | Purpose |
|----------|---------|
| `add_custom_agent/2` | Enters edit mode for a new agent (`"new"` sentinel `editing_agent_id`) |
| `edit_custom_agent/2` | Enters edit mode for an existing agent id |
| `cancel_edit_custom_agent/2` | Clears edit mode |
| `save_custom_agent/2` | Parses form params into an agent def (whitelisted `agent_type`/`delegation_level` atoms; optional int `max_turns`; nil-safe `tools`/`subagents` lists) → `NodeContext.save_custom_agent/2`; maps core error atoms (`:duplicate_id`, `:missing_name`, `:invalid_prompt`, ...) to gettext error flashes; reloads the list on success |
| `delete_custom_agent/2` | `NodeContext.delete_custom_agent/2` + reload |
| `save_model_selection_script/2` | `NodeContext.save_model_selection_script/2`; then reloads and surfaces the compile error (core returns `:ok` even for broken scripts — the error only appears via the reloaded `script_status`) |
| `test_model_selection_script/2` | Invalidates the script compile cache via `EvoDash.NodeContext.reload_custom_agents/1`, then evaluates `ModelSelector.select_model/1` on 3 sample attribute maps (depth-0 `EvoGit.Agents.Architect`, depth-2 `EvoGit.Agents.Executor`, custom agent `"my-agent"` at depth-1) through `EvoDash.NodeContext.call_remote/4` and renders the resulting model ids |

## Constraints

- Both modules follow the project's `try/rescue` anti-pattern policy: whitelist `Map` lookups for atom conversion, no defensive rescuing of core runtime calls.
- `ModelProfileHelpers` delegates shared utilities to `EvoDash.SettingsUtils`.
- `ConfigIO` delegates to `EvoGit.Config`, `EvoGit.AgentScheduler`, and `EvoGit.Config.Schema` — never calls them through `try/rescue`.
- `NodeData` is the ONE justified exception: its `try/rescue` is at the RPC/config-file boundary (expected failure = unreachable node) and funnels every failure mode into the results map (see above).

## Async node-data loading (NodeData) — behavior contract

SettingsLive navigation loads are ASYNC (remote-SSH UX optimization #4); per-save flows remain synchronous.

- **`handle_params/3`** (settings_live.ex:678): `assign_node/2` → `assign(:current_path)` → **seed the shell** (no synchronous platform gating): `schemas_by_category = all_schemas_by_category` (the UNFILTERED snapshot), `platform_os = platform_os || :unknown` (previous value or `:unknown`) → `seed_category/2` (flash-minimizing seed rule: `params["category"]` resolved against the UNFILTERED map via `ConfigIO.category_str_to_atom`, with `"remote_connections"`/`"agents"` special-cased first exactly like the pre-async code; `:nix`/`:sandbox` — potentially gated categories — and unresolvable params seed the current `active_category` when it is a stable non-gated value, else the safe `:llm`; non-gated categories render their section immediately with zero flash) → assign `active_category` when changed → `EvoDashWeb.SettingsLive.NodeData.start(socket, @node_data_tag, params["category"])` → `{:noreply, socket}`. The WHOLE platform gating + category resolution is async: the LiveView render loop never blocks on `os_for_node`/`filter_schemas_by_category`/`filter_nix_category` RPCs on remote nodes (up to 3 `:erpc` calls, 10s ceiling each) — all run asynchronously, `/settings` navigation never blocks.
- **Result message**: `{:settings_node_data_loaded, requested_node, category_param, results}` (`@node_data_tag :settings_node_data_loaded`, settings_live.ex:18). `requested_node` is the node captured at spawn time; `category_param` is the captured `?category=` URL param for re-resolution.
- **Stale-guard** (`handle_info({@node_data_tag, requested_node, category_param, results}, socket)`, settings_live.ex:752): the result is DROPPED when `requested_node != socket.assigns.current_node` — the user switched nodes while the load was in flight and a newer load is already running for the new node. Never flashes the wrong node's config/agents.
- **`apply_node_data_results/3`** (private, settings_live.ex:1653): assigns `platform_os` + `schemas_by_category` (the FILTERED map) first, then `file_config`, `config_status`, `remote_config: false` (legacy assign preserved), `remote_config_error` (nil → nil; reason → gettext `"Could not load configuration from the remote node: %{reason} — the node may be unreachable."` with `inspect(reason)`), then **re-resolves the active category** via `resolve_category/2` (settings_live.ex:1709: `category_param` → whitelist lookup against the FILTERED map via `ConfigIO.category_str_to_atom` with `"remote_connections"`/`"agents"` special-cased → fallback to the current `active_category` → `:llm` when the resolved atom is missing from the filtered map — preserves the `:sandbox`-on-Windows fallback and the hidden-nix fallback exactly as the pre-async code), assigns `active_category` when it changes, and finally the custom-agent assigns (`custom_agents`, `model_selection_script`, `script_status`, plus resets `editing_agent_id: nil`, `script_save_error: nil`, `script_test_results: []` — mirrors the old synchronous `load_custom_agents_data/1` reset semantics).
- **mount/3 stays synchronous** (runs with `current_node` = local default — NodeAware resolves `?node=` only in `handle_params`): seeds `file_config`/`config_status`/`remote_config_error: nil`/`custom_agents` from LOCAL reads, so the first render is never blank and local tests remain deterministic (mount seeds the same values the async task later re-assigns). Mount ALSO snapshots `all_schemas_by_category` (settings_live.ex:618 — the map after the `:remote_connections`/`:agents` `Map.put`s, BEFORE the platform filtering) and applies its own local-only filtering (cheap: `current_node` is nil/local at mount). `handle_params/3` reseeds the unfiltered shell on EVERY navigation (local too) until the async task re-applies the filtered values — the known acceptable race: a save within the sub-second pre-result window sees the unfiltered schemas (per the objective, deliberately NOT engineered around).
- **Per-save flows stay synchronous** (user-initiated, flash feedback): `save_category` (settings_live.ex:1027), `save_search` (:1128), `save_api_key` (:1493), `persist_file_config/3` (:1759), and all `CustomAgentEvents` saves reload their own fresh data (`ConfigIO.load_file_config()` / `get_remote_config` + `remote_config_to_file_config/1` / `NodeContext.save_user_config/2` + `reload_remote_config/1`). `load_custom_agents_data/1` (public, settings_live.ex:1840) remains for these synchronous reloads.
- **`remote_config_to_file_config/1`** (settings_live.ex:1741) is LEGACY: the navigation load path and the persist paths now fetch the FULL resolved config via `get_resolved_config/1`. The flat scheduler-map converter remains ONLY for `save_category`/`save_search` (settings_live.ex) and `SearchEvents.handle_reset_key/2`.

## Test strategy (async loads)

- The async result arrives as a message, so tests asserting async-loaded content must deliver it deterministically: **`send(view.pid, {:settings_node_data_loaded, node, category_param, results})` + `render(view)`** (render drains the mailbox synchronously). This is the same direct-send pattern as the LLM connection test. `render_async/1` does NOT help — it only awaits LiveView `start_async`/`assign_async` pids, not `TaskSupervisor` tasks.
- **Test helpers** (`settings_live_test.exs`, after `assigns/1` at :429): `default_node_results(view, overrides \\ %{})` builds the deterministic results map by applying the pure `PlatformInfo` filters (`filter_nix_category(filter_schemas_by_category(all_schemas, os), node)`) to the `:all_schemas_by_category` snapshot with `node = assigns[:current_node]` and `platform_os = PlatformInfo.os_for_node(node)` — deterministic on ANY host because the `:platform_os_override`/`:nix_available_override` seams short-circuit FIRST (checked inside the task) — plus the config/agents fields from the current assigns; `overrides` win per-key. `deliver_node_data(view, category_param \\ nil, overrides \\ %{})` sends the 4-tuple tagged with the CURRENT node and drains the mailbox.
- The real task may also deliver its message (same node, same deterministic values under the override seams) — a duplicate delivery is an idempotent no-op, so direct-send tests are race-free (the real task's message lands first; ours is processed last).
- **Stale-guard test** (`settings_live_test.exs`, "stale async result for a different node is dropped"): deliver a results map with sentinel values — INCLUDING platform sentinels (`platform_os: :windows`, `filtered_schemas_by_category: %{sentinel: []}`) — tagged with a DIFFERENT node atom (`:"some_other_node@host"`), then `refute` each sentinel in the assigns (refutes hold regardless of whether the real in-flight load has landed).
- **Shell-seeding tests** ("shell seeding (async platform gating)" describe): before the result arrives, `?category=agents` (non-gated) renders `:agents` immediately (seed against the UNFILTERED map); `?category=sandbox`/`?category=nix` (gated) seed `:llm` (assert the shell html — `live/3` returns the seed-shell render; the async task message cannot interleave with mount/handle_params, so seed-state asserts are deterministic); after `deliver_node_data(view, "sandbox")`/`"nix"` the result handler re-resolves the gated category correctly.
- Local-node tests asserting platform-gated content (nix hidden, `:sandbox`-on-Windows fallback) MUST deliver the result deterministically before asserting — `handle_params/3` reseeds the UNFILTERED schemas on every navigation (local too), so gated content is not filtered until `deliver_node_data/3` re-applies the filtered map.
- Remote-node tests in `settings_live_agents_test.exs` need no changes: all use non-gated `?category=agents` (seeds immediately); mount's LOCAL `load_custom_agents_data/1` seeds the same empty defaults, and the async task's tolerant fetch degrades to the same empties.

## Peak/Off-Peak Hour Concurrency (model profiles)

Each `[[llm.models]]` profile supports OPTIONAL fields for time-based concurrency scaling:

- `peak_concurrency` — non-negative integer; the concurrency slot count during peak hours (`0` = hard pause — zero slots during peak).
- `peak_hours` — list of daily time-window maps `[%{start: "09:00", end: "12:00"}, %{start: "14:00", end: "18:00"}]`, 24h `"HH:MM"` local time (two same-day periods is the motivating example).
- `off_peak_days` — profile-level list of day strings restricting when the off-peak/peak fields apply.
- Per-window `days` — each `peak_hours` entry may carry a `days` list; absent = every day.

**Day vocabulary** (lowercase canonical strings, 9 values): `mon`, `tue`, `wed`, `thu`, `fri`, `sat`, `sun`, `weekdays`, `weekends`.

**Serialization rule**: missing/empty → DISABLED. The keys are ABSENT from the profile map so the TOML omits them — never emit `peak_concurrency: nil`, `peak_hours: []`, `off_peak_days: []`, or a `days: []` window. A no-days window stays EXACTLY `%{start: "HH:MM", end: "HH:MM"}`. (The evo_git Config schema — authoritative, owned by the core — serializes absent keys as absent.)

**Form-param ↔ profile-map shapes** (the editor emits; `parse_model_profile_params/2` consumes):

- `params["peak_concurrency"]` — plain string from `<input type="number" name="peak_concurrency" min="0">`; empty/absent → key ABSENT.
- `params["peak_hours"]` — Phoenix-nested map from inputs named `peak_hours[<index>][start]` / `peak_hours[<index>][end]`, i.e. `%{"0" => %{"start" => "09:00", "end" => "12:00"}, "1" => %{"start" => "14:00", "end" => "18:00"}}`. Parse accepts a map keyed by string index (sorted numerically to preserve order), a list, or absent. All-rows-blank → key ABSENT.
- `params["off_peak_days"]` — a LIST of day strings from a multi-checkbox group, a BARE string (Plug collapses a repeated param to a single value when exactly ONE checkbox is submitted — `off_peak_days=weekends` arrives as `"weekends"`, NOT a list), or ABSENT. The UI includes a hidden seed input `value=""`, so the list may contain `""` entries (e.g. `[""]` when nothing checked, or `["", "mon", "sat"]`) → maps to the optional `:off_peak_days` profile key.
- Per-window `peak_hours[<index>][days]` — a LIST of day strings on the row, a BARE string (same single-checked-chip collapse), or absent (unchecked-all → key absent → every day) → maps to the optional `:days` window key.
- Profile map (atom keys): `peak_concurrency: non_neg_integer`, `peak_hours: [%{start: "HH:MM", end: "HH:MM", days: [...]}]`, `off_peak_days: [day strings]` (both `:off_peak_days` and per-window `:days` present ONLY when the normalized list is non-empty).

**Day normalization (dashboard side)**: `ModelProfileHelpers.normalize_days/1` (public, TOTAL, single shared implementation for ALL consumers — save-time parsing, the `model_profile_form_change` draft builder, and the editor template's pre-fill helpers) wraps a bare binary via `List.wrap`, then trim + downcase per entry, drop blanks, drop entries NOT in the 9-value vocabulary (whitelist MapSet membership lookup — no `String.to_atom`/`to_existing_atom`), order-preserving `Enum.uniq`. Absent/empty/odd → `[]` → key omitted. The draft builder normalizes `off_peak_days` (and `normalize_peak_hours_draft/1` each window's `days`) AT THE BOUNDARY so the template's day-chip `Enum.member?` never sees a binary; the template's pre-fill helpers (`profile_off_peak_days/1`, `peak_window_days/1`) additionally route through `normalize_days/1`, making the render total against ANY draft shape. **There are NO dashboard-side validation ERRORS for day values** — the `:evo_git` core (`EvoGit.PeakHours`/config schema) owns authoritative validation; the four dashboard error strings stay exactly `"peak_concurrency_invalid"`, `"peak_hours_invalid_time"`, `"peak_hours_start_equals_end"`, `"peak_hours_overlap"`.

**Row add/remove events** (editor emits → `ModelProfileEvents` handles, delegated from `settings_live.ex`; in-memory `file_config` mutation only, NO persist; active only in edit mode — `editing_profile_id` non-nil):

- `add_peak_hours_row` — no params; appends an empty row `%{start: "", end: ""}` to the editing profile's `peak_hours` (creates the key if absent; a fresh row has no days key = every day).
- `remove_peak_hours_row` — carries `phx-value-index`; removes that row (safe `Integer.parse` index handling); when the list becomes empty the `peak_hours` key is removed from the profile map (absent = disabled).

**Validation semantics** (UI-side UX validation in `parse_model_profile_params/2`; evo_git owns authoritative schema validation):

- `peak_concurrency` blank/absent → absent; else must be a NON-NEGATIVE integer → error `"peak_concurrency_invalid"` (-1 and non-numeric are invalid; `0` is valid = hard pause).
- Each window: `start`/`end` must be valid 24h clock times (format `HH:MM`, hour 0-23, minute 0-59) → error `"peak_hours_invalid_time"`; a row with exactly one of start/end filled → same error. The blank-row logic is driven by start/end ONLY — a row with days but blank start/end is dropped as blank.
- `start != end` → error `"peak_hours_start_equals_end"`.
- Windows pairwise non-overlapping (strict overlap `startA < endB && startB < endA`; touching boundaries e.g. `[09:00,12:00]`+`[12:00,15:00]` allowed) → error `"peak_hours_overlap"`.
- All rows fully blank → `peak_hours` omitted.
- **Known gap — overnight-window overlap misses**: the minutes-since-midnight strict-interval check treats overnight windows (`start > end`) as single segments, so two overnight windows that genuinely overlap (e.g. `[22:00,06:00]` + `[23:00,07:00]`) pass dashboard validation but are rejected by the evo_git schema (`EvoGit.PeakHours.validate_windows`, overnight-vs-same-day + identical-window overlaps) → the save fails LOUDLY via `Schema.validate` ("Failed to save configuration"), never silently corrupts. Single overnight windows are legal end-to-end.

`save_model_profile/2` maps the four error strings to user-facing gettext error flashes.

## Notes for Agents — model-profile id naming (model_value → base name)

- `add_model_profile/2` derives the new profile id from the **model value**, not a counter. All callers — `model_profile_events.ex` (`select_llm_model_shortcut`, `save_custom_model`, `save_quick_setup`), `welcome_live.ex` `do_save_model_profile`, and the Settings "Add Profile" draft button (nil) — pass the model value / nil.
- **Test gotcha (conflict-suffix tests):** when seeding existing profiles to test `-2`/`-3` suffixing through `add_model_profile/2`, the seeded profiles MUST carry a `:model` key — `add_model_profile/2` drops incomplete profiles (no/empty `:model`) BEFORE id generation, so a seeded `%{id: "deepseek-flash", concurrency: 3}` (no model) would be removed and the new profile would get the base id with no suffix. Direct `generate_profile_id/2` unit tests are unaffected (no draft-cleaning).

## Design Notes — Remote-Connection Bootstrap Progress & Form

- **Bootstrap progress steps must stay in sync with the core** (`EvoGit.RemoteConnection` bootstrap stages, `apps/evo_git/lib/evo_git/remote_connection.ex`). `settings_live.ex` renders a daisyUI `<ul class="steps steps-horizontal text-xs w-full">` in the Settings page target card with FIVE steps, driven by `@bootstrap_progress[target.id]` (entry shape + template cases in the frozen-final-state bullet below; the stored `:stage` is the MAPPED 0-4 index — the template must NOT re-map it). The 5-step mapping (monotonic in BOTH real bootstrap paths — do not reorder without checking the core):
  - step 0 "Probing / preparing" ← `:probing_platform`, `:uploading`, `:detecting_os`
  - step 1 "Downloading" ← `:downloading`, `:downloading_locally`
  - step 2 "Extracting" ← `:extracting`
  - step 3 "Configuring" ← `:setting_permissions`, `:copying_config`, `:generating_cookie`, `:patching_binaries`, `:stopping_daemon` (new — fired when a re-bootstrap stops the already-running daemon)
  - step 4 "Starting daemon" ← `:starting_daemon`
  Unknown atoms → -1 (no step highlighted). Any new core stage added in `remote_connection.ex` must be added to the `bootstrap_stage_idx/1` case (the `<li>` list is fixed at 5).
- **Frozen final state — the progress bar persists after bootstrap ends.** Per-target `@bootstrap_progress[target_id]` entries carry `%{stage: nil | 0..4, active: boolean, status: :active | :success | :error, error: String.t() | nil}`. Transitions: the click handlers (`bootstrap_remote_target`, `confirm_bootstrap_restart`) seed `%{stage: nil, active: true, status: :active}`; `handle_info({:remote_connection_status, ...})` (via `update_bootstrap_progress/3`) advances to `:active` on `%{phase: :bootstrapping, bootstrap_stage: stage}` broadcasts (mapping the atom to 0-4), freezes `:error` (keeps last-known stage + the `last_error` message) when a phase `:error`/`last_error` broadcast arrives for a target whose entry is `:active`, and freezes `:success` at stage 4 when the phase leaves `:bootstrapping` (the core sets `phase: :disconnected, bootstrap_stage: nil` right after a successful bootstrap, so `:disconnected` counts as ended). Unrelated broadcasts (other targets, plain connect/disconnect, or a target with a frozen entry) PRESERVE the entry — do not clobber frozen state. The definitive terminal states come from `handle_info({:bootstrap_complete, id, result})`: `{:ok, _}`/`:ok` → `:success`, `{:error, reason}` → `:error` (+ existing error flash), `{:error, {:daemon_running, details}}` → entry removed + permission dialog (next bullet). Template render cases for a target with an entry: `:active` → bar only (no buttons); `:success` → all-green bar (`step-primary` on all five) + Bootstrap/Connect buttons still visible; `:error` → partial bar (steps up to the failure `step-primary`, failing step `step-error`) + error text + Bootstrap (retry) button. Step classes come from `bootstrap_step_class/3` (nil-stage-safe).
- **Permission dialog for an already-running daemon** (`@bootstrap_restart_confirm`, nil = closed, `%{id:, details:}` = open): when `bootstrap_complete` returns `{:error, {:daemon_running, details}}` (daemon already running with the default `on_running: :refuse` — no staging, no kill, no state broadcast), settings_live opens a daisyUI-style confirmation modal (fixed overlay, mirrors the system_live warning-modal pattern) INSTEAD of flashing a generic error. Events: `confirm_bootstrap_restart` (`%{"target_id" => id}` — closes the dialog, seeds the active progress entry, spawns a Task calling `EvoDash.NodeContext.bootstrap(id, on_running: :restart)`); `cancel_bootstrap_restart` (`%{"target_id" => id}` — dismisses). The core stops the running daemon (broadcasting `:stopping_daemon` → step 3 "Configuring") then bootstraps fresh; the existing `{:bootstrap_complete, ...}` path then shows progress + final state as usual.
- **Remote-connection form fields** (Settings page): `local_binary_path` is OPTIONAL — blank means the runtime auto-downloads the `genesis_remote` release tarball on the remote (help text under the input). An optional `platform` text input (`"linux_x64"` / `"darwin_arm64"` / `"windows_x64"`, blank = auto-probe remote OS/arch) is persisted via `build_remote_target_from_params/1` (`platform: params["platform"] || ""`) into the target map; `EvoGit.RemoteConnections.get_target` carries the `platform` key (nil when unset). New-target defaults in `add_remote_target` include `platform: nil`.
- **Progressive disclosure — "Advanced settings" toggle**: the add/edit remote-connection form hides the advanced fields (`dist_port`, `local_binary_path`, `remote_path`, `platform`) behind a ghost "Advanced settings" toggle button (chevron up/down, `toggle_remote_advanced` event flipping the `remote_show_advanced` assign; reset to `false` in `add_remote_target`/`edit_remote_target`/`cancel_edit_remote` so every form opens collapsed). The four fields are wrapped in ONE `col-span-2` container with an inner `grid grid-cols-2 gap-4` (preserving the side-by-side Dist Port/Remote Path layout) that is hidden via the CSS `hidden` class — NOT `:if` — so the inputs stay in the DOM and are still submitted on save: editing an existing target with a non-default `dist_port`/`remote_path` keeps submitting those prefilled values (backend defaults only apply when the inputs are absent), and `build_remote_target_from_params/1` remains unchanged.
- New gettext strings (`Probing / preparing`, `Configuring`, `Remote daemon already running`, `The remote daemon is already running. Re-bootstrapping will stop it and any tasks running on the remote.`, `Stop & re-bootstrap`) will NOT appear in the POT/PO until the next release-time extraction — expected, do NOT run `mix gettext.extract`/`merge` during development.

## SettingsLive platform gating (EvoDashWeb.PlatformInfo)

- `schemas_by_category` is filtered per node OS in `mount/3` AND re-filtered in `handle_params/3` (BEFORE `category_str_to_atom` so `?category=sandbox` resolves nil on Windows → falls back; if resolved/persisted active category is `:sandbox` but the filtered map lacks it → falls back to `:llm`).

- The Settings sandbox banner (`SettingsComponents.category_section/1` in `components/settings_components.ex`) renders an amber `:bwrap` clause ("Filesystem isolation active (bubblewrap); resource limits/syscall filtering unavailable").
