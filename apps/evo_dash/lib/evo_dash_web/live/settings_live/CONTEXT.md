# SettingsLive Support Modules

## Intent

Support modules extracted from `EvoDashWeb.SettingsLive` to keep the main LiveView module focused on lifecycle callbacks and event handlers.

## Routing Table

None — leaf directory (six module files: `node_data.ex`, `model_profile_helpers.ex`, `model_profile_events.ex`, `config_io.ex`, `search_events.ex`, `custom_agent_events.ex`).

## API Surface

### `EvoDashWeb.SettingsLive.NodeData` (`node_data.ex`)

Async node-aware data loading for the Settings page (remote-SSH UX optimization #4). `handle_params/3` must never block the LiveView render loop on cross-node RPCs — `EvoDash.NodeContext.get_resolved_config/1` (a FULL merged config map) can take up to 30s on a slow or unreachable remote node, and every navigation used to run it (plus config status, platform info, and the custom-agents list) synchronously in the LiveView process. The async task computes the PLATFORM gating (OS detection + schema filtering + nix gating) too — those calls (`PlatformInfo.os_for_node/1`, `filter_schemas_by_category/2`, `filter_nix_category/2`) are pure and total and short-circuit on the `:platform_os_override`/`:nix_available_override` test seams, so they run inside the task with zero render-loop blocking.

| Function | Purpose |
|----------|---------|
| `start/3` | Spawns the supervised load task (`Task.Supervisor.start_child(EvoDash.TaskSupervisor, ...)`) for the socket's current node, capturing `parent` + `node` + the `?category=` URL param (`params["category"]`, passed from `handle_params/3`) BEFORE spawning. Reads the UNFILTERED schemas snapshot from `socket.assigns.all_schemas_by_category`. Returns `:ok` (fire-and-forget). The task body runs under `EvoDash.SafeCall.run/1` (the ONE exit-safe boundary, `apps/evo_dash/lib/evo_dash/safe_call.ex`), so EVERY failure mode — an `:erpc`/`GenServer.call` exit (a dead or slow node EXITS its caller and is not rescue-able), a config-parse raise — arrives as `{:error, reason}` and the result message is ALWAYS sent; the LiveView degrades it into the error results map so the page renders the error banner instead of silently keeping mount's stale data. |

Results map: `%{platform_os: :linux | :macos | :windows | :unknown, filtered_schemas_by_category: map(), file_config: map(), config_status: map(), remote_config_error: nil | term(), custom_agents: %{agents: [map()], model_selection_script: String.t(), script_status: :ok | {:error, {:compile_error, String.t()}}}, custom_tools_status: %{ok: [map()], errors: [map()]} | {:error, term()}}` — `platform_os`/`filtered_schemas_by_category` are computed inside the task via the existing pure `PlatformInfo` functions (`filter_nix_category(filter_schemas_by_category(all_schemas, os), node)`); the error funnel degrades conservatively (`:unknown` OS → `:sandbox` dropped, nix hidden when undeterminable) and ALWAYS includes `custom_agents` so `apply_node_data_results/3` never KeyErrors.

Local and remote share ONE code path (`EvoDash.NodeContext` unifies local-direct with `:erpc`): local → `ConfigIO.load_file_config()` + `EvoGit.Config.config_status()`; remote → `get_resolved_config/1` (failure → `%{}` file_config + `remote_config_error: reason` — never a silently-empty config that would trigger a spurious "No LLM Model Configured" box) + `get_remote_config_status/1` (safe degraded map). `fetch_custom_agents/1` is TOLERANT (any non-matching result shape → empty defaults) — the LiveView's synchronous `load_custom_agents_data/1` keeps its strict match for the save flows.

### `EvoDashWeb.SettingsLive.ModelProfileHelpers` (`model_profile_helpers.ex`)

Pure data-transformation functions for model profile CRUD operations on the `[[llm.models]]` configuration list.

| Function | Purpose |
|----------|---------|
| `add_model_profile/2` | Adds a new model profile with a unique ID and default concurrency (3). **IDs are named after the model**: `generate_profile_id(models, base_name)` produces `<base>`, `<base>-2`, `<base>-3`, ... (suffix from 2, skipping existing ids); base is derived from `model_value` (string `"provider:model_id"` → part after first `:`; plain string → itself; map spec → `:id`; slugified downcase + non-alphanumeric runs → `-`); nil/empty/unusable base falls back to the `profile-N` scheme (draft flow — `add_model_profile(file_config, nil)` — keeps `profile-N` ids). `generate_profile_id/1` kept as a wrapper delegating to `/2` with nil base. |
| `update_model_profile/3` | Updates an existing profile's fields. |
| `replace_model_profiles/2` | Replaces all profiles in a category. |
| `mirror_model_profiles_by_provider/2` | Copies profiles from one provider to another. |
| `parse_model_profile_params/2` | Parses form params, composing ReqLLM-native map model specs (provider, id, base_url, extra). Also parses the OPTIONAL peak/off-peak fields: `peak_concurrency` (string number) and `peak_hours` (Phoenix-nested map keyed by string index, list, or absent). Both keys stay ABSENT from the profile when disabled/empty so TOML omits them (never `nil`/`[]`). UI-side UX validation surfaces one of `"peak_concurrency_invalid"`, `"peak_hours_invalid_time"`, `"peak_hours_start_equals_end"`, `"peak_hours_overlap"` (strict overlap `startA < endB && startB < endA` in minutes-since-midnight; touching boundaries allowed). Error precedence: spec → provider_options → peak. Blank/absent numeric gen fields (`temperature`/`max_tokens`/`top_p`/`top_k`/`frequency_penalty`/`presence_penalty`) are DROPPED entirely (never `""`/`0`) — `concurrency` is the ONE defaulted key (`maybe_put_int(..., 3)`), the optional `context_window` is parsed the same way but with NO default (blank/garbage → key ABSENT, core default applies), and `provider_options` is omitted unless non-blank JSON. A freshly created profile therefore carries exactly `%{id, concurrency: 3}` (+ `:model` when set) — no flat `[llm]` value is ever copied in. The editor's numeric generation-parameter inputs carry NO HTML default (`value={nil}` → empty) and the `reasoning_effort` select (a visible field beside Concurrency, outside the generation-parameter group) defaults to its `value=""` "(provider default)" option, so an untouched edit form submits BLANK values that `maybe_put_*` drops: a saved profile carries a generation-parameter key ONLY when the user typed a value for it (i.e. a `[[llm.models]]` profile added via the dashboard with just provider/model never gains `temperature`/`top_p`/`top_k`/`max_tokens`/`reasoning_effort`/`frequency_penalty`/`presence_penalty`). The one injection path for gen params is the legacy flat-config migration (`Schema.LLM.build_legacy_default_profile/1`, evo_git), which runs ONLY when `llm.models` is empty/absent — a config that already has profiles is never touched by it. See "Peak/Off-Peak Hour Concurrency (model profiles)" below. |
| `parse_peak_fields/1` | Public — parses `params["peak_concurrency"]` + `params["peak_hours"]` + `params["off_peak_days"]` (+ per-window `days`) into `{:ok, %{}}` (disabled), `{:ok, %{peak_concurrency: non_neg_int, peak_hours: [...], timezone: "IANA", off_peak_days: [...]}}` (absent keys omitted), or `{:error, reason}`. |
| `normalize_days/1`, `normalize_peak_hours_draft/1` | Public pure normalizers for the day-chip fields: `normalize_days/1` → canonical 9-value day list from ANY shape (bare string / list with `""` seed entries / absent / odd → `[]`); `normalize_peak_hours_draft/1` → numerically-sorted atom-keyed window list for draft re-renders (keeps `:days` only when non-empty). |
| `valid_clock_time?/1`, `clock_to_minutes/1` | Public pure helpers: `valid_clock_time?` matches strict 24h `HH:MM` (regex `\A(?:[01]\d|2[0-3]):[0-5]\d\z` — `"9:00"`, `"24:00"`, `"12:60"`, `"12:0"` all false); `clock_to_minutes` → minutes-since-midnight (`nil` for non-conforming strings). |
| `model_profile_collision?/3` | Checks for duplicate provider+model combos. |

All functions are pure — no I/O, no socket, no process calls.

### `EvoDashWeb.SettingsLive.ModelProfileEvents` (`model_profile_events.ex`)

Event handlers for the model-profiles editor (delegated from `settings_live.ex`). `save_model_profile/2` maps `parse_model_profile_params/2`'s four peak error strings to gettext flashes ("Peak concurrency must be a non-negative integer.", "Peak hours must use HH:MM 24-hour format.", "Peak hour window start and end must differ.", "Peak hour windows must not overlap." — zh_CN comments anchor the release-time translator).

**Peak-hours row editor (in-memory only — nothing persisted until the enclosing save form submits)**: `add_peak_hours_row/2` appends `%{start: "", end: ""}` to the editing profile's `peak_hours` (creating the key if absent); `remove_peak_hours_row/2` parses the `phx-value-index` via `Integer.parse` (malformed → -1, out-of-bounds → no-op) and `List.delete_at/2`; removing the LAST row deletes the `peak_hours` key entirely (absent = disabled). Both target the profile whose id == `socket.assigns.editing_profile_id` (via `ModelProfileHelpers.profile_id/1`, atom-or-string key safe), read existing rows atom-or-string defensively, write atom keys, keep `editing_profile_id` set, and no-op (`{:noreply, socket}`) when no editing profile matches. **Wiring note**: `settings_live.ex` must route `"add_peak_hours_row"` / `"remove_peak_hours_row"` phx events to these functions (guarded on `editing_profile_id` non-nil).

### `EvoDashWeb.SettingsLive.ConfigIO` (`config_io.ex`)

Configuration I/O bridge between the Settings LiveView and the core runtime.

| Function | Purpose |
|----------|---------|
| `load_file_config/0` | Loads the full resolved user config via `EvoGit.Config.resolve/0`. |
| `build_config_from_category_params/2` | Converts category form params into a config map for persistence. |
| `list_of_strings_value/1` | Parses a submitted `:list_of_strings` form value: list → binaries with blanks filtered (so `[]`/blank-only round-trips as `[]`, NEVER treated as delete); any non-list → `:explicitly_empty` (the only delete signal — absent/nil params). Used by the `:list_of_strings` branch in `params_to_category_config/3`. |
| `update_runtime_from_file_config/2` | Accepts and returns a LiveView socket — pushes runtime config changes to `EvoGit.AgentScheduler`. |
| `build_whitelist/1`, `build_provider_whitelist/1` | Builds whitelist maps for safe untrusted-string-to-atom conversion (avoids `String.to_existing_atom/1` + `try/rescue`). |

Only `update_runtime_from_file_config/2` touches the socket — all other functions are pure.

Flat global `[llm]` cards (including boolean and float typed keys such as `tool_result_pruning` / `tool_result_pruning_target_fraction`) need NO dashboard code: the LLM category renders every `EvoGit.Config.Schema.schemas_by_category/0` entry not in `SettingCard.@flat_llm_excluded_key_paths` through `<.setting_card>` (`:float` → `number` input with `step="0.01"`, `:boolean` → hidden `"false"` + toggle `"true"`), and `params_to_category_config/3` parses the very same schemas back.
A boolean card's absence (or any value other than the string `"true"`) parses as `false` and is written — never treated as a delete — because the `:boolean` branch runs before the nil/`""` check; the hidden companion input guarantees an unchecked toggle submits `"false"`.
A float card's unparsable value (`"abc"`, a repeated-name list) is dropped from both accumulators (written nowhere, deleted nowhere), while an emptied float field queues the key for deletion.
Both branches are covered by `apps/evo_dash/test/evo_dash_web/live/settings_live/config_io_test.exs` ("params_to_category_config/3 with :boolean and :float schemas").

## Constraints

- Both modules follow the project's `try/rescue` anti-pattern policy: whitelist `Map` lookups for atom conversion, no defensive rescuing of core runtime calls.
- `ModelProfileHelpers` delegates shared utilities to `EvoDash.SettingsUtils`.
- `ConfigIO` delegates to `EvoGit.Config`, `EvoGit.AgentScheduler`, and `EvoGit.Config.Schema` — never calls them through `try/rescue`.
- `NodeData` adds no `try/rescue` of its own: its store/RPC calls go through `EvoDash.SafeCall.run/1` — the codebase's one exit-safe boundary — which funnels every failure mode into `{:error, reason}` (see above).

## Async node-data loading (NodeData) — behavior contract

SettingsLive never blocks its render loop on a store / registry / cross-node RPC: the dead render performs only exit-safe LOCAL reads, navigations load node data asynchronously via `NodeData`, and every config / credential / reset persistence goes through `persist_config/4` (local synchronous but `EvoDash.SafeCall`-wrapped, remote supervised).

- **`handle_params/3`** (settings_live.ex:822): `assign_node/2` → `assign(:current_path)` → **seed the shell** (no synchronous platform gating): `schemas_by_category = all_schemas_by_category` (the UNFILTERED snapshot), `platform_os = platform_os || :unknown` (previous value or `:unknown`) → `seed_category/2` (flash-minimizing seed rule: `params["category"]` resolved against the UNFILTERED map via `ConfigIO.category_str_to_atom`, with `"remote_connections"`/`"agents"` special-cased first exactly like the pre-async code; `:nix`/`:sandbox` — potentially gated categories — and unresolvable params seed the current `active_category` when it is a stable non-gated value, else the safe `:llm`; non-gated categories render their section immediately with zero flash) → assign `active_category` when changed → `EvoDashWeb.SettingsLive.NodeData.start(socket, @node_data_tag, params["category"])` → `{:noreply, socket}`. The WHOLE platform gating + category resolution is async: the LiveView render loop never blocks on `os_for_node`/`filter_schemas_by_category`/`filter_nix_category` RPCs on remote nodes (up to 3 `:erpc` calls, 10s ceiling each) — all run asynchronously, `/settings` navigation never blocks.
- **Result message**: `{:settings_node_data_loaded, requested_node, category_param, results}` (`@node_data_tag :settings_node_data_loaded`, settings_live.ex:18). `requested_node` is the node captured at spawn time; `category_param` is the captured `?category=` URL param for re-resolution.
- **Stale-guard** (`handle_info({@node_data_tag, requested_node, category_param, results}, socket)`, settings_live.ex:896): the result is DROPPED when `requested_node != socket.assigns.current_node` — the user switched nodes while the load was in flight and a newer load is already running for the new node. Never flashes the wrong node's config/agents.
- **`apply_node_data_results/3`** (private, settings_live.ex:1999): assigns `platform_os` + `schemas_by_category` (the FILTERED map) first, then `file_config`, `config_status`, `remote_config: false` (legacy assign preserved), `remote_config_error` (nil → nil; reason → gettext `"Could not load configuration from the remote node: %{reason} — the node may be unreachable."` with `inspect(reason)`), then **re-resolves the active category** via `resolve_category/2` (settings_live.ex:2059: `category_param` → whitelist lookup against the FILTERED map via `ConfigIO.category_str_to_atom` with `"remote_connections"`/`"agents"` special-cased → fallback to the current `active_category` → `:llm` when the resolved atom is missing from the filtered map — preserves the `:sandbox`-on-Windows fallback and the hidden-nix fallback exactly as the pre-async code), assigns `active_category` when it changes, and finally the custom-agent assigns (`custom_agents`, `model_selection_script`, `script_status`, plus resets `editing_agent_id: nil`, `script_save_error: nil`, `script_test_results: []` — mirrors the old synchronous `load_custom_agents_data/1` reset semantics), then the custom-tools assigns (`custom_tools_status` from `Map.get(results, :custom_tools_status, %{ok: [], errors: []})`, `custom_tools_loading: false`).
- **mount/3 stays synchronous** (runs with `current_node` = local default — NodeAware resolves `?node=` only in `handle_params`): seeds `file_config`/`config_status`/`remote_config_error: nil`/`custom_agents` from LOCAL reads, so the first render is never blank and local tests remain deterministic (mount seeds the same values the async task later re-assigns). Mount ALSO snapshots `all_schemas_by_category` (settings_live.ex:755 — the map after the `:remote_connections`/`:agents` `Map.put`s, BEFORE the platform filtering) and applies its own local-only filtering (cheap: `current_node` is nil/local at mount). `handle_params/3` reseeds the unfiltered shell on EVERY navigation (local too) until the async task re-applies the filtered values — the known acceptable race: a save within the sub-second pre-result window sees the unfiltered schemas (per the objective, deliberately NOT engineered around).
- **ALL config persistence goes through `persist_config/4`** (private, reached through the public `@doc false` `persist_file_config/3`, which first assigns the new in-memory `file_config` and passes `runtime?: true`): `save_category`, `save_search`, `SearchEvents.handle_reset_key`, and every `ModelProfileEvents` save that reloads through `persist_file_config/3`. LOCAL saves stay SYNCHRONOUS (`persist_config_local/4` — a plain file write, so tests assert the success flash in the submit reply) with every call wrapped in `EvoDash.SafeCall.run/1` (a dead scheduler / unreadable config flashes the error instead of crashing the page); the success branch reloads the authoritative config, sets `config_status`/`config_file_exists`, clears `per_category_errors` and the appearance accent draft, flashes, and pushes LLM/scheduler keys to the local scheduler when `runtime?`.
- **REMOTE saves run in ONE supervised task** (`start_remote_config_save/4` → `remote_config_save/2` via `EvoDash.SafeCall.start/4`): the write, the best-effort `reload_remote_config`, the full `get_resolved_config` re-fetch and the `get_remote_config_status` all happen off the LiveView process; `config_saving` drives the shared in-page "Saving configuration…" indicator (`#settings-config-saving`).
- **`handle_info({{:config_saved, node, success_msg}, result}, socket)`** applies it: the node is stale-guarded (a save whose node the user has left is dropped), `config_saving` is cleared on EVERY branch including the stale one, `{:ok, %{file_config: nil}}` means the write succeeded while the re-fetch failed (the just-saved in-memory config is kept and `remote_config_error` surfaces the existing "Remote Configuration Unavailable" banner), and a write/fetch failure flashes `"Failed to save configuration: %{reason}"`.
- **`remote_config_to_file_config/1`** (settings_live.ex) is LEGACY and now has NO callers: every load and persist path fetches the FULL resolved config via `get_resolved_config/1`. It is kept only as documented dead code — do not route new work through it.

## Exit safety & off-process persistence (current rule)

The dead render never blocks on a store / registry / cross-node RPC — it performs only exit-safe LOCAL reads.
Node data loads asynchronously through `NodeData` (`EvoDash.TaskSupervisor` child + self-message + node stale guard).
ALL config / credential / reset persistence goes through `persist_config/4` (public entry point `persist_file_config/3`).
LOCAL persistence stays synchronous, so tests still assert the success flash in the submit reply, but every call is `EvoDash.SafeCall.run/1`-wrapped.
REMOTE persistence runs in ONE supervised task (`EvoDash.SafeCall.start/4`) with `config_saving` set while in flight and a node stale guard on the result.
The result handlers (`{{:config_saved, ...}, result}` and `{{:credentials_saved, ...}, result}`) clear `config_saving` on EVERY branch, including the stale one.
`save_api_key` re-fetches `config_status` + `credentials` after the write: LOCAL synchronously (`save_api_key_local/2`), REMOTE via `save_api_key_remote/4` → `remote_credentials_save/2`; a nil `config_status` degrades to `NodeData.degraded_config_status/0` and a nil `credentials` keeps the current assign.
`test_llm` is exit-safe: the chosen call (`EvoGit.RemoteNode.llm_test/3` remote / `EvoGit.SystemCheck.llm_test/2` local) is `SafeCall.run/1`-wrapped, normalized by `normalize_llm_test_result/1`, and `{:llm_test_result, result}` is ALWAYS sent.
Every in-progress flag (`config_saving`, `custom_tools_loading`, `llm_test_status`) also clears on the error branch, so no flag can stick.
`SearchEvents.handle_reset_key/2` persists through `EvoDashWeb.SettingsLive.persist_file_config/3` and owns only its invalid-key-path guard.
The `:agents`-category mutations (`CustomAgentEvents.save_custom_agent/2` / `delete_custom_agent/2` / `save_model_selection_script/2` / `test_model_selection_script/2`) run every `EvoDash.NodeContext` call through `EvoDash.SafeCall.run/1` and surface failures as their existing error flashes (`error_message/1`, `script_save_error_message/1`, `{:error, reason}` test-result entries), so a dead remote node never crashes the LiveView.
They stay synchronous-but-exit-safe on the LiveView process for BOTH local and remote nodes (`CustomAgentEvents` has no result-message plumbing), while their follow-up custom-agents / custom-tools refreshes stay async through `SettingsLive.load_custom_agents_data/1` and the supervised `SettingsLive.refresh_custom_tools/1`.

## Test strategy (async loads)

- The async result arrives as a message, so tests asserting async-loaded content must deliver it deterministically: **`send(view.pid, {:settings_node_data_loaded, node, category_param, results})` + `render(view)`** (render drains the mailbox synchronously). This is the same direct-send pattern as the LLM connection test. `render_async/1` does NOT help — it only awaits LiveView `start_async`/`assign_async` pids, not `TaskSupervisor` tasks.
- **Test helpers** (`settings_live_test.exs`, after `assigns/1` at :429): `default_node_results(view, overrides \\ %{})` builds the deterministic results map by applying the pure `PlatformInfo` filters (`filter_nix_category(filter_schemas_by_category(all_schemas, os), node)`) to the `:all_schemas_by_category` snapshot with `node = assigns[:current_node]` and `platform_os = PlatformInfo.os_for_node(node)` — deterministic on ANY host because the `:platform_os_override`/`:nix_available_override` seams short-circuit FIRST (checked inside the task) — plus the config/agents fields from the current assigns; `overrides` win per-key. `deliver_node_data(view, category_param \\ nil, overrides \\ %{})` sends the 4-tuple tagged with the CURRENT node and drains the mailbox.
- The real task may also deliver its message (same node, same deterministic values under the override seams) — a duplicate delivery is an idempotent no-op, so direct-send tests are race-free (the real task's message lands first; ours is processed last).
- **Stale-guard test** (`settings_live_test.exs`, "stale async result for a different node is dropped"): deliver a results map with sentinel values — INCLUDING platform sentinels (`platform_os: :windows`, `filtered_schemas_by_category: %{sentinel: []}`) — tagged with a DIFFERENT node atom (`:"some_other_node@host"`), then `refute` each sentinel in the assigns (refutes hold regardless of whether the real in-flight load has landed).
- **Shell-seeding tests** ("shell seeding (async platform gating)" describe): before the result arrives, `?category=agents` (non-gated) renders `:agents` immediately (seed against the UNFILTERED map); `?category=sandbox`/`?category=nix` (gated) seed `:llm` (assert the shell html — `live/3` returns the seed-shell render; the async task message cannot interleave with mount/handle_params, so seed-state asserts are deterministic); after `deliver_node_data(view, "sandbox")`/`"nix"` the result handler re-resolves the gated category correctly.
- Local-node tests asserting platform-gated content (nix hidden, `:sandbox`-on-Windows fallback) MUST deliver the result deterministically before asserting — `handle_params/3` reseeds the UNFILTERED schemas on every navigation (local too), so gated content is not filtered until `deliver_node_data/3` re-applies the filtered map.
- Remote-node tests in `settings_live_agents_test.exs` need no changes: all use non-gated `?category=agents` (seeds immediately); mount's LOCAL `load_custom_agents_data/1` seeds the same empty defaults, and the async task's tolerant fetch degrades to the same empties.

## Context Window (model profiles)

Each `[[llm.models]]` profile supports the OPTIONAL integer field `context_window` — the model's maximum context window in tokens, used by the core's context-compression thresholds (the core applies a default of 200000 when the key is absent).
The Settings editor renders it as `<input type="number" name="context_window" min="1024" placeholder="200000">` in the visible performance group beside Concurrency and Reasoning Effort (the three share one row on wide screens), pre-filled from the draft (draft wins) or the saved profile value.
`parse_model_profile_params/2` parses it via `maybe_put_int(:context_window, params["context_window"])` in the fixed-key profile rebuild pipeline — an integer string becomes an integer `:context_window` profile key.
**Serialization rule**: a blank/absent/non-numeric form value OMITS the `:context_window` key from the profile map, so the TOML omits it (never `nil`) and the core default applies.
That one pipeline line is load-bearing: the profile is rebuilt from a FIXED key set, so dropping it would silently discard the field on every save.

## Peak/Off-Peak Hour Concurrency (model profiles)

Each `[[llm.models]]` profile supports OPTIONAL fields for time-based concurrency scaling:

- `peak_concurrency` — non-negative integer; the concurrency slot count during peak hours (`0` = hard pause — zero slots during peak).
- `peak_hours` — list of daily time-window maps `[%{start: "09:00", end: "12:00"}, %{start: "14:00", end: "18:00"}]`, 24h `"HH:MM"` local time (two same-day periods is the motivating example).
- `off_peak_days` — profile-level list of day strings restricting when the off-peak/peak fields apply.
- Per-window `days` — each `peak_hours` entry may carry a `days` list; absent = every day.

**Day vocabulary** (lowercase canonical strings, 9 values): `mon`, `tue`, `wed`, `thu`, `fri`, `sat`, `sun`, `weekdays`, `weekends`.

**Serialization rule**: missing/empty → DISABLED. The keys are ABSENT from the profile map so the TOML omits them — never emit `peak_concurrency: nil`, `peak_hours: []`, `off_peak_days: []`, or a `days: []` window. A no-days window stays EXACTLY `%{start: "HH:MM", end: "HH:MM"}`. (The evo_git Config schema — authoritative, owned by the core — serializes absent keys as absent.)

**Form-param ↔ profile-map shapes** (the editor emits; `parse_model_profile_params/2` consumes):

- `params["peak_concurrency"]` — plain string from `<input type="number" name="peak_concurrency" min="0">`; empty/absent → key ABSENT.
- `params["peak_hours"]` — Phoenix-nested map from inputs named `peak_hours[<index>][start]` / `peak_hours[<index>][end]`, i.e. `%{"0" => %{"start" => "09:00", "end" => "12:00"}, "1" => %{"start" => "14:00", "end" => "18:00"}}`. Parse accepts a map keyed by string index (sorted numerically to preserve order), a list, or absent. All-rows-blank → key ABSENT.
- `params["off_peak_days"]` — a LIST of day strings from a multi-checkbox group, a BARE string (Plug collapses a repeated param to a single value when exactly ONE checkbox is submitted — `off_peak_days=weekends` arrives as `"weekends"`, NOT a list), or ABSENT. The UI includes a hidden seed input `value=""`, so the list may contain `""` entries (e.g. `[""]` when nothing checked, or `["", "mon", "sat"]`) → maps to the optional `:off_peak_days` profile key.
- Per-window `peak_hours[<index>][days]` — a LIST of day strings on the row, a BARE string (same single-checked-chip collapse), or absent (unchecked-all → key absent → every day) → maps to the optional `:days` window key.
- Profile map (atom keys): `peak_concurrency: non_neg_integer`, `peak_hours: [%{start: "HH:MM", end: "HH:MM", days: [...]}]`, `off_peak_days: [day strings]` (both `:off_peak_days` and per-window `:days` present ONLY when the normalized list is non-empty).

**Day normalization (dashboard side)**: `ModelProfileHelpers.normalize_days/1` (public, TOTAL, single shared implementation for ALL consumers — save-time parsing, the `model_profile_form_change` draft builder, and the editor template's pre-fill helpers) wraps a bare binary via `List.wrap`, then trim + downcase per entry, drop blanks, drop entries NOT in the 9-value vocabulary (whitelist MapSet membership lookup — no `String.to_atom`/`to_existing_atom`), order-preserving `Enum.uniq`. Absent/empty/odd → `[]` → key omitted. The draft builder normalizes `off_peak_days` (and `normalize_peak_hours_draft/1` each window's `days`) AT THE BOUNDARY so the template's day-chip `Enum.member?` never sees a binary; the template's pre-fill helpers (`profile_off_peak_days/1`, `peak_window_days/1`) additionally route through `normalize_days/1`, making the render total against ANY draft shape. **There are NO dashboard-side validation ERRORS for day values** — the `:evo_git` core (`EvoGit.PeakHours`/config schema) owns authoritative validation; the four dashboard error strings stay exactly `"peak_concurrency_invalid"`, `"peak_hours_invalid_time"`, `"peak_hours_start_equals_end"`, `"peak_hours_overlap"`.

**Row add/remove events** (editor emits → `ModelProfileEvents` handles, delegated from `settings_live.ex`; in-memory `file_config` mutation only, NO persist; active only in edit mode — `editing_profile_id` non-nil):

- `add_peak_hours_row` — no params; appends an empty row `%{start: "", end: ""}` to the editing profile's `peak_hours` (creates the key if absent; a fresh row has no days key = every day).
- `remove_peak_hours_row` — carries `phx-value-index`; removes that row (safe `Integer.parse` index handling); when the list becomes empty the `peak_hours` key is removed from the profile map (absent = disabled).
- `toggle_profile_advanced` — no params; flips `:profile_advanced_open` to the OPPOSITE of the currently effective disclosure state (the same `ModelProfilesEditor.advanced_open?/3` helper the template uses, so a `nil` override resolves via the auto rule first), no-ops while `editing_profile_id` is nil, and is reset to `nil` by every edit-session identity change.

**Validation semantics** (UI-side UX validation in `parse_model_profile_params/2`; evo_git owns authoritative schema validation):

- `peak_concurrency` blank/absent → absent; else must be a NON-NEGATIVE integer → error `"peak_concurrency_invalid"` (-1 and non-numeric are invalid; `0` is valid = hard pause).
- Each window: `start`/`end` must be valid 24h clock times (format `HH:MM`, hour 0-23, minute 0-59) → error `"peak_hours_invalid_time"`; a row with exactly one of start/end filled → same error. The blank-row logic is driven by start/end ONLY — a row with days but blank start/end is dropped as blank.
- `start != end` → error `"peak_hours_start_equals_end"`.
- Windows pairwise non-overlapping (strict overlap `startA < endB && startB < endA`; touching boundaries e.g. `[09:00,12:00]`+`[12:00,15:00]` allowed) → error `"peak_hours_overlap"`.
- All rows fully blank → `peak_hours` omitted.
- **Known gap — overnight-window overlap misses**: the minutes-since-midnight strict-interval check treats overnight windows (`start > end`) as single segments, so two overnight windows that genuinely overlap (e.g. `[22:00,06:00]` + `[23:00,07:00]`) pass dashboard validation but are rejected by the evo_git schema (`EvoGit.PeakHours.validate_windows`, overnight-vs-same-day + identical-window overlaps) → the save fails LOUDLY via `Schema.validate` ("Failed to save configuration"), never silently corrupts. Single overnight windows are legal end-to-end.

`save_model_profile/2` maps the four error strings to user-facing gettext error flashes.

- **Bootstrap progress steps must stay in sync with the core** (`EvoGit.RemoteConnection` bootstrap stages, `apps/evo_git/lib/evo_git/remote_connection.ex`). `settings_live.ex` renders a daisyUI `<ul class="steps steps-horizontal text-xs w-full">` in the Settings page target card with FIVE steps, driven by `@bootstrap_progress[target.id]` (entry shape + template cases in the frozen-final-state bullet below; the stored `:stage` is the MAPPED 0-4 index — the template must NOT re-map it).   - step 4 "Starting daemon" ← `:starting_daemon`

- **User-facing "Install" vs internal `bootstrap_*`**: the remote-connection action buttons and lifecycle flashes are labeled "Install" (user-facing) while the events (`bootstrap_remote_target`, `confirm_bootstrap_restart`), the connection phase `:bootstrapping`, and the progress helpers keep their `bootstrap_*` internal names — do NOT rename them. The two-step explainer banner at the top of the Remote Connections category introduces the workflow: first **Install** the remote daemon on the server, then **Connect** to it; once connected, tasks run on the server and keep running even when the local app is closed.
- **Connection form Name auto-fill**: in the add-connection form, the Name field auto-fills from the SSH Target while the user has not typed a custom name — a `phx-change="remote_connections_form_change"` handler rebuilds the whole `@remote_form_target` assign from the submitted params each keystroke (keeping `:name` equal to the full `:ssh_target` as it is typed). Once the user types into Name, that value is kept verbatim and never clobbered by later SSH Target edits. The auto-tracking state is an internal `:auto_name` marker on the LiveView assign only (seeded `true` in `add_remote_target`, `false` in `edit_remote_target`) — never persisted. Save-side guarantee: `build_remote_target_from_params/1` falls back to `ssh_target` when the submitted `name` is blank/absent, so a direct submit with a blank Name persists `name == ssh_target` (and the target id slugs from the effective name).

## SettingsLive platform gating (EvoDashWeb.PlatformInfo)

- `schemas_by_category` is filtered per node OS in `mount/3` AND re-filtered in `handle_params/3` (BEFORE `category_str_to_atom` so `?category=sandbox` resolves nil on Windows → falls back; if resolved/persisted active category is `:sandbox` but the filtered map lacks it → falls back to `:llm`).
- **Data-safety**: filtering is BOTH the display mechanism AND the save round-trip protection — `save_category` only processes schemas present in the filtered list, and `params_to_category_config` deep-deletes params absent from the form, so hidden sandbox fields (e.g. `[:sandbox,:resources]`, `[:sandbox,:linux]` on macOS) are never clobbered on save.
- `sandbox_backend(assigns)` private helper: local → `@scheduler_config[:sandbox_backend]` (accurate, reflects binary availability); remote → `PlatformInfo.sandbox_backend_for(@platform_os)` (scheduler_config is loaded from the LOCAL scheduler only — `ConfigIO.load_scheduler_config()` in mount).
- The Settings sandbox banner (`SettingsComponents.category_section/1` in `components/settings_components.ex`) renders an amber `:bwrap` clause ("Filesystem isolation active (bubblewrap); resource limits/syscall filtering unavailable").
- Note: `EvoDashWeb.PlatformInfo` itself (`live/platform_info.ex` — `os_for_node/1` with the `:platform_os_override` test seam, `windows?/macos?/linux?/show_sandbox?/sandbox_backend_for`, `filter_schemas_by_category/2`) is documented at the `apps/evo_dash/lib/evo_dash_web/live/` level (the parent live/CONTEXT.md keeps a condensed pointer); this file documents only how SettingsLive APPLIES it.
