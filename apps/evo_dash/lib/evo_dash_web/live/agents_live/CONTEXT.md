# AgentsLive Support Modules

## Intent

Support modules extracted from `EvoDashWeb.AgentsLive` to keep the main LiveView module and its companion template focused on rendering and lifecycle callbacks.

## API Surface

| Module | Purpose |
|--------|---------|
| `CommitGraph` | Pure COMMIT-DAG view-model assembly for the left panel's TEMPORAL (git commit history) view — a commit-centric HORIZONTAL DAG: one NODE per commit, one EDGE per child → parent link present in the fetched graph, ancestry flowing LEFT → RIGHT (oldest → newest), plus one horizontal LANE (band) per agent; the markup is the separate renderer (`../../components/agents_components/CONTEXT.md`). `grouping_key/1` (agent → `repo_root || repo_id`; the tree's repo grouping) and `repo_display_name/1` (`"primary"`/`:primary`/nil → "Primary Repo", absolute path → basename, else "Repo: %{repo_id}", fallback "Unknown Repo") are shared with the tree path (`agents_live.ex`'s `grouping_key/1`/`repo_display_name/1` are thin delegates). `build(raw_by_repo, agents)` returns one `repo_view` per repository group sorted by `{repo_name, repo_dom_id}`. **Nodes** — every ADDRESSABLE fetched commit (a map with a non-empty binary `:sha`, de-duplicated by sha) PLUS one synthesized `kind: :base` node per distinct agent `:base_commit` absent from the fetched commits; each node is `%{sha, short_sha, message, author_name, date, refs, x, y, kind, owner_id, start_ids, end_ids}` where `short_sha` is the commit's `:short_sha` (else `String.slice(sha, 0, 8)`), `message` is the commit message's FIRST LINE (`""` for a base node), `author_name` is a binary or nil, `date` is a `%DateTime{}` or nil, `refs` a list (else `[]`; always `[]` for a base node), `x` the grid COLUMN, `y` the grid ROW = the owning lane's index, `owner_id` the owning agent's id, and `start_ids`/`end_ids` the agent ids that fork from / tip at the sha (lane order; a node can be a start for one agent and an end for another). **`x` (rank → column)** — a real commit's `x` is a memoized TOPOLOGICAL rank over the FETCHED parents (no fetched parent → 0, otherwise `1 + max(rank(parent))`; the DFS carries a `visiting` set so a malformed parent cycle terminates — a revisit returns the memoized rank when there is one, else 0), while a synthesized base node gets `min_real_rank - 1` — ONE column left of the oldest real commits (`-1` when the repo has no real commit); ranking rather than fetch order matters because each range is its own `git log`, so the fetched list is not globally newest-first, and `%DateTime{}` structs are never compared directly (term order looks at `day` before `month`/`year`). **Base synthesis** — the fetch is `git log base..tip`, which EXCLUDES the base commit, so a fork point no agent committed on has no fetched commit to hang an edge on; a fetched commit that equals some agent's `:base_commit` stays a NORMAL `:commit` node and is never duplicated. **Edges (child → parent)** — for every real node and every one of its `:parents` present in the node set (fetched commits ∪ synthesized base shas): `%{from_sha, to_sha, from, to, kind, owner_id}` with `from`/`to` the `{x, y}` grid coordinates of the child/parent, `kind: :parent` for the FIRST present parent in the commit's `:parents` order and `:merge` for every other present parent, and `owner_id` the CHILD node's owner; absent parents produce no edge and identical `{from_sha, to_sha}` edges are de-duplicated (a base node has no parents, so it is always an edge TARGET). **Lanes** — one per agent in ascending `{depth, id}` order (the page's agent sort), `y` = its index: `%{agent_id, task_local_id, status, depth (normalized), color (depth hue), y, x_start, x_end, node_count, start_sha, end_sha}` where `x_start`/`x_end` are the MIN/MAX `x` among the nodes the lane OWNS (nil when it owns none), `node_count` how many nodes it owns, and `start_sha`/`end_sha` the agent's `:base_commit`/`:current_commit`. **Ownership** — a commit on at least one agent's progress path belongs to the agent with the MAXIMUM depth (ties broken by the SMALLEST lane index); a fetched commit on NO path (a merged-in side commit) inherits the owner of the commit it is the FIRST parent of — the deepest such child, ties by smallest lane index — falling back to the first lane when it has no owned child, resolved in DESCENDING rank order so children are owned before their parents; a synthesized base node belongs to the agent with the SMALLEST `{depth, lane index}` forked from it, so a shared task base lands in the shallowest root lane. A repo without agents has no lanes and therefore no nodes or edges. **Progress path** — a first-parent walk from the agent's `current_commit` backwards, stopping WITHOUT collecting at a non-binary sha, at `base_commit`, at an already-seen sha (cycle guard), or at a sha absent from the fetched graph; the walk yields NEWEST → OLDEST. **Depth→hue formula (verbatim)**: `color(depth) = EvoDashWeb.ThemeColor.hsl_to_hex(hue, 70, 54)` where `hue = Integer.mod(round(depth * 137.508) + 265, 360)` — golden-angle step 137.508° per depth level (deterministic, maximally spread hues), +265° offset so depth 0 lands on blue-violet and common shallow depths stay away from the status colors (red/green/amber), saturation 70 / lightness 54 identical to `ThemeColor`'s project accents; reuses the public `ThemeColor.hsl_to_hex/3` (no local HSL reimplementation); non-integer/nil/negative depth → 0. **Output shape**: `%{repo_key, repo_dom_id, repo_name, node_count, edge_count, lane_count, row_count, max_x, nodes, edges, lanes}` with `row_count == lane_count` and `max_x` the max node `x` (`0` when empty); `nodes` is sorted by `{x, y, sha}`, `edges` by `{from_sha, to_sha}` and `lanes` by `{depth, id}`, and repos by `{repo_name, repo_dom_id}` — all deterministic, so LiveView patches the graph incrementally; `repo_dom_id` is the unchanged stable DOM id. The module emits NO render/DOM concerns — no DOM ids beyond `repo_dom_id`, no colors beyond `lane.color`, no SVG geometry. Total: defensive `Map.get/2` reads, non-map/garbage input degrades to empty nodes/edges/lanes, never raises, no try/rescue. |
| `ToolCallDisplay` | Pure rendering contract for tool-call messages in the chat history viewer (inline detail panel + full-message modal). `display/1` returns `%{label, kind: :structured, rows}` for subagent (`subagent_*` prefix) and shell (`run_bash`/`run_powershell`) calls — key/value rows (path + truncated objective / truncated command) — or `%{label, kind: :inline, summary}` for all other calls (compact one-line arguments summary, truncated to 160 chars). Both forms are height-constrained by the template: structured blocks render in a `max-h` + `overflow-y-auto` container, inline summaries are one line with CSS ellipsis. Raw arguments JSON is never dumped for subagent/shell calls. |
| `OptimisticMessages` | Pure helpers for the optimistic display of user-sent messages in the chat history viewer. `append/3` appends `%{content, sent_at}` to the per-agent optimistic map (new message at the END). `merge/2` merges real history entries with pending optimistic entries (optimistic entries APPENDED after real history — base indices unchanged) and drops an optimistic entry once a real `"user"`-type history entry with the same content appears (first-match consumption: each real user entry reflects at most one optimistic entry, so sending identical text twice works; uppercase `"USER"` tolerated). `latest_turn/1` returns the max history turn (or 0). Optimistic entries render in the same `%{turn, type: "user", data: %{content}, optimistic: true}` shape the template's `"user"` case consumes. |
| `LoadData` | Data loading for the Agents page, extracted so it runs inside `EvoDash.TaskSupervisor` children (never in the LiveView process — cross-node RPCs never block the page). `load/2` = page load: agent summaries + `config_status` (layout banner) + a refreshed threshold cache → `{:ok, %{agents:, config_status:, threshold_cache:}}`. `refresh/2` = broadcast-triggered refresh path: agent summaries + threshold cache → `{agents, cache}` (no config_status). `find_children_from_agents/2` computes `{agent_id, status}` children from `parent_id` (public — AgentsLive's in-memory incremental paths reuse it). Builds the rich agent maps from `RemoteAPI.list_agents/0` summaries, carrying `:message_count` through for the history gate. Env seams resolved at call time (inside the tasks): `:agents_list_runner` (default `&EvoDash.NodeContext.list_agents/1`), `:agents_config_runner` (default `&EvoDash.NodeContext.get_resolved_config/1`). |
| `HistoryGate` | Pure history-fetch gating (payload fix): `need_fetch?/3` = `Map.get(last_seen, agent_id) != message_count` (a nil last-seen entry = brand-new agent = must fetch); `record/3` stores the count a fetched history corresponds to; `known?/2` = `Map.has_key?(last_seen, agent_id)` — the gate already observed this agent on the CURRENT node, which separates a same-node refetch from a brand-new agent OR a cross-node leftover (a node switch resets the gate while `@agents` is kept and agent ids are per-node). `RemoteAPI.list_agents/0` summaries carry `:message_count` (number of messages in the agent's session-memory context), and the `{:agent_updated, id, changed_fields, node}` broadcast carries `:message_count` whenever the agent's context changed — so an unchanged count means the already-fetched history is current, and full histories are never re-transferred over the node boundary. Gate state = the `:history_gate` socket assign (`%{agent_id => count}`, seeded `%{}` in mount, reset on node switch — agent ids are per-node). |
| `ThresholdCache` | Per-node cache for the LLM compression threshold used by the compression % bars. The threshold lives at `[:llm, :compression_threshold_tokens]` in the FULL resolved config (`EvoGit.Config.resolve/0`, default 180_000) — the scheduler config (`get_remote_config/1`) has NO `:llm` section, which was the old remote-branch bug. Cache shape `{node, threshold, fetched_at_monotonic}` (nil = empty); `read/3` (fresh within 30s) / `put/4` / `fetch/3` (cache miss → node-aware runner via the `:agents_config_runner` seam, resolved at call time) / `threshold_from_config/1` (accepts `{:ok, config} | {:error, reason}`) / `default_threshold/0`. The fetch runs ONLY inside the async load/refresh tasks — never in a `handle_info`/`handle_event`. |
| `PendingEvents` | Pure bookkeeping for the Agents page's agent-event coalescing buffer (no socket, no process, no I/O). `flush_ms/0` = the trailing-edge window (300ms, shared with the debounce). `new/0` = empty buffer. `append/2` prepends the raw event (newest-first, O(1)). `should_schedule?/1` = `not scheduled?` — only the first event of a window arms the flush timer. `drain/1` = `Enum.reverse/1` (restores strict arrival order). The buffer is a plain list stored in the `:pending_agent_events` assign; the socket-mutating merge/flush logic stays in `agents_live.ex`. |

## Constraints

- Pure functions — no I/O, no socket, no process calls (`ToolCallDisplay`, `OptimisticMessages`, `HistoryGate`, `PendingEvents`; `ThresholdCache.read/3`/`put/4`/`threshold_from_config/1`/`default_threshold/0` are pure). Deliberate exceptions: `LoadData` and `ThresholdCache.fetch/3` perform I/O (NodeContext RPCs via the env-seam runners) — they are designed to run inside `EvoDash.TaskSupervisor` children, never in the LiveView process.
- No `try/rescue` — defensive extraction + pattern matching/`case` only (project-wide anti-pattern policy). The node-boundary `try/rescue` wrappers live in `agents_live.ex`'s spawn functions (`start_async_load/1` / `spawn_agents_refresh/1` / `spawn_history_fetch/3` / `spawn_commit_graph_fetch/2`), each carrying a justification comment.
- Reuses `EvoDashWeb.Helpers` defensive extraction (`tool_call_name/1`, `tool_call_arguments/1`, `tool_call_is_shell?/1`) — do not reimplement; `EvoDashWeb.Helpers.tool_call_display/1` is not used by the Agents page; it stays as a public, test-pinned helper (do not remove it).
- New user-facing strings use `gettext` (backend `EvoDashWeb.Gettext`); `Path`/`Objective`/`Command` entries appear in the POT/PO at release-time extraction only — do not run `mix gettext.extract`/`merge`/`translate` during development.

## Left-Panel View Switcher & Commit-History (Temporal) View

The left panel renders EITHER the spatial agent tree OR the temporal git-commit graph, switched by a segmented control in the panel header (two `phx-click="switch_left_view"` buttons, `id="left-view-tree"` / `id="left-view-commits"`, each carrying `phx-value-view="tree"|"commits"`).
The active view is the `:left_view` assign (`:tree | :commits`, default `:tree` in `mount/3`).
`switch_left_view` whitelists the view by PATTERN MATCHING the two literal binaries — any other value falls through to a no-op clause (no atom conversion, no `String.to_atom`).
Switching to `:commits` triggers an immediate force-refresh commit-graph load; switching back to `:tree` renders the tree and never touches the git RPC.
`:left_view` SURVIVES a node switch (it is a user preference) and is NOT in the `handle_params/3` reset branch, while the commit-graph DATA is per-node and IS reset there.
The tree view (and its `"Agent Tree"` label) stays the default, so the agent tree, right-hand detail panel and status legend chips are behaviourally unchanged.

### Commit-graph async contract

- Assigns (seeded in `mount/3`; the data assigns are reset on a node switch): `@left_view`, `@commit_graph` (built `[repo_view]`), `@commit_graph_raw` (`%{repo_key => %{commits:, refs:}}`), `@commit_graph_loaded`, `@commit_graph_loading`, `@commit_graph_error`, `@commit_graph_seq` (monotonic — NEVER reset, mirrors `@refresh_seq`), `@commit_graph_fetched_at` (monotonic ms of the last fetch), `@commit_graph_tick_scheduled` (one-shot-tick guard).
- `maybe_load_commit_graph/2` is a NO-OP unless `@left_view == :commits` — the tree view never triggers a git RPC.
- It first rebuilds `@commit_graph` from `@commit_graph_raw` + the current `@agents` (`rebuild_commit_graph/1`), so a newly-spawned child's lane and its nodes appear immediately without a fetch.
- `commit_graph_groups/1` groups eligible agents (`repo_root`, `base_commit`, `current_commit` all binaries) by `repo_root` into de-duplicated `{base_commit, current_commit}` ranges, sorted for deterministic task input; an empty group list marks the view loaded with an empty graph.
- `spawn_commit_graph_fetch/2` runs in an `EvoDash.TaskSupervisor` child (never the LiveView process), calls the runner ONCE per distinct `repo_root` (`limit: @commit_graph_limit`, 100), and sends `{:commit_graph_loaded, node, seq, result}` where `result = {:ok, raw_by_repo} | {:error, reason}` (any non-`{:ok, %{commits: list}}` repo reply halts with `{:error, {:commit_graph_repo_failed, repo_root, other}}`).
- The runner seam is `:agents_commit_graph_runner` (default `&EvoDash.NodeContext.list_commit_graph/4`), resolved AT SPAWN TIME so tests can stub it; the spawn carries a justified node-boundary `try/rescue` (an error keeps the last good graph — the view never wedges on a spinner).
- The `{:commit_graph_loaded, ...}` result is stale-guarded on the viewed node AND the monotonic seq; a stale node/seq is dropped, `{:ok, raw_by_repo}` builds + assigns the graph (clearing loading/error), `{:error, reason}` only clears loading and records the error (the last good `@commit_graph` stays rendered).
- Throttling: a refetch is skipped when `@commit_graph_fetched_at` is within `@commit_graph_min_interval_ms` (1000ms); a throttled request arms ONE one-shot `:commit_graph_tick` (never a repeating poll — `@commit_graph_tick_scheduled` guarantees one timer per window) whose handler re-attempts with `force: true`.
- Refresh triggers: `apply_agents_result/2` (async load + broadcast refresh result path) and the end of `handle_info(:flush_agent_events, ...)` (a burst of agent commits extends the timeline — new nodes/edges, moved lanes) both end with `maybe_load_commit_graph(socket, [])`; first activation / the tick use `force: true`.

### Commit view markup (contract boundary)

The view is rendered by `EvoDashWeb.AgentsComponents.CommitGraphView.commit_graph_view/1` (called FULLY QUALIFIED in `agents_live.html.heex`; attrs `repos` / `selected_id` / `loading` / `error` / `node_key`), fed `repos={@commit_graph}`, `selected_id={@selected_agent_id}`, `loading={@commit_graph_loading}`, `error={@commit_graph_error}` and `node_key={@current_node_id || "local"}`.
The contract boundary: this builder owns ONLY the view model (`repo_key`/`repo_dom_id`/`repo_name` + `nodes` + `edges` + `lanes`); every DOM id, element, tooltip, legend chip and client-side hook belongs to the renderer — see `../../components/agents_components/CONTEXT.md`.

### Commit-graph colors

`CommitGraph.build/2` emits exactly ONE color per lane — `lane.color`, the agent's depth hue (`EvoDashWeb.ThemeColor.hsl_to_hex(hue, 70, 54)` with `hue = Integer.mod(round(depth * 137.508) + 265, 360)`; depth 0 = `#7c38dc`).
Node fills, edge strokes, status palettes (`EvoDashWeb.Helpers.agent_status_svg_color/1`) and per-theme CSS-var tokens are the renderer's concern — the builder never chooses them.

## Send-Message Flow (in `agents_live.ex` + `agents_live.html.heex`)

User-sent messages display optimistically via the `OptimisticMessages` support module (below).

- **Event handlers in `agents_live.ex`**: `open_send_message` (sets `send_message_agent_id` + clears `send_message_text`), `close_send_message`, `validate_send_message` (`phx-change` syncs `@send_message_text`), **`send_agent_message`** — the submit handler. Params: `%{"agent_id" => id, "message" => message}` (hidden input heex line 670 + textarea). It calls `EvoDash.NodeContext.send_user_message(node, agent_id, message)`.
- **Return matching**: only `{:ok, :ok}` is a real success (local AND remote). Missing agent = `{:ok, {:error, :not_found}}` (the local path wraps the RemoteAPI result); erpc failures = `{:error, reason}`. Both error shapes show the error flash `"Failed to send message: %{reason}"` (shared private helper `send_message_error_flash/1`). On success: info flash `"Message sent to agent"` + modal close + the message is appended to `@optimistic_messages[agent_id]` (via `OptimisticMessages.append/3`, preserving order; new message at the END).
- **`@optimistic_messages` assign**: `agent_id => [%{content, sent_at}]` map, initialized to `%{}` in mount and RESET to `%{}` only on node switch in `handle_params/3` (agent ids are per-node). It is independent of `@agents` and deliberately survives all history reloads (`{:agents_updated, node}`, `{:agent_updated, id, fields, node}`, `select_agent`, async load/refresh results) — drained messages are dropped by the render-time dedupe, not by clearing the assign.
- **Send call chain** (into sibling `evo_git` subtree): `EvoDash.NodeContext.send_user_message/3` (`node_context.ex:291`) → `EvoGit.RemoteNode.send_agent_message/3` (`remote_node.ex:276`; local = direct, remote = `:erpc.call`) → `EvoGit.AgentScheduler.RemoteAPI.send_agent_message/2` (`remote_api.ex:264`) → `EvoGit.AgentScheduler.send_user_message/2` (GenServer.call, `agent_scheduler.ex:242`) → `handle_call({:send_user_message, ...})` (`agent_scheduler.ex:739`) → `Store.append_pending_user_message/2` (`store.ex:155`) → appends to `AgentState.pending_user_messages` (`agent_state.ex:61`). Returns `:ok` / `{:error, :not_found}` / `{:error, :scheduler_not_started}`.
- **Pending messages are INVISIBLE to the history read path**: `RemoteAPI.get_agent_history/1` (`remote_api.ex:85`) returns only `agent_state.context.messages`. The queue is drained ONLY at the top of the agent's next turn: `drain_and_inject_user_messages/1` (`apps/evo_git/lib/evo_git/agent/runner.ex:232`) drains via `Store.drain_pending_user_messages/1` (`store.ex:182`) and appends each message as a `user(msg)` role entry tagged with the current turn, then `sync_context_to_ets/2` → `Store.update_agent_context/2` (`store.ex:348`) → `put_agent_state`. Only then does the message appear in history. **Note:** appending to the queue DOES broadcast `{:agent_updated, agent_id, [pending_user_messages: ...]}` (`pending_user_messages` is in `@agent_state_tracked_fields`, `store.ex:447`) — the LiveView does NOT refetch on that (no `:message_count` in the changed fields), so the message stays invisible in the panel until the agent's next turn actually drains it into context. The optimistic copy bridges that gap.
- **History refresh mechanics** (all ASYNC; results are applied in place): fetches run via `spawn_history_fetch/3` — an `EvoDash.TaskSupervisor` child calling the `:agents_history_runner` seam (default `EvoDash.NodeContext.get_agent_history/2`, resolved inside the task) — and the result is applied from `{:agent_history_loaded, agent_id, node, result, index}` (stale-guarded on selected agent + current node; `history_loading_agent_id`/`full_message_pending_agent_id` assigns drive the small "Loading history…" spinner). Fetches are GATED on `:message_count` via `HistoryGate` (`need_fetch?/3`): a fetch happens only when the gate's last-seen count differs from the fresh summary count (nil = must fetch), so unchanged conversations are never re-transferred. `apply_agents_result/2` carries the already-fetched history over for an old row ONLY when the history gate already KNOWS that id on the current node (`old_agent != nil and old_agent.history != [] and HistoryGate.known?/2`) — this keeps the panel from being blanked to the spinner mid-refetch WITHIN a node, while a node switch (which resets the gate but keeps `@agents`) can never leak a previous node's history through a colliding per-node agent id (a brand-new agent has `history: []` anyway, so skipping the carry-over is a no-op for it). The gate is recorded ONLY when the count is unchanged (`!need_fetch?/3`) — a moved count still reports "needs fetch" and the refetch is still triggered. Triggers: (1) `{:agents_updated, node}` full reload → `apply_agents_result/2` → `maybe_fetch_selected_history/1` (gate-checked); (2) `{:agent_updated, id, changed_fields, node}` of the selected agent WITH `:message_count` in changed_fields (the contract: it is present whenever the context changed) → at flush end AT MOST ONE `refetch_selected_history/1` (gate-checked against the merged fresh count — no refetch when the count is unchanged or the field is absent; skipped entirely when the flush spawned a refresh); (3) `select_agent` lazy-load (gate-checked); (4) `view_full_message` empty-history safety net (carries the entry `index` in the result message). Subscription: `Phoenix.PubSub.subscribe(EvoGit.PubSub, "agents")` in `mount/3`.
- **History entry shape**: `messages_to_history_entries/1` / `message_to_history_entry/1` produce `%{turn, timestamp, type, data}` with `type = Atom.to_string(msg.role)` (lowercase: "user"/"assistant"/"tool"/"system") and `data.content` = joined ContentPart renderings — text parts contribute their text, image/audio parts contribute short metadata labels (`"[image: <name>]"` / `"[audio: <name>]"` — see the multimodal content-part label note below), and every other non-text part type contributes nothing (unchanged). Raw part binaries never reach `data.content`. Template rendering: `agents_live.html.heex` lines 330-509 ("Chat History / Session Memory"); the `"user"` case renders `entry.data.content` in a `bg-info/10` panel. Styling helpers in `EvoDashWeb.Helpers`: `history_entry_icon/1`, `history_entry_color/1`. Uppercase types ("USER_PROMPT", "THOUGHT_CHUNK", "TOOL_CALL_START", "COMPLETE", "QUEUED", etc.) are cased in the template but nothing produces them; "QUEUED" renders `entry.data.message` — a queued-message display that is dead.
- **Optimistic rendering**: the chat-history template computes `history_entries = OptimisticMessages.merge(agent.history || [], Map.get(@optimistic_messages, agent.id, []))` and iterates THAT (the empty-state condition uses `history_entries != []`, so an empty real history with pending messages still renders). Optimistic entries are APPENDED after the real history (never interleaved) → base-history indices are unchanged, and `view_full_message` looks up from the merged list (`merged_history/2` private helper) so optimistic entries are viewable in the modal too. Optimistic entries carry `optimistic: true`; the `"user"` case renders a small italic pending hint (`"Pending — will be added on the agent's next turn"`, gettext-wrapped, gated on `Map.get(entry, :optimistic, false)` — plain dot access would raise KeyError for real entries). Once the agent drains the queue, the real `"user"` entry appears in history on the next reload and the render-time dedupe drops the optimistic copy — no duplicates.
- **Mounted panel across refetches / keyed history entries**: the iterated history entries in `agents_live.html.heex` each carry a STABLE root id (`id={"agent-history-entry-#{@selected_agent_id}-#{index}"}`). On a refetch result LiveView's keyed comprehension matches the unchanged prefix by id, so those entries keep their DOM nodes — no full-list re-render and no re-run of the `history-entry-appear` CSS animation — and only the appended tail is inserted. Divergent/compressed histories (no shared prefix) still update the entries in place; optimistic-message dedupe/removal keeps working (no `phx-update="append"/"prepend"` — entries must stay updatable/removable).

## Agent Event Contract (push-based, node-identity, coalesced flush)

The Agents page is FULLY push-based — there is NO periodic poll.
The `:evo_git` emitters broadcast EXACTLY these four shapes on `EvoGit.PubSub` topic `"agents"`, every one carrying the BEAM node atom of the publisher.
Every event is node-filtered FIRST via `EvoDashWeb.LiveHooks.NodeAware.event_from_current_node?(socket.assigns, event_node)` (viewed node identity = `socket.assigns[:current_node]`; local → `node()`, remote → the remote daemon's BEAM node atom).
Foreign-node events are dropped BEFORE buffering — they never arm a flush and never leak into the viewed node's tree.
The three incremental events (`:agent_registered` / `:agent_updated` / `:agent_removed`) are COALESCED: each `handle_info` clause only buffers the raw event into the `:pending_agent_events` assign (`PendingEvents.append/2`, newest-first) and arms ONE 300ms trailing-edge timer (`Process.send_after(self(), :flush_agent_events, PendingEvents.flush_ms())`).
The `:agent_flush_scheduled` boolean guarantees the timer is armed only by the FIRST event of a window — subsequent events just append to the existing buffer.
`{:agents_updated, node}` sets the coalesced `:pending_agents_refresh` boolean and arms the same timer — it never spawns a refresh per event.
`handle_info(:flush_agent_events, socket)` drains the buffer in ARRIVAL order (`PendingEvents.drain/1`), applies every event through the incremental merge paths below (threading the socket through each apply), and returns ONE `{:noreply, socket}`.
One flush therefore yields exactly ONE render/DOM diff for the whole burst — no LiveView mailbox starvation of user `phx-click`/`phx-submit` events, and no burst/blink when a backgrounded tab is foregrounded.
The buffer + `:agent_flush_scheduled` + `:pending_agents_refresh` are seeded in `mount/3` and RESET on the `handle_params/3` node-change branch (stale-node events never leak); a timer already in flight after a node switch is harmless — the buffer is empty, so the flush is a no-op.
The fallback refresh is COALESCED: a buffered `:agent_registered` with an incomplete summary, a buffered `:agent_updated` for an unknown id, and a `{:agents_updated, node}` all set the refresh flag, and the flush spawns AT MOST ONE `spawn_agents_refresh/1` (async full reload, seq-guarded via the monotonic `:refresh_seq` assign).
The selected-agent history refetch is COALESCED: the flush tracks whether ANY buffered `:agent_updated` for the currently-selected agent carried `:message_count`, then calls `refetch_selected_history/1` AT MOST ONCE at the end — and NOT when a refresh was spawned (that path already runs the identical `maybe_fetch_selected_history/1`).
Both refetch paths are the same gate-checked call against `HistoryGate.need_fetch?/3` (plus the `history_loading_agent_id` overlap guard), so a burst collapses to one gate-checked fetch.
All heavy loads stay in `EvoDash.TaskSupervisor` children — never in `handle_info` (`start_async_load/1` / `spawn_agents_refresh/1` / `spawn_history_fetch/3` unchanged; their stale-guards `{:agents_data_loaded, ...}` / `{:agents_refresh_result, ...}` / `{:agent_history_loaded, ...}` are untouched).

- `{:agents_updated, node}` — throttled bulk-change signal → node-match → sets the coalesced refresh flag → one `spawn_agents_refresh/1` per flush window; foreign → ignored.
- `{:agent_registered, id, summary, node}` — the event carries the agent's full summary (the same `RemoteAPI.list_agents/0` summary shape `LoadData.build_agents` consumes: `id, task_local_id, repo_id, repo_root, task_id, task_number, status, depth, parent_id, worktree, retries, agent_module, model_id, objective, context_path, current_commit, base_commit, usage, total_tokens, compression_count, message_count`). Applied at flush time, merged IN-MEMORY for BOTH local and remote events through ONE shared path (`merge_registered_agent/3` → `build_registered_agent/2`): the row is built with the `LoadData` field mapping (defaults for absent fields, `usage` normalized to a `%Usage{}` struct), derived fields recomputed exactly like the load path (children/has_children from `parent_id`, `compression_pct` from `total_tokens` + the node threshold via `safe_compression_threshold/1`), inserted at the sorted `{depth, id}` position, the parent's children list refreshed, and `id_to_display`/`previous_agent_ids`/`new_agent_ids`/`repo_trees` updated. A duplicate id (race with the `{:agents_updated, node}` fallback) is a no-op; a summary missing the fields the tree needs (`status`/`depth`/`parent_id`) sets the coalesced refresh flag (one `spawn_agents_refresh/1` at flush end).
- `{:agent_updated, id, changed_fields, node}` — `changed_fields` NEVER contains `:context`; it DOES contain `:message_count` whenever the agent's context changed. Applied at flush time, the in-memory merge runs for BOTH local and remote (special fields: `context_node` → `context_path`, `phylo_node` → `current_commit`, nil `usage` → zero, `compression_pct` recompute on `total_tokens`, children recalc on `parent_id`, status-change tracking into `previous_statuses`/`changed_status_ids`, `id_to_display` on `task_local_id`, `repo_trees` rebuild on `context_node`/`repo_root`). The selected-agent history refetch is deferred to the flush (at most one gate-checked `refetch_selected_history/1` when any buffered update for the selected agent carried `:message_count`). A missing agent row (race) sets the coalesced refresh flag (one `spawn_agents_refresh/1` at flush end).
- `{:agent_removed, id, node}` — applied at flush time; the row is dropped in-memory (children orphaned to `parent_id: nil`, parent's children list refreshed, tracking sets/selection/repo_trees cleaned) for BOTH local and remote; foreign → ignored.

## Notes for Agents — Tool-call display layout contract

The Agents page chat history viewer renders tool-call messages (both the inline detail panel and the full-message modal) through `EvoDashWeb.AgentsLive.ToolCallDisplay.display/1` (aliased as `ToolCallDisplay` in `agents_live.ex`). Durable facts:

- **Return contract**: `display/1` returns `%{label: String.t(), kind: :structured, rows: [{String.t(), String.t()}]}` (subagent + shell calls) or `%{label: String.t(), kind: :inline, summary: String.t()}` (all other calls). The template branches on `display.kind == :structured`.
- **Structured calls**: `subagent_*`-prefixed names (core `subagent_tool_name/0` family — `subagent_manager`, `subagent_executor`, `subagent_investigator`, `subagent_task_scheduler`, `subagent_genesis_planner`, `subagent_architect`, `subagent_context_extractor`; prefix detection covers future variants) show rows `Path` (first of `"path"`/`"file_path"`) + `Objective` (truncated to 200 chars with `…`); `run_bash`/`run_powershell` shell calls show a single `Command` row (truncated to 200 chars, `"command"` from decoded args with raw-args-collapsed fallback). Raw arguments JSON is NEVER dumped for these.
- **One-line calls**: every other tool (read_file, write_file, edit_file, rg, glob, list_dir, make_dir, create_files, read_context, write_context, search_context, skill_*, complete_task, unknown, …) renders a single-line summary: path-like field (`"path"`/`"file_path"`/`"dir_path"`/`"paths"`, list values joined with `" "`) if present, else compact single-line `Jason.encode/1` of the decoded args, else whitespace-collapsed raw arguments, else `""` — truncated to 160 chars with `…`.
- **Height-constrained everywhere**: structured blocks render inside `max-h-12` (inline panel, ~2 lines) / `max-h-60` (modal) `overflow-y-auto` containers; structured rows render flat inside the parent container (no separate box/background layer) — only the parent "Tool Calls" box keeps its background. Inline summaries are one line (`whitespace-nowrap overflow-hidden text-ellipsis`). No new CSS in `app.css` — stock Tailwind 4 / DaisyUI utilities only.
- **Label/rows layout contract (both render sites)**: the tool-call label ("Shell call" / "subagent_manager" / etc.) is INLINE beside the rows — a flex row (`flex items-start gap-2`) with the label as a `shrink-0` span and the rows container as `min-w-0 flex-1`, so the label and the first structured row key ("Command" / "Path") sit on the SAME line, top-aligned. The key column is `w-20 shrink-0` with 10px uppercase text; the rows containers carry NO padding offsets (`p-1.5`/`pt-0.5`/`p-2` are absent). The inline-summary else-branch is a `min-w-0` span (not a div) in both sites.
- `EvoDashWeb.Helpers.tool_call_display/1` is NOT used by the Agents page — it remains a public, test-pinned helper in `helpers.ex` (do not remove it). `ToolCallDisplay` reuses Helpers' defensive extractors (`tool_call_name/1`, `tool_call_arguments/1`, `tool_call_is_shell?/1`) and adds its own non-crashing `Jason` handling via pattern-matched `case` — no `try/rescue` (project policy).
- New gettext strings (`Path`, `Objective`, `Command`) will not appear in the POT/PO until release-time extraction — expected, do NOT run `mix gettext.extract`/`merge`/`translate` during development.

## Notes for Agents — Agents page layout & legend tooltip

The Agents page uses a fixed-viewport layout (`xl+` only): `.agents-page-layout` (grid, `overflow: hidden`), `.agents-left-col` (column flex, `overflow: hidden`), `.agents-tree-panel` (card, `flex: 1 1 0`), with the tree content scrolling inside `.agents-tree-panel .card-body` (`overflow-y: auto`) and the legend (`.agents-legend`) as a SIBLING of card-body at the panel's bottom. On mobile (<xl) it is normal flow under `#main-scroll` (`overflow: auto`) inside `#app-layout` (`overflow: hidden`).

- **Legend tooltips use the `LegendTooltip` JS hook (`assets/js/hooks/legend_tooltip.js`) — NOT DaisyUI `.tooltip`.** DaisyUI's tooltip pseudo-element is absolutely positioned and horizontally CENTERED on the chip, so the long `data-tip` texts (max-width 20rem) on the right-aligned legend chips extend past the panel's right edge and get clipped by the page-level overflow containers (`#app-layout`, `#main-scroll`, `.agents-page-layout`, `.agents-left-col`). CSS-only anchoring can't fix this (the panel is ~480px wide at xl, so any single anchor overflows on some chip). The hook renders the tip as a `position: fixed` element appended to **`document.body`** — mandatory because `.agents-page-layout`'s `animate-fade-in-up` uses `animation-fill-mode: both`, so `transform: translateY(0)` PERSISTS on the layout and would trap even `position: fixed` descendants inside its `overflow: hidden`. The chips carry `data-tip` (gettext) + `phx-hook="LegendTooltip"` + unique ids (LiveView requires `id` for phx-hook); the `tooltip` class was REMOVED so DaisyUI's clipped tooltip doesn't double-render. The "Send Message" button tooltip (`tooltip` class, short text near the card edge) stays inside its container and is NOT affected — do not convert it.

## Notes for Agents — Session-memory message timestamps

The agents-page chat history (`AgentsLive` → `messages_to_history_entries/1` → `message_to_history_entry/1`) consumes `%ReqLLM.Message{}` structs from `EvoGit.AgentScheduler.RemoteAPI.get_agent_history/1`, which returns the raw `AgentState.context.messages` list.

- **Timestamps are stamped at the source** by the `:evo_git` runtime into each message's `metadata[:timestamp]` (a free-form map). Representation: **Unix-seconds integer** or a **`DateTime`** (the dashboard formatter also accepts ISO8601 binaries defensively). Historical messages may lack the key.
- **Dashboard rendering**: `message_to_history_entry/1` carries the raw value as `timestamp:` in the entry map; the agents detail panel renders a short **LOCAL** 24h time (`"HH:MM:SS"`, seconds precision) next to "Turn x" via `EvoDashWeb.Helpers.format_history_timestamp/1`. Local conversion uses the offset between `:calendar.local_time/0` and `:calendar.universal_time/0` (stdlib-only; no tz DB — the default `Calendar.UTCOnlyTimeZoneDatabase` only supports "Etc/UTC"). **Graceful fallback**: when `timestamp` is absent, no time is rendered — just "Turn x", no placeholders.
- **Multimodal content-part labels** (`message_to_history_entry/1`, agents_live.ex:1205-1229): each content part renders via `content_part_label/1` (agents_live.ex:1237-1247) — nil → `Map.get(part, :text)` (unchanged text/thinking extraction), non-nil label → the label — then `Enum.reject(&is_nil/1)` + `Enum.join()`. Image parts render `"[image: <name>]"`, audio parts `"[audio: <name>]"`, with `part_name_suffix/1` (:1265-1270) supplying `": <name>"` from the part's `filename` field (prefers it) or a `name` key — bare `"[image]"`/`"[audio]"` when no filename — so messages whose content is image/audio parts are never blank. EVERY other part type (text/image_url/video_url/thinking/unknown) returns nil and behaves exactly as before. Audio detection (`audio_part?/2`, :1251-1260) matches type `:audio`/`"audio"` AND type `:file`/`"file"` with an `audio/*` `media_type`; type/media_type/name reads are atom-or-string-key tolerant via `pget/2` (:1273). The helpers are TOTAL (never raise), accept `%ReqLLM.Message.ContentPart{}` structs AND map shapes, and NEVER touch a part's raw `data` binary — labels are metadata strings only, so `entry.data.content` (and the template's `<empty message>` fallback, now reachable only for genuinely empty content) never sees raw binary.
