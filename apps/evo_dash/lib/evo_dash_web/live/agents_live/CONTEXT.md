# AgentsLive Support Modules

## Intent

Support modules extracted from `EvoDashWeb.AgentsLive` to keep the main LiveView module and its companion template focused on rendering and lifecycle callbacks.

## API Surface

| Module | Purpose |
|--------|---------|
| `ToolCallDisplay` | Pure rendering contract for tool-call messages in the chat history viewer (inline detail panel + full-message modal). `display/1` returns `%{label, kind: :structured, rows}` for subagent (`subagent_*` prefix) and shell (`run_bash`/`run_powershell`) calls — key/value rows (path + truncated objective / truncated command) — or `%{label, kind: :inline, summary}` for all other calls (compact one-line arguments summary, truncated to 160 chars). Both forms are height-constrained by the template: structured blocks render in a `max-h` + `overflow-y-auto` container, inline summaries are one line with CSS ellipsis. Raw arguments JSON is never dumped for subagent/shell calls. |

## Constraints

- Pure functions — no I/O, no socket, no process calls.
- No `try/rescue` — defensive extraction + pattern matching/`case` only (project-wide anti-pattern policy).
- Reuses `EvoDashWeb.Helpers` defensive extraction (`tool_call_name/1`, `tool_call_arguments/1`, `tool_call_is_shell?/1`) — do not reimplement; `EvoDashWeb.Helpers.tool_call_display/1` is no longer used by the Agents page but stays as a public, test-pinned helper (do not remove it).
- New user-facing strings use `gettext` (backend `EvoDashWeb.Gettext`); `Path`/`Objective`/`Command` entries appear in the POT/PO at release-time extraction only — do not run `mix gettext.extract`/`merge`/`translate` during development.

## Send-Message Flow (in `agents_live.ex` + `agents_live.html.heex`)

Knowledge captured for the optimistic-display feasibility question (no code changes made).

- **Event handlers in `agents_live.ex`**: `open_send_message` (line 526, sets `send_message_agent_id` + clears `send_message_text`), `close_send_message` (line 532), `validate_send_message` (line 537, `phx-change` syncs `@send_message_text`), **`send_agent_message` (lines 542-561)** — the submit handler. Params: `%{"agent_id" => id, "message" => message}` (hidden input heex line 670 + textarea). It calls `EvoDash.NodeContext.send_user_message(node, agent_id, message)` and on `{:ok, _}` shows an info flash "Message sent to agent" + closes the modal; on `{:error, reason}` an error flash. **It does NOT touch history or any agent assign — no optimistic display exists today.** Template: send-message modal at heex lines 657-694 (form `phx-submit="send_agent_message"` line 669; helper text "Your message will be added to the agent's context on its next turn." line 666).
- **Send call chain** (into sibling `evo_git` subtree): `EvoDash.NodeContext.send_user_message/3` (`node_context.ex:291`) → `EvoGit.RemoteNode.send_agent_message/3` (`remote_node.ex:276`; local = direct, remote = `:erpc.call`) → `EvoGit.AgentScheduler.RemoteAPI.send_agent_message/2` (`remote_api.ex:264`) → `EvoGit.AgentScheduler.send_user_message/2` (GenServer.call, `agent_scheduler.ex:242`) → `handle_call({:send_user_message, ...})` (`agent_scheduler.ex:739`) → `Store.append_pending_user_message/2` (`store.ex:155`) → appends to `AgentState.pending_user_messages` (`agent_state.ex:61`). Returns `:ok` / `{:error, :not_found}` / `{:error, :scheduler_not_started}`.
- **Pending messages are INVISIBLE to the history read path**: `RemoteAPI.get_agent_history/1` (`remote_api.ex:85`) returns only `agent_state.context.messages`. The queue is drained ONLY at the top of the agent's next turn: `drain_and_inject_user_messages/1` (`apps/evo_git/lib/evo_git/agent/runner.ex:232`) drains via `Store.drain_pending_user_messages/1` (`store.ex:182`) and appends each message as a `user(msg)` role entry tagged with the current turn, then `sync_context_to_ets/2` → `Store.update_agent_context/2` (`store.ex:348`) → `put_agent_state`. Only then does the message appear in history. **Note:** appending to the queue DOES broadcast `{:agent_updated, agent_id, [pending_user_messages: ...]}` (`pending_user_messages` is in `@agent_state_tracked_fields`, `store.ex:447`) — so the LiveView's `handle_info({:agent_updated, ...})` reloads the selected agent's history immediately after send, but the message is still absent from `context.messages` until the next turn. The `context` field itself is excluded from `:agent_updated` deltas (`store.ex:424-427`); context changes only fire the throttled `{:agents_updated}`.
- **History refresh mechanics** (all REPLACE the whole per-agent history list — `reload_selected_agent_history/3` at `agents_live.ex:1005`, or `load_agent_history` in the `agent_updated` path at line 314): (1) `{:agents_updated}` full reload (line 116); (2) `{:agent_updated, agent_id, _}` reloads only if `agent_id == selected_agent_id` (line 312); (3) 3s `:remote_poll` for remote nodes only (line 182, reloads selected history at line 203); (4) `select_agent` lazy-load (line 432); (5) `view_full_message` safety-net load (line 478). Subscription: `Phoenix.PubSub.subscribe(EvoGit.PubSub, "agents")` in `mount/3` (line 22).
- **History entry shape**: `messages_to_history_entries/1` / `message_to_history_entry/1` (`agents_live.ex:978-1001`) produce `%{turn, timestamp, type, data}` with `type = Atom.to_string(msg.role)` (lowercase: "user"/"assistant"/"tool"/"system") and `data.content` = joined ContentPart texts. Template rendering: `agents_live.html.heex` lines 330-509 ("Chat History / Session Memory"); the `"user"` case (lines 429-438) renders `entry.data.content` in a `bg-info/10` panel — an optimistic entry just needs that shape. Styling helpers in `EvoDashWeb.Helpers`: `history_entry_icon/1` (helpers.ex:291), `history_entry_color/1` (helpers.ex:300). Legacy uppercase types ("USER_PROMPT", "THOUGHT_CHUNK", "TOOL_CALL_START", "COMPLETE", "QUEUED", etc.) are still cased in the template (lines 366-420) but nothing produces them today; "QUEUED" (line 410) renders `entry.data.message` — a historical queued-message display that is currently dead.
- **Feasibility notes for optimistic display**: an optimistic entry appended to `agent.history` would be WIPED by the next reload (all reload paths replace the whole list), and the `{:agent_updated, pending_user_messages...}` delta arrives ~immediately after send on the local node. A robust approach keeps optimistic entries in a SEPARATE assign (keyed by agent_id, with a client-side id/timestamp) merged at render time, and dedupes against the real `"user"` entry once the agent's next turn drains the queue into context (else the message renders twice). On remote nodes PubSub is unreliable — only the 3s poll reloads, so optimistic entries persist longer there. `RemoteAPI.get_agent_state/1` (`remote_api.ex:107`) DOES expose `pending_user_messages` (full AgentState minus context), but AgentsLive never calls it and the `list_agents` summary layer (`build_agent_summary/3`, `remote_api.ex:541`) omits it.
