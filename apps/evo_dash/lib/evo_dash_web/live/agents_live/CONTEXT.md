# AgentsLive Support Modules

## Intent

Support modules extracted from `EvoDashWeb.AgentsLive` to keep the main LiveView module and its companion template focused on rendering and lifecycle callbacks.

## API Surface

| Module | Purpose |
|--------|---------|
| `CommitGraph` | Pure COMMIT-DAG view-model assembly for the left panel's TEMPORAL (git commit history) view — a VERTICAL, commit-centric DAG (GitKraken/GitLen shape): ONE VISIBLE ROW per commit, GLOBALLY interleaved across agents, plus a left GUTTER LANE per node so the renderer can draw the commit → parent edges and the agent-level spawn / merge-back edges between the rows; the markup is the separate renderer (`../../components/agents_components/CONTEXT.md`). Public API: `build/2`, `grouping_key/1` (agent → `repo_root || repo_id`; the tree's repo grouping) and `repo_display_name/1` (`"primary"`/`:primary`/nil → "Primary Repo", absolute path → basename, else "Repo: %{repo_id}", fallback "Unknown Repo"; shared with the tree path — `agents_live.ex`'s versions are thin delegates). The layout internals live in the `commit_graph/` submodule dir: `CommitGraph.Interleave` (topological layers, the global row order, lanes, no-op stubs) and `CommitGraph.Edges` (edge derivation), sharing three total shape readers exposed on the parent (`parents_list/1`, `sha_or_nil/1`, `stringify/1`). `build(raw_by_repo, agents)` returns one `repo_view` per repository group sorted by `{repo_name, repo_dom_id}`, where each raw repo map is `%{commits:, refs:, truncated:}` (the flag optional — read via a total `Map.get`, surfaced on the repo_view as `truncated`, non-`true` → `false`). **Nodes** — every ADDRESSABLE fetched commit (a map with a non-empty binary `:sha`, de-duplicated by sha) PLUS one synthesized `kind: :base` node per distinct agent `:base_commit` absent from the fetched commits PLUS one synthesized `kind: :noop` stub per no-op child agent; each node is `%{sha, short_sha, message, author_name, date, refs, row, column, depth, kind, owner_id, start_ids, end_ids}` (`kind` `:commit | :base | :noop`) where `short_sha` is the commit's `:short_sha` (else `String.slice(sha, 0, 8)`), `message` is the commit message's FIRST LINE (`""` for base/noop), `author_name` a binary or nil, `date` a `%DateTime{}` or nil, `refs` a list (else `[]`; always `[]` for base/noop), `row` the unique top → bottom position (rows exactly `0 .. node_count - 1`, so `row_count == node_count`), `column` the owner's LANE (0 for unowned), `depth` the owner's normalized depth, `owner_id` the owning agent's id (nil = unowned) and `start_ids`/`end_ids` the agent ids that fork from / tip at the sha (agent order; a node can be a start for one agent and an end for another; a noop stub is only ever an END of its child). **Rows — global interleaving** — every node carries a cycle-safe topological LAYER `L` over its PRESENT parents (parents that are nodes of this repo: `L = 0` with none, else `max(L(parent)) + 1`; memoized DFS with a `visiting` set so a malformed parent cycle terminates; synthesized base nodes join the walk as parentless pseudo commits so a child's oldest commit listing the fork as a parent keeps the fork row strictly above it); the global row order is ALL nodes sorted ascending `{L, date_unix, sha}` (missing date → 0) — `L` strictly increases along every edge, so parents sit above children and the fork point sits above the child's first row, while commits of PARALLEL AGENTS interleave by date instead of forming per-agent blocks (no per-agent contiguous grouping). **Lanes (one per agent)** — agents order in a DFS / SUBTREE-CONTIGUOUS walk: pre-order from the ROOTS (nil `parent_id`, or one matching no agent of the repo group — the same resolution rule the agent-level edges use), each root's children visited recursively in stable `{task_local_id, agent_id}` order (nil `task_local_id` sorts after every integer — deterministic; `agent_id` the final tie-break), so every parent's subtree occupies CONSECUTIVE lanes (children of different parents never interleave across the gutter — the `:spawn`/`:merge_back` connectors of one subtree do not weave through unrelated lanes); a malformed parent CYCLE cannot loop the walk (a visited set stops re-entry) and its members still get exactly one lane each (agents no root reaches are appended as fallback roots in the stable order); `depth` is NO LONGER an ordering key (it still drives the hue and ownership tie-breaks); every agent owns ONE lane = its index in that order, SHIFTED RIGHT BY 1 when the repo has ≥1 unowned node — lane 0 is then the NEUTRAL lane, holding pre-task/disconnected commits no agent claims (`owner_id: nil`) instead of misattributing them to the root agent; `node.column` = the owner's lane (0 for unowned); `column_count = max(max(node.column) + 1, max(agent.lane) + 1, 1)` so a lane owning no node still counts (its header chip renders). **Base synthesis** — the fetch is `git log base..tip`, which EXCLUDES the base commit, so a fork point no agent committed on has no fetched commit to hang an edge on; a fetched commit that equals some agent's `:base_commit` stays a NORMAL `:commit` node and is never duplicated. **No-op stubs** — a child agent whose progress path is EMPTY (forked but committed nothing — `current_commit` nil, equal to its base, or absent from the fetch) and whose parent resolves in the same repo group gets ONE `kind: :noop` stub node: `sha = "noop-" <> agent_key` (synthetic — never collides with a hex git sha), `start_ids: []`, `end_ids: [child_id]`, owned by the child, on the child's lane, at layer `fork layer + 1` (just below the fork); its agent-level edges hang off the stub. **Edges** — `%{from_sha, to_sha, from_column, from_row, to_column, to_row, kind, owner_id}` carrying both endpoints' `{lane, row}`; a VIRTUAL landing carries `to_sha: nil` with authoritative `to_column`/`to_row`. (1) COMMIT edges: for every real commit node and every one of its `:parents` present in the node set, `kind: :parent` for the FIRST present parent (first-parent lineage) and `:merge` for every other present parent; `owner_id` is the CHILD node's owner; absent parents produce no edge; identical `{from_sha, to_sha}` pairs de-duplicated; DROP RULE — any commit edge whose UNORDERED sha pair equals an agent-level edge's unordered pair is dropped (the agent-level edge replaces it visually: the child's oldest→fork `:parent` yields to the dashed `:spawn`, the fast-forward continuation→tip `:parent` yields to the `:merge_back`). (2) AGENT-LEVEL edges, per child agent C whose parent agent P resolves in the same repo group (`P.id == C.parent_id`; unresolvable → none): `:spawn` — dashed branch-out from the fork node (`C.base_commit`, a fetched commit or the synthesized `:base` node; skipped when the base is nil/non-binary) to C's OLDEST progress-path commit (or its noop stub), `owner_id` = C (child-colored stroke); `:merge_back` — dashed return of C's tip (the node whose sha is `C.current_commit`, or the stub when the path is empty) into P's lane, targeting the TOPMOST (min-row) P-owned node strictly BELOW the source row, else a VIRTUAL landing (`to_sha: nil`, `to_column` = P's lane, `to_row` = the source's own row — the renderer's endpoint fallback consumes the column/row fields); a REAL merge (a parent-lane commit listing the child tip among its 2nd+ parents) is already drawn by the dashed `:merge` edge, so no `:merge_back` duplicates it. Sorting: commit edges by `{from_sha, to_sha}`, agent edges by `{kind, owner_key (owner id stringified), from_sha, to_sha}`, `edges` = commit edges ++ agent edges. **`agents`** — one entry per agent in the SAME DFS subtree-contiguous lane-assignment order (see "Lanes"): `%{agent_id, task_local_id, status, depth (normalized), lane, parent_id, color (depth hue), start_sha, end_sha, ended}` where `lane` is the agent's gutter lane, `parent_id` the RAW parent agent id from the input map (nil for roots), `start_sha`/`end_sha` are the agent's `:base_commit`/`:current_commit` and `ended` = `Map.get(agent, :ended) == true` (retained in-session agents). No per-agent row band / `lane_count` / `max_x` / per-node `x`/`y` (the node/edge `row`/`column` fields are the grid, and the key sets are test-pinned). **Ownership** — a commit on at least one agent's progress path belongs to the agent with the MAXIMUM depth (ties broken by the SMALLEST agent-order index); a fetched commit on NO path (a merged-in side commit) inherits the owner of the commit it is the FIRST parent of — the deepest such OWNED child, ties by smallest agent-order index — and when NO owned child claims it the commit is UNOWNED (`owner_id: nil`, neutral lane 0), resolved in DESCENDING layer order so children are owned before their parents; a synthesized base node belongs to the agent with the SMALLEST `{depth, index}` forked from it (a shared task base lands in the shallowest root lane); a noop stub belongs to its child by construction. A repo without agents has no owners and therefore no nodes, edges or agents. **Progress path** — a first-parent walk from the agent's `current_commit` backwards, stopping WITHOUT collecting at a non-binary sha, at `base_commit`, at an already-seen sha (cycle guard), or at a sha absent from the fetched graph; the walk yields NEWEST → OLDEST. **Depth→hue formula (verbatim)**: `color(depth) = EvoDashWeb.ThemeColor.hsl_to_hex(hue, 70, 54)` where `hue = Integer.mod(round(depth * 137.508) + 265, 360)` — golden-angle step 137.508° per depth level (deterministic, maximally spread hues), +265° offset so depth 0 lands on blue-violet and common shallow depths stay away from the status colors (red/green/amber), saturation 70 / lightness 54 identical to `ThemeColor`'s project accents; reuses the public `ThemeColor.hsl_to_hex/3` (no local HSL reimplementation); non-integer/nil/negative depth → 0. **Output shape**: `%{repo_key, repo_dom_id, repo_name, node_count, edge_count, row_count, column_count, truncated, nodes, edges, agents}` with `row_count == node_count`; `truncated` is the raw repo map's `truncated` flag surfaced verbatim (a total `Map.get` read — absent/non-true → `false`; present on empty-body repo views too); `nodes` sort by ascending `row`, `edges` commit-then-agent as above, `agents` in the DFS subtree-contiguous lane order and repos by `{repo_name, repo_dom_id}` — all deterministic, so LiveView patches the graph incrementally; `repo_dom_id` is the unchanged stable DOM id. The module emits NO render/DOM concerns — no DOM ids beyond `repo_dom_id`, no colors beyond `agent.color`, no SVG geometry. Total: defensive `Map.get/2` reads, non-map/garbage input degrades to empty nodes/edges/agents, never raises, no try/rescue. |
| `ToolCallDisplay` | Pure rendering contract for tool-call messages in the chat history viewer (inline detail panel + full-message modal). `display/1` and `display/2` (opts `mode: :compact` — the default — or `:full`) return the same shape either way: `%{label, kind: :structured, rows}` for subagent (`subagent_*` prefix — the alias spellings `task`/`subagent` normalize into it) and shell (ANY accepted spelling of the platform shell tool, via the alias-aware `EvoDashWeb.Helpers.tool_call_is_shell?/1`) calls — key/value rows (path + objective / command) — or `%{label, kind: :inline, summary}` for all other calls (one-line arguments summary). The tool key is resolved ONCE through the core alias spine `EvoGit.Agent.ToolNames.normalize/1` (case-insensitive; a name the spine does not know — a custom tool — passes through UNCHANGED) and is what `:label` carries for both the grouping test and the inline label, so the model-facing names render exactly like the historical internal ones (`read`→`read_file`, `edit`→`edit_file`, `write`→`write_file`, `web_search`→`search_web`), `rg`/`glob` are untouched, and shell calls label "Shell call" (a shell call made with `run_in_background: true` labels "Background shell call" and additionally carries `variant: :background_shell` — the ONLY descriptor with a `:variant` key, see "Background shell calls carry a `:variant`" below). `:compact` caps the objective/command rows at 200 chars and the summary at 160 chars (trailing `…`); `:full` returns the complete strings uncut. Height-constrained at BOTH render sites: the compact inline detail panel (chat-history list) renders `display/1` — structured blocks in a `max-h-12` + `overflow-y-auto` container, the inline summary one line with CSS ellipsis; the full-message modal ("zoom-in" view) renders `display(call, mode: :full)` inside scrollable `max-h-[60vh] overflow-y-auto` regions, with the inline summary wrapping (`whitespace-pre-wrap`) instead of ellipsizing. Raw arguments JSON is never dumped for subagent/shell calls. |
| `LoadData` | Data loading for the Agents page, extracted so it runs inside `EvoDash.TaskSupervisor` children (never in the LiveView process — cross-node RPCs never block the page). `load/2` = page load: agent summaries + `config_status` (layout banner) + a refreshed threshold cache → `{:ok, %{agents:, config_status:, threshold_cache:}}`. `refresh/2` = broadcast-triggered refresh path: agent summaries + threshold cache → `{agents, cache}` (no config_status). `find_children_from_agents/2` computes `{agent_id, status}` children from `parent_id` (public — AgentsLive's in-memory incremental paths reuse it). Builds the rich agent maps from `RemoteAPI.list_agents/0` summaries, carrying `:message_count` through as an informational field. Each agent map's `compression_threshold` prefers the summary's own value (else the node-level threshold via `ThresholdCache.threshold_for_agent/2`), and `compression_pct` derives from that effective denominator (still rendered as the legacy `count (pct%)` label). Each agent map also carries `context_window` — the OPTIONAL summary key `:context_window` (atom or string key, POSITIVE INTEGER only; absent/null/0/negative/non-integer → the core default 200_000) read through the single shared `ContextMeter.context_window_from/1`, which is the Context tile's full-bar width. Env seams resolved at call time (inside the tasks): `:agents_list_runner` (default `&EvoDash.NodeContext.list_agents/1`), `:agents_config_runner` (default `&EvoDash.NodeContext.get_resolved_config/1`). |
| `ThresholdCache` | Per-node cache for the LLM compression threshold consumed by the Context meter's tick and by the per-agent `compression_pct` label. The node-level threshold lives at `[:llm, :compression_threshold_tokens]` in the FULL resolved config (`EvoGit.Config.resolve/0`) — the scheduler config (`get_remote_config/1`) has NO `:llm` section, which was the old remote-branch bug. The setting is OPTIONAL in the core (nil = derived per model from its context window), so `threshold_from_config/1` is total: missing key / nil / non-positive / non-integer (or a non-map result) → `default_threshold/0` (180_000), never a crash. `threshold_for_agent/2` prefers an agent summary's OWN `compression_threshold` when it is a positive integer (defensive atom- OR string-key read; absent/nil/non-integer → the node-level fallback), which is the denominator of the per-agent `compression_pct` label. Cache shape `{node, threshold, fetched_at_monotonic}` (nil = empty); `read/3` (fresh within 30s) / `put/4` / `fetch/3` (cache miss → node-aware runner via the `:agents_config_runner` seam, resolved at call time) / `default_threshold/0`. The fetch runs ONLY inside the async load/refresh tasks — never in a `handle_info`/`handle_event`. |
| `ContextMeter` | Pure, TOTAL geometry + label derivation for the detail panel's Context tile (no I/O, no processes, no try/rescue, never raises). `build/1` takes an agent map (or summary map — atom OR string keys, any missing/garbage field degrades) and returns `%{fill_pct, fill_label, tick_pct, tick_label, zone, fill_class, tick_class, current_tokens, threshold_tokens, window_tokens, compression_count}`. The bar's full width is the CONTEXT WINDOW (`context_window_from/1`: `:context_window`/`"context_window"` positive integer, else `default_context_window/0` = 200_000); the fill is the agent's CURRENT context (`:total_tokens`, nil/negative/non-integer → 0) and the tick marks the compression THRESHOLD (`:compression_threshold`, nil/non-positive/non-integer → `tick_pct`/`tick_label` nil = tick hidden). **Rounding contract**: every percentage is rounded to EXACTLY one decimal via `Float.round/2` and rendered by `:erlang.float_to_binary(_, decimals: 1)` — always one decimal place (`"0.0"`, `"63.1"`, `"100.0"`), clamped to 0..100, and the numeric `fill_pct`/`tick_pct` derive from the SAME rounded float as `fill_label`/`tick_label`, so a CSS width and a `data-*` attribute can never disagree. **Zones** (current vs THRESHOLD, integer math — `current * 5 < threshold * 4` is exactly `< 80%`): `< 80%` → `:success`, `< 100%` → `:warning`, `>= 100%` → `:error`; an unknown threshold → `:success`. `fill_class/1` → `bg-success`/`bg-warning`/`bg-error`; `tick_class/0` → `bg-base-content` (contrasting theme token, never a color literal). The module carries no user-facing prose — the tick's tooltip is built in the template with gettext. |
| `PendingEvents` | Pure bookkeeping for the Agents page's agent-event coalescing buffer (no socket, no process, no I/O). `flush_ms/0` = the trailing-edge window (300ms, shared with the debounce). `new/0` = empty buffer. `append/2` prepends the raw event (newest-first, O(1)). `should_schedule?/1` = `not scheduled?` — only the first event of a window arms the flush timer. `drain/1` = `Enum.reverse/1` (restores strict arrival order). The buffer is a plain list stored in the `:pending_agent_events` assign; the socket-mutating merge/flush logic stays in `agents_live.ex`. |
| `CommitGraphRefresh` | Pure fetch-result folding + commit-relevance fingerprinting for the temporal view (no socket, no process, no I/O; invoked from INSIDE the TaskSupervisor fetch child / the LiveView's refresh helpers). **`fetch_result/3`** folds the per-group runner calls with PARTIAL-SUCCESS semantics: ONE `runner.(node, task_id, repo_key, live_tips, limit: 100)` per group; any reply other than `{:ok, %{commits: list}}` drops only THAT group (recorded as a `{:commit_graph_repo_failed, {repo_key, task_id}, reply}` failure) while the remaining groups still fold — `{:ok, raw_by_repo}` when ≥1 group succeeded (groups sharing a `repo_key` UNIONED via `merge_repo_graph/5`), `{:error, last_failure}` only when EVERY group failed (the reduce PREPENDS failures so the head is the LAST failing group's — a single-group page keeps the exact former halt shape; the reason is display-only, either failure renders the same strip). Each successful reply's `truncated` flag (the core `EvoGit.CommitGraph.for_task/4` marker that a tip range was cut at the limit; absent → `false`, garbage → `false`) rides along and is OR-unioned into the merged repo entry. `limit/0` = the per-group cap (100) — the single source; `merge_repo_graph/5` (the arity-4 form remains as a backward-compatible delegate writing `false`) is total (commits de-duped by `:sha`, non-map entries dropped, malformed refs degrade, `truncated` OR-unioned and ALWAYS written as an explicit boolean). **`fingerprint/1`** = the order-insensitive commit-relevance digest of the temporal view's agent set — a MapSet of `{id, repo_root \|\| repo_id, task_id, task_local_id, depth, parent_id, base_commit, current_commit, ended}` tuples covering exactly what `CommitGraph.build/2` + the fetch grouping read; `status`/tokens/usage/message-count/objective are deliberately EXCLUDED (the view never reads them), so an unchanged fingerprint means a flush was commit-irrelevant and BOTH the rebuild and the git-RPC refetch can be skipped. |

## Constraints

- Pure functions — no I/O, no socket, no process calls (`ToolCallDisplay`, `PendingEvents`; `ThresholdCache.read/3`/`put/4`/`threshold_from_config/1`/`threshold_for_agent/2`/`default_threshold/0` are pure). The model-label derivation is the shared `EvoDashWeb.ModelLabel` (`../../model_label.ex`), also pure. Deliberate exceptions: `LoadData` and `ThresholdCache.fetch/3` perform I/O (NodeContext RPCs via the env-seam runners) — they are designed to run inside `EvoDash.TaskSupervisor` children, never in the LiveView process.
- No `try/rescue` — defensive extraction + pattern matching/`case` only (project-wide anti-pattern policy). The exit-safe boundary lives in `agents_live.ex`'s spawn functions (`start_async_load/1` / `spawn_agents_refresh/1` / `spawn_commit_graph_fetch/1`), which call `EvoDash.SafeCall.run/1` (an EXIT from a `GenServer.call` timeout / dead target becomes an error VALUE) instead of wrapping the call in `try/rescue`.
- Reuses `EvoDashWeb.Helpers` defensive extraction (`tool_call_name/1`, `tool_call_arguments/1`, `tool_call_is_shell?/1`) — do not reimplement; `EvoDashWeb.Helpers.tool_call_display/1` is not used by the Agents page; it stays as a public, test-pinned helper (do not remove it).
- New user-facing strings use `gettext` (backend `EvoDashWeb.Gettext`); `Path`/`Objective`/`Command` entries appear in the POT/PO at release-time extraction only — do not run `mix gettext.extract`/`merge`/`translate` during development.

## Async Load & Exit-Safety Contract

No AgentsLive render path (mount / `handle_params/3` / `handle_event/3` / `handle_info/2`) blocks on a store, scheduler or cross-node RPC call: every such read runs in an `EvoDash.TaskSupervisor` child and reports back as a tagged message.
The initial page load is spawned by `handle_params/3` ONLY on the connected mount (`if connected?(socket), do: start_async_load(socket), else: socket`) — the dead render paints the shell (`@agents_loading` seeds `true` in `mount/3`) and never spawns a load whose result would be sent to a dying process.
Every spawned loader calls its loader/runner through `EvoDash.SafeCall.run/1` INSIDE the task body, so a `GenServer.call` timeout or a dead target (an EXIT, which `rescue` cannot catch) is captured as an error value and the result message is ALWAYS sent — no task can die silently and wedge a loading flag.
Result message shapes (unchanged): `{:agents_data_loaded, node, gen, result}`, `{:agents_refresh_result, seq, node, result}`, `{:commit_graph_loaded, node, seq, result}`; `result` is `{:ok, ...}` or `{:error, reason}`.
Each result is stale-guarded on its monotonic counter (`@load_generation` / `@refresh_seq` / `@commit_graph_seq`) AND the viewed node.
The loader seams (`:agents_list_runner` / `:agents_config_runner` via `LoadData`, `:agents_commit_graph_runner`) are resolved AT SPAWN TIME inside the task, so tests can stub them.
`ThresholdCache.fetch/3` runs ONLY inside those spawned tasks (never in the LiveView process) and has no flag of its own to wedge.
Every loading/error assign clears on its result path: `@agents_loading` + `@agents_error` (page load), `@commit_graph_loading` + `@commit_graph_error` (commit-graph fetch).
A failed page load keeps the last good tree, clears `@agents_loading` and records `@agents_error`, which the template renders as a compact inline banner (`#agents-load-error`, `rounded-lg border border-error/30 bg-error/5`) with a Retry button (`#agents-load-retry`, `phx-click="retry_agents_load"`).
`retry_agents_load` clears `@agents_error` and re-runs `start_async_load/1`; there is NO polling and NO auto-retry timer, and `@agents_error` is cleared whenever a load starts, on any successful load, and on a node switch.

## Left-Panel View Switcher & Commit-History (Temporal) View

The left panel renders EITHER the spatial agent tree OR the temporal git-commit graph, switched by a segmented control in the panel header (two `phx-click="switch_left_view"` buttons, `id="left-view-tree"` / `id="left-view-commits"`, each carrying `phx-value-view="tree"|"commits"`).
The active view is the `:left_view` assign (`:tree | :commits`, default `:tree` in `mount/3`).
`switch_left_view` whitelists the view by PATTERN MATCHING the two literal binaries — any other value falls through to a no-op clause (no atom conversion, no `String.to_atom`).
Switching to `:commits` triggers an immediate force-refresh commit-graph load; switching back to `:tree` renders the tree and never touches the git RPC.
`:left_view` SURVIVES a node switch (it is a user preference) and is NOT in the `handle_params/3` reset branch, while the commit-graph DATA is per-node and IS reset there.
The tree view (and its `"Agent Tree"` label) stays the default, so the agent tree, right-hand detail panel and status legend chips are behaviourally unchanged.

### Commit-graph async contract

- Assigns (seeded in `mount/3`; the data assigns are reset on a node switch): `@left_view`, `@commit_graph` (built `[repo_view]`), `@commit_graph_raw` (`%{repo_key => %{commits:, refs:, truncated:}}`), `@commit_graph_loaded`, `@commit_graph_loading`, `@commit_graph_error`, `@commit_graph_seq` (monotonic — NEVER reset, mirrors `@refresh_seq`), `@commit_graph_fingerprint` (the `CommitGraphRefresh.fingerprint/1` of the agent set the LAST build consumed; nil until the first build/fetch), `@commit_graph_fetched_at` (monotonic ms of the last fetch), `@commit_graph_tick_scheduled` (one-shot-tick guard), `@retained_agents` (`%{agent_id => agent_map}` — in-session RETAINED ended agents; RESET to `%{}` on a node switch alongside the other per-node commit-graph data).
- `maybe_load_commit_graph/2` is a NO-OP unless `@left_view == :commits` — the tree view never triggers a git RPC.
- **Fingerprint gate (commit-relevance)**: on a NON-forced call (an agent-event flush / refresh result path; a call is forced when `force: true` OR the graph is not yet loaded) the agent set's commit-relevance fingerprint (`CommitGraphRefresh.fingerprint/1` over `commit_graph_agents/1`) is compared against `@commit_graph_fingerprint`; an UNCHANGED, non-empty fingerprint skips BOTH the rebuild and the refetch spawn entirely (a status/token/usage/message-count-only flush costs nothing). A CHANGED (or still-nil) fingerprint rebuilds + refetches as before and stores the new one. Bypasses: `force: true` (first activation, the one-shot tick, a view re-switch) and the initial load never compare; a fetch already in flight (`@commit_graph_loading`) also bypasses the gate — its result applies through `{:commit_graph_loaded, ...}` and re-stores the fingerprint of the agent set it built from, so an in-flight fetch always converges and a SUCCESSFUL fetch yielding an identical raw map CANNOT loop (the next flush compares equal and skips). SELECTION (`select_agent`) needs neither a rebuild nor a refetch — selection is renderer-side only: the view model's `start_ids`/`end_ids` are computed for EVERY agent at build time and the renderer derives its markers/readout from `selected_id` at render time, so no path reloads the graph on selection.
- It first rebuilds `@commit_graph` from `@commit_graph_raw` + the MERGED agent set (`rebuild_commit_graph/3`), so a newly-spawned child's own lane and its nodes appear immediately without a fetch; the rebuild stores the fingerprint of the agent set it built from.
- **`commit_graph_agents/1` is the ONE agent set the TEMPORAL view is built from**: `@agents` (LIVE) MERGED with `Map.values(@retained_agents)` (ended, retained in-session), de-duplicated by `id` with the LIVE copy winning. It feeds BOTH `commit_graph_groups/1` AND `CommitGraph.build/2` — i.e. `rebuild_commit_graph/3` AND the `{:commit_graph_loaded, ...}` success branch. The agent TREE still renders `@agents` only (retained agents never appear there).
- `commit_graph_groups/1` groups eligible agents (`repo_root`, `base_commit`, `current_commit`, `task_id` all binaries) by `{repo_key, task_id}` (repo_key = `repo_root`) and carries per group `%{repo_key:, task_id:, live_tips:}` where `live_tips` = the de-duplicated `current_commit`s of the group's NON-ended agents only (a retained/ended agent contributes its agent entry but never a tip — its commits are already in the task's durable ref ancestry). Sorted by `{repo_key, task_id}` for deterministic task input; an empty group list marks the view loaded with an empty graph.
- `spawn_commit_graph_fetch/1` runs in an `EvoDash.TaskSupervisor` child (never the LiveView process), calls the runner ONCE per `{repo_key, task_id}` group through `CommitGraphRefresh.fetch_result/3` (the per-group limit — `limit: 100` — is `CommitGraphRefresh.limit/0`, the single source) and sends `{:commit_graph_loaded, node, seq, result}` where `result = {:ok, raw_by_repo} | {:error, reason}`.
- **PARTIAL SUCCESS — one failing group no longer blanks the view** (`CommitGraphRefresh.fetch_result/3`): a reply other than `{:ok, %{commits: list}}` drops only THAT group's data; the remaining groups still fold into `raw_by_repo`, so a page with several repos/tasks renders the SUCCESSFUL groups when a single git RPC fails (a failed group's repo still shows its lanes/START-END from the agent set — only its commits stop at the last fetch). `{:error, reason}` is sent ONLY when EVERY group failed, carrying the LAST failing group's `{:commit_graph_repo_failed, {repo_key, task_id}, reply}` (the reduce PREPENDS failures, so the head is the most recently processed group; display-only — either failure renders the same strip) — for a single-group page that is exactly the former halt shape, so the renderer's error strip (first load) / stale-warning strip (after a load) semantics are unchanged.
- **`raw_by_repo` is keyed by `repo_key`** (REQUIRED by the assembler, which groups agents by `repo_root || repo_id`): groups sharing a `repo_key` (two tasks in one repo) are UNIONED via `CommitGraphRefresh.merge_repo_graph/5` — `commits` de-duped by `:sha` (non-map entries dropped), the `refs` name lists unioned per sha, and each reply's `truncated` flag OR-unioned (total; the merged entry always carries an explicit boolean).
- The runner seam is `:agents_commit_graph_runner` (arity 5, default `&EvoDash.NodeContext.list_task_commit_graph/5` — the durable TASK-SCOPED core RPC), resolved AT SPAWN TIME so tests can stub it; the spawn wraps `CommitGraphRefresh.fetch_result/3` in `EvoDash.SafeCall.run/1` (an EXIT becomes `{:error, :commit_graph_fetch_failed}`, a folded per-group `{:error, failure}` passes through verbatim) so the result message is always sent and the view never wedges on a spinner.
- The `{:commit_graph_loaded, ...}` result is stale-guarded on the viewed node AND the monotonic seq; a stale node/seq is dropped, `{:ok, raw_by_repo}` builds + assigns the graph from `commit_graph_agents/1` (clearing loading/error AND re-storing `@commit_graph_fingerprint` for the agent set it built from), `{:error, reason}` only clears loading and records the error (the last good `@commit_graph` stays rendered).
- Throttling: a refetch is skipped when `@commit_graph_fetched_at` is within the minimum interval (1000ms, read AT CALL TIME through the private `commit_graph_min_interval_ms/0` helper using the app-env seam `:agents_live_commit_graph_tick_ms`, default 1000 — the SAME helper feeds `schedule_commit_graph_tick/1` so the throttle window and the armed tick delay can never diverge); a throttled request arms ONE one-shot `:commit_graph_tick` (never a repeating poll — `@commit_graph_tick_scheduled` guarantees one timer per window) whose handler re-attempts with `force: true` (bypassing BOTH the throttle AND the fingerprint gate, so a throttled commit-relevant change always lands).
- Refresh triggers: `apply_agents_result/2` (async load + broadcast refresh result path) and the end of `handle_info(:flush_agent_events, ...)` (a burst of agent commits extends the timeline — new nodes/edges, re-laid-out rows) both end with `maybe_load_commit_graph(socket, [])`; first activation / the tick use `force: true`.
- **Base-node de-duplication relies on the assembler**: the task-scoped fetch INCLUDES the real base commit as its own node, and `CommitGraph.base_shas/2` already suppresses a synthesized `kind: :base` node whenever the sha IS present in the fetched commits — so a fetched commit equal to an agent `base_commit` renders as a NORMAL `:commit` node and is NEVER duplicated by a synthesized base. Do not add a second base node.
- **The per-group limit (100, `CommitGraphRefresh.limit/0`) cuts at the limit and is FLAGGED in the data layer**: the core `CommitGraph.for_task/4` returns `commits` capped at 100 per tip range plus a `truncated: boolean` flag (true when a tip range was cut), which `merge_repo_graph/5` OR-unions across the groups sharing a repo_key and `CommitGraph.build/2` surfaces on the repo_view (`repo_view.truncated`) — the DATA layer therefore knows whether more commits exist, but the renderer does not yet render a "+N more" indicator, so a long-running task's older commits still just stop appearing.

### Retained ended agents (in-session)

The core DELETES an agent's ETS rows (and its `evogit-agent-*` branch) when it recycles it, so without retention a finished agent would vanish from the TEMPORAL view and take its lane of rows plus its START/END markers with it. `@retained_agents` (`%{agent_id => agent_map}`) is the in-session remedy — committed agents only, NOT a durable store (the core persists no per-agent commit attribution, so retention does NOT survive a page reload).

- A retained entry is the agent's full last-known map with `ended: true` added (`Map.put(agent, :ended, true)`), preserving `id, task_local_id, task_id, repo_id, repo_root, depth, status, base_commit, current_commit, usage, ...`.
- `apply_agent_removed/2` (`{:agent_removed, id, node}` flush) captures the removed row into `@retained_agents` instead of only dropping it, and KEEPS `selected_agent_id` pointing at it (the graph's START/END annotation must persist; the right-hand detail panel renders its natural "Agent not found" empty state). The rest of the cleanup is unchanged (removed from `@agents` — the tree — children orphaned to `parent_id: nil`, parent's children refreshed, tracking sets/`repo_trees` cleaned).
- `apply_agents_result/2` (full refresh): any id present in `@agents` or `@retained_agents` but ABSENT from the fresh list is moved into `@retained_agents` marked `ended: true` (`retain_absent_agents/3`); any id present in the fresh list is DROPPED from `@retained_agents` (a live agent supersedes its retained copy). Nothing is mass-retained on the first apply / after a node switch (both lists are empty then).
- `merge_registered_agent/2` (re-registration) deletes the id from `@retained_agents` — a live agent supersedes its retained copy.
- `CommitGraph.build/2` reports the flag as `ended` on the entry in the `agents` list; retention contributes agent entries and grouping (a group whose agents ALL ended still gets fetched — with empty `live_tips` — so the whole task is recovered from its durable refs) but never tips.

## Inspector RuntimeStream Reducer

`RuntimeStream` is a pure inspector reducer with `new/2`, `seed/3`, `apply_batch/4` and `active?/1`, independent of the Assistant transcript reducer.
Core snapshots and ordered activity events carry `%{phase: :idle | :llm_waiting | :llm | :llm_complete | :retry_wait | :tools, current_call: nil | %{id: binary, turn: integer, attempt: integer, text: binary, thinking: binary}}`.
Each activity event replaces the WHOLE current-call projection, including full accumulated text/thinking; ordinary text/thinking chunks append only to an existing call.
Core captures current-call content even without watchers, so a mid-call snapshot proves complete source capture when both text and thinking are explicit binaries, without invented coverage flags or message-start events.
The reducer stores the authoritative phase in `state.activity` and bounded content in `state.projections`, avoiding an unbounded duplicate of the producer's activity map.
Only the current call is retained, with `%{identity: %{id: id}, turn:, attempt:, message_index:, response:, thinking:, tool_calls:, complete:, generation_complete:, capture_coverage:, chunks_seen:, omitted_response_bytes:, omitted_thinking_bytes:, omitted_tools:}`.
Same-id replacement preserves tool descriptors and the local DOM ordinal, while a fresh attempt id replaces all old content and tools and advances that ordinal even after retirement.
`current_call: nil` retires all excerpts and tools, including aborted retries and checkpointed calls; subsequent chunks, accounting, yield and tool announcements cannot resurrect them.
Generation completion follows only `:llm_complete` or `:tools`, never turn accounting, yield, retry, failure or lifecycle finish.
Yield updates lifecycle/status to `:awaiting_input` without treating its checkpoint response text as another live replacement, and finish freezes later events without asserting successful generation.
`active?/1` means only a nonterminal running/cancelling lifecycle and is not a model/tool execution guess.
Seed preserves agent/node ownership and raw checkpoint messages, rejects an explicitly foreign agent, and uses an explicit nonnegative seq before the embedded seq before zero.
Atomic reseeding preserves the local DOM ordinal and valid same-call tool descriptors, but replaces response/thinking from the snapshot's complete prefix rather than appending it.
An admitted snapshot with missing, malformed or empty activity clears all stale live projections, response, thinking and tools while preserving the monotonic local DOM ordinal.
Explicit `current_call: nil` retirement likewise clears the live projection, and later orphaned chunks cannot resurrect it.
`current_call_id/1` reads only the live call id and `checkpoint_transition?/2` scans every ordered activity replacement in a batch for retirement or replacement of an existing call, even when a later event starts another call in the same batch.
Batch admission rejects stale/invalid seq, foreign agent and post-finish events, while unknown events are inert and an accepted newer batch still advances the watermark.
Snapshot admission, node guards and watch-generation guards belong to StreamWatch rather than this reducer.
The obsolete top-level in-flight, message-start, flattened activity identity and caller-owned capture-coverage protocols are not consumed.
No checkpoint-message identity reader or content/turn/index-based suppression API is exposed.
`StreamLimits` exposes the existing upper budgets of 12 projections, 48_000 bytes independently per response/thinking prefix, 20 tool descriptors and 1_024 bytes per tool name; the current-call policy is tighter at one projection.
UTF-8-safe prefix slices are copied, and bounded appends never concatenate an unbounded incoming chunk first.
Once bytes are omitted, later chunks are counted rather than inserted after a missing UTF-8 boundary; an authoritative replacement recomputes missing bytes from its full value rather than double-counting retransmitted omissions.
Tool retention keeps the first 20 descriptors, counts later unretained announcements and upgrades matching anonymous announcements when dispatch supplies ids.
Tool results still update retained descriptors, names carry exact byte omissions and tool announcements never imply execution.
Checkpoint messages and opaque protocol identities are not truncated by the excerpt policy, and no raw history text is extracted by this reducer.

## Inspector StreamWatch Lifecycle
`StreamWatch.attach(socket, agent_id)` subscribes in the connected LiveView process and asynchronously registers that same LiveView pid through one serialized, consumer-monitored worker.
Forward `{:inspector_stream_ready, node, token, agent_id, result}` to `StreamWatch.ready/5` and `{:agent_delta, agent_id, seq, events}` to `StreamWatch.push/4`, then render `socket.assigns.inspector_stream.state` as the `RuntimeStream` projection.
`active?/2` includes initial snapshot-pending and reconciling watches and excludes errors, allowing the page to suppress independent whole-history reads while watched.
The rendered checkpoint source is exclusively `inspector_stream.state.messages`, atomically seeded with live activity from `inspector_stream.snapshot`.
`reconcile/1` coalesces explicit refreshes while a request is outstanding and retains the old coherent checkpoint/live pair while buffering every newer delta.
A batch retiring or replacing the existing current call automatically starts reconciliation BEFORE applying any event in that batch, so checkpoint adoption never mixes with an obsolete live excerpt.
Forward `{:inspector_stream_reconciled, node, token, agent_id, request, result}` to `reconciled/6`, whose guards require the viewed node, watch token, agent id and current outstanding request.
Reconciliation reuses the SAME idempotent watcher-registration runner and serial worker without unregistering between snapshots, preserving the live subscription.
An admitted snapshot replaces checkpoint messages and activity together, and buffered batches replay only above its authoritative sequence.
Replay crossing another ownership boundary freezes that entire batch and starts another coalesced snapshot request rather than rendering an inconsistent pair.
The stream fields `snapshot_request`, `reconciling` and `required_seq` distinguish the outstanding request and its minimum watermark from the rendered `seq`.
A snapshot before its triggering boundary, RPC failure or buffer overflow visibly fails the watch while preserving the last coherent rendered pair and requires explicit reattachment; there are no automatic error retries.
`StreamWatch.detach/1` clears the render state and consumer-local subscription immediately, with asynchronous serialized unregister on selection, node or lifecycle teardown.
Keep `inspector_stream_token`, private `inspector_stream_worker` and `inspector_stream_worker_monitor` bookkeeping across page resets, since tokens must remain monotonic and the same worker orders rapid A-to-B-to-A registration changes.
Forward worker `{:DOWN, ref, :process, pid, reason}` messages to `StreamWatch.down/4` after handling other page-owned monitors; matching death explicitly fails the watch, unsubscribes and allows a retry while unrelated monitors are inert.
Pending remote contexts cannot attach locally, readiness and push application require the current viewed node, negative sequence watermarks are rejected, and a snapshot explicitly naming another agent fails the watch.
Initial attachment and reconciliation deltas buffer up to 128 ordered batches or 1 MiB, duplicate/stale batches consume no capacity, and overflow or supervisor-start failures produce explicit watch errors instead of silent loss or stuck loading.
Runner seams are `:agents_watch_runner` and `:agents_unwatch_runner`, both `(node, agent_id, liveview_pid)`, defaulting to the corresponding `NodeContext` watcher functions.
The worker performs RPC through `SafeCall`, cleans up after consumer death, and uses no polling; delta messages have no publisher-node stamp.
`StreamWatch.closed/4` admits the direct `{:agent_stream_closed, agent_id, snapshot, seq}` terminal handoff atomically, including after a finished delta, summary removal or failed async snapshot request.
Admission requires a `Snapshot` with matching agent, `phase: :done` and embedded sequence, selected-agent/current-token/target-id/viewed-node ownership, and a sequence at least as new as the rendered, required and buffered watermarks.
The final handoff replaces checkpoint messages and activity together, clears pending buffers/errors, unsubscribes live deltas and seals the pair against late ready/reconciled failures, worker death and deltas without replaying older buffered events.
`RuntimeStream.seed/3` treats `:done` as terminal and preserves the snapshot's terminal status when present.
`StreamWatch.owns?/2` includes selected pending, failed and terminal watches, while `terminal?/2` means an admitted final handoff and `active?/2` excludes that sealed watch.
A same-target attach preserves a sealed watch, and only explicit selection/node/lifecycle teardown should detach it.
The parent must retain the selected watch across summary removal or absence, forward the handoff to `closed/4`, project its checkpoint in the same callback and use the retained ended agent row to keep the selected detail panel visible.
No handoff can recover a watch already explicitly detached, and retained terminal history remains page-local rather than durable.

`StreamPresentation.build/1` applies a second render cap of 12_000 graphemes per response/thinking part and at most 20 tools without mutating the reducer or checkpoint history.
The public max-message budget remains 12, but production state contains only the current call and retirement removes its article.
Grapheme omission fields describe render-stage loss, while byte omission fields sum reducer and render loss without counting full replacements twice.
Activity labels cover every core phase: generating, waiting for model capacity, response generated, waiting to retry, executing tools and idle; absent/unknown activity is unavailable.
`thinking_status/1` returns `:none` only for generation-complete, completely captured, empty, unomitted thinking, and StreamPanel renders exactly `gettext("No thinking content available")` for that case.
Missing thinking in malformed call data remains partial capture, and no lifecycle, accounting or caller-supplied flag upgrades it.
Checkpoint messages have no core call id or coverage watermark, and no checkpoint-part suppression predicate is exposed.
Atomic checkpoint/live ownership is established only by StreamWatch snapshot reconciliation, never fabricated row/turn/content matches.

Live excerpts are temporary current-call detail rather than a separate growing transcript or a lossless replay.

## Inspector Streaming Integration & Core Constraints

The parent page forwards ready, reconciled and delta messages through StreamWatch and projects the admitted state's raw messages into checkpoint rows in the SAME callback as the live-state update.
Support owns reconciliation requests, snapshot admission and bounded buffered replay, while the parent owns checkpoint-row rendering without speculative response/thinking suppression.
Watch tokens and serialized worker bookkeeping survive scope resets, and snapshot-pending, reconciling and failed watches own their checkpoint rows exclusively.
Independent history reads and late history results cannot overwrite a watched checkpoint/live pair, including a failed watch's last coherent pair.
Explicit watched history Retry and full-message refresh use StreamWatch.reconcile/1, while unwatchable agents retain the separately scoped independent history fallback.
The stable `agent-history-<id>` root uses `InspectorMessages`, with `data-inspector-scope` binding node/target/selection/watch/snapshot scope and stable `data-inspector-message` row markers without changing existing DOM ids.
Only newly keyed rows animate, reduced motion is respected and history scrolling stays instant.

Core transport and snapshot contracts live in `apps/evo_git/lib/evo_git/agent/stream/CONTEXT.md` and lifecycle/activity limitations in `apps/evo_git/lib/evo_git/agent/session/CONTEXT.md`.
The core snapshot includes session-owned `activity: %{phase:, current_call: nil | %{id:, turn:, attempt:, text:, thinking:}}`, and ordered `{:activity, projection}` events replace that projection while ordinary text/thinking events append to its current call.
The core snapshot atomically captures checkpoint `messages`, complete accumulated `activity` and its authoritative `seq`, and a completed current call remains available until atomic checkpoint retirement.
Core phases are `:idle`, `:llm_waiting`, `:llm`, `:llm_complete`, `:retry_wait` and `:tools`, and activity capture continues without watchers; watch and snapshot flush pending events before returning the authoritative sequence.
The inspector adopts `activity.current_call` from snapshots and replacements and appends only strictly newer chunks through the existing StreamWatch buffering/sequence admission.
Fresh core call ids separate retry attempts, and nil current-call retirement clears obsolete live excerpts without modifying raw checkpoint history.

## Inspector Protocol Boundaries

Tool-result/yield/finish events alone cannot replace the automatic retirement/replacement snapshot trigger.
Hand-built StreamWatch fixtures must include `snapshot_request: 0`, `reconciling: false` and `required_seq: 0`, preserve real snapshot agent ids, and account for duplicate/stale batches not consuming buffer capacity.
Activity fixtures use real nested `current_call` projections; synthetic `in_flight`, flattened activity identities, `message_start`, bare chunks without a current call and the removed `message_identity/1` API are not supported protocols.
All six core phases have truthful presentation labels, and successful empty-thinking notices require complete binary capture plus `:llm_complete` or `:tools`.
Current deltas expose text/thinking chunks and tool id/name/status but not tool arguments, result bodies or full history-message changes.
There is no checkpoint-message call identity or checkpoint-coverage watermark, so checkpoint suppression and historical excerpt reconciliation by guessed turn/content are unsupported.
The inspector uses its own bounded `RuntimeStream` reducer rather than the Assistant's bubble-oriented `Delta` reducer (`../home_live/CONTEXT.md`), and neither is a lossless history model.

## Agent Event Contract (push-based, node-identity, coalesced flush)

The Agents page is FULLY push-based — there is NO periodic poll.
The `:evo_git` emitters broadcast EXACTLY these four shapes on `EvoGit.PubSub` topic `"agents"`, every one carrying the BEAM node atom of the publisher.
Every event is node-filtered FIRST via `EvoDashWeb.LiveHooks.NodeAware.event_from_current_node?(socket.assigns, event_node)` (viewed node identity = `socket.assigns[:current_node]`; local → `node()`, remote → the remote daemon's BEAM node atom).
Foreign-node events are dropped BEFORE buffering — they never arm a flush and never leak into the viewed node's tree.
The three incremental events (`:agent_registered` / `:agent_updated` / `:agent_removed`) are COALESCED: each `handle_info` clause only buffers the raw event into the `:pending_agent_events` assign (`PendingEvents.append/2`, newest-first) and arms ONE trailing-edge timer (`Process.send_after(self(), :flush_agent_events, Application.get_env(:evo_dash, :agents_live_flush_ms, PendingEvents.flush_ms()))`).
The flush window is read **AT CALL TIME** at the `maybe_schedule_agent_flush/1` call site via the app-env seam `:agents_live_flush_ms` (production default = `PendingEvents.flush_ms/0` = 300ms) so tests can shrink it; `PendingEvents` itself stays a PURE constant-only module (no app-env reads) and the message name `:flush_agent_events` + the one-timer-per-window gating are unchanged.
The `:agent_flush_scheduled` boolean guarantees the timer is armed only by the FIRST event of a window — subsequent events just append to the existing buffer.
`{:agents_updated, node}` sets the coalesced `:pending_agents_refresh` boolean and arms the same timer — it never spawns a refresh per event.
`handle_info(:flush_agent_events, socket)` drains the buffer in ARRIVAL order (`PendingEvents.drain/1`), applies every event through the incremental merge paths below (threading the socket through each apply), and returns ONE `{:noreply, socket}`.
One flush therefore yields exactly ONE render/DOM diff for the whole burst — no LiveView mailbox starvation of user `phx-click`/`phx-submit` events, and no burst/blink when a backgrounded tab is foregrounded.
The buffer + `:agent_flush_scheduled` + `:pending_agents_refresh` are seeded in `mount/3` and RESET on the `handle_params/3` node-change branch (stale-node events never leak); a timer already in flight after a node switch is harmless — the buffer is empty, so the flush is a no-op.
The fallback refresh is COALESCED: a buffered `:agent_registered` with an incomplete summary, a buffered `:agent_updated` for an unknown id, and a `{:agents_updated, node}` all set the refresh flag, and the flush spawns AT MOST ONE `spawn_agents_refresh/1` (async full reload, seq-guarded via the monotonic `:refresh_seq` assign).
All heavy loads stay in `EvoDash.TaskSupervisor` children — never in `handle_info` (`start_async_load/1` / `spawn_agents_refresh/1` / `spawn_commit_graph_fetch/1` all run their calls through `EvoDash.SafeCall.run/1`; their stale-guards `{:agents_data_loaded, ...}` / `{:agents_refresh_result, ...}` / `{:commit_graph_loaded, ...}` are unchanged).

- `{:agents_updated, node}` — throttled bulk-change signal → node-match → sets the coalesced refresh flag → one `spawn_agents_refresh/1` per flush window; foreign → ignored.
- `{:agent_registered, id, summary, node}` — the event carries the agent's full summary (the same `RemoteAPI.list_agents/0` summary shape `LoadData.build_agents` consumes: `id, task_local_id, repo_id, repo_root, task_id, task_number, status, depth, parent_id, worktree, retries, agent_module, model_id, objective, context_path, current_commit, base_commit, usage, total_tokens, compression_count, compression_threshold, context_window, message_count`). Applied at flush time, merged IN-MEMORY for BOTH local and remote events through ONE shared path (`merge_registered_agent/3` → `build_registered_agent/2`): the row is built with the `LoadData` field mapping (defaults for absent fields, `usage` normalized to a `%Usage{}` struct), derived fields recomputed exactly like the load path (children/has_children from `parent_id`, the effective `compression_threshold` from `ThresholdCache.threshold_for_agent/2` — the summary's own value else `safe_compression_threshold/1` — `compression_pct` from `total_tokens` + that threshold, and `context_window` from `ContextMeter.context_window_from/1` — the OPTIONAL summary key, 200_000 when absent), inserted at the sorted `{depth, id}` position, the parent's children list refreshed, and `id_to_display`/`previous_agent_ids`/`new_agent_ids`/`repo_trees` updated. A duplicate id (race with the `{:agents_updated, node}` fallback) is a no-op; a summary missing the fields the tree needs (`status`/`depth`/`parent_id`) sets the coalesced refresh flag (one `spawn_agents_refresh/1` at flush end).
- `{:agent_updated, id, changed_fields, node}` — `changed_fields` NEVER contains `:context`. Applied at flush time, the in-memory merge runs for BOTH local and remote (special fields: `context_node` → `context_path`, `phylo_node` → `current_commit`, nil `usage` → zero, `compression_pct` recompute on `total_tokens` OR `compression_threshold` (a nil/non-positive threshold delta keeps the row's previous denominator, so a percentage can never divide by nil), `context_window` is NOT part of the delta contract (the merge keeps the row's value when the delta omits it, and a nil/non-positive delta value restores the previous known window — a known window is never reset to the 200_000 default), children recalc on `parent_id`, status-change tracking into `previous_statuses`/`changed_status_ids`, `id_to_display` on `task_local_id`, `repo_trees` rebuild on `context_node`/`repo_root`). A missing agent row (race) sets the coalesced refresh flag (one `spawn_agents_refresh/1` at flush end).
- `{:agent_removed, id, node}` — applied at flush time; the row is dropped in-memory (children orphaned to `parent_id: nil`, parent's children list refreshed, tracking sets/selection/repo_trees cleaned) for BOTH local and remote; foreign → ignored.

## Notes for Agents — Tool-call display layout contract

The Agents page chat history viewer renders tool-call messages (both the inline detail panel and the full-message modal) through `EvoDashWeb.AgentsLive.ToolCallDisplay.display/1` (aliased as `ToolCallDisplay` in `agents_live.ex`). Durable facts:

- **Return contract**: `display/1` and `display/2` return `%{label: String.t(), kind: :structured, rows: [{String.t(), String.t()}]}` (subagent + shell calls) or `%{label: String.t(), kind: :inline, summary: String.t()}` (all other calls). The template branches on `display.kind == :structured`.
- **Two display modes**: `display/2` takes a keyword list of options whose `opts[:mode]` is `:compact` (the default, and the `display/1` behaviour) or `:full`. A non-keyword `opts`, an unknown `:mode`, or no options at all resolves to `:compact` (defensive matching — no `try/rescue`). Both modes yield the IDENTICAL descriptor shape, keys and label text — they differ ONLY in whether values are capped.
- **`:compact` mode caps values, `:full` mode does not**: compact truncates the structured `Objective` / `Command` values to 200 chars and the inline `summary` to 160 chars, each with a trailing `…`; `:full` applies no character cap and appends no `…`, carrying the complete string (the `Path` row is never capped in either mode). The uncapped value is exactly the same string compact mode caps — the complete objective / command / path, decoded-arguments JSON or whitespace-collapsed raw arguments.
- **Structured calls**: the normalized key's `subagent_*`-prefixed names (core `subagent_tool_name/0` family — `subagent_manager`, `subagent_executor`, `subagent_investigator`, `subagent_task_scheduler`, `subagent_genesis_planner`, `subagent_architect`, `subagent_context_extractor`; prefix detection covers future variants AND the accepted alias spellings `task`/`subagent`, which `EvoGit.Agent.ToolNames.normalize/1` maps onto it) show rows `Path` (first of `"path"`/`"file_path"`) + `Objective`; shell calls (every accepted spelling — `bash` model-facing, `run_bash`/`run_powershell` internal, classified by `tool_call_is_shell?/1` through `EvoGit.Agent.ToolNames`) show a single `Command` row (`"command"` from decoded args with raw-args-collapsed fallback). Raw arguments JSON is NEVER dumped for these.
- **One-line calls**: every other tool renders a single-line summary labelled with its normalized (internal dispatch) key — `read`→`read_file`, `edit`→`edit_file`, `write`→`write_file`, `web_search`→`search_web`, while `rg`, `glob`, `list_dir`, `make_dir`, `create_files`, `read_context`, `write_context`, `search_context`, `skill_*`, unknown and custom names keep their own name: path-like field (`"path"`/`"file_path"`/`"dir_path"`/`"paths"`, list values joined with `" "`) if present, else compact single-line `Jason.encode/1` of the decoded args, else whitespace-collapsed raw arguments, else `""`.
- **Height-constrained everywhere**: structured rows render flat inside the parent container (no separate box/background layer) — only the parent "Tool Calls" box keeps its background. No new CSS in `app.css` — stock Tailwind 4 / DaisyUI utilities only.
- **Compact INLINE detail panel** (chat-history list) keeps `display/1` rendering: structured blocks render inside a `max-h-12` (≈2 lines) `overflow-y-auto` container, and the inline summary stays one line (`whitespace-nowrap overflow-hidden text-ellipsis`).
- **FULL-MESSAGE MODAL** ("zoom-in" view) uses `ToolCallDisplay.display(call, mode: :full)` so values are untruncated, and renders them inside scrollable `max-h-[60vh] overflow-y-auto` regions — structured blocks keep the `min-w-0 flex-1` container, and the inline summary is a `min-w-0 flex-1 max-h-[60vh] overflow-y-auto` container holding a `whitespace-pre-wrap break-all` span (wraps and scrolls instead of ellipsizing).
- **Label/rows layout contract (both render sites)**: the tool-call label ("Shell call" / "subagent_manager" / etc.) is INLINE beside the rows — a flex row (`flex items-start gap-2`) with the label as a `shrink-0` span and the rows container as `min-w-0 flex-1`, so the label and the first structured row key ("Command" / "Path") sit on the SAME line, top-aligned. The key column is `w-20 shrink-0` with 10px uppercase text; the rows containers carry NO padding offsets (`p-1.5`/`pt-0.5`/`p-2` are absent). The inline-summary else-branch is a `min-w-0` (or `min-w-0 flex-1`) span/div in both sites.
- `EvoDashWeb.Helpers.tool_call_display/1` is NOT used by the Agents page — it remains a public, test-pinned helper in `helpers.ex` (do not remove it). `ToolCallDisplay` reuses Helpers' defensive extractors (`tool_call_name/1`, `tool_call_arguments/1`, `tool_call_is_shell?/1`) and depends on the core alias spine `EvoGit.Agent.ToolNames` (`normalize/1` for the tool key behind the subagent grouping test + the inline label — never an exact-string comparison), and adds its own non-crashing `Jason` handling via pattern-matched `case` — no `try/rescue` (project policy).
- **Background shell calls carry a `:variant`** (`ToolCallDisplay`): the shell tool called with a truthy `run_in_background` argument (the core's lenient reading — the JSON boolean `true` or the string `"true"`; `false`/`"false"`/absent/junk are FOREGROUND) returns the SAME `%{label, kind: :structured, rows}` shape with `label: "Background shell call"` PLUS `variant: :background_shell` and the same single `Command` row (200-char compact cap unchanged). The `:variant` key is present ONLY on that descriptor — every other descriptor keeps the historical shape byte-identical, so read it with `Map.get(display, :variant)` (never dot access). Markup gives it a distinct accent in BOTH sites: the inline row gets a `bg-info/10` rounded chip, the label span `text-info` + a `hero-clock` icon (`<.icon name="hero-clock" class="size-3" />`); the modal per-call box swaps `bg-secondary/10` for `bg-info/10 border-l-2 border-info/40` (same padding/rounding).
- **Tool-RESULT entries have their OWN branch, never `ToolCallDisplay`** — the `"tool"` case (`agents_live.html.heex` inline + full-message modal) keys its panel on `EvoDashWeb.Helpers.tool_result_presentation/1` (which delegates the classification to `tool_result_kind/1`, both in `helpers.ex`). The name is `msg.name`, i.e. the RAW model-emitted tool name (the `name` argument of `ToolDispatch.assemble_tool_result/3` = `ReqLLM.ToolCall.name(call)`, so `bash`, `run_bash`, `read`, `subagent_investigator`, `job_output`, …), normalized through `EvoGit.Agent.ToolNames.normalize/1` before any prefix/alias test, yielding three kinds:
  - `:subagent` — a `subagent_*` delegation result (a subagent's returned report; the alias spellings `task`/`subagent` normalize into it): label `gettext("Subagent Report: %{name}")`, `hero-user-group` icon, `text-accent` + `bg-accent/20` header chip + `bg-accent/10` body panel with `border-l-2 border-accent/40`.
  - `:background_job` — `job_output`/`job_list`/`job_kill` (every accepted alias normalizes onto them): label `gettext("Background job: %{name}")`, `hero-clock` icon, `text-info` + `bg-info/20` chip + `bg-info/10` body panel with `border-l-2 border-info/40` — the natural companion to the background-shell call callout.
  - `:default` — every other result: unchanged success palette (`gettext("Tool Result: %{name}")`, `bg-success/20` chip, `bg-success/10` body, no icon, no left border).
  The helper returns the accent class TOKENS (`text_class` / `chip_class` / `panel_class` / `border_class`) and each site composes them with its own box geometry; the class literals live ONLY in `helpers.ex` so `/assistant`'s "Thought process" (`HomeLive.AssistantMessage`) cannot drift from `/agents`. Inline result bodies keep the 500-char truncation + `max-h-48` scroll and the `<empty result>` fallback; the `run_in_background` flag still lives only in the ORIGINATING assistant entry's `data.tool_calls` (the tool entry itself carries no arguments — `message_to_history_entry/1` drops `msg.tool_call_id`), so result-side distinguishing data is `tool_name` + `content` (+ `metadata`, which for tool messages holds only `:turn`/`:timestamp`).
- New gettext strings (`Path`, `Objective`, `Command`, `Shell call`, `Background shell call`, `Subagent Report: %{name}`, `Background job: %{name}`, `Tool Result: %{name}`) will not appear in the POT/PO until release-time extraction — expected, do NOT run `mix gettext.extract`/`merge`/`translate` during development.

## Notes for Agents — Agents page layout & legend tooltip

The Agents page uses a fixed-viewport layout (`xl+` only): `.agents-page-layout` (grid, `overflow: hidden`), `.agents-left-col` (column flex, `overflow: hidden`), `.agents-tree-panel` (card, `flex: 1 1 0`), with the tree content scrolling inside `.agents-tree-panel .card-body` (`overflow-y: auto`) and the legend (`.agents-legend`) as a SIBLING of card-body at the panel's bottom. The chips carry `data-tip` (gettext) + `phx-hook="LegendTooltip"` + unique ids (LiveView requires `id` for phx-hook); the `tooltip` class was REMOVED so DaisyUI's clipped tooltip doesn't double-render. ## Notes for Agents — Context tile (context-usage meter)
The detail panel's usage section renders the Context tile as a context-usage METER, not a threshold-relative `progress` element: the bar's full width is the model's CONTEXT WINDOW, the fill is the agent's current context size (`:total_tokens`) and a vertical TICK marks the compression THRESHOLD.
The tile is a full-width sunken tile (`bg-base-200/50 border border-base-300 rounded-lg p-2.5`) directly below the 2-column Cached Tokens / Cache Hit Rate grid, inside the same bordered usage section.
All geometry and every derived numeric label come from ONE `<% meter = ContextMeter.build(agent) %>` block in `agents_live.html.heex`; user-facing prose is gettext in the markup — no phx-hook, no JS.
Meter root (`id="agent-context-meter"`, class `relative mt-2`) data-attribute contract (render-test pinned): `data-context-fill-pct` (one-decimal fill % of the window), `data-context-tick-pct` (one-decimal threshold % of the window, OMITTED when the threshold is unknown), `data-context-zone` (`success` / `warning` / `error`), `data-context-window-tokens`, `data-context-threshold-tokens` (OMITTED when unknown), `data-context-current-tokens` (plain integers).
The fill div carries `style="width: <fill_label>%"` — the SAME one-decimal string as `data-context-fill-pct`, so CSS and data attributes can never disagree — and its class is `meter.fill_class` (`bg-success` / `bg-warning` / `bg-error`).
The tick renders only when `meter.tick_pct` is non-nil: an absolutely positioned 2px line (`w-0.5`, `meter.tick_class` = `bg-base-content`, centred via `-translate-x-1/2`) plus a rotated-square cap at its top, at `style="left: <tick_label>%"`, with `title={gettext("Compression triggers at %{tokens} tokens", tokens: format_number(meter.threshold_tokens))}` (the exact threshold token count, comma-grouped; built in the template so no tooltip renders when the tick is hidden).
The tile header's right side shows the context readout `current / threshold` (both `EvoDashWeb.Helpers.format_number/1`-grouped; current only when the threshold is unknown), and the caption row shows `gettext("Compression at %{tokens}", …)` (or "Compression threshold unknown" when there is no tick) on the left and `gettext("Compressions")` plus the legacy `count (pct%)` label on the right (`agent.compression_pct` keeps its threshold-relative value).
Zones colour the FILL only; the tick always uses `bg-base-content` so it stays visible over every fill colour and in both themes.
The tick-hidden "Compression threshold unknown" render is only reachable for an agent map carrying NO `:compression_threshold` key: `ThresholdCache.threshold_for_agent/2` always resolves a positive integer (its 180_000 last resort) and the update path restores a known threshold, so the normal page flow never shows the unknown state.

## Notes for Agents — `whitespace-pre-wrap` content must sit flush against its tags

HEEx emits the newline + indentation sitting between an element's opening tag and its interpolated content as a literal text node. Under `whitespace-pre-wrap` (or a `<pre>`) that whitespace is PRESERVED, so a block written across multiple template lines renders with a spurious leading indent.

- **Rule**: every `whitespace-pre-wrap` element must be emitted on ONE line with its interpolation flush against the tags — which is why the page's pre-wrap site (the full-objective modal) is a single-line `<pre ...>…</pre>`.
