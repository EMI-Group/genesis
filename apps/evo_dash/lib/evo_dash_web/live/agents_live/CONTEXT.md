# AgentsLive Support Modules

## Intent

Support modules extracted from `EvoDashWeb.AgentsLive` to keep the main LiveView module and its companion template focused on rendering and lifecycle callbacks.

## API Surface

| Module | Purpose |
|--------|---------|
| `ToolCallDisplay` | Pure rendering contract for tool-call messages in the chat history viewer (inline detail panel + full-message modal). `display/1` returns `%{label, kind: :structured, rows}` for subagent (`subagent_*` prefix) and shell (`run_bash`/`run_powershell`) calls — key/value rows (path + truncated objective / truncated command) — or `%{label, kind: :inline, summary}` for all other calls (compact one-line arguments summary, truncated to 160 chars). Both forms are height-constrained by the template: structured blocks render in a `max-h` + `overflow-y-auto` container, inline summaries are one line with CSS ellipsis. Raw arguments JSON is never dumped for subagent/shell calls. |
| `OptimisticMessages` | Pure helpers for the optimistic display of user-sent messages in the chat history viewer. `append/3` appends `%{content, sent_at}` to the per-agent optimistic map (new message at the END). `merge/2` merges real history entries with pending optimistic entries (optimistic entries APPENDED after real history — base indices unchanged) and drops an optimistic entry once a real `"user"`-type history entry with the same content appears (first-match consumption: each real user entry reflects at most one optimistic entry, so sending identical text twice works; uppercase `"USER"` tolerated). `latest_turn/1` returns the max history turn (or 0). Optimistic entries render in the same `%{turn, type: "user", data: %{content}, optimistic: true}` shape the template's `"user"` case consumes. |
| `LoadData` | Data loading for the Agents page, extracted so it runs inside `EvoDash.TaskSupervisor` children (never in the LiveView process — cross-node RPCs never block the page). `load/2` = page load: agent summaries + `config_status` (layout banner) + a refreshed threshold cache → `{:ok, %{agents:, config_status:, threshold_cache:}}`. `refresh/2` = broadcast-triggered refresh path: agent summaries + threshold cache → `{agents, cache}` (no config_status). `find_children_from_agents/2` computes `{agent_id, status}` children from `parent_id` (public — AgentsLive's in-memory incremental paths reuse it). Builds the rich agent maps from `RemoteAPI.list_agents/0` summaries, carrying `:message_count` through for the history gate. Env seams resolved at call time (inside the tasks): `:agents_list_runner` (default `&EvoDash.NodeContext.list_agents/1`), `:agents_config_runner` (default `&EvoDash.NodeContext.get_resolved_config/1`). |
| `HistoryGate` | Pure history-fetch gating (payload fix): `need_fetch?/3` = `Map.get(last_seen, agent_id) != message_count` (a nil last-seen entry = brand-new agent = must fetch); `record/3` stores the count a fetched history corresponds to. `RemoteAPI.list_agents/0` summaries carry `:message_count` (number of messages in the agent's session-memory context), and the `{:agent_updated, id, changed_fields, node}` broadcast carries `:message_count` whenever the agent's context changed — so an unchanged count means the already-fetched history is current, and full histories are never re-transferred over the node boundary. Gate state = the `:history_gate` socket assign (`%{agent_id => count}`, seeded `%{}` in mount, reset on node switch — agent ids are per-node). |
| `ThresholdCache` | Per-node cache for the LLM compression threshold used by the compression % bars. The threshold lives at `[:llm, :compression_threshold_tokens]` in the FULL resolved config (`EvoGit.Config.resolve/0`, default 100_000) — the scheduler config (`get_remote_config/1`) has NO `:llm` section, which was the old remote-branch bug. Cache shape `{node, threshold, fetched_at_monotonic}` (nil = empty); `read/3` (fresh within 30s) / `put/4` / `fetch/3` (cache miss → node-aware runner via the `:agents_config_runner` seam, resolved at call time) / `threshold_from_config/1` (accepts `{:ok, config} | {:error, reason}`) / `default_threshold/0`. The fetch runs ONLY inside the async load/refresh tasks — never in a `handle_info`/`handle_event`. |

## Constraints

- Pure functions — no I/O, no socket, no process calls (`ToolCallDisplay`, `OptimisticMessages`, `HistoryGate`; `ThresholdCache.read/3`/`put/4`/`threshold_from_config/1`/`default_threshold/0` are pure). Deliberate exceptions: `LoadData` and `ThresholdCache.fetch/3` perform I/O (NodeContext RPCs via the env-seam runners) — they are designed to run inside `EvoDash.TaskSupervisor` children, never in the LiveView process.
- No `try/rescue` — defensive extraction + pattern matching/`case` only (project-wide anti-pattern policy). The node-boundary `try/rescue` wrappers live in `agents_live.ex`'s spawn functions (`start_async_load/1` / `spawn_agents_refresh/1` / `spawn_history_fetch/3`), each carrying a justification comment.
- Reuses `EvoDashWeb.Helpers` defensive extraction (`tool_call_name/1`, `tool_call_arguments/1`, `tool_call_is_shell?/1`) — do not reimplement; `EvoDashWeb.Helpers.tool_call_display/1` is not used by the Agents page; it stays as a public, test-pinned helper (do not remove it).
- New user-facing strings use `gettext` (backend `EvoDashWeb.Gettext`); `Path`/`Objective`/`Command` entries appear in the POT/PO at release-time extraction only — do not run `mix gettext.extract`/`merge`/`translate` during development.

## Send-Message Flow (in `agents_live.ex` + `agents_live.html.heex`)

User-sent messages display optimistically via the `OptimisticMessages` support module (below).

- **Event handlers in `agents_live.ex`**: `open_send_message` (sets `send_message_agent_id` + clears `send_message_text`), `close_send_message`, `validate_send_message` (`phx-change` syncs `@send_message_text`), **`send_agent_message`** — the submit handler. Params: `%{"agent_id" => id, "message" => message}` (hidden input heex line 670 + textarea). It calls `EvoDash.NodeContext.send_user_message(node, agent_id, message)`.
- **Return matching**: only `{:ok, :ok}` is a real success (local AND remote). Missing agent = `{:ok, {:error, :not_found}}` (the local path wraps the RemoteAPI result); erpc failures = `{:error, reason}`. Both error shapes show the error flash `"Failed to send message: %{reason}"` (shared private helper `send_message_error_flash/1`). On success: info flash `"Message sent to agent"` + modal close + the message is appended to `@optimistic_messages[agent_id]` (via `OptimisticMessages.append/3`, preserving order; new message at the END).
- **`@optimistic_messages` assign**: `agent_id => [%{content, sent_at}]` map, initialized to `%{}` in mount and RESET to `%{}` only on node switch in `handle_params/3` (agent ids are per-node). It is independent of `@agents` and deliberately survives all history reloads (`{:agents_updated, node}`, `{:agent_updated, id, fields, node}`, `select_agent`, async load/refresh results) — drained messages are dropped by the render-time dedupe, not by clearing the assign.
- **Send call chain** (into sibling `evo_git` subtree): `EvoDash.NodeContext.send_user_message/3` (`node_context.ex:291`) → `EvoGit.RemoteNode.send_agent_message/3` (`remote_node.ex:276`; local = direct, remote = `:erpc.call`) → `EvoGit.AgentScheduler.RemoteAPI.send_agent_message/2` (`remote_api.ex:264`) → `EvoGit.AgentScheduler.send_user_message/2` (GenServer.call, `agent_scheduler.ex:242`) → `handle_call({:send_user_message, ...})` (`agent_scheduler.ex:739`) → `Store.append_pending_user_message/2` (`store.ex:155`) → appends to `AgentState.pending_user_messages` (`agent_state.ex:61`). Returns `:ok` / `{:error, :not_found}` / `{:error, :scheduler_not_started}`.
- **Pending messages are INVISIBLE to the history read path**: `RemoteAPI.get_agent_history/1` (`remote_api.ex:85`) returns only `agent_state.context.messages`. The queue is drained ONLY at the top of the agent's next turn: `drain_and_inject_user_messages/1` (`apps/evo_git/lib/evo_git/agent/runner.ex:232`) drains via `Store.drain_pending_user_messages/1` (`store.ex:182`) and appends each message as a `user(msg)` role entry tagged with the current turn, then `sync_context_to_ets/2` → `Store.update_agent_context/2` (`store.ex:348`) → `put_agent_state`. Only then does the message appear in history. **Note:** appending to the queue DOES broadcast `{:agent_updated, agent_id, [pending_user_messages: ...]}` (`pending_user_messages` is in `@agent_state_tracked_fields`, `store.ex:447`) — the LiveView does NOT refetch on that (no `:message_count` in the changed fields), so the message stays invisible in the panel until the agent's next turn actually drains it into context. The optimistic copy bridges that gap.
- **History refresh mechanics** (all ASYNC, all REPLACE the whole per-agent history list): fetches run via `spawn_history_fetch/3` — an `EvoDash.TaskSupervisor` child calling the `:agents_history_runner` seam (default `EvoDash.NodeContext.get_agent_history/2`, resolved inside the task) — and the result is applied from `{:agent_history_loaded, agent_id, node, result, index}` (stale-guarded on selected agent + current node; `history_loading_agent_id`/`full_message_pending_agent_id` assigns drive the small "Loading history…" spinner). Fetches are GATED on `:message_count` via `HistoryGate` (`need_fetch?/3`): a fetch happens only when the gate's last-seen count differs from the fresh summary count (nil = must fetch), so unchanged conversations are never re-transferred — `apply_agents_result/2` carries over the already-fetched history instead. Triggers: (1) `{:agents_updated, node}` full reload → `apply_agents_result/2` → `maybe_fetch_selected_history/1` (gate-checked); (2) `{:agent_updated, id, changed_fields, node}` of the selected agent WITH `:message_count` in changed_fields (the contract: it is present whenever the context changed) → `refetch_selected_history/1` (gate-checked against the merged fresh count — no refetch when the count is unchanged or the field is absent); (3) `select_agent` lazy-load (gate-checked); (4) `view_full_message` empty-history safety net (carries the entry `index` in the result message). Subscription: `Phoenix.PubSub.subscribe(EvoGit.PubSub, "agents")` in `mount/3`.
- **History entry shape**: `messages_to_history_entries/1` / `message_to_history_entry/1` produce `%{turn, timestamp, type, data}` with `type = Atom.to_string(msg.role)` (lowercase: "user"/"assistant"/"tool"/"system") and `data.content` = joined ContentPart texts. Template rendering: `agents_live.html.heex` lines 330-509 ("Chat History / Session Memory"); the `"user"` case renders `entry.data.content` in a `bg-info/10` panel. Styling helpers in `EvoDashWeb.Helpers`: `history_entry_icon/1`, `history_entry_color/1`. Uppercase types ("USER_PROMPT", "THOUGHT_CHUNK", "TOOL_CALL_START", "COMPLETE", "QUEUED", etc.) are cased in the template but nothing produces them; "QUEUED" renders `entry.data.message` — a queued-message display that is dead.
- **Optimistic rendering**: the chat-history template computes `history_entries = OptimisticMessages.merge(agent.history || [], Map.get(@optimistic_messages, agent.id, []))` and iterates THAT (the empty-state condition uses `history_entries != []`, so an empty real history with pending messages still renders). Optimistic entries are APPENDED after the real history (never interleaved) → base-history indices are unchanged, and `view_full_message` looks up from the merged list (`merged_history/2` private helper) so optimistic entries are viewable in the modal too. Optimistic entries carry `optimistic: true`; the `"user"` case renders a small italic pending hint (`"Pending — will be added on the agent's next turn"`, gettext-wrapped, gated on `Map.get(entry, :optimistic, false)` — plain dot access would raise KeyError for real entries). Once the agent drains the queue, the real `"user"` entry appears in history on the next reload and the render-time dedupe drops the optimistic copy — no duplicates.

## Agent Event Contract (push-based, node-identity)

The Agents page is FULLY push-based — there is NO periodic poll. The `:evo_git` emitters broadcast EXACTLY these four shapes on `EvoGit.PubSub` topic `"agents"`, every one carrying the BEAM node atom of the publisher:

- `{:agents_updated, node}` — throttled bulk-change signal → node-match → `spawn_agents_refresh/1` (async full reload, seq-guarded via the monotonic `:refresh_seq` assign); foreign → ignored.
- `{:agent_registered, id, summary, node}` — the event carries the agent's full summary (the same `RemoteAPI.list_agents/0` summary shape `LoadData.build_agents` consumes: `id, task_local_id, repo_id, repo_root, task_id, task_number, status, depth, parent_id, worktree, retries, agent_module, model_id, objective, context_path, current_commit, base_commit, usage, total_tokens, compression_count, message_count`). Merged IN-MEMORY for BOTH local and remote events through ONE shared path (`merge_registered_agent/3` → `build_registered_agent/2`): the row is built with the `LoadData` field mapping (defaults for absent fields, `usage` normalized to a `%Usage{}` struct), derived fields recomputed exactly like the load path (children/has_children from `parent_id`, `compression_pct` from `total_tokens` + the node threshold via `safe_compression_threshold/1`), inserted at the sorted `{depth, id}` position, the parent's children list refreshed, and `id_to_display`/`previous_agent_ids`/`new_agent_ids`/`repo_trees` updated. A duplicate id (race with the `{:agents_updated, node}` fallback) is a no-op; a summary missing the fields the tree needs (`status`/`depth`/`parent_id`) falls back to `spawn_agents_refresh/1`. The old local/remote branch (`handle_local_agent_registered/3`, ETS reads) is gone.
- `{:agent_updated, id, changed_fields, node}` — `changed_fields` NEVER contains `:context`; it DOES contain `:message_count` whenever the agent's context changed. Node-match → the existing in-memory merge applies for BOTH local and remote (special fields: `context_node` → `context_path`, `phylo_node` → `current_commit`, nil `usage` → zero, `compression_pct` recompute on `total_tokens`, children recalc on `parent_id`, status-change tracking into `previous_statuses`/`changed_status_ids`, `id_to_display` on `task_local_id`, `repo_trees` rebuild on `context_node`/`repo_root`). The selected-agent history refetch is gated: only when `changed_fields` contains `:message_count` AND `HistoryGate.need_fetch?/3` says the merged fresh count moved vs the gate's last-seen (`refetch_selected_history/1`; the `history_loading_agent_id` overlap guard still applies). A missing agent row (race) → `spawn_agents_refresh/1`.
- `{:agent_removed, id, node}` — node-match → the row is dropped in-memory (children orphaned to `parent_id: nil`, parent's children list refreshed, tracking sets/selection/repo_trees cleaned) for BOTH local and remote (fixes the old bug where remote removals were invisible without a poll); foreign → ignored.

**Node filtering**: EVERY one of the four handlers first checks `EvoDashWeb.LiveHooks.NodeAware.event_from_current_node?(socket.assigns, event_node)` — the viewed node's identity is `socket.assigns[:current_node]` (local → `node()`, remote → the remote daemon's BEAM node atom). Foreign-node events are dropped with the socket unchanged (no UI update, no refresh spawn). There are no per-node forks left in the handlers — local and remote share one code path.
