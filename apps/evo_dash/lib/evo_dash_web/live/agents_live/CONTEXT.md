# AgentsLive Support Modules

## Intent

Support modules extracted from `EvoDashWeb.AgentsLive` to keep the main LiveView module and its companion template focused on rendering and lifecycle callbacks.

## API Surface

| Module | Purpose |
|--------|---------|
| `ToolCallDisplay` | Pure rendering contract for tool-call messages in the chat history viewer (inline detail panel + full-message modal). `display/1` returns `%{label, kind: :structured, rows}` for subagent (`subagent_*` prefix) and shell (`run_bash`/`run_powershell`) calls — key/value rows (path + truncated objective / truncated command) — or `%{label, kind: :inline, summary}` for all other calls (compact one-line arguments summary, truncated to 160 chars). Both forms are height-constrained by the template: structured blocks render in a `max-h` + `overflow-y-auto` container, inline summaries are one line with CSS ellipsis. Raw arguments JSON is never dumped for subagent/shell calls. |
| `OptimisticMessages` | Pure helpers for the optimistic display of user-sent messages in the chat history viewer. `append/3` appends `%{content, sent_at}` to the per-agent optimistic map (new message at the END). `merge/2` merges real history entries with pending optimistic entries (optimistic entries APPENDED after real history — base indices unchanged) and drops an optimistic entry once a real `"user"`-type history entry with the same content appears (first-match consumption: each real user entry reflects at most one optimistic entry, so sending identical text twice works; uppercase `"USER"` tolerated). `latest_turn/1` returns the max history turn (or 0). Optimistic entries render in the same `%{turn, type: "user", data: %{content}, optimistic: true}` shape the template's `"user"` case consumes. |

## Constraints

- Pure functions — no I/O, no socket, no process calls.
- No `try/rescue` — defensive extraction + pattern matching/`case` only (project-wide anti-pattern policy).
- Reuses `EvoDashWeb.Helpers` defensive extraction (`tool_call_name/1`, `tool_call_arguments/1`, `tool_call_is_shell?/1`) — do not reimplement; `EvoDashWeb.Helpers.tool_call_display/1` is not used by the Agents page; it stays as a public, test-pinned helper (do not remove it).
- New user-facing strings use `gettext` (backend `EvoDashWeb.Gettext`); `Path`/`Objective`/`Command` entries appear in the POT/PO at release-time extraction only — do not run `mix gettext.extract`/`merge`/`translate` during development.

## Send-Message Flow (in `agents_live.ex` + `agents_live.html.heex`)

User-sent messages display optimistically via the `OptimisticMessages` support module (below).

- **Event handlers in `agents_live.ex`**: `open_send_message` (sets `send_message_agent_id` + clears `send_message_text`), `close_send_message`, `validate_send_message` (`phx-change` syncs `@send_message_text`), **`send_agent_message`** — the submit handler. Params: `%{"agent_id" => id, "message" => message}` (hidden input heex line 670 + textarea). It calls `EvoDash.NodeContext.send_user_message(node, agent_id, message)`.
- **Return matching**: only `{:ok, :ok}` is a real success (local AND remote). Missing agent = `{:ok, {:error, :not_found}}` (the local path wraps the RemoteAPI result); erpc failures = `{:error, reason}`. Both error shapes show the error flash `"Failed to send message: %{reason}"` (shared private helper `send_message_error_flash/1`). On success: info flash `"Message sent to agent"` + modal close + the message is appended to `@optimistic_messages[agent_id]` (via `OptimisticMessages.append/3`, preserving order; new message at the END).
- **`@optimistic_messages` assign**: `agent_id => [%{content, sent_at}]` map, initialized to `%{}` in mount and RESET to `%{}` only on node switch in `handle_params/3` (agent ids are per-node). It is independent of `@agents` and deliberately survives all history reloads (`{:agents_updated}`, `{:agent_updated, ...}`, `:remote_poll`, `select_agent`, `full_reload`) — drained messages are dropped by the render-time dedupe, not by clearing the assign.
- **Send call chain** (into sibling `evo_git` subtree): `EvoDash.NodeContext.send_user_message/3` (`node_context.ex:291`) → `EvoGit.RemoteNode.send_agent_message/3` (`remote_node.ex:276`; local = direct, remote = `:erpc.call`) → `EvoGit.AgentScheduler.RemoteAPI.send_agent_message/2` (`remote_api.ex:264`) → `EvoGit.AgentScheduler.send_user_message/2` (GenServer.call, `agent_scheduler.ex:242`) → `handle_call({:send_user_message, ...})` (`agent_scheduler.ex:739`) → `Store.append_pending_user_message/2` (`store.ex:155`) → appends to `AgentState.pending_user_messages` (`agent_state.ex:61`). Returns `:ok` / `{:error, :not_found}` / `{:error, :scheduler_not_started}`.
- **Pending messages are INVISIBLE to the history read path**: `RemoteAPI.get_agent_history/1` (`remote_api.ex:85`) returns only `agent_state.context.messages`. The queue is drained ONLY at the top of the agent's next turn: `drain_and_inject_user_messages/1` (`apps/evo_git/lib/evo_git/agent/runner.ex:232`) drains via `Store.drain_pending_user_messages/1` (`store.ex:182`) and appends each message as a `user(msg)` role entry tagged with the current turn, then `sync_context_to_ets/2` → `Store.update_agent_context/2` (`store.ex:348`) → `put_agent_state`. Only then does the message appear in history. **Note:** appending to the queue DOES broadcast `{:agent_updated, agent_id, [pending_user_messages: ...]}` (`pending_user_messages` is in `@agent_state_tracked_fields`, `store.ex:447`) — the LiveView reloads the selected agent's history immediately after send, but the message is still absent from `context.messages` until the next turn. The optimistic copy bridges that gap.
- **History refresh mechanics** (all REPLACE the whole per-agent history list — `reload_selected_agent_history/3`, or `load_agent_history` in the `agent_updated` path): (1) `{:agents_updated}` full reload; (2) `{:agent_updated, agent_id, _}` reloads only if `agent_id == selected_agent_id`; (3) 3s `:remote_poll` for remote nodes only; (4) `select_agent` lazy-load; (5) `view_full_message` safety-net load. Subscription: `Phoenix.PubSub.subscribe(EvoGit.PubSub, "agents")` in `mount/3`.
- **History entry shape**: `messages_to_history_entries/1` / `message_to_history_entry/1` produce `%{turn, timestamp, type, data}` with `type = Atom.to_string(msg.role)` (lowercase: "user"/"assistant"/"tool"/"system") and `data.content` = joined ContentPart texts. Template rendering: `agents_live.html.heex` lines 330-509 ("Chat History / Session Memory"); the `"user"` case renders `entry.data.content` in a `bg-info/10` panel. Styling helpers in `EvoDashWeb.Helpers`: `history_entry_icon/1`, `history_entry_color/1`. Uppercase types ("USER_PROMPT", "THOUGHT_CHUNK", "TOOL_CALL_START", "COMPLETE", "QUEUED", etc.) are cased in the template but nothing produces them; "QUEUED" renders `entry.data.message` — a queued-message display that is dead.
- **Optimistic rendering**: the chat-history template computes `history_entries = OptimisticMessages.merge(agent.history || [], Map.get(@optimistic_messages, agent.id, []))` and iterates THAT (the empty-state condition uses `history_entries != []`, so an empty real history with pending messages still renders). Optimistic entries are APPENDED after the real history (never interleaved) → base-history indices are unchanged, and `view_full_message` looks up from the merged list (`merged_history/2` private helper) so optimistic entries are viewable in the modal too. Optimistic entries carry `optimistic: true`; the `"user"` case renders a small italic pending hint (`"Pending — will be added on the agent's next turn"`, gettext-wrapped, gated on `Map.get(entry, :optimistic, false)` — plain dot access would raise KeyError for real entries). Once the agent drains the queue, the real `"user"` entry appears in history on the next reload and the render-time dedupe drops the optimistic copy — no duplicates.
