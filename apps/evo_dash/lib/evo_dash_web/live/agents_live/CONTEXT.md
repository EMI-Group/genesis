# AgentsLive Support Modules

## Intent

`agents_live.ex` is the LiveView ONLY: `mount/3`, `handle_params/3`, one-expression `handle_info`/`handle_event` routers, `terminate/2` and bare template delegates — no template helpers, no presentation logic.
Every state transition those routers delegate to lives in a module in this directory, and the template renders only what those modules computed.
`agents_live.html.heex` is a THIN COMPOSITION (~50 lines): the `Layouts.app` shell, the remote-connection gate, the `.agents-page-layout` wrapper and three function-component calls — `TreePanel.tree_panel/1` (left column), `DetailPanel.detail_panel/1` (right column) and `Modals.modals/1` (the three modals).

## Template Composition (`agents_live.html.heex`)

The template is a THIN COMPOSITION and holds no markup of its own beyond the shell: the `EvoDashWeb.Layouts.app` call (flash/config/node/sidebar/update/guide/accent assigns), the `EvoDashWeb.RemoteGateComponents.gate_active?/1` branch (gate active → the remote gate; otherwise the workbench), the `div.agents-page-layout.animate-fade-in-up.animation-delay-100` wrapper, and the three component calls.
`TreePanel` renders `<div class="agents-left-col">` (banner + tree panel card + legend); `DetailPanel` renders `<div class="agents-detail-col">`; `Modals` renders the three modals as SIBLINGS of `.agents-page-layout`.
Function components render no wrapper element, so the DOM is byte-for-byte the pre-split markup: `.agents-page-layout` still has exactly the two column children and each column owns its own root class.
The partials `use EvoDashWeb, :html` (gettext, `CoreComponents`/`Helpers` imports and `~H` behave as in the template) and hold NO state, NO event handling and NO async work — every event still routes through `Inspector`, `SendMessage`, `CommitGraphState` and the page's other state modules.
`TreePanel` takes explicit attrs; `DetailPanel` takes the whole-assigns passthrough described above, and shell-side fallbacks (`assigns[:commit_graph] || []`, `assigns[:commit_graph_loading] == true`, `assigns[:commit_graph_error]`, `assigns[:send_message_text] || ""`) keep a partial-assigns render working (`agents_stream_render_test.exs`).
`agents_live.ex` carries no template helpers, no `ContextMeter`/`StreamPanel` alias, and no `HistoryEntry`/`ToolCallDisplay` alias.

## Constraints

- Pure functions — no I/O, no socket, no process calls (`ToolCallDisplay`, `PendingEvents`, `HistoryGate`, `ContextMeter`, `AgentList`, `TreeView`, `OptimisticMessages`, `RuntimeStream`, `StreamLimits`, `StreamPresentation`; `ThresholdCache.read/3`/`put/4`/`threshold_from_config/1`/`threshold_for_agent/2`/`default_threshold/0` are pure). The model-label derivation is the shared `EvoDashWeb.ModelLabel`, also pure. Deliberate exceptions: `LoadData` and `ThresholdCache.fetch/3` perform I/O (NodeContext RPCs via the env-seam runners) — they are designed to run inside `EvoDash.TaskSupervisor` children, never in the LiveView process.
- No `try/rescue` — defensive extraction + pattern matching/`case` only (project-wide anti-pattern policy). The exit-safe boundary lives in the async spawners — `Loader.start_page_load/1`, `Loader.spawn_refresh/1`, `CommitGraphState`'s private `spawn_commit_graph_fetch/2`, `Inspector`'s private `spawn_history_fetch/1` and `SendMessage`'s private `send_user_message_safely/3` — all of which call `EvoDash.SafeCall.run/1` (an EXIT from a `GenServer.call` timeout / dead target becomes an error VALUE).
- Config reads in this node are exactly three: the threshold (`NodeContext.get_resolved_config/1` via the `:agents_config_runner` seam in `ThresholdCache.fetch/3`, reached from `LoadData.load/2` and `LoadData.refresh/2`), the layout-banner health status (`LoadData.node_config_status/1` — local `EvoGit.Config.config_status()`, remote `NodeContext.get_remote_config_status/1`), and the LIVEVIEW-process local fallback in `AgentMerge`'s private `safe_compression_threshold/1` (also reached from its private `restore_threshold/2`): a fresh `ThresholdCache.read/3` hit is used, a LOCAL cache miss calls `EvoGit.Config.resolve([:llm, :compression_threshold_tokens])` inline (never an RPC), and a REMOTE cache miss returns `default_threshold/0` until the next async load/refresh.
- `@config_status` is (re)loaded ONLY by the page-load path (`LoadData.load/2`); `LoadData.refresh/2` never re-reads it, so the layout banner keeps its mount-time value until a page load (`Loader.start_page_load/1` on a node switch or from `retry_agents_load`).
- The page subscribes to the `"agents"` topic only (`mount/3`) plus NodeAware's `"tasks"`/`"remote_connections"` — NO `"scheduler_config"` and NO config topic — so neither `@config_status` nor `@threshold_cache` is invalidated by a config change; the threshold refreshes only when a load/refresh task runs after the 30 s TTL.
- Reuses `EvoDashWeb.Helpers` defensive extraction (`tool_call_name/1`, `tool_call_arguments/1`, `tool_call_is_shell?/1`) — do not reimplement. `EvoDashWeb.Helpers.tool_call_display/1` is NOT used by the Agents page; it stays a public, test-pinned helper (do not remove it).
- New user-facing strings use `gettext` (backend `EvoDashWeb.Gettext`); new POT/PO entries appear at release-time extraction only — do not run `mix gettext.extract`/`merge`/`translate` during development.
- `commit_graph.ex` is ~1 213 lines and legitimately long: ~437 lines are the `@moduledoc` that IS the pinned output contract (node/edge/agent key sets, row and lane rules, ownership, folding), and its per-concern internals live in `commit_graph/` (`Interleave`, `Edges`, `Fold`) — extract a further concern there rather than trimming the contract.

## Async Load & Exit-Safety Contract

No AgentsLive render path (mount / `handle_params/3` / `handle_event/3` / `handle_info/2`) blocks on a store, scheduler or cross-node RPC call: every such read runs in an `EvoDash.TaskSupervisor` child and reports back as a tagged message.
The initial page load is spawned by `handle_params/3` ONLY on the connected mount (`if connected?(socket), do: Loader.start_page_load(socket), else: socket`) — the dead render paints the shell (`@agents_loading` seeds `true` in `mount/3`) and never spawns a load whose result would be sent to a dying process.
`Loader.start_page_load/1` sets the loading flag, bumps `load_generation` and clears `@agents_error`; `Loader.spawn_refresh/1` bumps the never-reset `refresh_seq`.
Every spawned loader calls its loader/runner through `EvoDash.SafeCall.run/1` INSIDE the task body, so a `GenServer.call` timeout or a dead target (an EXIT, which `rescue` cannot catch) is captured as an error value and the result message is ALWAYS sent — no task can die silently and wedge a loading flag.
Result message shapes: `{:agents_data_loaded, node, gen, result}`, `{:agents_refresh_result, seq, node, result}`, `{:commit_graph_loaded, node, seq, result}`; `result` is `{:ok, ...}` or `{:error, reason}`, and each is stale-guarded on its monotonic counter (`@load_generation` / `@refresh_seq` / `@commit_graph_seq`) AND the viewed node.
The loader seams (`:agents_list_runner` / `:agents_config_runner` via `LoadData`, `:agents_commit_graph_runner`) are resolved AT SPAWN TIME inside the task, so tests can stub them.
`ThresholdCache.fetch/3` runs ONLY inside those spawned tasks and has no flag of its own to wedge.
Every loading/error assign clears on its result path: `@agents_loading` + `@agents_error` (page load), `@commit_graph_loading` + `@commit_graph_error` (commit-graph fetch).
A failed page load keeps the last good tree, clears `@agents_loading` and records `@agents_error`, which `TreePanel` renders as a compact inline banner (`#agents-load-error`) with a Retry button (`#agents-load-retry`, `phx-click="retry_agents_load"`).
`retry_agents_load` clears `@agents_error` and re-runs `Loader.start_page_load/1`; there is NO polling and NO auto-retry timer, and `@agents_error` is cleared whenever a load starts, on any successful load, and on a node switch.

## Left-Panel View Switcher & Commit-History (Temporal) View

The left panel renders EITHER the spatial agent tree OR the temporal git-commit graph, switched by a segmented control in the panel header (two `phx-click="switch_left_view"` buttons, `id="left-view-tree"` / `id="left-view-commits"`, each carrying `phx-value-view="tree"` or `"commits"`).
The active view is the `:left_view` assign (`:tree | :commits`, default `:tree` in `mount/3`).
`switch_left_view` whitelists the view by PATTERN MATCHING the two literal binaries (`CommitGraphState.switch_left_view/2`) — any other value falls through to a no-op clause (no atom conversion, no `String.to_atom`).
Switching to `:commits` triggers an immediate force-refresh commit-graph load; switching back to `:tree` renders the tree and never touches the git RPC.
`:left_view` SURVIVES a node switch (a user preference) and is NOT in the `handle_params/3` reset branch, while the commit-graph DATA is per-node and IS reset there.
The tree view (and its "Agent Tree" label) stays the default, so the agent tree, right-hand detail panel and status legend chips are behaviourally unchanged.

### Commit-graph async contract

- Assigns (seeded in `mount/3`; the data assigns reset on a node switch): `@left_view`, `@commit_graph` (built `[repo_view]`), `@commit_graph_raw` (`%{repo_key => %{commits:, refs:, truncated:}}`), `@commit_graph_loaded`, `@commit_graph_loading`, `@commit_graph_error`, `@commit_graph_seq` (monotonic — NEVER reset, mirrors `@refresh_seq`), `@commit_graph_fingerprint` (the `CommitGraphRefresh.fingerprint/1` of the agent set the LAST build consumed; nil until the first build/fetch), `@commit_graph_fetched_at` (monotonic ms of the last fetch), `@commit_graph_tick_scheduled` (one-shot-tick guard), `@commit_graph_fold_expanded` (the expanded fold-key `MapSet`, per-node view state) and `@retained_agents` (`%{agent_id => agent_map}` — in-session RETAINED ended agents, RESET to `%{}` on a node switch).
- `CommitGraphState.maybe_load/2` is a NO-OP unless `@left_view == :commits` — the tree view never triggers a git RPC.
- **Fingerprint gate (commit-relevance)**: on a NON-forced call (a call is forced when `force: true` OR the graph is not yet loaded) the agent set's commit-relevance fingerprint (`CommitGraphRefresh.fingerprint/1` over `commit_graph_agents/1`) is compared against `@commit_graph_fingerprint`; an UNCHANGED, non-empty fingerprint skips BOTH the rebuild and the refetch spawn (a status/token/usage/message-count-only flush costs nothing). A CHANGED (or still-nil) fingerprint rebuilds + refetches and stores the new one. Bypasses: `force: true` (first activation, the one-shot tick, a view re-switch), the initial load, and a fetch already in flight (`@commit_graph_loading`) — that result applies through `{:commit_graph_loaded, ...}` and re-stores the fingerprint of the agent set it built from, so an in-flight fetch always converges and a SUCCESSFUL fetch yielding an identical raw map cannot loop. SELECTION (`select_agent`) needs neither a rebuild nor a refetch: `start_ids`/`end_ids` are computed for EVERY agent at build time and the renderer derives its markers from `selected_id` at render time.
- It first rebuilds `@commit_graph` from `@commit_graph_raw` + the MERGED agent set (private `rebuild_commit_graph/3`), so a newly-spawned child's own lane and its nodes appear immediately without a fetch; the rebuild stores the fingerprint of the agent set it built from.
- **`commit_graph_agents/1` is the ONE agent set the TEMPORAL view is built from**: `@agents` (LIVE) MERGED with `Map.values(@retained_agents)` (ended), de-duplicated by `id` with the LIVE copy winning. It feeds BOTH `commit_graph_groups/1` AND `CommitGraph.build/2` — the rebuild AND the `{:commit_graph_loaded, ...}` success branch. The agent TREE still renders `@agents` only.
- **`commit_graph_groups/1`** groups eligible agents (`repo_root`, `base_commit`, `current_commit`, `task_id` all binaries) by `{repo_key, task_id}` (repo_key = `repo_root`) with per group `%{repo_key:, task_id:, live_tips:}`, where `live_tips` = the de-duplicated `current_commit`s of the group's NON-ended agents only (a retained/ended agent contributes its entry but never a tip — its commits are already in the task's durable ref ancestry). Sorted by `{repo_key, task_id}`; an empty group list marks the view loaded with an empty graph.
- **`spawn_commit_graph_fetch/2`** runs in an `EvoDash.TaskSupervisor` child (never the LiveView process), calls the runner ONCE per group through `CommitGraphRefresh.fetch_result/3` (the per-group limit is `CommitGraphRefresh.limit/0`, 100) and sends `{:commit_graph_loaded, node, seq, result}` where `result = {:ok, raw_by_repo} or {:error, reason}`.
- **PARTIAL SUCCESS** (`CommitGraphRefresh.fetch_result/3`): a reply other than `{:ok, %{commits: list}}` drops only THAT group's data; the remaining groups still fold into `raw_by_repo`, so a page with several repos/tasks renders the successful groups when a single git RPC fails (a failed group's repo still shows its lanes/START-END from the agent set — only its commits stop at the last fetch). `{:error, reason}` is sent ONLY when EVERY group failed, carrying the LAST failing group's `{:commit_graph_repo_failed, {repo_key, task_id}, reply}` (the reduce PREPENDS failures); for a single-group page that is exactly the former halt shape, so the renderer's error strip (first load) / stale-warning strip (after a load) semantics are unchanged.
- **`raw_by_repo` is keyed by `repo_key`** (the assembler groups agents by `repo_root || repo_id`): groups sharing a `repo_key` (two tasks in one repo) are UNIONED via `CommitGraphRefresh.merge_repo_graph/5` — commits de-duped by `:sha` (non-map entries dropped), `refs` name lists unioned per sha, and each reply's `truncated` flag OR-unioned (the merged entry always carries an explicit boolean).
- The runner seam is `:agents_commit_graph_runner` (arity 5, default `&EvoDash.NodeContext.list_task_commit_graph/5` — the durable TASK-SCOPED core RPC), resolved AT SPAWN TIME; the spawn wraps `fetch_result/3` in `EvoDash.SafeCall.run/1` (an EXIT becomes `{:error, :commit_graph_fetch_failed}`, a folded per-group error passes through verbatim) so the result message is always sent and the view never wedges on a spinner.
- The `{:commit_graph_loaded, ...}` result is stale-guarded on the viewed node AND the monotonic seq; a stale node/seq is dropped, `{:ok, raw_by_repo}` builds + assigns the graph from `commit_graph_agents/1` (clearing loading/error AND re-storing `@commit_graph_fingerprint`), `{:error, reason}` only clears loading and records the error (the last good `@commit_graph` stays rendered).
- **Throttling**: a refetch is skipped when `@commit_graph_fetched_at` is within the minimum interval (1000 ms, read AT CALL TIME through the private `commit_graph_min_interval_ms/0` using the app-env seam `:agents_live_commit_graph_tick_ms`, default 1000 — the SAME helper feeds the private `schedule_commit_graph_tick/1`, so the throttle window and the armed tick delay never diverge); a throttled request arms ONE one-shot `:commit_graph_tick` (never a repeating poll — `@commit_graph_tick_scheduled` guarantees one timer per window) whose `CommitGraphState.tick/1` handler re-attempts with `force: true` (bypassing BOTH the throttle and the fingerprint gate).
- Refresh triggers: `AgentMerge.apply_result/2` and `AgentMerge.flush/1` answering `:refresh` are both followed by ONE `CommitGraphState.maybe_load(socket, [])` call in the LiveView; first activation and the tick use `force: true`.
- **Base-node de-duplication relies on the assembler**: the task-scoped fetch INCLUDES the real base commit as its own node, and `CommitGraph.base_shas/2` suppresses a synthesized `kind: :base` node whenever the sha IS present in the fetched commits — so a fetched commit equal to an agent `base_commit` renders as a NORMAL `:commit` node and is NEVER duplicated. Do not add a second base node.
- **The per-group limit is FLAGGED in the data layer**: the core `CommitGraph.for_task/4` returns `commits` capped at 100 per tip range plus `truncated: boolean` (true when a tip range was cut), which `merge_repo_graph/5` OR-unions per repo_key and `CommitGraph.build/2` surfaces as `repo_view.truncated`; the renderer does not yet render a "+N more" indicator, so a long-running task's older commits just stop appearing.

### Retained ended agents (in-session)

The core DELETES an agent's ETS rows (and its `evogit-agent-*` branch) when it recycles it, so without retention a finished agent would vanish from the TEMPORAL view and take its lane of rows plus its START/END markers. `@retained_agents` (`%{agent_id => agent_map}`) is the in-session remedy — committed agents only, NOT a durable store (the core persists no per-agent commit attribution, so retention does NOT survive a page reload).

- A retained entry is the agent's full last-known map with `ended: true` added (`Map.put(agent, :ended, true)`), preserving `id, task_local_id, task_id, repo_id, repo_root, depth, status, base_commit, current_commit, usage, ...`.
- `AgentMerge`'s private `apply_agent_removed/2` (the `{:agent_removed, id, node}` flush path) captures the removed row into `@retained_agents` instead of only dropping it, and KEEPS `selected_agent_id` pointing at it (the graph's START/END annotation must persist; the detail panel renders its natural "Agent not found" empty state). The rest of the cleanup is unchanged (removed from `@agents`, children orphaned to `parent_id: nil`, parent's children refreshed, tracking sets/`repo_trees` cleaned).
- `AgentMerge.apply_result/2` (full refresh): any id in `@agents` or `@retained_agents` but ABSENT from the fresh list moves into `@retained_agents` marked `ended: true` (private `retain_absent_agents/3`); an id present in the fresh list is DROPPED from `@retained_agents`. Nothing is mass-retained on the first apply / after a node switch (both lists are empty then).
- `AgentMerge`'s private `merge_registered_agent/3` deletes the id from `@retained_agents` — a live agent supersedes its retained copy.
- `CommitGraph.build/2` reports the flag as `ended` on the entry in the `agents` list; retention contributes agent entries and grouping (a group whose agents ALL ended still gets fetched — with empty `live_tips` — so the whole task is recovered from its durable refs) but never tips.

### Commit-Graph View Model (`CommitGraph` + `commit_graph/`)

`build/2` (collapsed — identical to `build(raw_by_repo, agents, MapSet.new())`) and `build/3` (3rd arg = the EXPANDED fold keys: a `MapSet` or list of binaries; any other shape means collapsed) return one `repo_view` per repo group, sorted by `{repo_name, repo_dom_id}`, from a raw `%{repo_key => %{commits:, refs:, truncated:}}` map. `fold_keys/2` lists every fold key (the "expand all" driver); `grouping_key/1` (`repo_root || repo_id`) and `repo_display_name/1` ("Primary Repo" / path basename / "Repo: <repo_id>" / "Unknown Repo") are shared with `TreeView`. Total: defensive `Map.get/2` reads, non-map input degrades to empty nodes/edges/agents, never raises, no try/rescue.

- **Nodes** — every ADDRESSABLE fetched commit (de-duplicated by sha) PLUS one synthesized `kind: :base` node per distinct agent `base_commit` absent from the fetched commits PLUS one `kind: :noop` stub per no-op child (empty progress path — `current_commit` nil, equal to its base, or absent from the fetch). Key set: `%{sha, short_sha, message, author_name, date, refs, row, column, depth, kind, owner_id, start_ids, end_ids}` (`kind: :commit | :base | :noop | :gap`); `short_sha` = the commit's `:short_sha` else `String.slice(sha, 0, 8)`, `message` = first line (`""` for base/noop), `date` a `%DateTime{}` or nil, `refs` a list (`[]` for base/noop), `row` the unique top→bottom position, `column`/`depth` the owner's lane/depth (0 for unowned), `owner_id` the owning agent id (nil = unowned), `start_ids`/`end_ids` the agents forking from / tipping at the sha (a stub is only ever its child's END).
- **Rows — global interleaving** — every node carries a cycle-safe topological LAYER over its PRESENT parents (`L = 0` with none, else `max(L(parent)) + 1`; memoized DFS with a `visiting` set so a malformed cycle terminates; base nodes join as parentless pseudo commits). Rows sort ascending `{L, date_unix, sha}` (missing date → 0), so parents sit strictly above children while parallel agents interleave by date instead of forming per-agent blocks.
- **Lanes (one per agent)** — agents order in a DFS / SUBTREE-CONTIGUOUS walk: pre-order from the ROOTS (nil `parent_id`, or one matching no agent of the group), children visited recursively in stable `{task_local_id, agent_id}` order, so every parent's subtree occupies CONSECUTIVE lanes; a cycle stops the walk and unreachable agents are appended as fallback roots. `depth` is not an ordering key. Each agent owns ONE lane = its index, SHIFTED RIGHT BY 1 when the repo has ≥1 unowned node, so lane 0 is the NEUTRAL lane for pre-task/disconnected commits.
- **Ownership / progress path** — a first-parent walk from `current_commit` backwards that stops WITHOUT collecting at a non-binary sha, at `base_commit`, at an already-seen sha or at a sha absent from the fetched graph (yields NEWEST → OLDEST). A commit on ≥1 agent's path belongs to the agent with the MAXIMUM depth (ties: smallest agent-order index); a commit on NO path inherits the owner of the commit it is the FIRST parent of (deepest owned child, ties by smallest index), resolved in DESCENDING layer order, else it is UNOWNED; a base node belongs to the agent with the smallest `{depth, index}` forked from it; a stub belongs to its child. A repo without agents has no nodes, edges or agents.
- **Edges** — `%{from_sha, to_sha, from_column, from_row, to_column, to_row, kind, owner_id}`; no edge ever carries `to_sha: nil`. Commit edges: `kind: :parent` for the FIRST present parent and `:merge` for every other (`owner_id` = the child node's owner), identical `{from_sha, to_sha}` pairs de-duplicated, and DROPPED when the UNORDERED sha pair equals an agent-level edge's. Agent-level edges (per child C whose parent P resolves in the group): `:spawn` dashed from the fork node (`C.base_commit`) to C's OLDEST progress-path commit (or its stub), `owner_id` = C; `:merge_back` dashed from C's tip (or stub) into P's lane, landing on the TOPMOST P-owned node strictly BELOW the source, else the NEAREST P-owned node ABOVE, else DROPPED — NEVER a mid-air stub and never on the source's own row (a real parent-lane `:merge` already covers an actual merge). Sorting: commit edges by `{from_sha, to_sha}`, agent edges by `{kind, owner_key, from_sha, to_sha}`; `edges` = commit ++ agent.
- **`agents` list** — one entry per agent in lane order: `%{agent_id, task_local_id, status, depth, lane, parent_id (raw), color, start_sha, end_sha, ended}` (`start_sha`/`end_sha` = `base_commit`/`current_commit`, `ended` = `Map.get(agent, :ended) == true`).
- **Folding — COLLAPSED BY DEFAULT** — `CommitGraph.Fold` keeps only structural ANCHORS visible: the lane owner's START and END, any node named in any `start_ids`/`end_ids`, every node carrying `refs`, every `:base`/`:noop` stub and every unowned neutral-lane node. A maximal run of hidden interior commits on ONE lane folds ONLY at length ≥ 2 into EXACTLY ONE `kind: :gap` node (`sha: "gap-" <> fold_key`, empty `short_sha`/`message`/`author_name`/`date`, `refs: []`, empty `start_ids`/`end_ids`, the run owner's `column`/`depth`, plus `fold_key`, `hidden_count`, `expanded`) in BOTH states; it takes the run head's row slot, so visible rows re-index `0..n-1`. A lone hidden commit stays a real `:commit` row, never hidden and never aliased. `fold_key = "<agent_key>|<above_key>|<below_key>"` with the nearest VISIBLE same-lane anchor shas and `"^"`/`"$"` sentinels, stable while the commit set is unchanged. ONE alias map (hidden sha → its gap sha) covers commit AND agent-level edges, so a connector into a hidden commit lands on the visible gap row; an edge whose endpoints alias to the same node is dropped. `repo_view.fold_count` counts the runs (expanded or not); an unknown/stale key is ignored. A fold toggle rebuilds the pure view model in-process from `@commit_graph_raw` — NO git RPC, no fetch spawn, no throttle/fingerprint consultation.
- **Depth hue (verbatim)** — `color = EvoDashWeb.ThemeColor.hsl_to_hex(hue, 70, 54)` with `hue = Integer.mod(round(depth * 137.508) + 265, 360)` (golden-angle step, +265° offset; depth 0 = `#7c38dc`); non-integer/nil/negative depth → 0. Node fills, edge strokes, status palettes (`EvoDashWeb.Helpers.agent_status_svg_color/1`) and per-theme CSS-var tokens are the renderer's concern.
- **Output shape** — `%{repo_key, repo_dom_id, repo_name, node_count, edge_count, row_count, column_count, truncated, fold_count, nodes, edges, agents}` with `row_count == node_count`; `nodes` sort by `row`; `truncated` is the raw flag surfaced verbatim (present on empty-body views too). `repo_dom_id` is the stable DOM id; the module emits no further render/DOM concern.

## Inspector RuntimeStream Reducer

`RuntimeStream` is a pure inspector reducer with `new/2`, `seed/3`, `apply_batch/4`, `active?/1`, `replace_activity/2`, `current_call_id/1` and `checkpoint_transition?/2`, independent of the Assistant transcript reducer.
Core snapshots and ordered activity events carry `%{phase: :idle | :llm_waiting | :llm | :llm_complete | :retry_wait | :tools | :compressing | :preparing, current_call: nil | %{id: binary, turn: integer, attempt: integer, text: binary, thinking: binary}}`.
`:compressing` (a context-compression LLM call) and `:preparing` (assembling the next turn between a tool batch and the next request) are admitted NON-call phases: stored and labelled, but only `:llm_complete`/`:tools` prove generation completion and only `:llm` is an active call phase.
- An activity event replaces the WHOLE current-call projection, including full accumulated text/thinking; ordinary text/thinking chunks append only to an existing call.
- Core captures current-call content even without watchers, so a mid-call snapshot proves complete source capture when both text and thinking are explicit binaries — no invented coverage flags or message-start events.
- The reducer stores the authoritative phase in `state.activity` and bounded content in `state.projections`. Only the current call is retained: `%{identity: %{id: id}, turn:, attempt:, message_index:, response:, thinking:, tool_calls:, complete:, generation_complete:, capture_coverage:, chunks_seen:, omitted_response_bytes:, omitted_thinking_bytes:, omitted_tools:}`.
- Same-id replacement preserves tool descriptors and the local DOM ordinal; a fresh attempt id replaces all old content and tools and advances that ordinal even after retirement. `current_call: nil` retires all excerpts and tools (including aborted retries and checkpointed calls), and later chunks, accounting, yield or tool announcements cannot resurrect them.
- Generation completion follows only `:llm_complete` or `:tools` — never turn accounting, yield, retry, failure or lifecycle finish. Yield updates lifecycle/status to `:awaiting_input` without treating its checkpoint response text as another live replacement; finish freezes later events without asserting successful generation. `active?/1` means only a nonterminal running/cancelling lifecycle.
- `seed/3` preserves agent/node ownership and raw checkpoint messages, rejects an explicitly foreign agent, and prefers an explicit nonnegative seq over the embedded seq over zero. Atomic reseeding preserves the DOM ordinal and same-call tool descriptors but replaces response/thinking from the snapshot's complete prefix rather than appending it; an admitted snapshot with missing/malformed/empty activity (or explicit `current_call: nil`) clears stale projections, response, thinking and tools while preserving the monotonic ordinal.
- `apply_batch/4` rejects stale/invalid seq, foreign agent and post-finish events; unknown events are inert and an accepted newer batch still advances the watermark. `current_call_id/1` reads only the live call id; `checkpoint_transition?/2` scans every ordered activity replacement in a batch for retirement/replacement of an existing call, even when a later event starts another call in the same batch.
- Snapshot admission, node guards and watch-generation guards belong to StreamWatch. The obsolete top-level in-flight, message-start, flattened-activity and caller-owned capture-coverage protocols are not consumed, and no checkpoint-message identity reader or content/turn/index-based suppression API is exposed.
- `StreamLimits` owns the budgets: UTF-8-safe copied prefix slices; bounded appends never first concatenate an unbounded chunk; once bytes are omitted later chunks are counted rather than inserted after a missing UTF-8 boundary; an authoritative replacement recomputes missing bytes from its full value (no double-counting retransmits); tool retention keeps the first 20 descriptors, counts later unretained announcements and upgrades matching anonymous announcements when dispatch supplies ids; tool results still update retained descriptors; names carry exact byte omissions and tool announcements never imply execution. Checkpoint messages and opaque protocol identities are never truncated by the excerpt policy, and no raw history text is extracted here.

## Inspector StreamWatch Lifecycle

`StreamWatch.attach(socket, agent_id)` subscribes in the connected LiveView process and asynchronously registers that same LiveView pid through one serialized, consumer-monitored worker.
Forward `{:inspector_stream_ready, node, token, agent_id, result}` to `StreamWatch.ready/5` and `{:agent_delta, agent_id, seq, events}` to `StreamWatch.push/4`, then render `socket.assigns.inspector_stream.state` as the `RuntimeStream` projection.
`active?/2` includes initial snapshot-pending and reconciling watches and excludes errors, letting the page suppress independent whole-history reads while watched.
The rendered checkpoint source is exclusively `inspector_stream.state.messages`, atomically seeded with live activity from `inspector_stream.snapshot`.
- `reconcile/1` coalesces explicit refreshes while a request is outstanding and retains the old coherent checkpoint/live pair while buffering every newer delta. A batch retiring or replacing the existing current call starts reconciliation BEFORE applying any event in that batch, so checkpoint adoption never mixes with an obsolete live excerpt.
- Forward `{:inspector_stream_reconciled, node, token, agent_id, request, result}` to `reconciled/6`, whose guards require the viewed node, watch token, agent id and current outstanding request. Reconciliation reuses the SAME idempotent watcher-registration runner and serial worker without unregistering between snapshots, preserving the live subscription.
- An admitted snapshot replaces checkpoint messages and activity together, and buffered batches replay only above its authoritative sequence. Replay crossing another ownership boundary freezes that entire batch and starts another coalesced snapshot request rather than rendering an inconsistent pair.
- The stream fields `snapshot_request`, `reconciling` and `required_seq` distinguish the outstanding request and its minimum watermark from the rendered `seq`. A snapshot before its triggering boundary, an RPC failure or a buffer overflow visibly FAILS the watch while preserving the last coherent rendered pair and requires explicit reattachment; there are NO automatic error retries.
- `detach/1` clears the render state and consumer-local subscription immediately, with asynchronous serialized unregister on selection, node or lifecycle teardown. Keep `inspector_stream_token`, the private `inspector_stream_worker` and `inspector_stream_worker_monitor` bookkeeping across page resets, since tokens must stay monotonic and the same worker orders rapid A→B→A registration changes.
- Forward worker `{:DOWN, ref, :process, pid, reason}` messages to `StreamWatch.down/4` after handling other page-owned monitors; a matching death explicitly fails the watch, unsubscribes and allows a retry, while unrelated monitors are inert.
- Pending remote contexts cannot attach locally; readiness and push application require the current viewed node; negative sequence watermarks are rejected; a snapshot explicitly naming another agent fails the watch.
- Initial attachment and reconciliation deltas buffer up to 128 ordered batches or 1 MiB; duplicate/stale batches consume no capacity; overflow or supervisor-start failures produce explicit watch errors instead of silent loss or stuck loading.
- Runner seams are `:agents_watch_runner` and `:agents_unwatch_runner`, both `(node, agent_id, liveview_pid)`, defaulting to the corresponding `NodeContext` watcher functions. The worker performs RPC through `SafeCall`, cleans up after consumer death and uses no polling; delta messages have no publisher-node stamp.
- `closed/4` admits the direct `{:agent_stream_closed, agent_id, snapshot, seq}` terminal handoff atomically, including after a finished delta, summary removal or failed async snapshot request. Admission requires a `Snapshot` with matching agent, `phase: :done` and embedded sequence, selected-agent/current-token/target-id/viewed-node ownership, and a sequence at least as new as the rendered, required and buffered watermarks. The final handoff replaces checkpoint messages and activity together, clears pending buffers/errors, unsubscribes live deltas and seals the pair against late ready/reconciled failures, worker death and deltas without replaying older buffered events. `RuntimeStream.seed/3` treats `:done` as terminal and preserves the snapshot's terminal status when present.
- `owns?/2` includes selected pending, failed and terminal watches, `terminal?/2` means an admitted final handoff and `active?/2` excludes that sealed watch. A same-target attach preserves a sealed watch; only explicit selection/node/lifecycle teardown should detach it. The parent must retain the selected watch across summary removal or absence, forward the handoff to `closed/4`, project its checkpoint in the same callback and use the retained ended agent row to keep the selected detail panel visible. No handoff can recover an already-detached watch, and retained terminal history remains page-local rather than durable.

## Inspector Stream Presentation

`StreamPresentation.build/1` applies a second render cap of 12_000 graphemes per response/thinking part and at most 20 tools without mutating the reducer or checkpoint history; the public max-message budget stays 12 (equal to `StreamLimits.max_projections/0`), but production state contains only the current call and retirement removes its article.
Grapheme omission fields describe render-stage loss, while byte omission fields sum reducer and render loss without counting full replacements twice.
`StreamPresentation.activity/1` translates the eight core phases for display: `:llm` → `:llm`, `:tools` → `:tool`, `:idle` → `:idle`, `:llm_waiting` → `:waiting`, `:llm_complete` → `:llm_complete`, `:retry_wait` → `:retry_wait`, `:compressing` → `:compressing`, `:preparing` → `:preparing`; anything else (absent/malformed) → `:unknown`.
The label text exists in exactly ONE place, `StreamPanel`'s `#inspector-activity`: `:llm` → "Generating response", `:tool` → "Executing tools", `:idle` → "Idle", `:waiting` → "Waiting for model capacity", `:llm_complete` → "Response generated", `:retry_wait` → "Waiting to retry", `:compressing` → "Compressing context", `:preparing` → "Preparing next turn", any other value → "Activity unavailable".
"Idle" therefore renders ONLY from an ADMITTED server phase (a `%Snapshot{activity: %{phase: :idle, current_call: nil}}` or an `{:activity, %{phase: :idle, ...}}` delta) — never from a client-side timeout, placeholder or missing state; a snapshot without activity renders "Activity unavailable" and a pre-snapshot watch additionally shows "Connecting to live updates…".
No inspector timer re-renders or ages the label: it shows the last admitted phase until the next delta/snapshot, so a stale `:idle` is a SERVER fact.
`RuntimeStream.replace_activity/2` updates the phase ONLY when the activity map carries a `:current_call` key (nil or a call map) AND the phase is one of the eight; a map missing that key or naming another phase leaves the previous phase rendered. An unrecognized phase never degrades to "Idle": a live delta keeps the last admitted label, and only a snapshot whose activity is absent/unknown renders "Activity unavailable" (a seeded snapshot phase outside the eight is dropped by the same guard).
`thinking_status/1` returns `:none` only for generation-complete, completely captured, empty and unomitted thinking (`StreamPanel` then renders exactly `gettext("No thinking content available")`); missing thinking in malformed call data remains `:unavailable` (partial capture), and no lifecycle, accounting or caller-supplied flag upgrades it.
`StreamPanel.stream_panel/1` exposes a cohesive `#inspector-stream` tail-row container placed AFTER checkpoint rows inside the memory list, with no separate heading, panel border, checkpoint-position explanation or standalone skeleton.
Each current-call article retains `inspector-live-message-N` and `data-inspector-message="live-N"`, matches the history row's styling and assistant icon/identity header, and displays activity plus an in-row compact generation indicator with the existing `inspector-thinking` accessibility/reduced-motion contract.
Shared status chrome appears in the live row's header, or as a compact status-only row when no projection exists, preserving connecting/error/Retry without fabricating an assistant message.
`StreamPanel` escapes bounded content, shows all byte/tool omissions and exposes the parent-owned `retry_inspector_stream` event on transport errors.
It gates the live header's `#inspector-thinking` skeleton, cursor pulse and thinking-summary-only `.inspector-thinking` shimmer on `message.active` AND an error-free watch, so completed calls and failed watches retaining `:llm` excerpts stay static and reduced motion is respected.
The activity protocol has no distinct thinking-versus-response streaming subphase, so active LLM generation is the most precise existing animation predicate without new producer signals.
`RuntimeStream.message_index` is a local monotonic live-call DOM ordinal, not an index into checkpoint messages, and neither it nor `turn` can identify a checkpoint bubble to replace.
The detail panel never calls `OptimisticMessages.merge/2` directly: `Inspector.merged_history(agent, page.optimistic_messages)` (used by `DetailPanel`) is the ONE entry source for the panel, and it returns `agent.history` verbatim (no merge, no per-entry hashing) when that agent has no optimistic entries.

## Inspector Streaming Integration & Protocol Boundaries

The parent page forwards ready, reconciled and delta messages through StreamWatch and projects the admitted state's raw messages into checkpoint rows in the SAME callback as the live-state update.
Support owns reconciliation requests, snapshot admission and bounded buffered replay, while the parent owns checkpoint-row rendering without speculative response/thinking suppression.
Watch tokens and serialized worker bookkeeping survive scope resets, and snapshot-pending, reconciling and failed watches own their checkpoint rows exclusively.
Independent history reads and late history results cannot overwrite a watched checkpoint/live pair, including a failed watch's last coherent pair.
Explicit watched-history Retry and full-message refresh use `StreamWatch.reconcile/1`, while unwatchable agents retain the separately scoped independent history fallback.
The detail panel's history list is TWO nested elements: the OUTER `#agent-history-scroll-<id>` (`class="agent-history-scroll overflow-y-auto bg-base-200/50 border border-base-300 rounded-lg"`, `phx-hook="AgentHistoryAutoScroll"`) is the ONE bounded scroller and a DIRECT child of `.agent-detail-history` (CSS pins `.agent-detail-history > .agent-history-scroll { flex: 1 1 0 }`); the INNER `#agent-history-<id>` keeps `phx-hook="InspectorMessages"` plus `data-inspector-scope` (node/target/selection/watch/snapshot scope) and the checkpoint rows' stable `data-inspector-message` markers, so every existing DOM id is unchanged.
The inner element carries `divide-y divide-base-300`, preserving the pinned entrance-animation selector `.agent-history-scroll > .divide-y > div` (`InspectorMessages` animates only newly keyed rows, respects reduced motion and never scrolls — scrolling belongs to `AgentHistoryAutoScroll` alone, ONE hook per element).
The `#inspector-history-error` banner is the inner element's FIRST child; the `StreamPanel.stream_panel/1` tail row is its last.
Core transport and snapshot contracts live in `apps/evo_git/lib/evo_git/agent/stream/CONTEXT.md` and lifecycle/activity limitations in `apps/evo_git/lib/evo_git/agent/session/CONTEXT.md`.
The core snapshot includes session-owned `activity: %{phase:, current_call: nil | %{id:, turn:, attempt:, text:, thinking:}}`; ordered `{:activity, projection}` events replace that projection while ordinary text/thinking events append to its current call; and the snapshot atomically captures checkpoint `messages`, complete accumulated `activity` and its authoritative `seq`, with a completed current call remaining available until atomic checkpoint retirement.
Core phases are `:idle`, `:llm_waiting`, `:llm`, `:llm_complete`, `:retry_wait`, `:tools`, `:compressing` and `:preparing`; activity capture continues without watchers, and watch/snapshot flush pending events before returning the authoritative sequence.
The inspector adopts `activity.current_call` from snapshots and replacements and appends only strictly newer chunks through the existing StreamWatch buffering/sequence admission. Fresh core call ids separate retry attempts, and nil current-call retirement clears obsolete live excerpts without modifying raw checkpoint history.
Protocol boundaries:
- Tool-result/yield/finish events alone cannot replace the automatic retirement/replacement snapshot trigger.
- Hand-built StreamWatch fixtures must include `snapshot_request: 0`, `reconciling: false` and `required_seq: 0`, preserve real snapshot agent ids, and account for duplicate/stale batches not consuming buffer capacity.
- Activity fixtures use real nested `current_call` projections; synthetic `in_flight`, flattened activity identities, `message_start`, bare chunks without a current call and the removed `message_identity/1` API are not supported protocols.
- All eight core phases have truthful presentation labels, and successful empty-thinking notices require complete binary capture plus `:llm_complete` or `:tools` (never `:compressing`/`:preparing`).
- Current deltas expose text/thinking chunks and tool id/name/status but not tool arguments, result bodies or full history-message changes.
- There is no checkpoint-message call identity or checkpoint-coverage watermark, so checkpoint suppression and historical excerpt reconciliation by guessed turn/content are unsupported.
- The inspector uses its own bounded `RuntimeStream` reducer rather than the Assistant's bubble-oriented `Delta` reducer (`../home_live/CONTEXT.md`), and neither is a lossless history model.

## Send-Message Flow (`SendMessage` + `agents_live/modals.ex`)

- **Events**: `open_send_message` → `SendMessage.open/2` (a STRING agent id → `send_message_agent_id` + cleared `send_message_text`), `close_send_message` → `close/1`, `validate_send_message` (`phx-change`) → `validate/2`, `send_agent_message` → `send/3` (params `%{"agent_id" => id, "message" => message}`). Delivery goes through `EvoDash.NodeContext.send_user_message/3` inside the private `send_user_message_safely/3`, which resolves the call-time `:agents_send_message_runner` seam, wraps the call in `EvoDash.SafeCall.run/1` and FLATTENS the wrapper (a call timeout / dead scheduler becomes `{:error, reason}` instead of exiting the LiveView).
- **Return matching**: only `{:ok, :ok}` is a real success (local AND remote). A missing agent is `{:ok, {:error, :not_found}}` (the local path wraps the RemoteAPI result), erpc failure `{:error, reason}`; both (and any other unexpected return value) show the `"Failed to send message: %{reason}"` flash rather than crashing the page. Success appends the optimistic user message (`OptimisticMessages.append/3`), shows `"Message sent to agent"` and closes the modal.
- **Send chain**: `EvoDash.NodeContext.send_user_message/3` → `EvoGit.RemoteNode.send_agent_message/3` (local = direct, remote = `:erpc.call`) → `EvoGit.AgentScheduler.RemoteAPI.send_agent_message/2` → `EvoGit.AgentScheduler.send_user_message/2` → `Store.append_pending_user_message/2`, which appends to the agent's inbox in `EvoGit.AgentScheduler.ControlPlane` (the summary row carries no message queue). Answers `:ok`, `{:error, :not_found}` or `{:error, :scheduler_not_started}`.
- **Pending messages drain at the agent's next turn**: `RemoteAPI.get_agent_history/1` serves the LIVE `EvoGit.Agent.Session`'s conversation (`[]` once the session is gone) — the summary row carries no `context` — so the queue drains only at the top of the agent's next turn: `EvoGit.Agent.Exchange.Pending.drain_and_inject_user_messages/2` drains via `Store.drain_pending_user_messages/1` (`ControlPlane.drain_messages/1`) and appends each message as a `user(msg)` role entry tagged with the current turn. ## Agent Event Contract (push-based, node-identity, coalesced flush)

The Agents page is FULLY push-based — there is NO periodic poll.
The `:evo_git` emitters broadcast EXACTLY these four shapes on `EvoGit.PubSub` topic `"agents"`, every one carrying the BEAM node atom of the publisher.
Every event is node-filtered FIRST via `EvoDashWeb.LiveHooks.NodeAware.event_from_current_node?(socket.assigns, event_node)` (viewed node identity = `socket.assigns[:current_node]`; local → `node()`, remote → the remote daemon's BEAM node atom). Foreign-node events are dropped BEFORE buffering — they never arm a flush and never leak into the viewed node's tree.
The three incremental events (`:agent_registered` / `:agent_updated` / `:agent_removed`) are COALESCED: each `handle_info` clause only hands the raw event to `AgentMerge.buffer_event/2`, which node-filters it, appends it to the `:pending_agent_events` assign (`PendingEvents.append/2`, newest-first) and arms ONE trailing-edge timer.
The flush window is read AT CALL TIME at `AgentMerge`'s private `maybe_schedule_agent_flush/1` site via the app-env seam `:agents_live_flush_ms` (production default `PendingEvents.flush_ms/0` = 300 ms) so tests can shrink it; `PendingEvents` itself stays PURE (no app-env reads), and the message name `:flush_agent_events` plus the one-timer-per-window gating (`:agent_flush_scheduled`) are unchanged — only the FIRST event of a window arms the timer, later events just append.
`{:agents_updated, node}` → `AgentMerge.buffer_refresh/1` sets the coalesced `:pending_agents_refresh` boolean and arms the same timer — never one refresh per event.
`handle_info(:flush_agent_events, socket)` calls `AgentMerge.flush/1`, which drains the buffer in ARRIVAL order (`PendingEvents.drain/1`) and answers `{socket, after_flush}`: the LiveView turns `:refresh` into ONE `Loader.spawn_refresh/1`, `:refetch` into ONE `Inspector.refetch_selected_history/1`, and `:none` into nothing.
One flush therefore yields exactly ONE render/DOM diff for the whole burst — no LiveView mailbox starvation of user `phx-click`/`phx-submit` events, and no burst/blink when a backgrounded tab is foregrounded.
The buffer + `:agent_flush_scheduled` + `:pending_agents_refresh` are seeded in `mount/3` and RESET on the `handle_params/3` node-change branch (stale-node events never leak); a timer already in flight after a node switch is harmless (the buffer is empty, so the flush is a no-op).
The fallback refresh is COALESCED: a buffered `:agent_registered` with an incomplete summary, a buffered `:agent_updated` for an unknown id, and a `{:agents_updated, node}` all set the refresh flag, and the flush's `:refresh` answer spawns AT MOST ONE `Loader.spawn_refresh/1` (async full reload, seq-guarded via `@refresh_seq`).
All heavy loads stay in `EvoDash.TaskSupervisor` children — never in `handle_info`.

- `{:agents_updated, node}` — throttled bulk-change signal → node-match → sets the coalesced refresh flag → one `Loader.spawn_refresh/1` per flush window; foreign → ignored.
- `{:agent_registered, id, summary, node}` — carries the agent's full summary (the same `RemoteAPI.list_agents/0` shape `LoadData` consumes: `id, task_local_id, repo_id, repo_root, task_id, task_number, status, depth, parent_id, worktree, retries, agent_module, model_id, objective, context_path, current_commit, base_commit, usage, total_tokens, compression_count, compression_threshold, context_window, message_count`). Applied at flush time and merged IN-MEMORY for BOTH local and remote through ONE shared path (private `merge_registered_agent/3` → private `build_registered_agent/2`): the row uses the `LoadData` field mapping (defaults for absent fields, `usage` normalized to a `%Usage{}` struct), derived fields are recomputed exactly like the load path (children/`has_children` from `parent_id`, effective `compression_threshold` from `ThresholdCache.threshold_for_agent/2`, `compression_pct` from `total_tokens` + that threshold, `context_window` from `ContextMeter.context_window_from/1`), inserted at the sorted `{depth, id}` position, the parent's children list refreshed, and `id_to_display`/`previous_agent_ids`/`new_agent_ids`/`repo_trees` updated. A duplicate id (race with the `{:agents_updated, node}` fallback) is a no-op; a summary missing `status`/`depth`/`parent_id` sets the coalesced refresh flag.
- `{:agent_updated, id, changed_fields, node}` — `changed_fields` NEVER contains `:context`. Applied at flush time, the in-memory merge runs for BOTH local and remote; special fields: `context_node` → `context_path`, `phylo_node` → `current_commit`, nil `usage` → zero, `compression_pct` recompute on `total_tokens` OR `compression_threshold` (a nil/non-positive threshold delta keeps the row's previous denominator, so a percentage can never divide by nil), `context_window` is NOT part of the delta contract (the merge keeps the row's value when the delta omits it, and a nil/non-positive delta value restores the previous known window — a known window is never reset to the 200_000 default), children recalc on `parent_id`, status-change tracking into `previous_statuses`/`changed_status_ids`, `id_to_display` on `task_local_id`, `repo_trees` rebuild on `context_node`/`repo_root`, and the queue anchoring described above on `:pending_user_messages` (a delta WITHOUT that key leaves the queue snapshot untouched). A missing agent row (race) sets the coalesced refresh flag.
- `{:agent_removed, id, node}` — applied at flush time: the row is dropped in-memory (children orphaned to `parent_id: nil`, parent's children list refreshed, tracking sets/selection/`repo_trees` cleaned) and captured into `@retained_agents` for BOTH local and remote; foreign → ignored.

## Notes for Agents — coalesced flush (one index, one pass)

`AgentMerge.flush/1` answers `{socket, after_flush}` (`:refresh` | `:refetch` | `:none`) and never spawns a task or touches the commit graph — the LiveView performs that ONE follow-up.
A flush builds ONE `%{id => agent}` row index and ONE `%{id => position}` index for the whole burst (`AgentList.by_id/1` / `AgentList.positions/1`), so an `:agent_updated` merge is a map lookup plus a map put instead of `Enum.find_index/2` plus `List.replace_at/2`.
Accumulated merges fold back into the agent list in ONE final `Enum.map` pass, so a burst of k events over n agents costs O(k + n).
Arrival order is part of the contract: every merge reads the CURRENT row — the one already merged earlier in the same burst — as its base. A structural event (`:agent_registered` / `:agent_removed`) first folds the pending merges into the list, then mutates it.
Preserved semantics: the fallback refresh for an unknown agent or an incomplete summary, `Inspector.preserve_terminal/2` retained-terminal settlement, threshold/context-window carry-over (`restore_threshold/2`), `compression_pct` recompute gating, children recalculation on `:parent_id`, ONE `repo_trees` rebuild per flush and at most one selected-history refetch per burst.

`ContextMeter.build/1` derives every percentage as `Float.round/2`-rounded to EXACTLY one decimal and rendered by `:erlang.float_to_binary(_, decimals: 1)` (clamped 0..100), with the numeric and label forms deriving from the SAME rounded float so CSS and `data-*` can never disagree. The fill div carries `style="width: <fill_label>%"` and class `meter.fill_class` (`bg-success` / `bg-warning` / `bg-error`).
Zones (integer math, current vs threshold): `< 80%` → `:success`, `< 100%` → `:warning`, `>= 100%` → `:error`, unknown threshold → `:success`; `fill_class/1` → `bg-success`/`bg-warning`/`bg-error`, `tick_class/0` → `bg-base-content`.
The tick renders only when `meter.tick_pct` is non-nil: an absolutely positioned 2px line (`w-0.5`, `meter.tick_class` = `bg-base-content`, centred via `-translate-x-1/2`) plus a rotated-square cap at its top, at `style="left: <tick_label>%"`, with `title={gettext("Compression triggers at %{tokens} tokens", tokens: format_number(meter.threshold_tokens))}` — built in the template so no tooltip renders when the tick is hidden.
The tile header's right side shows the context readout `current / threshold` (both `EvoDashWeb.Helpers.format_number/1`-grouped; current only when the threshold is unknown), and the caption row shows `gettext("Compression at %{tokens}", …)` (or "Compression threshold unknown" when there is no tick) on the left and `gettext("Compressions")` plus the legacy `count (pct%)` label on the right (`agent.compression_pct` keeps its threshold-relative value).
Zones colour the FILL only; the tick always uses `bg-base-content` so it stays visible over every fill colour and in both themes.
The tick-hidden "Compression threshold unknown" render is only reachable for an agent map carrying NO `:compression_threshold` key: `ThresholdCache.threshold_for_agent/2` always resolves a positive integer (its 180_000 last resort) and the update path restores a known threshold, so the normal page flow never shows the unknown state.

## Notes for Agents — `whitespace-pre-wrap` content must sit flush against its tags

HEEx emits the newline + indentation sitting between an element's opening tag and its interpolated content as a literal text node. Under `whitespace-pre-wrap` (or a `<pre>`) that whitespace is PRESERVED, so a block written across multiple template lines renders with a spurious leading indent.
Rule: every `whitespace-pre-wrap` element must be emitted on ONE line with its interpolation flush against the tags — which is why the page's pre-wrap site (the full-objective modal) is a single-line `<pre ...>…</pre>`.
