# ProjectsLive Support Modules

## Intent

Support modules extracted from `EvoDashWeb.ProjectsLive` to keep the main LiveView module focused on lifecycle callbacks and event handlers.

## Routing Table

None — leaf directory (eight module files: `state_persistence.ex`, `project.ex`, `project_flow.ex`, `assigns.ex`, `github.ex`, `remote_view.ex`, `attach_file.ex`, `async_load.ex`).

## Notes

- **Task-form layout — server-seeded + client-driven**: The task-form layout (compact vs expanded) is seeded server-side at render from prompt length via `TaskFormComponents.layout_for/1` (threshold > 600 graphemes OR > 16 lines) and updated client-side while typing by the AdaptiveInput JS hook (mirrors the same thresholds). The hook also re-asserts the computed layout whenever the server re-seeds `data-layout` from its possibly-stale `@task_prompt` — a MutationObserver on `.input-layout` (attributeFilter: ['data-layout']) re-runs the computation on any server re-render (e.g. toggling mode/model), converging immediately (the hook only writes the attribute when the computed value differs) with zero network events, so the layout never snaps back to compact while a long prompt remains in the box. There is no per-keystroke prompt-change event — the textarea has no `phx-change`, so `@task_prompt` is updated only by `restore_state` and `task_submit` (single, non-keystroke events). Prompt draft persistence is purely client-side (the StatePersistence input watcher in app.js).
- **Post-submit prompt clear**: After a successful `task_submit`, `assign_form_defaults/1` resets `task_prompt: ""` (so the next render seeds `data-layout="compact"`), and the handler pushes a `"clear_prompt"` event (via `push_event/3`). The AdaptiveInput JS hook handles it: it empties the visible textarea (morphdom skips it under `phx-update="ignore"`), re-asserts autogrow + layout (converges — `applyLayout` only writes the attribute when the computed value differs, no MutationObserver loop), and clears the `task_prompt` field in the persisted `dashboard_state` sessionStorage blob so a reload cannot resurrect the submitted prompt. Mode/model selects and all other form state are untouched.
- **task_submit opts contract** (`projects_live.ex:1133-1158` + `do_task_submit/4` at `:2120-2259`): the handler pattern-matches `%{"prompt" => prompt, "mode" => combined_mode}` and builds the start_task opts as `[path: active_project_path, mode: <"new"|"existing"|"simple"|"custom">]` (mode mapped from `genesis_new`/`genesis_existing`/`evolve_simple`/`custom_agent`; `custom_agent` → task type `:evolve` with mode string `"custom"` — the UI combined-mode string differs from the core mode string), then conditionally adds: `:prompt` (genesis — trimmed textarea text) XOR `:objective` (evolve — same trimmed text), `:build_system` (genesis, `String.to_existing_atom`), `:node_path` + `:starting_commit` + `:resume_from` (evolve, non-blank only), `:foreign_repos` (from `@foreign_repos` assign when non-empty), `:archive` (true when checkbox), `:model_id` (from `@selected_model_id`), `:agent` (from `@selected_agent_id` when non-empty). **Custom Agent mode REQUIRES the `:agent` opt**: the handler guards before `do_task_submit/4` — `combined_mode == "custom_agent"` with nil/"" `@selected_agent_id` flashes gettext "Custom Agent mode requires selecting a custom agent." and refuses to start; `task_change` to `"custom_agent"` auto-selects the first custom agent (from `@custom_agents`) when none is selected. Dispatched as `NodeContext.start_task(node, task_type, opts)` when `@remote?` else `TaskRegistry.start_task(task_type, opts)`; `NodeContext.start_task/3` (`node_context.ex:517-519`) is a thin delegate to `EvoGit.RemoteNode.start_task/3`. Other dashboard start_task call sites: `merge_check.ex:128` (auto-resolve: `:evolve` with hardcoded `:objective` + `:starting_commit`/`:merge_from`/`:merge_target`) and `review_live.ex:685` (`:extract_skills`). Objective display reads `opts[:prompt] || opts[:objective]` (`task_card_components.ex:94` and `:489`; `review_live.ex:821`).
- **NO file-upload/attachment machinery exists for objectives**: the objective comes exclusively from the `<textarea name="prompt">` (`task_form_components.ex:161-181`) as a plain form string. Zero hits in evo_dash for `allow_upload`/`Phoenix.LiveView.Upload`/`consume_uploaded_entries`/`live_file_input`/`<.live_file_input>`/`type="file"`/`accept=`; no FileReader-style JS hook (`assets/js/hooks/` = `adaptive_input.js`, `sidebar_collapse.js`, `node_switch_fade.js` only). The only upload-adjacent traces are boilerplate: the standard `:multipart` parser in `endpoint.ex:41`, the live_reload `priv/static/(?!uploads/)` exclusion in `config/dev.exs:50`, and a doc-comment pointer to `Phoenix.Component.live_file_input/1` in `core_components.ex:149`. The directory picker is server-side (wx/native dialog, `EvoDash.DirectoryPicker`) and never reads file contents. No evo_dash code path reads an objective/prompt from disk (evo_dash `File.read`/`File.ls` uses are config.toml, genesis.toml, VERSION, and path-autocomplete browsing only).

## Design Notes — Dashboard Top Bar & Command Palette Keyboard

- **Palette keyboard binding must live on the focused element:** LiveView `phx-keydown` bindings do NOT bubble to ancestor elements — the handler only fires when the focused element itself carries the binding. The command palette's `phx-keydown="palette_keydown"` must therefore be on the search input (project_components.ex), NOT on the overlay div. Since `handle_palette_key/3` (`projects_live.ex`) only acts on special keys — `"Escape"` (closes, any mode), `"ArrowDown"`/`"ArrowUp"` (menu index nav), `"Enter"` (menu selection) — and has a catch-all clause returning the socket unchanged for everything else, printable characters typed into the search input are no-ops server-side: typing + `palette_search` filtering (a separate `phx-change` event) coexist without interference. Event path: input `phx-keydown` → `handle_event("palette_keydown", %{"key" => key}, socket)` → `handle_palette_key/3` (catch-all at the end). Palette close event name: `close_project_palette` (the backdrop uses `phx-click="close_project_palette"` and click-away uses the same name).
- **Top bar spacing (`ProjectsLive.top_bar/1`):** container `dashboard-topbar` uses `gap-3 px-4 py-3`; the Configure button is `btn btn-md btn-ghost gap-2`; dropdown section headers ("Task Options" / "Project Settings") use `text-xs`.
- **No-project hint + page dim:** when no project is open (`is_nil(@active_project)`) and the hint is not dismissed, the LOCAL top bar (only — gated `!@remote and !@hide_palette`) carries `data-no-project="true"`, renders a clickable `.no-project-hint` pill ("Open or create a project", `phx-click="open_project_palette"` + dismiss X with `phx-click="dismiss_no_project_hint"` + `phx-stop-propagation`), and the page body renders `<div class="no-project-overlay" aria-hidden="true">` (fixed, `pointer-events: none`, z-20 — pure visual dim below the top bar's z-30). Events/assigns: `dismiss_no_project_hint` sets `@no_project_hint_dismissed` (mount default `false`; reset to `false` in `activate_project/2` so the hint returns for a future no-project session). The hint/overlay naturally disappear once a project activates. CSS lives in `assets/css/app.css` ("No-Project Hint" section: `.no-project-overlay`, `.dashboard-topbar[data-no-project="true"]` taller padding + box-shadow pulse — NO backdrop-filter/filter/transform on the topbar, containing-block trap; `.no-project-hint`). New gettext strings ("Open or create a project", "Dismiss", "Project path") land in the .pot at release time — do NOT run extract.
- **New-project form is a SINGLE full-path input:** `palette_new_project/1` submits `phx-submit="create_project"` with one `name="path"` field (`id="new-project-path-input"`, `phx-change="new_project_path_input"`, debounce 150, `list="new-project-path-suggestions"`). Backend: `ProjectFlow.create_project/2` takes `%{"path" => path}` and `File.mkdir_p`s missing dirs (returns plain `:ok`!). The open-by-path input placeholder is neutral ("Project path") — no example paths anywhere (`platform_placeholder/1` returns the neutral string for all platforms).

## Performance Notes — Blocking I/O in support modules

The ~1-2s "GET /" load and ~25MB page memory are driven by synchronous I/O in the LiveView process. File:line refs are current. **All node-aware loads run asynchronously** via the AsyncLoad coordinator outside `handle_params/3`: every NODE-AWARE load (custom agents, model profiles, remote agents, remote project config/mode, recent projects) runs in ONE `EvoDash.TaskSupervisor` task per handle_params run via `AsyncLoad.maybe_spawn/2`, and remote project activation runs via `ProjectFlow.spawn_remote_project_activation/2` — see "Async Node-Aware Loads" below. Local-only I/O (SQLite, config, FS) remains synchronous.

### The per-navigation (GET /) cost — why it's slow

LiveView runs `mount/3` TWICE per full page load (dead HTTP render + WebSocket connect), and `handle_params/3` after each. Per mount cycle:

1. **NodeAware.on_mount** (applied to ALL LiveViews via `evo_dash_web.ex`): `NodeContext.list_targets()` (TOML read) + `connection_status()` (GenServer) + **`list_tasks_summary` #1 on the CONNECTED mount only** (node_aware.ex — the dead-render skip gates the sidebar load behind `connected?/1`, so the dead HTTP render fires NO summary query; the connected mount fires exactly one).
2. **ProjectsLive.mount**: `list_recent_projects()` (SQLite) + `Config.resolve()` + `build_systems()` (module attr, pure) + `list_task_ids` #1 + deferred `:load_config_status`. ProjectsLive has no sidebar loader of its own — the unified NodeAware loader is the single path.
3. **handle_params**: `assign_node/2`'s summary reload is dedup-guarded by `:tasks_node_loaded` (node_aware.ex:175-183 — prevents the mount double-fetch and the dead-render re-fetch); ProjectsLive's fallback branches run only the `list_task_ids` notified-set union; with a project → `activate_project` (File.dir? + detect_mode FS + **genesis.toml read** + `list_task_ids`). **The node-aware loads are NOT here anymore**: `AsyncLoad.maybe_spawn/2` (projects_live.ex:754, connected mounts) fires ONE supervised task running the custom-agents / model-profiles / recents / (remote) agents+config+mode loads outside the LiveView process — the result arrives as `{:async_project_load, ...}` a frame later and never blocks this step (see "Async Node-Aware Loads").
4. **`:load_config_status`** (deferred one frame): `EvoGit.Config.config_status()` — re-reads config.toml + credentials.toml (cached parse + stat) — blocks a frame in the LiveView process.

⇒ **A single full page load fires `list_tasks_summary` exactly ONCE** (on the connected mount; the dead render skips it and `assign_node`'s dedup guard suppresses the handle_params re-fetch). Each call blocks the LiveView while the single-connection Store GenServer runs the query and the Task process decodes rows. SPA-style push_patch navigation re-runs only handle_params (dedup-guarded: NO summary, just task_ids + recents + genesis.toml read when a project is active, unless the node context changed).

### Memory (~25MB/page)

Retained in the LiveView heap per tab (N tabs = N copies): `@running_tasks` + `@pending_tasks` — the statuses-filtered summary maps. **`result` is not decoded/read from summary maps** — `show_review_button?` is column-based (`branch_name`) and the summary projection excludes `result`, so the per-row `Codec.decode_result` (which rebuilt `%Usage{}` + archive_records — the largest blob in the DB) never runs for summary rows. `pending_tasks` = every completed-unreviewed-with-branch task (full summary map). Small retainers: `@recent_projects`, `@notified_task_ids` (ids only), `@model_profiles`, `@project_config`/`@commands`/`@foreign_repos`, `@config_status`. LiveView processes live until the tab closes (no `live_disconnect_timeout` in LV 1.2.8).

### Wasteful patterns to fix (candidate list)

1. **Summary query not project-scoped** — scans all projects' running/pending/finalizing/completed rows on every navigation.
2. Store queries serialize on the single-connection Store GenServer with runtime writes.
3. `:node_aware_reload_tasks` (300ms after EVERY task broadcast): `list_task_ids` + summary + genesis.toml re-read when project settings shown — the broadcast-driven hotspot (see evo_git/CONTEXT.md:80).

### Summary decode location

All summary variants delegate decoding to short-lived Tasks (task_registry.ex:416-427, 430-443, 446-457); only `list_task_ids` (460-465) replies inline by design. The **LiveView heap retention** is the remaining memory driver.

## Async Node-Aware Loads

Remote-node data loading on the Projects page never blocks the LiveView process. Two async flows — the handle_params grouped load and remote project activation — spawn supervised `EvoDash.TaskSupervisor` tasks (the established pattern: `github.ex` `maybe_check`, `settings_live.ex:1317-1360`, `review_live/merge_check.ex:197-224`) whose results arrive as `handle_info` messages with stale-guards. Local + remote share ONE code path: `EvoDash.NodeContext` unifies the node, the async conversion applies to the shared path, and the local flow stays synchronous (mount seeds every assign synchronously, so the first paint never depends on the async result — the async refresh overrides it idempotently a frame later).

### handle_params grouped load — `AsyncLoad.maybe_spawn/2`

`handle_params/3` ends with `AsyncLoad.maybe_spawn(socket, prev_node_id)` (`projects_live.ex:754`; connected mounts only, dead renders skip) — ONE supervised task per handle_params run executing the sequence custom agents → model profiles (+ the `selected_model_id` switch validation) → recents → (remote only) remote agents + remote project config/mode. Result: `{:async_project_load, node, prev_node_id, path, results}`; `handle_info` (`projects_live.ex:1729`) applies via `AsyncLoad.handle_result/5` then re-runs `GitHub.maybe_check/1` (the remote `task_mode` now arrives via this continuation — maybe_check is self-guarding, harmless elsewhere).

- **Results-map keys** (`async_load.ex:53-62`): ALWAYS `custom_agents | model_selection_enabled | model_profiles | default_selected_model_id | recent_projects`; plus remote-only extras when the spawn-time context was remote WITH an active project path: `remote_agents | project_config | worktree_script | commands | foreign_repos | task_mode | task_mode_info` (omitted entirely for local nodes — the local `activate_project` flow owns those assigns). `model_profiles`/`default_selected_model_id` are consumed by the continuation itself (resolved into `:selected_model_id`), not blanket-assigned.
- **Stale-guard** (`handle_result/5`, async_load.ex:83-109): the result is DROPPED when the captured `node != socket.assigns[:current_node]` OR the captured `path != socket.assigns[:active_project_path]` — a result for a different node or project never lands on the current view.
- **`selected_model_id` continuation** (`resolve_selected_model_id/3`, async_load.ex:214-227): replicates the original synchronous node-switch validation — when the spawn-time run was a node switch (`prev_node_id != current_node_id`) the carried selection is kept only when it names a profile that exists on the (new) node, else `default_selected_model_id` ("" when a model-selection script is enabled, else the first profile id, or nil); same-node runs keep the current selection (owned by `select_model` / `restore_state`). Known minor edge: `maybe_persist_state` runs before the continuation corrects the selection, so sessionStorage can briefly carry the pre-validation value — the socket assign is always corrected.

### Async remote project activation — `ProjectFlow.spawn_remote_project_activation/2`

`activate_remote_project/2` (`project_flow.ex:403`) — used by `open_project/2`, `select_project/2`, and the palette Enter path `activate_remote_palette_project/2` when `current_node_id != nil` — runs ONLY the synchronous gate guard + `normalize_remote_project_path/2` (its `{:error, :blank}` / `{:error, :relative}` flashes fire in the event handler). Success delegates to the public `spawn_remote_project_activation/2` (`project_flow.ex:458`): sets `@remote_project_loading` to the path, closes the palette (`project_palette_open false` + `palette_mode :menu`) so the UI responds instantly, and spawns the RPC sequence `dir? → add_recent_project → list_recent_projects (node-filtered) → read_project_config → detect_mode → load_project_config → load_foreign_repos` in a supervised task (`remote_project_load/2`, project_flow.ex:485-519).

- **Re-trigger / supersede semantics**: an activation already in flight for the SAME path is a no-op (no re-spawn); a DIFFERENT path supersedes — the flag is replaced, so the older task's result is dropped by the stale-guard.
- **Result / stale-guard** (`handle_info({:async_remote_project, node, path, result})`, projects_live.ex:1750): dropped when `node != current_node` OR `path != @remote_project_loading` (a node switch clears the flag in handle_params/3). `{:ok, results}` applies the assigns the sync flow applied (recents, display-only `active_project`/`active_project_path`, `task_mode` + `task_mode_info`, `project_config` / `worktree_script` / `commands` / `foreign_repos`, `show_add_foreign_repo_form: false`), resets GitHub state when the project changed, re-runs `GitHub.maybe_check/1`, then `push_patch`es to `project_url(socket, path)` (the URL carries `&node=` so handle_params re-runs in the same remote context). `{:error, :not_a_directory}` clears the flag + gettext flash "Directory does not exist on the remote node: %{path}" (the one RPC-derived error of the sequence — it must run in the continuation, not the event handler).
- **Loading state**: `@remote_project_loading` is seeded `nil` in mount (`projects_live.ex:559`), cleared on node switch (`projects_live.ex:665`), set to the in-flight path at spawn. The render/1 remote branch (`projects_live.ex:302-308`) shows a loading banner while non-nil — `loading loading-spinner` + `gettext("Loading project…")` (Chinese meaning comment in code: 正在通过远程节点加载所选项目，加载完成前任务表单保持禁用) + the in-flight path in `<code>` — the task form is effectively unavailable until the continuation applies. A palette-row spinner was deliberately NOT implemented (the banner covers the feedback); `remote_view.ex` / `project_components.ex` are untouched.

### path_suggestions — known limitation

`Project.path_suggestions/3`'s per-keystroke `NodeContext.list_path_suggestions` RPC (`project.ex:222`) is deliberately left SYNCHRONOUS: the `path_input` / `new_project_path_input` events are already `phx-debounce=150`, and a per-keystroke last-write-wins async conversion was assessed as not worth the complexity.

### Test strategy

- Tests asserting content right after `live()`/`render()` on remote nodes need `render_async(view)` — results arrive asynchronously (the fake-remote `:erpc` degrades fast, so `render_async` settles the async tasks).
- Stale-guard tests inject the messages directly: `send(view.pid, {:async_project_load, other_node, prev_node_id, path, results})` / `send(view.pid, {:async_remote_project, node, path, result})` with a DIFFERENT node or path, then assert the assigns are unchanged.
- Async activation tests assert the "Loading project…" banner right after the triggering event (asserting `assigns(view)[:remote_project_loading] == path` is racy — a fast degraded task may already have cleared it); full determinism comes from invoking `EvoDashWeb.ProjectsLive.handle_info/2` directly on the raw socket with the captured `{:async_remote_project, ...}` message and asserting the applied assigns + `socket.redirected == {:live, :patch, %{to: ..., kind: :push}}`.

## Constraints

- All modules are pure functions — no I/O, no socket, no process calls (except `StatePersistence` which interacts with assigns/session).
- Follows the project-wide `try/rescue` anti-pattern policy.

## Windows Path Handling (Project Open/Create Flow)

Name-only project input must never be joined to the backend's cwd by `Path.expand/1`: on the Windows desktop app the backend's cwd is the Tauri process's inherited cwd — `desktop/src-tauri/src/sidecar.rs` spawns the launcher with NO `current_dir` → typically the install dir `C:\Users\<user>\AppData\Local\genesis-desktop` (NSIS per-user install) — so `Path.expand("Test")` would yield `C:/Users/<user>/AppData/Local/genesis-desktop/Test` (FORWARD slashes — Elixir's win32 `do_absname_join` converts `\`→`/`). Elixir's `Path.type/1` is OS-gated (win32 recognizes `X:\`/`X:/`/UNC as `:absolute`; a bare name or `X:` volume-relative input is joined to cwd — verified in Elixir 1.20.2 `lib/elixir/lib/path.ex`). There is NO literal `C:\` hardcoding anywhere in evo_dash/desktop/evo_git code — `C:` in errors is runtime `File.cwd!()`, not a hardcode.

**`ProjectFlow.normalize_project_path/1`** (public, `@spec normalize_project_path(String.t()) :: {:ok, String.t()} | {:error, :blank} | {:error, :relative}`): every server-side project-path entry point in `project_flow.ex` normalizes input through this helper instead of bare `Path.expand/1`. Semantics: `String.trim/1` first; blank → `{:error, :blank}`; genuine tilde expansion (`~`, `~/...`, and — ONLY on Windows — `~\\...`, decided by the private `expandable_tilde?/1` predicate) → `{:ok, Path.expand(trimmed)}` (tilde expansion is cwd-independent); UNC-prefixed (two+ leading separators `//` or `\\`, e.g. `//wsl.localhost/...`, `\\server\share\...`) → `{:ok, normalized}` with backslashes converted to forward slashes and trailing separators stripped (`EvoGit.Platform.normalize_separators/1` + `trim_trailing_separators/1`) — NEVER `Path.expand`ed, because on a non-Windows node `Path.expand("//wsl...")` collapses `//`→`/` and `Path.expand("\\server\share")` cwd-joins (on Windows the UNC root survives, but the forward-slash normalized form is used for internal consistency); drive-letter absolute (`C:\`/`D:/` — `EvoGit.Platform.absolute_path?/1` true and NOT UNC-prefixed) → `{:ok, Path.expand(trimmed)}` (idempotent for absolute paths); anything else — bare names, volume-relative `D:Test`, root-relative `\Test`, `~foo`, non-Windows `~\x` — → `{:error, :relative}`. **Never-cwd-join rule**: `Path.expand/1` must never see a value that would be cwd-joined. Elixir's tilde handling (verified against stdlib `resolve_home/1`): `~`/`~/...` expand on ALL platforms, `~\...` ONLY on win32 (literal + cwd-joined on Unix), `~foo` NEVER on any platform (literal + cwd-joined) — `expandable_tilde?/1` guarantees `~foo` and off-Windows `~\x` fall through to `{:error, :relative}`. **LOCAL-only** — never used for remote paths (its `Path.expand/1` runs against the dashboard's OS, which corrupts remote paths; see the remote normalizer below).

**`ProjectFlow.normalize_remote_project_path/2`** (public, `@spec normalize_remote_project_path(node(), String.t()) :: {:ok, String.t()} | {:error, :blank} | {:error, :relative}`): remote-aware normalization used ONLY by `activate_remote_project/2`. Performs **NO local `Path.expand` on absolute input** (a Windows dashboard would rewrite `/home/...` to a drive-letter path and classify it `:volumerelative`; a POSIX dashboard would cwd-join `C:\work`): blank → `{:error, :blank}`; any node-agnostic absolute form — POSIX absolute (leading `/`, which also covers `//`-prefixed forward-slash UNC) OR Windows-style absolute (drive letter / backslash UNC, via the shared private `remote_absolute_path?/1` predicate, which delegates the drive/UNC checks to `EvoGit.Platform.absolute_path?/1`) — → `{:ok, trimmed}` passed through VERBATIM: no `Path.expand`, no separator normalization (the remote node's own OS understands its separators; the same predicate backs `absolute_path_for_node?/2`'s remote branch); genuinely tilde-expandable (`~`, `~/...`, `~\...` — same `expandable_tilde?/1` predicate) → expanded on the REMOTE node via the node-aware RPC (`NodeContext.call_remote(node, Path, :expand, [trimmed])`) so the remote user's home resolves, NOT the dashboard user's — the expander is injectable via the test seam `Application.get_env(:evo_dash, :remote_path_expand_runner)` (read at call time, default = a capture of the private `default_remote_path_expand/2`; RPC failure or a non-binary result falls back to `{:ok, trimmed}`); anything else → `{:error, :relative}`. The `EvoDashWeb.RemoteGateComponents.gate_active?/1` guard runs before normalization and is unchanged.

Applied at `create_project/2`, `open_project/2`, `select_project/2` (all local flows, `normalize_project_path/1`), and at `activate_remote_project/2` (`normalize_remote_project_path/2`, remote-aware): `{:error, :blank}` → "Invalid project name" gettext flash; `{:error, :relative}` → gettext flash `Enter a full path, e.g. D:\Projects\myproject or /home/user/myproject`; `{:ok, expanded}` → create: `validate_project_name(Path.basename(expanded))` → `File.dir?` → `register_and_open_project` / `File.mkdir_p` chain; open/select: dir check + recents + push_patch; activate_remote_project (remote): gate guard + `normalize_remote_project_path/2` synchronously, then the async `spawn_remote_project_activation/2` — `dir?` validation, recents reload, and config/mode loading run in a supervised task; the `{:error, :not_a_directory}` error surfaces via the async continuation flash and success ends with a push_patch (see "Async Node-Aware Loads"). "Directory does not exist…" / "…on the remote node…" flashes fire for absolute-but-missing directories.

**Recents filtering — node-aware**: the shared public predicate **`ProjectFlow.absolute_path_for_node?(node, path)`** (`@spec absolute_path_for_node?(node(), term()) :: boolean()`) is the single source of truth for recents filtering: local node (`node == node()`) → `EvoGit.Platform.absolute_path?/1` (local semantics unchanged); remote node → true for POSIX-absolute (leading `/`) OR Windows-absolute (`EvoGit.Platform.absolute_path?/1`) paths — a remote node's recents must not be judged by the dashboard's host OS (a Windows dashboard would drop `/home/user/repo` as `:volumerelative`, a POSIX dashboard would drop `C:\work`); non-binary paths → false. The public filter wrappers live in **`AsyncLoad`** (`filter_absolute_recent_projects/1`, `filter_absolute_recent_projects_for_node/2`, async_load.ex:135-158); `ProjectFlow`'s private pair (project_flow.ex:219,226) remains for the local flows and the activation task body, and `projects_live.ex`'s private pair (projects_live.ex:2003-2015) delegates to AsyncLoad. Remote `:recent_projects` sites: (1) `AsyncLoad.load_recent_projects/3` (async_load.ex:163-174 — the handle_params async load + `{:async_project_load}` continuation), (2) the `{:recent_projects_updated}` handler (projects_live.ex:1670, still synchronous), (3) the async activation task body (`remote_project_load/2`, project_flow.ex:490) — plus `Project.path_suggestions/3`'s recents filter. The local sites (`register_and_open_project`, `open_project`, `select_project`, mount, local handle_params/handle_info branches, palette-key local selection, `remove_recent_project`) keep the private `filter_absolute_recent_projects/1` (`Enum.filter(recent_projects, &EvoGit.Platform.absolute_path?(&1.path))`) unchanged — non-absolute (cwd-joined) entries never render in the palette.

**Foreign-repo construction — node-aware raw storage (`ProjectFlow.build_foreign_repo/4`)**: `EvoGit.Core.ForeignRepo.new/3` (evo_git core) runs `Path.expand/1` on the root against the DASHBOARD's OS, which mangles remote paths (a Windows dashboard rewrites `/home/...` to a drive-letter path; a POSIX dashboard cwd-joins `D:\stuff\repo`). The public helper **`ProjectFlow.build_foreign_repo(node, id, path, opts \\ [])`** (`@spec build_foreign_repo(node() | nil, String.t(), String.t(), keyword()) :: EvoGit.Core.ForeignRepo.t()`) is the single construction seam: LOCAL node (`node == nil or node == node()`) → `ForeignRepo.new/3` (exact legacy behavior — its tilde/relative `Path.expand` semantics AND its `writable:`/`base_sha:` opt coercion are kept); REMOTE node → a RAW `%EvoGit.Core.ForeignRepo{id: id, root: path, description: Keyword.get(opts, :description), writable: Keyword.get(opts, :writable, false), base_sha: Keyword.get(opts, :base_sha)}` — the root AND `base_sha` are stored verbatim (no local expansion/rewrite; only `ForeignRepo.new/3` coerces them and it is never used for remote roots). Remote-context call sites (each stores raw roots for remote nodes; every local variant keeps `ForeignRepo.new/3` byte-identical): (1) `projects_live.ex` `add_foreign_repo`/`save_foreign_repo` handlers — after validation, `remote_context? = socket.assigns[:remote?] or socket.assigns[:current_node] != node()` picks `current_node` (remote) or `node()` (local); (2) `Project.load_foreign_repos/3` remote branch — threads the node through the private `extract_foreign_repos/2` + `build_foreign_repo/3` (the local `load_foreign_repos/1` + `/2` variants and the local `extract_foreign_repos/1` delegate keep using `ForeignRepo.new/3`); (3) `StatePersistence.maybe_restore_foreign_repos/2` — same `remote?/current_node` context check rebuilds raw structs on restore, closing the persist/restore round-trip so a remote-added POSIX repo survives state persistence unmangled. `projects_live.ex` `maybe_restore_foreign_repos_from_task/2` is deliberately NOT node-aware — it restores from a LOCAL task's opts (local paths), current behavior is correct.

**genesis.toml is NEVER written by the dashboard** — add/edit/remove foreign repos (`handle_event("add_foreign_repo")` projects_live.ex:1248, `save_foreign_repo` :1382, `remove_foreign_repo` :1336) only mutate the in-memory `@foreign_repos` socket assign (persisted solely to browser sessionStorage via `StatePersistence`). The ONLY genesis.toml write path in the entire codebase is `EvoGit.ProjectConfig.write_worktree_script/2`, called exclusively by the evo_git genesis runtime (`runtime/genesis.ex:101,259`) to write build-system worktree init scripts — never by evo_dash. A foreign-repo edit therefore lives for the tab/session and is silently lost on reload/node switch; per-project persistence would require a new write path.

**Read-write foreign repos — per-repo `writable`/`base_sha` + edit-in-place flow**: each foreign repo in the settings editor carries `writable` (boolean, default `false` — read-only unless explicitly checked; `name="writable"` checkbox present = `"true"` → `params["writable"] == "true"`) and `base_sha` (optional per-repo starting commit, trimmed; blank → `nil` = HEAD). The three edit-in-place events (all in projects_live.ex, near the add/remove handlers): **`edit_foreign_repo`** (`%{"repo_id" => id}`) finds the repo in `@foreign_repos` and seeds `@editing_foreign_repo_id` + `@foreign_repo_edit_form = %{description: repo.description, writable: repo.writable, base_sha: repo.base_sha}`; unknown id → error flash `gettext("Repo '%{id}' not found.", id: id)` (deliberately mirrors `remove_foreign_repo`'s unknown-id choice — a stale repo_id from an outdated render surfaces as a user-visible error instead of a crash). **`save_foreign_repo`** (`%{"repo_id" => id, "path" => ..., "description" => ..., "writable" => "true"|nil, "base_sha" => ...}`) re-runs the SAME real validation as add (see below), rebuilds the repo via `ProjectFlow.build_foreign_repo/4` with the same node resolution as add (remote contexts keep the raw root + raw base_sha), REPLACES the entry with the same id (preserving id; sorted like add), clears `@editing_foreign_repo_id` + `@foreign_repo_edit_form`, `maybe_persist_state()`, info flash `gettext("Foreign repo '%{repo_id}' updated successfully.", repo_id: repo_id)`. On validation failure: error flash and STAY in edit mode (form + assigns kept). Unknown id → `gettext("Repo '%{id}' not found.", id: id)`. **`cancel_edit_foreign_repo`** clears `@editing_foreign_repo_id` + `@foreign_repo_edit_form`. The three edit assigns (`:new_repo_base_sha` default `""`, `:editing_foreign_repo_id` default `nil`, `:foreign_repo_edit_form` default `nil`) are seeded in mount, `toggle_add_foreign_repo_form`, and `StatePersistence.maybe_clear_state_on_node_switch/3`.

**Foreign-repo REAL validation (shared by `add_foreign_repo` and `save_foreign_repo` — private `validate_foreign_repo_input/3`, never crashes, cond/case only, NO try/rescue)**: path non-blank + absolute (existing checks) → existence → git-ness → base_sha resolvability. Existence: local → `File.dir?(path)`; remote → `EvoDash.NodeContext.dir?(node, path)` — error flash `gettext("Foreign repo path does not exist: %{path}", path: path)`. Git-ness: local → `EvoGit.Adapters.Git.rev_parse(path)` returns `{:ok, _}` (the core adapter — NEVER shell out); remote → `NodeContext.list_branches(node, path)` returns `{:ok, _}` — error flash `gettext("Path is not a git repository: %{path}", path: path)`. base_sha resolvability (non-nil/non-blank only): local → `EvoGit.Adapters.Git.rev_parse(path, base_sha)` returns `{:ok, _}` — error flash `gettext("Base commit %{base_sha} not found in repository: %{path}", base_sha: base_sha, path: path)`; **REMOTE base_sha check deliberately SKIPPED by design** — NodeContext exposes NO ref-resolution wrapper (verified), and the core's up-front task-start validation (`Runtime.Helpers.load_foreign_repos/2`) still raises ArgumentError for a bad remote base_sha, failing the task before any agent spawns (see the task-start section below). No new core API was hacked in, nothing shells out.

**Core-ArgumentError at task start (VERIFIED — the "Failed to start task" flash does NOT fire)**: `do_task_submit/4` threads `socket.assigns[:foreign_repos]` (full `%ForeignRepo{}` structs carrying `writable`/`base_sha`) into `opts[:foreign_repos]`; the core validates them up front via `Runtime.Helpers.load_foreign_repos/2` (evolution.ex:116 → `run_resolved_root_agent/7`), which raises `ArgumentError` for a non-git path or an unresolvable `base_sha`. **The raise is NOT caught synchronously**: `EvoGit.TaskRegistry.start_task/2` (task_registry.ex:51-54) returns `{:ok, task}` immediately (task marked `:running`) and spawns the execution via `Task.Supervisor.async_nolink` → `TaskExecutor.execute_task/3` → `Runtime.Evolution.run/2`; the ArgumentError propagates out of the spawned task process, and TaskRegistry's `handle_info({ref, result})` (task_registry.ex:1205) maps the `{:exit, reason}` result to `:failed` (the `{:DOWN, ...}` handler at :1283 covers the same path when no agents exist). Consequences: (1) the existing `gettext("Failed to start task: %{reason}", reason: inspect(reason))` flash (projects_live.ex, `do_task_submit/4` error branch) does NOT fire for a bad foreign-repo entry — it only fires for synchronous `{:error, reason}` returns (today only the `:cancelled` guard); (2) the task IS created and briefly `:running`, then fails fast and appears as `:failed` in the task list; (3) crucially the raise happens BEFORE `AgentScheduler.run_agent` (evolution.ex:131), so NO agent ever spawns — the user is fully protected from bad entries (especially remote `base_sha` values the editor cannot validate), just with a `:failed` task instead of an error flash. The ArgumentError message naming the repo id/path/problem is preserved in the failure reason/logs.

**Read-write foreign-repo persistence round-trip**: `StatePersistence.serialize_foreign_repos/1` (:85-95) now emits `"writable"` + `"base_sha"` alongside `id`/`path`/`description` for the sessionStorage snapshot; `maybe_restore_foreign_repos/2` (:153-190) restores them like `description` — `writable` with a tolerant `true`/`"true"` check (sessionStorage JSON gives booleans, defensive against strings), `base_sha` only when a non-empty binary (blank → nil), and threads BOTH through `ProjectFlow.build_foreign_repo/4` (the local branch now goes through `build_foreign_repo(node(), ...)` too — behavior byte-identical to the previous direct `ForeignRepo.new/3` call, since build_foreign_repo delegates to it for local nodes). Task-resume restore (`maybe_restore_foreign_repos_from_task/2`, projects_live.ex) also threads `writable`/`base_sha` from the string-keyed map branch into `ForeignRepo.new/3` (which coerces/validates them); the `%ForeignRepo{}` branch already carries them. So after add/edit/restore, `@foreign_repos` structs always carry correct `writable`/`base_sha` values end-to-end into `do_task_submit/4`'s `opts[:foreign_repos]`.

**projects_live.ex growth is deliberate**: the file is ~2479 lines after this feature (already ~2266 before) — policy-threshold-justified (module size policy prefers one big LiveView over premature splitting); it was EXTENDED, not split. Keep additions here unless a genuine split case emerges.

**DECISION RECORD — no evo_dash-side test seam for remote validation**: remote existence/git-ness checks in `validate_foreign_repo_input/3` call `NodeContext.dir?/2` / `list_branches/2` directly (production behavior identical to local — no seam, no injectable runner). Rationale: the checks are cheap, user-click-triggered mutations (not page loads), and the failure paths are covered by LiveView tests (the remote add test asserting the "does not exist" flash against a fake node); remote RAW-preservation + `writable`/`base_sha` threading are covered at unit level in `project_flow_test.exs` (`build_foreign_repo/4` describe block) and `state_persistence_test.exs`.

**`@foreign_repos` NEVER contains the primary repo** — it holds only `[foreign_repos]` genesis.toml entries (plus session-restored/added entries); the primary repo is `active_project_path`, not a `%ForeignRepo{}` in the list. The `"primary"` id in this codebase is a defensive legacy concept only: sort-first in `load_foreign_repos`/`maybe_restore_foreign_repos`/`add_foreign_repo`, the `remove_foreign_repo` guard ("Cannot remove the primary repository."), and the default id when a persisted entry lacks one (state_persistence.ex:152). No code path constructs or requires a `%ForeignRepo{id: "primary"}` on the dashboard side; the core (`EvoGit.Runtime.Helpers`) treats repo_id `"primary"` specially when it receives task opts.

**`Project.filesystem_suggestions/1` delegates to `EvoGit.PathSuggestions.suggest/1`** (project.ex:252 — the single source of truth the remote daemon branch already uses, so local and remote autocomplete are identical). Semantics: absolute or genuinely tilde-expandable input only; relative input (`~foo`, non-Windows `~\x`, bare names) → `[]`; no `File.cwd!()`-anchored fallback. **Trailing-separator gotcha**: the `<dir>/` (list-the-directory-itself) decision runs on the RAW typed value because `Path.expand/1` strips trailing separators (`Path.expand("/tmp/foo/") == "/tmp/foo"`) — never check the expanded path for a trailing separator, or typing `<dir>/` lists the parent filtered by the basename instead of the directory's contents. Bare `~` / `~/` list the home directory's own entries.
