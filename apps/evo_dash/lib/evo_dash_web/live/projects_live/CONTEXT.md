# ProjectsLive — Support Modules & Page Notes

## Intent

Support modules for `EvoDashWeb.ProjectsLive` (`GET /` and `GET /projects`) plus the durable design notes for the Projects page (project overview, command palette, project activation, task form threading, foreign repos, node handling).

**The governing rule of this node: no `ProjectsLive` process ever blocks on a task-store or RPC call** — §The Rule below is the full contract (reads and slow writes spawned with a seq/in-flight-marker guard, instant click mutations only `EvoDash.SafeCall.run/1`-wrapped).
Cross-suite test mechanics: `test/evo_dash_web/live/CONTEXT.md`; widget + shared-boundary detail: `../../components/CONTEXT.md`, `../CONTEXT.md`, `../draft_scope.ex`.

## The Rule — nothing in the LiveView process blocks

The umbrella-wide contract (spawn-only-when-connected, `EvoDash.SafeCall` as the ONLY boundary, the NESTED-tag message shape, seq/node stale guards) lives in `../CONTEXT.md` §"Async data-load & exit-safety contract"; page-specific additions:
Page-specific: the reads (`NodeContext.projects/1`, `list_task_ids`, `get_task_lite`, `get_resolved_config`, `list_custom_agents`, remote RPCs) never run in `mount/3`, `handle_params/3`, `handle_event/3` or `handle_info/2` (spawned inside a `Task.Supervisor.start_child(EvoDash.TaskSupervisor, …)` body, `SafeCall.run/1`-wrapped there, result `send/2`-ed back), the instant click mutations whose effect must be observable immediately (`clear_finished_tasks`, `delete_task`, `cancel_task`, the palette/form `NodeContext.mount_project/3`) stay synchronous but `SafeCall`-wrapped, the slow writes (`start_task`, `run_command`, an attachment read) use the async write path, and `forget_project` is optimistic + fully async.

### Async write path (the ONE shape)

Bump a monotonic seq (or record the picker id in `:attach_pending`), set its `*_running`/`*_pending` marker, spawn with `EvoDash.SafeCall.start/3,4` against `EvoDash.TaskSupervisor`, then apply the result in a seq-marked (or marker-gated) `handle_info/2` that clears the marker — a purely-instant validation failure stays synchronous and owns its own flash (`:attachments_over_cap`, a missing custom agent, a stale-model `{:error, reason}`, a failed `SafeCall.start` itself), and a failed spawn clears nothing it never set (`task_launching`/`command_running` stay false), so no affordance is wedged.
The GitHub issue-fix launch is the deliberate exception: a synchronous `SafeCall.run/1` start (`GitHub.start_fix_task/3`), because it already runs off the async issues flow and its result drives the modal close.

## Mount & handle_params

- **Dead render (`connected?(socket) == false`) makes ZERO task-store calls**: `projects: []`, `notified_task_ids: MapSet.new()`, `notified_task_ids_ready?: false`, `task_notifications_seq: 0`, `projects_seq: 0`, `clear_history_seq: 0`, `foreign_repos_restoring_from: nil`, `auto_activate_candidate?: false`, the in-flight markers at rest (`command_seq: 0`, `command_running: nil`, `task_launch_seq: 0`, `task_launching: false`, `attach_pending: %{}`), `project_config_mtime: nil`, no PubSub subscriptions, no registry read.
- **Connected mount** subscribes `"tasks"`, `"vct"` and `"config"` and sends `:load_config_status`; it performs only LOCAL, cheap, non-store setup: a memoized `EvoGit.Config.resolve()` (`Process.put(:memo_config_resolve, …)`, read only by `Project.load_model_selection/2` / `load_model_profiles/1`, which run inside the AsyncLoad task — so the memo does NOT serve the deferred `:load_config_status` read), `AsyncLoad.load_custom_agents/1` (local `agents.toml`) and `EvoGit.Runtime.WorktreeInitScript.build_systems()`. At mount the node is always LOCAL (NodeAware seeds local; `?node=` resolves later), so these are local file reads, not RPC.
- `Project.load_model_profiles/0,1` (the legacy `{profiles, selected_id}` tuple API) has NO production call site — only tests; the page uses `Project.load_model_selection/2` via the AsyncLoad batch.
- `handle_params/3` captures `prev_node_id` BEFORE `assign_node/2` so the node-switch reset and the batch loader see the transition, sets `auto_activate_candidate?: is_nil(params["project"]) and is_nil(current_node_id)`, and ends with `AsyncLoad.maybe_spawn(socket, prev_node_id)` (connected only) — SKIPPED while `workbench_project_selection` is set (that continuation spawns the batch instead, §Model-selection loading state). It never seeds `notified_task_ids`.
- Auto-activation of the newest VCT project is a **continuation** of the batch (`maybe_auto_activate_project/1`), not part of mount: it requires `auto_activate_candidate?`, `applied? and results[:auto_activate?]`, no remote context, no active project, a `%{path: path}` first entry with a binary `path`, and `File.dir?` before `activate_project/2`. Because it lands one frame after `live/2`, tests must `wait_assigns` for `active_project_path`.

## Project overview — the two entry points

`Overview.visible?/1` renders the overview for a selected project or VCT workspace unless a connection gate, explicit compose request or idle workbench suppresses it.
A connected local mount without a project param can assign the newest VCT project while `workbench_idle?` remains true, so `active_project_path` alone does not imply an overview or eligibility to open a draft.
The overview puts the primary **New task** action and secondary **Chat with Assistant** action directly below the selection heading; neither requires opening a settings disclosure.
An unavailable workspace roster entry is shown as unavailable with disabled entry points (never as an empty workspace and never as the previously active project).
The composer is an explicit step: `handle_params/3` sets `compose_task?: overview_compose_task?(params)` (`wb_task=1` or a non-blank `resume_from`/`starting_commit`) and `maybe_restore_compose_task/1` additionally SETS it when a restored browser draft carries a prompt or a resume id — it never clears a flag the URL set — so a returning user with saved draft state never sees the overview.
`#overview-new-task` (`phx-click="compose_task"`) patches to `/projects?project=<exec_path>&wb_task=1` via `overview_compose_url/2` → `WorkbenchComponent.navigation_path/3` (a remote context keeps `&node=`; never `Helpers.with_node_param/2`, which appends `?` and would corrupt the query); `wb_task=1` is load-bearing because `overview_compose_task?/1` reads it BACK as `compose_task?`, so a reload or deep link of that URL lands in the composer, and `exec_path` is always a resolved absolute OS path (a workspace contributes its chosen/first-resolvable member's path), never a VCT token.
A selection with no execution path cannot compose: the handler flashes `overview_missing_members_message/1` (naming `Overview.missing_refs/1`) instead of patching, and both entry points render disabled.
`Overview.assistant_path/1` returns `/assistant?wb_project=…&wb_draft=…[&node=…]` only with a draft id and a confirmed scope: the active project's absolute path and VCT point must match a row in the loaded project roster, or the selected workspace must have a resolved member with an absolute path.
`a#overview-chat-assistant` uses that URL; `wb_project` is the OS path for a project and the WORKSPACE POINT for a workspace (the Assistant resolves the group itself, a member path is never substituted), `wb_draft` is the 24-lowercase-hex id `Overview.draft_id/0` mints once per `handle_params/3` run (stable across async re-renders), and `node` is present only in a remote context.
An executable local project opened directly by path without a registry match keeps New task enabled but shows a disabled Chat with Assistant button and `#overview-assistant-project-picker` guidance to open it through the project picker.
The explicit hand-off uses only the page's loaded roster/member data and never reads Git state, queries the registry or mounts a project.
`Overview.default_draft_path/1` adds automatic-open guards to that same helper: the overview must be visible and the explicit URL selection must match the confirmed scope path or workspace point.
A route with no `project` key never offers a default draft, even when the recent-project continuation has activated a local project; implicit activation does not change overview visibility.
No offer is made for a blank explicit selection, an unconfirmed project, pending/gated nodes, an in-flight activation, explicit compose/resume/starting-commit intent, deliberate `wb_home=1`, or an open or requested palette.
Eligibility does not depend on Git state or overview metadata; the browser opens the unsent draft only if the restored tab rail for that scope is empty.
Identity is rendered rather than left to the user: `#overview-title` carries the name (`data-overview-name`), `[data-overview-path]` the absolute OS path (or "Grouping point — no OS path" for a workspace), `[data-overview-point]` the VCT point, `[data-overview-node]` the node label, `[data-overview-head]` `branch @ short-sha`, and `[data-overview-meta]` the node label plus the HEAD subject.
A workspace is framed as a grouping point that is never runnable and never reaches `start_task`: its ordered RESOLVED members are listed (unresolved refs render as `[data-overview-missing]`), exactly ONE member is the stated execution target through `Overview.execution_member/2` (the chosen key while it still resolves, else the FIRST resolvable member) selected with `#overview-member-form`'s `overview_select_member` picker (`[data-overview-execution-member]` states it), and a workspace whose members all fail resolution refuses both entry points via `[data-overview-no-member]`.
`overview_select_member` assigns the key and re-runs `Overview.maybe_spawn/1`, so the execution target and the activity/git payload follow the chosen member; a project change resets `overview_member` to nil, and non-binary params are ignored (no atom conversion of client input).
Recent activity and git identity are read OFF-PROCESS: `Overview.maybe_spawn/1` spawns `Overview.load/2` (the default body of the `:projects_overview_runner` app-env seam, resolved at spawn time) through `SafeCall.start/4` behind the monotonic `overview_load_seq`, so the payload arrives NESTED as `{{:overview_loaded, seq, node, path}, %{git:, tasks:}}` and is accepted only for the current seq, node and `Overview.scope(assigns).exec_path`.
`overview_loaded_for` deduplicates reads and gates displayed metadata by `{target_id, node, path}`; a different scope clears the old payload and a failed spawn does not stamp the key.
Each half is its own `SafeCall.run/1` boundary (a missing git repository never hides the task list and vice versa) and an unavailable or empty half is OMITTED — the git rows disappear and the "Recent activity" block only renders with at least one task (`at most five` summary rows through `list_tasks_page/2` with `project_path:`), so an error state is never a spinner or a placeholder.

## Browser notifications — `notified_task_ids_ready?`

`@notified_task_ids` is a `MapSet` of terminal ids already accounted for; `@notified_task_ids_ready?` says the set has been SEEDED from the store.

- A fresh connected mount starts `ready? == false` with an empty set, and detection is **skipped entirely** while not ready — diffing against an unseeded set would notify every historical terminal task.
- The seed arrives with the batch (`:terminal_ids`, local context only, only while `ready? == false`) or, after a clear-history, with `{:task_history_cleared, …}`.
- Once ready, each `:node_aware_reload_tasks` spawns ONE `Notifications.spawn_scan/4` with the current known set; ids absent from it are new, and an id whose `get_task_lite` returns nil is marked notified without notifying.
- Notifications are **LOCAL-context only** (`current_node_id == nil`); remote contexts never scan, never seed, never push.
- `clear_task_history` flips `ready?` to false before clearing so the in-flight window cannot notify, then restores it on arrival (error included).

## Guarded mutations

- `clear_task_history`: sets `notified_task_ids_ready?: false`, empties the sidebar lists immediately via `NodeAware.assign_active_tasks/1` (an ETS-hub read, no store call), and spawns `SafeCall.run(fn -> TaskRegistry.clear_finished_tasks(); Notifications.load_terminal_ids() end)` → `{:task_history_cleared, seq, node, result}`; the rest of the refresh arrives through the regular node-filtered broadcasts.
- `forget_project`: bumps `projects_seq`, drops the row optimistically by `point` (`Enum.reject`), resets `palette_selected_index`, and runs the forget plus an authoritative reload in ONE supervised task → `{:projects_forgotten, seq, node, result}`, with the `{:vct_updated, node}` broadcast as backstop; `cancel_task`/`delete_task` are plain `SafeCall.run/1` calls whose error flashes instead of crashing.
- `task_submit` / `do_task_submit/4`: the INSTANT half is synchronous and pure — the pending-remote, missing-project, in-flight foreign-repo restore (`foreign_repos_restoring_from == task_resume_from` → "Still loading the previous task's settings. Please try again in a moment."), missing-custom-agent and `TaskSubmit.build_opts/6` refusals all flash without spawning anything, so the restore can never lose the race against submit.
- `run_command`: the instant half resolves the command via `Commands.lookup/2` (unknown → `"Command not found: …"`) and the OS call runs in a supervised task, with `:command_running` plus the `"Running '<cmd>'…"` info flash as the only in-flight feedback (the Configure buttons live in `ProjectComponents`); a failed spawn flashes `"Could not run '<cmd>'. Please try again."` and sets no marker.
- attach-file picks: the instant half only validates (the manual path's `File.regular?/1`) and refuses a capped binary pick via `AttachFile.count_cap_reached?/1` + `push_count_cap_error/2`, while the spawned read's `{{:attachment_loaded, …}}` applies only while that picker id is pending; a node-context change clears `:attach_pending` (with `:file_pick_bases`/`:staged_attachments`) and command/launch continuations are rejected by their own seq + project-root/node guards, with markers reset by the next run of that action.

## Foreign-repo resume restore

`start_foreign_repos_restore/2` marks `foreign_repos_restoring_from: task_id` and spawns a `SafeCall.run(TaskRegistry.get_task_lite(task_id))` whose only consumed field is `opts[:foreign_repos]`, arriving as `{:foreign_repos_restored, task_id, node, result}`; the handler drops it unless the task is still the resume target on the same node.
The lookup is deliberately the LOCAL `TaskRegistry.get_task_lite/1` (same struct as `get_task/1` minus the archive); the node-aware restore for a remote activation lives in `ProjectFlow.task_foreign_repos_for_resume/2`, inside the supervised remote-activation task.
Remote activation also resolves `Application.get_env(:evo_dash, :remote_project_load_runner, &remote_project_load/2)` at call time INSIDE that task (arity 2, `(node, path)`, same `{:ok, results_map}`/error contract), and for a nonempty resume task id `Application.get_env(:evo_dash, :remote_resume_task_runner, &NodeContext.get_task_lite/2)` (arity 2, `(node, task_id)`, the lite task or nil). Both seams are inert unless configured and preserve pending-target admission, result messages/stale guards and task-repos-win precedence.

## RPC / I/O audit

- `projects_live.ex` — besides the §The Rule split, only pure `TaskSubmit`/`LaunchOptions` building runs in the LiveView, and `attach_file.ex` reads the LOCAL filesystem OFF-PROCESS (the node dropdown never proxies it), so a 15 MiB image or a large PDF never decodes in the LiveView.
- `github.ex` — all `gh` work runs through the `:github_runner`/`:github_issues_runner`/`:github_issue_markdown_runner` seams (resolved at spawn time) in supervised tasks, and dispatch requires a usable target, so a pending/gated remote target never falls back to local RPC or task launch. Message tuples keep their arity but carry an opaque request-scoped envelope (target identity + request token), so handlers ignore unscoped results and validate target, BEAM node, path and request identity; closing/reopening the modal, changing filters or superseding a fix (repeated same-issue requests included) invalidates earlier replies, accepted results are consumed once, and `SafeCall` turns a runner exit into a reported result.
- `project.ex` / `project_flow.ex` — local TOML/FS reads: `project_config_mtime/1` is the ONE cheap `File.stat/1` the task-broadcast debounce runs; backslashes normalize to `/` before suggestions and `dir?` checks, the EXPANDED path is what gets validated (`NodeContext.dir?/2` remotely, `File.dir?/1` locally), stored in the URL and registered in the VCT; the local click does an exit-safe mount but uses its returned row rather than re-reading the list, and `mount_point_for/2` is pure (suggestion matching: `../CONTEXT.md` §SSH Remote UX).
- `AsyncLoad` does not read outgoing remote project settings while a new remote activation is in flight; an ordinary remote extras load never uses a local filesystem mtime to represent remote config freshness.
- Everything else (`async_load.ex`, `notifications.ex`, `remote_view.ex`, `assigns.ex`, `state_persistence.ex`) does its I/O in a spawned task or not at all, and `handle_result/5` is pure assignment plus the `:resume_foreign_repos_guard` drop for `:foreign_repos`.

## Model-selection helper contracts

The shared boundary (`LLMSelection.from_config/2`, `reconcile/2`, `task_opts/2`, the identity/selection split and picker-state shape) is `../llm_selection.ex` + `../CONTEXT.md` §Canonical LLM selection. Page-specific rules:
- `selected_model_spec` holds only string-keyed `provider_profile_id`, `model` and optional `reasoning_effort`; `%{}` = explicit Auto, nil = uninitialized/use the node default.
- `Project.load_model_selection/0,1,2` → `LLMSelection.from_config/2` for the EXECUTING node (`load_model_selection_from_config/2` is its pure projection seam); local honors `:memo_config_resolve`, a remote transport failure is `{:error, reason}` (never a successful empty configuration), and the bundle is in-memory only — never browser storage, never task opts.
- `task_opts/2` emits `model_spec: <canonical string map>, model_id_locked: true` or `[]` for Auto and ERRORS on a stale/invalid explicit choice instead of launching as Auto; the canonical map is rebuilt from resolved `provider_profile_id` + `model` + reasoning, never from `resolved.model_spec` (the ReqLLM-ready identifier).
- `ModelSelectionScope.bundle/1` validates `model_selection_scope` against `{current_node_id, current_node || node()}` (pending remote targets, failed/not-ready loads and malformed bundles rejected; an unstamped bundle is accepted only in the local `{nil, node()}` context for mount compatibility) and answers the SAME `{:error, :model_selection_not_loaded}` for "still loading" and "no bundle", so only the raw `model_selection_ready?`/`model_selection_error` pair distinguishes them; `LaunchOptions` uses that boundary plus a rejection of any non-nil `pending_model_selection` (explicit pending Auto included).
- Failure is a value: a failed read or guarded whole-batch failure invalidates bundle/scope/readiness and records `model_selection_error` while preserving `selected_model_spec`/`pending_model_selection` with no reconciliation or partial persistence; every connected batch marks readiness false before spawning and ALWAYS delivers a scoped result (runner raise/exit, invalid shape, supervisor-start failure), so a whole-batch failure answers `{socket, false}` and no successful-load continuation runs.
- Freshness: canonical batches carry `model_selection` (assigned with `provider_profiles`/`model_selections`, `selected_model_spec` reconciled on same-node refreshes too); the five-tuple tag and `load_scope` metadata (projects_load_seq, target id, captured selection) are unchanged, stale generation/target/BEAM-node/path results are rejected, a newer user choice is never overwritten, and unstamped legacy `model_profiles`/`default_selected_model_id` maps are still accepted.
- `maybe_restore_model_selection/2` runs on the whole persisted string-keyed state after the parent's node check (`model_spec` outranks `selected_model_id`, explicit Auto included); a restore arriving before an owned ready bundle becomes `pending_model_selection`, validated when that target's bundle lands, and an unowned/mismatched remote bundle never reconciles or consumes it.
- A node switch clears projects, bundle, picker projections, selected canonical/legacy ids, scope, error, readiness and pending restore before fetching the new node (a changed stamped BEAM-node scope resets even at the same target id), and `model_selection_state/1` serializes only the three canonical keys — never credentials or bundle metadata.
- `maybe_persist_model_selection/1` emits the merge-only `persist_model_selection` event (`%{node, model_spec}` + `project` when set + `scope_token` for a VCT-point draft) only for an owned ready bundle without load error or pending restore; the browser merges those fields into the same node's state instead of replacing DOM-owned prompt/form data, while full-form `persist_state` stays a replacement event. Provider/model/reasoning change handlers clear `pending_model_selection` so an earlier restore cannot override a newer interaction.
- `ModelSelectionScope.bundle/1` answers the same `{:error, :model_selection_not_loaded}` for "still loading" and "no bundle", so only the raw `model_selection_ready?`/`model_selection_error` pair distinguishes them; `:model_selection_scope_mismatch` cannot persist on the owned path because `apply_model_selection/3` stamps `ModelSelectionScope.current/1` itself.
- `LaunchOptions.apply/2` is pure, preserves unrelated fields, strips stale `model_id`/`model_spec`/lock keys before merging validated options, emits nonempty custom-agent ids and the explicit `:persistent_state` opt, omits default balanced quality, and additionally rejects any non-nil `pending_model_selection` (explicit pending Auto included) and a missing bundle (`:model_selection_not_loaded`); non-empty `provider_profiles` with an EMPTY `model_selections` list is the READY state, not loading — `launch_disabled` is true, `#task-model-setup` ("Configure a model") renders, the capsule shows "No models are available for this provider profile." and `apply/2` answers `{:error, :no_task_model}`; GitHub fixes use the SAME helper, and quality (`fast`/`balanced`/`high_quality`) stays independent of reasoning.
- The page seeds `model_selection_scope: nil`, `model_selection_ready?: false` and `model_selection_error: nil` beside the nil bundle and NEVER seeds the bundle synchronously (`Project.load_model_selection/2` has exactly one call site, `AsyncLoad.default_batch/6`); `change_model_selection/2` must use `ModelSelectionScope.bundle/1` and swallows every `{:error, _}` as a no-op, while an error is displayed and retryable — never converted into Auto.

## Model-selection loading state (recoverable, never stuck)
`@model_selection_ready? == false and is_nil(@model_selection_error)` is the ONLY "loading" state: the task form renders `#model-selection-loading` ("Loading models…", `role="status"`) with `launch_disabled` and `#model-selection-loading-retry` (`retry_model_selection`, disabled on a pending remote target or an active connection gate), so it is always escapable; readiness goes false in `AsyncLoad.maybe_spawn/2` (which also clears the error for the new generation), `ModelSelectionScope.invalidate/2` and `StatePersistence.clear_node_state/1`, and true ONLY in `AsyncLoad.apply_model_selection/3` for a valid bundle at the owning scope.
A DROPPED batch result never leaves loading with no error: `ModelSelectionScope.settle_dropped/2` keeps the socket unchanged while a valid bundle is already applied at the owning scope and otherwise invalidates with a typed reason — `:model_selection_pending_remote` (`pending_remote?/1`) or `:model_selection_superseded` (node, `active_project_path` or `load_scope` seq/node drop) — and `handle_result/5` still answers `{socket, false}`, so no successful-load continuation runs.
A batch WITHOUT a `:model_selection` key settles as `:model_selection_missing` (`apply_model_selection/3`'s catch-all; the legacy `%{model_profiles: …}` clause still applies), and `handle_params/3` skips the spawn entirely while `workbench_project_selection` is set — that assign's handler spawns the batch itself and the assign deliberately STAYS set for the render's `workbench_project` fallback.
`maybe_auto_activate_project/1` is a path hazard: it sets `active_project_path` without spawning a batch, so a still-in-flight batch is dropped by the path guard as a recorded `:model_selection_superseded` error plus the loading-state Retry, never a silent stuck placeholder.
Recovery paths (no polling): a later `handle_params` run, `retry_model_selection` from either affordance, or a node-matching `{:config_reloaded, …}` broadcast.

## Open-project / selection state persistence (where the "current project" lives)

There is exactly ONE active project per page (`active_project` + `active_project_path`), a display-only `%{path:, name:, point:}` map where `name` is the visible identity with `path` secondary and the point is kept only as the registry/search/forget identity; the palette's VCT workspaces are grouping mounts that can never become the active project.
Private `ProjectFlow.mount_project/3` unwraps the guarded `NodeContext.mount_project/3` result to a typed mount or nil; the local click puts the returned mount first in the optimistic roster, while remote activation takes its point from the returned mount and reads the roster off-process.
The VCT broadcast and async batch retain authority over the project roster; `ProjectFlow.mount_point_for/2` is the pure lookup over an already loaded roster.
The open project lives in URL query params — `?project=<absolute path>` plus the remote `node` — encoded by `WorkbenchComponent.navigation_path/3` so spaces and delimiters in the raw path survive the patch.
`handle_params/3` re-derives it on every navigation: local → `ProjectFlow.normalize_project_path/1` + `File.dir?/1` then `activate_project/2` (relative/blank params ignored, an existing-but-invalid absolute path clears the project); remote → `normalize_remote_project_path/2` + `spawn_remote_project_activation/2,3` (gated on no pending target / no active remote gate), and every LOCAL entry point delegates to `ProjectFlow.activate_local_project/3` — the ONE local body: normalize/expand → `File.dir?/1` → VCT mount (`mount_project/3`) → optimistic assigns with the palette closed and reset → `push_patch`, where `open_project/2`/`select_project/2` only choose their own missing-directory wording and `create_project/2` → `create_local_directory/1` adds only the "Project created" info flash.
Browser persistence is `sessionStorage` ONLY (never `localStorage`), owned by the `StatePersistence` JS hook on `#dashboard-root`; the identity rule, `store_key/2`/`legacy_store_key/2` and "token is scope ONLY" live in `../draft_scope.ex` + `../CONTEXT.md` §Draft scope, while page-side `StatePersistence.draft_scope/1` is the ONE scope computation (path from the `"project"` URL/reconnect param, else `active_project_path`; then the point from `active_project.point` when it belongs to that path, else the PURE `ProjectFlow.mount_point_for/2` over `@projects`; never a store/RPC read on the render path), `data-task-draft-scope` is the ONLY scope attribute (`data-task-draft-project` stays the legacy raw-path identity), and a point landing after the first frame is a MIGRATION not a reset.
`maybe_persist_state/1` pushes the whole form snapshot (form fields incl. `project`/`scope_token`/`task_mode`/`task_prompt`, the `node_path`/`starting_commit`/`resume_from` trio, the advanced/project-settings/archive toggles, `persist_agent_state?`, serialized `foreign_repos`, `node` and `model_selection_state/1`'s `model_spec` or legacy `selected_model_id`) and fires only on server events (mode/agent change, quality level, project-settings toggle, foreign-repo add/edit/remove, successful `task_submit`, the node-switch clear), so project ACTIVATION pushes nothing; `scope_token` rides `persist_state` and the merge-only `persist_model_selection`, and the client watcher (`persistFormState`, 300 ms debounce, reading `data-project`) refreshes the saved `project` between server events.
On mount the hook pushes the saved object back as `restore_state`; the handler gates on `(params["node"] || "local") == (current_node_id || "local")` and restores the project only while `active_project` is nil (URL `starting_commit`/`resume_from` win over saved ones), activating locally or via `spawn_remote_project_activation/3`.
Foreign-repo add/edit/remove has NO durable write: `EvoGit.ProjectConfig` exposes only `read/1` plus `write_worktree_script/…`, so the sessionStorage snapshot is the only copy between launches and a started task freezes it into `opts[:foreign_repos]`.
`:node_path` is the context-tree starting node (`EvoGit.Core.ContextNode.load/3`, default `./`, validated by `Runtime.Helpers.validate_node_path/2`), not a BEAM node — the evolve-only "Starting Node" input is the dashboard's only context-tree addressing surface.

Projects are node-scoped by each node's own mount table, not a column: `AsyncLoad.load_projects/3` uses `NodeContext.projects(node)` on a connected remote, `[]` for a pending/failing remote context and the local VCT otherwise; every mutation goes through node-aware RPC (`mount_project/3` inside `ProjectFlow`/palette Enter, `forget_project/2` for local AND remote), and the asset-side paths are `ProjectComponents.project_omnibox` + the `PaletteList`/`FocusInput`/`PathAutocomplete` hooks plus the `open_project`/`select_project`/`create_project`/`palette_keydown`/`forget_project` events.

## Workspace surface (VCT workspace mounts)

A VCT workspace (`%EvoGit.VCT.Mount{kind: "workspace", path: nil, members: [ordered %{"point", "path"}]}`) is a pure GROUPING point rendered in the palette; it is never a runnable project, never an `active_project`, and never reaches `path_suggestions/3`, `StatePersistence` or any task-launch path.
Page assigns: `workspaces` (per-workspace view maps, `[]` on the dead render), `expanded_workspaces` (expanded workspace points), `new_workspace_members` (ordered member points chosen in the form), `workspaces_seq` (stale guard of the LIST) and `workspace_create_seq` (a SEPARATE guard of the create/replace write, because `EvoGit.VCT` broadcasts `{:vct_updated, node}` BEFORE it replies — a shared guard would drop every `{:workspace_created, …}` continuation and lose the flash, the return to the palette menu and the expanded row).
`AsyncLoad.load_workspaces(remote?, current_node_id, node)` returns `[%{workspace: mount, resolved: [%{point:, name:, path:}], missing: [ref], nested: [ref]}]` — one entry per workspace, newest first, from ONE batched read (`EvoDash.NodeContext.workspace_entries/1` → the node's `EvoGit.VCT.workspace_entries/1`, so a refresh costs one round trip instead of 1+W) — and `[]` for a pending remote context (`remote? == false` with a binary node id) or a failed read. Resolved members are FLAT `%{point:, name:, path:}` maps (not mount structs), and an entry without resolved members keeps `resolved: []` and lists every stored member ref in `missing`, where a ref is the member's non-nil `"point"` else its `"path"`.
Workspaces never pass through `filter_absolute_projects/1` (a workspace has `path: nil` and must stay listed), and `AsyncLoad.create_workspace(node, name, members, opts)` is the write seam (the core's idempotent slug-keyed UPSERT) that runs only inside a supervised task.
The batch loader sends `{:workspaces_loaded, seq, node, result}` from the SAME task as the project load, and `{:vct_updated, node}` delegates to the private `reload_vct/1`, which bumps BOTH seqs and sends `{:projects_loaded, …}` plus `{:workspaces_loaded, …}`; an error result keeps the current list and prunes `expanded_workspaces` to surviving points.
`handle_event("create_workspace", …)` builds ordered member refs from `new_workspace_members` (vanished points skipped) and spawns `{:workspace_created, seq, node, result}`; success clears the member list, returns `palette_mode: :menu`, expands the created point, flashes and reloads authoritatively, while `{:error, reason}` keeps the form and flashes the mapped message (`:invalid_name`, `{:member_is_workspace, ref}`, `{:invalid_member, ref}`, `:invalid_members`, `:vct_unavailable`, generic fallback).
Workspace events: `palette_mode` (`phx-value-mode="new_workspace"` enters the form and clears the member list), `toggle_workspace` (`phx-value-point`, pure expand/collapse), `toggle_workspace_member` (`phx-value-point`, APPENDS on add so click order is the member order) and `create_workspace` (`name` plus an optional `description`).
Palette keyboard arithmetic is `Palette.item_count/3` (filtered rows + 3 actions locally, 2 remotely) and `Palette.new_workspace_index/2`; the action exists on remote nodes (unlike "Create New Project"), and the form's ordered refs, description and refusal copy come from `Workspace.member_refs/2`, `description_param/1` and `error_message/1`. A node switch resets `workspaces`, `expanded_workspaces` and `new_workspace_members`, so a remote view never shows another node's workspaces.

## Test strategy (load-bearing pins only)

Cadences, fixtures and seams: `test/evo_dash_web/live/CONTEXT.md` + `test/evo_dash_web/live/projects_live/CONTEXT.md`. Contracts a change must not break:
- `projects_live_test.exs` drives the real store, so assertions on `projects`, `active_project_path` and notifications use `wait_assigns(view, predicate)`; project fixtures are VCT mounts (`Helpers.seed_project/2`, `Helpers.clear_projects/0`, `Helpers.wait_for_projects/2`), and forgetting drives `forget_project` with `phx-value-point`.
- The batch message shape (`{:async_project_load, node, prev_node_id, path, results}`) and `AsyncLoad.handle_result/5`'s `{socket, applied?}` return are test-pinned; `handle_result/5` stays tolerant of result maps built without newer keys (`Map.get/3`).
- Canonical task-admission tests must expose the same provider configuration to the singleton `EvoGit.TaskRegistry` as to the test/LiveView: a process-local `ConfigDir.isolate!/1` override propagates through `$callers` to LiveView/loader processes but not to an already-running singleton, and a picker-visible account absent from the registry's config causes `{:provider_profile_not_found, id}` on both normal and GitHub launches. Synchronous launch tests need a restored shared config-directory override, never weaker model-lock assertions.
- Positive remote fixtures may inject `:remote_project_load_runner` / `:remote_resume_task_runner` without a live distributed node (restore both app-env keys after each test; serialize tests mutating these shared keys); positive remote persistence fixtures need a distinct BEAM-node atom plus an owned bundle with matching `{target_id, beam_node}` scope, readiness true and no load error — target-id plus local BEAM identity is a PENDING target and must neither persist nor consume async batches, and local-as-remote / unowned bundles must produce no model-only persistence event.
- Notification tests seed `notified_task_ids` + `notified_task_ids_ready?: true` explicitly; a test leaving `ready?` false asserts NO `task_notification` event.
- `change_model_selection/2` must obtain its bundle through `ModelSelectionScope.bundle/1`; checking only `is_map(model_selection)` bypasses the ownership/readiness boundary used by launch and persistence. Unreachable remote tests assert an unavailable bundle, false readiness and a load error, not a successful empty Auto selection (an earlier explicit or pending selection stays preserved on failure).
- Canonical-lock page assertions are not evidence that `resolved.model_spec` belongs in task opts: the shared helper already reconstructs canonical picker maps, core admission preserves them, and the Store codec preserves nested string keys.
- Node-switch behaviour (state clearing, `&node=` push_patch, gate states, stale-node restore skip) lives in the same file; `<node>` tests register a fake ConnectionManager in the real `EvoGit.RemoteConnection.Registry`.

## Constraints

- Keep `projects_live.ex` from growing: new loaders go into `async_load.ex` / `notifications.ex`, pure payload building into `task_submit.ex` / `launch_options.ex`, palette arithmetic into `palette.ex`, workspace form helpers into `workspace.ex`, foreign-repo helpers into `foreign_repos.ex`, shell execution into `commands.ex`, and anything else into a new small support module — not the main file (3 072 lines and the page's event surface).
- Every new async message needs: a unique tag, a monotonic seq assign when more than one can be in flight, and a node (+ context, e.g. path/task id) stale guard. Never apply a result keyed only by "latest".
- No polling. All PubSub handling stays node-filtered through `NodeAware.event_from_current_node?/2`; the 300 ms debounce is the only coalescing mechanism.
- No `try/rescue` around store/RPC calls — use `EvoDash.SafeCall`. No `String.to_atom/1`/`to_existing_atom` on client input (whitelist maps only).
- User-facing strings are `gettext`-wrapped; never run gettext extract/merge during feature work.
