# ProjectsLive — Support Modules & Page Notes

## Intent

Support modules for `EvoDashWeb.ProjectsLive` (`GET /` and `GET /projects`) plus the durable design notes for the Projects page (command palette, project activation, task form threading, foreign repos, node handling).

**The governing rule of this node: no `ProjectsLive` process ever blocks on a task-store or RPC call.**
Every store/registry/`EvoDash.NodeContext` read AND every slow write (task launch, project command, attachment read) runs in a supervised `EvoDash.TaskSupervisor` child and lands back as a message with a monotonic seq or an in-flight marker as its stale guard.
The only work left in the process is the instant click mutation (`cancel_task`, `delete_task`, `clear_finished_tasks`, a project mount) and pure validation, wrapped in `EvoDash.SafeCall.run/1` so a `GenServer.call` exit/`:timeout` becomes a flash instead of a crashed LiveView.

## The Rule — nothing in the LiveView process blocks

- **Reads** (`NodeContext.projects/1`, `list_task_ids`, `get_task_lite`, `list_tasks_paginated`, `get_resolved_config`, `list_custom_agents`, remote RPCs) never run in `mount/3`, `handle_params/3`, `handle_event/3` or `handle_info/2`. They run inside a `Task.Supervisor.start_child(EvoDash.TaskSupervisor, fn -> … end)` body, are `EvoDash.SafeCall.run/1`-wrapped there, and `send/2` their result to the LiveView.
- A store call can take many seconds and a `GenServer.call` can EXIT (`:timeout`, dead server) — which `rescue` cannot catch, hence `SafeCall`.
- **Writes** split by cost: the instant click mutations whose effect must be observable immediately (`clear_finished_tasks`, `delete_task`, `cancel_task`, plus the palette/form project mount `NodeContext.mount_project/3`) stay synchronous but `SafeCall`-wrapped; the slow writes (`start_task`, a project `run_command`, an attachment read) use the async write path below, `forget_project` is optimistic + fully async, and their follow-up reload/scan work is async either way.

### Async write path (the ONE shape)

Every blocking write — a task launch, a project command, an attachment read — has ONE shape: bump a monotonic seq (or record the picker id in `:attach_pending`), set its `*_running`/`*_pending` marker, spawn the work with `EvoDash.SafeCall.start/3,4` against `EvoDash.TaskSupervisor` (never a bare `Task.start`), then apply the result in a seq-marked (or marker-gated) `handle_info/2` that clears the marker, so the tab never blocks.
A purely-instant validation failure stays synchronous and owns its own flash (`:attachments_over_cap`, a missing custom agent, a stale-model `{:error, reason}`, a failed `SafeCall.start` itself).
A failed spawn clears nothing it never set (`task_launching`/`command_running` stay false) and flashes a retry-able error, so no affordance is left wedged.
The GitHub issue-fix launch is the deliberate exception: a synchronous `SafeCall.run/1` start (`GitHub.start_fix_task/3`), because it already runs off the async issues flow and its result drives the modal close.

## Mount & handle_params

- **Dead render (`connected?(socket) == false`) makes ZERO task-store calls**: `projects: []`, `notified_task_ids: MapSet.new()`, `notified_task_ids_ready?: false`, `task_notifications_seq: 0`, `projects_seq: 0`, `clear_history_seq: 0`, `foreign_repos_restoring_from: nil`, `auto_activate_candidate?: false`, the in-flight markers at rest (`command_seq: 0`, `command_running: nil`, `task_launch_seq: 0`, `task_launching: false`, `attach_pending: %{}`), `project_config_mtime: nil`, no PubSub subscriptions. No registry read (the VCT project set, `list_task_ids`) happens on this path.
- **Connected mount** subscribes the page topics and sends `:load_config_status`; it performs only LOCAL, cheap, non-store setup: a memoized `EvoGit.Config.resolve()` (`Process.put(:memo_config_resolve, …)`, read only by `Project.load_model_selection/2` / `load_model_profiles/1`, which run inside the AsyncLoad task — so the memo does NOT serve the deferred `:load_config_status` read), `AsyncLoad.load_custom_agents/1` (local `agents.toml`) and `EvoGit.Runtime.WorktreeInitScript.build_systems()`. At mount the node is always LOCAL (NodeAware seeds local; `?node=` resolves later), so these are local file reads, not RPC.
- `Project.load_model_profiles/0,1` (the legacy `{profiles, selected_id}` tuple API) has NO production call site — only tests; the page uses `Project.load_model_selection/2` via the AsyncLoad batch.
- `handle_params/3` captures `prev_node_id` BEFORE `assign_node/2` so the node-switch reset and the batch loader see the transition, sets `auto_activate_candidate?: is_nil(params["project"]) and is_nil(current_node_id)`, and ends with `AsyncLoad.maybe_spawn(socket, prev_node_id)` (connected only). It never seeds `notified_task_ids` itself.
- Auto-activation of the newest VCT project is a **continuation** of the batch (`maybe_auto_activate_project/1`), not part of mount: it also requires `auto_activate_candidate?`, `applied? and results[:auto_activate?]`, no remote context, no active project, a `%{path: path}` first entry with a binary `path`, and `File.dir?` before `activate_project/2`. Because it lands one frame after `live/2`, tests must `wait_assigns` for `active_project_path`.

## Browser notifications — `notified_task_ids_ready?`

`@notified_task_ids` is a `MapSet` of terminal ids already accounted for; `@notified_task_ids_ready?` says the set has been SEEDED from the store.

- A fresh connected mount starts `ready? == false` with an empty set, and detection is **skipped entirely** while not ready — diffing against an unseeded set would notify every historical terminal task.
- The seed arrives with the batch (`:terminal_ids`, local context only, only while `ready? == false`) or, after a clear-history, with `{:task_history_cleared, …}`.
- Once ready, each `:node_aware_reload_tasks` spawns ONE `Notifications.spawn_scan/4` with the current known set; ids absent from it are new, and an id whose `get_task_lite` returns nil is marked notified without notifying.
- Notifications are **LOCAL-context only** (`current_node_id == nil`); remote contexts never scan, never seed, never push.
- `clear_task_history` flips `ready?` to false before clearing so the in-flight window cannot notify, then restores it on arrival (error included).

## Guarded mutations

- `clear_task_history`: sets `notified_task_ids_ready?: false`, empties the sidebar lists immediately via `NodeAware.assign_active_tasks/1` (an ETS-hub read, no store call), and spawns a task running `SafeCall.run(fn -> TaskRegistry.clear_finished_tasks(); Notifications.load_terminal_ids() end)` → `{:task_history_cleared, seq, node, result}`; the rest of the refresh arrives through the regular node-filtered broadcasts.
- `forget_project`: bumps `projects_seq`, drops the row optimistically by `point` (`Enum.reject`), resets `palette_selected_index`, and runs the forget + authoritative reload in ONE supervised task → `{:projects_forgotten, seq, node, result}`; the `{:vct_updated, node}` broadcast is the backstop.
- `cancel_task` / `delete_task`: `SafeCall.run/1`; an error flashes instead of crashing.
- `task_submit` / `do_task_submit/4`: the INSTANT half is synchronous and pure — the pending-remote, missing-project, in-flight foreign-repo restore (`foreign_repos_restoring_from == task_resume_from` → "Still loading the previous task's settings. Please try again in a moment."), missing-custom-agent and `TaskSubmit.build_opts/6` refusals all flash without spawning anything, so the restore can never lose the race against submit.
- `run_command`: the instant half resolves the command from `@commands` via `Commands.lookup/2` (unknown → `"Command not found: …"`); the `Commands.run/2` OS call runs in a supervised task, and `:command_running` plus the `"Running '<cmd>'…"` info flash are the page's only in-flight feedback (the Configure buttons live in `ProjectComponents`). A failed spawn flashes `"Could not run '<cmd>'. Please try again."` and sets no marker.
- attach-file picks: the instant half only validates (the manual path's `File.regular?/1`) and refuses a capped binary pick via `AttachFile.count_cap_reached?/1` + `push_count_cap_error/2`; the read is spawned and its `{{:attachment_loaded, …}}` result applies only while that picker id is pending.
- A node-context change clears `:attach_pending` (with `:file_pick_bases` and `:staged_attachments`), so a read started on the previous node is dropped; the command and launch continuations are rejected by their own seq + project-root/node guards, and their markers (`:command_running`, `:task_launching`) are reset by the next run of that same action.

## Foreign-repo resume restore

`start_foreign_repos_restore/2` marks `foreign_repos_restoring_from: task_id` and spawns a `SafeCall.run(TaskRegistry.get_task_lite(task_id))` whose only consumed field is `opts[:foreign_repos]`, arriving as `{:foreign_repos_restored, task_id, node, result}`; the handler drops it unless the task is still the resume target on the same node.
The lookup is deliberately the LOCAL `TaskRegistry.get_task_lite/1` (same struct as `get_task/1` minus the archive); the node-aware restore for a remote activation lives in `ProjectFlow.task_foreign_repos_for_resume/2`, inside the supervised remote-activation task.
Remote activation also resolves `Application.get_env(:evo_dash, :remote_project_load_runner, &remote_project_load/2)` at call time INSIDE that task (arity 2, `(node, path)`, same `{:ok, results_map}`/error contract), and for a nonempty resume task id `Application.get_env(:evo_dash, :remote_resume_task_runner, &NodeContext.get_task_lite/2)` (arity 2, `(node, task_id)`, the lite task or nil).
Both seams are inert unless configured and preserve pending-target admission, result messages/stale guards and task-repos-win precedence.

## RPC / I/O audit

- `projects_live.ex` — only the instant `SafeCall`-wrapped mutations above (`cancel_task`, `delete_task`, `clear_finished_tasks`, `NodeContext.mount_project/3` on a palette Enter, then `push_patch`) and pure `TaskSubmit`/`LaunchOptions` building run in the LiveView; launches, commands and attachment reads are spawned.
- `github.ex` — all `gh` work runs through the `:github_runner`/`:github_issues_runner`/`:github_issue_markdown_runner` seams (resolved at spawn time) in supervised tasks; dispatch and result application require a usable target (a pending/gated remote target never falls back to local RPC or task launch). Message tuples keep their arity but carry an opaque request-scoped envelope (target identity + unique request token): handlers ignore unscoped results and validate target, BEAM node, path and request identity; closing/reopening the modal, changing filters or superseding a fix invalidates earlier replies (repeated same-issue requests included); accepted results are consumed once; runners and task dispatch use `SafeCall` so an exit becomes a reported result.
- `project.ex` / `project_flow.ex` — local TOML/FS reads; `project_config_mtime/1` is the ONE cheap `File.stat/1` the task-broadcast debounce runs; `path_suggestions/3` calls `EvoGit.PathSuggestions.suggest/1` locally and `NodeContext.list_path_suggestions/2` remotely; local mounts and `File.dir?`/`Path.expand` stay synchronous (cheap, user-initiated), `mount_point_for/2` is pure.
- Everything else (`async_load.ex`, `notifications.ex`, `remote_view.ex`, `assigns.ex`, `state_persistence.ex`, `attach_file.ex`) does its I/O in a spawned task or not at all; `handle_result/5` is pure assignment + the `:resume_foreign_repos_guard` drop for `:foreign_repos`, and `attach_file.ex` reads the LOCAL node's filesystem OFF-PROCESS (the node dropdown never proxies it), so a 15 MiB image or a large PDF never decodes in the LiveView.

## Project-config freshness (`genesis.toml` mtime gate)

The page keeps the parsed `genesis.toml` (`project_config`, `worktree_script`, `commands`) beside `:project_config_mtime`, captured WITH that parse through `Project.project_config_mtime/1` (nil = not read yet, no file, or a remote path).
Every site assigning the config captures the mtime beside it: `activate_project/2`, `AsyncLoad.remote_extras/3` and the `{:async_remote_project, …}` handler.
`refresh_project_config/2` re-parses ONLY when forced (`force?:` opening the Configure/Project Settings panel always shows current settings) or the mtime differs, so the `:node_aware_reload_tasks` debounce costs one `File.stat/1` per broadcast and never a TOML parse.
A REMOTE project's `genesis.toml` lives on the other host, so `remote?` is excluded from the local re-read (it would clobber the RPC-loaded config with nil); that config arrives with the activation/AsyncLoad result.
The foreign-repo list is in-memory and not re-read by this path; `EvoGit.ProjectConfig.read/1` stays for the eager activation and forced panel-open reads — only the per-broadcast re-parse is gated.

## Resolved-config reads & freshness (`EvoGit.Config`)

- `EvoGit.Config.resolve/0` runs in the LIVEVIEW process only twice: the mount memo (see above) and the deferred `:load_config_status` handler (→ `Helpers.config_status/0` → `EvoGit.Config.config_status/0`, which also reads `credentials.toml`); every picker/custom-agent read happens inside the AsyncLoad task.
- This node makes NO `reload_config`-family call (`NodeContext.reload_remote_config/1` / `RemoteAPI.reload_config/0` appear only in Settings).
- The page subscribes only to `"tasks"` and `"vct"`: there is no config-change push, so resolved-config-derived assigns (`@model_selection` — which carries the whole resolved config, `ModelSelectionScope.bundle?/1` requires its `:config` key — `@provider_profiles`, `@model_selections`, `@model_selection_enabled`, `@custom_agents`, `@selected_model_spec`, `@config_status`) refresh ONLY on `handle_params` (AsyncLoad batch), `retry_model_selection`, a node switch (`StatePersistence` keeps `@custom_agents`) or a remount.
- `@config_status` is computed once per connected mount and never refreshed, so the config warning banner stays stale after any config.toml/credentials.toml change until remount.
- `EvoGit.Config.VersionState.onboarding_needed?/0` runs on the DEAD render only.
- No `File.read`/`File.stat`/`File.exists?` of `config.toml`/`credentials.toml` and no config-path computation exist in this subtree; the only filesystem reads are `genesis.toml` (`ProjectConfig.read` in `projects_live.ex`, `project.ex` and `NodeContext.read_project_config` from `async_load.ex`, plus the `project_config_mtime/1` stat), `agents.toml` and the project-mode `CONTEXT.md` existence check (`project.ex`, local and remote).

## Model-selection helper contracts

The canonical task-picker assign is `selected_model_spec`: a STRING-keyed map holding only `provider_profile_id`, `model` and optional `reasoning_effort`; `%{}` is explicit Auto, nil means uninitialized/use the node default.
`Project.load_model_selection/0,1,2` returns `LLMSelection.from_config(config, rules_enabled)` for the executing node, and `load_model_selection_from_config/2` is its pure projection seam. Local loading honors the process-local `:memo_config_resolve`; remote loading uses the target's resolved config and returns `{:error, reason}` on transport failure — never a successful empty configuration.
`LLMSelection.from_config/2` returns at least `provider_profiles` (canonical string maps) and `model_selections` (ordered core atom-map projections); the bundle is an in-memory picker value, never persisted to browser storage or sent as task opts.
`reconcile/2` normalizes a string-keyed candidate (nil → defaults, `%{}`/legacy `""` → Auto, legacy ids migrated, removed provider/model/effort → valid node default); `task_opts/2` yields explicit `model_spec: <canonical string map>, model_id_locked: true` or `[]` for Auto, and ERRORS on a stale/invalid explicit choice rather than launching as Auto.
Membership/reasoning/legacy normalization live in that helper (`Schema.provider_profiles/1`, `model_selections/1`, `resolve_model_spec/2`); the canonical selection is rebuilt from resolved `provider_profile_id` + `model` + reasoning, never from `resolved.model_spec` (the ReqLLM-ready identifier).
`ModelSelectionScope.bundle/1` validates the server-only `model_selection_scope` against `{current_node_id, current_node || node()}`, rejecting pending remote targets, failed/not-ready loads and malformed bundles; it accepts an unstamped bundle only in the local `{nil, node()}` context for mount compatibility. `LaunchOptions` uses the same boundary and additionally rejects any non-nil `pending_model_selection` (explicit pending Auto included).
A failed model read or guarded whole-batch failure invalidates bundle/scope/readiness and records `model_selection_error`, preserving `selected_model_spec` and `pending_model_selection` with no reconciliation or partial persistence. Every connected batch marks readiness false before spawning and always delivers a scoped result (runner raise/exit, invalid shape and supervisor-start failure included); whole-batch failure returns `{socket, false}` so no successful-load continuation runs.
Freshness/restoration: canonical batches carry `model_selection` (assigned with `provider_profiles`/`model_selections`, then `selected_model_spec` reconciled on same-node refreshes too); the five-tuple tag and its `load_scope` metadata (projects_load_seq, target id, captured selection) are unchanged; stale generation/target/BEAM-node/path results are rejected and a newer user choice is never overwritten; unstamped legacy result maps carrying `model_profiles`/`default_selected_model_id` are still accepted.
`StatePersistence.maybe_restore_model_selection/2` runs on the whole persisted string-keyed state after the parent's node check (`model_spec` outranks `selected_model_id`, explicit Auto included); a restore arriving before an owned ready bundle is stored as `pending_model_selection` and validated when that target's bundle lands, and an unowned/mismatched remote bundle never reconciles or consumes it.
Node switches clear projects, bundle, picker projections, selected canonical/legacy ids, scope, error, readiness and pending restore before fetching the new node; a changed stamped BEAM-node scope resets state even when the target id is unchanged. `model_selection_state/1` serializes only the three canonical keys (never credentials or bundle metadata); legacy-only callers keep `selected_model_id` until migration completes.
`maybe_persist_model_selection/1` emits the merge-only `persist_model_selection` event (`%{node, model_spec}` plus `project` when a project param is set and `scope_token` when the draft scope is a VCT point) only for an owned ready bundle without load error or pending restore; the browser merges those fields into the same node's state instead of replacing DOM-owned prompt/form data, while full-form `persist_state` stays a separate replacement event. Provider/model/reasoning change handlers clear `pending_model_selection` so an earlier restore cannot override a newer interaction.
`LaunchOptions.apply/2` is pure, preserves unrelated fields, removes stale `model_id`/`model_spec`/lock keys before merging validated options, emits nonempty custom-agent ids and the explicit `:persistent_state` opt, and omits default balanced quality; a missing bundle fails launch with `:model_selection_not_loaded`. GitHub fixes use the SAME helper. Quality (`fast`/`balanced`/`high_quality`) and reasoning stay independent policies.
The page seeds `model_selection_scope: nil`, `model_selection_ready?: false` and `model_selection_error: nil` beside the nil bundle (a local `Project.load_model_selection/0` seed instead uses scope `{nil, node()}`, readiness true, error nil); `change_model_selection/2` must use `ModelSelectionScope.bundle/1`, and a `model_selection_error` is displayed and retryable, never converted into Auto.

## Task-form toolbar & `task_submit` payload

The form keeps ONE `.input-controls` toolbar: LEFT cluster = the attach-kind dropdown + the fused mode+speed capsule; RIGHT cluster (`ml-auto` on its first element) = optional custom-agent select → model capsule (`@use_llm_selection?`; else the custom-agent select, else the legacy model select) → circular send button.
Mode, quality (speed) and reasoning are independent policies, and the event payload keys are unchanged: `mode`, `level`, `provider_profile_id`, `model` (plus the legacy `model_id` variant), `reasoning_effort`, `agent`.
`handle_event("task_submit", %{"prompt" => prompt, "mode" => combined_mode})` matches STRICTLY on both keys — no tolerant fallback clause — so `#task-form` must always carry `mode`, a hidden `<input type="hidden" name="mode" value={@mode}>` rendered from the capsule's `@mode` (`= @task_mode`); the capsule's Layer-2 buttons are `type="button"` and fire `task_change`, which moves that server-side truth.
`node_path` / `starting_commit` / `resume_from` / `build_system` / `archive` arrive through the Configure dropdown's `form="task-form"` inputs (always in the DOM, class-hidden), while `quality_level` is never a form field — `LaunchOptions.apply/2` reads the `:quality_level` assign.
Opt assembly is PURE in `EvoDashWeb.ProjectsLive.TaskSubmit`: `mode/1` maps the combined string to `{task_type, core_mode}` (`"custom_agent"` → `{:evolve, "custom"}`, unknown → `{:evolve, "simple"}`); `build_opts/6` puts `:path`, `:mode`, the trimmed `:prompt`/`:objective`, `:build_system` (genesis only, `String.to_existing_atom/1` so an unknown system stays a visible `ArgumentError`), `:node_path`/`:starting_commit`/`:resume_from` (evolve only), `:foreign_repos`, `:archive`, the base64 `:attachments` (raw `"data"` bytes are staged in memory and encoded only here, because the store Jason-encodes opts) and ends in `LaunchOptions.apply/2`; it re-checks the attachment cap and answers `{:error, :attachments_over_cap}` WITHOUT touching staged state.
The launch is ASYNC: `do_task_submit/4` bumps `:task_launch_seq`, sets `:task_launching`, spawns `EvoDash.SafeCall.start(self(), {:task_started, seq, task_type}, …)` (local `TaskRegistry.start_task/2` or remote `NodeContext.start_task/3`, both `SafeCall.run/1`-guarded), and the seq-guarded ack owns the flash and form reset — so the prompt clears only on success and a refused launch leaves prompt, staged attachments and form intact.

## Persist agent state (per-task, default ON)

The page owns the `:persist_agent_state?` assign, defaulted `true` by `Assigns.assign_form_defaults/1` and reset to `true` by `StatePersistence.clear_node_state/1` on a node switch.
`toggle_persist_agent_state` sets it to `params["value"] == "true"` and re-persists form state: the Task Options checkbox is server-assign-driven and has no `name`, so a checked click sends `%{"value" => "true"}` and an unchecked click omits the key; the control lives in `TaskFormComponents.persist_agent_state_toggle/1`.
`StatePersistence.maybe_persist_state/1` pushes `persist_agent_state?` and `restore_state` restores it through `maybe_restore_persist_agent_state/2`, which accepts `true`/`false` and their string forms and leaves the assign untouched otherwise, so the ON default survives a payload without the key (unlike `maybe_restore_task_archive/2`).
`LaunchOptions.apply/2` ALWAYS puts the `:persistent_state` opt explicitly — the boolean assign verbatim, any non-boolean/nil assign (GitHub fix, restored payload, older browser state) as `true` — so the opt is self-describing and covers both `TaskSubmit.build_opts/6` and the GitHub fix path; `review_live/actions.ex` (resume / extract-skills / auto-resolve) and the Assistant/`HomeLive` session path deliberately omit it and inherit the core default (`true`).

## Payload-vs-consumed gaps

- `get_resolved_config` / `load_model_profiles_from_config/2` transfer the whole resolved config and full `Schema.model_profiles/1` maps; `list_custom_agents` transfers definitions + script + script_status (only ids and script non-empty-ness consumed); `read_project_config` transfers the whole genesis.toml (`"worktree"`, `"script"`, `"commands"`, `"foreign_repos"` consumed); `github_upstream`'s `url` is never read (only `owner`, `repo`, `gh_available`).

## Path autocomplete & Windows handling

`Project.path_suggestions/3` matches typed text against the loaded project mounts' OS paths as a case-insensitive SUBSTRING (infix), deduped over `ProjectFlow.absolute_path_for_node?/2`, capped at 8 with project paths first; filesystem entries come from `EvoGit.PathSuggestions.suggest/1` (local) or `NodeContext.list_path_suggestions/2` (remote), so `<dir>/` lists that directory and `~` lists home identically on both branches. Backslashes normalize to `/` before suggestion/dir checks; the expanded path is what gets validated (`NodeContext.dir?/2` remotely, `File.dir?/1` locally), stored in the URL and registered in the VCT.

## Memory

The page keeps summary maps only: `projects` (`%EvoGit.VCT.Mount{}` rows, display-only), `notified_task_ids` (a `MapSet` of ids), plus the sidebar lists owned by `NodeAware`. No full `%TaskInfo{}` row is retained; notification titles are computed in the spawned scan and discarded after `push_event`.

## Open-project / selection state persistence (where the "current project" lives)

There is exactly ONE active project per page (`active_project` + `active_project_path`): no project tab list or tab bar, and the palette's VCT workspaces are grouping mounts that can never become the active project.
`active_project` is a display-only `%{path:, name:, point:}` map; on a LOCAL activation `point` comes from the PURE `ProjectFlow.mount_point_for/2` over the already-loaded `@projects`. The UI renders `name` as the visible identity with `path` secondary, and the point is kept only as the registry/search/forget identity.
A REMOTE activation takes its point from `ProjectFlow.remote_project_load/2` through the shared private `mount_project_point/3`, which unwraps the doubly-wrapped `SafeCall.run/1` + `NodeContext.mount_project/3` result and maps every failure shape (outer/inner `{:error, …}`, non-mount payload, non-binary point) to nil; a nil point is simply not rendered.
The open project lives in URL query params — `?project=<absolute path>` plus `&node=<target id>` remotely — hand-built by `project_url/2` (`project_flow.ex`, duplicated in `projects_live.ex`), never via `Helpers.with_node_param/2` (it appends `?` and would corrupt the query).
`handle_params/3` re-derives it on every navigation: local → `ProjectFlow.normalize_project_path/1` + `File.dir?/1` then `activate_project/2` (relative/blank params ignored, an existing-but-invalid absolute path clears the project); remote → `normalize_remote_project_path/2` + `spawn_remote_project_activation/2,3` (gated on no pending target / no active remote gate).
Every LOCAL entry point delegates to `ProjectFlow.activate_local_project/3`, the ONE local body: normalize/expand → `File.dir?/1` → VCT mount (`mount_project_point/3`) → optimistic `projects`/`active_project`/`active_project_path` with the palette closed and reset → `push_patch`; `open_project/2`/`select_project/2` only choose their own missing-directory wording, and `create_project/2` → `create_local_directory/1` adds only the "Project created" info flash.
Browser persistence is `sessionStorage` ONLY (never `localStorage`), owned by the `StatePersistence` JS hook on `#dashboard-root` (`phx-hook="StatePersistence"`; `data-project`, `data-task-mode`, `data-node-id`, `data-task-draft-project`, `data-task-draft-scope`).
Draft scope identity is `{node, EvoDashWeb.DraftScope.token(...)}`: the selected project's VCT POINT (`vct:///projects/<name>`), else the raw absolute OS path (verbatim, never `Path.expand/1`ed) only for a project with no mount; the hook stores under `"dashboard_state:" <> JSON.stringify([node, token])` and falls back to the bare `dashboard_state` key when the page has no project token at all. One repo re-spelled keeps ONE draft, while two points over one OS path stay separate, and the token is scope ONLY — admission, `mount_project` and task start always take the resolved OS path (`DraftScope.path/1`), and a workspace token never reaches `start_task`.
`StatePersistence.draft_scope/1` is the ONE scope computation: the path comes from the SAME source as the payload's `project` field (`"project"` URL/reconnect param, else `active_project_path`), then the point from `active_project.point` when it belongs to that path, else from the PURE `ProjectFlow.mount_point_for/2` over the async-loaded `@projects` — never a store/RPC read on the render path.
`data-task-draft-scope` is the ONLY scope attribute (the hook's token source); `data-task-draft-project` stays the legacy raw-path identity the hook adopts a path-keyed entry through.
A point arriving after the first frame (the async mount load) is a MIGRATION, not a reset: the first frame saves under the raw-path token and the scoped key adopts that path-keyed entry once the point lands.
`scope_token` rides both `persist_state` and the merge-only `persist_model_selection`, carrying the VCT POINT the hook's `matches/2` verifies before adopting a stored entry — a raw-path scope is left unstamped (the hook stamps path scopes on its own writes) and a page with no project carries no `scope_token` at all. `restore_state` stays node- and project-gated only, so a legacy payload with just `project` + `task_prompt` restores normally.
`StatePersistence.maybe_persist_state/1` pushes `persist_state` with keys `project`, `scope_token`, `task_mode`, `selected_agent_id`, `quality_level`, `task_prompt`, `task_node_path`, `task_starting_commit`, `task_resume_from`, `show_advanced`, `show_project_settings`, `task_archive`, `persist_agent_state?`, `foreign_repos` (serialized id/path/description/writable/base_sha), `node`, plus `model_selection_state/1`'s `model_spec` or legacy `selected_model_id`. It fires only on server events (mode/agent change, quality level, project-settings toggle, foreign-repo add/edit/remove, successful `task_submit`, the node-switch clear), so project ACTIVATION pushes nothing and the saved `project` is refreshed only by a later persist or the client watcher (`persistFormState`, 300 ms debounce over `prompt`/`node_path`/`seeds`/`starting_commit`, reading `data-project`).
On mount the hook pushes the saved object back as `restore_state`; the handler gates on `(params["node"] || "local") == (current_node_id || "local")` and restores the project only while `active_project` is nil (URL `starting_commit`/`resume_from` win over saved ones), activating locally or via `spawn_remote_project_activation/3`.
Foreign-repo add/edit/remove has NO durable write: `EvoGit.ProjectConfig` exposes only `read/1` plus `write_worktree_script/…`, so the sessionStorage snapshot is the only copy between launches and a started task freezes it into `opts[:foreign_repos]`.
`:node_path` is the context-tree starting node (`EvoGit.Core.ContextNode.load/3`, default `./`, validated by `Runtime.Helpers.validate_node_path/2`), not a BEAM node — the evolve-only "Starting Node" input is the dashboard's only context-tree addressing surface.
No server-side record of "the open project" exists: the only core-kept project state is the VCT mount registry in the task store's `vct_mounts` table, so a fresh mount without `?project=` auto-activates the newest mount via `maybe_auto_activate_project/1` (local context only).
The VCT owns ordering (`last_opened_at` DESC, nil last) and the cap (`EvoGit.VCT.max_projects/0`, 100 by default, app env `:vct_max_projects`; an over-cap registration evicts the oldest), and the palette renders exactly the rows `NodeContext.projects/1` returns.
A mount whose OS path is missing is NORMAL (portability): still listed, never filtered out, and opening it never creates the directory.
`"vct"` is the project-registry topic: `EvoGit.VCT` broadcasts `{:vct_updated, node}` after every successful mount/forget, and the handler skips a node mismatch or a pending remote target, else bumps `projects_seq` and reloads off-process.
Projects are node-scoped by each node's own mount table, not a column: `AsyncLoad.load_projects/3` uses `NodeContext.projects(node)` on a connected remote, `[]` for a pending/failing remote context and the local VCT otherwise; every mutation goes through node-aware RPC (`mount_project/3` inside `ProjectFlow`/palette Enter, `forget_project/2` for local AND remote), and the asset-side paths are `ProjectComponents.project_omnibox` + the `PaletteList`/`FocusInput`/`PathAutocomplete` hooks plus the `open_project`/`select_project`/`create_project`/`palette_keydown`/`forget_project` events.

## Workspace surface (VCT workspace mounts)

A VCT workspace (`%EvoGit.VCT.Mount{kind: "workspace", path: nil, members: [ordered %{"point", "path"}]}`) is a pure GROUPING point rendered in the palette; it is never a runnable project, never an `active_project`, and never reaches `path_suggestions/3`, `StatePersistence` or any task-launch path.
Page assigns: `workspaces` (per-workspace view maps, `[]` on the dead render), `expanded_workspaces` (expanded workspace points), `new_workspace_members` (ordered member points chosen in the form), `workspaces_seq` (the monotonic stale guard of the LIST) and `workspace_create_seq` (a SEPARATE guard of the create/replace write, because `EvoGit.VCT` broadcasts `{:vct_updated, node}` BEFORE it replies — a shared guard would drop every `{:workspace_created, …}` continuation and lose the flash, the return to the palette menu and the expanded row).
`AsyncLoad.load_workspaces(remote?, current_node_id, node)` returns `[%{workspace: mount, resolved: [%{point:, name:, path:}], missing: [ref], nested: [ref]}]` — one entry per workspace, newest first, from ONE batched read (`EvoDash.NodeContext.workspace_entries/1` → the node's `EvoGit.VCT.workspace_entries/1`, so a refresh costs one round trip instead of 1+W) — and `[]` for a pending remote context (`remote? == false` with a binary node id) or a failed read. Resolved members are FLAT `%{point:, name:, path:}` maps (not mount structs), and an entry without resolved members keeps `resolved: []` and lists every stored member ref in `missing`, where a ref is the member's non-nil `"point"` else its `"path"`.
Workspaces never pass through `filter_absolute_projects/1`: a workspace has `path: nil` and must stay listed.
`AsyncLoad.create_workspace(node, name, members, opts)` is the write seam (the core's idempotent slug-keyed UPSERT) and runs only inside a supervised task.
The batch loader sends `{:workspaces_loaded, seq, node, result}` from the SAME task as the project load, and `{:vct_updated, node}` delegates to the private `reload_vct/1`, which bumps BOTH seqs and sends `{:projects_loaded, …}` plus `{:workspaces_loaded, …}`; an error result keeps the current list and prunes `expanded_workspaces` to surviving points.
`handle_event("create_workspace", …)` builds ordered member refs from `new_workspace_members` by looking each point up in `@projects` (vanished points skipped) and spawns `{:workspace_created, seq, node, result}`; success clears the member list, returns `palette_mode: :menu`, expands the created point, flashes `Workspace %{name} saved.` and reloads authoritatively, while `{:error, reason}` keeps the form and flashes the mapped message (`:invalid_name`, `{:member_is_workspace, ref}`, `{:invalid_member, ref}`, `:invalid_members`, `:vct_unavailable`, generic fallback).
Workspace events: `palette_mode` (`phx-value-mode="new_workspace"` enters the form and clears the member list), `toggle_workspace` (`phx-value-point`, pure expand/collapse), `toggle_workspace_member` (`phx-value-point`, APPENDS on add so click order is the member order) and `create_workspace` (`name` plus an optional `description`).
Palette keyboard arithmetic is `Palette.item_count/3` (filtered rows + 3 actions locally, 2 remotely) and `Palette.new_workspace_index/2`; the action exists on remote nodes (unlike "Create New Project"), and the form's ordered refs, description and refusal copy come from `Workspace.member_refs/2`, `description_param/1` and `error_message/1`.
A node switch resets `workspaces`, `expanded_workspaces` and `new_workspace_members`, so a remote view never shows another node's workspaces.

## Test strategy

- `test/evo_dash_web/live/projects_live_test.exs` drives the real store; because mount/handle_params work is async, assertions on `projects`, `active_project_path` and notifications use `wait_assigns(view, predicate)` (~300 attempts) instead of asserting right after `live/2`.
- Project fixtures are VCT mounts: `Helpers.seed_project/2` asserts `{:ok, %EvoGit.VCT.Mount{}} = EvoGit.VCT.mount(path, name: name)` and forgets it in `on_exit`, `Helpers.clear_projects/0` forgets every registry row, `Helpers.wait_for_projects/2` polls the page's `projects` assign; palette assertions read `%Mount{}` `point`/`path`/`name`, and forgetting drives `forget_project` with `phx-value-point`.
- Canonical task-admission tests must expose the same provider configuration to the singleton `EvoGit.TaskRegistry` as to the test/LiveView; a process-local `ConfigDir.isolate!/1` override propagates through `$callers` to LiveView/loader processes but not to an already-running singleton.
- A picker-visible account absent from the registry's config causes `{:provider_profile_not_found, id}` on both normal and GitHub launches; synchronous launch tests need a restored shared config-directory override rather than weaker model-lock assertions.
- Positive remote URL/resume integration fixtures can inject `:remote_project_load_runner` and `:remote_resume_task_runner` without a live distributed node; restore both app-env keys after each test and serialize tests mutating these shared keys.
- Positive remote persistence fixtures need a distinct BEAM-node atom, an owned bundle with matching `{target_id, beam_node}` scope, readiness true and no load error (target-id plus local BEAM identity is a pending target and must not persist or consume async batches); local-as-remote and unowned bundles must produce no model-only persistence event.
- The batch loader's message shape (`{:async_project_load, node, prev_node_id, path, results}`) and `AsyncLoad.handle_result/5`'s `{socket, applied?}` return are test-pinned; keep `handle_result/5` tolerant of result maps built without newer keys (`Map.get/3`).
- Notification tests seed `notified_task_ids` + `notified_task_ids_ready?: true` explicitly; a test leaving `ready?` false asserts NO `task_notification` event.
- Node-switch behaviour (state clearing, `&node=` push_patch, gate states, stale-node restore skip) lives in the same file; `<node>` tests register a fake ConnectionManager in the real `EvoGit.RemoteConnection.Registry`.
- A fixture with a non-nil target id and `current_node == node()` is pending-remote to `ModelSelectionScope` and `AsyncLoad.handle_result/5`, even if a fake connection manager calls it connected, so it cannot assert successful picker loading or resume-guard consumption.
- Unreachable remote tests assert an unavailable bundle, false readiness and a load error, not a successful empty Auto selection; an earlier explicit or pending selection stays preserved on failure.
- The parent page's `change_model_selection/2` must obtain its bundle through `ModelSelectionScope.bundle/1`; checking only `is_map(model_selection)` bypasses the ownership/readiness boundary used by launch and persistence.
- Canonical-lock page assertions are not evidence that `resolved.model_spec` belongs in task opts: the shared helper already reconstructs canonical picker maps, core admission preserves them, and the Store codec preserves nested string keys.

## Constraints

- Keep `projects_live.ex` from growing: new loaders go into `async_load.ex` / `notifications.ex`, pure payload building into `task_submit.ex` / `launch_options.ex`, palette arithmetic into `palette.ex`, workspace form helpers into `workspace.ex`, foreign-repo helpers into `foreign_repos.ex`, shell execution into `commands.ex`, and anything else into a new small support module — not the main file (3 072 lines and the page's event surface).
- Every new async message needs: a unique tag, a monotonic seq assign when more than one can be in flight, and a node (+ context, e.g. path/task id) stale guard. Never apply a result keyed only by "latest".
- No polling. All PubSub handling stays node-filtered through `NodeAware.event_from_current_node?/2`; the 300 ms debounce is the only coalescing mechanism.
- No `try/rescue` around store/RPC calls — use `EvoDash.SafeCall`. No `String.to_atom/1`/`to_existing_atom` on client input (whitelist maps only).
- User-facing strings are `gettext`-wrapped; never run gettext extract/merge during feature work.
