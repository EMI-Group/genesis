# ProjectsLive Support Modules

## Intent

Support modules extracted from `EvoDashWeb.ProjectsLive` to keep the main LiveView module focused on lifecycle callbacks and event handlers.

## Routing Table

None — leaf directory (eight module files: `state_persistence.ex`, `project.ex`, `project_flow.ex`, `assigns.ex`, `github.ex`, `remote_view.ex`, `attach_file.ex`, `async_load.ex`).

## Notes

- **Task-form layout — server-seeded + client-driven**: The task-form layout (compact vs expanded) is seeded server-side at render from prompt length via `TaskFormComponents.layout_for/1` (threshold > 600 graphemes OR > 16 lines) and updated client-side while typing by the AdaptiveInput JS hook (mirrors the same thresholds). The hook also re-asserts the computed layout whenever the server re-seeds `data-layout` from its possibly-stale `@task_prompt` — a MutationObserver on `.input-layout` (attributeFilter: ['data-layout']) re-runs the computation on any server re-render (e.g. toggling mode/model), converging immediately (the hook only writes the attribute when the computed value differs) with zero network events, so the layout never snaps back to compact while a long prompt remains in the box. There is no per-keystroke prompt-change event — the textarea has no `phx-change`, so `@task_prompt` is updated only by `restore_state` and `task_submit` (single, non-keystroke events). Prompt draft persistence is purely client-side (the StatePersistence input watcher in app.js).
- **Post-submit prompt clear**: After a successful `task_submit`, `assign_form_defaults/1` resets `task_prompt: ""` (so the next render seeds `data-layout="compact"`), and the handler pushes a `"clear_prompt"` event (via `push_event/3`). The AdaptiveInput JS hook handles it: it empties the visible textarea (morphdom skips it under `phx-update="ignore"`), re-asserts autogrow + layout (converges — `applyLayout` only writes the attribute when the computed value differs, no MutationObserver loop), and clears the `task_prompt` field in the persisted `dashboard_state` sessionStorage blob so a reload cannot resurrect the submitted prompt. Mode/model selects and all other form state are untouched.
- **task_submit opts contract** (`projects_live.ex:1092-1118` + `do_task_submit/4` at `:2004`): the handler pattern-matches `%{"prompt" => prompt, "mode" => combined_mode}` and builds the start_task opts as `[path: active_project_path, mode: <"new"|"existing"|"simple"|"custom">]` (mode mapped from `genesis_new`/`genesis_existing`/`evolve_simple`/`custom_agent`; `custom_agent` → task type `:evolve` with mode string `"custom"` — the UI combined-mode string differs from the core mode string), then conditionally adds: `:prompt` (genesis — trimmed textarea text) XOR `:objective` (evolve — same trimmed text), `:build_system` (genesis, `String.to_existing_atom`), `:node_path` + `:starting_commit` + `:resume_from` (evolve, non-blank only), `:foreign_repos` (from `@foreign_repos` assign when non-empty), `:archive` (true when checkbox), `:model_id` (from `@selected_model_id`), `:agent` (from `@selected_agent_id` when non-empty). **Custom Agent mode REQUIRES the `:agent` opt**: the handler guards before `do_task_submit/4` — `combined_mode == "custom_agent"` with nil/"" `@selected_agent_id` flashes gettext "Custom Agent mode requires selecting a custom agent." and refuses to start; `task_change` to `"custom_agent"` auto-selects the first custom agent (from `@custom_agents`) when none is selected. Dispatched as `NodeContext.start_task(node, task_type, opts)` when `@remote?` else `TaskRegistry.start_task(task_type, opts)`; `NodeContext.start_task/3` (`node_context.ex:517-519`) is a thin delegate to `EvoGit.RemoteNode.start_task/3`. Other dashboard start_task call sites: `merge_check.ex:128` (auto-resolve: `:evolve` with hardcoded `:objective` + `:starting_commit`/`:merge_from`/`:merge_target`) and `review_live.ex:685` (`:extract_skills`). Objective display reads `opts[:prompt] || opts[:objective]` (`task_card_components.ex:94` and `:489`; `review_live.ex:821`).
- **NO file-upload/attachment machinery exists for objectives**: the objective comes exclusively from the `<textarea name="prompt">` (`task_form_components.ex:161-181`) as a plain form string. Zero hits in evo_dash for `allow_upload`/`Phoenix.LiveView.Upload`/`consume_uploaded_entries`/`live_file_input`/`<.live_file_input>`/`type="file"`/`accept=`; no FileReader-style JS hook (`assets/js/hooks/` = `adaptive_input.js`, `sidebar_collapse.js`, `node_switch_fade.js` only). The only upload-adjacent traces are boilerplate: the standard `:multipart` parser in `endpoint.ex:41`, the live_reload `priv/static/(?!uploads/)` exclusion in `config/dev.exs:50`, and a doc-comment pointer to `Phoenix.Component.live_file_input/1` in `core_components.ex:149`. The directory picker is server-side (wx/native dialog, `EvoDash.DirectoryPicker`) and never reads file contents. No evo_dash code path reads an objective/prompt from disk (evo_dash `File.read`/`File.ls` uses are config.toml, genesis.toml, VERSION, and path-autocomplete browsing only).

### The per-navigation (GET /) cost — why it's slow

LiveView runs `mount/3` TWICE per full page load (dead HTTP render + WebSocket connect), and `handle_params/3` after each. Per mount cycle:

1. **NodeAware.on_mount** (applied to ALL LiveViews via `evo_dash_web.ex`): `NodeContext.list_targets()` (TOML read) + `connection_status()` (GenServer) + **`list_tasks_summary` #1 on the CONNECTED mount only** (node_aware.ex — the dead-render skip gates the sidebar load behind `connected?/1`, so the dead HTTP render fires NO summary query; the connected mount fires exactly one).
2. **ProjectsLive.mount**: `list_recent_projects()` (SQLite) + `Config.resolve()` + `build_systems()` (module attr, pure) + `list_task_ids` #1 + deferred `:load_config_status`. ProjectsLive has no sidebar loader of its own — the unified NodeAware loader is the single path.
3. **handle_params**: `assign_node/2`'s summary reload is dedup-guarded by `:tasks_node_loaded` (node_aware.ex:175-183 — prevents the mount double-fetch and the dead-render re-fetch); ProjectsLive's fallback branches run only the `list_task_ids` notified-set union; with a project → `activate_project` (File.dir? + detect_mode FS + **genesis.toml read** + `list_task_ids`).
4. **`:load_config_status`** (deferred one frame): `EvoGit.Config.config_status()` — re-reads config.toml + credentials.toml (cached parse + stat) — blocks a frame in the LiveView process.

⇒ **A single full page load fires `list_tasks_summary` exactly ONCE** (on the connected mount; the dead render skips it and `assign_node`'s dedup guard suppresses the handle_params re-fetch). Each call blocks the LiveView while the single-connection Store GenServer runs the query and the Task process decodes rows. SPA-style push_patch navigation re-runs only handle_params (dedup-guarded: NO summary, just task_ids + recents + genesis.toml read when a project is active, unless the node context changed).

### Memory (~25MB/page)

Retained in the LiveView heap per tab (N tabs = N copies): `@running_tasks` + `@pending_tasks` — the statuses-filtered summary maps. **`result` is not decoded/read from summary maps** — `show_review_button?` is column-based (`branch_name`) and the summary projection excludes `result`, so the per-row `Codec.decode_result` (which rebuilt `%Usage{}` + archive_records — the largest blob in the DB) never runs for summary rows. `pending_tasks` = every completed-unreviewed-with-branch task (full summary map). Small retainers: `@recent_projects`, `@notified_task_ids` (ids only), `@model_profiles`, `@project_config`/`@commands`/`@foreign_repos`, `@config_status`. LiveView processes live until the tab closes (no `live_disconnect_timeout` in LV 1.2.8).

### Wasteful patterns to fix (candidate list)

1. **Summary query not project-scoped** — scans all projects' running/pending/finalizing/completed rows on every navigation.
2. Store queries serialize on the single-connection Store GenServer with runtime writes.
3. `:node_aware_reload_tasks` (300ms after EVERY task broadcast): `list_task_ids` + summary + genesis.toml re-read when project settings shown — the broadcast-driven hotspot (see evo_git/CONTEXT.md:80).

### Summary decode location

All summary variants delegate decoding to short-lived Tasks (task_registry.ex:416-427, 430-443, 446-457); only `list_task_ids` (460-465) replies inline by design. The **LiveView heap retention** is the remaining memory driver.

## Constraints

- All modules are pure functions — no I/O, no socket, no process calls (except `StatePersistence` which interacts with assigns/session).
- Follows the project-wide `try/rescue` anti-pattern policy.

## Windows Path Handling (Project Open/Create Flow)

Name-only project input must never be joined to the backend's cwd by `Path.expand/1`: on the Windows desktop app the backend's cwd is the Tauri process's inherited cwd — `desktop/src-tauri/src/sidecar.rs` spawns the launcher with NO `current_dir` → typically the install dir `C:\Users\<user>\AppData\Local\genesis-desktop` (NSIS per-user install) — so `Path.expand("Test")` would yield `C:/Users/<user>/AppData/Local/genesis-desktop/Test` (FORWARD slashes — Elixir's win32 `do_absname_join` converts `\`→`/`). Elixir's `Path.type/1` is OS-gated (win32 recognizes `X:\`/`X:/`/UNC as `:absolute`; a bare name or `X:` volume-relative input is joined to cwd — verified in Elixir 1.20.2 `lib/elixir/lib/path.ex`). There is NO literal `C:\` hardcoding anywhere in evo_dash/desktop/evo_git code — `C:` in errors is runtime `File.cwd!()`, not a hardcode.

**`ProjectFlow.normalize_project_path/1`** (public, `@spec normalize_project_path(String.t()) :: {:ok, String.t()} | {:error, :blank} | {:error, :relative}`): every server-side project-path entry point in `project_flow.ex` normalizes input through this helper instead of bare `Path.expand/1`. Semantics: `String.trim/1` first; blank → `{:error, :blank}`; genuine tilde expansion (`~`, `~/...`, and — ONLY on Windows — `~\\...`, decided by the private `expandable_tilde?/1` predicate) → `{:ok, Path.expand(trimmed)}` (tilde expansion is cwd-independent); `EvoGit.Platform.absolute_path?/1` true → `{:ok, Path.expand(trimmed)}` (idempotent for absolute paths); anything else — bare names, volume-relative `D:Test`, root-relative `\Test`, `~foo`, non-Windows `~\x` — → `{:error, :relative}`. **Never-cwd-join rule**: `Path.expand/1` must never see a value that would be cwd-joined. Elixir's tilde handling (verified against stdlib `resolve_home/1`): `~`/`~/...` expand on ALL platforms, `~\...` ONLY on win32 (literal + cwd-joined on Unix), `~foo` NEVER on any platform (literal + cwd-joined) — `expandable_tilde?/1` guarantees `~foo` and off-Windows `~\x` fall through to `{:error, :relative}`. **LOCAL-only** — never used for remote paths (its `Path.expand/1` runs against the dashboard's OS, which corrupts remote paths; see the remote normalizer below).

**`ProjectFlow.normalize_remote_project_path/2`** (public, `@spec normalize_remote_project_path(node(), String.t()) :: {:ok, String.t()} | {:error, :blank} | {:error, :relative}`): remote-aware normalization used ONLY by `activate_remote_project/2`. Performs **NO local `Path.expand` on absolute input** (a Windows dashboard would rewrite `/home/...` to a drive-letter path and classify it `:volumerelative`; a POSIX dashboard would cwd-join `C:\work`): blank → `{:error, :blank}`; POSIX absolute (leading `/`) → `{:ok, trimmed}` passed through verbatim; Windows-style absolute (drive letter / UNC, via `EvoGit.Platform.absolute_path?/1`) → `{:ok, trimmed}` passed through verbatim; genuinely tilde-expandable (`~`, `~/...`, `~\...` — same `expandable_tilde?/1` predicate) → expanded on the REMOTE node via the node-aware RPC (`NodeContext.call_remote(node, Path, :expand, [trimmed])`) so the remote user's home resolves, NOT the dashboard user's — the expander is injectable via the test seam `Application.get_env(:evo_dash, :remote_path_expand_runner)` (read at call time, default = a capture of the private `default_remote_path_expand/2`; RPC failure or a non-binary result falls back to `{:ok, trimmed}`); anything else → `{:error, :relative}`. The `EvoDashWeb.RemoteGateComponents.gate_active?/1` guard runs before normalization and is unchanged.

Applied at `create_project/2`, `open_project/2`, `select_project/2` (all local flows, `normalize_project_path/1`), and at `activate_remote_project/2` (`normalize_remote_project_path/2`, remote-aware): `{:error, :blank}` → "Invalid project name" gettext flash; `{:error, :relative}` → gettext flash `Enter a full path, e.g. D:\Projects\myproject or /home/user/myproject`; `{:ok, expanded}` → create: `validate_project_name(Path.basename(expanded))` → `File.dir?` → `register_and_open_project` / `File.mkdir_p` chain; open/select: dir check + recents + push_patch; activate_remote_project: gate guard first, then `EvoDash.NodeContext.dir?` remote validation + recents + push_patch. "Directory does not exist…" / "…on the remote node…" flashes fire for absolute-but-missing directories.

**Recents filtering — node-aware**: the shared public predicate **`ProjectFlow.absolute_path_for_node?(node, path)`** (`@spec absolute_path_for_node?(node(), term()) :: boolean()`) is the single source of truth for recents filtering: local node (`node == node()`) → `EvoGit.Platform.absolute_path?/1` (local semantics unchanged); remote node → true for POSIX-absolute (leading `/`) OR Windows-absolute (`EvoGit.Platform.absolute_path?/1`) paths — a remote node's recents must not be judged by the dashboard's host OS (a Windows dashboard would drop `/home/user/repo` as `:volumerelative`, a POSIX dashboard would drop `C:\work`); non-binary paths → false. Used via `ProjectFlow`'s private `filter_absolute_recent_projects_for_node/2` (in `activate_remote_project/2`) and `projects_live.ex`'s private `filter_absolute_recent_projects_for_node/2` at the THREE remote `:recent_projects` sites (`handle_params/3` remote branch, the `{:recent_projects_updated}` handler, `activate_remote_palette_project/2`) — plus `Project.path_suggestions/3`'s recents filter. The local sites (`register_and_open_project`, `open_project`, `select_project`, mount, local handle_params/handle_info branches, palette-key local selection, `remove_recent_project`) keep the private `filter_absolute_recent_projects/1` (`Enum.filter(recent_projects, &EvoGit.Platform.absolute_path?(&1.path))`) unchanged — non-absolute (cwd-joined) entries never render in the palette.

**Foreign-repo construction — node-aware raw storage (`ProjectFlow.build_foreign_repo/4`)**: `EvoGit.Core.ForeignRepo.new/3` (evo_git core) runs `Path.expand/1` on the root against the DASHBOARD's OS, which mangles remote paths (a Windows dashboard rewrites `/home/...` to a drive-letter path; a POSIX dashboard cwd-joins `D:\stuff\repo`). The public helper **`ProjectFlow.build_foreign_repo(node, id, path, opts \\ [])`** (`@spec build_foreign_repo(node() | nil, String.t(), String.t(), keyword()) :: EvoGit.Core.ForeignRepo.t()`) is the single construction seam: LOCAL node (`node == nil or node == node()`) → `ForeignRepo.new/3` (exact legacy behavior — its tilde/relative `Path.expand` semantics are kept); REMOTE node → `%EvoGit.Core.ForeignRepo{id: id, root: path, description: Keyword.get(opts, :description)}` with the RAW root (no local expansion). Remote-context call sites (each stores raw roots for remote nodes; every local variant keeps `ForeignRepo.new/3` byte-identical): (1) `projects_live.ex` `add_foreign_repo` handler — after the `foreign_repo_path_absolute?/2` validation gate, `remote_context? = socket.assigns[:remote?] or socket.assigns[:current_node] != node()` picks `current_node` (remote) or `node()` (local); (2) `Project.load_foreign_repos/3` remote branch — threads the node through the private `extract_foreign_repos/2` + `build_foreign_repo/3` (the local `load_foreign_repos/1` + `/2` variants and the local `extract_foreign_repos/1` delegate keep using `ForeignRepo.new/3`); (3) `StatePersistence.maybe_restore_foreign_repos/2` — same `remote?/current_node` context check rebuilds raw structs on restore, closing the persist/restore round-trip so a remote-added POSIX repo survives state persistence unmangled. `projects_live.ex` `maybe_restore_foreign_repos_from_task/2` is deliberately NOT node-aware — it restores from a LOCAL task's opts (local paths), current behavior is correct.

**`Project.filesystem_suggestions/1` absolute/tilde guard**: suggestions are produced ONLY when `ProjectFlow.normalize_project_path(value)` returns `{:ok, expanded}` (absolute or genuinely tilde-expandable input); relative input (`~foo`, non-Windows `~\x`, bare names) → `[]`. There is no `File.cwd!()`-anchored fallback for relative input.

**Directory picker — server-side wx protocol**: `handle_event("directory_pick", %{"picker_id" => id})` (pushed by the JS `DirectoryPicker` hook) branches on the node: local (`socket.assigns.current_node == node()`) → the picker module (`Application.get_env(:evo_dash, :directory_picker_module, EvoDash.DirectoryPicker)`, guarded by `Code.ensure_loaded?/1`) `pick/2`s `self()` — `:ok` returns immediately (async dialog), `{:error, :unavailable}` pushes `picker_result:<id>` with `%{unavailable: true}`; remote/headless node → `%{unavailable: true}` pushed immediately (a wx dialog must never pop on a remote node). The async result arrives as `handle_info({:directory_picker_result, picker_id, result})` and is pushed as `picker_result:<id>` with `%{path: path}` / `%{cancelled: true}` / `%{unavailable: true}`. LiveView tests live in `test/evo_dash_web/live/projects_live_test.exs` ("directory picker" block: remote→unavailable, disabled→unavailable, fake-module happy path via `EvoDash.DirectoryPicker.Fake` in `test/support/`), plus `normalize_project_path/1` relative-input rejection tests.

**Attach-file manual fallback — `file_pick_manual` event** (objective editor's "+" button; see the attach-file paragraph in `apps/evo_dash/lib/evo_dash_web/CONTEXT.md` for the full flow): the FilePicker JS hook (app.js) reveals the hidden `.file-manual` path input (rendered in `task_form_components.ex`, `phx-update="ignore"`) when the native picker pushes `%{unavailable: true}` (remote node, picker disabled, headless). Enter/confirm → `handle_event("file_pick_manual", params, socket)` in `projects_live.ex` (catch-all params shape — never crashes): `picker_id` defaults to `@attach_picker_id "objective_file"`, `prompt` coerced to a binary, validation via `cond` (no try/rescue): non-binary/empty path → gettext `"Please enter a file path."`, `not File.regular?(path)` → gettext `"File not found: %{path}"` — both push `%{error: true, reason: ...}` + error flash via the private `push_manual_attach_error/3`; valid path → snapshot `prompt` into `file_pick_bases` (identical base semantics to the native `file_pick` flow) then `AttachFile.handle_attach_result/2` (the shared pipeline — success push `%{prompt, block, attached: true, name}` / read-error flash + `%{error: true}`). Manual reads always hit the LOCAL node's filesystem (also on remote-node views — remote file reads are unsupported because `genesis_remote` ships no ex_pdf). Tests: "file attach" block in `projects_live_test.exs` (valid-path append pins the exact block + `task_prompt`/`file_pick_bases` assigns; empty/nil/missing-params/nonexistent → error push without crash).
