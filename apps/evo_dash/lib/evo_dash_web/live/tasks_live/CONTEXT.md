# TasksLive — Tasks Page
## Intent
Support documentation for `EvoDashWeb.TasksLive` (`tasks_live.ex`), the cross-project task list page (`GET /tasks`): filtering by status, project, review state and session mode, search, server-side pagination, expandable task cards, and task actions (graceful cancel, force kill, pause, resume, close session, delete, clear history).
The page is the cross-project LIFECYCLE + REVIEW-TRIAGING surface: every task state is filterable, the review queue is one filter away (`needs_review`), finished work exits to `/review/<id>` from the card, and live work is inspected in place.
Node-aware — reads task history via `EvoDash.NodeContext` for both the local BEAM node and a remote daemon (the `genesis_server` release in remote-dev mode).
ONE page load transfers one page of the 18-key task SUMMARY projection (`pause_kind` included); the heavy per-card payloads (`result`, `usage`, `logs`) are fetched lazily per card on expand, and the agent archive arrives in bounded pages only after an explicit disclosure.
## Routing Table
- `tasks_live.ex` — the LiveView: filters, pagination, keyed task stream, modals, mutating events.
- `page_load.ex` — `EvoDashWeb.TasksLive.PageLoad`: the ONE async, exit-safe page-load path (spawn seams, loader task, pure helpers) over the summary projection, and the owner of the filter vocabulary — `filters/1` (the SQL keyword), `needs_review_filter?/1`, `review_status_filter/1` (status-filter precedence) and the single client-side post-load choke point `visible_tasks/2,3`.
- `task_detail.ex` — `EvoDashWeb.TasksLive.TaskDetail`: the lazy per-card DETAIL + PAGED ARCHIVE cache (async fetches, cache/in-flight guards, invalidation, seq/node stale guards, one-page prune).
- `session.ex` — `EvoDashWeb.TasksLive.Session`: stateless idle-session close confirmation markup (`confirm_close_session_modal/1`, `busy` attr driving the confirm button's disabled/spinner state).
- `EvoDashWeb.ModalHelpers` (`live/modal_helpers.ex`) — the `__using__` macro injecting `view_full_result/2`, `close_result_modal/1`, `view_full_options/2`, `close_options_modal/1`; only TasksLive uses it.
## Push-based change detection (no polling)
TasksLive is FULLY push-based — no poll, no dirty tracker, no `list_tasks_changed_since/2`.
`:evo_git` emits node-tagged `"tasks"` events: `{:task_updated, task_id, status, node}` (`status` ∈ `:pending|:running|:awaiting_input|:finalizing|:cancelling|:pausing|:paused|:completed|:failed|:cancelled`, `nil` for review-only mutations) and `{:task_deleted, task_id, node}`.
TasksLive forwards both VERBATIM to `EvoDashWeb.LiveHooks.NodeAware.handle_task_info/2` (returns `{:noreply, socket}` — return it directly, never re-wrap), which node-filters via `event_from_current_node?/2` (event node vs `socket.assigns[:current_node]`) BEFORE the trailing-edge 300 ms debounce (`:node_aware_reload_tasks` + `:tasks_reload_pending`); a foreign-node event is dropped before the debounce and never reaches the UI, and a node-matching one first drops that task's cached detail (`TaskDetail.invalidate/2`) so a stale `result`/`usage` is never re-rendered.
`handle_info(:node_aware_reload_tasks, …)` never touches the store: page refresh `PageLoad.start(socket, socket.assigns.current_page, false)` (async, `show_loading? false` keeps stale rows), sidebar `NodeAware.reload_tasks/1`, then `NodeAware.clear_task_reload_pending/1` clears the flag the moment the reload is DISPATCHED so a later burst re-schedules; unknown messages hit the catch-all `handle_info(_msg, socket)`.
The same path serves local and remote nodes; the debounce gates bursts while `:page_load_seq` gates overlapping loads — a burst during an in-flight load spawns a new load whose result wins and the superseded result is dropped. The `mount/3` + `on_mount/4` double subscription can refetch an expanded card twice, which the cache/in-flight guards and the debounce keep bounded.
## Async page load (the only page-load path)
Every page load goes through `EvoDashWeb.TasksLive.PageLoad` (`tasks_live/page_load.ex`); the LiveView never fetches a page inline.
- `PageLoad.start/3` bumps the monotonic `:page_load_seq` (its only writer), optionally sets `:tasks_loading`, and hands the spawn fun to the `:tasks_page_load_hook` seam.
- `PageLoad.load/4` — the ONLY store-facing function (no other module knows the row shape) — issues ONE `EvoDash.NodeContext.list_tasks_page/2` read (`limit: page_size`, `offset: (requested_page - 1) * page_size`, the current `filters`) plus `get_unique_paths/1` and the node's idle sessions (`list_awaiting_input/1`), returning `%{tasks:, current_page:, total_count:, total_pages:, project_paths:, awaiting_sessions: %{task_id => agent_id}}`.
- Rows are the 18-key summary projection — `id`, `status`, `review_status`, `started_at`, `finished_at`, `type`, `project_path`, `opts`, `branch_name`, `model_id`, `agent_count`, `base_sha`, `commit_sha`, `lease_expires_at`, `updated_at`, `error`, `session_mode`, `pause_kind` — never `result`/`usage`/`logs`/`archive_metadata`.
- There is NO second fetch: the store CLAMPS an out-of-range offset onto the LAST page of the filtered set, so the returned page already IS the clamped page and only `current_page = min(max(1, requested_page), total_pages(total_count, page_size))` is derived arithmetically.
- `PageLoad.run/6` runs `load/4` in a supervised `EvoDash.TaskSupervisor` task behind `EvoDash.SafeCall.run/1` and ALWAYS sends exactly one `{:tasks_page_loaded, seq, node, result}` — even on an exit, a raise or a remote RPC failure; `result` is `{:ok, %{tasks:, current_page:, total_count:, total_pages:, project_paths:, awaiting_sessions:}} | {:error, reason}` with `reason` a VALUE (`{:exit, reason}` / `{:exception, exception}` / a returned remote error), never a crash.
- **Stale guards** in `handle_info({:tasks_page_loaded, seq, node, result}, _)`: a `seq` older than `:page_load_seq`, or a `node` that no longer matches `socket.assigns.current_node`, drops the result.
- `show_loading?` is decided by the page's private `reload/3`: `socket.assigns.filtered_tasks == []` (a first load) shows the placeholder; every later filter/search/pagination/sort/session-mode/toggle/retry load sets `:tasks_refreshing` and leaves the mounted rows alone, so a keystroke never blanks and re-staggers the list.
- **Kickoff is connected-gated** (`handle_params/3`), which also runs on the disconnected static render whose async result is discarded: the load spawns ONLY when `connected?(socket)`, and the else branch assigns `:tasks_loading, true` so static HTML paints the same placeholder. Every pagination `push_patch` and filter event still loads — the guard is `connected?/1`, not first-only.
- **Three independent load counters** — `:page_load_seq` (page load, `PageLoad.start/3` only writer), `:tasks_load_seq` (`NodeAware`'s sidebar fetch, `request_tasks_load/1` only writer, `handle_tasks_result/2` requiring an exact match) and `:task_detail_seq` (`TaskDetail`); the debounced reload spawns both page and sidebar loads, so a shared counter would invalidate the other's in-flight result. Never merge them; never bump `:tasks_load_seq` from this file.
- **`:tasks_page_load_hook`** (1-arity, default identity) resolves at spawn time so tests can count spawns (`:page_load_spawned`); **`:tasks_page_load_runner`** (4-arity, default `&load/4`) resolves INSIDE `run/6`, so a test can inject an exiting loader and prove the LiveView survives with `:tasks_loading` cleared.
## `?task=<id>` — focused single-task view
`params["task"]` (a binary of 1..128 bytes, else nil) sets `@focused_task_id` in `handle_params/3`, which auto-expands that id and passes `workbench_task` to the layout (`workbench_reconnect_params: Map.take(params, ["task"])`, `workbench_remote_requested: params["node"] not in [nil, "local"]`).
In that mode `PageLoad.start/3` replaces the filter keyword with `[focused_task: id, pending_remote: workbench_remote_requested and node == node()]`, and `load/4` runs a single `get_task_lite/2` read (ONE row, page 1/1, no project paths, `awaiting_sessions` limited to that id) instead of `list_tasks_page/2`.
The page renders that one card (`focused` attr), hides the pagination and the list header, skips the `:reflect` hiding for it (`show_reflect_tasks or not is_nil(focused_task_id)` in the landed-load fold) and shows "Task not found" + a "Task History" link when the read yields nothing; `list_enter_scope/1` includes `focused_task_id`.
## Page-load state & failure handling (`:tasks_loading` / `:tasks_error`)
- `:tasks_loading` (seeded `false`; set by `PageLoad.start/3` when `show_loading?`, cleared by every APPLIED `{:tasks_page_loaded, ...}`) drives ONLY the first-load placeholder — daisyUI `skeleton` rows inside `#tasks-loading` (`role="status"`, `aria-live="polite"`, visually hidden `gettext("Loading tasks...")`, the text tests flush on).
- `:tasks_refreshing` (seeded `false`) is set for a non-first load and cleared at the TOP of every `{:tasks_page_loaded, ...}` outcome (ok, error and stale alike) so it can never stick; while true the list renders ONE thin inline line above the rows (`#tasks-refreshing`, `role="status"`, spinner + `gettext("Refreshing tasks…")`) with the loaded rows still mounted.
- **Keyed stream contract**: `#tasks-list` is the outer `ListEnter` scope wrapper (`phx-hook="ListEnter"` + `data-list-enter-scope={list_enter_scope(assigns)}`, a stable identity of node + filters + page + focus); `#tasks-stream` inside it is the ONLY `phx-update="stream"` container. Each row's DOM id is exactly `task-<id>` (explicit `dom_id: &task_dom_id/1`; the stream name `:tasks` would default to `tasks-<id>`) plus `data-list-enter-key={task.id}`, so `ListEnter` animates only genuinely new rows and reseeds a silent baseline on a scope change.
- The stream is populated in ONE place — `put_tasks_stream/2` (`stream(:tasks, rows, reset: true, dom_id: …)`) in the success branch — so a first load, filter change, page change, node switch and every refresh RESET the container while a push or a mutation never does.
- The plain `:tasks`/`:filtered_tasks` assigns stay RETAINED and populated beside `@streams.tasks`: the count line reads `length(@filtered_tasks)`, the empty/error branches test it, and `ModalHelpers.view_full_options/2` plus several tests look rows up in `socket.assigns.tasks`.
- `:tasks_error` (seeded `nil`) holds the LAST failed load's reason; it is NOT interpolated into the DOM, only selects the error UI, and a failed load NEVER clears loaded rows (`:tasks`/`:filtered_tasks`/`:total_count`/`:total_pages`/`:project_paths` untouched).
- With `@filtered_tasks == []` a failed load renders the centered "Could not load tasks." block (`#tasks-load-error`) + Retry — never an endless spinner (the spinner shows only while `:tasks_loading`); with rows on screen it renders normally plus a compact `#tasks-refresh-error` strip above `#tasks-list` ("Could not refresh tasks." + Retry).
- `retry_load` re-runs `PageLoad.start/3` on the CURRENT page, showing the placeholder only when `filtered_tasks == []`; a successful load assigns `tasks_error: nil`, so strip/block disappear.
## Lazy per-card detail & archive
The rendered list holds summary rows only; heavy data is fetched per card by `EvoDashWeb.TasksLive.TaskDetail` (`tasks_live/task_detail.ex`) — the SINGLE owner of the `:task_details` cache and its `:task_detail_seq` stale-guard. Nothing is fetched at mount or on page load; an entry exists only once the user expands a card.
### Entry shape
`:task_details` maps `task_id => entry`: `%{state: :loading | :ok | :error, task: %EvoGit.TaskInfo{} | nil, error: term() | nil, seq: pos_integer(), archive: nil | %{state: :loading | :ok | :error, entries: [map()], total: non_neg_integer(), server_total: non_neg_integer() | nil, dropped: non_neg_integer(), exhausted?: boolean(), next_offset: non_neg_integer(), loading_more?: boolean(), more_error: term() | nil, error: term() | nil, seq: pos_integer(), agent_results: %{agent_id => %{state: :loading | :ok | :error, entry: map() | nil, error: term() | nil}}}}`.
`task` is meaningful only when `state == :ok`, `error` only when `state == :error`.
The archive envelope is PAGED: `entries` holds the pages read so far (bounded by the retention window), `total` the EFFECTIVE total that drives paging, `server_total` the server's own count for the label only (`nil` when a page carried none), `dropped` the entries the retention window evicted, `exhausted?` a short/empty page that proved there is nothing more, `next_offset` the cumulative count of RAW rows fetched (the offset the next/in-flight page is requested at), and `agent_results` the lazily fetched per-agent full entries (the paged read omits every `"result"`); `total`/`server_total` are OPTIONAL inputs, so a page read may stop returning a per-page `COUNT(*)` and the fold stays total.
The detail entry and its nested archive entry carry their OWN seq drawn from the same monotonic `:task_detail_seq`, so a detail refetch never invalidates a landed archive (and vice versa); an append keeps the archive's seq and is identified by `next_offset`.
`entries` is bounded by `EvoDashWeb.ArchiveHelpers.retain_window/2,3` at `ArchiveHelpers.max_retained/0` (500 = 5 pages), keeping the most RECENT and accumulating evicted (oldest) rows in `dropped`; a SHORT page (`length(page_entries) < 100`, empty included) sets `exhausted?: true` and clamps `total` to `dropped + length(entries)` so a stale server count can never keep the pager alive, while a full page sets `total = max(fetched, server_total || 0)`.
The private `more_pages?/1` is the single pager predicate: `not exhausted? and ArchiveHelpers.more_pages?(length(entries), dropped, total) and not loading_more?` — never `length(entries) < total`, which is wrong once rows are evicted; and `prune/2` keeps only entries whose id is on the freshly loaded page, so the cache never exceeds ONE page.
### Reads and seams
| read | returns | app-env seam | default |
|------|---------|--------------|---------|
| lite detail | `%EvoGit.TaskInfo{}` with `archive_metadata: nil` and no `:archive_records` in the result | `:tasks_task_detail_runner` (2-arity) | `EvoDash.NodeContext.get_task_lite/2` |
| archive PAGE | `%{entries: [map()]}` plus an OPTIONAL `total` (a non-negative integer becomes `server_total`) for `limit: 100, offset: <page>, include_results: false` | `:tasks_task_archive_runner` (3-arity `fn node, task_id, opts -> end`) | `EvoDash.NodeContext.list_task_archives/3` |
| one agent's full entry | the entry map INCLUDING its `"result"` (`nil` when absent) | `:tasks_task_archive_agent_runner` (3-arity `fn node, task_id, agent_id -> end`) | `EvoDash.NodeContext.get_agent_archive/3` |
All three seams are resolved AT SPAWN TIME from app env (the dashboard's runner-seam idiom), so a test can inject an exiting runner and assert the LiveView survives.
Every fetch is ONE supervised `EvoDash.TaskSupervisor` child running `EvoDash.SafeCall.run/1` around the runner call and always reporting back: `{:task_detail_loaded, seq, node, task_id, result}` / `{:task_archive_loaded, seq, node, task_id, result}` / `{:task_archive_agent_loaded, seq, node, task_id, agent_id, result}`. No polling — results arrive only from those three messages.
### Guards and result folding
`apply_detail/5`, `apply_archive/5` and `apply_archive_agent/6` drop a result unless the message's `node` still equals `socket.assigns.current_node`, the entry still exists, AND the entry's (archive) seq equals the message's seq (a newer fetch, a pruned entry or an invalidated entry supersedes the older result); `apply_archive_agent/6` additionally requires the agent to still be tracked in `agent_results`.
- Detail: `{:ok, %EvoGit.TaskInfo{}}` → `:ok`; `{:ok, nil}` (the task vanished between page load and expand) → `:error` with `:not_found`; `{:error, reason}` (including a SafeCall-captured exit) → `:error` with that reason; any other shape → `:error`.
- Archive FIRST page: `{:ok, %{entries: list}}` (with or without a `total`) → `:ok` — the empty list is a valid "this task archived nothing"; `{:error, reason}` and any other shape → `:error` (Retry → `load_archive/2`).
- APPEND (`loading_more?: true`): success merges the page in (deduped by `agent_id`, order preserved), advances `next_offset` by the RAW rows fetched, refreshes `dropped`/`exhausted?`/`server_total` and the effective `total`; failure keeps the loaded page, clears `loading_more?` and records `more_error` (Retry → `load_more_archive/2`).
- Per-agent: `{:ok, entry_map}` caches `%{state: :ok, entry: entry}` AND folds the entry into `entries` via `ArchiveHelpers.merge_entry/2`; `{:ok, nil}` / `{:error, reason}` / anything else → `%{state: :error, error: reason}`.
### Public API (total — a missing assign reads as an empty cache)
- `toggle/2` — collapse drops the id from `:expanded_task_ids` and keeps the cached entry (a re-expand renders instantly); open adds the id and `ensure/2`s.
- `ensure/2` — fetch when no entry exists; an entry in ANY state (including `:error`) is a no-op, so this is both the cache guard and the in-flight guard.
- `retry/2` — drop the entry, then `ensure/2` (backs the error strip's Retry).
- `load_archive/2` — no-op unless the detail entry is `:ok`; fetches the FIRST page when `archive` is `nil` or an `:error` archive, never while `:loading`/`:ok`.
- `load_more_archive/2` — no-op unless the archive is `:ok` and `more_pages?/1` is true.
- `load_agent_result/3` — no-op unless the archive is `:ok`; per-agent cache/in-flight guard (`:loading`/`:ok` left alone, `:error` refetched). Never called on render.
- `invalidate/2` — drop the entry (archive AND every cached agent result go with it); when the card is still in `:expanded_task_ids` it immediately `ensure/2`s again, so an open card shows the loading state and then the fresh detail instead of blanking. This is the ONLY archive invalidation path.
- `prune/2` — keep only the entries for ids present in the landed page rows.
- `ensure_expanded/2` — after `prune/2`, refetch the detail of every still-expanded row on the new page (an open card survives a background refresh / pagination round-trip).
- `apply_detail/5` / `apply_archive/5` / `apply_archive_agent/6` — the guarded message folds.
### TasksLive wiring
- `toggle_task_details` (`%{"task_id" => id}`) → `TaskDetail.toggle/2` (ensure ONLY when OPENING).
- `retry_task_detail` (`%{"task_id" => id}`) → `TaskDetail.retry/2`; `load_task_archive` (`%{"task_id" => id}`) → `TaskDetail.load_archive/2`; `load_more_task_archive` (`%{"task_id" => id}`) → `TaskDetail.load_more_archive/2`; `load_task_archive_agent_result` (`%{"task_id" => id, "agent_id" => agent_id}`) → `TaskDetail.load_agent_result/3`.
- `{:task_updated, ...}` / `{:task_deleted, ...}` invalidate that id (only when `NodeAware.event_from_current_node?/2`) BEFORE delegating to `NodeAware.handle_task_info/2`.
- A node-context change in `handle_params/3` resets `:task_details` to `%{}` and clears the four confirm ids, `:action_busy`, `:awaiting_sessions`, `:clearing_history` and `:tasks_refreshing` — all belong to the OLD node, and in-flight results are then rejected by the node + entry guards.
- A landed page load runs `TaskDetail.prune/2` then `TaskDetail.ensure_expanded/2`.
### Card rendering states
The card receives `detail={Map.get(@task_details, task.id)}`; while `nil` or `:loading` the expanded body renders the compact `#task-<id>-detail-loading` placeholder ("Loading task details…"), and on `:error` the retry-able `#task-<id>-detail-error` strip ("Could not load task details." + Retry → `retry_task_detail`).
The heavy sections — Agent Message, Token & Cost Usage, Execution Logs and the archive — read `detail.task`; the Agents Spawned tile reads the summary's `agent_count`/`model_id` but is reached only once the detail has landed. The expanded structured-failure block is the exception: it reads the summary's `error` and renders even while the detail is loading.
### Archive disclosure
The archive section appears only when the detail is `:ok` AND (`opts[:archive]` is truthy OR an archive envelope already exists). Records are NEVER fetched with the detail: the section first shows a "Show archive" button (`load_task_archive`) and the hint "The archive loads on demand."
States: not requested (button + hint) → `:loading` spinner → `:ok` with a page rendered through `ArchiveComponents.archive_details` (count/range label, the tree, "Load more" only while `not exhausted? and ArchiveHelpers.more_pages?(loaded, dropped, effective_total)`, per-agent "Show result") → `:ok` with `[]` → "No archived agents for this task." → `:error` strip ("Could not load the task archive.") whose Retry re-fires `load_task_archive`.
An append failure is INLINE and non-destructive: the loaded page stays, `more_error` renders "Could not load more archive pages." + Retry (same `load_more_task_archive` event). Each agent's heavy `"result"` is fetched only when the user presses "Show result" (`load_task_archive_agent_result`), rendered capped through `blob_preview`, never auto-fetched on render.
## Load profile, async boundaries & no N+1
`mount/3` runs NO store query: `project_paths` is seeded `[]` and filled by the async load's `get_unique_paths/1` (a mount-time call would be redundant and wrong — at mount the node context is still local, before `handle_params/3` resolves `?node=`); it does call `Helpers.config_status/0` → `EvoGit.Config.config_status/0` synchronously (local, persistent_term-cached).
Everything else is ASYNC in `EvoDash.TaskSupervisor` and off the socket: page loads via `PageLoad` (the connected mount, `push_patch` pagination, every filter/search/toggle event, `retry_load`, the post-mutation reload and the debounced PubSub reload, landing as `{:tasks_page_loaded, seq, node, result}` guarded by `:page_load_seq` + node identity), `TaskDetail` fetches (`{:task_detail_loaded, …}` / `{:task_archive_loaded, …}` / `{:task_archive_agent_loaded, …}`, guarded by `:task_detail_seq` + the entry + node identity), and every mutation via `EvoDash.SafeCall.start/3` (NESTED `{{tag, …}, result}` — see "Mutating events"); `mount/3`'s `config_status/0` is the ONLY synchronous call in the LiveView process.
- **Stream row re-render rule**: a stream row is NOT re-rendered when a plain assign it reads changes, so every arm that mutates `@expanded_task_ids` / `@task_details` re-inserts the affected row through `refresh_stream_row/2` (`stream_insert/3`, keeping the captured `dom_id`): `toggle_task_details`, `retry_task_detail`, `load_task_archive`, `load_more_task_archive`, `load_task_archive_agent_result` and the three detail/archive result messages. A row that disappears WITHOUT a reload is removed surgically: the `{:delete_result, id}` success path calls `stream_delete/3` (guarded on the stream existing); every path ending in a page load needs no extra work because the reset covers it.
- **No per-task N+1 I/O**: `TaskCardComponents.task_card/1` performs NO git subprocess, `File.stat`/`exists?`, `System.cmd` or `NodeContext` call at render time — it renders the summary row plus whatever `detail` holds, so extra round trips are bounded by what the user opened, never by rows per page.
- Per-load SQL cost, the pool-backed reads (`EvoGit.Store.Boot.default_pool_size/0` = 4) with writes serialized through `EvoGit.Store.Writer`, and the `get_unique_paths/1` scan: `apps/evo_git/lib/evo_git/store/CONTEXT.md`.
- **Measured payload** (pin: `tasks_live_test.exs` "a multi-MB result never rides the page load"): a fixture whose `result` is `String.duplicate("multi-mb-payload ", 140_000)` = 2,380,000 B costs 984 B as its ONE-row page load vs 2,381,183 B (≈ 2.27 MiB) through `EvoDash.NodeContext.list_tasks_paginated(node, limit: 50)` — ≈ 2420× smaller, because the summary projection never selects `result`; `term_bytes/1` measures `:erts_debug.size/1 * 8` PLUS every referenced binary's payload (size alone reports 114 words vs 141, a 2 MB refc binary costing ~8 heap words) and the assertions are `page_bytes * 50 <= full_bytes` and `page_bytes < byte_size(big) / 50`.
- **Measured latency** (isolated `mix run` harness over a COPY of a live `tasks.sqlite`, 854 rows / 29.7 MB, real async `TaskSupervisor` path), medians: connected mount + first render ≈ 8 ms (first paint ≈ 24 ms), pure `render(view)` of 24 cards ≈ 2 ms, one collapsed `TaskCardComponents.task_card` ≈ 0.03–0.07 ms (per-card render is NOT a bottleneck), sidebar `list_tasks_summary` (752 rows incl. `:completed`) ≈ 20–24 ms async off the Store GenServer (one pooled connection, shared with a concurrent page read); a filtered page load is DB-bound, so a broad `status = "completed"` filter is materially slower than a selective one.
## `:reflect` tasks hidden by default (reveal toggle)
The page hides `:reflect` tasks (repo-less Home-chat tasks) by default. Page-local filter state `@show_reflect_tasks` (default `false`, seeded in `mount/3` with the other filters) drives it; the filter-bar checkbox (`name="show_reflect_tasks"`, `value="true"`, `phx-change="toggle_reflect_tasks"`, gettext label "Show chat tasks") reveals them, parsing `params["show_reflect_tasks"] not in [nil, "false"]` and reloading via `PageLoad.start(socket, 1, true)`.
The exclusion is applied **client-side post-load** by `PageLoad.visible_tasks/2,3` (`Enum.reject/2` when hiding, then the `needs_review` exactness guard) at the single choke point where loaded rows become the displayed list — the `{:tasks_page_loaded, ...}` handler, which assigns the post-load filtered list to BOTH `:tasks` and `:filtered_tasks`.
`visible_tasks/3` rejects `type == :reflect` rows whose `session_mode` is not `"interactive"` (so a live interactive session is never hidden by this toggle) and, while the status filter is `needs_review`, every row that already carries a `review_status`. A SQL `filters` keyword (`PageLoad.filters/1`) cannot express "exclude type" because the WHERE builder lives in the read-only sibling app `evo_git`.
Rows are 18-key summary maps, so `type` is already a decoded atom and is read with `Map.get/2` — summary-safe, never a dot access. `@total_count`/`@total_pages`/pagination stay SQL-truthful and untouched — a page may show slightly fewer cards when reflect rows are dropped (accepted by design).
The toggle is a **reveal preference, not a narrowing filter**: it survives pagination `push_patch`es and filter reloads (a plain socket assign, never cleared by `handle_params/3`), is NOT reset by `reset_filters`, and does NOT appear in the active-filters indicator. When reflect-hiding empties the list with no other filter active, the empty state shows "Try adjusting your filters or search query." instead of the start-tasks hint (`not @show_reflect_tasks` in the first branch's condition).
## Reads: payload audit, store shapes & round trips
Every read goes `EvoDash.NodeContext.<f>` (local direct / remote `:erpc`) → `EvoGit.RemoteNode` → `EvoGit.AgentScheduler.RemoteAPI` → `EvoGit.TaskRegistry` → `EvoGit.Store`; reads share a small pool (`EvoGit.Store.Boot.default_pool_size/0` = 4) while every write serializes through `EvoGit.Store.Writer`, and the registry offloads `list_tasks_page`, `get_task_lite`, `list_task_archives` and `get_agent_archive` (only `get_unique_paths/1` blocks the core TaskRegistry; the store side is still offloaded).
- **`list_tasks_page/2`** — the page data; opts `[limit: 25, offset: (page-1)*25, filters: [status:, project_path:, review_status:, search:, session_mode:]]`, every key a SQL predicate in the store's shared WHERE builder (`EvoGit.Store.Operations.Filters.where_filters/2`; `"all"`/`""`/absent/unknown means "no clause"). Returns `%{rows: [summary_map], total: total_count}`; the card reads `id`, `type`, `opts`, `status`, `review_status`, `started_at`, `finished_at`, `agent_count`, `model_id`, `commit_sha`, `branch_name`, `error`, while `project_path`, `base_sha`, `lease_expires_at`, `updated_at`, `session_mode` and `pause_kind` ride along (`session_mode` read by the server-side filter, `pause_kind` by a card's paused explainer / resume confirmation).
- **Search** is a case-insensitive raw SQL LIKE (leading wildcard, full-table scan) over `id`, `opts`, `project_path` and `branch_name`; the agent RESPONSE (`result`) is NOT searchable and is not loaded until a card is expanded.
- **`get_task_lite/2`** — ONE read per EXPANDED card (through `TaskDetail`): a full `%EvoGit.TaskInfo{}` decoded exactly like `get_task/2` except `archive_metadata` is `nil` and there are no `:archive_records`; consumed are `result` (Agent Message, Full Result modal, expanded "Repositories"), `usage`, `logs`, `opts` and `commit_sha`/`branch_name` for multi-repo enrichment.
- **`list_task_archives/3`** — ONE read per archive page (`[limit: 100, offset: page, include_results: false]`) answering `%{entries: [string-keyed map], total: non_neg_integer()}`, entered WITHOUT its `"result"` (degraded to `%{entries: [], total: 0}` on a failed remote call); **`get_agent_archive/3`** is ONE read per agent the user asked about: its single full entry INCLUDING `"result"` (nil when unknown to that task).
- **`get_unique_paths/1`** — fetched ONCE per page load inside the async load task (`PageLoad.load/4`), never from `mount/3`; assigned as `@project_paths` → filter-dropdown options + active-filter badge.
- **`cancel_task/2` / `force_kill_task/2` / `delete_task/2` / `clear_finished_tasks/1`** — phx-event triggered and spawned OFF-PROCESS through `EvoDash.SafeCall.start/3` (see "Mutating events"), never called inline; each returns `:ok | {:error, reason}`, normalized by `mutation_result/1`.
- **Multi-repo `repos` result key** — results may carry a top-level `repos` map (STRING keys) `%{repo_id => %{"commit_sha" => sha, "branch_name" => branch | nil}}`: `"primary"` is ALWAYS present (nil branch_name = no changes), each writable foreign repo that produced commits is present, read-only repos are ABSENT, and top-level `commit_sha`/`branch_name` stay the PRIMARY's. The COLLAPSED card derives per-repo badges from the SUMMARY through the pure `TaskCardComponents.task_repos(task, detail)` (foreign repos from `opts[:foreign_repos]`, enriched by the detail result's `repos` once landed; `nil` unless genuinely multi-repo); `result_repos/1` + `result_repos_badges/1` back the expanded `render_result/2` "Repositories" section and the Full Result modal.
- **Not issued here**: `list_task_ids/2` (consumers are `ProjectsLive.Notifications` for terminal statuses and `ServerStatusController` / `SystemLive.UpdateCard` for active ones), `list_tasks_changed_since/2` (nobody — change detection is broadcast-driven), `list_tasks_paginated/2` and `get_task/2` (full-row reads incl. `Codec.decode_result/1`).
- **Round-trip inventory**: minimum per navigation = 2 core RPCs (page summary + distinct paths) and 1 SQL page statement carrying its own `count(*) OVER ()` total (`ORDER BY started_at DESC LIMIT/OFFSET`, index-served by `idx_tasks_started_at` or a matching composite) plus the `DISTINCT project_path` scan, all OUTSIDE the LiveView process (a separate `COUNT(*)` runs only for the rare out-of-range-offset last-page refetch); a mutation adds ONE single-row call off-process plus the same page-read cost in its async reload, expanding a card ONE lite read, disclosing an archive ONE page read (plus one per "Load more"), each "Show result" ONE agent read.
## Task cancellation UX (graceful cancel + force kill)
Two two-step server-side confirmation-modal flows (SystemLive warning-modal pattern; NO custom JS — assigns drive visibility):
- **Graceful cancel** (card's inline Cancel button, visible `[:pending, :running, :awaiting_input]`): `open_cancel_modal` → assign `:confirm_cancel_task_id`; `confirm_cancel_task` → `EvoDash.NodeContext.cancel_task(current_node, task_id)` (GRACEFUL — agents save + exit, result preserved; `:pending` → immediate `:cancelled`) spawned OFF-PROCESS through `EvoDash.SafeCall.start/3` tagged `{:cancel_result, task_id}`; `:ok` → collapse the expanded card + `PageLoad.start(socket, current_page, false)`; error → flash `gettext("Failed to cancel task: %{reason}", reason: inspect(reason))`. Modal: title `gettext("Cancel Task?")`, confirm `gettext("Cancel Task")` (`btn-warning`), dismiss `gettext("Keep Running")`.
- **Force kill** (card's three-dot dropdown, visible `[:running, :awaiting_input, :cancelling, :pausing, :paused]` — a draining or stuck pause must always be killable; "Danger zone" divider): `open_force_kill_modal` → assign `:confirm_force_kill_task_id`; `confirm_force_kill_task` → `EvoDash.NodeContext.force_kill_task(current_node, task_id)` (BRUTAL — kills all agents, result nil'd; escalation from `:cancelling`) through `SafeCall.start/3` tagged `{:force_kill_result, task_id}`; same `:ok` collapse + async reload / error-flash handling. Modal: title `gettext("Force Kill Task?")`, confirm `gettext("Force Kill")` (`btn-error`).
- **Status filter & reviewability**: the filter covers every lifecycle state — the exact stored-TEXT statuses (`finalizing`, `cancelling`, `pausing`, `paused`, `awaiting_input`, …) pass through as a pure SQL equality with no evo_dash-side atom whitelist, while `needs_review` is a derived predicate (see "Status filter inventory"). The Review button shows for every FINISHED task — the `:completed`/`:cancelled`/`:failed` allowlist of `show_review_button?/1`, repo-less `:reflect` excluded; one without a branch still opens the review page showing no changes — while a `:pausing`/`:paused` task is NOT reviewable: the page offers Resume instead and force kill is the only terminal exit from a pause.
- **Modal-state lifecycle**: `@confirm_cancel_task_id`, `@confirm_force_kill_task_id`, `@confirm_close_session_task_id` and `@confirm_pause_task_id` are seeded `nil` in `mount/3`, MUTUALLY EXCLUSIVE (every opening handler nils the siblings, so exactly one modal is open), cleared on a node switch in `handle_params/3` (with `action_busy`); nil-guarded confirms are no-ops.
- **`session_mode` filtering is SERVER-SIDE**: a real `tasks` column with a shared-WHERE predicate (`EvoGit.Store.Operations.Filters.where_filters/2`) travelling in `PageLoad.filters/1` exactly like `status`/`project_path`/`review_status`/`search`, so a page load stays ONE `list_tasks_page/2` read whose `count(*) OVER ()` reports the FILTERED total — no in-Elixir scan, no in-memory pagination. `normalize_session_mode/1`: `"oneshot"` matches a stored `NULL` and a legacy blank cell (both decode to `"oneshot"`), `"interactive"` only `'interactive'`, `"all"`/absent/unknown adds no clause. Events: `filter_session_mode` (whitelist match on the three values — unknown keeps the current filter, never an atom conversion) and `clear_filter` with `%{"filter" => "session_mode"}`; `reset_filters` resets it; the filter bar renders `<select name="session_mode_filter">` plus an active-filter chip (`session_mode_label/1`).
- **Idle sessions on this page**: the page load also returns `awaiting_sessions` — a `%{task_id => agent_id}` map from `EvoDash.NodeContext.list_awaiting_input/1` (empty on a degraded read) — and `session_agent_id/2` resolves a card's id tolerantly (string, integer or integer-parsed key), so `task_card/1` renders the reply panel only for a `:awaiting_input` task whose session is known. Events: `session_send_message` (`%{"task_id", "message"}` → `EvoDash.NodeContext.send_session_message(node, agent_id, text, :queue)` via `SafeCall.start/3`, arriving NESTED as `{{:session_message_sent, task_id}, result}` alongside a flat `{:session_message_sent, task_id, result}` clause; blank text or a session that stopped waiting flashes instead of sending), `open_close_session_modal` / `close_close_session_modal` (mutually exclusive with the cancel and force-kill modals), and `confirm_close_session` (`EvoDash.NodeContext.close_session(node, agent_id, :normal)` through `start_task_mutation/5`, tagged `{:close_session_result, task_id}`; the confirm button renders the modal's `busy` attr, the card's controls disable while in flight, and confirm assign, busy marker and expansion settle on EVERY outcome — success reloads without blanking, failure flashes). `EvoDashWeb.TasksLive.Session.confirm_close_session_modal/1` owns the markup.
## Task pause / resume UX (`:pausing`, `:paused`)
Pause and resume follow the same two-step / off-process discipline as cancel, but ASYNC because they are slow: a pause drains the task's agents at their next turn boundary (an in-flight tool call is never interrupted) and a resume re-dispatches an agent — neither may block the LiveView.
- **Assigns**: `:confirm_pause_task_id` (pause confirmation modal) and `:action_busy` — the page's ONE per-task busy map (see "Mutating events"), passed to `task_card/1` so every control of that task disables and the matching spinner renders. Both are cleared in `handle_params/3`'s node-switch branch; the busy entry is deleted on EVERY async result arm.
- **Pause**: card `open_pause_modal` (`phx-value-task_id`) → assign `:confirm_pause_task_id` (nils the other three confirm ids); `close_pause_modal` clears it. Modal: title `gettext("Pause task?")` with a `gettext("Task: %{task_id}", task_id: …)` line, and a `confirm_pause_task` (`phx-value-task_id`) that closes the modal, collapses the card and sets the busy marker immediately, then runs `EvoDash.NodeContext.pause_task(current_node, task_id)` through `EvoDash.SafeCall.start/3` tagged `{:pause_result, task_id}` (arriving NESTED). A confirm without an open modal is a no-op.
- **Resume**: the card posts `resume_task` (`phx-value-task_id`, DIRECT for a `:clean` pause / `phx-confirm`-gated for a `:dirty` one) → `EvoDash.NodeContext.resume_task(current_node, task_id)` through `SafeCall.start/3` tagged `{:resume_result, task_id}`; a nil `current_node`, or a missing/blank task id, is a silent no-op. The core resumes the WHOLE durable run tree (root plus every still-running subagent, each with its conversation, worktree and branch; an already-consumed child is not revived and a record-less one is reported lost — the card's `:dirty` explainer says exactly that).
- **Result application** (`pause_resume_result/4`): the busy marker is deleted and the card collapsed on EVERY arm, so a failed action can never leave a permanently spinning control; `{:ok, :ok}` starts `PageLoad.start/3` (async reload), while `{:ok, {:error, reason}}` (a documented refusal) and `{:error, reason}` (a transport/exit failure) each flash.
- **Error mapping** — one precise gettext line per documented reason: `:not_found` → "Task not found.", `:not_running` → "Only a running task can be paused.", `:not_pausable` → "This task cannot be paused (interactive sessions can't be paused).", `:not_resumable` → "This task can't be resumed because durable agent state is disabled for it.", `:scheduler_unavailable` → "The scheduler is unavailable right now.", `:not_paused` → "Only a paused task can be resumed.", `{kind, _}` with `kind ∈ [:exit, :throw, :error]` → "The node could not be reached — the task's state is unchanged.", plus a generic `gettext("Failed to pause task: %{reason}")` / `gettext("Failed to resume task: %{reason}")` with `inspect/1` for anything unexpected.
- **This is the ONLY LiveView with TASK pause/resume controls** — three unrelated same-named features live elsewhere: scheduler pause (`system_live` `toggle_pause` → `EvoGit.AgentScheduler.pause/0`/`resume/0`), process pause (`processes_live` `pause_process`/`resume_process` → `NodeContext.process_control/4`), and `/review`'s `resume` event (`TaskActions.resume/2`), which prepares a FOLLOW-UP task off `review_status: :continued`; none of them touches a task's `:pausing`/`:paused` status.
- **No paused-task agent surface**: `/agents` builds its tree from LIVE agent summaries only (`AgentsLive.LoadData.list_agents/1`), `home_live/task_tracking.ex` stops its 3 s poll once status is outside `pending|running|pausing|finalizing|cancelling`, and the card's lazy detail/archive reads (`TaskDetail`, `list_task_archives/3`) are NOT status-gated — nothing in the dashboard re-reads a paused run's durable agent rows, so a paused task shows no agents until it is resumed.
## Status filter inventory
The status `<select name="status_filter">` carries one option per addressable filter state; the value strings ARE the persisted status TEXT, so nothing is atomized on the way in or out.
Current option set, in lifecycle order: `all`, `running`, `pending`, `finalizing`, `cancelling`, `awaiting_input`, `pausing`, `paused`, `completed`, `failed`, `cancelled`, `needs_review`.
All twelve `<option>` elements are rendered by `tasks_live.ex` from the `@status_filters` whitelist, so `finalizing` and the DERIVED `needs_review` are both selectable now, and `needs_review` is understood by `page_load.ex` (`needs_review_filter?/1`, `review_status_filter/1`, `enforce_review_exactness/2`).
`PageLoad.filters/1` maps the selection to the store keyword; the store's WHERE builder is `EvoGit.Store.Operations.Filters.where_filters/2` in the read-only sibling app.
| option | store clause |
|--------|--------------|
| `all` | no status clause |
| `running` / `pending` / `finalizing` / `cancelling` / `awaiting_input` / `pausing` / `paused` / `completed` / `failed` / `cancelled` | exact stored TEXT equality (`t.status == ^value`) — no dashboard-side atom whitelist, so a core status round-trips as soon as its option exists here |
| `needs_review` | NOT a stored status: `filters/1` emits `status: "all"` plus `review_status: "pending"`, which the store builds as the composite `status = 'completed' AND review_status IS NULL AND branch_name IS NOT NULL` |
`PageLoad.needs_review_filter?/1` is the ONE predicate recognizing the derived option, and `PageLoad.review_status_filter/1` gives the status filter PRECEDENCE over the separate `review_filter` select: while the status filter is `needs_review` it answers `"pending"` regardless of the chosen review value, otherwise it passes the review value through.
A `:completed` task with no `branch_name` can never appear under `needs_review` (the store predicate requires a branch) — a documented limitation of the review queue, not a defect.
The derived option is additionally guarded CLIENT-side at the ONE post-load choke point `PageLoad.visible_tasks/2,3` → `enforce_review_exactness/2`, which drops every landed row that already carries a `review_status` (a blank `""` counts as unset), so no partial or stale server predicate can list a task whose review decision is already made.
That guard is total: an absent, nil or unreadable `review_status` counts as "no decision" and a non-map row is kept rather than raising.
`@total_count`/`@total_pages` stay SQL-truthful even when the client-side guard drops rows — the same accepted trade-off as `:reflect` hiding.

## URL is state (filters, search, focused task)
`handle_params/3` is the single seed of page state from the query string: `?page=N` (pagination), `?task=<id>` (the focused single-task view), `?node=<target_id>` (the viewed remote node) and the five filters `?status`, `?project`, `?review`, `?session`, `?q` (seeded by the one private `seed_filters/2`, whitelisted against `@status_filters` / `@review_filters` / `@session_filters`, `project` any non-empty binary, `q` verbatim, every unknown/absent value back to its default).
`tasks_url(socket, page, overrides \\ [])` (`tasks_url/3`) is the ONE URL builder: it uses the CURRENT filter assigns with `overrides` for the value being changed and emits ONLY non-default values as `&`-appended pairs in the order `page`, `status`, `project`, `review`, `session`, `q`, `node`.
Defaults are page 1 / `all` / `all` / `all` / `all` / `""`, so a plain list stays `/tasks`, and every value is query-encoded with `URI.encode_www_form/1` because a project filter is an absolute filesystem path.
It appends `&node=<target_id>` itself — never `Helpers.with_node_param/2`, which appends `?`.
Every filter/search/reset/clear event (`filter_tasks`, `filter_review`, `search_tasks`, `filter_session_mode`, `reset_filters`, the five `clear_filter` clauses) and all three pagination events converge on the same path: compute the values → `push_patch` (page 1 for a filter/search/reset/clear change, the current filters preserved by pagination) → ONE load in `handle_params/3`, never an "assign + reload" pair.
`toggle_reflect_tasks` is the ONE remaining assign + `reload(1)` path, because the reveal toggle is page-local (below).
The search box patches with `replace: true` (no history entry per debounce tick), and `tasks_url/3` never emits `task`, so a filter change while a focused `?task=<id>` view is active DROPS the focus — focus mode exits instead of silently narrowing.
`?task=<id>` keeps its full contract: a binary of 1..128 bytes (else nil), it auto-expands that card, switches `PageLoad.start/3` to the focused single-row `get_task_lite/2` read, passes `workbench_reconnect_params: Map.take(params, ["task"])` to the layout, hides the pagination, skips the `:reflect` hiding for it, and renders "Task not found" plus a "Task History" link when the read yields nothing.
`show_reflect_tasks` is deliberately PAGE-LOCAL and never becomes URL state: it is a reveal preference, not a narrowing filter — not reset by `reset_filters`, not seeded by `handle_params/3`, not in the active-filter chip strip.
`@current_path` is `tasks_url(socket, requested_page)` — the page's CURRENT url, filters included — not the bare `~p"/tasks"`, because `LiveHooks.NodeAware.handle_node_selected/2` rebuilds the node-switch URL from it (see `live_hooks/CONTEXT.md` "Node-switch URL rule"), so switching node keeps `/tasks?status=needs_review` instead of resetting to the default view.

## Destination rule (finished → review, live → in-page detail)
A FINISHED row links to `/review/<id>` through the card (`EvoDashWeb.TaskCardComponents`, `Helpers.with_node_param(~p"/review/#{id}", @current_node_id)`), so the rendered `href` is `/review/<id>` locally and `/review/<id>?node=<target_id>` on a remote `?node=` view.
The route allowlist is `TaskCardComponents.show_review_button?/1`'s `:completed`/`:cancelled`/`:failed` (repo-less `:reflect` excluded, pinned by the test suite): `:failed` keeps its salvage branch and any salvaged changes and the review page renders a failure honestly, so a failed run is reviewable; `:cancelled` keeps its result/branch the same way.
A `:failed` row gets that review ROUTE without entering the "Needs review" TRIAGE bucket, which stays the store's composite `:completed` + nil `review_status` + live-`branch_name` predicate (the derived `needs_review` status filter above, and the sidebar's partition).
A LIVE task (running/pending/finalizing/cancelling/awaiting_input/pausing/paused) has NO review route: the allowlist above is the whole predicate, and the only detail route for live work is expanding the card on this page (the lazy `TaskDetail` fetch) or the `?task=<id>` focus deep link.

## Action matrix (status × control)
Each control is rendered by the card and gated by the page's ONE `@action_busy` map; "—" means the control is not rendered for that status at all, and every action runs OFF-PROCESS through `EvoDash.SafeCall.start/3`.
| status | cancel | pause | resume | force kill | close session | delete |
|--------|--------|-------|--------|-----------|---------------|--------|
| `pending` | yes | — | — | — | — | yes |
| `running` | yes | yes | — | yes | — | yes |
| `finalizing` | — | — | — | — | — | yes |
| `awaiting_input` | yes | — | — | yes | yes (confirm-gated idle session) | yes |
| `cancelling` | — | — | — | yes (escalation) | — | yes |
| `pausing` | — | disabled (Pause renders for `[:running, :pausing]` and stays inert while draining) | — | yes | — | yes |
| `paused` | — | — | yes | yes | — | yes |
| `completed` / `failed` / `cancelled` | — | — | — | — | — | yes |
Event markers behind the matrix: Cancel `open_cancel_modal`, Pause `open_pause_modal`, Resume `resume_task` (direct for `:clean`, `phx-confirm`-gated for `:dirty`), Force kill `open_force_kill_modal`, Close session `open_close_session_modal`, Delete `delete_task` (unconditional, behind the card's "Danger zone" divider).
`action_busy` makes every action idempotent: `start_task_mutation/5` returns unchanged while that task id already holds a busy marker, so a duplicate `confirm_pause_task` or a double-clicked confirm dispatches exactly ONE core call.

## needs-review count line & empty state
The count line reads `dngettext("default", "%{count} task found", "%{count} tasks found", length(@filtered_tasks))` for every filter except `needs_review`, whose honest wording is `dngettext("default", "%{count} task needs review", "%{count} tasks need review", length(@filtered_tasks))`.
With `status_filter == "needs_review"` and an empty visible list the h2 is `gettext("No tasks need review")` and the hint is `gettext("Finished tasks that still need a review decision appear here.")`.
`Task not found` still wins when `@focused_task_id` is set, and every other filter keeps the existing "No tasks found" branches byte-compatible (the adjust-filters hint when a filter is active or rows were dropped by the reveal toggle, else the start-tasks hint).

## ModalHelpers (full result / full objective)
`view_full_result/2` reads the CACHED `:task_details` entry (never `socket.assigns.tasks` — those rows carry no `result`). `@selected_result` is modal STATE: `nil | %{state: :loading} | %{state: :ok, result: result} | %{state: :error, error: reason}`.
The Full Result modal (`gettext("Task Result")`) renders `TaskCardComponents.render_result_full(result)` and the `#full-result-copy` ClipboardCopy button ONLY in `:ok`; `#full-result-error` ("Could not load the task result.") for `:error` and `#full-result-loading` ("Task result is not loaded yet.") otherwise.
`view_full_options/2` reads the summary `opts` from `socket.assigns.tasks` (always present) → `opts[:prompt] || opts[:objective]`, so it needs no detail fetch; the Full Objective modal (`gettext("Full Objective")`) carries the `#full-options-copy` ClipboardCopy button. TasksLive implements the required `handle_event("copied", ...)` → "Copied to clipboard" flash handler.
## Failed-task error rendering (legacy error result + structured failure record)
A `:failed` task can surface its failure through TWO separate records: the legacy `{:error, reason}` / `{:exit, reason}` task RESULT shape and the structured `error` map field on the task row. Both may coexist, and a `:failed` task may carry either, both, or neither (legacy failed rows have `error` nil).
`error` (ATOM keys after decode) is `%{kind: atom, source: atom, message: String.t(), stacktrace: [String.t()] | nil}` with `kind` ∈ `:error | :exit | :down | :force_kill | :timeout | :restart | :lease_expired | :recheck` and `source` ∈ `:result_handler | :down_handler | :force_kill_task | :finalizing_watchdog | :startup_reconcile | :lease_sweep | :recheck_resolve`. It is `nil` on every non-`:failed` row and rides the SUMMARY projection, so it is available before — and independently of — the lazy detail.
- tasks_live.ex NEVER reads `task.result` / `task.error` itself — every row is delegated whole to `EvoDashWeb.TaskCardComponents.task_card task={task} show_details=... detail={Map.get(@task_details, task.id)} current_node_id=...`; all failure reading/rendering lives in the component.
- COLLAPSED `:failed` card (legacy shape): badge `Helpers.task_status_badge(:failed)` (`bg-error/10 text-error`), accent bar via `task_accent_color/1` → `Helpers.task_status_dot_class(:failed)`, tint `task_card_tint/1` → `Helpers.task_status_tint(:failed)`; badge text is the raw atom and no error text is visible. WITH a structured `error` map it additionally renders a compact error-tinted failure line — the truncated `error.message` (`Helpers.truncate_string/2`, ~160 chars); nil/non-map → nothing extra.
- EXPANDED structured failure block: reads the summary `error` — kind + source captions via `Helpers.task_error_kind_label/1` / `Helpers.task_error_source_label/1` (unknown atoms → a safe generic fallback), the full untruncated `error.message`, and the last ≤8 `stacktrace` frames as monospace lines. It renders even while the detail is loading.
- EXPANDED legacy result box: the Agent Message section is gated on `Map.get(detail.task, :result)` — an `{:error, _}` tuple is truthy, so it renders once the detail lands. Body = `render_result/2`, rendering `{:error, reason}` as a red box headed `gettext("Error")` (hero-x-circle icon) with `<pre> inspect(reason, limit: :infinity)` and `{:exit, reason}` as a "Crashed" box; `:failed` with a nil result → no Agent Message section (the legacy force-killed shape). Its only "Full" entry is `view_full_result/2` (cached detail; `result_copy_text/1` for `{:error, reason}` = `inspect(reason, limit: :infinity)`).
- Guards are read-only (`status == :failed and is_map(error)` + `Map.get`) and tolerant of nil/non-map/legacy shapes on BOTH the summary projection and full `%TaskInfo{}` rows. `show_review_button?/1` matches EVERY finished task (the `:completed`/`:cancelled`/`:failed` allowlist, repo-less `:reflect` excluded), so a `:failed` card DOES link to `/review/<id>` (test-pinned) — what stays `:completed`-only is the "Needs review" triage BUCKET, never the route.
- Legacy result decoded-shape note (evo_git codec contract): `{:error, reason}` persists tagged, and a non-JSON-safe reason (e.g. a tuple `{128, "fatal: ..."}`) is stored as `inspect(reason)` and decoded back as that string, so the dashboard sees `{:error, "{128, \"fatal: ...\"}"}` and displays it verbatim in the Error box (test-pinned for a string reason; no test covers tuple-shaped reasons). `render_result`'s catch-all pretty-inspects any non-tuple/non-map shape, so no stored result shape can crash a task card.

## Mutating events (SafeCall-wrapped, async reload)
- ALL five mutations are ASYNC and share ONE helper pair and ONE busy contract: `start_task_mutation/5` guards a duplicate submit (the `@action_busy` entry for that task id already present → no-op), sets the marker and calls `SafeCall.start(self(), tag, fn -> … end)`; the spawn-failure arm clears the marker immediately (a child that never started sends nothing).
- `@action_busy` is `%{task_id_string => :pause | :resume | :cancel | :force_kill | :close | :delete}` (already passed to `task_card/1`); `action_busy?/2` reads it for the page's own confirm modals, which disable their confirm button and swap the icon for a spinner while busy. `clear_task_history` uses the page-level `:clearing_history` flag (Clear History button disabled + `gettext("Clearing…")`) instead of a task key.
- `task_mutation_result/4` settles EVERY outcome: the busy entry is deleted first (success, `{:error, _}` and SafeCall's captured exit alike, so a button can never wedge), the matching confirm assign is cleared (`clear_confirm_assign/2`), then `:ok` collapses `:expanded_task_ids` for that id and runs `reload(socket, current_page)`, while `{:error, reason}` flashes the existing `gettext("Failed to cancel task: %{reason}", …)` / `gettext("Failed to force kill task: %{reason}", …)` / `gettext("Failed to close session: %{reason}", …)` / `gettext("Failed to delete task: %{reason}", …)` message.
- `clear_task_history` → `SafeCall.start(self(), {:clear_finished_result}, fn -> NodeContext.clear_finished_tasks(node) end)`. Success clears `:expanded_task_ids` and re-runs `reload(socket, 1)`; failure flashes `gettext("Failed to clear task history: %{reason}", reason: inspect(reason))` and does NOT reload; both clear `:clearing_history`.
- `delete_task` has NO confirmation modal (the card's dropdown posts it directly), so `clear_confirm_assign/2` leaves the socket untouched for it while the busy marker and expansion settle like the three confirmed mutations.
- Because the mutation is off-process, the click RETURNS before the store row settles: tests (and any UI copy) await the pushed result / the busy marker clearing, never the click's HTML. Node-aware argument reads (`current_node`, the `session_agent_id/2` lookup for close-session), the nil-confirm no-op and every existing flash string are unchanged.
- `mutation_result/1` (private) normalizes SafeCall's output to `:ok | {:error, reason}`: the NodeContext mutating functions return `:ok | {:error, reason}` (so SafeCall yields `{:ok, :ok}` / `{:ok, {:error, reason}}`) and a caught exit/raise yields `{:error, reason}`.
## Constraints
- Do NOT reintroduce polling (`:remote_poll` / `Process.send_after` self-ticks) or the DirtyTracker module — push events are the single change-detection mechanism, and detail/archive/agent-result values arrive only from their three messages.
- The page loads SUMMARY rows only (`list_tasks_page/2`); heavy data is fetched per card through `TaskDetail` (`get_task_lite/2` / `list_task_archives/3` / `get_agent_archive/3`) and is NEVER transferred with the list or rendered from the summary.
- Keep every load ASYNC and connected-gated: `handle_params/3` must only spawn behind `connected?(socket)`, and every page load — including the debounced reload and the post-mutation reload — must go through `PageLoad.start/3`. Never fetch a page inline in the LiveView.
- Every store/RPC call is exit-safe and OFF the socket: page loads via `PageLoad.run/6`'s `EvoDash.SafeCall.run/1`, detail/archive via `TaskDetail`'s spawned runners, mutations via `EvoDash.SafeCall.start/3` (ONE `handle_info` per tag, clearing its busy marker on every outcome). Never add a bare `EvoDash.NodeContext` / `EvoGit.TaskRegistry` call to a LiveView event handler.
- A `:loading`, `:error` or `nil` detail must always be a renderable state — the card shows the loading placeholder or the retry-able error strip; never a stuck spinner, never a crash, and never a heavy section rendered without `detail.task`.
- `:task_details` is bounded to ONE page: every landed page load must run `TaskDetail.prune/2` (then `ensure_expanded/2`), and a node-context change must reset it to `%{}`.
- Failure is a VALUE, not a crash: a failed load assigns `:tasks_error` and keeps the already-loaded rows; the UI offers `retry_load`. Never revert to a flash-only failure on the page-load path, and never clear `:tasks` on error.
- `:page_load_seq`, `:tasks_load_seq` and `:task_detail_seq` are INDEPENDENT stale-guards (page load / sidebar / per-card detail + archive). Never merge them and never bump another owner's counter.
- The node filter lives in `NodeAware.handle_task_info/2` (shared by every consumer of the `"tasks"` topic) — TasksLive only forwards and reloads; the detail invalidation applies the same `event_from_current_node?/2` filter itself.
- Modal state assigns are server-side (no custom JS); follow the warning-modal pattern for any new destructive action.
