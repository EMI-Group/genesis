# EvoDash Web Interface

## Intent
The web interface layer for the EvoDash Phoenix application — a real-time dashboard for the EvoGit evolutionary software development system. Contains the Phoenix endpoint, router, telemetry supervisor, and delegates interactive UI to LiveView pages, reusable components, and classic controllers in subdirectories.

## Routing Table
- `live/` → Phoenix LiveView pages (Dashboard, Agents, Settings, System & Config)
- `live_hooks/` → On-mount hooks: `SetLocale` (locale), `NodeAware` (node-aware dashboard)
- `components/` → Reusable HEEx UI components and layout templates
- `controllers/` → Classic HTTP controllers and error handlers
- `plugs/` → HTTP middleware plugs (Locale)

### Task Cancellation Model (graceful cancel + force kill)

The backend (`:evo_git`) provides two cancels: `EvoGit.RemoteNode.cancel_task/2` = GRACEFUL (`:pending` → immediate `:cancelled`; `:running` → `:cancelling`, agents messaged to save + exit, 3-turn grace, then `:cancelled` WITH result/archive preserved) and `EvoGit.RemoteNode.force_kill_task/2` = BRUTAL (kills all agents + wrapper → `:failed`, result nil'd; from `:running`/`:cancelling` = escalation). `EvoDash.NodeContext.cancel_task/2` and `EvoDash.NodeContext.force_kill_task/2` delegate to them (see `./evo_dash/CONTEXT.md`).

Dashboard UX: the task card's inline button is a graceful **Cancel** (`phx-click="open_cancel_modal"`, visible `[:pending, :running]`) and the three-dot dropdown has a destructive **Force kill** (`phx-click="open_force_kill_modal"`, visible `[:running, :cancelling]`). TasksLive implements both as two-step server-side confirmation modals (SystemLive warning-modal pattern — see `./live/CONTEXT.md`). The `:cancelling` status is treated as IN-PROGRESS everywhere: violet badge (`Helpers.task_status_badge`), violet pulsing-dot card label (`task_card_components.ex`), violet sidebar dot (`layouts.ex`), included in the sidebar `@active_statuses` + running partition (`NodeAware`), and filterable via the TasksLive status dropdown (`value="cancelling"`, pure SQL string filter).

### Agent Status Display (frontend merges `:blocked` into `:pending`)

The frontend presents `:blocked` and `:pending` agents identically as **"Pending"** on all agent status surfaces — to the user, both mean "queued / waiting to be scheduled" (`Helpers.agent_status_label/1` is the single source of label text; the four `agent_status_*` presentation helpers delegate `:blocked` → the `:pending` clause). The backend scheduler keeps `:blocked` and `:pending` distinct. Note: the SystemLive scheduler charts (`live/system_live/charts.ex`) consume the raw `:blocked` COUNT as the slot-saturation "waiting" telemetry series — that is scheduler telemetry, not an agent-status display.

## Constraints
- All web modules use `use EvoDashWeb, <role>` as their entrypoint — do not bypass the shared `__using__` macro.
- New interactive pages should be LiveViews in `live/`, not controllers in `controllers/`.
- Subdirectory naming conventions: `<name>_live.ex` for LiveViews, `<name>_components.ex` for component modules, `<name>_controller.ex` for controllers.
- Static assets served from `priv/static` under paths defined in `EvoDashWeb.static_paths/0`.
- Styling is Tailwind CSS + daisyUI throughout.
- **Professional design language** (Settings, Tasks, Review, System pages): compact, dense, "power-tool" aesthetic inspired by VS Code / GitHub — `rounded-lg`/`rounded-md` radii (no `rounded-3xl`/`rounded-2xl` large cards), subtle borders, restrained color, no gradient hero boxes or decorative blurs. Settings uses one-config-value-per-full-width-row layout; the config file path is shown at the top with a copy-to-clipboard button (`ClipboardCopy` hook).
- **`try/rescue` is an anti-pattern here.** Do NOT wrap config/core-value loading (`EvoGit.Config.*`, `EvoGit.AgentScheduler.*`, `EvoGit.SystemCheck.*`) in `try/rescue` — if these crash, the LiveView SHOULD crash truthfully so the real error is visible (displaying a wrong default like `%{}`, `false`, or `100_000` is worse than a visible crash). The only accepted `try/rescue` use is: genuinely untrusted external execution like `System.cmd` running user-defined shell commands (`ProjectsLive`). Every retained `try/rescue` MUST carry an inline justification comment. For converting untrusted strings to atoms, use whitelist `Map` lookups (`Map.get/2`/`Map.fetch/2`) — never bare `String.to_existing_atom/1` on client input, and never `String.to_atom/1` (atom-table exhaustion DoS risk).

## Known Issues — Task Archive Display (archive_components.ex / review_components.ex / archive_helpers.ex)

Investigated with the core runtime (`apps/evo_git`, see its CONTEXT.md "Archive record — exact structure & crash semantics"). Facts future agents should know:

- **Crashed/failed/aborted agents are NEVER in `archive_metadata`.** The core writes an archive record only when the `complete_task` tool runs with `archive && base_commit`; collection into the result happens only on successful root completion (`{:ok, %EvoGit.Agent.Result{}}`). There is no status/outcome field in records. The dashboard archive tree therefore shows ONLY completed agents — a crashed agent's failure is visible only via the task card's task-level status badge, not per-agent. `archive_details`/`archive_review_section` render nothing for a task whose root never completed (empty state text in `review_live.ex:164-165`).
- **Per-agent token/cost tiles display 0 / $0.000000 after a DB round-trip.** `archive_metadata` is persisted via `EvoGit.Store.Codec.encode_archive/decode_archive` (plain `Jason.encode/decode`, no key re-atomization) — so records arrive in the LiveView as STRING-keyed maps, INCLUDING the nested `usage` sub-map. `ArchiveHelpers.normalize_agent_keys/1` whitelist-converts only TOP-LEVEL keys (`"usage"` → `:usage`), so `@agent[:usage][:input_tokens]` (archive_components.ex:148, review_components.ex:214) hits string keys → `nil` → `|| 0` → renders "0". The grid renders (because `@agent[:usage]` is truthy) but every cell shows 0. The JSON export is NOT affected — it dumps raw values.
- **Per-agent Cost tile is always $0.000000 even with atom keys**: the components read `@agent[:usage][:cost]` but the core's archive usage map has no `cost` key — it writes `input_cost`/`output_cost`/`total_cost` (core `complete_task.ex` `format_usage_for_archive/1`). Fixing this needs either reading `total_cost` or key normalization of the nested usage map.
- **Task-level totals come from `TaskInfo.usage` (a `%EvoGit.Agent.Usage{}` struct, atom-keyed after `decode_usage` reconstruction — works fine), NOT from summing archive records.** The dash app never aggregates per-agent usages (no `Usage.add` in evo_dash). Export envelope carries both: `usage: task.usage` (task-level) + `archive_records` (per-agent, raw).
- **Where archive UI renders**: (1) Tasks page expanded task card (`tasks_live.ex:166` → `task_card_components.ex:386-391` — full tasks with `archive_metadata`), (2) Review page "Archive" tab (`review_live.ex:154-165` → `review_components.ex`). The Projects page task list strips `archive_metadata` (`projects_live/assigns.ex:130`), and `EvoDash.NodeContext.list_tasks_summary` also omits it — sidebar lists never show it.
- **Export endpoint** (`TaskExportController.export`, `GET /tasks/:task_id/export`): 404 when task missing or `archive_metadata` nil/[]; otherwise envelope `%{task_id, task_type, repo_path, status, started_at, finished_at, agent_count, usage, archive_records}` normalized by `normalize_for_json/1` (structs→maps, DateTime→ISO8601 string, atom keys→strings, tuples→lists, PID/ref/port/fun→`inspect/1` string) and sent as attachment `archive-<task_id>.json`.
- **ArchiveHelpers guardrails**: `build_archive_tree/1` and `build_archive_tree_for_review/1` use a visited-set + `agent_id` nil/"" filter to survive cyclic/self-referential or string-keyed data (pinned by `test/evo_dash_web/components/archive_tree_test.exs` and `review_live_test.exs:144-217`).
- **nil `parent_id` is faithfully preserved end-to-end — the dashboard can neither drop it nor invent it.** (1) **Export**: `TaskExportController.normalize_for_json/1` keeps every map key (`Map.new(map, fn {k,v} -> {to_string(k), ...} end)`, task_export_controller.ex:55-57) and nil values pass through the catch-all clause (line 73), so a nil `parent_id` is emitted as `"parent_id": null` — never dropped, never renamed (test-pinned: task_export_controller_test.exs:87 `assert first["parent_id"] == nil`). A stored NON-nil parent_id cannot be lost: no key rename, no struct mismatch (`Map.from_struct` keeps all fields), and `Codec.encode_archive` is plain `Jason.encode` (nil → `null`), `decode_archive` plain `Jason.decode` (no key re-atomization). (2) **Tree**: `build_archive_tree/1` (archive_helpers.ex:47-55) groups records by `agent_key(&1, :parent_id)` (atom-first, string fallback) and treats `by_parent[nil]` as ROOTS — MULTIPLE roots are fully supported (the `Enum.map` at line 54 returns a list; both `ArchiveComponents.archive_tree` archive_components.ex:52-61 and `ReviewComponents.archive_review_section` review_components.ex:118-120 `for`-loop over the roots list). Each nil-parent record renders as its own top-level node; no single-root assumption, no flattening, no dedup — the tree shows exactly N top-level nodes for N stored nil-parent records (minus records with nil/"" `agent_id`, filtered at line 53). (3) **The tree can only HIDE records, never inflate**: records whose non-nil parent_id matches no `agent_id` (orphans) are reachable only via a parent's children lookup, so they never render (but remain in JSON + in the raw `length(@archive_metadata)` count, review_live.ex:85). `build_archive_tree_for_review`'s `_ -> nil` catch-all (line 65-70) would mislabel a non-binary non-nil parent_id as root, but after the JSON DB round-trip parent_id is always a string or nil, so it cannot fire for stored data. (4) **No dashboard write path**: `archive_metadata` is only read/stripped/exported in evo_dash; the sole task-launch entry points (`task_submit` → `TaskRegistry.start_task`, projects_live.ex:693; `confirm_extract_skills`, review_live.ex:536) launch a single root task and never touch archive records. The Review "Resume" button (review_live.ex:423-452) only prepares a NEW evolve form (`?resume_from=`), and `AgentsLive`'s `parent_id` mutations (agents_live.ex:374) are display-only in-memory ETS views. Therefore N records with nil `parent_id` in the dashboard/JSON ⇒ exactly N stored records; 10 observed nil-parent records in a Genesis run must originate in the CORE-written archive data (`CompleteTask.complete/4` agent-state parent_id), not in export/UI logic.

## Task Summary Data Flow — SQL-side filtering + debounce optimization

Coordinated design across `live_hooks/`, `live/`, `components/`, and the `evo_git` core. Detailed per-subtree notes in `live/CONTEXT.md`, `live_hooks/CONTEXT.md`, `components/CONTEXT.md`.

- **Sidebar summary is SQL-filtered + UNIFIED (single loader)**: `EvoDashWeb.LiveHooks.NodeAware` is the ONE sidebar Active Tasks implementation — `fetch_active_tasks/1` (node-aware: local `TaskRegistry.list_tasks_summary(@active_statuses)` / remote `NodeContext.list_tasks_summary(node, @active_statuses)` RPC; pending-remote guard → `{[], []}`) → `partition_active_tasks/1` (pure) → `assign_active_tasks/1` (assigns `:running_tasks`/`:pending_tasks`); `load_running_and_pending_tasks/1` delegates. The sidebar is served exclusively by `EvoDashWeb.LiveHooks.NodeAware` (no `Assigns.assign_running_and_pending_tasks/1`/`2` variants exist). The SQL query skips finished tasks that can never appear in the sidebar. Elixir-side filtering (running filter + pending-review derivation + sort) unchanged. `show_review_button?/1` is public and column-based (`branch_name`) — NO `result` reads from summary maps. on_mount fires the load ONLY on the connected mount (dead-render skip).
- **Debounced task reloads (push-based, no poll)**: task events are now `{:task_updated, task_id, status, node}` and `{:task_deleted, task_id, node}`. `NodeAware.handle_task_info/2` (returns `{:noreply, socket}` — do NOT re-wrap in LiveViews) applies the node filter via `event_from_current_node?/2` BEFORE calling `debounce_task_reload/1` — foreign-node events are dropped, protecting every page's reload and ProjectsLive's local-only browser-notification diff — then sets `:tasks_reload_pending` and schedules `Process.send_after(self(), :node_aware_reload_tasks, 300)`; bursts are coalesced into ONE trailing reload (intermediate broadcasts dropped). The actual reload happens in each LiveView's `handle_info(:node_aware_reload_tasks, socket)` clause: simple views call `NodeAware.reload_tasks(socket)`; `projects_live` runs its custom full reload (project-config refresh + browser notifications + sidebar) and ends with `NodeAware.clear_task_reload_pending(socket)`; `tasks_live` additionally refreshes its page data (`reload_current_page`) — the same debounced path serves BOTH local and remote (no poll); `review_live` runs a **broadcast-guarded async reload**: only a node-matching `{:task_updated, task_id, _, _}` for THE REVIEWED task re-fetches the review data (via the async `start_async_load/2` — the page-data load is `Task.Supervisor`-spawned, result applied from `{:review_data_loaded, ...}` with a stale guard, never blocking `handle_params`); `{:task_deleted, ...}` never reloads or stashes review data (the `last_broadcast_task_id` stash is reset at the end of the reload handler); the sidebar refresh (`NodeAware.reload_tasks/1`) runs in all cases. `{:recent_projects_updated}` is intentionally NOT debounced.
- **`assign_node/2` dedup guard**: tracks `:tasks_node_loaded` (`{current_node_id, current_node}`); skips the sidebar reload when the resolved node context is unchanged (prevents the mount double-fetch: `on_mount` seeds `{nil, node()}`; pagination/palette push_patches do not re-fetch). Node switches (local↔remote, pending→connected) reload.
- **No dashboard main task list**: the dashboard renders no main task list — `Assigns.current_tasks/1` and all `assign(:tasks, ...)` sites are deleted. The sidebar (`@running_tasks`/`@pending_tasks`) is statuses-filtered summary maps (`TaskRegistry.list_tasks_summary([:running, :pending, :finalizing, :completed])` — no full-row decode; no logs/usage/archive_metadata). Summary maps are already light — no stripping helpers exist. Browser notifications use the minimal id-only projection (`TaskRegistry.list_task_ids([:completed, :failed, :cancelled])`) + per-new-id `TaskRegistry.get_task/1`.
- **Sidebar loader is unified**: the sidebar is served exclusively by `EvoDashWeb.LiveHooks.NodeAware.assign_active_tasks/1` (with the delegating `load_running_and_pending_tasks/1` entry, node_aware.ex). No `Assigns.assign_running_and_pending_tasks/1`/`2` variants exist.
- **Summary map contract** (from `EvoGit.TaskRegistry.list_tasks_summary`): plain maps with `id, status, review_status, started_at, finished_at, type, project_path, opts, branch_name, model_id, agent_count, base_sha, commit_sha, lease_expires_at, updated_at` (opts = decoded keyword list; `updated_at` = raw fixed-precision ISO string). Heavy fields EXCLUDED — `result` is deliberately dropped from the projection (`EvoGit.Store` `@summary_columns`/`decode_summary_row`); evo_dash never reads `result` from these maps (`show_review_button?` is `branch_name`-column-based). Components must dot-access ONLY contract keys (`Map.get` for optional) — a dot access on a missing map key raises KeyError (see `components/CONTEXT.md` audit table; e.g. `task_card_components.ex:343` uses `Map.get(@task, :logs) not in [nil, []]`).
- **No periodic polling**: `tasks_live` and `agents_live` have NO 3s remote polls (the old `:remote_poll` timers were deleted). Remote-node updates arrive through the same node-filtered push events as local ones — TasksLive: `{:task_updated, ...}` / `{:task_deleted, ...}` → 300ms debounce → full async page reload; AgentsLive: the four `"agents"`-topic shapes. The page-load path (`list_tasks_paginated`) still transfers FULL TaskInfo structs for the expandable cards (archive_metadata/logs/usage) — but only on explicit page loads/reloads, never on a timer.
