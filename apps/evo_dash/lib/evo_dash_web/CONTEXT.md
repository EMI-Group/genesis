# EvoDash Web Interface

## Intent
The web interface layer for the EvoDash Phoenix application — a real-time dashboard for the EvoGit evolutionary software development system.
Contains the Phoenix endpoint, router, telemetry supervisor and delegates interactive UI to LiveView pages, reusable components and classic controllers in subdirectories.

## Routing Table
- `live/` → Phoenix LiveView pages (Projects, Home, Tasks, Agents, Settings, System, Review, Process, Welcome) + `live/components/` LiveComponents
- `live_hooks/` → On-mount hooks: `SetLocale`, `NodeAware`, `Appearance`, `DesktopQuit`, `UpdateStatus`, `Guide` — registered in this order by `EvoDashWeb.live_view/0`, Guide LAST
- `llm_setup/` → shared wizard foundation behind `/welcome` and Settings (`Wizard`, `Reasoning`, `Identity`, `Schedule`, `ChatGPTSignIn`) → `llm_setup/CONTEXT.md`
- `components/` → Reusable HEEx UI components and layout templates (`components/agents_components/` → Agents-page commit-history view sub-components; `components/settings_components/` → Settings provider surface)
- `controllers/` → Classic HTTP controllers and error handlers
- `plugs/` → HTTP middleware plugs (`Locale`, `MCP`)
- Canonical provider/model/reasoning selection and server-only configuration ownership → `live/CONTEXT.md`, `live/projects_live/`, `live/home_live/` and `components/llm_selection_components.ex`.
- The "Model" label rendered by the Agents detail panel and the task card — ONE pure derivation (canonical `model_spec` → `llm_model` → legacy `model_id` → nil, plus a task-opts wrapper) in `model_label.ex` (`EvoDashWeb.ModelLabel`) → `live/agents_live/CONTEXT.md`, `components/task_card_components/CONTEXT.md`.
- Canonical Settings provider-account surface — one panel with one summary row per account, at most ONE expanded editor at a time, provider-derived account identity, schedule presets and the two inline add-account/add-model wizards; scoped asynchronous persistence and field errors → `live/settings_live/CONTEXT.md` and `components/settings_components/CONTEXT.md`.
- Progressive Settings provider detail — provider choice, authentication, compact model rows and the real default-model/default-reasoning selects stay visible; optional account settings (including the nonsecret API-key environment-variable name), the schedule editor, shared context and the generation defaults live in the collapsed `#provider-profile-advanced` / `#provider-generation-defaults` / `#provider-model-details-<index>` disclosures → `components/settings_components/CONTEXT.md`.
- Settings editor state and parsing — the zero-row `default_model_name` helper synchronizes with the default-model select without synthesizing overrides, and explicitly clearing a model's reasoning override inventory removes its obsolete default while absent overrides retain inheritance → `live/settings_live/CONTEXT.md`.
- Default-only provider save validation is core-owned; the validator rejects a nonempty default model with an empty override list, so the dashboard preserves the rejected draft rather than inventing an override row.

### Task Cancellation & Pause Model (dashboard half)

Core semantics (graceful `:cancelling` with a 3-turn grace and preserved result/archive vs force kill → `:failed` with a nil result; clean vs dirty pause) live in the root `./CONTEXT.md` and `apps/evo_dash/CONTEXT.md`; here `EvoDash.NodeContext.cancel_task/2`, `force_kill_task/2`, `pause_task/2` and `resume_task/2` are plain `EvoGit.RemoteNode` delegations with NO local/remote split (`:ok | {:error, reason}`, verbatim).
`:pausing` is still WORKING (freezing the task tree — in-flight tool batches get a bounded quiesce — wrapper + lease alive) → every BUSY list, amber, `Pausing…`; `:cancelling` is IN-PROGRESS everywhere (amber busy family badge/dot/label/pulse, sidebar live list, SQL status filter); `:paused` is NON-terminal (no wrapper/lease, `finished_at` nil, survives `clear_finished_tasks`), RESUMABLE and NOT busy → its own blue `info` family, never pulsing; `pause_kind` (`:clean`/`:dirty`/`nil`) is the 18th task-summary key and drives the card explainer plus the dirty-resume confirm.
A paused card has no Review button (`show_review_button?/1` is an allowlist over FINISHED statuses — `:completed`/`:cancelled`/`:failed` — and a pause is not finished); force kill is the only terminal exit from a pause. Refusals are values: `:not_found`, `:not_running`, `:not_pausable` (interactive session), `:not_resumable` (`persistent_state: false`), `:scheduler_unavailable`, `:not_paused`, plus `{:error, {kind, reason}}`.

**`:awaiting_input` — the idle interactive session status.** Non-terminal: the root agent is a live session that finished a turn and waits, holding no worker, LLM/tool slot or timer. It is admitted wherever a task is ACTIVE (sidebar lists + running partition, TasksLive status filter, task card) but never treated as busy — `/server/status` keeps its five-status busy set, and the update wind-down asks sessions to close. Presentation is a VIOLET family, deliberately outside both the amber busy family and the neutral terminal family. `TaskCardComponents.Session.session_panel/1` (rendered only for an idle session whose agent id the page resolved) posts `session_send_message` → `NodeContext.send_session_message/4` (`:queue`) and offers `open_close_session_modal`/`confirm_close_session` → `close_session/3` (`:normal`); the sidebar lists sessions in their own group. Detail: `live/tasks_live/CONTEXT.md`, `components/task_card_components/CONTEXT.md`, `live_hooks/CONTEXT.md`.

### Task-status admission inventory (where any new task status must be wired)

Every dashboard status list is an independent literal — no shared status enum exists dashboard-side, and the store filter is a pure SQL string comparison, so an unwired status still round-trips from the core. Sites:
- `helpers.ex` `task_status_badge/1`, `task_status_dot_class/1`, `task_status_tint/1` — each ends in a catch-all (a missing status renders neutral gray).
- `components/task_card_components.ex` — pulse set `[:running, :cancelling, :awaiting_input, :pausing]` (`:paused` never pulses), the label `cond` (`true ->` prints the raw atom), Pause `[:running, :pausing]`, Resume `[:paused]`, Cancel `[:pending, :running, :awaiting_input]`, Force kill `[:running, :awaiting_input, :cancelling, :pausing, :paused]`.
- `components/workbench_active_tasks.ex` — sidebar live/active rows `live_task?/1` `[:running, :pending, :finalizing, :cancelling, :pausing, :paused]` (a paused task stays findable, `:awaiting_input` excluded because sessions render in the Conversations block), `pulsing_status?/1` the busy subset `[:running, :pending, :finalizing, :cancelling, :pausing]`, `active_status_title/1` the "Paused"/"Pausing" tooltips; `components/layouts.ex` owns no task-status list.
- `live_hooks/node_aware.ex` — `@active_statuses` (the SQL `WHERE status IN (...)`) includes the pause pair plus `:awaiting_input`; `partition_active_tasks/1` decides the sidebar groups.
- `live/tasks_live.ex` — the status-filter `<option>` list (string values passed through as exact stored TEXT).
- Terminal sets `[:completed, :cancelled, :failed]` in `live/home_live/stream_fold.ex`, `task_events.ex` and `send_path.ex`; Assistant persistence in `live/home_live/chat_state.ex` (`@task_statuses` whitelist, unknown atom → nil) and `SessionList` `@live_statuses`.
- Update gate `live/system_live/update_card.ex` and the headless CLI gate `controllers/server_status_controller.ex` both use the five-status busy set `[:running, :pending, :cancelling, :finalizing, :pausing]` — `:pausing` holds a wrapper and lease mid-freeze so an update waits; `:awaiting_input`/`:paused` are excluded (nothing holds a worker or lease).
- Review page needs none: the raw status passes through as `String.capitalize(to_string(status))`, reloading only when the value changes.
- MCP: the `genesis_list_tasks` status enum lives in the core (`EvoGit.TaskControl.Tools`, `EvoGit.TaskControl.status_filters/0`); `lib/evo_dash/mcp/tools.ex` is only a `defdelegate` to it.

### Agent Status Display (frontend merges `:blocked` into `:pending`)

The frontend presents `:blocked` and `:pending` agents identically as **"Pending"** on all agent status surfaces (`Helpers.agent_status_label/1` is the single source of label text; the four `agent_status_*` presentation helpers delegate `:blocked` → the `:pending` clause). The backend scheduler keeps them distinct, and the SystemLive charts consume the raw `:blocked` COUNT as the slot-saturation "waiting" telemetry series — scheduler telemetry, not an agent-status display.

### Agents page — left-panel view switcher (spatial tree / temporal commit history)

The Agents page visualizes BOTH dimensions: the recursive agent tree (spatial) and a VERTICAL, commit-centric DAG of the git history (temporal).
The left column (`live/agents_live.html.heex`) carries a segmented control (`#left-view-tree` / `#left-view-commits`) that swaps the panel body via `switch_left_view` (`phx-value-view` whitelisted by pattern match — never an atom conversion); the `@left_view` assign (`:tree | :commits`, default `:tree`) survives a node switch while the commit-graph data resets.
The commit view is rendered by `EvoDashWeb.AgentsComponents.CommitGraphView.commit_graph_view/1` (`components/agents_components/`, gutter SVG) from `@commit_graph` — the per-repo view model built by the pure `EvoDashWeb.AgentsLive.CommitGraph.build/3` (the collapsed `build/2` passes an empty expansion set), which also owns the shared repo `grouping_key/1` / `repo_display_name/1` naming (the tree delegates to it).
Layout rules: one ROW per VISIBLE node top → bottom in the GLOBAL interleave `{layer, date_unix, sort_sha}` (parents strictly above children) with one GUTTER LANE per agent (neutral lane 0 = unowned commits), rows re-indexed `0..n-1` over VISIBLE nodes only, and `phx-click="select_agent"` (`phx-value-id`) so graph selection reuses the tree event.
Each lane is COLLAPSED BY DEFAULT to structural ANCHORS (lane START/END, any node named in `start_ids`/`end_ids`, nodes carrying `refs`, `:base`/`:noop` stubs, unowned nodes); a maximal run of 2+ hidden interior commits on ONE lane becomes exactly ONE `kind: :gap` row (`sha: "gap-" <> fold_key`, plus `fold_key`/`hidden_count`/`expanded`) toggled per run by `toggle_commit_fold`, while a lone interior commit stays a real `:commit` row.
Edges whose endpoint folded into a gap are ALIASED to that gap's sha (deduped, `:parent` = first surviving parent, self-loops dropped); a `:merge_back` lands by a THREE-STEP rule — the topmost parent-owned node strictly BELOW the source, else the NEAREST parent-owned node ABOVE, else the edge is DROPPED (never `to_sha: nil`), a synthesized BASE node exists per distinct `base_commit` absent from the fetched commits, an agent TIP (END) node is filled with `Helpers.agent_status_svg_color/1`, a commit's non-first present parent draws a dashed `:merge` edge, and nodes carry a native `<title>` tooltip.
Scrolling: the commit view FILLS its panel at xl+ through a flex chain (card body carries `agents-tree-body-commits`; `#commit-graph` → `#commit-graph-body-<node_key>` → `.cg-repo` → `.cg-scroll`, each link a flex column with `min-height: 0`) whose ONE scroller is `.cg-scroll` (both axes, bounded below xl, dropped at xl+ where each `.cg-repo` takes `flex: 1 1 0`); the sticky `.cg-lane-header` resolves against it and there is no pan/zoom.
The `.agents-legend` chips swap per view (status legend ↔ Commit / Agent / Agent status / Merge edge); the right-hand detail panel is unchanged.
All commit-graph fetching is async (`EvoDash.TaskSupervisor`, seam `:agents_commit_graph_runner`) and happens ONLY while the commit view is active — a tree-only session never issues a git RPC. Depth-hue mapping, edge/route geometry, assigns/async/throttle and the frozen gutter DOM contract: `live/agents_live/CONTEXT.md` + `components/agents_components/CONTEXT.md`.

### Task mode resolution & `:reflect` (web↔core contract)

Dashboard combined-mode strings map to `{task_type, core_mode_string}` in `ProjectsLive.TaskSubmit.mode/1`: `{:genesis, "new"|"existing"}`, `{:evolve, "simple"|"custom"}` (`"custom_agent"` → `{:evolve, "custom"}`), and any unknown string falls back to `{:evolve, "simple"}`. The core `EvoGit.TaskRegistry.RuntimeOpts.mode_atom/2` dispatches to `genesis_mode_atom/1` or `evolution_mode_atom/1`; unknown evolution modes raise `ArgumentError`, and `:genesis` with `"custom"` raises "custom mode is evolve-only".

**:reflect (repo-less chat)**: interactive sessions are the PRIMARY `/assistant` driver (one live session per conversation, NOT a fresh task per message); the one-shot `:reflect` task is the FALLBACK when a node cannot run a session. reflect tasks carry NO `:path` (nil `project_path`), result `{:ok, %{result: <text>, commit_sha: nil, branch_name: nil, tag: nil}}`, and `:reflect` IS in `EvoGit.Store.Codec` `@known_atoms`. `TaskExecutor.execute_task(:reflect, ...)` routes directly to `Runtime.SelfReflective.run`, bypassing `build_common_runtime_opts` (which `Keyword.fetch!(:path)`-raises). Detail: `live/home_live/CONTEXT.md`.

## Config Read Path & Reload (dashboard web layer)

- Config freshness is per-render: pages read `EvoDash.NodeContext.get_resolved_config/1` (local `EvoGit.Config.resolve/0`) on mount/`handle_params` and cache the result in socket assigns. Only `EvoDashWeb.ProjectsLive` consumes a config event: it subscribes to the core's `"config"` topic and handles `{:config_reloaded, node, dir, generation}` (node filter + `{dir, generation}` guard) by re-spawning its picker batch — every other page subscribes to no config event, and a page without a matching clause silently drops such a broadcast.
- The ONLY explicit `NodeContext.reload_remote_config/1` call site is the remote credential save in `EvoDashWeb.SettingsLive.CategoryEvents`; the Settings config save depends on the reload implicit inside `RemoteAPI.save_user_config/1` and then re-reads (`live/settings_live/config_save.ex`).
- `NodeContext.get_remote_config/1` has ZERO production callers — it returns the scheduler config, which carries no `:llm` section (hence `get_resolved_config/1` everywhere). `get_remote_config_status/1` is the node-aware `config_status` read used by Settings, System, Agents and CategoryEvents; `EvoDashWeb.Helpers.config_status/0` is the local config-warning banner's single core call.
- `{:scheduler_config_updated, node}` is consumed only by SettingsLive (`AsyncResults.scheduler_config_updated/2`, which re-assigns the LOCAL `scheduler_config` even for a remote node) and SystemLive (paused flag only) — neither reloads user config.
- The only raw config-file read in the web layer is `live/welcome_live/setup.ex` (`File.read(EvoGit.Config.config_path())` — a deliberate read-modify-write bypassing `resolve/0`); the only config-path computation is `SettingsLive.PageState.initial_assigns/1` (path + `File.exists?`, mount only, never re-checked).
- Remote connect/bootstrap performs NO config refresh or reload: the node selector connects then `push_patch`es, and `AsyncResults.remote_connection_status/2` only refreshes connection statuses — the dashboard assumes the remote already observes copied config files.

`EvoDashWeb.Gettext` (`gettext.ex`) is the umbrella's only Gettext backend and is deliberately declared with `split_module_by: [:locale, :domain]` — Gettext then emits one small `EvoDashWeb.Gettext.T_<locale>_<domain>` module per locale (parallel compile) instead of a single ~16k-clause module. Keep this option; the public API (`gettext`/`lgettext`/`put_locale`/`known_locales`, `use Gettext, backend: EvoDashWeb.Gettext`) is unchanged.

**Development policy** (root `./CONTEXT.md` → "Internationalization (i18n) Development Policy"): during feature work NEVER run `mix gettext.extract`, `mix gettext.merge` or `mix translate` — POT/PO and translations are maintained centrally and refreshed once per release (`mix gettext.extract` → `mix gettext.merge` → `mix translate apps/evo_dash/priv/gettext/default.pot all`).
Every user-facing string in LiveViews, components, helpers and templates is `gettext`-wrapped; just write the wrapped string, and when a meaning needs anchoring for the release-time AI translator (ambiguous short labels, domain jargon) add a **Chinese comment** beside the `gettext` call — the ONLY i18n work expected during development.

## Constraints
- All web modules use `use EvoDashWeb, <role>` as their entrypoint — do not bypass the shared `__using__` macro.
- New interactive pages should be LiveViews in `live/`, not controllers in `controllers/`.
- Subdirectory naming conventions: `<name>_live.ex` for LiveViews, `<name>_components.ex` for component modules, `<name>_controller.ex` for controllers.
- Static assets are served from `priv/static` under paths defined in `EvoDashWeb.static_paths/0`; styling is Tailwind CSS + daisyUI.
- **Professional design language** (Settings, Tasks, Review, System): compact, dense, "power-tool" aesthetic — `rounded-lg`/`rounded-md` radii (no large hero cards), subtle borders, restrained color, no gradient boxes or decorative blurs. Settings uses one-config-value-per-full-width-row layout; the config file path sits at the top with a `ClipboardCopy` button.
- **`try/rescue` is an anti-pattern here.** Do NOT wrap config/core-value loading (`EvoGit.Config.*`, `EvoGit.AgentScheduler.*`, `EvoGit.SystemCheck.*`) in `try/rescue` — if these crash, the LiveView SHOULD crash truthfully (a wrong default like `%{}`, `false` or `100_000` is worse than a visible crash). The only accepted use is genuinely untrusted external execution such as `System.cmd` running user-defined shell commands (`ProjectsLive`), and every retained `try/rescue` MUST carry an inline justification comment. Convert untrusted strings to atoms with whitelist `Map` lookups (`Map.get/2`/`Map.fetch/2`) — never bare `String.to_existing_atom/1` on client input and never `String.to_atom/1` (atom-table exhaustion DoS).

## Endpoint Host, Origin & Connection Diagnostics (Bandit)

- **No evo_dash page behavior depends on the origin host being `localhost`**: layouts/root/nav use relative `~p` paths, the LiveView socket is the relative `"/live"`, and desktop/dev set `check_origin: false`, so `http://127.0.0.1:<port>` behaves identically to `http://localhost:<port>`. The ONE absolute-URL builder is `EvoDash.MCP.Links` (`EvoDashWeb.Endpoint.url()`, configured endpoint only, never request headers); any future absolute URL must keep its host matched to the bind address (or the server must also listen on `::1`).
- **Endpoint host mirrors the bind address in desktop/server mode**: `config/runtime.exs` derives `url: [host: desktop_host]` from the resolved bind address (`127.0.0.1` by default, or `PHX_IP` / `[server] listen_ip`), so advertised URLs name an address the IPv4-only loopback listener actually serves — `localhost` would resolve to `::1` first on macOS/Windows. The compile-time `config/config.exs` `url: [host: "localhost"]` default still applies to dev/test endpoints.
- **`** (Bandit.HTTPError) Read timeout` at ERROR level** = a connection open ~120 s WITHOUT ever sending a complete HTTP request (wire sniff blocks ThousandIsland's 60 s `:read_timeout`, then the HTTP/1.1 handler blocks another 60 s on an empty buffer before `request_error!("Read timeout", :request_timeout)`); an IDLE KEEP-ALIVE socket does NOT produce it. Observed clients: browser/WebView speculative preconnects or a bare-TCP liveness probe that never writes.
- **Peer info comes from connection-scoped logger metadata, not the error**: Bandit's protocol-error metadata carries only `domain`/`crash_reason` and the formatter prints only configured keys (`:request_id`), so `::1` vs `127.0.0.1` is unrecoverable there. `EvoDash.ConnectionDiagnostics` (`apps/evo_dash/lib/evo_dash/connection_diagnostics.ex`) attaches a `:telemetry` handler to `[:thousand_island, :connection, :start]`, reads the span's `remote_address`/`remote_port`, and calls `Logger.metadata(remote_ip: …, remote_port: …)` in the emitting connection process, so the peer appears on every later line of that connection (including the read-timeout ERROR) provided `config/config.exs`'s formatter `metadata:` list includes `:remote_ip`/`:remote_port` (that config lives outside the dashboard). Wired from `EvoDash.Application.start/2`, non-fatal.

## Known Issues — Task Archive Display (archive_components.ex / review_components.ex / archive_helpers.ex)

- **Crashed/failed/aborted agents are NEVER in the archive.** The core writes an archive row and refs at agent completion from the implicit (text-reply) route only when `archive && base_commit`; records are collected only on successful root completion and have no status/outcome field, so the dashboard tree shows only completed agents — a crashed agent is visible only via the task-level status badge, and the archive sections render nothing when the root never completed.
- **Task-level totals come from `TaskInfo.usage`** (a `%EvoGit.Agent.Usage{}` struct, atom-keyed after `decode_usage`), NOT from summing archive records; evo_dash never aggregates per-agent usages. The export envelope carries both `usage` (task-level) and `archive_records` (per-agent, raw).
- **Where archive UI renders**: (1) the Tasks page expanded card (`TaskCardComponents.task_card/1` → `ArchiveComponents.archive_details/1`) from the card's lazy, PAGED disclosure; (2) the Review page "Archive" tab (`ReviewLive.ArchiveLoad.panel/1`), only when the persisted opts opted into archiving (`ArchiveHelpers.archive_opt?/1` — otherwise the tab is not rendered and `ArchiveLoad` never fetches), first page on tab open plus "Load more". Both render the RETAINED window (at most `max_retained/0` = 500 newest entries) through the shared `ArchiveComponents.archive_count_line/1` — honest total, retained span, "earlier entries omitted; export JSON for the full archive" when rows were dropped, and "No more archive entries." once exhausted — and each agent's heavy `result` only after its own "Show result" click. A page with FEWER entries than requested (including empty) exhausts the archive: the effective total clamps to what was fetched and the pager disappears, so a server `total` larger than the rows returned can never spin "Load more" forever. No other surface renders it (sidebar and Projects read summary rows, which carry no archive data).
- **ArchiveHelpers guardrails**: the capped builders cap the record slice, keep the cycle-safety visited sets + `agent_id` nil/"" filter, and never drop a record inside the rendered slice (an out-of-page parent becomes a top-level node); only the LiveView retention window evicts rows, and it reports how many (`dropped`); pinned by `test/evo_dash_web/components/archive_tree_test.exs`, `blob_caps_test.exs` and `review_live_test.exs`.
- **nil `parent_id` is preserved end-to-end — the dashboard can neither drop it nor invent it.** Export stringifies every map key, so a stored nil `parent_id` is emitted as `"parent_id": null` (test-pinned) and a non-nil id survives unchanged. The tree groups by `agent_key(&1, :parent_id)` and treats `by_parent[nil]` as ROOTS (multiple roots supported); a record whose non-nil `parent_id` matches no row in the LOADED PAGE is PROMOTED to a top-level node (normal under paged loading), rendered once and counted in the shown/total label. There is NO dashboard write path (the archive is only read or exported; Review "Resume" only prepares a new evolve form; AgentsLive `parent_id` mutations are display-only ETS views), so stored nil-parent records originate in CORE-written archive data, not in export/UI logic.

## Task Summary Data Flow — SQL-side filtering + debounce optimization

Coordinated design across `live_hooks/`, `live/`, `components/` and the `evo_git` core; the memory profile, retention and export analysis live in `apps/evo_dash/CONTEXT.md` ("Dashboard → Store Data Flow & Memory Profile"), per-subtree detail in `live/CONTEXT.md`, `live_hooks/CONTEXT.md`, `components/CONTEXT.md`.

- **Sidebar summary is SQL-filtered + UNIFIED (single loader)**: `EvoDashWeb.LiveHooks.NodeAware` is the ONE sidebar Active Tasks implementation — `fetch_active_tasks/1` (node-aware: local `TaskRegistry.list_tasks_summary(@active_statuses)` / remote `NodeContext.list_tasks_summary(node, @active_statuses)`; pending-remote guard → `{[], []}`) → `partition_active_tasks/1` (pure) → `assign_active_tasks/1` (`:running_tasks`/`:pending_tasks`). The statuses filter is pushed into SQL (`WHERE status IN (...)`), and `show_review_button?/1` is public + summary-based (reads only `status`/`type`; true for every FINISHED status — `:completed`, `:cancelled`, `:failed` — except repo-less `:reflect`) — no `result` reads. The review ROUTE is wider than the triage BUCKET: `partition_active_tasks/1`'s pending list still keeps only `:completed` + nil `review_status`, so a `:failed` task is reviewable without occupying a "Needs review" slot (§Review-entry matrix in `components/CONTEXT.md`). The load fires only on the connected mount (dead-render skip); the statuses variants `TaskRegistry.list_tasks_summary/1`, `list_tasks_summary_by_path/2` and the node-aware equivalents always SQL-push the filter down.
- **Debounced task reloads (push-based, no poll)**: `{:task_updated, task_id, status, node}` / `{:task_deleted, task_id, node}` → `NodeAware.handle_task_info/2` (returns `{:noreply, socket}` — do NOT re-wrap in LiveViews) node-filters via `event_from_current_node?/2` BEFORE a 300 ms trailing-edge debounce (`:node_aware_reload_tasks`). Each LiveView's own clause does the reload: simple views call `NodeAware.reload_tasks/1`; `projects_live` runs a full reload (project config + notifications + sidebar) and ends with `clear_task_reload_pending/1`; `tasks_live` refreshes through the ASYNC page load (`TasksLive.PageLoad`); `review_live` re-fetches only a node-matching event for THE reviewed task, asynchronously. The same path serves local and remote. `{:vct_updated, node}` is intentionally NOT debounced (only ProjectsLive consumes it, reloading the node's registry in a supervised task behind node + sequence stale guards).
- **`assign_node/2` dedup guard**: tracks `:tasks_node_loaded` (`{current_node_id, current_node}`) and skips the reload when the context is unchanged (prevents the mount double-fetch; pagination/palette push_patches do not re-fetch). Node switches (local↔remote, pending→connected) reload.
- **No dashboard main task list, no periodic polling**: no `Assigns.current_tasks/1` / `assign(:tasks, ...)` sites; `tasks_live` and `agents_live` have no poll timers. Browser notifications use the minimal id-only projection `TaskRegistry.list_task_ids([:completed, :failed, :cancelled])` plus one `get_task_lite/1` per newly-terminal id; a page load is ONE `list_tasks_page/2` of 18-key summary rows, a card's detail arrives lazily on expand (`get_task_lite/2`), and its archive only as bounded pages on explicit disclosure (`list_task_archives/3` plus one `get_agent_archive/3` per shown result).
- **Summary map contract** (from `EvoGit.TaskRegistry.list_tasks_summary`): plain maps with `id, status, review_status, started_at, finished_at, type, project_path, opts, branch_name, model_id, agent_count, base_sha, commit_sha, lease_expires_at, updated_at, error, session_mode` (`opts` = decoded keyword list; `updated_at` = raw fixed-precision ISO string; `error` = structured `kind`/`source`/`message`/`stacktrace` map, `nil` unless `:failed`; `session_mode` = persisted `"oneshot" | "interactive"`, NULL → `"oneshot"`, so reads use `Map.get(task, :session_mode, "oneshot")`). Heavy fields are EXCLUDED — the store projection drops `result`, so evo_dash never reads it from these maps. Components dot-access ONLY contract keys (`Map.get` for optional); a missing key raises KeyError (audit table in `components/CONTEXT.md`).

## Design Conventions — Adwaita token grammar (markup)

Rules for NEW markup (full catalog; sibling records: `components/CONTEXT.md`, `live/system_live/CONTEXT.md`, `live/components/CONTEXT.md`).

- **Tokens over literals**: no raw color literals (`text-red-500`, `bg-white/10`, `bg-black/10`, unmapped `bg-neutral text-neutral-content`) → `text-error`, `bg-error/10`, `bg-base-200`, `bg-base-content/5`; `bg-base-50` is a dead class (only base-100/200/300 exist in both themes).
- **Alpha**: user-relevant text ≥ `/50`, labels/meta ≥ `/60`, small/primary content ≥ `/70`, fold `text-[10px]`/`text-[11px]` to `text-xs`; decorative large icons may keep `/30`–`/40`; empty/loading states get exactly ONE dim layer; small body text prefers `text-base-content/80` over `--color-secondary` (≈3.8:1).
- **Borders/corners**: `border-base-300` on content surfaces (base-200 is ≈1.06:1 invisible there; base-200 only on base-200 chrome); cards/panels `rounded-xl` max (prefer `rounded-lg`), action buttons `rounded-lg`/`rounded-md`, pills `rounded-full`.
- **`*-content` tokens only on solid fills** — on `/10`–`/20` tints use full `text-<semantic>`; `badge-ghost` on a tinted strip → `badge-outline border-base-content/25 text-base-content/80`; the sidebar brand wordmark is plain `text-base-content`.
- Locked single-source schemes — never "fix": `Helpers.task_status_*`/`agent_status_*`/`connection_status_*` (tests pin them), chart `--chart-*` CSS-var strings, `theme_color.ex` palette, the home chat bottom fade.
