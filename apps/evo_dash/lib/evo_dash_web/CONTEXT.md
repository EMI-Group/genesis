# EvoDash Web Interface

## Intent
The web interface layer for the EvoDash Phoenix application — a real-time dashboard for the EvoGit evolutionary software development system. Contains the Phoenix endpoint, router, telemetry supervisor, and delegates interactive UI to LiveView pages, reusable components, and classic controllers in subdirectories.

## Routing Table
- `live/` → Phoenix LiveView pages (Projects, Home, Tasks, Agents, Settings, System, Review, Welcome) + `live/components/` LiveComponents
- `live_hooks/` → On-mount hooks: `SetLocale`, `NodeAware`, `DesktopQuit`, `UpdateStatus`, `Guide` — registered in this order by `EvoDashWeb.live_view/0`
- `components/` → Reusable HEEx UI components and layout templates
- `controllers/` → Classic HTTP controllers and error handlers
- `plugs/` → HTTP middleware plugs (Locale)

### Task Cancellation Model (graceful cancel + force kill)

The backend (`:evo_git`) provides two cancels: `EvoGit.RemoteNode.cancel_task/2` = GRACEFUL (`:pending` → immediate `:cancelled`; `:running` → `:cancelling`, agents messaged to save + exit with a 3-turn grace, then `:cancelled` WITH result/archive preserved) and `EvoGit.RemoteNode.force_kill_task/2` = BRUTAL (kills all agents + wrapper → `:failed`, result nil'd; escalation from `:cancelling`). `EvoDash.NodeContext.cancel_task/2` and `EvoDash.NodeContext.force_kill_task/2` delegate to them (see `./evo_dash/CONTEXT.md`).

Dashboard UX: the task card's inline button is a graceful **Cancel** (`phx-click="open_cancel_modal"`, visible `[:pending, :running]`); the three-dot dropdown has a destructive **Force kill** (`phx-click="open_force_kill_modal"`, visible `[:running, :cancelling]`). TasksLive implements both as two-step server-side confirmation modals (SystemLive warning-modal pattern — see `./live/CONTEXT.md`). The `:cancelling` status is treated as IN-PROGRESS everywhere: violet badge (`Helpers.task_status_badge`), pulsing-dot card label (`task_card_components.ex`), violet sidebar dot (`layouts.ex`), in the sidebar `@active_statuses` + running partition (`NodeAware`), and filterable via the TasksLive status dropdown (pure SQL string filter).

### Agent Status Display (frontend merges `:blocked` into `:pending`)

The frontend presents `:blocked` and `:pending` agents identically as **"Pending"** on all agent status surfaces — to the user, both mean "queued / waiting to be scheduled" (`Helpers.agent_status_label/1` is the single source of label text; the four `agent_status_*` presentation helpers delegate `:blocked` → the `:pending` clause). The backend scheduler keeps `:blocked` and `:pending` distinct. Note: the SystemLive scheduler charts (`live/system_live/charts.ex`) consume the raw `:blocked` COUNT as the slot-saturation "waiting" telemetry series — that is scheduler telemetry, not an agent-status display.

### Task mode resolution & `:reflect` (web↔core contract)

Dashboard combined-mode strings (`"genesis_new"`/`"genesis_existing"`/`"evolve_simple"`/`"custom_agent"`) map to `{task_type, core_mode_string}` in `ProjectsLive.do_task_submit/4` (`projects_live.ex:2123-2133`): `{:genesis, "new"|"existing"}`, `{:evolve, "simple"|"custom"}` (unknown strings fall back to `{:evolve, "simple"}`). The core `EvoGit.TaskRegistry.RuntimeOpts.mode_atom/2` (`apps/evo_git/lib/evo_git/task_registry/runtime_opts.ex:124-125`) dispatches to `genesis_mode_atom/1` (`"new"`/`"existing"`) or `evolution_mode_atom/1` (`"simple"`/`"custom"` — `"custom"` IS accepted, runtime_opts.ex:98-99). Unknown evolution modes raise `ArgumentError` (runtime_opts.ex:101-102); `:genesis` with mode `"custom"` raises "custom mode is evolve-only" (runtime_opts.ex:110-112).

**:reflect (repo-less chat) facts**: reflect tasks carry NO `:path` in opts and run with nil `project_path`; result shape `{:ok, %{result: <text>, commit_sha: nil, branch_name: nil, tag: nil}}`. `:reflect` IS in `EvoGit.Store.Codec` `@known_atoms` (store/codec.ex:217-218). `TaskExecutor.execute_task(:reflect, ...)` routes directly to `Runtime.SelfReflective.run`, deliberately bypassing `build_common_runtime_opts` (which `Keyword.fetch!(:path)`-raises) — `RuntimeOpts.mode_atom/2` needs no reflect clause. Full chat/send-flow detail: `live/home_live/CONTEXT.md`; core agent/runtime: `apps/evo_git/CONTEXT.md` "Self-Reflective Agent (repo-less)".

## Constraints
- All web modules use `use EvoDashWeb, <role>` as their entrypoint — do not bypass the shared `__using__` macro.
- New interactive pages should be LiveViews in `live/`, not controllers in `controllers/`.
- Subdirectory naming conventions: `<name>_live.ex` for LiveViews, `<name>_components.ex` for component modules, `<name>_controller.ex` for controllers.
- Static assets served from `priv/static` under paths defined in `EvoDashWeb.static_paths/0`.
- Styling is Tailwind CSS + daisyUI throughout.
- **Professional design language** (Settings, Tasks, Review, System pages): compact, dense, "power-tool" aesthetic inspired by VS Code / GitHub — `rounded-lg`/`rounded-md` radii (no `rounded-3xl`/`rounded-2xl` large cards), subtle borders, restrained color, no gradient hero boxes or decorative blurs. Settings uses one-config-value-per-full-width-row layout; the config file path is shown at the top with a copy-to-clipboard button (`ClipboardCopy` hook).
- **`try/rescue` is an anti-pattern here.** Do NOT wrap config/core-value loading (`EvoGit.Config.*`, `EvoGit.AgentScheduler.*`, `EvoGit.SystemCheck.*`) in `try/rescue` — if these crash, the LiveView SHOULD crash truthfully so the real error is visible (displaying a wrong default like `%{}`, `false`, or `100_000` is worse than a visible crash). The only accepted `try/rescue` use is: genuinely untrusted external execution like `System.cmd` running user-defined shell commands (`ProjectsLive`). Every retained `try/rescue` MUST carry an inline justification comment. For converting untrusted strings to atoms, use whitelist `Map` lookups (`Map.get/2`/`Map.fetch/2`) — never bare `String.to_existing_atom/1` on client input, and never `String.to_atom/1` (atom-table exhaustion DoS risk).

## Known Issues — Task Archive Display (archive_components.ex / review_components.ex / archive_helpers.ex)

Current bugs/gotchas verified against the code (core semantics in `apps/evo_git/CONTEXT.md` "Archive record — exact structure & crash semantics"):

- **Crashed/failed/aborted agents are NEVER in `archive_metadata`.** The core writes an archive record only when `complete_task` runs with `archive && base_commit`, collected only on successful root completion (`{:ok, %EvoGit.Agent.Result{}}`); records have no status/outcome field. The dashboard archive tree therefore shows only completed agents — a crashed agent's failure is visible only via the task-level status badge. `archive_details`/`archive_review_section` render nothing when the root never completed.
- **Per-agent token/cost tiles display 0 / $0.000000 after a DB round-trip.** `encode_archive/decode_archive` is plain `Jason.encode/decode` (no key re-atomization) — records arrive STRING-keyed, including the nested `usage` sub-map. `ArchiveHelpers.normalize_agent_keys/1` whitelist-converts only TOP-LEVEL keys, so `@agent[:usage][:input_tokens]` (archive_components.ex:148, review_components.ex:214) hits string keys → `nil` → `|| 0` → renders "0". The JSON export is NOT affected — it dumps raw values.
- **Per-agent Cost tile is always $0.000000 even with atom keys**: it reads `@agent[:usage][:cost]` (archive_components.ex:165) but the core's archive usage map has no `cost` key — it writes `input_cost`/`output_cost`/`total_cost` (core `complete_task.ex` `format_usage_for_archive/1`). Fix: read `total_cost` or normalize the nested usage map.
- **Task-level totals come from `TaskInfo.usage`** (a `%EvoGit.Agent.Usage{}` struct, atom-keyed after `decode_usage` — works), NOT from summing archive records; evo_dash never aggregates per-agent usages. Export envelope carries both: `usage` (task-level) + `archive_records` (per-agent, raw).
- **Where archive UI renders**: (1) Tasks page expanded task card (`tasks_live.ex:166` → `task_card_components.ex:386-391`), (2) Review page "Archive" tab (`review_live.ex:154-165` → `review_components.ex`). The Projects page task list strips `archive_metadata` (`projects_live/assigns.ex:130`) and `EvoDash.NodeContext.list_tasks_summary` omits it — sidebar lists never show it.
- **ArchiveHelpers guardrails**: `build_archive_tree/1` and `build_archive_tree_for_review/1` use a visited-set + `agent_id` nil/"" filter to survive cyclic/self-referential or string-keyed data (pinned by `test/evo_dash_web/components/archive_tree_test.exs` and `review_live_test.exs`).
- **nil `parent_id` is preserved end-to-end — the dashboard can neither drop it nor invent it.** Export keeps every map key (`Map.new(map, fn {k,v} -> {to_string(k), ...} end)`), so a stored nil `parent_id` is emitted as `"parent_id": null` (test-pinned) and a stored non-nil id survives unchanged (no key rename, no struct mismatch). The tree groups records by `agent_key(&1, :parent_id)` and treats `by_parent[nil]` as ROOTS — multiple roots are fully supported, each nil-parent record renders as its own top-level node. Orphans (non-nil parent_id matching no `agent_id`) never render but remain in JSON + the raw `length(@archive_metadata)` count. There is NO dashboard write path (`archive_metadata` is only read/stripped/exported; Review "Resume" only prepares a new evolve form; AgentsLive `parent_id` mutations are display-only ETS views) — N stored nil-parent records originate in the CORE-written archive data (`CompleteTask.complete/4` agent-state `parent_id`), not in export/UI logic.

## Task Summary Data Flow — SQL-side filtering + debounce optimization

Coordinated design across `live_hooks/`, `live/`, `components/`, and the `evo_git` core. Detailed per-subtree notes in `live/CONTEXT.md`, `live_hooks/CONTEXT.md`, `components/CONTEXT.md`.

- **Sidebar summary is SQL-filtered + UNIFIED (single loader)**: `EvoDashWeb.LiveHooks.NodeAware` is the ONE sidebar Active Tasks implementation — `fetch_active_tasks/1` (node-aware: local `TaskRegistry.list_tasks_summary(@active_statuses)` / remote `NodeContext.list_tasks_summary(node, @active_statuses)` RPC; pending-remote guard → `{[], []}`) → `partition_active_tasks/1` (pure) → `assign_active_tasks/1` (assigns `:running_tasks`/`:pending_tasks`); `load_running_and_pending_tasks/1` delegates. The SQL query pushes the statuses filter down (`WHERE status IN (...)`), skipping finished tasks that can never appear in the sidebar. `show_review_button?/1` is public and column-based (`branch_name`) — NO `result` reads from summary maps. on_mount fires the load ONLY on the connected mount (dead-render skip).
- **Debounced task reloads (push-based, no poll)**: `{:task_updated, task_id, status, node}` / `{:task_deleted, task_id, node}` events → `NodeAware.handle_task_info/2` (returns `{:noreply, socket}` — do NOT re-wrap in LiveViews) applies the node filter via `event_from_current_node?/2` BEFORE a 300ms trailing-edge debounce (`:node_aware_reload_tasks`, bursts coalesced into one reload). The actual reload runs in each LiveView's `handle_info(:node_aware_reload_tasks, socket)` clause: simple views call `NodeAware.reload_tasks(socket)`; `projects_live` runs a custom full reload (project-config refresh + browser notifications + sidebar) and ends with `NodeAware.clear_task_reload_pending(socket)`; `tasks_live` additionally refreshes its page data (`reload_current_page`); `review_live` runs a broadcast-guarded async reload (only a node-matching event for THE reviewed task re-fetches review data via the async `start_async_load/2`, never blocking `handle_params`). The same debounced path serves BOTH local and remote — no poll. `{:recent_projects_updated}` is intentionally NOT debounced.
- **`assign_node/2` dedup guard**: tracks `:tasks_node_loaded` (`{current_node_id, current_node}`); skips the sidebar reload when the resolved node context is unchanged (prevents the mount double-fetch; pagination/palette push_patches do not re-fetch). Node switches (local↔remote, pending→connected) reload.
- **No dashboard main task list**: no `Assigns.current_tasks/1` / `assign(:tasks, ...)` sites. The sidebar (`@running_tasks`/`@pending_tasks`) is statuses-filtered summary maps (no full-row decode; no logs/usage/archive_metadata). Browser notifications use the minimal id-only projection (`TaskRegistry.list_task_ids([:completed, :failed, :cancelled])`) + per-new-id `TaskRegistry.get_task/1`.
- **Summary map contract** (from `EvoGit.TaskRegistry.list_tasks_summary`): plain maps with `id, status, review_status, started_at, finished_at, type, project_path, opts, branch_name, model_id, agent_count, base_sha, commit_sha, lease_expires_at, updated_at` (opts = decoded keyword list; `updated_at` = raw fixed-precision ISO string). Heavy fields EXCLUDED — `result` is deliberately dropped from the projection (`EvoGit.Store` `@summary_columns`/`decode_summary_row`); evo_dash never reads `result` from these maps.
