# EvoDash Web Interface

## Intent
The web interface layer for the EvoDash Phoenix application — a real-time dashboard for the EvoGit evolutionary software development system. Contains the Phoenix endpoint, router, telemetry supervisor, and delegates interactive UI to LiveView pages, reusable components, and classic controllers in subdirectories.

## Routing Table
- `live/` → Phoenix LiveView pages (Dashboard, Agents, Settings, System & Config)
- `live_hooks/` → On-mount hooks: `SetLocale` (locale), `NodeAware` (node-aware dashboard)
- `components/` → Reusable HEEx UI components and layout templates
- `controllers/` → Classic HTTP controllers and error handlers
- `plugs/` → HTTP middleware plugs (Locale)

|--------|------|---------|

| `EvoDashWeb.Gettext` | `gettext.ex` | Gettext backend for i18n (`use Gettext, otp_app: :evo_dash`). Imported via `html_helpers/0` into all LiveViews/components. |
| `EvoDashWeb` | `evo_dash_web.ex` | Shared `__using__` macro dispatching to role-specific `import`s/`use`s. **On-mount hooks**: the `live_view/0` macro registers `EvoDashWeb.LiveHooks.SetLocale` and `EvoDashWeb.LiveHooks.NodeAware`, so ALL LiveViews are locale-set and node-aware by default. |
| `EvoDashWeb.LiveHooks.SetLocale` | `live_hooks/set_locale.ex` | On-mount hook that sets the Gettext locale from the `locale` session/param. |
| `EvoDashWeb.LiveHooks.NodeAware` | `live_hooks/node_aware.ex` | On-mount hook + helpers for **SSH Remote Development** (node-aware dashboard, Phase 2). Sets node-context assigns (`@current_node`, `@current_node_name`, `@current_node_id`, `@remote_targets`, `@connection_statuses`) with safe local defaults and subscribes to the `EvoGit.PubSub` `"remote_connections"` topic. Helpers: `assign_node/2` (reads the `?node=` query param in `handle_params`, resolving a saved+connected target or falling back to local), `handle_node_selected/2` (builds a `push_patch` to update the URL), `handle_connection_status/2`. |

### Subdirectories
| Directory | Purpose |
|-----------|---------|

### LiveView Routes
| Route | LiveView | Purpose |
|-------|----------|---------|
| `GET /` | `DashboardLive` | Unified dashboard — project selector, task form, project settings, task history. URL-based project state via `?project=<path>` query param. |
| `GET /review/:task_id` | `ReviewLive` (`:show`) | Code review page — diff viewer with expandable context, commit list, merge/reject/continue actions. Supports post-merge re-review via persisted SHAs. |
| `GET /review/:task_id/commit/:commit_sha` | `ReviewLive` (`:commit`) | Single-commit inspection — reuses the shared diff viewer component to show changes for one commit. |
| `GET /agents` | `AgentsLive` | Agent tree inspector with real-time hierarchy |
| `GET /settings` | `SettingsLive` | Runtime scheduler configuration |
| `GET /system` | `SystemLive` | Scheduler controls, system controls (restart/stop), system self-check, and usage guides/references |
| `GET /tasks/:task_id/export` | `TaskExportController` (`:export`) | Downloads a task's `archive_metadata` as a JSON file (`archive-<task_id>.json`). Returns 404 when the task or archive data is missing. |

## Constraints
- All web modules use `use EvoDashWeb, <role>` as their entrypoint — do not bypass the shared `__using__` macro.
- New interactive pages should be LiveViews in `live/`, not controllers in `controllers/`.
- Subdirectory naming conventions: `<name>_live.ex` for LiveViews, `<name>_components.ex` for component modules, `<name>_controller.ex` for controllers.
- Static assets served from `priv/static` under paths defined in `EvoDashWeb.static_paths/0`.
- Styling is Tailwind CSS + daisyUI throughout.
- **Professional design language** (Settings, Tasks, Review, System pages): compact, dense, "power-tool" aesthetic inspired by VS Code / GitHub — `rounded-lg`/`rounded-md` radii (no `rounded-3xl`/`rounded-2xl` large cards), subtle borders, restrained color, no gradient hero boxes or decorative blurs. Settings uses one-config-value-per-full-width-row layout; the config file path is shown at the top with a copy-to-clipboard button (`ClipboardCopy` hook).
- **`try/rescue` is an anti-pattern here.** Do NOT wrap config/core-value loading (`EvoGit.Config.*`, `EvoGit.AgentScheduler.*`, `EvoGit.SystemCheck.*`) in `try/rescue` — if these crash, the LiveView SHOULD crash truthfully so the real error is visible (displaying a wrong default like `%{}`, `false`, or `100_000` is worse than a visible crash). The only accepted `try/rescue` uses are: (1) genuinely untrusted external execution like `System.cmd` running user-defined shell commands (`DashboardLive`), and (2) `Lumis.highlight!` per-line in `review_components.ex` (no non-crashing variant exists). Every retained `try/rescue` MUST carry an inline justification comment. For converting untrusted strings to atoms, use whitelist `Map` lookups (`Map.get/2`/`Map.fetch/2`) — never bare `String.to_existing_atom/1` on client input, and never `String.to_atom/1` (atom-table exhaustion DoS risk).

## Known Issues — Task Archive Display (archive_components.ex / review_components.ex / archive_helpers.ex)

Investigated with the core runtime (`apps/evo_git`, see its CONTEXT.md "Archive record — exact structure & crash semantics"). Facts future agents should know:

- **Crashed/failed/aborted agents are NEVER in `archive_metadata`.** The core writes an archive record only when the `complete_task` tool runs with `archive && base_commit`; collection into the result happens only on successful root completion (`{:ok, %EvoGit.Agent.Result{}}`). There is no status/outcome field in records. The dashboard archive tree therefore shows ONLY completed agents — a crashed agent's failure is visible only via the task card's task-level status badge, not per-agent. `archive_details`/`archive_review_section` render nothing for a task whose root never completed (empty state text in `review_live.ex:164-165`).
- **Per-agent token/cost tiles display 0 / $0.000000 after a DB round-trip.** `archive_metadata` is persisted via `EvoGit.Store.Codec.encode_archive/decode_archive` (plain `Jason.encode/decode`, no key re-atomization) — so records arrive in the LiveView as STRING-keyed maps, INCLUDING the nested `usage` sub-map. `ArchiveHelpers.normalize_agent_keys/1` whitelist-converts only TOP-LEVEL keys (`"usage"` → `:usage`), so `@agent[:usage][:input_tokens]` (archive_components.ex:148, review_components.ex:214) hits string keys → `nil` → `|| 0` → renders "0". The grid renders (because `@agent[:usage]` is truthy) but every cell shows 0. The JSON export is NOT affected — it dumps raw values.
- **Per-agent Cost tile is always $0.000000 even with atom keys**: the components read `@agent[:usage][:cost]` but the core's archive usage map has no `cost` key — it writes `input_cost`/`output_cost`/`total_cost` (core `complete_task.ex` `format_usage_for_archive/1`). Fixing this needs either reading `total_cost` or key normalization of the nested usage map.
- **Task-level totals come from `TaskInfo.usage` (a `%EvoGit.Agent.Usage{}` struct, atom-keyed after `decode_usage` reconstruction — works fine), NOT from summing archive records.** The dash app never aggregates per-agent usages (no `Usage.add` in evo_dash). Export envelope carries both: `usage: task.usage` (task-level) + `archive_records` (per-agent, raw).
- **Where archive UI renders**: (1) Tasks page expanded task card (`tasks_live.ex:166` → `task_card_components.ex:386-391` — full tasks with `archive_metadata`), (2) Review page "Archive" tab (`review_live.ex:154-165` → `review_components.ex`). The Dashboard page task list strips `archive_metadata` (`dashboard_live/assigns.ex:130`), and `EvoDash.NodeContext.list_tasks_summary` also omits it — sidebar lists never show it.
- **Export endpoint** (`TaskExportController.export`, `GET /tasks/:task_id/export`): 404 when task missing or `archive_metadata` nil/[]; otherwise envelope `%{task_id, task_type, repo_path, status, started_at, finished_at, agent_count, usage, archive_records}` normalized by `normalize_for_json/1` (structs→maps, DateTime→ISO8601 string, atom keys→strings, tuples→lists, PID/ref/port/fun→`inspect/1` string) and sent as attachment `archive-<task_id>.json`.
- **ArchiveHelpers guardrails**: `build_archive_tree/1` and `build_archive_tree_for_review/1` use a visited-set + `agent_id` nil/"" filter to survive cyclic/self-referential or string-keyed data (pinned by `test/evo_dash_web/components/archive_tree_test.exs` and `review_live_test.exs:144-217`; previously an infinite-recursion/OOM bug).
- **nil `parent_id` is faithfully preserved end-to-end — the dashboard can neither drop it nor invent it.** (1) **Export**: `TaskExportController.normalize_for_json/1` keeps every map key (`Map.new(map, fn {k,v} -> {to_string(k), ...} end)`, task_export_controller.ex:55-57) and nil values pass through the catch-all clause (line 73), so a nil `parent_id` is emitted as `"parent_id": null` — never dropped, never renamed (test-pinned: task_export_controller_test.exs:87 `assert first["parent_id"] == nil`). A stored NON-nil parent_id cannot be lost: no key rename, no struct mismatch (`Map.from_struct` keeps all fields), and `Codec.encode_archive` is plain `Jason.encode` (nil → `null`), `decode_archive` plain `Jason.decode` (no key re-atomization). (2) **Tree**: `build_archive_tree/1` (archive_helpers.ex:47-55) groups records by `agent_key(&1, :parent_id)` (atom-first, string fallback) and treats `by_parent[nil]` as ROOTS — MULTIPLE roots are fully supported (the `Enum.map` at line 54 returns a list; both `ArchiveComponents.archive_tree` archive_components.ex:52-61 and `ReviewComponents.archive_review_section` review_components.ex:118-120 `for`-loop over the roots list). Each nil-parent record renders as its own top-level node; no single-root assumption, no flattening, no dedup — the tree shows exactly N top-level nodes for N stored nil-parent records (minus records with nil/"" `agent_id`, filtered at line 53). (3) **The tree can only HIDE records, never inflate**: records whose non-nil parent_id matches no `agent_id` (orphans) are reachable only via a parent's children lookup, so they never render (but remain in JSON + in the raw `length(@archive_metadata)` count, review_live.ex:85). `build_archive_tree_for_review`'s `_ -> nil` catch-all (line 65-70) would mislabel a non-binary non-nil parent_id as root, but after the JSON DB round-trip parent_id is always a string or nil, so it cannot fire for stored data. (4) **No dashboard write path**: `archive_metadata` is only read/stripped/exported in evo_dash; the sole task-launch entry points (`task_submit` → `TaskRegistry.start_task`, dashboard_live.ex:693; `confirm_extract_skills`, review_live.ex:536) launch a single root task and never touch archive records. The Review "Continue" button (review_live.ex:423-452) only prepares a NEW evolve form (`?resume_from=`), and `AgentsLive`'s `parent_id` mutations (agents_live.ex:374) are display-only in-memory ETS views. Therefore N records with nil `parent_id` in the dashboard/JSON ⇒ exactly N stored records; 10 observed nil-parent records in a Genesis run must originate in the CORE-written archive data (`CompleteTask.complete/4` agent-state parent_id), not in export/UI logic.
