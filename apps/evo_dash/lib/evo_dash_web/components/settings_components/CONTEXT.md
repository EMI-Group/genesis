# SettingsComponents — Sub-Components

## Intent

Sub-component modules extracted from `EvoDashWeb.SettingsComponents` to keep each component focused: `CategoryMetadata` (pure helpers for display names, icons, schema matching, API key hints), `SettingCard` (schema-driven form field component with type-dispatched input controls), `ModelProfilesEditor` (list editor for `[[llm.models]]` profiles with inline edit form), `CustomAgentsEditor` (list editor for `agents.toml` custom agents with inline edit form), `ModelSelectionEditor` (model-selection script editor with contract help + compile-error display), `Sidebar` (settings sidebar with search filter and category navigation), `SearchResults` (search results grouped by category).

## Routing Table

None — leaf directory (seven module files).

## Notes for Agents — Model Profiles Editor: Peak Hours (optional)

The profile edit form (`ModelProfilesEditor.model_profile_edit_form/1`, private) renders an optional **"Peak hours"** section directly under the concurrency field. Each `[[llm.models]]` profile may carry two OPTIONAL fields (absent/nil/empty = disabled; the parse side omits the keys from the profile map so TOML omits them):

- `peak_concurrency` — non-negative int, concurrency used during peak hours (`0` = hard pause — zero LLM slots during peak). `<input type="number" name="peak_concurrency" min="0">`; pre-filled via `profile_param/2` (atom-or-string key tolerant), blank (`""`) when absent.
- `peak_hours` — list of daily time-window maps `[%{start: "HH:MM", end: "HH:MM"}]`, 24h local time. Rendered as indexed rows of `<input type="time">` pairs named `peak_hours[<index>][start]` / `peak_hours[<index>][end]` (Phoenix parses these into the nested map the parse side consumes). Absent/`[]` → a single blank row so users can start adding.

Row events (both buttons `type="button"` so they never submit the form; handlers live in `live/settings_live/`, not in this module): `add_peak_hours_row` (`phx-click="add_peak_hours_row"`, no payload, appends an empty row server-side) and `remove_peak_hours_row` (`phx-click="remove_peak_hours_row"` + `phx-value-index={index}` on a per-row button). After add/remove the server re-renders the edit form pre-filled from file_config.

Pre-fill helpers (private, all nil-safe): `profile_peak_concurrency/1` (→ `""` when absent), `profile_peak_hours/1` (normalizes each window to `%{start: "", end: ""}` strings; single blank row fallback), `peak_window_value/2` (atom-or-string key tolerant), `normalize_peak_window/1`.

**Display gap**: the READ-ONLY profile row (`model_profile_row/1`) shows only the `concurrency` slots badge + generation-params summary (`profile_params_summary/1`) — peak fields (`peak_concurrency`, `peak_hours`, `timezone`) are NOT summarized, so a saved peak config is only visible by re-opening the Edit form. There is also NO dashboard surface anywhere showing the currently-effective concurrency or in/out-of-peak state (SystemLive charts only show the live aggregated `llm_capacity`); the Settings editor itself never misrepresents peak state because it never displays it.

## Notes for Agents — `:list_of_strings` editor (SettingCard)
- `setting_card/1` renders `:list_of_strings` schemas (e.g. `[:sandbox, :write_paths]`) as a list editor: editable text inputs ALL named with the dotted key path (`sandbox.write_paths`) so repeated names submit as a list under one param key, plus per-entry remove buttons (`remove_list_entry` with `phx-value-key_path` + `phx-value-index`) and an "Add path" button (`add_list_entry` with `phx-value-key_path`). All editor buttons are `type="button"` so they never submit the enclosing `save_category`/`save_search` form.
- **Hidden-sentinel semantics (subtle — preserve):** when the value is a SET list (incl. `[]`), a hidden `type="hidden" name={key} value=""` input renders alongside the entry inputs, so a set-but-empty list always submits at least `[""]` → parses to `[]` and is STORED as `[]` (meaningful: replaces built-in defaults with nothing). An ABSENT param (nil/unset value) is the ONLY delete signal. When the value is nil, no sentinel renders — just the "Not set" hint + Add button. Non-list non-nil values normalize to a one-entry list so an invalid config.toml can't crash the render.
- Blank entries are filtered server-side (`ConfigIO.list_of_strings_value/1`) — a trailing empty "add" row never persists as `""`.
- `default_label/1` joins list defaults with `", "` and renders "(none)" for `[]`; nil → "empty".

## Notes for Agents — registering a NEW settings category
Adding a new top-level Settings sidebar category requires touching BOTH sides. The `:appearance` category (`[:appearance, :accent_color]`, declared in the core schema as `type: :string, default: "blue", validation: [in: ~w(blue teal green yellow orange red pink purple brown slate)]`) is the worked example — fully implemented in the Adwaita Batch 2 (this directory + `live/settings_live.ex`); use it as the template:
- **Core schema map** (`:evo_git`): the category list shown in the sidebar is `EvoGit.Config.Schema.schemas_by_category/0` (all 93 schema maps in `apps/evo_git/lib/evo_git/config/schema/definitions.ex`, grouped by their `category:` key) PLUS the two dashboard-only pseudo-categories `:remote_connections`/`:agents` injected in `SettingsLive.mount/3` (settings_live.ex:677-678) with empty schema lists. A genuinely config-backed category is declared in `definitions.ex` with `category: :appearance` (additive-safe — category-count tests in `apps/evo_git/test/evo_git/config/schema_test.exs` pin counts PER CATEGORY, so adding a NEW category is safe; adding keys to an EXISTING category breaks the counts). A dashboard-only pseudo-category works too but must be special-cased in the `SettingsLive` render (settings_live.ex:162 `:remote_connections`, :580 `:agents`) and in `seed_category`/`category_str_to_atom` — NOT the generic `category_section` path.
- **Dashboard metadata** (`CategoryMetadata` in this directory): `category_display_name/1` (category_metadata.ex:19-35), `category_icon/1` (:37-52), and `category_description/1` (:56-101) have NO catch-all clause — a new category atom raises `FunctionClauseError` until a clause is added for each. `:appearance` got `gettext("Appearance")` / `"hero-paint-brush"` / `gettext("Customize the dashboard's accent color.")`. `sort_categories/1` (category_metadata.ex:125-147) has an explicit `order` list (:126-144, missing categories sort last via `|| 99`); `:appearance` is inserted DIRECTLY AFTER `:scheduler` (:129-133) — deliberate: both are app-level "environment" settings (how the machine runs / how the UI looks), as opposed to the behavior-of-agents categories (:user, :git, :sandbox, ...). `category_match_count/3` (:149) is generic.
- **Input rendering** (`SettingCard` in this directory): an enum schema (`type: :atom, validation: [in: [...]]`) renders as a plain `<select>` (setting_card.ex:220-235); `type: :string` + `validation: [in: [...]]` renders as a text input UNLESS special-cased. Two key_path special cases now exist at the top of the form-control div (setting_card.ex:115-168): `[:appearance, :accent_color]` → the swatch picker (see the dedicated section below), `[:llm, :reasoning_effort]` → dropdown. Form inputs are named `Enum.join(schema.key_path, ".")` (dotted, e.g. `appearance.accent_color`) — `ConfigIO.params_to_category_config/3` deep-walks exactly those dotted keys on save.
- **Save round-trip is fully generic** for a config-backed category: `save_category` (settings_live.ex:1012) → `ConfigIO.build_config_from_category_params/4` → `params_to_category_config/3` (config_io.ex:102; `:atom` values via `SettingsUtils.parse_atom/2` whitelisted to `validation[:in]`) → `EvoGit.Config.Schema.validate` → `EvoDash.NodeContext.save_user_config` → `EvoGit.Config.save_user_config/1`. Runtime push happens only for `category in [:scheduler, :llm]` (settings_live.ex:1077). ⚠️ Core gotcha for `:atom` enums: `EvoGit.Config.resolve/0` re-atomizes TOML-read string enums ONLY for hardcoded keys in `EvoGit.Config.atomize_enum_values/1` (config.ex:182-275) — a new `[:appearance, :accent]` :atom key would round-trip as a string with a warning unless a clause is added there; declaring the key `type: :string` + `validation: [in: [...]]` (the `[:llm, :reasoning_effort]` precedent) avoids the core change entirely.

## Notes for Agents — `appearance.accent_color` swatch picker
The `:appearance` category's single key renders as a row of 10 round color-swatch buttons (GNOME/libadwaita palette), not a text input. Mechanism (implemented in the Adwaita Batch 2 — extend, don't reinvent):

- **Special case**: `setting_card/1` checks `@schema.key_path == [:appearance, :accent_color]` at the TOP of the form-control div (setting_card.ex:115-147, BEFORE the `[:llm, :reasoning_effort]` case — the reasoning_effort + generic branches are its `else`). Renders: one hidden `<input type="hidden" name="appearance.accent_color" value={active}>` (so the generic `save_category` flow persists it — `:string` passes through `params_to_category_config/3` raw) + the swatch row.
- **Palette/hexes — single source of truth**: `@accent_palette` module attribute (setting_card.ex:18-29), 10 `{name, hex}` tuples in schema-validation order (which equals app.css order). The NAMES are the config values; the HEXES (blue `#3584e4`, teal `#2190a4`, green `#2ec27e`, yellow `#f5c211`, orange `#ff7800`, red `#e01b24`, pink `#ff61a8`, purple `#9141ac`, brown `#986a44`, slate `#3d3846`) must stay in sync with `assets/css/app.css` (read-only source of truth for the swatch backgrounds). Public helpers: `accent_palette/0`, `accent_name?/1` (whitelist check used by SettingsLive's event handler), `accent_active/2` (nil → schema default `"blue"`; unknown value → `"blue"`), `accent_label/1` (gettext display labels — palette names ARE the config values; zh anchors: 蓝色/青色/绿色/黄色/橙色/红色/粉色/紫色/棕色/石板灰).
- **Interaction mechanism — server-driven draft, NO JS**: each swatch is `<button type="button" phx-click="select_appearance_accent" phx-value-accent={name}>` (type="button" so the enclosing `save_category` form is never submitted). `SettingsLive.handle_event("select_appearance_accent", %{"accent" => accent}, socket)` (settings_live.ex:1220-1233) whitelists via `SettingCard.accent_name?/1` and assigns ONLY the pending `:appearance_accent_draft` string assign (unknown name → error flash). The draft is NOT written to file_config — nothing persists until Save. Active-ring + hidden-input re-render come from the draft threading (below). `accent_check_class/1` picks the check-glyph color: yellow gets `text-black`, the other 9 get `text-white` (contrast on the light swatch).
- **Draft threading**: `category_section/1` gained optional `attr(:appearance_accent_draft, :string, default: nil)` (settings_components.ex:59-62); the generic "Other categories" card loop passes `value={card_value(@file_config, schema, @appearance_accent_draft)}` (settings_components.ex:807). `card_value(file_config, schema, draft)` (private, settings_components.ex:876-889) returns the draft ONLY for key_path `[:appearance, :accent_color]` when the draft is a binary, else `get_in(file_config, schema.key_path)` — every other schema is untouched. The `:appearance` category is NOT `:llm`/`:sandbox`, so it flows through that generic loop; the LLM flat-card, sandbox sub-category, and SearchResults sites pass raw `get_in` and are deliberately NOT draft-aware (SearchResults shows the SAVED value, correct for a search preview). `SettingsLive` threads `appearance_accent_draft={@appearance_accent_draft}` into the `category_section` call (settings_live.ex:649).
- **Draft lifecycle**: cleared (assigned nil) wherever file_config is replaced by an authoritative load so the card always reflects persisted state after any reload: mount (settings_live.ex:736, comment :732-735), `apply_node_data_results` (:1880, comment :1876-1879 — navigation + node-data loads), `save_category`/`save_search` success paths (:1072 / :1164 — the reloaded file_config is authoritative; if the appearance form was submitted the value is already persisted via the hidden input), node switch `handle_info({:node_selected, ...})` (:854, comment :851-853 — a draft picked on one node's config must not leak onto another node's), and `reset_key`.
- **Reset semantics**: the appearance card's reset button is the generic `reset_key` flow — `SearchEvents.handle_reset_key/2` puts `schema.default` ("blue") into file_config, persists, reloads. `SettingsLive.handle_event("reset_key", ...)` (settings_live.ex:1210-1216) wraps it: destructures `{:noreply, socket} = SearchEvents.handle_reset_key(socket, params)` and assigns the draft nil, so a stale draft can never override the reset value on re-render. `handle_reset_key/2` returns `{:noreply, socket}` on BOTH its success and error branches, so the wrapper is safe.

## Constraints
- All component modules use `use EvoDashWeb, :html`.
- Styling is Tailwind CSS + DaisyUI.
- Components are pure functions — they receive assigns and return HEEx markup.
- Follows the project-wide `try/rescue` anti-pattern policy (no defensive rescuing of core runtime calls; whitelist `Map` lookups for atom conversion).
