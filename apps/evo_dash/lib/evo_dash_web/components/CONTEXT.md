# UI Components

## Intent

Reusable UI component modules and layout templates for the EvoDash web interface — the presentation layer, Phoenix function components rendered via HEEx, organized by domain concern.

## Routing Table

- `layouts/` → HTML layout templates (only the root layout shell: meta tags, CSRF, theme persistence).
- `agents_components/` → Agents-page commit-history sub-components (`CommitGraphView` + `commit_graph/geometry.ex`) — full detail: `agents_components/CONTEXT.md`.
- `review_components/` → Review-page sub-components (`DiffViewer`, `Header`, `Actions`, `RepoCards`, `Stats`) + the review-subtree render caps — full detail: `review_components/CONTEXT.md`.
- `settings_components/` → Settings sub-components (`CategoryMetadata`, `SettingCard`, `ProviderProfilesEditor`, `ProviderProfileFields`, legacy `ModelProfilesEditor`, `CustomAgentsEditor`, `CustomToolsPanel`, `ModelSelectionEditor`, `Sidebar`, `SearchResults`), the shared `SaveBar`/`SectionHeader`/`CardShell`/`FormFooter` building blocks, and the Settings pane layout/config-path-footer contract — full detail: `settings_components/CONTEXT.md`.
- `task_card_components/` → the card's helper submodules (`ResultRender`, `Options`, `Repos`, `Archive`, `Errors`, re-exported via `EvoDashWeb.TaskCardComponents` delegates) + the card's SUMMARY-map/`detail` contract and card-scoped caps — full detail: `task_card_components/CONTEXT.md`.
- Narrow-width (mobile) layout conventions — branch-name badge truncation (`ResultRender.branch_badge_class/0`) → `task_card_components/CONTEXT.md`; agent-tree `pl-7 xl:pl-0` indent → `agents_components/CONTEXT.md`.

### Usage Pattern
All component modules use `use EvoDashWeb, :html` (`use Phoenix.Component` + HTML imports); components are invoked as function components:
```heex
<.button phx-click="save">Save</.button>
<.task_card task={@task} />
<.agent_tree agents={@agents} />
<.flash kind={:warning} flash={@flash} />
```

### Theme delivery chain (client-side theme state + server-driven global accent)
- **Theme state is 100% client-side.** `layouts/root.html.heex`'s inline script resolves `localStorage["phx:theme"]` (default `"system"`) via `matchMedia("(prefers-color-scheme: dark)")` into `data-theme` (`"light"`/`"dark"`) + `data-theme-mode` and swaps the favicon/`theme-color` meta; cross-tab `storage` sync and system-mode re-resolve only (full mechanics: parent `lib/evo_dash_web/CONTEXT.md`).
- **Toggle buttons never touch the server**: `theme_toggle_compact/1` / legacy `theme_toggle/1` fire `phx-click={JS.dispatch("phx:set-theme")}` with `data-phx-theme`; Tailwind's `dark:` binds to `@custom-variant dark (&:where([data-theme=dark], [data-theme=dark] *))` and DaisyUI's `themes: false` means custom CSS uses `--color-base-*` + `color-mix`.
- **The global accent IS server-driven**: `EvoDashWeb.LiveHooks.Appearance` resolves `EvoGit.Config.resolve([:appearance, :accent_color])` node-aware through `EvoDash.AccentCache` (local → synchronous resolve; remote → warm cache read, then a stale-guarded async fetch that writes the cache — never an RPC on the render path) and seeds `@accent_color`, which `Layouts.app` (`attr(:accent_color, :string, default: "blue")`) sets as `data-accent-color` on `#app-layout`, activating the ten `[data-accent-color="<name>"]` rules in `app.css`; distinct from ProjectsLive's per-project `--project-accent`/`--project-ring-accent` on `#dashboard-root` (parent `lib/evo_dash_web/CONTEXT.md`).
- **Shell chrome is token-based (Adwaita)**: `#app-layout` + sidebar `bg-base-200`, `#main-scroll`/`main#main-content` `bg-base-100`, body `bg-base-200` — no slate/white literals.

## Constraints

- Every component module **must** use `use EvoDashWeb, :html`.
- Styling is Tailwind CSS + daisyUI — no inline CSS or external stylesheets in components.
- Icons use the Heroicon set via `icon/1` (naming convention: `hero-<name>[-style]`).
- Layout templates live under `layouts/`; only the root layout exists.
- Components are pure functions — assigns in, HEEx out; no side effects or direct LiveView process calls.
- No component here renders a project's CONTEXT.md, the context tree, or a repository file listing; the only tree/graph renderers are `agents_components.ex` `path_tree/1`, the review changed-files sidebar (`review_components/diff_viewer.ex` `file_tree_sidebar/1`, built from a diff, not the repo) and `agents_components/commit_graph_view.ex`; "CONTEXT.md" appears in this layer only as mode copy in `EvoDashWeb.Helpers` (`mode_label/1`, `mode_description/1`, `detect_mode` hints), never as rendered file content.
- Shared cross-component utilities come from `EvoDashWeb.Helpers` (status badges, formatting, `blob_preview/2`/`list_preview/2`, `tip/1`) to avoid duplication between modules.
- **Task cancellation UX (graceful + force kill)** (`task_card_components.ex`): the inline Cancel button is GRACEFUL (`phx-click="open_cancel_modal"`, no `phx-confirm` — the modal confirms), visible `[:pending, :running]` only; the three-dot dropdown adds a `text-error` "Force kill" item (`open_force_kill_modal`, `[:running, :cancelling]`) under a `gettext("Danger zone")` menu-title divider (Delete keeps its `phx-confirm`). `:cancelling` renders as IN-PROGRESS (warning pulsing dot + `gettext("Cancelling…")` through the shared `Helpers.task_status_dot_class/1` / `task_status_tint/1`); `layouts.ex` treats `:cancelling` as running and has NO cancel surface — the Tasks page dropdown is the force-kill surface.
- Desktop-only surfaces stay inert outside the Tauri shell: directory/file pickers render only when `@tauri_detected and !@remote` (`EVOGIT_DESKTOP`-gated in the page), so the headless server shows the manual path inputs.

### `try/rescue` Policy

`try/rescue` is an anti-pattern in these component files.

- **Do NOT** wrap `String.to_existing_atom/1` in `try/rescue`: normalize untrusted DB-sourced data (e.g. agent archive maps after a Jason round-trip) with an explicit **whitelist map lookup** (`@known_agent_keys` in `normalize_agent_keys/1`) and `Map.get/3` defaulting to the original key — no dynamic atom creation, no rescue.
- Any new `try/rescue` MUST carry an inline comment explaining why it is justified.

## Blob & Collection Rendering Caps

No component in this subtree may render an unbounded task blob or collection: a task can carry a 100+ MB `result` and every component here re-executes on EVERY LiveView render (nothing memoizes).

- The two `EvoDashWeb.Helpers` functions are the SINGLE source of previews — never write ad-hoc `String.slice` caps: `blob_preview/2` → `%{text:, truncated?:, total_bytes:}` (UTF-8-safe prefix of at most `limit` BYTES, default `16_384`) and `list_preview/2` → `%{items:, total:, truncated?:}` (at most `limit` leading elements) — both TOTAL (non-binary/non-list → empty preview; a non-integer/negative limit → the default).
- A truncation note renders ONLY when `truncated?: true`; a complete payload renders no note and no cap-related `title`, and a multi-MB string is previewed BEFORE `EvoDash.MarkdownRender.render/1` (never rendered whole).
- The ONLY uncapped payload paths are explicit user actions: the Full Result / Full Options modal bodies (`render_result_full/1` / `render_options_full/1`, `truncate: false`), the public `result_copy_text/1` / `objective_text/1`, and the `TaskExportController` JSON export.

| Site | Cap |
|---|---|
| `archive_components.ex` `archive_tree/1` | `300` records via `ArchiveHelpers.build_tree_capped/2` (`@max_agent_records`), computed ONCE per render, + a "Showing %{shown} of %{total} agent records — export JSON for the full archive" line only when truncated. Paging is the real bound (100 per page); the tree cap is the second safety net |
| `archive_components.ex` `archive_tree_node/1` | `result` `8_192` bytes, `objective` `4_096` bytes, each with its own byte note; the `result` block renders only once the user fetched that agent's entry (`result_loaded?/1`), otherwise "Show result" / a spinner / a retry line |

Task-card cap rows (`@in_card_blob_limit`, `@in_card_log_limit`, `@copy_payload_limit`) live in `task_card_components/CONTEXT.md`; the review-subtree caps (`review_components/header.ex` previews + copy payload, `archive_review_section/1` `300` records, `diff_viewer.ex` `2_000`-line per-file bound, `file_tree_sidebar/1` `500` entries) live in `review_components/CONTEXT.md`.

- `ArchiveHelpers.build_tree_capped(records, max_records \\ 100)` → `%{tree:, total:, shown:, truncated?:}` with `%{agent:, children:}` node maps; `build_review_tree_capped/2` returns the same envelope with `{agent, children}` tuple nodes. Both drop non-map entries, cap the record list BEFORE normalizing/grouping (so per-render cost follows the cap, not the archive size), prefer root records in the slice, keep the cycle-safety visited sets, and count `shown` AFTER building — a record whose `parent_id` is on an unloaded/broken page is PROMOTED to top level as its own root and counts as shown, so the rendered count never loses records.
- `ArchiveComponents.archive_count_line/1` is the ONE count/exhaustion line both archive render sites use (attrs `total` — the LABEL total, i.e. the archive's true size — `first`/`last` — 1-based retained range — `dropped` — rows evicted by the retention window — `more?` — a pager renders — `exhausted?`): `more? or dropped > 0` renders "%{total} agents — showing %{first}–%{last}" (with "(earlier entries omitted; export JSON for the full archive)" when `dropped > 0`), otherwise "%{total} agents", plus a muted "No more archive entries." line when `exhausted?` (that replaces the pager — a short/empty page means the archive is exhausted). It renders ONLY paragraphs; the parents supply layout/spacing.
- `ArchiveComponents.archive_details/1` renders ONE PAGE of the archive plus its own controls: attrs `archive_metadata` (a legacy ATTRIBUTE NAME for the loaded page entries — no `%EvoGit.TaskInfo{}` field or stored blob of that name exists) + `total` (EFFECTIVE paging total, nil → loaded count) / `server_total` (true archive size for the label, nil → effective total) / `dropped` / `exhausted?` / `agent_results` / `loading_more?` / `more_error` / `task_id` / `export_url`; the count line is the shared `<.archive_count_line/>` with bounds from `ArchiveHelpers.retained_page_bounds/3`, "Load more" (`load_more_task_archive`) appears only while `not exhausted? and ArchiveHelpers.more_pages?(loaded, dropped, effective_total)` (NEVER `loaded < total` — that is wrong once rows are evicted), and each agent's heavy `result` is fetched on click (`load_task_archive_agent_result`, `phx-value-agent-id`) — never on render.
- The "Export JSON" link is node-aware — href = `export_url` when supplied (a remote node's `/tasks/<task_id>/export?node=<target_id>`), else `/tasks/<task_id>/export` (local) — and renders only while `task_id` is present.
- Only the CAPPED builders exist: every production render path goes through `build_tree_capped/2` (task card) or `build_review_tree_capped/2` (review tab).
- Archive msgids owned here (keep verbatim for the release-time extraction pass): "Showing %{shown} of %{total} agent records — export JSON for the full archive" (shared by the task-card tree and the review archive section — one msgid, do not split), "%{total} agents — showing %{first}–%{last}" (shared by both archive count lines, keep one msgid), "%{total} agents — showing %{first}–%{last} (earlier entries omitted; export JSON for the full archive)", "%{total} agents", "No more archive entries.", "Load more", "Show result", "Loading result…", "Could not load this agent's result.", "Could not load more archive pages.".
  Task-card msgids ("Showing %{shown} of %{total} bytes", "Showing the last %{shown} of %{total} log entries", "last %{shown} of %{count}", the task-card copy hint) → `task_card_components/CONTEXT.md`; diff/header msgids ("%{count} more lines not shown", "Showing %{shown} of %{total} files", the review copy hint) → `review_components/CONTEXT.md`.
  The copy hint exists as TWO distinct msgids ("… open Full for the complete text" in the task card, "… open the Full view for the complete text" in the review header) — do not merge them.

## Design Notes

### Restrained shell and core controls

`Layouts.app/1` keeps a semibold base-size wordmark and flat tinted active navigation without a selection shadow.
The Assistant link keeps the unchanged `/help` route and the Gettext-wrapped `gettext("Assistant")` label (`hero-chat-bubble-left-right`), sits last after System, keys to `current_page == :help` and threads the current node through `with_node_param/2`; the label is the single rename surface — renaming it never touches the route, the `current_page` key, the icon or node threading.
The chat approval surface belongs to `live/home_live/approval_card.ex`, not this node (`project_components.ex`'s Dev Commands `phx-click="run_command"` is a project shortcut, not command-approval UI).
The shared guide panel in `layouts.ex` renders only when `@guide` exists, is titled "Genesis Guide", shows plain message text, conditionally offers Dismiss when `dismissible` and a node-aware "Go" link when `page` is a binary — guidance/navigation presentation only.
Below `lg` the main content uses `pt-16` to clear the fixed navigation toggle; desktop uses `lg:pt-4`, with the flex/min-height chain and scroll backgrounds unchanged; the fixed configuration notice is viewport-minus-two-rem wide capped at `max-w-sm`, wrapping warning text on an opaque base surface with a subtle shadow.
Shell navigation, branding, toggles, core default buttons, tabs, accordion summaries and notice close buttons use theme-token focus-visible outlines; core notices use one subtle ring, wrapping text and a translated Close label, default core buttons use `rounded-lg` and form labels `text-base-content/70`.

### Task Form — Single-Card Two-Layout Design (`task_form_components.ex`)

The launch panel is ONE card (`.input-card`) containing the objective textarea AND the bottom toolbar (`.input-controls`) as its last element, in normal flow (never `position: fixed`).
The layout is **server-seeded at render + client-driven**: `layout_for/1` computes the initial `data-layout` on `.input-layout` from `@prompt` (public, unit-tested) — `@short_objective_threshold 1200` means `:expanded` when the prompt exceeds 1200 graphemes OR 32 explicit lines, else `:compact` (also for non-binary input); compact auto-grows to ~16 lines while expanded fills the card (`flex: 1`, internal scroll, no max-height — the card's `overflow: hidden` bounds it).
There is NO per-keystroke server event (no `phx-change`/`phx-debounce`; `@task_prompt` changes only via `restore_state`/`task_submit`, and the `phx-update="ignore"` textarea is never clobbered by re-renders; draft persistence is client-side).

### Shared LLM Selection (`llm_selection_components.ex`)

`EvoDashWeb.LLMSelectionComponents.llm_selection/1` is a pure reusable provider-profile/model/discrete-reasoning picker for Projects, Assistant, onboarding and Settings.

Controls carry unique associated labels, native keyboard navigation, `aria-pressed` stop state and translated labels.
`TaskFormComponents.task_form/1` takes the same three projection/spec + three event attrs and renders the picker (`id="task-llm-selection"`) in the toolbar's right cluster (see "Task Form"); with all new attrs empty, `model_profiles` / `selected_model_id` / `show_auto_model_option` preserve legacy behavior unchanged.

## Known Issues

### Command Palette (`project_omnibox`) — client-side wiring

- **Keyboard**: `phx-keydown="palette_keydown"` lives on the search input (`input#palette-search-input` in `palette_menu/1`) — Phoenix fires keydown only when the event TARGET carries the binding (it does not walk ancestors). The input carries both `phx-keydown` and `phx-change="palette_search"` (coexisting; printable keys are no-ops via `handle_palette_key/3`'s catch-all); the `:open_path` input keeps its own `phx-keydown` + `phx-key="Escape"`. Do NOT add `phx-window-keydown` — Enter would activate a project page-wide.
- **VCT-aware project identity**: the palette row and omnibox trigger show the mount `name` (nil/blank → the `point`, then the OS path) with the OS `path` secondary, while the `point` remains the registry identity, the Forget value and a `filter_projects/2` search term.
  `filter_projects/2` matches name, OS path and point (case-insensitive substring; empty query short-circuits to the full list); a mount may point at a missing OS path — the palette never filters on existence and never creates directories — and `ProjectFlow.mount_point_for/2` is the PURE OS-path→`point` lookup over the already-loaded `@projects`; Select buttons stay OS-path-keyed (`phx-value-path={project.path}`) while the Forget button is point-keyed (`phx-value-point={Map.get(project, :point)}`, `phx-stop-propagation`, `aria-label` "Forget <name>") and renders for local AND remote rows.
- **Click-outside**: `phx-click-away="close_project_palette"` is on `.project-palette-overlay`; the backdrop's `phx-click="close_project_palette"` remains as belt-and-braces.
- **Overlay paint**: the legacy `--b1/--b2/--b3` DaisyUI namespace does not exist in the vendored DaisyUI 5 themes, so overlay rules in `app.css` use `color-mix(...)` / `var(--color-base-*)`, and `.dashboard-topbar` carries NO `backdrop-filter` (one would create a containing block trapping the fixed backdrop/overlay to the topbar strip).
- **Latent focus bug (open, benign)**: the `FocusInput` hook re-focuses on `updated()` only when the element HAS class `focus-on-update` (inverted intent) and no markup adds it; benign while morphdom preserves focus.
- **Regression guard**: `project_components_test.exs` pins the search input's `phx-keydown`, the overlay's `phx-click-away` (+ the backdrop's `phx-click`), and trigger rendering.

### Sidebar must stay `overflow-visible` — SSH node-selector dropdown clipping

The sidebar (`layouts.ex`) is a `z-50` stacking context above `#main-scroll` (`z-0`), so its overflowing dropdowns paint above the content — and it must never clip them: the `SidebarCollapse` hook adds `overflow-visible` in BOTH branches and `<aside id="sidebar">` also carries `overflow-visible!` as defense-in-depth (removing either clips the node-selector dropdown `w-72` at the sidebar edge `w-60`/`w-16`); the comment above the `<aside>` documents the same invariant.

### Sidebar bottom-bar dropdowns never auto-close (native `<details>`)

All three bottom-bar dropdowns (`theme_toggle_compact/1`, `language_selector/1`, `EvoDashWeb.NodeSelectorComponent`) are `<details>`-based: the panel opens/closes ONLY on a `<summary>` click, and `SidebarCollapse.applyCollapsed/1` toggles classes but never removes `open`, so collapsing the sidebar leaves an open dropdown floating over content; picking a theme also leaves it open (`phx:set-theme` only re-applies the theme) and picking a language reloads the page. There is NO reusable outside-click-close infra (no generic `details`-close or click-away handler in `app.js`; the old `toggle_dropdown`/`close_parent` JS commands do not exist), and the Projects-page Configure dropdown is a different, page-local server-driven idiom — closing these is JS-side work owned by `apps/evo_dash/assets/`.

- **z-index contract** (do not disturb): sidebar `<aside>` `z-50`; `#main-scroll` `z-0` (stacking context, traps page modals below the sidebar); `.dropdown-content { z-index: 50 !important }` in `app.css`; mobile overlay + config warning banner `z-40`; hamburger `z-50`.
- **`simple_nav` mode** (WelcomeLive) renders branding only — the node selector lives inside the `if !@simple_nav` block.

### `Layouts.app` content background lives on the scroll container (`#main-scroll`)

The page content background is `bg-base-100` on **`#main-scroll`** — the actual scroll container (`flex-1 overflow-auto` inside the fixed `h-dvh` chain `body` / `#app-layout` `bg-base-200` → `#desktop-quit-hook` `flex-1 min-h-0`). It must stay there: a scroll container's own background paints its visible box at every scroll offset, whereas a background on the non-scrolling inner `main#main-content` only paints the first viewport and would reveal the shell's `base-200` as a bottom seam once the page scrolls. `main#main-content` (`flex-1 min-h-0`) keeps a redundant same-color `bg-base-100` and MUST keep `min-h-0` — main being viewport-capped is what makes Projects' expanded task-form pin-to-bottom and Home's internal chat scroll work.

### `phx-click` + JS hook on the same element — double firing

`phx-click` + a `phx-hook` on the SAME element sends BOTH the hook's handling AND the `phx-click` event to the server; don't put both on one element unless a matching `handle_event/3` clause exists.

The three directory-picker "Browse" buttons in `project_components.ex` (`project-path-browse-button`, `new-project-location-browse-button`, `foreign-repo-path-browse-button`) carry ONLY `phx-hook="DirectoryPicker"` — the hook pushes `"directory_pick"`, ProjectsLive runs `EvoDash.DirectoryPicker` and pushes back `picker_result:<picker_id>`; adding `phx-click` there has no clause → `FunctionClauseError` → LiveView crash (pinned by `project_components_test.exs`).

**Remote-node gating**: those buttons render only when `@tauri_detected and !@remote` — the picker runs on the LOCAL dashboard machine, so under a `?node=` context the manual path inputs (`project-path-input`, `new-project-path-input`, `foreign-repo-path-input` with PathAutocomplete) are the fallback. The `remote` attr threads from `project_omnibox/1` into `palette_open_path`/`palette_new_project` and from `RemoteView.top_bar/1` into `project_settings_tab/1` (via the shared `project_settings_body/1`).

## Design Conventions — Adwaita token grammar (markup)

Rules for writing NEW markup in this subtree (full repo-wide catalog: parent `lib/evo_dash_web/CONTEXT.md`):

- **Alpha floor** (base-content on light is the binding constraint): user-relevant text never below `/50`; labels/meta ≥ `/60`; small/primary content ≥ `/70`; fold `text-[10px]`/`text-[11px]` → `text-xs` where feasible; decorative large icons and "·" separators may keep `/30`–`/40`.
- **Hairlines/dividers on flat `bg-base-100` content surfaces** use `border-base-300` (never `border-base-200` — ≈1.06:1 invisible); tinted wells may keep `border-base-200/80`.
- **Corners**: cards/panels `rounded-xl` max (prefer `rounded-lg`); normal action buttons `rounded-lg`/`rounded-md`; only genuine pill/badge elements keep `rounded-full`.
- **`*-content` color tokens are tuned for solid fills** — never `text-*-content` on translucent tints; on `/10`–`/30` tints use `text-error`/`text-warning`/`text-success`, and `-content` only on solid fills.
- **No raw color literals** (`text-red-500`, `bg-white/10`, `bg-black/10`, `bg-neutral text-neutral-content`, `bg-base-50` — the last is a dead class compiling to no fill) → theme tokens (`text-error`, `bg-error/10`, `bg-base-200`, `bg-base-content/5`, …).
- **Empty/loading states**: exactly ONE dim layer (icon and copy should not both sit at floor alpha).
- **Locked contracts — never restyle helper OUTPUTS**: the `EvoDashWeb.Helpers.task_status_*` / `agent_status_*` / `connection_status_*` class helpers, the task-form bottom-toolbar DOM order (attach-kind dropdown | mode+speed capsule | right cluster: custom-agent select? | model capsule | send) + `data-layout`, the `phx-hook`/`phx-click` bindings, and the chart CSS-var strings. Markup class LITERALS may be polished; helper outputs are the single source of truth.
