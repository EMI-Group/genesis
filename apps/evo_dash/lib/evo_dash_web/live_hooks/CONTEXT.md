# LiveHooks — On-Mount Hooks

## Intent

Phoenix LiveView on-mount hooks registered globally by the `live_view/0` macro in `evo_dash_web.ex` (`apps/evo_dash/lib/evo_dash_web.ex:52-57`).
Six hooks — `SetLocale`, `NodeAware`, `Appearance`, `DesktopQuit`, `UpdateStatus`, `Guide` — apply to ALL LiveViews (including Welcome/WelcomeComplete) automatically; no per-LiveView opt-in.
`NodeAware` also owns the shared app-layout sidebar's data loads — the Active Tasks lists and the Conversations (Genesis Assistant session) list.

## Routing Table

None — leaf directory (six module files: `set_locale.ex`, `node_aware.ex`, `appearance.ex`, `desktop_quit.ex`, `update_status.ex`, `guide.ex`).

## API Surface

### `EvoDashWeb.LiveHooks.SetLocale` (`set_locale.ex`)

Restores the Gettext locale from the HTTP session into each LiveView process.

- **Problem**: the `Locale` plug sets `Gettext.put_locale/2` during HTTP requests, but LiveViews run in their own BEAM processes where the process dictionary is empty.
- **Solution**: reads `session["locale"]` on mount and calls `Gettext.put_locale(EvoDashWeb.Gettext, locale)`.
- **Default**: `"en"` when the session carries no locale.
- **Fifteen languages** are supported: ar, de, en, es, fr, id, it, ja, ko, pt, ru, th, vi, zh_CN, zh_HK.

### `EvoDashWeb.LiveHooks.NodeAware` (`node_aware.ex`)

The "spatial glue" for SSH Remote Development node-aware navigation — on-mount setup plus helpers used by LiveViews and the shared layout.

**Async remote connect**: remote-node connections start through `initiate_remote_connect/2` (spawns on `EvoDash.TaskSupervisor`, returns the socket unchanged); never call `EvoDash.NodeContext.connect/1` inline in a LiveView/LiveComponent.
Terminal outcomes arrive ONLY as `"remote_connections"` broadcasts (`{:remote_connection_status, target_id, %{phase:, node:, last_error:, target:, bootstrap_stage:}}`) handled by `handle_connection_status/2`, so `{:ok, _}` results need no socket action.
Only connect FAILURES are self-messaged to the view: `{:remote_connect_result, target_id, {:error, reason}}` (pages must handle it — narrow clause or catch-all — or the remote-connection gate never reconciles) plus `{:node_aware_refresh_connections, target_id}`, which the attached hook consumes via `refresh_remote_assigns/2` to re-derive `:connection_statuses` (and `:remote_status` for the viewed node) on arms that never broadcast.
Both the spawn (`Task.Supervisor.start_child/2`, a `GenServer.call` that exits when the supervisor is down) and the connect call run inside `EvoDash.SafeCall`, so an unreachable/hung target surfaces as `{:error, {:exit, reason}}` (an unexpected return shape as `{:error, {:unexpected_result, value}}`) instead of silently killing the spawned task; `initiate_remote_connect(socket, nil)` is a no-op.

**On-mount setup**:
- `assign_new/3` seeds `:current_node`, `:current_node_name` ("Local"), `:current_node_id`, `:remote_status` with safe local defaults.
- `:remote_targets` / `:connection_statuses` seed from `EvoDash.WorkbenchSidebarCache.get(socket, :remote_context)` (per-transport last-known sidebar cache, `{targets, statuses}`), falling back to `[]` / `%{}`; the dead render issues no registry call, and the connected mount refreshes them asynchronously (see "Async node-context load").
- `:running_tasks` / `:pending_tasks` seed SYNCHRONOUSLY from the `EvoDash.ActiveTasks` hub (`hub_snapshot/2`; empty hub → `[]`).
- on_mount runs BEFORE `handle_params`, so the hub key is the context the page WILL have after `assign_node/2`, resolved from `?node=` by `node_context_from_params/1` (mirrors `assign_node/2`'s resolution: `{nil, node()}` local / `{node_param, remote_node}` connected-remote / `{node_param, node()}` pending), so a local page can never seed from a remote hub key (and vice versa).
- Seeds `:tasks_reload_pending` (`false`), `:tasks_load_seq` (`0`), `:remote_context_seq` (`0`), `:tasks_node_loaded` (`{nil, node()}`, dedup guard seed) and the Conversations state `:session_list` (`[]`), `:session_list_loading` (`false`), `:session_list_error` (`nil`), `:session_list_seq` (`0`).
- Attaches `attach_hook(:node_aware_active_tasks, :handle_info, &handle_info/2)` on BOTH the dead-render and connected paths (same pattern as `DesktopQuit`'s `:handle_event` hook) — it intercepts the async loader messages (see the `handle_info/2` row) and passes everything else through `{:cont, socket}`.
- Subscribes to `EvoGit.PubSub` topics `"remote_connections"` and `"tasks"` on the connected mount only.
- The connected mount spawns the node-context load for EVERY context, plus — for the pure-local context only (`seed_node_id == nil`) — the Active Tasks and Conversations loads; remote/pending pages get those two from `assign_node/2`'s context change.

**Async node-context load** (`request_remote_context_load/1` → `{:node_aware_remote_context, seq, node_id, node, {:ok, {targets, statuses}} | {:error, reason}}`) — the ONLY loader for `@remote_targets` / `@connection_statuses`, spawned once per connected mount and again on `:remote_targets_changed`:
- captures the view pid, node context and next `:remote_context_seq`, bumps the seq assign, and spawns (spawn `SafeCall`-guarded) a task running ONE `EvoDash.SafeCall.run/1` around `{EvoDash.NodeContext.list_targets(), EvoDash.NodeContext.connection_status()}`.
- `connection_status/0` fans out over every live connection manager (`GenServer.call`, own timeout) and can BLOCK or EXIT — `SafeCall` turns either into `{:error, reason}`, and the result message is ALWAYS sent.
- `handle_remote_context_result/2` (public, pure socket-in/out) drops the result when `seq != :remote_context_seq`; on a match it applies `{:ok, {targets, statuses}}`, assigning each field only when it is a list / map respectively (else keeping the last-known value), then caches the pair via `EvoDash.WorkbenchSidebarCache.put(socket, :remote_context, {targets, statuses})`.
- Any other payload (including `{:error, reason}`) leaves the previous assigns untouched — an RPC failure must never blank the node selector.
- The node context is deliberately NOT part of this guard (targets/statuses are node-independent bookkeeping), unlike the sidebar's `{node_id, node}` guard.
- Later changes arrive as `"remote_connections"` broadcasts — there is NO polling.
- Every inline `get_target/1` / `connection_status/1` lookup on the resolution path is `SafeCall`-wrapped with a safe fallback: `safe_get_target/1` degrades a failing registry → `:local`, `remote_status/1` → `%{phase: :disconnected, last_error: nil}`.

**Async sidebar "Active Tasks" load** — `load_running_and_pending_tasks/1`, `assign_active_tasks/1` and `reload_tasks/1` all delegate to the private `request_tasks_load/1`: it captures the view pid, node context and next `:tasks_load_seq` BEFORE spawning, bumps the seq assign, spawns a supervised fetch (spawn `SafeCall`-guarded; if the spawn fails, `:tasks_reload_pending` is cleared because no result will ever arrive), and returns the socket UNCHANGED — the previous sidebar content stays visible until the fresh result arrives (no loading indicator, no clearing on spawn).
The fetch runs inside `EvoDash.SafeCall.run/1`, so a `GenServer.call` timeout / dead store / dead remote node (an EXIT, not a `rescue`-able exception) becomes `{:error, reason}` and the result message is ALWAYS sent.
It is **statuses-filtered**: `fetch_active_tasks/2` runs `TaskRegistry.list_tasks_summary(@active_statuses)` (local) or `EvoDash.NodeContext.list_tasks_summary(current_node, @active_statuses)` (remote RPC) with `@active_statuses = [:running, :pending, :finalizing, :cancelling, :awaiting_input, :pausing, :paused, :completed]` — the SQL `WHERE status IN (...)` skips finished rows that can never appear in the sidebar.
Pending-remote guard: `current_node_id != nil and current_node == node()` → `{[], []}`, so local tasks never leak into a not-yet-connected remote context.
`partition_active_tasks/1` (pure) puts `[:running, :pending, :finalizing, :cancelling, :awaiting_input, :pausing, :paused]` in `running` — `:awaiting_input` is a NON-terminal idle interactive session and the pause pair must stay findable/resumable, so `Layouts` splits sessions into their own group — and in `pending` every `:completed` task with nil `review_status` that passes `show_review_button?/1` (repo-less `:reflect` excluded), sorted `{:desc, DateTime}` by `finished_at || started_at` (both nil → Unix epoch, so the sorter never compares nil).
`show_review_button?/1` is the ROUTE predicate, wider than that bucket: it admits every FINISHED status (`:completed`, `:cancelled`, `:failed`) except repo-less `:reflect`, so a failed or cancelled task links to `/review/<id>` without entering the "Needs review" triage list (the store's composite `:completed` + nil `review_status` + live-branch predicate — §Review-entry matrix in `../components/CONTEXT.md`).
Review candidacy is decided from summary columns alone, deliberately NOT from the result/branch: a task that changed only writable foreign repos is still reviewable.
The tagged message `{:node_aware_active_tasks, seq, node_id, node, {:ok, {running, pending}} | {:error, reason}}` is then sent to the captured pid.
`fetch_active_tasks/2` may EXIT — it is only ever called inside `EvoDash.SafeCall.run/1`; `fetch_active_tasks/1` is the socket wrapper.

**Connected-mount LOCAL fetch is UNCONDITIONAL** — `on_mount/4` spawns it on every connected LOCAL mount (`seed_node_id == nil`, the only context with a nil node id).
It is the staleness catch-up: terminal task broadcasts (`{:task_updated, id, :completed|:failed|:cancelled, node}`) are one-shot with no replay and no polling backstop, so a LiveView generation that missed one leaves the hub warm-but-stale; the sync hub seed still paints the first render blink-free and the stale-guarded fresh result then assigns and writes the hub back.
Remote/pending pages never fetch on mount (it would query pre-`assign_node` local assigns AND double-fetch the guaranteed `assign_node` reload); their context-change reload fires the one correct fetch, and a warm remote hub / `WorkbenchSidebarCache` entry makes that first render instant.

**Stale-guard** (`handle_tasks_result/2` — public pure socket-in/out seam, called by the attached `handle_info/2` hook): drops the result (socket unchanged) when `node_id != :current_node_id`, `node != :current_node` (a node switch mid-flight), or `seq != :tasks_load_seq` (a newer load was spawned); a dropped result leaves `:tasks_reload_pending` to the newer request.
On a match it first clears `:tasks_reload_pending` (BOTH outcomes — the flag gates the debounce, so a failed load must not wedge every later reload), then applies the payload:
- `{:ok, {running, pending}}` → sanitize, `EvoDash.ActiveTasks.put/4` (keyed by the message's own `node_id`/`node`, the authoritative context of the fetch), then assign `:running_tasks` / `:pending_tasks`.
- `{:error, reason}` → NO assign and NO hub write: the sidebar KEEPS its last-known content instead of collapsing to empty. Never raises, never logs a user-facing error.
- any other payload shape (defensive) → leaves BOTH lists untouched; a legacy bare `{running, pending}` payload is still applied.
Stale/dropped results never write the hub.
**Sanitized task lists**: both the hub read (`hub_snapshot/2`) and the async apply (`write_active_tasks/5`, BEFORE the hub write AND the assign) run `running`/`pending` through `sanitize_tasks/1` (only `is_map/1` entries; a non-list → `[]`), because `EvoDash.ActiveTasks` is shape-agnostic and lives outside this node — a non-map entry would crash `Layouts.app/1` with a `BadMapError` in `group_tasks_by_project/2` and poison the hub for later mounts. Well-formed summary maps pass through unchanged.

**Async sidebar "Conversations" load** — the shared sidebar's Conversations section (`EvoDashWeb.HomeLive.SessionList.session_list/1`, below Active Tasks on EVERY page) follows the same async / stale-guarded / exit-safe pattern and local-vs-remote rule as Active Tasks.
- `request_session_list_load/1` is the hook's single spawn site: a connected socket delegates the whole contract to `EvoDashWeb.HomeLive.SessionList.spawn_load(socket, node)` (seq bump, `:session_list_loading` / `:session_list_error`, `SafeCall.start/4` load, NESTED report `{{:session_list_loaded, seq, node}, result}`); the dead render is a no-op; when `EvoDashWeb.RemoteGateComponents.gate_active?/1` is true it assigns an EMPTY list with a bumped seq instead of fetching.
- Three request sites: the connected LOCAL mount (`seed_node_id == nil`), `assign_node/2`'s context change (a remote page must show the REMOTE node's sessions), and every `:node_aware_reload_tasks` debounce.
- The attached hook intercepts `{{:session_list_loaded, seq, node}, result}` (the tag is NESTED in the message's first element) and returns `{:halt, SessionList.applied(socket, seq, node, result)}`, which owns the seq (`:session_list_seq`) + node (`:current_node`) stale guards and the loading/error bookkeeping: a matching success replaces `:session_list`, a matching error records `:session_list_error` while keeping the shown rows, and a matching result always clears `:session_list_loading`.
- No polling; the Assistant may request a page-local refresh through `SessionList.spawn_load/2` after adopting or closing a session.

**Debounced task reload** (trailing-edge 300 ms, node-filtered): `handle_task_info/2` routes `"tasks"` broadcasts through `debounce_task_reload/1`, coalescing bursts into one trailing-edge reload.
- **Event contract** (from `:evo_git` on `EvoGit.PubSub` topic `"tasks"`): `{:task_updated, task_id, status, node}` (status atom `:pending|:running|:finalizing|:cancelling|:completed|:failed|:cancelled`, or `nil` for review-only mutations) and `{:task_deleted, task_id, node}`.
- **Node filter**: every event carries the publishing BEAM node atom and only updates the UI when it matches the viewed node identity (`event_from_current_node?/2`: local → `node()`, remote → the daemon's node atom). Foreign-node events are dropped in `handle_task_info/2` BEFORE the debounce is scheduled — socket unchanged, `:tasks_reload_pending` NOT set, no `:node_aware_reload_tasks` message — protecting every page reload and ProjectsLive's browser-notification diff from cross-node leakage.
- `debounce_task_reload/1`: while `:tasks_reload_pending` is truthy the broadcast is dropped; otherwise it schedules `Process.send_after(self(), :node_aware_reload_tasks, debounce_ms)` and sets the flag. `debounce_ms` is resolved AT CALL TIME from `:node_aware_reload_debounce_ms` (`Application.get_env(:evo_dash, :node_aware_reload_debounce_ms, 300)` — test seam, 300 ms in production).
- `reload_tasks/1` spawns the async sidebar load then clears `:tasks_reload_pending`; LiveViews handle the message with `handle_info(:node_aware_reload_tasks, socket)` → `{:noreply, NodeAware.reload_tasks(socket)}`.
- **Per-LiveView handlers** (all route `{:task_updated, _, _, _}` / `{:task_deleted, _, _}` into `handle_task_info/2` first, so the node filter applies): TasksLive = async page load + sidebar + clear-pending; ProjectsLive = CUSTOM: project-settings refresh when its panel is open + local-only browser-notification diff (`list_task_ids([:completed, :failed, :cancelled])` + per-new-id `get_task/1`) + `load_running_and_pending_tasks/1` + `clear_task_reload_pending/1` (never `reload_tasks/1`); ReviewLive = sidebar always + broadcast-guarded async review reload ONLY when the broadcast's task id matches the reviewed task; AgentsLive, SettingsLive, SystemLive = sidebar only.

**`assign_node/2,3` dedup guard** (`:tasks_node_loaded`): after the node-context `case` assigns `:current_node` / `:current_node_id` / `:current_node_name` / `:remote_status`, `context = {current_node_id, current_node}`; when it equals `:tasks_node_loaded` the socket is returned without reloading, otherwise it triggers the ASYNC sidebar AND Conversations loads and records the context.
Node switches (local↔remote, pending→connected) reload since the tuple differs, and the stale-guard drops in-flight results from the previous context.
on_mount seeds the guard with `{nil, node()}`, so a local page's first `handle_params` does not double-fetch what the connected-mount local fetch already loaded; a remote/pending page's resolved context differs, so its one correct remote fetch fires.
`assign_node(socket, params, preserve_unresolved?: true)` — used by `projects_live.ex` and `home_live/session_resolution.ex` — marks an unresolved-but-requested `?node=` id as `%{phase: :error, error: :not_found}` instead of silently falling back to local; every other unknown id resolves to local.

**Review-action refresh (`EvoDash.ActiveTasks.invalidate/2`)** — a review-status mutation (merge/reject/resume/ignore success paths in `review_live.ex`, plus auto-resolve's `:continued` marking in `ReviewLive.MergeCheck.handle_auto_resolve/1`) removes the task from the sidebar's pending-review partition, so the acting LiveView calls `EvoDash.ActiveTasks.invalidate(current_node_id, current_node)` — the same `{node_id, node}` pair the hub keys on — AFTER `set_review_status` and BEFORE `push_navigate` (shared private `invalidate_active_tasks/1` in `review_live.ex`; `merge_check.ex` calls `invalidate/2` directly).
Deleting that context's snapshot means the destination mount's FIRST PAINT cannot show the pre-action snapshot.
- **Local destination**: the hub key is empty → no stale review candidate on first paint; the unconditional connected-mount local fetch then populates the corrected lists (invalidate is first-paint polish, not the refresh trigger).
- **Remote destination**: the fresh mount seeds `{[], []}` from the empty hub key, but `assign_node/2`'s context-change reload ALWAYS fires (the seeded `{nil, node()}` guard differs from the resolved remote context), so the sidebar is never stranded empty-and-unfetched.
- **Mounted pages** refresh through the core's `{:task_updated, task_id, nil, node}` broadcast → 300 ms debounce → node-filtered reload.
- Partial-failure branches (merge/reject with any failed repo) stay on the page and do NOT invalidate — the broadcast path refreshes them.

**Statuses API**: `EvoGit.TaskRegistry.list_tasks_summary/1` (statuses `\\ []`), `list_tasks_summary_by_path/2`, `EvoDash.NodeContext.list_tasks_summary/2` and `EvoGit.RemoteNode.list_tasks_summary/2` push the statuses filter down to SQL (`WHERE status IN (...)`). Keep using the statuses-filtered form — it is the cheapest sidebar query.

**Node-switch URL rule** — a node switch is view-PRESERVING: `handle_node_selected/2` rebuilds the URL from the page's `@current_path`, so that assign must carry the CURRENT query string (path + `?…`) when the page's state lives there — `TaskCardComponents`-style filter pages keep `/tasks?status=needs_review&session=interactive`, Settings keeps `?category=`, Agents keeps the selected agent.
`node=<id>` is put INTO the existing query string: a previous `node` key is REPLACED (never duplicated), every other pair is kept VERBATIM (the query is spliced as text, never decoded/re-encoded, so an already-encoded value such as `q=needs%20review` survives byte-for-byte), empty segments are dropped (no stray `?`/`&&`), a path with no query becomes exactly `<path>?node=<id>`, and selecting `"local"` REMOVES the `node` key (the bare path when it was the only param).
`handle_connection_status/2` obeys the SAME rule: its transition patch splices `workbench_reconnect_params` + `node` into `@current_path`'s query instead of appending a second `?`, so a filtered `/tasks?status=needs_review` keeps its filter across a connection-status change.

### `EvoDashWeb.LiveHooks.Appearance` (`appearance.ex`)

Global on-mount hook applying the VIEWED node's configured accent color to the app shell; registered AFTER `NodeAware`, BEFORE `DesktopQuit` (`evo_dash_web.ex:54`), with `Guide` LAST.
The local read is `EvoGit.Config.resolve([:appearance, :accent_color])` (schema default `"blue"`, validated against `EvoGit.Config.Schema.Definitions.accent_palette/0` via the compile-time `@known_accents` attribute).
`EvoDashWeb.Layouts.app` declares `attr(:accent_color, :string, default: "blue")` and sets `data-accent-color={@accent_color}` on the `#app-layout` shell, activating the `[data-accent-color="<name>"]` rules in app.css (un-layered author CSS after the daisyUI `@plugin` blocks) that retarget `--color-primary` / `--color-accent` within that subtree.

- **Per-node accent cache (`EvoDash.AccentCache`, `lib/evo_dash/accent_cache.ex`)** — a boot-created named public ETS table (no process, created by `EvoDash.Application.start/2` next to `:evo_dash_active_tasks`), so a page viewing a node renders ONLY that node's accent from the first paint (no interim local/default color on dead render, connected mount, cross-LiveView navigation or node switch).
  It is keyed by the connection-target id ALONE (`nil` = local) — NOT `{node_id, node}` like the ActiveTasks hub — because the accent is a per-target CONFIG value that must hit the same entry across the pending→connected BEAM-node-atom flip.
  API: `get(node_id)` → `{:ok, accent} | :empty`, `put(node_id, accent)`, `reset/0` (test hygiene); every function `:ets.whereis`-guarded, single-object atomic ops, graceful pre-boot degradation.
  There is NO per-key invalidation, TTL or eviction: a warm remote entry is refreshed only when a connected remote re-resolution's async fetch succeeds.
  The LOCAL accent is never cached in production (no `nil`-key write outside tests) — it is re-resolved on each new socket mount / node-context change.
  Values are normalized names (`resolve_accent/1` runs before every write), and only the non-stale apply of a SUCCESSFUL async fetch writes, so a known warm value is never regressed.
- **Seed + attach** (`on_mount/4`): `assign_new(:accent_color, fn -> seed_accent(params["node"]) end)` — a synchronous cache read (never an RPC), so a warm remote/pending page's very first assign is already its own accent while cold/local pages fall back to `"blue"`.
  Then `attach_hook(:appearance_accent, :handle_params, &handle_params/3)` + `attach_hook(:appearance_accent, :handle_info, &handle_info/2)` on EVERY mount path (dead render AND connected — no desktop-mode gate; the async fetch itself is gated on `connected?` inside the interceptor).
  This is the codebase's FIRST `:handle_params` interceptor: no collision, attached hooks run before the LiveView's own `handle_params/3`, and the framework runs them on mount even for views with no own `handle_params` (e.g. WelcomeLive).
- **Node-aware resolution** happens in the `:handle_params` interceptor (which runs after mount on both the dead render and the connected mount, and on every push_patch/push_navigate); modes mirror `NodeAware.assign_node/2` — `{:local, nil}` / `{:pending, node_param}` / `{:remote, node_param, remote_node}`:
  - **Local node** (no `?node=`, `"local"`, or unknown id): SYNCHRONOUS `EvoGit.Config.resolve([:appearance, :accent_color])` — a cheap local file read, so the accent is correct on first paint (no flash).
  - **Remote node** (a connected remote target: `NodeContext.get_target/1` + `connection_status/1` `%{phase: :connected, node: binary}`): the cache is read SYNCHRONOUSLY FIRST (warm → assigned before the first paint; a cold first visit keeps the seed until the async result lands).
    On a connected socket the async fetch is ALWAYS spawned — it heals a cold cache AND refreshes a warm one, so a remote accent change propagates on the next page load: `Task.Supervisor.start_child(EvoDash.TaskSupervisor, ...)` calling `EvoDash.NodeContext.get_resolved_config(remote_node)` (the remote's FULL resolved config, the same RPC SettingsLive uses) → `{:ok, config}` → `accent_from_config/1` → `{:ok, accent}`; any error/exception at the async boundary (rescue with comment — the documented acceptable pattern) → `{:error, reason}`.
    The spawn captures pid + next `:accent_fetch_seq` BEFORE spawning and bumps the seq assign (latest-request-wins), mirroring `request_tasks_load/1` — NEVER an RPC on the render path.
  - **Pending target** (known but not connected): the target's warm cache value is preferred over the local accent (no local-color flash while it connects); a genuinely cold target falls back to the local accent (data still comes from the local node). Pending never spawns a fetch.
  - **Re-resolve trigger**: only when `params["node"]` OR the resolved node mode CHANGED since the last run (tracked in `:accent_node_param` / `:accent_node_mode`), so the initial mount, node switches and a pending→connected transition (NodeAware's `handle_connection_status/2` push_patch re-runs `handle_params` with the same `?node=` but a `{:remote, ...}` mode) all re-resolve while pagination/search push_patches pass through cheaply. Always returns `{:cont, socket}` — the page's own `handle_params` must run regardless.
  - Consequence: a config accent change (on disk or by another tab) is picked up only on the next NEW socket mount (cross-page `push_navigate`) or node-context change — a same-node `push_patch` of an already-mounted page never re-resolves the local accent, and no hook subscribes to a config-reload topic, so an open page never repaints on a config change.
  - **`handle_info` interceptor**: `{:appearance_accent_result, seq, node_param, {:ok, accent} | {:error, reason}}` → `{:halt, handle_accent_result(...)}`; the stale-guard drops the result (socket unchanged, cache untouched) when `seq` != `:accent_fetch_seq` or `node_param` != `:accent_node_param` (node switched mid-flight / newer fetch superseded). A matching `{:ok, accent}` assigns `:accent_color` (normalized via `resolve_accent/1`) AND writes the cache (`EvoDash.AccentCache.put(node_param, accent)` — one fetch serves all later loads); a matching `{:error, _}` is a NO-OP, because a transient RPC failure must never regress a known warm accent (or the seed) to the default. All other messages pass `{:cont, socket}`.
- **No PubSub subscription and no cache invalidation**: `on_mount` + the two interceptors suffice; `EvoDash.AccentCache` has exactly one production writer (the non-stale successful async apply) plus the test-only `reset/0`, and a warm entry heals only on the next mount / node re-resolution.
- **Pure test seams** (`@doc false`): `resolve_accent/1` (whitelist normalization — the `EvoGit.Config.Schema.Definitions.accent_palette/0` names pass, everything else → `"blue"`) and `accent_from_config/1` (`get_in(config, [:appearance, :accent_color])` → normalize; non-map → `"blue"`).
  Bare-socket unit tests drive `on_mount/4` / `handle_params/3` / `handle_info/2` and the pure helpers directly (local params resolve the local config, `"blue"` with no user config file — deterministic in the isolated test env); whole-page `live()` mounts assert `data-accent-color` on `#app-layout`.
  Remote-target tests save a target via `EvoGit.RemoteConnections.save/1` and register the suite-local fake `EvoDashWeb.AppearanceTest.ConnectionManager` (same idiom as `node_aware_test.exs`) in `EvoGit.RemoteConnection.Registry`; a fake whose `:node` is the LOCAL BEAM node makes the supervised fetch resolve the isolated local config (a deterministic SUCCESS path with no new seam), and a nonexistent node fails fast (`:noconnection` → no-op).

### `EvoDashWeb.LiveHooks.UpdateStatus` (`update_status.ex`)

Global on-mount hook bridging the Tauri updater hub (`EvoDash.UpdateStatus`, which broadcasts `{:update_status, state}` on `EvoGit.PubSub` topic `"updates"` from every `handle_cast`). The reference pattern for a global push-based hook:

- `on_mount/4`: `desktop? = UpdateStatus.desktop?()`; seeds `@update_status` via `initial_assign(desktop?, params["node"] != nil)` (the full `UpdateStatus.get()` state ONLY on desktop+local views, `nil` otherwise); calls `maybe_attach(desktop?)`.
- `maybe_attach/2`: when desktop AND `connected?(socket)` → `Phoenix.PubSub.subscribe(EvoGit.PubSub, "updates")` + `attach_hook(:update_status, :handle_info, &handle_info/2)` + `attach_hook(:update_status, :handle_event, &handle_event/3)`. The dead render skips (mirrors NodeAware); non-desktop is a dormant no-op.
- `handle_info` interceptor: `{:update_status, state}` → `{:halt, assign(socket, :update_status, state)}` (attached hooks run BEFORE the LiveView's own `handle_info`); other messages pass `{:cont, socket}`. The broadcast assign is UNCONDITIONAL — only the INITIAL seed is hidden on remote views.
- `handle_event` interceptor: consumes the four JS-hook result events (`update_check_result`, `update_download_result`, `update_apply_confirmed`, `update_apply_failed`) with `{:halt, socket}` so no page sees unhandled-pushEvent warnings; everything else passes `{:cont, socket}`. Check results may auto-request a download via `push_event`, and `update_apply_confirmed` stops the backend through the shared `:evo_dash, :desktop_quit_stop_fun` config seam (default `DesktopQuit.default_stop/0`).
- Because the hook is registered globally, every page receives broadcasts; the shared layout renders the System-nav notification dot from `@update_status` for phases `:available` / `:ready`.

### `EvoDashWeb.LiveHooks.DesktopQuit` (`desktop_quit.ex`)

On-mount hook for the Tauri desktop tray "Quit Genesis" confirm dialog. No subscriptions, no timers, no polling. Seeds `@desktop_quit_confirm` (`false`) and attaches a `:handle_event` interceptor consuming three tray-quit events:

- `desktop_quit_requested` → `{:halt, assign(:desktop_quit_confirm, true)}`. The shared app layout (`EvoDashWeb.Layouts.app`, which every page renders through) shows a warning confirm dialog whenever the assign is true, so the dialog works on ANY page. Its Quit button is the `DesktopQuitConfirm` JS hook (`assets/js/hooks/desktop_quit.js`), which first invokes the Tauri `begin_quit` command (the shell sets its intentional-shutdown flag so its watchdog won't restart the backend) and then pushes `desktop_quit_confirmed`.
- `desktop_quit_cancelled` → assign false + push `"desktop_quit_closed"`.
- `desktop_quit_confirmed` → stop via the `:evo_dash, :desktop_quit_stop_fun` config seam (default `default_stop/0` = spawn + 150 ms delay + `System.stop/0`, so tests inject a fake and the REAL `System.stop/0` never runs in the test VM), assign false + push `"desktop_quit_closed"`.

Handlers are idempotent (`requested` always assigns true, `cancelled` assigns false), and both cancel and confirm push `"desktop_quit_closed"` via `Phoenix.LiveView.push_event/3` to re-arm the JS latch.
No remote-node branch: the tray event only comes from the desktop shell, whose webview serves the LOCAL dashboard VM; outside the Tauri shell the JS listener never fires and the hook stays dormant.

**Delivery contract (latch + dedup + retry + reconnect re-push)**: the JS hook (`assets/js/hooks/desktop_quit.js`) latches every Tauri `quit-requested` event into `_quitPending`, dedups while a quit awaits delivery or the dialog is open, and retries the `desktop_quit_requested` push on rejection (1 s `setTimeout`) plus once more from `reconnected()` when the LiveSocket re-establishes.
The latch exists because `pushEvent` is NOT buffered: while the window sits hidden in the tray, the client-side heartbeat kills the socket and phoenix.js suspends reconnects while the page is hidden (`pageHidden`, resumed only on window show via `visibilitychange`), so `pushHookEvent` rejects with "unable to push hook event. LiveView not connected".
Rust emits `quit-requested` ONCE right after show+focus — i.e. exactly inside that reconnect window (WS open + channel join + server mount + full re-render) — so the latch IS the delivery guarantee.
The latch is released ONLY when the server pushes `desktop_quit_closed` (cancel and confirm handlers); a stale latch would silently dedup every later tray quit.
`reconnected()` fires only when the hook was marked disconnected (socket-error/heartbeat-timeout, the primary scenario — the hook is NOT re-mounted on reconnect, so `mounted()` does not re-run and the Tauri listener survives). Server-side LiveView has NO heartbeat-based socket close — liveness is purely client-side.
Tests (`test/evo_dash_web/live_hooks/desktop_quit_test.exs`) are server-side only (`render_click` + `assert_push_event`) — they pin the `desktop_quit_closed` re-arm contract, idempotency and re-open behaviour, but cannot exercise the JS-side drop/retry.

**No timeout-based force-quit**: the hook handles only quit-requested delivery/latching + the `begin_quit` confirm. There is NO liveness-heartbeat/keeper mechanism and NO guaranteed-exit timer — tray Quit with a healthy backend waits indefinitely for the user's confirmation. The only immediate quit is the backend-already-down path, where no dashboard exists to confirm with and no tasks can be running.

### `EvoDashWeb.LiveHooks.Guide` (`guide.ex`)

Global on-mount hook bridging the core's `guide_user` tool broadcasts to the floating "Genesis Guide" panel in `EvoDashWeb.Layouts.app` (registered LAST in the `live_view/0` macro, after `UpdateStatus`). It only maintains `@guide`; every live page passes `guide={@guide}` through to the layout.

- **PubSub contract**: subscribes to `EvoGit.PubSub` topic `"guides"` on the connected mount only (`maybe_attach/1`, dead-render skip); message shape `{:guide_updated, guide_id, %{message: String.t(), page: String.t() | nil, selector: String.t() | nil, dismissible: boolean}, node()}`.
- **Node filtering**: the attached `handle_info/2` drops foreign-node broadcasts FIRST via the pure `relevant?/2` wrapper over `NodeAware.event_from_current_node?/2` — a guide broadcast on a remote node only surfaces while that node is being viewed.
- **Client-id retention**: `on_mount/4` seeds `@guide` via `assign_new(:guide, fn -> stored_guide(socket) end)` (nil-safe default). Retention is a `:persistent_term` store keyed by a per-tab `guide_client_id` that the `Guide` JS hook (`assets/js/hooks/guide.js`) generates once per page load (sessionStorage-backed) and passes in the LiveSocket connect params (`assets/js/app.js`), read via `client_id/1` from `socket.private[:connect_params]["guide_client_id"]` (atom-key fallback tolerated; nil when absent, e.g. dead render/bare test sockets). `handle_info` persists every accepted guide via `store_guide/2`; because `push_navigate` keeps the same WebSocket connection (and thus the same client id), the destination mount restores both the panel and the highlight.
- **`page` field → user-click "Go" link (NOT auto-navigation)**: the hook itself never navigates. The ONLY consumer of `guide.page` is `Layouts.app`, which renders a `.link navigate={with_node_param(@guide.page, @current_node_id)}` "Go" button when it is a non-nil binary; nothing auto-redirects on a guide broadcast, and the JS hook (`assets/js/hooks/guide.js`) handles only `guide_highlight` / `guide_cleared` (scroll + temporary CSS class — no `location`/history change anywhere). The agent can *offer* a page jump via `guide_user ... page=/path` but cannot force the browser to navigate.
- **Highlight**: when `guide.selector` is a non-nil binary the hook pushes `"guide_highlight"` (`%{selector: selector}`) via `push_event/3`, consumed by the `Guide` JS hook, which re-applies it from its module-level store on navigation.
- **Dismissal**: `handle_event("guide_dismissed", ...)` clears BOTH the `:guide` assign and the retention store (`clear_guide/2` — `:persistent_term.erase` on the client-id key) AND pushes `"guide_cleared"` (`%{}`) so the JS hook drops its highlight store (without it a stale highlight would re-apply after a later navigation), all with `{:halt, socket}`; all other events pass through `{:cont, socket}`.
- **Pure helpers** (`@doc false`, unit-test seams): `relevant?/2` (node-filter decision) and `normalize_guide/2` (defensive normalizer tolerant of atom- AND string-keyed payloads: `message` → binary or `""`, `page` / `selector` → binary or nil, `dismissible` → boolean defaulting to `false`; never raises). Pinned by `test/evo_dash_web/live_hooks/guide_pure_test.exs`, with hook behaviour in `guide_test.exs`.

### Hook registration, process lifetime & reconnection

- **Registration**: all six hooks are registered via `on_mount` in the shared `live_view/0` macro (`apps/evo_dash/lib/evo_dash_web.ex:52-57`) — SetLocale → NodeAware → Appearance → DesktopQuit → UpdateStatus → Guide.
- **Process lifetime**: one LiveView process per connected page session. `on_mount` runs TWICE per page load: the dead render inside the initial HTTP request process (`connected?/1` false → NO PubSub subscriptions, though interceptor attaches and assign seeds still apply) and the connected mount in the NEW LiveView process (`connected?/1` true → subscribe + initial loads). Subscriptions are per-process and die with it (Phoenix PubSub auto-cleans); nothing re-subscribes within a process.
- **Navigation**: `push_patch` (palette/pagination/node switches) re-runs `handle_params/3` on the SAME process — no re-subscription, and `assign_node/2`'s dedup prevents redundant sidebar reloads. `push_navigate` to a DIFFERENT LiveView module (all dashboard routes are distinct modules) spawns a NEW process → full re-mount → re-subscribe; `push_navigate` to the same module keeps the process.
- **Disconnect/reconnect**: on socket close the channel stops the LiveView process (`{:shutdown, :closed}`); on reconnect the client mounts a NEW process → `on_mount` re-runs → re-subscribes. Missed-event catch-up is per-hook reload-on-mount (no cursors/replay): NodeAware re-seeds the sidebar from the hub and its unconditional LOCAL fetch re-queries the DB (remote/pending contexts re-fetch via `assign_node`'s context-change reload), and UpdateStatus re-reads the hub's CURRENT state via `UpdateStatus.get()`.

## Known Issues

- **Narrow re-warm race on review actions (local only, largely theoretical)**: between a review action's `invalidate/2` and the destination mount's hub read, a PRE-action sidebar-fetch result delivered to the still-shutting-down review LiveView could re-warm the hub key with stale data. It requires (a) a sidebar fetch already in flight at the click moment, (b) its pre-action result landing while the navigating review process still lives and its stale-guard still matches, and (c) a LOCAL destination (remote destinations self-heal via `assign_node`'s reload, and a local destination's unconditional mount fetch corrects the lists right after the first paint). Local queries are ~ms, so the overlap is extremely narrow, and the acting LiveView cannot order another process's hub write — deliberately not fixed with tombstone/version machinery. The stale sidebar self-corrects on the next task broadcast or the destination mount's own fetch.
- **A dead store / unreachable remote node degrades silently by design**: loader exits become `{:error, reason}` (`EvoDash.SafeCall`), the pending flag clears, and the sidebar keeps its last-known content — correct (no disappearing data/UI), but a PERMANENTLY broken store therefore shows a stale sidebar with no visible error surface (the dashboard has no banner for it).
- **The sidebar summary fetch is UNBOUNDED in row count.** `@active_statuses` includes `:completed` and the SQL filter is status-only (`Summaries.where_statuses/2`) with no `review_status` filter and no `ORDER BY`/`LIMIT` — every completed task row is materialized and its `opts` decoded, even though `partition_active_tasks/1` then keeps only the `review_status == nil` ones. On a large `tasks.sqlite` this is the heaviest single read the dashboard performs, and it runs on every mount + every 300 ms-debounced task broadcast.
- **The dead render issues NO registry call**: `@remote_targets` / `@connection_statuses` seed from `EvoDash.WorkbenchSidebarCache` (or `[]` / `%{}`) and the connected mount loads them asynchronously (`request_remote_context_load/1`); the sidebar load is gated on `connected?`. The `?node=`-resolution path still calls `get_target/1` / `connection_status/1` synchronously in `handle_params/3`, but `SafeCall`-wrapped — a dead registry degrades to `:local` / `%{phase: :disconnected, last_error: nil}` instead of crashing the mount.
- **`handle_connection_status/2` refreshes `@connection_statuses` synchronously on every `"remote_connections"` broadcast** (`refresh_connection_statuses/1` → `SafeCall`-guarded `EvoDash.NodeContext.connection_status/0`, plus `remote_status/1` for the viewed node) — `GenServer.call`s up to the manager timeout each, in the LiveView process; no DB access, and an exit degrades to "keep the previous statuses" instead of crashing.

## Constraints

- Hooks use `assign_new/3` (safe assigns — first-write-wins).
- Domain logic is delegated to `EvoDash.NodeContext` — hooks are thin wrappers.
- Safe fallbacks everywhere: locale defaults to `"en"`, node resolution falls back to `:local` on all failure paths, node name falls back to "Local".
- **Task reload debounce**: `handle_task_info/2` NEVER reloads synchronously — always `debounce_task_reload/1` → `:node_aware_reload_tasks` (300 ms trailing-edge) → `reload_tasks/1`. LiveViews doing custom reloads must call `clear_task_reload_pending/1` afterwards so the next broadcast can schedule a fresh reload. The same debounced message also refreshes the Conversations list (the attached hook returns `{:cont, request_session_list_load(socket)}`), so the page's own task reload and the Conversations load both run.
- **Sidebar dedup**: `assign_node/2` skips the sidebar + Conversations reloads when `:tasks_node_loaded == {current_node_id, current_node}`. Do not remove the guard without also handling the mount double-fetch it prevents.
- **Statuses-filtered sidebar fetch**: use `EvoGit.TaskRegistry.list_tasks_summary/1` and `EvoDash.NodeContext.list_tasks_summary/2` (via `EvoGit.RemoteNode.list_tasks_summary/2` → `EvoGit.AgentScheduler.RemoteAPI.list_tasks_summary/1`; statuses IN pushed down to SQL). Do NOT revert to unfiltered `/0`/`/1` calls — skipping finished rows in SQL is the whole point.
- **The hook NEVER blocks a LiveView on a store/RPC call**: every loader is spawned on `EvoDash.TaskSupervisor` (spawn itself wrapped in `EvoDash.SafeCall`) and every blocking call inside it runs in `EvoDash.SafeCall.run/1`, so the spawned task always sends a `{:ok, ...} | {:error, reason}` result and can never die silently. Never add a bare `try/rescue`-only boundary around a `GenServer.call`/`:erpc` call here — a call timeout is an EXIT that `rescue` cannot catch.
- **Sidebar loads are ALWAYS async**: `load_running_and_pending_tasks/1`, `assign_active_tasks/1` and `reload_tasks/1` MUST go through the private `request_tasks_load/1` spawner (supervised fetch, `:tasks_load_seq` bump, socket returned unchanged). Do NOT reintroduce synchronous fetch/assign — a remote `:erpc` fetch can block the LiveView for up to 30 s. The result message is `{:node_aware_active_tasks, seq, node_id, node, {:ok, {running, pending}} | {:error, reason}}`; never change its shape without updating the attached `handle_info/2` hook and the `handle_tasks_result/2` stale-guard. The Conversations load follows the same rule: `request_session_list_load/1` MUST go through `SessionList.spawn_load/2`, and its `{{:session_list_loaded, seq, node}, result}` report is consumed only by the attached hook via `SessionList.applied/4`.
- **Loading/pending flags always clear**: `:tasks_reload_pending` clears on EVERY applied sidebar outcome (`{:ok, _}` AND `{:error, _}`) and when the spawn itself fails; an in-flight result for a superseded `seq`/node context leaves the flag to the newer request. A flag that can stick would wedge every later debounced reload.
- **Errors keep the last-known state**: an `{:error, reason}` sidebar result or node-context result NEVER wipes `:running_tasks` / `:pending_tasks`, the hub, `@remote_targets` or `@connection_statuses`.
- **Three result tags, three guards**: `{:node_aware_active_tasks, seq, node_id, node, result}` is guarded by `{node_id, node}` + `seq` (`:tasks_load_seq`); `{:node_aware_remote_context, seq, node_id, node, result}` by `seq` alone (`:remote_context_seq`); `{{:session_list_loaded, seq, node}, result}` by `seq` (`:session_list_seq`) + `node` (`:current_node`) inside `SessionList.applied/4`. All three are consumed by the attached `handle_info/2` hook — never match them by tuple shape in a LiveView.
- **No dead-render registry calls**: do NOT move `list_targets/0` or `connection_status/0` back into `on_mount`'s `assign_new` — they belong to `request_remote_context_load/1` on the connected mount only.
- **Previous sidebar content is kept** until the fresh result arrives (no loading indicator, no clearing on spawn); a dropped/stale result leaves the sidebar untouched. The Conversations section alone has a visible loading/error surface: `spawn_load/2` sets `:session_list_loading` and clears `:session_list_error`, and `SessionList.applied/4` keeps the shown rows and records `:session_list_error` on a matching failure.
- **Sanitize at both sidebar boundaries**: never assign `:running_tasks` / `:pending_tasks` from a raw hub read or async payload — always run the lists through `sanitize_tasks/1`. This module is the ONLY source of those two assigns (verified across `apps/*/lib`).
- **LiveView pages do NOT need to change**: the attached `:handle_info` hook consumes the loader result messages (`{:halt, socket}`) and returns `{:cont, socket}` for every other message — including `:node_aware_reload_tasks`, whose clause only prefixes the Conversations load. LiveViews keep calling `load_running_and_pending_tasks/1` / `assign_active_tasks/1` / `reload_tasks/1` exactly as before.

## Test Strategy (async sidebar load)

`test/evo_dash_web/live_hooks/node_aware_test.exs` is unit-style with bare `%Phoenix.LiveView.Socket{}`s and **resets the shared `EvoDash.ActiveTasks` hub per test in setup** (`EvoDash.ActiveTasks.reset()` — the canonical idiom; the hub is a boot-created named public ETS table owned by the long-lived `EvoDash.Application` process, alive for the whole `mix test` run with a `{nil, node()}` local key shared across ALL suites; reads/writes are direct `:ets` operations, no GenServer).
The hub-seeded on_mount (synchronous per-context seed + the unconditional connected-mount LOCAL fetch) is exercised by calling `on_mount/4` directly on boot-shaped sockets: dead-render `mount_socket/1` (`transport_pid: nil`) and connected `connected_mount_socket/1` (`transport_pid: self()` makes `Phoenix.LiveView.connected?/1` true); boot sockets preset no `:running_tasks` / `:pending_tasks`, so `assign_new` seeds from the hub.
Because the spawned task's captured `view_pid` IS the test process (`EvoDash.TaskSupervisor` runs under `mix test`), tests use the **send-pattern**: `assert_receive {:node_aware_active_tasks, seq, node_id, node, result}` (1000 ms) / `refute_receive` (short timeout) on the payload — never synchronous `assigns` assertions after a load-triggering call (the socket comes back unchanged). `result` is `{:ok, {running, pending}}` on success and `{:error, reason}` when the guarded call exits, so every assertion must unwrap the tag first.
The connected mount also emits ONE `{:node_aware_remote_context, seq, node_id, node, {:ok, {targets, statuses}} | {:error, reason}}` message per mount — assert/receive it alongside the sidebar message, and drive `handle_remote_context_result/2` directly for the seq-guard/apply cases (mirroring the `handle_tasks_result/2` seam tests).
The warm-hub staleness-catch-up regression mounts `on_mount` with a hub snapshot showing a task as `:running` and asserts the fetch still fires and the fresh (empty) result heals both the assigns and the hub.
The **stale-guard** is tested via the public `handle_tasks_result/2` seam (node mismatch dropped, outdated seq dropped, matching case assigns + hub write, stale results leave the hub unwritten); **node-switch dedup** by calling `assign_node/2` twice with the same context and `refute_receive`-ing a second spawn; **exit safety** by exercising the pure seams (an `{:error, reason}` result clears `:tasks_reload_pending` while leaving both lists and the hub untouched, and an `{:error, reason}` node-context result leaves `@remote_targets` / `@connection_statuses` untouched).
A connected LOCAL mount additionally spawns the Conversations load (`SessionList.spawn_load/2`), whose nested-tag report lands in the same captured pid's mailbox; the `SessionList` pure suite (`test/evo_dash_web/live/home_live/session_list_test.exs`) covers the `spawn_load/2` seq/loading bump and the `applied/4` seq + node stale guards.
