# LiveHooks — On-Mount Hooks

## Intent

Phoenix LiveView on-mount hooks registered globally via the `live_view/0` macro in `evo_dash_web.ex` (`apps/evo_dash/lib/evo_dash_web.ex:52-57`). Six hooks — `SetLocale`, `NodeAware`, `Appearance`, `DesktopQuit`, `UpdateStatus`, `Guide` — apply to ALL LiveViews (including Welcome/WelcomeComplete) automatically; no per-LiveView opt-in required.

## Routing Table

None — leaf directory (six module files: `set_locale.ex`, `node_aware.ex`, `appearance.ex`, `desktop_quit.ex`, `update_status.ex`, `guide.ex`).

## API Surface

### `EvoDashWeb.LiveHooks.SetLocale` (`set_locale.ex`)

Restores the Gettext locale from the HTTP session into each LiveView process.

- **Problem**: The `Locale` Plug sets `Gettext.put_locale/2` during HTTP requests, but LiveViews run in separate BEAM processes where the process dictionary is empty.
- **Solution**: Reads `session["locale"]` on mount and calls `Gettext.put_locale(EvoDashWeb.Gettext, locale)`.
- **Default**: Falls back to `"en"` when no locale is in the session.
- **Fifteen languages** are supported: ar, de, en, es, fr, id, it, ja, ko, pt, ru, th, vi, zh_CN, zh_HK.

### `EvoDashWeb.LiveHooks.NodeAware` (`node_aware.ex`)

The "spatial glue" for SSH Remote Development node-aware navigation. Provides on-mount setup and helper functions used by LiveViews and the shared layout.

**On-mount setup**:
- Sets initial node-context assigns via `assign_new/3` with safe local defaults: `@current_node`, `@current_node_name`, `@current_node_id`, `@remote_targets`, `@connection_statuses`. Seeds `:running_tasks`/`:pending_tasks` SYNCHRONOUSLY from the `EvoDash.ActiveTasks` hub (`hub_snapshot/2`; empty hub → `[]`) — on_mount runs BEFORE `handle_params`, so the seed key is the node context the page WILL have after `assign_node/2`: resolved from the page's `?node=` param by `node_context_from_params/1` (mirrors `assign_node/2`'s resolution exactly → `{nil, node()}` local / `{node_param, remote_node}` connected-remote / `{node_param, node()}` pending), so a local page can never seed from a remote hub key (and vice versa). Seeds `:tasks_reload_pending` (`false`, debounce flag), `:tasks_load_seq` (`0`, async-load request sequence), and `:tasks_node_loaded` (`{nil, node()}`, dedup guard seed — prevents the mount double-fetch).
- Attaches `attach_hook(:node_aware_active_tasks, :handle_info, &handle_info/2)` on BOTH the dead-render and connected paths (same pattern as `DesktopQuit`'s `:handle_event` hook) — it intercepts `{:node_aware_active_tasks, ...}` result messages and routes them through the stale-guard; every other message passes through (`{:cont, socket}`), so LiveViews' own `handle_info` clauses are untouched.
- Subscribes to `EvoGit.PubSub` topics `"remote_connections"` and `"tasks"` on the connected mount only; the dead render keeps the hub-seeded assigns and fires no query.

**Async sidebar "Active Tasks" load** — `load_running_and_pending_tasks/1`, `assign_active_tasks/1`, and `reload_tasks/1` all delegate to the private `request_tasks_load/1`, which (1) captures the view pid, the node context (`current_node`/`current_node_id` from the assigns), and the next `:tasks_load_seq` value BEFORE spawning, (2) bumps the `:tasks_load_seq` assign, (3) spawns a supervised fetch on `EvoDash.TaskSupervisor`, and (4) returns the socket UNCHANGED — the previous sidebar content stays visible until the fresh result arrives (no loading indicator, no clearing on spawn). The fetch is **statuses-filtered**: `fetch_active_tasks/2` runs `TaskRegistry.list_tasks_summary(@active_statuses)` (local) or `EvoDash.NodeContext.list_tasks_summary(current_node, @active_statuses)` (remote RPC) with `@active_statuses = [:running, :pending, :finalizing, :cancelling, :completed]` — the SQL `WHERE status IN (...)` skips finished rows that can never appear in the sidebar (running/pending tasks + `:completed` review candidates). Then `partition_active_tasks/1` → sends `{:node_aware_active_tasks, seq, node_id, node, {running, pending}}` to the captured pid. The pending-remote guard (`current_node_id != nil and current_node == node()` → `{[], []}`) keeps local tasks from leaking into a not-yet-connected remote context. The spawned fn never raises — an unexpected fetch failure is rescued at the async boundary to `{[], []}` (mirrors NodeContext's `[]`-on-RPC-failure defensive mode; commented per the try/rescue policy).

**Connected-mount fetch is conditional** — `on_mount/4` spawns this load on the connected mount ONLY when the page's resolved context is a cold LOCAL one (`seed_node_id == nil` and `EvoDash.ActiveTasks.get(nil, node()) == :empty`). Warm local pages and all remote/pending pages render the hub's last-known state instead and stay fresh through the push-based PubSub cycle (task events → 300ms debounce → fetch → apply); `assign_node/2`'s existing context-change reload fires the remote/pending page's one correct fetch (a mount-time fetch would query the pre-`assign_node` local assigns AND double-fetch the guaranteed `assign_node` reload — the mount never double-fetches remote). Every SUCCESSFULLY APPLIED (non-stale) result feeds the hub: `handle_tasks_result/2` calls `EvoDash.ActiveTasks.put/4` (keyed by the message's own `node_id`/`node` — the authoritative context of the fetch) before assigning, so the next remount on that node context seeds instantly (no sidebar collapse/re-pop blink on navigation); stale/dropped results never write.

**Stale-guard** (`handle_tasks_result/2` — public pure socket-in/out seam, called by the attached `handle_info/2` hook): drops the result (socket unchanged) when `node_id` != `:current_node_id`, OR `node` != `:current_node` (the user switched nodes while the fetch was in flight), OR `seq` != the current `:tasks_load_seq` (a newer load was spawned — only the latest request's result is ever applied); otherwise assigns `:running_tasks`/`:pending_tasks` AND writes the hub (`EvoDash.ActiveTasks.put/4`, keyed by the message's own `node_id`/`node` — the authoritative context of the fetch, which the guard just matched). Stale/dropped results never write the hub. `handle_info/2` returns `{:halt, socket}` for the matched message and `{:cont, socket}` for everything else.

**Debounced task reload** (trailing-edge 300ms, node-filtered): `handle_task_info/2` routes the `"tasks"`-topic broadcasts through `debounce_task_reload/1`, coalescing bursts into a single trailing-edge reload:
- **Event contract** (emitted by `:evo_git` on `EvoGit.PubSub` topic `"tasks"`): `{:task_updated, task_id, status, node}` (status = status atom `:pending|:running|:finalizing|:cancelling|:completed|:failed|:cancelled`, or `nil` for review-only mutations) and `{:task_deleted, task_id, node}`.
- **Node-filtering rule**: every event carries the BEAM node atom of the publishing node. An event only triggers UI updates when its `node` matches the currently-viewed node identity (`event_from_current_node?/2` — local viewing → `node()`, remote viewing → the remote daemon's BEAM name atom). Foreign-node events are dropped in `handle_task_info/2` BEFORE the debounce is scheduled — the socket is returned unchanged, `:tasks_reload_pending` is NOT set, and no `:node_aware_reload_tasks` message fires. This protects every page's reload and ProjectsLive's browser-notification diff from cross-node leakage.
- `debounce_task_reload/1`: if `:tasks_reload_pending` is truthy the intermediate broadcast is dropped (socket returned unchanged); otherwise it schedules `Process.send_after(self(), :node_aware_reload_tasks, 300)` and sets the flag to `true`.
- `reload_tasks/1`: spawns the async sidebar load (via `load_running_and_pending_tasks/1`) then clears `:tasks_reload_pending` to `false`. **LiveViews** handle the `:node_aware_reload_tasks` message with a `handle_info(:node_aware_reload_tasks, socket)` clause calling `{:noreply, NodeAware.reload_tasks(socket)}`.
- **Per-LiveView `:node_aware_reload_tasks` handlers** (all route `{:task_updated, _, _, _}` / `{:task_deleted, _, _}` broadcasts into `handle_task_info/2` first, which applies the node filter): TasksLive (tasks_live.ex:542) = page reload (`reload_current_page/1`) + sidebar + clear-pending; ProjectsLive (projects_live.ex:1619) = CUSTOM handler: project-settings refresh if the panel is open + local-only browser-notification diff (`list_task_ids([:completed, :failed, :cancelled])` + per-new-id `get_task/1`) + `load_running_and_pending_tasks/1` + `clear_task_reload_pending/1` (does NOT call `reload_tasks/1`); ReviewLive (review_live.ex:736) = sidebar always + broadcast-guarded review-data async reload ONLY when the broadcast's task id matches the reviewed task id; AgentsLive (agents_live.ex:217), SettingsLive (settings_live.ex:867), SystemLive (system_live.ex:1518) = sidebar only.

**`assign_node/2` dedup guard** (`:tasks_node_loaded`): After the node-context `case` assigns `:current_node`/`:current_node_id`/`:current_node_name`, `assign_node/2` computes `context = {socket.assigns[:current_node_id], socket.assigns[:current_node]}`. If it equals the stored `:tasks_node_loaded`, the socket is returned without reloading the sidebar; otherwise it triggers the ASYNC sidebar load AND records the new context. Node switches (local↔remote, pending→connected) reload since the tuple differs; the stale-guard drops any in-flight result from the previous context. `on_mount` seeds the guard with the LOCAL context `{nil, node()}` so the first `handle_params` → `assign_node/2` on a local page does not double-fetch what the connected-mount cold-local fetch already loaded (or what a warm hub seeded); a REMOTE/pending page's resolved context differs from the seed, so `assign_node/2`'s context-change reload fires that page's one correct remote fetch.

**Review-action cold-mount refresh (`EvoDash.ActiveTasks.invalidate/2`)** — when a review action on a completed task changes the task's review status (merge/reject/resume/ignore success paths in `review_live.ex`, plus auto-resolve's `:continued` marking in `ReviewLive.MergeCheck.handle_auto_resolve/1`), the acted-on task leaves the sidebar's pending-review partition. The acting LiveView calls `EvoDash.ActiveTasks.invalidate(current_node_id, current_node)` — the same `{node_id, node}` pair the hub keys on — immediately AFTER the `set_review_status` call and BEFORE the `push_navigate` (one shared private helper `invalidate_active_tasks/1` in `review_live.ex`; `merge_check.ex` calls `invalidate/2` directly with the same assigns pair). Deleting the acting node context's snapshot makes the destination mount COLD (`get/2` returns `:empty` there), so the existing fetch machinery refreshes the sidebar instead of seeding the pre-action snapshot:
- **Local destination** (`current_node_id` nil): the connected-mount cold-local fetch fires — `on_mount/4` checks `seed_node_id == nil and EvoDash.ActiveTasks.get(nil, node()) == :empty` (node_aware.ex:151) → true → fresh fetch + hub write.
- **Remote destination**: the fresh mount seeds `{[], []}` from the now-empty hub key, but `assign_node/2`'s context-change reload ALWAYS fires on a fresh remote mount — the seeded dedup guard `{nil, node()}` (node_aware.ex:168) differs from the resolved remote context `{node_id, remote_node}` (guard comparison node_aware.ex:444-452) → the sidebar is fetched, never stranded empty-and-unfetched.
- **Mounted pages** (another tab on the same context, or a review action that does NOT navigate): unchanged — the core's `{:task_updated, task_id, nil, node}` broadcast → 300ms trailing-edge debounce → `:node_aware_reload_tasks` path refreshes them (node-filtered).
- **Blink-free**: `invalidate/2` runs ONLY on review-status mutations (status-change success paths that navigate away). Ordinary non-mutating navigation still seeds instantly from a warm hub (on_mount seeding unchanged — a direct `:ets` read of the boot-created table), and partial-failure branches (merge/reject with any failed repo) that stay on the page do NOT invalidate — a still-mounted page refreshes via the broadcast + debounce path.

## Known Issues

- **Narrow re-warm race on review actions (local only, largely theoretical)**: between a review action's `invalidate/2` and the destination mount's hub read, a PRE-action sidebar-fetch result delivered to the still-shutting-down review LiveView process could re-warm the hub key with stale data. The full race requires (a) a sidebar fetch already in flight at the click moment (a task broadcast within the prior ~1s whose debounced reload has not yet completed), (b) its pre-action result landing inside the brief window while the navigating review process still lives and its stale-guard still matches (same node context, same `:tasks_load_seq`), and (c) a LOCAL destination (remote destinations self-heal — a fresh remote mount's `assign_node` context-change reload always fires). Local sidebar queries are ~ms, so (a)+(b) overlap is extremely narrow. Not closed by a trivial ordering change (the hub write comes from an async result in another process — the acting LiveView cannot order it); deliberately NOT fixed with tombstone/version machinery per review directive. The stale sidebar self-corrects on the next task broadcast (300ms debounce → reload).

**Statuses API**: the statuses forms of `list_tasks_summary` exist — `EvoGit.TaskRegistry.list_tasks_summary/1` (`task_registry.ex:116`, statuses \\ []), `list_tasks_summary_by_path/2`, `EvoDash.NodeContext.list_tasks_summary/2` and `EvoGit.RemoteNode.list_tasks_summary/2` (`remote_node.ex:358`) — with the statuses filter SQL-pushed-down (`WHERE status IN (...)`) all the way to the Store. Keep using the statuses-filtered form; it is the cheapest sidebar query.

### `EvoDashWeb.LiveHooks.Appearance` (`appearance.ex`)

Global on-mount hook that applies the user-configured accent color to the app shell. Registered AFTER `NodeAware`, BEFORE `DesktopQuit` in the `live_view/0` macro (`evo_dash_web.ex:54`) — Guide stays LAST. Reads `EvoGit.Config.resolve([:appearance, :accent_color])` (schema default `"blue"`, validated to one of the ten CSS-known names) and seeds `@accent_color`; `EvoDashWeb.Layouts.app` declares `attr(:accent_color, :string, default: "blue")` and sets `data-accent-color={@accent_color}` on the `#app-layout` shell div, activating the ten `[data-accent-color="<name>"]` override rules in app.css (un-layered author CSS after the daisyUI theme `@plugin` blocks) that retarget `--color-primary`/`--color-accent` within the shell subtree.

- **Seed + attach** (`on_mount/4`): `assign_new(:accent_color, fn -> "blue" end)` (never raises on bare sockets / absent config) then `attach_hook(:appearance_accent, :handle_params, &handle_params/3)` + `attach_hook(:appearance_accent, :handle_info, &handle_info/2)` on EVERY mount path (dead render AND connected — no desktop-mode gate; the async remote fetch itself is gated on `connected?` inside the interceptor). The FIRST hook to attach a `:handle_params` interceptor in the codebase (no collision; attached hooks run before the LiveView's own `handle_params/3`).
- **Node-aware resolution** happens in the `:handle_params` interceptor (handle_params runs after mount on BOTH the dead render and the connected mount, and on every push_patch/push_navigate):
  - **Local node** (no `?node=`, `"local"`, unknown id, or known-but-not-yet-connected target): SYNCHRONOUS `EvoGit.Config.resolve([:appearance, :accent_color])` — a local file read, cheap on every mount, so the accent is correct on first paint (no flash).
  - **Remote node** (`params["node"]` naming a connected `genesis_remote` target — presence heuristic + `NodeContext.get_target/1` + `connection_status/1` `%{phase: :connected, node: binary}`, mirroring `NodeAware`'s resolution): ASYNC via `Task.Supervisor.start_child(EvoDash.TaskSupervisor, ...)` calling `EvoDash.NodeContext.get_resolved_config(remote_node)` (the remote's FULL resolved config — the same RPC SettingsLive uses; `{:ok, config}` → `accent_from_config/1`, anything else → `"blue"`, rescue at the async boundary) → `send(pid, {:appearance_accent_result, seq, node_param, accent})`. The seed stays until the result lands — NEVER an RPC on the render path. The spawn captures pid + next `:accent_fetch_seq` BEFORE spawning and bumps the seq assign (latest-request-wins), mirroring `request_tasks_load/1`.
  - **Re-resolve trigger**: re-resolves only when `params["node"]` OR the resolved node mode (`:local` vs `{:remote, node_atom}`) CHANGED since the last run (tracked in `:accent_node_param`/`:accent_node_mode` assigns). Initial mount, node switches, AND a pending→connected transition (NodeAware's `handle_connection_status/2` push_patch re-runs `handle_params` with the same `?node=` but the mode now resolves remote) all re-resolve; pagination/search push_patches that leave the node context untouched pass through cheaply. Always returns `{:cont, socket}` — the page's own `handle_params` (assign_node etc.) must run regardless.
  - **`handle_info` interceptor**: `{:appearance_accent_result, seq, node_param, accent}` → `{:halt, handle_accent_result(...)}` — the stale-guard drops the result when `seq` != `:accent_fetch_seq` or `node_param` != `:accent_node_param` (node switched mid-flight / newer fetch superseded); a matching result assigns `:accent_color` (normalized via `resolve_accent/1`). All other messages pass `{:cont, socket}`.
- **No PubSub subscription**: the accent is static per node until the config changes (which requires a page reload anyway); `on_mount` + the two interceptors suffice.
- **Pure test seams** (`@doc false`): `resolve_accent/1` (whitelist normalization — the ten known names pass, everything else → `"blue"`) and `accent_from_config/1` (`get_in(config, [:appearance, :accent_color])` → normalize; non-map → `"blue"`). Bare-socket unit tests drive `on_mount/4` / `handle_params/3` (local params resolve the local config, which is `"blue"` with no user config file — deterministic in the isolated test env) and the pure helpers directly.

### `EvoDashWeb.LiveHooks.UpdateStatus` (`update_status.ex`)

Global on-mount hook bridging the Tauri updater hub (`EvoDash.UpdateStatus` GenServer, which broadcasts `{:update_status, state}` on `EvoGit.PubSub` topic `"updates"` from every `handle_cast` transition, `apps/evo_dash/lib/evo_dash/update_status.ex:236`). The reference pattern for a global push-based hook:

- `on_mount/4` (update_status.ex:46-55): computes `desktop? = UpdateStatus.desktop?()`; seeds `@update_status` via `initial_assign(desktop?, params["node"] != nil)` (update_status.ex:61-64 — full hub state map `UpdateStatus.get()` ONLY on desktop+local views, `nil` otherwise: non-desktop or remote-node viewing); calls `maybe_attach(desktop?)`.
- `maybe_attach/2` (update_status.ex:160-172): when desktop AND `connected?(socket)` → `Phoenix.PubSub.subscribe(EvoGit.PubSub, "updates")` + `attach_hook(:update_status, :handle_info, &handle_info/2)` + `attach_hook(:update_status, :handle_event, &handle_event/3)`. Dead-render skip mirrors NodeAware. Non-desktop → no-op (dormant hook).
- `handle_info` interceptor (update_status.ex:117-124): `{:update_status, state}` → `{:halt, assign(socket, :update_status, state)}` — attached hooks run BEFORE the LiveView's own `handle_info`; other messages pass `{:cont, socket}`. NOTE: the broadcast assign is UNCONDITIONAL — a transition on a remote-view page would populate the assign (only the INITIAL seed is hidden on remote views).
- `handle_event` interceptor (update_status.ex:127-155): consumes the four JS-hook result events (`update_check_result`, `update_download_result`, `update_apply_confirmed`, `update_apply_failed`) with `{:halt, socket}` so no page sees unhandled-pushEvent warnings; everything else passes `{:cont, socket}`. Check results may auto-request a download via `push_event` (line 129). `update_apply_confirmed` stops the backend through the shared `:evo_dash, :desktop_quit_stop_fun` config seam (default `DesktopQuit.default_stop/0`).
- Every page receives broadcasts because the hook is registered globally (evo_dash_web.ex:56); the shared layout renders the System-nav notification dot from `@update_status` (layouts.ex:49, 148, 450-451 — only phases `:available`/`:ready`).

### `EvoDashWeb.LiveHooks.DesktopQuit` (`desktop_quit.ex`)

On-mount hook for the Tauri desktop tray "Quit Genesis" confirm dialog. No subscriptions, no timers, no polling. Seeds `@desktop_quit_confirm` (false) and attaches a `:handle_event` interceptor (desktop_quit.ex:41) consuming the three tray-quit events (desktop_quit.ex:49-61):

- `desktop_quit_requested` → `{:halt, assign(:desktop_quit_confirm, true)}`. The shared app layout (`EvoDashWeb.Layouts.app` — every page renders through it) shows a warning confirm dialog whenever the assign is true, so the dialog works on ANY page. The dialog's Quit button is a `DesktopQuitConfirm` JS hook that first invokes the Tauri `begin_quit` command (the shell sets its intentional-shutdown flag so its watchdog won't restart the backend) and then pushes `desktop_quit_confirmed`.
- `desktop_quit_cancelled` → assign false + push `"desktop_quit_closed"` (re-arms the JS latch).
- `desktop_quit_confirmed` → stop via the `:evo_dash, :desktop_quit_stop_fun` config seam (default `default_stop/0` = spawn + 150ms delay + `System.stop/0`, so tests inject a fake and the REAL `System.stop/0` never runs in the test VM), assign false + push `"desktop_quit_closed"`.

Handlers are idempotent (`requested` always assigns true; `cancelled` assigns false). Both the cancel AND confirm handlers push `"desktop_quit_closed"` via `Phoenix.LiveView.push_event/3` to re-arm the JS latch. No remote-node branch: the tray event only comes from the desktop shell, whose webview serves the LOCAL dashboard VM; outside the Tauri shell the JS listener never fires and the hook stays dormant.

**Delivery contract (JS latch + dedup + retry + reconnect re-push)**: the `DesktopQuit` JS hook (`assets/js/app.js:678`) latches every Tauri `quit-requested` event into `_quitPending`, dedups while a quit awaits delivery or the dialog is open, and retries the `desktop_quit_requested` push on rejection (1s `setTimeout`) plus once more from `reconnected()` when the LiveSocket re-establishes. The latch exists because `pushEvent` is NOT buffered: while the window sits hidden in the tray, the client-side heartbeat kills the socket and phoenix.js suspends reconnects while the page is hidden (`pageHidden` — reconnect resumes only on window show via `visibilitychange`); `pushHookEvent` then rejects with "unable to push hook event. LiveView not connected". Rust emits `quit-requested` ONCE (desktop/src-tauri/src/main.rs:619) right after show+focus — i.e. exactly inside the reconnect window (WS open + channel join + server mount + full re-render) — so the latch is the primary delivery guarantee. The latch is released ONLY when the server pushes `desktop_quit_closed` (from the cancel and confirm handlers); a stale latch would silently dedup every later tray quit. `reconnected()` fires only when the hook was marked disconnected (socket-error/heartbeat-timeout path — the primary scenario; the hook is NOT re-mounted on reconnect, so `mounted()` does not re-run and the Tauri listener survives). Server-side (LiveView) has NO heartbeat-based socket close — liveness is purely client-side. Tests (`test/evo_dash_web/live_hooks/desktop_quit_test.exs`) are server-side only (`render_click` + `assert_push_event`) — they pin the `desktop_quit_closed` re-arm contract, idempotency, and re-open behavior but cannot exercise the JS-side drop/retry.

**No timeout-based force-quit**: the hook handles only quit-requested delivery/latching + `begin_quit` confirm. There is NO liveness-heartbeat/keeper mechanism and NO guaranteed-exit timer — tray Quit with a healthy backend waits indefinitely for the user's confirmation. The only immediate quit is the backend-already-down path, where no dashboard exists to confirm with and no tasks can be running.

### Hook registration, process lifetime & reconnection

- **Registration**: all six hooks are registered via `on_mount` in the shared `live_view/0` macro (`apps/evo_dash/lib/evo_dash_web.ex:52-57`) — SetLocale → NodeAware → Appearance → DesktopQuit → UpdateStatus → Guide. Every LiveView (including Welcome/WelcomeComplete) gets them automatically.
- **Process lifetime**: one LiveView process per connected page session. `on_mount` runs TWICE per page load: (1) dead render inside the initial HTTP request process — `connected?/1` false → NO PubSub subscriptions (interceptor attaches and assign seeds still apply); (2) connected mount in the NEW LiveView process — `connected?/1` true → subscribe + initial loads. Subscriptions are per-process and die with the process (Phoenix PubSub auto-cleans); nothing re-subscribes within a process.
- **Navigation**: `push_patch` (palette/pagination/node switches) re-runs `handle_params/3` on the SAME process — no re-subscription; `assign_node/2`'s `:tasks_node_loaded` dedup prevents redundant sidebar reloads. `push_navigate` to a DIFFERENT LiveView module (all dashboard routes are distinct modules) spawns a NEW process → full re-mount → re-subscribe. `push_navigate` to the same module keeps the process.
- **Disconnect/reconnect**: on socket close the channel stops the LiveView process (`{:shutdown, :closed}`); on reconnect the client mounts a NEW process → `on_mount` re-runs → re-subscribes. Missed-event catch-up is per-hook reload-on-mount only (no cursors/replay): NodeAware's connected mount re-seeds the sidebar synchronously from the `EvoDash.ActiveTasks` hub and fires its conditional fetch only (node_aware.ex:133-155 — full DB/RPC re-query only when the resolved context is a cold LOCAL one); UpdateStatus re-reads the hub's CURRENT state via `UpdateStatus.get()` (update_status.ex:63 — GenServer snapshot).

## Constraints

- Hooks use `assign_new/3` (safe assigns — first-write-wins).
- Domain logic is delegated to `EvoDash.NodeContext` — hooks are thin wrappers.
- Safe fallbacks everywhere: locale defaults to `"en"`, node resolution falls back to `:local` on all failure paths.
- Node name fallback: "Local" when no remote node is active.
- **Task reload debounce**: `handle_task_info/2` NEVER reloads synchronously — always go through `debounce_task_reload/1` → `:node_aware_reload_tasks` (300ms trailing-edge) → `reload_tasks/1`. LiveViews that do custom reloads must call `clear_task_reload_pending/1` afterwards so the next broadcast can schedule a fresh reload.
- **Sidebar dedup**: `assign_node/2` skips the sidebar reload when `:tasks_node_loaded == {current_node_id, current_node}`. Do not remove the guard without also handling the mount double-fetch it prevents.
- **Statuses-filtered sidebar fetch**: `load_running_and_pending_tasks/1` uses the statuses-filtered forms `EvoGit.TaskRegistry.list_tasks_summary/1` and `EvoDash.NodeContext.list_tasks_summary/2` (via `EvoGit.RemoteNode.list_tasks_summary/2` → `EvoGit.AgentScheduler.RemoteAPI.list_tasks_summary/1`; SQL-pushed-down statuses IN filter). Do NOT revert to unfiltered `/0`/`/1` calls — the statuses-filtered call is the whole point (skips finished rows in SQL).
- **Sidebar loads are ALWAYS async**: `load_running_and_pending_tasks/1`, `assign_active_tasks/1`, and `reload_tasks/1` MUST go through the private `request_tasks_load/1` spawner (supervised fetch on `EvoDash.TaskSupervisor`, `:tasks_load_seq` bump, socket returned unchanged). Do NOT reintroduce synchronous fetch/assign — a remote `:erpc` fetch can block the LiveView process for up to 30s. The result message is `{:node_aware_active_tasks, seq, node_id, node, {running, pending}}`; never change its shape without updating the attached `handle_info/2` hook and the `handle_tasks_result/2` stale-guard.
- **Stale-guard is mandatory**: results are applied ONLY when `node_id`/`node` match the current node-context assigns AND `seq` matches `:tasks_load_seq` (latest request wins). The `:tasks_load_seq` assign is bumped by every load request; never reset it to a lower value mid-view.
- **Previous sidebar content is kept** until the fresh result arrives (no loading indicator, no clearing on spawn). A dropped/stale result leaves the sidebar untouched.
- **LiveView pages do NOT need to change**: the attached `:handle_info` hook consumes the result message (`{:halt, socket}`); all other messages pass through (`{:cont, socket}`). LiveViews keep calling `load_running_and_pending_tasks/1` / `assign_active_tasks/1` / `reload_tasks/1` exactly as before — the call sites are non-blocking without any LiveView edit.

## Test Strategy (async sidebar load)

`test/evo_dash_web/live_hooks/node_aware_test.exs` is unit-style with bare `%Phoenix.LiveView.Socket{}`s and **resets the shared `EvoDash.ActiveTasks` hub per test in setup** (`EvoDash.ActiveTasks.reset()` — the canonical shared-hub reset idiom; the hub is a boot-created named public ETS table owned by the long-lived `EvoDash.Application` process (created in `EvoDash.Application.start/2` before `Supervisor.start_link`), alive for the whole `mix test` run with a `{nil, node()}` local key shared across ALL suites; reads/writes are direct `:ets` operations — no GenServer). The hub-seeded on_mount (synchronous per-context seed + the conditional cold-local connected-mount fetch) is exercised by mounting `on_mount/4` directly on boot-shaped sockets: dead-render `mount_socket/1` (`transport_pid: nil`) and connected `connected_mount_socket/1` (`transport_pid: self()` makes `Phoenix.LiveView.connected?/1` true); boot sockets preset no `:running_tasks`/`:pending_tasks`, so `assign_new` seeds from the hub. Because the spawned task's captured `view_pid` IS the test process (the `EvoDash.TaskSupervisor` runs under `mix test`), tests use the **send-pattern**: `assert_receive {:node_aware_active_tasks, seq, node_id, node, {running, pending}}` (1000ms timeout) / `refute_receive` (short timeout) on the message payload — never synchronous `assigns` assertions after a load-triggering call (the socket comes back unchanged). The **stale-guard** is tested directly via the public `handle_tasks_result/2` seam (pure socket in/out: node mismatch dropped, outdated seq dropped, matching case assigns + hub write; stale results leave the hub unwritten). **Node-switch dedup** is tested by calling `assign_node/2` twice with the same context and `refute_receive`-ing the absence of a second spawn. Full-page LiveView suites (`home_live_test.exs`, `projects_live_test.exs`, `tasks_live_test.exs`, `review_live_test.exs`, plus every other whole-page-mounting suite) each reset the shared hub per test in setup (`EvoDash.ActiveTasks.reset()` — required because sidebar-visible rows in the store while an applied fetch runs warm the local key NON-EMPTY, and a warm key suppresses the mount fetch, which would render a stale sidebar in later mounts). `home_live_test.exs`'s "sidebar robustness" describe also carries an instant-seed regression ("warm ActiveTasks hub seeds the sidebar instantly on mount (no broadcast needed)") proving the no-blink contract end-to-end. All mounting suites are `async: false`, so the per-test reset is safe and fully effective — any NEW suite asserting whole-page html through `Layouts.app` must add it to setup (detail: `apps/evo_dash/test/CONTEXT.md`); when asserting sidebar assigns, use `render_async(view)` (or the send-pattern) to flush the async result.

### `EvoDashWeb.LiveHooks.Guide` (`guide.ex`)

Global on-mount hook bridging the core's `guide_user` tool broadcasts to the floating "Genesis Guide" panel in `EvoDashWeb.Layouts.app` (registered LAST in the `live_view/0` macro, after `UpdateStatus`, `evo_dash_web.ex:57`). The panel renders from `@guide`; the 9 `guide={@guide}` call sites in the live pages pass it through (layouts + home/welcome/welcome_complete/projects/tasks/review/agents/settings/system). This hook only maintains the assign.

- **PubSub contract**: subscribes to `EvoGit.PubSub` topic `"guides"` on the connected mount only (`maybe_attach/1`, dead-render skip); message shape `{:guide_updated, guide_id, %{message: String.t(), page: String.t() | nil, selector: String.t() | nil, dismissible: boolean}, node()}`.
- **Node filtering**: the attached `handle_info/2` drops foreign-node broadcasts FIRST via the pure `relevant?/2` wrapper over `NodeAware.event_from_current_node?/2` (node_aware.ex:592) — a guide broadcast on a remote `genesis_remote` node only surfaces while that node is being viewed.
- **Client-id retention**: `on_mount/4` seeds `@guide` via `assign_new(:guide, fn -> stored_guide(socket) end)` (nil-safe default). Retention is implemented with a `:persistent_term` store keyed by a **per-tab `guide_client_id`** that the `Guide` JS hook generates once per page load (sessionStorage-backed) and passes in the LiveSocket connect params — read via `client_id/1` from `socket.private[:connect_params]["guide_client_id"]` (atom-key fallback tolerated; nil when absent, e.g. dead render/bare test sockets). `handle_info` persists every accepted guide via `store_guide/2`; because `push_navigate` keeps the same WebSocket connection (and thus the same client id), the destination mount restores both the panel and the highlight.
- **Highlight**: when `guide.selector` is a non-nil binary, the hook pushes `"guide_highlight"` (`%{selector: selector}`) via `push_event/3` — consumed by the `Guide` JS hook (`assets/js/app.js`), which re-applies the highlight from its module-level store on navigation.
- **Dismissal**: `handle_event("guide_dismissed", ...)` clears BOTH the `:guide` assign and the retention store (`clear_guide/2` — `:persistent_term.erase` on the client-id key), AND pushes `"guide_cleared"` (`%{}`) so the JS hook drops its module-level highlight store (without it a stale highlight would re-apply on a later navigation after dismissal), all with `{:halt, socket}`; all other events pass through `{:cont, socket}`.
- **Pure helpers** (`@doc false`, unit-test seams): `relevant?/2` (node-filter decision), `normalize_guide/2` (defensive normalizer tolerant of atom- AND string-keyed payloads: `message` → binary or `""`, `page`/`selector` → binary or nil, `dismissible` → boolean defaulting to `false`; never raises). Tested by `test/evo_dash_web/live_hooks/guide_test.exs`.
