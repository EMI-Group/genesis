# EvoDash Domain Logic

## Intent

Domain layer for the EvoDash Phoenix application. Contains the OTP `Application` supervisor, the in-memory `ChatHistory` chat-history store, the `NodeContext` SSH remote-development thin client, the `DirectoryPicker` native dialog picker (with its `Wx` seam), the `UpdateStatus` auto-update state hub, the ETS-backed `ActiveTasks` sidebar last-known-state cache, the desktop-only `DesktopLifetime` Tauri-shell watcher, the Sign in with ChatGPT loopback sign-in flow (`EvoDash.ChatGPTLogin`) with its terminal client (`EvoDash.ChatGPTCLI`), and small pure helpers (`AttachedFile`, `MarkdownRender`, `SettingsUtils`). The persistence/registry modules (`Store`, `Store.Codec`, `TaskInfo`, `TaskRegistry` and the `task_registry/` helper submodules) live in `:evo_git` as `EvoGit.Store`, `EvoGit.TaskInfo`, `EvoGit.TaskRegistry` (and friends), together with the project registry `EvoGit.VCT` (mount table + publish). EvoDash owns no persistence or registry code.

## API Surface

### `EvoDash.Application` (`application.ex`)

OTP Application callback module. Supervision tree (`:one_for_one`, `max_restarts: 10`, `max_seconds: 60`):
The list is built by the PUBLIC `children/0` (so tests can pin that the endpoint's presence is mode-INVARIANT; it reads the desktop gating env vars at CALL time) and `start/2` passes it straight to `Supervisor.start_link/2`:

1. `EvoDashWeb.Telemetry`
2. `Phoenix.PubSub` (registered as `EvoDash.PubSub`)
3. `Task.Supervisor` (registered as `EvoDash.TaskSupervisor` — the generic async-runner for dashboard LiveViews: all node-aware data loads and per-click RPCs run as `Task.Supervisor.start_child(EvoDash.TaskSupervisor, ...)` outside the LiveView process)
4. `EvoDash.WorkbenchSidebarCache`
5. `EvoDash.ChatHistory` (in-memory chat-history store; LiveViews mount after app boot so it is always available)
6. `EvoDash.DirectoryPicker`
7. `EvoDash.UpdateStatus`
8. `{DynamicSupervisor, strategy: :one_for_one, name: EvoDash.ChatGPTLogin.Supervisor}` then `EvoDash.ChatGPTLogin` — the Sign in with ChatGPT flow supervisor (its `:temporary` children each bind their own `127.0.0.1` callback listener) and the facade holding the flow registry; both BEFORE the endpoint so a settings sign-in cannot race a page mount.
9. `EvoDashWeb.Endpoint` — ALWAYS a child, in every mode. There is exactly ONE `genesis_server` instance per host: it serves the Phoenix dashboard over HTTP (loopback by default) and has Erlang distribution enabled/disabled at runtime on that same BEAM (`EvoGit.DaemonControl`, driven by `<launcher> remote start|stop`), so a remote-dev host exposes its dashboard too and no env var may drop the endpoint.
10. `{EvoDash.DesktopLifetime, []}` — appended only when BOTH `EVOGIT_DESKTOP=1` and `EVOGIT_LIFETIME_PORT` are set (only the Tauri sidecar sets both); the module's `init/1` self-disable is belt-and-suspenders.

Before `Supervisor.start_link`, `start/2` creates the `:evo_dash_active_tasks` ETS table via the idempotent private `ensure_ets_table/2` helper — owned by the long-lived application process (NOT a supervised child) so it survives child restarts and lives for the whole `mix test` run; creation is a no-op when the table already exists (e.g. application restart after a soft crash). `EvoDash.ActiveTasks` is a pure ETS-helper module with no process, so it is deliberately absent from the children list.

`start/2` also calls `_ = EvoDash.ConnectionDiagnostics.attach()` (idempotent, non-fatal) so the peer-address diagnostics handler is registered in desktop AND normal modes; it is NOT a supervised child (the children list is unchanged).

`EvoGit.Store`, the task-registry `Registry`, and `EvoGit.TaskRegistry` are children of `EvoGit.Application`'s supervision tree, not of this supervisor.

#### Boot memory profile (`mix phx.server` vs a `genesis_server` release)

- Children are mode-INVARIANT apart from `DesktopLifetime`: `RELEASE_NAME=genesis_server`, `EVOGIT_SERVER=1`, `:server_release` and `PHX_SERVER` only set `EvoDashWeb.Endpoint` `server: true` plus secret-key/logging handling in `config/runtime.exs`.
- No boot-time SQLite read and no rehydration: this app owns no Store/Ecto code and every boot store it creates is empty (`:evo_dash_chat_history`, `:evo_dash_active_tasks`, `:evo_dash_accent_cache`); `UpdateStatus` starts at `initial_state()`, `DirectoryPicker` starts no `wxe_server`, and Telemetry runs a poller with zero periodic measurements and no reporter.
- The only PROD-only boot work is static-manifest warmup (`cache_static_manifest`, produced by `mix assets.deploy`, gitignored → an absent file skips it); DEV is the heavier shape (code/live reload, esbuild/tailwind watchers, Mix in the BEAM, compile-time HEEx debug annotations).
- The largest reachable RSS item is not here: the 11.7 MB `deps/llm_db` snapshot decoded into `:persistent_term` by the first model-metadata lookup (`EvoGit.AgentScheduler.init/1` → ReqLLM → `LLMDB.ensure_loaded!`), mode-invariant and off-heap.
- The only unbounded-by-default dashboard store is `EvoDash.ChatHistory` (opaque ETS transcripts, pruned only by `HomeLive`'s `prune(10)` on New chat) — a runtime growth vector, not boot work, that dies with the BEAM.

### `EvoDash.ChatGPTLogin` (`chatgpt_login.ex` + `chatgpt_login/`)
The ONE Sign in with ChatGPT (SIWC) loopback sign-in implementation; the dashboard wizard and the terminal CLI both drive it, so PKCE/state/callback/exchange/persist logic exists exactly once.
`begin(account, opts)` → `{:ok, %{id, url, port}} | {:error, reason}` binds `127.0.0.1` on `:port` (default `0` = ephemeral free port; the CLI keeps 1455) BEFORE minting the authorization URL, so the redirect URI is always the REAL `http://127.0.0.1:<bound port>/auth/callback` and the flow keeps the attempt (state/nonce/verifier) in the listener's own state.
`status(id)` → `:pending | {:ok, %{account, status}} | {:error, reason}`, `cancel(id)` → `:ok | {:error, :unknown_flow}`, `active_for(account)` → `id | nil`, `pending?/0`.
Terminal values: `{:ok, %{account:, status:}}` (the store's own status map, else `%{account_id: account}`) or `{:error, reason}` where reason is `:authorization_denied`, `:authorization_timeout`, `:cancelled`, `:superseded`, `:loopback_listener_unavailable`, `{:flow_crashed, reason}`, or any reason the store/exchange returned (`:plan_not_authorized`, `:chatgpt_account_alias_in_use`, …) passed through unchanged.
Terminal values are retained for `:retention_ms` (default `300_000`) and then `status/1` answers `{:error, :unknown_flow}`; an id that was never issued answers the same.
ONE flow per account: a repeat `begin/2` for the same account supersedes the old flow (its terminal value becomes `{:error, :superseded}` and its registered `:caller` is notified) and starts the new one.
A `:caller` option receives exactly ONE `{:chatgpt_login, id, result}`; every exit path (success, failure, timeout, cancel, supersede, facade `DOWN`) stops the Bandit listener, and flows run as `:temporary` children of `EvoDash.ChatGPTLogin.Supervisor` monitored by the facade, so a crashed flow becomes `{:error, {:flow_crashed, reason}}` and never takes the facade or the app down.
`chatgpt_login/callback.ex` serves only `GET /auth/callback` on a loopback host, validates `state`, and answers with a self-contained HTML page (no params or tokens echoed, `cache-control: no-store`, `referrer-policy: no-referrer`); a callback carrying `error=` denies (`{:error, :authorization_denied}`) WITHOUT calling the exchange.
Hermetic-test seams resolved AT CALL TIME: `opts[:exchange] || Application.get_env(:evo_dash, :chatgpt_login_exchange, &EvoGit.Auth.ChatGPT.exchange/2)` and `opts[:store] || Application.get_env(:evo_dash, :chatgpt_login_store, EvoGit.Auth.ChatGPT.Store)`; a `:store` module provides `path/1`, `registration/1`, `host_id/0`, `install/2`, `status/1`.
Persistence and cross-process serialization come from the store's own install lock, so the CLI and a running dashboard cannot corrupt each other.
`ensure_started/0` (`@doc false`) boots the supervisor + facade on demand, so `mix genesis.chatgpt login` from a source checkout works without an application boot.

### `EvoDash.ChatGPTCLI` (`chatgpt_cli.ex`)
Thin terminal client for `genesis chatgpt <login|status|models|logout|import FILE> [--account NAME] [--port PORT]` (default port 1455), calling `EvoDash.ChatGPTLogin.begin(account, port: port, caller: self())` and waiting bounded for `{:chatgpt_login, id, result}` with a `status/1` fallback.
`login` prints the URL, "Waiting for ChatGPT authorization." and, on success, "Connected ChatGPT account <name>." plus the model list; the usage text and the `ChatGPT: <inspect>` / exit-code-1 error contract are unchanged.
`status`/`models`/`logout`/`import` stay store-backed through the same call-time `:store` seam, which is what makes every command hermetically testable.
### `EvoDash.ChatHistory` (`chat_history.ex`)

In-memory (ETS-backed, NO disk persistence) chat-history store for the Genesis Assistant page (`EvoDashWeb.HomeLive`) — keeps per-chat transcripts alive across LiveView remounts. A GenServer (supervised child of `EvoDash.Application`, after `EvoDash.TaskSupervisor` and before the Endpoint) owns a named public ETS table (`:evo_dash_chat_history`, `:public`, `read_concurrency: true`); the table dies with the GenServer (no heir) — chats are volatile by design (they survive LiveView remounts, not BEAM restarts or a store crash). **ALL operations go through synchronous GenServer calls**: compound ops (`new_chat/0` inserts the chat AND makes it current, `delete_chat/1` removes AND may clear the current pointer, `prune/1` scans and deletes, `reset/0` clears everything) are serialized race-free by construction; single-key ops (`put_state/2`, `get_state/1`) would be safe directly on ETS (writes are atomic per call) but go through the GenServer too for one trivially-reasoned concurrency model (chat ops are low-frequency, so serialization cost is negligible). External DIRECT READS of the public table are safe (atomic) but mutations must go through the API. Shape-agnostic: per-chat state is an opaque `term()` — the LiveView owns the transcript/message shape. API: `new_chat/0` (id from `System.unique_integer([:positive])` — unique but NOT guaranteed ordered; creation order is a separate internal monotonic seq that drives `list_chats/0`'s newest-first order), `current_chat_id/0`, `set_current_chat/1` (no existence validation — a dangling current id renders as an empty chat), `list_chats/0` (newest-first), `delete_chat/1` (clears current if it was current; no-op for unknown ids), `prune/1` (keeps only the newest N; caller-driven, NEVER automatic; non-integer/negative bounds ignored, `0` clears all), `put_state/2` (upserts; an unknown id registers a new newest chat), `get_state/1` (`nil` for unknown/unset), `reset/0` (clears all — test helper). All callbacks are total — no raising on bad input. Table entries: `{:current}` → `chat_id | :none` (the current pointer), `{:chat, chat_id}` → `{seq, state}` (monotonic creation seq driving newest-first order + opaque per-chat state). Enumeration uses `:ets.match_object/2` with a plain match pattern — NOT `:ets.select` match specs, whose match heads on this OTP cannot contain nested tuples and therefore cannot match tuple keys.
Interactive Assistant conversations are keyed by their SESSION agent id — an agent id is a positive integer, which is already a valid chat id, so no synthetic mapping exists and the first `put_state/2` registers the conversation as the newest chat.

#### Chat isolation and recovery limits

`ChatHistory` has one process-global `{:current}` pointer and keys state only by `chat_id`, with no user, browser session, remote target or BEAM-node namespace and no remote forwarding.
The opaque state may contain caller-defined node metadata, but the store itself does not enforce ownership or node isolation.
`put_state/2` replaces the entire stored state, without a version check or merge, so serialized calls do not prevent two LiveViews from overwriting each other's stale snapshots.
There is no transcript byte/message cap, TTL, disk journal, replication, subscription or task/approval reconciliation in this store; `prune/1` bounds chat count only when explicitly called.
Public functions use ordinary synchronous `GenServer.call/2` without a failure guard, so a dead or busy ChatHistory process can exit the caller even though callbacks handle malformed values safely.
`prune/1` documents and implements zero as clear-all and malformed/negative bounds as no-ops, but its `pos_integer()` input spec excludes zero; these behaviors are directly pinned in `test/evo_dash/chat_history_test.exs`.
`SafeCall.run/1,2` likewise explicitly handles invalid nonzero-arity-function arguments while its input specs admit only zero-arity functions, and `test/evo_dash/safe_call_test.exs` pins the invalid-function error and fallback contracts.

### `EvoDash.NodeContext` (`node_context.ex`)

Thin client for the dashboard's SSH remote-development feature; wraps three `:evo_git` layers and presents one API to the dashboard LiveViews.

1. **`EvoGit.RemoteConnections`** — connection-target persistence (`list_targets/0`, `get_target/1`, `save_target/1`, `delete_target/1`).
2. **`EvoGit.RemoteConnection`** — connection lifecycle (a per-target GenServer that stops again after a graceful disconnect, so it may not be running at call time); `connect/1`, `disconnect/1`, `bootstrap/1,2`, `connection_status/0,1` and `connected?/1` degrade through the private `with_remote_connection/4` guard to `{:error, :remote_connection_unavailable}` / `%{}` / `:disconnected` / `false`.
3. **`EvoGit.RemoteNode`** — the cross-node RPC helpers below.

- **Task, review, project and config wrappers are one-line `EvoGit.RemoteNode` delegations and the node is the ONLY routing input** (apart from the local-first process path, no local/remote branch lives here; the split is `EvoGit.RemoteNode.call_remote/4`). No module in this directory references `EvoGit.Store`/`EvoGit.TaskRegistry`, and the only direct `:erpc.call/5` is `approval_response/3`'s remote arm.
- **Connect is event-driven at the core**: `connect/1` returns `{:ok, :connecting}` (a duplicate while `:connecting`/`:connected` is an idempotent no-op) and terminal outcomes arrive ONLY via the `"remote_connections"` broadcast `{:remote_connection_status, target_id, status_map}` (`:connecting`, `:connected`, `:error` with `last_error`). The wrapper can queue behind a long bootstrap, so every LiveView/LiveComponent entry point MUST call it inside `EvoDash.TaskSupervisor`.
- **Interactive sessions**: `start_session/2` (`%EvoGit.AgentSpec{}` or `SessionOpts.build/1` opts → `{:ok, agent_id}`, no blocking), `send_session_message/4` (`:queue` default, `:interrupt` opt-in; binary or `%{text:, attachments:}`), `close_session/3` (`:normal`; the ONLY non-cancel way out of `:awaiting_input`), `await_close/3` (default 30 000 ms bounds the WAIT only) and `list_awaiting_input/1` (entries `%{agent_id, task_id, session_pid, task_number, mode}`; any non-list answer degrades to `[]`, so `[]` also means "the node could not be asked"). Envelopes pass through VERBATIM: a session's `{:error, {:session, reason}}` and a transport `{:error, {kind, reason}}` are both the node's real answer.
- **Assistant-session extras** — `send_message_with_workspace/5`, `stop_current_turn/2` and `update_assistant_workspace/3` call `EvoGit.Agent.Session` directly when `target == node()` and via `call_remote/4` otherwise.
- **Agent streams** — `subscribe_agent_deltas/1`/`unsubscribe_agent_deltas/1` are LOCAL `EvoGit.Agent.Stream` calls, `register_agent_watcher/3`/`unregister_agent_watcher/3` are local-only (a remote node answers `{:error, {:not_found, :invalid_consumer}}` / `:ok` with no call), and `watch_agent_snapshot/2` delegates to `EvoGit.RemoteNode.watch_snapshot/2`.
- **Task wrappers** — summary/ID/page/changed-since/unique-paths reads, `start_task/3` (`{:ok, %TaskInfo{}}`), `get_task/2`, `get_task_lite/2`, the archive pair, the cancellation pair (`cancel_task/2` GRACEFUL → `:cancelling`, result/archive preserved; `force_kill_task/2` → `:failed` with a nil result, escalation from `:cancelling`), the pause pair (`pause_task/2` → `:pausing` → `:paused`; `resume_task/2` re-dispatches the SAME task id, refusals `:not_found`/`:not_running`/`:not_pausable`/`:not_resumable`/`:scheduler_unavailable`/`:not_paused`), `delete_task/2` and `clear_finished_tasks/1`.
- **Lightweight reads** (the escape hatch from full `%TaskInfo{}` rows): `list_tasks_page/2` → `%{rows: [summary_map], total: non_neg_integer}` of atom-keyed summary maps, with `opts` `:limit` (default 25, capped 50), `:offset` and the filters `:status` (the on-disk STRING), `:project_path`, `:review_status`, `:search`; `get_task_lite/2` is the full struct with result data but NO `:archive_records` (the archive lives only in the relational `task_agent_archives` table); `list_task_archives/3` → `%{entries: [string-keyed map], total: non_neg_integer}` for one page ordered `depth, agent_id`, with `:limit` (default 100, 1..1000), `:offset`, `:include_results` (default false — the entry then omits `"result"`), `:include_settings` (default false — the export-only `"llm_settings"`/`"agent_settings"`/`"foreign_repos"` columns are absent) and `:include_total` (default true; false skips `COUNT(*)` and normalizes `total: nil` to `0`); `get_agent_archive/3` fetches ONE full entry on demand. Failures degrade to `%{rows: [], total: 0}` / `nil` / `%{entries: [], total: 0}` / `nil` via `normalize_archive_page/1` (atom- or string-keyed pages, non-list entries → `[]`, bad total → `0`) and `normalize_archive_entry/1`. Consumers: the /tasks page load, expanded cards (`TasksLive.TaskDetail`), the review page, the home chat terminal fetch, resume/notification scans and the paged archive disclosures; no dashboard page issues `list_tasks_paginated/2` or `get_task/2`.
- **Data shapes forwarded verbatim**: the 18-key summary (`id, status, review_status, started_at, finished_at, type, project_path, opts, branch_name, model_id, agent_count, base_sha, commit_sha, lease_expires_at, updated_at, error, session_mode, pause_kind`; `updated_at` a raw ISO string, `pause_kind` `:clean | :dirty | nil`, `opts` a decoded keyword list, `error` nil unless `:failed`, and no `result`/`logs`/`usage`/`archive_metadata`); `list_task_ids/2` = `id/status/updated_at` maps; `projects/1` = `[%EvoGit.VCT.Mount{}]`.
- **Core-side branch**: `EvoGit.RemoteNode.call_remote/4` calls the local `EvoGit.AgentScheduler.RemoteAPI` directly (`{:ok, result}`, errors not caught) or `:erpc.call/5` (30 s default, `:remote_rpc_timeout` override) normalizing failures to `{:error, {kind, reason}}`; per-fn wrappers then collapse list-shape errors to `[]`, paginated to `{[], 0}` and `get_task` to `nil`.
- **Review & git operations** (`list_commits/3`, `load_review_data/3`, `load_review_metadata/3`, `load_file_diff/5,6`, `load_review_metadata_from_shas/4`, `list_commits_from_shas/4`, `load_commit_files/3`, `load_commit_file_diff/4`, `merge_branch/3,4`, `default_merge_target/2`, `list_branches/2`, `reject_branch/3`, `create_github_pr/5`, `github_upstream/2`, `list_github_issues/3`, `github_issue_markdown/3`, `branch_exists?/3`, `check_merge/4`, `list_commit_graph/4`, `list_task_commit_graph/5`, `set_review_status/3`, `set_review_metadata/4`) return the VERBATIM underlying value in BOTH paths — only a transport failure surfaces as `{:error, {kind, reason}}`. Every repo-scoped op takes ONE absolute `repo_path` (no `repo_id`/target parameter anywhere in the chain), so a per-repo caller just calls once per path; ONLY `set_review_status/3` and `set_review_metadata/4` are `task_id`-keyed (one base/commit SHA pair, not representable per repo). No runner seams live here — the review and export seams are resolved in the web layer.
- **Managed processes are LOCAL-FIRST**: `list_processes_result/2`, `list_processes/2`, `get_process/2`, `process_stats/2` and `process_control/4` call `EvoGit.ProcessManager` in-BEAM when the viewed node IS this BEAM, else `call_remote/4` with `EvoGit.AgentScheduler.RemoteAPI`. `opts`/`action`/`reason` pass verbatim; the control action is resolved first (`:pause | :resume | :kill | {:signal, s}`, anything else → `{:error, {:unknown_action, action}}`); `list_processes/2` degrades to `[]` while `list_processes_result/2` preserves the error so the inspector can offer a retry; an absent or dead manager answers `{:error, :process_manager_unavailable}` and a non-binary id `{:error, :not_found}` with no call. The remote transport is the call-time seam `Process.get(:node_context_process_rpc) || Application.get_env(:evo_dash, :node_context_process_rpc, &EvoGit.RemoteNode.call_remote/4)`; tests: `test/evo_dash/node_context_test.exs`.
- **Custom agents & tools** — `list_custom_agents/1`, `save_custom_agent/2`, `delete_custom_agent/2`, `save_model_selection_script/2`, `reload_custom_agents/1` target the viewed node's own `agents.toml`, and a failed fetch reads as `{:ok, %{agents: [], model_selection_script: nil, script_status: :ok}}`; `custom_tools_status/1` passes `EvoGit.RemoteNode.custom_tools_status/1` through VERBATIM (`%{ok: [%{name, file, module, read_only?: boolean}], errors: [%{file, reason}]}`, read from the node's `<config_dir>/tools/`) and does NOT degrade — RPC failures stay `{:error, term()}`.
#### Projects, workspaces & the VCT registry (no project CRUD in this layer)

A project is a VCT PROJECT mount (`%EvoGit.VCT.Mount{}`: `point` `vct:///projects/<name>[-N]`, absolute OS `path`, `name`, `kind`, `last_opened_at`); reserved mounts (`vct:///genesis-source`) are never returned, and there is no project entity or CRUD here.
- `projects/1` → newest-opened first, `[]` on RPC failure or a non-list payload.
- `mount_project/3` `(node, path, name)` → `{:ok, %EvoGit.VCT.Mount{}} | {:error, term()}`; `forget_project/2` `(node, key)` → `:ok | {:error, :not_found | :invalid_point | {kind, reason}}`, where `key` is a VCT point or a raw OS path.
- `read_project_config/2` → parsed `genesis.toml` map | `nil`; `list_tasks_summary_by_path/3` → `[summary_map]`; `list_path_suggestions/2`, `dir?/2`, `file_exists?/2` and `ls/2` are the path probes.
- Workspaces group, never execute: `workspaces/1` (workspace mounts — never in `projects/1`), `workspace_entries/1` (ONE node round trip with members already resolved; entries `%{workspace:, members:, missing:, nested:}`; degrades to `[]`), `create_workspace/4` (idempotent slug-keyed UPSERT; `:invalid_name` / `{:member_is_workspace, point}` / `{:invalid_member, ref}` / `:invalid_members` / `:vct_unavailable`), `workspace_members/2` (a point or bare name → `{:ok, %{workspace:, members:, missing:, nested:}}` or `:not_found`/`:not_a_workspace`/`:invalid_point`) and `workspaces_for/2` (covering workspaces of a point/name/path, `[]` when none or on failure).
The registry lives in each node's core (`EvoGit.VCT`, `vct_mounts` table, supervised in `EvoGit.Application`), so it is implicitly per-node; the core owns point allocation, newest-first ordering, the `max_projects/0` cap (100, oldest evicted; workspaces uncapped) and the `{:vct_updated, node}` broadcast on `"vct"`. A mount's OS path may be missing: not filtered, never created.
No project state is cached here — `ChatHistory` holds opaque chat state, `ActiveTasks` task lists and `AccentCache` an accent per target id; the only "current project" state is the Projects page's `?project=` param plus its browser draft (`EvoDashWeb.DraftScope`) and the Assistant's per-chat `workspace` selection.
Remote identity is opaque here: lifecycle functions take a target-id STRING, RPC functions take a BEAM `node()` atom; NodeContext never builds `genesis_remote_<id>@127.0.0.1` (that mapping lives in `EvoGit.RemoteConnection`), and local-vs-remote routing happens inside `EvoGit.RemoteNode.call_remote/4` (`node == node()` → direct call, else `:erpc.call/5`), never in NodeContext.

#### Configuration and task-payload boundary

`get_resolved_config/1` is the ONLY path to `EvoGit.Config.resolve/0` (`call_remote(node, EvoGit.Config, :resolve, [])`, remote `:erpc` bypassing `RemoteAPI`), answering an explicit `{:ok, config}` envelope; `get_remote_config/1` is scheduler RAM (`EvoGit.AgentScheduler.get_config/0`, documented `%{}` fallback) with no production dashboard caller, and `get_remote_config_status/1` reaches `EvoGit.Config.config_status/0`.
`save_user_config/2`, `save_credentials/2` and `start_task/3` are plain synchronous forwards with no local validation, schema conversion, migration or transactional save-and-reload; `start_task/3` has no opt whitelist, so mode strings, model specs/locks, custom-agent selection and repo-less constraints are caller/core contracts.
Known task opts include `:persistent_state` (boolean, absent → the core default `true`); the `genesis_start_task` MCP tool advertises it as a boolean defaulting to `true`, and it reaches the core only through `EvoGit.TaskControl.start/1`'s `@start_keys` whitelist (in `:evo_git`).
The layer offers no provider/model CRUD, OAuth-status, peak-schedule, connection-test or default-model API and no provider-profile flattening or model-selection normalization; callers use generic `call_remote/4` or build whole config maps and task keyword lists themselves, and old remote daemons receive new shapes without capability negotiation.
`reload_remote_config/1` (→ `EvoGit.RemoteNode.reload_config/1` → `AgentScheduler.RemoteAPI.reload_config/0`) is the force-disk-reread path; its sole dashboard caller is the remote-credentials save, and `save_user_config/2` relies on the core's implicit post-save reload.
No config residency, freshness, generation or subscription state lives here — it never subscribes to a config topic (only the agent-stream delegates), so a broadcast must be consumed by the owning LiveView/`NodeAware`, and the async-load guards here are page-private counters, not config generations.
The only config-dir filesystem access in this directory is `EvoDash.MCP.Auth` reading `<config_dir>/mcp-token`; nothing here reads `config.toml` or `credentials.toml`.

#### Approval routing and control-result caveats

`approval_response/3` accepts only `"approve"`, `"deny"`, `:approve` and `:deny` (anything else is rejected before dispatch) and adds no request-id/task/agent/session ownership validation; it transports only the BEAM node, request id and decision — never the displayed command — so exact invocation binding must be enforced by the core's pending-request/execution association.
Routing compares the supplied node atom with `node()`: local → guarded `EvoGit.CommandApproval.respond/2` (`Code.ensure_loaded?` + `apply/3`, `{:error, :command_approval_unavailable}` when absent), remote → `EvoGit.AgentScheduler.RemoteAPI.respond_approval/2` with a HARDCODED 15 000 ms `:erpc` timeout instead of `RemoteNode`'s generic budget.
The local guard catches exits and missing modules only, so a local responder exception can still raise; the remote branch catches every exception/exit/throw into an error tuple. `restart_remote/1` and `stop_remote/1` discard the RPC result and return `:ok`, so their success value cannot prove delivery.
Data wrappers (`list_agents/1`, `get_agent_history/2`, `paused?/1`, task lists) document empty/false fallbacks that conflate unavailable with genuinely empty; `get_resolved_config/1` and `get_recent_system_samples/1` preserve explicit envelopes and are preferable when a consumer must tell the two apart.

### `EvoDash.DesktopLifetime` (`desktop_lifetime.ex`)

Desktop-only Tauri-shell lifetime watcher over a TCP lifetime pipe: the Rust shell binds a `TcpListener` on `127.0.0.1:0`, holds one connection per backend instance, passes the port as `EVOGIT_LIFETIME_PORT`, and never writes on it; when the shell dies the OS closes the socket, `:gen_tcp.recv/3` errors and the watcher stops the VM (`System.stop(0)`), freeing the port.
Appended by `EvoDash.Application.children/0` only when BOTH `EVOGIT_DESKTOP=1` and `EVOGIT_LIFETIME_PORT` are set (`init/1` also self-disables on a missing/empty/invalid port), so the headless `genesis_server` release never starts it. It starts LAST, after `EvoDashWeb.Endpoint`, with its blocking connect+recv work deferred to `handle_continue/2`, so it never delays boot or the listener bind (the endpoint in turn cannot bind before `EvoGit.Application`, including `EvoGit.Store`'s synchronous migrations).
Test seams: `:parent_stop_fun` (app env, read at `init/1`) plus `:connect_retries`/`:connect_retry_delay` and `:recv_retries`/`:recv_retry_delay`/`:recv_fun` (`start_link` opts ONLY — the application starts it with `[]`, so production budgets are not config-tunable). Budgets: up to 5 connect attempts of a 1 000 ms `:gen_tcp.connect` + 200 ms sleep (≈6 s worst case, normally instant because the shell's listener backlog is bound BEFORE the backend spawns), then 3 recv retries × 200 ms.

Only two outcomes invoke the stop fun: connect-budget exhaustion (logs `Tauri shell is gone (lifetime connection could not be established)` — which cannot distinguish a dead shell from a live-but-not-accepting one, a stale/foreign port or a firewall) and a GENUINE peer close `{:error, :closed}` (logs `Tauri shell is gone (lifetime connection closed) — shutting down`).
Every other recv error (`:econnreset`, `:eacces`, `:timeout`, …) is AMBIGUOUS: it warns and retries the budget before giving up with `[desktop] lifetime recv kept failing … after retry budget exhausted — shutting down`, so an OS/AV/firewall reset or a hard-killed peer ends the VM through this branch rather than the peer-close one (`{:ok, _data}` resets the counter). `classify_recv_result/1` is the public pure classifier (`:closed` | `:data` | `:ambiguous`); a log cross-check must accept all three warnings.
It reacts to the SOCKET, not the shell process: an orderly FIN from an early-ended Rust hold thread (or an accept-thread failure) still reads as shell death while the shell lives.
The warning is NOT logged on the BEAM-initiated stops (tray-quit confirm → `DesktopQuit.default_stop/0`, System-page Stop, update apply → `UpdateStatus.stop_backend/0` via the shared `:desktop_quit_stop_fun` seam), because `System.stop(0)` tears the VM down before its own socket can observe a peer close — it appears only when the SHELL closes the pipe first.
Known coupling: exit code 0 is ambiguous — the Tauri watchdog's `classify_exit/2` (`desktop/src-tauri/src/backend_watchdog.rs`) treats `Some(0)` as an INTENTIONAL shutdown, so a spurious lifetime close makes the shell `app.exit(0)`: the app vanishes silently instead of showing the error page and restarting the backend.
Nothing is logged on a successful start or connect, so `backend.log` cannot confirm the pipe was ever established — only its loss is visible.
Orderly-stop tail: children stop in reverse start order, so `EvoDashWeb.Endpoint` stops AFTER the warning; with ≥1 open LiveView socket Phoenix's socket drainer appends `DRAINING N of M total connection(s) for socket Phoenix.LiveView.Socket every 2000ms - round 1 of 1` (created by default because `Keyword.get(opts, :drainer, [])` is truthy) — logged with the socket HANDLER module, NOT the endpoint, so check both spellings; its presence proves only an orderly stop with a live socket.
Discriminator: `<data_dir>/logs/shell.log` records `backend exited cleanly (code 0) — treating as intentional shutdown` for THIS stop, byte-identical to the tray-quit / System-page Stop / update-apply stops, so the `backend.log` lifetime warning is the only proof the SHELL closed the pipe rather than the BEAM stopping itself.

Attaches a `:telemetry` handler to `[:thousand_island, :connection, :start]` so each HTTP connection's peer address lands on the connection PROCESS's `Logger.metadata` — making Bandit's `Read timeout` ERROR lines (a client that opens a connection and sends nothing) attributable to `::1` vs `127.0.0.1`.

### MCP endpoint (`mcp/`)

`EvoDash.MCP.Server` is the stateless MCP JSON-RPC tools endpoint (accepted protocol versions `2025-11-25` and `2025-06-18`, exposed by `versions/0`): `handle/1` answers `initialize`, `ping`, `tools/list` and `tools/call`, treats an `id`-less `notifications/*` method as `:accepted`, and returns JSON-RPC errors for everything else.

### `EvoDash.AttachedFile` (`attached_file.ex`)

Reads attached objective files picked from the objective editor's attach-file '+' button (local files on the dashboard node).
`read/1` dispatches on extension: plain text (`.txt`/`.md`/any) read verbatim and trimmed; `.docx` extracted to plain text with OTP stdlib only (`:zip` + regexes — only `word/document.xml` is read; headers/footers/footnotes/comments ignored, field codes stripped); `.pdf` extracted to Markdown via the pure-BEAM `ex_pdf` reader (each page → `## Page N`, a conversion note prepended; scanned/image-only PDFs → `{:empty, _}`, password-protected → `{:invalid, ...}`, opened with `recover: true`).
Text-pipeline error shapes: bare POSIX atom (file read failure), `{:invalid, reason}` (malformed input), `{:empty, reason}` (valid but no text).
`read_kind/2` reads image/audio attachments (binary kinds `"image"`/`"audio"`) — the extension is validated against the kind's pinned allowlist (image `.png`/`.jpg`/`.jpeg`/`.gif`/`.webp`/`.bmp`; audio `.mp3`/`.wav`/`.ogg`/`.m4a`/`.flac`), the 15 MiB raw per-file cap is enforced (the per-task cap of 4 attachments is caller-enforced), and the raw bytes are returned verbatim — never rendered, logged, or sent to the client.
`media_type_for/1` maps a normalized lowercase extension to its pinned IANA media type (`nil` when unknown).
`read_kind/2` returns `{:ok, %{type:, media_type:, bytes:}}`; error shapes: bare POSIX atom, `{:unsupported_extension, ext}`, `{:file_too_large, byte_size}`, `{:unsupported_kind, kind}`.
`describe_error/2` builds user-ready messages for all error shapes.
Browser uploads use `upload_name/1` (basename normalization, control-character cleanup and invalid-name rejection), `upload_extensions/0`, and `read_uploaded/2`, which classifies an extensionless temporary file by the sanitized original client filename, rejects unsupported/nonregular/oversized files, and returns either `%{type: "text", name:, text:}` or the existing image/audio byte payload.
`read/1` intentionally treats unknown extensions, including media extensions, as plain text, whereas `read_uploaded/2` explicitly recognizes image/audio; any shared document-dispatch helper must preserve those distinct outer policies.
The upload media lookup is rebuilt from fixed module-attribute maps by `upload_media_types/0` on each call, and text/DOCX/PDF dispatch is repeated between `read/1` and `read_uploaded/2`.
Coverage lives in `test/evo_dash/attached_file_test.exs`, including original-filename upload dispatch and the deliberate `read/1` versus `read_kind/2` distinction; `upload_extensions/0` and the full uploaded-media matrix have no direct tests.

### `EvoDash.MarkdownRender` (`markdown_render.ex`)

Markdown → safe HTML for agent summary output using the non-crashing `MDEx.to_html/1`. `render/1` returns `""` for nil; on rendering failure logs a warning and falls back to HTML-escaped text (never crashes, never raw/unescaped markdown).

### `EvoDash.SettingsUtils` (`settings_utils.ex`)

Pure config-form helpers used by the settings LiveView: `deep_put/3`, `deep_merge/2`, `deep_delete/2`, `parse_int/1`, `parse_float/1`, `parse_atom/2` and `maybe_add_kw/3`.
`deep_put/3` and `deep_delete/2` accept nonempty key paths through MAPS only, preserve key types exactly and do not traverse array-of-table lists; `deep_put/3` creates missing maps but raises when an existing intermediate is nil, a scalar or a list, while `deep_delete/2` ignores non-map intermediates and prunes empty parent maps.
`deep_merge/2` recursively merges maps only and replaces every list wholesale with the right-hand list, so provider/model arrays need caller-owned id-aware editing rather than indexed key paths or implicit merging.
`parse_int/1` and `parse_float/1` accept only binaries fully consumed by the parser without caller-independent trimming or range validation, and already-numeric values return nil.
`parse_atom/2` compares strings against ATOM members of `schema[:validation][:in]` without creating atoms, so dynamic provider/profile ids and string-valued enums need a different whitelist parser.
`maybe_add_kw/3` omits ONLY nil and otherwise uses `Keyword.put/3`, preserving false, 0, empty strings and empty lists; it is not a blank/default-field normalizer.

### `EvoDash.SourceStatus` (`source_status.ex`)

Total (never-raising) shared wrapper around the optionally-present `EvoGit.SelfReflectiveSource` core backend. Guards each call with `Code.ensure_loaded?/1` + `function_exported?/3` (arity 0) and dispatches via `apply/3` — a direct call to a possibly-missing module would emit an "undefined function" compile warning — returning `{:unavailable, reason}` (`:module_missing` | `:function_missing` | `:call_failed`) instead of raising so callers can render a degraded UI.
Single private `guarded/2` dispatcher keeps all four public wrappers one-liners: `available?/0` → `boolean() | {:unavailable, reason}`; `status/0` → map or `{:unavailable, reason}`; `clone/0` and `update/0` → `{:ok, status} | {:error, reason} | {:unavailable, reason}`.
Consumers: `EvoDashWeb.SystemLive.SourceCard` + `EvoDashWeb.HomeLive`.

## Constraints

- `EvoDash.Application` starts NO persistence/registry children — those belong to `EvoGit.Application`.
- `EvoDash.ChatHistory` is in-memory only: a public ETS table owned by its GenServer, no disk persistence, no heir, no automatic pruning (`prune/1` is caller-driven). Mutations MUST go through the API (GenServer-serialized); direct table reads are safe but read-only by convention.
- `EvoDash.TaskSupervisor` IS started and IS used (async loads across all LiveViews). Do NOT remove it.
- `NodeContext` keeps its public API stable; web-layer callers should never touch `EvoGit.RemoteNode`/`EvoGit.RemoteConnection`/`EvoGit.RemoteConnections` directly.
- `DesktopLifetime` is desktop-only: gated on `EVOGIT_DESKTOP=1` + `EVOGIT_LIFETIME_PORT`, so the headless `genesis_server` release never starts it.
- Depends on `evo_git` application at compile and runtime.
