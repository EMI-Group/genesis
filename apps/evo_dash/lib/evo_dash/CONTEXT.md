# EvoDash Domain Logic

## Intent

Domain layer for the EvoDash Phoenix application — one module per file, mapped in the Routing Table below, with its contract in the API Surface.
Persistence and registry code (`EvoGit.Store`, `EvoGit.Store.Codec`, `EvoGit.TaskInfo`, `EvoGit.TaskRegistry` + `task_registry/`, `EvoGit.VCT`) lives in `:evo_git`; EvoDash owns none.

## API Surface

### `EvoDash.Application` (`application.ex`)

OTP Application callback module; supervision `:one_for_one`, `max_restarts: 10`, `max_seconds: 60`. The PUBLIC `children/0` builds the list — tests pin the endpoint's mode-INVARIANT presence, and it reads the desktop gating env vars at CALL time — and `start/2` passes it straight to `Supervisor.start_link/2`, in this order:

1. `EvoDashWeb.Telemetry`
2. `Phoenix.PubSub` (as `EvoDash.PubSub`)
3. `Task.Supervisor` (as `EvoDash.TaskSupervisor` — every node-aware data load and per-click RPC runs there, outside the LiveView process)
4. `EvoDash.WorkbenchSidebarCache`
5. `EvoDash.ChatHistory` (LiveViews mount after app boot, so it is always available)
6. `EvoDash.DirectoryPicker`
7. `EvoDash.UpdateStatus`
8. `{DynamicSupervisor, strategy: :one_for_one, name: EvoDash.ChatGPTLogin.Supervisor}` then `EvoDash.ChatGPTLogin` — SIWC flow supervisor (`:temporary` children, each binding its own `127.0.0.1` callback listener) + the flow-registry facade, both BEFORE the endpoint so a settings sign-in cannot race a page mount
9. `EvoDashWeb.Endpoint` — ALWAYS a child, in every mode: exactly ONE `genesis_server` per host serves the dashboard over HTTP (loopback by default) and toggles distribution at runtime on that same BEAM (`EvoGit.DaemonControl`, driven by `<launcher> remote start|stop`), so no env var may drop the endpoint
10. `{EvoDash.DesktopLifetime, []}` — appended only when BOTH `EVOGIT_DESKTOP=1` and `EVOGIT_LIFETIME_PORT` are set (only the Tauri sidecar sets both); the module's `init/1` self-disable is belt-and-suspenders

Before `Supervisor.start_link`, `start/2` creates `:evo_dash_active_tasks` through the idempotent private `ensure_ets_table/2`: owned by the long-lived application process (NOT a supervised child), so it survives child restarts and lives for the whole `mix test` run; a no-op when the table exists. `ActiveTasks`/`AccentCache` are pure ETS helpers with no process, so neither is a child.
`start/2` also calls `_ = EvoDash.ConnectionDiagnostics.attach()` (idempotent, non-fatal, NOT a child) in desktop AND normal modes. `EvoGit.Store`, the task-registry `Registry` and `EvoGit.TaskRegistry` are children of `EvoGit.Application`.

#### Boot memory profile (`mix phx.server` vs a `genesis_server` release)

- Children are mode-INVARIANT apart from `DesktopLifetime`: `RELEASE_NAME=genesis_server`, `EVOGIT_SERVER=1`, `:server_release` and `PHX_SERVER` only set `EvoDashWeb.Endpoint` `server: true` plus secret-key/logging handling in `config/runtime.exs`. No boot-time SQLite read or rehydration — this app owns no Store/Ecto code and every store it creates is empty (`:evo_dash_chat_history`, `:evo_dash_active_tasks`, `:evo_dash_accent_cache`); `UpdateStatus` starts at `initial_state()`, `DirectoryPicker` starts no `wxe_server`, Telemetry runs zero periodic measurements and no reporter, and the only PROD-only boot work is static-manifest warmup (`cache_static_manifest`, absent → skipped).
- The largest reachable RSS item is not here: the 11.7 MB `deps/llm_db` snapshot decoded into `:persistent_term` by the first model-metadata lookup (`EvoGit.AgentScheduler.init/1` → ReqLLM → `LLMDB.ensure_loaded!`), mode-invariant and off-heap. The only unbounded-by-default dashboard store is `ChatHistory` (opaque ETS transcripts, capped at 10 chats — at creation and by `HomeLive`'s `prune(10)` on New chat): runtime growth, not boot work, dying with the BEAM.

### `EvoDash.ChatGPTLogin` (`chatgpt_login.ex` + `chatgpt_login/`)

The ONE SIWC loopback implementation shared by the dashboard wizard and the CLI (PKCE/state/callback/exchange/persist exists exactly once).
`begin(account, opts)` → `{:ok, %{id, url, port, mode}} | {:error, reason}` binds `127.0.0.1` on `:port` (default `0` = ephemeral; the CLI keeps 1455) BEFORE minting the authorization URL, so the redirect URI is always the REAL `http://127.0.0.1:<bound port>/auth/callback`; the attempt (state/nonce/verifier) lives in the listener's own state.
`mode` is `:loopback` while the attempt owns that listener and `:manual` when it could NOT be bound — a bind failure degrades the attempt instead of failing it, the redirect URI then names a concrete port (1455 for an ephemeral request) and only a pasted callback can finish it.
`submit_callback(id, input)` → `{:ok, %{id: id}} | {:error, :unknown_flow | :already_finished | :invalid_callback | :no_code | :login_unavailable}` hands a pasted redirect URL, query string or bare code to the SAME attempt (the ACK only: the terminal result still arrives through `status/1` / the `:caller` notification) and is the manual completion `EvoDashWeb.SettingsComponents.ChatGPTSignInPanel` and the CLI both use; a rejected paste leaves the attempt pending.
`status(id)` → `:pending | {:ok, %{account, status}} | {:error, reason}`; `cancel(id)` → `:ok | {:error, :unknown_flow}`; `active_for(account)` → `id | nil`; `pending?/0`.
Terminal values `{:ok, %{account:, status:}}` (the store's status map, else `%{account_id: account}`) or `{:error, reason}` with `:authorization_denied` | `:authorization_timeout` | `:cancelled` | `:superseded` | `:loopback_listener_unavailable` | `{:flow_crashed, reason}` | any store/exchange reason (`:plan_not_authorized`, `:chatgpt_account_alias_in_use`, …) unchanged; retained `:retention_ms` (default `300_000`), after which `status/1` answers `{:error, :unknown_flow}` (as for an id never issued).
ONE flow per account: a repeat `begin/2` supersedes the old (terminal `{:error, :superseded}`, its `:caller` notified); a `:caller` gets exactly ONE `{:chatgpt_login, id, result}`.
Every exit path (success, failure, timeout, cancel, supersede, facade `DOWN`) stops the Bandit listener; flows are `:temporary` children of `EvoDash.ChatGPTLogin.Supervisor` monitored by the facade, so a crash is `{:error, {:flow_crashed, reason}}` and never takes the facade or the app down.
`chatgpt_login/callback.ex` serves only `GET /auth/callback` on a loopback host, validates `state`, and returns a self-contained HTML page (no params/tokens echoed, `cache-control: no-store`, `referrer-policy: no-referrer`); `error=` denies (`{:error, :authorization_denied}`) WITHOUT calling the exchange.
Call-time seams: `opts[:exchange] || Application.get_env(:evo_dash, :chatgpt_login_exchange, &EvoGit.Auth.ChatGPT.exchange/2)` and `opts[:store] || Application.get_env(:evo_dash, :chatgpt_login_store, EvoGit.Auth.ChatGPT.Store)`; a `:store` provides `path/1`, `registration/1`, `host_id/0`, `install/2`, `status/1`.
The store's install lock owns persistence and cross-process serialization (CLI and a running dashboard cannot corrupt each other); `ensure_started/0` (`@doc false`) boots supervisor + facade on demand, so `mix genesis.chatgpt login` works from a checkout without an application boot.
A successful sign-in is ONE side effect — the store's credential JSON under `<config_dir>/chatgpt/` — with no `config.toml`/`credentials.toml` write, no config-snapshot refresh and no PubSub broadcast; the resulting model list lives only in the terminal `%{models: …}` status map handed to `:caller`/`status/1` (detail: `chatgpt_login/CONTEXT.md`).

### `EvoDash.ChatGPTCLI` (`chatgpt_cli.ex`)

Thin terminal client for `genesis chatgpt <login|status|models|logout|import FILE> [--account NAME] [--port PORT]` (default port 1455): `EvoDash.ChatGPTLogin.begin(account, port: port, caller: self())`, then a bounded wait for `{:chatgpt_login, id, result}` with a `status/1` fallback.
`login` prints the URL, "Waiting for ChatGPT authorization." and, on success, "Connected ChatGPT account <name>." plus the model list; the usage text and the `ChatGPT: <inspect>` / exit-code-1 error contract are unchanged.
Because a browser on another machine cannot reach this host's loopback listener, `login` ALSO reads stdin: a pasted redirect address (or just the code) goes through `ChatGPTLogin.submit_callback/2` to the SAME attempt, a rejected paste prints a retry hint and restarts the bounded wait, and a `mode: :manual` attempt says up front that only the pasted link can complete it.
`status`/`models`/`logout`/`import` stay store-backed through the same call-time `:store` seam, which makes every command hermetically testable.

### `EvoDash.ChatHistory` (`chat_history.ex`)

In-memory (ETS-backed, NO disk persistence) chat store for the Genesis Assistant page (`EvoDashWeb.HomeLive`): a GenServer (child of `EvoDash.Application`, after `TaskSupervisor`, before the Endpoint) owns a named public ETS table (`:evo_dash_chat_history`, `:public`, `read_concurrency: true`) that dies with it (no heir) — chats survive LiveView remounts, not BEAM restarts or a store crash.
**Single-key operations hit the public table directly** (`get_state/1`, `put_state/2`, `list_chats/0`, `conversations/0`, `get_draft/1`, `put_draft/2`, `delete_draft/1`, the current-pointer verbs): atomic per call and TOTAL when the table is missing (`nil` / `[]` / `:ok`), so a transcript save never queues behind the GenServer. **Only compound operations are GenServer-serialized**: `new_chat/0,1` (inserts the chat AND makes it current for that scope), `delete_chat/1` (removes AND clears every scope's pointer to it), `prune/1`, `reset/0`, `discard_workbench_draft/1`. External DIRECT READS of the table are safe (atomic); mutations must go through the API.
Per-chat state is an opaque `term()` (the LiveView owns the transcript shape). API: `new_chat/0,1` (id from `System.unique_integer([:positive])`, unique but NOT guaranteed ordered; a separate internal monotonic creation seq drives newest-first order; keeps only the newest `@max_chats` (10), so the cap applies at CREATION too), `default_scope/0` (`{nil, node()}`), `current_chat_id/0,1`, `set_current_chat/1,2` (no existence validation — a dangling id renders an empty chat), `list_chats/0` (ids, newest-first), `conversations/0` (`[%{id:, state:}]` newest-first from ONE table scan, no N+1 `get_state/1`), `delete_chat/1` (no-op for unknown ids), `prune/1` (keeps the newest N — the explicit lever; non-integer/negative bounds ignored, `0` clears all), `put_state/2` (upserts; an unknown id registers a new newest chat), `get_state/1` (`nil` for unknown/unset), `reset/0` (test helper). All callbacks are total.
Table entries: `{{:current, {client_id, node}}, chat_id | :none}` (current pointer, SCOPED per browser client + BEAM node, so two viewers never adopt each other's conversation) and `{:chat, chat_id}` → `{seq, state}`. Enumeration uses `:ets.match_object/2` with a plain match pattern — NOT `:ets.select` match specs, whose match heads on this OTP cannot contain nested tuples and therefore cannot match tuple keys.
Interactive Assistant conversations are keyed by their SESSION agent id (a positive integer is already a valid chat id), so no synthetic mapping exists.

#### Chat isolation and recovery limits

The current pointer is scoped `{client_id, node}` but chat STATE is keyed only by `chat_id`, so any caller that knows a chat id can read or overwrite it: no user or authorisation layer, no remote forwarding (a remote node's conversations live in that node's BEAM), and no ownership/node-isolation enforcement even though the opaque state may carry caller-defined node metadata. `put_state/2` replaces the entire stored state with no version check or merge, so serialization does not stop two LiveViews overwriting each other's stale snapshots; there is no transcript byte/message cap, TTL, disk journal, replication, subscription or task/approval reconciliation, and `prune/1` bounds chat count only when explicitly called.
The single-key path is total (direct ETS; missing table answers `nil`/`[]`/`:ok`); the compound path uses ordinary synchronous `GenServer.call/2` with no failure guard, so a dead or busy ChatHistory process can exit the caller even though callbacks handle malformed values safely. Two documented oddities stay pinned as-is (`test/evo_dash/chat_history_test.exs`, `test/evo_dash/safe_call_test.exs`): `prune/1`'s `pos_integer()` spec excludes the zero it documents as clear-all, and `SafeCall.run/1,2`'s specs admit zero-arity functions while it handles invalid nonzero-arity ones.

### `EvoDash.NodeContext` (`node_context.ex`)

Thin client for the dashboard's SSH remote-development feature; wraps three `:evo_git` layers behind one API:

1. **`EvoGit.RemoteConnections`** — connection-target persistence (`list_targets/0`, `get_target/1`, `save_target/1`, `delete_target/1`).
2. **`EvoGit.RemoteConnection`** — connection lifecycle (a per-target GenServer that stops again after a graceful disconnect, so it may not be running at call time); `connect/1`, `disconnect/1`, `bootstrap/1,2`, `connection_status/0,1`, `connected?/1` degrade through the private `with_remote_connection/4` guard to `{:error, :remote_connection_unavailable}` / `%{}` / `:disconnected` / `false`.
3. **`EvoGit.RemoteNode`** — the cross-node RPC helpers below.

- **Task, review, project and config wrappers are one-line `EvoGit.RemoteNode` delegations and the node is the ONLY routing input** (apart from the local-first process path, no local/remote branch lives here — the split is `EvoGit.RemoteNode.call_remote/4`). No module here references `EvoGit.Store`/`EvoGit.TaskRegistry`; the only direct `:erpc.call/5` is `approval_response/3`'s remote arm.
- **Connect is event-driven at the core**: `connect/1` returns `{:ok, :connecting}` (a duplicate while `:connecting`/`:connected` is an idempotent no-op) and terminal outcomes arrive ONLY via the `"remote_connections"` broadcast `{:remote_connection_status, target_id, status_map}` (`:connecting`, `:connected`, `:error` with `last_error`). The wrapper can queue behind a long bootstrap, so every LiveView/LiveComponent entry point MUST call it inside `EvoDash.TaskSupervisor`.
- **Interactive sessions**: `start_session/2` (`%EvoGit.AgentSpec{}` or `SessionOpts.build/1` opts → `{:ok, agent_id}`, no blocking), `send_session_message/4` (`:queue` default, `:interrupt` opt-in; binary or `%{text:, attachments:}`), `close_session/3` (`:normal`; the ONLY non-cancel way out of `:awaiting_input`), `await_close/3` (default 30 000 ms bounds the WAIT only — over RPC the whole call is capped by `:remote_rpc_timeout`, so long human-driven waits are a local-core operation), `list_awaiting_input/1` (entries `%{agent_id, task_id, session_pid, task_number, mode}`; any non-list answer degrades to `[]`, so `[]` also means "the node could not be asked"). Envelopes pass through VERBATIM — a session's `{:error, {:session, reason}}` and a transport `{:error, {kind, reason}}` are both the node's real answer.
- **Assistant-session extras** — `send_message_with_workspace/5`, `stop_current_turn/2`, `update_assistant_workspace/3` call `EvoGit.Agent.Session` directly when `target == node()`, else `call_remote/4`. **Agent streams**: `subscribe_agent_deltas/1`/`unsubscribe_agent_deltas/1` are LOCAL `EvoGit.Agent.Stream` calls, `register_agent_watcher/3`/`unregister_agent_watcher/3` are local-only (a remote node answers `{:error, {:not_found, :invalid_consumer}}` / `:ok` with no call), `watch_agent_snapshot/2` delegates to `EvoGit.RemoteNode.watch_snapshot/2`.
- **Task wrappers** — summary/ID/page/changed-since/unique-paths reads, `start_task/3` (`{:ok, %TaskInfo{}}`), `get_task/2`, `get_task_lite/2`, the archive pair, the cancellation pair (`cancel_task/2` GRACEFUL → `:cancelling`, result/archive preserved; `force_kill_task/2` → `:failed` with a nil result, escalation from `:cancelling`), the pause pair (`pause_task/2` freezes every agent of the task at its current position → `:pausing` → `:paused`; `resume_task/2` re-dispatches the SAME task id and thaws the WHOLE frozen tree in place with the same agent ids, refusals `:not_found`/`:not_running`/`:not_pausable`/`:not_resumable`/`:scheduler_unavailable`/`:not_paused`), `delete_task/2`, `clear_finished_tasks/1`.
- **Lightweight reads** are the escape hatch from full `%TaskInfo{}` rows, and every one degrades rather than raises: `list_tasks_page/2` → `%{rows: [summary_map], total: non_neg_integer}` of atom-keyed summary maps with `:limit` (default 25, capped 50), `:offset` and the filters `:status` (the on-disk STRING), `:project_path`, `:review_status`, `:session_mode`, `:search`; `get_task_lite/2` = the full struct with result data but NO `:archive_records` (the archive lives only in the relational `task_agent_archives` table); `list_task_archives/3` → `%{entries: [string-keyed map], total: non_neg_integer}` for one page ordered `depth, agent_id`, with `:limit` (default 100, 1..1000), `:offset`, `:include_results` (default false — the entry then omits `"result"`), `:include_settings` (default false — the export-only `"llm_settings"`/`"agent_settings"`/`"foreign_repos"` columns are absent) and `:include_total` (default true; false skips `COUNT(*)` and normalizes `total: nil` to `0`); `get_agent_archive/3` fetches ONE full entry on demand. Failures degrade to `%{rows: [], total: 0}` / `nil` / `%{entries: [], total: 0}` / `nil` via `normalize_archive_page/1` (atom- or string-keyed pages, non-list entries → `[]`, bad total → `0`) and `normalize_archive_entry/1`, and no dashboard page issues `list_tasks_paginated/2` or `get_task/2`.
- **Data shapes forwarded verbatim**: the 18-key summary (`id, status, review_status, started_at, finished_at, type, project_path, opts, branch_name, model_id, agent_count, base_sha, commit_sha, lease_expires_at, updated_at, error, session_mode, pause_kind`; `updated_at` a raw ISO string, `pause_kind` `:clean | :dirty | nil`, `opts` a decoded keyword list, `error` nil unless `:failed`, no `result`/`logs`/`usage`/`archive_metadata`); `list_task_ids/2` = `id/status/updated_at` maps; `projects/1` = `[%EvoGit.VCT.Mount{}]`.
- **No field allowlist or projection exists in this layer**: every read forwards the core's payload untouched (no pattern-matching on `%EvoGit.TaskInfo{}` fields, no key filtering), so a NEW core summary key or `%TaskInfo{}` field — e.g. a pause snapshot/phase field — reaches callers automatically and only the documented key lists in `node_context.ex` + this file need updating.
- **No task-status enumeration lives in this directory**: status atom sets (`:pausing`/`:paused`/`:awaiting_input` busy/live lists) are owned by the web layer (`evo_dash_web/live_hooks/node_aware.ex` `@active_statuses`, page modules), and `EvoDash.ActiveTasks` stores whatever lists it is handed verbatim.
- **Core-side branch**: `EvoGit.RemoteNode.call_remote/4` calls the local `EvoGit.AgentScheduler.RemoteAPI` directly (`{:ok, result}`, errors not caught) or `:erpc.call/5` (30 s default, `:remote_rpc_timeout` override) normalizing failures to `{:error, {kind, reason}}`; per-fn wrappers then collapse list-shape errors to `[]`, paginated to `{[], 0}`, `get_task` to `nil`.
- **Review & git operations** (`list_commits/3`, `load_review_data/3`, `load_review_metadata/3`, `load_file_diff/5,6`, `load_review_metadata_from_shas/4`, `list_commits_from_shas/4`, `load_commit_files/3`, `load_commit_file_diff/4`, `merge_branch/3,4`, `default_merge_target/2`, `list_branches/2`, `reject_branch/3`, `create_github_pr/5`, `github_upstream/2`, `list_github_issues/3`, `github_issue_markdown/3`, `branch_exists?/3`, `check_merge/4`, `list_commit_graph/4`, `list_task_commit_graph/5`, `set_review_status/3`, `set_review_metadata/4`) return the VERBATIM underlying value in BOTH paths — only a transport failure surfaces as `{:error, {kind, reason}}`. Every repo-scoped op takes ONE absolute `repo_path` (no `repo_id`/target parameter anywhere in the chain), so a per-repo caller calls once per path; ONLY `set_review_status/3` and `set_review_metadata/4` are `task_id`-keyed (one base/commit SHA pair, not representable per repo). No runner seams live here — review/export seams resolve in the web layer.
- **Managed processes are LOCAL-FIRST**: `list_processes_result/2`, `list_processes/2`, `get_process/2`, `process_stats/2`, `process_control/4` call `EvoGit.ProcessManager` in-BEAM when the viewed node IS this BEAM, else `call_remote/4` with `EvoGit.AgentScheduler.RemoteAPI`. `opts`/`action`/`reason` pass verbatim; the control action resolves first (`:pause | :resume | :kill | {:signal, s}`, anything else → `{:error, {:unknown_action, action}}`); `list_processes/2` degrades to `[]` while `list_processes_result/2` preserves the error so the inspector can offer a retry; an absent or dead manager answers `{:error, :process_manager_unavailable}` and a non-binary id `{:error, :not_found}` with no call. Remote transport is the call-time seam `Process.get(:node_context_process_rpc) || Application.get_env(:evo_dash, :node_context_process_rpc, &EvoGit.RemoteNode.call_remote/4)`; tests: `test/evo_dash/node_context_test.exs`.
- **Custom agents & tools** — `list_custom_agents/1`, `save_custom_agent/2`, `delete_custom_agent/2`, `save_model_selection_script/2`, `reload_custom_agents/1` target the viewed node's own `agents.toml`; a failed fetch reads as `{:ok, %{agents: [], model_selection_script: nil, script_status: :ok}}`. `custom_tools_status/1` passes `EvoGit.RemoteNode.custom_tools_status/1` through VERBATIM (`%{ok: [%{name, file, module, read_only?: boolean}], errors: [%{file, reason}]}`, read from the node's `<config_dir>/tools/`) and does NOT degrade — RPC failures stay `{:error, term()}`.

#### Projects, workspaces & the VCT registry (no project CRUD in this layer)

A project is a VCT PROJECT mount (`%EvoGit.VCT.Mount{}`: `point` `vct:///projects/<name>[-N]`, absolute OS `path`, `name`, `kind`, `last_opened_at`); reserved mounts (`vct:///genesis-source`) are never returned, and there is no project entity or CRUD here.
- `projects/1` → newest-opened first, `[]` on RPC failure or a non-list payload.
- `mount_project/3` `(node, path, name)` → `{:ok, %EvoGit.VCT.Mount{}} | {:error, term()}`; `forget_project/2` `(node, key)` → `:ok | {:error, :not_found | :invalid_point | {kind, reason}}`, `key` being a VCT point or a raw OS path.
- `read_project_config/2` → parsed `genesis.toml` map | `nil`; `list_tasks_summary_by_path/3` → `[summary_map]`; `list_path_suggestions/2`, `dir?/2`, `file_exists?/2`, `ls/2` are the path probes.
- Workspaces group, never execute: `workspaces/1` (workspace mounts — never in `projects/1`), `workspace_entries/1` (ONE node round trip, members already resolved; entries `%{workspace:, members:, missing:, nested:}`; degrades to `[]`), `create_workspace/4` (idempotent slug-keyed UPSERT; `:invalid_name` / `{:member_is_workspace, point}` / `{:invalid_member, ref}` / `:invalid_members` / `:vct_unavailable`), `workspace_members/2` (a point or bare name → the same entry map, or `:not_found`/`:not_a_workspace`/`:invalid_point`) and `workspaces_for/2` (covering workspaces of a point/name/path, `[]` when none or on failure) — per-function detail: `apps/evo_dash/CONTEXT.md`.
Every one of those calls wraps the core delegation in `EvoDash.VCTScope.scoped/1`, which carries the VCT instance designated by the caller's SPAWN CHAIN (`Process.put(:evogit_vct_server, name)` in a page owner reaches the page and its supervised load tasks) — default-inert, so production keeps the registered singleton.
The registry lives in each node's core (`EvoGit.VCT`, `vct_mounts`, supervised in `EvoGit.Application`), so it is implicitly per-node; the core owns point allocation, newest-first ordering, the `max_projects/0` cap (100, oldest evicted; workspaces uncapped) and the `{:vct_updated, node}` broadcast on `"vct"`. A mount's OS path may be missing: not filtered, never created.
No project state is cached here — `ChatHistory` holds opaque chat state, `ActiveTasks` task lists, `AccentCache` an accent per target id; the only "current project" state is the Projects page's `?project=` param plus its browser draft (`EvoDashWeb.DraftScope`) and the Assistant's per-chat `workspace` selection.
Remote identity is opaque here: lifecycle functions take a target-id STRING, RPC functions a BEAM `node()` atom; NodeContext never builds `genesis_remote_<id>@127.0.0.1` (that mapping lives in `EvoGit.RemoteConnection`), and local-vs-remote routing happens inside `EvoGit.RemoteNode.call_remote/4`, never here.

#### Configuration and task-payload boundary

`get_resolved_config/1` is the ONLY path to `EvoGit.Config.resolve/0` (`call_remote(node, EvoGit.Config, :resolve, [])`, remote `:erpc` bypassing `RemoteAPI`), answering an explicit `{:ok, config}` envelope; `get_remote_config/1` is scheduler RAM (`EvoGit.AgentScheduler.get_config/0`, documented `%{}` fallback) with no production dashboard caller; `get_remote_config_status/1` reaches `EvoGit.Config.config_status/0`.
`save_user_config/2`, `save_credentials/2` and `start_task/3` are plain synchronous forwards with no local validation, schema conversion, migration or transactional save-and-reload; `start_task/3` has no opt whitelist, so mode strings, model specs/locks, custom-agent selection and repo-less constraints are caller/core contracts. Known opts include `:persistent_state` (boolean, absent → core default `true`), which reaches the core only through `EvoGit.TaskControl.start/1`'s `@start_keys` whitelist (in `:evo_git`) and is advertised by the `genesis_start_task` MCP tool.
The layer offers no provider/model CRUD, OAuth-status, peak-schedule, connection-test or default-model API and no provider-profile flattening or model-selection normalization; callers use generic `call_remote/4` or build whole config maps and task keyword lists themselves.
`reload_remote_config/1` (→ `EvoGit.RemoteNode.reload_config/1` → `AgentScheduler.RemoteAPI.reload_config/0`) is the force-disk-reread path; its sole dashboard caller is the remote-credentials save, and `save_user_config/2` relies on the core's implicit post-save reload.
No config residency, freshness, generation or subscription state lives here — it never subscribes to a config topic (only the agent-stream delegates), so a broadcast must be consumed by the owning LiveView/`NodeAware`, and the async-load guards here are page-private counters, not config generations. The only config-dir filesystem access in this directory is `EvoDash.MCP.Auth` reading `<config_dir>/mcp-token`; nothing here reads `config.toml` or `credentials.toml`.

#### Approval routing and control-result caveats

`approval_response/3` accepts only `"approve"`, `"deny"`, `:approve`, `:deny` (anything else is rejected before dispatch) and adds no request-id/task/agent/session ownership validation; it transports only the BEAM node, request id and decision — never the displayed command — so exact invocation binding must be enforced by the core's pending-request/execution association.
Routing compares the supplied node atom with `node()`: local → guarded `EvoGit.CommandApproval.respond/2` (`Code.ensure_loaded?` + `apply/3`, `{:error, :command_approval_unavailable}` when absent), remote → `EvoGit.AgentScheduler.RemoteAPI.respond_approval/2` with a HARDCODED 15 000 ms `:erpc` timeout instead of `RemoteNode`'s generic budget.
The local guard catches exits and missing modules only, so a local responder exception can still raise; the remote branch catches every exception/exit/throw into an error tuple. `restart_remote/1`/`stop_remote/1` discard the RPC result and return `:ok`, so their success value cannot prove delivery.
Data wrappers (`list_agents/1`, `get_agent_history/2`, `paused?/1`, task lists) document empty/false fallbacks that conflate unavailable with genuinely empty; `get_resolved_config/1` and `get_recent_system_samples/1` preserve explicit envelopes and are preferable when a consumer must tell the two apart.

### `EvoDash.Seam` (`seam.ex`)
The ONE resolver for every injectable `:evo_dash` seam, so an override can be scoped to a test's own process tree instead of the whole BEAM.

### `EvoDash.DesktopLifetime` (`desktop_lifetime.ex`)

Desktop-only Tauri-shell lifetime watcher over a TCP lifetime pipe: the Rust shell binds a `TcpListener` on `127.0.0.1:0`, holds one connection per backend instance, passes the port as `EVOGIT_LIFETIME_PORT`, and never writes on it; when the shell dies the OS closes the socket, `:gen_tcp.recv/3` errors and the watcher stops the VM (`System.stop(0)`), freeing the port.
Appended by `EvoDash.Application.children/0` only when BOTH `EVOGIT_DESKTOP=1` and `EVOGIT_LIFETIME_PORT` are set (`init/1` also self-disables on a missing/empty/invalid port), so the headless `genesis_server` release never starts it. It starts LAST, after `EvoDashWeb.Endpoint`, with its blocking connect+recv work deferred to `handle_continue/2`, so it never delays boot or the listener bind (the endpoint in turn cannot bind before `EvoGit.Application`, including `EvoGit.Store`'s synchronous migrations).
Test seams: `:parent_stop_fun` (app env, read at `init/1`) plus `:connect_retries`/`:connect_retry_delay` and `:recv_retries`/`:recv_retry_delay`/`:recv_fun` (`start_link` opts ONLY — the application starts it with `[]`, so production budgets are not config-tunable). Budgets: up to 5 connect attempts of a 1 000 ms `:gen_tcp.connect` + 200 ms sleep (≈6 s worst case, normally instant because the shell's listener backlog is bound BEFORE the backend spawns), then 3 recv retries × 200 ms.

Only two outcomes invoke the stop fun: connect-budget exhaustion (logs `Tauri shell is gone (lifetime connection could not be established)` — indistinguishable from a live-but-not-accepting shell, a stale/foreign port or a firewall) and a GENUINE peer close `{:error, :closed}` (logs `Tauri shell is gone (lifetime connection closed) — shutting down`); every other recv error (`:econnreset`, `:eacces`, `:timeout`, …) is AMBIGUOUS — warn, retry the budget, then give up with `[desktop] lifetime recv kept failing … after retry budget exhausted — shutting down` (`{:ok, _data}` resets the counter) — so an OS/AV/firewall reset or a hard-killed peer ends the VM here rather than through the peer-close branch, while `classify_recv_result/1` (`:closed` | `:data` | `:ambiguous`) is the public pure classifier a log cross-check must accept all three of.
It reacts to the SOCKET, not the shell process: an orderly FIN from an early-ended Rust hold thread (or an accept-thread failure) still reads as shell death while the shell lives. The warning is NOT logged on BEAM-initiated stops (tray-quit confirm → `DesktopQuit.default_stop/0`, System-page Stop, update apply → `UpdateStatus.stop_backend/0`, all via the shared `:desktop_quit_stop_fun` seam), because `System.stop(0)` tears the VM down before its own socket can observe a peer close — it appears only when the SHELL closes the pipe first.
Exit code 0 is ambiguous: the Tauri watchdog's `classify_exit/2` (`desktop/src-tauri/src/backend_watchdog.rs`; semantics owned by `desktop/src-tauri/CONTEXT.md`) treats `Some(0)` as an INTENTIONAL shutdown, so a spurious lifetime close makes the shell `app.exit(0)` and the app vanishes silently instead of showing the error page and restarting the backend. Nothing is logged on a successful start or connect, so `backend.log` proves only the pipe's loss.
Discriminator: children stop in reverse start order, so the endpoint stops AFTER the warning and an open LiveView socket adds the drainer's `DRAINING N of M total connection(s) for socket Phoenix.LiveView.Socket …` line under the socket HANDLER module (NOT the endpoint — check both spellings); `<data_dir>/logs/shell.log` records `backend exited cleanly (code 0) — treating as intentional shutdown` for THIS stop, byte-identical to the tray-quit / System-page Stop / update-apply stops, so the `backend.log` lifetime warning is the only proof the SHELL closed the pipe rather than the BEAM stopping itself.

### `EvoDash.AttachedFile` (`attached_file.ex`)

Reads attached objective files picked from the objective editor's attach-file '+' button (local files on the dashboard node).
`read/1` dispatches on extension: plain text (`.txt`/`.md`/any) verbatim and trimmed; `.docx` to plain text with OTP stdlib only (`:zip` + regexes — only `word/document.xml`, headers/footers/footnotes/comments ignored, field codes stripped); `.pdf` to Markdown via the pure-BEAM `ex_pdf` reader (each page → `## Page N`, a conversion note prepended; scanned/image-only → `{:empty, _}`, password-protected → `{:invalid, ...}`, opened with `recover: true`). `read/1` intentionally treats unknown extensions, including media ones, as plain text while `read_uploaded/2` explicitly recognizes image/audio; any shared document-dispatch helper must preserve those distinct outer policies. The upload media lookup is rebuilt from fixed module-attribute maps by `upload_media_types/0` on each call, and text/DOCX/PDF dispatch is repeated between `read/1` and `read_uploaded/2`.

### `EvoDash.SourceStatus` (`source_status.ex`)

Total (never-raising) shared wrapper around the optionally-present `EvoGit.SelfReflectiveSource` core backend: guards each call with `Code.ensure_loaded?/1` + `function_exported?/3` (arity 0) and dispatches via `apply/3` — a direct call to a possibly-missing module would emit an "undefined function" compile warning — returning `{:unavailable, reason}` (`:module_missing` | `:function_missing` | `:call_failed`) instead of raising, so callers can render a degraded UI.
Single private `guarded/2` dispatcher keeps the four public wrappers one-liners: `available?/0` → `boolean() | {:unavailable, reason}`; `status/0` → map or `{:unavailable, reason}`; `clone/0`, `update/0` → `{:ok, status} | {:error, reason} | {:unavailable, reason}`. Consumers: `EvoDashWeb.SystemLive.SourceCard` + `EvoDashWeb.HomeLive`.
The `status/0` map may additionally carry the OPTIONAL keys `source_mode` (`:source` | `:release`), `running_version` (string | `nil`) and `managed_dir` (string).
Because they are optional, a backend that omits them still yields a renderable map and the card keeps rendering its clone/update buttons (`SourceCard.running_from_source?/1` tolerates absence).

## Constraints

- `EvoDash.Application` starts NO persistence/registry children — those belong to `EvoGit.Application`; this app depends on `evo_git` at compile and runtime.
- `EvoDash.TaskSupervisor` IS started and IS used (async loads across all LiveViews). Do NOT remove it.
- `EvoDash.ChatHistory` is in-memory only, and its tables are mutated ONLY through the API (contract: `EvoDash.ChatHistory` above).
- `NodeContext` keeps its public API stable; web-layer callers should never touch `EvoGit.RemoteNode`/`EvoGit.RemoteConnection`/`EvoGit.RemoteConnections` directly.
- `DesktopLifetime` is desktop-only: gated on `EVOGIT_DESKTOP=1` + `EVOGIT_LIFETIME_PORT`, so the headless `genesis_server` release never starts it.
