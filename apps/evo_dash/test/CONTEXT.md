# Test Directory

## Intent

ExUnit suite for the `:evo_dash` app: the runner bootstrap, shared support modules, and suites that mirror `apps/evo_dash/lib/`.
Test files (`*_test.exs`) live in `evo_dash/` and `evo_dash_web/` beside the code they cover, plus `support/config_dir_test.exs` and `evo_dash/runtime_config_test.exs` covering the root `config/runtime.exs`; bootstrap is `test_helper.exs`, helpers are `support/`.
`support/` holds 7 compiled `.ex` modules plus ONE test script, `support/config_dir_test.exs` (only `*.ex` files are compiled, so ExUnit loads the `_test.exs` like any suite).
Case modules split between `async: true` and globally constrained `async: false` suites; the sync inventory and parallelism policy live under "Async policy".
`mix test apps/evo_dash/test` from the umbrella root runs exactly this app's suite; bare root `mix test` also runs the `evo_git` suite first.
The domain singletons (`EvoGit.Store`, `EvoGit.TaskRegistry`, `EvoGit.TaskInfo`, `EvoGit.VCT`) live in `:evo_git` and are tested there; per-test Store/TaskRegistry isolation is `EvoDash.Test.IsolatedTaskStore` (children of `EvoGit.Supervisor`, NOT `EvoDash.Supervisor`).
`EvoGit.VCT` is the project registry: each opened project is a `%EvoGit.VCT.Mount{}` (`point` = `vct:///projects/<name>`, absolute OS `path`, `name`, `kind`, `last_opened_at`) persisted in the shared task store's `vct_mounts` table, newest-opened first, capped by `EvoGit.VCT.max_projects/0` (100 by default; over-cap registration evicts the oldest).

## API Surface

### `test_helper.exs`

`XDG_DATA_HOME` → `<tmp>/evogit_test_data`; the real per-run database dir comes from `config/test.exs`'s `:evo_git, :data_dir` (`.../evogit_test_data/genesis-<os pid>-<unique int>`), shared by both umbrella apps within one run and unique per BEAM across runs.
`XDG_CONFIG_HOME` → a run-unique EMPTY dir (`.../evogit_test_config/genesis-<os pid>-<unique int>`), so nothing reads or writes the developer's real `~/.config/genesis`; the redirect is a no-op on macOS (`EvoGit.Platform.base_dir/3` ignores XDG there).
It is only the FALLBACK: a suite needing its own config dir isolates it per process (`EvoDash.Test.ConfigDir.isolate!/1` in `setup`) and never repoints the BEAM-global env var.
`ExUnit.after_suite/1` removes ONLY this run's own data dir and config dir, never the shared `<tmp>/evogit_test_data` / `<tmp>/evogit_test_config` parents (a concurrent run owns siblings).
Directory picker disabled (`Application.put_env(:evo_dash, :directory_picker, enabled: false)`, mirrored by `config/test.exs`) so no native modal dialog can hang the suite.
`:evo_git, :nix_enabled` pinned `false` so `EvoGit.Nix.enabled?/0` never reads the developer's config or shells out to real nix; suites needing nix enable it explicitly.
Six CALL-TIME timer seams are shrunk: `:agents_live_flush_ms` (10), `:agents_live_commit_graph_tick_ms` (10), `:system_samples_seed_retry_ms` (10), `:flush_loading_poll_ms` (1), `:node_aware_reload_debounce_ms` (10), `:llm_retry_backoff_base_ms` (25, an `:evo_git` seam).
The last one exists so a REAL provider retry (503 / truncated stream) costs 25 ms instead of the production ~1 s jittered backoff; only `async: false` modules may pin it, because ExUnit drains the async cohort first.
The LLMDB catalog is warmed ONCE here (`LLMDB.Catalog.ensure_loaded!()`) before the parallel phase: its first touch is a `:global`-locked packaged-catalog parse, and inside a scheduler callback that first touch wedges every scheduler caller for seconds.
Each seam is read at the call site via `Application.get_env(:evo_dash, key, <prod default>)`, so production timings are untouched when the block is absent.
`ExUnit.start(capture_log: true)`.
The default-inert per-process config-dir seam: `Application.put_env(:evo_git, :config_dir_fun, {EvoDash.Test.ConfigDir, :resolve, []})` — the same `{m, f, a}` shape and process-dictionary key (`:evogit_config_dir`) `:evo_git`'s own helper installs, so a root `mix test` resolves identically whichever helper loaded last and production (which never sets the key) is byte-identical.
`config/test.exs` additionally disables the system sampler (`:system_sample_interval_ms` 86 400 000) and shortens the finalizing watchdog grace to 1 minute.

## Notes for Agents — cross-cutting rules

### Console output must be zero stray lines
`capture_log: true` is WINDOW-based (ExUnit swaps the `:default` handler only while ≥1 test runs), so a Logger line emitted in a between-test gap by a global/async process prints to the console.
Any test that triggers logged work from a process OUTSIDE the test process (TaskRegistry crash, offloaded `EvoGit.Store` read, reflect-task `:llm_not_configured`, provider request, remote-connection warning, desktop-lifetime watcher) must capture the triggering action AND await that work inside the same capture window.
Use `ExUnit.CaptureLog.capture_log/2` for fire-and-forget work and `with_log/2` when the call's return value is also asserted.
Never silence noise by raising the global Logger level.
The one leak class the suite structurally prevents is a `EvoGit.TaskRegistry` read worker calling a store that is being stopped; keep `IsolatedTaskStore`'s ordered teardown instead of reaching for a Logger-level silencing.

### Deterministic waits (no fixed sleeps, no tight windows)
Bounded polls run at a 1–2 ms cadence (`@wait_poll_ms 2`, `@poll_ms 1`); a fixed `Process.sleep` is never a wait mechanism.
`refute_receive`/`refute_push_event` may use a 0 ms window ONLY after a preceding drain or `:sys.get_state` round-trip has provably completed the mailbox.
A timed NEGATIVE window ("nothing else arrives") is dead time unless the claim itself is timing: prefer a structural witness read through `assigns/1`, then a 0 ms refute.
The witness idioms, each proven non-vacuous in place:
- a monotonic counter / flag written INSIDE the same callback that spawns the work (`chat_fetch_seq` for a history fetch, `approval_responses[id]` for an approval dispatch, `send_pending`/`send_in_flight` for an upload-gated send);
- the supervised-child SET (`Task.Supervisor.children(EvoDash.TaskSupervisor)` filtered by `:"$callers"`), because `EvoDash.SafeCall.start/3` registers its child synchronously before the click returns;
- a sole-sender serial worker parked in its idle `receive` (`Process.info(pid, :current_function)`), which proves it has emitted everything it was going to (`home_live/watch_readiness_test.exs` `await_worker_idle/2`).
Never shorten a window that IS the detection mechanism; positive assertions keep generous second-scale timeouts so real breakage still fails loudly.
`assigns/1` is a synchronous `:sys.get_state(view.pid, 30_000)` round-trip and Erlang guarantees per-sender ordering, so `send(view.pid, msg)` followed by any `assigns/1` read is already synchronized.
Always pass that explicit timeout: `:sys.get_state/1`'s 5 s default exits the test whenever the LiveView is starved on this shared host.
The same applies to `Phoenix.LiveViewTest.render_async/2`, whose 5 s sibling is its 100 ms DEFAULT: pass the file's async budget (`render_async(view, async_wait_budget())` in `projects_live_test.exs`), because a fixed 100 ms is a load assumption, not a correctness bound.
Debounce-sensitive waits poll the page's own pending flag or reuse the file-local `wait_until/2` / `flush_*_load/2` helper; async-load deadlines and poll budgets are 30 s module attributes (`@async_wait_budget_ms`, `@assigns_timeout_ms`, `@runner_start_timeout`, `@settle_timeout_ms`).
Per-suite wait contracts: `live/CONTEXT.md`, `live_hooks/CONTEXT.md`, `evo_dash/CONTEXT.md`.

### Per-test config dirs — cleanup drains supervised writers before removing
`EvoDash.Test.ConfigDir.isolate!/1` (installed from a `setup` block) creates one unique `<tmp>/<prefix>-<int>` dir per test and removes it in `on_exit`.
That removal is only safe while no LIVE process can recreate an entry under it, and the shared `EvoDash.TaskSupervisor` never stops children per test: a spawned page-load child keeps the test pid in its `:"$callers"` chain, resolves `<override>/genesis` and writes a skeleton (`EvoGit.RemoteConnections.list/0`), so `File.rm_rf` can meet a just-recreated tree and fail `{:error, :eexist, _}`.
The seam's invariant (detail: `support/CONTEXT.md`): the `on_exit` closure captures the REGISTRAR pid and first waits, monitor-based and bounded, for every `EvoDash.TaskSupervisor` child that still lists it in `:"$callers"`, then removes the dir; a surviving `:eexist` is retried boundedly for a re-creator with no registrar in its chain, and every other error still raises through `File.rm_rf!/1`.
`isolate!` is therefore the covered path — a module-level `isolate_module!` dir is only backstopped, because its registrar is the `setup_all` process, which appears in no child's chain.
A new config-isolating suite needs nothing extra: call `isolate!/1` from `setup` and keep the module `async: true`.
The drain also logs a `Logger.warning` when it actually WAITS more than 1 s (two `System.monotonic_time` reads otherwise, so it is free and silent on a healthy run) — a blocked drain is invisible in ExUnit's per-test time and was the symptom of the suite's two worst hidden costs.
A test must RELEASE a blocking stub/worker it started; leaving one to time out makes the test pay that timeout serially in this drain, outside every reported timing.
The historical biggest offender was not a leaked stub but `:global` lock contention on the LLMDB catalog load (see the warm-up in `test_helper.exs`).

### Mount funnels — a page-load result must never clobber test-driven state
Some LiveViews spawn an `EvoDash.TaskSupervisor` child at mount or on a `handle_params` patch, and its result message REPLACES assigns with the mount-time snapshot.
Apply the file-local funnel right after `live/3` (and after the relevant `render_patch/2`), BEFORE driving any event: `settings_live_test.await_mount_async_loads/1`, `review_live_test.flush_review_load/2` + `settle_debounced_task_reload/1`, `projects_live_test.await_async_loads/1`, `tasks_live_test.flush_tasks_load/2`, `settings_live_agents_test.mount_settings/1` → `await_view_async_loads/1`.
They locate this mount's children by the view pid in the child's `:"$callers"` entry (`mount_async_task_pids/1` + `task_callers/1`) and wait for those pids to exit, then a `render(view)` drains the queued apply (or, for `settings_live_test`'s monitor-only variant, the test's next synchronous `render`/`:sys.get_state`).
The `:"$callers"` filter is load-bearing: `EvoDash.TaskSupervisor` never kills children per test, so waiting on EVERY supervisor child made each mount pay its whole deadline; the owner-aware poll (2 ms cadence, 30 s best-effort cap) looks only at this mount's tasks.
`review_live_test.flush_review_load/2` composes the funnel with `EvoDashWeb.TestHelpers.flush_loading/4` (funnel first, then the loading marker), and `tasks_live_test.flush_tasks_load/2` adds a `tasks_loading == false` poll plus a final `render(view)`.
Reuse one of these helpers instead of re-deriving the race; `render_async/2` does NOT await `Task.Supervisor` children, which is why `flush_loading/4` and the funnels exist.
A funnel must EXCLUDE the pids the page itself declares long-lived (the inspector's serial `StreamWatch` worker in `assigns[:inspector_stream_worker]`), because such a child cannot exit while it is attached and the funnel would sit on its whole fallback — that single mistake cost `agents_live_test` 5 s.
The trailing `render/1` of a funnel is load-bearing: LiveViewTest relays queued `push_event`s only when the proxy applies a diff, so skipping it defers the same merge cost instead of removing it.
`EvoDashWeb.TestHelpers.flush_loading/4` is a loading-marker poll bound, not a `$callers` monitor; only the page funnels monitor children.

### Definition order inside a test file is load-bearing
An `async: true` module is handed to the ExUnit runner as soon as its `defmodule` is evaluated, i.e. while the rest of the file is still loading.
Any module an async module references at runtime (`start_supervised!` target, fake `ConnectionManager`, helper module) must therefore sit ABOVE it; a module defined lower can still be `:non_existing` and raise "was given as a child to a supervisor but it does not exist".
Only `async: false` modules may sit at the end of a file.
Files that depend on this ordering: `projects_live_test.exs`, `settings_live_test.exs`, `settings_live_agents_test.exs`, `system_live_test.exs`, `welcome_live_test.exs`, `welcome_complete_live_test.exs`, `task_export_controller_test.exs`, `live_hooks/appearance_test.exs` (its fake `ConnectionManager` must stay above the async module), and `review_live_test.exs` (its fake `ConnectionManager` sits above every test module).

### Flipping a module to async exposes run-wide-store hazards
Every suite shares ONE `EvoGit.Store`; only the `IsolatedTaskStore` users swap it.
A test that sweeps globally — `clear_finished_tasks/0` (`clear_task_history`), retention/cleanup sweeps, deleting rows it did not create — removes another module's live fixture the moment it runs concurrently, so such a test belongs in an `async: false` module (`ProjectsLiveSyncTest` owns the notification-scan describes, whose zero-timeout `refute_push_event(view, "task_notification", …)` calls are claims about GLOBAL quiet).
The project registry is process-global too: `mount_project/3` writes `EvoGit.VCT`'s ONE table visible to every suite, so a mounting test cleans up with `EvoGit.VCT.forget/1` and a "no active project" page assertion is conclusive only while no other module can open one.
`projects_live_test.exs`'s `Helpers` own the VCT fixtures: `seed_project/2` asserts `{:ok, %EvoGit.VCT.Mount{}} = EvoGit.VCT.mount(path, name: name)` and forgets that mount in `on_exit`, `clear_projects/0` forgets every registry row, and `wait_for_projects/2` polls the page's `projects` assign.
The matching quiet-side rule: a `refute_push_event`/`refute_receive` about a `"tasks"` broadcast is conclusive only when no async module can publish one.

### Async review actions — every review test must await the settle
`ReviewLive` runs every review action through `spawn_action/4` (supervised task) and applies it in `handle_info({:review_action_result, task_id, node, action, ref, result})`, so a `render_click` proves dispatch only.
Any test asserting action-derived state (a repo's `resolution`, `local_repo_resolutions`, `review_status`, the completion banner, the hub snapshot) or inspecting an injected runner-seam message MUST call `await_review_action_settled/1` after the click — the hard rule for every new review test.
`await_review_action_settled/1` (one `Helpers` function in the shared `EvoDashWeb.ReviewLiveTest.Helpers` module, imported by all nine case modules in `review_live_test.exs`) polls `assigns(view)[:review_action] == nil` (a stopped view counts as settled via a conditional `catch :exit`) and returns the post-settle render, or `""` when the view is gone.
The two nav-away cases (`ignore`, `auto_resolve`) synchronize differently: `render_click` → `assert_redirect`, then a synchronous `EvoGit.TaskRegistry.get_task/1` proves the queued cast landed, so the hub `== :empty` assertion is non-vacuous.
Do not read action-derived state right after a bare `render_click` anywhere else.
A render captured by `await_review_action_settled/1` is the settle of the CLICK, not of a follow-up background action: the multi-repo aggregate `review_status` is persisted by a SEPARATE action spawned once the last repo settles, so a banner assertion must wait for the persisted status, then `settle_debounced_task_reload/1` and poll a FRESH `render(view)` — never assert against an `html` captured before that wait.

### Async Assistant sends — every Assistant test must await the settle
The send/start and stop/cancel RPCs settle ASYNCHRONOUSLY in the LiveView process (`{:chat_send_result, seq}`, `{:chat_stop_result, …}`, `{:chat_finish_result, …}`), so `render_submit`/`render_click` return BEFORE the page applied the answer, and `assert_receive` cannot observe a message delivered to the view.
An Assistant test therefore awaits the settle through the view's assigns — `send_in_flight`/`send_pending` via the file-local bounded `wait_until/2` helper (`await_send_settled/1`, `send_and_await_terminal/2`), or the expected status/flash for the control paths.
`await_reflect_terminal/0` alone is NOT a settle signal, because an empty `:reflect` row set counts as settled and it can return before the async start has run.
The settle reads are deterministic: `assigns/1` is a `:sys.get_state` round-trip, so it observes state only between callbacks, after the whole result callback (optimistic rollback, one-shot `:reflect` fallback, flash) has run.
### Push-based event contract testing
Events are injected by hand: `send(view.pid, {:task_updated, id, status, node()})`, `{:task_deleted, id, node()}`, `{:agent_updated, id, changed_fields, node}` (the `:agent_updated` payload `changed_fields` is a KEYWORD LIST — guard with `is_list`/`Keyword.has_key?`), `{:system_sample, node, seq, sample}`, `{:remote_connection_status, id, status_map}`.
Foreign-node events (`node != node()`) must be asserted ignored.
Stale-guard paths are driven by injecting the pages' own result messages: `{:tasks_page_loaded, seq, node, result}`, `{:agents_data_loaded, ...}`, `{:agents_refresh_result, seq, node, result}`, `{:system_checks_result, result}`, `{:system_samples_seeded, seq, node, result}`, `{:chat_history_loaded, node, seq, id, msgs}`, `{:chat_task_loaded, node, seq, id, result}`.
The event table itself: `apps/evo_dash/CONTEXT.md` → "Push-based event contract".

### Global state inventory and isolation
Boot-created, process-wide named hubs shared by ALL suites: `EvoDash.ActiveTasks` (`:evo_dash_active_tasks`, process-less pure ETS, keyed by node context), `EvoDash.ChatHistory` (`:evo_dash_chat_history`, GenServer-owned, flat chat ids + `{:current}`), `EvoDash.AccentCache` (`:evo_dash_accent_cache`, keyed by connection-target id), plus the `EvoGit.AgentScheduler` tables.
None is per-test scoped, so an EXACT-contents assertion is safe only against writers that cannot run concurrently.
**`EvoDash.ActiveTasks` rule — an async-visible clear deletes ONLY the local context**: use `EvoDash.ActiveTasks.invalidate(nil, node())`, never the whole-table `reset/0`.
`EvoDashWeb.ConnCase` does that in `setup` and in `on_exit`; the `async: true` modules that mount whole pages and clear the hub themselves (`settings_live_test`, `settings_live_agents_test`, the six async review modules, `desktop_quit_test`, `agents_live_test`, `projects_live_test` via `Helpers.reset_active_tasks_hub/1`) do the same.
Whole-table `reset/0` survives ONLY inside `async: false` modules (`active_tasks_test`, `page_controller_test`, `home_live_test`, `tasks_live_test`, `real_stream_consumers_test`, `system_live_test`'s sync module, `settings_live_test`'s sync module, `node_aware_test`'s sync module, the three sync review modules), which ExUnit never runs concurrently with anything.
`reset/0` is `:ets.delete_all_objects`, so one module's wipe can delete another module's per-test-unique `{target, remote_node}` snapshot between `put/4` and `get/2` — a unique KEY cannot defend against a table-wide wipe.
Scoping loses nothing: a local mount seeds only from `{nil, node()}`, a pending context holds `{[], []}`, and task-bearing remote keys need a real cross-node `:erpc`.
Consequence for new tests: an exact `EvoDash.ActiveTasks.get/2` assertion may stay `async: true` for any non-local key (`NodeAwareRunWideTest` keeps the remote half); never reintroduce a whole-table clear into an async module.
**`EvoDash.ChatHistory` is written by every connected `/assistant` mount** (`HomeLive` calls `current_chat_id() || new_chat()` + `put_state`), so the exact-global reader `evo_dash/chat_history_test.exs` (async) is safe only because EVERY connected `/assistant` mount is `async: false`: `home_live_test`, `real_stream_consumers_test`, `home_live/browser_upload_test`, `home_live/task_picker_test` and the "mounts HomeLive at /assistant" case in `ProjectsLiveSyncTest`.
Plain-GET-only suites (`redirect_controller_test`, `page_controller_test`) never write it, and async `projects_live_test` hosts no `/assistant` mount — a new async `/assistant` mount would race it and belongs in a sync module.
`EvoDash.AccentCache` has the same structural pattern but no live victim: only `appearance_test` resets it, its reads use keys written by that same module, and a concurrent miss merely re-resolves.
Process-global `EvoGit.Store`/`EvoGit.TaskRegistry` isolation is `EvoDash.Test.IsolatedTaskStore.isolate!/1`, called by five suites: `home_live_test` and `tasks_live_test` (module setup), `node_aware_test` (the describes whose assertions need a store-backed registry), `home_live/task_picker_test`, and `isolated_task_store_test` itself.
**Migrated-template immutability** — the helper builds its run-scoped migrated sqlite template once per run and then FINISHES materialization itself, because `EvoGit.Store.Boot.stop/1` returns once the pool is down while SQLite's last-connection WAL cleanup (which UNLINKS `-wal`/`-shm`) runs later at an uncontrolled moment, changing the template's on-disk identity inside a later suite's snapshot window.
`build_template!` therefore deletes the leftover sidecars (the WAL is already truncated), proves the main file carries every migration, and chmods a proven template read-only, so the template is ONE immutable file for the rest of the run.
`seed_isolated_database!/2` restores owner write (0600) on each per-test COPY because `File.cp!/2` carries the source mode.
`isolated_task_store_test.exs` pins the contract (one file, no sidecars, read-only, byte-identical across `isolate!/1`) and its mutation assertion names the exact changed key, path, size and sha256 of both snapshots.
Every other store-touching suite writes into the RUN-WIDE per-run store (`EvoGit.Store`, never terminated) whole-store-safely: per-test unique ids (`System.unique_integer/1`, sometimes under a unique `project_path` for an exact-count paged read), assertions scoped to those ids, and an `on_exit` deleting through the DIRECT Store (`EvoGit.Store.delete_task(EvoGit.Store, id)` — never a `TaskRegistry` cast, which broadcasts on `"tasks"`).

### Async first — test runtime is part of test quality
New tests default to `async: true`; an unnecessary `async: false` module is a defect, because the sync phase is serial and every future cycle pays its full cost.
Prefer event-driven synchronization and bounded polls over fixed sleeps, and ONE mount driving a state machine over many mounts of the same page.
ExUnit parallelises across MODULES, never within one, so splitting one long file into several modules is what shortens the run (see `review_live_test.exs`).

### Suite runtime: what actually costs time
No hidden per-test tax: a typical LiveView test mounts and clicks in 20–100 ms; `enable_expensive_runtime_checks: true` (root `config/test.exs`) is COMPILE-time only, and `EvoDash.Test.IsolatedTaskStore` costs ≈6.5 ms per call.
The cost structure is app boot per `mix test` invocation (~3–4 s), the SERIAL `async: false` phase, and a PARALLEL phase floored by the largest async module.
Whichever test runs FIRST in a BEAM carries a one-time ~1.7–1.9 s warm-up (the first `AgentScheduler {:update_config, …}` and the LLMDB catalog build), so a lone file measured in isolation always shows one bogus outlier — it is not that test's cost and must not be "fixed".
Measured test-side FLOORS (do not re-investigate these without new evidence): `HomeLiveTest` ≈7 s for 164 tests at the `/assistant` mount floor (4–15 ms each); `ProjectsLiveSyncTest` ≈900 ms for 26 tests; the review sync modules are real-git bound (repo template copies plus a ~25 ms `LoadData.load/3` per repo); `TasksLiveTest`'s archive tests are assertion-bearing 500-entry renders.
Moving a suite out of the serial tail is the one test-side transformation that shortens a run; clearing the remaining floor needs the production levers above.
Measured production-side costs that inflate the suite (each needs an `apps/evo_git` or `apps/evo_dash/lib` change, not a test change): `AgentScheduler.handle_call` deriving catalog metadata synchronously (wedges every caller on first touch), `AgentScheduler.config_map/1` recomputing `EvoGit.Platform.sandbox_backend/0` (a PATH scan) on every call, `EvoGit.Review.default_merge_target/1` re-spawning `git show-ref` after `list_branches/1`, and `ReviewLive` spawning TWO `LoadData.load` tasks per connected mount.
This host is SHARED: timings swing 10–30× on load, so compare same-session A/B runs.

### Test-file `try/rescue`
Allowed — and encouraged — in `on_exit`/teardown cleanup, because a teardown failure must not mask a real test failure; each such rescue carries a brief comment explaining why.
Forbidden around assertions or the behavior under test: if an assertion would fail, the test must fail loudly.

### LiveViewTest and module-loading limits
`render/1` cannot see `:sys.replace_state` mutations on the LiveView process (the test proxy renders its own cached `html_tree`); drive the real event path or send the actual `handle_info` message instead.
For transient states (a `:testing` spinner) the same rule applies: no direct state surgery.
Prefer clicking the rendered ELEMENT (`element(view, sel) |> render_click()`, no values) over `render_click(view, event, %{"id" => …})`: an explicit value set masks a broken component contract, and a `phx-value-*` attribute in KEBAB case arrives hyphenated (LiveView strips only the `phx-value-` prefix) so a kebab attribute silently produces `"task-id"` and a `FunctionClauseError` in a snake_case handler — every `phx-value-*` must be snake_case.
`function_exported?/3` does NOT load a module, so a test asserting an export must call `Code.ensure_loaded!/1` first (`evo_dash/node_context_test.exs` carries the regression example).
