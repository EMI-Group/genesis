# Live Hooks Test Directory

## Intent

ExUnit suites for the global on-mount hooks. The `live_view/0` macro (`apps/evo_dash/lib/evo_dash_web.ex` L49-58) registers them in order: SetLocale → **NodeAware** → Appearance → DesktopQuit → UpdateStatus → Guide, so EVERY real LiveView mount (dead render AND connected) runs the full chain — including the NodeAware sidebar hub seed (`on_mount/4` → `EvoDash.ActiveTasks.get` at `node_aware.ex` L110-111 + `assign_new` seeds L121-122).

Two styles: **pure unit/socket tests** (no LiveView boot) and **full LiveView integration through `Layouts.app`** (which exercises the shared on-mount chain as a side effect).

All five suites are `async: false` (123 tests total). Feasibility of flipping any of them: see "Notes for Agents — async-conversion feasibility".

## Notes for Agents

- **NodeAware hub seed runs on every real mount in this directory**: `EvoDash.ActiveTasks` is a boot-created named public ETS table (`:evo_dash_active_tasks`, created idempotently at the top of `EvoDash.Application.start/2` and owned by the long-lived application process — the module is a pure ETS helper with no process), alive for the whole `mix test` run since the app boots once, and its `{nil, node()}` local key is shared across ALL evo_dash suites in the OS process. node_aware_test resets it per test in setup (L52) and the mounting suites in this directory now do too — guide_test L111, desktop_quit_test L26, appearance_test L65 (each setup calls `EvoDash.ActiveTasks.reset()`; appearance_test additionally resets the sibling `EvoDash.AccentCache` per-node accent hub at L70 — same boot-created named-ETS shape, so one test's warm remote accent never leaks into the next test's cold mounts). A warm non-empty local hub from any earlier suite would otherwise seed sidebar tasks into their dead-render html.
- **Connected-mount fetch side effect**: EVERY mounting suite with a LOCAL page spawns a fire-and-forget fetch (`EvoDash.TaskSupervisor`) on each connected mount against the TaskRegistry in force at mount time (the local fetch is unconditional). guide_test isolates its registry (empty → harmless); desktop_quit_test and appearance_test run against the REAL global registry — task rows left by other suites could surface as fetched sidebar rows mid-test, and the spawned fetch can overlap other async:false suites' TaskRegistry terminate/restart windows (the documented ~1-in-7 full-suite flake mechanism; see `apps/evo_dash/test/CONTEXT.md` Known Issues).
- **Fragility of HTML assertions**: no suite in this directory asserts on "Active Tasks" sidebar content/absence. Asserted strings are modal/guide-specific ("Quit Genesis?", "Stop System?", "Genesis Guide", "hello guide", "fixed top-4 right-4 z-50", phx-click/hook attrs, "Go" link text) — none collide with sidebar task rows, but note guide_test L126-128 already documents that a literal "Genesis Guide" assertion would false-positive on the layout's always-rendered HTML comment (the tests use the unique panel class `fixed top-4 right-4 z-50` instead). Layout gate: `layouts.ex` L179 (`@running_tasks != [] or @pending_tasks != []`).
- **Direct on_mount calls DO read the hub**: `node_aware.ex` L114-115 (`node_context_from_params` + `hub_snapshot`) runs unconditionally on both dead and connected paths — the connected-mount FETCH (L141-164) is gated only on `connected?(socket)` AND a LOCAL context (`seed_node_id == nil`, node_aware.ex:158). Direct-call tests therefore observe: reset-cold hub → seeds `[]` via `assign_new` (boot sockets preset no running/pending); pre-warmed hub → seeds the snapshot synchronously (then the connected local fetch still fires); dead-render sockets never receive a fetch message; connected local sockets receive `{:node_aware_active_tasks, 1, nil, node(), ...}`; connected remote/pending sockets never do on mount.
- **`use ExUnit.Case` vs `use EvoDashWeb.ConnCase`**: node_aware_test and update_status_test use plain `ExUnit.Case` (no conn fixtures); the three mounting suites use `ConnCase` + `import Phoenix.LiveViewTest`. All five are `async: false`.

## Notes for Agents — async-conversion feasibility (per-suite, verified)

**Scheduling model that decides every verdict**: ExUnit runs ALL `async: true` modules first (concurrently, up to `max_cases`) and only then runs `async: false` modules one at a time — so a sync module NEVER overlaps another module (async or sync), and an async module's only concurrency partners are the other async modules (`conn_case.ex` L43-46 documents this assumption; verified against the installed runner: `async_loop` takes async modules first and waits for `running` to drain before running sync modules — Elixir 1.20.3 `ex_unit/lib/ex_unit/runner.ex` L104-137). A flip is therefore only unsafe when ANOTHER module that is already (or will also be) `async: true` touches the same global state.
Today (29 `async: true` modules in this app) NO async module touches `EvoGit.Store`/`TaskRegistry`, the `EvoDash.ActiveTasks`/`AccentCache` hubs, `XDG_CONFIG_HOME`, or `EvoDash.UpdateStatus`; the single real cross-talk link is `platform_info_test.exs` (async: true) reading the config path via `PlatformInfo.show_nix_category?/1` → `EvoGit.Config.user_config/0` (`lib/evo_dash_web/live/platform_info.ex:188`), which `XDG_CONFIG_HOME` controls.
- **update_status_test.exs → `ASYNC-READY`** (biggest cheap win, 11 tests): no mounts, no Store/TaskRegistry, no XDG, no `ActiveTasks`; its only globals are `:update_notify_only_override` (save/restored at L20-26/L146-152), `EvoDash.UpdateStatus.reset()` (L22) and `:desktop_quit_stop_fun` (L112) — all keys/hubs whose other users (`system_live_test.exs` L29/L1460, `evo_dash/update_status_test.exs` L12/L24, `live_hooks/system_live_test` hubs) are and should remain `async: false`. Only cleanup: L117 `Application.delete_env(:desktop_quit_stop_fun)` should save/restore the previous value instead (a `delete_env` while a sibling async suite relies on that seam can leave the VM-killing default in place).
- **desktop_quit_test.exs → `ASYNC-AFTER-CHEAP-FIX`** (7 tests): the file's stated reason (L7-9, "injects a global fake stop function via app env") is only PARTIALLY genuine — global app env alone is not a blocker by this repo's own precedent (`platform_info_test` and `project_flow_test` are `async: true` with global app env). The genuine blocker is that `:desktop_quit_stop_fun` is ALSO mutated by `live_hooks/update_status_test.exs` L112-118, and with the key missing `DesktopQuit.stop_fun/0` falls back to `default_stop/0` (`lib/evo_dash_web/live_hooks/desktop_quit.ex` L83-88) → a real `System.stop()` 150 ms later → **the whole test VM dies, not a mere flake**. Exact cheap fix: keep it the SOLE async owner of that seam (i.e. flip update_status_test, not both) and replace `Application.delete_env` (L29) with a save/restore of the previous value. Its only other global is the `ActiveTasks` hub (reset L26 + ConnCase L47-48) and the mount-time Store read — both safe while no async suite manipulates the store.
- **appearance_test.exs → `MUST-STAY-SYNC`** (20 tests; the claimed reason L31-34 is genuine, but the framing is not the whole story): `System.put_env("XDG_CONFIG_HOME", ...)` (L50) mutates a process-global env var, and per-test unique temp dirs do NOT fix it (two concurrent suites each clobber the other's dir; no `System.put_env` can be scoped to a test process). It is also the only writer of the `AccentCache` hub (L70 reset + L269/L360 puts) and resets `ActiveTasks` (L65). No test-only fix exists; a product-side seam (injectable config dir / resolve fun) would be needed — expensive.
- **guide_test.exs → `MUST-STAY-SYNC`** (16 tests): the claimed reason (L21-24) is VERIFIED genuine — the integration setup terminates the production `EvoGit.TaskRegistry`/`EvoGit.Store` children of the global `EvoGit.Supervisor` (L94-95) and starts isolated instances under the FIXED registered name `EvoGit.TaskRegistry` (L102-106), restarting the production children in on_exit (L115-116). Cheap partial win: the 7 pure tests (L31-88: `normalize_guide/2` + `relevant?/2`) touch no global state and can move into an `async: true` module.
- **node_aware_test.exs → `MUST-STAY-SYNC`** (69 tests, the largest file in this directory): decisive blocker is `setup_isolated_registry/1` (L148-171) — global `EvoGit.Supervisor` terminate/restart of `EvoGit.Store` + `EvoGit.TaskRegistry` with an isolated instance registered under the fixed global name — used by 7 describes (L565, L698, L754, L1007, L1243, L1467, L1516); additionally `isolate_config_dir/1` mutates global `XDG_CONFIG_HOME` (L187, used at L1008/L1093/L1244/L1468/L1517), the module setup resets the global `ActiveTasks` hub (L52), and 12 fake `ConnectionManager`s register in the global unique `EvoGit.RemoteConnection.Registry` (L391/L413/L1033/L1053/L1164/L1319/L1478/L1526/L1556/L1577/L1596/L1613). Cheap partial win: the pure-socket describes — `handle_connection_status/2` (L225-459), `partition_active_tasks/1` (L461-551), `handle_task_info/2` debounce (L875-976), `event_from_current_node?/2` (L978-994) ≈ 25 tests — need only the hand-built socket and the Registry, so they can move to an `async: true` module (the hub-writing `handle_tasks_result/2` describe L1371-1456 must stay with the hub owner).
- **Cross-suite hazard for ANY future async fake-manager suite**: `EvoGit.RemoteConnection.Registry` is `keys: :unique` (`apps/evo_git/lib/evo_git/application.ex:78`) and the fakes call non-bang `Registry.register/3` whose error tuple is ignored — two suites using the SAME target id concurrently would silently route lookups to the first-registered manager (assertion failures, not a crash). Current ids are suite-distinct (`accent-*` here, `test-err`/`test-conn`/`test-target`/`target-*`/`conn-*` in node_aware, `test-remote` in home_live_test); keep new async fake ids unique.
