# Test Directory — EvoDashWeb Live Tests

## Intent

ExUnit suites for the EvoDash LiveView pages and their support modules, mirroring `apps/evo_dash/lib/evo_dash_web/live/`.
Page suites are split by MODULE for parallelism, so "is this page suite async?" has no per-file answer — check the module (census + forcing globals: `apps/evo_dash/test/CONTEXT.md`).
This node owns the live-page cross-suite mechanics (wait cadences, the ReviewLive suite, async mount loads, exit-safety seams); per-suite detail: `./projects_live/CONTEXT.md`, `./settings_live/CONTEXT.md`, `./home_live/CONTEXT.md`, `./agents_live/CONTEXT.md`.
No suite writes the config dir BEAM-globally: per-process `EvoDash.Test.ConfigDir.isolate!/1` (proof `../support/config_dir_test.exs`).

## Notes for Agents — deterministic waits (the single rule future edits must not break)

App-wide wait, capture-log and mount-funnel rules live in `apps/evo_dash/test/CONTEXT.md`; here only the live-page cadences.
Every wait is deterministic: a synchronous `assigns/1` read (`:sys.get_state/2`, EXPLICIT 30 s — never the 5 s default), a monotonic seq/counter written inside the handler, or a bounded 1–2 ms poll; every async-load budget is `@async_wait_budget_ms` (or the file's equivalent) = 30 s for this shared host's 10–30× load swings, and assertions keep full strength.
- `tasks_live_test.exs` — `@wait_poll_ms` = 2 ms via `wait_until/3`; `flush_tasks_load/2` = `flush_loading` → `tasks_loading == false` (30 s `:sys.get_state/2`) → `drain_async_loads/2` (leading socket read, wait out an armed `tasks_reload_pending` debounce, then `await_view_async_loads/2`) → `render/1`.
- `review_live_test.exs` — `@wait_poll_ms` = 2 ms inside `wait_until/2`.
- `home_live_test.exs` — `@poll_interval_ms` = 2 ms inside `wait_until/2` (30 s); `await_source_available/3` 30 s.
- `projects_live_test.exs` — `wait_assigns/3`, `wait_for_fake_callers/3`, `await_async_loads/1`, the GitHub describe's `wait_until/3` at 2 ms under 30 s; `wait_for_task_terminal/2` polls `TaskRegistry.get_task/1` every 2 ms under a 10 s best-effort budget (only keeps a still-spawning git port from racing a temp-dir teardown).
- `agents_live_test.exs` — `wait_until/2` / `await_latch/2` at 10 ms / 1 ms under 30 s (`await_latch/2` never raises); `render_until/3` + `submit_until_pending_hint/3` poll `render/1` for out-of-band applies and return the LAST render, so a persistent failure still fails with the real output.
- `settings_live_test.exs`, `settings_live_agents_test.exs`, `settings_live/provider_panel_live_test.exs`, `settings_live/provider_wizard_test.exs`, `system_live_test.exs` — 1–2 ms under 30 s budgets (`@settle_timeout_ms`, `wait_settings`, `await_mount_async_loads`, `await_config_save`, the system awaits).
- `welcome_live_test.exs` — `@runner_start_timeout` and `@async_wait_budget_ms` = 30 s (`assert_receive {:welcome_test_started, …}`, `await_status`); every sign-in stub message on `@async_wait_budget_ms` ("in-browser sign-in waits").

**The 0 ms rule** (parent form): a zero-length `refute_receive` / `refute_push_event` is allowed ONLY after the mailbox provably drained (a synchronous `:sys.get_state` round-trip, a completed drain helper, a dead-helper-process await); then it is conclusive and stronger than any timed window; without that precedent use a bounded backstop (monotonic counter assertion) plus a small margin.
In force: `tasks_live_test`'s `refute_receive :page_load_spawned, 0` (after `page_load_seq == 1/2` + a `:sys.get_state`), `agents_live_test`'s `refute_receive {:commit_graph_call, …}, 0` after both commit-graph assigns are false, and the seven `refute_push_event(view, "task_notification", %{}, 0)` probes in `ProjectsLiveSyncTest` (never in the async module — the scan is store-global) after `drain_task_reload/1`.
No fixed `Process.sleep` is a mechanism; the only fixed waits are deliberate and documented per suite.

## Notes for Agents — inspector stream lifecycle and integration boundary

`agents_stream_watch_lifecycle_test.exs` drives real public `StreamWatch.attach/2`, `detach/1` and `ready/5` in an isolated connected consumer with actual supervised serial workers (not fabricated worker-command capture).
Its synchronous module owns the BEAM-global `:agents_watch_runner` / `:agents_unwatch_runner` seams; every RPC blocks on a reference-specific release handshake, all consumer/worker cleanup is monitored and awaited before the seams are restored, and teardown owner monitors release blocked runners even when an assertion fails.
Handshakes pin the consumer pid (the LiveView-equivalent subscriber), never the worker pid, and the exact next RPC identity/order across blocked A→B→A coalescing, obsolete-registration cleanup before reattach, detach and same-id node switches.
Consumer death is covered after registration and while registration is blocked, including late-success unregister and normal worker exit; error results, exits, exceptions and malformed registration results must clean up and permit retry on the same worker, and a failed unregister logs once without retrying or blocking the next selection.
Negative RPC probes occur only after the worker's terminal DOWN, never after an arbitrary quiet window.
The child async `agents_live/stream_watch_test.exs` covers pure snapshot/replay and worker-command boundaries, not real RPC ordering or consumer-death cleanup.

`agents_stream_integration_test.exs` covers the mounted `/agents` inspector-stream path through actual selection/watch seams, buffered snapshot replay, stale/duplicate/foreign deltas, authoritative LLM/tools phases and suppression of message-count history refetch while watched; it also pins selection/close/local-to-remote URL-patch cleanup and atomic checkpoint reconciliation failure with retained content and explicit retry.
Synchronous because its global app-env runner seams overlap the async page suites, and its monitored consumer/worker teardown completes before those seams are restored.

## Notes for Agents — async policy (live-page deltas)

ExUnit runs ALL async modules first, then sync ones one at a time — a flip is unsafe only when another ASYNC module touches the same global state (census + forcing globals + production levers: `apps/evo_dash/test/CONTEXT.md`).
- **Suites are split by module, not file** — `agents_live_test.exs` and `settings_live_agents_test.exs` fully async; `review_live_test.exs` 6 async + 3 sync; `projects_live_test`, `settings_live_test`, `system_live_test`, `welcome_live_test` and `welcome_complete_live_test` each pair one async page module with a trailing sync module; `tasks_live_test`, `home_live_test` and `processes_live_test` remain one sync module each; the pure support-module units are all async.
- **Sync reasons are process-global resources with no per-test seam**: the `EvoGit.Store`/`EvoGit.TaskRegistry` singleton (isolation or fixture rows), `EvoGit.AgentScheduler` state (`pause`/`resume`, `update_config`), app-owned ETS `:evogit_sched_meta` / `:evogit_agent_summary`, the `EvoDash.ActiveTasks` / `EvoDash.UpdateStatus` / `EvoDash.ChatHistory` hubs, shared app-env seams (`:platform_os_override`, `:directory_picker`, `:remote_path_expand_runner`), the `"tasks"` and `"processes"` PubSub topics, the process-global `EvoGit.VCT` mount table.
- **A module that CLICKS a task-mutating action is a publisher** and stays sync (the `"tasks"` broadcast arms every mounted page's reload debounce).
- **The notification scan is store-global**: `EvoDashWeb.ProjectsLive.Notifications` diffs terminal ids read from the RUN-WIDE `EvoGit.Store` against the view's mount seed, so a zero-timeout `refute_push_event(view, "task_notification", %{}, 0)` is a GLOBAL-quiet claim and MUST live in the sync module; content-pinned positive `assert_push_event`s stay async.
- **Project mounts are global too**: opening a project calls `EvoDash.NodeContext.mount_project/3` → `EvoGit.VCT`, whose one table every suite shares, so a mounting suite must clean up with `EvoGit.VCT.forget/1`.
- **Per-process config isolation is NOT itself a sync reason**: `EvoGit.Platform.config_dir/1` resolves through the `:config_dir_fun` seam per process (own dictionary, then the `$callers` chain), so a config-writing test isolates with `EvoDash.Test.ConfigDir.isolate!/1` and stays async; the mounted-only config-dir proof runs sync only because async Projects tests own the global `:projects_async_load_runner`.
- **`agents_live_test.exs` is async**: it seeds the global `:evogit_sched_meta` / `:evogit_agent_summary` rows under a UNIQUE per-test agent id (`System.unique_integer([:positive]) + 10_000_000`, via `agent_id/0` reading the process dictionary), so no two concurrent modules collide.

## Notes for Agents — in-browser sign-in waits

`welcome_live_test.exs` and the Settings sign-in suites assert EVERY sign-in stub notification (`{:begin, …}` / `{:cancel, …}` / `{:status, …}`) on `@async_wait_budget_ms` and order `begin`/`cancel` state-first, proving the observable half of the interaction (`#welcome-chatgpt-waiting`, or the return to `#welcome-chatgpt-sign-in` plus `chatgpt_sign_in == %{phase: :idle}`) before reading its notification.
Those suites raise the `:chatgpt_signin_call_timeout_ms` seam to that same 30 s budget (`EvoDash.Test.ChatGPTLoginStub.install!/1` for the Settings surfaces, `/welcome`'s file-local `WelcomeLiveTest.SignInStub` per process), so the product's 15 s default can never kill the notification-emitting `Task.async` before it runs: a stubbed flow call is bounded by the same async budget its assertion uses.
`/welcome` waits for the ANSWER-BEARING tick (`{:signin_stub, {:status, flow_id, answer}}`, proving the `ChatGPTSignIn` poll READ that answer, not merely that it ticked) on `@async_wait_budget_ms`, then for the applied page state; residual window: `assert_receive` skips non-matching `:pending` ticks, so the barrier proves the terminal answer was read, not that it was read on the first tick, and in the cancelling test the stale result's delivery races the two `refute`s while the `flow_id` guard itself is pinned by `ignores a result for a flow it is not waiting for`.
Because the flow call is an ASYNC RPC, every read of sign-in markup after a flow-STARTING click first awaits the APPLIED phase — `welcome_live_test.exs`'s `await_sign_in_phase/2` (bounded `await/1` over `assigns(view).chatgpt_sign_in.phase`), `settings_live/chatgpt_sign_in_surfaces_test.exs`'s `await_page_sign_in/3`, `settings_live/provider_wizard_test.exs`'s `await_sign_in/2` — so a loaded host cannot fail a markup read on a phase the page has not assigned; exact markup assertions stay unchanged.
**Transient sign-in states come from the snapshot that ESTABLISHED them**: `provider_wizard_test.exs` "a local sign-in waits on a real link and continues with the connected account" reads `#settings-chatgpt-waiting` and its `#settings-chatgpt-sign-in-url` link (`href` + `target="_blank"`) from the CLICK's own `render_click/1` reply, because its stub queues a terminal status (`[:pending, {:ok, …}]`) that may be applied the moment the event returns and `has_element?/2` then `element/3 |> render/1` are two separate later renders that can already show the connected state; the click reply is atomic with the state it pins (the event diff renders before the proxy merges any later poll diff), so the waiting block and link come from that ONE snapshot.
`settings_live/chatgpt_sign_in_surfaces_test.exs` makes `:waiting` a stable APPLIED state instead: `status_gate/1` answers `:pending` while a test-controlled `:counters` flag is closed and the flow's verdict once `open_status_gate/1` sets it, so the click render and every later markup read observe that same waiting surface, and opening the gate lets the page's REAL poll deliver the verdict and finish its poll task (a never-terminating flow would make `settle_mount_loads/1` sit on its whole budget).
`welcome_live_test.exs` takes the other route: its stub answers `:pending` until the test flips it after the link assertions, and every waiting-markup read awaits that applied `:waiting` phase.
A stub answering a TERMINAL verdict immediately makes `:waiting` unobservable: with a 5 ms poll the success can be applied before or while the click's own render is captured, so that render legitimately shows the completed surface.
The only OTHER way a click render can lack the waiting surface is the product's bounded flow call failing — `begin/1` answers `{:error, :sign_in_unavailable}` at the `:chatgpt_signin_call_timeout_ms` budget and the page renders its `:error` phase, pinned by its own regression test; that surface is honest and retry-able, never asserted away.
`settings_live/chatgpt_sign_in_state_test.exs` and `llm_setup/chatgpt_signin_test.exs` need no barrier: they set their stub answer synchronously before asserting.
