## Notes for Agents

- **NO real LLM/exec in dashboard live tests** (suite policy): a test must never be able to reach `AgentScheduler.run_agent`/the network.
  - Home chat (`home_live_test.exs`): chat state is seeded via `seed_chat_state/2` + synthetic `{:task_updated, ...}` events and terminal paths via `finalize_failed/2` / `insert_task_fixture!` — NOT by submitting `send_message` to start a real `:reflect` task. Exactly ONE real-send canonical pin ("starts a reflect task with the right opts") remains and is network-free by construction: the suite setup pushes `model_profiles: []` into the AgentScheduler (`update_config`, restored in on_exit — the same seam `:evo_git`'s own suites use), so `run_agent` rejects every spawn synchronously with `{:error, :llm_not_configured}` before any agent registration or HTTP call. Note the counterintuitive fact (verified): a BOGUS `model_id` does NOT fail fast — `Dispatch.resolve_model_for_agent/2` warns and falls back to the FIRST real profile, which would hit the ambient expired-key LLM.
  - Projects page (`projects_live_test.exs`): the ~10 task-form/GitHub-fix launches pin the dashboard→TaskRegistry opts-threading contract on the persisted `EvoGit.TaskInfo` row and are kept real for exactly that contract, but structurally cannot reach the LLM: 9 fail fast at `validate_node_path` via the `node_path: "./nonexistent-dir"` lever (a VALID node path would pass validation and proceed to `run_agent` with the boot-time ambient LLM config — there is no valid-but-quiet path), and the GitHub-fix test dies at `resolve_starting_commit` on an unborn-HEAD repo seed (`make_git_repo!` gives an empty committed repo so `ensure_repo` no-ops). In-body `cancel` calls were dropped (wrapper already terminal) and `stub_github_upstream_check!/0` keeps the async GitHub-upstream `git remote get-url` from racing setup `on_exit` teardown.
  - `ExUnit.start(capture_log: true)` in `test_helper.exs` hides these side effects for passing tests, which is WHY the policy is structural (no path to the LLM), not output-grep-based.

- **SystemLive chart tests must stub the seed runner**: any test that asserts on `chart_samples` (e.g. "a foreign-node system sample broadcast is ignored") MUST set `Application.put_env(:evo_dash, :system_samples_runner, stub)` in the test body BEFORE mounting. The default runner reads the real `EvoGit.SystemSampler` ring buffer, which is non-empty whenever any sampler tick has occurred in the VM (the evo_git suite's `system_sampler_test.exs` ticks the registered sampler; umbrella `mix test` runs both apps in one VM). Test env disables the tick via `config/test.exs:32` (`:system_sample_interval_ms, 86_400_000`), but that is an accident of config, not a guarantee — the file-level setup block restores the env in `on_exit`.
- **Remote-node test pattern** (used by the cross-OS path tests): save a unique target via `EvoGit.RemoteConnections.save/1` under per-test isolated `XDG_CONFIG_HOME`, then `start_supervised!` a fake `ConnectionManager` GenServer registered in `EvoGit.RemoteConnection.Registry` with `%{phase: :connected, node: "genesis_remote@127.0.0.1", last_error: nil}`. `:erpc` calls to the fake node fail fast, so RPC-dependent remote success paths (e.g. `NodeContext.dir?/1` → true) are unreachable in tests — only the validation/degradation branches are covered end-to-end.
- **`normalize_remote_project_path/2` tilde seam**: `Application.get_env(:evo_dash, :remote_path_expand_runner)` is read at CALL time; tests inject fakes with `Application.put_env` + `on_exit` restore (see `project_flow_test.exs` `install_expand_runner/1`).
- **Foreign-repo raw storage in remote contexts**: `EvoGit.Core.ForeignRepo.new/3` runs `Path.expand/1` on the root, so EvoDash remote contexts bypass it via the node-aware seam `ProjectFlow.build_foreign_repo/4` (local node → `ForeignRepo.new/3`; remote node → RAW root, no local expansion). Wired into the `add_foreign_repo` handler, `Project.load_foreign_repos/3` (remote genesis.toml loading), and `StatePersistence.maybe_restore_foreign_repos/2` (persist/restore round-trip). Tests assert raw-verbatim roots (POSIX and Windows, host-OS independent) in `project_flow_test.exs` + `state_persistence_test.exs`.
- **`EvoDash.ActiveTasks` sidebar-hub pollution (page suites)**: every full-page `live(conn, path)` mount seeds `:running_tasks`/`:pending_tasks` from the shared in-memory `EvoDash.ActiveTasks` hub (local key `{nil, node()}`, remote `{node_param, remote_node}`) via `LiveHooks.NodeAware.on_mount` (`apps/evo_dash/lib/evo_dash_web/live_hooks/node_aware.ex` L102-176; the connected-mount LOCAL fetch is UNCONDITIONAL — remote/pending contexts never fetch on mount — and every applied fetch writes the hub; `{[], []}` IS a valid snapshot, a fetch against an empty registry warms it empty). **Every page suite in this subtree resets the hub per test in setup** (`EvoDash.ActiveTasks.reset()` — home_live L51, tasks_live L27, projects_live via its `reset_active_tasks_hub/1` setup tag (L75), review_live L22, system_live L35, agents_live L26, settings_live L46, settings_live_agents L34, welcome L35, welcome_complete L37). Reason: suites that insert sidebar-visible rows (status `:running/:pending/:finalizing/:cancelling`, or `:completed` + `branch_name` + `review_status: nil`) leave rows in the shared store (home_live/tasks_live/projects_live/review_live), and the per-test Store/TaskRegistry isolation (terminate + `start_supervised` + restart_child) and `ChatHistory.reset()` do NOT clear the hub — without the reset, a warm key would seed those leftover rows into later whole-page mounts' first paint, and the (unconditional) mount fetch against the shared store could fetch them back into the sidebar (gate: `apps/evo_dash/lib/evo_dash_web/components/layouts.ex` L179). Contract: any NEW suite that mounts whole pages through `Layouts.app` must call `EvoDash.ActiveTasks.reset()` in setup (sidebar labels derive from `opts[:objective] || opts[:prompt]`, truncated to 30 chars — `task_label/1` in layouts.ex).
- **Review per-repo actions vs the ActiveTasks hub** (regression pins in `review_live_test.exs`): a per-repo merge/reject settles ONLY that repo (`MergeCheck.update_repo/3`) and the page NEVER navigates; `EvoDash.ActiveTasks.invalidate/2` — via `review_live.ex` `invalidate_active_tasks/1` — runs ONLY on the COMPLETION path, i.e. when every repo's resolution became TERMINAL (the aggregate status is then persisted via `NodeContext.set_review_status/3` with a success flash and the completion banner; `ignore`/`resume`/`auto_resolve` still `push_navigate`). Asserted with the file-local `wait_hub_warm/0` idiom (wait for the connected-mount fetch to warm `{nil, node()}`, act, then compare `EvoDash.ActiveTasks.get(nil, node())`): a partial resolution leaves the warmed snapshot byte-for-byte unchanged, the final terminal resolution yields `:empty`.
- **`test_llm` handlers spawn REAL provider requests — a `mix test` console-noise source**:
  `SettingsLive.handle_event("test_llm", …)` (`settings_live.ex`) and `WelcomeLive.handle_event("test_llm", …)` (`welcome_live.ex`) each start a DETACHED `EvoDash.TaskSupervisor` child running `EvoGit.SystemCheck.llm_test/1,2` → `ReqLLM.stream_text/3`.
  When a provider key is resolvable (env var / the process-global `ReqLLM` key store, which tests populate via `EvoGit.Config.credentials/0`) that child makes a real streaming HTTP request, and ReqLLM's `ReqLLM.Streaming.Failure.log/1` (`deps/req_llm/.../streaming/failure.ex`) emits `[warning] Streaming provider/API request failed: status=403, provider_code="forbidden", …`.
  The child outlives its test, so when the network is slow/blocked the line lands OUTSIDE ExUnit's per-test `capture_log` window and leaks into the `mix test` console (a fast response is absorbed by a later test's capture window — the leak is network-timing-dependent, not assertion-related).
  With no key at all the call fails BEFORE HTTP (`[error] Provider failed to build streaming request …`, no `Streaming provider/API request failed` line).
  Five tests can fire such requests.
  The two `settings_live_test.exs` "LLM connection test" tests ("test_llm handler routes through remote node when remote_config is true" / "… proceeds when remote_config is false") are quiet by construction: their profile fixture uses `model: ""`, which is still truthy for the handler's `if model do` branch (so the found-profile path still runs and `llm_test_status` still reaches `:testing`) but makes `SystemCheck.guarded_llm_test/3` return `{:error, "No LLM model configured"}` before any network I/O.
  The three `welcome_live_test.exs` "LLM connection test" tests ("typed API key is saved before the connection test runs" — always, it saves its own key; "testing state renders the spinner"; "test_llm handler starts the test (unit-style)") STILL issue real requests, because `resolve_welcome_model_value/4` never yields the `""`/`%{}` short-circuit value and neither handler has an app-env runner seam — silencing them cleanly needs a production-side `:llm_test_runner` seam in `lib/`, not a test-only change.
  Note the first settings test's NAME is misleading: the handler derives `remote?` from `current_node != node()` (not the `remote_config` assign), so with `current_node: node()` it exercises the LOCAL branch.
- **Running this subtree's tests**: use `mix test apps/evo_dash/test` (or an explicit file path). ⚠️ The directory form `mix test apps/evo_dash` silently produces NO output and runs nothing in this repo — always point at `apps/evo_dash/test`. App-wide/umbrella runs are ORDER- AND TIMING-SENSITIVE (pre-existing): the `async: false` suites here repeatedly terminate/restart the GLOBAL `EvoGit.Store`/`EvoGit.TaskRegistry`, and a leaked shared-hub snapshot can break an unrelated later mount (e.g. the sidebar's `Layouts.group_tasks_by_project/2` crashing on a junk atom left by a hub round-trip test that never cleans up). So an occasional single failure in a DIFFERENT suite is not necessarily caused by the file under test — re-run the failing file standalone (and with a couple of seeds) before suspecting a regression.

- **Async policy (per-suite)**: the PAGE suites here are all `async: false` except `agents_live_test.exs`; the pure support-module unit tests are `async: true` (`project_flow_test`, `state_persistence_test`, `platform_info_test`, `settings_live/config_io_test`, `settings_live/model_profile_helpers_test`, `system_live/charts_test`, the `home_live/*` and `agents_live/*` unit tests) except `projects_live/project_test.exs`, which is `async: false` (its tests isolate the process-global `XDG_CONFIG_HOME`). Each sync page suite touches at least one BEAM/process-wide mutable resource with no per-test seam:
  - **XDG_CONFIG_HOME** (process-wide env; `EvoGit.Config.config_dir/0` → `EvoGit.Platform.config_dir/1` reads it — there is NO config-dir app-env/process-dict override; an app-env override would NOT help since app env is itself global). Two concurrently-running modules that set it clobber each other. `test_helper.exs` seeds it at boot to a run-unique EMPTY dir (a no-op on macOS, where `EvoGit.Platform.base_dir/3` ignores it), so a suite that only READS config would no longer need to set it — but every suite listed here WRITES config (or saves a remote target / version-state marker) into its own per-test temp dir, which is why each stays `async: false`. Used by: `projects_live_test`, `settings_live_test`, `review_live_test` (2 remote describes), `home_live_test`, `system_live_test` (several describes), `welcome_live_test`, `settings_live_agents_test`, `welcome_complete_live_test`, `projects_live/project_test`. EVERY module that sets it is `async: false` — including `evo_dash_web/controllers/task_export_controller_test.exs` (saves/restores it around its 3 `?node=` tests), which is sync for exactly that reason.
  - **`EvoGit.Store` / `EvoGit.TaskRegistry` GLOBAL singleton**: `tasks_live_test` + `home_live_test` terminate + isolate + `restart_child` it; `projects_live_test` + `review_live_test` insert fixture rows (unique ids, on_exit cleanup) into the SHARED store. Terminating the singleton conflicts with any concurrent store reader/writer.

## Notes for Agents — Agents-page commit-history view (temporal) tests

The Agents page (`/agents`) has a left-panel VIEW SWITCHER: `@left_view` (`:tree` default | `:commits`), toggled by `handle_event("switch_left_view", %{"view" => "tree"|"commits"})` (any other value is a no-op); the segmented buttons are `#left-view-tree` / `#left-view-commits` in `agents_live.html.heex`.
Switching to `:commits` lazily fetches the TEMPORAL commit graph via the app-env seam `:agents_commit_graph_runner` (default `&EvoDash.NodeContext.list_task_commit_graph/5`), resolved AT SPAWN TIME inside an `EvoDash.TaskSupervisor` child — stub it (`Application.put_env` + `on_exit`) BEFORE `live/3`, and never let a test reach the real RPC/core (the core `EvoGit.CommitGraph` may be absent).
The fetch is TASK-SCOPED: `commit_graph_groups/1` groups the eligible agents by `{repo_key, task_id}` (repo_key = `repo_root`; eligible = binary `repo_root`, `base_commit`, `current_commit`, `task_id`; groups sorted by `{repo_key, task_id}`) and each group issues ONE call `runner.(node, task_id, repo_key, live_tips, limit: 100)`, where `live_tips` = that group's de-duplicated non-nil `current_commit`s among its NON-ended agents (an all-ended group is still fetched, with `live_tips == []`). Drive the agent list with the existing `:agents_list_runner` seam (`summary_agent/1` / `full_agent/1` overrides; their default `task_id` is the non-nil binary `"task-1"` because eligibility requires it). A non-`{:ok, _}` reply HALTS the per-group loop.
Result apply is `handle_info({:commit_graph_loaded, node, seq, result}, socket)`, stale-guarded on the viewed node AND `seq < commit_graph_seq`; `result = {:ok, raw_by_repo} | {:error, reason}` with `raw_by_repo` keyed by `repo_key` — groups sharing a repo_key are UNIONED (commits deduped by `:sha`, refs merged) — and `{:error, reason}` KEEPS the last good graph, only setting `commit_graph_error`.
The graph is fed by the MERGED agent set `commit_graph_agents/1` = live `@agents` ++ `@retained_agents` (live wins); the agent TREE still shows only `@agents`. `@retained_agents` is `%{agent_id => agent_map}` holding an ended agent's full last-known map with `ended: true` — populated on `{:agent_removed, ...}` or when an agent disappears on a full refresh, dropped when it reappears/is live, RESET on a node switch; `apply_agent_removed/2` does NOT clear `selected_agent_id`, so a removed agent keeps its graph `agents` entry (its rows rendered dim, its agent-tag tooltip gaining `gettext("terminated")`) AND its START/END annotation.
Test helpers live in `agents_live_test.exs`: `install_agents/1`, `install_commit_graph_runner/1` (an ARITY-5 stub recording the 6-tuple `{:commit_graph_call, node, task_id, repo_root, live_tips, opts}`, its responder keyed by `repo_root`), `graph_error_responder/0`, `graph_partial_responder/1`, `mount_loaded_commit_graph/2` (`select: true` selects the agent in the tree view before switching to commits); `clear_agents_env/0` also clears `:agents_commit_graph_runner`.

A loaded commit graph IS renderable at page level: the vertical commit graph (`components/agents_components/commit_graph_view.ex`) carries no `phx-update` mode, so incremental patching relies on the stable, unique child ids.
So the page suite asserts the loaded graph's markup directly from the rendered DOM, deriving `repo.repo_dom_id`, the agent id and the node shas from the live socket's `@commit_graph` rather than hardcoding ids: `#commit-graph` + `phx-hook="CommitGraph"` → the per-repo wrapper whose id IS `repo.repo_dom_id` → `#cg-list-<dom>.cg-list.relative` holding the absolute gutter `svg.cg-gutter` (derived `viewBox`, `pointer-events: none`, NO `g.cg-viewport`) plus the `.cg-rows` container (left-padded by the gutter width — `padding-left: 40px` in the fixture); the gutter holds, in paint order, every `path.cg-edge` (`#commit-edge-<dom>-<from_sha>-<to_sha>`, `data-commit-graph-anim="edge"`, a VERTICAL bezier `d`, dashed only for a `:merge` side parent) then every `g.cg-node` (`#commit-node-<dom>-<sha>`, `data-commit-graph-anim="node"`, `data-cg-sha`/`data-cg-agent-id`, no click), while the rows are `div.cg-row` (`#commit-row-<dom>-<sha>`, `data-commit-graph-anim="row"`, `style="height: 44px"`) carrying the `select_agent` click contract + `phx-value-id` (both omitted for an unowned node) and the `.cg-row-sha`/`.cg-row-message`/`.cg-row-meta` spans (a base row shows `.cg-base-label` "base" and NO message instead); agent chips are `button.cg-agent-tag` (`#commit-agent-tag-<dom>-<sha>-<start|end>-<akey>`, class `cg-agent-tag-start`/`cg-agent-tag-end`, the same `select_agent` contract) and ref chips `span.cg-ref-tag` (non-clickable).
The sibling COMPONENT suite (`test/evo_dash_web/components/commit_graph_view_test.exs`) renders the component in isolation via `render_component/2` (bypassing the diff path).
Socket-state assertions remain the right tool for the stale-seq / foreign-node / failed-refresh cases (they assert state after a direct `send/2`).
Node-switch reset is tested by invoking `EvoDashWeb.AgentsLive.handle_params(%{}, "/agents", socket)` directly on the socket from `:sys.get_state(view.pid)` with `previous_node` forced to differ (mutating `current_node` via `:sys.replace_state` does NOT run the reset); the reset clears the commit-graph assigns while `@left_view` SURVIVES.
The sibling node `./agents_live/commit_graph_test.exs` unit-tests the PURE `EvoDashWeb.AgentsLive.CommitGraph` (`build/2`, `grouping_key/1`, `repo_display_name/1`) with no I/O — including the agent `ended` flag (true ONLY for an agent map carrying `:ended == true`, else false) and base-node de-dup (a fetched commit equal to an agent `base_commit` is ONE `:commit` node; an explicitly-counted mixed case — one covered + one uncovered base in the same repo → 1 synthesized `:base` node — pins it).
Beyond the switcher/async describes, `agents_live_test.exs` covers the task-scoped contract in `describe "commit history view — task-scoped groups"` (two agents in ONE repo with DIFFERENT `task_id` → TWO runner calls, one per group; two groups sharing a `repo_key` both `{:ok, _}` → the merged `raw_by_repo[repo_key]` unions commits deduped by `:sha` + merges refs into one repo graph covering both agents; an all-ended group still fetched with `live_tips == []`; a fetch that INCLUDES the real base commit renders it as ONE normal `:commit` node) and `describe "commit history view — retained ended agents"` (an `{:agent_removed, ...}` broadcast keeps its graph `agents` entry `ended: true`, the `@retained_agents[id].ended` copy and the selection annotation while the agent leaves the tree; a re-registration OR a full-refresh reappearance supersedes the retained copy → exactly ONE `agents` entry and `retained_agents == %{}`; a node switch resets `retained_agents` while `left_view` survives).
Two production behaviours the tests must work around: the commits-view right-hand detail panel keeps the last-known agent data after a removal (it shows no "agent not found" state), so asserting the removed agent's ABSENCE means toggling back to the tree view; and `live_tips` order inside a group is agent iteration order (not sorted), so tests assert order only for groups with distinct tips.
