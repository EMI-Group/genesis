# Test Directory — EvoDashWeb Live Tests

## Intent

ExUnit suites for the EvoDash LiveView pages and their support modules (968 tests), mirroring `apps/evo_dash/lib/evo_dash_web/live/`.
The page suites are SPLIT BY MODULE for parallelism, so "is this page suite async?" has no per-file answer — check the module.
Every page file leads with an `async: true` page module and trails only its global-bound tests in a sync module: `agents_live_test.exs` and `settings_live_agents_test.exs` are entirely async, `review_live_test.exs` holds 6 `async: true` + 3 `async: false`, `projects_live_test`/`settings_live_test`/`system_live_test`/`welcome_live_test`/`welcome_complete_live_test` each pair one async module with a trailing sync module, and `tasks_live_test.exs` and `home_live_test.exs` are a single `async: false` module each; `node_aware_test.exs` (in `../live_hooks/`) holds 1 + 1.
The pure support-module units under `projects_live/`, `settings_live/`, `system_live/`, `home_live/` and `agents_live/` are `async: true` (see "async policy").
No page or unit suite writes the config dir BEAM-globally: it is isolated per process through `EvoDash.Test.ConfigDir.isolate!/1` (proof: `../support/config_dir_test.exs`).

## Notes for Agents — deterministic waits (the single rule future edits must not break)

Every wait is deterministic: a synchronous `assigns/1` read (`:sys.get_state/1`), a monotonic seq/counter written inside the handler, or a bounded poll at a 1–2 ms cadence.
Per-suite cadences and budgets:

- `tasks_live_test.exs` — `@wait_poll_ms` = 2 ms via `wait_until/3` (a 2000 ms default deadline; the function's own comment still says "in seconds" — the code compares milliseconds); `flush_tasks_load/2` drains a load chain `flush_loading` → `tasks_loading == false` → `drain_async_loads/2` (a leading `:sys.get_state/1`, then wait out an armed `tasks_reload_pending` debounce, then `await_view_async_loads/2`) → `render/1`.
- `review_live_test.exs` — `@wait_poll_ms` = 2 ms inside `wait_until/2` (5 s budget).
- `home_live_test.exs` — `@poll_interval_ms` = 2 ms inside `wait_until/2` (2 s budget); `await_source_available/3` 2 s.
- `welcome_live_test.exs` — `@llm_test_poll_ms` = 2 ms under a `@llm_test_await_ms` 5 s budget (`await_llm_test_result/1`, `await_spawned_llm_test/0`; neither ever fails the test).
- `projects_live_test.exs` — `wait_assigns/3`, `wait_for_fake_callers/3` and the GitHub describe's `wait_until/3` poll at 2 ms (3 s / 2 s budgets); `wait_for_task_terminal/2` polls `TaskRegistry.get_task/1` every 2 ms with a 10 s budget and is best-effort (it only keeps a still-spawning git port from racing a temp-dir teardown).
- `agents_live_test.exs` — `wait_until/2` still polls at 10 ms (5 s budget) and `await_latch/2` polls a shared `:atomics` flag at 1 ms (5 s, never raises).

**The 0 ms rule**: zero-length `refute_receive` / `refute_push_event` probes are allowed ONLY after the mailbox has provably drained — i.e. after a synchronous `:sys.get_state` round-trip, a completed drain helper, or a dead-helper-process await has ALREADY proved the preceding work finished.
Then the 0 ms probe is conclusive and strictly stronger than any timed window; without such a precedent, use a bounded backstop (a monotonic counter assertion) plus a small margin.
Examples in force: `tasks_live_test`'s `refute_receive :page_load_spawned, 0` (preceded by `page_load_seq == 1/2` — the only writer is `start_async_page_load/3`, the hook's only caller — and by the synchronous `:sys.get_state`), `agents_live_test`'s `refute_receive {:commit_graph_call, …}, 0` after asserting both commit-graph assigns false, and the three `refute_push_event(view, "task_notification", %{}, 0)` probes in `ProjectsLiveSyncTest` (never in the async module — see "the notification scan is store-global" below) after `drain_task_reload/1`.
The drain alone is NOT sufficient for a `task_notification` refute: the scan reads the RUN-WIDE store, so GLOBAL quiet is the other half of the precondition.
No fixed `Process.sleep` is a mechanism anywhere; the only fixed waits are deliberate and documented per suite (see each suite's note below).

## Notes for Agents — ReviewLive suite (`review_live_test.exs`)

**The file is ONE file with ELEVEN modules, split for parallelism**: the file-local `EvoDashWeb.ReviewLiveTest.Helpers` (shared helpers + fixtures, no tests), nine `use EvoDashWeb.ConnCase` suites — `ReviewLiveArchiveTest` (21 tests, async), `ReviewLiveMergeCheckTest` (2, async), `ReviewLiveLoadTest` (14, async), `ReviewLiveMultiRepoTest` (13, async), `ReviewLiveChromeTest` (16, async), `ReviewLiveRemoteAutoResolveTest` (1, async — `auto_resolve` against an UNREACHABLE remote node publishes nothing), `ReviewLiveMergeTest` (24, sync), `ReviewLiveAutoResolveTest` (3, sync), `ReviewLiveSyncTest` (19, sync) — and a `ConnectionManager` fake; 113 tests, ~6 900 lines, intentionally long.
The insight that motivated it belongs to the whole suite: ExUnit parallelises across MODULES, never within one, so a single `async: true` module gains nothing — carving one long file into several modules is what actually shortens the run.
Which module a test lands in is decided by two PROCESS-GLOBAL hazards, both symmetric (a writer and a reader must not overlap): app env (`Application.put_env/2` seams) + the `EvoDash.ActiveTasks` hub + `PATH`, and the `"tasks"` PubSub topic — `EvoGit.TaskRegistry` broadcasts `{:task_updated, …}`/`{:task_deleted, …}` on every mutation, which arms `NodeAware`'s reload debounce on EVERY mounted page in the BEAM, so a module that CLICKS a task-mutating review action is a publisher and must stay sync.
Fixture SEEDS go through `EvoGit.Store.put_task` and cleanup goes through `delete_seeded_task!/1` (a direct Store delete, no broadcast) for exactly that reason.

**Every review action runs OFF-PROCESS.** `ReviewLive.spawn_action/4` starts an `EvoDash.TaskSupervisor` child behind `EvoDash.SafeCall.run/1` that always reports `{:review_action_result, task_id, node, action, action_ref, result}`, applied by `apply_action_result/4` after the in-progress marker (`@review_action`, nil | `%{kind:, repo_id:, seq:}`) is cleared.
Consequence for tests: `render_click`/`render_submit` only prove DISPATCH.
Any assertion on action-derived state — `local_repo_resolutions` / a repo's `resolution`, `review_status`, the completion banner, the `EvoDash.ActiveTasks` hub snapshot, a flash from an action — or on an injected runner-seam message MUST call the file-local `await_review_action_settled/1` after the click (it polls `:sys.get_state` for `review_action == nil` and returns a fresh render; a STOPPED view — resume/ignore navigate unconditionally — counts as settled and yields `""`, which is why `await_review_action_settled/1` tolerates `:noproc`).
`settle_debounced_task_reload/1,2` is still required before the NEXT mutation click and before durable reads: it syncs on `TaskRegistry.list_tasks/0` (so the arming cast's broadcast is already delivered), drains the debounce via `assigns/1`, waits `:tasks_reload_pending → false`, then flushes a landing async review load.
Transient post-action state (`branch_exists == false`) is read BEFORE settling; durable state (`:resolution`, banner, `review_status`, hub snapshot, card DOM) AFTER.
The suite does NOT depend on a wide `:node_aware_reload_debounce_ms` window.

Helper inventory (all public on the shared `EvoDashWeb.ReviewLiveTest.Helpers` module and imported by every suite module — verify before naming anything new; `target_branch_selection/1` never existed, it is `target_branch_select/1` + `selected_option_value/1`):
`await_review_action_settled/1`, `settle_debounced_task_reload/1,2`, `flush_review_load/2` (delegates to `EvoDashWeb.TestHelpers.flush_loading/4` after `await_mount_async_loads/1`), `await_mount_async_loads/1`, `mount_async_task_pids/1`, `wait_hub_warm/1`, `assert_hub_excludes_task/1`, `wait_until/2`, `repo_resolution/2`, `mount_with_repos/3` (injects a `{:review_data_loaded, …}` at the CURRENT `load_generation`), `repo_card_html/2`, `overflow_menu/1`, `repo_select_state/1`, `repo_target_selection/2`, `completion_back_href/1`, `target_branch_select/1`, `selected_option_value/1`, `merge_submit_state/2`, `reject_button_state/2`, `task_action_state/2`, `control_state/2`, `install_blocking_merge_runner/2`, `install_blocking_reject_runner/1`, `install_failing_gh_cli/0`, and the seeding/git-fixture helpers below.
The blocking runners signal `{tag, runner_pid, repo_path}` and block on `receive :release` — a deterministic "still in flight" window with no sleeps.

The suite is organised around FOLDED multi-scenario tests (one mount drives a whole state machine), which is why describes carry few `test` blocks.

**Module setup (identical in all eight suites)**: `EvoDash.Test.IsolatedTaskStore.assert_production!()` (fail loudly if a prior suite leaked an isolated pair); `install_canonical_merge_check_runner()` in `setup_all` — ONE canonical `Helpers.canonical_merge_check_runner/4` stub that is installed for the whole file family and NEVER deleted (an unstubbed runner does real `merge-tree` work that races ExUnit's temp-repo teardown, and a per-test DELETE would punch a hole a concurrently mounting sibling could fall into; only this file family reads the key, so leaving it installed is inert).
The merge-check module's BLOCKING stubs therefore do NOT replace the app-env value: they register their own fixture repos in a per-test `:persistent_term` set consulted by that one canonical function (a replaced `:merge_check_runner` would be clobbered mid-test by a concurrently starting sibling's `setup_all`), and every other repo resolves to `:clean` immediately.
The six `async: true` suites clear ONLY the local `{nil, node()}` context (`EvoDash.ActiveTasks.invalidate(nil, node())`, on entry AND in `on_exit`) so a concurrent module's per-test snapshot survives; the three `async: false` suites keep the whole-table `EvoDash.ActiveTasks.reset()` (they run alone). Both clear the last test's sidebar snapshot so it cannot leak into a later whole-page dead render, e.g. `PageControllerTest`.

**Per-repo card contract**: one card per repo (`RepoCards.repo_cards/1`; the primary-scoped Continue-task + "…" overflow menu live in `Actions.task_actions/1`). Merge/reject are per-repo and never navigate — `render_submit` on `#merge-form-<repo_id>` (hidden `name="repo_id"` + its own `<select name="target_branch">`) or `render_click(view, "reject", %{"repo_id" => id})`; the runner seam is invoked ONCE per call.

Resolution states: `nil` (actions rendered iff `branch_exists`), TERMINAL `:merged`(`target`) / `:rejected` / `:handled` (load-time seed: non-blank `branch_name` ∧ NOT `branch_exists`), non-terminal `:error` / `:conflict`(`detail`).
Merge targets travel in `:review_merge_runner` / `:review_reject_runner`; the async merge check in `:merge_check_runner` (results injected as a 6-tuple `:merge_check_result`).
Archive seams: `:review_archive_runner` (3-arity `(node, task_id, opts) -> %{entries: [map()], total: non_neg_integer()}`) and `:review_archive_agent_runner` (3-arity `(node, task_id, agent_id) -> map() | nil`), resolved INSIDE the spawned child at CALL time (a seam injected after `live/3` is honoured) and installed/deleted around the click.
Result messages: `{:review_archive_loaded, task_id, node, seq, offset, result}` (`offset == 0` REPLACES, larger APPENDS deduped by `agent_id`) and `{:review_archive_agent_loaded, task_id, node, agent_id, seq, result}`; both are stale-dropped on a task/node mismatch or a `seq` below their own generation (`archive_seq` for pages, `archive_agent_seq` for results).
`NodeContext.get_task_lite/2` is the page load (LITE — no archive key); `ArchiveLoad.sync_context/1` is unit-tested on a hand-built `%Phoenix.LiveView.Socket{}` (`archive_socket/1` must carry `__changed__: nil` because `force_assign/3` reads it).

**Git fixtures** (`describe "paged lazy archive load"` and the multi-repo describes): the suite needs REAL repos (a base commit, a primary branch renamed from the machine's `init.defaultBranch`, an optional secondary branch, an agent `task-branch` with a change commit).
- Module templates (PER module, never shared): each suite module's `setup_all` pre-builds ONE repo per required `{primary, secondary}` shape — as needed `{"main", "dev"}`, `{"dev", nil}`, `{"main", nil}` — via `build_templates!/1` → `build_repo_with_task_branch!/3`, hands the `%{{primary, secondary} => %{dir:, change_sha:, base_sha:}}` map to `on_exit` by closure, and passes it into each test through `Process.put(:review_templates, templates)` in a `setup` block.
- Why the process dictionary: the helpers live on a module shared by eight suites, so they must not key fixtures on `__MODULE__`; `review_template!/2` reads `Process.get(:review_templates)` and every `on_exit` closure captures the map instead of reading it (on_exit runs outside the test process).
- Per-test copy: `create_review_task_with_repo!/3` and `create_multi_repo_review_task!/2` call `copy_review_template!/3`, which `File.cp_r!/2`s the template into a unique `System.tmp_dir!()` dir and returns `{copy_dir, template_change_sha}`; return tuples and task seeding are unchanged. The multi-repo fixture copies the SAME `{"main", "dev"}` template for both roles, so `primary_sha == foreign_sha` in every multi-repo test (no test compares them).
- Isolation contract (must hold): the copy is a plain recursive BYTE copy — never `cp -l`/hard links, never `git clone --shared` into the template's object store — so a test may freely mutate its copy (one test does a REAL `git merge` + branch delete). The template is quiescent when copied (`build_repo_with_task_branch!/3` ends on a `git checkout`; no `index.lock`). Cleanup registers `on_exit` for each copy.
- `review_template!/2` RAISES when asked for a pair this module's `setup_all` did not pre-build — add the pair to that module's `build_templates!/1` list instead of expecting a from-scratch fallback.

## Notes for Agents — async mount loads & exit-safety seams

`ProjectsLive`, `TasksLive` and `SettingsLive` do ZERO task-store work in `mount/3`: loads run through app-env RUNNER seams resolved AT SPAWN TIME inside `EvoDash.SafeCall.run/1`, so a runner that exits/raises becomes an error VALUE (or sends nothing) instead of crashing the page.
Install seams with `Application.put_env` before `live/3` and delete them in `on_exit`.

- **ProjectsLive async batch** — `:projects_async_load_runner` is a 0-arity fun returning the results map, whose `model_profiles` and `default_selected_model_id` keys are MANDATORY (read by dot access) while `recent_projects` / `terminal_ids` / `auto_activate?` are optional.
  Success message: `{:async_project_load, node, prev_node_id, path, results}`; a runner that exits/raises sends NOTHING, so the page keeps `recent_projects: []` / `notified_task_ids_ready?: false`.
  Helpers: `install_projects_async_load_runner/1`, `restore_registry_on_exit/0` (frozen-registry safety net), `wait_for_recent_projects/2` and `wait_notified_ids_ready/1` (both via `wait_assigns/2`), `await_async_loads/1` (synchronous `assigns/1` drain FIRST, then monitor this view's `EvoDash.TaskSupervisor` children via `$callers`).
  Any test that seeds recents and then asserts palette contents / path suggestions / auto-activation must call `wait_for_recent_projects/2` right after `live/3`; notification tests must call `wait_notified_ids_ready/1` BEFORE `send(view.pid, :node_aware_reload_tasks)` and `await_async_loads/1` before `assert_push_event` / `refute_push_event`.
  Off-process proof: `:sys.suspend(EvoGit.TaskRegistry)` (+ `restore_registry_on_exit/0`), send `:node_aware_reload_tasks`, and show the synchronous `assigns/1` round-trip returns while the store is frozen (`mount_async_task_pids(view.pid) != []`), then resume.
  Zero-store mount proof: freeze the registry around BOTH the dead render (`get(conn, ~p"/projects")`) and `live/3`.
  A blocked-batch test makes "recents not present yet" deterministic: the injected fun sends `{:batch_started, self()}`, blocks on `receive`, then returns; assert the mount defaults, send `:proceed`, then `wait_for_recent_projects/2`.
- **ProjectsLive `?resume_from=` foreign-repo restore is ASYNC too** — `handle_params` calls `start_foreign_repos_restore/2`, which spawns an `EvoDash.TaskSupervisor` child that reads the previous task's `opts[:foreign_repos]` and replies `{:foreign_repos_restored, task_id, node, result}`; until that message is handled `@foreign_repos` stays whatever the mount seeded (`[]` when no project is active).
  Reading `assigns(view)[:foreign_repos]` straight after `live/3` is therefore a RACE, and `projects_live_test.exs:3275` ("resume_from restores foreign repos from the previous task (writable + base_sha)") is its ONLY site — under heavy host load it surfaces as `assert %ForeignRepo{id: "orig", …} = nil`, i.e. `Enum.find/2` saw an empty list, not a wrong struct.
  Deterministic form: wait first, as the sibling remote-resume test does (`wait_assigns(view, &(&1[:active_project_path] == tmp_dir))`); `await_async_loads/1` also settles this child because it carries the view pid in `$callers`.
  An empty assign has two other load-dependent sources: `TaskRegistry.get_task_lite/1`'s offloaded read degrades to `nil` at its 28 s `ReadOffload` deadline, and a `GenServer.call` timeout arrives as `{:error, _}` from `SafeCall` — both land on the `{:ok, []}` / `{:error, _}` arms of `handle_info({:foreign_repos_restored, …})`, which leave `[]` untouched (the error arm only adds a flash).
- **TasksLive page load** — `:tasks_page_load_runner` is a 4-arity `(node, page, page_size, filters)` fun resolved inside `PageLoad.run/6`; `{:tasks_page_loaded, seq, node, result}` is ALWAYS sent, so `exit(:boom)` / `raise "boom"` runners leave the LiveView alive with `tasks_loading == false` and `tasks_error != nil`.
  `:tasks_page_load_hook` (installed by `install_page_load_hook/0`) observes every spawn; `:page_load_seq` is bumped only by `start_async_page_load/3` — the hook's only caller — so it is the deterministic witness for "a load was spawned", paired with a 0 ms `refute_receive`.
  Error UI: a load that never succeeded with no rows renders `#tasks-load-error` ("Could not load tasks.") INSIDE `#tasks-list`; a failed BACKGROUND reload keeps the rows and renders `#tasks-refresh-error` ("Could not refresh tasks.") ABOVE `#tasks-list` (assert the strip via `render(view)`, rows via `render_tasks_list(view)`). Recovery: delete the seam, `render_click(view, "retry_load")`, wait `tasks_error == nil`.
  `flush_tasks_load/2` must be the LAST statement of every test that mounts `~p"/tasks"` (see "Store-offloaded reads" below).
- **SettingsLive mount funnel** — `mount_settings/2` funnels every mount in the file: `live/3`, then `await_mount_async_loads/1` (monitor this mount's `$callers` children, then drain), and only then hands the view to the test, so a late node-data apply can never clobber test-driven state. The ORIGINAL mount HTML is returned unchanged (the "shell seeding" describe asserts on it).
  The same `await_mount_async_loads/1` pattern exists in `review_live_test.exs` and `projects_live_test.exs` (`await_async_loads/1`).
  `settings_live_agents_test.exs` uses its OWN owner-aware variant (`mount_settings/1` → `await_view_async_loads/1`): a bounded 2 ms poll (`@wait_poll_ms`) on "no live `EvoDash.TaskSupervisor` child whose `$callers` contain THIS view pid", a ~5 s best-effort cap (`@settle_timeout_ms`), then a `render/1` drain — the same helper is reused at the `reload_custom_tools` click so a sentinel injected afterwards is provably the last status applied. An unset `$callers` counts as waitable (a freshly spawned child may not have run yet) and converges because every `Task.Supervised` child sets it before running.
  `projects_live_test.exs` builds ONE `git init` + empty-commit template in `setup_all` and gives every repo-needing test a `File.cp_r!` copy (~3.5 ms per copy against ~13 ms for a fresh `git init` + commit) — always a plain recursive byte copy, never hard links or `git clone --shared`, and `.git/hooks` sample scripts are dropped from the template as the biggest part of the copy cost.
  `settings_live_test.exs` SEEDS model-profile fixtures straight into `config.toml` (`seed_model_profiles/1`, the same TOML shape `save_model_profile` persists) instead of driving the add/save UI for setup — those events remain the subject of the dedicated `add_model_profile` / `save_model_profile` tests, and each one costs a full page render.

## Notes for Agents — Agents-page commit-history view (temporal) tests

`@left_view` (`:tree` default | `:commits`) is toggled by `handle_event("switch_left_view", %{"view" => "tree"|"commits"})` (any other value is a no-op); the segmented buttons are `#left-view-tree` / `#left-view-commits`.
Switching to `:commits` lazily fetches the TEMPORAL graph via `:agents_commit_graph_runner` (default `&EvoDash.NodeContext.list_task_commit_graph/5`), resolved AT SPAWN TIME inside an `EvoDash.TaskSupervisor` child — stub it BEFORE `live/3` and never let a test reach the real RPC/core (`EvoGit.CommitGraph` may be absent).
The fetch is TASK-SCOPED: `commit_graph_groups/1` groups eligible agents by `{repo_key, task_id}` (repo_key = `repo_root`; eligible = binary `repo_root`, `base_commit`, `current_commit`, `task_id`; groups sorted by `{repo_key, task_id}`) and each group issues ONE call `runner.(node, task_id, repo_key, live_tips, limit: 100)`, where `live_tips` is that group's de-duplicated non-nil `current_commit`s among its NON-ended agents (an all-ended group is still fetched with `live_tips == []`). A non-`{:ok, _}` reply HALTS the per-group loop.
