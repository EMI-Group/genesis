# JS Hooks

## Intent

Phoenix LiveView JavaScript hooks for the EvoDash dashboard. A LiveView JS hook is a plain
JS object with lifecycle callbacks (`mounted`, `updated`, `destroyed`) registered with the
`LiveSocket` and attached to a DOM element via the `phx-hook="<Name>"` attribute.

## API Surface

### Hook Registration

Hooks used by page markup must be registered in `../app.js` in the `LiveSocket` constructor's `hooks:` map.
Every hook module in this directory is imported and registered by `../app.js`, so a page only has to mount `phx-hook="<Name>"` and supply the attributes its integration contract below requires.

```js
import {hooks as colocatedHooks} from "phoenix-colocated/evo_dash"
import SidebarCollapse from "./hooks/sidebar_collapse.js"
import NodeSwitchFade from "./hooks/node_switch_fade.js"
import AdaptiveInput from "./hooks/adaptive_input.js"
import LegendTooltip from "./hooks/legend_tooltip.js"
import DiffViewer from "./hooks/diff_viewer.js"
import CommitGraph from "./hooks/commit_graph.js"
import CapsulePanel from "./hooks/capsule_panel.js"
import DisclosureMotion from "./hooks/disclosure_motion.js"
import DirectoryPicker from "./hooks/directory_picker.js"
import FilePicker from "./hooks/file_picker.js"
import StatePersistence from "./hooks/state_persistence.js"
import AgentHistoryAutoScroll from "./hooks/agent_history_scroll.js"
import {DesktopQuit, DesktopQuitConfirm} from "./hooks/desktop_quit.js"
import UpdateStatus from "./hooks/update_status.js"
import Guide, {guideClientId} from "./hooks/guide.js"
import ListEnter from "./hooks/list_enter.js"
// ...plus the hooks declared inline in app.js (TauriDetect, PathAutocomplete,
// ClipboardCopy, AutoClearFlash, PlatformDetect, FocusInput, PaletteList)
hooks: {...colocatedHooks, TauriDetect, DesktopQuit, DesktopQuitConfirm, UpdateStatus,
        PlatformDetect, PathAutocomplete, DirectoryPicker, FilePicker, Guide,
        StatePersistence, BrowserNotifications, AutoClearFlash, ClipboardCopy,
        AgentHistoryAutoScroll, DialogModal, SidebarCollapse, NodeSwitchFade,
        AdaptiveInput, LegendTooltip, FocusInput, PaletteList, DiffViewer, CommitGraph,
        CapsulePanel, InspectorMessages, AssistantDisclosure, AssistantComposer,
        DisclosureMotion, ListEnter}
```

`../app.js` is a thin entry: the `LiveSocket` + `hooks:` map, `longestCommonPrefix`, the hooks declared inline (`TauriDetect`, `PathAutocomplete`, `ClipboardCopy`, `AutoClearFlash`, `PlatformDetect`, `FocusInput`, `PaletteList`), the `guide_client_id` connect param (imported from `./guide.js`) and the topbar/live-reload tail.

### ClipboardCopy hook — copy strategy & fallback

`ClipboardCopy` is the SINGLE copy mechanism for ALL copy buttons (Tasks, Code Review, Projects, Settings, Welcome). Reads `data-content` from the element (`phx-hook="ClipboardCopy"` + `data-content`); a falsy/empty `data-content` is a no-op. Copy strategy, in order:

1. **`navigator.clipboard.writeText(content)`** — used when available (secure contexts only: https, `localhost`/`127.0.0.1`, `file:`). On REJECTION the error is `console.warn`ed and execution falls through to the execCommand fallback (the rejection is never swallowed silently).
2. **Legacy fallback — hidden textarea + `document.execCommand("copy")`** — used when `navigator.clipboard` is unavailable (plain HTTP served at a LAN IP / non-localhost hostname — the documented prod and `PHX_IP` remote-access configurations) or after a `writeText` rejection. Creates a temporary `<textarea>` (`position: absolute; left: -9999px; readonly`), sets its value, `select()`s it + `setSelectionRange(0, value.length)`, calls `document.execCommand("copy")`, removes the textarea, and restores the user's prior selection/range (`getSelection()` saved before, `removeAllRanges()` + `addRange()` after). Works in non-secure contexts and most webviews because it runs inside the user-gesture click handler.

On ANY successful copy the hook pushes `"copied"` (the server flashes `gettext("Copied to clipboard")` — handlers exist in `tasks_live.ex`, `review_live.ex`, `projects_live.ex`, `welcome_complete_live.ex`; SettingsLive has no handler, so its copy works but shows no flash) and briefly tints the button's first `<svg>` with a 2s `text-success` class. Success handling is shared via the hook's `markCopied()` method — every success path (writeText resolve, execCommand true) goes through it. If BOTH paths fail (execCommand returns false or throws), NO fake `"copied"` event is pushed; a clear `console.warn` surfaces the failure so it is never invisible.

### UpdateStatus hook — module-level once-bound listener/timer pattern

`UpdateStatus` is the **reference pattern for a global push-based hook**: module-level `let updateListenersBound = false; let updateTimersStarted = false; let updateCurrentHook = null;`. `mounted()` guards on the Tauri detection (`const isTauri = !!(window.__TAURI__ || window.__TAURI_OS_INTERNALS__)`) and returns early outside the shell; sets `updateCurrentHook = this`; binds the three window listeners ONCE:

```js
if (!updateListenersBound) {
  updateListenersBound = true;
  window.addEventListener("phx:update_check_requested", () => invokeUpdateCheck());
  window.addEventListener("phx:update_download_requested", () => invokeUpdateDownload());
  window.addEventListener("phx:update_apply_requested", () => invokeUpdateApply());
}
```

and starts the timers once: `setTimeout(() => invokeUpdateCheck(), 30000)` (startup check) + `setInterval(() => invokeUpdateCheck(), 6 * 60 * 60 * 1000)` (periodic). `destroyed()` only clears `updateCurrentHook` if it still points at this instance (another mount may have taken over). The `invoke*` functions `window.__TAURI__.core.invoke(...)` the Rust commands (`check_update`/`download_update`/`begin_update`) and push results back via `pushUpdateEvent` (guards the ref and try/catches `hook.pushEvent`). Server side: `EvoDashWeb.LiveHooks.UpdateStatus` (`lib/evo_dash_web/live_hooks/update_status.ex`) attaches `handle_info`+`handle_event` interceptors on EVERY page and is the reference pattern for a **server-side global push hook** (`live_hooks/CONTEXT.md`). This whole module is the model for any one-time global listener hook (module-level once-bound state + `destroyed()` handoff).

### CapsulePanel hook — animated capsule open/close + view drill-down

`CapsulePanel` is attached to every fused-capsule `<details>` root and owns the client half of the capsules' interaction model; the server only renders the markup (initial `data-capsule-view="model"` on the model capsule) and the persistence events.
It writes exactly TWO data attributes: `data-capsule-state="closing"` (present only while the exit animation runs — `css/app.css` keys the close keyframes off it, and it is removed the instant the panel really closes) and `data-capsule-view="model"|"provider"` (which `.capsule-view` is displayed; only roots that actually contain `.capsule-view` children ever receive it, so the mode+speed capsule never grows one).
Every instance is independent: its own document `pointerdown` (capture) + `keydown` (capture) listeners are scoped to its own root, so several capsules on one page close only themselves.
`destroyed()` removes every listener AND completes a close still in flight through the shared helper with `fallbackMs: 0`, so a mid-exit teardown can never leave `data-capsule-state="closing"` behind on a removed node.
Outside click (`pointerdown`, so the press — not the later click — is the dismiss signal) and `Escape` both run `closeAnimated();` Escape additionally `preventDefault()`s and focuses the root `<summary>` (only a panel that is actually `open` reacts, so a closed capsule never steals the key).
`closeAnimated()` delegates the whole exit to the shared `closeAnimated(el, {panel: el.querySelector(".capsule-panel"), attr: "data-capsule-state", onComplete})` from `./disclosure_motion.js`: the helper writes the state attribute, waits for the panel's own target-verified `animationend` (a child view animation must not finish the close early) or its bounded fallback, then removes BOTH the attribute and `open`, and short-circuits in the same task under reduced motion or with no animatable panel.
The hook keeps only its intent bookkeeping: drop `openRequested` first so everything downstream agrees the panel is meant to be closed, ignore a second outside press/Escape while `closing`, and re-assert the flag in the completion callback so a straggling toggle or patch cannot resurrect a closed panel.
One delegated `click` handler on the root intercepts ONLY the root `<summary>` (a native close cannot animate) — a click on the nested `details.capsule-sub > summary` resolves to a different summary and keeps its native toggle.
The same handler drives the view switch: `[data-capsule-drill]` → `setView(dataset.capsuleDrill)`, `[data-capsule-back]` → `setView("model")`, and a `role="option"` (or `.capsule-item` fallback) inside `[data-view="provider"]` → `setView("model")` WITHOUT `preventDefault()` so the item's LiveView `phx-click` still reaches the server and its re-render shows the newly scoped model list.
`setView` writes `data-capsule-view` only when it differs; there is no `phx-click` on the hook element and nothing stops propagation, so LiveView-bound clicks are never swallowed.
An open panel survives server re-renders: a `toggle` listener records `openRequested` (and resets to the model view on a GENUINE closed → open transition), while `updated()` — only when `openRequested` — restores a stripped `open` attribute, clears a leftover `closing` state and re-asserts the current view (a LiveView patch removes every attribute the server does not render, including `open` and both hook-owned data attributes).
Never touch the DOM of a closed capsule in `updated()`: LiveView re-renders the form on nearly every selection, and re-opening a user-closed panel would fight the user.

### InspectorMessages hook — stable-key transcript entries

`InspectorMessages` owns entry animation only and never reads or writes scroll position.
It is registered in `../app.js`; a page only has to mount `phx-hook="InspectorMessages"` on a wrapper with a unique DOM `id` and a nonempty `data-inspector-scope` encoding the viewed node and agent/session identity, and put `data-inspector-message="<stable-key>"` on each message entry descendant.
Keys are opaque strings, not CSS selectors, and must stay unchanged across streamed text/token patches, Markdown re-renders and DOM replacements (never token counts, content hashes or shifting indices); the wrapper is the sole scope boundary, so do not nest differently scoped inspectors inside it.
The mount snapshot and the complete snapshot of every scope change are recorded without animation, so an empty/missing scope is inert and becoming scoped seeds a baseline; change the scope and its transcript together in the same DOM patch.
A scope-local Set remembers keys across removal/reinsertion and node replacement, so only a genuinely new key receives `inspector-message-enter`, duplicate markers never animate twice, and the history lasts until the scope changes or the hook is destroyed.
A MutationObserver watches child-list changes throughout the subtree and only the `data-inspector-scope`/`data-inspector-message` attributes, with an idempotent `updated()` reconciliation for LiveView patches; character-data and class/style mutations are not observed.
Integrators must supply the `.inspector-message-enter` CSS/keyframes plus a `prefers-reduced-motion: reduce` CSS guard in `../../css/app.css`, using theme tokens rather than JS style writes; the hook also respects reduced motion in JS, remembering suppressed keys so they cannot replay, and clears active animations on a live preference change.
An entry's own `animationend`/`animationcancel` removes its class and both listeners (bubbled descendant events are ignored), and removed/re-keyed entries, scope changes and `destroyed()` release everything — destruction disconnects the observer and media listener, with no timers, rAF or polling to cancel.
Keep `AgentHistoryAutoScroll` on a DIFFERENT wrapper (for example the outer scroll container with this hook on its inner message list), because LiveView accepts only one hook name per element and the scroll hook remains the sole scrolling owner.
`./inspector_messages.test.cjs` runs the actual module through `node:vm` against a focused DOM/MutationObserver/media-query seam with no npm dependencies or browser bundle.

### AgentHistoryAutoScroll hook — instant, coalesced stick-to-bottom

The hook keeps a transcript scroller at the latest content while the user is reading the bottom and stays out of the way otherwise; there is NO animation — a single coalesced `requestAnimationFrame` assigns `scrollTop = scrollHeight`.
The pure decision is `shouldFollowLatest(scrollTop, scrollHeight, clientHeight, threshold?)` with `STICK_TO_BOTTOM_THRESHOLD_PX = 56`: the boundary is inclusive, non-finite geometry follows (a no-op assignment is harmless, a lost pin is not), and content that fits or an overscroll past the bottom counts as "at the latest".
`pinned` (initially `true`) is re-evaluated only on USER intent — `scroll`, `wheel`, `touchmove`, `keydown` — and the intent events are coalesced onto the next frame so the geometry already reflects the movement.
A programmatic write also fires `scroll`, but by then the write has landed at the bottom, so the recomputed distance is ~0 and the pin survives — there is no suppression flag and no timestamp window.
While pinned, content growth schedules ONE stick per frame; while unpinned the hook early-returns and DISCONNECTS both observers, so reading history costs no observer work.
A `ResizeObserver` on the scroller and its direct children re-follows late layout changes (Markdown render, images, a `<details>` opening inside a message), and a `MutationObserver` on the scroller (`childList`) re-syncs the observed child set.
Lifecycle: `mounted()` sets the initial pin, attaches the listeners/observers and schedules a stick; `updated()` schedules a stick; `reconnected()` re-derives the pin from live geometry and re-attaches; `destroyed()` cancels both pending frames and releases every listener and observer.
The CSS invariants for the two panels it drives live in `../../css/app.css` ("Auto-scrolled transcripts") and are load-bearing: `overflow-anchor: none` (the hook owns scroll anchoring), `overscroll-behavior: contain` (no scroll chaining at either end) and `scroll-behavior: auto`.
`scroll-behavior: auto` matters because the document sets `html { scroll-behavior: smooth }`; a smooth behavior on these panels would animate every `scrollTop = scrollHeight` assignment into exactly the perpetual-motion shaking the hook removes.
`min-height: 0` on the panels keeps them shrinkable flex children, so a tall transcript scrolls INSIDE the panel instead of growing the column.
The pinning decision is pinned by `../agent_history_scroll.test.cjs` (see `../CONTEXT.md` → "JS Unit Tests").

### ListEnter hook — shared list entry animation

`ListEnter` owns the ONE entry animation for server-rendered lists (task cards, conversation rows, process rows) and never scrolls or orders anything.
The Elixir side owns the DOM contract: the hook mounts on a LIST WRAPPER carrying a nonempty `data-list-enter-scope` (e.g. `"<node>|<project>"`), and each row carries `data-list-enter-key="<stable unique key>"` that survives text/token patches and DOM replacements.
Rows that are genuinely NEW in the CURRENT scope receive the `motion-list-enter` class; its keyframes/timings come from the shared motion foundation (`../../css/motion.css`'s `motion-slide-in` + tokens) and the rule itself lives in `css/app.css`.
The pure planner is `planListEnter({scope, previousScope, keys, seen, reducedMotion})` → `{changedScope, seen, animate}`: side-effect free, never mutating the input `seen` (it returns a NEW Set), ignoring empty/non-string keys and keeping the first occurrence of a key.
The FIRST snapshot (`previousScope` undefined) and ANY scope change are baseline-only — they re-seed `seen` from the current keys alone, so a project/node/session switch paints silently and only later insertions move — and nothing animates under reduced motion or on an unscoped wrapper (`animate` stays empty while keys are still remembered).
One coalesced `requestAnimationFrame` per mutation burst reconciles (so a patch that appends ten rows plans once against the final list), a scope change clears any running animation, and detached/re-keyed rows, `animationend`/`animationcancel` and `destroyed()` all release the class and its listeners.
The hook is INERT until a template opts in with the two data attributes; `./list_enter.test.cjs` pins the planner through `node:vm`.

### Motion foundation (DisclosureMotion + close helpers)
`./disclosure_motion.js` is the ONE motion foundation for exits: every duration, easing and keyframe lives in `assets/css/motion.css` (`--motion-fast` 120 ms, `--motion-base` 170 ms, `--motion-slow` 220 ms, `--motion-ease-out`/`--motion-ease-in`, the `motion-fade-in`/`motion-fade-out`/`motion-slide-in` keyframes and ONE global `prefers-reduced-motion` backstop), and JS only decides WHEN an exit is over.
No CSS and no timing is duplicated in JS; the hook writes exactly one attribute and the stylesheet owns the rest.
Markup recipes later packages apply:
- `<details class="motion-disclosure" phx-hook="DisclosureMotion">` → animated open AND close: the hook intercepts a click on the element's OWN `<summary>` while open, sets `data-disclosure-state="closing"` and only then removes `open`.
- `<details class="motion-disclosure">` (no `phx-hook`) → animated open only; closing stays the browser's instantaneous native toggle.
- `closeAnimated(el, {panel, attr, fallbackMs, onComplete})` → the reusable exit primitive for any `:if`-mounted or `<dialog>` node whose hide must wait for an animation.
`closeAnimated` is idempotent — exactly ONE completion however many events, timers or repeated requests arrive — and completes IN THE SAME TASK (synchronously, before returning) under reduced motion, with no animatable panel, or while a previous close is already running.
Only an `animationend` whose `target` IS the panel finishes an exit; a child element's animation (a nested disclosure, a spinner) and a native `::backdrop` event never can.
`DISCLOSURE_CLOSE_FALLBACK_MS` (200 ms, documented bound `0 < x <= 500`) is the safety net for a panel that fires no animation at all.
A `<dialog>`-shaped root is released through its own `close()` so a window's `"close"` listeners still fire; everything else simply loses the `open` attribute.
Opening is deliberately the CSS-only path (`details.motion-disclosure[open] > :not(summary)`), so `updated()` re-arms nothing and never fights a LiveView patch, and Enter/Space on the focused summary still closes (as an intercepted click).
`destroyed()` removes the click listener and releases a running exit.
`prefersReducedMotion(win = globalThis.window)` is the ONE guarded `matchMedia` call (`false` where `matchMedia` is absent) and is published on `globalThis.genesisMotion` next to `closeAnimated`, because `../dialog_modal.js` is vm-sliced as a CLASSIC script by its test and cannot statically import this module — the same side-effect contract `highlight_setup.js` uses for `window.hljs`.
Attribute contracts: `data-disclosure-state="closing"` (the `<details>` exit), `data-window-state="closing"` (the workbench `<dialog class="workbench-window">` exit, written by `closeAnimated` through `Workbench.closeWindow/1`), and `data-dialog-state="opening"|"open"|"closing"` (the native modal, owned by `../dialog_modal.js`).
Reduced motion never waits: every one of those paths tears down in the same task instead of waiting for an `animationend` that may never arrive.
The decisions are pinned by `./disclosure_motion.test.cjs`.

### DialogModal hook — integration routing

`../dialog_modal.js` is imported and registered by `../app.js`; `../CONTEXT.md` → "DialogModal Integration Contract" is authoritative for host markup, accessibility, focus restoration, native/nonmodal fallback behavior, dismissal and lifecycle semantics.
The close is TWO-PHASE and owned by the hook: `_hide()` writes `data-dialog-state="closing"` (the stylesheet keys the dialog and its `::backdrop` exit off it, while the element is still open) and runs the immediate teardown on the `animationend` of the `.modal-box` panel whose `target` IS that panel, or on the 200 ms bound.
`_openModal()` mirrors it with `"opening"` → `"open"`, and a genuine reopen cancels a pending exit so its timer can never close the freshly reopened dialog.
Without an animatable `.modal-box`, without the `matchMedia` bridge, and under reduced motion the teardown happens in the SAME TASK — which is what lets the fake-DOM `../dialog_modal.test.cjs` (every node's `querySelector` returns `null`, no `matchMedia`) keep asserting `open`/focus immediately after an event.
`destroyed()` (server teardown) stays fully SYNCHRONOUS: it removes its listeners, tears the dialog down and restores focus in one task, never leaving a closing dialog or focus inside a removed node.
Dismissal semantics: `_dismiss()` pushes `dialog_closed` synchronously and keeps the `_closed` latch.

### Workbench right panel — hidden by default, animated, server-driven search

`#workbench-history` and `#workbench-git` are `aside.workbench-history` siblings the server renders with `hidden` **and** `data-panel-state="closed"`; the `Workbench` hook (in `workbench.js`) owns the attribute from then on.
The panel has exactly three states — `closed` (the aside carries `hidden`), `open`, `closing` (the exit animation runs and `hidden` is already absent) — and the pure decisions live in `./workbench_panel.js` (`initialPanelState/1`, `planPanelRequest/2`, `completePanelClose/1`, `isPanelCloseTransition/2`, `panelCloseWaitsForTransition/2`).
**A fresh tab starts CLOSED on every breakpoint**: `genesis-workbench.history` / `genesis-workbench.git` in `sessionStorage` only remember an explicit user choice (`true` opens, anything else — including `null` — is closed), so there is no desktop default-open and no `/assistant` special case.
Opening removes `hidden`, paints ONE frame at `data-panel-state="closed"` (`requestAnimationFrame`) and only then sets `"open"`, which is what gives the CSS transition a starting point; re-opening during `closing` simply continues from the live interpolated style (the pending hidden-marking is cancelled, never raced).
Closing sets `"closing"` and finishes on the `transform` `transitionend` for that same aside (opacity/flex-basis/padding fire their own events and must not finish it early) or on the bounded `PANEL_CLOSE_FALLBACK_MS` (300 ms) timer, then sets `hidden` + `"closed"`.
A close completes exactly once, so a duplicated event is inert; `prefers-reduced-motion: reduce` removes the transition and closes in the same task instead of waiting for the timer.
Every LiveView patch re-runs `syncHistoryPanel/1`, so an unchanged state is a pure re-assert (it restores attributes morphdom reset from the server markup) and never restarts a running close or re-animates a stable open; the FIRST sync (`panelReady` false) only seeds the state so a stored open preference does not play an entrance on page load.
Invariants: `aria-expanded` on `#workbench-history-toggle` / `#workbench-git-toggle`, `#workbench-history-overlay` + `#workbench-right-resize`, the drawer-vs-docked split (`<1280 px` overlay drawer with `data-workbench-history-drawer-open`), the center column's `inert` while the drawer or a project preview is up, and the `workbench:history-drawer` event.
The panel's query, project filter, status filter and kind control are ordinary server-rendered live-component controls, so the hook never filters rows by title/kind, writes `#workbench-history-project`, toggles `[data-workbench-more]` or juggles `[data-workbench-empty]`; `renderHistory/0` only marks the row whose window is already open (`data-workbench-open` → `is-current`).
The decisions are pinned by `./workbench_panel.test.cjs`.

### WorkbenchProjectPreview — bounded handoff cache + release()

`./workbench_project_preview.js` keeps the last rendered `#main-content` snapshot of each project for the visual handoff while its live view mounts, so the cache is BOUNDED: `MAX_WINDOWS = 2` entries, at most two live windows, because only the project being LEFT is ever handed off.
Recency is Map insertion order — a hit is a `delete` + `set` touch — and an insert (or an over-full cache) evicts the OLDEST entries, never the entry just inserted, so a live handoff is never evicted by its own insert.
`projectPreview.release()` is the exported teardown seam: it clears a pending handoff, empties the cache and removes the shadow-DOM host (a later `remember()` re-creates it and re-clones the stylesheets); `workbench.js` does not call it yet.
The pure planning (`touch`/`keysToEvict`/`store`) carries no DOM and is pinned by `./workbench_project_preview.test.cjs`.

### Server→client push_event patterns

Server `push_event(socket, "name", payload)` reaches the client two ways:

1. **`this.handleEvent("name", cb)`** inside a hook (hook-level; listener lives until the hook is destroyed, survives reconnects): `scroll_to_file` (diff_viewer.js), `picker_result:<id>` (file_picker.js), `persist_state` (state_persistence.js), `task_notification` (../browser_notifications.js), `dialog_open` (../dialog_modal.js), `desktop_quit_closed` (desktop_quit.js). Callback receives the payload as its argument (LiveSocket destructures the CustomEvent detail).
2. **`window.addEventListener("phx:name", ...)`** — LiveSocket dispatches every server push as a `CustomEvent("phx:" + event, {detail: payload})` on `window`, so `e.detail` is the payload map. Examples: `phx:update_check_requested`, `phx:page-loading-start/stop` (detail ignored), `phx:live_reload:attached` (`({detail: reloader})` destructures the detail).

## Constraints

- **NOT colocated**: there are **zero `.exh` files** in the project, so the `colocatedHooks` import from `phoenix-colocated/evo_dash` (see `../app.js`) resolves to an empty object; ALL hooks are hand-written modules in this directory (including `directory_picker.js`, `file_picker.js`, `state_persistence.js`, `agent_history_scroll.js`, `desktop_quit.js`, `update_status.js`, `guide.js`, `list_enter.js` and the `workbench.js` trio with its pure `workbench_panel.js`), and only `TauriDetect`, `PathAutocomplete`, `ClipboardCopy`, `AutoClearFlash`, `PlatformDetect`, `FocusInput` and `PaletteList` remain inline in `app.js`. Do not rely on `.exh` colocated hook generation.
- The hook modules export proper ES modules (`export default`, plus named pure helpers where they exist — `closeAnimated`/`prefersReducedMotion`, `planListEnter`/`LIST_ENTER_CLASS`, `shouldFollowLatest`/`STICK_TO_BOTTOM_THRESHOLD_PX`, `guideClientId`, `DesktopQuit`/`DesktopQuitConfirm`, the `Workbench` trio); the hooks in `app.js` are `const` objects, one per name.
- **Mobile sidebar toggle**: The `#sidebar-mobile-toggle` hamburger button and `#sidebar-overlay` (in `layouts.ex`) are wired up by the `SidebarCollapse` hook. On mobile (< lg breakpoint, checked via `window.matchMedia('(max-width: 1023.98px)')`): hamburger click **opens** the sidebar (removes `-translate-x-full` from `#sidebar`, shows overlay by removing `opacity-0`/`pointer-events-none`, locks body scroll via `overflow-hidden`); overlay click **closes** the sidebar (reverses the above); nav link clicks inside the sidebar close it (event delegation on the sidebar element, survives morphdom re-renders); `updated()` re-applies the mobile open/close state after LiveView navigation patches reset the sidebar's classes. Mobile state is tracked independently from desktop collapse state via `this.mobileOpen`. On desktop, the mobile handlers are no-ops (guarded by `isMobile()`).
- **`SidebarCollapse` sync is probe-guarded**: the collapse sweep (the four `querySelectorAll` walks over the sidebar subtree plus per-element class writes) runs only when the pure probe `collapseSyncNeeded(state, collapsed)` says the DOM disagrees with the intended state, so an ordinary patch of `#sidebar` costs a handful of `querySelector`/`classList.contains` checks instead of the whole sweep.
  The probes are the applied state, the `data-sidebar-collapsed` attribute, the width class (`w-16`/`w-60`), a wrong-state `.sidebar-label`, a wrong-state `.sidebar-collapsed-only`, a wrong-state `[data-sidebar-task-link]` and the collapse toggle's expected chevron class; a MISSING probe element counts as fine (no markup → nothing to fix), and the label/row families are probed with `:not(...)` because they also live inside dynamic lists.
  The icon swap is a non-destructive `classList.replace(from, to)` on the existing element (no `innerHTML` rewrite), and `applyMobileState()` runs on every patch — only the desktop collapse sweep is gated.
  The probe is pinned by `./sidebar_collapse.test.cjs`.
- **Sidebar dropdown dismissal (outside click + collapse)**: the three sidebar `<details>` dropdowns (theme toggle, language selector, node selector) only close on their own `<summary>` click, so the `SidebarCollapse` hook — whose `<aside id="sidebar">` wraps all three — closes every open `details[open]` descendant on a document-level outside click (listener added in `mounted()`, removed in `destroyed()`) and whenever the sidebar is collapsed (the collapsed branch of `applyCollapsed()`, covering the collapse toggle, mount/update re-application, and mobile). Clicks inside an open dropdown's content are excluded so they register before anything closes; opening one dropdown dismisses the others. Dismissal is scoped to the sidebar aside via `closeOpenDropdowns()` and uses `removeAttribute('open')` — DaisyUI's close mechanism.
- **`SetLocale` is NOT a JS hook** — it is a server-side Elixir LiveView on-mount hook (`EvoDashWeb.LiveHooks.SetLocale` in `lib/evo_dash_web/live_hooks/set_locale.ex`). Do not look for it in JS assets.
- **AdaptiveInput `--app-vh` sync (mobile keyboard-aware heights)**: in `mounted()` the hook binds `resize`+`scroll` listeners on `window.visualViewport` (guarded on `'visualViewport' in window`) that set `--app-vh` on `document.documentElement.style` to the keyboard-visible viewport height (initialized once on mount; removed in `destroyed()`). The `@media (max-width: 640px)` overrides in `css/app.css` (Adaptive Input Layout section) consume it so the expanded task-form card bounds to the area above the virtual keyboard; when visualViewport is absent the var stays unset and the CSS falls back to `100dvh`.
- **AdaptiveInput placeholder mirroring (`data-placeholder` is the LIVE channel)**: the prompt textarea is `phx-update="ignore"`, so LiveView re-merges only its `data-*` attributes — the SSR `placeholder` is a first-paint value and `updated()` never fires for that element.
`_syncPlaceholder()` writes `this.el.placeholder = this.el.dataset.placeholder || ""` behind an equality guard and runs on mount, at the top of `_apply()` (so every input, `updated()`, `data-layout` observer and `clear_prompt` refresh also refreshes the hint), and from a second `MutationObserver` on the textarea (`attributeFilter: ['data-placeholder']`, disconnected in `destroyed()`).
Never move the hint back to `placeholder`-only or drop the `data-placeholder` observer: a project becoming active or a mode switch re-renders the hint server-side and only that observer delivers it.

## Known Issues

- **LiveView 1.2 `phx-hook` accepts exactly ONE hook name per element.** The ENTIRE attribute value is looked up as a single hook name (no whitespace splitting) — space-separated multi-hook lists were pre-1.2 behavior and now silently attach NOTHING, logging `unknown hook found for "..."` in the browser console. Never use space-separated hook lists on an element; merge the behaviors into a single hook instead (which is why the diff-viewer hook combines syntax highlighting AND scroll-to-file in one `DiffViewer` hook).
- **`AdaptiveInput.measureAndApply` height write must be UNCONDITIONAL — never "skip when unchanged".** The data-layout equality guard in `applyLayout` is load-bearing (it terminates the observer cycle), but the height write in `measureAndApply` is NOT observed by any observer, so it must always write `ta.style.height = scrollHeight + "px"`. A `prevHeight` skip-guard is a regression: whenever the measured `scrollHeight` equals the previous inline height (e.g. typing on the same line), the write is skipped and the inline style stays at `"auto"` (the value set for measurement) — the CSS `min-height: 120px` then collapses the box, content overflows (scrollbar), and the next keystroke measures from the collapsed state and restores the taller height. The box oscillates between the two heights on every keystroke in compact layout. An unconditional write cannot loop (only `data-layout` is observed) and writing a value identical to the current inline value is a rendering no-op. Do NOT reintroduce a guard on the height write.
- **MutationObserver fires on same-value attribute sets — the `AdaptiveInput` equality guard is MANDATORY.** Chrome fires `MutationObserver` callbacks even when an attribute is set to the value it already holds (e.g. `el.dataset.layout = 'compact'` when it is already `'compact'`). `AdaptiveInput` has a MutationObserver on `.input-layout` (`attributeFilter: ['data-layout']`) whose callback runs `_apply()`. If `applyLayout()` writes `data-layout` unconditionally, every write re-triggers the observer → `observer → write → observer` **infinite synchronous microtask loop** that pegs the CPU and blocks the page. The equality guard (`if (layoutEl.dataset.layout !== layout) layoutEl.dataset.layout = layout;`) is what makes the observer→write cycle terminate in ≤2 firings. NEVER "simplify" it away; it is load-bearing. Same rule applies to any future observer+write pattern: never mutate an observed property inside its own observer without an equality guard.
