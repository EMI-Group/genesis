# Frontend Assets

## Intent

This directory holds all frontend source assets (JavaScript, CSS, vendor libraries, and editor config) for the EvoDash Phoenix web application.
It is the single source of truth for client-side code, compiled by **esbuild** (JS) and **Tailwind CSS 4** (styles) via Mix aliases (`assets.build`, `assets.deploy`).

### How to use

- **Add a new JS module**: place it under `js/` and import from `app.js` (or add a hook module under `js/hooks/` and register it in the `LiveSocket` `hooks:` map).
- **Add custom CSS**: extend `css/app.css` or create additional files under `css/` (auto-scanned by Tailwind).
- **Add a vendor library**: drop a `.js` file in `vendor/` and import via relative path (e.g., `import "../vendor/my-lib"`).
- **Update DaisyUI/Heroicons**: replace the corresponding `.js` file in `vendor/` with the latest release.
- **Update highlight.js**: download `highlight.min.js` (the FULL default build) plus the packs (v11.11.1) from cdnjs into `vendor/`; **zig is NOT on cdnjs** — re-adapt it from the third-party repo into the self-registering IIFE form. Verify the byte counts in the table above (commit them) and run `mix assets.build`.
  Packs MUST stay the cdnjs IIFE form (self-registering on the global `hljs`); an ES-module pack would break the `window.hljs` load-order contract.
  Runtime loading is fully esbuild-bundled — there are NO runtime CDN `<script>` tags.

### Client-side syntax highlighting (highlight.js)

The review diff viewer highlights code in the BROWSER (no server-side highlighter): the backend renders escaped plain-text diff lines and stamps `data-language` (Lumis-style names from `EvoGit.Review.language_for_file/1`) on each `.diff-file-section`; the `DiffViewer` hook highlights the `.diff-split-cell` cells with vendored highlight.js 11.11.1.

- **`js/highlight_setup.js`** — exposes the instance as `window.hljs` via a module SIDE EFFECT. This is load-bearing: the cdnjs packs are IIFEs that self-register on the global `hljs` and export nothing, so `app.js` imports `highlight_setup.js` BEFORE the vendored pack imports (ESM evaluation is depth-first in import order); a changed order makes the packs throw `ReferenceError: hljs is not defined` at bundle load.
- **Language coverage** — the FULL default build registers the ~35 common grammars; the 19 packs add elixir, dart, dockerfile and the 16-language "tier-2" set (zig, nix, erlang, haskell, clojure, scala, julia, nim, crystal, elm, groovy, powershell, ocaml, fsharp, lisp, scheme).
  Every lumis name resolves through the DiffViewer's `LANG_MAP` (`c_sharp`→`csharp`, `text`→`plaintext`) plus hljs aliases (`html`→xml, `toml`→ini, `jsx`→javascript, `tsx`→typescript); an unknown name is skipped harmlessly.
- **`js/hooks/diff_viewer.js`** — the `DiffViewer` hook (`phx-hook="DiffViewer"` on `#diff-viewer`). Runs in `mounted()` AND `updated()`; per `.diff-file-section` reads `data-language`, skips unknown languages, highlights each unmarked `.diff-split-cell` (`dataset.hl === "1"` and empty/whitespace-only cells skipped) via `hljs.highlight` in try/catch (a throw leaves the cell as plain text — never breaks the page), and marks `dataset.hl = "1"`. No-ops if hljs failed to load.
- **CSS palette** (`css/app.css`, `.hljs-*` tokens for BOTH themes). Light: comment `#6e7781`, keyword `#cf222e`, string/regexp `#0a3069`, number/literal/built_in/type/selector-class/id/attr `#0550ae`, title/function_/class_/meta `#8250df`, attr/attribute/symbol/variable/section/doctag `#953800`, strong = `font-weight: 700`, emphasis = `font-style: italic` (GitHub markup: weight/style only, color inherited). Dark (`[data-theme="dark"]`): comment `#8b949e`, keyword `#ff7b72`, string/regexp `#a5d6ff`, number/literal/built_in/type/selector-class/id/attr `#79c0ff`, title/function_/class_/meta `#d2a8ff`, attr/attribute/symbol/variable/section/doctag `#ffa657`.
  Markdown/diff/yaml/html tokens: code/quote `#6e7781` / `#8b949e`, link `#0969da` / `#58a6ff`, bullet `#735c0f` / `#f2cc60`, name/selector-tag/selector-pseudo `#116329` / `#7ee787`, subst `#24292e` / `#c9d1d9`, addition `#22863a` / `#aff5b4`, deletion `#b31d28` / `#ffdcd7`.
  `hljs-tag`/`hljs-punctuation` and the `hljs-class`/`hljs-function` wrappers stay default (their children carry the colors, matching GitHub), and the span-neutralizer rules (`.diff-line-content span` / `.diff-split-cell span` → inline, transparent background, inherited font but NOT `color: inherit`) keep the injected spans from breaking the diff grid.

## Constraints

- **Build tooling**: JS is bundled by esbuild; CSS is processed by Tailwind CSS 4. No Node.js toolchain is required — vendor libs are committed directly.
- **Tailwind source scanning** is explicitly configured via `@source` directives in `app.css` covering `css/`, `js/`, and `lib/evo_dash_web/`. Any new directory with Tailwind classes must be added as an `@source` entry.
- **CSS import order**: `@import` must precede every other rule, so `motion.css`/`view_transitions.css` sit in `app.css`'s import block (`view_transitions.css` LAST) and before the `@source` lines.
- **Theme system**: DaisyUI's built-in themes are disabled (`themes: false`); only the custom "dark" and "light" themes exist, and dark mode is driven by the `data-theme="dark"` attribute, not `prefers-color-scheme` alone.
- **Phoenix LiveView hooks** are hand-written — there are zero colocated `.exh` files, so the `phoenix-colocated/evo_dash` import in `app.js` resolves to an empty object. All hooks live in `js/hooks/` (own files) or inline in `app.js`; full registration table in `js/hooks/CONTEXT.md`.
- **Live reload features** (server logs, click-to-editor) are gated behind `process.env.NODE_ENV === "development"` and must not be relied upon in production.
- **No `node_modules/`**: dependencies live in `vendor/` or resolve via esbuild path aliasing to `../deps/`. Do not run `npm install` unless a `package.json` is introduced.
- **Motion invariants** — new animation goes through `css/motion.css` (a class or one data attribute) and, for exits of `:if`-mounted or `<dialog>` nodes, through `closeAnimated/1` or the `JS.hide(transition: …)` recipe; never per-component keyframes or hand-written JS timers.
  Motion is opacity/transform only (the single exception is `.motion-collapse-grid`'s bounded `grid-template-rows`), never `height`/`width` on the transcript scrollers, the composer or the sidebar, and never `scroll-behavior: smooth` on `#chat-messages`, `.agent-history-scroll`, `.cg-scroll` or `#workbench-history`.
  The global reduced-motion backstop must stay the LAST rule in `motion.css`.

## Notes for Agents

- **StatePersistence — draft scope key contract** (`js/hooks/state_persistence.js`; the server-side identity is `EvoDashWeb.DraftScope`, the ONE place the token and key shape are defined): the hook reads `data-task-draft-project` (raw path) and `data-task-draft-scope` (canonical token: a `vct:///projects/…` point or `vct:///workspaces/…` for a workspace; absent/empty until the server knows one) off `#dashboard-root`.
  Its scope is `{node, token}` with `token = taskDraftScope || project`, so a plain path is its own token and keeps the exact legacy key.
  Keys are `dashboard_state:["<node>","<token>"]` (bare `dashboard_state` when the token is nil) plus `legacyKey` = the path-keyed key, non-null only when the token differs from the path.
  Restore order is the scoped key, then `legacyKey`, then bare `dashboard_state`; a match requires the node AND `scope_token` to equal the token exactly, while a pre-point entry (no `scope_token`) matches by `project` path so an old path-keyed draft is adopted.
  Every write (`persist_state`, `persist_model_selection`, `clear_prompt`, the debounced flush) stamps `scope_token` through ONE `stamp(state, scope)` helper.
  A scope-key change flushes the pending edit under the OLD scope before switching, and the textarea is cleared only when the node or project changed, so a project gaining its VCT point keeps the in-flight typing.
  Two VCT points over one OS path are separate drafts; one point reached through another path spelling (symlink, second mount, workspace member) is ONE draft.
- **Brand icon sizing (`.brand-icon svg`)**: `brand-*` icons (`EvoDashWeb.CoreComponents.icon/1` — `git.svg`, `nix.svg` under `vendor/brand/`) are raw inline SVGs with NO `width`/`height` attributes, rendered inside a `size-*` wrapper span; `.brand-icon svg { display: block; width: 100%; height: 100%; }` fills the wrapper, so the span's `size-*` class controls the rendered size. Keep new brand SVGs square. Regression symptom if removed: the System page self-check git logo renders larger than the ripgrep badge check-circle.
- **DirectoryPicker — server-side pick protocol** (`js/hooks/directory_picker.js`): a thin LiveView client — no Tauri, no File System Access API. Click → `this.pushEvent("directory_pick", {picker_id})` → `ProjectsLive` (local node only) → `EvoDash.DirectoryPicker` GenServer runs the platform-native dialog in a Task (macOS `osascript` / Linux `zenity` / Windows PowerShell .NET, `:wx` `wxDirDialog` fallback) → the server pushes `picker_result:<picker_id>` with `{path, cancelled, unavailable}`.
  `path` → absolute-path regex guard → `fillInput`; then the `data-picker-id="project"`/`"new-project"` browse buttons auto-submit the enclosing form via `form.requestSubmit()` (a full absolute path needs no extra "Open" click; the server re-validates), while `"foreign-repo"` only fills its input. `cancelled` → no-op; `unavailable` → `markManualFallback` (`data-picker-error="manual"`, styled in `app.css`; cleared by `fillInput`).
  `handleEvent` is registered in `mounted()` (survives reconnects) with NO JS-side timeout — the native dialog may stay open for minutes. Degrades to `unavailable` on a remote/headless node, picker disabled (`config :evo_dash, :directory_picker, enabled: false`), no native tool and no wx, picker busy, or GenServer not running.
  Re-entrancy guard `this._picking` prevents stacked dialogs (re-armed by `picker_result` and `reconnected()`). **Remote nodes hide the Browse buttons entirely** (`@tauri_detected and !@remote` in `project_components.ex`); the manual path inputs remain.
- **FilePicker — attach-file protocol (`file_pick`, kind dropdown)** (`js/hooks/file_picker.js`): the objective editor's "+" attach control — a daisyUI `<details class="dropdown ..." phx-hook="FilePicker">` that is a DIRECT child of the toolbar div `.input-controls` (the manual panel `<div id="objective-file-manual" class="file-manual" phx-update="ignore" hidden>` is a SIBLING, unchanged in position/ids).
  Its `<summary id="objective-file-button">` is the visual "+" trigger (native details toggling; summary clicks never start a pick), and the `dropdown-content` menu holds exactly three `<button type="button">` items with NO `phx-click`: `data-picker-kind="text"` + `data-picker-id="objective_file"`, `data-picker-kind="image"` + `data-picker-id="objective_file_image"`, `data-picker-kind="audio"` + `data-picker-id="objective_file_audio"` (`task_form_components.ex`).
  ONE hook instance on the `<details>` owns all clicks by delegation: a `[data-picker-kind]` click closes the dropdown and pushes `file_pick` with `%{picker_id, prompt: <current textarea value, captured as this._basePrompt>, kind}`; any other click is ignored.
  `mounted()` registers the SAME shared handler for each `picker_result:<id>`; the event flows `ProjectsLive` (local node only) → `EvoDash.DirectoryPicker` (`:file` mode) → per-kind payloads.
  Text success is `%{prompt, block, attached: true, name}` (`prompt` = full new objective = base prompt + attached-file Markdown block; `block` = the appended block) and drives the push-back below; image/audio success is `%{attached: true, name, kind}` with NO `prompt`/`block`, so the hook does NOT write the textarea (the server re-render of the staged-attachment chip row is the feedback). `%{cancelled: true}` no-ops, `%{unavailable: true}` opens the manual fallback, `%{error: true}` (+ optional `reason`) console.warns and no-ops.
  **`phx-update="ignore"` push-back (text only)**: the objective textarea (`textarea[name="prompt"]`) is server-untouched, so the hook writes `textarea.value` and dispatches `input` + `change` (AdaptiveInput reacts to `input`; StatePersistence persists on `input`). **Append-not-clobber**: if `textarea.value` still equals `this._basePrompt` the hook applies the full `prompt`, else it appends ONLY `block` (never clobbers typing); with no `block` and a changed value it does nothing.
  **Manual fallback (shared across kinds)**: `unavailable` → `openManual()` reveals the `#objective-file-manual` path input (a popover above the toolbar "+"; CSS in `app.css`); confirm/Enter pushes `file_pick_manual` with the pending id + kind captured at item-click time (`_pendingPick = %{picker_id, kind}`, retained through the unavailable result and cleared when the flow ends).
  **Manual panel exit**: `closeManual()` never flips `hidden` in the same task — it writes `data-file-manual-state="closing"` and delegates to `closeAnimated` (`.file-manual-input-wrap` animates `motion-fade-out`), hiding only on its target-verified `animationend` or bounded fallback, and `openManual()`/`destroyed()` settle an in-flight close synchronously first so a reopen is never hidden and a remount never inherits a stale timer.
  The server answers a manual submission with the SAME `picker_result` payloads: success → close (image/audio only close), `error` → inline error + panel stays open with `_pendingPick` retained for a retry, unavailable/cancelled → close.
  `this._picking` prevents stacked dialogs (re-armed by the result handler and `reconnected()`, which also re-arms `_manualSubmitted`; `_pendingPick` survives a reconnect).
- **Guide — Genesis Guide overlay client (`Guide` hook + `.guide-highlight`)** (`js/hooks/guide.js`): the server-side `EvoDashWeb.LiveHooks.Guide` on-mount hook pushes `"guide_highlight"` with `%{selector}`; the client retries boundedly (~10 × 250 ms, then silent give-up), scrolls the target into view (centering inside `#main-scroll` when it contains the target, else `scrollIntoView({block: "center"})`), adds `guide-highlight` and removes it after ~3 s.
  On dismissal the server pushes `"guide_cleared"` and the hook clears the stored `lastGuideHighlight` so a remount cannot re-apply a stale highlight.
  A stable per-tab `guide_client_id` (`crypto.randomUUID()` with a `Math.random` fallback, sessionStorage-backed) is sent in the LiveSocket connect params; the server keys its guide store by it (stable across `push_navigate` because the socket persists), restores the `@guide` assign per page, and the module-level `lastGuideHighlight` re-applies the highlight on remount.
  No `window.__TAURI__` gating. `.guide-highlight` (app.css Utility section) is a 2px `var(--color-primary-standalone)` outline + 2px offset + `border-radius: 0.25rem`; panel styling is markup-only Tailwind.
- **CommitGraph — vertical commit graph client (Agents page temporal view)** (`js/hooks/commit_graph.js` + the "Commit Graph" section of `css/app.css`): a VERTICAL GitLen/GitKraken-style agent-DAG — one visible ROW per visible node (commit, stub, or folded-run `:gap` row) top → bottom, scrolling inside the `.cg-scroll` both-axis container with a fixed left `<svg class="cg-gutter">` drawing dots and child → parent edges.
  **Commits-mode fill chain (xl+)**: the LiveView adds `agents-tree-body-commits` to the `.agents-tree-panel` card body only while the commits view is active, and app.css hands the panel's height down `.agents-tree-panel .card-body.agents-tree-body-commits` → `#commit-graph` → `#commit-graph-body-<node_key>` → `.cg-repo` → `.cg-scroll` (every link a flex column with `min-height: 0; overflow: hidden`).
  The view-switch row and the error/stale/loading/empty strips are `flex: 0 0 auto`. `.cg-scroll` is the ONE bounded VERTICAL scroller — the lane header's `position: sticky; top: 0` resolves against it, so it never takes an `overflow-*` override; below xl the cap is `min(26rem, 60vh)` (xl+ outside commits mode `min(38rem, 70vh)`). The truncation strip `#cg-truncated-<dom>` and `.cg-empty-note` stay INSIDE `.cg-scroll`.
  **Multi-repo height**: each repo wrapper carries `cg-repo` and is `flex: 1 1 0` over a `min-height: 0; overflow: hidden` flex column (header + selection readout `flex: 0 0 auto`), so N repos split the panel equally, a single repo fills it, and no repo is bounded by its content. ## Known Issues — Custom CSS Variables (`css/app.css`)

- **(i) No old DaisyUI `--b1/--b2/--b3/--bc/--p` namespace.** Because DaisyUI is loaded with `themes: false`, only the new `--color-base-100/-200/-300`, `--color-base-content`, `--color-primary` (etc.) variables exist, defined by the two `@plugin "../vendor/daisyui-theme"` blocks at the top of `app.css`. ## Form-control focus styling ("glow-on-focus")

**ONE global un-layered rule in `css/app.css` is the single source of truth** for every DaisyUI `.input`/`.select`/`.textarea` focus look (solid standalone-accent border + 2px ring at 40% opacity): `:focus` on all three plus `:focus-within` on `.input` (mirroring DaisyUI's own selectors), each guarded with `:not(<class>-success):not(<class>-error)` so state classes keep their own focus styling (`input-success` on the API-key inputs, `-error` validation classes via `CoreComponents`).
It sets `outline: none; border-color: var(--color-primary-standalone); box-shadow: 0 0 0 2px color-mix(in oklab, var(--color-primary-standalone) 40%, transparent)` — colors via `color-mix + var(--color-*)` only, never `--input-color` re-pointing.

**Why un-layered**: DaisyUI 5 emits its own form-control focus rule (`outline: 2px solid var(--input-color)` — the "detached double border") inside `@layer components`, so a layer-wrapped rule would LOSE to it; `app.css` has no `@layer` blocks and its un-layered author CSS beats the plugin's layered styles (the same precedence the accent overrides rely on).
Tailwind `focus:ring-*`/`focus:border-*` utilities are therefore redundant and were removed from every DaisyUI input/select/textarea control (tasks live filter bar, projects live build select, welcome model search, project pickers, task-form selects/inputs, settings sidebar search — which keeps `focus:bg-base-100`). Any new control just gets the class — no focus utilities needed.

**Exceptions (intentionally unchanged)**: HomeLive's composer (`#chat-form`: the picker capsule renders only buttons/listboxes and the borderless composer textarea glows via `.help-composer:focus-within`); `.input-prompt` (task-form textarea, custom class, `.input-prompt:focus { outline: none }`); `.file-manual-input:focus` (amber border). Checkboxes/toggles keep DaisyUI's `:focus-visible` outline and are out of scope.

**Regeneration recipe (run whenever `images/logo.svg` changes):**

```bash
# 1. Render PNGs at nominal widths 16/32/48/64/128/256 — height follows the
#    logo's aspect ratio (1.2334), transparent background, no distortion:
for W in 16 32 48 64 128 256; do
  inkscape --export-type=png --export-filename=favicon-$W.png --export-width=$W priv/static/images/logo.svg
done
# 2. Combine into a multi-size ICO with alpha. Prefer PNG-compressed entries
#    (compact, ~28 KB); a Python one-liner stitching ICONDIR + PNG blobs works,
#    or ImageMagick: magick favicon-16.png ... favicon-256.png favicon.ico
#    (note: IM writes uncompressed BMP entries → ~300 KB; PNG entries are better)
cp favicon.ico priv/static/favicon.ico
# 3. favicon.svg = square-fitted copy of logo.svg (square viewBox, logo group
#    centered via transform="translate(0 <(squareH - logoH)/2>)", width/height 180)
```
