# Frontend Assets

## Intent

This directory holds all frontend source assets (JavaScript, CSS, vendor libraries, and editor config) for the EvoDash Phoenix web application. It is the single source of truth for client-side code, compiled by **esbuild** (JS) and **Tailwind CSS 4** (styles) via Mix aliases (`assets.build`, `assets.deploy`).

## Routing Table

- `./js/` → JavaScript source (LiveSocket setup, inline hooks, topbar; `app.js` + `highlight_setup.js`)
- `./js/hooks/` → Standalone JS hook files (`sidebar_collapse.js`, `node_switch_fade.js`, `adaptive_input.js`, `legend_tooltip.js`, `diff_viewer.js`) — registration table + behavior notes in `js/hooks/CONTEXT.md`
- `./css/` → Stylesheets (Tailwind CSS 4 configuration, DaisyUI themes)
- `./vendor/` → Third-party JS libraries (DaisyUI, Heroicons, Topbar, highlight.js, brand SVGs)

### How to use

- **Add a new JS module**: place it under `js/` and import from `app.js` (or add a new hook module under `js/hooks/` and register it in the `LiveSocket` `hooks:` map in `app.js`).
- **Add custom CSS**: extend `css/app.css` or create additional files under `css/` (they are auto-scanned by Tailwind).
- **Add a vendor library**: drop a `.js` file in `vendor/` and import via relative path (e.g., `import "../vendor/my-lib"`).
- **Update DaisyUI/Heroicons**: replace the corresponding `.js` file in `vendor/` with the latest release.
- **Update highlight.js**: download `highlight.min.js` and `languages/elixir.min.js` (v11.11.1) from cdnjs into `vendor/`, verify the byte counts match the table above (they change with the version — commit them), and run `mix assets.build`. The language pack MUST stay the cdnjs IIFE form (self-registering on the global `hljs`) — an ES-module pack would break the `window.hljs` load-order contract (see below).

### Client-side syntax highlighting (highlight.js)

The review diff viewer highlights code in the BROWSER (no server-side highlighter): the backend renders escaped plain-text diff lines and stamps `data-language` (Lumis-style names from `EvoGit.Review.language_for_file/1`) on each `.diff-file-section`; the `DiffViewer` hook highlights the `.diff-split-cell` cells with vendored highlight.js 11.11.1.

- **`js/highlight_setup.js`** — exposes the imported highlight.js instance as `window.hljs` via a module SIDE EFFECT. This is load-bearing: the cdnjs language pack is an IIFE that self-registers on the global `hljs` and exports nothing, so `app.js` imports `highlight_setup.js` BEFORE the vendored pack import (ESM evaluation is depth-first in import order); the pack registers "elixir" on that same instance, which the `DiffViewer` hook also imports (bundler dedup → one shared instance). If the import order is changed, the pack throws `ReferenceError: hljs is not defined` at bundle load.
- **`js/hooks/diff_viewer.js`** — the `DiffViewer` hook (registered in `app.js`, attached via `phx-hook="DiffViewer"` on `#diff-viewer`). Runs its pass in `mounted()` AND `updated()`; per `.diff-file-section` reads `data-language` (lumis→hljs map: `c_sharp`→`csharp`, `text`→`plaintext`, else passthrough), skips sections with unknown languages, highlights each unmarked `.diff-split-cell` (`dataset.hl === "1"` and empty/whitespace-only cells skipped) via `hljs.highlight` in try/catch (a throw leaves the cell as plain text — never breaks the page), and marks `dataset.hl = "1"`. No-ops gracefully if hljs failed to load.
- **CSS palette** (`css/app.css`): `.hljs-*` token colors for BOTH themes — light: comment `#6e7781`, keyword `#cf222e`, string `#0a3069`, number/literal/built_in/type `#0550ae`, title/function_/class_/meta `#8250df`, attr/symbol/variable/section/doctag `#953800`, operator/params inherit; dark (`[data-theme="dark"]`): comment `#8b949e`, keyword `#ff7b72`, string `#a5d6ff`, number/literal/built_in/type `#79c0ff`, title/function_/class_/meta `#d2a8ff`, attr/symbol/variable/section/doctag `#ffa657`. The span-neutralizer rules (`.diff-line-content span` / `.diff-split-cell span` → inline, transparent background, inherited font — but NOT `color: inherit`, so token colors show through) keep the injected highlight spans from breaking the diff grid.

## Constraints

- **Build tooling**: JS is bundled by esbuild; CSS is processed by Tailwind CSS 4. No Node.js toolchain is required — vendor libs are committed directly.
- **Tailwind source scanning** is explicitly configured via `@source` directives in `app.css` covering `css/`, `js/`, and `lib/evo_dash_web/`. Any new directories with Tailwind classes must be added as `@source` entries.
- **Theme system**: DaisyUI's built-in themes are disabled (`themes: false`). Only the two custom themes ("dark" and "light") are available. Dark mode is driven by the `data-theme="dark"` attribute, not `prefers-color-scheme` alone.
- **Phoenix LiveView hooks** are hand-written — there are zero colocated `.exh` hook files in the project, so the `phoenix-colocated/evo_dash` import in `app.js` resolves to an empty object. All hooks live in `js/hooks/` (own files) or inline in `app.js`; see `js/hooks/CONTEXT.md` for the full registration table.
- **Live reload features** (server logs, click-to-editor) are gated behind `process.env.NODE_ENV === "development"` and must not be relied upon in production.
- **No `node_modules/`**: Dependencies are either in `vendor/` or resolved via esbuild's path aliasing to `../deps/`. Do not run `npm install` unless a `package.json` is introduced.

## Notes for Agents

- **DirectoryPicker auto-confirm (project picker)**: server-side picks return a full absolute path, so after filling the input the `data-picker-id="project"` browse button submits the enclosing `open_project` form directly via `form.requestSubmit()` — the project opens immediately with no extra "Open" click. The `data-picker-id="new-project"` picker also auto-submits (the form still needs a name); `"foreign-repo"` only fills its input (a settings form field). The server-side `open_project` handler (`ProjectFlow.open_project/2`) validates the path (`Path.expand` + `File.dir?`), so auto-submitting is safe even for a stale/bad selection.
- **Brand icon sizing (`.brand-icon svg`)**: `brand-*` icons (`EvoDashWeb.CoreComponents.icon/1` — `git.svg`, `nix.svg` under `vendor/brand/`) are raw inline SVGs with NO `width`/`height` attributes, rendered inside a `size-*` wrapper span. The rule `.brand-icon svg { display: block; width: 100%; height: 100%; }` in `css/app.css` makes the SVG fill its wrapper span, so the span's `size-*` class (e.g. `size-4` = 16px) controls the rendered size. Keep new brand SVGs square — `viewBox` must match the `width/height` ratio to avoid distortion. Regression symptom if removed: System page self-check git logo renders larger than the ripgrep badge check-circle.
- **DirectoryPicker — server-side pick protocol** (hook in `js/app.js`): the hook is a thin LiveView client — no Tauri, no File System Access API. Click → `this.pushEvent("directory_pick", {picker_id})` → `ProjectsLive` (local node only) → `EvoDash.DirectoryPicker` GenServer runs the platform-native dialog in a Task (macOS `osascript` / Linux `zenity` / Windows PowerShell .NET, with Erlang `:wx` `wxDirDialog` fallback — see `apps/evo_dash/CONTEXT.md`) → the server pushes `picker_result:<picker_id>` with `{path, cancelled, unavailable}`. The hook handles: `path` → absolute-path regex guard → `fillInput` → auto-submit for `project`/`new-project` / fill-only for `foreign-repo`; `cancelled` → no-op; `unavailable` → `markManualFallback` (`data-picker-error="manual"`, styled in `css/app.css` per Known Issue (i); cleared by `fillInput` on success). `handleEvent` is registered in `mounted()` (survives reconnects); NO JS-side timeout — the native dialog may legitimately stay open minutes. Degrades to `unavailable` when: remote/headless node, picker disabled (`config :evo_dash, :directory_picker, enabled: false`), neither native tool nor wx available, picker busy, or GenServer not running. Re-entrancy guard `this._picking` prevents stacked dialogs (re-armed by `picker_result` and `reconnected()`). **Remote nodes additionally hide the Browse buttons entirely** (component gating `@tauri_detected and !@remote` in `project_components.ex` — the dialog is local-machine-only): the manual path inputs remain the fallback.
- **FilePicker — attach-file protocol (`file_pick`)** (hook in `js/app.js`): client side of the objective editor's "+" attach-file button (`phx-hook="FilePicker"`, `data-picker-id="objective_file"`). Click → `this.pushEvent("file_pick", {picker_id, prompt})` (`prompt` = the CURRENT textarea value, captured as `this._basePrompt`) → `ProjectsLive` (local node only) → `EvoDash.DirectoryPicker` GenServer in `:file` mode → server pushes `picker_result:<picker_id>` with `%{prompt, block, attached, name}` (success — `prompt` is the full new objective = base prompt + attached-file Markdown block; `block` is the appended block alone) or `%{cancelled}` / `%{unavailable}` / `%{error}` (console.warn, no-op). **`phx-update="ignore"` push-back requirement**: the objective textarea (`textarea[name="prompt"]`) has `phx-update="ignore"` + `phx-hook="AdaptiveInput"` — server re-renders NEVER touch its DOM value, so the hook itself writes `textarea.value` and dispatches `input` + `change` events (AdaptiveInput reacts to `input` for autogrow/layout; the StatePersistence input watcher persists the draft on `input`). **Append-not-clobber**: on success, if `textarea.value` still equals `this._basePrompt` (user didn't type since the click) the hook applies the server-computed full `prompt`; if the user typed meanwhile it appends ONLY `block` (never clobbers typing); with no `block` info and a changed value it does nothing. **Manual fallback**: `unavailable` → `openManual()` reveals the `.file-manual` path input next to the button (`task_form_components.ex`); Enter/confirm pushes `file_pick_manual` and the server replies with the SAME `picker_result` payloads (success → write textarea + close, `error` → inline error + keep open, unavailable/cancelled → close). Re-entrancy guard `this._picking` prevents stacked dialogs (re-armed by the result handler and `reconnected()`).
- **Guide — Genesis Guide overlay client (`Guide` hook + `.guide-highlight`)** (inline in `js/app.js`): client side of the self-reflective Genesis Guide overlay. The server-side `EvoDashWeb.LiveHooks.Guide` on-mount hook pushes `"guide_highlight"` with `%{selector}`; the client receives it via `this.handleEvent("guide_highlight", ...)`. Behavior: bounded retry for late-rendering elements (~10 × 250ms, then silent give-up); scrolls the target into view — prefers centering within the `#main-scroll` container (`scroller.scrollTo({behavior: "smooth"})`) when it contains the target, otherwise `target.scrollIntoView({behavior: "smooth", block: "center"})`; adds `class="guide-highlight"` and removes it after ~3000ms. **Dismissal contract**: on guide dismissal the server pushes `"guide_cleared"`, and the hook clears the stored `lastGuideHighlight` so a later remount/navigation doesn't re-apply a stale highlight. **Navigation retention**: the JS generates a stable per-tab `guide_client_id` (sessionStorage-backed, `crypto.randomUUID()` with a `Math.random` fallback) sent in the LiveSocket connect params; the server-side Guide hook keys its guide store by this id — stable across `push_navigate` since the WebSocket connection persists — and restores the `@guide` assign on each page, while the module-level `lastGuideHighlight` re-applies the highlight on remount (the DOM on the new page may need the retry loop). No `window.__TAURI__` gating — works in plain browsers. The matching `.guide-highlight` utility lives in `css/app.css` (Utility classes section): a 2px `var(--color-primary)` outline + 2px offset + `border-radius: 0.25rem`. Panel styling lives entirely in the layout markup as Tailwind classes — no panel CSS in `app.css`.

## Known Issues — Custom CSS Variables (`css/app.css`)

- **(i) No old DaisyUI `--b1/--b2/--b3/--bc/--p` namespace.** Because DaisyUI is loaded with `themes: false`, only the new `--color-base-100/-200/-300`, `--color-base-content`, `--color-primary` (etc.) variables exist — they are defined by the two `@plugin "../vendor/daisyui-theme"` blocks at the top of `app.css`. Custom rules MUST use the `--color-base-*` namespace. For alpha, use `color-mix(in oklab, var(--color-base-100) 98%, transparent)` (or `in oklch` for accent colors) — never `oklch(var(--x) / a)` nesting: `oklch()` cannot take a variable that is already an `oklch()` color, so the declaration is silently dropped. Grep `--b1|--b2|--b3|--bc|var(--p)` after any CSS work to confirm no regressions.
- **(ii) `.dashboard-topbar` must NOT have `backdrop-filter`.** `backdrop-filter` creates a containing block, which traps the fixed-position command-palette backdrop/overlay (`.project-palette-backdrop`, `.project-palette-overlay` — both descendants of the topbar) so they only cover the ~50px topbar strip instead of the viewport. The topbar's translucency comes from `background: color-mix(in oklab, var(--color-base-100) 80%, transparent)` alone. Other elements keep their `backdrop-filter` (`.glass-card`, `.input-card`, the palette backdrop/overlay themselves).
- **(iii) Input ring + layered glow are UNIFIED on the base `.input-card` rule** (`app.css`, Adaptive Input Layout section): the accent-tinted border, the layered glow `box-shadow` (base card elevation shadow, plus a FAINT 2px accent ring at low alpha — `0 0 0 2px color-mix(in oklch, var(--project-accent) 15%, transparent)` — and a two-layer background glow: a mid glow with negative spread (`0 0 90px -18px color-mix(in oklch, var(--project-accent) 25%, transparent)`) and a wide, very-low-alpha bloom with positive spread (`0 0 160px 20px color-mix(in oklch, var(--project-accent) 12%, transparent)`) so the accent reads as depth BEHIND the card rather than a ring hugging it), and the 2px accent top-edge gradient (`.input-card::before`) live on the BASE rules and apply to BOTH layouts (compact and expanded render identically). Do NOT add layout-specific shadows to `.input-layout[data-layout=...] .input-card` rules — only sizing/centering (compact) and flex (expanded) belong there.

## Theming & Color System (Tailwind CSS 4 + DaisyUI `themes:false`)

**Single CSS entry point** `css/app.css` (2222 lines) — Tailwind CSS 4 CSS-first config: `@import "tailwindcss" source(none)` + three `@source` dirs (`../css`, `../js`, `../../lib/evo_dash_web`), `@plugin "../vendor/heroicons"`, `@plugin "../vendor/daisyui" { themes: false }`, and **two `@plugin "../vendor/daisyui-theme"` blocks** defining the only two themes: `"dark"` (L23-68, `default: false`, `prefersdark: true`, `color-scheme: "dark"`) and `"light"` (L70-116, `default: true`). Ten active `[data-accent-color=...]` override rules follow at L129-201 (explanatory comment header L118-128; see "Accent-color overrides" below). NO `@theme` block, NO `tailwind.config.js` (Tailwind v4 CLI run from `config/config.exs:42-51`: `tailwind evo_dash --input=assets/css/app.css --output=priv/static/assets/css/app.css`, version 4.1.7). Mechanism: daisyUI-theme plugin (`vendor/daisyui-theme.js:59-97`) emits base rules keyed on `[data-theme="<name>"]` (selector built at L69; `:where(:root),` prepended when `default: true` at L70-72; `prefersdark: true` additionally emits the dark tokens on `:root` inside `@media (prefers-color-scheme: dark)` at L88-94 — the no-JS OS-dark default). Theme tokens are emitted CSS variables in the NEW daisyUI v5 namespace, NOT `--p/--pf/--pc` legacy: `--color-base-100/200/300`, `--color-base-content`, `--color-primary(-content)`, `--color-secondary(-content)`, `--color-accent(-content)`, `--color-neutral(-content)`, `--color-info/success/warning/error(-content)` + `--radius-selector/field/box`, `--size-selector/field`, `--border`, `--depth`, `--noise`. Do NOT introduce `--b1/--p/--pc` legacy vars (Known Issue (i) below).
