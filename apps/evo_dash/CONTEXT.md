# EvoDash — Phoenix LiveView Dashboard

## Intent

EvoDash is the web dashboard for the EvoGit umbrella project. It provides a project-based real-time browser interface for launching and monitoring EvoGit tasks (genesis and evolve), inspecting the agent tree hierarchy, viewing task logs, managing runtime scheduler settings, editing user configuration, and managing per-project settings including foreign repositories — powered by Phoenix LiveView.

Users open a Project (a Git repository path), and the dashboard auto-detects the appropriate task mode. Multiple projects can be open simultaneously with tab-based navigation.

This is a Phoenix 1.8 umbrella child app (`:evo_dash`) that depends on the sibling `:evo_git` application.

## API Surface

### Core Modules

- `EvoDash.Application` — OTP supervisor (Telemetry → PubSub → TaskSupervisor → DirectoryPicker → Endpoint)
- `EvoDash.DirectoryPicker` — GenServer serializing native directory-dialog usage (the dashboard's Browse buttons). Uses a **"native first, wx fallback"** model on all platforms: macOS → `osascript` (`choose folder`), Linux → `zenity --file-selection --directory`, Windows → PowerShell `[System.Windows.Forms.FolderBrowserDialog]`. Falls back to Erlang's `:wx` (`wxDirDialog`) if the native tool is unavailable or fails at runtime. `pick(reply_to, picker_id)` (directory mode — the Browse buttons) / `pick(reply_to, picker_id, kind)` with `kind = :directory | :file` (the objective editor's attach-file "+" button; `pick/2` delegates to `pick/3` `:directory`) spawn a Task that tries native first, then wx; the Task delivers `{:directory_picker_result, picker_id, {:ok, path} | :cancelled | :unavailable}` to the caller. Per-kind native commands: macOS `osascript` `choose folder` vs `choose file`, Linux `zenity --file-selection` with/without `--directory`, Windows `FolderBrowserDialog` vs `OpenFileDialog`. The wx fallback creates `wxDirDialog` vs `wxFileDialog` (`new_dir_dialog`/`new_file_dialog` in the `EvoDash.DirectoryPicker.Wx` seam; wxFileDialog options are `message`/`defaultDir` — NOT `title`/`defaultPath`); the seam's `show_modal`/`get_path`/`destroy` are type-dispatched on the ref's `#wx_ref{}` type field (hardcoding `:wxDirDialog` on a `wxFileDialog` ref raises and degrades the fallback to `:unavailable` — the fake in `test/support/fake_directory_picker_wx.ex` mirrors the same dispatch). Never raises: returns `{:error, :unavailable}` when disabled (`config :evo_dash, :directory_picker, enabled: false`), neither native nor wx is available, the GenServer isn't running, or busy (one pick at a time). **wx is initialized fresh in each fallback pick Task** (not cached in GenServer state) — avoids unnecessary wx startup on macOS. Injectable for tests via `config :evo_dash, :directory_picker_wx, Module` (see `EvoDash.DirectoryPicker.Wx` + `test/support/fake_directory_picker_wx.ex`).
- `EvoGit.Store` — SQLite (xqlite) backed persistent store (single GenServer holding one connection, column-based tables) for task history and recent projects; started under supervision before TaskRegistry. Uses **explicit durability PRAGMAs** (`journal_mode=WAL`, `synchronous=NORMAL`) and **graceful connection close** in `terminate/2`. Delegates ALL serialization to `EvoGit.Store.Codec` (pure functions). Data is stored in **proper typed columns** (TEXT, INTEGER) — not `term_to_binary` blobs — and JSON encoding (via Jason) for ALL complex nested fields (opts, logs, usage, archive_metadata, result); the `result` field stores runtime return tuples (`{:ok, %{...}}`, `{:error, _}`, `{:exit, _}`) as tagged JSON with a `"__result_tag__"` discriminator, reconstructing tuples + atom keys + the embedded `%EvoGit.Agent.Usage{}` struct on decode. The codec is STRICT canonical — only `__result_tag__`-tagged JSON decodes; anything else raises, and undecodable rows are skipped+logged by the Store's safe-select boundary. Atom fields (`type`, `status`, `review_status`) use `encode_atom/1` which accepts nil, atoms, and strings for full round-trip safety, and `decode_atom/1` using a whitelist of known atoms (`@known_atoms`, `MapSet` membership + `String.to_atom/1`), returning nil for unknown values (never crashes). Defines `EvoGit.TaskInfo` and `EvoGit.RecentProject` structs. Provides crash-safe read helpers (`safe_select_all_tasks/1`, `safe_select_all_projects/1`) that SKIP corrupt (un-deserializable) rows with a `Logger.warning` (never raises; rows stay untouched in the live table — there is no quarantine/integrity machinery (DETS-era legacy)). Schema creation is handled by `Schema.create_tables/1`, which runs on Store init — there is NO auto-migration. Existing DBs are upgraded manually via the one-time `mix migrate.store` task (`Mix.Tasks.Migrate.Store` in `apps/evo_git/lib/mix/tasks/migrate.store.ex`), which is standalone (never starts the `:evo_git` application).
- `EvoGit.TaskRegistry` — GenServer tracking tasks, persisted to SQLite; spawns `EvoGit.Runtime.*` processes. Uses `EvoGit.TaskRegistry.ProcessRegistry` (Elixir `Registry`, `:unique` keys) to track live task processes by task_id at runtime — spawned task processes self-register via `register_task_process/1`. Implements a **Lease & Heartbeat** pattern (see Data-safety architecture) for multi-instance robustness: tasks carry a `lease_expires_at` timestamp; the owning instance renews leases via a periodic `:heartbeat` timer; lease **checking/sweeping** is a **two-check, one-shot** design — it runs once at startup (via `reconcile_task_status/2`) and once more after the lease duration (via a one-shot `:lease_sweep` timer scheduled in `init`), NOT continuously on every heartbeat; startup reconciliation uses `Registry.lookup/2` to detect surviving task processes after a TaskRegistry restart (the Registry is a sibling under `:one_for_one`, so it survives a TaskRegistry restart), and marks running tasks `:failed` only when the lease has genuinely expired (not just because the process is dead/foreign). PIDs are NOT persisted to the database.
- `EvoDashWeb.Endpoint` — Phoenix endpoint (LiveView socket, static files, Plug pipeline)
- `EvoDashWeb.Router` — Routes to LiveViews and Phoenix LiveDashboard
- `EvoDashWeb.Helpers` — Shared UI utilities (status badges, datetime formatting, icons, modals)
- `EvoDashWeb.TaskExportController` — JSON download endpoint for a task's `archive_metadata` (`GET /tasks/:task_id/export`); normalizes structs/DateTimes to plain JSON-safe maps before encoding with Jason
- `EvoDash.NodeContext` — Thin client for SSH Remote Development. Wraps three `:evo_git` layers for the dashboard: (1) **target persistence** — `list_targets/0`, `get_target/1`, `save_target/1`, `delete_target/1` delegate to `EvoGit.RemoteConnections` (pure TOML functions); (2) **connection lifecycle** — `connect/1`, `disconnect/1`, `bootstrap/1`, `connection_status/0,1`, `connected?/1` delegate to `EvoGit.RemoteConnection` (GenServer) with **graceful degradation** when that module isn't compiled/started (returns safe fallbacks: `{:error, :remote_connection_unavailable}`, `%{}`, `:disconnected`, `false`); (3) **cross-node RPC helpers** — `call_remote/4` wraps `:erpc.call/5` (10s timeout, returns `{:ok, _} | {:error, _}`; local node calls directly without erpc), plus `list_agents/1`, `get_agent_history/2`, `get_agent_state/2`, `get_remote_config/1`, `get_remote_config_status/1`, `get_resolved_config/1` (full resolved config — `EvoGit.Config.resolve/0` shape, `{:ok, map} | {:error, {kind, reason}}`), `paused?/1`, `reload_remote_config/1`, `save_user_config/2`, `save_credentials/2`, `send_user_message/3`, **task-history RPC** (`list_tasks/1`, `list_tasks_paginated/2`, `list_tasks_summary/2`, `list_tasks_changed_since/2` — lightweight changed-since summaries with raw `updated_at` ISO strings, no longer called by any dashboard page since change detection is push-based via the `"tasks"` PubSub events; `get_unique_paths/1`, `cancel_task/2`, `delete_task/2`, `clear_finished_tasks/1`) plus **system-sample seed RPC** (`get_recent_system_samples/1` → `{:ok, [samples]} | {:error, _}`, passthrough delegate to `EvoGit.RemoteNode.get_recent_system_samples/1` — seeds the SystemLive chart on mount/node-switch), **task-review RPC** (review-page ops, node first: `get_task/2` — bare `%TaskInfo{} | nil`, nil on RPC failure; `set_review_status/3` + `set_review_metadata/4` — `:ok | {:error, term}`; plus 17 `EvoGit.Review` passthrough delegates — `list_commits/3`, `load_review_data/3`, `load_review_metadata/3`, `load_file_diff/5` + `/6`, `load_review_metadata_from_shas/4`, `list_commits_from_shas/4`, `load_commit_files/3`, `load_commit_file_diff/4`, `merge_branch/3` + `/4`, `check_merge/4` (async non-mutating dry-run merge-conflict check → `EvoGit.RemoteNode.check_merge/4`; `{:ok, :clean} | {:ok, {:conflict, [String.t()]}} | {:error, reason}`), `default_merge_target/2`, `list_branches/2`, `reject_branch/3`, `create_github_pr/5`, `branch_exists?/3`, **GitHub-issue delegates** (`github_upstream/2` — resolves the repo's GitHub upstream `{:ok, %{owner, repo, url, gh_available}} | {:error, reason}`; `list_github_issues/3` — issue list, default opts `[]` → backend `state: "open"`/`limit: 100`, explicit `state:`/`limit:` supported; `github_issue_markdown/3` — deterministic Markdown for a single issue — all via `EvoGit.RemoteNode.*`) — RemoteNode returns the VERBATIM underlying value on both local and remote paths, only transport failures return `{:error, {kind, reason}}`), **recent-projects RPC** (`list_recent_projects/1`, `add_recent_project/3`), **custom-agents RPC** (`list_custom_agents/1` → `{:ok, %{agents: [def_map], model_selection_script: String.t() | nil, script_status: :ok | {:error, {:compile_error, msg}}}}` — the local node calls `EvoGit.CustomAgents` directly and wraps the result in the same shape; on RPC transport failure it degrades to `{:ok, %{agents: [], model_selection_script: nil, script_status: :ok}}`; `save_custom_agent/2`, `delete_custom_agent/2`, `save_model_selection_script/2`, `reload_custom_agents/1` — delegates to `EvoGit.RemoteNode.*`, which edit the SELECTED node's `agents.toml`), and **remote system control** (`restart_remote/1`, `stop_remote/1` — call `System.restart/0`/`System.stop/0` on the remote node via `:erpc`; the RPC failure is expected since the node tears down mid-call, so these always return `:ok`). All delegate to `EvoGit.RemoteNode.*` (local node calls the function directly, remote routes through `:erpc`). All degradation is centralized in a private `with_remote_connection/4` guard (`Code.ensure_loaded?/1` + `catch :exit`). Only exception handling in the module: a justified `try/catch` in `call_remote/4` (cross-node RPC boundary) and justified `catch :exit` for the possibly-dead GenServer.
- `EvoDash.UpdateStatus` — auto-update state hub (GenServer in `EvoDash.Application` children, after `EvoDash.DirectoryPicker`). Single source of truth for the Tauri-updater UI state; see the "Auto-Update (Tauri Updater)" section below.
- `EvoDash.DesktopLifetime` — desktop Tauri-shell lifetime watcher (TCP pipe), GenServer in `EvoDash.Application` children (desktop only). The Rust shell binds a `TcpListener` on `127.0.0.1:0` at startup and passes the port to the backend via the `EVOGIT_LIFETIME_PORT` env var, never writing data on the pipe; this watcher connects and blocks on `:gen_tcp.recv(sock, 0, :infinity)` — when the shell dies the OS closes the socket, recv errors, and it logs a warning and stops the VM via `System.stop(0)` (`default_stop/0`, overridable through the `:parent_stop_fun` test seam read from the `:evo_dash` app env at `init/1`; `:connect_retries`/`:connect_retry_delay` `start_link` opts default 5/200ms, `@connect_timeout 1_000`). Gating in `EvoDash.Application.start/2`: appended to the supervision tree only when BOTH `EVOGIT_DESKTOP=1` and `EVOGIT_LIFETIME_PORT` are set (only the Tauri sidecar sets both; manually-launched releases and the remote daemon set neither); the module's `init/1` self-disables as belt-and-suspenders when the port var is missing, empty, or not a valid port number. Lives in the frontend app by design: desktop-only lifecycle code belongs here so `genesis_remote` (evo_git-only headless daemon) never ships it.

### Multi-Model LLM Support

The dashboard supports the core runtime's **multi-model** architecture (`[[llm.models]]` array-of-tables config format). Each model profile has its own id, model, concurrency slots, and generation params.

- **Settings page model profiles editor** (`SettingsLive` + `SettingsComponents.model_profiles_editor/1`): A list-based editor in the LLM category that lets users add/edit/delete model profiles. Each profile row shows id, model, concurrency, and a gen-params summary; expanding it reveals inputs for all fields (temperature, reasoning_effort, max_tokens, top_p, top_k, frequency_penalty, presence_penalty). The Quick Setup provider shortcuts and custom model form **add a new profile** to the list. Events: `add_model_profile`, `edit_model_profile`, `save_model_profile`, `delete_model_profile`, `cancel_edit_model_profile`, `model_profile_form_change`, `add_peak_hours_row`, `remove_peak_hours_row`. Duplicate profile ids are rejected. **Flat gen-param cards**: only `compression_threshold_tokens` is rendered as a flat card (a global setting); the model-level gen params (temperature, reasoning_effort, max_tokens, top_p, top_k, frequency_penalty, presence_penalty) are configured per model profile. The LLM category's `category_section/1` renders its own form internally: Quick Setup + Model Profiles editor + Connection Test render OUTSIDE the `save_category` form (no nested-form HTML), with only `compression_threshold_tokens` + Save button inside a dedicated form. **Peak/off-peak fields** (serialization contract shared with the backend): the edit form has a "Peak Concurrency (optional)" number input (non-negative integer; `min="0"` — `0` is valid and round-trips, meaning hard pause — zero LLM slots during peak windows; blank/absent omits the key), a "Peak Hours (optional)" window-list editor (24h HH:MM rows, add/remove buttons, absent/empty → key omitted), and a **"Timezone (optional)" text input** (IANA string e.g. `Asia/Shanghai`; blank/nil omits the key so TOML omits it; placeholder + hint say empty = server local time; no client-side format validation — the evo_git schema validates IANA names). **Draft-tracking**: the edit form carries `phx-change="model_profile_form_change"`, whose handler (`ModelProfileEvents.model_profile_form_change/2`) stores the WHOLE form's params as a `:profile_form_draft` socket assign (peak_hours normalized to the canonical atom-keyed list via `ModelProfileHelpers.normalize_peak_hours_draft/1`; total — never crashes on partial/odd params). Every input pre-fills draft-first via `draft_or_profile/3` and the draft's peak_hours row list is authoritative once a draft exists. This exists because `phx-click` (the add/remove row buttons) does NOT send the enclosing form's data — without the draft, those buttons re-rendered the form from `file_config` and wiped ALL unsaved typing. `add_peak_hours_row/2` / `remove_peak_hours_row/2` read the current window values from the draft (falling back to the profile's saved peak_hours when no draft), mirror the modified list into BOTH the draft and the in-memory profile, and re-render with every typed value preserved. The draft is cleared on save (success or error), cancel, delete, and when opening a different profile's edit form (`edit_model_profile` / `add_model_profile`); `save_model_profile` keeps reading the freshly-submitted phx-submit params.
- **Runtime update**: `update_runtime_from_file_config/2` pushes `:model_profiles` (via `Schema.model_profiles/1`) to `EvoGit.AgentScheduler.update_config/1`.
- **Per-task agent + model selection** (`ProjectsLive` + `TaskFormComponents.task_form/1`): The agent dropdown, model dropdown, and task mode selector are merged into a **single shared card** with a responsive `grid grid-cols-1 lg:grid-cols-2 gap-4 min-w-0` layout (side-by-side on desktop, stacked on mobile). **Agent select** (rendered only when `@custom_agents != []`): "Auto (recommended)" (empty value) + every custom agent from `EvoGit.CustomAgents.list/0` (loaded per node). Selecting a custom agent threads `:agent => id` into the runtime opts in `task_submit` (Auto/nil/"" threads nothing — the runtime spawns its default root agent); the selection persists across form state saves (`selected_agent_id` key in `ProjectsLive.StatePersistence`). Event: `select_agent`. **Custom Agent mode** — the task-form's 4th mode option (next to Create New / Initialize Existing / Evolution): maps to `{:evolve, "custom"}` at task_submit (task type stays `:evolve`) with the selected custom agent threaded as the REQUIRED `:agent` opt; in this mode the "Auto (recommended)" option is hidden in the agent select, `task_change` auto-selects the first custom agent when none is chosen, and submitting without a selected agent flashes an error without starting a task. The mode gets a violet accent (`ThemeColor` + Launch-button hover ring), a hint under the controls row ("Runs the selected custom agent as the root agent of an evolution task." — warning variant pointing to Settings → Agents when no custom agents exist), and evolve-family gating (textarea placeholder, advanced options). **Model select**: first option **"Auto (by rules)"** (empty value) — shown when a model-selection script is configured (`EvoGit.CustomAgents.ModelSelector.enabled?/0`; the default selection comes from `Project.load_model_profiles/0`, which returns `{profiles, ""}` in that case) and whenever the current selection is nil/empty. **Threading in `task_submit`** (opts are built inline there — there is no `build_common_runtime_opts/3` in the codebase): a specific profile → `:model_id => id` AND `:model_id_locked => true` (set UNCONDITIONALLY per the cross-app contract — an explicit user choice always defers the model-selection script; the lock is a no-op when no script is configured); "Auto (by rules)" / nil / "" → NEITHER key, so the script (or the default model) decides. Event: `select_model`. Tests: `test/evo_dash_web/live/projects_live_test.exs` (agent select render/threading, Auto-vs-specific `:model_id`/`:model_id_locked` threading incl. the no-script case) + `test/evo_dash_web/components/task_form_components_test.exs` (auto option first).
- **Welcome modal**: `show_welcome` checks `model_profiles == []`.
- **System page**: The example config reference and FAQ use the `[[llm.models]]` format.

### SSH Remote Development — Node-Aware Dashboard

The dashboard supports connecting to a **remote headless `genesis_remote` daemon** over Erlang distribution via an SSH tunnel. The local Phoenix frontend controls the remote runtime. The architecture has three layers:

- **`EvoDash.NodeContext`** (`lib/evo_dash/node_context.ex`) — domain-layer thin client (see Core Modules above). The single entry point for the web layer; wraps `EvoGit.RemoteConnections` (target persistence), `EvoGit.RemoteConnection` (lifecycle GenServer), and cross-node `:erpc` RPC.
- **`EvoDashWeb.LiveHooks.NodeAware`** (`lib/evo_dash_web/live_hooks/node_aware.ex`) — on-mount hook + helpers applied to ALL LiveViews via the `live_view/0` macro in `evo_dash_web.ex` (alongside `SetLocale`). Sets node-context assigns (`@current_node`, `@current_node_name`, `@current_node_id`, `@remote_targets`, `@connection_statuses`) with safe local defaults and subscribes to `EvoGit.PubSub` topic `"remote_connections"` for real-time status updates. `assign_node/2` reads the `?node=` query param in each LiveView's `handle_params/3`, resolving it to a saved+connected target or falling back to local; it then calls `load_running_and_pending_tasks/1` so the **sidebar "Active Tasks" section reloads from the correct node on every navigation and node switch**. The sidebar loader is UNIFIED here: `load_running_and_pending_tasks/1` delegates to `fetch_active_tasks/1` (node-aware: local → `TaskRegistry.list_tasks_summary(@active_statuses)`, remote → `EvoDash.NodeContext.list_tasks_summary(node, @active_statuses)` RPC, with the pending-remote empty-list guard) → `partition_active_tasks/1` (pure) → `assign_active_tasks/1` (assigns `:running_tasks`/`:pending_tasks`). `on_mount/4` fires the load only on the connected mount (dead-render skip) and `assign_node/2` dedup-guards reloads via `:tasks_node_loaded`. `show_review_button?/1` is column-based (`branch_name`) — summary maps are never read for `result`. `handle_node_selected/2` builds a `push_patch` to update the URL. `handle_connection_status/2` refreshes `@connection_statuses` on every broadcast. When the status change is for the currently selected node AND represents a meaningful local↔remote transition (`%{phase: :connected, node: remote_node}` with `@current_node` currently local, or `:disconnected`/`:error` with `@current_node` currently remote), it does NOT update `@current_node` inline — instead it `push_patch`es the current path (preserving `?node=`) so `handle_params/3` re-runs and reloads ALL page-specific node data (`@remote?`, remote agents, remote config, etc. — that data-loading logic lives in `handle_params/3`, which is not re-run otherwise). Non-transition statuses (`:connecting`, `:bootstrapping`, duplicate, non-selected node) only refresh statuses and do NOT reload.
- **`EvoDashWeb.LiveHooks.DesktopQuit`** (`lib/evo_dash_web/live_hooks/desktop_quit.ex`) — on-mount hook applied to ALL LiveViews via the `live_view/0` macro in `evo_dash_web.ex` (alongside `SetLocale`/`NodeAware`). Seeds `@desktop_quit_confirm` (false) and attaches a `:handle_event` interceptor for the three tray-quit events (`desktop_quit_requested` / `desktop_quit_cancelled` / `desktop_quit_confirmed`); the shared app layout (`EvoDashWeb.Layouts.app` — every page renders through it) shows the confirm dialog whenever the assign is true, so the dialog works on ANY page. `desktop_quit_confirmed` gracefully stops the VM via the `:evo_dash, :desktop_quit_stop_fun` config seam (default `default_stop/0` = delayed `System.stop/0`, mirroring the System page's local Stop button; tests inject a fake so the REAL `System.stop/0` never runs in the test VM). No remote-node branch — the tray event only comes from the desktop shell, whose webview serves the LOCAL dashboard VM. See "Desktop tray quit confirm dialog" below for the full protocol flow.
- **`EvoDashWeb.NodeSelectorComponent`** (`lib/evo_dash_web/live/components/node_selector_component.ex`) — a **LiveComponent** rendered in the navbar (next to the brand name) that shows the current node (status dot + name), a dropdown for switching nodes (Local / saved targets / "Manage Connections..."), and a full **connection manager modal** (add/edit/delete targets, bootstrap/connect/disconnect, status badges). Manages its own state; selects nodes by sending `{:node_selected, id}` to the parent LiveView. **Auto-connect on select**: when a user selects a remote target that isn't connected yet, `handle_event("select_node")` calls `EvoDash.NodeContext.connect(node_id)` to initiate the connection asynchronously (the GenServer handles it in the background). The page shows a "connecting" status, and once the connection completes, the status broadcast triggers `NodeAware.handle_connection_status/2`, which detects the local→remote transition and `push_patch`es the current path to force `handle_params/3` to re-run, reloading `@current_node` from local to the remote BEAM node along with all page-specific data.

**URL param threading**: When a remote node is selected, ALL navigation links carry `?node=<target_id>` so the node context persists across page navigation. The `with_node_param/2` helper in `layouts.ex` appends the query string when `@current_node_id` is non-nil; applied to all desktop + mobile nav links + the brand logo link.

**Graceful degradation**: `NodeContext` connection-lifecycle calls return safe fallbacks when the `EvoGit.RemoteConnection` GenServer is not compiled/started. The node selector renders "Local" by default and saved targets appear (they're read from TOML, which always works) but show "Disconnected" status until connections can be made.

**LiveView Node-Aware Integration (node name resolution + node-aware data loading)**: All LiveViews route their data access through the node context so that viewing a remote node fetches data from the remote server via RPC.

- **Node name resolution**: `assign_node/2`'s `resolve_node_context/1` resolves the actual remote BEAM node name from `EvoDash.NodeContext.connection_status(target.id)`. When the connection status is `%{phase: :connected, node: "genesis_remote@host"}`, `@current_node` is set to `String.to_atom(node_name)` so `EvoDash.NodeContext.*(@current_node)` functions route `:erpc.call/5` to the correct node. Falls back to local for nil/`"local"` params, unknown ids, disconnected targets, or targets whose connection manager hasn't reported a node name yet.

- **AgentsLive node-aware data loading (async, push-driven)**: All data access goes through `EvoDash.NodeContext` (`list_agents/1`, `get_agent_history/2`, `get_remote_config_status/1`, `get_resolved_config/1` for the compression threshold). The page load, push-driven refresh events, and per-click history fetches all run in `EvoDash.TaskSupervisor` children OUTSIDE the LiveView process — the page never blocks on cross-node RPCs. `handle_params/3` spawns `EvoDashWeb.AgentsLive.LoadData.load/2` (`agents_live/load_data.ex`), sending `{:agents_data_loaded, node, generation, result}`; the handle_info stale-guard drops results unless `node == @current_node` and `generation >= @load_generation` (monotonic counter seeded 0 in mount). Local and remote paths are unified (local node calls `RemoteAPI` directly, no `:erpc`). Node changes trigger a full async reload (tracked via `:previous_node` assign).

- **Cross-node PubSub (push-based, no polling)**: ALL dashboard periodic polling was deleted — the dashboard is fully event-driven. `:evo_git` broadcasts enriched events carrying the publishing BEAM node atom on `EvoGit.PubSub` (see "Push-based event contract" below); every consumer applies `EvoDashWeb.LiveHooks.NodeAware.event_from_current_node?/2` so only events from the currently-viewed node trigger UI updates. ### Push-based event contract (node-identity PubSub)

The dashboard is fully PUSH-based — all periodic polling was deleted. `:evo_git` broadcasts enriched events on `EvoGit.PubSub`; every event carries the **BEAM node atom of the publishing node**. The viewed node's identity is the dashboard's own `node()` atom for local viewing, or the remote daemon's BEAM name (resolved by NodeAware) for remote viewing. **Node-filtering rule**: an event only triggers UI updates when its `node` matches the currently-viewed node — `EvoDashWeb.LiveHooks.NodeAware.event_from_current_node?(assigns, event_node)` compares against the resolved `socket.assigns.current_node`. Every consumer (NodeAware, AgentsLive, TasksLive, ReviewLive, SystemLive, SettingsLive, ProjectsLive) applies the filter; NodeAware drops foreign-node `"tasks"` events BEFORE the 300ms `:node_aware_reload_tasks` trailing-edge debounce, protecting ProjectsLive's local-only browser-notification diff and every page's reload from cross-node leakage.

| Topic | Events | Consumers |
|-------|--------|-----------|
| `"tasks"` | `{:task_updated, task_id, status, node}` — status `:pending\|:running\|:finalizing\|:cancelling\|:completed\|:failed\|:cancelled`, or `nil` for review-only mutations; `{:task_deleted, task_id, node}` | NodeAware (debounced sidebar + page reloads), TasksLive, ProjectsLive, ReviewLive (broadcast-guarded review-data reload), AgentsLive, SettingsLive, SystemLive |
| `"agents"` | `{:agent_registered, id, summary, node}`, `{:agent_updated, id, changed_fields, node}` (changed_fields NEVER contains `:context`; it DOES contain `:message_count` when the agent's context changed), `{:agent_removed, id, node}`, `{:agents_updated, node}` | AgentsLive |
| `"scheduler_config"` | `{:scheduler_config_updated, node}` | SettingsLive, SystemLive (node-filtered → async reloads) |
| `"system"` | `{:system_sample, node, seq, sample}` every 3s from a node-side sampler; sample keys `llm_used, llm_waiting, tool_used, tool_waiting, llm_capacity, tool_capacity, agents_total, agents_running, agents_blocked, agents_waiting, agents_pending, scheduler_alive` | SystemLive chart (ring buffer, cap 60) |
| `"recent_projects"` | `{:recent_projects_updated}` | ProjectsLive |

**SystemLive chart seed**: on mount/node-switch ONE async `EvoDash.NodeContext.get_recent_system_samples(current_node)` runs via `EvoDash.TaskSupervisor` + self-message + stale-guard (monotonic `chart_seed_seq` + node); on error ONE retry after 3s (one-shot, gated by `chart_seed_retried` — NOT periodic); on node switch the buffer is cleared + re-seeded. The `:system_samples_runner` app-env test seam is resolved AT SPAWN TIME.

### Task Cancellation Model

The dashboard exposes TWO task-cancellation actions (backed by `EvoGit.RemoteNode.cancel_task/2` graceful + `EvoGit.RemoteNode.force_kill_task/2` brutal):

- **Graceful Cancel** — `EvoDash.NodeContext.cancel_task/2` (thin delegate to the graceful `RemoteNode.cancel_task/2`). Task enters `:cancelling`, agents are messaged via the pending-user-message channel to save work + call complete_task (3-turn grace), finally persisted `:cancelled` WITH result/archive preserved. Works from `:pending` (immediate `:cancelled`) and `:running`; `:finalizing`/terminal → `{:error, :not_running}`; missing → `{:error, :not_found}`. UI surface: the task-card "Cancel" button (visible for `:pending`/`:running` only), which opens a **confirmation modal** (`"Cancel Task?"` — agents informed to immediately save changes and exit; intermediate results will be saved; dismiss button "Keep Running").
- **Force kill** — `EvoDash.NodeContext.force_kill_task/2` (thin delegate to `RemoteNode.force_kill_task/2`). Kills all agents + wrapper immediately, status → `:failed`, result nil'd (ALL progress lost, cannot be undone). Works from `:running` and `:cancelling` (escalation); requires an owned live wrapper process in `task_refs` (a bare store-only `:running` row → `{:error, :not_running}`). UI surface: the three-dot dropdown "Force kill" item (visible for `:running`/`:cancelling`, under a "Danger zone" menu-title divider above Delete), opening a **confirmation modal** (`"Force Kill Task?"` — progress loss warning; `btn-error` confirm).

**`:cancelled` reviewability** — gracefully-cancelled (`:cancelled`) tasks ARE reviewable on the Tasks page exactly like completed tasks: the task card shows the Review button (via `TaskCardComponents.show_review_button?/1`, which matches `:cancelled` with a preserved branch/no_changes result) and `/review/:task_id` renders the diff with merge/reject/ignore/resume; a `:cancelled` task without a branch is treated as no-changes like a completed one. Sidebar active-task semantics: `:cancelled` is not an active status (`@active_statuses` excludes it); `:cancelling` is.

**`:cancelling` status UI** — violet "in progress, stopping" presentation end-to-end (NOT terminal): `task_status_badge(:cancelling)` (`bg-violet-500/10 text-violet-500`), `status_accent_color(:cancelling)` (`bg-violet-500`), `task_card_tint(%{status: :cancelling})`, a pulsing violet dot + `gettext("Cancelling…")` label on the card, sidebar inclusion via `NodeAware.@active_statuses` (`[:running, :pending, :finalizing, :cancelling, :completed]`) + `partition_active_tasks/1` running filter (`[:running, :pending, :finalizing, :cancelling]`) and `layouts.ex` `is_running`/`task_status_dot_color(:cancelling)`, and a "Cancelling" option in the TasksLive status filter (pure SQL string passthrough — no evo_dash atom whitelist; `:cancelling` round-trips the Store codec).

**TasksLive modal-state pattern** (SystemLive-style warning modal, server-side assigns, NO custom JS): `:confirm_cancel_task_id` / `:confirm_force_kill_task_id` assigns (mutually exclusive — opening one clears the other), seeded nil in `mount/3` and cleared on node switch in `handle_params/3`. Events: graceful `open_cancel_modal` / `close_cancel_modal` / `confirm_cancel_task`; force-kill `open_force_kill_modal` / `close_force_kill_modal` / `confirm_force_kill_task`; nil-guarded confirms are no-ops. On success the task card collapses + the page reloads; on `{:error, reason}` the appropriate error flash fires (`"Failed to cancel task"` / `"Failed to force kill task"`).

**Notes**: `ProjectsLive.handle_event("cancel_task", ...)` calls `EvoGit.TaskRegistry.cancel_task/1` directly (local-only, graceful) but no UI fires it — the TasksLive card button opens the cancel modal instead, and the sidebar has no cancel button. Force kill is intentionally NOT exposed in the sidebar. Tests: `test/evo_dash_web/live/tasks_live_test.exs` covers the modal flows + `:cancelling` display/filter; `test/evo_dash/node_context_test.exs` covers the delegation shape; `node_aware_test.exs` covers the running-partition inclusion.

## Constraints

- Depends on `:evo_git` at compile and runtime
- Runs on port 4100 in development, uses Bandit adapter
- Tailwind CSS 4 + DaisyUI (no Node.js toolchain)
- Task state and recent projects persisted via SQLite (xqlite — Rust-based panic-free NIF bindings with precompiled binaries for Windows, macOS, and Linux incl. ARM); no external database server
- **Data-safety architecture**: The TaskRegistry GenServer `handle_*` callbacks have NO try/rescue — if a Store call fails, the GenServer crashes and the supervisor restarts it. The Store GenServer's `handle_*` callbacks also have NO try/rescue — SQLite failures crash it and the supervisor restarts with a fresh connection (data is safe in WAL mode). Serialization is delegated to `EvoGit.Store.Codec` (pure functions: TOTAL encode via non-crashing `Jason.encode/1` + `case`, raise-on-bad-decode). `select_all_tasks`/`select_all_projects` use `EvoGit.Store.safe_select_all_tasks/1` / `safe_select_all_projects/1` which SKIP rows whose data fails to decode (per-row rescue + `Logger.warning`, never raises; rows stay in the live table — there is no quarantine/integrity machinery (DETS-era legacy); the only startup DB check is pure-SQL lease reconciliation). Batch deletions go through `EvoGit.Store.delete_tasks/2`. `cleanup_expired_tasks` runs only on task-completion transitions, explicit `clear_finished_tasks`, and `init` — not on every mutation — and uses a single-pass scan. The completed task's `EvoGit.Store.put_task` in `update_status` runs BEFORE `cleanup_expired_tasks`, so a crash mid-cleanup never loses the completed task. On registry restart, `reconcile_task_status/2` uses a **lease & heartbeat** pattern for multi-instance robustness: a running task carries a `lease_expires_at` timestamp (granted on start, renewed every 60s via a `:heartbeat` timer, cleared on terminal status). A running task is checked against the `EvoGit.TaskRegistry.ProcessRegistry` (Elixir `Registry`) first — `Registry.lookup/2` finds task processes that survived a TaskRegistry restart (the Registry is a sibling under `:one_for_one` supervision, so it survives). If found, the task is re-monitored and re-owned. If no live process is found, the task is marked `:failed` ONLY if its lease has genuinely expired (`lease_valid?/1` returns false for nil or past timestamps) — this prevents a second BEAM VM instance from incorrectly marking the first instance's running tasks as `:failed`. Tasks with a valid lease are left `:running` (the one-shot `:lease_sweep` will catch them if the lease eventually expires — no periodic per-task recheck). The lease-expiry sweep is a **two-check, one-shot** design, NOT continuous-on-every-heartbeat: a one-shot `:lease_sweep` timer (scheduled in `init`, firing after the lease duration + a buffer) sweeps unowned running tasks with expired leases; the `:heartbeat` handler does ONLY lease renewal for owned tasks. Same-VM result recovery (`:recheck_task`) is a separate concern (a periodic same-VM mechanism for tasks whose wrapper died but agents are still running in ETS). `reconcile_task_status/2` also checks `:evogit_sched_meta` ETS (via `:ets.info/1`, non-crashing) for active agents as a same-VM recovery edge case.
- **Supervision robustness**: `EvoDash.Supervisor` uses `:one_for_one` with `max_restarts: 10, max_seconds: 60` so the Phoenix Endpoint survives a transient TaskRegistry restart. `:one_for_one` (not `:rest_for_one`) is correct because TaskStore must stay alive across TaskRegistry restarts (TaskRegistry holds no state — it reads the store fresh on every call, so a restart loses nothing durable).
- Single-node (no distributed clustering)
- Naming conventions: domain modules in `./lib/evo_dash/`, web modules in `./lib/evo_dash_web/`
- Build: `mix assets.build` (esbuild + tailwind), `mix assets.deploy` (minified + digested)
- No CI/CD pipeline, no Docker, no `rel/` directory — release packaging not yet configured
- **`try/rescue` anti-pattern policy**: `try/rescue` is normally an anti-pattern in Elixir. The following rules apply across the codebase:
  - **LiveView config/core-value loading** (e.g. `EvoGit.Config.resolve`, `EvoGit.AgentScheduler.get_config`, `EvoGit.Config.config_status`): do NOT wrap in `try/rescue` swallowing to a default. Let the LiveView crash truthfully — a visible crash is better than displaying a wrong/default value that hides a real bug in the core system.
  - **JSON encoding**: use the non-crashing `Jason.encode/1` (returns `{:ok, _} | {:error, _}`) with `case`, NOT `Jason.encode!` wrapped in `try/rescue`. (The built-in `JSON` module exists in Elixir 1.20 but does not export `encode/1` — `Jason.encode/1` is the correct non-crashing variant.)
  - **Atom conversion from untrusted input** (DB-sourced strings, URL params): use a whitelist `Map.get/3` lookup instead of `try/rescue` around `String.to_existing_atom/1`. For trusted input where the atom is expected to exist, let it crash.
  - **ETS table existence checks**: use `:ets.info/1` (returns `:undefined` for missing tables, non-crashing), NOT `try/rescue` around `:ets.match/2`.
  - **Acceptable `try/rescue` (rare, each MUST have a comment answering: (1) do we expect this error? (2) is try/rescue the cleanest approach?)**: `terminate/2` in GenServers (shutdown safety), deliberate data-recovery boundaries (the Store's skip-and-log decode boundary for corrupt DB rows), and boundaries with untrusted persisted data where no non-crashing variant exists (`String.to_existing_atom` for best-effort decode), and the Store's `ALTER TABLE DROP COLUMN` migration (older SQLite versions don't support it; the leftover `pid` column is harmless if it can't be dropped). Test-cleanup rescues in `on_exit`/teardown are acceptable (cleanup failures should not mask test results) but must have a comment.

## Desktop Mode (Tauri Shell)

The backend is a **standalone web server** with no desktop-shell dependency (no `:desktop`). Desktop mode is provided externally by a **Tauri shell** (in `./desktop/` at the repository root) that launches this backend as a sidecar process.

- **Directory picking is handled SERVER-SIDE by `EvoDash.DirectoryPicker`** (Erlang `:wx` → `wxDirDialog`), NOT via Tauri or the browser File System Access API. Flow: the JS `DirectoryPicker` hook pushes `directory_pick` → `ProjectsLive` (local node only; remote/headless nodes get an immediate `unavailable`) → the picker GenServer runs the modal dialog in a Task → result pushed back to the client as `picker_result:<picker_id>` with `%{path: path}` / `%{cancelled: true}` / `%{unavailable: true}`.
- `EvoDash.DirectoryPicker` is a GenServer in the supervision tree, lazy-starting wx on the first pick (never at boot).
- There are NO references to `:desktop`, `Desktop.Window`, `desktop_port`, `is_desktop`, `?client=desktop`, or `detect_desktop_client` in the codebase. `EVOGIT_DESKTOP` IS referenced — by `EvoDash.UpdateStatus.desktop?/0` (`lib/evo_dash/update_status.ex:154`) and by `EvoDash.DesktopLifetime`'s supervision gating in `EvoDash.Application.start/2`. `:wx` IS referenced (only by `EvoDash.DirectoryPicker` + its `EvoDash.DirectoryPicker.Wx` seam — the seam exists purely so tests can inject a deterministic fake wx backend) — deliberately NOT an umbrella app dependency: dev/test `mix` runs prune it from the code path (picker degrades to the manual-entry fallback), while the `genesis`/`genesis_desktop` releases load it via `wx: :load` in the root `mix.exs` (`genesis_remote` stays wx-free). Disabled via `config :evo_dash, :directory_picker, enabled: false`.

### Desktop tray quit confirm dialog

When the user clicks the Tauri shell's tray "Quit Genesis" item, Rust shows the window and emits the Tauri event `"quit-requested"`. The dashboard shows a warning confirm dialog on whichever page is being viewed and, on confirm, gracefully stops the backend the same way the System page's Stop button does (`System.stop/0` — NOT force kill):

- **JS hooks** (`assets/js/app.js`): `DesktopQuit` (mounted on a wrapper div around the app layout's `<main id="main-content">` — inside the LiveView root DOM, so it is re-established on every page navigation) listens via `window.__TAURI__.event.listen("quit-requested", ...)` (same `!!(window.__TAURI__ || window.__TAURI_OS_INTERNALS__)` detection as `TauriDetect`; complete no-op in normal browsers) and pushes `"desktop_quit_requested"`. There is no guaranteed-exit fallback — tray Quit with a healthy backend waits indefinitely for the user's confirmation. `DesktopQuitConfirm` (on the dialog's red Quit button) first awaits `window.__TAURI__.core.invoke("begin_quit")` (the shell sets its intentional-shutdown flag so its watchdog won't restart the backend; a failure must still proceed — wrapped in try/catch) and then pushes `"desktop_quit_confirmed"`; without Tauri it pushes the event directly (browser testing path).
- **Server**: `EvoDashWeb.LiveHooks.DesktopQuit` (registered via `on_mount` in `evo_dash_web.ex`) seeds the `@desktop_quit_confirm` assign on every LiveView and intercepts the three events via an attached `:handle_event` hook (runs BEFORE the LiveView's own `handle_event/3`; `{:halt, socket}` consumes them, all other events pass through). `desktop_quit_confirmed` runs the graceful stop through the injectable `:evo_dash, :desktop_quit_stop_fun` config seam (default `default_stop/0` = `spawn(fn -> Process.sleep(150); System.stop() end)` — the delay lets the server close the dialog before the VM tears down). No remote-node branch: the tray event only comes from the desktop shell, whose webview serves the LOCAL dashboard VM.
- **UI**: `EvoDashWeb.Layouts.app` declares the `desktop_quit_confirm` attr (each page passes `desktop_quit_confirm={@desktop_quit_confirm}`) and renders the warning modal (SystemLive-style fixed overlay: warning icon, "Quit Genesis?" title, interrupted-tasks/progress-loss warning body, Cancel button with `phx-click="desktop_quit_cancelled"` and red Quit button with `phx-hook="DesktopQuitConfirm"`). Works on EVERY page, including Welcome/WelcomeComplete (both render through `Layouts.app`). All strings gettext-wrapped.
- **Tests**: `test/evo_dash_web/live_hooks/desktop_quit_test.exs` — open/cancel/confirm flows on the System page, unrelated-event passthrough, and modal-on-Welcome; the stop seam is injected via `Application.put_env(:evo_dash, :desktop_quit_stop_fun, ...)` so the REAL `System.stop/0` is never invoked in the test VM.

### Known Issues / Notes for Agents

- **Remote Settings page config loading**: `SettingsLive.load_node_config/1`'s remote branch fetches the FULL resolved config via `EvoDash.NodeContext.get_resolved_config/1` — local → `EvoGit.Config.resolve/0`, remote → `:erpc` to `EvoGit.Config.resolve/0` on the remote daemon (atom-keyed nested map, defaults merged; `{:ok, map} | {:error, {kind, reason}}`) — and assigns it DIRECTLY as `file_config` (no transformation needed), so every section renders: scheduler, tools, evolution, truncation, nix, `[[llm.models]]`, `compression_threshold_tokens`. `persist_file_config/1`'s remote branch refetches via `get_resolved_config` after `reload_remote_config`, so the editor round-trips the FULL config through `save_user_config` (same materialize-defaults semantics as the local path) — a remote save does not wipe sections. On RPC fetch failure, `load_node_config` assigns `remote_config_error` (gettext message) → a visible "Remote Configuration Unavailable" error banner renders, and the "No LLM Model Configured" box is gated on `remote_config_error == nil` so it never fires on top of the real problem (a genuinely unconfigured REMOTE still shows it). mount/3 seeds `remote_config_error: nil`; `handle_params/3` runs `assign_node` BEFORE `load_node_config`, so the remote branch always executes with the correctly resolved node. `remote_config_to_file_config/1` + `maybe_put/2` remain as a LEGACY helper for the flat scheduler-map shape (still used by `save_category`/`save_search`/`SearchEvents.handle_reset_key` remote re-fetch paths) — do not delete. `AgentScheduler.get_config`'s map form includes `model_profiles`. **Tests**: `settings_live_test.exs` covers the fetch-FAILURE degradation path (fake ConnectionManager seam — `EvoGit.RemoteConnection.Registry`-registered fake with `%{phase: :connected, node: "genesis_remote@127.0.0.1"}`, erpc fails fast → error banner renders, "No LLM Model Configured" absent) + a local-node no-banner test; the remote HAPPY-PATH render (profiles shown from a successful resolved fetch) remains UNTESTED — no seam exists to inject successful RPC results (test/support/ has no NodeContext/RemoteNode fakes).
- **OTP's `wxe_server` is NOT a permanent singleton** — it stops when the last registered user exits. Every process that calls `:wx.new/0` or `:wx.set_env/1` registers with `wxe_server` as a "user" (`wxe_server.erl` `handle_call(register_me, ...)` monitors the caller), and `handle_info({'DOWN', ...})` STOPS the server when the LAST registered user exits. In the current design, wx is initialized fresh in each fallback pick Task (not cached in GenServer state). Each Task calls `:wx.new/0`, uses the dialog, then exits — the wxe_server stops with it and the next pick creates a brand-new server. ## Auto-Update (Tauri Updater)

Dashboard-side integration of the Tauri updater (design: root `CONTEXT.md` → "Auto-Update / Push-Update"; UX spec: `docs/auto-update.md` §11). **The Elixir/dashboard side is fully implemented**; the Rust `check_update`/`download_update`/`begin_update` commands and the CI `latest.json` manifest pipeline are separate workstreams (see `desktop/src-tauri/CONTEXT.md` / `.github/workflows/CONTEXT.md`). The Rust commands are invoked from JS and coded against defensively (missing keys tolerated → hub normalizes to `:error`).

**Architecture — three layers connected by an event-name protocol** (no module cross-references between the card and the global hook; the protocol is the contract):

1. **State hub** `EvoDash.UpdateStatus` (`lib/evo_dash/update_status.ex`) — GenServer holding the update UI state: `phase ∈ :idle|:checking|:up_to_date|:available|:ready|:error|:applying`, `current_version`, `latest_version`, `notes`, `date`, `error`, `last_checked_at`, `notify_only`, `download_requested_version` (all atom keys). API: `get/0`, `phase/0`, `check_started/0`, `handle_check_result/1` (string-keyed payloads: `"available"` → populates versions/notes/date + recomputes `notify_only`; `"up_to_date"`; `"not_configured"` → `:error` with `error: "not_configured"` sentinel; `"not_available"` → `:error` with `error: "not_available"` sentinel, KEEPING the feed's `latest_version`/`notes`/`date` when the payload carries them so unsupported platforms still show the latest release; `"error"` → `:error` with the backend's descriptive error string (fallback `"check_failed"`) plus `latest_version: payload["version"] || state.latest_version` when the payload carries a version; unknown/malformed/non-map → `:error "check_failed"`, never raises), `handle_download_result/1` (`"ready"` → `:ready`; `"error"` → back to `:available` from `:available/:checking/:ready`, `:error` from `:idle`), `request_download?/0` (atomic once-per-version auto-download guard — true only when `:available` && !notify_only && latest_version present; a NEW version re-arms it, a same-version re-check does NOT), `applying/0`, `apply_failed/1` (reverts `:applying` → `:error`, never wedges), `check_failed/1`, `reset/0`, `desktop?/0` (`config :evo_dash, :desktop_release, false` or `EVOGIT_DESKTOP=1`), `visible?/1` (desktop && node ∈ [nil, node()]), `notify_only?/0` (Linux non-AppImage detection with `:update_notify_only_override` seam first). **Every transition broadcasts `{:update_status, state}` on `EvoGit.PubSub` topic `"updates"`** (inside `handle_cast` — callers never block). Never-wedge invariants: every check-result path + `check_failed/1` terminate `:checking`; `:error` is retryable; `:applying` reversible.
2. **Global on-mount hook** `EvoDashWeb.LiveHooks.UpdateStatus` (`lib/evo_dash_web/live_hooks/update_status.ex`) — registered LAST in `evo_dash_web.ex`'s `live_view/0` (after DesktopQuit). Seeds `@update_status` on every page via the pure `initial_assign(desktop?, remote_view?)/2` (desktop && `params["node"] == nil` → hub `get()`, else `nil` — hides the dot on remote-node views, keeps templates safe outside Tauri). When `desktop?()` && `connected?(socket)`: subscribes to `"updates"`, attaches a `:handle_info` interceptor (`{:update_status, state}` → assign + halt) and a `:handle_event` interceptor consuming the four client→server events on ANY page (so no unhandled-pushEvent warnings): `update_check_result` → hub + auto-push `"update_download_requested"` when `request_download?()`; `update_download_result` → hub; `update_apply_confirmed` → `stop_backend/0`; `update_apply_failed` → `UpdateStatus.apply_failed/1`. `stop_backend/0` routes through the `:evo_dash, :desktop_quit_stop_fun` seam (shared with DesktopQuit; default = DesktopQuit's 150ms-delayed `System.stop/0` — NEVER `bin/genesis_desktop stop`, broken under `RELEASE_DISTRIBUTION=none`).
3. **JS hook** `UpdateStatus` in `assets/js/app.js` (~L753) — module-level `updateListenersBound`/`updateTimersStarted`/`updateCurrentHook` state; complete no-op outside Tauri (`window.__TAURI__ || window.__TAURI_OS_INTERNALS__` guard, TauriDetect pattern). Binds `phx:update_check_requested` / `phx:update_download_requested` / `phx:update_apply_requested` window listeners ONCE (server→client `push_event`s arrive as `phx:<event>` CustomEvents) and starts the 30s-delayed startup check + 6h periodic check ONCE. `invokeUpdateCheck/Download/Apply` wrap `window.__TAURI__.core.invoke("check_update"/"download_update"/"begin_update")` in try/catch with null-guarded `pushEvent` (the element may unmount mid-timer); `begin_update` returning `{ok: true}` → `update_apply_confirmed`, else/exception → `update_apply_failed`.

**SystemLive Software Update card** (`system_live.ex` ~L120 between System Control and System Self-Check; support module `lib/evo_dash_web/live/system_live/update_card.ex` mirroring the `MergeCheck` pattern) — gated on `@update_card_visible` = `UpdateStatus.visible?(@current_node)` (computed in `handle_params/3` after `assign_node`; hidden on the `mix` dev server and on remote `genesis_remote` nodes). States per `docs/auto-update.md` §11.2: `:checking` (spinner), `:up_to_date` ("Genesis <current> is up to date" + last-checked), `:available` ("Version <latest> is available" + notes + **Download** button + amber dot; **notify-only mode** — Linux non-AppImage deb/rpm/portable — shows "update via your package manager" info instead, NO self-download), `:ready` ("Update ready — version <latest>" + **Restart & Update** + blue `animate-ping` dot), `:error` ("Check failed" + **Retry**; `error == "not_configured"` renders a friendly pre-key message; `error == "not_available"` renders "Latest version <v> — no auto-update for this platform" when the feed's `latest_version` is known, else the fallback "No auto update on this platform" — info icon styling; any OTHER error renders the raw backend `error` string in small muted text under the "Check failed" label so real failures are diagnosable), `:applying` (buttons disabled), `:idle` (Check now). Mount-triggered check fires in `handle_params/3` when visible && connected && hub `:idle`.

**Flows**:
- **Check** (Phase 1, safe anytime): `check_for_updates` (or the mount trigger) → `UpdateStatus.check_started()` + `push_event(socket, "update_check_requested", %{})` + `spawn_check_watchdog/1` on `EvoDash.TaskSupervisor`. The watchdog runs the `:update_check_runner` seam (default `default_watchdog/1`: sleep `:update_check_timeout` (30s) then `check_failed("timeout")` if still `:checking`) wrapped in try/rescue — the `:checking` phase can NEVER stick. When a runner seam is injected, the timeout watchdog also runs in parallel (belt-and-braces for tests). Results come back via hub broadcasts (real path) or the send-pattern `send(view.pid, {:update_check_result, payload})` (test seam) → `handle_info` → hub.
- **Auto-download**: after an `"available"` check result, the global hook's interceptor pushes `"update_download_requested"` once per version (`request_download?()` guard); a download failure keeps `:available` with the manual **Download** button (`download_update` handler pushes the same event). Download is inert/verified (Phase 1).
- **Apply** (Phase 2, gated — the only dangerous step): "Restart & Update" → `active_task_ids(:gate)` = `:update_active_task_ids` seam (list OR one-arg fun `(ctx)`, ctx ∈ `:gate | :winddown_poll`) or node-aware `EvoDash.NodeContext.list_task_ids(node(), [:running, :pending, :cancelling, :finalizing])`. **Idle** → `proceed_apply/1` (`UpdateStatus.applying()` + push `"update_apply_requested"`; JS invokes `begin_update` → `update_apply_confirmed` → `stop_backend`). **Busy** → modal "N task(s) still running" with **Defer** (stay put) or **"Apply & gracefully stop tasks"** → `start_winddown/1` on `EvoDash.TaskSupervisor`: loops cancelling ALL active tasks (`TaskRegistry.cancel_task/1` — graceful: 3-turn grace, worktree auto-commit, results preserved `:cancelled` and reviewable; v1 deliberately uses `:cancelled` + the review page, the `:interrupted` status is deferred per plan §9 #7) until empty (`{:update_winddown_complete}` → apply) or the deadline passes (`:update_winddown_timeout`, default ~35 min — grace is NOT wall-clock bounded: LLM retries ~9min, per-tool cap 30min; poll interval `:update_winddown_poll_ms`, default 5s; keeps cancelling newly-appearing tasks so nothing starts mid-wind-down) → user-warned force-kill modal ("in-flight work will be lost and tasks will need manual review") → `confirm_force_kill_update` → `force_kill_all/0` (`TaskRegistry.force_kill_task/1`) → apply. Wind-down crashes send `{:update_winddown_error, _}` → error flash (never wedge).

**Sidebar notification dot** (`components/layouts.ex`): `sidebar_nav_link/1` gained a `notification` attr; the System nav link passes `notification={update_status_notification(@update_status)}` — amber dot (`bg-amber-500`) when `:available`, blue `animate-ping` (`bg-blue-500`) when `:ready`. `@update_status` comes from the global on_mount hook, so the dot appears on every page and updates from `"updates"` broadcasts. All 9 `Layouts.app` call sites pass `update_status={@update_status}` (same pattern as `desktop_quit_confirm`); the JS hook mount point is `<div id="update-status-hook" phx-hook="UpdateStatus" />` inside the app layout near the DesktopQuit wrapper.

**Test seams** (`config :evo_dash, ...`): `:desktop_release` (visibility gate), `:update_check_runner` (`(view_pid) -> any`, send-pattern `send(view.pid, {:update_check_result, payload})`), `:update_check_timeout`, `:update_active_task_ids` (list or one-arg fun), `:update_winddown_timeout`, `:update_winddown_poll_ms`, `:update_notify_only_override`, `:desktop_quit_stop_fun` (shared with DesktopQuit). Tests: `test/evo_dash/update_status_test.exs` (hub unit tests — state machine, never-wedge, once-per-version guard, broadcast), `test/evo_dash_web/live_hooks/update_status_test.exs` (hook handlers, stop seam, seed matrix), `test/evo_dash_web/live/system_live_test.exs` (card states, check-now, never-wedge, mount trigger, manual download, apply idle/busy/Defer/graceful/force-fallback, hidden when not desktop / remote). All new user-facing strings gettext-wrapped with Chinese meaning comments.

**Exhaustive "Check failed" trigger enumeration** — the card renders "Check failed" (`system_live.ex:275`) exactly when `phase == :error` AND `error` is neither `"not_configured"` (friendly pre-key message, sentinel arm at `update_status.ex:319-326`) nor `"not_available"` (info-style no-auto-update message, sentinel arm at `update_status.ex:303-317`; the Rust side returns it when the feed was fetched but has no payload for this platform). The two sentinels are the ONLY check-status values that bypass "Check failed". Generic `:error` states additionally render the raw backend `error` string below the "Check failed" label (`system_live.ex:271-282`, nil-guarded — `apply_download_result`'s error path can leave it nil). Every path into `:error` with a non-sentinel error:

1. **Check-result payload → `:error`** (`apply_check_result/2`, `update_status.ex:266-347`): (a) non-map payload (nil/atom/list/...; only reachable via the seam send-pattern — JS always pushes a map) → `"check_failed"`; (b) dedicated `"status" => "error"` arm → `payload["error"] || "check_failed"` (JS catch `{status:"error", error:String(err)}` `app.js:807`, or Rust `"Update check failed: {err}"` `desktop/src-tauri/src/main.rs:126/138`) PLUS `latest_version: payload["version"] || state.latest_version` — an error payload that still carries the feed's version (feed fetchable, e.g. signature/platform failure) shows it on the card; (c) `"status" => "not_available"` → `:error` sentinel `"not_available"` while KEEPING the payload's `latest_version`/`notes`/`date` (feed fetchable but no platform payload — e.g. Linux when `latest.json` lacks a `linux-x86_64` entry) so the card can show "Latest version <v> — no auto-update for this platform"; (d) any OTHER/absent/non-string status (e.g. `%{}`, `"weird"`) → `payload["error"] || "check_failed"`. Rust only ever emits the 4 statuses, so unknown-status payloads imply a stale/mismatched Rust build or a seam.
2. **Watchdog timeout** — `default_watchdog/1` (`update_card.ex:136-143`): if `phase == :checking` after `:update_check_timeout` (default 30s) → `check_failed("timeout")`. Spawned on every SystemLive check trigger (`system_live.ex:871` mount-trigger, `:1058` Check-now click) and in parallel whenever the runner seam is set (`update_card.ex:75-79`). Real-world causes: the JS result never arrives (hook unmounted mid-navigation → `pushUpdateEvent` guard no-ops `app.js:789-799`), or the Rust check takes >30s (its own plugin timeout is also 30s `main.rs:115` — a slow fetch can produce a transient "Check failed" then be overridden by the late JS result, which is still a legal transition). NOTE: JS timer-driven checks (30s startup / 6h periodic, `app.js:772-773`) do NOT spawn a watchdog — but they also never call `check_started/0`, so they cannot create a `:checking` spinner; only SystemLive-triggered checks enter `:checking`, and both call sites spawn the watchdog immediately (never-wedge invariant holds).
3. **Crashing check runner** — `spawn_check_watchdog/1` try/rescue (`update_card.ex:67-73`) → `check_failed("check_failed")`. Production-irrelevant (default watchdog cannot raise); only fires with a configured `:update_check_runner` seam.
4. **Download-result errors landing in `:error`** (`apply_download_result/2`, `update_status.ex:350-376`; JS `invokeUpdateDownload` `app.js:811-819`): non-map payload → `"check_failed"`; `"status" => "error"` while phase NOT in `[:available, :checking, :ready]` → `:error` with `payload["error"]` (can be nil → still renders "Check failed"); unknown download status → `"check_failed"`. From `:available` (the normal download state) an error returns to `:available` and the card does NOT show "Check failed". Note the Rust download `not_configured` branch returns the LONG message string as `error` (`main.rs:178-181`), NOT the `"not_configured"` sentinel — so a download error from an unexpected phase renders "Check failed" even pre-key.
5. **Apply failures** (`apply_failed/1` `update_status.ex:221-223`; on-mount hook `handle_event("update_apply_failed")` → `apply_failed(payload["error"] or "apply_failed")`): `:applying` → `:error` → the card shows "Check failed" (shared `:error` branch). From JS `invokeUpdateApply` (`app.js:824-836`): `begin_update` resolving without `{ok: true}` or throwing.

**Broadcast/subscription notes**: `mount/3` subscribes to `"updates"` (`system_live.ex:779`) AND the on-mount hook subscribes the same pid (`update_status.ex:162`) — Phoenix PubSub dedupes identical {pid, topic} subscriptions, so exactly one copy of each broadcast is delivered. The on-mount `:handle_info` interceptor consumes `{:update_status, state}` with `{:halt, ...}` BEFORE SystemLive's own clause (`system_live.ex:1175-1180`, dead code in the merged system — its comment says so) — both assign the same state, no divergence. `mount/3`'s `update_status: UpdateStatus.get()` snapshot (line 804) is taken before handle_params triggers `check_started/0`, so the first paint shows `:idle` then `:checking` via broadcast — no gap (handle_params runs after mount's subscription is established). Late-arriving results always override earlier `:error`/`:checking` states (no phase guard on `apply_check_result`), and the timeout watchdog no-ops once phase leaves `:checking` — the UI can never permanently wedge on "Checking for updates…".

**SystemLive Genesis Source card** (`system_live.ex` between the Software Update card and System Self-Check, root `id="genesis-source-card"`; support module `lib/evo_dash_web/live/system_live/source_card.ex` mirroring `update_card.ex`) — controls the LOCAL Genesis source checkout used as the self-reflective agent's reference. - **Visibility** — `source_card_visible?/1` (private in `system_live.ex`, mirrors `update_card_visible?/1`): local node ONLY — `@source_card_visible` computed in `handle_params/3` when `@current_node` is nil or `node()`. ## Internationalization (i18n)

EvoDash uses **Gettext** for internationalization. All user-facing strings in LiveViews, components, helpers, and templates are wrapped with `gettext/1,2` calls.

> **⚠️ Development note:** Do NOT run `mix gettext.extract`, `mix gettext.merge`, or `mix translate` during normal development. The POT/PO files and all translations are maintained centrally and updated on each release — there is no need to regenerate or retranslate them during feature work. New `gettext` calls in code will be picked up when the maintainer runs the extraction/translation pipeline at release time. Just keep developing normally and write `gettext`-wrapped strings. When a string's meaning needs anchoring for the release-time AI translator (ambiguous short labels, domain jargon, etc.), write a **Chinese comment** next to the `gettext` call explaining the intended meaning — this is the ONLY i18n-related work expected during development.

- **Backend**: `EvoDashWeb.Gettext` (`lib/evo_dash_web/gettext.ex`) — `use Gettext, otp_app: :evo_dash`
- **Import**: `import EvoDashWeb.Gettext` in `evo_dash_web.ex` `html_helpers/0` — available in all LiveViews and HTML components
- **Translation files**: `priv/gettext/default.pot` (template, 253 messages), `priv/gettext/en/LC_MESSAGES/default.po` (English source strings)
- **Dynamic locale**: `root.html.heex` uses `Gettext.get_locale(EvoDashWeb.Gettext)` for the `<html lang>` attribute
- **Workflow**: `mix gettext.extract` → `mix gettext.merge priv/gettext --locale=<lang>` to add new languages (release-time only). The full pipeline (`mix gettext.extract` → `mix gettext.merge` → `mix translate ... all`) runs ONCE per release, translating ALL untranslated texts in a single run.
- **AI Translation**: `mix translate apps/evo_dash/priv/gettext/default.pot all` — translates the POT file to all supported languages using LLM (`deepseek-v4-flash`), covering all untranslated texts in one single release-time run. Supports `--force/-f` to re-translate existing entries and `--prefix/-p` to filter by source file prefix. See `lib/mix/tasks/translate.ex`. Release-time only.
- **CLI excluded**: The `:evo_git` CLI interface does NOT use gettext — only the web dashboard is internationalized
