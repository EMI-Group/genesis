# EvoDash — Phoenix LiveView Dashboard

## Intent

EvoDash is the web dashboard of the EvoGit umbrella: a project-based real-time Phoenix LiveView interface to launch and monitor tasks (genesis / evolve), inspect the agent tree, review results, and manage scheduler settings, user configuration and per-project settings incl. foreign repositories.
Users open a Project (a Git repository path) through the command-palette selector, which mounts it in the core's Virtual Context Tree and makes it the single active project; the dashboard auto-detects the task mode.
Phoenix 1.8 umbrella child app (`:evo_dash`) depending on sibling `:evo_git`.

### Workbench chrome & draft scope

- **Sidebar order** (`Layouts.app/1`): brand → `#workbench-active-tasks` (`WorkbenchActiveTasks`) → separate conditional Needs review → Assistant link → `#workbench-projects` (≤5 recency shortcuts, never a per-project task tree) → the four always-visible direct links Agents/Tasks/Processes/System → `#workbench-conversations`.
  Active one-shot tasks route to task-scoped `/agents?task=<id>` while pending, running, finalizing, cancelling or pausing; paused tasks route to `/tasks?task=<id>` for Resume, review candidates to `/review/<id>`, and conversations retain their own destination.
- **Shell** — the recessed sidebar and subtly secondary-tinted right dock frame an inset, rounded work canvas; only floating surfaces elevate (`assets/css/surfaces.css`, `assets/css/workbench.css`).
  Page, tab and settings navigation do not animate the document; the right panel, settings window and other local controls still honor the reduced-motion-aware motion vocabulary.
- **Tab rail = the ONE open-view list** (`Layouts.app/1` `.workbench-tab-rail`) — `#workbench-tabs` is server-rendered empty and `phx-update="ignore"`; the `Workbench` hook restores the compact grouped rail from `assets/js/hooks/workbench_tabs.js` (`sessionStorage` `genesis-workbench.tabs.v1`, up to 40 tabs per node/project scope), and the active tab joins the canvas on the shortened desktop rail.
  A task is one tab per node and task id across `/agents?task=…`, `/tasks?task=…`, `/review/:id`, and `/review/:id/commit/:sha`; the exact destination is separate from that key and a pending navigation sets `aria-busy`, not `aria-current`.
  The rail, overflow, close neighbour and Alt+Arrow cycling use the same stable group order (project, task, chat, diff, other); the rail-end overflow only appears on real scroll, and the left sidebar never enumerates open views.
  There is one reusable preview per project, draft/project/Assistant/diff tabs are pinned, and middle-click pins a preview without navigating.
- **Project entries** — the overview offers a conversational Assistant draft and a direct New Task composer, both using the shared `ComposerComponents` surface, editor and toolbar while retaining their own events, launch controls, attachments and draft state.
  New Task has a separate canvas tone underneath its composer, template variants leave the Assistant transcript in control of its own scroll, and the composer mode and model triggers are flat at rest.
  Task Options and the separate Project Settings form are inline native disclosures; application-level Settings remains the workbench settings window.
  Opening, creating or selecting a project uses the normal overview route; the deliberate last-tab close uses `wb_home=1` and never reopens the draft.
  A confirmed project or resolved workspace overview advertises its exact scoped draft URL via `data-workbench-default-draft`; the browser opens the unsent draft only when the restored rail is empty and suppresses the default for explicit compose/resume and Back/Forward.
  A direct path to an unregistered repo can still use the manual composer; the project picker must register it before scoped Assistant chat is offered.
- **Right dock** — History and Source Control start closed and preserve the panel state, overlay and resize contracts in `workbench_panel*.js`.
  History puts project and status filters before search, uses a locally animated Tasks/Conversations pill, and lists compact title and metadata rows without repeated task icons.
  Search stays server-side and paged (`WorkbenchComponent`, size 15, current project default, off-process behind a monotonic guard); history destinations remain the Tasks focus view for live tasks, Review for terminal tasks and Assistant for conversations.
  Source Control has intrinsic-height Changes/Branches/Commits controls and a bounded scrolling active view; working-tree and commit diffs open in the central canvas through a portal, with drawer dismissal and focus handled by the workbench hook (`components/CONTEXT.md`, `assets/css/CONTEXT.md`).
- **Draft scope** — `{node, token}` drafts via `EvoDashWeb.DraftScope` (`token/1`, `project/1`, `workspace/1`, `point?/1`, `path/1`, `store_key/2`, `legacy_store_key/2`); the token is the VCT point (`vct:///projects/<name>` / `vct:///workspaces/<slug>`), else the raw absolute OS path (verbatim, never `Path.expand`ed) — one repo re-spelled keeps ONE draft, two points over one OS path stay separate, a legacy OS-path draft is ADOPTED; the token is scope ONLY (admission, `mount_project` and session start take `DraftScope.path/1`; a workspace token never reaches `start_task`); the form exposes `data-task-draft-scope` beside legacy `data-task-draft-project` and stamps `scope_token` on `persist_state`/`persist_model_selection` → `live/draft_scope.ex`, `live/projects_live/`, `live/home_live/`, `assets/js/app.js`.

### Canonical LLM Provider Profiles & Selection

Canonical config is `llm.providers` + `llm.default_provider_profile` (never a flat `llm.models` editor); the identity/selection split, reasoning ladder, provider-derived `id`/`name`, `config_opts/1` push contract and the SIWC flow belong to the root `./CONTEXT.md` provider-profile bullets and `docs/llm-oauth.md`.
`LLMSelection` (`live/llm_selection.ex`) is the dashboard's ONE boundary over core `Schema.provider_profiles/1`, `model_selections/1` and `resolve_model_spec/2`: the fused `LLMSelectionComponents` capsule shows model + effort, a provider drill row switching to a provider view (Auto + a disabled stale row), and the model's ordered effort stops decoded by `resolve_reasoning_effort/3`.
Picker state holds only string-keyed `provider_profile_id`, `model` and optional `reasoning_effort` (nil = node default, `%{}` = explicit Auto); reconciliation migrates/falls back for stale saved choices but launch validation REJECTS invalid explicit selections; explicit choices emit `:model_spec` + `model_id_locked: true` and Auto removes both; Projects stores `model_spec` per target node and `persist_model_selection` merges selection fields without replacing form data, while Assistant scopes by target id AND BEAM node — a pending/disconnected remote target never borrows local models or credentials.
Settings is ONE guided provider surface (compact roster → ONE expanded account editor + inline `SettingsComponents.ProviderWizard` steps, no Quick Setup path) over `LLMSetup.Identity`/`Reasoning`/`Schedule` (see the root provider-profile bullets); OAuth belongs to the profile (`auth_mode`, optional `oauth_file` overriding `EvoGit.Auth.default_oauth_file/0`), `AuthStatus` loads credential status off-process behind node/sequence stale guards, and in-app SIWC (`EvoDash.ChatGPTLogin`) is LOCAL-node only while a remote node keeps the `genesis chatgpt login` CLI guidance, and every waiting sign-in panel offers the manual paste-the-redirect-URL fallback so a browser that cannot reach the listener still finishes the attempt.

## Desktop Mode (Tauri Shell)

The backend is a **standalone web server** with no desktop-shell dependency (no `:desktop`); desktop mode is provided externally by a Tauri shell (repo root `./desktop/`) launching the backend as a sidecar.

- **Directory picking is server-side** via `EvoDash.DirectoryPicker` (native tools, `:wx` fallback) — NOT Tauri, NOT the browser File System Access API: the `DirectoryPicker` hook pushes `directory_pick` → `ProjectsLive` (local node only; remote/headless → `unavailable`) → picker GenServer → `picker_result:<picker_id>`; remote nodes hide Browse; disable via `config :evo_dash, :directory_picker, enabled: false`. No `:desktop`/`Desktop.Window`/`is_desktop`/`?client=desktop` plumbing exists: `EVOGIT_DESKTOP` is referenced by `UpdateStatus.desktop?/0` and `DesktopLifetime`'s gating, and `:wx` ONLY by `DirectoryPicker` + its `Wx` seam (loaded via `wx: :load` in the root `mix.exs`; `genesis_server` stays wx-free).

- **Static assets** (`priv/static/`): `favicon.ico` + `images/favicon.svg` are DERIVED from `images/logo.svg` (source of truth; dark gray `#373435` + red `#C8383C`, aspect ≈ 1.2334); `images/logo-alt.svg` is the dark-theme variant; regeneration recipe: `assets/CONTEXT.md` → "Static Assets".

### Backend Boot Order (HTTP listener is bound LAST)

The Tauri readiness probe measures the ENTIRE umbrella boot — the port accepts connections only after `:evo_git` has fully started.

- `evo_dash.app` lists `:evo_git`, so `EvoGit.Application.start/2` completes first (incl. `EvoGit.Store.init/1` → synchronous `Store.Boot.start_dynamic/2` migrations and `TaskRegistry.init/1`'s lease read); the endpoint is the LAST child of `EvoDash.Application` and Bandit/ThousandIsland binds synchronously in its Listener `init/1` before `start/2` returns (`server: true` from `config/runtime.exs`), so a slow `:evo_git` boot presents as "backend unavailable" with no listener.
- **Boot observability is thin**: neither app logs a boot line, and `backend.log` exists only via the root `config/runtime.exs` (`type: :file`, APPENDED, 10 MB × 5 files); the markers are Ecto's `Migrations already up` and `Running EvoDashWeb.Endpoint with Bandit <vsn> at <address>:<port> (http)` per successful bind at `:info`, plus `… failed, port <port> already in use`. `PORT`/`PHX_IP` are read ONCE per BEAM; a BOOT bind failure aborts `start/2` while a RUNTIME restart retries to the endpoint supervisor's intensity (3/5 s) then `EvoDash.Supervisor`'s (10/60 s); no OS pid is logged, so `backend.log` cannot distinguish repeated boots, sidecar respawns and `System.restart/0`.
- `DesktopLifetime` is the ONLY self-exit (5 connect attempts × 200 ms, 1 s timeout, then a warning + `System.stop(0)`; exit 0 is INTENTIONAL to the Tauri watchdog → silent quit, not the error page — `lib/evo_dash/CONTEXT.md`), and the shell error page is NOT the first-run `push_navigate(to: "/welcome")`: that 302 on `GET /` is real, but the load latch matches host+port only and post-upgrade launches never take it, because `VersionState.onboarding_needed?/0` keys on the version-state FILE existing.

## Research Notes — ReqLLM-Native Multimodal (Image/Audio) Attachments

Refines the root `./CONTEXT.md` note ("Research Notes: PDF/DOCX → Plain Text Extraction"): the plain-text pipeline (`EvoDash.AttachedFile.read/1` + `ex_pdf`) is unchanged, and image/audio attachments are ADDITIONALLY staged as raw-binary content parts (`AttachedFile.read_kind/2` — image/audio kinds, extension allowlist, 15 MiB cap) into the Projects page's `:staged_attachments` and submitted as the `:attachments` task opt (base64 `"data"`, string-keyed maps) → `lib/evo_dash/CONTEXT.md` + `live/projects_live/CONTEXT.md`.

- Part types are `:text | :image_url | :video_url | :image | :file | :thinking | :provider_block` (no `input_image`/`input_audio`), and encoding is per-provider at encode time — the OpenAI-compatible flock turns ANY `:file` bytes into an `image_url` data-URI (silently mis-encoding non-images) — so check BOTH codec path and modality: capability truth is `:llm_db`'s `%LLMDB.Model{modalities: %{input: [...]}}` (`LLMDB.model/2`), with no "accepts image?" helper. Under `EvoGit.Config.LLMCatalog` the reachable set is anthropic (image), openai (image + pdf), google (image + audio + video + pdf), deepseek-v4-flash-vision-exp (image), openrouter (image + pdf + mp3/wav audio).
