# EvoDash — Phoenix LiveView Dashboard

## Intent

EvoDash is the web dashboard of the EvoGit umbrella: a project-based real-time Phoenix LiveView interface to launch and monitor tasks (genesis / evolve), inspect the agent tree, review results, and manage scheduler settings, user configuration and per-project settings incl. foreign repositories.
Users open a Project (a Git repository path) through the command-palette selector, which mounts it in the core's Virtual Context Tree and makes it the single active project; the dashboard auto-detects the task mode.
Phoenix 1.8 umbrella child app (`:evo_dash`) depending on sibling `:evo_git`.

### Canonical LLM Provider Profiles & Selection

Canonical config is `llm.providers` + `llm.default_provider_profile`, NOT a flat `llm.models` editor: a profile owns identity, auth/endpoint, shared concurrency/peak schedules, defaults, `default_model` and nested models, needs a nonempty `models` list naming `default_model`, and legacy `llm.models`/profile ids are migration inputs resolved through core projections.
`LLMSelection` is the shared boundary (core `Schema.provider_profiles/1`, `model_selections/1`, `resolve_model_spec/2`); the fused capsule shows model + effort, a provider drill row switching to a provider view (Auto + disabled stale row), and the model's ordered effort stops decoded by `resolve_reasoning_effort/3`.
Picker state holds only string-keyed `provider_profile_id`, `model` and optional `reasoning_effort` (nil = node default, `%{}` = explicit Auto); reconciliation migrates/falls back for stale saved choices but launch validation REJECTS invalid explicit selections; explicit choices emit `:model_spec` + `model_id_locked: true`, Auto removes both.
Projects stores `model_spec` per target node (canonical outranks `selected_model_id`) and `persist_model_selection` merges selection fields without replacing form data; Assistant scopes by target id AND BEAM node; pending/disconnected remote targets never borrow local models or credentials; loaded bundles stay server-only; runtime updates push `ModelSelection.config_opts/1` (keeping the scheduler's snapshot) while connection tests resolve the viewed node's persisted provider/model with its own auth.
Settings is ONE guided provider surface (compact roster → ONE expanded account editor + inline wizard from `SettingsComponents.ProviderWizard` steps, no Quick Setup path); `LLMSetup.Identity` derives `id`/`name` from the PROVIDER (collision-safe `-2`/`-3`); reasoning = ONE chip list over `LLMSetup.Reasoning.efforts/0` (`none minimal low medium high xhigh`, no `max`) plus a separate inventory-scoped default select; `LLMSetup.Schedule` owns presets/holidays (`off_peak_holidays` = holidays plus weekends off-peak).
OAuth belongs to the profile (`auth_mode` API key vs subscription, OAuth-only providers force subscription, optional `oauth_file` overrides `EvoGit.Auth.default_oauth_file/0`, no global `[llm] oauth_file`); `AuthStatus` loads credential status off-process with node/sequence stale guards and distinguishes missing login / unwritable managed file / unknown.
**In-app SIWC** — `:openai_codex` signs in FROM THE BROWSER for a LOCAL node (`EvoDash.ChatGPTLogin` binds an ephemeral `127.0.0.1` listener carrying the real port, `LLMSetup.ChatGPTSignIn` polls off-process then reloads accounts); a REMOTE node keeps `genesis chatgpt login` CLI guidance; the CLI drives the SAME flow.

### SSH Remote Development — Node-Aware Dashboard

The dashboard controls a remote headless daemon over Erlang distribution via an SSH tunnel (ONE `genesis_server` instance per host, distribution enabled by `<launcher> remote start`; node `genesis_remote_<target_id>@127.0.0.1`) through `NodeContext`, `LiveHooks.NodeAware` (node assigns, `?node=` resolution, unified sidebar Active-Tasks loader, connection status) and `NodeSelectorComponent`.

- **URL threading**: nav links carry `?node=<target_id>` (`with_node_param/2`; ⚠️ it appends with `?`, so query-string URLs need a manual `&node=`); every load routes through `NodeContext` (local direct, remote `:erpc`) off the LiveView process with no polling — push-based via `EvoGit.PubSub` (PG2/`:pg`); evo_dash owns no SQLite/Ecto/xqlite and has ZERO `EvoGit.Store` references in production code.
- **Per-page**: SettingsLive edits remote config (`save_user_config` + `reload_remote_config`), SystemLive controls via RPC (update + source cards hidden), ProjectsLive shows the remote form with read-only projects, TasksLive reads the full remote list; lifecycle calls return safe fallbacks and the selector renders "Local" by default. ### Push-based event contract (node-identity PubSub)

`:evo_git` broadcasts on `EvoGit.PubSub`; every event carries the **publisher's BEAM node atom** and only a matching viewed node updates the UI — `NodeAware.event_from_current_node?/2`; task events flow through `NodeAware.handle_task_info/2` (300 ms trailing debounce → `:node_aware_reload_tasks`).

| Topic | Events | Consumers |
|-------|--------|-----------|

No config write exists outside the core save APIs: `config.toml` funnels through `ConfigSave.start/4` → `NodeContext.save_user_config/2`, credentials through `NodeContext.save_credentials/2` (remote adds `reload_remote_config/1`), `agents.toml`/`remote_connections.toml`/`version_state.toml` through their own APIs; post-save freshness is ASSUMED, never polled (`ConfigSave` re-reads in the SAME supervised task, local credential saves re-read inline, Welcome re-reads `resolve/0` + `credentials/0` in the LiveView).
**Nothing subscribes to config changes**: `config_status` is captured once per mount (`projects_live.ex` deferred `:load_config_status`, `tasks_live.ex`, `review_live.ex`, `processes_live.ex`, `agents_live/load_data.ex`) and the accent re-resolves only on a new socket mount or node change (`live_hooks/appearance.ex`; `EvoDash.AccentCache` has no TTL or per-key invalidation), so an outside edit (CLI, MCP, another tab, a vendor OAuth login, the remote bootstrap config copy) surfaces only on the next remount; MCP is the documented external-edit path (`genesis_check` advertises paths, then `genesis_reload_config` → `EvoGit.TaskControl.reload_config/1` → `RemoteAPI.reload_config/0` is the only forced re-read).
`config_status/0`'s `ok?`/`validation_errors` come from a caller-process side channel that `resolve/0` writes, so every banner is only truthful while `resolve/0` validates in the reading process. Contracts: `live/CONTEXT.md`, `live/settings_live/CONTEXT.md`, `live/projects_live/CONTEXT.md`, `live/home_live/CONTEXT.md`, `live/welcome_live/CONTEXT.md`.

## Constraints

- Depends on `:evo_git` at compile and runtime (persistence/registry code lives there; evo_dash owns none); port 4100 in development on Bandit; Tailwind CSS 4 + DaisyUI (no Node.js toolchain), JS bundled by esbuild.
- Task state persisted via SQLite in the core (xqlite Rust NIFs); no external DB server; Store + TaskRegistry are evo_git-owned (`apps/evo_git/CONTEXT.md`).
- The project registry is the core's Virtual Context Tree: `EvoGit.VCT` owns `vct_mounts` in the task-store database, mounting each opened project at `vct:///projects/<basename>[-N]` with `last_opened_at` ordering and a `VCT.max_projects/0` cap (100 default, oldest evicted); the dashboard sees only PROJECT mounts — reserved mounts such as `vct:///genesis-source` are deliberately absent from `projects/1`/`search/2`.
- Registry access is only `NodeContext.projects/1` / `mount_project/3` / `forget_project/2`, and `EvoGit.VCT` broadcasts `{:vct_updated, node}` on `"vct"` after every successful mutation; `%EvoGit.VCT.Mount{}` carries `point`, `path`, `name`, `kind`, `last_opened_at`; palette rows show `name` with the OS `path` secondary, while the `point` stays the registry/forget identity and stays searchable in `filter_projects/2`.
- **VCT workspace mounts (grouping only)** — a workspace is `%EvoGit.VCT.Mount{kind: "workspace", point: "vct:///workspaces/<slug>", path: nil, members: [ordered %{"point", "path"}], description: …}`: a pure GROUPING point, never a runnable project, never the active project, never a task execution path; reached only through `NodeContext.workspaces/1` / `workspace_entries/1` / `create_workspace/4` / `workspace_members/2` / `workspaces_for/2` (roster reads degrade to `[]`, the other two return `{:error, reason}`; `create_workspace/4` is an idempotent slug-keyed UPSERT, `workspace_entries/1` the BATCHED read returning `%{point:, name:, path:}` plus stored `missing`/`nested` refs).
  Surface: the Projects palette's **Workspaces** section (name/point/description rows with a member disclosure marking missing refs) plus a **New Workspace** form with an ordered member picker, both node-scoped and reset on node switch; only `workspaces/1` lists them (`projects/1` and `search/2` exclude workspaces and reserved mounts) — `live/projects_live/CONTEXT.md` + `components/CONTEXT.md`.
- **Data-safety architecture**: TaskRegistry/Store `handle_*` callbacks have NO try/rescue — a Store failure crashes the GenServer and the supervisor restarts it (WAL keeps data safe); serialization is `EvoGit.Store.Codec` (total encode, raise-on-bad-decode); `safe_select_all_tasks/projects` SKIP corrupt rows with a `Logger.warning`; `cleanup_expired_tasks` runs only on completion transitions / explicit clear / init, and the completed task's `put_task` runs BEFORE cleanup; running tasks carry `lease_expires_at` (renewed every 60 s), lease checking is two-check, one-shot (startup reconcile + one `:lease_sweep`), and a task is marked `:failed` only when the lease has genuinely expired (a second BEAM instance cannot kill the first's running tasks) → `apps/evo_git/CONTEXT.md`.
- **Supervision robustness**: `:one_for_one` with `max_restarts: 10`, `max_seconds: 60` so the Endpoint survives a transient TaskRegistry restart.
- **`try/rescue` anti-pattern policy**: never wrap LiveView config/core-value loading (`EvoGit.Config.*`, `EvoGit.AgentScheduler.*`) — let the LiveView crash truthfully; JSON via non-crashing `Jason.encode/1` + `case`; atom conversion from untrusted input via whitelist `Map.get/3` (never `String.to_existing_atom/1` + rescue, never bare `String.to_atom/1`); ETS existence via `:ets.info/1`. Acceptable try/rescue (MUST carry a comment answering "expected error?" + "cleanest approach?"): GenServer `terminate/2`, deliberate data-recovery boundaries, untrusted persisted data with no non-crashing variant, the Store's `ALTER TABLE DROP COLUMN` migration, test-cleanup rescues in `on_exit`/teardown.
- Naming: domain modules in `./lib/evo_dash/`, web modules in `./lib/evo_dash_web/`; build via `mix assets.build` (esbuild + tailwind) and `mix assets.deploy` (minified + digested).
- **No context-tree UI**: the dashboard renders no repo directory/node hierarchy, node browser or CONTEXT.md viewer; context-tree addressing exists only as the evolve-only free-text "Starting Node" (`:node_path`) task field (`task_form_components.ex`) and AgentsLive's per-turn `CONTEXT_TREE` history dump (`agents_live.html.heex`), the nearest hierarchies being the agent tree (`agents_components.ex`), the review file/diff tree (`review_components/diff_viewer.ex`) and archive trees.
- Desktop-mode gating: desktop-only code (`DesktopLifetime`, update-status integration) lives in the frontend app and stays inert outside the Tauri shell, so the headless `genesis_server` release never activates it; gating env vars `EVOGIT_DESKTOP` / `EVOGIT_LIFETIME_PORT`.

## Desktop Mode (Tauri Shell)

The backend is a **standalone web server** with no desktop-shell dependency (no `:desktop`); desktop mode is provided externally by a Tauri shell (repo root `./desktop/`) launching the backend as a sidecar.

- **Directory picking is server-side** via `EvoDash.DirectoryPicker` (native tools, `:wx` fallback) — NOT Tauri, NOT the browser File System Access API: the `DirectoryPicker` hook pushes `directory_pick` → `ProjectsLive` (local node only; remote/headless → `unavailable`) → picker GenServer → `picker_result:<picker_id>`; remote nodes hide Browse; disable via `config :evo_dash, :directory_picker, enabled: false`.
- **Codebase references**: no `:desktop`/`Desktop.Window`/`is_desktop`/`?client=desktop` plumbing; `EVOGIT_DESKTOP` IS referenced by `UpdateStatus.desktop?/0` and `DesktopLifetime`'s gating, and `:wx` ONLY by `DirectoryPicker` + its `Wx` seam (the `genesis`/`genesis_desktop` releases load it via `wx: :load` in the root `mix.exs`, `genesis_server` stays wx-free).
- **Tray quit confirm**: tray "Quit Genesis" → Rust emits `quit-requested` → the `DesktopQuit` hook pushes `desktop_quit_requested` → `LiveHooks.DesktopQuit` shows a confirm dialog on ANY page → confirm runs graceful `System.stop(0)` through the `:desktop_quit_stop_fun` seam (150 ms-delayed, NO force quit, no timeout) → `live_hooks/CONTEXT.md` + `desktop/CONTEXT.md`.
- **Static assets** (`priv/static/`): `favicon.ico` + `images/favicon.svg` are DERIVED from `images/logo.svg` (source of truth; dark gray `#373435` + red `#C8383C`, aspect ≈ 1.2334); `images/logo-alt.svg` is the dark-theme variant; regeneration recipe: `assets/CONTEXT.md` → "Static Assets".
- **Release configuration** (owned by the ROOT `mix.exs` — this app has no `rel/`): releases `genesis` (both apps, dev), `genesis_desktop` (bakes `evo_dash: [desktop_release: true]`, bundled as a Tauri resource) and `genesis_server` (the only headless distribution: dashboard server AND SSH remote daemon, wx-free, `include_erts`); `config/runtime.exs` handles `PHX_SERVER=true` and server mode (ONE `genesis_server` per host serves HTTP and may enable distribution at runtime on the same BEAM); production needs `SECRET_KEY_BASE` + `PHX_HOST`.

### Backend Boot Order (HTTP listener is bound LAST)

The Tauri readiness probe measures the ENTIRE umbrella boot — the port accepts connections only after `:evo_git` has fully started.

- `evo_dash.app` lists `:evo_git`, so `EvoGit.Application.start/2` completes first (incl. `EvoGit.Store.init/1` → synchronous `Store.Boot.start_dynamic/2` migrations and `TaskRegistry.init/1`'s lease read); inside `EvoDash.Application` the endpoint is the LAST child and Bandit/ThousandIsland binds synchronously in its Listener `init/1`, so the bind completes before `start/2` returns (`server: true` from `config/runtime.exs`); a slow `:evo_git` boot presents as "backend unavailable" with no listener.
- **Boot observability is thin**: neither app logs a boot line and `backend.log` is configured ONLY by the root `config/runtime.exs` (`:default_handler` `type: :file`, APPENDED across launches, 10 MB × 5 files, prod `:info`); markers are dep lines — Ecto's `Migrations already up` / `== Running <v> <mod>.up/0` and `Running EvoDashWeb.Endpoint with Bandit <vsn> at <address>:<port> (http)` at `:info` on EVERY successful bind, plus `Access EvoDashWeb.Endpoint at http://<host>:<port>` per endpoint-supervisor start and `… failed, port <port> already in use`.
- `PORT`/`PHX_IP` are read ONCE per BEAM at config-provider time; nothing re-reads or re-binds at runtime (the only `config_change` forwards to `Phoenix.Endpoint.Supervisor.config_change/3`); a BOOT bind failure aborts `start/2` (no retry) while a RUNTIME restart failure retries until the endpoint supervisor's intensity (3/5 s) then `EvoDash.Supervisor`'s (10/60 s); `config/config.exs` logs NO OS pid, so `backend.log` cannot distinguish repeated boots from sidecar respawns vs `System.restart/0`.
- `DesktopLifetime` is the ONLY self-exit here: 5 connect attempts × 200 ms with a 1 s timeout each, then a warning + `System.stop(0)` — exit 0 is classified INTENTIONAL by the Tauri watchdog, so it yields a silent quit, NOT the "backend unavailable" page (`lib/evo_dash/CONTEXT.md`).
- The shell error page is NOT caused by the first-time-user `push_navigate(to: "/welcome")`: it IS a real 302 on `GET /`, but the shell's load latch matches by host+port only, and post-upgrade launches never take that branch because `VersionState.onboarding_needed?/0` keys on the version-state FILE existing, not on the version changing.

## Research Notes — ReqLLM-Native Multimodal (Image/Audio) Attachments

Refines the root `./CONTEXT.md` note ("Research Notes: PDF/DOCX → Plain Text Extraction"). The plain-text pipeline (`EvoDash.AttachedFile.read/1` + `ex_pdf`) is unchanged; image/audio attachments are additionally server-side-staged raw-binary content parts (`AttachedFile.read_kind/2` — image/audio kinds, extension allowlist, 15 MiB cap) staged into the Projects page's `:staged_attachments` assign and submitted as the `:attachments` task opt (base64 `"data"`, string-keyed maps) → `lib/evo_dash/CONTEXT.md` + `live/projects_live/CONTEXT.md`.

- `ReqLLM.Message.ContentPart` types: `:text | :image_url | :video_url | :image | :file | :thinking | :provider_block`; no canonical `input_image`/`input_audio` chat part. Images ride `:image`, `:image_url` or `:file`; chat audio is a `:file` part with an `audio/*` media_type, practically OpenRouter-only (mp3/wav → `input_audio`, other audio raises) — otherwise `ReqLLM.transcribe/3`, `ReqLLM.speak/3` or the experimental `ReqLLM.OpenAI.Realtime` websocket.
- Wire translation is per-provider at encode time: the OpenAI-compatible flock (deepseek/qwen/zai/alibaba/groq/mistral/venice/...) encodes ANY raw `:file` bytes as an `image_url` data-URI, silently mis-encoding non-image parts; OpenAI Chat rejects non-image `:file` while Responses accepts image + pdf only; Anthropic maps `:file` to image/document base64 blocks; Gemini `inlineData`/`fileData` carries arbitrary mime; OpenRouter handles image + pdf + mp3/wav audio; Bedrock Converse is image-only-inline.
- Capability truth lives in `:llm_db`: `LLMDB.model/2` → `%LLMDB.Model{modalities: %{input: [...]}}` from `./deps/llm_db/priv/llm_db/snapshot.json`; no "accepts image?" helper, so read `.modalities.input` and check BOTH codec path and modality (`google` 19 / `openrouter` 72 audio-input models; image input near-universal); reachable multimodal set given `EvoGit.Config.LLMCatalog`: anthropic (image), openai (image + pdf via Responses), google (image + audio + video + pdf), deepseek-v4-flash-vision-exp (image), openrouter (image + pdf + mp3/wav audio).
