# EvoDash — Phoenix LiveView Dashboard

## Intent

EvoDash is the web dashboard for the EvoGit umbrella project: a project-based real-time browser interface for launching and monitoring EvoGit tasks (genesis / evolve), inspecting the agent tree hierarchy, viewing task logs, managing runtime scheduler settings, editing user configuration, and managing per-project settings including foreign repositories — powered by Phoenix LiveView.

Users open a Project (a Git repository path), and the dashboard auto-detects the appropriate task mode. Multiple projects can be open simultaneously with tab-based navigation. This is a Phoenix 1.8 umbrella child app (`:evo_dash`) that depends on the sibling `:evo_git` application.

### Multi-Model LLM Support

The dashboard supports the core's multi-model architecture (`[[llm.models]]` array-of-tables config). Every model profile has its own id, model, concurrency, and gen params (temperature, reasoning_effort, max_tokens, top_p, top_k, frequency_penalty, presence_penalty) plus optional peak/off-peak fields (`peak_concurrency`, `peak_hours`, `timezone`).

- **Model profiles editor** (Settings LLM category) — `SettingsLive` + `SettingsComponents.model_profiles_editor/1` + support modules `ModelProfileHelpers`/`ModelProfileEvents`. Events: `add_model_profile`, `edit_model_profile`, `save_model_profile`, `delete_model_profile`, `cancel_edit_model_profile`, `model_profile_form_change`, `add_peak_hours_row`, `remove_peak_hours_row`. Duplicate ids rejected. **Peak/off-peak serialization contract**: absent/empty keys are OMITTED from the profile so TOML omits them (never nil/`[]`); `peak_concurrency = 0` is a valid hard pause; timezone blank = server local time. **Draft-tracking**: the edit form's `phx-change="model_profile_form_change"` stores the whole form as a `:profile_form_draft` assign so the add/remove peak-hour row buttons never wipe unsaved typing (phx-click does not submit the enclosing form). Full detail: `live/settings_live/CONTEXT.md` → "Peak/Off-Peak Hour Concurrency".
- **LLM category layout**: Quick Setup + Model Profiles editor + Connection Test render OUTSIDE the `save_category` form (no nested-form HTML); only `compression_threshold_tokens` (the one flat global card) + Save sit inside the form. `params_to_category_config/3` skips `:model_profiles`-type schemas so the generic category save never clobbers the models list. `select_llm_model_shortcut`/`save_custom_model` ADD a profile to the list.
- **Runtime update**: `update_runtime_from_file_config/2` pushes `:model_profiles` (via `Schema.model_profiles/1`) + scheduler concurrency keys to `EvoGit.AgentScheduler.update_config/1` (local only — remote saves use `reload_remote_config`).
- **Per-task agent + model selection** (ProjectsLive + `TaskFormComponents.task_form/1`) — a single shared card (`grid grid-cols-1 lg:grid-cols-2`): **Agent select** (only when `@custom_agents != []`; "Auto (recommended)" + custom agents from `EvoGit.CustomAgents.list/0`; selection threads `:agent => id`, persists via `StatePersistence` `selected_agent_id`); **Custom Agent mode** (4th task mode → `{:evolve, "custom"}` with the selected agent as REQUIRED `:agent`; auto-selects first agent; violet accent); **Model select** ("Auto (by rules)" first when a model-selection script is configured). Threading contract in `task_submit`: a specific profile → `:model_id => id` AND `:model_id_locked => true` (set UNCONDITIONALLY — an explicit choice always defers the model-selection script); "Auto (by rules)"/nil/"" → NEITHER key (script or default decides). No `build_common_runtime_opts/3` exists — opts are built inline. Detail: `components/CONTEXT.md` (Task Form section) + `live/projects_live/CONTEXT.md`.
- Welcome modal gate: `show_welcome` checks `model_profiles == []`. System page example-config/FAQ use the `[[llm.models]]` format.

### SSH Remote Development — Node-Aware Dashboard

The dashboard controls a remote headless `genesis_remote` daemon over Erlang distribution via an SSH tunnel. Three layers: `EvoDash.NodeContext` (thin client, `lib/evo_dash/node_context.ex`), `EvoDashWeb.LiveHooks.NodeAware` (on-mount hook: node-context assigns, `?node=` resolution, unified sidebar Active-Tasks loader, connection-status handling with push_patch on local↔remote transitions), and `EvoDashWeb.NodeSelectorComponent` (navbar node selector + connection-manager modal, auto-connect on select).

- **URL threading**: ALL nav links carry `?node=<target_id>` when a remote node is selected (`with_node_param/2` in `layouts.ex`; ⚠️ appends with `?`, so query-string URLs must use a manual `&node=` suffix — see `lib/evo_dash_web/CONTEXT.md`).
- **Data access**: every LiveView routes through `EvoDash.NodeContext` (local direct call, remote `:erpc`); all node-aware page loads run in `EvoDash.TaskSupervisor` children outside the LiveView process with stale-guards; **no polling anywhere** — fully push-based via cluster-aware `EvoGit.PubSub` (PG2/`:pg`).
- **Per-page remote behavior**: SettingsLive (editable remote config, saves via `save_user_config` + `reload_remote_config`; `get_resolved_config` full-config round-trip), SystemLive (pause/resume + restart/stop via RPC; software-update + source cards hidden on remote), ProjectsLive (remote view shows the node's active agents; task launch is local-only; remote projects read-only), TasksLive (full remote task list via RPC, same push-based reload path). AgentsLive is fully async + push-driven with `HistoryGate` (skip refetch when `:message_count` unchanged) + `ThresholdCache` (30s freshness per node). Detail: `lib/evo_dash_web/CONTEXT.md` ("SSH Remote UX" + node-locking) + `live_hooks/CONTEXT.md` + `live/agents_live/CONTEXT.md`.
- Graceful degradation: lifecycle calls return safe fallbacks when `EvoGit.RemoteConnection` is unavailable; the node selector renders "Local" by default.

### Push-based event contract (node-identity PubSub)

The dashboard is fully push-based — no periodic polling. `:evo_git` broadcasts enriched events on `EvoGit.PubSub`; every event carries the **BEAM node atom of the publisher**. **Node-filtering rule**: an event only triggers UI updates when its `node` matches the viewed node — `EvoDashWeb.LiveHooks.NodeAware.event_from_current_node?/2` (event node vs `socket.assigns.current_node`). Consumers: NodeAware, AgentsLive, TasksLive, ReviewLive, SystemLive, SettingsLive, ProjectsLive. `{:task_updated, ...}` / `{:task_deleted, ...}` flow through `NodeAware.handle_task_info/2` (300ms trailing-edge debounce → `:node_aware_reload_tasks`).

| Topic | Events | Consumers |
|-------|--------|-----------|
| `"tasks"` | `{:task_updated, task_id, status, node}` (status `:pending\|:running\|:finalizing\|:cancelling\|:completed\|:failed\|:cancelled` or `nil` for review-only mutations); `{:task_deleted, task_id, node}` | NodeAware (debounced sidebar + reloads), TasksLive, ProjectsLive, ReviewLive, AgentsLive, SettingsLive, SystemLive |
| `"agents"` | `{:agent_registered, id, summary, node}`, `{:agent_updated, id, changed_fields, node}` (NEVER `:context`; contains `:message_count` when context changed), `{:agent_removed, id, node}`, `{:agents_updated, node}` | AgentsLive |
| `"scheduler_config"` | `{:scheduler_config_updated, node}` | SettingsLive, SystemLive (node-filtered → async reloads) |
| `"system"` | `{:system_sample, node, seq, sample}` every 3s; keys `llm_used, llm_waiting, tool_used, tool_waiting, llm_capacity, tool_capacity, agents_total, agents_running, agents_blocked, agents_waiting, agents_pending, scheduler_alive` | SystemLive chart (ring buffer, cap 60) |
| `"recent_projects"` | `{:recent_projects_updated}` | ProjectsLive |
| `"guides"` | `{:guide_updated, id, %{message, page, selector, dismissible}, node}` | `LiveHooks.Guide` overlay |
| `"updates"` | `{:update_status, state}` | UpdateStatus hook, SystemLive |

**SystemLive chart seed**: on mount/node-switch ONE async `get_recent_system_samples/1` via `EvoDash.TaskSupervisor` + stale-guard (monotonic `chart_seed_seq` + node); one retry after 3s (`chart_seed_retried`); `:system_samples_runner` test seam resolved AT SPAWN TIME.

### Task Archive Feature

When a task is started with the **archive** checkbox, the core collects per-agent metadata (`archive_records`) and EvoDash persists it in `EvoGit.TaskInfo.archive_metadata` (`[map()] | nil`, backfill-safe). Archived tasks show the agent parent-child tree (per-agent objective/return/start-end commits/token usage/archive refs) and provide JSON export. Opt-in only — no archive sections render when disabled.

- **Threading**: `:archive` opt (built inline in `ProjectsLive.do_task_submit/4`) → core; on completion `archive_records` extracted from the result map → `update_task_status/4` → persisted.
- **Mode resolution**: UI combined-mode strings `"genesis_new"`/`"genesis_existing"`/`"evolve_simple"`/`"custom_agent"` → `{task_type, core_mode_string}` in `do_task_submit/4` (`{:genesis, "new"\|"existing"}`, `{:evolve, "simple"\|"custom"}`; unknown strings fall back to `{:evolve, "simple"}`). Core `RuntimeOpts.mode_atom/2` accepts `"custom"` for evolution; unknown evolution modes raise `ArgumentError`; `:genesis` + `"custom"` raises "custom mode is evolve-only".
- **JSON export**: `GET /tasks/:task_id/export` → `TaskExportController` (normalizes structs to plain maps).
- Archive UI render sites + known gotchas (string-keyed usage, missing `cost` key, crashed agents absent from metadata): `lib/evo_dash_web/CONTEXT.md` → "Known Issues — Task Archive Display".

### Self-Reflective Task Mode & Guide Overlay

- **`:reflect` task mode** — repo-less conversational task type whose ONLY dashboard entry point is the **Home chat page** (`HomeLive` at `GET /help`); the Projects task form offers no reflect mode. Reflect tasks carry NO `:path`, run with nil `project_path` (task cards are nil-path-safe), and their result is the agent's final text (`{:ok, %{result: <text>, commit_sha: nil, branch_name: nil, tag: nil}}`). `:reflect` is in `Store.Codec` `@known_atoms`; `execute_task(:reflect)` routes directly to `Runtime.SelfReflective.run`, bypassing `build_common_runtime_opts` (which `Keyword.fetch!(:path)`-raises). Core detail: `apps/evo_git/CONTEXT.md`; dashboard: `live/home_live/CONTEXT.md`.
- **Guide overlay** — global floating UI through which a running reflective agent guides the user. Core broadcasts on `"guides"`; consumed by `EvoDashWeb.LiveHooks.Guide` (registered LAST in `live_view/0`): node-filters, assigns `@guide`, persists per-tab via `guide_client_id` (`:persistent_term`), pushes `"guide_highlight"` (`%{selector}`). `Layouts.app` renders the floating panel (`fixed top-4 right-4 z-50`); the `Guide` JS hook scrolls + applies `.guide-highlight` (~3s). Detail: `live_hooks/CONTEXT.md` + `assets/CONTEXT.md`.

### Home Chat Page (`HomeLive` at `GET /help`)

ChatGPT-style chat wired to the self-reflective agent — the ONLY entry for `:reflect` tasks; sidebar **Help** nav entry; renders through `Layouts.app` with `current_page={:help}`. Send flow: `Transcript.build_preamble/1` (conversation memory — last 8 exchanges, 600 chars/entry, 4000-char cap) + message → `EvoDash.NodeContext.start_task(node, :reflect, mode: "reflect", objective: ...)` with NO `:path`. Streaming via `"agents"`/`"tasks"` PubSub + async `get_agent_history/2` (the core broadcasts `:agent_updated` `changed_fields` as a KEYWORD LIST — guard with `is_list/Keyword.has_key?`, not tuple `in`); terminal rendering from the task result (`:completed`/`:cancelled` show the final text, `:failed` shows the error); two monotonic stale-guards (`chat_fetch_seq`, `chat_task_fetch_seq`). The assistant response is a **mini task-card chat message** (`home_live/assistant_message.ex`): reuses `Helpers.task_status_badge/1` (live `:pending→:running→:completed…` transitions), streams the assistant text, and shows a collapsible "Thought process" (思考过程) built from the agent's context history via the agents-page `AgentsLive.ToolCallDisplay`. **Chat state survives LiveView remounts** via `EvoDash.ChatHistory` (`lib/evo_dash/chat_history.ex`, ETS-backed, supervised in `EvoDash.Application`): the transcript + task/agent refs are persisted per chat and restored on connected mount (mid-run mounts get a one-shot reconciliation fetch, no polling); New chat = new persisted chat + `prune(10)` (old chats kept in memory, local-node only). Enter to send / Shift+Enter newline (zero-JS shift-latch), Stop = graceful cancel. Full detail: `live/home_live/CONTEXT.md`.

### Task Cancellation Model

Two node-aware actions backed by `EvoGit.RemoteNode`:
- **Graceful cancel** (`EvoDash.NodeContext.cancel_task/2`): `:pending` → immediate `:cancelled`; `:running` → `:cancelling` (agents messaged to save + exit, 3-turn grace) → `:cancelled` WITH result/archive preserved. `:cancelled` tasks ARE reviewable (Review button via `TaskCardComponents.show_review_button?/1` matches `:cancelled` with a branch/no_changes result).
- **Force kill** (`force_kill_task/2`): kills all agents + wrapper → `:failed`, result nil'd; escalation from `:cancelling`.

UI: TasksLive card Cancel button (`[:pending, :running]`) → confirmation modal; three-dot dropdown "Force kill" (`[:running, :cancelling]`, "Danger zone" divider) → warning modal. `:cancelling` renders as violet in-progress end-to-end (`task_status_badge`, `status_accent_color`, `task_card_tint`, pulsing dot + `gettext("Cancelling…")`, sidebar running partition via `@active_statuses` `[:running, :pending, :finalizing, :cancelling, :completed]`, TasksLive status filter "Cancelling"). Detail: `live/tasks_live/CONTEXT.md` + `components/CONTEXT.md` + `lib/evo_dash_web/CONTEXT.md`.

### GitHub Issue Integration

The Projects page surfaces the active project's GitHub issues (existing repos only) in the top bar:
- **Async upstream detection**: on project activation `ProjectsLive.GitHub.maybe_check/1` spawns a supervised task resolving the repo's GitHub upstream (`EvoGit.RemoteNode.github_upstream/2` — `gh` CLI runs on the repo's node, local or remote). Top-bar button renders only for `%{state: :ok, owner, repo}`.
- **Issues modal** (`GitHubComponents.issues_modal/1`): `open`/`closed`/`all` filter, issue rows, loading/empty/error states; `error_message/1` surfaces `gh` CLI errors.
- **Fix flow**: per-row `github_fix_issue` fetches the issue Markdown, then starts an `:evolve` task like `task_submit` (`[path:, mode: "simple", objective: "Fix <title>\n\n<markdown>"]` + foreign_repos + selected model).

3. **JS hook** `UpdateStatus` in `app.js` — 30s-delayed startup check + 6h periodic, wraps `check_update`/`download_update`/`begin_update`.

**SystemLive Software Update card** (`system_live/update_card.ex`) — gated on `UpdateStatus.visible?(@current_node)` (hidden on dev server + remote nodes). ### Code Review Page — Node-Aware (SSH Remote Support)

The review page is fully node-aware — remote-node tasks are reviewable end-to-end:
- **Loading**: `ReviewLive.load_task_data/2` fetches via `NodeContext.get_task(@current_node, task_id)` (local + remote; nil on RPC failure → error state); async via `Task.Supervisor` + `:tasks_loaded_for` dedup guard; diffs are LAZY (per-file `load_file_diff` on select/expand events; `load_review_data/3` eager variant is dead in the dashboard).
- **All review ops routed through `EvoDash.NodeContext`** (node first): `load_review_data`, `load_review_metadata`, `load_review_metadata_from_shas`, `list_commits(_from_shas)`, `load_commit_files(_diff)`, `load_file_diff` (both arities), `list_branches`, `branch_exists?`, `default_merge_target`, `merge_branch` (both), `reject_branch`, `create_github_pr`, `set_review_status`/`set_review_metadata`, `check_merge`, `start_task` (Extract Skills / auto-resolve). RemoteNode returns VERBATIM underlying values — only transport failures add `{:error, {kind, reason}}`.
- **Merge + conflict**: Merge button in `ReviewComponents.Actions.action_buttons/1` (`phx-submit="merge"` + `target_branch` select); `handle_event("merge")` matches `{:ok, sha}` (→ `:merged` + navigate to `/projects`), `{:conflict, details}` (→ "Merge conflict! Please resolve manually." — raw git stdout truncated to 200 chars via `Helpers.truncate_string/2`), `{:error, reason}`. **Async merge check + auto-resolve**: `ReviewLive.MergeCheck` runs a non-mutating `check_merge/4` dry-run (`git merge-tree --write-tree`) after load; `%{state: :checking|:clean|:conflict|:error}` block above the merge form; `auto_resolve` (conflict state only) marks the task `:continued` and starts a new `:evolve` task with `[path:, mode: "simple", objective:, starting_commit:, merge_from: <task_id>, merge_target: <branch>]` — the core `MergeContext` runs the merge agent. Detail: `live/review_live/CONTEXT.md`.
- **SHAs**: base/end commits come from `TaskInfo.base_sha`/`commit_sha` + result map; persisted via `set_review_metadata`; post-merge/reject reloads from persisted SHAs.
- **Resume**: sets `:continued` and navigates to `/projects?resume_from=<id>&starting_commit=<sha>&project=<path>[&node=]`; `ProjectsLive` threads `:starting_commit`/`:resume_from` into `start_task(:evolve, ...)`; core `ResumeContext.apply_resume_context/3` prepends the previous-task context and overrides `starting_commit`.
- **Export node-aware** (`?node=` in `TaskExportController`); review button shows for remote tasks (`with_node_param`). Module sizes are deliberate: `review_live.ex` ~1120 lines, `node_context.ex` ~870 lines (per file-size policy). Tests + async-patterns inventory: `live/review_live/CONTEXT.md`.

### Multi-Repo Read-Write Foreign Repos (dashboard half)

The dashboard consumes the core's writable-foreign-repo feature (core contract: `apps/evo_git/CONTEXT.md` → "Multi-Repo Read-Write Foreign Repos"). One primary repo per task + foreign repos that may be **writable** (agents can modify them; changes tracked on `evogit-agent-*` branches, NEVER merged by the task — merge/reject happens on the review page). The task result carries a **`repos` map** (STRING keys): `%{repo_id => %{"commit_sha" => sha, "branch_name" => branch | nil}}` — `"primary"` always present (nil branch = no changes), writable foreign repos with commits present, read-only repos ABSENT. Top-level `commit_sha`/`branch_name` stay the PRIMARY's (backward compat); legacy tasks without `repos` render exactly as before.

- **Task form / settings editor** (ProjectsLive + ProjectComponents): the foreign-repo settings editor (project settings panel, `project_settings_body/1`) gained per-repo **writable** checkbox + optional **starting commit (`base_sha`)** input (SHA or branch name; blank = HEAD) on Add, plus **edit-in-place** (pencil → inline edit form for description/writable/base_sha/path) and a `badge-warning` "Writable" badge + `<code>` base_sha in the list rows. **Real validation** mirrors the core's up-front errors (existence → `File.dir?`/`NodeContext.dir?`; git-ness → `EvoGit.Adapters.Git.rev_parse` local / `NodeContext.list_branches` remote; base_sha resolvability → `rev_parse(path, base_sha)` local; remote base_sha is a documented skip — the core's task-start `ArgumentError` in `Runtime.Helpers.load_foreign_repos/2` is the safety net, landing the task `:failed` with a descriptive message). `do_task_submit/4` threads `foreign_repos` (structs with writable/base_sha) into task opts; `StatePersistence` round-trips the new fields; `maybe_restore_foreign_repos_from_task/2` restores them on resume. Genesis.toml loading stays description-only (the dashboard never writes genesis.toml). Detail: `live/projects_live/CONTEXT.md` + `components/CONTEXT.md`.
- **Review page — multi-repo** (`ReviewLive`): `LoadData` builds `@review_repos` (per-repo maps `%{repo_id, repo_path, branch_name, commit_sha, base_sha, branch_exists, review_data, commits, merge_targets, default_merge_target, merge_status}`, primary FIRST) from the result's `repos` + `opts[:foreign_repos]` normalized via `EvoGit.Core.ForeignRepo.normalize/1`; only repos with a non-nil branch_name get sections; legacy → single primary entry. **Per-repo tabs** (`repo_tabs/1`, shown only when >1 repo; `switch_repo` event; flat assigns = active-repo projection). Diffs stay LAZY per repo (`selected_file`/`expanded_files`/`file_context_levels` keyed `%{repo_id => ...}` on SHOW). **Merge/reject are broadcast**: `merge` calls `merge_branch` for EVERY repo (each into its own target) — all `{:ok,_}` → `:merged` + navigate; any conflict/error → per-repo `@merge_outcomes` panel (which merged / which conflicted + file list) and stays on page, never partially silent. Reject is symmetric. Per-repo async merge check (`MergeCheck` message is now a 6-tuple `{:merge_check_result, task_id, node, repo_id, target, result}`); `auto_resolve` stays primary-scoped (a foreign-repo conflict is surfaced per-repo, documented limitation). `create_pr`/`extract_skills`/`:commit` route + `review_status`/`set_review_metadata` stay primary-scoped. Test seams: `:review_merge_runner`/`:review_reject_runner` (resolved at call time, `:merge_check_runner` pattern). Detail: `live/review_live/CONTEXT.md`.
- **Resume/auto-resolve carry foreign repos**: core `ResumeContext.apply_resume_context/3` and `MergeContext.apply_merge_context/4` carry `:foreign_repos` from the previous task; the dashboard's existing resume (`resume_from`/`starting_commit`/`project` query params → `maybe_restore_foreign_repos_from_task`) and auto-resolve (`merge_from`/`merge_target`) opts suffice — confirmed by tests against core behavior.
- **TasksLive repo dimension** (`task_card_components.ex`): when a full TaskInfo's decoded result carries `repos`, the card renders a per-repo badge row (`result_repos/1` + `result_repos_badges/1` helpers — primary first, foreign sorted by id, short SHAs, "no changes" hint for nil primary branch) in the collapsed indicator, expanded detail view, and Full Result modal. Summary-map safe (`Map.get` guards); legacy results render nothing new. The summary projection is NOT extended (TasksLive uses the full paginated path).

## Constraints

- Depends on `:evo_git` at compile and runtime (persistence/registry code lives in `:evo_git`; evo_dash owns none).
- Runs on port 4100 in development, uses the Bandit adapter.
- Tailwind CSS 4 + DaisyUI (no Node.js toolchain); JS bundled by esbuild.
- Task state and recent projects persisted via SQLite (xqlite — Rust-based NIFs, precompiled for Win/macOS/Linux incl. ARM); no external DB server. Store + TaskRegistry are evo_git-owned (see `apps/evo_git/CONTEXT.md`).
- **Data-safety architecture**: TaskRegistry and Store `handle_*` callbacks have NO try/rescue — a Store failure crashes the GenServer and the supervisor restarts it (data safe in WAL mode). Serialization is `EvoGit.Store.Codec` (pure; total encode, raise-on-bad-decode). `safe_select_all_tasks/projects` SKIP corrupt rows with a `Logger.warning` (never raise; no quarantine — rows stay in the live table). `cleanup_expired_tasks` runs only on completion transitions / explicit clear / init; the completed task's `put_task` runs BEFORE cleanup so a mid-cleanup crash never loses it. **Lease & heartbeat**: running tasks carry `lease_expires_at` (renewed every 60s via `:heartbeat`); lease checking is **two-check, one-shot** (startup reconcile + one-shot `:lease_sweep` timer, NOT continuous); `Registry.lookup/2` finds task processes surviving a TaskRegistry restart (the Registry is a sibling under `:one_for_one`); a task is marked `:failed` only when the lease has genuinely expired (prevents a second BEAM instance from killing the first's running tasks). Detail: `apps/evo_git/CONTEXT.md`.
- **Supervision robustness**: `EvoDash.Application` uses `:one_for_one` with `max_restarts: 10, max_seconds: 60` so the Phoenix Endpoint survives a transient TaskRegistry restart.
- **`try/rescue` anti-pattern policy** (across the codebase):
  - LiveView config/core-value loading (`EvoGit.Config.*`, `EvoGit.AgentScheduler.*`): do NOT wrap in try/rescue swallowing to a default — let the LiveView crash truthfully (a visible crash beats a wrong default hiding a real bug).
  - JSON encoding: non-crashing `Jason.encode/1` with `case`, NOT `Jason.encode!` + try/rescue.
  - Atom conversion from untrusted input (DB strings, URL params): whitelist `Map.get/3` lookup, never `String.to_existing_atom/1` + rescue, never bare `String.to_atom/1` (atom-table exhaustion).
  - ETS existence checks: `:ets.info/1` (non-crashing), not rescue around `:ets.match/2`.
  - Acceptable try/rescue (rare; MUST carry a comment answering "expected error?" + "cleanest approach?"): GenServer `terminate/2`, deliberate data-recovery boundaries (Store skip-and-log decode), untrusted persisted data with no non-crashing variant, the Store's `ALTER TABLE DROP COLUMN` migration, and test-cleanup rescues in `on_exit`/teardown.
- Naming conventions: domain modules in `./lib/evo_dash/`, web modules in `./lib/evo_dash_web/`.
- Build: `mix assets.build` (esbuild + tailwind), `mix assets.deploy` (minified + digested).
- Desktop-mode gating: desktop-only code (`DesktopLifetime`, the update-status integration) lives in the frontend app by design so the `genesis_remote` (evo_git-only) release never ships it; gating env vars are `EVOGIT_DESKTOP` / `EVOGIT_LIFETIME_PORT` (see Desktop Mode below).

## Desktop Mode (Tauri Shell)

The backend is a **standalone web server** with no desktop-shell dependency (no `:desktop`). Desktop mode is provided externally by a **Tauri shell** (repo root `./desktop/`) that launches the backend as a sidecar process.

- **Directory picking is server-side** via `EvoDash.DirectoryPicker` (native tools, `:wx` fallback) — NOT Tauri and NOT the browser File System Access API. Flow: JS `DirectoryPicker` hook pushes `directory_pick` → `ProjectsLive` (local node only; remote/headless → `unavailable`) → picker GenServer runs the dialog → `picker_result:<picker_id>` pushed to the client. Remote nodes hide the Browse buttons entirely (the dialog is local-machine-only).
- **Codebase references**: NO `:desktop`/`Desktop.Window`/`desktop_port`/`is_desktop`/`?client=desktop`/`detect_desktop_client` anywhere. `EVOGIT_DESKTOP` IS referenced — by `EvoDash.UpdateStatus.desktop?/0` and by `EvoDash.DesktopLifetime`'s supervision gating. `:wx` is referenced ONLY by `EvoDash.DirectoryPicker` + its `Wx` seam — deliberately NOT an umbrella dep (dev/test degrade to the manual-entry fallback); the `genesis`/`genesis_desktop` releases load it via `wx: :load` in the root `mix.exs` (`genesis_remote` stays wx-free). Picker disabled via `config :evo_dash, :directory_picker, enabled: false`.
- **Desktop tray quit confirm dialog**: tray "Quit Genesis" → Rust emits `quit-requested` → the `DesktopQuit` JS hook pushes `desktop_quit_requested` → the `EvoDashWeb.LiveHooks.DesktopQuit` on-mount hook shows a confirm dialog on ANY page (via the shared `Layouts.app`) → confirm runs graceful `System.stop(0)` through the `:desktop_quit_stop_fun` seam (default 150ms-delayed stop; NO force quit, no timeout — the tray handler re-emits and waits indefinitely). Detail: `live_hooks/CONTEXT.md` + `desktop/CONTEXT.md`.
- **Static assets** (`priv/static/`): `favicon.ico` + `images/favicon.svg` are DERIVED from `images/logo.svg` (source of truth; dark gray `#373435` + red `#C8383C`, aspect ≈ 1.2334); `images/logo-alt.svg` is the dark-theme variant (referenced directly); `robots.txt` (commented-out directives). Regeneration recipe (inkscape PNG loop → ICO combine → square-fit favicon.svg `translate`): `assets/CONTEXT.md` → "Static Assets".
- **Release configuration** (owned by the ROOT `mix.exs` / `./CONTEXT.md` — this app has no `rel/`): umbrella releases `genesis` (both apps), `genesis_desktop` (bakes `evo_dash: [desktop_release: true]`, bundled as a Tauri resource), `genesis_remote` (evo_git-only headless daemon, wx-free). `config/runtime.exs` handles `PHX_SERVER=true`; production needs `SECRET_KEY_BASE` + `PHX_HOST`. The Tauri shell packages the backend as a sidecar.

## Internationalization (i18n)

EvoDash uses **Gettext** (`EvoDashWeb.Gettext`, `use Gettext, otp_app: :evo_dash`; imported via `html_helpers/0` in `evo_dash_web.ex`). All user-facing strings in LiveViews/components/helpers/templates are `gettext`-wrapped. The CLI (`:evo_git`) is deliberately NOT internationalized.

**Development policy** (per root `./CONTEXT.md` → "Internationalization (i18n) Development Policy"): do NOT run `mix gettext.extract`/`merge`/`translate` during feature work — POT/PO files and translations are maintained centrally and updated ONCE per release (`mix gettext.extract` → `mix gettext.merge` → `mix translate apps/evo_dash/priv/gettext/default.pot all`, AI-powered). Just write gettext-wrapped strings; when a string's meaning needs anchoring for the release-time AI translator, write a **Chinese comment** next to the `gettext` call — that is the ONLY i18n work expected during development. Dynamic locale: `root.html.heex` uses `Gettext.get_locale(EvoDashWeb.Gettext)` for the `<html lang>` attribute.
