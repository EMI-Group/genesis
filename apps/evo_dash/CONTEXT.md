# EvoDash — Phoenix LiveView Dashboard

## Intent

EvoDash is the web dashboard for the EvoGit umbrella project: a project-based real-time browser interface for launching and monitoring EvoGit tasks (genesis / evolve), inspecting the agent tree hierarchy, viewing task logs, managing runtime scheduler settings, editing user configuration, and managing per-project settings including foreign repositories — powered by Phoenix LiveView.

Users open a Project (a Git repository path), and the dashboard auto-detects the appropriate task mode. Multiple projects can be open simultaneously with tab-based navigation. This is a Phoenix 1.8 umbrella child app (`:evo_dash`) that depends on the sibling `:evo_git` application.

### Multi-Model LLM Support

The dashboard supports the core's multi-model architecture (`[[llm.models]]` array-of-tables config). Every model profile has its own id, model, concurrency, and gen params (temperature, reasoning_effort, max_tokens, top_p, top_k, frequency_penalty, presence_penalty) plus optional peak/off-peak fields (`peak_concurrency`, `peak_hours`, `timezone`, `off_peak_days` — profile-level all-day off-peak days) and per-`peak_hours`-window optional `days`.

- **Model profiles editor** (Settings LLM category) — `SettingsLive` + `SettingsComponents.model_profiles_editor/1` + support modules `ModelProfileHelpers`/`ModelProfileEvents`. Events: `add_model_profile`, `edit_model_profile`, `save_model_profile`, `delete_model_profile`, `cancel_edit_model_profile`, `model_profile_form_change`, `add_peak_hours_row`, `remove_peak_hours_row`. Duplicate ids rejected. **Peak/off-peak serialization contract**: absent/empty keys are OMITTED from the profile so TOML omits them (never nil/`[]`); `peak_concurrency = 0` is a valid hard pause; timezone blank = server local time; `off_peak_days` (list of `mon|tue|wed|thu|fri|sat|sun` + keywords `weekdays`/`weekends`) = the profile is off-peak the ENTIRE day on those days (normal `concurrency` applies 24/7, all `peak_hours` windows suppressed, `peak_concurrency` incl. hard-pause 0 never applies); each `peak_hours` window may carry an optional `days` key (same vocabulary) restricting the window to those days — absent = every day (backward compatible). The editor renders an "Off-peak days" chip group (7 days + 2 keywords) on the profile edit form and a per-window "Days" chip row; day values are normalized (trim + downcase + vocabulary MapSet filter, order-preserving uniq) with NO dashboard-side validation (the core owns it) — normalization flows through the single shared public `ModelProfileHelpers.normalize_days/1` (TOTAL: a bare binary — Plug's single-checked-chip collapse of a repeated param — is `List.wrap`-ed, `""` seed entries dropped, odd shapes → `[]`) at EVERY consumption point (draft builder, save parsing, template pre-fill), so the chip membership render can never hit a non-list value. **Draft-tracking**: the edit form's `phx-change="model_profile_form_change"` stores the whole form as a `:profile_form_draft` assign (peak_hours + off_peak_days normalized at the boundary) so the add/remove peak-hour row buttons never wipe unsaved typing (phx-click does not submit the enclosing form). Full detail: `live/settings_live/CONTEXT.md` → "Peak/Off-Peak Hour Concurrency".
- **LLM category layout**: Quick Setup + Model Profiles editor + Connection Test render OUTSIDE the `save_category` form (no nested-form HTML); only `compression_threshold_tokens` (the one flat global card) + Save sit inside the form. `params_to_category_config/3` skips `:model_profiles`-type schemas so the generic category save never clobbers the models list. `select_llm_model_shortcut`/`save_custom_model` ADD a profile to the list.
- **Runtime update**: `update_runtime_from_file_config/2` pushes `:model_profiles` (via `Schema.model_profiles/1`) + scheduler concurrency keys to `EvoGit.AgentScheduler.update_config/1` (local only — remote saves use `reload_remote_config`).
- **Per-task agent + model selection** (ProjectsLive + `TaskFormComponents.task_form/1`) — a single shared card (`grid grid-cols-1 lg:grid-cols-2`): **Agent select** (only when `@custom_agents != []`; "Auto (recommended)" + custom agents from `EvoGit.CustomAgents.list/0`; selection threads `:agent => id`, persists via `StatePersistence` `selected_agent_id`); **Custom Agent mode** (4th task mode → `{:evolve, "custom"}` with the selected agent as REQUIRED `:agent`; auto-selects first agent; violet accent); **Model select** ("Auto (by rules)" first when a model-selection script is configured). Threading contract in `task_submit`: a specific profile → `:model_id => id` AND `:model_id_locked => true` (set UNCONDITIONALLY — an explicit choice always defers the model-selection script); "Auto (by rules)"/nil/"" → NEITHER key (script or default decides). No `build_common_runtime_opts/3` exists — opts are built inline. Detail: `components/CONTEXT.md` (Task Form section) + `live/projects_live/CONTEXT.md`.
- Welcome modal gate: `show_welcome` checks `model_profiles == []`. System page example-config/FAQ use the `[[llm.models]]` format.

### Custom Tools (Settings → Agents)

Users define custom tool modules by dropping `.ex`/`.exs`/`.beam` files into `<config_dir>/tools/` (per-node directory, next to `config.toml`; core: `apps/evo_git/lib/evo_git/custom_tools/CONTEXT.md`).
A custom agent's `tools = [...]` whitelist in `agents.toml` accepts built-in names OR custom tool names, and the dashboard surfaces the loader status in the Settings `:agents` category.

- **RPC**: `EvoDash.NodeContext.custom_tools_status/1` — node-first thin pass-through to `EvoGit.RemoteNode.custom_tools_status/1` (local → direct call; remote → `:erpc`).
  It returns the status map VERBATIM on success (`%{ok: [%{name: String.t(), file: String.t(), module: module(), read_only?: boolean()}], errors: [%{file: String.t(), reason: String.t()}]}`) and `{:error, term()}` on remote RPC failure — deliberately NOT swallowed into an empty map, so a real RPC/backend problem stays visible.
- **Async load**: `EvoDashWeb.SettingsLive.NodeData.fetch_custom_tools_status/1` is the sole normalizer (status map → atom-keyed with list values; `{:error, reason}` preserved; any odd shape → `%{ok: [], errors: []}`), carried in the NodeData results map under `:custom_tools_status` in BOTH the success map and the failure funnel.
  `apply_node_data_results/3` reads it tolerantly (`Map.get/3` default) so results maps built without the key still render the empty state.
- **Assigns / events**: `@custom_tools_status` (default `%{ok: [], errors: []}`) + `@custom_tools_loading` (default false); mount seeds locally via `SettingsLive.load_custom_tools_data/1`.
  `reload_custom_tools` → `SettingsLive.refresh_custom_tools/1`, a supervised `EvoDash.TaskSupervisor` fetch (never inline in the LiveView) that reports `{:custom_tools_loaded, requested_node, result}` — node stale-guarded, always clears loading, NO polling; it is also triggered by the four custom-agent mutation flows in `CustomAgentEvents`.
- **Panel**: `EvoDashWeb.SettingsComponents.CustomToolsPanel.custom_tools_panel/1` (`components/settings_components/custom_tools_panel.ex`) — a read-only card in the `:agents` category between the custom-agents editor and the model-selection editor.
  It renders a Refresh button, the `ok[]` rows (name, module, file + a `Read-only` ghost badge vs a `Write` warning badge from `read_only?`), the `errors[]` rows (file + reason, error-tinted), a dashed empty state for a READABLE empty status, and a "Custom Tools Unavailable" banner for `{:error, reason}` — the banner and the empty state are MUTUALLY EXCLUSIVE.
  All reads are total (atom-or-string keys, non-list → `[]`, non-map entries dropped, no `try/rescue`); its public pure `custom_tool_names/1` is the single source of the loaded tool names.
- **Tools whitelist chips**: `custom_agents_editor/1` declares `attr :custom_tool_names` — the loaded names render as an ADDITIONAL visually-distinct chip group using the SAME `tools[]` checkbox markup, so the save path and `save_custom_agent` parsing are unchanged (names colliding with a built-in are dropped).
  A UI-only amber warning lists any selected tool that matches neither a built-in nor a loaded custom tool; the `agents.toml` store stays lenient (the core's `:invalid_tools` semantics are untouched — no dashboard-side validation).
- **Tests**: `test/evo_dash_web/live/settings_live_agents_test.exs` (`describe "custom tools panel"`), `test/evo_dash_web/components/custom_tools_panel_test.exs` + `custom_agents_editor_test.exs`, `test/evo_dash/node_context_test.exs` (see the test-tree CONTEXT.md files for injection shapes and gotchas).
- Detail: `lib/evo_dash/CONTEXT.md` (NodeContext wrapper), `lib/evo_dash_web/live/settings_live/CONTEXT.md` (assigns/events/async contract), `lib/evo_dash_web/components/CONTEXT.md` + `components/settings_components/CONTEXT.md` (panel + editor chips).

### SSH Remote Development — Node-Aware Dashboard

The dashboard controls a remote headless `genesis_remote` daemon over Erlang distribution via an SSH tunnel. Three layers: `EvoDash.NodeContext` (thin client, `lib/evo_dash/node_context.ex`), `EvoDashWeb.LiveHooks.NodeAware` (on-mount hook: node-context assigns, `?node=` resolution, unified sidebar Active-Tasks loader, connection-status handling with push_patch on local↔remote transitions), and `EvoDashWeb.NodeSelectorComponent` (navbar node selector + connection-manager modal, auto-connect on select).

- **URL threading**: ALL nav links carry `?node=<target_id>` when a remote node is selected (`with_node_param/2` in `layouts.ex`; ⚠️ appends with `?`, so query-string URLs must use a manual `&node=` suffix — see `lib/evo_dash_web/CONTEXT.md`).
- **Data access**: every NODE-AWARE load routes through `EvoDash.NodeContext` (local direct call, remote `:erpc`); all node-aware page loads run in `EvoDash.TaskSupervisor` children outside the LiveView process with stale-guards; **no polling anywhere** — fully push-based via cluster-aware `EvoGit.PubSub` (PG2/`:pg`).
- **Persistence consumption (read-only)**: evo_dash has **ZERO `EvoGit.Store` references in production code** (comment/doc mentions only, e.g. `task_card_components.ex:723`; test-support `IsolatedTaskStore` uses it for test isolation). It reads tasks via three routes: (1) `EvoDash.NodeContext` → `EvoGit.RemoteNode` (local `apply` / remote `:erpc` → `EvoGit.AgentScheduler.RemoteAPI` → `EvoGit.TaskRegistry`) — TasksLive `list_tasks_paginated` (FULL `%TaskInfo{}`), ReviewLive/HomeLive/export `get_task`; (2) **deliberate local-only `EvoGit.TaskRegistry` shortcuts** (no NodeContext): the unified sidebar loader `live_hooks/node_aware.ex:219` (`list_tasks_summary/1` — 16-key SUMMARY map, no `result`/`usage`/`logs`/`archive_metadata`; `updated_at` is in the projection but NO evo_dash code reads it), `controllers/task_export_controller.ex:52-53` (`get_task/1`), the ProjectsLive family (`projects_live.ex`, `assigns.ex:26`, `async_load.ex:198`, `project_flow.ex`, `github.ex:313` — recent projects / notifications / local `start_task`), and `system_live/update_card.ex:106,117` (cancel/force-kill, desktop+local gated); (3) `list_task_ids` minimal projection (`id, status, updated_at`). Full inventory: `lib/evo_dash/CONTEXT.md` + `live/CONTEXT.md` + `live_hooks/CONTEXT.md`.
- evo_dash owns **no SQLite/Ecto/xqlite of its own** (mix.exs deps have none; `EvoDash.Application` starts no persistence children — Store/TaskRegistry are `EvoGit.Application` children).
- **Per-page remote behavior**: SettingsLive (editable remote config, saves via `save_user_config` + `reload_remote_config`; `get_resolved_config` full-config round-trip), SystemLive (pause/resume + restart/stop via RPC; software-update + source cards hidden on remote), ProjectsLive (remote view shows the remote node's task form; remote projects read-only), TasksLive (full remote task list via RPC, same push-based reload path). AgentsLive is fully async + push-driven with `HistoryGate` (skip refetch when `:message_count` unchanged) + `ThresholdCache` (30s freshness per node). Detail: `lib/evo_dash_web/CONTEXT.md` ("SSH Remote UX" + node-locking) + `live_hooks/CONTEXT.md` + `live/agents_live/CONTEXT.md`.
- Graceful degradation: lifecycle calls return safe fallbacks when `EvoGit.RemoteConnection` is unavailable; the node selector renders "Local" by default.

### Push-based event contract (node-identity PubSub)

The dashboard is fully push-based — no periodic polling. `:evo_git` broadcasts enriched events on `EvoGit.PubSub`; every event carries the **BEAM node atom of the publisher**. **Node-filtering rule**: an event only triggers UI updates when its `node` matches the viewed node — `EvoDashWeb.LiveHooks.NodeAware.event_from_current_node?/2` (event node vs `socket.assigns.current_node`). Consumers: NodeAware, AgentsLive, TasksLive, ReviewLive, SystemLive, SettingsLive, ProjectsLive. `{:task_updated, ...}` / `{:task_deleted, ...}` flow through `NodeAware.handle_task_info/2` (300ms trailing-edge debounce → `:node_aware_reload_tasks`).

|-------|--------|-----------|
| `"tasks"` | `{:task_updated, task_id, status, node}` (status `:pending\|:running\|:finalizing\|:cancelling\|:completed\|:failed\|:cancelled` or `nil` for review-only mutations); `{:task_deleted, task_id, node}` | NodeAware (debounced sidebar + reloads), TasksLive, ProjectsLive, ReviewLive, AgentsLive, SettingsLive, SystemLive |

### Task Archive Feature

When a task is started with the **archive** checkbox, the core collects per-agent metadata (`archive_records`) and EvoDash persists it in `EvoGit.TaskInfo.archive_metadata` (`[map()] | nil`, backfill-safe). Archived tasks show the agent parent-child tree (per-agent objective/return/start-end commits/token usage/archive refs) and provide JSON export. Opt-in only — no archive sections render when disabled.

- **Threading**: `:archive` opt (built inline in `ProjectsLive.do_task_submit/4`) → core; on completion `archive_records` extracted from the result map → `update_task_status/4` → persisted.
- **Mode resolution**: UI combined-mode strings `"genesis_new"`/`"genesis_existing"`/`"evolve_simple"`/`"custom_agent"` → `{task_type, core_mode_string}` in `do_task_submit/4` (`{:genesis, "new"\|"existing"}`, `{:evolve, "simple"\|"custom"}`; unknown strings fall back to `{:evolve, "simple"}`). Core `RuntimeOpts.mode_atom/2` accepts `"custom"` for evolution; unknown evolution modes raise `ArgumentError`; `:genesis` + `"custom"` raises "custom mode is evolve-only".
- **JSON export**: `GET /tasks/:task_id/export` → `TaskExportController` (normalizes structs to plain maps).
- Archive UI render sites + known gotchas (crashed agents absent from metadata): `lib/evo_dash_web/CONTEXT.md` → "Known Issues — Task Archive Display".

### Self-Reflective Task Mode & Guide Overlay

- **`:reflect` task mode** — repo-less conversational task type whose ONLY dashboard entry point is the **Home chat page** (`HomeLive` at `GET /help`); the Projects task form offers no reflect mode. Reflect tasks carry NO `:path`, run with nil `project_path` (task cards are nil-path-safe), and their result is the agent's final text (`{:ok, %{result: <text>, commit_sha: nil, branch_name: nil, tag: nil}}`). `:reflect` is in `Store.Codec` `@known_atoms`; `execute_task(:reflect)` routes directly to `Runtime.SelfReflective.run`, bypassing `build_common_runtime_opts` (which `Keyword.fetch!(:path)`-raises). Core detail: `apps/evo_git/CONTEXT.md`; dashboard: `live/home_live/CONTEXT.md`.
- **Guide overlay** — global floating UI through which a running reflective agent guides the user. Core broadcasts on `"guides"`; consumed by `EvoDashWeb.LiveHooks.Guide` (registered LAST in `live_view/0`): node-filters, assigns `@guide`, persists per-tab via `guide_client_id` (`:persistent_term`), pushes `"guide_highlight"` (`%{selector}`). `Layouts.app` renders the floating panel (`fixed top-4 right-4 z-50`); the `Guide` JS hook scrolls + applies `.guide-highlight` (~3s). Detail: `live_hooks/CONTEXT.md` + `assets/CONTEXT.md`.

### Home Chat Page (`HomeLive` at `GET /help`)

ChatGPT-style chat wired to the self-reflective agent — the ONLY entry for `:reflect` tasks; sidebar **Help** nav entry; renders through `Layouts.app` with `current_page={:help}`. Send flow: `Transcript.build_preamble/1` (conversation memory — last 8 exchanges, 600 chars/entry, 4000-char cap) + message → `EvoDash.NodeContext.start_task(node, :reflect, mode: "reflect", objective: ...)` with NO `:path`. ### Config-Status Warning Surfaces (no-LLM-model warnings) & Reload Semantics

The dashboard has THREE different notions of "LLM model configured", which can visibly diverge (a user whose model works can still see "Missing Configuration" warnings):

1. **Core `EvoGit.Config.config_status/0`** (`apps/evo_git/lib/evo_git/config/config.ex:619-663`, message "LLM model is not configured. Set [llm] model in config.toml.") — requires at least one resolved profile whose `:model` is a NON-EMPTY BINARY (`is_binary(m) and m != ""`); a ReqLLM map-form `:model` spec (with `base_url`/`extra`, produced by `model_profile_helpers.ex:250-255` for OpenAI-compatible endpoints) fails this check although the schema, editor dropdowns, scheduler, and connection test all accept it — known divergence, recorded in `apps/evo_git/lib/evo_git/config/CONTEXT.md`.
2. **Global layout toast** (`components/layouts.ex:299-328`) — fixed bottom-right, rendered on EVERY page when `@config_status && not @config_status.ok?`, listing `config_status.warnings`; the `config_status` assign is seeded per-page and NO page re-runs it on config-save events, so it goes STALE after a Settings save until a full page remount (refresh / reconnect / node switch re-running the loader).
3. **Settings page banners** (`live/settings_live.ex`) — amber "Missing Configuration" (41-61, same `config_status.ok?`); red "Remote Configuration Unavailable" (67-79, `@remote_config_error` truthy, suppresses the next box); red "No LLM Model Configured" (84-107) which checks ONLY list presence of `get_in(@file_config, [:llm, :models])` — it can be silent while config_status still warns (map-form model) and vice versa.

Per-page `config_status` assignment (see child CONTEXT.md files): projects_live (mount-deferred `:load_config_status` → LOCAL `EvoGit.Config.config_status()` at :1825-1831), tasks_live (:469 local), review_live (:242 local), agents_live (`LoadData.node_config_status/1` load_data.ex:170-176 — node-aware, but the refresh path drops config_status), system_live (async `safe_system_checks` :1513-1517 — REMOTE status correctly fetched via `get_remote_config_status(node)`; only refreshed by manual `rerun_checks`), settings_live (node-aware via `NodeData`), home_live + welcome_live + welcome_complete_live (no `config_status` attr passed → no toast on /help or /welcome).
projects/tasks/review compute the LOCAL machine's config_status ONCE at mount BEFORE `?node=` resolution, so a page viewing a REMOTE node shows the LOCAL config's health (mismatch: the remote may be configured while the local machine is not, or vice versa); agents/system/settings are node-correct.

## Constraints

- Depends on `:evo_git` at compile and runtime (persistence/registry code lives in `:evo_git`; evo_dash owns none).
- Runs on port 4100 in development, uses the Bandit adapter.
- Tailwind CSS 4 + DaisyUI (no Node.js toolchain); JS bundled by esbuild.
- Task state and recent projects persisted via SQLite (xqlite — Rust-based NIFs, precompiled for Win/macOS/Linux incl. ARM); no external DB server. Store + TaskRegistry are evo_git-owned (see `apps/evo_git/CONTEXT.md`).
- **Data-safety architecture**: TaskRegistry and Store `handle_*` callbacks have NO try/rescue — a Store failure crashes the GenServer and the supervisor restarts it (data safe in WAL mode). Serialization is `EvoGit.Store.Codec` (pure; total encode, raise-on-bad-decode). `safe_select_all_tasks/projects` SKIP corrupt rows with a `Logger.warning` (never raise; no quarantine — rows stay in the live table). `cleanup_expired_tasks` runs only on completion transitions / explicit clear / init; the completed task's `put_task` runs BEFORE cleanup so a mid-cleanup crash never loses it. **Lease & heartbeat**: running tasks carry `lease_expires_at` (renewed every 60s via `:heartbeat`); lease checking is **two-check, one-shot** (startup reconcile + one-shot `:lease_sweep` timer, NOT continuous); `Registry.lookup/2` finds task processes surviving a TaskRegistry restart (the Registry is a sibling under `:one_for_one`); a task is marked `:failed` only when the lease has genuinely expired (prevents a second BEAM instance from killing the first's running tasks). Detail: `apps/evo_git/CONTEXT.md`.
- **Supervision robustness**: `EvoDash.Application` uses `:one_for_one` with `max_restarts: 10, max_seconds: 60` so the Phoenix Endpoint survives a transient TaskRegistry restart.
- **`try/rescue` anti-pattern policy** (across the codebase):
  - LiveView config/core-value loading (`EvoGit.Config.*`, `EvoGit.AgentScheduler.*`): do NOT wrap in try/rescue swallowing to a default — let the LiveView crash truthfully (a visible crash beats a wrong default hiding a real bug).
  - JSON encoding: non-crashing `Jason.encode/1` with `case`, NOT `Jason.encode!` + try/rescue.
  - Atom conversion from untrusted input (DB strings, URL params): whitelist `Map.get/3` lookup, never `String.to_existing_atom/1` + rescue, never bare `String.to_atom/1` (atom-table exhaustion).
  - ETS existence checks: `:ets.info/1` (non-crashing), not rescue around `:ets.match/2`.
  - Acceptable try/rescue (rare; MUST carry a comment answering "expected error?" + "cleanest approach?"): GenServer `terminate/2`, deliberate data-recovery boundaries (Store skip-and-log decode), untrusted persisted data with no non-crashing variant, the Store's `ALTER TABLE DROP COLUMN` migration, and test-cleanup rescues in `on_exit`/teardown.
- Naming conventions: domain modules in `./lib/evo_dash/`, web modules in `./lib/evo_dash_web/`.
- Build: `mix assets.build` (esbuild + tailwind), `mix assets.deploy` (minified + digested).
- Desktop-mode gating: desktop-only code (`DesktopLifetime`, the update-status integration) lives in the frontend app by design so the `genesis_remote` (evo_git-only) release never ships it; gating env vars are `EVOGIT_DESKTOP` / `EVOGIT_LIFETIME_PORT` (see Desktop Mode below).

## Desktop Mode (Tauri Shell)

The backend is a **standalone web server** with no desktop-shell dependency (no `:desktop`). Desktop mode is provided externally by a **Tauri shell** (repo root `./desktop/`) that launches the backend as a sidecar process.

- **Directory picking is server-side** via `EvoDash.DirectoryPicker` (native tools, `:wx` fallback) — NOT Tauri and NOT the browser File System Access API. Flow: JS `DirectoryPicker` hook pushes `directory_pick` → `ProjectsLive` (local node only; remote/headless → `unavailable`) → picker GenServer runs the dialog → `picker_result:<picker_id>` pushed to the client. - **Codebase references**: NO `:desktop`/`Desktop.Window`/`desktop_port`/`is_desktop`/`?client=desktop`/`detect_desktop_client` anywhere. `EVOGIT_DESKTOP` IS referenced — by `EvoDash.UpdateStatus.desktop?/0` and by `EvoDash.DesktopLifetime`'s supervision gating. `:wx` is referenced ONLY by `EvoDash.DirectoryPicker` + its `Wx` seam — deliberately NOT an umbrella dep (dev/test degrade to the manual-entry fallback); the `genesis`/`genesis_desktop` releases load it via `wx: :load` in the root `mix.exs` (`genesis_remote` stays wx-free). ## Internationalization (i18n)

EvoDash uses **Gettext** (`EvoDashWeb.Gettext`, `use Gettext, otp_app: :evo_dash`; imported via `html_helpers/0` in `evo_dash_web.ex`). All user-facing strings in LiveViews/components/helpers/templates are `gettext`-wrapped. The CLI (`:evo_git`) is deliberately NOT internationalized.

**Compile-time**: the `EvoDashWeb.Gettext` backend is deliberately declared with `split_module_by: [:locale, :domain]` (`lib/evo_dash_web/gettext.ex`) — Gettext then emits one small `EvoDashWeb.Gettext.T_<locale>_<domain>` module per locale (compiled in parallel) instead of a single ~16k-clause module, which otherwise dominates every evo_dash recompile. Keep this option; the public API and every `use Gettext, backend: EvoDashWeb.Gettext` site are unchanged.

**Development policy** (per root `./CONTEXT.md` → "Internationalization (i18n) Development Policy"): do NOT run `mix gettext.extract`/`merge`/`translate` during feature work — POT/PO files and translations are maintained centrally and updated ONCE per release (`mix gettext.extract` → `mix gettext.merge` → `mix translate apps/evo_dash/priv/gettext/default.pot all`, AI-powered). Just write gettext-wrapped strings; when a string's meaning needs anchoring for the release-time AI translator, write a **Chinese comment** next to the `gettext` call — that is the ONLY i18n work expected during development. Dynamic locale: `root.html.heex` uses `Gettext.get_locale(EvoDashWeb.Gettext)` for the `<html lang>` attribute.

**Product-name convention**: the product brand "EvoX Genesis" (company EvoX, product 启元 Genesis) renders localized in CJK locales — zh_CN 天演 · 启元 / zh_HK 天演 · 啟元 / ja 啓元 (EvoX stays Latin in ja). The ja rendering 啓元 is encoded in the `mix translate` ja glossary (`lib/mix/tasks/translate.ex`, `"Genesis" => "啓元"` / `"EvoX Genesis" => "EvoX 啓元"`) and applied in `priv/gettext/ja/LC_MESSAGES/default.po` msgstrs (the `Co-authored-by: Genesis <noreply@evogit.ai>` git-trailer literal inside the one config-description msgstr stays ASCII and must NOT be renamed). Keep these in sync whenever the brand name or glossary changes.

## Research Notes — ReqLLM-Native Multimodal (Image/Audio) File Attachments (survey addendum)

Refines the "ReqLLM-native file attachment alternative" discussion of the root `./CONTEXT.md` research note ("Research Notes: PDF/DOCX → Plain Text Extraction", which routes detail here); the plain-text pipeline (`EvoDash.AttachedFile.read/1` + `ex_pdf`) is unchanged, and image/audio attachments are additionally implemented as server-side-staged raw-binary content parts (`EvoDash.AttachedFile.read_kind/2` — image/audio kinds, extension allowlist, 15 MiB per-file cap) staged into the Projects page's `:staged_attachments` assign and submitted as the `:attachments` task opt (base64 `"data"`, string-keyed maps; contract + lifecycle: `lib/evo_dash/CONTEXT.md` + `lib/evo_dash_web/live/projects_live/CONTEXT.md`).
Survey facts below are current as of the vendored `:req_llm` v1.22.0 and `:llm_db` deps (`./deps/req_llm/`, `./deps/llm_db/`).
`ReqLLM.Message.ContentPart` types are `:text | :image_url | :video_url | :image | :file | :thinking`; there is no canonical `input_image`/`input_audio` chat-part type, those names exist only at the provider wire level.
Images ride in `:image` (inline bytes), `:image_url`, or `:file` parts, where `:file` carries raw bytes or a provider-uploaded `file_id`/`owned_file_id` reference.
Audio in chat is a `:file` part with an `audio/*` media_type, which is practically OpenRouter-only (mp3/wav encode to `input_audio`; other audio raises).
Audio otherwise lives on separate endpoints: `ReqLLM.transcribe/3` (multipart STT), `ReqLLM.speak/3` (TTS), and the experimental `ReqLLM.OpenAI.Realtime` websocket; OpenAI `modalities: ["audio"]` is output-only.
Wire translation is per-provider adapter at encode time: the OpenAI-compatible flock (deepseek/qwen/zai/alibaba/groq/mistral/venice/...) encodes ANY raw `:file` bytes as an `image_url` data-URI (`deps/req_llm/lib/req_llm/provider/defaults.ex:1055-1072`), so the older root claim about DeepSeek/Qwen mis-encoding is confirmed.
OpenAI Chat gating rejects non-image `:file` parts first, while OpenAI Responses accepts image + pdf only.
Anthropic maps `:file` to image/document base64 blocks; Google Gemini `inlineData`/`fileData` carries arbitrary mime (image + audio + video + pdf).
OpenRouter handles image + pdf + mp3/wav audio; Bedrock Converse is image-only-inline (drops `:image_url` and audio).
Provider capability truth lives in `:llm_db`: `LLMDB.model/2` → `%LLMDB.Model{modalities: %{input: [...]}}` from `./deps/llm_db/priv/llm_db/snapshot.json`, and there is no convenience "accepts image?" helper, so read `.modalities.input`.
The codec path AND the llm_db modality must BOTH be checked, since a model may claim audio while its codec cannot ship it.
llm_db audio-input model counts are google 19, openrouter 72, google_vertex 16, alibaba 13, alibaba_cn 6, etc.; image input is near-universal (deepseek-v4-flash-vision-exp, gemini-3.5-flash, claude-sonnet-4-6, gpt-5.4, grok-4.5 all carry `image`).
Given `EvoGit.Config.LLMCatalog` (provider cards: anthropic/openai/google/deepseek/zai/alibaba/minimax/moonshotai/xai/openrouter/openai_compatible), the practically reachable multimodal-capable set is anthropic (image), openai (image + pdf via Responses), google (image + audio + video + pdf), deepseek-v4-flash-vision-exp (image), plus openrouter (image + pdf + mp3/wav audio).
