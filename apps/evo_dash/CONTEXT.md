# EvoDash — Phoenix LiveView Dashboard

## Intent

EvoDash is the web dashboard for the EvoGit umbrella project — a project-based real-time Phoenix LiveView interface for launching and monitoring EvoGit tasks (genesis / evolve), inspecting the agent tree hierarchy, viewing task logs, managing runtime scheduler settings, editing user configuration, and managing per-project settings including foreign repositories.

Users open a Project (a Git repository path) and the dashboard auto-detects the appropriate task mode; multiple projects can be open simultaneously with tab-based navigation. This is a Phoenix 1.8 umbrella child app (`:evo_dash`) that depends on the sibling `:evo_git` application.

### Multi-Model LLM Support

The dashboard supports the core's `[[llm.models]]` profile array: per profile id, model, concurrency, gen params, optional `context_window` (blank = core default 200000) and optional peak/off-peak fields (`peak_concurrency`, `peak_hours`, `timezone`, `off_peak_days`, per-window `days`). Absent/empty peak keys are OMITTED from the profile so TOML omits them; `peak_concurrency = 0` is a valid hard pause.

- **Model profiles editor** (Settings LLM category) — `SettingsComponents.model_profiles_editor/1` + `ModelProfileHelpers`/`ModelProfileEvents`; duplicate ids rejected; day values normalize through the TOTAL `ModelProfileHelpers.normalize_days/1` at every consumption point; the edit form keeps unsaved input in a `:profile_form_draft` assign so peak-row add/remove never wipes typing. Detail: `live/settings_live/CONTEXT.md`.
- **LLM category layout** — Quick Setup + editor + Connection Test render OUTSIDE the `save_category` form; the flat `[llm]` cards are DATA-DRIVEN from `EvoGit.Config.Schema.schemas_by_category/0` (`flat_llm_schemas/1`), so `compression_threshold_tokens`, `tool_result_pruning` and `tool_result_pruning_target_fraction` need no dashboard code. `update_runtime_from_file_config/2` pushes `:model_profiles` + concurrency keys to `EvoGit.AgentScheduler.update_config/1` (local only; remote saves use `reload_remote_config`).
- **Per-task agent + model selection** (ProjectsLive + `TaskFormComponents.task_form/1`) — one card: Agent select (only when `@custom_agents != []`), Custom Agent mode (4th task mode → `{:evolve, "custom"}`, `:agent` REQUIRED), Model select ("Auto (by rules)" first when a model-selection script exists). An explicit profile threads `:model_id` + `:model_id_locked => true` unconditionally; "Auto (by rules)"/nil/"" → neither key. Detail: `components/CONTEXT.md` (Task Form) + `live/projects_live/CONTEXT.md`; the System-page example config and FAQ use the `[[llm.models]]` format.

### Custom Tools (Settings → Agents)

Users define custom LLM-callable tools by dropping `.ex`/`.exs`/`.beam` files into `<config_dir>/tools/` (per-node, next to `config.toml`; core: `apps/evo_git/lib/evo_git/custom_tools/CONTEXT.md`); a custom agent's `tools = [...]` whitelist accepts built-in or custom names, surfaced in the Settings `:agents` category.

- **Contract**: `NodeContext.custom_tools_status/1` passes through to `EvoGit.RemoteNode.custom_tools_status/1`, returning the status map VERBATIM (`%{ok: [%{name:, file:, module:, read_only?:}], errors: [%{file:, reason:}]}`) or `{:error, term()}` — never swallowed; `SettingsLive.NodeData.fetch_custom_tools_status/1` is the sole normalizer, and `reload_custom_tools` → `SettingsLive.refresh_custom_tools/1` runs in `EvoDash.TaskSupervisor` (node stale-guarded, no polling, also triggered by the custom-agent mutations).
- **Presentation**: `SettingsComponents.CustomToolsPanel.custom_tools_panel/1` is a read-only card (Refresh, `ok[]` rows with read-only/write badges, `errors[]` rows, dashed readable-empty state, `{:error, reason}` banner — banner and empty state mutually exclusive; all reads total; pure `custom_tool_names/1` is the single source of loaded names). `custom_agents_editor/1` renders those names as an extra chip group using the SAME `tools[]` markup, compared alias-aware through `EvoGit.Agent.ToolNames` (`matches_any?/2`, `normalize/1`) so legacy `agents.toml` spellings survive, with a UI-only amber warning for unknown selections (the store stays lenient — core `:invalid_tools` semantics untouched).
- Detail: `lib/evo_dash/CONTEXT.md`, `live/settings_live/CONTEXT.md`, `components/CONTEXT.md` + `components/settings_components/CONTEXT.md`; tests → `test/CONTEXT.md`.

### SSH Remote Development — Node-Aware Dashboard

The dashboard controls a remote headless `genesis_remote` daemon over Erlang distribution via an SSH tunnel, through three layers: `EvoDash.NodeContext` (thin client), `EvoDashWeb.LiveHooks.NodeAware` (on-mount hook: node-context assigns, `?node=` resolution, unified sidebar Active-Tasks loader, connection status with push_patch on local↔remote transitions) and `EvoDashWeb.NodeSelectorComponent` (navbar selector + connection-manager modal, auto-connect on select).

- **URL threading**: nav links carry `?node=<target_id>` (`with_node_param/2` in `layouts.ex`; ⚠️ it appends with `?`, so query-string URLs need a manual `&node=` suffix).
- **Data access**: every node-aware load routes through `NodeContext` (local direct call, remote `:erpc`), always off the LiveView process, with no polling — push-based via cluster-aware `EvoGit.PubSub` (PG2/`:pg`). evo_dash owns no SQLite/Ecto/xqlite and has ZERO `EvoGit.Store` references in production code: reads go through `NodeContext` → `EvoGit.RemoteNode` → `RemoteAPI` → `TaskRegistry`, deliberate local-only `TaskRegistry` shortcuts, or the minimal `list_task_ids` projection. Inventory: `lib/CONTEXT.md` + `lib/evo_dash/CONTEXT.md` + `live/CONTEXT.md` + `live_hooks/CONTEXT.md`.
- **Per-page remote behavior**: SettingsLive edits remote config (`save_user_config` + `reload_remote_config`), SystemLive pauses/resumes/restarts/stops via RPC (update + source cards hidden on remote), ProjectsLive shows the remote task form with read-only projects, TasksLive reads the full remote task list. Detail: `lib/evo_dash_web/CONTEXT.md` ("SSH Remote UX" + node-locking) + `live_hooks/CONTEXT.md` + `live/agents_live/CONTEXT.md`. Graceful degradation: lifecycle calls return safe fallbacks; the node selector renders "Local" by default.

### Push-based event contract (node-identity PubSub)

`:evo_git` broadcasts enriched events on `EvoGit.PubSub`; every event carries the **BEAM node atom of the publisher**, and an event only updates the UI when its `node` matches the viewed node — `EvoDashWeb.LiveHooks.NodeAware.event_from_current_node?/2`. `{:task_updated, ...}` / `{:task_deleted, ...}` flow through `NodeAware.handle_task_info/2` (300 ms trailing-edge debounce → `:node_aware_reload_tasks`).

| Topic | Events | Consumers |
|-------|--------|-----------|
| `"tasks"` | `{:task_updated, task_id, status, node}` (status `:pending\|:running\|:finalizing\|:cancelling\|:completed\|:failed\|:cancelled`, or `nil` for review-only mutations); `{:task_deleted, task_id, node}` | NodeAware, TasksLive, ProjectsLive, ReviewLive, AgentsLive, SettingsLive, SystemLive |
| `"agents"` | `{:agent_registered, id, summary, node}`, `{:agent_updated, id, changed_fields, node}` (NEVER `:context`; carries `:message_count` when context changed), `{:agent_removed, id, node}`, `{:agents_updated, node}` | AgentsLive |
| `"scheduler_config"` | `{:scheduler_config_updated, node}` | SettingsLive, SystemLive (node-filtered → async reloads) |
| `"system"` | `{:system_sample, node, seq, sample}` every 3 s: legacy aggregates plus **`llm_slots`** (per-model `%{used:, waiting:, capacity:}`, real counts for every configured profile incl. peak-paused 0-capacity; `%{}` when the scheduler is dead) | SystemLive charts (ring buffer, cap 60) |
| `"recent_projects"` | `{:recent_projects_updated}` | ProjectsLive |
| `"guides"` | `{:guide_updated, id, %{message, page, selector, dismissible}, node}` | `LiveHooks.Guide` overlay |
| `"updates"` | `{:update_status, state}` | UpdateStatus hook, SystemLive |

Key detail + subscriber specifics: `lib/CONTEXT.md` (§ PubSub Topics), `live/system_live/CONTEXT.md` (sample keys, the per-model LLM Slots chart + one-shot seed), `live_hooks/CONTEXT.md` (guide shape).

### Task Archive Feature

With the **archive** checkbox the core collects per-agent metadata (`archive_records`) and stores one archive row per successfully completed agent; archived tasks show the agent parent-child tree (objective/return/start-end commits/token usage/archive refs) and offer JSON export.
Opt-in only, and the archive NEVER rides a page load: every page reads a lite task row and the archive arrives in bounded pages (`NodeContext.list_task_archives/3` — 100 entries, `include_results: false`), with one agent's full entry fetched lazily (`NodeContext.get_agent_archive/3`); tasks page on an explicit archive disclosure, review page only when its Archive tab opens, both cached per `{task_id, node}`.

- Threading: the `:archive` opt (built inline in `ProjectsLive.do_task_submit/4`) → core; the dashboard writes nothing back.
- Mode resolution: UI strings `"genesis_new"`/`"genesis_existing"`/`"evolve_simple"`/`"custom_agent"` → `{task_type, core_mode_string}` in `do_task_submit/4` (unknown → `{:evolve, "simple"}`). Core `RuntimeOpts.mode_atom/2` accepts `"custom"`; unknown evolution modes raise `ArgumentError`; `:genesis` + `"custom"` raises "custom mode is evolve-only".
- Export: `GET /tasks/:task_id/export` → `TaskExportController` — `?node=` resolution, a LITE task read, then pages of 200 WITH results from offset 0 until the reported `total` or an empty page, each record encoded one at a time into a temp file that is sent with `send_download/3` and deleted afterwards. The envelope stays flat: `task_id, task_type, repo_path, status, started_at, finished_at, agent_count, usage, archive_records`. Render sites + gotchas: `lib/evo_dash_web/CONTEXT.md` → "Known Issues — Task Archive Display"; paged reads: `live/tasks_live/CONTEXT.md` + `live/review_live/CONTEXT.md`.

### Self-Reflective Task Mode & Guide Overlay

- **`:reflect` task mode** — repo-less conversational task type whose ONLY dashboard entry point is the Home chat page (`HomeLive` at `GET /help`); the Projects task form offers no reflect mode. Reflect tasks carry NO `:path` (nil `project_path`; task cards are nil-path-safe) and their result is the agent's final text. `:reflect` is in `Store.Codec` `@known_atoms`; `execute_task(:reflect)` routes directly to `Runtime.SelfReflective.run`, bypassing `build_common_runtime_opts` (which `Keyword.fetch!(:path)`-raises). Core detail: `apps/evo_git/CONTEXT.md`; dashboard: `live/home_live/CONTEXT.md`.
- **Guide overlay** — global floating UI through which a running reflective agent guides the user: core broadcasts on `"guides"`, consumed by `EvoDashWeb.LiveHooks.Guide` (registered LAST in `live_view/0`) which node-filters, assigns `@guide`, persists per tab via `guide_client_id` (`:persistent_term`) and pushes `"guide_highlight"`. `Layouts.app` renders the floating panel (`fixed top-4 right-4 z-50`); the `Guide` JS hook scrolls + applies `.guide-highlight` (~3s). Detail: `live_hooks/CONTEXT.md` + `assets/CONTEXT.md`.

### Home Chat Page (`HomeLive` at `GET /help`)

ChatGPT-style chat wired to the self-reflective agent — the ONLY entry for `:reflect` tasks; sidebar **Help** entry. Send flow: `Transcript.build_preamble/1` (last 8 exchanges, 600 chars/entry, 4000-char cap) + message → `EvoDash.NodeContext.start_task(node, :reflect, mode: "reflect", objective: ...)` with NO `:path`; streaming rides `"agents"`/`"tasks"` PubSub + async `get_agent_history/2` (the `:agent_updated` `changed_fields` is a KEYWORD LIST — guard with `is_list`/`Keyword.has_key?`); the terminal render comes from the task result, behind two monotonic stale-guards (`chat_fetch_seq`, `chat_task_fetch_seq`). Each assistant response is a **mini task-card chat message** (`home_live/assistant_message.ex`) reusing `Helpers.task_status_badge/1`, the streamed text, and a collapsible "Thought process" (思考过程) via `AgentsLive.ToolCallDisplay`. Chat state survives remounts via `EvoDash.ChatHistory` (ETS-backed), restored on connected mount (mid-run mounts get a one-shot reconciliation fetch, no polling); New chat = new persisted chat + `prune(10)` (local node only). Enter sends / Shift+Enter newlines, Stop = graceful cancel.

**Interactive command approvals (security levels 2 & 3)** — the reflect agent's `run_command` tool carries a security level: level 1 executes with no UI, levels 2 & 3 BLOCK mid-turn until the user decides. HomeLive subscribes to `"approvals"` and renders one confirmation card per pending request (`home_live/approval_card.ex`), level-distinct (level 3 danger styling, level 2 informational); Confirm/Deny → `handle_event("approval_response", ...)` answers through the call-time `:approval_responder` seam (default `NodeContext.approval_response/3`) and optimistically removes the card. Only requests matching the chat's own task/agent AND node are kept; `pending_approvals` is ephemeral. Detail: `live/home_live/CONTEXT.md` + `live_hooks/CONTEXT.md`.

### Task Cancellation Model

Two node-aware actions backed by `EvoGit.RemoteNode`: **graceful cancel** (`EvoDash.NodeContext.cancel_task/2` — `:pending` → immediate `:cancelled`; `:running` → `:cancelling` with agents messaged to save + exit and a 3-turn grace → `:cancelled` WITH result/archive preserved, so cancelled tasks ARE reviewable) and **force kill** (`force_kill_task/2` — kills all agents + wrapper → `:failed`, result nil'd; escalation from `:cancelling`). `TaskCardComponents.show_review_button?/1` therefore shows Review for every `:completed`/`:cancelled` task (repo-less `:reflect` excluded).

UI: the TasksLive card Cancel button (`[:pending, :running]`) → confirmation modal; the three-dot dropdown "Force kill" (`[:running, :cancelling]`, "Danger zone" divider) → warning modal. `:cancelling` renders as violet in-progress end-to-end (badge, accent, tint, pulsing dot + `gettext("Cancelling…")`, sidebar running partition, TasksLive status filter). Detail: `live/tasks_live/CONTEXT.md` + `components/CONTEXT.md` + `lib/evo_dash_web/CONTEXT.md`.

### Config-Status Warning Surfaces (no-LLM-model warnings) & Reload Semantics

Three notions of "LLM model configured" can visibly diverge (a working model can still raise "Missing Configuration"):

1. **Core `EvoGit.Config.config_status/0`** requires a resolved profile whose `:model` is a NON-EMPTY BINARY; a ReqLLM map-form `:model` spec (with `base_url`/`extra`, used for OpenAI-compatible endpoints) fails it although the schema, editor dropdowns, scheduler and connection test all accept it — divergence recorded in `apps/evo_git/lib/evo_git/config/CONTEXT.md`.
2. **Global layout toast** (`components/layouts.ex`) — fixed bottom-right on EVERY page when `@config_status && not @config_status.ok?`; the assign is seeded per page and no page re-runs it on config-save events, so it goes STALE after a Settings save until a full remount.
3. **Settings banners** (`live/settings_live.ex`) — amber "Missing Configuration" (same `config_status.ok?`), red "Remote Configuration Unavailable" (`@remote_config_error`), red "No LLM Model Configured" (checks ONLY `get_in(@file_config, [:llm, :models])` list presence — silent while config_status warns, and vice versa).

- **Node correctness**: projects/tasks/review compute the LOCAL config_status once at mount BEFORE `?node=` resolution (a remote-node page shows the LOCAL health); agents/system/settings are node-correct (per-page assigns in the respective `live/*/CONTEXT.md`). A Settings save broadcasts only `{:scheduler_config_updated, node}`, whose subscribers refresh paused state — not config_status.
- **Save plumbing**: local `persist_file_config/3` → `NodeContext.save_user_config` → `EvoGit.Config.save_user_config/1` (writes `Config.config_path()`, the path config_status reads) → re-read + `config_status()` + `update_runtime_from_file_config/2` → `AgentScheduler.update_config` → broadcast. Remote saves use `reload_remote_config(node)` → `get_resolved_config(node)` (FULL nested config, map-form `llm.models` preserved); the legacy FLAT-map `remote_config_to_file_config/1` sets `llm.models` only when `:model_profiles` is non-nil and non-empty, so missing/`[]` fires "No LLM Model Configured".
- **Connection test** (`test_llm`) tests the persisted profile (never unsaved drafts) via `EvoGit.SystemCheck.llm_test/2` (binary OR map model, real request, per node) and never re-runs config_status — a pass proves reachability, not config-status-green. No launch-time validation exists: the task form hides the model select when `@model_profiles == []` silently and `task_submit` threads no `:model_id`, so the core rejects at agent spawn → `:failed`.
- **Welcome flow / empty states**: the projects-page first-run gate is `EvoGit.Config.VersionState.onboarding_needed?()` → `push_navigate` to `/welcome` (no `show_welcome` modal); welcome_live's `has_model?` is raw `file_config[:llm][:models] != []`. `Helpers.config_status_badge/1` is DEAD code (no embed sites); a `:model`-empty profile still renders as a selectable row everywhere — only nil/blank `id` is filtered.

## Constraints

- Depends on `:evo_git` at compile and runtime (persistence/registry code lives there; evo_dash owns none).
- Runs on port 4100 in development, uses the Bandit adapter.
- Tailwind CSS 4 + DaisyUI (no Node.js toolchain); JS bundled by esbuild.

- **Data-safety architecture**: TaskRegistry/Store `handle_*` callbacks have NO try/rescue — a Store failure crashes the GenServer and the supervisor restarts it (WAL mode keeps data safe). Serialization is `EvoGit.Store.Codec` (total encode, raise-on-bad-decode). `safe_select_all_tasks/projects` SKIP corrupt rows with a `Logger.warning` (never raise, no quarantine). `cleanup_expired_tasks` runs only on completion transitions / explicit clear / init, and the completed task's `put_task` runs BEFORE cleanup. **Lease & heartbeat**: running tasks carry `lease_expires_at` (renewed every 60 s); lease checking is two-check, one-shot (startup reconcile + one `:lease_sweep`); a task is marked `:failed` only when the lease has genuinely expired (a second BEAM instance cannot kill the first's running tasks). Detail: `apps/evo_git/CONTEXT.md`.
- **Supervision robustness**: `:one_for_one` with `max_restarts: 10`, `max_seconds: 60` so the Endpoint survives a transient TaskRegistry restart.
- **`try/rescue` anti-pattern policy**: never wrap LiveView config/core-value loading (`EvoGit.Config.*`, `EvoGit.AgentScheduler.*`) — let the LiveView crash truthfully; JSON via non-crashing `Jason.encode/1` + `case`; atom conversion from untrusted input via whitelist `Map.get/3` (never `String.to_existing_atom/1` + rescue, never bare `String.to_atom/1`); ETS existence via `:ets.info/1`. Acceptable try/rescue (MUST carry a comment answering "expected error?" + "cleanest approach?"): GenServer `terminate/2`, deliberate data-recovery boundaries, untrusted persisted data with no non-crashing variant, the Store's `ALTER TABLE DROP COLUMN` migration, test-cleanup rescues in `on_exit`/teardown.
- Naming: domain modules in `./lib/evo_dash/`, web modules in `./lib/evo_dash_web/`.
- Build: `mix assets.build` (esbuild + tailwind), `mix assets.deploy` (minified + digested).
- Desktop-mode gating: desktop-only code (`DesktopLifetime`, update-status integration) lives in the frontend app so the `genesis_remote` (evo_git-only) release never ships it; gating env vars `EVOGIT_DESKTOP` / `EVOGIT_LIFETIME_PORT` (see Desktop Mode).

### Backend Boot Order (HTTP listener is bound LAST)

The Tauri shell's readiness probe measures the ENTIRE umbrella boot — the port accepts connections only after `:evo_git` has fully started.

- Ordering follows the release graph: `evo_dash.app` lists `:evo_git`, so `EvoGit.Application.start/2` completes first, including `EvoGit.Store.init/1` → synchronous `Store.Boot.start_dynamic/2` (mkdir + Ecto migrations) and `TaskRegistry.init/1`'s lease read. Inside `EvoDash.Application` the endpoint is the LAST child; Bandit/ThousandIsland binds synchronously in its Listener `init/1`, so the bind completes before `start/2` returns (`server: true` from `config/runtime.exs`). A slow/blocked `:evo_git` boot therefore presents as "backend unavailable" with no listener yet.
- **Boot-phase observability is thin**: neither app logs a boot line, and `backend.log` is configured ONLY by the root `config/runtime.exs` (`:default_handler` `type: :file`, APPENDED across launches, 10 MB × 5 files, prod `:info`). Markers come from deps: Ecto's `Migrations already up` / `== Running <v> <mod>.up/0`, and the definitive listener line `Running EvoDashWeb.Endpoint with Bandit <vsn> at <address>:<port> (http)` at `:info` on EVERY successful bind (so a restarted endpoint child/supervisor re-logs it); Phoenix adds `Access EvoDashWeb.Endpoint at http://<host>:<port>` per endpoint-supervisor start, and a failed bind logs `… failed, port <port> already in use`.
- `PORT`/`PHX_IP` are read ONCE per BEAM at config-provider time; nothing re-reads or re-binds at runtime (the only `config_change` forwards to `Phoenix.Endpoint.Supervisor.config_change/3`). A BOOT bind failure aborts `start/2` (no retry); a RUNTIME restart failure retries until the endpoint supervisor's intensity (3/5 s) then `EvoDash.Supervisor`'s (10/60 s). `config/config.exs` logs NO OS pid, so `backend.log` cannot distinguish repeated boots from sidecar respawns vs `System.restart/0` (`live/system_live/CONTEXT.md`).
- `DesktopLifetime` is the ONLY self-exit on this path: 5 connect attempts × 200 ms with a 1 s timeout each, then a warning + `System.stop(0)` — exit 0 is classified INTENTIONAL by the Tauri watchdog, so it yields a silent quit, NOT the "backend unavailable" page (`lib/evo_dash/CONTEXT.md`).
- Ruled out as a cause of the shell's error page: the first-time-user `push_navigate(to: "/welcome")` IS a real 302 on `GET /`, but the shell's load latch matches by host+port only — and post-upgrade launches never take that branch, because `VersionState.onboarding_needed?/0` keys on the version-state FILE existing, not on the version changing. Nothing here is keyed to the release VERSION or install path.

## Research Notes — ReqLLM-Native Multimodal (Image/Audio) File Attachments (survey addendum)

Refines the root `./CONTEXT.md` note ("Research Notes: PDF/DOCX → Plain Text Extraction"). The plain-text pipeline (`EvoDash.AttachedFile.read/1` + `ex_pdf`) is unchanged; image/audio attachments are additionally implemented as server-side-staged raw-binary content parts (`EvoDash.AttachedFile.read_kind/2` — image/audio kinds, extension allowlist, 15 MiB per-file cap) staged into the Projects page's `:staged_attachments` assign and submitted as the `:attachments` task opt (base64 `"data"`, string-keyed maps; contract: `lib/evo_dash/CONTEXT.md` + `live/projects_live/CONTEXT.md`).

Survey facts (vendored `:req_llm` + `:llm_db` deps):

- `ReqLLM.Message.ContentPart` types: `:text | :image_url | :video_url | :image | :file | :thinking | :provider_block` (`:provider_block` = opaque provider-owned block replayed unchanged); there is no canonical `input_image`/`input_audio` chat-part type — those exist only at the provider wire level. Images ride `:image` (inline bytes), `:image_url`, or `:file` (raw bytes or a provider-uploaded `file_id`/`owned_file_id`).
- Audio in chat is a `:file` part with an `audio/*` media_type, practically OpenRouter-only (mp3/wav → `input_audio`, other audio raises). Audio otherwise lives on separate endpoints: `ReqLLM.transcribe/3` (STT), `ReqLLM.speak/3` (TTS), the experimental `ReqLLM.OpenAI.Realtime` websocket; OpenAI `modalities: ["audio"]` is output-only.
- Wire translation is per-provider at encode time: the OpenAI-compatible flock (deepseek/qwen/zai/alibaba/groq/mistral/venice/...) encodes ANY raw `:file` bytes as an `image_url` data-URI, silently mis-encoding non-image `:file` parts. OpenAI Chat rejects non-image `:file` while OpenAI Responses accepts image + pdf only; Anthropic maps `:file` to image/document base64 blocks; Gemini `inlineData`/`fileData` carries arbitrary mime (image/audio/video/pdf); OpenRouter handles image + pdf + mp3/wav audio; Bedrock Converse is image-only-inline.
- Capability truth lives in `:llm_db`: `LLMDB.model/2` → `%LLMDB.Model{modalities: %{input: [...]}}` from `./deps/llm_db/priv/llm_db/snapshot.json`; no "accepts image?" helper, so read `.modalities.input` — and check BOTH codec path and modality (a model may claim audio its codec cannot ship). Audio-input counts: google 19, openrouter 72, google_vertex 16, alibaba 13, alibaba_cn 6; image input is near-universal.
- Given `EvoGit.Config.LLMCatalog` (anthropic/openai/google/deepseek/zai/alibaba/minimax/moonshotai/xai/openrouter/openai_compatible), the practically reachable multimodal set is anthropic (image), openai (image + pdf via Responses), google (image + audio + video + pdf), deepseek-v4-flash-vision-exp (image), plus openrouter (image + pdf + mp3/wav audio).
