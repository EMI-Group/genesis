# EvoDash — Phoenix LiveView Dashboard

## Intent

EvoDash is the web dashboard of the EvoGit umbrella: a project-based real-time Phoenix LiveView interface to launch and monitor tasks (genesis / evolve), inspect the agent tree, review results, and manage scheduler settings, user configuration and per-project settings incl. foreign repositories.
Users open a Project (a Git repository path) through the command-palette selector, which mounts it in the core's Virtual Context Tree and makes it the single active project; the dashboard auto-detects the task mode.
Phoenix 1.8 umbrella child app (`:evo_dash`) depending on sibling `:evo_git`.

### Canonical LLM Provider Profiles & Selection

- Canonical config = `llm.providers` + `llm.default_provider_profile`, NOT a flat `llm.models` editor; profiles own identity, auth/endpoint, shared concurrency/peak schedules, context/generation/reasoning defaults, `default_model` and nested models with overrides; maps use string keys while the persistence boundary writes the atom-keyed `:llm` container; profiles require a nonempty `models` list naming `default_model` (mounted success fixtures must satisfy it); legacy `llm.models` and saved profile ids are migration inputs resolved through core projections.
- `EvoDashWeb.LLMSelection` is the shared boundary (core `Schema.provider_profiles/1`, `model_selections/1`, `resolve_model_spec/2`); `LLMSelectionComponents.llm_selection/1` is the fused capsule — pill = model + effort; model view = provider drill row ("Provider profile · <current name>") + model listbox + that model's ordered effort stops (omitted when none); the drill row switches the same panel to a provider view (Auto + disabled stale-profile row) and returns without closing; effort stops submit a zero-based index decoded by `resolve_reasoning_effort/3`, never a raw provider string.
- Picker state holds only string-keyed `provider_profile_id`, `model` and optional `reasoning_effort` (nil = uninitialized/node default, `%{}` or legacy empty string = explicit Auto); provider/model changes reset downstream defaults; display reconciliation migrates legacy ids and falls back to valid node defaults for stale saved choices, but launch validation REJECTS invalid explicit selections; explicit choices emit `:model_spec` + `model_id_locked: true`, Auto removes `:model_spec`, legacy `:model_id` and the lock.
- Node-aware persistence: loaded bundles stay server-only; browser state and ChatHistory keep only canonical selection fields + scope metadata; Projects stores `model_spec` per target node (canonical outranks legacy `selected_model_id`, incl. explicit Auto) and `persist_model_selection` merges selection fields without replacing prompt/form data; Assistant scopes by target id AND BEAM node, retains across same-scope New chat, resets on scope change, and pending/disconnected remote targets never borrow local models or credentials.

### Task Archive Feature

The **archive** checkbox makes the core collect per-agent metadata (`archive_records`), one row per successfully completed agent; archived tasks show the agent tree (objective/return/start-end commits/token usage/archive refs) and offer JSON export.
Opt-in only, and the archive NEVER rides a page load: every page reads a lite task row, pages arrive via `NodeContext.list_task_archives/3` (100 entries, `include_results: false`) and one agent's full entry via `NodeContext.get_agent_archive/3`; the tasks page opens it on an explicit disclosure, the review page only when its Archive tab opens, both cached per `{task_id, node}`.
`EvoDashWeb.ArchiveHelpers` owns the shared primitives: `archive_opt?/1` (the single `opts[:archive]` predicate), `max_retained/0` (500 = 5 pages), `retain_window/2,3` (slide the window, count evicted rows), `retained_page_bounds/3`, `more_pages?/3`.

- **Opt-in gate**: without `archive: true` the review Archive tab is not rendered (`LoadData` sets `archive_opt_in?` from persisted opts), `switch_tab "archive"` is a no-op and `ArchiveLoad.ensure_loaded/1` never fetches; the tab badge shows the archive's own total and renders nothing at 0/unknown.
- **Bounded accumulation**: pages are windowed to the most recent 500 entries with the evicted count tracked; the next offset is the cumulative RAW row count, never `length(archive_records)`.
- **Exhaustion**: a page shorter than the limit (empty included) ends the archive — the effective total is clamped so the pager disappears and the count line says "No more archive entries.", keeping a `total` that counts unrendered rows from spinning "Load more" forever.
- Threading: `ProjectsLive.TaskSubmit.build_opts/6` puts `:archive` from the submitted `"archive"` param and `ProjectsLive.do_task_submit/4` passes the returned opts to `start_task`.
- Mode resolution: UI strings `"genesis_new"`/`"genesis_existing"`/`"evolve_simple"`/`"custom_agent"` → `{task_type, core_mode_string}` in `ProjectsLive.TaskSubmit.mode/1` (unknown → `{:evolve, "simple"}`); core `RuntimeOpts.mode_atom/2` accepts `"custom"`, unknown evolution modes raise `ArgumentError`, `:genesis` + `"custom"` raises "custom mode is evolve-only".
- Export: `TaskExportController` — `?node=` resolution, a LITE task read, then pages of 200 WITH results from offset 0 until a known `total`, an empty page or a short page (a page without a usable `total` is written in full, so a lean roster read never truncates it), each record encoded one at a time into a temp file sent with `send_download/3` and deleted after; `fetch_page/3` is the ONE call site passing `include_results: true` + `include_settings: true`; the envelope stays flat (`task_id, task_type, repo_path, status, started_at, finished_at, agent_count, usage, archive_records`). ### Task Cancellation Model

Two node-aware **cancellation** actions via `EvoGit.RemoteNode`: **graceful cancel** (`NodeContext.cancel_task/2` — `:pending` → immediate `:cancelled`; `:running` → `:cancelling`, agents messaged to save + exit with a 3-turn grace → `:cancelled` WITH result/archive preserved, so cancelled tasks ARE reviewable) and **force kill** (`force_kill_task/2` — kills all agents + wrapper → `:failed`, result nil'd; escalation from `:cancelling`); `TaskCardComponents.show_review_button?/1` therefore shows Review for every `:completed`/`:cancelled` task (repo-less `:reflect` excluded).

**Pause / resume** — the third node-aware verb pair, `NodeContext.pause_task/2` / `resume_task/2`, one-line delegations to `EvoGit.RemoteNode` (`:ok | {:error, reason}`) with NO local/remote split dashboard-side; a pause is a graceful DRAIN, not a kill, and resume re-dispatches the SAME task id with WHOLE-TREE restore (root AND still-running subagents, each with restored conversation/worktree/branch; an already-collected child is not revived, a record-less one reported lost, agents told the last batch may be half-executed); refusals are values (`:not_found`, `:not_running`, `:not_pausable`, `:not_resumable`, `:scheduler_unavailable`, `:not_paused`, transport `{:error, {kind, reason}}`) and a paused task is RESUMED, never reviewed, so force kill (→ `:failed`) is its only terminal exit. - **Supervision robustness**: `:one_for_one` with `max_restarts: 10`, `max_seconds: 60` so the Endpoint survives a transient TaskRegistry restart.
- **`try/rescue` anti-pattern policy**: never wrap LiveView config/core-value loading (`EvoGit.Config.*`, `EvoGit.AgentScheduler.*`) — let the LiveView crash truthfully; JSON via non-crashing `Jason.encode/1` + `case`; atom conversion from untrusted input via whitelist `Map.get/3` (never `String.to_existing_atom/1` + rescue, never bare `String.to_atom/1`); ETS existence via `:ets.info/1`. Acceptable try/rescue (MUST carry a comment answering "expected error?" + "cleanest approach?"): GenServer `terminate/2`, deliberate data-recovery boundaries, untrusted persisted data with no non-crashing variant, the Store's `ALTER TABLE DROP COLUMN` migration, test-cleanup rescues in `on_exit`/teardown.
- Naming: domain modules in `./lib/evo_dash/`, web modules in `./lib/evo_dash_web/`; build via `mix assets.build` (esbuild + tailwind) and `mix assets.deploy` (minified + digested).

### Backend Boot Order (HTTP listener is bound LAST)

The Tauri shell's readiness probe measures the ENTIRE umbrella boot — the port accepts connections only after `:evo_git` has fully started.

- Ordering follows the release graph: `evo_dash.app` lists `:evo_git`, so `EvoGit.Application.start/2` completes first (incl. `EvoGit.Store.init/1` → synchronous `Store.Boot.start_dynamic/2` migrations and `TaskRegistry.init/1`'s lease read); inside `EvoDash.Application` the endpoint is the LAST child and Bandit/ThousandIsland binds synchronously in its Listener `init/1`, so the bind completes before `start/2` returns (`server: true` from `config/runtime.exs`); a slow `:evo_git` boot presents as "backend unavailable" with no listener.
- **Boot-phase observability is thin**: neither app logs a boot line and `backend.log` is configured ONLY by the root `config/runtime.exs` (`:default_handler` `type: :file`, APPENDED across launches, 10 MB × 5 files, prod `:info`); markers are dep lines — Ecto's `Migrations already up` / `== Running <v> <mod>.up/0` and `Running EvoDashWeb.Endpoint with Bandit <vsn> at <address>:<port> (http)` at `:info` on EVERY successful bind, plus `Access EvoDashWeb.Endpoint at http://<host>:<port>` per endpoint-supervisor start and `… failed, port <port> already in use` on a failed bind.
- `PORT`/`PHX_IP` are read ONCE per BEAM at config-provider time; nothing re-reads or re-binds at runtime (the only `config_change` forwards to `Phoenix.Endpoint.Supervisor.config_change/3`); a BOOT bind failure aborts `start/2` (no retry) while a RUNTIME restart failure retries until the endpoint supervisor's intensity (3/5 s) then `EvoDash.Supervisor`'s (10/60 s); `config/config.exs` logs NO OS pid, so `backend.log` cannot distinguish repeated boots from sidecar respawns vs `System.restart/0`.
- `DesktopLifetime` is the ONLY self-exit here: 5 connect attempts × 200 ms with a 1 s timeout each, then a warning + `System.stop(0)` — exit 0 is classified INTENTIONAL by the Tauri watchdog, so it yields a silent quit, NOT the "backend unavailable" page (`lib/evo_dash/CONTEXT.md`).
- The shell error page is NOT caused by the first-time-user `push_navigate(to: "/welcome")`: it IS a real 302 on `GET /`, but the shell's load latch matches by host+port only, and post-upgrade launches never take that branch because `VersionState.onboarding_needed?/0` keys on the version-state FILE existing, not on the version changing.

## Research Notes — ReqLLM-Native Multimodal (Image/Audio) Attachments

Refines the root `./CONTEXT.md` note ("Research Notes: PDF/DOCX → Plain Text Extraction"). The plain-text pipeline (`EvoDash.AttachedFile.read/1` + `ex_pdf`) is unchanged; image/audio attachments are additionally server-side-staged raw-binary content parts (`EvoDash.AttachedFile.read_kind/2` — image/audio kinds, extension allowlist, 15 MiB per-file cap) staged into the Projects page's `:staged_attachments` assign and submitted as the `:attachments` task opt (base64 `"data"`, string-keyed maps) → `lib/evo_dash/CONTEXT.md` + `live/projects_live/CONTEXT.md`.

- `ReqLLM.Message.ContentPart` types: `:text | :image_url | :video_url | :image | :file | :thinking | :provider_block`; no canonical `input_image`/`input_audio` chat part (wire level only). Images ride `:image` (inline bytes), `:image_url`, or `:file` (raw bytes or a provider-uploaded `file_id`/`owned_file_id`); chat audio is a `:file` part with an `audio/*` media_type, practically OpenRouter-only (mp3/wav → `input_audio`, other audio raises) — otherwise audio is `ReqLLM.transcribe/3`, `ReqLLM.speak/3` or the experimental `ReqLLM.OpenAI.Realtime` websocket, and OpenAI `modalities: ["audio"]` is output-only.
- Wire translation is per-provider at encode time: the OpenAI-compatible flock (deepseek/qwen/zai/alibaba/groq/mistral/venice/...) encodes ANY raw `:file` bytes as an `image_url` data-URI, silently mis-encoding non-image parts; OpenAI Chat rejects non-image `:file` while Responses accepts image + pdf only; Anthropic maps `:file` to image/document base64 blocks; Gemini `inlineData`/`fileData` carries arbitrary mime; OpenRouter handles image + pdf + mp3/wav audio; Bedrock Converse is image-only-inline.
- Capability truth lives in `:llm_db`: `LLMDB.model/2` → `%LLMDB.Model{modalities: %{input: [...]}}` from `./deps/llm_db/priv/llm_db/snapshot.json`; no "accepts image?" helper, so read `.modalities.input` and check BOTH codec path and modality; audio-input counts: google 19, openrouter 72, google_vertex 16, alibaba 13, alibaba_cn 6 (image input is near-universal); given `EvoGit.Config.LLMCatalog` (anthropic/openai/google/deepseek/zai/alibaba/minimax/moonshotai/xai/openrouter/openai_compatible), the practically reachable multimodal set is anthropic (image), openai (image + pdf via Responses), google (image + audio + video + pdf), deepseek-v4-flash-vision-exp (image), plus openrouter (image + pdf + mp3/wav audio).
