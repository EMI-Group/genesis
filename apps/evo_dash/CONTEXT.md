# EvoDash — Phoenix LiveView Dashboard

## Intent

EvoDash is the web dashboard of the EvoGit umbrella: a project-based real-time Phoenix LiveView interface to launch and monitor tasks (genesis / evolve), inspect the agent tree, review results, and manage scheduler settings, user configuration and per-project settings incl. foreign repositories.
Users open a Project (a Git repository path) through the command-palette selector, which mounts it in the core's Virtual Context Tree and makes it the single active project; the dashboard auto-detects the task mode.
Phoenix 1.8 umbrella child app (`:evo_dash`) depending on sibling `:evo_git`.

### Canonical LLM Provider Profiles & Selection

Canonical configuration is `llm.providers` + `llm.default_provider_profile`, not a flat `llm.models` editor.
Profiles hold account identity, auth/endpoint, shared concurrency and peak schedules, context/generation/reasoning defaults, a `default_model` and nested models with optional overrides; provider/model maps use string keys, while the Settings persistence boundary writes the atom-keyed `:llm` container and canonical collection/default keys.
Profiles require a nonempty `models` list with `default_model` naming a configured one (mounted success fixtures must satisfy it); legacy `llm.models` and saved profile ids are migration inputs resolved through core projections, never by splitting ids in dashboard code.

**Task controls** — `EvoDashWeb.LLMSelection` is the shared selection boundary (core `Schema.provider_profiles/1`, `model_selections/1`, `resolve_model_spec/2`); `LLMSelectionComponents.llm_selection/1` renders the fused model+reasoning capsule: pill = current model + effort, the model view carries a provider drill row ("Provider profile · <current name>") above the model listbox then that model's ordered effort stops (omitted when none), and the drill row switches the same panel to a provider view (listbox incl. Auto and a disabled stale-profile row) returning to the model view without closing.
Effort stops submit a zero-based index decoded by `resolve_reasoning_effort/3`, never a raw provider string; provider/model changes reset downstream defaults and unsupported reasoning is omitted.

### Task Archive Feature

The **archive** checkbox makes the core collect per-agent metadata (`archive_records`), one row per successfully completed agent; archived tasks show the agent tree (objective/return/start-end commits/token usage/archive refs) and offer JSON export.
Opt-in only, and the archive NEVER rides a page load: every page reads a lite task row and the archive arrives in bounded pages (`NodeContext.list_task_archives/3` — 100 entries, `include_results: false`), one agent's full entry fetched lazily (`NodeContext.get_agent_archive/3`); the tasks page opens it on an explicit disclosure, the review page only when its Archive tab opens, both cached per `{task_id, node}`.
`EvoDashWeb.ArchiveHelpers` owns the shared primitives: `archive_opt?/1` (the single `opts[:archive]` predicate), `max_retained/0` (500 = 5 pages), `retain_window/2,3` (slide the window, count evicted rows), `retained_page_bounds/3` (the honest "showing 6,501–7,000" span) and `more_pages?/3`.

- **Opt-in gate**: without `archive: true` the review page's Archive tab is not rendered (`LoadData` sets `archive_opt_in?` from persisted opts), `switch_tab "archive"` is a no-op and `ArchiveLoad.ensure_loaded/1` never fetches; the tab badge shows the archive's own total and renders nothing at 0/unknown.
- **Bounded accumulation**: pages are windowed to the most recent 500 entries with the evicted count tracked, so a multi-thousand-agent task cannot grow the LiveView heap; the next offset is the cumulative RAW row count, never `length(archive_records)`.
- **Exhaustion**: a page shorter than the limit (empty included) ends the archive — the effective total is clamped so the pager disappears and the count line says "No more archive entries.", keeping a `total` that counts unrendered rows from spinning "Load more" forever.
- Threading: `ProjectsLive.TaskSubmit.build_opts/6` puts `:archive` from the submitted `"archive"` param and `ProjectsLive.do_task_submit/4` passes the returned opts to `start_task`; the dashboard writes nothing back.
- Mode resolution: UI strings `"genesis_new"`/`"genesis_existing"`/`"evolve_simple"`/`"custom_agent"` → `{task_type, core_mode_string}` in `ProjectsLive.TaskSubmit.mode/1` (unknown → `{:evolve, "simple"}`). Core `RuntimeOpts.mode_atom/2` accepts `"custom"`; unknown evolution modes raise `ArgumentError`; `:genesis` + `"custom"` raises "custom mode is evolve-only".
- Export: `TaskExportController` — `?node=` resolution, a LITE task read, then pages of 200 WITH results from offset 0 until a known `total`, an empty page or a short page (a page without a usable `total` is written in full, so a lean roster read never truncates it), each record encoded one at a time into a temp file sent with `send_download/3` and deleted after. `fetch_page/3` is the ONE call site passing `include_results: true` + `include_settings: true`. Envelope stays flat: `task_id, task_type, repo_path, status, started_at, finished_at, agent_count, usage, archive_records`. Render sites + gotchas: `lib/evo_dash_web/CONTEXT.md` → "Known Issues — Task Archive Display"; paged reads: `live/tasks_live/CONTEXT.md` + `live/review_live/CONTEXT.md`.

### Task Cancellation Model

Two node-aware **cancellation** actions via `EvoGit.RemoteNode`: **graceful cancel** (`NodeContext.cancel_task/2` — `:pending` → immediate `:cancelled`; `:running` → `:cancelling`, agents messaged to save + exit with a 3-turn grace → `:cancelled` WITH result/archive preserved, so cancelled tasks ARE reviewable) and **force kill** (`force_kill_task/2` — kills all agents + wrapper → `:failed`, result nil'd; escalation from `:cancelling`). `TaskCardComponents.show_review_button?/1` therefore shows Review for every `:completed`/`:cancelled` task (repo-less `:reflect` excluded).
UI: the card Cancel button (`[:pending, :running, :awaiting_input]`) → confirmation modal; the three-dot "Force kill" (`[:running, :awaiting_input, :cancelling, :pausing, :paused]` — a draining or stuck pause must always be killable; Delete stays unconditional behind a "Danger zone" divider) → warning modal. `:cancelling` renders violet in-progress end-to-end (badge, accent, tint, pulsing dot + `gettext("Cancelling…")`, sidebar running partition, status filter). Detail: `live/tasks_live/CONTEXT.md` + `components/CONTEXT.md` + `lib/evo_dash_web/CONTEXT.md`.
**Pause / resume** — the third node-aware verb pair, `NodeContext.pause_task/2` / `resume_task/2`, one-line delegations to `EvoGit.RemoteNode` (`:ok | {:error, reason}`) with NO local/remote split dashboard-side; a pause is a graceful DRAIN, not a kill (each agent stops at its next turn boundary, in-flight tools are never interrupted, wrapper and lease stay alive) and resume re-dispatches the SAME task id with WHOLE-TREE restore (root AND still-running subagents, each with restored conversation/worktree/branch; an already-collected child is not revived, a record-less one is reported lost, and agents are told the last tool batch may be half-executed).
Refusals are values: `:not_found`, `:not_running`, `:not_pausable` (an interactive session is user-driven), `:not_resumable` (`persistent_state: false`), `:scheduler_unavailable`, `:not_paused`, plus a transport `{:error, {kind, reason}}`; a paused task is RESUMED, never reviewed (`show_review_button?/1` stays an allowlist on `:completed`/`:cancelled`), so force kill (→ `:failed`) is the only terminal exit from a pause.

### Config Status & Reload Semantics

`config_status` drives the global layout warning and the Settings "Missing Configuration" banner; it is a core health verdict, not a replacement for canonical selection validation.
Settings' "No LLM Model Configured" banner checks `ConfigIO.model_selections(@file_config)`, not raw legacy `llm.models`; remote config-load failures have a separate "Remote Configuration Unavailable" banner.
All Settings save paths use the canonical persistence boundary, then reload authoritative config and refresh Settings health/OAuth state; other mounted pages' health assigns may stay stale until their own reload/remount, and a successful connection test proves provider reachability, not that every health surface was recomputed.
Projects' first-run gate remains `EvoGit.Config.VersionState.onboarding_needed?()` → `/welcome`; Welcome's all-set state uses `Setup.has_model?/1` for canonical or legacy config; Projects and Assistant validate explicit canonical selections before launch, and missing, stale or pending-remote selection data must never silently fall back to a local/default task.
Contracts: `live/CONTEXT.md`, `live/settings_live/CONTEXT.md`, `live/projects_live/CONTEXT.md`, `live/home_live/CONTEXT.md`, `live/welcome_live/CONTEXT.md`.

**Config read surface** — the dashboard touches `config.toml`/`credentials.toml` with `File` APIs in exactly two places: `welcome_live/setup.ex`'s raw-TOML read-modify-write base (`File.read(EvoGit.Config.config_path())`, bypassing `resolve/0` so resolved defaults never land in the file) and `settings_live.ex`'s mount-only `File.exists?(config_path())` sidebar hint; everything else reads through `EvoGit.Config.resolve/0,1` (→ `user_config/0`), `credentials/0`, `config_status/0`, `VersionState` or pure `Schema.*` projections (exhaustive inventory: `live/CONTEXT.md` → "Complete `EvoGit.Config.*` read inventory").
The dashboard has NO config write outside the core save APIs: whole-file `config.toml` writes funnel through `ConfigSave.start/4` → `NodeContext.save_user_config/2`, credentials through `NodeContext.save_credentials/2` (remote adds an explicit `reload_remote_config/1`), and `agents.toml` / `remote_connections.toml` / `version_state.toml` go through their own core APIs.
Post-save freshness is ASSUMED, never polled: `ConfigSave` re-reads authoritative config in the SAME supervised task right after the writer returns, local credential saves re-read `config_status/0` + `credentials/0` inline, and Welcome re-reads `resolve/0` + `credentials/0` in the LiveView process — all relying on the write path leaving a fresh BEAM-global snapshot.
Nothing on the dashboard subscribes to config changes: `config_status` is captured once per mount (`projects_live.ex` deferred `:load_config_status`, `tasks_live.ex`, `review_live.ex`, `processes_live.ex`, `agents_live/load_data.ex`) and the accent re-resolves only on a new socket mount or node change (`live_hooks/appearance.ex`, whose `EvoDash.AccentCache` has no TTL or per-key invalidation), so an outside edit (CLI, MCP, another tab, a vendor OAuth login, the remote bootstrap config copy) surfaces only on the next remount/navigation.
MCP is the documented external-edit path: `genesis_check` advertises the config paths, the user edits them, then `genesis_reload_config` → `EvoGit.TaskControl.reload_config/1` → `RemoteAPI.reload_config/0` is the only forced re-read, and no page issues one (nothing reloads after `EvoGit.RemoteConnection`'s bootstrap config copy).
`config_status/0`'s `ok?`/`validation_errors` come from a caller-process side channel that `resolve/0` writes, so every banner (layout warning, Settings health, System self-check) is only truthful while `resolve/0` validates in the reading process.

The dashboard sees only PROJECT mounts under `vct:///projects/…`: reserved mounts such as `vct:///genesis-source` are deliberately absent from `projects/1`/`search/2`.

  Reached only through `NodeContext.workspaces/1` / `workspace_entries/1` / `create_workspace/4` / `workspace_members/2` / `workspaces_for/2` (roster reads degrade to `[]`; the other two return `{:error, reason}`), and `create_workspace/4` is an idempotent slug-keyed UPSERT (re-submitting a name REPLACES it).
  `NodeContext.workspace_entries/1` is the BATCHED roster read (`EvoGit.VCT.workspace_entries/1` on the node, one round trip) returning each workspace with resolved members flattened to `%{point:, name:, path:}` plus stored `missing`/`nested` refs; both roster consumers (Projects palette, Assistant picker) use it instead of one call per workspace.
  Surface: the Projects palette's **Workspaces** section (name/point/description rows with a member disclosure marking missing refs) plus a **New Workspace** form with an ordered member picker, both node-scoped and reset on node switch; only `workspaces/1` lists them (`projects/1` and `search/2` exclude workspaces and reserved mounts) — `live/projects_live/CONTEXT.md` + `components/CONTEXT.md`.
- **Data-safety architecture**: TaskRegistry/Store `handle_*` callbacks have NO try/rescue — a Store failure crashes the GenServer and the supervisor restarts it (WAL keeps data safe). Serialization is `EvoGit.Store.Codec` (total encode, raise-on-bad-decode). `safe_select_all_tasks/projects` SKIP corrupt rows with a `Logger.warning` (never raise, no quarantine). `cleanup_expired_tasks` runs only on completion transitions / explicit clear / init, and the completed task's `put_task` runs BEFORE cleanup. **Lease & heartbeat**: running tasks carry `lease_expires_at` (renewed every 60 s); lease checking is two-check, one-shot (startup reconcile + one `:lease_sweep`); a task is marked `:failed` only when the lease has genuinely expired (a second BEAM instance cannot kill the first's running tasks). Detail: `apps/evo_git/CONTEXT.md`.
- **Supervision robustness**: `:one_for_one` with `max_restarts: 10`, `max_seconds: 60` so the Endpoint survives a transient TaskRegistry restart.
- **`try/rescue` anti-pattern policy**: never wrap LiveView config/core-value loading (`EvoGit.Config.*`, `EvoGit.AgentScheduler.*`) — let the LiveView crash truthfully; JSON via non-crashing `Jason.encode/1` + `case`; atom conversion from untrusted input via whitelist `Map.get/3` (never `String.to_existing_atom/1` + rescue, never bare `String.to_atom/1`); ETS existence via `:ets.info/1`. Acceptable try/rescue (MUST carry a comment answering "expected error?" + "cleanest approach?"): GenServer `terminate/2`, deliberate data-recovery boundaries, untrusted persisted data with no non-crashing variant, the Store's `ALTER TABLE DROP COLUMN` migration, test-cleanup rescues in `on_exit`/teardown.

- **No context-tree UI**: the dashboard renders no repo directory/node hierarchy, no node browser and no CONTEXT.md viewer; context-tree addressing exists only as the evolve-only free-text "Starting Node" (`:node_path`) task field (`task_form_components.ex`) and AgentsLive's per-turn `CONTEXT_TREE` history dump (`agents_live.html.heex`), the nearest hierarchies being the agent tree (`agents_components.ex`), the review file/diff tree (`review_components/diff_viewer.ex`) and archive trees.

### Backend Boot Order (HTTP listener is bound LAST)

The Tauri shell's readiness probe measures the ENTIRE umbrella boot — the port accepts connections only after `:evo_git` has fully started.

- Ordering follows the release graph: `evo_dash.app` lists `:evo_git`, so `EvoGit.Application.start/2` completes first, including `EvoGit.Store.init/1` → synchronous `Store.Boot.start_dynamic/2` (mkdir + Ecto migrations) and `TaskRegistry.init/1`'s lease read. Inside `EvoDash.Application` the endpoint is the LAST child; Bandit/ThousandIsland binds synchronously in its Listener `init/1`, so the bind completes before `start/2` returns (`server: true` from `config/runtime.exs`). A slow/blocked `:evo_git` boot presents as "backend unavailable" with no listener yet.
- **Boot-phase observability is thin**: neither app logs a boot line, and `backend.log` is configured ONLY by the root `config/runtime.exs` (`:default_handler` `type: :file`, APPENDED across launches, 10 MB × 5 files, prod `:info`). Markers are dep lines: Ecto's `Migrations already up` / `== Running <v> <mod>.up/0`, and the listener line `Running EvoDashWeb.Endpoint with Bandit <vsn> at <address>:<port> (http)` at `:info` on EVERY successful bind; Phoenix adds `Access EvoDashWeb.Endpoint at http://<host>:<port>` per endpoint-supervisor start, and a failed bind logs `… failed, port <port> already in use`.
- `PORT`/`PHX_IP` are read ONCE per BEAM at config-provider time; nothing re-reads or re-binds at runtime (the only `config_change` forwards to `Phoenix.Endpoint.Supervisor.config_change/3`). A BOOT bind failure aborts `start/2` (no retry); a RUNTIME restart failure retries until the endpoint supervisor's intensity (3/5 s) then `EvoDash.Supervisor`'s (10/60 s). `config/config.exs` logs NO OS pid, so `backend.log` cannot distinguish repeated boots from sidecar respawns vs `System.restart/0` (`live/system_live/CONTEXT.md`).
- `DesktopLifetime` is the ONLY self-exit on this path: 5 connect attempts × 200 ms with a 1 s timeout each, then a warning + `System.stop(0)` — exit 0 is classified INTENTIONAL by the Tauri watchdog, so it yields a silent quit, NOT the "backend unavailable" page (`lib/evo_dash/CONTEXT.md`).
- The shell error page is NOT caused by the first-time-user `push_navigate(to: "/welcome")`: it IS a real 302 on `GET /`, but the shell's load latch matches by host+port only, and post-upgrade launches never take that branch because `VersionState.onboarding_needed?/0` keys on the version-state FILE existing, not on the version changing.

## Internationalization (i18n)

EvoDash uses **Gettext** (`EvoDashWeb.Gettext`, `use Gettext, otp_app: :evo_dash`, imported via `html_helpers/0` in `evo_dash_web.ex`); all user-facing strings are `gettext`-wrapped while the `:evo_git` core stays English-only. The backend declares `split_module_by: [:locale, :domain]` (one small module per locale) — keep that option; detail: `lib/evo_dash_web/CONTEXT.md` → "i18n / Gettext Backend".

**Development policy** (root `./CONTEXT.md` → "Internationalization (i18n) Development Policy"): do NOT run `mix gettext.extract`/`merge`/`translate` during feature work — POT/PO files and translations are maintained centrally, once per release. Just write gettext-wrapped strings; when a meaning needs anchoring for the release-time AI translator, add a **Chinese comment** next to the `gettext` call — the ONLY i18n work expected during development. Dynamic locale: `root.html.heex` uses `Gettext.get_locale(EvoDashWeb.Gettext)` for `<html lang>`.

**Product-name convention**: the brand "EvoX Genesis" renders localized in CJK locales — zh_CN 天演 · 启元 / zh_HK 天演 · 啟元 / ja 啓元 (EvoX stays Latin in ja). The ja rendering lives in the `mix translate` ja glossary (`lib/mix/tasks/translate.ex`, `"Genesis" => "啓元"` / `"EvoX Genesis" => "EvoX 啓元"`) and in `priv/gettext/ja/LC_MESSAGES/default.po` msgstrs (the `Co-authored-by: Genesis <noreply@evogit.ai>` trailer literal inside one config-description msgstr stays ASCII and must NOT be renamed). Keep them in sync when the brand or glossary changes.

## Research Notes — ReqLLM-Native Multimodal (Image/Audio) Attachments

Refines the root `./CONTEXT.md` note ("Research Notes: PDF/DOCX → Plain Text Extraction"). The plain-text pipeline (`EvoDash.AttachedFile.read/1` + `ex_pdf`) is unchanged; image/audio attachments are additionally server-side-staged raw-binary content parts (`EvoDash.AttachedFile.read_kind/2` — image/audio kinds, extension allowlist, 15 MiB per-file cap) staged into the Projects page's `:staged_attachments` assign and submitted as the `:attachments` task opt (base64 `"data"`, string-keyed maps; contract: `lib/evo_dash/CONTEXT.md` + `live/projects_live/CONTEXT.md`).

- `ReqLLM.Message.ContentPart` types: `:text | :image_url | :video_url | :image | :file | :thinking | :provider_block` (opaque provider-owned block replayed unchanged); no canonical `input_image`/`input_audio` chat-part type — those exist only at the provider wire level. Images ride `:image` (inline bytes), `:image_url`, or `:file` (raw bytes or a provider-uploaded `file_id`/`owned_file_id`).
- Audio in chat is a `:file` part with an `audio/*` media_type, practically OpenRouter-only (mp3/wav → `input_audio`, other audio raises). Otherwise audio lives on separate endpoints: `ReqLLM.transcribe/3` (STT), `ReqLLM.speak/3` (TTS), the experimental `ReqLLM.OpenAI.Realtime` websocket; OpenAI `modalities: ["audio"]` is output-only.
- Wire translation is per-provider at encode time: the OpenAI-compatible flock (deepseek/qwen/zai/alibaba/groq/mistral/venice/...) encodes ANY raw `:file` bytes as an `image_url` data-URI, silently mis-encoding non-image parts. OpenAI Chat rejects non-image `:file` while Responses accepts image + pdf only; Anthropic maps `:file` to image/document base64 blocks; Gemini `inlineData`/`fileData` carries arbitrary mime (image/audio/video/pdf); OpenRouter handles image + pdf + mp3/wav audio; Bedrock Converse is image-only-inline.
- Capability truth lives in `:llm_db`: `LLMDB.model/2` → `%LLMDB.Model{modalities: %{input: [...]}}` from `./deps/llm_db/priv/llm_db/snapshot.json`; no "accepts image?" helper, so read `.modalities.input` — and check BOTH codec path and modality (a model may claim audio its codec cannot ship). Audio-input counts: google 19, openrouter 72, google_vertex 16, alibaba 13, alibaba_cn 6; image input is near-universal.
- Given `EvoGit.Config.LLMCatalog` (anthropic/openai/google/deepseek/zai/alibaba/minimax/moonshotai/xai/openrouter/openai_compatible), the practically reachable multimodal set is anthropic (image), openai (image + pdf via Responses), google (image + audio + video + pdf), deepseek-v4-flash-vision-exp (image), plus openrouter (image + pdf + mp3/wav audio).
