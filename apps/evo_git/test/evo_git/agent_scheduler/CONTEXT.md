# AgentScheduler Test Directory

## Intent

ExUnit tests for the `EvoGit.AgentScheduler` subsystem — scheduling (no worktree init in `run_agent`), slot pools (LLM/tool), lifecycle (crash retry, force-kill, graceful cancel), subagent spatial-contract validation (incl. cross-repo read-write foreign-repo gate), authority-gated foreign-repo-commit roll-up (`store_sub_result/3,4`), per-repo WorktreeManager init scoping (foreign vs primary), ETS store, PubSub throttling, and RPC surface.

## Canonical Provider-Profile Regression Contracts
`model_selection_regression_test.exs` is async and covers legacy/empty reload compatibility, one account pool for multiple model selections, configured defaults independent of inventory order, atom-keyed script maps, fail-closed wire/schema errors before ETS writes, explicit/script/definition/legacy precedence, and endpoint identifiers.
Its locked canonical root is registered through `Dispatch.register_agent/7`, then a child and grandchild with conflicting struct/opts/default/legacy selections must retain the complete account/model/effort choice and lock.
A dispatched run started by `Dispatch.try_dispatch/2` is a real `EvoGit.Agent.Session`, whose exchange reads the effective ETS binding and the inherited spec without creating worktrees or calling an LLM (the `:agent_exchange_llm_call` app-env seam supplies the scripted reply).
`Schema.resolve_model_spec/2` returns a ReqLLM identifier in `resolved.model_spec`, so expected task-selection maps are constructed from `provider_profile_id`, `model` and optional `reasoning_effort`, while request identifier, generation parameters and context window are compared separately.
Generation parameters are compared against the schema's complete result and are not assumed credential-free; provider/model defaults and actual supported reasoning parameters are pinned separately.
`provider_pool_regression_test.exs` is async and registers real selections against two accounts using the same provider and models, with pure `State`/`Slots` handlers thereafter.
Different models and different efforts share the account's capacity, queue, recency and all three exhaustion-backoff classes, while another account remains independent even for an identical concrete model.
Backoff expiry is driven by moving the account deadline and queued deadline copies into the past and invoking the retry handler, never by sleeping for production backoffs or changing global timing seams.
Release after ETS deletion, cancellation/death purge, canonical reload and removed-account live-pool retention preserve holder counts and reply to queued callers exactly once.
Pause regressions require releases, floor increases and expired-backoff sweeps to leave account waiters blocked until an explicit resume.
`tool_pause_regression_test.exs` adds async in-process coverage for tool-holder release, `State.do_update_config/2` tool-capacity increases and combined LLM/tool holder death cleanup during global pause.
These boundaries free released/dead holders and remove dead-agent LLM recency without draining surviving queues or replying to waiters until explicit resume.
Resume assertions pin exact holder sets, empty queues, running-status updates and exactly-once replies, including a repeated no-op grant sweep.
The module uses unique ids without ETS writes, global scheduler/config mutation, sleeps or quiet-window assertions.
The legacy model-id-only parent-lock regression supplies conflicting canonical selections through both the child struct and opts and asserts the resolved parent account; the sibling legacy test additionally pins script bypass.
Unlocked-parent dispatch tests register a blank child or an independently explicit child, and default-model-spec tests manually supply the fallback, so these scheduler tests do not establish that the subagent producer emits unlocked inheritance as `default_model_spec` rather than explicit `model_spec`.
The unlocked inheritance producer belongs to `EvoGit.Agent.SubagentProcessing`, outside this scheduler-test node.
`provider_scheduler_api_test.exs` is sync because it replaces the app-global scheduler's state and drives actual public config/status, pause/resume and update APIs.
It suspends `PeakHourEngine` before pinning state, restores the original scheduler state before resuming the engine, and uses same-sender GenServer requests plus FIFO-ordered status reads to prove pending requests without quiet-window waits.
Its API assertions cover account-keyed status, shared capacity floors, reload preservation of the runtime floor, zero-capacity hard pauses with in-flight holders retained, and the engine's explicit skip-floor map.
`model_selection_config` is an internal snapshot rather than a public `get_config/1` key; `provider_profiles` is public, and `model_concurrency` is available through the single-key accessor rather than the map-form config reply.
All three modules allocate monotonic, high-range per-test agent ids and delete exactly their own ETS rows in `on_exit`, without whole-table wipes.

## Per-Task `:persistent_state` Scheduler Threading
`persistent_state_dispatch_test.exs` observes the STARTED session's own `dispatch_ctx` (`:sys.get_state/1` on the `gen_statem` answers `{phase, data}`; the file's `dispatch_ctx/1` helper is total) while the session is PARKED on the `:worktree_create_fun` probe, so the assertion sees what the session received rather than a re-derivation of the scheduler's intent.
It pins the resolved flag (an ABSENT spec opt and an explicit `true` both yield `persistent_state: true`, an explicit `false` yields `false`), that a FIRST attempt always carries `restore_agent_state: false` with `retries: 0`, that a crash retry under `agent_max_retries: 3` re-dispatches the SAME `agent_id` with `retries: 1` + `restore_agent_state: true` (and with BOTH flags `false` when the task opted out), and that an `:interactive` SchedMeta crash is TERMINAL — `"Interactive sessions are never retried"`, both `Store` rows gone, nothing registered, and the caller receives `{:error, {:session_crashed, reason}}`, never `:agent_max_retries_exceeded`.
`retry_agent/3` re-dispatches SYNCHRONOUSLY inside `handle_agent_crash/3` when the in-process `%State{paused: false}` allows it (the `paused: true` queue path lives in `lifecycle_test.exs`), so no scheduler GenServer is started or mutated — the `%State{}` is a plain in-process value.
`persistent_state_restore_test.exs` is the production merge point on the consuming side: `Setup.build_initial_state/3` with a retry-SHAPED ctx (`restore_agent_state: true` + `persistent_state: true`) replaces the freshly built `[system, user]` pair with the seeded transcript byte-identically and restores `turn` / `usage` / `total_tokens` / `compression_count` / `prompt_cache_key` / `objective` / `pending_inputs` / `current_commit`, while `repo_path`/`repo_root`/`agent_id`/`task_id`/`repo_id`/`llm_model`/`model_id`/`model_id_locked`/`phase` stay the FRESH run's; `restore_agent_state: false` and `persistent_state: false` each skip the merge with the seeded record still readable.
Its durable store is an UNNAMED `EvoGit.AgentState` server on a per-test `:tmp_dir` sqlite file, reached through the `:evogit_agent_state_server` process-dictionary seam in the TEST process (`Process.put` before `build_initial_state/3` — the seam is per process and an `on_exit` callback does not see it), seeded through the real writer path (`checkpoint/4` + `flush/1`).
`session_opts_test.exs` pins `SessionOpts.build/1` alone: `:persistent_state` lands in `%EvoGit.AgentSpec{}.opts` for both shapes, the consumed keys (`:agent_module`/`:objective`/`:path`/`:node_path`/`:depth`/`:parent_id`) are dropped, `session_mode: "interactive"` becomes `:interactive`, and a repo-less spec keeps `repo_less: true` with a `nil` `phylo_node`.
`:foreign_repos` is forwarded only when the CALLER supplies it — `AgentSpec.new/5` hoists `foreign_repos`/`repo_notes` onto the struct with `[]`/`nil` defaults WITHOUT injecting the key into opts — so the repo-backed shape passes `foreign_repos: []` explicitly instead of expecting it.

## Tool-Slot Accounting Coverage Boundaries
`tool_permits_test.exs` drives `ToolPermits` against an in-process `%State{}` and the scheduler's acquire/transfer/release `handle_call/3` routes without invoking the app-global scheduler or writing ETS.
It stays `async: true`: monitors belong to the test process, owners are test-local parked processes, and agent ids are unique high-range values.
Explicit permits count every invocation, including multiple simultaneous calls by the same agent, independently of the legacy one-holder-per-agent slots.
Transfer uses the unguessable permit reference as a capability and deliberately does not require the transferring caller to be the current owner, so a background registry may transfer on a tool task's behalf.
Release is current-owner-only, with missing and nonowner releases returning `:ok` without changing capacity; the hub regression explicitly pins the caller pid forwarded to release after transfer.
The tests deliver observed real owner DOWN monitor refs to the handler, pin queued-caller removal and transferred-owner reclamation, and require exactly one surviving queued grant with empty monitor/permit maps after cleanup.
Invalid, waiting, missing and dead-owner transfer cases preserve state and return their documented errors.
These handler tests do not establish the public wrappers' singleton GenServer transport, the scheduler's live DOWN routing, or detached-job lifetime integration.

## Notes for Agents

- `pubsub_test.exs` drives the throttle debounce SYNCHRONOUSLY: the `:schedule` casts are FIFO-ordered ahead of a `:sys.get_state/1`, so after N casts the state already holds the ONE pending timer ref; the test cancels that ref and delivers the `:flush` itself, then pins `:sys.get_state(Throttle) == nil` and a short (25 ms) no-duplicate probe — three casts still yield exactly one `{:agents_updated, node}`.
- **Wait budgets in `worktrees_test.exs` are deliberately GENEROUS — do NOT tighten them.** The shared `wait_until/2` default is 30 s and the `assert_receive {:agent_ready, ...}, 30_000` create/re-create awaits match it, because every site relying on them waits on REAL work: `git worktree add`/prune/branch-delete subprocesses and monitor-driven `:DOWN` reclaim. Under host CPU oversubscription those round trips slow 10-25x, so a 5 s default (and a 10 s re-create await) flunks a slow-but-CORRECT event with a misleading `wait_until timed out`. Pure in-BEAM waits keep their own modest explicit deadlines (`restart_manager/1`'s 10 s `Process.whereis` poll and `finish_agent/3`'s 10 s `{:DOWN, ...}` receive).
  The POLL BEAT is a separate knob from the budget: `wait_until/2` starts at 1 ms and doubles to a 15 ms cap, so a wait whose event is about to happen is not quantized to a full 15 ms — only the interval shrinks, never a deadline or an assertion.
- **Deterministic slow-git reproduction (no load generators needed)**: put a PATH shim `git` on `PATH` that `sleep`s before `exec`ing the real git binary (e.g. `#!/bin/sh` + `sleep 0.8` + `exec /path/to/git "$@"`) and run the file with `--no-compile`. At 0.8 s per git invocation the pre-hardening file fails 21/23 (`wait_until timed out` in "retry-after-crash gets a fresh worktree" and in "defers a re-create request while the previous create is still in flight") while the 30 s budgets pass 23/23 — this is the cheapest way to exercise the load-sensitivity without a loaded host.

## Global-State Hygiene (BEAM-global ETS + app env)

**Rule: any test that inserts rows into a VM-GLOBAL named ETS table must delete exactly those rows in an `on_exit`.**
Those tables are created once at app boot by `EvoGit.Application.start/2` and owned by the application process, so a row outlives its test process and stays visible to every module that runs later in the same BEAM (the per-file `create_ets_if_missing/1` helpers are no-ops under `mix test`; their `:ets.whereis/1` guards only matter for `--no-start`).
Tables in play in this node: `:evogit_agent_summary` (the SUMMARY row), `:evogit_agent_inbox` + `:evogit_agent_control` + `:evogit_task_pause` (the per-agent and per-task CONTROL PLANE), `:evogit_sched_meta`, `:evogit_cancelling_tasks`, `:evogit_worktree_repos`.
A leaked `:evogit_agent_summary` row is a REAL flake cause, not cosmetic: `EvoGit.AgentScheduler.Slots.resolve_model_id/2` reads the agent's `model_id` from that table and falls back to the scheduler default ONLY for an id that has no row, so a stale row for a small literal id reroutes another module's slot request into that row's model pool (an empty pool grants immediately instead of queueing, which makes a "waiting" assertion unreachable → deadline burn + failure under host load). The victim shape is literal small ids (1, 2, 99) reused across modules.
Prefer TARGETED deletion of the inserted ids over a wholesale `:ets.delete_all_objects/1`, which could nuke rows another module legitimately owns; keep the cleanup idempotent (`:ets.delete/2` on a missing key is a no-op, guard `:ets.whereis/1` when the table may not exist).
App-env seams (`:llm_backoff_sweep_epsilon_ms`, `:max_concurrent_worktree_creation`, `:worktree_create_fun`) and OS env (`XDG_CONFIG_HOME`, `GENESIS_SOURCE_ROOT`) must be restored nil-aware (delete the key when it was originally unset).

Per-file state (current):
- `slots_test.exs` — targeted: `put_meta/2` and `put_agent_state/2` (the ONLY insert sites) each register an `on_exit` deleting exactly that id from their own table via the guarded, idempotent `delete_ets_row/2` (ids inserted: 1, 2, 3, 4, 99; models `"default"`/`"fast"`). Its `setup` still wipes both tables at test start as the module's defensive precondition; there is deliberately NO wholesale teardown.
- `remote_api_test.exs`, `worktree_admission_test.exs`, `worktrees_test.exs` — wholesale `clear_ets/0` (`:ets.delete_all_objects/1`, `:ets.whereis/1`-guarded) in `on_exit`; complete. `remote_api_test.exs` additionally deletes its injected `EvoGit.Store` task row targeted, `worktree_admission_test.exs` restores both app-env seams nil-aware.
- `lifecycle_test.exs`, `store_test.exs`, `pending_user_messages_test.exs`, `session_runtime_invariants_test.exs`, `task_pause_test.exs` — NO teardown and NO wipe (they are `async: true`): every row is keyed by a per-test-unique id from the module's own range (`lifecycle_test.exs` 9_700_000+, `store_test.exs` / `pending_user_messages_test.exs` 9_950_000+, `session_runtime_invariants_test.exs` 9_970_000+, `task_pause_test.exs` 9_960_000+ with a per-test unique task id), so a leftover row is invisible to any other module. `store_test.exs` keys the summary row AND the control-plane rows (inbox item, cancel flag) by that same per-test id, and its `delete_agent_state/1` case removes all three.

A parked create is always released `:fail` INSIDE `capture_log/1` and awaited by a registry-drain poll, because the session dies through its crash path and would otherwise log outside the test window.

**Order dependence to preserve:** `state_test.exs` (`async: true`) READS the global tables for literal id 3 without inserting (`Slots.handle_request_llm_slot(3, …)` → `resolve_model_id/2` + depth lookup) and asserts the scheduler-default fallback. It is safe only because the async cohort fully drains before any `async: false` module runs, and because the sync module that seeds id 3 (`slots_test.exs`) seeds it on model `"default"` — the same model `state_test.exs` assumes. Never flip `slots_test.exs` (or any id-3 seeder) into the async cohort — and an async module must never write small literal ids at all: `lifecycle_test.exs` moved to its own `unique_agent_id/0` range for exactly this reason (it used to seed 1-4, id 3 included).
**How to verify a no-leak claim** (used to prove the `slots_test.exs` teardown): add a TEMPORARY sync probe module whose single test asserts `:ets.lookup(:evogit_agent_summary, id) == []` (and the same for `:evogit_sched_meta`) for each literal id the module under test inserts, then run it in ONE BEAM after that module — `mix test --seed 3 --max-requires 1 <probe> <module>` — because `mix test` SHUFFLES the file list by seed and ExUnit runs sync modules in reverse of the shuffled list, so module order must be confirmed with `--trace` (with `--seed 3` the probe runs second). The leak is only observable when the LAST-executed test of the module under test inserts a row (each test's `setup` re-wipes the tables at start), which is why the seed matters. Delete the probe afterwards.
