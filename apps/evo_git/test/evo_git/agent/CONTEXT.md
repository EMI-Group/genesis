# evo_git/agent — Agent Test Tree

## Intent

ExUnit suites for the `:evo_git` agent layer (`EvoGit.Agent.*`): the Runner loop (cancel-grace, turn limits/warnings), context building/compression, subagent processing, tool dispatch, and usage/delegation/result/output helpers.
Each file mirrors its source module under `apps/evo_git/lib/evo_git/agent/`.

## Routing Table

- `./tools/` → Per-tool tests (`Tools.execute/5`, individual tool modules, the command shell) — own node.

## Async-Safety Policy (this directory)

A module is `async: true` ONLY if it mutates no BEAM-global state observable by a concurrently running module.
Every `async: false` module names its exact forcing global in its `@moduledoc`; when in doubt, keep `async: false`.

Genuinely `async: true` (pure functions / per-test `:tmp_dir` / process-local state):
`coder_test`, `coder_2_test`, `context_builder_test`, `context_compression_test`, `delegation_hints_test`, `llm_error_test`, `output_sanitizer_test`, `result_test`, `turn_limit_test`, `turn_warning_test`, `truncation_feedback_test`, `usage_test`.

## Notes for Agents

- Test-env seam for retry-backoff timing: `Application.put_env(:evo_git, :llm_retry_backoff_base_ms, ms)` is read at call time by `EvoGit.Agent.ToolDispatch.retry_backoff_base_ms/0` (production default `@default_retry_backoff_ms` = 1_000 ms).
  `tool_dispatch_retry_slot_test` AND `llm_error_failfast_test` both pin it to 25ms (`@retry_backoff_base_ms`) instead of sleeping through the real 1s/2s/4s backoff.
  25ms is verified robustly deterministic across 9 runs (seeds 1-5, back-to-back, and a fully saturated machine) because every wait is anchored on PERSISTENT scheduler state (`AgentScheduler.get_llm_slot_status/0`, `paused?/0`), never on the clock.
  The smallest randomized window (25 × 0.9 = 22.5ms) stays ~9× the measured worst-case connection-refused attempt (1.0-2.5ms over 300 samples) and far above a scheduler round trip (≤0.03ms).
  Timed impact: `tool_dispatch_retry_slot_test` 1.5s → 0.7s; `llm_error_failfast_test`'s 500-retry test 240ms → 91ms.
- Wait DEADLINES in `tool_dispatch_retry_slot_test` are deliberately generous: ONE shared `@load_robust_deadline_ms` (30_000) is the default for the slot-status poll deadline AND for every `request_llm_slot`/`Task.await` timeout, because those waits are anchored on persistent scheduler state and only host-load scheduling latency can delay them (no short-lived window to race) — a deadline expiry still flunks.
  The one elapsed-time budget that is not a plain wait deadline uses 15_000 (below the deadline above, so it stays the tighter, non-vacuous gate); its structural claim ("no model-exhaustion 60s wait happened") stays far below the backoff it rules out.
- Console-noise capture in `setup_all/1`: `llm_error_failfast_test`, `tool_dispatch_retry_slot_test` and `context_compression_fail_fast_test` each wrap their ReqLLM warm-up call in `ExUnit.CaptureLog.capture_log/1`.
  The warm-up's request to the dead loopback `http://127.0.0.1:1` makes ReqLLM's Finch pool PROCESS log 3× `[warning] Retrying streaming request after transient transport error` + 1× `[error] Finch streaming transport failed`; those come from another process, so the per-test `capture_log: true` cannot attribute them and they would leak to the console.
  Wrapping the warm-up call swallows exactly those lines without changing what the warm-up does (the in-test connection-refused attempts produce none — the pool is already poisoned by the warm-up).
- No new production seam was required for these three modules: every real wait they exercise goes through an EXISTING call-time app-env seam (`:llm_retry_backoff_base_ms`; the exhaustion seams below).
  The remaining hardcoded real-sleep timer in this layer is `Runner.setup_dispatch_context/1`'s crash-retry wait `Process.sleep(30_000 * retries)` (`runner.ex:332` repo-less, `:361` normal) — it has NO seam and these three modules do NOT exercise it (they call `ToolDispatch` directly); a future test that drives the crash-retry path would need a new call-time seam.
- Model-exhaustion (HTTP 402 "insufficient balance") retry timing has TWO app-env seams, read at call time by `EvoGit.Agent.LlmRetryPolicy`: `:llm_model_exhaustion_backoff_base_ms` (default 60_000) and `:llm_model_exhaustion_backoff_cap_ms` (default 28_800_000).
  `llm_retry_policy_test` (NEW) shrinks them (10/80 → a 15-entry, 1.03s-total schedule) to pin the schedule math; production keeps the 60s-doubling-to-8h default.
  Tests must NEVER sleep hours: `tool_dispatch_retry_slot_test`'s 402 tests assert the DEFAULT 60s / 8h backoff by reading the scheduler's `llm_backoff_until` and by asserting the retry queues behind it (`AgentScheduler.get_llm_slot_status/0`) — the wait itself is never performed (the blocked task is killed and its pool purged in `on_exit`).
- `EvoGit.TestLlmServer` (`test/support/llm_server.ex`) is the raw-TCP HTTP/1.1 harness for real LLM HTTP error responses: `start!/2` (status + body) returns a `%{port:, url:}` whose `url` is handed to a fake model spec's `base_url`, so ReqLLM surfaces a genuine `%ReqLLM.Error.API.Request{}` (e.g. 402) to the retry loop.
  `llm_error_failfast_test.exs` drives the 400 fail-fast end-to-end through it (exactly one request + one `Logger.error`, no backoff, no slot left — plus the 402/500 negatives), asserting the delivered `{:error, {:llm_request_rejected, message}}` also carries the self-diagnosing tail (`Request parameters sent: …` / `Check the model profile for model …`) and that the per-attempt debug log line names the parameters sent.
  `context_compression_fail_fast_test.exs` reuses the same harness to drive `EvoGit.Agent.ContextCompression.compress_if_needed/2`'s failure paths end-to-end: HTTP 400 → the terminal `{:error, {:llm_request_rejected, msg}}` tuple (one request, one `Logger.error`, no scheduler backoff, slot released), and HTTP 500 / HTTP 402 ("Insufficient Balance") / a refused transport → the pre-existing `MatchError` whose `term` is `{:error, %ReqLLM.Error.API.Stream{...}}`.
- `llm_error_test.exs` (`async: true`) covers the whole pure `EvoGit.Agent.LlmError` surface: `non_retryable?/1` classification + wrapper peeling (incl. the phrase-less-402-stays-retryable-at-any-wrapping-depth block), `format_failure/1,2` (including the self-diagnosing parameter-name / model-spec tail and its omission rules), `parameter_names/1` (incl. its totality across struct/tuple/number/function/pid/ref inputs and the `:__struct__` marker-key rejection) and `format_parameter_names/1`.
- **A stale row in the app-global `:evogit_agent_state` ETS table for a SMALL LITERAL agent id silently reroutes an LLM slot request to another model pool.**
  `EvoGit.AgentScheduler.Slots.resolve_model_id/2` takes the requesting agent's pool from that VM-global table and falls back to the scheduler default model id ONLY for an id with NO row, so a leftover row sends the request to a different — usually EMPTY — pool where it is granted IMMEDIATELY instead of queueing.
  Nothing logs the misroute; the only observable is that the per-model entry the test reads (`AgentScheduler.get_llm_slot_status/0` keyed by the EXPECTED model id) simply never moves, so a state-anchored wait burns its whole (generous) budget and flunks.
  `agent_scheduler/slots_test.exs` is a known leaker: its `on_exit` clears only `:evogit_sched_meta` after inserting ids 1-4 and 99 on a second model (`"fast"`), so any later module in the same BEAM can observe a stale row for exactly those ids.
  **Rule for this directory**: any test that drives the slot pool with a small literal id must REGISTER an explicit `:evogit_agent_state` row for it (e.g. `register_agent/1`, which sets `model_id: @model_id`) so the POOL — not just the queue state — is deterministic. Do NOT rely on the "unknown id resolves to the default model" fallback across the suite.
- `tool_dispatch_retry_slot_test` stays state-anchored: it synchronizes on `AgentScheduler.get_llm_slot_status/0` (per-model `used`/`waiting`/`capacity`) and `AgentScheduler.paused?/0` rather than fixed sleeps.
  Both ids its slot hand-offs drive (owner `@slot_owner_agent_id` 99 and probe `@probe_agent_id` 2) are registered FIRST — via `acquire_llm_slot/1` and at the probe's request site — which pins their model pool to `@model_id` (see the stale-row bullet above); neither relies on the unknown-id default fallback any more. The probe still has NO `:evogit_sched_meta` row, so it stays at depth 999 and the release sweep keeps preferring the earlier queue entry.
  Its two slot-re-acquisition tests are built so NO assertion depends on the test process winning a wall-clock race against the retrying agent's backoff windows.
  In "releases the LLM slot between retry attempts", the probe agent's slot request is PRE-QUEUED from a separate `Task` while the owner still holds the only slot (asserted via `await_llm_waiting(2)`), so the SCHEDULER's own release sweep — not a reactive re-acquisition by the test process — grants the probe inside the between-attempts interval; the retrying agent's next attempt then provably re-queues behind the probe's persistently-held slot.
  In "a paused scheduler blocks the retrying agent's next attempt at slot re-acquisition", `AgentScheduler.pause/0` is called BEFORE the owner's slot is released, so the pause is in place before ANY attempt acquires the slot — this relies on the verified fact that the release sweep is not paused-gated (`Slots.handle_release_llm_slot/2` → `grant_pending_llm_slots/1` has no `paused` check), which lets the queued first attempt run while its successor is then blocked by the pause (`used: 0` + `waiting: 1` + `paused: true`).
  Grant order is deterministic: the probe (`@probe_agent_id`) has its `:evogit_sched_meta` row deleted so it sits at the absent-default depth (`Slots.depth_of/1` → 999), and `better_entry/5` prefers the EARLIER queue entry on a full tie, so the first attempt is always granted before the probe.
  Cleanup releases all three agent ids (`@slot_owner_agent_id`, the retrying agent, `@probe_agent_id`) twice from ONE `on_exit` process (ordered casts) so a flunked assertion cannot leave a holder that a later release-sweep would otherwise promote from the waiting queue.
- The ~2.5-3.4s `LLMDB.load/1` cost is llm_db decoding its packaged 8.6 MB `priv/llm_db/snapshot.json` (MEASURED 2.54s standalone) and is a **per-BEAM one-off**: within ONE `mix test` invocation only the FIRST ReqLLM-touching module pays it (later ReqLLM calls reuse the `:persistent_term` cache); run standalone, each file pays it once.
  It is NOT Finch per-origin pool creation (a fresh destination costs ~2-3ms once the catalog is loaded) and is not reducible from `apps/evo_git/test/` — each module's `setup_all/1` warm-up only stops it being charged to whichever TEST runs first; it does not lower total wall clock.
  A single shared warm-up (e.g. in `test/test_helper.exs`) would move the one-off out of the first module's `setup_all` for better attribution at the same total wall clock — NOT implemented (that file is owned outside this node).
- `tool_dispatch_test`'s parallel-shell test proves concurrency by an EVENT-DRIVEN rendezvous: each command appends its start marker, then waits (bounded at 400 × 50ms = 20s) for the PEER's start marker before appending its end marker.
  The concurrency proof is the marker interleaving (`start2` before `end1`) — a serialized run exhausts the bound and fails; no wall-clock bound is asserted.
  The POSIX `run_bash` and Windows `run_powershell` command strings differ and are built by the test's `parallel_marker_commands/1`.
- The only fake-LLM harness is `EvoGit.TestLlmServer` (raw-TCP, answers a fixed status + JSON body; `request_count/1` exposes the additive per-server request counter used to assert how many LLM attempts were actually issued), consumed by `tool_dispatch_retry_slot_test` (402 model-exhaustion retry), `llm_error_failfast_test` (400 fail-fast: exactly one request + one `Logger.error`, no backoff, no slot left — plus the 402/500 negatives) and `context_compression_fail_fast_test` (compression 400 terminal + 500/402/refused-transport `MatchError`); agent runs to COMPLETION are still exercised only through error paths (`without_model_profiles/1`, connection-refused model specs, and the test server's HTTP 402).
  Details in `../CONTEXT.md` ("Known Issues & Test Env Notes").
- Same-named `test` cases across different `describe` blocks cover DIFFERENT functions (e.g. in `context_builder_test`, `delegation_hints_test`, `turn_warning_test`) — not duplicates.
- **A wait deadline is NOT a correctness lever.** Widening a `@load_robust_deadline_ms`-style budget can never fix a slot test: the awaited transition must be reachable BY CONSTRUCTION (the requesting id's model pool AND queue state pinned by the test itself). Whenever a slot test's outcome differs between idle and loaded runs at the SAME seed, suspect a routing/global-state difference rather than an undersized budget - a scheduler-side wait that keeps receiving fresh per-model statuses while never reaching its expected value is a REACHABILITY failure, not a latency one.
- **No production seam is required for this directory's slot-pool determinism** - the fix is entirely test-side registration.
  If one were ever wanted, the natural one is a call-time app-env seam around `EvoGit.AgentScheduler.Slots.resolve_model_id/2` (e.g. `:slots_resolve_model_id_fun`, read at call time, production default unchanged); the minimal alternative is a debug log in that function, because a mis-routed pool is currently COMPLETELY silent (no log, and `Lifecycle.apply_status_updates/1` no-ops without a sched-meta row), leaving the per-model `get_llm_slot_status/0` entry as the only observable.
- `subagent_processing_test.exs` runs slightly over the ~1000-line soft cap (~1046 lines) because it is ONE comprehensive suite over the subagent-processing surface (path resolution, phylo-node building, spawn-gate result formatting, real-builder authority coupling, model-id inheritance) sharing the same global-ETS + real-git-repo setup — splitting it would duplicate that setup for no cohesion gain, so it is intentionally NOT split. Prefer adding new subagent-processing tests to an existing `describe` block here.
- Full-suite parallel-run flakiness is pre-existing and documented in `../CONTEXT.md`.
