# evo_git/agent — Agent Test Tree

## Intent

ExUnit suites for the `:evo_git` agent layer (`EvoGit.Agent.*`): the `Exchange` turn loop (cancel-grace, turn limits/warnings, pending-message drain, background-job notices) driven through its opts seams, context building/compression, subagent processing, tool dispatch, and usage/delegation/result/output helpers.
Each file mirrors its source module under `apps/evo_git/lib/evo_git/agent/`.

## Async-Safety Policy (this directory)

A module is `async: true` ONLY if it mutates no BEAM-global state observable by a concurrently running module.
Every `async: false` module names its exact forcing global in its `@moduledoc`; when in doubt, keep `async: false`.

## Grace Budget & Report-Window Contract (`turn_limit_test.exs`, `cancel_grace_test.exs`, `turn_warning_test.exs`)

`Exchange.Grace`'s `@turn_limit_grace_turns` is 3 — the SAME budget as `@cancel_grace_turns` — because a tool-calling turn never finishes the run, so the window must fit the ONE permitted final commit PLUS the tool-free report turn.
`EvoGit.Agent.grace_period_continue_failed?/1` hard-stops at `grace_turns_remaining <= 1` (and at the struct default 0), so a budget of 3 yields exactly 3 continued turns then `{:error, :recovery_failed}`; both grace kinds share that predicate and its boundary.
`turn_limit_test.exs` pins the pure predicate/boundedness (3 and 2 allowed, 1 and the default 0 hard-stop, a `continue_until_fail/2` simulation proving exactly 3 continues); `cancel_grace_test.exs` pins the same through `Exchange.Grace.enter_grace/3` (turn-limit recovery grants `grace_turns_remaining == 3` and the budget is `> 1` and finite).
`enter_grace/3`'s recovery message (`recovery_warning_message/2`, no-objective and objective variants) must state: the exceeded turn budget with its reason, 3 final turns left, that a reply with NO tool calls ends the run and its text IS the report, that a turn ending with a tool call does NOT finish the run, that there will be NO report at all, at most ONE final commit, that already-committed work is safe, the honest-partial-report instruction (what was done with the commit, what remains, what a follow-up must pick up / "If you cannot complete the entire objective, that is acceptable: stop …"), plus the objective block and the "ENTIRE objective" summary requirement.
Both variants are asserted to contain no `"LOST"` claim (an uncommitted tree is auto-committed on exit).
`TurnWarning.message/1`'s `:end` and `:critical` texts are pinned to the same completion contract, including `:critical`'s "any further tool call ends the run immediately with NO report at all" and "a truthful partial report is a success here"; the `end_remaining`/`critical_remaining` threshold math has its own tests.

## Pure Exchange Engine Coverage (`exchange_golden_test.exs`)

The loop is testable WITHOUT a process: `Exchange.run(state, opts)` takes every collaboration point as an `opts` function, so a plain ExUnit process drives a whole run with no scheduler boot and no ETS-driven loop state.
Seam contracts: `llm_call: (context, tools, llm_generation_params, agent_id, max_retries) -> {:ok, response} | {:implicit_completion, response, text} | {:error, reason}`; `tool_batch: (indexed_calls, state) -> [{index, tool_call_id, name, output}]`; `scheduler: (kind, payload, state) -> term()` with the CONTROL-PLANE kinds `:drain_inputs`, `:cancel_requested?`, `:clear_cancel` and `:pause_requested?` (payload = agent id) ONLY (the `:context`/`:total_tokens`/`:turn`/`{:batch, fields}` ETS write-through kinds are gone); `checkpoint: (state) -> term()` (return value discarded).
A bare process still passes a `scheduler:` stub because the default arms reach `EvoGit.AgentScheduler.Store` (the drain/flag control plane), so an in-memory stub keeps an unwatched exchange runnable with no ETS row; per-turn publication is asserted through the `checkpoint:` seam.
The seams are passed as `opts` ONLY, never through the app-env keys (`:agent_exchange_llm_call` / `:agent_exchange_tool_batch` / `:agent_exchange_scheduler`), which are process-global and would serialize the module.
Clock determinism: `metadata[:timestamp]` is stamped through `EvoGit.Agent.Clock.now_seconds/0`, so any test comparing TWO exchanges' contexts or messages MUST pin `now: <fixed Unix second>` (the wall clock otherwise straddles a second boundary and the runs differ ONLY in that metadata); `EvoGit.Agent.Clock` keeps the pin in the process dictionary, so it is async-safe and needs no app-env global, and `clock_test.exs` pins the mechanism.
The golden test scripts three turns (`read`+`rg`, `write`, a plain-text reply) and pins in ONE assertion set: the exact `{turn, [{tool_name, args}]}` call sequence; three `llm_call` invocations with append-only growing contexts (each request is the previous prefix plus the new turn) and `tools` equal to `available_tools/0`; the resulting roles `[:system, :user, :assistant, :tool, :tool, :assistant, :tool, :assistant]` with assistant tags `[1, 2, 3]` and tool tags `[1, 1, 2]`; `state.turn == 3`; the terminal `{:finish, state, %Result{result: "scripted report text"}}`; the scheduler kinds per turn (loop-top `[:drain_inputs, :cancel_requested?, :pause_requested?]`, a batch turn adding the BATCH-boundary `:pause_requested?`, nothing else); and exactly ONE checkpoint per turn (`turn == [1, 2, 3]`, `total_tokens == [120, 120, 120]`, cumulative `usage.input_tokens == [100, 200, 300]`, each checkpointed context byte-equal to the NEXT request's).
It also pins that an unwatched exchange stays invisible: no watcher → no callbacks and no broadcast, so `state.watchers == %{}` after the run.
Residual coupling: `ToolDispatch.build_completion/2,3` reads the agent's scheduler row, so a COMPLETION-path case installs one uniquely-keyed production-shaped `%EvoGit.AgentScheduler.AgentState{}` row and deletes it in `on_exit`; the repo-less write guard needs `Process.put(:repo_less, true)`.
`EvoGit.Agent.Runner` is a helper module only (`refresh_commit_sha/1` plus `@doc false` delegates `check_limit_warnings/1`, `drain_and_inject_user_messages/1,2`, `inject_background_job_notices/1,2`, `enter_grace/2,3`, `maybe_enter_cancel_grace/1`), so a suite may reach the same behaviour through the Runner shim; session-level publication is covered by `exchange_checkpoint_seam_test.exs` and `session_test.exs`.

## Cost Recomputation Coverage (`cost_test.exs`)

One `describe` per public function of `EvoGit.Agent.Cost`.
Pins the off-peak and peak formulas against the verified `deepseek:deepseek-v4-flash` catalog rates on one shared usage fixture (`input_tokens: 14_434_811`, `output_tokens: 263_800`, `cached_tokens: 14_164_224` → cache-miss input 270_587): off-peak `0.083081 / 0.15828 / 0.241361`, peak exactly 2× (delta 2e-6, component-wise rounding), `total == round6(input + output)`.
Also pins the cache discount (cache reads billed 0.003/M instead of the full input; `cached_tokens: 0` → derived `input_includes_cached = false` → full input billed), the `token.reasoning` exclusion (a 999_999 `reasoning_tokens` fixture returns the reasoning-free result), totality (`nil` for an unresolvable model spec or non-map usage, the ZERO-cost map for `%{}`, no raise for arbitrary specs), the `apply_to_usage/3` override (only the three cost fields change; the struct stays byte-identical for nil/unknown agent ids and an unusable usage map), and period resolution via the clock seams (`period_for_profile/1`: peak vs off-peak incl. the half-open end, `off_peak_days` winning on a Monday, the `timezone` branch and its invalid-tz fallback; `period_for_model_id/1`: the temporary peak profile atom- and string-keyed, plus unknown/nil/non-matching ids → `"off_peak"`).

## Notes for Agents

- **A module that PINS `model_profiles` and then reads the per-model pool map MUST suspend `EvoGit.PeakHourEngine` for its duration** (`:sys.suspend(Process.whereis(EvoGit.PeakHourEngine))` in `setup`, `:sys.resume` in `on_exit` AFTER the profile restore — the `cost_test` / `agent_scheduler_test` idiom).
  Known users: `llm_error_failfast_test`, `context_compression_fail_fast_test`, `tool_dispatch_retry_slot_test` (setup-level suspend), `cost_test` (`with_peak_profiles!/1` suspends before installing), `provider_selection_cost_test`, `provider_model_inheritance_test`, `llm_prompting_activity_test`.
  The engine's `"scheduler_config"` wakeup is a READ-then-APPLY that is not atomic (read `model_profiles` + `default_llm_max_concurrency`, compute the floored map, then REPLACE `model_concurrency` wholesale), so a profile restore or the module's own pin landing between that read and that apply overwrites the pinned single-profile pool map with one computed from the PREVIOUS profile set.
  The pinned model id then vanishes from `AgentScheduler.get_llm_slot_status/0` (`State.all_model_ids/1` enumerates `model_concurrency`), so a `Map.fetch!` raises `KeyError`, a `Map.get(status, id, %{used: 0, waiting: 0})` reports a FALSELY clean pool, and any poll for that id is unreachable no matter how generous its deadline; the drift is TRANSIENT (the apply's own broadcast re-derives next iteration), so never widen a deadline for it.
- **Stubbed-LLM suites must declare their own provider credential.** `ReqLLM.Keys.get/2` resolves a key from `opts[:api_key]` → `Application.get_env(:req_llm, :openai_api_key)` → `OPENAI_API_KEY`, NEVER from the model spec's `api_key` field, so a stub spec carrying `api_key: "test-key"` is inert; without a resolvable key the request fails at BUILD time (`{:provider_build_failed, …}`) instead of the transport error the retry/error-shape assertions expect.
  Every module driving real `ReqLLM.stream_text/3` traffic at a loopback stub therefore sets `:req_llm, :openai_api_key` in `setup`/`setup_all` and restores-or-deletes it in `on_exit` (`implicit_completion_test`, `context_compression_stages_test`, `tool_dispatch_retry_slot_test`, `context_compression_fail_fast_test`, `llm_error_failfast_test`); a module that CLEARS credential keys snapshots and restores them (`config_test`), so the shared `:req_llm` app env never leaves a run emptier than it found it.
- Retry-backoff seam: `Application.put_env(:evo_git, :llm_retry_backoff_base_ms, ms)` is read at call time by `EvoGit.Agent.ToolDispatch.retry_backoff_base_ms/0` (production default 1_000 ms); `tool_dispatch_retry_slot_test` and `llm_error_failfast_test` pin it to 25 ms instead of sleeping through 1s/2s/4s.
  25 ms is robust because every wait is anchored on PERSISTENT scheduler state (`AgentScheduler.get_llm_slot_status/0`, `paused?/0`), never on the clock.
- Wait DEADLINES in `tool_dispatch_retry_slot_test` are deliberately generous: ONE shared `@load_robust_deadline_ms` (30_000) is the default for the slot-status poll deadline AND every `request_llm_slot`/`Task.await` timeout, since those waits are anchored on persistent scheduler state and only scheduling latency can delay them — a deadline expiry still flunks; its one elapsed-time budget uses 15_000 (tighter, non-vacuous) while the structural claim ("no model-exhaustion 60 s wait happened") stays far below the backoff it rules out.
- Console-noise capture in `setup_all/1`: `llm_error_failfast_test`, `tool_dispatch_retry_slot_test` and `context_compression_fail_fast_test` wrap their ReqLLM warm-up call in `ExUnit.CaptureLog.capture_log/1`, because the warm-up's request to the dead loopback `http://127.0.0.1:1` makes ReqLLM's Finch pool PROCESS log transient-transport retries and a transport failure from a process the per-test `capture_log: true` cannot attribute.
- Every real wait these modules exercise goes through an EXISTING call-time app-env seam (`:llm_retry_backoff_base_ms`; the exhaustion seams below) — no test-only production seam exists for them.
  The remaining hardcoded real-sleep timer in this layer is `EvoGit.Agent.Session.Setup.bind_worktree/2`'s crash-retry wait `Process.sleep(30_000 * retries)`: it has NO seam and these modules do NOT exercise it (they call `ToolDispatch` directly); a future crash-retry test would need a new call-time seam.

- **A stale row in the app-global `:evogit_agent_summary` ETS table for a SMALL LITERAL agent id silently reroutes an LLM slot request to another model pool.** `Slots.resolve_model_id/2` takes the requester's pool from that VM-global table and falls back to the scheduler default ONLY for an id with NO row, so a leftover row sends the request to a different (usually EMPTY) pool where it is granted IMMEDIATELY instead of queueing; nothing logs the misroute, and the per-model entry the test reads simply never moves, so a state-anchored wait burns its whole budget and flunks.
  **Rule for this directory**: any test that drives the slot pool with a small literal id must REGISTER an explicit `:evogit_agent_summary` row for it (e.g. `register_agent/1`, which sets `model_id: @model_id`) so the POOL — not just the queue state — is deterministic; never rely on the "unknown id resolves to the default model" fallback across the suite.
- `tool_dispatch_retry_slot_test` stays state-anchored on `get_llm_slot_status/0` and `paused?/0`, never fixed sleeps: both ids it drives (`@slot_owner_agent_id` 99, `@probe_agent_id` 2) are registered FIRST, pinning their pool to `@model_id`, and the probe has NO `:evogit_sched_meta` row so it sits at depth 999 and the release sweep prefers the earlier queue entry.
  Its two re-acquisition tests avoid wall-clock races: in "releases the LLM slot between retry attempts" the probe's request is PRE-QUEUED from a separate `Task` while the owner still holds the only slot (asserted via `await_llm_waiting(2)`), so the SCHEDULER's own release sweep grants it between attempts; in "a paused scheduler blocks the retrying agent's next attempt" `pause/0` runs BEFORE the owner's slot is released, relying on the release sweep being not paused-gated (`Slots.handle_release_llm_slot/2` → `grant_pending_llm_slots/1` has no `paused` check).
  Cleanup releases all three agent ids twice from ONE `on_exit` process (ordered casts), so a flunked assertion cannot leave a holder a later release sweep would promote.
- The ~2.5-3.4 s `LLMDB.load/1` cost is llm_db decoding its packaged snapshot, a **per-BEAM one-off**: within ONE `mix test` invocation only the FIRST ReqLLM-touching module pays it (later calls reuse the `:persistent_term` cache), and run standalone each file pays it once.
  It is NOT Finch per-origin pool creation (~2-3 ms once loaded) and is not reducible here; each module's `setup_all/1` warm-up only stops it being charged to whichever TEST runs first.
- `tool_dispatch_test`'s parallel-shell test proves concurrency by an EVENT-DRIVEN rendezvous: each command appends its start marker, then waits (bounded at 400 × 50 ms = 20 s) for the PEER's start marker before appending its end marker, so the proof is the marker interleaving (`start2` before `end1`) and no wall-clock bound is asserted; the POSIX `run_bash` and Windows `run_powershell` strings come from `parallel_marker_commands/1`.
- Same-named `test` cases across different `describe` blocks cover DIFFERENT functions (e.g. in `context_builder_test`, `delegation_hints_test`, `turn_warning_test`) — not duplicates.
- Coverage is split so each OUTPUT shape has ONE owner — `tools_test.exs` keeps only internal dispatch-key routing plus the model-facing schema/classification/gating describes (the `edit_file` / `make_dir` / `read_file` output shapes live in `tools/file_edit_test.exs`, `tools/make_dir_test.exs`, `tools/file_read_test.exs`), and `delegation_hints_test.exs` keeps per-input families table-driven (every case kept, with the prefix look-alikes `./src` vs `./src_backup` / `./lib` vs `./lib_test` retained verbatim).
- **A wait deadline is NOT a correctness lever.** Widening a `@load_robust_deadline_ms`-style budget can never fix a slot test: the awaited transition must be reachable BY CONSTRUCTION (the requesting id's model pool AND queue state pinned by the test itself); a scheduler-side wait that keeps receiving fresh per-model statuses while never reaching its expected value is a REACHABILITY failure, not a latency one.
- **No production seam is required for this directory's slot-pool determinism** — the fix is entirely test-side registration; if one were ever wanted, the natural one is a call-time app-env seam around `Slots.resolve_model_id/2` (e.g. `:slots_resolve_model_id_fun`), since a mis-routed pool is currently COMPLETELY silent and the per-model `get_llm_slot_status/0` entry is the only observable.
- `subagent_processing_test.exs` runs over the ~1000-line soft cap because it is ONE comprehensive suite over the subagent-processing surface (path resolution, phylo-node building, spawn-gate result formatting, real-builder authority coupling, model-id inheritance) sharing one global-ETS + real-git-repo setup — splitting it would duplicate that setup for no cohesion gain, so add new subagent-processing tests to an existing `describe` block.
  Like `context_merge_test.exs` it builds repos from a per-module git template, and its merge-wiring fixtures are the module's own `git fast-import` graph copied from a per-scenario snapshot.
- Full-suite parallel-run flakiness is pre-existing and documented in `../CONTEXT.md`.
