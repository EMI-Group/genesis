# evo_git/store — Test Tree

## Intent

Tests for the Ecto persistence layer of the SQLite store — the pure Operation modules (incl. the relational per-agent archive), the Ecto.Type wire formats (plain JSON TEXT — no compression), the boot/migration machinery (the six shipped migrations: baseline adoption — the ONE schema-creating step — data normalization, composite indexes, covering indexes, the merged `task_agent_archives` create + legacy-archive fan-out + column drop, and the redundant-index prune), the fresh-database canonical-schema proof, the dynamic-repo plumbing, the DBConnection pool size + maintenance, the facade's read fault isolation and write offload, and the error classifier.
All of them drive REAL unnamed dynamic `EvoGit.Repo` instances (`EvoGit.Store.Boot.start_dynamic/2`) on unique tmp SQLite files, except `types_test.exs`/`errors_test.exs`, which open no database at all.
The per-agent archive is a RELATIONAL table (`task_agent_archives`, one row per `(task_id, agent_id)`, plain JSON text columns, no compression), written STREAMING at agent completion through `EvoGit.Agent.Tools.CompleteTask.write_archive_refs/7` → `EvoGit.TaskRegistry.put_task_archive/1` → `EvoGit.Store.put_task_archive/2`; the suites here pin its Operations layer and the ONE migration that both creates the table and moves a legacy archive into it.
The released-version upgrade path has its own suite (`v0138_upgrade_path_test.exs`): a RAW-crafted v0.13.8 database (stamped only with the three migrations that release shipped) driven through the REAL pending set `…00004` … `…00006` — the one shape the per-migration suites deliberately do not cover.
Twenty of the twenty-five modules here are `async: true`; `pool_size_test.exs`, `store_write_offload_test.exs`, `maintenance_test.exs`, `read_fault_isolation_test.exs` and `archive_migration_test.exs` are deliberately `async: false` (see Constraints).
Most suites copy ONE schema-complete SQLite TEMPLATE per test BEAM (`EvoGit.TestSupport.StoreTemplate`) instead of re-running the DDL per test; the migration/schema-adoption suites keep a fresh real boot on purpose, because the boot IS the behaviour they assert.
The suites that terminate/restart the app-global `EvoGit.Store`/`EvoGit.TaskRegistry` singletons live one level up (`../store_test.exs`, `../store_summary_test.exs`, `../store_disk_full_test.exs`, `../migrate_store_test.exs`); `store_write_offload_test.exs` here is stateful too, but on an ISOLATED `EvoGit.TaskRegistryCase` store.

## Constraints

- **Async policy**: every module here is `async: true` except `pool_size_test.exs`, `store_write_offload_test.exs`, `maintenance_test.exs`, `read_fault_isolation_test.exs` and `archive_migration_test.exs`, which MUST stay `async: false` for the reasons in their own `@moduledoc`s — timing-sensitive concurrency/latency assertions that must not compete for CPU with sibling tests (and, in `pool_size_test`, tests that stop/start their own repos), a crash-semantics test that deliberately takes its store and its writer down, suites that stop the isolated store or swap a global app env, and `archive_migration_test`'s skipped-payload dump, which lands in the SHARED platform `migration_dumps` dir (other migration suites seed undecodable archives too) while one test temporarily blocks that path with a regular file.
  Do NOT flip those five to `async: true`, and do NOT flip the `async: true` modules to `async: false` — the async cohort shares no test-mutated BEAM global.
- **Schema template** (`EvoGit.TestSupport.StoreTemplate`, `test/support/store_template.ex`): `new!/0` returns a `destination -> destination` copy fun over ONE migrated, checkpointed SQLite file per test BEAM (~23 ms of real store boot replaced by a ~2 ms copy); every test still gets its own database FILE with the identical schema.
  The BEAM-wide template is cached in `:persistent_term` behind the same `:global.trans/2` double-checked idiom `EvoGit.Store.Boot` uses for its migration run, so concurrent `async: true` `setup_all/1` blocks build it exactly ONCE and every later module pays only the copy.
  The template file is IMMUTABLE (the only operation on it is `File.cp!/2`) and every copy is COMPLETE: the build runs a real boot → `PRAGMA wal_checkpoint(TRUNCATE)` → `EvoGit.Store.Boot.stop/1` → strips the `-wal`/`-shm` sidecars → asserts `sqlite_master` carries `tasks` (a template whose schema still sat in `-wal` would copy an EMPTY database).
  Its cleanup is a `System.at_exit/1` handler, never a module `on_exit/1` — the template outlives every module in the BEAM, so a module-scoped delete would remove the file under a still-running one.
  It is used by `store_test`, `store_summary_test`, the `operations/` suites, `repo_scope_test`, `store_invariants_test`, `task_page_api_test`, `maintenance_test` and `EvoGit.TaskRegistryCase`; the migration/schema-adoption suites (`boot_*`, `archive_migration`, `covering_index`, `composite_index`, `canonical_schema`, `v0138_upgrade_path`) keep a FRESH real boot because the boot is the behaviour under test, and `pool_size_test` builds its OWN checkpointed per-module template (it stops and restarts repos, so it must not consume a shared one).
- **Concurrent-boot safety lives in PRODUCTION, not in tests**: `EvoGit.Store.Boot` wraps the migration run in a cluster-safe `:global.trans({{:evo_git_store_migrations, self()}, fun})` lock and hands `Ecto.Migrator.run/4` the PRE-LOADED `[{version, module}]` source (`Boot.migration_source/0`) instead of the migrations DIRECTORY, so the `.exs` files are compiled at most ONCE per BEAM and no already-loaded module is ever redefined.
  The lock id is a single GLOBAL constant (NOT per repo path/instance) because the protected resource is the shared set of migration SOURCE modules; the `self()` LockRequesterId is what makes it exclude — a CONSTANT requester id is silently re-entrant (no exclusion).
  Tests call `Boot.start_dynamic/2`/`Boot.run_migrations/1` directly (the REAL production path) — no test-side lock wrapper is needed or allowed.
- **Pool size**: the store's production default is `EvoGit.Store.Boot.default_pool_size/0` (6), overridable per store with `:pool_size`; `mix migrate.store` deliberately pins `pool_size: 1`, and only such a deliberately-one-connection store supports the connection-scoped `PRAGMA query_only` disk-full arm — `../store_disk_full_test.exs` restarts its isolated store with an explicit `pool_size: 1` for exactly that reason.
- Assertions are intentionally **exact** (full return shapes, key sets, raw bytes where the output is deterministic) — keep them; do not weaken to `contains?`/smoke checks.
- No mocking libraries: inputs are plain literals and `%EvoGit.Agent.Usage{}`/`%TaskInfo{}`/datetime structs; legacy fixtures are raw SQL through xqlite.

## Notes for Agents

- Prefer an EVENT over an observation window: "a write is in flight" is constructed by holding the DB write lock externally (`BEGIN IMMEDIATE`), "the pool is saturated" is the pool's own `checkout_queue_length`, "every connection is ready" is a poll to `ready_conn_count == N`, and "nothing else happened" is a zero-wait `refute_receive … , 0` after a synchronous call — do not reintroduce fixed `refute_receive …, 200` windows.
- Tmp DB filenames must be unique ACROSS BEAM restarts too — embed the wall-clock ms (`System.system_time(:millisecond)`) alongside `System.unique_integer` + `inspect(self())`; a counter+pid alone collides with a previous run's leftover file and silently reopens its stale rows.
- Every per-test tmp DB must ALSO be deleted on exit: `File.rm` the DB plus its `-wal`/`-shm` sidecars (`{:error, :enoent}` for a missing path must not raise) — a merely unique name still leaves one file per test behind (136/270/408 leftovers after 3 consecutive store-suite runs before the cleanup landed).
- `ExUnit.CaptureIO.capture_io(:stderr, fun)` is GROUP-LEADER scoped, so inside an `async: true` module it captures only THIS test process's stderr (and the processes it spawns) — compiler-warning assertions stay deterministic.
  `boot_migration_source_test.exs` pins the absence of `redefining module` text around fresh-DB boots that way; `Boot` compiles inside the calling process.
- The dynamic repo is UNLINKED from the test process (`on_exit/1` runs after the process exits) and stopped through an alive-guard (`Boot.stop/1` on a dead pid RAISES "no process" — tests that stop their instance manually need `if Process.alive?(pid)` in cleanup).
- `types_test.exs`/`errors_test.exs` open NO database — pure function tests (zero xqlite calls, no `setup` blocks); the boot/operations/repo/pool suites open real databases under `System.tmp_dir!/0`.
- Normalization runs DURING boot, so pre-normalization data CANNOT be seeded through a booted repo (a second boot finds no pending migrations and never re-runs the rewrite) — `boot_normalization_test.exs` seeds RAW and only then calls `Boot.start_dynamic/1` (the path-only form, like the sibling `boot_migration_test.exs`).
- Both `pool_size_test.exs` and `store_write_offload_test.exs` reach the store's raw connection through the `EvoGit.Store.__repo_pid__/1` accessor plus `XqliteEcto3.with_xqlite/2` (the adapter's supported checkout) — `store_write_offload_test.exs` reuses that seam for its `PRAGMA query_only` disk-full arm, exactly like `../store_disk_full_test.exs`.
- `archive_migration_test.exs` builds its RAW fixtures through a connection opened with `journal_mode: :memory, synchronous: :off`: durability is meaningless for a throwaway fixture, and `journal_mode` for the rollback-journal modes is a CONNECTION-ONLY setting that is never recorded in the file, so the boot still upgrades the database to WAL exactly as production does.
  Its store helpers pin `pool_size: 1` (`Boot.start_dynamic/2` in `start_repo!/1`, `Store.start_link/1` in `start_store!/1`): these repos are driven strictly serially from the test process, so the production default's other five connections would only be opened and torn down per test for nothing.
- `store_write_offload_test.exs` allocates its 2 MB `@slow_result_bytes` payload ONCE in `setup_all/1` and hands every test the same refc binary — a reference, not a copy per test.
- The parent `../CONTEXT.md` (and the one above it at `../..`) documents the app-global store suites one level up, their shared-test-DB cautions, and the `EvoGit.TaskRegistryCase` isolated-store seam used by `store_write_offload_test.exs`.
