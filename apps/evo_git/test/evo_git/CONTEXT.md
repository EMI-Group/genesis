# evo_git — Test Tree

## Intent
ExUnit suites mirroring the source tree under `apps/evo_git/lib/evo_git/`.
The top-level `*.exs` files in THIS directory cover whole subsystems (CLI, remote, review, store, config, peak hours, system sampler, …); subdirectory files mirror lib paths and are documented by the child CONTEXT.md files below — do not duplicate that per-file detail here.
All suites use real git operations on temp dirs; none use mocks.

## Top-Level Modules — Async-Safety Map
Applies the policy in `../CONTEXT.md` → "Async-Safety Policy".
Do NOT flip these to `async: true`:
- XDG / OS-env redirectors (`System.put_env` on `XDG_CONFIG_HOME`, or `PATH` for `EvoGit.FakeGh`): `config_test`, `custom_agents_test`, `custom_agents_rpc_test`, `custom_tools_test`, `custom_tools_rpc_test`, `remote_connections_test`, `remote_connection_test`, `platform_test`, `distribution_test`, `git_env_test`, `remote_node_github_test`, `task_tmpdir_test`, `cli_agent_flag_test` (also rewrites the live scheduler `:model_profiles`).
- Shared app singletons / global ETS / global scheduler config: `system_sampler_test`, `peak_hour_engine_test`, `worktree_main_head_safety_test`, `application_test`, `sandbox_slice_test`, `sandbox_process_registry_test`, `self_reflective_source_test`, `system_check_test`. Each of those files' `@moduledoc` names its exact forcing global (`sandbox_slice_test` → the app-level `EvoGit.SandboxSlice` singleton; `sandbox_process_registry_test` → the globally named `EvoGit.SandboxProcessRegistry`; `system_check_test` → the `:evogit_nix_dev_env_state` `:persistent_term` written by `EvoGit.Nix.reset_state/0`).
- Global scheduler / global app-env mutators: `command_shell_test` (setup writes app-env `[:evo_git, :command_approval_timeout]`, read per request by `EvoGit.CommandApproval`; `without_model_profiles/1` also rewrites the global `EvoGit.AgentScheduler`'s `model_profiles`), `command_approval_test` (both `EvoGit.CommandApprovalTest` and `EvoGit.CommandApproval.RequestTest` write the same `:command_approval_timeout` key; `RequestTest` additionally unregisters the app-booted `EvoGit.CommandApproval` name for one test), `cli_task_routing_test` (setup redirects the process-wide `XDG_CONFIG_HOME`; `without_model_profiles/1` rewrites the global scheduler's `model_profiles`).
- `EvoGit.TaskRegistryCase` starts uniquely-named ISOLATED `EvoGit.Store`/`EvoGit.TaskRegistry` instances (no app-global mutation), so `use`ing it does NOT by itself force `async: false` — a module's async setting is decided by the globals above.
- `store_test` / `store_summary_test` do NOT use the case: they terminate/restart the app-level `EvoGit.Store` + `EvoGit.TaskRegistry` supervision children for the whole module and register their per-test isolated Store under the canonical `EvoGit.Store` name, so they must stay `async: false`.
- `evo_git_test.exs` (repo-root file) is stated explicitly as `async: false`, and its `@moduledoc` names its forcing globals: `XDG_CONFIG_HOME` via `System.put_env/2` + the `:nix_enabled` app-env key.
Genuinely `async: true` (verified to mutate no shared global): `attachments_test`, `cli_test`, `commit_graph_test` (own temp git repo per test; only cross-process write is the per-repo-path `EvoGit.GitEnv` identity memo), `epmd_dist_test`, `executable_test`, `migrate_store_test`, `path_suggestions_test`, `peak_hours_test`, `powershell_test`, `project_config_test`, `prompt_file_test`, `remote_bootstrap_test`, `remote_node_test`, `req_llm_pool_test` (drives a private standalone Finch, never the production `ReqLLM.Finch`), `review_test`, `skills_hierarchical_test`, `skills_test`, `store_disk_full_test` (arms `PRAGMA query_only` on its OWN isolated Store connection only), `utf8_test`. The pure Ecto-layer unit suites under `store/` (operations, types, boot_migration/boot_normalization, repo, repo_scope, errors) are all `async: true` too — see `store/CONTEXT.md`.

### Store persistence-layer suites (store_test / store_summary_test / store_disk_full_test / migrate_store_test + the pure unit tree in store/)

**store_test / store_summary_test — schema template + canonical name**: both build a schema-complete SQLite file ONCE in `setup_all` (a real `Store.init` + `GenServer.stop` — init/terminate both run `PRAGMA wal_checkpoint(TRUNCATE)`, leaving a single byte-copyable file with no `-wal`/`-shm` sidecars) and `File.cp!/2` it per test, instead of re-running the DDL per test (~24ms → ~2ms each).
The production `Store`/`TaskRegistry` are terminated for the whole module (`Supervisor.terminate_child(EvoGit.Supervisor, ...)` — TaskRegistry first, it depends on Store) and restored once in `setup_all`'s `on_exit`; the per-test store is `start_supervised({Store, data_dir: sqlite_path})` with NO `name:` and therefore claims the CANONICAL `EvoGit.Store` name, addressed as the module atom `Store` first-arg everywhere.
Do NOT switch these to a single shared DB truncated between tests — several tests mutate the schema (e.g. the projects skip-and-log test re-creates `projects` with INTEGER columns) and inject malformed rows, which would corrupt later tests.
`Codec.decode_reason/1` restores a pre-existing atom with `String.to_existing_atom/1`, so a `{:error, reason}` / `{:exit, reason}` round-trip test must use a UNIQUE reason string (e.g. `"boom_" <> Integer.to_string(System.unique_integer([:positive]))`), never a fixed literal.
A fixed literal only decodes back as a string while no module anywhere in the suite contains that atom literal, so any other test using e.g. `:boom` silently flips the assertion to the atom.
Raw-conn fixtures (`set_updated_at!`, undecodable-row injection, template bulk-insert) open their own `Xqlite` connection to the test's sqlite_path — the 16-key summary contract lives in BOTH files as a duplicated `@summary_keys` module attribute, asserted via `Map.keys(summary) |> Enum.sort() == Enum.sort(@summary_keys)`.

**store_disk_full_test** (`use EvoGit.TaskRegistryCase, async: true`): arms disk-full by executing `PRAGMA query_only = ON` on the Store's OWN connection — reached through the `EvoGit.Store.__repo_pid__/1` test seam + `XqliteEcto3.with_xqlite/2` (the Store is a facade over an UNNAMED dynamic repo with `pool_size: 1`, so that single pooled connection IS every store write's connection; `OFF` clears it so a retried write succeeds without restart). Transactional writes fail exactly ONCE per arming (the adapter treats a read-only `BEGIN` failure as a `:disconnect` — the next checkout gets a fresh connection), so the arm helper is re-invoked before every write under test.
The moduledoc records WHY not alternatives: chmod 0444 does not block WAL writes, chmod 555 dirs are bypassed as root, and a `RAISE(FAIL, 'database or disk is full')` trigger surfaces as `SQLITE_CONSTRAINT_TRIGGER` (code 19) — a shape `Store.Errors.disk_full_exception?/1` deliberately does NOT classify (so it hits the re-raise crash, not the graceful path).
Pins: the classifier's accepted shapes (`read_only_database` + `sqlite_failure` codes 8/10/13 + case-insensitive "database or disk is full" message fallback; refutes `{:ok,_}`, code 19, unknown codes, `:ok`); `put_task → {:error, :disk_full}` with a "Store: DISK FULL" warning naming the sqlite path, GenServer alive, reads still work; and TaskRegistry degradation via a direct `GenServer.call(registry, {:start_task, id, :genesis, [path: ...]})` — `{:ok, %TaskInfo{}}` reply, "continuing in-memory only" log, registry alive, `list_tasks() == []` (DB-backed), `:sys.get_state(registry).task_refs` carries the task id.

**Legacy-schema/data boot adoption + migration internals**: the retired top-level `store_schema_migration_test` is superseded by the pure unit tree in `store/` — `store/boot_migration_test.exs` (SCHEMA adoption: fresh DB, current 20-col table, 15/17-col legacy prefixes, the real 19-column v0.9.0–v0.12.5 shape incl. the accepted `…,updated_at,error` adopted tail) and `store/boot_normalization_test.exs` (DATA rewrites: fixed-ms timestamps, canonical result/opts incl. positional pair arrays, branch_name/updated_at backfills, quarantine drops), both through `Boot.start_dynamic/1` on raw-xqlite-crafted legacy fixtures. Routing table + constraints: `store/CONTEXT.md`.

**migrate_store_test** (`async: true`, `@moduletag :tmp_dir`): invokes `Mix.Tasks.Migrate.Store.run([path])` DIRECTLY inside `with_io/1` — no `root:`/`shell:` seams (the mix-tasks seam scope explicitly excludes migrate.store) and no global `Mix.shell/1` swap (default Mix.Shell.IO writes to :stdio, captured by the caller). The task boots a private unnamed dynamic `EvoGit.Repo` and calls `Boot.run_migrations/1`; scenarios mirror the boot-migration suites' fixtures (fresh path, already-current DB, legacy pre-Ecto DBs adopted by the task).
The migrations' own content is covered by `store/boot_migration_test.exs` + `store/boot_normalization_test.exs` — this suite pins only the TASK's behavior around them.

**Known coverage gaps**: `store_disk_full_test` does not assert the `{:task_updated, id, :running, node()}` PubSub broadcast fired during registry degradation; the summary suites never explicitly assert absence of ORDER BY/LIMIT (all id comparisons are `Enum.sort`ed client-side — order-independence is by convention, the summary queries carry no ORDER BY); no test pins the non-disk-full re-raise crash path end-to-end (a deliberately-unclassified write error still crashes the GenServer — only the classifier `refute`s are the evidence).

### task_tmpdir_test — per-task tmpdir
Covers the whole `EvoGit.TaskTmpdir` surface: `mode/0` (all three modes + unknown value + missing config.toml → `:system`), `path_for/2` + `managed_root/1` (exact string math per mode, `to_string/1` of integer ids, no mkdir), `ensure/2` (create, idempotent, never raises on failure), `put_current/1` + `current/0` (pdict round-trip incl. the non-binary → `nil` case), `reclaim/2` (removal, idempotence, nothing outside the root is touched, and all THREE containment-guard refusals — resolved dir == the managed root itself via `task_id "/.."`, wrong parent via `"../evil"`, and non-`task_` basename via `"/../victim"`; each fixture deliberately creates the literal `<root>/task_` directory so the UN-expanded `<root>/task_/..` path stays OS-resolvable, which makes the test prove the GUARD rather than a spurious `ENOENT`).
**Config seam gotcha**: `[:tmp, :mode]` / `[:tmp, :path]` have NO app-env override — the ONLY control is process-wide `XDG_CONFIG_HOME` isolation (its `config.toml` is written directly with `File.write!`; `Config.user_config/0` revalidates the cached TOML against mtime+size). Live `XDG_CONFIG_HOME` is read by `EvoGit.Config.resolve/1`, which is why the module is `async: false`.
**Safety**: `EvoGit.Platform.tmp_paths/0` is hardcoded (`/tmp`), so `:system` mode resolves under the REAL `/tmp/genesis` — only pure path-math assertions may target it. Every test that creates or deletes files runs in `:custom` mode against a test-owned scratch dir (or `:per_repo` against a test-owned repo) so `reclaim/2` never enumerates or deletes the real `/tmp/genesis`.

### commit_graph_test — read-only commit-graph API
Covers `EvoGit.CommitGraph.for_ranges/3` and `for_task/4` (+ the `EvoGit.RemoteNode.list_commit_graph/4` delegation) on real temp-dir repos: pretty-format parsing (full 40-hex `:sha` cross-checked against `git rev-parse`, `:short_sha` prefix, subject-only `:message`, deterministic `:author_name`/`:author_email`, `%DateTime{}` `:date`, exactly the seven documented keys), `:parents` for a `--no-ff` merge (both parent SHAs) and for a root commit, cross-range SHA dedupe, the per-range `:limit` cap (plus the default 100 and the non-positive-limit fallback), invalid/unresolvable/malformed ranges skipped without raising, an empty (`base == tip`) range, the `refs` map (branch/tag short names for returned commits only — a ref pointing at the base commit is absent), a non-git directory returning exactly `{:ok, %{commits: [], refs: %{}}}`, and the local `RemoteNode` identity unwrap. `for_task/4` additionally covers: the multi-tip UNION with cross-range dedupe, the BASE COMMIT node being present (with its REAL `:parents` and its branch/tag labels) while a pre-base commit stays ABSENT, the `nil`/blank base → `{:ok, %{commits: [], refs: %{}}}` case, `nil`/blank/non-binary/duplicate tips dropped, the `:limit` cap still keeping the base node, and degradation to empty for an unresolvable base / non-git directory.
**Fixture idiom**: `@moduletag :tmp_dir` gives each test a unique dir; a real repo is created inside it and a deterministic identity is written via raw `git config` BEFORE the first adapter call, so `EvoGit.GitEnv` memoizes that identity for the test's unique repo path (the only cross-process write, which is why the module may stay `async: true`). A disjoint root commit for the root-commit case is made with `git commit-tree`; the non-git-directory case uses a dir under `System.tmp_dir!()` (never a subdir of the checkout, since git discovery would walk up to the enclosing repo).

### task_commit_graph_test — durable task-scoped commit graph
`async: true` via `EvoGit.TaskRegistryCase` (isolated `EvoGit.Store` + `EvoGit.TaskRegistry` per test) + a real temp-dir git repo per test (same raw-`git config` idiom as `commit_graph_test`). Covers `EvoGit.TaskCommitGraph.resolve_refs/1` (nil task → empty map; `commit_sha`/`branch_name` gathered; `{:ok, %{"repos" => ...}}` entries contribute both fields; blanks/nils/dupes dropped; legacy/nil result never crashes), `resolve/1` (reads the persisted row through the isolated registry; nil/unknown → empty, incl. the defensive rescue/catch), and `for_task/4`: the live-agents-only fallback (unknown task + live tip → the merge-base of HEAD and the tip recovers the base, live commits ARE returned), the durable-commit-only case (row `commit_sha` + review `base_sha` → the durable range IS returned with no live agents), `opts[:base_sha]` override winning, the matching foreign-repo entry supplying the base (both the STRING-keyed round-trip map and the `%ForeignRepo{}` struct), degradation to an empty graph, and the `RemoteNode.list_task_commit_graph/5` local identity unwrap.
**Gotcha**: a persisted `%TaskInfo{}.result` is the DECODED result — an `{:ok, data}` tuple, NOT a bare data map — so the test writes `result: {:ok, %{"repos" => ...}}` and `resolve_refs/1` unwraps it (it also accepts a bare map).
## Notes for Agents
- `EvoGit.PeakHourEngine` asynchronously rewrites the global scheduler's `model_concurrency`: it subscribes to the `"scheduler_config"` PubSub topic and re-applies an effective map from the LIVE `model_profiles`, possibly after a test's own `AgentScheduler.update_config/1`. So do NOT assert exact equality against live scheduler-derived values (`get_llm_slot_status/0`, `model_concurrency`) after mutating global config — inject a per-call seam or compare against a FRESH live read. `agent_scheduler_test.exs` instead suspends `PeakHourEngine` per test.
- `EvoGit.SystemSampler` exposes per-call app-env seams `:system_sampler_llm_slots_fun` and `:system_sampler_config_fun` (0-arity funs read PER CALL; defaults are the real bounded scheduler reads). `system_sampler_test.exs` injects them via `put_seam/2` and deletes the keys in `on_exit`; its `setup` also defensively deletes both.
- LLM retry-backoff timing is injectable via the app-env seam `:llm_retry_backoff_base_ms` (read per call by `EvoGit.Agent.ToolDispatch.retry_backoff_base_ms/0`); `agent/tool_dispatch_retry_slot_test.exs` sets it to shrink waits.
- LLM **model-exhaustion** (HTTP 402 / insufficient-balance) retry timing has its own two app-env seams — `:llm_model_exhaustion_backoff_base_ms` (default 60_000) and `:llm_model_exhaustion_backoff_cap_ms` (default 28_800_000) — read per call by `EvoGit.Agent.LlmRetryPolicy`; `agent/llm_retry_policy_test.exs` (NEW, `async: false`) shrinks both to pin the schedule math, and `agent/tool_dispatch_retry_slot_test.exs` asserts the DEFAULT 60s/8h backoffs by reading the scheduler state instead of waiting them out.
- Tests must NEVER sleep hours: a model-exhaustion backoff is asserted by reading the stored `llm_backoff_until` / the queued slot request (`AgentScheduler.get_llm_slot_status/0`) or by shrinking the seams — the default 60s first entry and the 8h cap are read, never waited on.
- Real HTTP error responses (402/429/500) for the LLM retry loop come from `EvoGit.TestLlmServer` (`test/support/llm_server.ex`) — a raw-TCP HTTP/1.1 server answering every request with a fixed status + body, driven by `base_url` on a fake model spec; no mocks and no fixtures.
- Remote daemon-health polling delay is injectable via the app-env seam `:remote_daemon_health_delay_ms` (default 1000ms, read per call by `EvoGit.RemoteConnection.daemon_health_delay_ms/0`); `remote_connection_test.exs` sets it to 20ms so each bootstrap test no longer burns a mandatory second.
- `self_reflective_source_test.exs` fixture design: its non-git resolution tests (`reference_path/0` chain precedence, `available?/0`, and the negative "marked git dir without CONTEXT.md" case) use the local `managed_dir_fixture!/1` helper — a plain temp dir carrying an empty `.git` DIRECTORY plus a `CONTEXT.md`, which are exactly the two things the production `git_repo?/1` / `genesis_checkout?/1` helpers check; no git subprocesses are involved.
- Real git fixtures in that file (`genesis_fixture!/1` — work repo + bare origin + push) are reserved for the paths that genuinely shell out: `clone/0`, `update/0` (fast-forward), and `status/0`'s partial-checkout case (`commit`/`branch`/`remote_url`).
- Do NOT re-inflate those resolution tests back to full git fixtures — that costs ~63 git subprocess invocations and ~0.8s of standalone wall clock for no coverage gain.
- The `"tasks"` PubSub topic is process-global, so an isolated `EvoGit.TaskRegistry` instance also receives OTHER instances' `{:task_updated, id, status, node}` broadcasts — safe because only `:finalizing` is handled and it is an id-pinned no-op for an unknown/stale row (no phantom row is created); make any broadcast assertion id-pinned (`assert_receive {:task_updated, ^id, ...}`) and never assert exact counts on that topic.
