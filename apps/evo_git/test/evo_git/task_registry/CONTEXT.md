## async-safety policy — 5 async fixtures, 6 serialized

The shared harness `apps/evo_git/test/support/task_registry_case.ex` starts a UNIQUELY-NAMED isolated `EvoGit.Store` + `EvoGit.TaskRegistry` per test (never touching the app-global singletons or `EvoGit.Supervisor`), and points the TEST PROCESS at them via the process dictionary (`:evogit_task_registry_server` / `:evogit_test_store`), so in-test `EvoGit.TaskRegistry.*` calls and `store()` resolve to the isolated instances. That removes the fixture as a reason to serialize — the async decision now rests solely on whether a test reaches BEYOND the fixture into BEAM-global state.

**`async: true` (5 fixture modules)** — they mutate no BEAM-global state (no app-env key, no shared `:evogit_*` ETS write, no global scheduler config) and every task id is per-test unique: `lease_heartbeat`, `cleanup`, `store_skip_and_log`, `merge_context`, `resume_context`. `store_skip_and_log_test.exs` additionally starts its OWN uniquely-named Stores and never uses the fixture's store/registry.

**`async: false` (4 modules), each with the exact forcing global named in its `@moduledoc`**:

- `persistence` — the `describe "recheck_task resolution"` `setup` does an app-global `:ets.delete_all_objects(:evogit_sched_meta)` (setup AND `on_exit`, creating the named table when absent), and the `describe "graceful cancel_task / force_kill_task"` tests seed the global `:evogit_sched_meta` / `:evogit_agent_state` / `:evogit_cancelling_tasks` tables and drive the GLOBAL `EvoGit.AgentScheduler`. The already-`async: true` sibling `agent_scheduler/subagents_test.exs` inserts/reads those same global tables, so a concurrent `delete_all_objects` would corrupt it.
- `completion_logging` — `capture_info_logs/1` lowers the process-wide GLOBAL `Logger` level for the capture window.
- `finalizing_watchdog` — `set_grace/1` mutates the app-env key `:evo_git, :finalizing_watchdog_grace_minutes`, read by every registry instance at each local-node `:finalizing` broadcast.
- `task_executor_reflect` — `without_model_profiles/1` mutates the app-global `EvoGit.AgentScheduler`'s `:model_profiles` for the duration of each test.

Also `async: true`, no fixture (pure/isolated): `runtime_opts`, `diagnostics`, `merge_context_block`, `resume_context_block`.

## Harness — `test/support/task_registry_case.ex` (125 lines, owned centrally)

- `setup` returns `{:ok, %{data_dir: root, sqlite_path: sqlite_path, store: store_name, registry: registry_name}}`; it `start_supervised!`s both children with explicit unique `:id`s (both modules hardcode `id: __MODULE__` in their `child_spec/1`) and sets `Process.put(:evogit_task_registry_server, registry_name)` + `Process.put(:evogit_test_store, store_name)` IN THE TEST PROCESS.
- Helpers: `store/0` (pdict store, else `EvoGit.Store`), `trigger_cleanup!/0` (direct `Cleanup.cleanup_expired_tasks(store())`), `cleanup_process/1`, `old_age_days/0` / `within_age_days/0` (read runtime config, fallback 14).
- Supports both `use EvoGit.TaskRegistryCase` (async) and `use EvoGit.TaskRegistryCase, async: false`.
- **pdict hazard**: the pdict is set in the TEST process only. `on_exit` callbacks run in a DIFFERENT process, so a `EvoGit.TaskRegistry.*` call or a default-store `EvoGit.Store.*` call inside `on_exit` silently targets the GLOBAL singleton. Capture the context's `store`/`registry` in the closure (or touch a uniquely-keyed ETS row only) — all `on_exit` callbacks in this directory are ETS-keyed-only or `File.rm_rf`.
- **Registry restart pattern**: `stop_supervised(registry)` then `start_supervised(Supervisor.child_spec({TaskRegistry, task_store: store, data_dir: data_dir, name: registry}, id: registry))` — keep the SAME Store running (it is durable on disk) so data survives the registry restart. Never `stop_supervised(TaskRegistry)` / `name: EvoGit.TaskRegistry` (the child id would not match the fixture and the call would hit the global singleton).
- `EvoGit.Store` needs no seam: every client function takes the store name as its first argument (`store()` supplies it).
- `EvoGit.TaskRegistry` resolves its target via `EvoGit.TaskRegistry.server/0` (`Process.get(:evogit_task_registry_server) || __MODULE__`, read at CALL time) — so raw `send(TaskRegistry.server(), msg)` and `:sys.get_state(TaskRegistry.server())` hit the isolated instance from the test process.
- Sync idiom: `update_task_status` is a cast → always `TaskRegistry.list_tasks()` (a call) afterwards to flush the mailbox before asserting.
- The registry's own process carries the pdict key, so in-wrapper callbacks resolve back to the isolated instance.

## Timing & Robustness Patterns (use these, not fixed sleeps)

- **Event-driven waits over polling.** For anything the registry BROADCASTS, subscribe to `"tasks"` BEFORE triggering the action, then `receive` the `{:task_updated, id, status, node}` message with a generous bound (e.g. 5 s) and `flunk` on timeout. Never poll `get_task/1` in a `Process.sleep(N)` loop. Live examples: `task_executor_reflect_test.exs` (`await_terminal_status/1`), `persistence_test.exs` `describe "recheck_task resolution"`.
- **FIFO-sync instead of a blind quiet window.** To assert that NO broadcast was emitted, `send` the trigger, then make a synchronous `GenServer.call` to the same registry (e.g. `TaskRegistry.list_tasks()`), then `refute_receive ..., 0`. The call is queued strictly AFTER the trigger, so once it returns the handler has fully run; and any broadcast the handler emitted was sent registry→test-process BEFORE the call reply (same sender→same receiver ⇒ signal order guaranteed), so it is already in the mailbox. This makes the check complete evidence at zero wall-clock cost. Examples: `persistence_test.exs` `describe "recheck_task resolution"`, `finalizing_watchdog_test.exs` "late wrapper result ... is a no-op".
- **Always PIN the task id in a quiet-window assertion.** The `"tasks"` topic is process-global, so an unpinned `refute_receive` would be broken by another registry instance's traffic. `persistence_test.exs` pins `^task_id` in both shapes (`refute_receive {:task_updated, ^task_id, _, _}, 0`, and `assert_no_extra_task_broadcast/2` — a bounded 200 ms loop that flunks on the first `{:task_updated, ^task_id, ...}`/`{:task_deleted, ^task_id, ...}` and ignores other ids).
- **One shared quiet window for N message shapes.** Two sequential `refute_receive ..., 200` calls cost 400 ms. Use a single bounded `receive` loop that `flunk`s on the FIRST unexpected message instead (`persistence_test.exs` "graceful cancel emits exactly one tasks-topic broadcast").
- **`Process.sleep(:infinity)` inside `spawn(fn -> ... end)` is NOT a wait** — it keeps a fake wrapper process alive. Leave those alone.
- **A negative quiet window is only needed when an async trigger is unobservable** (e.g. a `Process.send_after` timer). There a bounded `refute_receive ..., N` (N ≈ 150 ms, far beyond any immediate-timer fire) is the right tool — see `finalizing_watchdog_test.exs` "disabled grace (false) ...".

## Key Status-Guard Semantics (pinned by `persistence_test.exs` `describe "status recovery from spurious :failed"` + `describe "cross-node PubSub filtering"`)

- **PubSub path** (`handle_info({:task_updated, id, status, node})`, lib `task_registry.ex`): updates are applied only when `node == node()` — a cross-node broadcast is ignored — and the handler is a **no-op when the task row is absent** (`task_get` → `nil`), so a broadcast about an unknown id can never create a phantom row. Stale update rejected ONLY when current status is `[:completed, :cancelled, :cancelling]`. `:failed` is deliberately NOT in the guard — a `:finalizing` broadcast after a spurious `:failed` is ACCEPTED ("recovery before completion": task seeded `:failed`, `Phoenix.PubSub.broadcast(EvoGit.PubSub, "tasks", {:task_updated, task_id, :finalizing, node()})`, assert `status == :finalizing`).
- **Cast path** (`handle_update_status`, lib `task_registry.ex`): rejects only terminal→terminal transitions where `task.status != status` and `status != :completed` — i.e. `:failed` → `:completed` recovery is allowed; `:completed`/`:cancelled` are never overwritten.
- **Terminal set is `[:completed, :failed, :cancelled]`** (cast path) but the PubSub guard uses only `[:completed, :cancelled, :cancelling]` — `:failed` is recoverable in both paths.
- Runtime emits ONLY `:finalizing` on the `"tasks"` topic (`Helpers.notify_finalizing/1`); a `:failed` received on PubSub triggers `Diagnostics.log_failed_transition(..., :task_updated_pubsub, ...)`.
- A local-node `:finalizing` PubSub broadcast now ALSO schedules the ONE-SHOT stuck-`:finalizing` grace watchdog (lib `task_registry.ex` handler → `schedule_finalizing_watchdog/1`, only on the successful `put_task` `:ok` arm — never the disk-full path): `Process.send_after(self(), {:recheck_task, task_id}, trunc(minutes * 60_000))`. Grace = `Application.get_env(:evo_git, :finalizing_watchdog_grace_minutes)`, declared in `config/`: 60 in `config/config.exs` (prod default; module fallback 60 when unset), **1 in `config/test.exs`**. `false` → disabled (no timer); numeric ≥ 0 → minutes (0 = immediate).

## Known Test Gaps

1. **No restart-recovery test for an unowned expired-lease `:running` row.** The `:finalizing` case IS covered (`describe "startup reconciliation of orphaned :finalizing tasks"`, incl. orphaned `:cancelling` → `:cancelled`): seeds a `:finalizing` row + a `:running` control row (both with future leases), restarts the registry, and asserts the orphaned `:finalizing` row → `:failed` (finished_at set, lease cleared, result a binary) while the `:running` row with a valid lease is left untouched (orphaned-`:running` sweeping is the `:lease_sweep` path). Untested: a fresh registry against a `:running` row with a valid lease leaves it untouched (only pinned as the startup-reconciliation control row); expired-lease unowned `:running` rows get swept only by the one-shot sweep 150 s after init (or `{:recheck_task, id}` resolution). The restart/backfill tests only use `:completed` tasks. Closest analogues: `lease_heartbeat_test.exs` (seeds an expired-lease unowned `:running` row and sends `:lease_sweep` DIRECTLY — no restart; the startup sweep is one-shot at `(@lease_duration + 30) * 1000` and never fires during a test run); `store_test.exs` (status field round-trips as atom for all known values incl. `:finalizing`).
2. **`:failed` → `:finalizing` via the CAST path** (`update_task_status/4`) is untested — only the PubSub path is covered.
3. **`:running`-row recheck resolution and the 30 s-reschedule path have NO timer-driven test** — all recheck tests drive the handler via raw `send(TaskRegistry.server(), {:recheck_task, id})` and never wait on the timer. The `:finalizing` recheck arm IS timer-driven now (`finalizing_watchdog_test.exs`, grace 0).
4. **No end-to-end `start_task(:genesis/:evolve)` lifecycle test in this dir — and `TaskExecutor.execute_task(:genesis/:evolve)` is never executed by any test here.** The ONLY real `start_task` lifecycle tests are `task_executor_reflect_test.exs` (`start_task(:reflect)` → terminal `:failed` with result `{:error, :llm_not_configured}` under `without_model_profiles`) and, outside this dir, `cli_task_routing_test.exs` / `cli_agent_flag_test.exs`. `start_task` elsewhere appears only as a direct `handle_call({:start_task, id, type, opts}, from, state)` invocation asserting the `:cancelled`/`:cancelling` guard reply `{:error, :cancelled}`. Fake `%Task{}` `mfa` payloads reference `TaskExecutor.execute_task` but are never invoked — their content is irrelevant. `merge_context_test.exs` states the `execute_task(:evolve, ...)` hook is deliberately untested (full Evolution/LLM runtime).
   Data-plane contract pinned by tests + lib: public `start_task(type, opts)` generates the id via `TaskExecutor.generate_id()` and `GenServer.call`s `{:start_task, id, type, opts}`; the handler guards existing rows with status `[:cancelled, :cancelling]` → `{:reply, {:error, :cancelled}, state}`; otherwise spawns `Task.Supervisor.async_nolink(EvoGit.TaskSupervisor, TaskExecutor, :execute_task, [type, opts, id])`, persists a `%TaskInfo{status: :running}` row (ref nulled — runtime-only; disk-full tolerated in-memory with warning), broadcasts `{:task_updated, id, :running, node()}` on `"tasks"`, and replies `{:ok, task}`. **Wrapper completion arrives as raw `{ref, result}`** (`{:ok, %{result:, commit_sha:, branch_name:, tag:}}` | `{:error, _}`) **and `{:DOWN, ref, :process, pid, reason}`** — exactly the shapes the fake-injection tests `send` directly; the terminal write removes the `task_refs` entry.
   ⚠️ **`RuntimeOpts` mode is STRICT STRING-ONLY**: `evolution_mode_atom`/`genesis_mode_atom` raise `ArgumentError` for atoms/non-strings, and genesis without an explicit `"new"`/`"existing"` raises. The CLI and shell task-opts modes are therefore ALWAYS STRINGS (never atoms).

### Known lib quirk (verified, tests pin the reachable semantics)
`TaskRegistry.resolve_recheck_task/3`'s `{:ok, %{branch_name: _}}` result-extraction branch remains **unreachable for `:running` rows at runtime** — `handle_info({:recheck_task, _})` gates on `Lease.sched_meta_has_active_agents?/1` (true when ANY ETS entry exists for the task_id → reschedules), while `Lease.lookup_sched_meta_result/1` (which supplies the result) REQUIRES an entry with `parent_id == nil` to exist. Mutually exclusive → the only reachable recheck outcome for a `:running` row is `{:completed, nil}` (warning logged). The grace watchdog schedules the FIRST recheck for tasks that entered `:finalizing` — those take the handler's dedicated `:finalizing` arm and never reach `resolve_recheck_task/3`; the generic `:running` arm has no production trigger of its own (nothing schedules a first recheck for a `:running` row — only the watchdog and the generic arm's own 30 s self-reschedule ever emit the message), so it is exercised only by raw `send` in tests.
Note the `describe "recheck_task resolution"` `setup` creates/deletes `:evogit_sched_meta` when the scheduler ETS table is absent and clears it before/after each test (`:ets.delete_all_objects` only, never `:ets.delete`).

## Notes for Agents

- **NEVER put pure-function tests inside the fixture case.** The fixture starts two extra processes (~30-35 ms) and exists only to provide an isolated Store + registry. Pure tests (helpers over a locally-built `%TaskInfo{}`, string builders, option builders) belong in an `async: true` plain `ExUnit.Case` module — `merge_context_block_test.exs` / `resume_context_block_test.exs` are the precedent.
- **Do NOT flip one of the 4 serialized modules without removing its forcing global.** `persistence` needs the global-`:evogit_sched_meta` clear/seed interaction gone, `completion_logging` needs a non-global Logger seam, `finalizing_watchdog` needs a per-instance grace seam, `task_executor_reflect` needs a scheduler-config seam.
- **`Process.sleep(N)` as a wait is banned here** — use the timing patterns above. The only acceptable fixed window is a bounded, id-pinned `refute_receive` for an unobservable async trigger.
- Only READ global `:evogit_*` ETS by a per-test-unique id from an async module; never `:ets.delete_all_objects` a shared table and never `:ets.new` a shared named table from an async module (both are cross-module races).
- `runtime_opts_test.exs` and `diagnostics_test.exs` were already `async: true` — keep them that way.

## Constraints

- No mocking — real SQLite via xqlite, real `EvoGit.Store`/`TaskRegistry` GenServers; corrupt rows injected via raw `XqliteNIF.execute`.
- `EvoGit.TaskRegistryCase, async: false` for the 4 modules that reach a named BEAM-global; plain `ExUnit.Case, async: true` for the 4 pure modules and `EvoGit.TaskRegistryCase, async: true` for the 5 isolated fixture modules.
- Tests must not mutate BEAM-global state outside their module's own fixture lifecycle; per-test global-env seams are snapshot + restored in `on_exit` (see `finalizing_watchdog_test.exs`'s `set_grace/1`).
