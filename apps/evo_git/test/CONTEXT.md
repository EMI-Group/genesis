# `:evo_git` Test Suite

## Intent
The ExUnit suite for the `:evo_git` core runtime — real git operations against per-test temp directories, no mocks.
Per-file detail lives in the child CONTEXT.md files below; this file carries only intent, routing, the cross-cutting async-safety policy, the measured cost profile, timing seams, shared infrastructure, assertion/fixture patterns, current known issues, and constraints.
Full per-file history lives in git (`git log -p -- apps/evo_git/test/CONTEXT.md`).

## Async-Safety Policy
`async: true` is allowed ONLY for a module whose tests mutate no BEAM-global state another concurrently-running module can observe.
A process-wide `XDG_CONFIG_HOME` redirect is NO LONGER a forcing global by itself: `support/config_dir.ex` (`EvoGit.TestSupport.ConfigDir`, installed suite-wide as the `:config_dir_fun` app env in `test_helper.exs`) makes config-dir resolution per PROCESS (`Process.get(:evogit_config_dir)`, then the first `$callers` entry), so `ConfigDir.isolate!/1` in `setup` isolates `~/.config/genesis` with no env var and the per-path `:persistent_term` config cache stays unique-dir safe.
The seam reaches the test process plus children IT starts (`proc_lib` propagates `$callers`), but NOT app-global singletons started at boot (`EvoGit.AgentScheduler`, `EvoGit.TaskRegistry`, `EvoGit.Store`, `EvoGit.PeakHourEngine`) and NOT a child started by `start_supervised!/1` (its starter is the ExUnit supervisor, not the test) — a config read inside one of those still needs `System.put_env("XDG_CONFIG_HOME")` and therefore `async: false`.
`System.put_env/2` on any var production or a child process reads (`XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `$TMPDIR`, `PATH`, `GIT_AUTHOR_*`, `GENESIS_SOURCE_ROOT`) stays a BEAM-global mutation regardless of the seam.
A module MUST be `async: false` when any test redirects a process-wide env var a child process reads (`PATH`, `XDG_DATA_HOME`, `$TMPDIR`, `GIT_AUTHOR_*`/`GIT_CONFIG_*`, `GENESIS_SOURCE_ROOT`, `GOOGLE_API_KEY`/`TEST_CRED_KEY`), mutates an app-env key another module reads at a DIFFERENT value, mutates `:persistent_term` read by others, or changes the global `Logger` level.
An app-env key every user wants at the SAME value is NOT a serialization reason: hoist it once into the "suite-wide fast test constants" block in `test_helper.exs` (`:nix_enabled, false` and `:req_llm, :openai_api_key, "test-key"` live there) and delete the per-test mutation; a key that needs two different values stays a local `on_exit`-restored write and keeps its module serialized.
A module MUST also be `async: false` when any test touches the global `EvoGit.AgentScheduler` (config, model profiles, turn caps, slot pools, `:sys.get_state`/`replace_state`), wipes an app-global `:evogit_*` ETS table wholesale (`:ets.delete_all_objects/1`) or reads one table-wide, drives an app-booted named singleton (`WorktreeManager`, `EvoGit.SandboxSlice`, `Throttle`, `EvoGit.CommandApproval`, the `EvoGit.RemoteConnection` Registry/DynamicSupervisor), the app-level `EvoGit.Store`/`EvoGit.TaskRegistry`, or a shared PubSub topic it asserts on without node/id filtering.
Writing rows into the app-global `:evogit_agent_state`/`:evogit_sched_meta` tables is NOT a serialization reason by itself: key every row with a per-test-unique id (`9_9xx_000 + System.unique_integer([:positive])`), delete only your own rows in `on_exit`, and never assert on table emptiness or size.
Those rows must carry the PRODUCTION SHAPE (`%EvoGit.AgentScheduler.AgentState{}` / `%EvoGit.AgentScheduler.SchedMeta{}`), never a plain map: production scans the tables wholesale and pattern-matches the struct (`AgentScheduler.agent_ids_for_task/1`, `SystemSampler.read_sched_metas/0`, `RemoteAPI.build_agent_summary/3`), so one map row makes a CONCURRENT module crash.
A `capture_io/2` / `capture_log/2` window is shared per named device, so another async module's compiler or log output can land inside it: a `refute output =~ "<warning>"` must scope the match to the module/artefact under test (and emit no redefinition warning of its own — `:code.purge/1` + `:code.delete/1` before recompiling a fixture module).
`EvoGit.TaskRegistryCase` is NOT itself a serialization reason: it starts a UNIQUELY-NAMED isolated `EvoGit.Store` + `EvoGit.TaskRegistry` pair per test (explicit child `id:` override) and never touches the app-global singletons, so `use EvoGit.TaskRegistryCase` may be `async: true`.
The 9 `EvoGit.TaskRegistryCase` modules still `async: false` name a SEPARATE forcing global: `persistence_test` (app-global `:evogit_sched_meta` + the global `EvoGit.AgentScheduler` on the cancel paths), `completion_logging_test` (global `Logger` level), `finalizing_watchdog_test` (app-env `:finalizing_watchdog_grace_minutes`, which needs four different values per test), `task_executor_reflect_test` / `command_shell_test` / `cli_task_routing_test` / `agent/tools/reflect_tools_test` (`without_model_profiles/1` on the global scheduler), `command_approval_test` (app-env `:command_approval_timeout`, two windows), and `task_registry/task_tmpdir_reclaim_test` (process-wide `XDG_CONFIG_HOME`: its reclaim runs inside a registry started by `start_supervised!/1`, which does NOT inherit the test's `:evogit_config_dir`, so the `ConfigDir` seam provably cannot reach it — and the env redirect is exactly what keeps the run off the real `/tmp/genesis`).
The three background-command modules are `async: false` for real OS process work rather than a BEAM global: `evo_git/background_jobs_test.exs` (real detached shell children, `kill -0` liveness probes, and the shared `<EvoGit.Sandbox.resolve_tmpdir()>/genesis` job-log scratch dir, whose before/after snapshot cleanup is only sound while the sync phase runs one module at a time), `evo_git/agent/tools/job_tools_test.exs` (the same real children + shared scratch dir, plus an isolated `EvoGit.BackgroundJobs` instance per test behind the `:evogit_background_jobs_server` pdict seam), and `evo_git/sandbox/background_test.exs` (one genuine `spawn_detached/1` spawn + `kill -0` probes, and the `:nix_enabled` app-env key).
Every forced-`async: false` module carries an in-file comment/`@moduledoc` naming what forces serialization — the exact BEAM-global, or a timing/isolation reason — keep it accurate when that changes.
**Runtime is part of test quality**: a NEW test module defaults to `async: true`; a module that must stay `async: false` names its forcing global in an in-file comment/`@moduledoc`; and a reviewer should treat an UNNECESSARY sync module as a defect to fix in the same change — the usual tells are a stale reason (it names a global the module no longer touches, or a global that now has a per-process seam), a wholesale `:ets.delete_all_objects/1` where per-test-unique ids would do, and a shared single-value app-env key that belongs in the `test_helper.exs` constant block.
The async setting is **per MODULE, not per file** — two files carry two test modules each: `command_shell_test.exs` = `EvoGit.CommandShellTest` (`EvoGit.TaskRegistryCase`, sync) + `EvoGit.CommandShellParsingTest` (`async: true`), and `command_approval_test.exs` = `EvoGit.CommandApprovalTest` (`EvoGit.TaskRegistryCase`, sync) + `EvoGit.CommandApproval.RequestTest` (`async: false`). A one-`use`-line-per-file scan misclassifies both.
Inventory (census — module count = explicit `use ExUnit.Case, async: …` / `use EvoGit.TaskRegistryCase, async: …` lines, the two mutually exclusive so they sum to the total; `defmodule` total = lines beginning with `defmodule` across the test tree, inline + `support/` helpers incl.): 212 test modules (217 `defmodule`s) — 152 `async: true`, 60 `async: false`, 0 untagged; 23 modules use `EvoGit.TaskRegistryCase` (14 `async: true`, 9 `async: false`).
What is still serialized, by forcing class: (a) the global `EvoGit.AgentScheduler` / an app-booted singleton — `agent_scheduler/{agent_scheduler,slots,pubsub,worktrees,worktree_admission}_test`, `agent/{context_compression_stages,context_compression_fail_fast,implicit_completion,cost,llm_error_failfast,tool_dispatch_retry_slot}_test`, `agent/tool_dispatch_containment_test`, `agent/tool_output_integration_test`, `peak_hour_engine_test`, `system_sampler_test`, `sandbox_slice_test`, `command_shell_test`, `cli_agent_flag_test`, `cli_task_routing_test`, `runtime/{evolution,self_reflective}_test`, `agent/tools/reflect_tools_test`, `task_registry/task_executor_reflect_test`; (b) an app-env key that needs more than one value — `agent/compression/{recency,threshold}_test`, `agent/llm_retry_policy_test`, `command_approval_test`, `config/llm_generation_params_test`, `task_registry/finalizing_watchdog_test`, `agent/tools_test`, `agent/tools/{web_fetch,web_search}_test`, `sandbox/nix_test`, `system_check_test`; (c) an app-global store/registry/ETS singleton — `store_test`, `store_summary_test`, `application_test`, `store/{archive_migration,maintenance}_test`, `task_registry/{persistence,completion_logging,task_tmpdir_reclaim}_test`, `agent_scheduler/remote_api_test`; (d) real OS / execution-environment work — `background_jobs_test`, `agent/tools/job_tools_test`, `sandbox/background_test`, `adapters/{github,cow_worktree}_test`, `remote_node_github_test`, `remote_connection_test`, `distribution_test`, `git_env_test`, `config_test`, `platform_test`, `self_reflective_source_test`, `sandbox/{bwrap,linux,macos}_test`; (e) one deliberate wall-clock budget — `agent/tool_dispatch_test`.

## Cost Profile (measured)
Suite wall clock = the `async: true` phase + the serial sum of the `async: false` modules (ExUnit drains the entire async cohort before it runs any sync module, then runs those one at a time), so only work removed from that serial tail, or made cheaper, shortens the suite; per-file detail lives in each directory's CONTEXT.md.
The suite is 4803 tests (12 doctests, 4791 tests), 0 failures, 0 invalid.
This host is SHARED with sibling worker agents, so absolute totals swing ±2x run to run: eleven consecutive runs of the current suite spanned 22.0-31.0 s (async 9.1-17.1 s, sync 12.5-19.0 s) while a load-spike run of an EARLIER commit reached 428.2 s (409.8 s async / 18.4 s sync — the ASYNC cohort, not the serial tail, absorbs host load). Compare a before/after in ONE session, and prefer a structural win (a module leaving the serial tail) over a single noisy total.
The suite is verified green AND console-quiet over six consecutive full runs at the current commit (4803 passed, zero `[info]/[warning]/[error]`/crash lines each time) — re-establish that with a run loop, not a single run, after any async-safety change.
Serial-tail result of the async-safety sweep that moved 33 modules out of the cohort (`async: false` 93 → 60 modules, `async: true` 119 → 152): a stash-controlled A/B of the same suite on one host gave sync **15.0 / 17.8 / 16.0 s before vs 13.8 / 13.2 / 16.2 s after** (median 16.0 → 13.8 s) with total 26.8 → 26.1 s. The per-file serial cost is a long FLAT tail — the largest remaining `async: false` file is ~2.4 s, most are 0.1-0.6 s — so the lever is modules LEAVING the cohort, never one hot module; and because a flipped module's real work (git/shell forks) now competes inside the ~28-way async cohort, a flip must be justified by the TOTAL, not by the sync figure.
What the tail is made of now: real OS subprocess FORKS. A `git` fork measures 2.4-6 ms, a trivial `#!/bin/sh` child 2.2-2.9 ms, `git worktree add` ~10 ms, and `File.cp_r!` of a template 0.6-2.8 ms — so FORK COUNT, not fixture size, is the lever everywhere (see Assertion & Fixture Patterns), and the remaining big suites sit at the production-fork floor (the merge path, the CoW create pipeline, the LSP handshake, the job-child spawns).
Timer waits are sunk: every remaining wait is event-driven and the seams below cover the cadence knobs.
The ONE-OFF ReqLLM `LLMDB.load/1` catalog decode (~2.5 s) is paid by the FIRST ReqLLM-touching module per BEAM and cannot be removed, only attributed (see `./evo_git/agent/CONTEXT.md`).
**Do NOT split a module into an `async: true` module just to shrink the sync number**: an 11-run interleaved A/B of exactly such a split (69 tests moved to `async: true` + 5 left serialized) reliably moved ~1.1s out of the sync phase but added ~1.0-3.2s to the async phase (the moved git/shell tests inflate under the ~28-way async cohort), for adjacent-pair TOTAL deltas of +0.1s / +0.2s / +0.5s — the split was reverted. TOTAL wall clock, not the sync figure, is the criterion for any sync→async move.
Rejected/blocked candidates: `cow_worktree_test` (per-process config dir now, but a `:persistent_term` `:evogit_cow_worktree_enabled` flag erased per test); `github_test` / `remote_node_github_test` / `remote_connection_test` (their test mechanism IS process-wide `PATH`, plus for the last one a connection manager under the APP supervisor, outside `$callers`); `self_reflective_source_test` (only 0-arity production readers, plus an already-`async: true` sibling mutating the same four env knobs), which stays sync with test-side-cheapened fixtures.
Rejected for the store suites: `store_test` / `store_summary_test` own the app-global `EvoGit.Store`/`EvoGit.TaskRegistry` for the whole module under the canonical `EvoGit.Store` name, so `async: true` would mean threading a unique store name through ~200 `Store.<fn>(Store, …)` call sites and ~150 test signatures — high-risk churn, no coverage benefit.
`without_model_profiles/1` (a global `EvoGit.AgentScheduler` `model_profiles` rewrite) is the single biggest remaining blocker — 7 modules — and replacing it needs an isolated-scheduler INSTANCE, deliberately not built (`test/CONTEXT.md` policy: no isolated-scheduler subsystem).
Smaller production levers, in leverage order, each worth ≲1 s of serial tail and therefore out of scope for an opportunistic sweep: a per-process `without_model_profiles/1` replacement (7 modules), `:llm_model_metadata_fun` (3), `:command_approval_timeout` (3), `:nix_enabled` + the nix `:persistent_term` (3), `:tool_dispatch_test_tools` (2).

## Timing Seams (default-inert, read at call time)

Production defaults are unchanged; each seam is an `Application.get_env(:evo_git, …)` read at CALL time, set and restored by the modules that need it — a per-test `setup` + `on_exit` when different tests need different values, or the `test_helper.exs` constant block when every user wants the same value.
`:background_tick_interval_ms` (default `@tick_interval_ms` = 1_000 ms) → `EvoGit.BackgroundJobs.resolved_tick_interval_ms/0`, feeding BOTH the public `tick_interval_ms/0` and the `:reconcile_tick` timer arm; a suite can also DISARM the tick (set `3_600_000`) because each tick forks `systemctl --user show` once per live `:unit` job, and only a test that proves the timer fires arms the real 25 ms cadence (`background_jobs_test`).
`:background_poll_interval_ms` (default `@poll_interval_ms` = 100 ms) → `EvoGit.BackgroundJobs.poll_interval_ms/0`, read on every sleep of a caller-side `wait: true` loop; `job_tools_test` sets 5 ms.
`:background_unit_stop_notify` (unset by default) → `EvoGit.Sandbox.Background.stop_unit_async/1` sends `{:background_unit_stop_finished, unit}` from its fire-and-forget stop task after the `systemctl --user stop` / `reset-failed` pair has run (and therefore after that path's warning line, whose log handler runs synchronously in that task); `background_jobs_test` hands it the test pid so `quiet_kill/1` awaits the stop instead of sleeping a settle margin.
`:kill_grace_ms` (default `@kill_grace_ms` = 100 ms) → `EvoGit.Sandbox.Helpers.posix_kill_tree/1` at both `Process.sleep` sites; tests set 0-10 ms when the post-kill assertion is a poll (a genuinely-dead pid is still asserted).
`:worktree_retry_delays` (default `[50, 100, 200]`) → `EvoGit.AgentScheduler.WorktreeRetry.delay_stream/1` (an explicit `:delays` opt still wins); tests set `[0, 0, 0]`.
Already-existing seams reused for the same purpose: `:remote_daemon_health_delay_ms` (default 1_000 ms, test 0 ms — `Process.sleep/1` still yields, so poll counters stay distinct), `:remote_tunnel_poll_interval_ms` (default 100 ms, read per call by `EvoGit.RemoteConnection`'s connect worker, test 5 ms), `:llm_backoff_sweep_epsilon_ms` (default 1_000 ms, read by `EvoGit.AgentScheduler.Slots` at both timer sites), `:llm_retry_backoff_base_ms` (default 1_000 ms, read by `EvoGit.Agent.ToolDispatch` at call time).
The `@doc false` `EvoGit.GitEnv.prime_config_identity_cache/3` is the write-side companion of `clear_config_identity_cache/1`: a fixture repo copied from a template whose config already pins the identity is primed with it, so its first git call skips the two `git config` forks a fresh repo path otherwise pays. Production code never calls it; the primed pair is byte-identical to what the memo would have read.
The test-only key `:agent_scheduler_test_observer` is read by the test's own `DummyAgent`, never by production code.

## Test-Case Pruning

The suite was pruned 4912 → 4642 tests (−270): tautologies, near-duplicates of a strictly stronger sibling, weaker copies of coverage owned by another module, log-wording assertions weaker than the behaviour they guard, and per-case families collapsed into ONE table-driven test (every case kept).
Rule: prefer deleting a whole redundant `describe` block over weakening a surviving assertion; never weaken a surviving assertion.
Verify a "duplicate" claim by reading the sibling test before deleting anything.

## Assertion & Fixture Patterns

In-flight assertions are HELD, not raced: `task_registry/archive_persistence_test` keeps a test-local store holding the archive reply until `release_archive_write/1`; `store/store_write_offload_test` has the TEST hold SQLite's write lock (`BEGIN IMMEDIATE`) so the writer blocks by construction; `store/pool_size_test` asserts the pool's own `checkout_queue_length` metric instead of a `Task.yield(task, 500)` window.
After a SYNCHRONOUS call, prove "no extra message" with `refute_receive _, 0` (registry→test FIFO), never a quiet window; where the reply is STRUCTURALLY impossible (the injected fun is parked on `receive :release` and the caller is blocked in an `:infinity` `GenServer.call`) use the zero-wait `refute_received` (`agent_scheduler/worktree_admission_test` case (g)).
Real git fixtures: ONE per-module template (`git init -q --template=<empty dir>`, `core.abbrev=40` so `git commit`'s summary line carries the full sha) copied per test with `File.cp_r!` (~0.6-2.8 ms) — used by `agent/context_merge_test`, `review_test`, `agent/tool_dispatch_containment_test`, `agent/tools/commit_files_test` (its two pure `commit_message_file_path/0` cases opt out with `@tag :no_repo`), `agent/tools/reflect_tools_test`, `agent/tools/complete_task_test` (a 3-SHAPE template set: no commit / one commit / two commits, shas captured once, selected per describe or by `@tag template: :empty`), `adapters/cow_worktree_test` and `adapters/github_test` (TWO templates selected by `@tag :no_origin`).
Multi-commit graphs are cheaper still with `git fast-import`: `agent/subagent_processing_test` imports its whole named graph in ONE subprocess (stream over a `Port` — `System.cmd/3` cannot write stdin — with `--export-marks` to read the SHAs back, pinned author/committer and epoch so fixture shas are stable), snapshots each finished scenario repo once in `setup_all`, and lets a test copy its snapshot — zero fixture git subprocesses, so its remaining ~11 forks per test are the production merge path under test.
Every copied fixture repo and worktree path is primed with `EvoGit.GitEnv.prime_config_identity_cache/3`; the worktree suites additionally pre-seed the per-repo init marker so a create skips the lazy-init forks (`agent_scheduler/CONTEXT.md`).
Timer/throttle assertions drive the event synchronously where the production call is FIFO-ordered: `agent_scheduler/pubsub_test` delivers the pending `:flush` and pins the cleared timer ref; registry ticks are awaited on the re-armed `tick_timer` ref (`background_jobs_test`).
Each LSP execute test execs the compiled fixture `EvoGit.FakeLspServer` (`test/support/fake_lsp_server.ex`) as a real OS child from ONE escript packed in `setup_all` (~120 ms boot against ~300 ms for `elixir <script>.exs`): 8 execute-level tests are the floor, and the "silent server" initialize budget is 400 ms (`agent/tools/lsp_test`).
A module that pins `model_profiles` and then reads the per-model pool map (`get_llm_slot_status/0`) must `:sys.suspend(EvoGit.PeakHourEngine)` BEFORE the pin and `:sys.resume` it in `on_exit` AFTER the profile restore — the engine's `"scheduler_config"` wakeup is a non-atomic read-then-apply, so a concurrent profile-set change can transiently replace the pool map with the ambient config's (`agent/CONTEXT.md` → "Notes for Agents").

## Shared Infrastructure
`test_helper.exs` runs after app boot and before any test: it redirects `XDG_DATA_HOME` to a temp dir as a fallback guard against the production DB, pins the suite-wide fast test constants in ONE commented block (`:nix_enabled, false` — set once because nix is only consulted lazily, so this is race-free for every async module, and the few sandbox modules that need it ON set it locally; and `:req_llm, :openai_api_key, "test-key"` — the exact literal every former writer used), installs the per-process config-dir seam (`Application.put_env(:evo_git, :config_dir_fun, {EvoGit.TestSupport.ConfigDir, :resolve, []})`), then calls `ExUnit.start(capture_log: true, timeout: 180_000)`.
Only a key EVERY writer sets identically belongs in that block; a key with two required values stays a local `on_exit`-restored write and keeps its module `async: false` — hoisting such a key would silently undo a sibling's local restore (sync module order is arbitrary).
The canonical DB guard is `config/test.exs` pinning `:evo_git, :data_dir` to a UNIQUE per-run path (`…/evogit_test_data/genesis-<os-pid>-<unique-integer>`): concurrent `mix test` runs and sibling worker worktrees never share a `tasks.sqlite`, and no rows accumulate across runs.
Each run's `after_suite` hook removes only its own dir (never the shared parent), so any whole-table or global-state failure is a REAL flake rather than test pollution.
`support/fake_gh.ex` — `EvoGit.FakeGh`: puts a fake `gh` on `PATH` (canned JSON, `GH_FAKE_MODE`, argv log); only usable from `async: false` modules, POSIX-gated.
`support/submodule_helper.ex` — the module is `EvoGit.TestSupport.Submodule` (name differs from the filename — grepping `SubmoduleHelper` finds nothing); builds gitlink/submodule entries without cloning.
`support/store_template.ex` — `EvoGit.TestSupport.StoreTemplate`: `new!/0` (called from `setup_all`, returns a `dest -> dest` copy function), `build!/0` (the module-scoped variant with `on_exit/1` cleanup), `copy!/2`; builds ONE schema-complete SQLite template per test BEAM and caches its path in `:persistent_term` behind the same `:global.trans/2` double-checked idiom `Store.Boot` uses, so concurrent `async: true` `setup_all` blocks build exactly once and every later module pays only the copy (19.2 ms → 2.3 ms per isolated DB). The template file is IMMUTABLE (`File.cp!/2` only, never re-opened by a store), copies are complete (a real `EvoGit.Store` → `PRAGMA wal_checkpoint(TRUNCATE)` → stop → strip `-wal`/`-shm` → assert `sqlite_master` carries `tasks`; the explicit checkpoint is REQUIRED because `EvoGit.Store.Boot.stop/1`'s checkpoint is asynchronous), and cleanup is a `System.at_exit/1` — never a module `on_exit/1`, which would delete the file out from under a module still running.
It is adopted by `EvoGit.TaskRegistryCase` (per-BEAM `setup_all` in its `using` block; 23 modules / 292 tests, isolation unchanged — every test still gets its own database file) and by the `store/` suites (`operations/*`, `task_page_api`, `store_invariants`, `repo_scope`); migration/schema suites (`boot_migration*`, `canonical_schema`, `composite_index`, `covering_index`, `archive_migration`, `v0138_upgrade_path`, `migrate_store`, `repo_test`) deliberately keep a fresh-schema boot because schema creation IS their subject.
`support/task_registry_case.ex` — `EvoGit.TaskRegistryCase` (used by 23 modules, 14 `async: true`): `setup` starts a UNIQUELY-NAMED isolated `EvoGit.Store` (`evogit_test_store_<n>`) + `EvoGit.TaskRegistry` (`evogit_test_registry_<n>`) via `start_supervised!/1` with an explicit child `id:` override (both modules hardcode `id: __MODULE__` in `child_spec/1`), on a per-test SQLite DB COPIED from the BEAM-wide template under a temp dir, then sets `:evogit_task_registry_server` + `:evogit_test_store` in the TEST process and returns `%{data_dir: root, sqlite_path: sqlite_path, store: store_name, registry: registry_name}`.
`TaskRegistry.server/0` resolves the registry name from the `:evogit_task_registry_server` pdict at CALL time (falling back to the `EvoGit.TaskRegistry` singleton), so in-test `EvoGit.TaskRegistry.*` calls hit the isolated instance; `EvoGit.Store` needs no seam because every client function takes the store name as its first arg — the case exposes the isolated name via `store/0`.
Helpers: `store/0`, `trigger_cleanup!/0` (direct `Cleanup.cleanup_expired_tasks/1` against the isolated store), `cleanup_process/1`, `old_age_days/0`, `within_age_days/0`.
No `EvoGit.Supervisor` child is ever terminated or restarted.

## Known Issues
**`EvoGit.SystemSampler` interval can only be changed via restart**: the sampler starts before `test_helper.exs`, so setting `:system_sample_interval_ms` there is too late; a test needing a fast tick sets the env then calls `Supervisor.terminate_child/2` + `Supervisor.restart_child/2` so `init/1` re-reads it (`terminate_child/2` alone leaves a permanent child `:undefined`).
**No fake-LLM harness**: no Mox/Meck and no injectable LLM runner, so a macro-driven agent cannot be run to completion; the only no-real-LLM idioms are error paths (empty the scheduler `model_profiles` → `{:error, :llm_not_configured}`, or point a model at an unreachable `base_url`) plus hand-built `%ReqLLM.ToolCall{}` fed to pure functions.
**Parallel-load timing is the historical failure mode**: never assert tight wall-clock bounds; make waits event-driven rather than `Process.sleep`-based.
**Two concurrent full-suite runs in one checkout are inherently flaky (revision-independent)**: `@moduletag :tmp_dir` paths are cwd-relative and deterministic (`tmp/<Module>/<test>-<md5>`), so two `mix test` processes in the SAME checkout collide; even in SEPARATE checkouts `sandbox/macos_test.exs` (reads and mutates the VM-global `$TMPDIR`), `system_sampler_test`, the `adapters/*` git tests and `agent_scheduler/subagents_test` flake under a 2-suite load. This is NOT an async-regression signal — use two separate checkouts (distinct cwd) and expect a few pre-existing flakes.
**Heavy host load has produced single-instance failures in two store-related suites** (a sibling agent compiling its own worktree while a full run executes): `store/covering_index_test` read an EMPTY `select_task_paths/0` result from a per-test copy of its own seeded template, and `task_registry/archive_persistence_test` reported its inline `SlowArchiveStore` helper as "does not exist". Both modules pass in isolation and in every idle full run; neither shares state with another module. Treat a lone failure there under load as host noise, not a test bug — do not "fix" it by weakening a wait.
**A wait deadline is NOT a correctness lever - the awaited event must be REACHABLE by construction.** A wait that burns its whole (generous) budget means suspect routing/global state, not latency; every wait below is event-driven and every budget only absorbs scheduling latency.
- `agent_scheduler/worktrees_test.exs` (retry-after-crash): 30s `wait_until/2` default PLUS a deterministic sync on proc A's create RESULT (the monitor-driven destroy can delete the transient worktree dir before the test's first poll).
- `task_registry/store_skip_and_log_test.exs`: the clean-window `refute` is scoped to the store's OWN row id, because `with_log/2` captures GLOBALLY - a concurrent `async: true` module emitting the same skip message would otherwise falsify an unscoped refute.
- `agent/tool_dispatch_retry_slot_test.exs`: 30s `@load_robust_deadline_ms` on every wait PLUS an explicit `:evogit_agent_state` row for every id it drives. `Slots.resolve_model_id/2` reads the requester's pool from the VM-global table, so a row leaked by ANOTHER module for a small literal id rerouted the probe into an empty pool (immediate grant → unreachable queue state; no budget could help); the leaker (`agent_scheduler/slots_test.exs`) now deletes exactly the rows it inserts in `on_exit` (rule: `./evo_git/agent_scheduler/CONTEXT.md` "Global-State Hygiene").
**No artificial CPU-load verification (project direction).** Do NOT generate CPU load (`yes` loops, burners) to "prove" load robustness - explicitly out of scope and a waste of the host. Prove determinism by CONSTRUCTION: make the awaited event reachable, add a deterministic injection (e.g. the relevant stale ETS row) and show the test still passes, then run the affected modules at idle load across several seeds.
**Load-robust default ExUnit timeout (`test_helper.exs`, 180s).** Every `System.cmd/3` / `System.find_executable/1` PATH lookup round-trips the BEAM's SINGLE `:file` server, which under heavy host load backs up for a minute or more; the 180s default lets that real I/O drain instead of aborting otherwise-passing git-heavy suites (`CommitGraphTest`, `ReviewTest`, `adapters/git_test`, …) as `ExUnit.TimeoutError` (always blocked in `:os.find_executable1` -> `:file.call/2`), and weakens no assertion.
**Residual under-load cost (needs a PRODUCTION seam).** `Git.run_git/2` calls `EvoGit.Executable.resolve/1` (`lib/evo_git/executable.ex`) for EVERY git invocation; it returns the BARE name (`"git"`) when found on PATH, so `System.cmd/3` re-resolves PATH — ~2 `:file` round trips per git call. Memoizing the resolved ABSOLUTE path (`:persistent_term`, like `EvoGit.GitEnv`) is the root fix but needs invalidation because `support/fake_gh.ex` mutates the process-wide PATH.
**`[:llm, :compression_threshold_tokens]` and `[:llm, :tool_result_pruning]` have NO app-env seam.** `EvoGit.Config.resolve/1` reads the operator's real `config.toml`, and a `compression_threshold_tokens` override there (this dev machine carries one) wins over every window-derived threshold. Suites pinning an ABSOLUTE threshold or the pruning gate isolate a fresh temp config dir through the per-process `EvoGit.TestSupport.ConfigDir.isolate!/1` (`agent/compression/threshold_test`, `agent/context_compression_stages_test`, `agent/context_compression_fail_fast_test`, `agent_scheduler/remote_api_test`) or a real `System.put_env("XDG_CONFIG_HOME")` when the read happens outside the test's `$callers` chain (`config_test`); all of them stay `async: false` for their OTHER globals.
**`sandbox/helpers_test.exs` holds its alive-port child on purpose**: the "`wait_for_os_pid/2` returns the real integer os pid of a live port, matching the child" test runs against a child that polls a release file (the test and `on_exit` both touch it, so a red run leaks nothing) — a short-lived `bash -c "echo $$"` exits in microseconds, so under CPU load the port auto-closes before the first poll and the CORRECT helper returns `:undefined`; do NOT shorten that child. Detail: `./evo_git/sandbox/CONTEXT.md`.

## Console Output (kept quiet)

The suite is kept quiet: console noise must be captured, never leaked between tests. `test_helper.exs` sets `ExUnit.start(capture_log: true)` (test-process logs), and OTHER-process sources are silenced at their source: `ExUnit.CaptureLog.capture_log/2` is WINDOW-based and catches logs from ANY process (the tool for boot-time/unlinked-process leaks), while raw subprocess stderr needs `stderr_to_stdout: true`.
- **Store read-worker faults (one line, no crash report)** — the offloaded read worker exits `{:shutdown, {:offload_failed, kind, reason, stacktrace}}` (a `:shutdown`-class exit emits NO OTP crash report) and `format_offload_reason/1` renders it with `Exception.format/3`, so ONE facade line (`Store: read <op> failed — …`) is the whole trace. Detail: `../lib/evo_git/store/CONTEXT.md`.
- **`Store: FAILED_WRITE …` seed diagnostics** — one line per seeded `:failed` row, fired from the STORE's write path (outside per-test capture): `store/covering_index_test.exs` wraps its ~500-row seed in ONE `capture_log/2` window (text dropped; a console-only window may also swallow a concurrent sibling's line).
- **`:unit` kill warnings** — `background_jobs_test.exs` wraps its `:unit`-shaped kills in `quiet_kill/1`, because `EvoGit.Sandbox.Background.stop_unit_async/1` logs asynchronously from an unlinked task.
- **ReqLLM refused-port warm-ups** — the three `setup_all` warm-ups (`agent/llm_error_failfast_test.exs`, `agent/tool_dispatch_retry_slot_test.exs`, `agent/context_compression_fail_fast_test.exs`) each make ONE real streaming request to the dead loopback `http://127.0.0.1:1`, whose 3 `[warning] Retrying streaming request after transient transport error` + 1 `[error] Finch streaming transport failed` come from the req_llm dep's Finch pool process; each warm-up is wrapped in `capture_log/2`.
- **Raw git stderr** — `review_test.exs`'s test-local `System.cmd("git", ["checkout", "--detach"], …)` calls pass `stderr_to_stdout: true`, capturing git's `HEAD is now at <sha>` banner (the Git adapter's `run_git/2` always does).
- **TaskRegistry crash warning** — `command_shell_test.exs`'s deliberately-crashing genesis task (no mode → `invalid genesis mode: "simple"`) wraps the action in `capture_log/2`, so the down-handler's `[warning] TaskRegistry: FAILED_TRANSITION …` never leaks.
- **Global Logger level window** — `task_registry/completion_logging_test.exs` lowers the GLOBAL `Logger` level (`Logger.configure(level: :debug)`) for its `:info` captures and restores it afterwards, so an unrelated background-process log line can reach the console while that module runs.

## Constraints
`@moduletag :tmp_dir` supplies the ExUnit temp-dir fixture.
No mocking libraries — git tests use real `git` on temporary repos.
Test module names mirror the source module path under test.
Each test file is self-contained; inline helper modules (`DummyAgent`, `HintAgent`, …) are defined where needed.
An inline helper module used by the SAME file's `async: true` test module MUST be defined ABOVE that test module: `mix test` starts the ExUnit runner (`ExUnit.async_run()`) BEFORE requiring the test files, so the async module's tests can already run while a helper defined later in the file is still unloaded — `Supervisor.child_spec/2` then raises "does not implement child_spec/1" (seed/timing-dependent, seen in `./evo_git/task_registry/archive_persistence_test.exs`).
Trailing modules that are themselves `ExUnit` modules (e.g. `command_shell_test.exs`, `command_approval_test.exs`) are fine, but a trailing STUB used at runtime (`delegation_hints_test.exs`'s `RoleWithUntitledSubagents`, the `evo_dash` `node_aware_test.exs` `ConnectionManager`) carries the same latent race.
`on_exit` callbacks run in a DIFFERENT process than the test, so the `EvoGit.TaskRegistryCase` pdict keys are NOT set there — an `on_exit` that calls `EvoGit.TaskRegistry.*` or a default-store `EvoGit.Store.*` silently hits the global singleton; capture and pass the isolated `store`/`registry` from the setup context instead.
`function_exported?/3` is a BIF that does NOT load its module, so a test asserting an export must call `Code.ensure_loaded!/1` first — in an `async: true` module nothing else guarantees the load happened (`agent/runner_injected_message_test.exs`, `agent/context_builder_test.exs`, `store/task_page_api_test.exs`); `module.module_info/1`, `Module.behaviour_info/1` and `apply/3` are REMOTE calls and auto-load, so those need no guard.
