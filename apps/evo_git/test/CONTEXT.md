# `:evo_git` Test Suite

## Intent
The ExUnit suite for the `:evo_git` core runtime — real git operations and real subprocesses against per-test temp directories, no mocking libraries.
Per-suite detail lives in the child CONTEXT.md files; this file carries routing, async-safety, the cost profile, timing seams, shared infrastructure, assertion/fixture patterns, known issues and constraints.

## Async-Safety Policy
- `test/evo_git/auth/env_token_test.exs` — class (b): mutates the global `CLAUDE_CODE_OAUTH_TOKEN`/`ANTHROPIC_OAUTH_TOKEN` env vars; `test/evo_git/auth/{auth_test,oauth_import_test}.exs` are `async: true` (hermetic via `opts[:home]`/`opts[:codex_home]`/`opts[:oauth_file]` and the `:auth_home_fun` seam).
`async: true` is allowed ONLY for a module whose tests mutate no BEAM-global state another concurrently-running module can observe.
**New tests default to `async: true`; an unnecessary `async: false` module is a defect to fix in the same change** — the usual tells are a stale reason (a global the module no longer touches, or one that now has a per-process seam), a wholesale `:ets.delete_all_objects/1` where per-test-unique ids would do, and a shared single-value app-env key that belongs in the `test_helper.exs` constant block.
Every forced-`async: false` module carries an in-file comment/`@moduledoc` naming the exact forcing global (or the timing/isolation reason); keep it accurate when that changes.
A process-wide `XDG_CONFIG_HOME` redirect is NOT a forcing global by itself: `support/config_dir.ex` (`EvoGit.TestSupport.ConfigDir`, installed suite-wide as the `:config_dir_fun` app env) makes config-dir resolution per PROCESS (`Process.get(:evogit_config_dir)`, then the first entry of the process' spawn chain — `$callers`, then `$ancestors`), so `ConfigDir.isolate!/1` in `setup` isolates `~/.config/genesis` with no env var.
**A test that writes `config.toml`/`credentials.toml` directly through `File.write!` MUST call `EvoGit.Config.Cache.reload()` (or `reload(dir: …)`) afterwards, or use `Config.save_user_config/1`/`save_credentials/1`**: `Config.resolve/0,1`, `user_config/0`, `credentials/0` and `config_status/0` read ONLY the RAM snapshot keyed `{EvoGit.Config.Cache, dir}` in `:persistent_term` — no `File.stat`, no re-read, no re-validation — so a raw write is invisible until a reload (the watcher's ~150 ms debounce does not exist in `:test`).
Put that reload in the per-module write helpers (`write_config!/2`, `with_tmp_config/2`, `install!/1`); a write into a dir the test process did not activate passes the dir explicitly.
Because the snapshot is per DIRECTORY, the isolation guarantee is the unique temp config dir, never the `async` setting: `config/cache_test.exs`, `config/watcher_test.exs` and `config/reload_event_test.exs` (`EvoGit.Config.ReloadEventTest` + `EvoGit.Config.ReloadEventWatchTest`) stay `async: true` on their own dirs, filtering every `"config"` PubSub assertion by that unique `dir` before matching `generation`.
The seam reaches the test process plus children IT starts (`$callers` for Elixir `Task` children, `$ancestors` for every `proc_lib` child — a plain `GenServer.start_link/3` such as ReqLLM's `StreamServer`, a `Supervisor`), but NOT app-global singletons started at boot (`EvoGit.AgentScheduler`, `EvoGit.TaskRegistry`, `EvoGit.Store`, `EvoGit.PeakHourEngine`) and NOT a `start_supervised!/1` child (its starter is the ExUnit supervisor) — a config read inside one of those still needs `System.put_env("XDG_CONFIG_HOME")` and therefore `async: false`.
A module MUST be `async: false` when any test redirects a process-wide env var production or a child reads (`XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `$TMPDIR`, `PATH`, `GIT_AUTHOR_*`, `GENESIS_SOURCE_ROOT`, `GOOGLE_API_KEY`/`TEST_CRED_KEY`), mutates an app-env key another module reads at a DIFFERENT value, mutates `:persistent_term` read by others, or changes the global `Logger` level.
An app-env key every user wants at the SAME value is NOT a serialization reason: hoist it into the "suite-wide fast test constants" block in `test_helper.exs` (`:nix_enabled, false` and `:req_llm, :openai_api_key, "test-key"` live there); a key needing two values stays a local `on_exit`-restored write and keeps its module serialized.
A module MUST also be `async: false` when any test touches the global `EvoGit.AgentScheduler` (config, model profiles, turn caps, slot pools, `:sys.get_state`/`replace_state`), wipes an app-global `:evogit_*` ETS table wholesale or reads one table-wide, drives an app-booted named singleton (`WorktreeManager`, `EvoGit.SandboxSlice`, `Throttle`, `EvoGit.CommandApproval`, the `EvoGit.RemoteConnection` Registry/DynamicSupervisor), the app-level `EvoGit.Store`/`EvoGit.TaskRegistry`, or a shared PubSub topic it asserts on without node/id filtering.
Writing rows into the app-global `:evogit_agent_summary`/`:evogit_sched_meta` tables is NOT a serialization reason by itself: key every row with a per-test-unique id (`9_9xx_000 + System.unique_integer([:positive])`), delete only your own rows in `on_exit`, and never assert on table emptiness or size.
Those rows must carry the PRODUCTION SHAPE (`%EvoGit.AgentScheduler.AgentState{}` / `%EvoGit.AgentScheduler.SchedMeta{}`), never a plain map: production scans the tables wholesale and pattern-matches the struct (`AgentScheduler.agent_ids_for_task/1`, `SystemSampler.read_sched_metas/0`, `RemoteAPI.build_agent_summary/3`), so one map row crashes a CONCURRENT module.
A `capture_io/2` / `capture_log/2` window is shared per named device, so another async module's output can land inside it: scope every `refute output =~ "<warning>"` to the module/artefact under test (and emit no redefinition warning of its own — `:code.purge/1` + `:code.delete/1` before recompiling a fixture module).
`EvoGit.TaskRegistryCase` is NOT itself a serialization reason: it starts a UNIQUELY-NAMED isolated `EvoGit.Store` + `EvoGit.VCT` + `EvoGit.TaskRegistry` trio per test (explicit child `id:` override) and never touches the app-global singletons.
The VCT suites are `async: true` because a test's mounts (project AND workspace) are rows in its OWN isolated SQLite database (the `vct_mounts` table), never a shared file: `./evo_git/vct/path_test.exs`, `./evo_git/vct/mount_test.exs`, `./evo_git/vct/table_workspace_test.exs`, `./evo_git/store/operations/vct_mounts_test.exs`, `./evo_git/store/vct_mounts_migration_test.exs`, `./evo_git/vct_test.exs`, `./evo_git/vct_workspace_test.exs`, `./evo_git/vct_workspace_rpc_test.exs`, `./evo_git/store/vct_workspace_mounts_migration_test.exs`, `./evo_git/task_registry/vct_path_admission_test.exs` and `./evo_git/core/context_node_test.exs`.
The ONE sync module among them is `EvoGit.VCTTest.CapTest` (in `./evo_git/vct_test.exs`): it writes the BEAM-global app-env key `:vct_max_projects` (restored in `on_exit/1`), the sole forcing reason.
The `EvoGit.TaskRegistryCase` modules that stay `async: false` name these SEPARATE forcing globals: `persistence_test` (app-global `:evogit_sched_meta` + the global `EvoGit.AgentScheduler` on the cancel paths), `completion_logging_test` (global `Logger` level), `finalizing_watchdog_test` (app-env `:finalizing_watchdog_grace_minutes`, four values per test), `task_executor_reflect_test` / `command_shell_test` / `agent/tools/reflect_tools_test` (`without_model_profiles/1` on the global scheduler), `command_approval_test` (app-env `:command_approval_timeout`, two windows), `task_registry/task_tmpdir_reclaim_test` (process-wide `XDG_CONFIG_HOME`: its reclaim runs in a `start_supervised!/1` registry that does not inherit `:evogit_config_dir`, and the redirect keeps the run off the real `/tmp/genesis`), and `agent_scheduler/whole_tree_resume_test` / `agent_state/durable_row_lifecycle_resume_test` (the app-global `EvoGit.PubSub` `"tasks"` topic their real `resume_task/1` / `force_kill_task/1` paths broadcast on; no `:pubsub` option can redirect it).
The six other serialized `TaskRegistryCase` modules are `command_approval_eval_test`, `agent/elixir_eval_dispatch_test` and `agent/tools/elixir_eval_{wrapper,configuration,direct_api,direct_configuration}_test` (the global CommandApproval service/topic; dispatch also seeds the global task store, the configuration suites mutate the global scheduler, and direct configuration replaces `:config_dir_fun`).
The three background-command modules are `async: false` for real OS process work rather than a BEAM global: `evo_git/background_jobs_test.exs` (real detached children, `kill -0` probes, and the shared `<EvoGit.Sandbox.resolve_tmpdir()>/genesis` job-log scratch dir, whose before/after snapshot cleanup is only sound one module at a time), `evo_git/agent/tools/job_tools_test.exs` (same children + scratch dir, plus an isolated `EvoGit.BackgroundJobs` instance per test behind the `:evogit_background_jobs_server` pdict seam) and `evo_git/sandbox/background_test.exs` (one genuine `spawn_detached/1` spawn + probes, and the `:nix_enabled` app-env key).
Two INDEPENDENT termination signals need ONE wait predicate: the scheduler's `handle_agent_down` ETS recycle and the session's `Registry` unregistration have no ordering between them, so a test that awaits the ETS rows and then asserts `Registry.lookup(EvoGit.Agent.Session.Registry, agent_id) == []` races the unregistration — fold both conditions into the same `wait_until/2` and keep the bare assertion after it (`agent_scheduler_test`'s scheduled-run case, `session_lifecycle_integration_test`'s crash-retry case); a `refute Process.alive?/1` needs no such wait when a `:DOWN` was already received or the pid's death is the observed event itself.
The async setting is **per MODULE, not per file**: `command_shell_test.exs` = sync `EvoGit.CommandShellTest` + async `EvoGit.CommandShellParsingTest`, `command_approval_test.exs` = sync `EvoGit.CommandApprovalTest` + async `EvoGit.CommandApproval.RequestTest`, `process_manager_test.exs` = async `EvoGit.ProcessManagerTest` + sync `EvoGit.ProcessManagerSeamsTest`; a one-`use`-line-per-file scan misclassifies them.

## Cost Profile (measured)
Suite wall clock = the `async: true` phase + the serial sum of the `async: false` modules (ExUnit drains the whole async cohort first, then runs sync modules one at a time), so only work removed from that serial tail, or made cheaper, shortens the suite.
Absolute totals swing ±2x under sibling load (the ASYNC cohort absorbs host load): compare a before/after in ONE session and prefer a structural win over one noisy total.
Measured on a 16-core host at `--seed 0`: ~98 s with a sibling app suite running (async ~67 s, sync ~31 s) and ~52 s on an idle host (async ~14 s, sync ~38 s).
**TOTAL wall clock is the criterion, not the sync figure** — moving git/shell tests into `async: true` shrinks the sync phase but inflates the ~28-way async cohort (measured adjacent-pair totals were positive).
The per-file serial cost is a long FLAT tail — the largest remaining `async: false` file is ~3.7 s (`remote_connection_test` / `agent/tools/job_tools_test`, both at the real-fork/real-child floor), most are 0.1-0.6 s — so the lever is modules LEAVING the cohort, never one hot module.
The tail is real OS subprocess FORKS: a `git` fork is 2.4-6 ms, a trivial `#!/bin/sh` child 2.2-2.9 ms, `git worktree add` ~10 ms, `File.cp_r!` of a template 0.6-2.8 ms — so FORK COUNT, not fixture size, is the lever, and the big suites sit at the production-fork floor (merge path, CoW create pipeline, LSP handshake, job-child spawns).
Timer waits are sunk: every remaining wait is event-driven and the seams below cover the cadence knobs; the ONE-OFF ReqLLM `LLMDB.load/1` decode (~2.5 s) is paid by the first ReqLLM-touching module per BEAM (`./evo_git/agent/CONTEXT.md`).
`without_model_profiles/1` (a global `EvoGit.AgentScheduler` `model_profiles` rewrite) is the single biggest remaining blocker — 7 modules — and replacing it needs an isolated-scheduler INSTANCE, deliberately not built.
Smaller levers, each ≲1 s of serial tail and out of scope for an opportunistic sweep: a per-process `without_model_profiles/1`, `:llm_model_metadata_fun` (3 modules), `:command_approval_timeout` (3), `:nix_enabled` + the nix `:persistent_term` (3), `:tool_dispatch_test_tools` (2).
`agent/elixir_eval_dispatch_test`'s shared-task approval-floor case injects a 200 ms `[:scheduler, :default_tool_timeout]` through `ConfigDir.isolate!/1` — PROBED in the batch process, which is where the executor resolves each call's timeout (`$callers` carries the seam) — instead of waiting the production 10 s twice.
Modules deliberately LEFT sync: `cow_worktree_test` (per-test `:persistent_term` flag), `github_test` / `remote_node_github_test` / `remote_connection_test` (process-wide `PATH`), `self_reflective_source_test` (one case hits the app-global `EvoGit.VCT`), `store_test` / `store_summary_test` (they own the app-global store/registry under the canonical name).

## Timing Seams (default-inert, read at call time)
Production defaults are unchanged; each seam is an `Application.get_env(:evo_git, …)` read at CALL time, set and restored by the modules that need it — a per-test `setup` + `on_exit` when different tests need different values, or the `test_helper.exs` constant block when every user wants the same value.
- `:background_tick_interval_ms` (default 1_000 ms) → `EvoGit.BackgroundJobs.resolved_tick_interval_ms/0`, feeding `tick_interval_ms/0` and the `:reconcile_tick` timer; a suite may DISARM it (set `3_600_000`) because each tick forks `systemctl --user show` once per live `:unit` job, and only a test proving the timer fires arms a 25 ms cadence (`background_jobs_test`).
- `:background_poll_interval_ms` (default 100 ms, non-negative) → `BackgroundJobs.poll_interval_ms/0`, the BASE of a caller-side `wait: true` exponential poll (×1.5, capped 3_000 ms; 0 floors to 1 ms); `job_tools_test` sets 5 ms.
- `:background_wait_default_ms` (default 120_000 ms, non-negative) → `BackgroundJobs.wait_default_ms/0`, the fallback budget for `JobOutput`; `job_tools_test` sets 120 ms to pin the default-budget marker without a 120 s wait.
- `:background_wait_max_ms` (unset; POSITIVE integers only) → `BackgroundJobs.wait_max_ms/0`, the hard cap on a `wait: true` budget; it OVERRIDES the derivation `[:scheduler, :max_tool_timeout] − dispatch_headroom_ms()` (25_000, floored at 1_000 — 1_775_000 ms by default); `job_tools_test` pins 60_000 to exercise the `<n>m` hint arm.
- `:background_unit_stop_notify` (unset) → `EvoGit.Sandbox.Background.stop_unit_async/1` sends `{:background_unit_stop_finished, unit}` after the `systemctl --user stop` / `reset-failed` pair; `background_jobs_test` hands it the test pid so `quiet_kill/1` awaits instead of sleeping.
- `:kill_grace_ms` (default 100 ms) → `EvoGit.Sandbox.Helpers.posix_kill_tree/1` at both `Process.sleep` sites; tests set 0-10 ms when the post-kill assertion is a poll.
- `:process_kill_grace_ms` (default 1_500 ms) → `EvoGit.ProcessManager.Control.kill_grace_ms/0`, the TERM→KILL escalation window; the CALLING process's `:process_kill_grace_ms` dictionary entry WINS over the app-env key (the OS kill runs in the caller, so this is an async-safe per-process shrink — `process_manager_test`'s POSIX round trip, `sandbox/foreground_tracking_test`'s pause/resume/kill case and `remote_api_process_test`'s round trip set it to 0; `EvoGit.ProcessManagerSeamsTest` and `agent/tool_dispatch_test` still use the app-env key and stay serialized).
- `:worktree_retry_delays` (default `[50, 100, 200]`) → `EvoGit.AgentScheduler.WorktreeRetry.delay_stream/1` (an explicit `:delays` opt wins); tests set `[0, 0, 0]`.
- Reused existing seams: `:remote_tunnel_poll_interval_ms` (100 ms, read per call by `EvoGit.RemoteConnection`'s connect worker), `:llm_backoff_sweep_epsilon_ms` (1_000 ms, `AgentScheduler.Slots` timer sites), `:llm_retry_backoff_base_ms` (1_000 ms, `EvoGit.Agent.ToolDispatch` at call time).
- The engine seams `:agent_exchange_llm_call` (arity 5) and `:agent_exchange_tool_batch` (arity 2) are app-env defaults read AT CALL time by every session's exchange worker (`EvoGit.Agent.Exchange.Seams.from_opts/1`); an explicit `exchange_opts:` in a directly started session's dispatch context wins over the app-env default.
The `@doc false` `EvoGit.GitEnv.prime_config_identity_cache/3` is the write-side companion of `clear_config_identity_cache/1`: a fixture repo copied from a template whose config pins the identity is primed with it, skipping the two `git config` forks a fresh repo path pays; production never calls it and the primed pair is byte-identical to the memo.
No test observes a `run/2` callback: the session never calls one.

## Assertion & Fixture Patterns
In-flight assertions are HELD, not raced: `task_registry/archive_persistence_test` keeps a test-local store holding the archive reply until `release_archive_write/1`; `store/store_write_offload_test` has the TEST hold SQLite's write lock (`BEGIN IMMEDIATE`) so the writer blocks by construction; `store/pool_size_test` asserts the pool's `checkout_queue_length` instead of a `Task.yield` window.
After a SYNCHRONOUS call, prove "no extra message" with `refute_receive _, 0` (registry→test FIFO), never a quiet window; where the reply is STRUCTURALLY impossible (injected fun parked on `receive :release`, caller blocked in an `:infinity` call) use the zero-wait `refute_received` (`agent_scheduler/worktree_admission_test` case (g)).
Real git fixtures: ONE per-module template (`git init -q --template=<empty dir>`, `core.abbrev=40` so `git commit`'s summary carries the full sha) copied per test with `File.cp_r!`: `agent/context_merge_test`, `agent/completion_test` (a 2-SHAPE template set selected per describe), `review_test`, `agent/tool_dispatch_containment_test`, `agent/tools/commit_files_test` (pure cases opt out with `@tag :no_repo`), `agent/tools/reflect_tools_test`, `adapters/cow_worktree_test`, `adapters/github_test` (TWO templates by `@tag :no_origin`).
Multi-commit graphs are cheaper with `git fast-import`: `agent/subagent_processing_test` imports its whole named graph in ONE subprocess (stream over a `Port` — `System.cmd/3` cannot write stdin — `--export-marks` to read shas back, pinned author/committer/epoch), snapshots each scenario repo once in `setup_all`, and lets a test copy its snapshot.
Every copied fixture repo and worktree path is primed with `EvoGit.GitEnv.prime_config_identity_cache/3`; worktree suites also pre-seed the per-repo init marker so a create skips the lazy-init forks (`agent_scheduler/CONTEXT.md`).
A scripted `:llm_call` seam runs in a FRESH worker per exchange, so its turn counter must live OUTSIDE the process dictionary: derive progress from `context.messages` (or hand the seam a test-owned agent) — a `Process.get`/`Process.put` counter replays the first scripted turn on every resume, and a lenient `await_yield`-style fallback then burns its whole budget silently (`agent/session/interactive_test.exs`).
Bounded-absence proofs stay at their documented floor: `agent/session/interactive_close_test.exs`'s 500 ms duplicate-notice window and its worktree-reappearance window are deliberate (one window each, never two), so do not tighten them to buy wall clock.
Timer/throttle assertions drive the event synchronously where production is FIFO-ordered: `agent_scheduler/pubsub_test` delivers the pending `:flush` and pins the cleared timer ref; registry ticks are awaited on the re-armed `tick_timer` ref (`background_jobs_test`).
Each LSP execute test execs the compiled fixture `EvoGit.FakeLspServer` (`test/support/fake_lsp_server.ex`) as a real OS child from ONE escript packed in `setup_all` (~120 ms boot vs ~300 ms for `elixir <script>.exs`); 8 execute-level tests are the floor and the "silent server" initialize budget is 400 ms (`agent/tools/lsp_test`).
A module that pins `model_profiles` and then reads the per-model pool map (`get_llm_slot_status/0`) must `:sys.suspend(EvoGit.PeakHourEngine)` BEFORE the pin and resume in `on_exit` AFTER the restore — the engine's `"scheduler_config"` wakeup is a non-atomic read-then-apply, so a concurrent profile change can transiently replace the pool map (`agent/CONTEXT.md` → "Notes for Agents").

## Shared Infrastructure
`test_helper.exs` runs after app boot and before any test: it redirects `XDG_DATA_HOME` to a temp dir as a fallback guard against the production DB, pins the suite-wide fast test constants in ONE commented block (`:nix_enabled, false` — race-free because nix is consulted lazily, and sandbox modules needing it ON set it locally; and `:req_llm, :openai_api_key, "test-key"`), installs the per-process config-dir seam (`Application.put_env(:evo_git, :config_dir_fun, {EvoGit.TestSupport.ConfigDir, :resolve, []})`), warms the vendored LLM catalog ONCE (`LLMDB.Catalog.ensure_loaded!/0`, best effort), then calls `ExUnit.start(capture_log: true, timeout: 180_000)`.
Only a key EVERY writer sets identically belongs in that block; hoisting a two-valued key would silently undo a sibling's restore (sync module order is arbitrary), so it stays local with `async: false`.
The canonical DB guard is `config/test.exs` pinning `:evo_git, :data_dir` to a UNIQUE per-run path (`…/evogit_test_data/genesis-<os-pid>-<unique-integer>`), so concurrent runs and sibling worker worktrees never share a `tasks.sqlite`; each run's `after_suite` hook removes only its own dir, so any whole-table/global-state failure is a REAL flake rather than pollution.
`support/config_dir.ex` — `EvoGit.TestSupport.ConfigDir`: the per-process `:config_dir_fun` seam (`Process.get(:evogit_config_dir)`, then the first entry of the process' spawn chain — `$callers`, then `$ancestors`) behind `isolate!/1`; the pdict key is the SAME `:evogit_config_dir` the `:evo_dash` mirror uses, so an umbrella run resolves identically.
A directory is named `<prefix>-<os pid>-<unique int>-<random hex>`: `System.unique_integer/1` is unique only WITHIN one BEAM, so two runs sharing a `TMPDIR` would compute one path and each `on_exit` would remove the OTHER run's LIVE config dir — the OS pid and random component are load-bearing, like the vendored-git temp-file naming and `test_helper.exs`'s per-OS-pid data-dir guard.
`activate/1` also records the activating pid as an OWNER via one marker file `<dir>/.evogit-owners/<pid textual form>` (read back with `:erlang.list_to_pid/1`, so it outlives the pid) — that is what makes a `setup_all`-created directory (`isolate_module!/1` + per-test `activate/1`) as drain-safe as a per-test one; the per-test `isolate!/1` deliberately skips the marker because the registrar IS the test process and appears in every child's spawn chain (whose first entry is `:"$callers"`, then `:"$ancestors"`).
`isolate!/1`/`isolate_module!/1` register the directory's ONLY `on_exit` cleanup — a suite must NOT add a second `File.rm_rf!/1` (an earlier LIFO callback without the drain reintroduces the race).
That cleanup drains first — `await_supervised_writers/2` / `await_dir_writers/3`, monitor-based, re-scanning after every wait, 5 s budget — every live `EvoGit.TaskSupervisor` child that carries the registrar in its spawn chain (`$callers` + `$ancestors`), OR resolves `dir` as its override, OR names a recorded owner pid, because such an app-global child outlives its test and `File.mkdir_p`s `<dir>/genesis` back; a drain that blocks ≥ 1 s logs a warning naming the SERIAL `on_exit` cost (invisible to ExUnit's per-test times).
`support/fs_cleanup.ex` — `EvoGit.TestSupport.FsCleanup.rm_rf!/2`: a DEADLINE (10 s), not an attempt count — `:before_attempt` re-drains with the REMAINING window before every attempt, only the transient `[:eexist, :enotempty]` races are retried, and a tree that genuinely cannot be removed still raises `File.Error` with its residual entries logged; never hand-roll a retry loop next to it.
`support/fake_gh.ex` — `EvoGit.FakeGh`: puts a fake `gh` on `PATH` (canned JSON, `GH_FAKE_MODE`, argv log); only usable from `async: false` modules, POSIX-gated.
`support/submodule_helper.ex` — the module is `EvoGit.TestSupport.Submodule` (name differs from the filename; grepping `SubmoduleHelper` finds nothing): builds gitlink/submodule entries without cloning.

## Evaluator Test Strategy
Evaluator suites use genuine Dune plus production-shaped owner/spec/ETS authority and isolated running reflective tasks, never mocked authorization or interpreter stubs.
`evo_git/agent/tools/elixir_eval_fixture_helper.exs` owns its private supervisor through ExUnit and monitors teardown without accepting unexpected shutdown failures.
Cold-facade tests must run without preloading evaluator allowlists, because lazy initialization failures are part of the tested boundary, and the evaluator regressions intentionally require embedded scheduler IDs to match their ETS lookup key (including revalidation after a held sudo approval).
Ordinary Mix execution requires the declared Dune dependency; a temporary validation run against externally compiled genuine Dune loads only its dependency beams before `Mix.CLI.main` with `--no-deps-check` and never substitutes evaluator production beams (e.g. `MIX_ENV=test elixir -pa <ABSOLUTE dune-ebin> -S mix do compile --no-deps-check --no-prune-code-paths + test --no-compile --no-deps-check <test-paths> --seed 42`; keep it absolute because background jobs may change `$TMPDIR`).

## Known Issues
**`EvoGit.SystemSampler` interval can only change via restart**: the sampler starts before `test_helper.exs`, so setting `:system_sample_interval_ms` there is too late — set it, then `Supervisor.terminate_child/2` + `restart_child/2` so `init/1` re-reads it (`terminate_child/2` alone leaves it `:undefined`).
**A SCHEDULED agent run IS scriptable through the engine seams** — no Mox/Meck and no real LLM: an `:agent_exchange_llm_call` seam returning `{:implicit_completion, response, text}` scripts the ONE reply (a reply with no tool calls ends the run), so a run through `EvoGit.AgentScheduler.run_agent/2` or a directly started session returns a real `%EvoGit.Agent.Result{}` (`agent_scheduler_test`, `session_dispatch_test`).
A parked seam is the idiom for observing an in-flight agent (send what the seam sees, then wait for a release) because it runs in the session's exchange worker and sees the WORKER's `Process.get(:repo_path)` and HEAD.
No-real-LLM error idioms: empty the scheduler `model_profiles` → `{:error, :llm_not_configured}`, point a model at an unreachable `base_url`, or feed hand-built `%ReqLLM.ToolCall{}` to pure functions.
`Exchange.run(state, opts)` still takes `llm_call:` / `tool_batch:` / `scheduler:` / `checkpoint:` opts, so per-turn behaviour (grace entry, warning cadence, pending drain, background-job notices, tool-call sequencing) stays drivable in a bare process (`./evo_git/agent/exchange_golden_test.exs`, `./evo_git/agent/exchange_checkpoint_seam_test.exs`).
**Parallel-load timing is the historical failure mode**: never assert tight wall-clock bounds; make waits event-driven rather than `Process.sleep`-based.
**Two concurrent full-suite runs in one checkout are inherently flaky**: `@moduletag :tmp_dir` paths are cwd-relative and deterministic (`tmp/<Module>/<test>-<md5>`), so two `mix test` processes in the SAME checkout collide; even in separate checkouts `sandbox/macos_test.exs` (VM-global `$TMPDIR`), `system_sampler_test`, the `adapters/*` git tests and `agent_scheduler/subagents_test` flake under a 2-suite load — not an async-regression signal.
Running the suite INSIDE a Genesis worker sets `TMPDIR=/tmp/genesis/task_<n>`, which the `sandbox/macos_test.exs` "emits no per-task tmpdir rules when none is installed" assertion matches, so that ONE test fails there — a harness artifact, never a regression signal.
**Heavy host load has produced lone failures in `store/covering_index_test`, `store/operations/safety_test.exs` (the 133-row chunked-fallback case) and `task_registry/archive_persistence_test`** (an empty `select_task_paths/0` from a per-test copy; an inline helper reported as "does not exist"). All pass in isolation and in idle full runs — host noise, never a reason to weaken a wait.
**A wait deadline is NOT a correctness lever — the awaited event must be REACHABLE by construction.** A wait that burns its budget means suspect routing/global state, not latency; every budget only absorbs scheduling latency.
- `agent_scheduler/worktrees_test.exs` (retry-after-crash): 30 s `wait_until/2` default PLUS a deterministic sync on proc A's create RESULT (the monitor-driven destroy can delete the transient worktree dir before the first poll).
- `task_registry/store_skip_and_log_test.exs`: the clean-window `refute` is scoped to the store's OWN row id, because `with_log/2` captures GLOBALLY.
- `agent/tool_dispatch_retry_slot_test.exs`: 30 s `@load_robust_deadline_ms` on every wait PLUS an explicit `:evogit_agent_summary` row per id it drives, because `Slots.resolve_model_id/2` reads the VM-global table and a leaked small literal id reroutes the probe into an empty pool (no budget could help); the leaker (`agent_scheduler/slots_test.exs`) deletes exactly the rows it inserts (`./evo_git/agent_scheduler/CONTEXT.md` "Global-State Hygiene").
**The vendored `:llm_db` catalog load holds a `:global` lock — no TEST process may be its first loader.** `LLMDB.Catalog.ensure_loaded!/0` serializes on `:global.trans/3`: the first caller decodes the 11.7 MB snapshot inside the lock while others retry in `:global.random_sleep/1`, so under the async cohort the cost lands on whichever module is waiting. `test_helper.exs` therefore warms it once before `ExUnit.start/1`; never add a per-test `LLMDB.Catalog.clear!/0` and never assert on a COLD catalog.
**A test comparing two `%ReqLLM.Context{}`s for equality must pin the agent clock.** `ContextBuilder` stamps `metadata[:timestamp]` from `EvoGit.Agent.Clock.now_seconds/0` (Unix seconds), so identical runs a second apart differ; `Exchange.run/2` and `Turn.run/3` take `now:` and install it in the PROCESS DICTIONARY (`Clock.with_opts/2`), which no sibling observes — `agent/exchange_checkpoint_seam_test.exs` pins the same `now:` on both runs, and `agent/compression/checkpoint_test.exs` compares against ONE bound fixture instead of a re-built one.
**A fixture directory that is ALSO a subprocess's cwd must not be `@moduletag :tmp_dir`.** The ExUnit path is cwd-relative, deterministic and recreated with `File.rm_rf!` + `mkdir_p!`, so a concurrent run of the same file empties the directory a running tool chdir'd into (ripgrep's `lib: No such file or directory` in `agent/tools/search_context_test.exs`); such a fixture builds a unique-per-run dir under `System.tmp_dir!()`.
**Scratch dirs shared through `System.tmp_dir!()` must carry the owning BEAM in their name.** `System.unique_integer/0` is unique only WITHIN one BEAM, so two concurrent `mix test` BEAMs can mint the same path and one teardown fails with `:eexist` (`runtime/helpers_test.exs`); name every dir `<prefix>_<:os.getpid()>_<positive monotonic unique_integer>` and remove it with the tolerant `File.rm_rf/1`.
**No artificial CPU-load verification (project direction).** Never generate CPU load to "prove" robustness: prove determinism by CONSTRUCTION — make the awaited event reachable, add a deterministic injection, then run the modules idle across several seeds.
**Load-robust default ExUnit timeout (180 s, `test_helper.exs`).** Every `System.cmd/3` / `find_executable/1` PATH lookup round-trips the BEAM's SINGLE `:file` server, which under load backs up for a minute or more; the 180 s default lets that real I/O drain instead of aborting passing git-heavy suites as `ExUnit.TimeoutError`, and weakens no assertion.
**Residual under-load cost (needs a PRODUCTION seam).** `Git.run_git/2` calls `EvoGit.Executable.resolve/1` on every invocation, which returns the BARE name when on PATH, so `System.cmd/3` re-resolves PATH (~2 `:file` round trips per git call); memoizing needs invalidation because `support/fake_gh.ex` mutates PATH.
**`[:llm, :compression_threshold_tokens]` and `[:llm, :tool_result_pruning]` have NO app-env seam.** `EvoGit.Config.resolve/1` reads the operator's real `config.toml`, so a `compression_threshold_tokens` there wins over every window-derived threshold; suites pinning an ABSOLUTE threshold or the pruning gate isolate a fresh temp config dir through `EvoGit.TestSupport.ConfigDir.isolate!/1` (`agent/compression/threshold_test`, `agent/context_compression_stages_test`, `agent/context_compression_fail_fast_test`, `agent_scheduler/remote_api_test`) or `System.put_env("XDG_CONFIG_HOME")` when the read happens outside `$callers` (`config_test`); all stay `async: false` for their OTHER globals.
**`Protocol.UndefinedError … String.Chars not implemented for XqliteEcto3.Query` in the `store/*index*` suites means a STALE consolidated beam, never a code or test bug.** Genesis worktrees copy `_build` with preserved timestamps, so Mix reuses the source checkout's `consolidated/` output, which can predate a newer dependency's protocol impl; new worktrees delete `_build/*/consolidated` and `_build/*/lib/*/consolidated` (`../lib/evo_git/runtime/CONTEXT.md`), and a pre-fix checkout recovers with `mix deps.compile xqlite_ecto3 --force`.
**`sandbox/helpers_test.exs` holds its alive-port child on purpose**: a short-lived `bash -c "echo $$"` exits in microseconds, so under load the port auto-closes before the first poll and the CORRECT helper returns `:undefined` — do NOT shorten that child (`./evo_git/sandbox/CONTEXT.md`).
**The app-global `EvoGit.VCT` boot mount is REAL host state** — `EvoGit.Application` starts it with `EvoGit.SelfReflectiveSource.system_mounts()` over the machine's real data dir, so `vct:///genesis-source` binds to the developer's own tree and `SelfReflectiveSource.reference_path/0` step 3 depends on the host and on whichever earlier test re-pointed that mount.
Rule: a test exercising the chain's VCT step pins `:evogit_vct_server` through `EvoGit.VCTTest.Helpers.start_stack/2` (an EMPTY per-test mount table) instead of inheriting the boot mount (`self_reflective_source_test.exs`'s negative `available?/0` case does).

## Console Output (kept quiet)
Console noise must be captured, never leaked: `test_helper.exs` sets `ExUnit.start(capture_log: true)`; `ExUnit.CaptureLog.capture_log/2` is WINDOW-based and catches logs from ANY process, while raw subprocess stderr needs `stderr_to_stdout: true`.
- Store read-worker faults: ONE facade line (`Store: read <op> failed — …`) from `format_offload_reason/1`; a `:shutdown`-class exit emits no crash report (`../lib/evo_git/store/CONTEXT.md`).
- `Store: FAILED_WRITE …` seed diagnostics come from the STORE's write path, outside per-test capture — `store/covering_index_test.exs` wraps its ~500-row seed in ONE `capture_log/2` window.
- `:unit` kill warnings: `background_jobs_test.exs` wraps them in `quiet_kill/1` (`Sandbox.Background.stop_unit_async/1` logs from an unlinked task).
- ReqLLM refused-port warm-ups: the `setup_all` warm-ups in `agent/llm_error_failfast_test.exs`, `agent/tool_dispatch_retry_slot_test.exs` and `agent/context_compression_fail_fast_test.exs` each make ONE request to `http://127.0.0.1:1`, whose retry/transport lines come from the dep's Finch pool — each is wrapped in `capture_log/2`.
- Raw git stderr: `review_test.exs` passes `stderr_to_stdout: true` to its `git checkout --detach`, as `run_git/2` does.
- TaskRegistry crash warning: `command_shell_test.exs`'s deliberately-crashing genesis task wraps the action in `capture_log/2`.
- Boot-time `AgentScheduler: LLM model not configured`: ONE expected line per run before ExUnit starts, because the config dir is an EMPTY temp tree.
- Global Logger level window: `task_registry/completion_logging_test.exs` lowers the GLOBAL level for its `:info` captures and restores it, so an unrelated background log can reach the console meanwhile.

## Constraints
`@moduletag :tmp_dir` supplies the ExUnit temp-dir fixture.
No mocking libraries — git tests use real `git` on temporary repos.
Test module names mirror the source module path under test.
Each test file is self-contained; inline helper modules (`DummyAgent`, `HintAgent`, …) are defined where needed.
An inline helper module used by the SAME file's `async: true` test module MUST be defined ABOVE it: `mix test` starts the ExUnit runner (`ExUnit.async_run()`) BEFORE requiring test files, so the async module's tests can run while a later helper is still unloaded — `Supervisor.child_spec/2` then raises "does not implement child_spec/1" (`./evo_git/task_registry/archive_persistence_test.exs`).
Trailing modules that are themselves `ExUnit` modules are fine, but a trailing STUB used at runtime (`delegation_hints_test.exs`'s `RoleWithUntitledSubagents`, the `evo_dash` `node_aware_test.exs` `ConnectionManager`) carries the same latent race.
`on_exit` callbacks run in a DIFFERENT process, so the `EvoGit.TaskRegistryCase` pdict keys are NOT set there — an `on_exit` calling `EvoGit.TaskRegistry.*` or a default-store `EvoGit.Store.*` silently hits the global singleton; capture and pass the isolated `store`/`registry` from the setup context.
`function_exported?/3` is a BIF that does NOT load its module, so a test asserting an export must call `Code.ensure_loaded!/1` first (`agent/runner_injected_message_test.exs`, `agent/context_builder_test.exs`, `store/task_page_api_test.exs`); `module.module_info/1`, `Module.behaviour_info/1` and `apply/3` are REMOTE calls and auto-load.
Fresh databases retire `projects` through `20260815000007_vct_mounts`, and clean/tagged-release upgrade fixtures use ordinary pending migrations with `all: true`.
Exact migration-ledger expectations include nine versions (`20260815000001` … `20260815000009`), including session mode and pause kind.
Fail-closed historical-remnant coverage belongs to `./evo_git/store/historical_sources_test.exs` and `./evo_git/migrate_store_test.exs`, whose synthetic databases pin refusal of interrupted preservation markers, hidden archive columns and hidden projects tables without modifying their data; development ledger-collision auto-reconciliation is NOT a supported upgrade path.
`:awaiting_input` — the non-terminal status of an idle interactive session — is a LIVE status everywhere `:running` counts as live: in the lease-renewable set, the killable and gracefully-cancellable sets, the not-finished set `clear_finished_tasks` skips, and the boot reconciliation that fails a session whose wrapper is gone; it is deliberately NOT a "busy" status, so a `/server/status` idle gate may wind it down gracefully.
`./evo_git/status_admission_totality_test.exs` enforces that pairing as a data table over every status list the runtime exposes, so a list admitting `:running` without `:awaiting_input` fails there rather than silently deleting or wedging a waiting session.
- Prefer deleting a whole redundant `describe` block over weakening a surviving assertion; NEVER weaken a surviving assertion.
- Verify a "duplicate" claim by reading the sibling test before deleting anything.
