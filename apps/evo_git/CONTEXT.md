# EvoGit — Core Runtime Application

## Intent
The `:evo_git` OTP application implements an evolutionary software development runtime where LLM-powered agents create, analyze, and modify codebases using git worktree isolation. The system models a codebase as a **Context Tree** (spatial dimension) and a **Phylogenetic Graph** (temporal dimension).

### SSH Remote Development
Genesis supports **SSH remote development** (like VSCode Remote SSH): a lightweight headless `:evo_git` daemon runs on a remote server (via `systemd-run --user`), and the local Phoenix dashboard connects to it via **Erlang distribution over an SSH tunnel**. The local web frontend controls the remote runtime. Two core foundation modules enable this:
- `EvoGit.RemoteConnections` — TOML-based store (`~/.config/genesis/remote_connections.toml`) for SSH target definitions. New schema uses `ssh_target` (a plain SSH host string like `gpu-server` or `user@host` — port/keys handled by `~/.ssh/config`), `local_binary_path` (path to local `genesis_remote` binary), `dist_port`, `remote_path`, `name`, `id`, `last_connected`. Old `host`/`user`/`port`/`identity_file` fields are auto-migrated to `ssh_target` on load.
- `EvoGit.AgentScheduler.RemoteAPI` — a read-only RPC API over the scheduler's ETS state, designed to be called via `:erpc.call/4` from the local dashboard. All returns are serialization-safe plain maps/lists/scalars (no struct references or PIDs cross-node). Distribution is enabled via Mix release env vars (`RELEASE_DISTRIBUTION`/`RELEASE_NODE`); the existing `Phoenix.PubSub` PG2 adapter already uses `:pg` (OTP 26+), which supports multi-node out of the box — no Redis or third-party PubSub required.

## Routing Table
- `./lib/` → Application source (agents, core domain, adapters, runtime, scheduler, config)

# Agent Loop Control Flow (relevant to injecting messages/notifications mid-run)
The agent turn loop has a clear single entry point per iteration where context is prepared **before** the next LLM call. The call chain is:

`EvoGit.Agent.Runner.run/3` → `do_run/2` (builds initial `%ReqLLM.Context{}`, creates `%LoopState{}`, calls `loop/1`) → **`loop/1` is the top of each turn** → `do_turn/1` (Runner) delegates to `ToolDispatch.do_turn/5` → `prompt_until_tools_or_limit/5` → `call_llm_with_retry/5` (inside `AgentScheduler.with_llm_slot/2`, calls `ReqLLM.stream_text/3`) → `process_llm_response/5` (appends assistant msg + tool results to context) → `loop_fn.(state)` re-enters `loop/1`.

**THE injection point for "before the next LLM call":** `Runner.loop/1` (`apps/evo_git/lib/evo_git/agent/runner.ex`, ~line 218). At the top of each iteration, after `compress_if_needed` and `check_limit_warnings` run, the context is finalized and about to be handed to `do_turn` (which calls the LLM). Appending a pending user message here (after warnings, before the `cond do`) is the clean "before next LLM call, not mid-call" spot. Context is a `%ReqLLM.Context{}` (a struct wrapping `messages: [ReqLLM.Message.t()]`); append via `ReqLLM.Context.append(context, user(msg))`. Turn-tagging helper: `EvoGit.Agent.ContextBuilder.tag_message_turn(msg, turn)`.

There is **NO existing inbox/pending-message concept** — the only dynamic context additions are turn-limit warnings and recovery messages, both injected in `loop/1`. `AgentState` (ETS) and `LoopState` (in-memory, threaded through the loop) are the two places state could carry a pending message; `AgentState` is the cross-process writable surface (dashboard writes via scheduler → ETS → agent reads at top of loop).

## Constraints
- Part of an **umbrella project** — deps, build artifacts, and lockfile live at the repository root.
- All git operations must go through `EvoGit.Adapters.Git` — no direct `System.cmd("git", ...)` in domain modules.

### Distribution & Release Setup (relevant to remote/SSH features)
- **EPMD-less distribution via custom module.** All `rel/vm.args.eex` files use `-epmd_module Elixir.EvoGit.EpmdDist` with `-start_epmd false`. The `EvoGit.EpmdDist` module implements the `erl_epmd` interface using `:persistent_term` as a node→port registry. No external `epmd` process is needed. Distribution is NOT started at boot for the local dashboard — it is enabled on-demand by `EvoGit.Distribution.enable_for_remote/1` when a user initiates a remote connection. The remote daemon starts distributed at boot (port 9000).

### SSH Remote Bootstrap Failure Modes (diagnosis reference — 3 issues FIXED)

**✅ FIXED — Problem (a): Bootstrap fails on a pre-existing failed systemd unit.**
`start_daemon/3` (Linux clause, `remote_connection.ex`) now runs `systemctl --user reset-failed genesis-remote 2>/dev/null; true` BEFORE the `systemd-run` launch command. This clears stale failed/inactive units idempotently (exits 0 if nothing to reset, non-zero if unit never existed — both acceptable). The reset result is ignored (best-effort), so bootstrap proceeds regardless.

**✅ FIXED — Problem (b): No launch health-check.**
`maybe_start_daemon/3` now calls `verify_daemon_healthy/2` after `start_daemon/3` returns `:ok`. This retries `daemon_running?/2` up to 3 times with 1s sleep between (total ~3s wait for BEAM VM boot). If the daemon never reaches `active`, returns `{:error, {:daemon_not_healthy, details}}` where details includes `systemctl --user status genesis-remote 2>&1 | tail -20` output on Linux. ### Config Caching Behavior (important for remote/SSH scenarios)

**`EvoGit.Config.resolve/0` has NO caching.** It reads config.toml from disk on every call (`File.read` + `TomlElixir.decode`). No `persistent_term`, module attributes, ETS, or memoization is used. `user_config/0`, `credentials/0`, and `defaults/0` all compute fresh values each call.

**The actual cache is the AgentScheduler GenServer state.** `AgentScheduler.init/1` calls `Config.resolve()` once at startup and stores the result in `%State{}`. `AgentScheduler.get_config/0` (and therefore `RemoteAPI.get_config/0`) returns values from this in-memory state — NOT from disk. This means:

| Path | Reads disk? |
|------|------------|
| `RemoteAPI.get_config/0` → `AgentScheduler.get_config/0` | ❌ No — returns cached GenServer state |
| `RemoteAPI.reload_config/0` → `Config.resolve()` → `AgentScheduler.update_config/1` | ✅ Yes — refreshes GenServer state from disk |
| `RemoteAPI.get_config_status/0` → `Config.config_status/0` → `Config.resolve()` | ✅ Yes — reads disk fresh every call |

**`save_user_config/1` does NOT auto-reload.** Writing to disk only persists the file; the caller must separately invoke `reload_config/0` to push changes into the running scheduler. The dashboard's `SettingsLive` does call `reload_remote_config/1` after saving remotely (settings_live.ex:612), but **the return value is not checked** — if the `:erpc.call/5` fails (timeout, node down), the scheduler silently retains its stale config while the user sees "Configuration saved successfully."

**`RemoteConnections` does NOT auto-create an empty `remote_connections.toml`.** `list/0` returns `[]` when the file doesn't exist. The file is only created on first `save/1` via `File.mkdir_p`. No empty file is bootstrapped at startup.
- **Slot discipline**: All LLM calls must acquire/release slots via `AgentScheduler`. **Multi-model support**: the runtime supports multiple LLM models simultaneously, each with its own independent concurrency slots, generation params, and per-model 60-second backoff (a rate-limit on one model does NOT block agents using other models). Config via `[[llm.models]]` TOML array-of-tables (each profile: `id`, `model`, `concurrency`, generation params). Old flat `[llm]` config auto-migrates to a single-profile list with id `"default"` **at load time only** (`Config.resolve/0` → `migrate_llm_models/1`). - **Genesis Mode B — Two-Root-Agent Architecture**: `Genesis.run_new_codebase/4` spawns TWO sequential root agents sharing a single `task_id`:
  1. **Phase 1 — Architecture**: `EvoGit.Agents.CodebaseLead` (renamed from `CodebaseArchitect`) runs as the first root agent. Its objective is the original user prompt. It designs the architecture (CONTEXT.md, directory structure, public API) and delegates child architecture to `subagent_codebase_lead` subagents. It does NOT implement code — it delegates implementation to `subagent_manager`.
  2. **Phase 2 — Implementation**: After the architect succeeds, `EvoGit.Agents.Manager` runs as a second root agent starting from the architect's final commit. Its objective combines the original objective + the architect's result report, instructing it to complete the implementation. The Manager has a "Genesis Implementation Mode" section in its prompt for this use case.
  - **Usage/cost aggregation**: Combined `usage` (via `Usage.add/2`), `agent_count`, and `archive_records` from both agents are merged into a single `%Result{}` passed to `merge_and_report/3`.
  - **Archive record deduplication (by construction)**: Since both root agents share a `task_id`, the old design needed a between-phase `Lifecycle.clear_archive_records/1` to avoid double-counting. With the per-task collection, no clear is needed: each phase's records are consumed (collected + cleared) at that phase's root completion (`Lifecycle.handle_task_result/3`), so the Manager phase starts with an empty per-task collection. The architect's records are preserved in `architect_output.archive_records` and combined with the Manager's at `genesis.ex:230-231`. The table is a `:set` keyed by `{task_id, agent_id}`.
  - **Error handling**: If the architect fails → immediate error return. If the architect succeeds but the Manager fails → the architect's result is returned as a partial success with a warning log.
  - **task_id generation**: `run_new_codebase/4` generates the `task_id` upfront (if not provided in opts) so both agents share it. Previously the scheduler auto-generated it; now genesis.ex controls it.
  - Mode A (existing codebase / ContextExtractor) is unchanged — single root agent.
- **No `try/rescue` anti-pattern**: `try/rescue` is normally a code smell in Elixir — it usually indicates we lack a clean process structure or supervision tree, and are manually handling process lifetimes or masking bugs. **Do NOT add new `try/rescue` blocks.** Before reaching for one, ask: (1) Do we really expect that error? If not → **let it crash**; the supervision tree / restart logic handles recovery (crashing is better than a silent error or corrupted value). (2) If we DO need to handle it, can we do it cleanly? Prefer `case`/`if`/`cond`/`with` with non-crashing function variants (`Regex.compile` not `Regex.compile!`, `JSON.encode/2` not `Jason.encode!/2` + rescue, `:persistent_term.get/2` not `get/1` + rescue, `Integer.parse/1` not `String.to_integer/1` + rescue). Only use `try/rescue` in the rare justified cases listed below. **Every `try/rescue` that remains in the codebase MUST have a comment explaining why it is justified** (answer both questions above).
  - **Justified `try/rescue` cases (rare):** `terminate/2` or cleanup/shutdown code that must never crash the caller; centralized exception boundaries (e.g. `safe_llm_call/2` in the evolution engine, the single rescue for all evolution LLM calls); `SystemCheck` public diagnostics functions that must never crash the dashboard LiveView; `String.to_existing_atom/1` on untrusted user config keys where there is no non-crashing variant; `try/catch` around functions with no non-crashing variant (e.g. `Path.wildcard`). See `EvoGit.Store` for a good "crash philosophy" reference doc.
  - **Eliminate immediately:** `try/rescue` around `!`-suffixed functions that have non-crashing variants; silent `rescue _ -> :ok` swallows; LLM-call rescues that degrade silently to defaults (either add retry logic or let it crash); broad rescues that hide bugs; redundant internal-helper rescues when the public entry point already rescues.
- **User Message Injection to Running Agents**: A user (via dashboard/RPC) can send a text message to a specific running agent. The message is appended to the agent's `pending_user_messages` queue (a new `AgentState` field) and drained at the top of the next turn in `Runner.loop/1` — injected as a user-role message **before** the next LLM call (not mid-call). Concurrency-safe: appends are serialized through the AgentScheduler GenServer (`send_user_message/2`); the drain re-reads fresh ETS state and only resets the one field. API chain: `EvoDash.NodeContext` → `EvoGit.RemoteNode.send_agent_message/3` → `EvoGit.AgentScheduler.RemoteAPI.send_agent_message/2` (RPC guard via `:ets.whereis/1`) → `EvoGit.AgentScheduler.send_user_message/2` (GenServer call) → `Store.append_pending_user_message/2`. Agent drain: `Runner.drain_and_inject_user_messages/1` → `Store.drain_pending_user_messages/1`. Messages are turn-tagged via `ContextBuilder.tag_message_turn/2`.
