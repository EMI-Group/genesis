# EvoGit — Core Runtime Application

## Intent
The `:evo_git` OTP application is an evolutionary software-development runtime: LLM agents create, analyze and modify codebases in isolated git worktrees, modeling a codebase as a **Context Tree** (spatial) and a **Phylogenetic Graph** (temporal) evolved through a DAG of commits.
Phases: **Genesis**, **Evolution**, and a repo-less **self-reflective** agent (`:reflect`), all on an LLM/tool slot-gated scheduler.
Task persistence (`EvoGit.Store`/`EvoGit.TaskRegistry`) lives here so the headless `genesis_server` daemon has full task history — detail: `lib/evo_git/CONTEXT.md`.

- `lib/evo_git/vct.ex` + `lib/evo_git/vct/` → the internal-only Virtual Context Tree namespace: `vct:///projects/<name>` project points and `vct:///workspaces/<slug>` workspace points persisted in `vct_mounts`, a capped project list (`max_projects/0`, 100) beside an UNCAPPED workspace list, RESERVED system mounts (declared via `:system_mounts` + `ensure_mount/3`), and an optional lazily-git-managed global context at `<data_dir>/vct/CONTEXT.md` — detail: `vct/CONTEXT.md`.
- Storage model: every JSON column (`opts`/`logs`/`result`/`usage`/`error`) is plain UTF-8 JSON TEXT — no compression layer (`store/codec.ex`).
- **The VCT is a pure INTERNAL namespace over OS paths, NOT a filesystem**: a mount binds a canonical `vct:///…` point to an absolute OS path as METADATA only (a workspace mount binds an ordered member list and no path), no symlink farm/bind/FUSE/junction exists, no directory is created for a point, and a mount's OS path need not exist.
- Task/agent execution is UNCHANGED by the VCT: an agent still runs in ONE concrete repo worktree, in-repo references stay relative and foreign-repo ones absolute; a `vct:///` URL is internal metadata, NEVER a prompt path — `EvoGit.Core.ContextNode.build_context/2` labels the global context `global/CONTEXT.md` and every in-repo stage `./…/CONTEXT.md`.
- The VCT owns the project list: `projects/1`/`search/2` return PROJECT mounts ONLY as `[%EvoGit.VCT.Mount{}]` newest first (`last_opened_at` DESC with `nil` LAST, then `point` ASC); `:limit` is a DISPLAY cap only while the table caps PROJECT mounts at `max_projects/0` evicting the OLDEST; reserved mounts never appear or auto-activate, `:include_workspaces` (default `false`) adds workspaces, and workspaces are never capped.
- A point is a PROJECT mount exactly when `vct:///projects/<name>[...]` (`Table.project_mount?/1`), a WORKSPACE mount exactly when `vct:///workspaces/<slug>` (`Table.workspace_point?/1`), and every other parseable point is a RESERVED system mount (`Table.reserved?/1`): resolvable through `resolve/1`/`mount_for_path/1`/`vct_path_for/2`, never listed, never evicted, refused by `forget/1` with `{:error, :reserved_point}`.
- `EvoGit.VCT` keeps the authoritative list in memory as its read cache and persists every mutation through the store (`Store.save_vct_mounts/2` atomic replace-all; `Store.list_vct_mounts/1` at `init/1`); `<data_dir>/vct/` holds only the optional GLOBAL context and its lazily-git-managed repository.
- `%EvoGit.VCT.Mount{point, path, name, kind: "git", last_opened_at, members: [], description: nil}`: `point` is the canonical URL and `path` the absolute OS path (listed even when missing); `workspace?/1`/`git?/1` classify the kind, `member/1` reads a member ref, `normalize_members/1` is the STRICT creation validator, and the LENIENT `from_map/1` preserves members as stored so a nested/unusable ref is reported by resolution.
- Mount points are VIRTUAL and listable even when the recorded OS path is missing: registering a path matching the name/basename of a mount whose path is gone RE-POINTS that mount (same point) instead of adding a second one, and no registration requires the path to exist.
- Project mounts over RPC: `RemoteAPI.projects/0` (PROJECT mounts only), `mount_project/2`, `forget_project/1`, mirrored as `RemoteNode.projects/1`, `mount_project/3`, `forget_project/2` — a mount list is implicitly per-BEAM-node, with no node/host column or shared table.
- Workspace mounts over RPC: `RemoteAPI.workspaces/0`, `create_workspace/3` (idempotent slug-keyed upsert), `workspace_members/1`, `workspaces_for/1`, mirrored as `RemoteNode.workspaces/1`, `create_workspace/4`, `workspace_members/2`, `workspaces_for/2`; list reads degrade to `[]`, `workspace_members/1` to `{:error, :not_found}`, a failed RPC to `{:error, {kind, reason}}`.
- `EvoGit.VCT` workspace API: `create_workspace/3` (member errors `{:member_is_workspace, point}`/`{:invalid_member, ref}`/`:invalid_members`; name `{:error, :invalid_name}`), `workspaces/1`, `workspace_members/1`, `workspaces_for/1`, `workspace_entries/1,2`; pure rules `Table.workspace_mounts/1`, `upsert_workspace/6`, `member_mount/2`, `workspaces_containing/3`; `forget/1` also accepts a workspace point or bare name; a **member ref** is STRING-keyed `%{"point" => point | nil, "path" => "/abs" | nil}` with at least one non-nil key.
- `TaskRegistry` owns task state only and holds no mount state; every mount read, write and broadcast belongs to `EvoGit.VCT` (`mount/2`, `ensure_mount/3`, `forget/1` → exactly one `{:vct_updated, node}` on `"vct"`).
- A **workspace IS the one grouping layer** over the flat machine-local mount list: a `kind: "workspace"` mount at `vct:///workspaces/<slug>` with NO OS path, an ORDERED `members` list and optional `description`, created idempotently through `EvoGit.VCT.create_workspace/3`; nesting is refused (exactly ONE level), workspaces are never capped and never an execution path or OS-path owner (`RuntimeOpts.admit_task_path/1` refuses one). The separate multi-REPO mechanism stays the TASK-level `[foreign_repos]` table in `<repo>/genesis.toml` (`EvoGit.ProjectConfig.foreign_repos/1` → `EvoGit.Core.ForeignRepo`); operator entry point `mix vct.workspace create` beside the dashboard Projects surface; the documented example `vct:///workspaces/foobar` groups `genesis`, `genesis-doc`, `evoclass`.
- Config is machine-global, per-project settings are the repo's `genesis.toml`: `EvoGit.Config.config_path/0` = `<EvoGit.Platform.config_dir()>/config.toml` (XDG `~/.config/genesis`, macOS `~/Library/Application Support/genesis`, Windows `%APPDATA%/genesis`; `credentials.toml`, `agents.toml`, `tools/`, `remote_connections.toml` beside it) and there is NO per-project settings table; per-project config is `<repo>/genesis.toml` only — `EvoGit.ProjectConfig.read/1` (`nil` when absent), `.worktree_script/1,2`, `.write_worktree_script/2`, `.foreign_repos/1`, `.commands/1`, exposed as `RemoteAPI.read_project_config/1` / `RemoteNode.read_project_config/2`.
- Archive: ONE row per agent in `task_agent_archives`, keyed `(task_id, agent_id)`, plain-JSON columns, written STREAMING at completion by `Completion.write_archive_refs/7` (gated `archive && base_commit`) → `TaskRegistry.put_task_archive/1` → `Store.put_task_archive/2` in the COMPLETING AGENT's process, so the row commits BEFORE the task reaches a terminal status; a task start clears its rows; reads `list_task_archives/3` (LEAN unless `:include_results`/`:include_settings`; `:include_total: false` skips `count(*)`), `get_agent_archive/3`, `delete_task_archives/2`, mirrored on `RemoteAPI`/`RemoteNode`; deletes cascade explicitly (`Archives.delete_by_task/2`, `delete_by_tasks/2`, `delete_all/1`) → `agent/completion.ex` + `store/operations/archives.ex`.
- Transcripts are NOT archived in the TASK store: `task_agent_archives` has NO messages column and `:evogit_agent_summary` never carried the context — a finished agent's conversation is reachable only through `agent_state.sqlite`, the live agent, or the tool's own side artifacts.
- **Persistent agent state (per-task durability, default ON)** → `agent_state/CONTEXT.md`: `:persistent_state` (default `true`, inherited by descendants) stores ONE row per running agent in `<data_dir>/agent_state.sqlite` (conversation chunks, depth/spawn position, git facts, `redispatch`, `status`/`result`), with stable `agent_id`s, one coalescing writer, `flush/1` the only synchronous call, non-fatal DEGRADED boot, hourly retention, and crash-in-tool-call repair via `EvoGit.Agent.Resume`; modules `agent_state.ex` + `agent_state/` (`supervisor.ex`, `server.ex`, `entry.ex`, `boot.ex`, `store.ex`, `record.ex`, `retention.ex`, `redispatch.ex`, `anchor.ex`).
- Archive caveat: the same `EvoGit.Agent.Completion.complete/4` also writes the `refs/notes/evogit` note (private `add_metadata_note/3`, gated on `base_commit` ALONE, a DIFFERENT usage shape with a legacy `cost` key; `Completion.get_agent_metadata/2` has NO caller in `lib/`).
- Read fault isolation: `Store.offload/5` (unlinked monitored worker, 25 s deadline, degrades to the read's empty shape); `TaskRegistry.ReadOffload` (supervised `Task.Supervisor` + 28 s deadline, replies the decoded term STRAIGHT to the caller) and `TaskRegistry.StoreGuard` (a failed write → `{:error, :store_unavailable}`) → `store/` + `task_registry/`.
- Lightweight reads: `select_tasks_page/2` (16-key rows + `total`), `get_task_lite/2`, mirrored on `TaskRegistry`/`RemoteAPI`/`RemoteNode` → `store/operations/{pages,lightweight}.ex`.
- `mix store.maintenance [--data-dir PATH] [--vacuum] [--no-optimize]` (on-demand reclaim; `--vacuum` flips `auto_vacuum` to incremental first; never at boot) → `lib/mix/tasks/` + `store/`.
- Peak/off-peak scheduling → `agent_scheduler/` + `config/`; presets → `config/provider_presets.ex`, holidays → `peak_hours/holidays.ex` (§ Peak/Off-Peak); tmpdir (`[tmp] mode` `:system`/`:custom`/`:per_repo` + `[tmp] path`, injected as `TMPDIR`, EVENT-DRIVEN reclaim on terminal status) → `task_tmpdir.ex` + `sandbox/`.

## Provider Profiles & Concrete Model Selections

Canonical config uses `[llm] default_provider_profile` to select an account in `[[llm.providers]]`; the first account is used only when no selector is supplied.
Each account owns a stable `id`, `provider`, shared authentication (`auth_mode`, `api_key_env_var` or `oauth_file`), endpoint, `concurrency` and peak/off-peak schedule for every model/effort in its nested ordered `models` inventory; OAuth paths are account settings, never a global `[llm] oauth_file`, and `LLM.profile_generation_params/1` remains the single generation/auth/provider-constraint assembly boundary.
The reasoning-effort ladder is `EvoGit.Config.Schema.LLM.reasoning_efforts/0`, which RE-EXPORTS `EvoGit.Config.Schema.ReasoningEffort.levels/0` (`[:none, :minimal, :low, :medium, :high, :xhigh]`, ascending, NO `:max`), with `reasoning_effort_options/0` adding `:default`, `allowed?/1` the acceptance predicate and `canonical_reasoning_effort/1` the normalizer; `max` is an accepted legacy ALIAS for `xhigh` on read, and the provider's documented spelling is emitted only at the request boundary (`LLMConstraints`'s `:reasoning_effort_wire_aliases`).
`default_model` selects a model (first when absent) and optional `default_reasoning_effort` is never inferred from effort order; `Schema.provider_profiles/1` returns canonical STRING-keyed accounts, `model_selections/1` enumerates ordered choices without reading credentials, and `resolve_model_spec/2` validates a default, account id or explicit selection.
A task `model_spec` is a STRING-keyed identity map (`provider_profile_id`, `model`, optional `reasoning_effort`) — not a ReqLLM identifier or secret-bearing parameters; the schema's resolved `model_spec` is the ReqLLM-ready qualified string or endpoint-override map, stored by dispatch as effective `llm_model` alongside `llm_generation_params`, configured `llm_context_window` and the complete canonical selection.
Explicit invalid selections fail closed before registration; a locked parent selection overrides child picks and scripts with the ENTIRE account/model/effort identity, while unlocked children inherit it as `default_model_spec`.
Legacy `[[llm.models]]`, flat `[llm] model` and legacy selection ids remain supported with one-for-one account normalization; nonempty canonical providers take precedence and saving canonical config strips legacy mirrors.
An explicit task selection is validated before enqueue and submitted as `model_spec` with `model_id_locked: true`, while no selection means Auto and omits both keys; legacy `model_id` accepts account ids, `id:provider:model` and matching inventory models (details: `lib/evo_git/CONTEXT.md`).
The dashboard Settings → LLM editor writes canonical accounts and defaults preserving unrelated settings; `Config.config_status/0` combines presence with validation errors (an invalid default selector is unhealthy even when another account works); `SystemCheck` resolves selections through Schema before testing the effective request.
Compression consumes the effective configured context window, never catalog limits, and cost prices effective `llm_model` with the account's peak/off-peak period; details belong to `config/`, `config/schema/`, `agent/` and `agent/compression/`.

## Custom Agents & Model Selection

User-defined agents live in `<config_dir>/agents.toml` with name/prompt, read/read_write authority, delegation level, optional turn cap, tools/subagents whitelists and optional canonical `model_spec` (legacy `model_id` remains a fallback).
`CustomAgents` normalizes selection keys/effort values, rejects malformed definitions with `:invalid_model_spec` on save and leaves existence checks to dispatch; whitelists are alias-aware and may include custom tools, an absent whitelist exposes built-ins only, and `CustomAgents.reload/0` invalidates caches.
`ModelSelector` evaluates the administrator's compile-once `fn agent -> <script> end` body per spawn and accepts a canonical account/model/effort map or legacy profile id, with nil/empty/false meaning fallback and script errors logged without crashing.
Dispatch priority is explicit task or inherited locked selection → script → canonical definition/inherited `default_model_spec` → legacy definition/inherited `model_id` → configured default; invalid canonical script selections fail closed, unknown legacy ids keep the default fallback, and custom `max_turns` overrides scheduler turn caps.
`Runtime.Helpers.resolve_root_agent/2` validates `:agent`, forwards canonical definition defaults without locking them, and builds the custom root whose Runner installs `:custom_agent_id`; schemas/scripts belong to `custom_agents/`, spec construction to `runtime/`, selection/inheritance to `agent_scheduler/` and `agent/`.

## Multi-Modal Content (objective, tool results, injected messages)

Media (images/audio) rides LLM content parts at THREE sites; wire contract `EvoGit.Attachments` (`lib/evo_git/attachments.ex`), structured tool output `EvoGit.Agent.ToolOutput` (`agent/tool_output.ex`).

- **Shape**: STRING-keyed `%{"type" => "image"|"audio", "name" => basename, "media_type" => IANA, "data" => base64}`; base64 is MANDATORY at every data-plane boundary (task opts, pending-message queue) because `Store.Codec` Jason-encodes whole opts and raw binaries abort Jason; decoding happens ONLY at materialization (`Attachments.to_content_parts/2`) as a plain `[ContentPart.text(text) | media parts]` list, NEVER `ReqLLM.ToolResult`; `Attachments.message/1` is the ONE normalizer.
- **Caps**: ≤ 4 attachments per message, each ≤ 15 MiB RAW bytes (`EvoGit.Attachments` attributes are the single source), per task opt AND per tool output; malformed payloads raise `ArgumentError`.
- **Site 1 — `:attachments` task opt (root-only)**: ROOT agent's FIRST user message only (`ContextBuilder.build_initial_messages/4`, gated on `parent_id == nil`; subagents never inherit); Genesis Mode A, both Mode B roots and the Evolve root receive it, Reflect never; validated by `RuntimeOpts` → `Attachments.validate/1`.
- **Site 2 — tool results (any agent, any turn)**: `Tools.execute/5` may return `String.t() | ToolOutput.t() | {:error, reason}`; `agent/tool_dispatch.ex` is the SOLE **wrap boundary** — sanitize/truncate + hint appenders hit the TEXT component only, media is re-wrapped, error/timeout/crash paths stay plain strings. Detail: `agent/`.
- **Site 3 — injected user messages (mid-run, NO root gate)**: `send_user_message/2`, `send_session_message/3`, `RemoteAPI.send_agent_message/2`, `RemoteNode.send_agent_message/3` accept `String.t() | %{text:, attachments:}`; `Store.append_pending_user_message/2` stores shape-for-shape in the `ControlPlane` inbox, materialized by `ContextBuilder.build_injected_message/2`. Detail: `agent_scheduler/` + `agent/session/CONTEXT.md`.
- **Invariants**: a plain-string tool result and a legacy string pending message behave BYTE-IDENTICALLY to pre-media behavior (`%ReqLLM.Message{}` struct-equality pin in `test/evo_git/agent/tool_output_pipeline_test.exs` + `tool_output_integration_test.exs`); compression keeps `[system, first_user]` BYTE-IDENTICALLY (objective attachments re-sent after every compression — the cached prefix must not change) and the last K turns VERBATIM, while OLDER tool-result media collapses into one `[... tool result media omitted ...]` placeholder; resume / merge-auto-resolve / GitHub-fix follow-ups do NOT re-carry `:attachments`.
- **No built-in producer**: no built-in tool returns media — `read` is text-only, there is no `read_image`/`screenshot`, `web_fetch` renders non-text bodies as `[binary content omitted: …]`, and custom tools are STRING-ONLY; only the test seam app env `:evo_git, :tool_dispatch_test_tools` produces tool-result media, and only the dashboard produces attachments (`EvoDash.AttachedFile`).
- **Deliberately NO modality gate**: nothing checks the selected model, so the part is always sent — ReqLLM encodes `:image` for OpenAI-compatible chat, Anthropic, OpenAI Responses/Codex, Google and zai; a text-only model answers HTTP 400, which `EvoGit.Agent.LlmError.non_retryable?/1` turns into a fail-fast `{:llm_request_rejected, message}` → `:failed` task. Audio is nominal (a `:file` part, expected to be provider-rejected).

## Multi-Repo Read-Write Foreign Repos

Foreign repos may be **writable** — still ONE primary repo + one final report per task; foreign modifications are tracked but NEVER merged back by the task (the review page merges/rejects).

- **Data model** (`Core.ForeignRepo`): `writable: boolean()` (default `false`) + `base_sha: String.t() | nil` (`nil` = foreign HEAD); `new/*`/`normalize/1` handle STRING-keyed Codec maps; a task `:foreign_repos` entry stays READ-ONLY unless `genesis.toml` marks the repo `writable` (TOML-only).
- **Registry**: NO `[[repos]]` table exists in `config.toml`; the declared set is per-project `genesis.toml` `[foreign_repos.<id>]` (`ProjectConfig.foreign_repos/1`: TOML key IS the id, `path` required, `description`/`writable`/`base_sha` optional), merged id-keyed with the task opt by `Runtime.Helpers.load_foreign_repos/2` (a task entry wins per id, never removes a TOML entry); existence/git-repo/`base_sha`/UNC validation is runtime-only and raises `ArgumentError`.
- **Per-repo history**: `EvoGit.TaskCommitGraph` resolves a repo's base from `opts[:foreign_repos]` (`foreign_base_for/2`) and walks the STRING-keyed `result["repos"]` map, while `EvoGit.Review` is repo-path-parameterized and foreign-repo-agnostic.
- **Spawn gate** (`Subagents.validate_spatial_contract_for_spec/3,4`): read-only cross-repo spawns UNRESTRICTED at any depth; `:read_write` cross-repo spawns need `writable: true` (`{:error, {:foreign_repo_read_only, msg}}`), are **root-only** (`{:error, {:foreign_repo_write_not_root, msg}}`) and **one per batch** (`{:error, {:foreign_repo_write_serialized, msg}}`); same-repo spawns inside a foreign repo are UNRESTRICTED. The role comes from id-matching `spec.foreign_repos`, NEVER the path; unknown ids → read-only.
- **Tool gating**: `Tools.execute/5` chains `maybe_block_read_only_foreign_repo/5` after `maybe_block_repo_less/5` — blocks every `@write_tools` entry (incl. `run_git`); `Shared.validate_file_scope/3` rejects write targets inside one; `Tools.read_only_schemas/0` = read tools + Context write/edit + ShellTool + `WebFetch` + `Lsp` only when `Config.lsp_enabled?/0`.
- **Roots + report** (`Runtime.Helpers.merge_and_report/3,4`): writable repos get worktree roots like the primary with ONE branch name per task reused across all. The report gains top-level **`repos: %{repo_id => %{commit_sha, branch_name}}`** (STRING keys): `"primary"` always, each writable repo that committed, read-only ABSENT; top-level `commit_sha`/`branch_name`/`result` stay the PRIMARY's. Source `Result.foreign_repo_commits`, rolled up by `Lifecycle.inject_foreign_repo_commits/2` + `store_sub_result/3` (child-wins).
- **Review + scoping**: each writable repo carries an `evogit-agent-*` branch at `repos[repo_id].commit_sha`; `Review.merge_branch/2,3` + `reject_branch` are per-repo-path; `maybe_init_repo/3` (required `primary?`) wipes `.genesis/workers` + `clean_orphaned_branches` ONLY for the primary, and `run_init_script` stays primary-only.
- **Persistent foreign worktree (read view)** at `<root>/.genesis/foreign_repos/<id>` (`ForeignRepo.worktree_path/1`), reset at task start (`ForeignWorktree.ensure_all/1`), advanced by `Agent.Runner.run/3` `try/after` → `sync_from_agent/0`; outside `.genesis/workers/`, never moves MAIN HEAD, kept at task end.
- **Validation + merge seeding**: `resolve_foreign_repo_starting_commit/2` = `base_sha` else foreign HEAD; subagent phylo precedence = task `base_sha` → tracked `foreign_repo_commits` → foreign HEAD. `apply_merge_context/4` carries `:foreign_repos` and overrides each `base_sha` from the prev task's `repos[repo_id]["commit_sha"]`; `apply_resume_context/3` keeps `:foreign_repos` and overrides per-repo base_sha in BOTH branches; shared `TaskRegistry.PrevTaskRepos`. Detail: `task_registry/`.
- **Prompts**: `:read_write` foreign spawns are ROOT-ONLY + ONE-AT-A-TIME; `PromptFragments.writable_foreign_repo_clause/0` is role-agnostic and tells NESTED agents to report upward, while each agent's role is stated in its FIRST-USER context by the pure `ContextBuilder.build_authority_section/1` (root signal `parent_id == nil`). Detail: `runtime/` + `agent/` + `core/`.

## Self-Reflective Agent (repo-less)

A **repo-less** Assistant with no repository or worktree uses tiered Elixir evaluation to inspect runtime state, control tasks and show transient guides.

- **Task type**: `:reflect` — `TaskExecutor.execute_task(:reflect, opts, task_id)` runs `Runtime.SelfReflective.run(opts ++ [task_id: task_id])`; codec atom `:reflect`, mode `"reflect"`; opts `objective`, optional `model_spec`/legacy `model_id`, `model_id_locked`, `source_root` and `task_id`, **NO `:path`** (the executor skips `RuntimeOpts.build_common_runtime_opts/1`); result `{:ok, %{result: summary, commit_sha: nil, branch_name: nil, tag: nil}}`.
- **Lifecycle + visibility**: a `:reflect` task is an ordinary `tasks` row — `TaskRegistry.start_task/2` persists it as `:running`, leases it, and settles it through the standard wrapper → `handle_wrapper_result/3` (`:completed`/`:failed`), with a graceful cancel force-mapping to `:cancelled`; the answer is `tasks.result["result"]`. Store list/summary/page/lite reads never filter by `task_type`, so reflect rows appear there (each carries `type`) and in `/server/status` `active_tasks`; hiding them and refusing review are caller/UI decisions (`EvoDashWeb.NodeAware.show_review_button?/1` returns false for a completed `:reflect`).
- **No session reuse on the one-shot path**: a `:reflect` task allocates a NEW task/session/agent id with a fresh conversation, and the session is gone once it ends, so consecutive runs share only scheduler/config/catalog caches and the managed source checkout; memory must be replayed as text inside `objective` (the dashboard's "Previous conversation:" preamble). Multi-message chat uses an interactive session instead (`Runtime.Assistant` + `send_session_message/3`), keeping ONE conversation, worktree and cache key.
- **Synthetic worktree name**: `Dispatch.try_dispatch/2` still builds `<source_root>/.genesis/workers/worker_T<n>_A<m>` and `next_task_number/1` `File.ls`es that directory, but no file or directory is ever created.
- **Plumbing**: `spec.opts[:repo_less] = true`, `phylo_node` nil; `Dispatch.resolve_agent_repo_root/2` short-circuits to `resolve_repo_less_root/0` (`SelfReflectiveSource.reference_path/0` → `File.cwd!()` → `"[system]"`); the Runner skips `create_worktree_for_agent`, sets `Process.put(:repo_less, true)`, `commit_pending_in_worktree/0` no-ops; **write guard** `Tools.execute/5` blocks `@write_tools` and `available_tools/0` omits them.
- **Modules**: `Agents.SelfReflective` (`agent_type :read`, `delegation_level :low`, `subagent_modules []`) exposes source-reading tools (`read`, `rg`, `glob`, `list_dir`, context/history readers), `web_fetch`, config-gated `web_search` and tiered `elixir_eval`, but no shell, file writes or `run_command`; read raw implementation before calling an admitted API, and inspecting source never authorizes an unlisted function.
- **One `elixir_eval` tool**: read/write use Dune with explicit real module/function/arity grants while projected Read/Write facades stay optional. Write requires exact-code approval and admits task lifecycle operations, runtime scheduler updates, persistent `Config.save_user_config/1` and explicit `AgentScheduler.RemoteAPI.reload_config/0`; saving replaces the whole config and refreshes the snapshot synchronously but applies no scheduler runtime state, so preserve unrelated settings with a read–modify–save. Sudo separately requires explicit approval for unrestricted native Elixir with full VM authority (not a sandbox), and refusals never trigger escalation. Each call has fresh bindings, fail-closed Assistant-owner authorization and bounded output; unlisted MFAs, wrong arities and the `CommandShell` registry stay unavailable — details: `agent/tools/elixir_eval/CONTEXT.md`.
- A reply with no tool calls ends the run; `Runtime.SelfReflective` owns source resolution/spec construction, and `SelfReflectiveSource` owns the managed clone and declares `vct:///genesis-source`.
- `:running → :completed/:failed/:cancelled` emits NO `:finalizing` broadcast; the root has `parent_id: nil` and a matching `task_id`. Live content: `EvoGit.Agent.Stream.watch/1` pushes `{:agent_delta, agent_id, seq, events}` (snapshot + `seq` is the only resync); a completed transcript is fetched once via `get_agent_history/1` — **history is gone once the session ends**.
- The persisted artifact is `task.result`, with no `resume_from`; tests include `reflect_tools_test.exs`, `self_reflective_source_test.exs`, `self_reflective_test.exs`, repo-less scheduler/tool-dispatch cases and `task_executor_reflect_test.exs`.
- Details belong to `agents/` and `runtime/`, with dashboard Home chat (`EvoDashWeb.HomeLive`, `GET /assistant`; legacy `GET /help` 302-redirects) in `apps/evo_dash/CONTEXT.md`.

## LLM Concurrency & Slot Gating

LLM resource pools are keyed by immutable `provider_profile_id`, so every concrete model/effort selection in an account shares concurrency and exhaustion backoff while distinct accounts stay isolated; historical fields such as `model_concurrency` and `llm_backoff_until` keep their names but hold account ids on the canonical path.
`AgentScheduler.with_llm_slot/2` blocks in a purgeable `:infinity` call, capacity-zero requests enqueue, and `default_llm_max_concurrency` is a floor/fallback rather than a global cap, preserving explicit zero pauses; runtime updates preserve live holders/waiters/backoff, global pause gates pending grants, and resume/capacity changes sweep eligible waiters without evicting in-flight holders.
Rate-limit and insufficient-balance failures report growing account-shared backoff through `AgentScheduler.report_llm_error/3`; agents park in the slot queue rather than sleeping, preserving cancellation responsiveness.
`ReqLLMPool` sizes HTTP capacity from account concurrency once per account, never multiplying by nested model/effort choices, and reconciliation remains grow-only.
Slot maps, retry policy, reload/legacy behavior and pause contracts belong to `agent_scheduler/` and `agent/`; Finch sizing and peak-engine integration to `lib/evo_git/CONTEXT.md`.

## Peak/Off-Peak Hour Concurrency Scheduling

Provider accounts own `peak_concurrency`, `peak_hours`, `off_peak_days`, `off_peak_holidays` and `timezone`, with `peak_concurrency = 0` a hard pause shared by all their models/efforts and exempt from the default-concurrency floor.
`EvoGit.PeakHours` is the single source of truth for half-open/overnight/day-scoped windows, the off-peak-day rule, local/IANA wall clocks, validation and transition math.
The day-level rule is ONE predicate: a date is off-peak when its weekday is in `off_peak_days` OR (`off_peak_holidays` names a calendar AND `EvoGit.PeakHours.Holidays.non_working_day?/1`) — so a statutory CN holiday, an ordinary weekend and a 调休 make-up Saturday (a WORKING day) all resolve through the same path.
`in_peak?/4` and `next_transition/4` take `off_peak_holidays` last (`/2` and `/3` are `nil`-calendar delegators), `effective_concurrency/2` reads the key off the profile map, `/3` resolves the wall clock first, and `next_transition`'s horizon is 21 days.
`EvoGit.PeakHours.Holidays` is a static, data-driven table (2025-2027 official 国办发明电 arrangements; extend yearly) — NOT a dependency, to avoid `mix.lock`/`mixFodDeps.hash` churn.
`EvoGit.Config.ProviderPresets` ships the built-in presets (DeepSeek off-peak discount, Z.AI GLM coding plan) as pure data with a string-keyed `schedule` that merges into a canonical account; `PeakHourEngine` prefers canonical profiles, falls back to legacy ones only when canonical accounts are absent, and applies one floored concurrency entry per account preserving explicit zero and peak exemptions.
Account TOML/validation contracts belong to `config/`, engine/RPC integration to `lib/evo_git/CONTEXT.md`, timer/queue/floor details to `agent_scheduler/`.

## Agent Loop Control Flow + Graceful Task Cancellation

**Loop injection point**: `EvoGit.Agent.Exchange` drains the session inbox at the top of each turn (after compression/limit warnings, before the LLM call); `ControlPlane.drain_messages/1` yields turn-tagged user messages appended to the conversation, so a parked interactive session resumes exactly where its `%State{}` was checkpointed.
API chain: `EvoDash.NodeContext` → `RemoteNode.send_agent_message/3` → `RemoteAPI.send_agent_message/2` (guards `{:error, :scheduler_not_started}` when `:evogit_agent_summary` is undefined) → `AgentScheduler.send_user_message/2` → the `ControlPlane` inbox append, returning `:ok | {:error, :not_found}`; interactive conversations use `send_session_message/3` → the session's `:input` command. Detail: `agent/` + `agent_scheduler/`.

**Two cancellation actions** (node-aware via `RemoteNode.cancel_task/2` + `force_kill_task/2`):
- **Graceful cancel** (`TaskRegistry.cancel_task/1`): `:pending` → immediate `:cancelled`; `:running`/`:awaiting_input` → `:cancelling` + `{:cancel, :graceful}` (the session appends a save-work user message through the inbox, records the cancel flag in `:evogit_agent_control`, plus an `:evogit_cancelling_tasks` marker). The exchange loop enters cancel-grace with a **3-turn budget** (a recovery auto-commit first); the final status persists `:cancelled` WITH result/usage/archive **preserved**. `:cancelling` is non-terminal + idempotent and blocks new root spawns (`{:error, :cancelled}`).
- **Force kill** (`force_kill_task/1`): kills the in-flight exchange worker, stops the session, kills the wrapper and persists **`:failed`** with result nil'd, from `:running`, `:awaiting_input`, `:pausing`, `:paused` and `:cancelling`; `:cancelled` means ONLY gracefully-cancelled tasks.
- **Task pause** (`pause_task/1` / `resume_task/1`): the two NON-terminal pause statuses `:pausing` (draining, wrapper alive, lease renewed) and `:paused` (resting, resumable IN PLACE through the same task id) — protocol, restart mapping and archive rules: `task_registry/CONTEXT.md`.
- **Dashboard**: a Cancel button (warning modal) and force kill in the card dropdown, both node-aware; `:cancelling` renders in the busy amber family and `:cancelled` is reviewable. Detail: `task_registry/` + `agent_scheduler/` + `apps/evo_dash/CONTEXT.md`.

## Update-Timing Safety

No restart/update machinery exists in `:evo_git` (zero `System.restart`/`:init.restart`/`:init.stop`, no signal handlers, no checkpointing on exit); graceful stop comes from `:evo_dash` (`DesktopQuit.default_stop/0`, SystemLive Stop — both `System.stop/0`), and the Rust shell NEVER sends SIGTERM (watchdog uses SIGKILL). `bin/<release> stop`/`restart` need `RELEASE_DISTRIBUTION != none` + a resolvable `RELEASE_NODE`, so the non-distributed desktop sidecar must be stopped from within; the pre-restart mechanism is **graceful cancel** (3-turn grace, NOT wall-clock bounded — each grace turn is a full LLM+tools cycle).
Idle-detection API: `TaskRegistry.list_task_ids(statuses \\ [])` / `list_tasks_summary(statuses \\ [], since \\ nil)` / `list_tasks_changed_since/1` / `get_task/1` (+ RemoteAPI/RemoteNode mirrors); in-flight set `[:running, :pending, :finalizing, :cancelling]`.
Task status lives ONLY in SQLite (`tasks.status`); scheduler ETS holds summary/control rows plus sched_meta for LIVE agents (never the conversation) and dies with the app — sessions are in-memory, so a BEAM restart fails any `:awaiting_input` session (`:failed`) and reclaims its worktree. Lease: `@lease_duration` 120s, heartbeat every 60s renews `[:running, :pending, :cancelling, :awaiting_input, :pausing]` (not `:finalizing`, never `:paused`); the one-shot `:lease_sweep` at `@sweep_after` 150s marks orphaned `:running` → `:failed` ONLY when the lease is invalid AND no live sched_meta agents. Startup reconciliation: `:finalizing` → `:failed`, `:cancelling` → `:cancelled` (result preserved), a RESUMABLE `:running`/`:pausing` row → `:paused` + `pause_kind: :dirty` (else `:running` untouched). In-place resume restores the durable ROOT of the SAME task id while the Review page's `resume_from` remains a NEW `:evolve` task (`ResumeContext`). Detail: `agent_scheduler/` + `task_registry/`.

## Backend Boot Profile (desktop sidecar readiness)

Boot work in `:evo_git` is CONSTANT-COST: nothing keyed to the release version or install path; no lockfile/`.genesis/` marker/cache verification/release-tree read at start.
Ordered `EvoGit.Application.start/2` work: (1) create the 4 ETS tables; (2) `Distribution.maybe_enable/0` (logs + returns `{:error, _}`, never raises); (3) `Calendar.put_time_zone_database(Tz.TimeZoneDatabase)`; (4) children: PubSub → **`Config.Watcher`** (skipped in `:test`) → Throttle → CommandApproval → RemoteConnection Registry/Supervisor → **`Store`** → `Store.Maintenance` → **`VCT`** → TaskRegistry ReadSupervisor/ProcessRegistry → TaskRegistry → BackgroundJobs → WorktreeManager → AgentGroupSupervisor (Task.Supervisor → **`EvoGit.CatalogWarmup`** → AgentScheduler) → PeakHourEngine → SystemSampler, plus SandboxProcessRegistry + SandboxSlice on Linux. `Config.Watcher` sits immediately after PubSub (its `"config"` broadcasts need it) and BEFORE the children that read config, priming the RAM snapshot in its own process; `VCT` starts after `Store` (loading `vct_mounts`) and before `TaskRegistry`, started as `{EvoGit.VCT, system_mounts: EvoGit.SelfReflectiveSource.system_mounts()}`; `CatalogWarmup` sits immediately before the scheduler (returns `:ignore`).
The ONE potentially slow child is `Store`, whose `init/1` runs migrations before any read/write (`Store.Boot.start_dynamic/2`); `TaskRegistry.init/1` then does a synchronous `Store.select_running_lease_info/1`; everything else is O(1).
**Boot-fatal paths** (a child EXIT ⇒ "Genesis backend unavailable"): an unwritable/missing data dir (`File.mkdir_p!` raises), a failed repo open (`{:stop, {:failed_to_open_sqlite, reason}}`), or ANY raise out of the migration run (baseline post-condition `Ecto.MigrationError`, bad `tasks` shape, `SQLITE_BUSY`, corrupt file); with `start_permanent: Mix.env() == :prod` a terminating permanent app takes the VM down.
`Store` opens with `journal_mode: :wal` + `default_transaction_mode: :immediate` + `busy_timeout: 30_000` (a locked `tasks.sqlite` stalls a statement up to ~30 s in the calling process) and WAL needs `-wal`/`-shm` sidecars on a shared-memory-capable filesystem (a network/UNC data dir can fail the open); no boot-time self-exit exists in `:evo_git`.
**Observability**: the boot path emits no phase logs of its own — only Ecto.Migrator's lines (`Store.Boot` has ZERO Logger calls), `Config.resolve/0` warnings, the `PeakHourEngine: starting — watched profiles: …` + `wakeup reason=:boot`/`next wakeup in` pair, and Linux `SandboxSlice` warnings.
**Boot lines CAN repeat inside ONE OS process**: a `Store` crash re-runs `init/1`, and `System.restart/0` re-boots all applications INSIDE the running node — its only caller is the dashboard System page (`system_live.ex`; remote `EvoDash.NodeContext.restart_remote/1`). `EvoGit.Supervisor`/`EvoGit.AgentGroupSupervisor` declare no restart intensities (OTP defaults 3/5s); exceeding them terminates the supervisor and, `evo_git` being `:permanent`, the node goes down — the Rust watchdog respawns a NEW OS process. The log handler appends (`type: :file` + rotation) and `<data_dir>/logs/backend.log` is configured in the ROOT `config/runtime.exs` (10 MB × 5), so nothing in `:evo_git` writes/truncates/rotates/deletes under `<data_dir>/logs/`.
**No first-start-of-a-NEW-release-dir delta exists on the Elixir side** — per-BEAM one-time costs recur on EVERY boot. Port resolution / orphan prevention: root `./CONTEXT.md`.

### Boot memory profile (what a boot can actually allocate)
- The five app-owned ETS tables are created EMPTY (one boot insert only: the registry's store pid); no boot child loads task rows (`TaskRegistry.init/1` reads lease info only, `AgentScheduler.init/1` reads NO SQLite), and `EvoGit.VCT.init/1` performs exactly ONE mount-table read (`Store.list_vct_mounts/1`) kept as its read cache.
- The SQLite page cache is per-connection and LAZY: `EvoGit.Repo.start_opts/0` sets `cache_size: -8_000` (8 MiB) × `Boot.default_pool_size/0` = 6 — a ~48 MB STEADY-STATE ceiling but ~0 at boot (the boot leg touches only `sqlite_schema` + `schema_migrations`) → `store/` + `repo.ex`.
- The ONE eager multi-megabyte boot allocation is the LLMDB catalog, and it lands in a THROWAWAY process: `EvoGit.CatalogWarmup` resolves the configured profiles in its own short-lived process (`Schema.llm_generation_params/1` → `model_metadata/1` → `ReqLLM.model/1` → `LLMDB.ensure_loaded!` decoding the 11.7 MB packaged snapshot, ~10k models, into `:persistent_term`), so the decode's transient heap dies there and only the catalog is retained for the BEAM lifetime.
- That load requires the provider ATOM to exist already (`Schema.LLM.catalog_key/1` uses `String.to_existing_atom`, rescuing to nil) and no path interns one: a provider STRING resolves through the compile-time `@known_providers` whitelist built from `LLMCatalog.providers/0`, so metadata resolves on the FIRST call for any model written as `"provider:model"`; the warm-up is skipped when no model is configured → `config/schema/CONTEXT.md`.
- Measured shape (4-profile config, isolated data dir, `[sandbox] mode = "disabled"`, `-mode embedded`): with the warm-up the scheduler holds KB-scale heap (~29 KB at boot, ~54-66 KB later) and the endpoint is up ~2.1 s after the first boot log line; without it the scheduler retained the catalog's ~92 MB dead heap for the whole BEAM lifetime — the failure the warm-up exists to prevent → `agent_scheduler/CONTEXT.md`.
- **Steady-state OS memory** (same config, one `GET /` at t≈15-25 s): embedded release ≈ **RSS 395-396 MB / PSS ≈ 329 MB** with boot peak **VmHWM ≈ 770 MB**; the same release booted interactive settles ≈ RSS 177 MB, and a fresh `mix phx.server` ≈ RSS 200 MB. Interactive vs embedded dominates, NOT dev-vs-prod (the embedded gap is preloaded code 81 vs 29 MB plus carrier pages ERTS never returns); **boot PEAK is 0.6-0.9 GB RSS in every mode**, so an early sample reads far above the steady floor.
- Runtime probe on a running node, no code change: node name/cookie come from `[node] node_name`/`shortnames`/`cookie`, so `elixir --name probe@127.0.0.1 --cookie <cookie> -e ':erpc.call(:"genesis@127.0.0.1", fn -> … end, [])'` runs arbitrary code remotely; read `:persistent_term.info/0` (cheap) and never `:persistent_term.get/0` (copies EVERY value and wedges the probe).
- Boot experiments must disable the sandbox (`[sandbox] mode = "disabled"` + isolated `XDG_CONFIG_HOME`/`XDG_DATA_HOME`): `SandboxSlice.init/1` runs `systemctl --user stop evogit.slice`, and an agent shell itself runs INSIDE that slice, so booting from such a shell SIGTERMs its own BEAM; `bin/<release> eval` starts no applications by itself and is INTERACTIVE.
- Migrations read blobs only on an UPGRADE (`20260815000002_data_normalization.exs` selects legacy `id, opts` rows in ONE result set; `20260815000005_task_agent_archives.exs` streams one legacy row at a time); a current/fresh DB runs no migration body, and the migration `[{version, module}]` source is compiled once with `Code.compile_file/1` and memoized in `:persistent_term` (`store/boot.ex`).
- Runtime (NOT boot) growth lives in the conversation, owned by the session in its own heap rather than ETS (`:evogit_agent_summary` carries only the summary projection and its row is removed when the session ends) → `agent_scheduler/CONTEXT.md` + `agent/session/CONTEXT.md`.
- Boot-time side effects that cost CPU/processes but no memory: `BackgroundJobs.init/1` fires an async `Sandbox.Background.sweep_stale_units/0` on Linux, and `SandboxSlice.init/1` runs `systemctl --user stop evogit.slice` + a 100 ms sleep before creating the slice.

## Known Issues

- **Whichever process first touches the LLMDB catalog on a fresh BEAM pays the whole load in ITS OWN heap — so at boot that process must be a throwaway one.** `:llm_db` loads `priv/llm_db/snapshot.json` (11,693,807 B, 239 providers, 10,100 models) lazily on the first query, decoding the JSON, building model lists + indexes and canonicalising the catalog for a `term_to_binary` digest — all in the caller's heap; `:persistent_term` READS never copy, so the retained MBs are dead garbage awaiting a fullsweep, NOT live state. `EvoGit.CatalogWarmup` therefore loads it in a short-lived process; the shape to avoid is a LONG-lived process that happens to be first (e.g. a scheduler booted after a warm-up timeout).
- **Process/thread exhaustion inside containers breaks git forks (EAGAIN).** In rootless podman every process shares the host user's UID, so the kernel's per-UID `RLIMIT_NPROC` (`ulimit -u`) spans container + host processes (every OS thread counts); when hit, `fork()` fails with `EAGAIN` — git prints "cannot fork() ... Resource temporarily unavailable" (e.g. in `git worktree add`). `WorktreeManager` survives (persistent init marker + re-monitoring) but the run loses agents to crash-retry. Prevention: raise the HOST user's nproc limit (`/etc/security/limits.conf` or `systemctl --user set-property user.slice TasksMax=infinity`); or `--ulimit nproc=65536:65536 --pids-limit -1` (`pids_limit = -1` + `default_ulimits` in `~/.config/containers/containers.conf`); or delegate the pids controller (`/etc/systemd/system/user@.service.d/delegate.conf` → `[Service] Delegate=cpu cpuset io memory pids`); verify via `ulimit -u` / `/sys/fs/cgroup/pids.max`; or reduce concurrency (`[scheduler] default_llm_max_concurrency`, per-profile `concurrency`).

## Constraints

- Part of an **umbrella project** — deps, artifacts and lockfile at the repo root; Elixir ~> 1.18; **Git CLI only** (no libgit2); no source at root — all code under `./apps/`; subdirectories follow Elixir convention (`./lib/evo_git/<subdir>/` ↔ `EvoGit.<Subdir>`).
- All git operations go through `EvoGit.Adapters.Git` (or `Shared.commit_files/4` → `EvoGit.sandbox_run`); no direct `System.cmd("git", ...)` in domain modules (exception: GitEnv's config reads).
- `remote_api.ex` and `remote_node.ex` are intentionally long cohesive RPC wrappers — do NOT split them; add new RPC functions there (`defnode` macro from `EvoGit.RemoteNode.Defnode` for identity-unwrap wrappers; per-function-fallback wrappers stay hand-written).
- Agents are transient modules using the `EvoGit.Agent` behaviour; framework state lives in ETS; execution happens in **isolated git worktrees** managed by `AgentScheduler.WorktreeManager`, never on the main working copy; agents commit before delegating subagents (auto-commit fallback enforced by the scheduler).
- **Three-level configuration** (`EvoGit.Config`): built-in defaults → user config (`~/.config/genesis/config.toml`, XDG) → runtime overrides; **no default model or username is hardcoded**.
- **Slot discipline**: agent LLM calls acquire/release account-shared slots via `AgentScheduler`, binding immutable `provider_profile_id` independently of concrete `model_spec` and effective `llm_model`; the canonical `[[llm.providers]]` account owns concurrency/peak/backoff and shared auth/endpoint defaults, and nested model/effort inventory creates no additional pools. Legacy `llm.models`/flat configuration and `model_id` remain compatibility inputs, while locked children inherit the full canonical selection and lock; details belong to `config/`, `agent_scheduler/` and `agent/`.
- **Task-scoped naming**: worktree dirs `worker_T<task_number>_A<task_local_id>`, branches `evogit-agent-T<task_number>-A<task_local_id>`; `task_id` = 16-char hex GUID, `task_number` = short integer from a linear scan of `.genesis/workers/`, used only for naming. The owning repo root is derived from a WORKTREE PATH by the one literal split `String.split(path, "/.genesis/workers/", parts: 2)` (`agent_scheduler/worktrees.ex`, `repo_root_from_worktree/1`), called only by `Dispatch.resolve_agent_repo_root_regular/2` (`agent_scheduler/dispatch.ex`) and `WorktreeManager`'s monitor rebuild fallback (`worktree_manager.ex`); a path outside `workers/` is returned unchanged, so repo identity is inferred from path SHAPE. Foreign-repo agents instead resolve their root by ID lookup in `spec.foreign_repos` — one repo root + one worktree per agent, never a per-task mount table.
- **VCT is metadata, never a filesystem**: mount points are virtual and listable even when a mount's OS path is missing (that is what makes a project list portable across machines); the mount table is machine-local `vct_mounts` rows in `tasks.sqlite` holding project mounts, uncapped one-level workspace mounts (no OS path, ordered members) and reserved system mounts, and the global context's git repository is initialized lazily only while that context is non-empty.
- **Task persistence runs in `:evo_git`** — `Store` + `TaskRegistry` sit in the supervision tree, so the `genesis_server` daemon has full task history; a freshly-started Registry leaves orphaned `:running` rows to the lease sweep; test isolation pins `config :evo_git, :data_dir` to a UNIQUE per-run temp path in `config/test.exs`. Detail: `store/` + `task_registry/`.
- **Task Archive (opt-in)**: the `:archive` task opt → `runtime_opts` → `AgentSpec.opts` → `%EvoGit.Agent.State{}.archive`; each completing agent writes `refs/genesis/archive/T{task_id}-A{agent_id}-start`/`-final` + a usage git note + ONE `task_agent_archives` row STREAMING at completion (idempotent upsert on `(task_id, agent_id)`). No buffer, nothing in `%Result{}`/report; CRASH/FAILURE/ABORT writes NO row (usage LOST — a retry resets to `Usage.zero()`); Genesis Mode B shares one `task_id` → exactly 2 nil-parent rows; JSON round-trip caveats (string keys/timestamps; keys `input_cost`/`output_cost`/`total_cost`, never `cost`). Detail: `store/` + `agent_scheduler/`.
- **Distribution & releases** (EPMD-less via `-epmd_module Elixir.EvoGit.EpmdDist` + `-start_epmd false` in all `rel/vm.args.eex`; daemon on port 9000; releases `genesis`/`genesis_desktop`/`genesis_server` in the root `mix.exs`; prod-only `PORT`/`PHX_IP` → `[server] listen_port`/`listen_ip`, default 9999; zombie prevention via dynamic port + `EVOGIT_LIFETIME_PORT`): detail `lib/evo_git/CONTEXT.md` + root `./CONTEXT.md`.
- **SSH remote bootstrap** (remote commands are argv arrays, never quote-wrapped spawn strings: `run_ssh_command/4` `{:spawn_executable, ...}` + one argv element, wrapped by `sh_wrap/1` as `/bin/sh -c '<script>'` — no `/usr/bin/env`, no bash, since stock NixOS lacks `/usr/bin/env` while `/bin/sh` is POSIX-mandated; every remote script is POSIX sh and single-quote-free by construction, so fish/nushell/tcsh login shells pass the wrapper through untouched; override seam app env `:remote_shell`; the daemon is the `genesis_server` release and ALL its lifecycle — systemd scope/unit, launchd plist, setsid fallback, readiness wait — is delegated to that release's `bin/genesis` CLI (`genesis remote start|stop|status|logs`); identity is verified from the node the CLI reports; NixOS patching happens only while the daemon is not running; best-effort `:copying_config`): detail `lib/evo_git/CONTEXT.md`.
- **Config caching is RAM-resident and event-refreshed** (`EvoGit.Config.Cache`: ONE `:persistent_term` snapshot per config dir holding user config + credentials + resolved map + validation errors + fingerprint, so `resolve/0,1` is a term lookup with no stat/merge/validate; `save_user_config/1`/`save_credentials/1` raise `EvoGit.Config.Watcher.notify_change/2` synchronously (total and bounded — a `nil`/dead/slow watcher falls back to the same guarded reload), the SAME handler the watcher's ~150 ms debounced file event runs, bumping `generation` and broadcasting `{:config_reloaded, node, dir, generation}` on `"config"`; `RemoteAPI.reload_config/0` forces a re-read; the ACTUAL runtime cache is AgentScheduler state, so a save does not apply scheduler settings; `RemoteConnections` does NOT auto-create `remote_connections.toml`): detail `config/`.
- **Genesis Mode B** (`Genesis.run_new_codebase/4`): Phase 1 `Agents.Architect` → Phase 2 `Agents.Manager` (second root from the architect's final commit; "Genesis Implementation Mode" prompt). Both share ONE `task_id`; usage and `agent_count` merge into a single `%Result{}` → `merge_and_report/3`; Architect fails → immediate error, Manager fails → architect's result as partial success; Mode A (`ContextExtractor`) uses one root. Detail: `runtime/`.
- **No `try/rescue` anti-pattern**: prefer `case`/`if`/`cond`/`with` + non-crashing variants (`Regex.compile`, `:persistent_term.get/2`, `Integer.parse/1`); justified only for `terminate/2` cleanup, centralized boundaries (`safe_llm_call/2`), `SystemCheck` diagnostics, `String.to_existing_atom/1` on untrusted keys, and `try/catch` around functions with no non-crashing variant (`Path.wildcard`). **Every remaining `try/rescue` MUST have a justifying comment.**
