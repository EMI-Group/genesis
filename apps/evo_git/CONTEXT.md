# EvoGit — Core Runtime Application

## Intent
The `:evo_git` OTP application implements an evolutionary software development runtime where LLM-powered agents create, analyze, and modify codebases using git worktree isolation. The system models a codebase as a **Context Tree** (spatial dimension) and a **Phylogenetic Graph** (temporal dimension).

### SSH Remote Development
Genesis supports **SSH remote development** (like VSCode Remote SSH): a lightweight headless `:evo_git` daemon runs on a remote server (via `systemd-run --user`), and the local Phoenix dashboard connects to it via **Erlang distribution over an SSH tunnel**. The local web frontend controls the remote runtime. Two core foundation modules enable this:
- `EvoGit.RemoteConnections` — TOML-based store (`~/.config/genesis/remote_connections.toml`) for SSH target definitions. The schema uses `ssh_target` (a plain SSH host string like `gpu-server` or `user@host` — port/keys handled by `~/.ssh/config`), `local_binary_path` (optional — local `genesis_remote` tarball; when absent or set-but-missing, bootstrap auto-probes the remote platform and downloads the matching release from GitHub), `platform` (optional `<os>_<arch>` override that skips the SSH platform probe), `dist_port`, `remote_path`, `name`, `id`, `last_connected`. Old `host`/`user`/`port`/`identity_file` fields are auto-migrated to `ssh_target` on load.
- `EvoGit.AgentScheduler.RemoteAPI` — a read-only RPC API over the scheduler's ETS state, designed to be called via `:erpc.call/4` from the local dashboard. All returns are serialization-safe plain maps/lists/scalars (no struct references or PIDs cross-node). Distribution is enabled via Mix release env vars (`RELEASE_DISTRIBUTION`/`RELEASE_NODE`); the existing `Phoenix.PubSub` PG2 adapter already uses `:pg` (OTP 26+), which supports multi-node out of the box — no Redis or third-party PubSub required.

## Routing Table
- `./lib/` → Application source (agents, core domain, adapters, runtime, scheduler, config)
- `./test/` → ExUnit test suite using real git operations on temp directories
- `./lib/evo_git/core/` → `ContextNode` (spatial) and `PhyloGraphNode` (temporal) data structures
- `./lib/evo_git/adapters/` → `Git` CLI adapter — thin wrapper around `System.cmd("git", ...)` — and `GitHub` (gh) CLI adapter — upstream detection + GitHub issue listing/markdown via the `gh` command
- `./lib/evo_git/agent/` → Agent behaviour, tool library, context compression, subagent processing, usage tracking
- `./lib/evo_git/agents/` → Agent implementations (Manager, Executor, TaskScheduler, Investigator, Architect, ContextExtractor, SkillExtractor, GenesisPlanner, Custom)
- `./lib/evo_git/custom_agents/` → `EvoGit.CustomAgents` (agents.toml store) + `EvoGit.CustomAgents.ModelSelector` (per-agent model selection script)
- `./lib/evo_git/runtime/` → Genesis, Evolution, and Prompts (LLM templates)
- `./lib/evo_git/agent_scheduler/` → `AgentState`, `SchedMeta`, `Slots`, `Worktrees`, `WorktreeManager`, `RemoteAPI` — ETS schemas, helper logic, worktree lifecycle, and RPC-readable state API for remote (SSH) dashboard connections
- `./lib/evo_git/config/` → `EvoGit.Config` — defaults, user TOML, credentials, API keys, version-state tracking
- `./lib/evo_git/sandbox/` → `EvoGit.Sandbox` — multi-platform sandbox backends (Linux systemd-run, Linux bwrap, macOS sandbox-exec, passthrough)
- `./lib/evo_git/store/` → `EvoGit.Store.Codec` — pure serialization for the SQLite store
- `./lib/evo_git/task_registry/` → `EvoGit.TaskRegistry` support modules — `Cleanup`, `Diagnostics`, `Lease`, `MergeContext`, `ResumeContext`, `RuntimeOpts`, `TaskExecutor`

| `EvoGit.AgentScheduler.WorktreeManager` | Stateful GenServer owning the entire worktree lifecycle (supervised in `EvoGit.Application`). **Lazy per-repo init**: on the FIRST `create_worktree_for_agent/6` request for a repo it runs rm_rf `.genesis/workers` → `Git.prune_worktrees` → orphaned `evogit-agent-*` branch cleanup → mkdir_p — never from the scheduler. **Request API**: `create_worktree_for_agent(agent_id, repo_root, worktree_path, spec, meta, agent_pid)` — a `GenServer.call` with a named 1-hour timeout (`@worktree_call_timeout` 3_600_000), called by the agent Runner; the handler offloads the blocking create I/O to a spawned `Task` (reply via `GenServer.reply/2` + `{:create_finished, agent_id}` cast — same pattern as TaskRegistry `:list_tasks`). Per-agent serialization: a second create request for an agent whose create is still in flight is stashed in `pending_requests` and started when the previous create finishes (retry-after-crash-during-setup race); agents that die mid-create are tracked in `pending_cleanup` and cleaned up when the create task finishes. **Monitor-driven reclaim**: `Process.monitor(agent_pid)` per agent; on `:DOWN` for ANY reason (normal exit, crash, cancel kill) the worktree is destroyed — `File.rm_rf(worktree_path)` → `Git.prune_worktrees(repo_root)` → `Git.delete_branch(repo_root, branch_name)` (this order — git refuses to delete a branch checked out in another worktree). Idempotent; the GenServer never crashes on agent exits. API: `workers_dir/1`, `start_link/1`. |

### Remote Bootstrap Asset Format

The SSH remote-bootstrap release asset is a **`.tar.xz`** archive: `genesis_remote_<platform>.tar.xz` (asset name, download URL, local cache path, and remote temp file all use `.tar.xz`). This is coordinated with `.github/workflows/build-desktop.yml`, which uploads per platform: `genesis_remote_linux_x64.tar.xz` and `genesis_remote_linux_arm64.tar.xz` (glibc is the default and ONLY published Linux variant — no `_glibc` suffix; the musl build is disabled for now), plus `genesis_remote_darwin_arm64.tar.xz` / `genesis_remote_windows_x64.tar.xz` (never suffixed). Extraction uses `tar -xJf` — the remote host needs xz-capable tar (works on all Linux distros with xz-utils, and macOS bsdtar supports xz natively). There is intentionally NO gz fallback: if xz extraction fails it should fail loudly.

**Linux asset variants:** glibc is the default and only published Linux variant — remote tarball names are NEVER suffixed (`genesis_remote_linux_x64.tar.xz`, `genesis_remote_linux_arm64.tar.xz`). The musl build is disabled for now. The previous libc-variant machinery was removed: `detect_libc/1` (ldd parser), `probe_libc/1` (SSH `ldd --version` probe), the private `effective_libc/2` normalization, the `_glibc` suffix in asset names/URLs/cache paths, and the `libc` params threaded through `resolve_platform` → `download_tarball` → `download_url`/`cache_path` (`resolve_platform/2` now returns `{:ok, daemon_os, platform}`). Downloads always resolve the default unsuffixed glibc asset. On NixOS hosts the glibc-only Linux asset runs via on-the-fly patchelf patching during bootstrap (`EvoGit.RemoteBootstrap.nixos_patch_script/1` + the `:patching_binaries` stage) — no new asset variants; glibc stays the only published Linux variant.

### SSH Tunnel Readiness (connect-path invariant)

`EvoGit.RemoteConnection.do_connect_distributed/1` must NOT call `Node.connect/1` before the SSH tunnel's local forwarded port actually accepts TCP connections. An `ssh -L <local_port>:127.0.0.1:<dist_port> -N <target>` forward can take well over a second to start listening on the local port (measured ~1.5s), and a too-early `Node.connect` fails instantly with econnrefused → `{:error, {:node_connect_failed, ...}}` with NO remote-side log entry (the dist handshake never reaches the daemon — do not hunt for cookie/EpmdDist causes when the remote log shows nothing). The connect path therefore polls local-port TCP readiness via `wait_for_tunnel/4` (`@tunnel_poll_interval_ms` 100ms, `@tunnel_wait_timeout_ms` 10s budget), fails fast when the ssh Port dies (draining its output into the error for diagnosability), and returns `{:error, {:tunnel_not_ready, reason}, state}` on timeout/death. `connect/1`'s GenServer call timeout is `@connect_call_timeout_ms` (wait budget + 15s) so callers can't exit with a raw `:timeout` while the handler is legitimately waiting. `wait_for_tunnel/4` is `@doc false` public solely so tests can drive it with tiny timeouts/poll intervals (see `test/evo_git/remote_connection_test.exs`). Remote-side rejection ("Invalid challenge reply" in the daemon journal) means a COOKIE mismatch — a different failure mode with a visible remote log entry.

## Custom Agents & Model Selection

User-defined agents and per-agent model selection live in ONE file: `<config_dir>/agents.toml` (same dir as config.toml, next to `remote_connections.toml`). Per-node semantics: agents.toml is read from the config dir of the node executing the agent — local node for local tasks, remote host for tasks on an SSH remote node (the RPC edits the file on the node whose config is being edited). The scheduler has NO cached copy; `Dispatch.register_agent/7` calls `EvoGit.CustomAgents`/`EvoGit.CustomAgents.ModelSelector` directly per spawn (both are stat-validated-cache backed, so per-spawn cost is one `File.stat` + one `:persistent_term.get`).

```toml
[model_selection]
script = """
if agent.custom_agent_id == "code_reviewer", do: "deepseek-reasoner", else: nil
"""

[[agents]]
name = "Code Reviewer"          # human name (required)
description = "Reviews code"    # optional
prompt = "You are..."           # system prompt (required) — persona/behavior rules
agent_type = "read"             # optional: "read" | "read_write" (default "read_write")
delegation_level = "low"        # optional: "high" | "low" (default "low")
model_id = "gpt-5"              # optional: default model PROFILE id for this agent (nil = auto/default)
max_turns = 40                  # optional: per-agent turn cap override
tools = ["read_file", "run_bash", "write_file"]  # optional whitelist; absent = all standard tools
subagents = ["executor", "investigator"]          # optional: built-in agent type names this agent may spawn
```

**Definition map** (atom keys): `%{id, name, description, prompt, agent_type: :read | :read_write, delegation_level: :high | :low, model_id, max_turns, tools: [String.t()] | nil, subagents: [String.t()]}`. Defaults applied on save: `agent_type :read_write`, `delegation_level :low`, `subagents []` (note: the `EvoGit.Agent` macro's built-in default is `:high`, but the agents.toml schema default is `:low` — the store normalizes, and `EvoGit.Agents.Custom` falls back to `:low`). `tools`/`subagents` entries are STRINGS in the TOML (atom-only saves are rejected with `:invalid_tools`/`:invalid_subagents`).

**Model-selection script contract** (see `EvoGit.CustomAgents.ModelSelector.describe_contract/0`): the script body is wrapped as `fn agent -> <body> end` — the variable `agent` (a plain map) is in scope and the LAST expression's value is the result. `agent = %{agent_type: module() | :custom, custom_agent_id: String.t() | nil, depth: non_neg_integer(), parent_id: pos_integer() | nil, task_id: String.t() | nil, objective: String.t()}`. Return: model profile id `String.t()` | nil (`""`/`false` also mean default). Script errors never crash the scheduler — compile errors and raises are captured and surface as `ModelSelector.status/0` → `{:error, {:compile_error, msg}}` (shown by the dashboard; a raising script evaluates with a logged warning and falls back to default at dispatch time).

**Dispatch priority chain** (in `Dispatch.register_agent/7`, before `resolve_model_for_agent/2`): (1) `spec.opts[:model_id_locked]` — user-explicit choice wins, script skipped; (2) model-selection script (when configured) — evaluated for EVERY spawn, root AND subagents, unless locked; (3) `spec.model_id` from custom-agent definition (`model_id` in agents.toml) or inherited value; (4) default profile via `resolve_model_for_agent/2` (which also logs + falls back for unknown ids). Subagent `model_id` inheritance (`subagent_processing.ex`) does NOT set the lock. Custom-agent `max_turns` (when present) overrides `state.max_turns_root`/`state.max_turns` for that spawn.

**Runtime opts threading**: task opts `:agent` (custom agent id — validated by `Runtime.Helpers.resolve_root_agent/2`, raises `ArgumentError` on unknown id since it runs in the task process where crashing loudly is a spec error; when unset the built-in modules are used: genesis Mode B → `Architect` + `Manager`, Mode A → `ContextExtractor`, evolution → `Manager`) and `:model_id_locked` (bool; CLI `-m` sets it; dashboard explicit model choices set it). Root `AgentSpec` for a custom agent: `agent_module: EvoGit.Agents.Custom` + `opts: [custom_agent_id: id, ...]` — `AgentSpec.new` stores opts verbatim, so runtime spawn sites merge `custom_agent_id` into `spec.opts` via `then/2`. The `Runner` puts `:custom_agent_id` into the process dictionary (`setup_dispatch_context/1`) — this is the zero-arity-callback bridge: `EvoGit.Agents.Custom`'s callbacks read `Process.get(:custom_agent_id)` (built-in agent modules untouched; process dictionary dies with the agent process). Custom agents are ROOT agents only in this version (`subagent_tool_name/0` → nil) — not spawnable as subagents. To run a custom agent as the root of an evolve task, use the custom task mode (next section).

## Custom Task Mode (evolve)

The `:evolve` task type supports a `"custom"` mode opt (task type stays `:evolve`) which runs a user-defined agents.toml agent as the ROOT agent instead of the built-in `EvoGit.Agents.Manager`. Semantics are otherwise identical to simple mode (same spec-building + `merge_and_report(repo_path, agent_output, "evolve")` → reviewable `genesis/agent_*` branch).

- **Mode value**: string `"custom"` (dashboard) or atom `:custom` (CLI); `"simple"`/`:simple`/nil/absent → simple; ANY other value → `Logger.warning` + simple fallback (backward compatible with legacy task opts). ## Task Summary Query Path — Full-Scan Analysis (investigation findings)

**Q: Why does the dashboard scan ALL task rows on every poll?** The SQL filter machinery is fully functional — the full scans come from dashboard call sites that invoke the no-arg forms. `select_tasks_summary` is a deliberately UNFILTERED full scan: "lightweight" means columns only (no logs/usage/archive_metadata), NOT rows — there is no WHERE/ORDER BY/LIMIT. The optional `statuses` filter (SQL pushdown, `WHERE status IN (...)`) and the `since` filter (`select_tasks_changed_since`, changed-since poll for the remote dashboard) exist and are index-backed, but the no-arg defaults (`statuses \\ []`, `since \\ nil`) mean "all rows", and most main-list call sites never pass filters.

**Exact SQL executed** (`store.ex:755-765`, `build_summary_where/2` at store.ex:960-974):
- `statuses=[] + since=nil` → `SELECT id, status, review_status, started_at, finished_at, type, project_path, opts, branch_name, model_id, agent_count, base_sha, commit_sha, lease_expires_at, updated_at FROM tasks` (the 15-column `@summary_columns` projection, store.ex:61) — **no WHERE** → full table scan; each row decoded by `decode_summary_row/1` (store.ex:1050 — 15 columns only; **`result` is deliberately NOT selected/decoded in the summary path**, so the heavy `Codec.decode_result` — embeds usage + archive_records — never runs here; `updated_at` stays raw ISO).
- `statuses≠[]` → `... WHERE status IN (?1..?N)` — **index-backed** by `idx_tasks_status` (schema.ex:76); only matching rows decoded.
- `since≠nil` → `... WHERE updated_at > ?1` — index-backed by `idx_tasks_updated_at`.
- by_path → `... WHERE project_path = ?1` (plus optional status/since) — index-backed by `idx_tasks_project_path` (schema.ex:95). **No ORDER BY / LIMIT in any summary query** (row order unspecified).

**Full call chain:** LiveView → `EvoGit.TaskRegistry.list_tasks_summary(statuses \\ [], since \\ nil)` / `list_tasks_summary_by_path/3` / `list_tasks_changed_since/1` (GenServer.call, task_registry.ex:116-139, 403-418) → `EvoGit.Store.select_tasks_summary/3` (GenServer.call) → `handle_call` → `XqliteNIF.query`. Remote node: LiveView → `EvoDash.NodeContext.list_tasks_summary/2` → `EvoGit.RemoteNode.list_tasks_summary/2` (remote_node.ex:358) → `:erpc.call` → `AgentScheduler.RemoteAPI.list_tasks_summary(statuses \\ [])` (remote_api.ex:323) → same TaskRegistry → Store chain.

**Who calls with what (dashboard call sites — verified against current `projects_live.ex`; function-name-based):**
- **Dashboard-driven summary queries are all statuses-filtered**:
  - `Assigns.build_notified_task_ids/1` (`projects_live/assigns.ex`) — **id-only projection**: `TaskRegistry.list_task_ids([:completed, :failed, :cancelled])` → `Store.select_task_ids/2` (`SELECT id, status, updated_at`, SQL status filter, index-backed by `idx_tasks_status`; no `result`/`opts` JSON decode). Called from `projects_live.ex` `mount/3`, `activate_project/2`, and the `handle_event("clear_task_history", ...)` handler.
  - `Assigns.assign_running_and_pending_tasks/1` (`projects_live/assigns.ex`) — statuses-filtered summary `TaskRegistry.list_tasks_summary([:running, :pending, :finalizing, :completed])` (index-backed, but includes `:completed` — over time still decodes every completed row's `result` on each reload; completed needed for review-candidate `pending_tasks`). Called from `node_aware.ex` `load_running_and_pending_tasks/1` (mount + every debounced reload) and from `projects_live.ex` `handle_event("task_submit", ...)` (by_path), `handle_event("cancel_task", ...)`, `handle_event("clear_task_history", ...)`, `handle_event("delete_task", ...)`, and `activate_project/2`.
- **`projects_live.ex` `handle_info(:node_aware_reload_tasks, ...)`** — runs on EVERY task-status broadcast after the 300ms debounce (the "every poll" hotspot in local mode): local context does `TaskRegistry.list_task_ids([:completed, :failed, :cancelled])` (id-only, index-backed) → diffs against the `notified_task_ids` MapSet → fetches FULL rows via `TaskRegistry.get_task/1` ONLY for newly-terminal ids (browser notifications) → then `NodeAware.load_running_and_pending_tasks/1` (sidebar).
- **Incremental poll (Tasks page)**: `tasks_live.ex` `handle_info(:remote_poll, ...)` — the 3s remote tick uses `list_tasks_changed_since(node, last_seen_updated_at)` (`WHERE updated_at > ?`, `idx_tasks_updated_at`) — NOT a full scan; the dirty tracker is seeded with the id-only `list_task_ids` (nil-tracker re-seed at the top of `:remote_poll`; node-switch seed in `seed_dirty_tracker/1`, called from `handle_params/3`), and a full page fetch happens only when the tracker reports `:reload`/`:resync`.

**Options to make it active-tasks-only** (all filters already exist and are index-backed):
1. Pass statuses at the unfiltered call sites. `notified_task_ids` already uses the statuses-filtered id-only projection (`list_task_ids([:completed, :failed, :cancelled])`); sidebar-only reloads already pass statuses. The remaining cost is the `:completed` inclusion in `assign_running_and_pending_tasks/1` (review candidates need completed rows) — a `since` window (updated_at cutoff, e.g. 7d) or a narrower review-candidate query would bound it without changing the API.
2. Narrower projection for sidebar-only consumers (drop `result`/`opts`) — NOT safe for the sidebar's review candidates (Review buttons) or `task_notification_content`, both of which need `result` (see evo_dash/lib/CONTEXT.md Memory Profile).
3. Task.start + `GenServer.reply` offload — **applied in `EvoGit.Store`**: the Store's heavy handlers (`select_tasks_summary*`, `select_tasks_changed_since`, `safe_select_all_tasks`, `safe_select_paginated_tasks`) run query+decode on a short-lived LINKED Task inside `EvoGit.Store` (reply via `GenServer.reply/2`, `{:noreply, state}`) — no large decoded terms are allocated on the Store GenServer heap (crash-on-decode-raise preserved via the Task link). TaskRegistry's `:list_tasks` family uses the same pattern (task_registry.ex:285-310). Remaining cost is the `:completed` inclusion in `assign_running_and_pending_tasks/1` — option 1's `since` window still applies.
4. ETS/in-memory active-task index is NOT needed: `task_refs` (running only) + `EvoGit.TaskRegistry.ProcessRegistry` don't cover `:pending` (not-yet-started) or review-candidate `:completed` rows, which exist only in SQL — and `idx_tasks_status` already makes the SQL status filter cheap. The real cost is per-row `result` decode, which an ETS mirror would still need (notification content).

## LLM Concurrency & Slot Gating (investigation findings)

**Effective per-model concurrency.** `State.concurrency_for/2` (agent_scheduler/state.ex:206-208) returns `Map.get(state.model_concurrency, model_id, state.default_llm_max_concurrency)` — a per-model map lookup with a fallback for unknown model_ids. Both slot enforcers read it: `Slots.do_handle_request_llm_slot/4` (slots.ex:103) and `Slots.grant_llm_from_queue/2` (slots.ex:399). `model_concurrency` is built ONLY by `State.from_model_profiles/2` (state.ex:146-151) from `[[llm.models]]` profile `concurrency` (hardcoded fallback 3), at exactly two places: `AgentScheduler.init/1` (agent_scheduler.ex:419) and the `:model_profiles` branch of `State.do_update_config/2` (state.ex:299-325). **There is no `runtime_overrides` map in `%State{}`** — runtime overrides are plain keyword opts into `AgentScheduler.update_config/1` (agent_scheduler.ex:155-158 → handle_call at 641 → `State.do_update_config`). `Config.resolve/0` deliberately EXCLUDES runtime overrides (config/config.ex:140-141) — they live only in the AgentScheduler GenServer state.

**Default concurrency chain (per model):** profile `concurrency` (TOML `[[llm.models]]`) → hardcoded `3` in `from_model_profiles` (state.ex:150) / `runtime.exs:50` → legacy flat path: `Schema.LLM.build_legacy_default_profile/1` reads `scheduler.default_llm_max_concurrency` (schema/llm.ex:123) into the synthesized "default" profile's `concurrency` → built-in schema default 3 (config/schema/definitions.ex:23-31).

**Override lifecycle — in-memory only, no session file.** `init/1` reads `Config.resolve()` fresh (agent_scheduler.ex:384); overrides applied after boot via `update_config/1` are lost on restart. No persistence exists. `RemoteAPI.reload_config/0` (remote_api.ex:140-145) re-reads disk (`Config.resolve()`) → `build_reload_opts/1` (remote_api.ex:192-222) → `update_config`. **Note:** `build_reload_opts` passes `default_llm_max_concurrency` explicitly — applied with floor semantics via `apply_default_llm_concurrency_override/2` (never lowers explicit profile concurrencies) — in addition to `model_profiles` (per-profile concurrency wins); the legacy profile synthesis carries `scheduler.default_llm_max_concurrency` into the "default" profile when no `[[llm.models]]` exist.

**CLI `-c`/`--concurrency` is live at runtime** — `CLI.Parser.configure_scheduler/1` (cli/parser.ex:64-78, `-c` at line 67) → `update_config(default_llm_max_concurrency: N)` → `State.do_update_config`'s dedicated `apply_default_llm_concurrency_override/2` step (state.ex): sets `state.default_llm_max_concurrency = N` **AND floors every `model_concurrency` entry to `max(c, N)`** — raising the default raises the effective capacity of ALL live pools immediately (with AND without `[[llm.models]]` profiles), never lowers explicit profile concurrencies, and the trailing `Slots.grant_pending_on_resume` grants queued waiters under the new capacity. `--tool-concurrency` → `max_tool_concurrency` takes effect the same way (slots.ex:219). Dashboard paths: local save → `ConfigIO.update_runtime_from_file_config/2` (evo_dash settings_live/config_io.ex:32-79, `update_config` at line 68 — passes `default_llm_max_concurrency` AND `model_profiles`; the `:model_profiles` branch passes opts through to `from_model_profiles/2` so the passed default is honored instead of being re-derived from the first profile); remote save → `save_user_config` auto-calls `reload_config` (remote_api.ex:158-168). Also `settings_live.ex:819/1362` call `update_runtime_from_file_config`. **Init semantics**: at boot, file-based `scheduler.default_llm_max_concurrency` flows via legacy profile synthesis / profile-wins; the floor applies to runtime `update_config` only.

**Non-slot-gated LLM calls (complete inventory in lib/evo_git — 2 sites, both auxiliary):**
- `system_check.ex:344` — `ReqLLM.stream_text` in `do_llm_test/2` (LLM connectivity self-check). NO `with_llm_slot`. Invoked by the dashboard Settings/Welcome pages via spawned Tasks (`EvoGit.SystemCheck.llm_test` from settings_live.ex:1197 / welcome_live.ex:650; remote via `RemoteNode.llm_test` remote_node.ex:254-258). Model: caller-supplied (defaults to `Config.resolve([:llm, :model])`).
- `runtime/pull_request.ex:153` — `ReqLLM.stream_text` in `generate_title_with_llm/4` (PR-title generation, "never raises" try/rescue, single attempt, no retry). Called from `PullRequest.try_create/4` (pull_request.ex:31) → `Review.create_github_pr` (review.ex:478). - Slot-gated (for contrast): the agent turn loop `ToolDispatch.call_llm_with_retry/5` wraps the ONLY main-path `ReqLLM.stream_text` (tool_dispatch.ex:196) in `with_llm_slot` (tool_dispatch.ex:188); context compression (agent/context_compression.ex:79-81) is also `with_llm_slot`-gated. `EvoGit.Agent.__using__` provides NO `stream_llm`/`llm_request` helpers — agents never call the LLM directly; they delegate to Runner → ToolDispatch (agent.ex:78-80).

- `apps/evo_dash` has no production LLM calls (only a `mix translate` task using `ReqLLM.stream_object`, apps/evo_dash/lib/mix/tasks/translate.ex:617).

**Slot-pool semantics (`agent_scheduler/{state,slots}.ex`)** (details in `agent_scheduler/CONTEXT.md`):
1. **Profile-update merge (no dropped waiters, no over-grant):** `do_update_config`'s `:model_profiles` branch merges the live `llm_holders`/`llm_waiting`/`llm_backoff_until`/`llm_last_granted` maps OVER the fresh ones (old entries win for overlapping ids; new ids get empty pools) — no queued waiter's `GenServer.from` is dropped (agents block in `request_llm_slot`'s `:infinity` call while capacity is free) and live holders stay counted; the trailing `grant_pending_on_resume` grants under the new capacity.
2. **Stale-model pools stay visible:** `State.all_model_ids/1` returns the UNION of `model_concurrency`/`llm_holders`/`llm_waiting`/`llm_backoff_until` keys — pools for model_ids absent from `model_concurrency` (agents whose ETS `model_id` went stale after a profiles update removed their profile) remain visible to grant sweeps, `:DOWN` cleanup, and purge; stale pools are swept with fallback capacity.
3. **LLM release scans all pools:** `Slots.handle_release_llm_slot/2` scans ALL pools (idempotent — an agent holds ≤1 LLM slot) and cleans `llm_last_granted`. `with_llm_slot`/`with_tool_slot` RAISE on a non-`:ok` slot-request result (only producer: the `{:error, :cancelled}` purge reply to dying agents) instead of silently proceeding without a slot.

**Finch pool vs slot gating (the "excess queuing" question):** `config/runtime.exs:38-54` sizes ReqLLM's Finch stream pool ONCE at boot as `max(sum(profile concurrencies) + 2, 8)`. It is a boot-time value; runtime `update_config` changes (CLI `-c`, dashboard sliders, `reload_config`) do NOT resize it. The scheduler's slot pools (per-model, from the same profile concurrencies) are the actual concurrency gate for agent LLM calls — when slot concurrency is raised at runtime above the boot-time pool count (or when non-gated auxiliary calls run concurrently with a full pool), `ReqLLM.stream_text` calls can queue on the fixed-size Finch pool (`Finch was unable to provide a connection...`). Slot waiting (blocked agents) is a separate queue inside the scheduler and does not consume Finch connections.

## GitEnv — Commit Identity Resolution (design decision)

`EvoGit.GitEnv.git_env/1` is the single source of truth for the env map injected into EVERY git invocation — both `EvoGit.Adapters.Git` and the sandbox backends (`git_env_list/1`). It always sets `LC_ALL=C` and `GIT_EDITOR` (resolved `true` path). Identity is resolved per key with priority:

1. **Inherited environment** (`System.get_env/1`, non-empty; empty string treated as unset, mirroring git) — never clobbered.
2. **Repository's effective `git config user.name`/`user.email`** (no scope flag → repo → global → system, exactly what git itself uses).
3. **Fallback** `"Genesis"`/`"noreply@evogit.ai"` only when nothing is configured anywhere, so automated commits never fail with "Please tell me who you are".

**Memoization**: the `git config` lookup runs in the PARENT process via raw `System.cmd` (`EvoGit.Executable.resolve("git")`; config reads don't commit → no recursion through the adapter; missing git binary → `ErlangError` rescued → treated as "no value"). Memoized per repo path in `:persistent_term` (`{GitEnv, :config_identity, repo_path}`; the `nil` key = global/no-repo resolution). Stale-if-config-changed until VM restart is an accepted trade-off (avoids 2 extra process spawns per git invocation); inherited env vars are read fresh at call time, never memoized. Test helper: `GitEnv.clear_config_identity_cache/1` (`@doc false`).

**Per-repo vs global**: ALL call sites pass the repo path — `git_env(cd|repo_path|path)` in the 10 `Adapters.Git` sites, `git_env_list(cwd)` in the sandbox backends (`none.ex` System.cmd `:env` map; `linux.ex`/`macos.ex` `--setenv` args — the effective identity is explicitly re-exported because `systemd-run --user` does NOT inherit the caller's full environment). Only bare `git_env/0` calls (nil path) resolve global-level identity. Tests: `test/evo_git/git_env_test.exs` (24 tests, `async: false` due to env manipulation; hermetic via `GIT_CONFIG_GLOBAL` → empty temp file + `GIT_CONFIG_NOSYSTEM=1` so ambient machine config can't leak in).

# Agent Loop Control Flow (relevant to injecting messages/notifications mid-run)
The agent turn loop has a clear single entry point per iteration where context is prepared **before** the next LLM call. The call chain is:

`EvoGit.Agent.Runner.run/3` → `do_run/2` (builds initial `%ReqLLM.Context{}`, creates `%LoopState{}`, calls `loop/1`) → **`loop/1` is the top of each turn** → `do_turn/1` (Runner) delegates to `ToolDispatch.do_turn/5` → `prompt_until_tools_or_limit/5` → `call_llm_with_retry/5` (inside `AgentScheduler.with_llm_slot/2`, calls `ReqLLM.stream_text/3`) → `process_llm_response/5` (appends assistant msg + tool results to context) → `loop_fn.(state)` re-enters `loop/1`.

**THE injection point for "before the next LLM call":** `Runner.loop/1` (`apps/evo_git/lib/evo_git/agent/runner.ex`, ~line 218). At the top of each iteration, after `compress_if_needed` and `check_limit_warnings` run, the context is finalized and about to be handed to `do_turn` (which calls the LLM). Appending a pending user message here (after warnings, before the `cond do`) is the clean "before next LLM call, not mid-call" spot. Context is a `%ReqLLM.Context{}` (a struct wrapping `messages: [ReqLLM.Message.t()]`); append via `ReqLLM.Context.append(context, user(msg))`. Turn-tagging helper: `EvoGit.Agent.ContextBuilder.tag_message_turn(msg, turn)`.

There **IS** a pending-message mechanism: `AgentState.pending_user_messages` (a list of Strings) is written by the scheduler via `AgentScheduler.Store.append_pending_user_message/2` (used by `AgentScheduler.send_user_message/2` AND by graceful cancellation) and drained at the top of every `loop/1` iteration by `drain_and_inject_user_messages/1` (runner.ex), which appends them to the context as user-role messages. `AgentState` (ETS) is the cross-process writable surface (dashboard writes via scheduler → ETS → agent reads at top of loop); `LoopState` is in-memory only, threaded through the loop.

## Graceful Task Cancellation (status `:cancelling`, `cancel_requested`, force kill)

The dashboard "Cancel" triggers a **graceful** cancel (`RemoteNode.cancel_task/2` → `TaskRegistry.cancel_task/1`), distinct from the separate force-kill action. Details live in `lib/evo_git/task_registry/CONTEXT.md` + `lib/evo_git/agent_scheduler/CONTEXT.md` + `lib/evo_git/agent/CONTEXT.md`; this is the end-to-end picture:

- **Task status `:cancelling`** (NON-terminal: task_refs entry stays, `finished_at` nil, lease valid). Added to the codec `@known_atoms` whitelist (required or the persisted status decodes as nil), the `TaskInfo` typespec, `Store.select_finished_task_ids` (`NOT IN ('running','pending','cancelling')` — `clear_finished_tasks` never deletes an in-flight cancelling task; `:finalizing` still counts as finished), and `Store.select_running_lease_info` (`IN ('running','finalizing','cancelling')`). Startup reconciliation marks orphaned `:cancelling` → `:cancelled` (alongside `:finalizing` → `:failed`). Heartbeat renews leases for `[:running, :pending, :cancelling]`. The `{:task_updated, id, :finalizing, node}` handler (guarded `node == node()` — cross-node broadcasts ignored) ignores `:cancelling` (keeps the more informative state). Final-result force-mapping in `handle_update_status/6`: stored `:cancelling` + incoming `:completed|:failed` → persisted `:cancelled`, with result/usage/archive **preserved** (never nil'd) — a cancelled task always ends `:cancelled`.
- **`TaskRegistry.cancel_task/1` (graceful):** `:pending` → immediate `:cancelled` (and `start_task` refuses already-`:cancelled`/`:cancelling` tasks with `{:error, :cancelled}`); `:running` → status `:cancelling` + `AgentScheduler.begin_graceful_cancel(task_id)`; `:cancelling` → `:ok` idempotent (no re-send); terminal/missing → `{:error, :not_running}`/`{:error, :not_found}`.
- **`AgentScheduler.begin_graceful_cancel/1`:** registers the task_id in the `:evogit_cancelling_tasks` ETS set (created in `application.ex`); SchedMeta.task_id scan; per live agent appends the cancel message via `Store.append_pending_user_message/2` (NOT `send_user_message` — self-call deadlock) and sets `AgentState.cancel_requested = true` via `Store.set_cancel_requested/1`. The `run_agent` handler replies `{:error, :cancelled}` WITHOUT dispatch when the task is in the marker (blocks Genesis Mode B's second root). `Dispatch.register_agent` guard: any agent (re)registered for a cancelling task immediately gets the message + flag (covers subagents in the cancel window, crash-retries, late-starting queued agents). Marker cleaned via `AgentScheduler.clear_cancelling_task/1`, called from TaskRegistry terminal transitions (`clear_cancelling_marker/1`).
- **Runner side:** `Runner.loop/1` checks `Store.cancel_requested?/1` right after the pending-message drain; if set, clears it and enters cancel-grace via `trigger_recovery(state, reason, opts)` with `:message` + `:grace_turns` opts (the turn-limit call site uses budget 1). Cancel-grace: budget **3** grace turns (`grace_turns_remaining` on LoopState), no duplicate message (the cancel message came from the drain), `maybe_recovery_auto_commit` runs first ("save the changes"). Budget-aware hard-stop: `grace_period_continue_failed?/1` → `n <= 1`; decrement at the continue sites in tool_dispatch.ex. `handle_complete_call`'s grace dirty-check skip applies to both grace kinds.
- **`TaskRegistry.force_kill_task/1`**: status gate `:running | :cancelling` → `AgentScheduler.force_kill_task_agents/1` + `Task.shutdown(:brutal_kill)` + direct terminal write persisting **`:failed`** (finished_at set, lease nil, **result nil** — force-killed tasks have no result) + `clear_cancelling_marker(task_id)`. **Semantics**: `:cancelled` means ONLY gracefully-cancelled tasks (via the `:cancelling` → `:cancelled` final-mapping path in `handle_update_status/6`, result/archive preserved); a force-killed task is persisted as `:failed`, never `:cancelled`. RPC surface: `RemoteAPI.cancel_task/1` (graceful) + `RemoteAPI.force_kill_task/1`; `RemoteNode.cancel_task/2` + `RemoteNode.force_kill_task/2` (local-direct + `:erpc`).
- **AgentState field:** `cancel_requested :: boolean() | nil` (default nil) + `AgentScheduler.Store` helpers `set_cancel_requested/1,/2`, `cancel_requested?/1`, `clear_cancel_requested/1`. Visible via `RemoteAPI.get_agent_state/1` (full struct minus context).

## Update-Timing Safety (auto-update investigation — what exists, what's missing)

Facts for designing a "safe to restart/update" flow for the desktop backend (long-running agent tasks inside the BEAM):

- **No restart/update machinery exists in `:evo_git`.** Zero `System.restart` / `:init.restart` / `:init.stop` / `os:set_signal` usages in `apps/evo_git/lib` (rg-verified; only signal *exit-code descriptions* in `agent/tools/shell_tool.ex:276-340`). Graceful stop is done from `:evo_dash`: `EvoDashWeb.LiveHooks.DesktopQuit.default_stop/0` (`apps/evo_dash/lib/evo_dash_web/live_hooks/desktop_quit.ex:75-80`, tray-quit confirm flow) and SystemLive's local Stop — both `System.stop/0` (150ms-delayed spawn so the LiveView reply flushes). The Rust shell NEVER sends SIGTERM: headless mode (`desktop/src-tauri/src/main.rs:184`) and the watchdog force-kill use `child.kill()` = **SIGKILL** on Unix. SIGTERM/SIGINT to the BEAM would be handled by the ERTS default (graceful `init:stop`, apps stop in reverse order) — but no evo_git code installs custom signal handlers or checkpoints state on exit.
- **`bin/<release> stop`/`restart`** (Mix-generated launcher, verified against Elixir 1.20.3 `Mix.Tasks.Release.Init.cli_text`): `rpc "System.stop()"` / `rpc "System.restart()"` — spawns a hidden helper BEAM that connects via distribution (`--rpc-eval "$RELEASE_NODE"`). Requires `RELEASE_DISTRIBUTION != none` and a resolvable `RELEASE_NODE` (defaults to `$RELEASE_NAME`). **Under the desktop sidecar env (`RELEASE_DISTRIBUTION=none`, `main.rs:132`) `stop` cannot connect** — the desktop backend is started non-distributed and must be stopped from within (`System.stop/0`); `bin/genesis_desktop stop` only works for manually-started (distributed) instances.
- **Launcher does NOT pin the release version**: `RELEASE_VSN` is read from `releases/start_erl.data` (`cut -d' ' -f2`) at every invocation; `RELEASE_COOKIE` from `releases/COOKIE`. A new version can be staged as `releases/<new_vsn>/` alongside the old and switched atomically by rewriting `start_erl.data` (exactly what `mix release` does per build) — no launcher change needed. Desktop bundles the whole release dir as `resources/genesis-backend` inside the app.
- **Remote daemon update precedent — NO stop-first.** `RemoteConnection` bootstrap (`maybe_start_daemon`, `remote_connection.ex:917-926`): if `daemon_running?` → `:ok` (leaves the old daemon running the OLD code); else `start_daemon` + `verify_daemon_healthy`. `extract_tarball` (`:821-831`) overwrites release files at `remote_path` while the daemon runs from memory; the daemon only picks up new code after a manual restart. No version comparison anywhere (`RemoteBootstrap.download_url/1` always returns `"latest"`), no remote `stop_daemon`/`restart` command exists.
- **Graceful-cancel as the pre-restart mechanism**: `TaskRegistry.cancel_task/1` (`task_registry.ex:486-555`) → `:cancelling` status + `AgentScheduler.begin_graceful_cancel/1` (`agent_scheduler.ex:729-760`: `:evogit_cancelling_tasks` ETS marker + per-agent `pending_user_messages` + `AgentState.cancel_requested`) → Runner 3-turn grace (`@cancel_grace_turns 3`, `agent/runner.ex:24`; `maybe_recovery_auto_commit` commits ALL worktree changes at grace entry, `runner.ex:443-459`) → final status force-mapped to `:cancelled` WITH result/archive preserved (`task_registry.ex:846-849`). **Not wall-clock bounded**: each grace turn is a full LLM+tools cycle (LLM retry backoff up to ~9min, per-tool cap 30min, subagents unbounded) — an update flow must wait for the task to reach a terminal status before stopping the VM, with a generous timeout, or force-kill (`force_kill_task/1` → `:failed`, result nil'd).
- **Idle-detection API** (dashboard "safe to restart" check): `TaskRegistry.list_task_ids(statuses \\ [])` / `list_tasks_summary(statuses \\ [], since \\ nil)` / `list_tasks_changed_since/1` / `get_task/1` (task_registry.ex:166,153,187,56); RPC mirrors `AgentScheduler.RemoteAPI.list_task_ids/1, list_tasks_summary/1, list_tasks_changed_since/1` (remote_api.ex:336,323,359) + `EvoGit.RemoteNode` wrappers (remote_node.ex:381,358). In-flight set = `[:running, :pending, :finalizing, :cancelling]`. Task status lives ONLY in SQLite (`tasks.status`); scheduler ETS (`:evogit_sched_meta`, `:evogit_agent_state`, `:evogit_cancelling_tasks`, `:evogit_archive_records`) holds only live-agent state and dies with the app.
- **Lease/heartbeat**: `@lease_duration 120` s, heartbeat every 60 s renews `[:running, :pending, :cancelling]` (not `:finalizing`), `@sweep_after = 150_000` ms ONE-SHOT `:lease_sweep` scheduled in `TaskRegistry.init/1` (task_registry.ex:299-303, handler 1354-1414): marks orphaned `:running` rows `:failed` only when `not Lease.lease_valid?` AND no live sched_meta agents. **Gotcha**: the sweep never reschedules — a `:running` row whose lease is still valid at 150s post-boot (VM down < ~30s with a fresh heartbeat) is skipped and stays `:running` FOREVER (`periodic_cleanup` at 300s only deletes finished rows by age/count, cleanup.ex:32-55). `:pending` rows are in NEITHER `select_running_lease_info` (store.ex:682) NOR `select_finished_task_ids` (store.ex:634) — never reconciled on restart. Startup reconciliation (task_registry.ex:262-289): `:finalizing` → `:failed` ("Runtime restarted during task finalization"), `:cancelling` → `:cancelled` ("...during task cancellation"), both synchronous, result preserved; `:running` deliberately untouched (lease-sweep territory).
- **What survives a hard kill**: the SQLite row (WAL + `synchronous: :normal`, store.ex:428 — process-kill safe; power-loss can drop the latest un-fsynced commits but never corrupts; graceful `Store.terminate/2` at store.ex:447-463 checkpoints + closes), git branches (`evogit-agent-T<n>-A<m>`, `genesis/agent_*`), `.genesis/workers/` dirs (cleaned only lazily on the next first `create_worktree_for_agent` per repo: `rm_rf .genesis/workers` → prune → orphaned-branch delete, worktree_manager.ex:236-283). **Lost**: in-flight turn, `context.messages` (ETS snapshot only, no disk checkpoint), `LoopState`, slot pools, wrapper/task_refs/ProcessRegistry, `:evogit_cancelling_tasks` marker, `commit_sha` (persisted ONLY at terminal result or `set_review_metadata` — a killed task's row has no anchor SHA, so `ResumeContext`/`MergeContext` (task_executor.ex:28-63) fall back to caller `starting_commit`/HEAD).
- **No auto-resume**: `TaskRegistry.init/1` reconciles but never resumes; resume is always a NEW `:evolve` task via dashboard Review page (`resume_from` → `ResumeContext`; `review_status: :continued` is a persisted marker only, `set_review_status/2` task_registry.ex:130-132). Core never gates on `review_status` — the human review step is pure dashboard UX. Auto-resume after an update would need new machinery.
- **Adding a distinct status (e.g. `:interrupted`) requires**: codec `@known_atoms` (store/codec.ex:217-221 — unknown status decodes to nil, and `decode_task` falls back to `:pending`, codec.ex:153), TaskInfo typespec (task_info.ex:30-31), and the hardcoded status lists: store.ex:634 (`NOT IN ('running','pending','cancelling')` — new status would be deleted by `clear_finished_tasks`), store.ex:682 (`IN ('running','finalizing','cancelling')`), task_registry.ex:317-319, 846-849, 851-861, 870-878, 1114, 1130-1138, 1324, 1364. Schema itself has NO CHECK/FK/ON CONFLICT constraints (schema.ex:36-56) — any string is accepted by the write path.

## Cross-Node RPC Payload Profile (SSH remote UX optimization — investigation findings)

Payload/severity analysis of the remote dashboard's RPC surface (`EvoGit.RemoteNode` → `EvoGit.AgentScheduler.RemoteAPI` via `:erpc.call/5`; local node = direct call). Transfer is **uncompressed native BEAM terms** (no distribution compression configured in `EvoGit.Distribution`); no JSON boundary. `:remote_rpc_timeout` default 30s read at call time (remote_node.ex:18,69-72). Every wrapper: local → direct call (errors surface truthfully), remote → `:erpc.call/5` normalized to `{:ok, _} | {:error, {kind, reason}}`; failure fallbacks (`[]`/`%{}`/`nil`/`false`) per function. Severity: 🔴 heavy payload / 🟠 moderate / 🟢 cheap.

**Agent-state reads (ETS-backed, `:evogit_agent_state` + `:evogit_sched_meta` — cheap server-side, `:ets.tab2list`/`:ets.lookup`):**
- `get_agent_history/1` 🔴 — returns the FULL `context.messages` list (`%ReqLLM.Message{}` structs: content parts, tool_calls with args, reasoning_details incl. signatures, metadata). No trimming. Worst case pre-compression ≈ `llm.compression_threshold_tokens` (default **100_000** tokens, config.ex:32) ≈ 400 KB–1 MB text per agent; tool outputs per-call capped (truncation config: 128 KB global ceiling / 16 KB default for high-output tools, output_sanitizer.ex:110-121). Compressed contexts are small (`[system, initial_user, summary]`).
- `get_agent_state/1` 🟢 — native `%AgentState{}` **with `:context` dropped** (remote_api.ex:108-113); carries foreign_repos, pending_user_messages, usage, phylo_node, context_node → ~1-2 KB. **Dead in the dashboard** (zero web-layer callers — NodeContext passthrough only).
- `list_agents/0` 🟠 — per-agent summary map (~21 keys: id, task_local_id, repo_id, status, depth, parent_id, **usage `%Usage{}`**, total_tokens, compression_count, **message_count** (integer — `context.messages` length, 0 when context is nil/absent; lets the dashboard detect LLM-history changes without re-transferring `get_agent_history/1`), **objective** (can be large — attached-file content is appended into objectives), agent_module, model_id, repo_root, context_path, worktree, current_commit, base_commit, task_id, task_number, retries). ~0.5-5 KB/agent typical; **objective dominates** when file content was attached. Dashboard (AgentsLive) consumes ~21 keys but re-fetches **every `{:agents_updated}` broadcast + every 3s remote poll tick** — the highest-frequency transfer in the system.

**Task reads (SQLite via TaskRegistry — server-side offloads heavy decodes to short-lived Tasks, task_registry.ex:285-310; status/updated_at filters are index-backed):**
- `list_tasks/0` 🔴 — FULL `%TaskInfo{}` decode: logs (capped @max_log_entries 500), result (embeds usage + archive_records), opts (objective + foreign_repos), archive_metadata. **No dashboard caller** (NodeContext passthrough only) — not a tunnel cost today.
- `get_task/1` 🔴/🟠 — full row incl. result blob. ReviewLive consumes all but `logs`; once per page load + per debounced broadcast burst.
- `list_tasks_paginated/1` 🔴 — 25 full TaskInfo rows/page; heavy fields (result/logs/usage/archive_metadata) transferred even when every card is collapsed; no lazy detail RPC exists. Per dirty change only.
- `list_tasks_summary/1` 🟢 — 15-key projection, **no `result`** (store.ex:78 `@summary_columns`); sidebar-only, broadcast-debounced (no polling).
- `list_tasks_changed_since/1` 🟢 but **worst transferred-vs-consumed gap** — full 15-key projection per row every 3s remote poll tick; DirtyTracker consumes ONLY `:updated_at` (14/15 keys unused). A `(id, updated_at)` projection is the natural optimization.
- `list_task_ids/1` 🟢 — 3-key projection; dashboard reads only `updated_at`.

**Config reads:**
- `get_config/0` 🟢 — scheduler state map (~17 keys); model_profiles carry NO api keys (credentials live in credentials.toml/ReqLLM key store) → ~1-3 KB. Consumed by SystemLive chart (~30s cadence) and AgentsLive threshold lookup (reads `[:llm, :compression_threshold_tokens]` which is **absent from the scheduler config** → remote nodes always fall back to 100_000 — known correctness gap).
- `get_config_status/0` 🟢 — small status map (missing/warnings/ok?/validation_errors).
- `reload_config/0`, `save_user_config/1`, `save_credentials/1` 🟢 — tiny returns; heavy work (disk write) runs remotely.

**Review/git functions (via RemoteAPI → `EvoGit.Review` — run git CLI processes ON the remote node, server-side cost is per-git-spawn; return values pass through verbatim):**
- `load_review_data/2` 🔴 — `git diff` full-branch diff string can be MBs; **never called by the dashboard (dead path)**; `load_review_metadata` is the live variant.
- `load_review_metadata/2` 🟠 — 4 git commands (rev_parse, merge-base, diff_numstat, diff_shortstat); payload = file list with counts (~small). Dashboard doesn't consume top-level `commit_sha`/`diff_stat`.
- `list_commits/2` 🟢 — 3 git commands; CommitInfo list (author_email unused by dashboard).
- `load_file_diff/4,5` 🟠 — 1 git command per file; payload = file diff (KB–MB with `-U999999` full-file context); dashboard loads **lazily per file click**.
- `load_commit_files/2` 🟢 / `load_commit_file_diff/3` 🟠 — per-commit variants; metadata-only / single-file diff.
- `get_file_content/3` 🟠 — `git show <sha>:<path>` — full file content (can be MBs); used for whole-file highlighting on demand.
- `check_merge/3` 🟢 — in-memory `git merge-tree` (non-mutating); returns `:clean | {:conflict, files}`.
- `merge_branch/2,3`, `reject_branch/2`, `branch_exists?/2`, `default_merge_target/1`, `list_branches/1` 🟢 — small returns; git work happens remotely.
- `create_github_pr/4`, `github_upstream/1`, `list_github_issues/2`, `github_issue_markdown/2` 🟠 — gh CLI + network on the remote; payloads small-medium.

**Custom-agents & system functions:** `list_custom_agents/0` 🟢 (~KB, file read of agents.toml); `save/delete/save_model_selection_script/reload_custom_agents` 🟢; `start_task/2` 🟢 (`{:ok, %TaskInfo{}}` — dashboard reads only the id); `file_exists?/1`, `ls/1`, `dir?/2`, `read_project_config/1`, `list_path_suggestions/1` 🟢 (path-list); `llm_test/2` 🟠 (runs a real LLM call remotely; returns model + response text).

**Top payload-reduction opportunities (cross-checked against apps/evo_dash consumption):**
1. `list_tasks_changed_since` — add a `(id, updated_at)`-only projection (biggest gap: 14/15 keys unused every 3s).
2. `get_agent_history` — re-transferred in full every 3s tick + every broadcast for the selected agent; dashboard renders only text content parts, tool_calls name/args, metadata.turn/timestamp, reasoning_details (full `metadata` map is dead wire weight). Trim server-side or fetch-on-change.

### Distribution & Release Setup (relevant to remote/SSH features)
- **EPMD-less distribution via custom module.** All `rel/vm.args.eex` files use `-epmd_module Elixir.EvoGit.EpmdDist` with `-start_epmd false`. The `EvoGit.EpmdDist` module implements the `erl_epmd` interface using `:persistent_term` as a node→port registry. No external `epmd` process is needed. Distribution is NOT started at boot for the local dashboard — it is enabled on-demand by `EvoGit.Distribution.enable_for_remote/1` when a user initiates a remote connection. The remote daemon starts distributed at boot (port 9000).

### SSH Remote Bootstrap Failure Modes (safeguards)

**Remote ssh commands are argv arrays, never quote-wrapped spawn strings; the command is additionally bash-wrapped for login-shell independence:** all remote ssh commands go through `EvoGit.RemoteConnection.run_ssh_command/3`, which runs the `ssh` executable via `Port.open({:spawn_executable, ...})` with the remote command as ONE argv element — never `{:spawn, String}` with a quote-wrapped remote command. This was the root cause of Windows bootstrap failing at the `:extracting` stage: the Windows CRT argv parser only consumes DOUBLE quotes, so single quotes travel to ssh.exe, reach the remote host, and remote bash parses the whole quoted string as ONE command name ("No such file or directory"). The naive double-quote swap is also wrong on Unix, where `{:spawn, String}` goes through `/bin/sh -c` and double quotes would trigger LOCAL `$`-expansion. OpenSSH joins its argv entries with single spaces and the remote shell re-parses them. Because OpenSSH executes the command via the REMOTE user's login shell (`$SHELL -c "<command>"`), `run_ssh_command/3` wraps the command as `/usr/bin/env bash -c '<escaped>'` using the pure builder `EvoGit.RemoteBootstrap.bash_wrap/1` (single quotes escaped as `'\''` — close-quote/escaped-quote/reopen-quote, parses correctly under fish/zsh/any POSIX-ish shell), so every remote command — including the NixOS patch script with its `$`, `$(...)` and single quotes — executes under bash regardless of the remote login shell (fixes bootstrap failing at PARSE time on NixOS hosts whose login shell is fish).

**Daemon launch against stale failed units:** `start_daemon/3` (Linux clause, `remote_connection.ex`) runs `systemctl --user reset-failed genesis-remote 2>/dev/null; true` BEFORE the `systemd-run` launch command. This clears stale failed/inactive units idempotently (exits 0 if nothing to reset, non-zero if unit never existed — both acceptable). The reset result is ignored (best-effort), so bootstrap proceeds regardless.

**Launch health-check:** `maybe_start_daemon/3` calls `verify_daemon_healthy/2` after `start_daemon/3` returns `:ok`. This retries `daemon_running?/2` up to 3 times with 1s sleep between (total ~3s wait for BEAM VM boot). If the daemon never reaches `active`, returns `{:error, {:daemon_not_healthy, details}}` where details includes `systemctl --user status genesis-remote 2>&1 | tail -20` output on Linux. Additionally, bootstrap has a `:copying_config` stage (`do_bootstrap_with_tarball/3`) that SCPs the local `config.toml` and `credentials.toml` (via `EvoGit.Config.config_path/0` / `credentials_path/0`) to the remote `~/.config/genesis/` directory — best-effort, missing files skipped, copy errors logged but don't fail bootstrap.

**EPMD module set at runtime:** `Distribution.enable_for_connection/1` sets `Application.put_env(:kernel, :epmd_module, Elixir.EvoGit.EpmdDist)` BEFORE `:net_kernel.start/1`. This ensures the VM uses the EPMD-less module even when distribution is started on-demand in dev mode (no release vm.args). Combined with `-epmd_module` in `rel/vm.args.eex`, `port_please/2` resolves the SSH tunnel port.

- **Phoenix.PubSub uses the bare `{Phoenix.PubSub, name: EvoGit.PubSub}`** (see `EvoGit.Application.start/2`, line 21) with NO adapter options → defaults to the PG2 adapter. EvoDash has its own separate `EvoDash.PubSub`. **PubSub does NOT work across nodes** without distribution + a distributed adapter; out of the box everything is single-node/local.
- **`Node.set_cookie`/`Node.connect` appear in `EvoGit.RemoteConnection`** (the SSH connection GenServer) and `EvoGit.Distribution` (`enable_for_remote/1`). These are exercised only at runtime when a user explicitly initiates a remote connection via `EvoGit.RemoteConnection.connect/1`; out of the box (no remote connection active), the local node remains `:nonode@nohost` and undistributed. When `connect/1` is called and the node is `:nonode@nohost`, it auto-enables distribution via `Distribution.enable_for_remote/1` (starts `:net_kernel` with `genesis@127.0.0.1`, longnames, cookie from config — auto-generated on first bootstrap).
- **Remote connection supervision**: `EvoGit.Application.start/2` starts `EvoGit.RemoteConnection.Registry` (unique-keyed Registry, keyed by target id) and `EvoGit.RemoteConnection.Supervisor` (DynamicSupervisor) **before** `EvoGit.AgentGroupSupervisor`. Connection manager GenServers are NOT started at boot — they are spawned on demand via `RemoteConnection.connect/1` or `bootstrap/1` (find-or-start against the Registry/DynamicSupervisor). The `:ssh` Erlang application is **not** in `extra_applications` — all SSH operations use CLI `ssh`/`scp` via `Port.open`.
- **Task persistence supervision**: `EvoGit.Application.start/2` also starts `EvoGit.Store` (SQLite GenServer, `data_dir: <data_dir>/tasks.sqlite`) and `EvoGit.TaskRegistry` (task lifecycle GenServer) alongside a unique `Registry` named `EvoGit.TaskRegistry.ProcessRegistry` (with explicit `id: :task_registry_process_registry` to avoid collision with the existing `EvoGit.RemoteConnection.Registry` child whose default id is `Registry`). Note: `Task.Supervisor, name: EvoGit.TaskSupervisor` is NOT started at the top level — it is owned by `EvoGit.AgentGroupSupervisor` (a `one_for_all` supervisor that links TaskSupervisor + AgentScheduler). `EvoGit.TaskRegistry` references `EvoGit.TaskSupervisor` by name at runtime.
- Release definitions live in the **umbrella root** `mix.exs` (`releases: [genesis:, genesis_desktop:]`), not under `apps/evo_git/rel/`. There are **no `apps/evo_git/rel/` overlays** — all `rel/` overlays are at the repo root (`rel/`).
- **Endpoint bind config** is resolved in `config/runtime.exs` (prod only): `PORT`/`PHX_IP` env vars take priority, else `config.toml` `[server] listen_port`/`listen_ip` (schema-defined in `EvoGit.Config.Schema.Definitions`, default port 9999). Desktop mode binds loopback by default; non-desktop prod binds `{0,0,0,0,0,0,0,0}` (all interfaces). **Desktop mode robustness**: the `genesis_desktop` release bakes a compile-time `:desktop_release` flag into `sys.config` (mix.exs). `runtime.exs` uses this flag as a fallback for `PORT` (→ 9999), `SECRET_KEY_BASE` (→ hardcoded local key), and `PHX_SERVER` (→ `server: true`) so the backend boots correctly even if the Tauri sidecar's env vars are not present.
- Agents are transient modules using `EvoGit.Agent` behaviour; the framework manages state via ETS.
- Agent execution happens in **isolated git worktrees** managed by `AgentScheduler.WorktreeManager` (monitor-driven reclaim) — never on the main working copy.
- Subdirectories follow Elixir convention: `./lib/evo_git/<subdir>/` maps to `EvoGit.<Subdir>` namespace.
- **Three-level configuration**: `EvoGit.Config` merges built-in defaults → user config (`~/.config/genesis/config.toml`) → runtime overrides. No default model or username is hardcoded.

### Config Caching Behavior (important for remote/SSH scenarios)

**`EvoGit.Config.resolve/0` uses an mtime+size-validated `:persistent_term` cache.** The parsed TOML maps of `user_config/0` and `credentials/0` are cached per file path; every call does a cheap `File.stat` and only re-reads + TOML-decodes when mtime/size changed (external edits and `RemoteAPI.reload_config/0` are picked up on the next call). `save_user_config/1`/`save_credentials/1` explicitly invalidate after writing. The resolve merge pipeline (merge → atomize → migrate → validate) still runs per call because it populates the process-dictionary validation errors read by `config_status/0`. Details: `config/CONTEXT.md` → Config Caching.

**The actual cache is the AgentScheduler GenServer state.** `AgentScheduler.init/1` calls `Config.resolve()` once at startup and stores the result in `%State{}`. `AgentScheduler.get_config/0` (and therefore `RemoteAPI.get_config/0`) returns values from this in-memory state — NOT from disk. This means:

| Path | Reads disk? |
|------|------------|
| `RemoteAPI.get_config/0` → `AgentScheduler.get_config/0` | ❌ No — returns cached GenServer state |
| `RemoteAPI.reload_config/0` → `Config.resolve()` → `AgentScheduler.update_config/1` | ✅ Yes — stat-validated; refreshes GenServer state whenever the file changed |
| `RemoteAPI.get_config_status/0` → `Config.config_status/0` → `Config.resolve()` | ✅ Yes — stat-validated (fresh when the file changed); validation errors from the per-call pipeline |

**`save_user_config/1` does NOT auto-reload.** Writing to disk only persists the file; the caller must separately invoke `reload_config/0` to push changes into the running scheduler. The dashboard's `SettingsLive` does call `reload_remote_config/1` after saving remotely (settings_live.ex:612), but **the return value is not checked** — if the `:erpc.call/5` fails (timeout, node down), the scheduler silently retains its stale config while the user sees "Configuration saved successfully."

**`RemoteConnections` does NOT auto-create an empty `remote_connections.toml`.** `list/0` returns `[]` when the file doesn't exist. The file is only created on first `save/1` via `File.mkdir_p`. No empty file is bootstrapped at startup.
- **Slot discipline**: All LLM calls must acquire/release slots via `AgentScheduler`. **Multi-model support**: the runtime supports multiple LLM models simultaneously, each with its own independent concurrency slots, generation params, and per-model 60-second backoff (a rate-limit on one model does NOT block agents using other models). Config via `[[llm.models]]` TOML array-of-tables (each profile: `id`, `model`, `concurrency`, generation params). Old flat `[llm]` config auto-migrates to a single-profile list with id `"default"` **at load time only** (`Config.resolve/0` → `migrate_llm_models/1`). On **save** (`Config.save_user_config/1`), flat gen-param fields are stripped from the written TOML when `llm.models` is non-empty — only `[[llm.models]]` + `compression_threshold_tokens` are written. `stringify_keys` recurses into lists so atom-keyed profile maps serialize correctly. `AgentSpec.model_id` binds an agent to a profile; child agents inherit the parent's `model_id` by default. Tool executions are independently throttled via `max_tool_concurrency`.
- **Task-scoped naming**: Worktree directories use `worker_T<task_number>_A<task_local_id>`, branches use `evogit-agent-T<task_number>-A<task_local_id>`. The `task_id` is a 16-char hex GUID used for global identification (archive refs, task grouping); the `task_number` is a short integer (from a linear scan of `.genesis/workers/`) used only for naming.
- **Test isolation guard:** `config/test.exs:29` sets `config :evo_git, :data_dir, Path.join(System.tmp_dir!(), "evogit_test_data/genesis")` — the canonical guard ensuring tests NEVER touch the production DB (`~/.local/share/genesis/tasks.sqlite`). `EvoGit.Store` reads `Application.get_env(:evo_git, :data_dir)` at startup, so the guard is enforced app-wide; Store/TaskRegistry tests additionally isolate to per-test temp dirs.
- **`trim_recent_projects/1` nil-safe sorting:** `add_recent_project/2` → `trim_recent_projects/1` uses `sort_projects_by_recency/1` (task_registry.ex:683-691), a nil-safe comparator that sorts nil `last_opened_at` LAST (the `DateTime` sorter would raise via `DateTime.compare/2` on nil elements), so rows with `last_opened_at = nil` (legacy data, decode-to-nil) cannot crash the TaskRegistry GenServer. Covered by task_registry/persistence_test.exs (nil-last + overflow trim).
- `EvoGit.Defaults` is a backward-compatibility shim. New code should use `EvoGit.Config` directly.
- **Startup reconciliation of orphaned `:finalizing` tasks:** `TaskRegistry.init/1` (`task_registry.ex:159-220`) performs startup reconciliation: it queries `EvoGit.Store.select_running_lease_info/1` (lightweight id+status+lease_expires_at, SQL-filtered to running/finalizing rows), filters `status == :finalizing`, and synchronously marks each `:failed` via the shared `handle_update_status/6` (`task_registry.ex:506`) with result `"Runtime restarted during task finalization"` and `caller_info = {:startup_reconcile, :finalizing}` (sets `finished_at`, clears the lease, broadcasts `{:task_updated, task_id, status, node()}`). An orphaned finalizing task — its wrapper died with the previous VM, so the in-process `{ref, result}` / `:DOWN` handlers keyed off the now-empty `task_refs` map can never fire — would otherwise stay stuck forever. `:running` rows are deliberately NOT touched at init: the one-shot `:lease_sweep` (`@sweep_after` 150s) handles orphaned `:running` owners, respecting lease validity for the legitimate multi-VM case. `:pending` rows are untouched. The `{:recheck_task, task_id}` handler is unused (nothing schedules the first recheck). Trigger: slow disk (NFS) makes `merge_and_report/3`'s two `System.cmd("git", ...)` calls (`Git.rev_parse`, `Git.create_branch` — both `:infinity` timeout, `runtime/helpers.ex:16,24`) hang while the task sits at `:finalizing`; if the app dies in that window (or the wrapper is killed), the terminal write never happens and the row stays `status='finalizing', finished_at=NULL` forever. Timeouts are deliberately long. See `apps/evo_git/lib/evo_git/task_registry/CONTEXT.md` (Restart Recovery & Status Transitions) and `apps/evo_git/lib/evo_git/runtime/CONTEXT.md` (finalizing window). Covered by `apps/evo_git/test/evo_git/task_registry/persistence_test.exs` (describe "startup reconciliation of orphaned :finalizing tasks" — also asserts a `:running` row is untouched at init).

### Sandbox & Test Suite Interaction (how the systemd-run sandbox relates to tests)
The sandbox mode is resolved via **`EvoGit.Config.resolve([:sandbox, :mode])`**, which merges schema defaults (`:auto`) → user TOML (`~/.config/genesis/config.toml`) → runtime overrides. **It does NOT read application env.** Despite this, `config/config.exs:57-58` sets `config :evo_git, sandbox: :auto` — this is **unused**: no lib module ever calls `Application.get_env(:evo_git, :sandbox)`. Consequently:
- **`Application.put_env(:evo_git, :sandbox, :disabled)` in tests is a NO-OP.** The sandbox mode is resolved via `EvoGit.Config.resolve([:sandbox, :mode])` which reads TOML config + schema defaults — NOT application env. Tests rely on the `@mix_env == :test` gate in `Linux.enabled?/0` to bypass systemd-run in test env.

**Test env sandbox mode resolution:** Test setup (`evo_git_test.exs:7-13`, `test_helper.exs`) redirects `XDG_CONFIG_HOME` to a temp dir with no `config.toml`, so `Config.resolve([:sandbox, :mode])` returns the schema default **`:auto`** (`definitions.exs:256`).

**`Linux.enabled?/0` has a test-env gate — consistent with SandboxSlice/Registry (and the bwrap backend).** All Linux sandbox modules use the same `@mix_env Mix.env()` compile-time gate:
- `EvoGit.Sandbox.Linux.enabled?/0` (`sandbox/linux.ex`) checks `@mix_env == :test -> false` as its first cond branch. In test env, the Linux backend falls through to its disabled path (wraps commands in `bash -c` with stdin redirect — identical to the `None` backend behavior).
- `EvoGit.Sandbox.Bwrap.enabled?/0` (`sandbox/bwrap.ex`) — same test gate; in non-test env resolves `[:sandbox, :mode]` with `:auto` → `EvoGit.Platform.bwrap_available?()`. `ensure_initialized/0` is a no-op (no slice, no unit registry).

### ⚠️ Task persistence runs in :evo_git
Task persistence (`EvoGit.Store` / `EvoGit.TaskRegistry`) lives in **`:evo_git`** and is started by `EvoGit.Application`'s supervision tree. This means the core runtime owns its own task lifecycle + persistence — the headless `genesis_remote` release (evo_git-only) has full task history capability without any dashboard dependency. `EvoGit.TaskRegistry` runs `reconcile_task_status` against the shared platform SQLite DB (`<data_dir>/genesis/tasks.sqlite`). If that DB already has in-progress `:running` tasks from another instance whose `:evogit_sched_meta` ETS is in a *different* BEAM VM, the freshly-started Registry marks them `:failed` (mitigated by the lease & heartbeat pattern).
- **Task Archive (opt-in)**: When `:archive` is enabled (`--archive` CLI flag → `runtime_opts` → `AgentSpec.opts` → `AgentState.archive`), each agent's completion (`CompleteTask.complete/4`) writes `refs/genesis/archive/T{task_id}-A{agent_id}-start` and `-final` git refs (protecting commits from gc), adds per-agent `usage` to the git note metadata, and writes an archive record to the `:evogit_archive_records` ETS table (a `:set` keyed by `{task_id, agent_id}` — see the per-task collection bullet below). The archive record is a plain map with: core fields (`agent_id`, `parent_id`, `depth`, `objective`, `result`, `base_commit`, `final_commit`, `archive_ref_start`/`final`, `branch_name`, `usage`, `compression_count`, `repo_path`, `repo_id`, `repo_root`, `started_at`, `completed_at`); `:llm_settings` (model name, `model_id` profile identifier, `context_compression_threshold`, and all generation params like `temperature`, `reasoning_effort`, `max_tokens`); `:agent_settings` (`max_turns`, `max_retries`, `max_agent_depth`); and `:foreign_repos` (list of `%{id, root, description}` maps for all configured foreign repos). At root-agent completion, the scheduler collects all records for the task, injects them into the `Result.archive_records` field, and clears the per-task collection (consumed). The result flows through `merge_and_report/3` to the final result map. When archive is disabled (default), no archive records are written.

- **No `try/rescue` anti-pattern**: `try/rescue` is normally a code smell in Elixir — it usually indicates we lack a clean process structure or supervision tree, and are manually handling process lifetimes or masking bugs. **Do NOT add new `try/rescue` blocks.** Before reaching for one, ask: (1) Do we really expect that error? If not → **let it crash**; the supervision tree / restart logic handles recovery (crashing is better than a silent error or corrupted value). (2) If we DO need to handle it, can we do it cleanly? Prefer `case`/`if`/`cond`/`with` with non-crashing function variants (`Regex.compile` not `Regex.compile!`, `JSON.encode/2` not `Jason.encode!/2` + rescue, `:persistent_term.get/2` not `get/1` + rescue, `Integer.parse/1` not `String.to_integer/1` + rescue). Only use `try/rescue` in the rare justified cases listed below. **Every `try/rescue` that remains in the codebase MUST have a comment explaining why it is justified** (answer both questions above).
  - **Justified `try/rescue` cases (rare):** `terminate/2` or cleanup/shutdown code that must never crash the caller; centralized exception boundaries (e.g. `safe_llm_call/2` in the evolution engine, the single rescue for all evolution LLM calls); `SystemCheck` public diagnostics functions that must never crash the dashboard LiveView; `String.to_existing_atom/1` on untrusted user config keys where there is no non-crashing variant; `try/catch` around functions with no non-crashing variant (e.g. `Path.wildcard`). See `EvoGit.Store` for a good "crash philosophy" reference doc.
  - **Eliminate immediately:** `try/rescue` around `!`-suffixed functions that have non-crashing variants; silent `rescue _ -> :ok` swallows; LLM-call rescues that degrade silently to defaults (either add retry logic or let it crash); broad rescues that hide bugs; redundant internal-helper rescues when the public entry point already rescues.
