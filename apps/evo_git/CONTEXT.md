# EvoGit — Core Runtime Application

## Intent
The `:evo_git` OTP application is an evolutionary software-development runtime: LLM agents create, analyze and modify codebases in isolated git worktrees, modeling a codebase as a **Context Tree** (spatial) and a **Phylogenetic Graph** (temporal) evolved through a DAG of commits.
Phases: **Genesis**, **Evolution**, and a repo-less **self-reflective** agent (`:reflect`), all on an LLM/tool slot-gated scheduler.
Task persistence (`EvoGit.Store`/`EvoGit.TaskRegistry`) lives here so the headless `genesis_server` daemon has full task history — detail: `lib/evo_git/CONTEXT.md`.

## Routing Table
Each row points at the child CONTEXT.md owning the detail (`./lib/evo_git/<subdir>/CONTEXT.md` unless stated).
- `./lib/` → application source; `./test/` → ExUnit suite (real git ops on temp dirs)
- `agent/` → Runner, tools, `ConflictState`/`TurnWarning`, effective selection propagation, configured-window compression and cost recomputed from effective `llm_model` plus the selected provider account's pricing period; `agent/compression/` → pruning/checkpoints and `Threshold` (effective configured `llm_context_window`, default 200_000, never catalog context limits; `[:llm, :compression_threshold_tokens]` override); `agent/tools/` → Assistant-only `elixir_eval`, `web_fetch` and config-gated `lsp`.
- `agents/` → Manager, Executor, TaskScheduler, Investigator, Architect, ContextExtractor, SkillExtractor, GenesisPlanner, Custom, SelfReflective
- **Agent lifecycle is ONE `EvoGit.Agent.Session` per agent, two drivers**: every agent — one-shot or interactive — is ONE supervised `EvoGit.Agent.Session` (`gen_statem`, `:handle_event_function`, `:temporary` under `Agent.Session.Supervisor`, registered by `agent_id` in `Agent.Session.Registry`) owning the single `%EvoGit.Agent.State{}`; the loop is a library (`EvoGit.Agent.Exchange.run/2` + `Agent.Turn`, with `Exchange.Seams`/`Grace`/`Pending`/`Warnings`) run in ONE short-lived `Agent.Session.Worker` Task per exchange that checkpoints `%State{}` back after every turn, so inspect/input/cancel/close stay answerable mid-run — including during `:starting`, where the durable worktree request runs in a supervised `Task.Supervisor.async_nolink` task (seams `:worktree_create_slow_warn_ms` 120 s and `:worktree_create_stall_timeout_ms` 30 min turn a hang into a terminal `{:error, {:worktree_create_failed | :worktree_create_stalled, _}}` instead of an unanswerable session); `AgentScheduler.run_agent/2` keeps its blocking `{:ok, %Result{}}` contract for one-shot agents, while `{:yield}` parks an interactive root in the non-terminal `:awaiting_input` status (explicit close, no idle TTL). Contracts: `agent/session/CONTEXT.md`.
- `lib/evo_git/agent/clock.ex` → `EvoGit.Agent.Clock`: the agent layer's ONE clock read (`now_seconds/0`, Unix seconds) for per-message `metadata[:timestamp]`, plus a default-inert PROCESS-DICTIONARY pin (`with_now/2`, `with_opts/2`) that `Exchange.run/2` and `Turn.run/3` accept as `now:` — so a test can make message timestamps deterministic without any app-env global, and an absent pin is byte-identical to reading the system clock.
- Mid-run input flows through the session's mailbox, not ETS: `EvoGit.AgentScheduler.ControlPlane` owns the atomic `:evogit_agent_inbox` (`{agent_id, {seq, message}}` bag) and `:evogit_agent_control` (cancel flag + compression count) tables the five `AgentScheduler.Store` helpers delegate to — appends and drains take `{seq, message}` items, never a whole-struct read-modify-write — and an append needs a LIVE session (`{:error, :not_found}` once it ends); a follow-up after completion is always a NEW task (resume/merge contexts re-enqueue, they never revive a pid). A conversation that must persist across messages is an interactive session (`send_session_message/3`), which `/assistant` now uses (one session per conversation); the one-shot repo-less `:reflect` task remains the fallback, replaying earlier chat only as a bounded text preamble.
- Assistant evaluation contract → `lib/evo_git/agent/tools/elixir_eval/CONTEXT.md`: one `elixir_eval` tool with read/write/sudo tiers, Dune-interpreted read/write capabilities and explicitly approved unrestricted native sudo; wrapper approval and dispatch integration live in the parent tools node.
- Trusted configuration-script evaluation precedent → `custom_agents/CONTEXT.md`: `ModelSelector` evaluates administrator code inline without process isolation/timeouts and is not an agent-code execution boundary.
- `agent_scheduler/` → `ModelSelection`, effective `AgentState` identity, locked child inheritance, account-shared `Slots` capacity/backoff, `SchedMeta`, worktrees, `RemoteAPI`, repo-less plumbing and cancellation.
- `core/` + `adapters/` → `ContextNode`, `PhyloGraphNode`, `ForeignRepo`; `Git`, `GitHub`, `CowWorktree`, `GitEnv`
- `runtime/` → Genesis (incl. Mode B), Evolution (simple + custom), SelfReflective, SkillExtraction, PullRequest; there is NO `EvoGit.Runtime.Prompts` and no `Runtime.Phase` module (prompt text lives in each agent's `system_prompt/0` and in `genesis.ex`'s inline Mode-B objective)

- `lib/evo_git/process_manager.ex` + `lib/evo_git/process_manager/` → `EvoGit.ProcessManager`: THE single source of truth for every execution an agent/task holds (one `Execution` + normalized `Handle` per tool call — builtin or OS-backed — and per background job), 3s stats sampling (CPU/memory/RSS/pids), owner-pid lifetime, bounded finished retention, and pause/resume/signal/kill over `systemctl --user`, `/proc`+`ps` (process-group aggregated) and `tasklist`/`taskkill`; `runtime` is the call ORIGIN (`:foreground` = the agent is blocked on it, `:background` = an `EvoGit.BackgroundJobs` job), `backend` is what runs it (`:builtin` = inside the BEAM with no OS process, `:systemd \| :bwrap \| :sandbox_exec \| :none` = an external OS process), `Execution.builtin?/1`/`external?/1`/`sampleable?/1` drive sampling and control, and a builtin record answers `{:error, :no_os_process}` to sample/signal/pause/resume/kill.
- Terminal facts are ONE vocabulary: `exit_code` (integer only for an external process that actually exited) plus `reason` (`:exited`, `:timeout`, `:invalid_arguments`, `:owner_died`, `{:killed_by, actor}`, `{:crashed, detail}`, `:no_os_process`), mapped to `:completed` (clean exit, including a non-zero code, and a finished builtin) / `:failed` (`:invalid_arguments`, `{:crashed, _}`, `:owner_died`) / `:killed` (`:timeout`, `{:killed_by, _}`) by `Execution.status_for_reason/1`; an operator kill is authoritative over the exit it causes (pending kill intent), and a later terminal finish on an already-terminal record is always a no-op.

- `store/` → `EvoGit.Store` over pure `Store.Operations.*`, `Store.Codec`, `Store.Boot`, `Store.Writer`, `Store.Maintenance`, `RepoScope`, schemas, types
- `task_registry/` → `Cleanup`, `Diagnostics`, `Lease`, `MergeContext`, `ResumeContext`, `RuntimeOpts`, `TaskExecutor`, cancel/kill, restart recovery
- `lib/mix/tasks/` → `Changelog`, `Bump.Version`, `Migrate.Store`, `Store.Maintenance`, `Bench.Io` — detail: `lib/mix/tasks/CONTEXT.md` + root `./CONTEXT.md`
- `lib/evo_git/bench/` → standalone I/O benchmark (`EvoGit.Bench` + `Stats`/`Report`/`SystemInfo`) driven by `mix bench.io`; measures worktree add/remove, file read/write and git status/add/commit over a throw-away synthetic repo with NO app boot — detail: `lib/evo_git/bench/CONTEXT.md`
- `lib/evo_git/vct.ex` + `lib/evo_git/vct/` → the internal-only Virtual Context Tree namespace: canonical `vct:///projects/<name>` project mount points persisted in the store's `vct_mounts` table, a capped project list (`max_projects/0`, 100), RESERVED system mounts outside that namespace (declared by hosts at boot through the `:system_mounts` init option and ensured with `ensure_mount/3`), and an optional lazily-git-managed global context at `<data_dir>/vct/CONTEXT.md` — detail: `lib/evo_git/vct/CONTEXT.md`
- Storage model: every JSON column (`opts`/`logs`/`result`/`usage`/`error`) is plain UTF-8 JSON TEXT — no compression layer, readable to plain SQL (`store/codec.ex`)
- **The Virtual Context Tree (VCT) is a pure INTERNAL namespace over OS paths, NOT a filesystem**: a mount binds a canonical `vct:///…` point (project or reserved) to an absolute OS path as METADATA only — no symlink farm, bind mount, FUSE mount or junction, no directory is ever created for a point, and a mount's OS path is never required to exist.
- Task/agent execution is UNCHANGED by the VCT: an agent still runs in ONE concrete repo worktree, in-repo references stay relative (`./src/auth`) and foreign-repo references stay absolute OS paths; a `vct:///` URL is internal metadata and is NEVER rendered as a CONTEXT.md file path (or any other prompt path) — `EvoGit.Core.ContextNode.build_context/2` labels the global context `global/CONTEXT.md` and every in-repo stage `./…/CONTEXT.md`.
- The VCT owns the project list: `projects/1` (and `search/2`) return PROJECT mounts ONLY as `[%EvoGit.VCT.Mount{}]` newest first (`last_opened_at` DESC with `nil` LAST, then `point` ASC), and an optional `:limit` is a DISPLAY cap only — the table caps PROJECT mounts at `max_projects/0` (100, app env `:vct_max_projects`), evicting the OLDEST, while reserved mounts never appear here and never auto-activate as the active project.
- A point is a PROJECT mount exactly when it is `vct:///projects/<name>[...]` (`Table.project_mount?/1`); every other point — `vct:///`, `vct:///projects`, another namespace such as `vct:///genesis-source` — is a RESERVED system mount (`Table.reserved?/1`): resolvable through `resolve/1`/`mount_for_path/1`/`vct_path_for/2`, declared by a host at boot via `VCT`'s `:system_mounts`, never listed as a project, never evicted by the cap, and refused by `forget/1` with `{:error, :reserved_point}`.
- `EvoGit.VCT` keeps the authoritative list in memory as its read cache and persists every mutation through the store (`Store.save_vct_mounts/2`, atomic replace-all; `Store.list_vct_mounts/1` at `init/1`), so `<data_dir>/vct/` holds only the optional GLOBAL context and its lazy local git repository (`<data_dir>/vct/CONTEXT.md`, committed only while that context is non-empty; `VCT.init/1` runs the same best-effort, idempotent, boot-safe sync when a non-blank file already exists).
- `%EvoGit.VCT.Mount{point, path, name, kind: "git", last_opened_at}` is the mount metadata: `point` is the canonical `vct:///…` URL (a `vct:///projects/<name>` project point or a reserved point) and `path` the absolute OS path, so a mount is listed even when that path is missing.
- Mount points are VIRTUAL and listable even when the recorded OS path is missing (portability across machines): registering a path that matches the name/basename of a mount whose recorded path is gone RE-POINTS that mount (same point) instead of adding a second one, and no registration requires the path to exist.
- Project mounts over RPC: `RemoteAPI.projects/0` (PROJECT mounts only, so a reserved system mount is never returned), `mount_project/2` and `forget_project/1`, mirrored as `RemoteNode.projects/1`, `mount_project/3` and `forget_project/2` — a project list is implicitly per-BEAM-node (each host's own `vct_mounts` rows, reached only by calling that node), and there is no node/host column or global/shared mount table.
- `TaskRegistry` owns task state only and holds no mount state; every mount read, write and broadcast belongs to `EvoGit.VCT` (`mount/2`, `ensure_mount/3`, `forget/1` → exactly one `{:vct_updated, node}` on `"vct"`).
- NO workspace/grouping layer above a single project exists beyond that FLAT machine-local mount list: "workspace" is only loose prose in `agents/manager.ex`/`agents/architect.ex` prompts, the remaining "mount" wording is sandbox/bwrap/bench, and the ONE multi-repo construct is the TASK-level `[foreign_repos]` table in `<repo>/genesis.toml` (`EvoGit.ProjectConfig.foreign_repos/1` → `EvoGit.Core.ForeignRepo`), which groups repos under a TASK, not projects under a workspace.
- Config is machine-global, per-project settings are the repo's `genesis.toml`: `EvoGit.Config.config_path/0` = `<EvoGit.Platform.config_dir()>/config.toml` (XDG `~/.config/genesis`, macOS `~/Library/Application Support/genesis`, Windows `%APPDATA%/genesis`; `credentials.toml`, `agents.toml`, `tools/`, `remote_connections.toml` live beside it) and there is NO per-project settings table/file in the store; per-project config is `<repo>/genesis.toml` only — `EvoGit.ProjectConfig.read/1` (`nil` when absent), `.worktree_script/1,2`, `.write_worktree_script/2`, `.foreign_repos/1`, `.commands/1`, exposed to the dashboard as `RemoteAPI.read_project_config/1` / `RemoteNode.read_project_config/2`.
- Archive: ONE row per agent in the relational `task_agent_archives` table, keyed `(task_id, agent_id)`, plain-JSON columns (no compression of any kind), written STREAMING at completion (never buffered) by `Completion.write_archive_refs/7` (gated `archive && base_commit`) → `TaskRegistry.put_task_archive/1` → `Store.put_task_archive/2`; `put_task_archive/1` runs in the COMPLETING AGENT's process, not the registry (the registry publishes its store pid in the `:evogit_task_registry_stores` ETS table), and stays synchronous for that caller, so the row is committed BEFORE the task reaches a terminal status; nothing in `%Result{}` or the report; a task start clears its rows; reads `list_task_archives/3` (LEAN roster: no `result` unless `include_results`, no settings columns unless `include_settings`; `:include_total: false` skips the `count(*)`), `get_agent_archive/3` (full row), `delete_task_archives/2`, mirrored on `RemoteAPI`/`RemoteNode`; task deletes cascade explicitly (`Archives.delete_by_task/2` / `delete_by_tasks/2` / `delete_all/1`, no foreign key) → `agent/completion.ex` + `store/operations/archives.ex`
- Transcripts are NOT archived: `task_agent_archives` has NO messages column (only the final `result` + usage/settings), and the session releases its worktree/process context exactly once when it ends and `:evogit_agent_summary` never carried the context, so a finished agent's conversation is unrecoverable post-hoc — forensic questions about which tool calls an agent made must be answered from the live agent or the tool's own side artifacts (background-job output files under `EvoGit.Sandbox.resolve_tmpdir()`), never from the store
- Archive caveat: the same `EvoGit.Agent.Completion.complete/4` also writes the `refs/notes/evogit` note (its private `add_metadata_note/3`, gated on `base_commit` ALONE, DIFFERENT usage shape with a legacy `cost` key; `EvoGit.Agent.Completion.get_agent_metadata/2` has NO caller in `lib/`)
- Read fault isolation: `Store.offload/5` (unlinked monitored worker, 25 s deadline, degrades to the read's own empty shape; writes keep `:ok`/`{:error, :disk_full}`/crash); `TaskRegistry.ReadOffload` (supervised `Task.Supervisor` + 28 s deadline, replies the decoded term STRAIGHT to the original caller so it never enters the registry heap) and `TaskRegistry.StoreGuard` (a failed write → `{:error, :store_unavailable}`) → `store/` + `task_registry/`
- Lightweight reads: `select_tasks_page/2` (16-key rows + `total`), `get_task_lite/2`, mirrored on `TaskRegistry`/`RemoteAPI`/`RemoteNode` → `store/operations/{pages,lightweight}.ex`
- `mix store.maintenance [--data-dir PATH] [--vacuum] [--no-optimize]` (on-demand reclaim; `--vacuum` flips `auto_vacuum` to incremental first; never at boot) → `lib/mix/tasks/` + `store/`
- Peak/off-peak scheduling → `agent_scheduler/` + `config/`; tmpdir (`[tmp] mode` `:system`/`:custom`/`:per_repo` + `[tmp] path`, injected as `TMPDIR` + sandbox-writable path, EVENT-DRIVEN reclaim on terminal status) → `task_tmpdir.ex` + `sandbox/`
- Windows/OTP-29 hazards (charlist-only `Port.open` `:env`, `Port.info(:os_pid)` + double-close raise, tool-raise containment, `GIT_EDITOR` quoting) and the cross-node RPC payload profile → `lib/evo_git/CONTEXT.md`
- Review API (per-repo-path capability vs task-level-only state) → `review.ex` + `remote_node.ex` + `store/` (single `tasks.review_status` column)
- Foreign-repo starting-commit tracking (authority-gated roll-up of `SchedMeta.foreign_repo_commits`: only a writable `:read_write` agent running IN a foreign repo advances it; `base_sha` precedence at spawn) → `agent_scheduler/` + `task_registry/` (`PrevTaskRepos`)
- `:quality_level` (default balanced, unknown → warning + balanced, ROOT prompt only, omitted when default) → `quality_level.ex` + `task_registry/`
- Subagent merge conflicts (`ContextMerge`: octopus fast path then per-child sequential; resolves ONLY `CONTEXT.md` by node ownership 3/2/1; reports + aborts source/same-ownership conflicts) → `agent/context_merge.ex`
- Desktop port / orphan prevention / cancellation / ReqLLMPool sizing / peak-hours TOML / merge check / directory picker → root `./CONTEXT.md` (do not duplicate)
- Cross-node RPC payload profile (`:erpc.call/5`, uncompressed native BEAM terms, `:remote_rpc_timeout` 30s at call time; wrappers `{:ok, _} | {:error, {kind, reason}}` with per-function fallbacks): 🔴 `get_agent_history/1`, `list_tasks/0`; 🟠 `list_agents/0`, `get_task/1`, `list_tasks_paginated/1`, `load_file_diff`/`get_file_content`; 🟢 `list_tasks_summary/1`, `list_task_ids/1`, `list_tasks_changed_since/1`, config reads, review metadata/commits/`check_merge`; dead: `get_agent_state/1`, `load_review_data/2` → `lib/evo_git/CONTEXT.md`

## Provider Profiles & Concrete Model Selections

Canonical config uses `[llm] default_provider_profile` to select an account in `[[llm.providers]]`, with the first account used only when no selector is supplied.
Each provider profile owns a stable account `id`, `provider`, shared authentication (`auth_mode`, `api_key_env_var` or `oauth_file`), endpoint (`base_url`/provider options), `concurrency` and peak/off-peak schedule for every model and reasoning effort in its nested ordered `models` inventory.
OAuth paths are account settings, never a global `[llm] oauth_file`, and `LLM.profile_generation_params/1` remains the single generation/auth/provider-constraint assembly boundary.
Provider generation/context defaults and ordered `reasoning_efforts` may be overridden by nested model settings, with explicit task effort taking final precedence.
`default_model` selects a model (first model when absent), while optional `default_reasoning_effort` is never inferred from effort order.
`Schema.provider_profiles/1` returns canonical STRING-keyed accounts, `model_selections/1` enumerates ordered model/effort choices without reading credentials or metadata, and `resolve_model_spec/2` validates a default, account id or explicit selection.
A task `model_spec` is a STRING-keyed identity map with `provider_profile_id`, `model` and optional `reasoning_effort`, not a ReqLLM identifier, provider profile or secret-bearing generation parameters.
The schema's resolved `model_spec` is instead the ReqLLM-ready qualified string or endpoint-override map; dispatch stores it as effective `llm_model` alongside `llm_generation_params`, configured `llm_context_window` and the complete canonical selection.
Explicit invalid selections fail closed before registration, and locked parent selections override child picks and scripts with the entire account/model/effort identity rather than only a legacy id.
Unlocked children inherit the effective parent selection as `default_model_spec`, leaving per-spawn scripts in control; dispatch and inheritance contracts belong to `agent_scheduler/` and `agent/`.
Legacy `[[llm.models]]`, flat `[llm] model` and legacy selection ids remain supported, with one-for-one account normalization preserving ids and separate account boundaries even for identical providers/models/endpoints.
Nonempty canonical providers take precedence over stale legacy fields, and saving canonical config strips legacy inventory and flat mirrors rather than maintaining two sources of truth.
Normalization, default/duplicate/effort errors, runtime-profile compatibility and generation/auth assembly details belong to `config/` and `config/schema/`.
An explicit task selection is validated before enqueue and submitted as `model_spec` with `model_id_locked: true`, while no selection means Auto and omits both keys; legacy `model_id` accepts account ids, `id:provider:model` and matching qualified/bare inventory models (details: `lib/evo_git/CONTEXT.md`).
The dashboard Settings → LLM provider-profile editor writes canonical accounts and defaults, preserving unrelated accounts, shared settings and nested overrides; details belong to `config/`.
`Config.config_status/0` combines model/credential presence with validation errors, so an invalid default selector is unhealthy even when another account has usable credentials; account-specific API-key checks never borrow a different account's custom key.
`SystemCheck` resolves default/account/task selections through Schema before testing the effective request, while retaining raw ReqLLM identifier compatibility; health and credential boundaries belong to `config/` and `lib/evo_git/CONTEXT.md`.
Compression consumes the effective configured context window, never catalog limits, and cost prices effective `llm_model` with the selected provider account's peak/off-peak period; details belong to `agent/` and `agent/compression/`.

## Custom Agents & Model Selection

User-defined agents live in `<config_dir>/agents.toml` with name/prompt, read/read_write authority, delegation level, optional turn cap, tools/subagents whitelists and optional canonical `model_spec` (legacy `model_id` remains a fallback).
`CustomAgents` normalizes selection keys and effort values, rejects structurally malformed definitions with `:invalid_model_spec` on save and leaves account/model existence checks to dispatch.
Tools whitelists are alias-aware and may include custom tools; an absent whitelist exposes built-ins only, while `CustomAgents.reload/0` invalidates agent/tool caches.
`ModelSelector` evaluates the administrator's compile-once `fn agent -> <script> end` body per spawn and accepts a canonical account/model/effort map or legacy profile id, with nil/empty/false meaning fallback and script errors logged without crashing.
Dispatch priority is explicit task or inherited locked selection → script → canonical definition/inherited `default_model_spec` → legacy definition/inherited `model_id` → configured default.
Invalid canonical script selections fail closed, while unknown legacy script ids retain default fallback; unlocked inheritance does not set the lock and custom `max_turns` still overrides scheduler turn caps.
`Runtime.Helpers.resolve_root_agent/2` validates `:agent`, forwards canonical definition defaults without locking them, and builds the custom root whose Runner installs `:custom_agent_id`.
Definition schemas and script contracts belong to `custom_agents/`, runtime spec construction to `runtime/`, and selection/error/inheritance details to `agent_scheduler/` and `agent/`.

## Multi-Modal Content (objective, tool results, injected messages)

Media (images/audio) rides LLM content parts at THREE sites; wire contract `EvoGit.Attachments` (`lib/evo_git/attachments.ex`), structured tool output `EvoGit.Agent.ToolOutput` (`agent/tool_output.ex`).

- **Shape**: STRING-keyed `%{"type" => "image"|"audio", "name" => <basename>, "media_type" => <IANA>, "data" => <base64 ASCII>}`; base64 is MANDATORY at every data-plane boundary (task opts, pending-message queue) because `Store.Codec` Jason-encodes whole opts and raw binaries abort Jason; decoding happens ONLY at materialization (`Attachments.to_content_parts/2`: image → `ReqLLM.ContentPart.image(raw, media_type)`, audio → a `:file` part), always a plain `[ContentPart.text(text) | media parts]` list, NEVER `ReqLLM.ToolResult`; `Attachments.message/1` is the ONE normalizer.
- **Caps**: ≤ 4 attachments per message, each ≤ 15 MiB RAW bytes (`EvoGit.Attachments` attributes are the single core source), per task opt AND per tool output; malformed payloads raise a descriptive `ArgumentError`.
- **Site 1 — `:attachments` task opt (root-only)**: ROOT agent's FIRST user message only (`ContextBuilder.build_initial_messages/4`, gated on `parent_id == nil` AND non-empty; subagents never inherit); Genesis Mode A, Mode B both roots and the Evolve root receive it, Reflect never; validated by `RuntimeOpts` → `Attachments.validate/1`.
- **Site 2 — tool results (any agent, any turn)**: `Tools.execute/5` may return `String.t() | ToolOutput.t() | {:error, reason}` (`ToolOutput` = `%{text, attachments}`, `new/2`/`wrap/1`/`with_text/2`/`to_content_parts/1`). `agent/tool_dispatch.ex` is the SOLE **wrap boundary**: sanitize/truncate + hint appenders hit the TEXT component only (`OutputSanitizer`/`TruncationFeedback`/`DelegationHints` keep a binary contract), media is re-wrapped; error/timeout/crash paths stay plain strings. Detail: `agent/`.
- **Site 3 — injected user messages (mid-run, NO root gate)**: `AgentScheduler.send_user_message/2` / `send_session_message/3` / `RemoteAPI.send_agent_message/2` / `RemoteNode.send_agent_message/3` accept `String.t() | %{text:, attachments:}`; `Store.append_pending_user_message/2` stores shape-for-shape (legacy binary VERBATIM) in the `ControlPlane` inbox, which the exchange loop drains and materializes via `ContextBuilder.build_injected_message/2`. Detail: `agent_scheduler/` + `agent/session/CONTEXT.md`.
- **Invariants / limits**: a plain-string tool result and a legacy string pending message behave BYTE-IDENTICALLY to pre-media behavior (`%ReqLLM.Message{}` struct-equality regressions in `test/evo_git/agent/tool_output_pipeline_test.exs` + `tool_output_integration_test.exs`). Compression keeps `[system, first_user]` BYTE-IDENTICALLY (objective attachments re-sent after every compression — the cached prefix must not change) and the last K turns VERBATIM, while OLDER tool-result media collapses into one `[... tool result media omitted ...]` placeholder per message (stage 1). Resume / merge-auto-resolve / GitHub-fix follow-ups do NOT re-carry `:attachments`. Detail: `store/` + `runtime/`.
- **No built-in producer (tool-result media is plumbing only)**: no built-in tool returns a media-carrying `%ToolOutput{}`, and none turns a local file into a content part — `read` (`agent/tools/file_read.ex`) is text-only with no binary/image detection (a `.png` is line-split and returned as invalid-UTF-8 text repaired by `EvoGit.UTF8.ensure_utf8/1`), there is no `read_image`/`screenshot` tool (`docs/harness-alignment.md` notes `dsh` has one), `web_fetch` renders non-text bodies as `[binary content omitted: …]`, and custom tools are STRING-ONLY (`CustomTools.execute/3` turns any non-string return into an error). Only the test seam app env `:evo_git, :tool_dispatch_test_tools` (`Tools.test_tool_override/1`) can produce tool-result media today, so site 2 is verified plumbing rather than a usable capability.
- **Only the dashboard produces attachments**: `EvoDash.AttachedFile` reads `png/jpg/jpeg/gif/webp/bmp` + `mp3/wav/ogg/m4a/flac` (≤ 4 files, ≤ 15 MiB raw) into base64 for the Projects task form's `:attachments` opt, and no dashboard surface sends an injected message WITH media (the agent inspector sends plain strings).
- **Deliberately NO modality gate**: nothing checks the selected model (`EvoGit.Attachments` moduledoc + `RuntimeOpts`), so the part is always sent — ReqLLM encodes `:image` for OpenAI-compatible chat (`image_url` data URI), Anthropic (base64 `image` block, also inside `tool_result`), OpenAI Responses/Codex (`input_image`), Google (`inline_data`) and zai; a text-only model answers HTTP 400, which `EvoGit.Agent.LlmError.non_retryable?/1` turns into a fail-fast `{:llm_request_rejected, message}` → `:failed` task (never stripped, never silently dropped by EvoGit).
- **Audio is nominal**: audio always materializes as a `ReqLLM.Message.ContentPart.file/3` `:file` part, which OpenAI-compatible chat encodes as an `image_url` data URI and Anthropic as a `document` block, so it is expected to be provider-rejected outside OpenAI-Responses-based endpoints.

## Multi-Repo Read-Write Foreign Repos

Foreign repos may be **writable** — still ONE primary repo + one final report per task; foreign modifications are tracked but NEVER merged back by the task (the review page merges/rejects).

- **Data model** (`Core.ForeignRepo`): `writable: boolean()` (default `false`) + `base_sha: String.t() | nil` (`nil` = foreign HEAD); `new/*`/`normalize/1` handle STRING-keyed Codec maps; `ProjectConfig` accepts both; a task `:foreign_repos` entry stays READ-ONLY unless `genesis.toml` marks the repo `writable` (TOML-only).
- **Registry**: NO `[[repos]]` table exists in `config.toml` — `Config.Schema.Definitions.schemas/0` has no repo key and the config layer validates no repo path; the declared set is per-project `genesis.toml` `[foreign_repos.<id>]` (`ProjectConfig.foreign_repos/1`: TOML key IS the id, `path` required, `description`/`writable`/`base_sha` optional), merged id-keyed with the task opt `:foreign_repos` by `Runtime.Helpers.load_foreign_repos/2` (a task entry wins per id and can never remove a TOML entry); existence/git-repo/`base_sha`/UNC validation is runtime-only and raises `ArgumentError`, then `ForeignWorktree.ensure_all/1` provisions the writable read views.
- **Per-repo history**: `EvoGit.TaskCommitGraph` resolves a repo's base from `opts[:foreign_repos]` (`foreign_base_for/2`) and walks the STRING-keyed `result["repos"]` map, while `EvoGit.Review` itself is repo-path-parameterized and foreign-repo-agnostic (`merge_branch`/`reject_branch`/`check_merge`/`default_merge_target` take one `repo_path`).
- **Spawn gate** (`Subagents.validate_spatial_contract_for_spec/3,4`; 3-arity = root depth 0): read-only cross-repo spawns UNRESTRICTED at any depth; `:read_write` cross-repo spawns need `writable: true` (else `{:error, {:foreign_repo_read_only, msg}}`), are **root-only** (depth 0, else `{:error, {:foreign_repo_write_not_root, msg}}`) and **one per batch** (`spawn_validated_subagents/5` threads `writable_accepted`; 2nd+ → `{:error, {:foreign_repo_write_serialized, msg}}`); same-repo spawns INSIDE a foreign repo are UNRESTRICTED. `format_subagent_result/1` surfaces all three verbatim as `"Error: #{msg}"`; the role comes from id-matching `spec.foreign_repos` (Runner puts `Process.get(:foreign_repos)`), NEVER the path; unknown ids → read-only.
- **Tool gating**: `Tools.execute/5` chains `maybe_block_read_only_foreign_repo/5` after `maybe_block_repo_less/5` — blocks every `@write_tools` entry (incl. `run_git`); `Shared.validate_file_scope/3` rejects write targets inside one; `Tools.read_only_schemas/0` = read tools + Context write/edit + ShellTool + `WebFetch` + `Lsp` only when `Config.lsp_enabled?/0`; there is no `curl` tool.
- **Roots + report** (`Runtime.Helpers.merge_and_report/3,4`): writable repos get worktree roots like the primary; ONE branch name per task reused across all (`Git.create_branch(repo.root, branch_name, sha)`; failure logs + `branch_name: nil`). Report gains top-level **`repos: %{repo_id => %{commit_sha, branch_name}}`** (STRING keys): `"primary"` always, each writable repo that committed, read-only ABSENT; top-level `commit_sha`/`branch_name`/`result` stay the PRIMARY's. Source `Result.foreign_repo_commits`, rolled up by `Lifecycle.inject_foreign_repo_commits/2` + `store_sub_result/3` (child-wins), read via `AgentScheduler.get_foreign_repo_commits/1` (`%{}` on missing sched_meta).
- **Review + scoping**: each writable repo carries an `evogit-agent-*` branch at `repos[repo_id].commit_sha`; `Review.merge_branch/2,3` + `reject_branch` are per-repo-path; `maybe_init_repo/3` (required `primary?`) wipes `.genesis/workers` + `clean_orphaned_branches` ONLY for the primary, and `run_init_script` stays primary-only.
- **Persistent foreign worktree (read view)** at `<root>/.genesis/foreign_repos/<id>` (`ForeignRepo.worktree_path/1`), reset at task start (`ForeignWorktree.ensure_all/1`), advanced by `Agent.Runner.run/3` `try/after` → `sync_from_agent/0`; outside `.genesis/workers/`, never moves MAIN HEAD, kept at task end — detail: `agent_scheduler/`.
- **Validation + merge seeding**: `load_foreign_repos/2` validates up front (exists, is a git repo, non-nil `base_sha` resolves) → descriptive `ArgumentError`; `SubagentProcessing` returns `{:error, {call, 0, "Error: foreign repository path does not exist or is not a git repository: <path>"}}`; `resolve_foreign_repo_starting_commit/2` = `base_sha` else foreign HEAD; subagent phylo precedence = task `base_sha` → tracked `foreign_repo_commits` → foreign HEAD. `apply_merge_context/4` carries `:foreign_repos` and overrides each `base_sha` from the prev task's `repos[repo_id]["commit_sha"]`; `apply_resume_context/3` keeps `:foreign_repos` and overrides per-repo base_sha in BOTH branches; shared `TaskRegistry.PrevTaskRepos`. Detail: `task_registry/`.
- **Prompts**: `:read_write` foreign spawns are ROOT-ONLY + ONE-AT-A-TIME; static prompts + `PromptFragments.writable_foreign_repo_clause/0` are role-agnostic and tell NESTED agents to report upward, while each agent's role is stated in its FIRST-USER context by the pure `ContextBuilder.build_authority_section/1` (root signal `%EvoGit.Agent.State{}.parent_id == nil`; `""` for repo-less and single-repo tasks). Detail: `runtime/` + `agent/` + `core/`.

## Self-Reflective Agent (repo-less)

A **repo-less** Assistant with no repository or worktree uses tiered Elixir evaluation to inspect runtime state, control tasks and show transient guides.

- **Task type**: `:reflect` — `TaskExecutor.execute_task(:reflect, opts, task_id)` runs `Runtime.SelfReflective.run(opts ++ [task_id: task_id])`; codec atom `:reflect`, mode `"reflect"`; opts `objective`, optional `model_spec`/legacy `model_id`, `model_id_locked`, `source_root` and `task_id`, **NO `:path`** (the executor skips `RuntimeOpts.build_common_runtime_opts`, which `Keyword.fetch!`s `:path`); result `{:ok, %{result: <summary>, commit_sha: nil, branch_name: nil, tag: nil}}`.
- **Lifecycle**: a `:reflect` task is an ordinary `tasks` row — `TaskRegistry.start_task/2` persists it directly as `:running` (no in-process `:pending` phase), leases it, and settles it through the standard wrapper `{ref, result}` → `handle_wrapper_result/3` path (`:completed`/`:failed`), with a graceful cancel force-mapping the terminal result to `:cancelled`; the final answer is `tasks.result["result"]`.
- **No session reuse on the one-shot path**: a `:reflect` task allocates a NEW task id and a NEW session/agent id with a fresh conversation, and the session is gone once it ends (its summary row is removed), so consecutive runs share only the scheduler/config/catalog caches and the managed source checkout; any conversation memory must be replayed by the caller as text inside `objective` (the dashboard's "Previous conversation:" preamble), which lands in the fresh first user message via `ContextBuilder.build_initial_messages/4`. Multi-message chat uses an interactive session instead (`Runtime.Assistant` + `send_session_message/3`), which keeps ONE conversation, worktree and cache key for its whole life.
- **Task-list visibility**: store list/summary/page/lite reads never filter by `task_type`, so `:reflect` rows appear in `list_tasks`/`list_task_ids`/`get_task_lite` (each carries `type`) and in the `/server/status` `active_tasks` count; hiding them from `/tasks` and refusing review are caller/UI decisions (`EvoDashWeb.NodeAware.show_review_button?/1` returns false for a completed `:reflect`).
- **Synthetic worktree name**: `Dispatch.try_dispatch/2` still builds `<source_root>/.genesis/workers/worker_T<n>_A<m>` and `next_task_number/1` `File.ls`es that directory, but no file or directory is ever created for a repo-less agent.
- **Plumbing**: `spec.opts[:repo_less] = true`, `phylo_node` nil; `Dispatch.resolve_agent_repo_root/2` short-circuits to `resolve_repo_less_root/0` (`SelfReflectiveSource.reference_path/0` → `File.cwd!()` → `"[system]"`); the Runner skips `create_worktree_for_agent`, sets `Process.put(:repo_less, true)`, `commit_pending_in_worktree/0` no-ops; **write guard** `Tools.execute/5` blocks `@write_tools` when `Process.get(:repo_less)` and `available_tools/0` omits them.
- **Modules**: `Agents.SelfReflective` is the repo-less Assistant (`agent_type :read`, `delegation_level :low`, `subagent_modules []`) exposing source-reading tools (`read`, `rg`, `glob`, `list_dir`, context/history readers), `web_fetch`, config-gated `web_search` and tiered `elixir_eval`, but no shell, file writes or `run_command`.
Read raw implementation before calling an explicitly admitted real API; inspecting source never authorizes an unlisted function.
A reply with no tool calls ends the run; `Runtime.SelfReflective` owns source resolution and spec construction, and `SelfReflectiveSource` owns the managed source clone and declares it as the reserved VCT mount `vct:///genesis-source` (the point the persona names to the agent).
- **One `elixir_eval` tool**: read/write use Dune with explicit real module/function/arity grants so the Assistant can inspect source and call admitted task/detail/agent/config/status APIs directly, while existing projected Read/Write facades remain optional conveniences.
Write requires exact-code user approval and admits task lifecycle operations, runtime scheduler updates, persistent `Config.save_user_config/1` and explicit `AgentScheduler.RemoteAPI.reload_config/0`; saving replaces the whole config and refreshes the config snapshot synchronously but applies no scheduler runtime state, so preserve unrelated settings with a read–modify–save and distinguish persisted settings from runtime overrides.
Sudo separately requires explicit approval for unrestricted native Elixir with full VM authority, not a security sandbox, and refusals never trigger automatic escalation.
Each call has fresh bindings, fail-closed Assistant-owner authorization and bounded execution/output; direct calls preserve actual return contracts and may expose sensitive/heavy data, but unlisted MFAs, wrong arities, arbitrary native APIs and the `CommandShell` registry remain unavailable in read/write.
Evaluator, capability, approval and cleanup details → `lib/evo_git/agent/tools/elixir_eval/CONTEXT.md`.
`:running → :completed/:failed/:cancelled` emits NO `:finalizing` broadcast; the root has `parent_id: nil` and a matching `task_id` (filter `list_agents/0`).
Live content: `EvoGit.Agent.Stream.watch/1` pushes `{:agent_delta, agent_id, seq, events}` for a running session (snapshot + `seq` is the only resync), while a completed transcript is fetched once via `get_agent_history/1` — **history is gone once the session ends**, since the summary row never carried the context.
The persisted artifact is `task.result`, with no `resume_from`; tests include `reflect_tools_test.exs`, `self_reflective_source_test.exs`, `self_reflective_test.exs`, repo-less scheduler/tool-dispatch cases and `task_executor_reflect_test.exs`.
Details belong to `agents/` and `runtime/`, with dashboard Home chat (`EvoDashWeb.HomeLive`, `GET /assistant`; the legacy `GET /help` 302-redirects to it) in `apps/evo_dash/CONTEXT.md`.

## LLM Concurrency & Slot Gating

LLM resource pools are keyed by immutable `provider_profile_id`, so every concrete model/effort selection in an account shares concurrency and exhaustion backoff, while distinct account profiles remain isolated.
Historical scheduler fields such as `model_concurrency` and `llm_backoff_until` retain their names but use account ids on the canonical path and legacy profile ids on compatibility paths.
`AgentScheduler.with_llm_slot/2` blocks in a purgeable `:infinity` call, capacity-zero requests enqueue, and `default_llm_max_concurrency` is a floor/fallback rather than a global cap, preserving explicit zero pauses.
Runtime updates preserve live holders/waiters/backoff, global pause gates pending grants, and resume/capacity changes sweep eligible waiters without evicting in-flight holders.
Rate-limit and insufficient-balance failures report growing account-shared backoff through `AgentScheduler.report_llm_error/3`; agents park in the slot queue rather than sleeping, preserving cancellation responsiveness.
`ReqLLMPool` sizes HTTP capacity from account concurrency once per account, never multiplying it by nested model/effort choices, and runtime reconciliation remains grow-only.
Slot maps, retry policy, reload/legacy behavior and pause contracts belong to `agent_scheduler/` and `agent/`; Finch sizing and peak-engine integration belong to `lib/evo_git/CONTEXT.md`.

## Peak/Off-Peak Hour Concurrency Scheduling

Provider accounts own `peak_concurrency`, `peak_hours`, `off_peak_days` and `timezone`, with `peak_concurrency = 0` a hard pause shared by all their models/efforts and exempt from the default-concurrency floor.
`EvoGit.PeakHours` remains the single source of truth for half-open/overnight/day-scoped windows, off-peak-day precedence, local/IANA wall clocks, validation and transition math.
`PeakHourEngine` prefers canonical provider profiles, falls back to legacy model profiles only when canonical accounts are absent, and applies one floored concurrency entry per account with explicit zero and peak exemptions preserved.
Account TOML/validation contracts belong to `config/`, engine/RPC integration to `lib/evo_git/CONTEXT.md`, and timer, queue and floor details to `agent_scheduler/`.

## Agent Loop Control Flow + Graceful Task Cancellation

**Loop injection point**: the exchange loop (`EvoGit.Agent.Exchange`) drains the session inbox at the top of each turn (after compression/limit warnings, before the LLM call); `ControlPlane.drain_messages/1` yields turn-tagged user messages that are appended to the conversation, so a parked interactive session resumes exactly where its `%State{}` was checkpointed.
API chain: `EvoDash.NodeContext` → `RemoteNode.send_agent_message/3` → `RemoteAPI.send_agent_message/2` (guards `{:error, :scheduler_not_started}` when `:evogit_agent_summary` is undefined) → `AgentScheduler.send_user_message/2` → the `ControlPlane` inbox append, returning `:ok | {:error, :not_found}`; ⚠️ RemoteNode's local path nests the inner error (`{:ok, {:error, :not_found}}`), so the dashboard falsely reports success for a missing agent. Interactive conversations use the session chain instead (`send_session_message/3` → the session's `:input` command). Detail: `agent/` + `agent_scheduler/`.

**Two cancellation actions** (node-aware via `RemoteNode.cancel_task/2` + `force_kill_task/2`):
- **Graceful cancel** (`TaskRegistry.cancel_task/1`): `:pending` → immediate `:cancelled`; `:running`/`:awaiting_input` → `:cancelling` + the session command `{:cancel, :graceful}` (the session enters `:cancelling`, appends a save-work user message through the `ControlPlane` inbox and records the cancel flag in `:evogit_agent_control`, plus an `:evogit_cancelling_tasks` marker). The exchange loop enters cancel-grace with a **3-turn budget** (a recovery auto-commit first); final status persists `:cancelled` WITH result/usage/archive **preserved**. `:cancelling` is non-terminal + idempotent (`clear_finished_tasks` skips it, reconciliation → `:cancelled`) and blocks new root spawns (`run_agent` → `{:error, :cancelled}`).
- **Force kill** (`force_kill_task/1`): kills the in-flight exchange worker, stops the session, kills the wrapper and persists **`:failed`** with result nil'd, from `:running`, `:awaiting_input` and `:cancelling`; `:cancelled` means ONLY gracefully-cancelled tasks.
- **Dashboard**: Cancel button (`[:pending, :running]`) → warning modal → `confirm_cancel_task`; force kill in the card dropdown (`[:running, :cancelling]`, "Danger zone") → `confirm_force_kill_task`; `:cancelling` renders violet and is reviewable (ReviewLive treats `:cancelled` like `:completed`). Detail: `task_registry/` + `agent_scheduler/`.

## Update-Timing Safety

No restart/update machinery exists in `:evo_git` (zero `System.restart`/`:init.restart`/`:init.stop`, no signal handlers, no checkpointing on exit); graceful stop comes from `:evo_dash` (`DesktopQuit.default_stop/0`, SystemLive Stop — both `System.stop/0`), and the Rust shell NEVER sends SIGTERM (watchdog uses SIGKILL). `bin/<release> stop`/`restart` need `RELEASE_DISTRIBUTION != none` + a resolvable `RELEASE_NODE`, so the non-distributed desktop sidecar must be stopped from within. Pre-restart mechanism = **graceful cancel** (3-turn grace, NOT wall-clock bounded — each grace turn is a full LLM+tools cycle, so wait for a terminal status with a generous timeout, or force-kill).
Idle-detection API: `TaskRegistry.list_task_ids(statuses \ [])` / `list_tasks_summary(statuses \ [], since \ nil)` / `list_tasks_changed_since/1` / `get_task/1` (+ RemoteAPI/RemoteNode mirrors); in-flight set `[:running, :pending, :finalizing, :cancelling]`.
Task status lives ONLY in SQLite (`tasks.status`); scheduler ETS holds the summary/control rows plus sched_meta for LIVE agents (never the conversation) and dies with the app — sessions are in-memory, so a BEAM restart fails any `:awaiting_input` session (`:failed`) and reclaims its worktree. Lease: `@lease_duration` 120s, heartbeat every 60s renews `[:running, :pending, :cancelling]` (not `:finalizing`); one-shot `:lease_sweep` at `@sweep_after` 150s marks orphaned `:running` → `:failed` ONLY when the lease is invalid AND no live sched_meta agents (never reschedules). Startup reconciliation: `:finalizing` → `:failed`, `:cancelling` → `:cancelled` (result preserved), `:running` untouched. **No auto-resume** — resume is a NEW `:evolve` task via the Review page (`resume_from` → `ResumeContext`; `review_status: :continued` is a persisted marker only). Detail: `agent_scheduler/` + `task_registry/`.

## Backend Boot Profile (desktop sidecar readiness)

Boot work in `:evo_git` is CONSTANT-COST: nothing keyed to the release version or install path; no lockfile/`.genesis/` marker/cache verification/release-tree read at start.
Ordered `EvoGit.Application.start/2` work: (1) create the 4 ETS tables; (2) `Distribution.maybe_enable/0` (logs + returns `{:error, _}`, never raises); (3) `Calendar.put_time_zone_database(Tz.TimeZoneDatabase)`; (4) children in order: PubSub → **`Config.Watcher`** (skipped when `Mix.env() == :test`) → Throttle → CommandApproval → RemoteConnection Registry/Supervisor → **`Store`** → `Store.Maintenance` → **`VCT`** → TaskRegistry ReadSupervisor/ProcessRegistry → TaskRegistry → BackgroundJobs → WorktreeManager → AgentGroupSupervisor (Task.Supervisor → **`EvoGit.CatalogWarmup`** → AgentScheduler) → PeakHourEngine → SystemSampler, plus SandboxProcessRegistry + SandboxSlice on Linux. `Config.Watcher` sits immediately after PubSub (its `"config"` broadcasts need it) and BEFORE the children that read config, and its `init/1` primes the RAM config snapshot in its own process (a fingerprint-diffed no-op when `runtime.exs` already built it), so every child's first read is a term lookup.
`VCT` starts AFTER `Store` (its `init/1` loads the mount table through `Store.list_vct_mounts/1`) and BEFORE `TaskRegistry`; it is started as `{EvoGit.VCT, system_mounts: EvoGit.SelfReflectiveSource.system_mounts()}`, so the reserved `vct:///genesis-source` mount is ensured idempotently at boot (persisted and broadcast only when it actually changes). `CatalogWarmup` sits IMMEDIATELY BEFORE the scheduler by design (it returns `:ignore`, so it is never a running child) so the LLM model catalog is already loaded when `AgentScheduler.init/1` first reads it.
The ONE potentially slow child is `Store`, whose `init/1` runs the migrations before any read/write (`Store.Boot.start_dynamic/2`); `TaskRegistry.init/1` then does a synchronous `Store.select_running_lease_info/1`; everything else is O(1). Per-migration cost: `store/`.
Catalog resolution can allocate a large transient heap on a fresh BEAM, so `EvoGit.CatalogWarmup` runs immediately before the scheduler and warms `Schema.effective_model_profiles/1`'s per-account default-model runtime projection in a throwaway process.
The scheduler then boots through `State.from_config/2` with the canonical selection snapshot and account-shared resource maps, reading the already-loaded catalog cheaply; boot allocation measurements and wiring belong to `lib/evo_git/agent_scheduler/CONTEXT.md` and `lib/evo_git/CONTEXT.md`.
**Boot-fatal paths** (a child EXIT ⇒ "Genesis backend unavailable"): an unwritable/missing data dir (`File.mkdir_p!` raises), a failed repo open (`{:stop, {:failed_to_open_sqlite, reason}}`), or ANY raise out of the migration run (baseline post-condition `Ecto.MigrationError`, bad `tasks` shape, `SQLITE_BUSY`, corrupt file) — uncaught in `init/1`; with `start_permanent: Mix.env() == :prod` a terminating permanent app takes the whole VM down.
`Store` opens with `journal_mode: :wal` + `default_transaction_mode: :immediate` + `busy_timeout: 30_000` (a locked `tasks.sqlite` stalls a statement up to ~30 s, waited in the calling process rather than on a VM thread) and WAL needs `-wal`/`-shm` sidecars on a shared-memory-capable filesystem (a network/UNC data dir can fail the open). No boot-time self-exit exists in `:evo_git`.
**Observability**: the boot path emits no phase logs of its own — only Ecto.Migrator's lines (`Store.Boot` has ZERO Logger calls), `Config.resolve/0` warnings (emitted by a snapshot build, i.e. the watcher's boot prime or a reload), `PeakHourEngine: starting — watched profiles: …` + `wakeup reason=:boot`/`next wakeup in` pair, and Linux `SandboxSlice` warnings.
**Boot lines CAN repeat inside ONE OS process**: a `Store` crash (`:one_for_one` child of `EvoGit.Supervisor`) re-runs `init/1` → the migration lines, and `System.restart/0` re-boots all applications INSIDE the running node (emulator not restarted) — its only caller is the dashboard System page (`system_live.ex`; remote variant `EvoDash.NodeContext.restart_remote/1`). `EvoGit.Supervisor`/`EvoGit.AgentGroupSupervisor` declare no restart intensities (OTP defaults 3/5s); exceeding them terminates the supervisor and, `evo_git` being `:permanent`, the node goes down — the Rust watchdog respawns a NEW OS process. The log handler appends (`type: :file` + rotation, no truncate-at-boot), so N boot sequences cannot distinguish in-place restarts from OS processes; `<data_dir>/logs/backend.log` is configured in the ROOT `config/runtime.exs` (rotating 10 MB × 5) and nothing in `:evo_git` writes/truncates/rotates/deletes under `<data_dir>/logs/`.
**No first-start-of-a-NEW-release-dir delta exists on the Elixir side** — per-BEAM one-time costs recur on EVERY boot. Port resolution / orphan prevention: root `./CONTEXT.md`.
### Boot memory profile (what a boot can actually allocate)
- The five app-owned ETS tables are created EMPTY in `EvoGit.Application.start/2` (`application.ex:20-62`); the only boot-time insert is ONE `{registry_name, store}` row in `:evogit_task_registry_stores` (`task_registry.ex:393`).
- No boot child loads task rows into its state: `TaskRegistry.init/1` reads only `select_running_lease_info/1` (id/status/lease_expires_at) and folds the list away (`task_registry.ex:413-446`), and `AgentScheduler.init/1` reads NO SQLite at all (`agent_scheduler.ex:526-658`).
- `EvoGit.VCT.init/1` performs exactly ONE mount-table read (`Store.list_vct_mounts/1` over `vct_mounts`: at most `max_projects/0` = 100 project mounts plus the reserved system mounts) and keeps it as its read cache; `<data_dir>/vct/` is created but never scanned, and a still-pending migration 7 is the only boot path that touches the retired `projects` table.
- The SQLite page cache is per-connection and LAZY: `EvoGit.Repo.start_opts/0` sets `cache_size: -8_000` (8 MiB/connection, ~2048 × 4 KiB pages) × `Boot.default_pool_size/0` = 6, i.e. a ~48 MB STEADY-STATE ceiling but ~0 at boot (the boot leg touches only `sqlite_schema` + `schema_migrations`) → `store/` + `repo.ex`.
- The ONE eager multi-megabyte boot allocation is the LLMDB catalog, and it lands in a THROWAWAY process: `EvoGit.CatalogWarmup` (a `:ignore` child of `EvoGit.AgentGroupSupervisor` immediately before the scheduler) resolves the configured profiles in its own short-lived process → `Schema.llm_generation_params/1` → `model_metadata/1` → `ReqLLM.model/1` → `LLMDB.ensure_loaded!` decodes the 11.7 MB packaged snapshot (`deps/llm_db/priv/llm_db/snapshot.json`, ~10k models) into `:persistent_term` (`deps/llm_db/lib/llm_db/catalog.ex:91-95`); the decode's transient heap dies with that process, and the catalog itself is retained for the whole BEAM lifetime.
- That load requires the provider ATOM to exist already (`Schema.LLM.catalog_key/1` uses `String.to_existing_atom`, rescuing to nil), so the FIRST `llm_generation_params/1` call merely CREATES it via `LLMConstraints` → `provider_from_model/1` (`String.to_atom`) and a LATER call in the same warm-up run then loads the catalog — deterministic for any model written in the documented `"provider:model"` form, and skipped entirely when no model is configured (the warm-up is inert: seam installed or no profile carries a `model`) → `config/schema/CONTEXT.md`.
- Measured PROOF, same 4-profile config / isolated data dir / `[sandbox] mode = "disabled"` / `-mode embedded` (the release and `genesis start` path), sampled in-node from the running scheduler: WITH the warm-up, `EvoGit.AgentScheduler` reads **28.8 KB at t=0 (boot finished), 66.3 KB at t=3-30 s and 53.8 KB at t=90 s** (13.9k reductions at t=0; `:erlang.memory(:total)` ≈ 225 MB, processes ≈ 40 MB), and the endpoint is up ~2.1 s after the first boot log line. The SAME harness against the pre-warm-up build retained **94,804.2 KB (92.6 MB) at every sample out to t=90 s** (189.0M reductions; `:erlang.memory(:total)` ≈ 318 MB, processes ≈ 136 MB, settled RSS 492 MB vs 396 MB) — i.e. the scheduler's heap is now KB-scale in interactive AND embedded boots, and boot time is unchanged → `agent_scheduler/CONTEXT.md`.
- **Steady-state OS memory by launch method** (same 4-profile config, fresh isolated data dir, one `GET /` at t≈15-25 s): embedded release ≈ **RSS 395-396 MB / PSS ≈ 329 MB** from ~20 s on with boot peak **VmHWM ≈ 770 MB** (`:erlang.memory(:total)` ≈ 225 MB: processes 40, system 184, code 81; pre-warm-up v0.13.12 read RSS 465-492 MB / `:total` ≈ 296 MB, the ~92 MB delta being the scheduler's retained dead heap plus its carrier pages).
- **Interactive vs embedded dominates, NOT dev-vs-prod**: the SAME release booted interactive settles at RSS ≈ 177 MB / `:erlang.memory(:total)` ≈ 122 MB (code 27 MB), and a fresh compiled `mix phx.server` (interactive, with watchers) settles at RSS ≈ 200 MB / PSS ≈ 166 MB. The embedded gap (≈ +174 MB BEAM) is preloaded code 81 vs 29 MB (3523 modules vs ~981 loaded on demand), binaries 36 vs 12 MB, and carrier/arena pages ERTS never returns after the spike — the catalog load no longer contributes, because its heap dies with the warm-up process.
- **Boot PEAK is 0.6-0.9 GB RSS in every mode** (770 MB embedded release, 529 MB interactive release, 597 MB clean dev boot, 904 MB dev boot that also compiled 369 files), so any RSS sample taken in the first ~10 s reads far above the steady floor — a ">300 MB for the server" observation is usually the boot window or a mixed metric (OS RSS vs LiveDashboard/`:erlang.memory` ≈ 129 MB on the dev node).
- Runtime probe on a running node, no code change: the node name/cookie come from `[node] node_name`/`shortnames`/`cookie` (`genesis@127.0.0.1` longnames — NOT `~/.erlang.cookie`, NOT the release `releases/COOKIE`), so `elixir --name probe@127.0.0.1 --cookie <cookie> -e ':erpc.call(:"genesis@127.0.0.1", fn -> … end, [])'` runs arbitrary code remotely; read `:persistent_term.info/0` (`%{count, memory}`, cheap) and never `:persistent_term.get/0` (copies EVERY value and wedges the probe).
- ⚠️ Boot experiments must disable the sandbox (`[sandbox] mode = "disabled"` with an isolated `XDG_CONFIG_HOME` + `XDG_DATA_HOME`): `SandboxSlice.init/1` runs `systemctl --user stop evogit.slice`, and an agent shell itself runs INSIDE `evogit.slice` (`/proc/self/cgroup`), so booting the app from such a shell SIGTERMs its own BEAM at the end of boot (4× "SIGTERM received - shutting down"); `bin/<release> eval` starts no applications by itself — `Application.ensure_all_started/1` does, and it returns only after a full successful boot (`PeakHourEngine` config broadcasts arrive right after `AgentScheduler.init/1`); `eval` is INTERACTIVE, so to reproduce the real embedded boot by hand run `releases/<vsn>/elixir --erl "-mode embedded" --erl-config <root>/releases/<vsn>/sys --boot <root>/releases/<vsn>/start --boot-var RELEASE_LIB <root>/lib --vm-args <root>/releases/<vsn>/vm.args` with `RELEASE_ROOT`, `RELEASE_VSN`, `RELEASE_SYS_CONFIG=<root>/releases/<vsn>/sys` and `RELEASE_NAME=genesis_server` exported (`RELEASE_NAME` is the server-mode signal — without it `runtime.exs` raises on the missing `SECRET_KEY_BASE`; a `setsid`/background launch must also keep the process group out of `evogit.slice`).
- Migrations read blobs only on an UPGRADE: `000002` selects every legacy `id, opts` pair-array row in ONE result set (`priv/repo/migrations/20260815000002_data_normalization.exs:103`) and `000005` streams one legacy `result, archive_metadata` row at a time (`…000005_task_agent_archives.exs:437-456`); a current/fresh DB runs no migration body at all.
- Per-BEAM one-time and permanent: the migration `[{version, module}]` source is compiled once with `Code.compile_file/1` and memoized in `:persistent_term` (`store/boot.ex:354-380`) — a few hundred bytes plus ~0.1-0.3 MB of code area.
- Runtime (NOT boot) growth lives in the conversation, which the session owns in its own heap rather than in ETS: `:evogit_agent_summary` carries the summary projection only (no context), and its row is removed when the session ends, so a long-lived interactive session is the only place a large context is retained → `agent_scheduler/CONTEXT.md` + `agent/session/CONTEXT.md`.
- Boot-time side effects that cost CPU/processes but no memory: `BackgroundJobs.init/1` fires an async `Sandbox.Background.sweep_stale_units/0` (systemctl) on Linux, and `SandboxSlice.init/1` runs `systemctl --user stop evogit.slice` + a 100 ms sleep before creating the slice.

## Known Issues

- **Whichever process first touches the LLMDB catalog on a fresh BEAM pays the whole load in ITS OWN heap — so at boot that process must be a throwaway one.** `:llm_db` loads `priv/llm_db/snapshot.json` (11,693,807 B, 239 providers, 10,100 models) lazily on the first query (`deps/llm_db/lib/llm_db/catalog.ex:107-132`, `:207-210`), and the load decodes the JSON, builds 3 full model lists + 5 indexes and canonicalises the whole catalog for a `term_to_binary` digest (`loader.ex:208-228`, `:546-566`, `:282-297`) — all in the caller's heap; `:persistent_term` READS never copy (ERTS `persistent_term.erl` docs), only the load allocates, so the retained MBs are dead garbage awaiting a fullsweep, NOT live state. `EvoGit.CatalogWarmup` therefore loads it in a short-lived process (see "Boot memory profile"); a LONG-lived process that happens to be first (a scheduler booted without the warm-up, e.g. after a warm-up timeout) is the one shape to avoid.
- Dispatch resolves concrete selections and populates effective `llm_model`, `llm_generation_params` and configured `llm_context_window` once at admission; ordinary turns and compression consume those fields rather than re-resolving provider defaults each turn.
Cost recomputation prices the effective model and resolves the selected account's current pricing schedule, while metadata/pricing reads reuse the warm catalog; consumer contracts belong to `agent/` and `agent/compression/`.
- **Interactive and embedded boots now agree on scheduler memory** (`-mode embedded` used to leave ~47 MB of the catalog's dead heap resident in `EvoGit.AgentScheduler` for the whole BEAM lifetime, because an embedded boot never fullsweeps and `init/1` is its last allocation-heavy work). With the warm-up owning the load, every boot samples 29-66 KB there; the remaining embedded/interactive delta is preloaded code + carrier pages, not dead heap.
- **Process/thread exhaustion inside containers breaks git forks (EAGAIN).** In rootless podman every process shares the host user's UID, so the kernel's per-UID `RLIMIT_NPROC` (`ulimit -u`) spans container + host processes (every OS thread counts); when hit, `fork()` fails with `EAGAIN` — git prints "cannot fork() ... Resource temporarily unavailable" (e.g. in `git worktree add`). `WorktreeManager` survives (persistent init marker + re-monitoring) but the run loses agents to crash-retry. Prevention: raise the HOST user's nproc limit (`/etc/security/limits.conf` or `systemctl --user set-property user.slice TasksMax=infinity`); or `--ulimit nproc=65536:65536 --pids-limit -1` (`pids_limit = -1` + `default_ulimits` in `~/.config/containers/containers.conf`); or delegate the pids controller (`/etc/systemd/system/user@.service.d/delegate.conf` → `[Service] Delegate=cpu cpuset io memory pids`); verify via `ulimit -u` / `/sys/fs/cgroup/pids.max`; or reduce concurrency (`[scheduler] default_llm_max_concurrency`, per-profile `concurrency`).

## Constraints

- Part of an **umbrella project** — deps, artifacts and lockfile at the repo root; Elixir ~> 1.18; **Git CLI only** (no libgit2); no source at root — all code under `./apps/`; subdirectories follow Elixir convention (`./lib/evo_git/<subdir>/` ↔ `EvoGit.<Subdir>`).
- All git operations go through `EvoGit.Adapters.Git` (or `Shared.commit_files/4` → `EvoGit.sandbox_run`); no direct `System.cmd("git", ...)` in domain modules (exception: GitEnv's config reads).
- `remote_api.ex` and `remote_node.ex` are intentionally long cohesive RPC wrappers — do NOT split them; add new RPC functions there (`defnode` macro from `EvoGit.RemoteNode.Defnode` for identity-unwrap wrappers; per-function-fallback wrappers stay hand-written).
- Agents are transient modules using the `EvoGit.Agent` behaviour; framework state lives in ETS; execution happens in **isolated git worktrees** managed by `AgentScheduler.WorktreeManager`, never on the main working copy; agents commit before delegating subagents (auto-commit fallback enforced by the scheduler).
- **Three-level configuration** (`EvoGit.Config`): built-in defaults → user config (`~/.config/genesis/config.toml`, XDG) → runtime overrides; **no default model or username is hardcoded**.
- **Slot discipline**: agent LLM calls acquire/release account-shared slots via `AgentScheduler`, binding immutable `provider_profile_id` independently of concrete `model_spec` and effective `llm_model`.
The canonical `[[llm.providers]]` account owns concurrency/peak/backoff and shared auth/endpoint defaults; nested model/effort inventory does not create additional pools.
Legacy `llm.models`/flat model configuration and `model_id` remain compatibility inputs, while locked children inherit the full canonical selection and lock.
Configuration/persistence details belong to `config/`, selection/pool semantics to `agent_scheduler/`, and effective request/compression/cost consumers to `agent/`.
- **Task-scoped naming**: worktree dirs `worker_T<task_number>_A<task_local_id>`, branches `evogit-agent-T<task_number>-A<task_local_id>`; `task_id` = 16-char hex GUID, `task_number` = short integer from a linear scan of `.genesis/workers/`, used only for naming.
The owning repo root is derived from a WORKTREE PATH by the one literal split `String.split(path, "/.genesis/workers/", parts: 2)` (`agent_scheduler/worktrees.ex:34`, `repo_root_from_worktree/1`), whose only callers are `Dispatch.resolve_agent_repo_root_regular/2` (primary branch, `agent_scheduler/dispatch.ex:681`) and `WorktreeManager`'s monitor rebuild fallback (`worktree_manager.ex:828`); a path outside `workers/` is returned unchanged, so repo identity is inferred from path SHAPE.
Foreign-repo agents instead resolve their root by ID lookup in `spec.foreign_repos` (`dispatch.ex:684-689`) — one repo root + one worktree per agent, never a per-task mount table (detail: `agent_scheduler/`, `agent/`).
- **VCT is metadata, never a filesystem**: mount points are virtual and listable even when a mount's OS path is missing (that is what makes a project list portable across machines); the mount table is machine-local `vct_mounts` rows in `tasks.sqlite` and the global context's git repository is initialized lazily only while that context is non-empty.
- **Task persistence runs in `:evo_git`** — `Store` + `TaskRegistry` sit in the supervision tree, so the `genesis_server` daemon has full task history; a freshly-started Registry leaves orphaned `:running` rows to the lease sweep; test isolation pins `config :evo_git, :data_dir` to a UNIQUE per-run temp path in `config/test.exs`. Detail: `store/` + `task_registry/`.
- **Task Archive (opt-in)**: the `:archive` task opt → `runtime_opts` → `AgentSpec.opts` → `%EvoGit.Agent.State{}.archive`; each completing agent writes `refs/genesis/archive/T{task_id}-A{agent_id}-start`/`-final` + a usage git note + ONE `task_agent_archives` row STREAMING at completion (idempotent upsert on `(task_id, agent_id)`). No buffer, nothing in `%Result{}`/report; CRASH/FAILURE/ABORT writes NO row (usage LOST — a retry resets to `Usage.zero()`); Genesis Mode B shares one `task_id` → exactly 2 nil-parent rows; JSON round-trip caveats (string keys/timestamps; keys `input_cost`/`output_cost`/`total_cost`, never `cost`). Detail: `store/` + `agent_scheduler/`.
- **Distribution & releases** (EPMD-less via `-epmd_module Elixir.EvoGit.EpmdDist` + `-start_epmd false` in all `rel/vm.args.eex`; daemon on port 9000; releases `genesis`/`genesis_desktop`/`genesis_server` in the root `mix.exs`; prod-only `PORT`/`PHX_IP` → `[server] listen_port`/`listen_ip`, default 9999; zombie prevention via dynamic port + `EVOGIT_LIFETIME_PORT`): detail `lib/evo_git/CONTEXT.md` + root `./CONTEXT.md`.
- **SSH remote bootstrap** (remote commands are argv arrays, never quote-wrapped spawn strings — `run_ssh_command/4` `{:spawn_executable, ...}` + one argv element, wrapped by `sh_wrap/1` as `/bin/sh -c '<script>'` — no `/usr/bin/env`, no bash: stock NixOS lacks `/usr/bin/env` while `/bin/sh` is POSIX-mandated and is NixOS's `environment.binsh`; every remote script is POSIX sh and single-quote-free by construction, so fish/nushell/tcsh login shells pass the wrapper through untouched; override seam app env `:remote_shell`; the daemon itself is the `genesis_server` release and ALL of its lifecycle — systemd scope/unit, launchd plist, setsid fallback, readiness wait — is delegated to that release's `bin/genesis` CLI (`genesis remote start|stop|status|logs`), so Elixir only shells out `<launcher> remote status|stop|start --unit genesis-remote-<id>`; identity is verified from the node the CLI reports; NixOS patching happens only while the daemon is not running; best-effort `:copying_config`): detail `lib/evo_git/CONTEXT.md`.
- **Config caching is RAM-resident and event-refreshed** (`EvoGit.Config.Cache`: ONE `:persistent_term` snapshot per config dir holding user config + credentials + resolved map + validation errors + fingerprint, so `resolve/0,1` is a term lookup with no stat/merge/validate; `save_user_config/1`/`save_credentials/1` raise `EvoGit.Config.Watcher.notify_change/2` synchronously (total and bounded — a `nil`/dead/slow watcher falls back to the same guarded reload), which is the SAME handler the watcher's ~150 ms debounced `config.toml`/`credentials.toml` file event runs, bumping `generation` and broadcasting `{:config_reloaded, node, dir, generation}` on `"config"`; `RemoteAPI.reload_config/0` forces a re-read; the ACTUAL runtime cache is still AgentScheduler state, so a save does not apply scheduler settings; `RemoteConnections` does NOT auto-create `remote_connections.toml`): detail `config/`.
- **Genesis Mode B** (`Genesis.run_new_codebase/4`): Phase 1 `Agents.Architect` → Phase 2 `Agents.Manager` (second root from the architect's final commit; "Genesis Implementation Mode" prompt). Both share ONE `task_id`; usage and `agent_count` merge into a single `%Result{}` → `merge_and_report/3`; Architect fails → immediate error, Manager fails → architect's result as partial success; Mode A (`ContextExtractor`) uses one root. Detail: `runtime/`.
- **No `try/rescue` anti-pattern**: prefer `case`/`if`/`cond`/`with` + non-crashing variants (`Regex.compile`, `:persistent_term.get/2`, `Integer.parse/1`); justified only for `terminate/2` cleanup, centralized boundaries (`safe_llm_call/2`), `SystemCheck` diagnostics, `String.to_existing_atom/1` on untrusted keys, and `try/catch` around functions with no non-crashing variant (`Path.wildcard`). **Every remaining `try/rescue` MUST have a justifying comment.**
