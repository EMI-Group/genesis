# EvoGit — Core Runtime Application

## Intent
The `:evo_git` OTP application is an evolutionary software-development runtime: LLM agents create, analyze and modify codebases in isolated git worktrees, modeling a codebase as a **Context Tree** (spatial) and a **Phylogenetic Graph** (temporal) evolved through a DAG of commits.
Phases: **Genesis**, **Evolution**, and a repo-less **self-reflective** agent (`:reflect`), all on an LLM/tool slot-gated scheduler.
Task persistence (`EvoGit.Store`/`EvoGit.TaskRegistry`) lives here so the headless `genesis_server` daemon has full task history — detail: `lib/evo_git/CONTEXT.md`.

## PubSub Event Contract (event-driven dashboard)

All dashboard-visible state changes are PUSHED on `EvoGit.PubSub` (Phoenix.PubSub PG2, cluster-aware); every message carries the emitting `node` as its final element and subscribers MUST ignore messages whose node ≠ their own for node-local state. Emitter detail: `task_registry/CONTEXT.md`.

| Topic | Message | Emitted by | Notes |
|---|---|---|---|
| `"tasks"` | `{:task_updated, task_id, status, node}` | TaskRegistry mutations; `Runtime.Helpers.notify_finalizing/1` | status = the task's CURRENT status (`:pending \| :running \| :finalizing \| :cancelling \| :completed \| :failed \| :cancelled`), `nil` for review-status/metadata updates; no broadcast on stale/no-op/missing-row updates; heartbeat silent; **`notify_finalizing/1` is the ONE broadcast fired BEFORE its persist**, all others AFTER the store write |
| `"tasks"` | `{:task_deleted, task_id, node}` | `clear_finished_tasks` (one per id), `delete_task` | **`Cleanup.cleanup_expired_tasks/1` deletes rows with NO broadcast** |
| `"agents"` | `{:agent_registered, agent_id, summary, node}` · `{:agent_updated, agent_id, changed_fields, node}` · `{:agent_removed, agent_id, node}` · `{:agents_updated, node}` | `AgentScheduler.PubSub` helpers (Throttle flush or immediate fallback) | `:agent_updated` deltas strip `:context`; `message_count` is prepended so consumers detect history changes without re-transferring `get_agent_history/1` |
| `"scheduler_config"` | `{:scheduler_config_updated, node}` | `AgentScheduler.broadcast_config_updated/0` | |
| `"system"` | `{:system_sample, node, seq, sample}` | `EvoGit.SystemSampler` every 3s | keys EXACTLY `llm_used, llm_waiting, tool_used, tool_waiting, llm_capacity, tool_capacity, agents_total, agents_running, agents_blocked, agents_waiting, agents_pending, scheduler_alive, llm_slots`; `llm_slots = %{pool_id => %{used, waiting, capacity}}` = REAL account-pool occupancy (legacy profile ids on compatibility paths) (`get_llm_slot_status/0`; `%{}` when down), while `llm_used`/`llm_waiting` stay running/blocked proxies; seq monotonic per sampler |
| `"guides"` | `{:guide_updated, guide_id, %{message, page, selector, dismissible}, node}` | Guide capability (`elixir_eval` write tier) or CLI guide command | transient guide push; best-effort |

## Provider Profiles & Concrete Model Selections

Canonical config uses `[llm] default_provider_profile` to select an account in `[[llm.providers]]`, with the first account used only when no selector is supplied.
Each provider profile owns a stable account `id`, `provider`, shared authentication (`auth_mode`, `api_key_env_var` or `oauth_file`), endpoint (`base_url`/provider options), `concurrency` and peak/off-peak schedule for every model and reasoning effort in its nested ordered `models` inventory.
OAuth paths are account settings, never a global `[llm] oauth_file`, and `LLM.profile_generation_params/1` remains the single generation/auth/provider-constraint assembly boundary.
Provider generation/context defaults and ordered `reasoning_efforts` may be overridden by nested model settings, with explicit task effort taking final precedence.
`default_model` selects a model (first model when absent), while optional `default_reasoning_effort` is never inferred from effort order.
`Schema.provider_profiles/1` returns canonical STRING-keyed accounts, `model_selections/1` enumerates ordered model/effort choices without reading credentials or metadata, and `resolve_model_spec/2` validates a default, account id or explicit selection.
A task `model_spec` is a STRING-keyed identity map with `provider_profile_id`, `model` and optional `reasoning_effort`, not a ReqLLM identifier, provider profile or secret-bearing generation parameters.
The schema's resolved `model_spec` is instead the ReqLLM-ready qualified string or endpoint-override map; dispatch stores it as effective `llm_model` alongside `llm_generation_params`, configured `llm_context_window` and the complete canonical selection.
Explicit invalid selections fail closed before registration, and locked parent selections override child picks and scripts with the entire account/model/effort identity rather than only a legacy id.
Unlocked children inherit the effective parent selection as `default_model_spec`, leaving per-spawn scripts in control; dispatch and inheritance contracts belong to `agent_scheduler/` and `agent/`.
Legacy `[[llm.models]]`, flat `[llm] model` and legacy selection ids remain supported, with one-for-one account normalization preserving ids and separate account boundaries even for identical providers/models/endpoints.
Nonempty canonical providers take precedence over stale legacy fields, and saving canonical config strips legacy inventory and flat mirrors rather than maintaining two sources of truth.
Normalization, default/duplicate/effort errors, runtime-profile compatibility and generation/auth assembly details belong to `config/` and `config/schema/`.
CLI `--provider-profile <id> --model <model> [--reasoning-effort <effort>]` validates before enqueue and submits task `model_spec` with `model_id_locked: true`; no selection flags means Auto and omits both keys.
Legacy `-m` accepts profile ids, `id:provider:model` and matching qualified/bare inventory models, while `genesis setup` writes canonical accounts/defaults and preserves unrelated accounts, shared settings and nested overrides; details belong to `cli/` and `lib/evo_git/CONTEXT.md`.
`Config.config_status/0` combines model/credential presence with validation errors, so an invalid default selector is unhealthy even when another account has usable credentials; account-specific API-key checks never borrow a different account's custom key.
`SystemCheck` resolves default/account/task selections through Schema before testing the effective request, while retaining raw ReqLLM identifier compatibility; health and credential boundaries belong to `config/` and `lib/evo_git/CONTEXT.md`.
Compression consumes the effective configured context window, never catalog limits, and cost prices effective `llm_model` with the selected provider account's peak/off-peak period; details belong to `agent/` and `agent/compression/`.

## Custom Agents & Model Selection

User-defined agents live in `<config_dir>/agents.toml` with name/prompt, read/read_write authority, delegation level, optional turn cap, tools/subagents whitelists and optional canonical `model_spec` (legacy `model_id` remains a fallback).
`CustomAgents` normalizes selection keys and effort values, rejects structurally malformed definitions with `:invalid_model_spec` on save and leaves account/model existence checks to dispatch.
Tools whitelists are alias-aware and may include custom tools; an absent whitelist exposes built-ins only, while `CustomAgents.reload/0` invalidates agent/tool caches.
`ModelSelector` evaluates the administrator's compile-once `fn agent -> <script> end` body per spawn and accepts a canonical account/model/effort map or legacy profile id, with nil/empty/false meaning fallback and script errors logged without crashing.
Dispatch priority is explicit task or inherited locked selection → script → canonical definition/inherited `default_model_spec` → legacy definition/inherited `model_id` → configured default.
Invalid canonical script selections fail closed, while unknown legacy script ids retain default fallback; unlocked inheritance does not set the lock and custom `max_turns` still overrides scheduler turn caps.
`Runtime.Helpers.resolve_root_agent/2` validates `:agent`, forwards canonical definition defaults without locking them, and builds the custom root whose Runner installs `:custom_agent_id`.
Definition schemas and script contracts belong to `custom_agents/`, runtime spec construction to `runtime/`, and selection/error/inheritance details to `agent_scheduler/` and `agent/`.

## Multi-Modal Content (objective, tool results, injected messages)

Media (images/audio) rides LLM content parts at THREE sites; wire contract `EvoGit.Attachments` (`lib/evo_git/attachments.ex`), structured tool output `EvoGit.Agent.ToolOutput` (`agent/tool_output.ex`).

- **Shape**: STRING-keyed `%{"type" => "image"|"audio", "name" => <basename>, "media_type" => <IANA>, "data" => <base64 ASCII>}`; base64 is MANDATORY at every data-plane boundary (task opts, pending-message queue) because `Store.Codec` Jason-encodes whole opts and raw binaries abort Jason; decoding happens ONLY at materialization (`Attachments.to_content_parts/2`: image → `ReqLLM.ContentPart.image(raw, media_type)`, audio → a `:file` part), always a plain `[ContentPart.text(text) | media parts]` list, NEVER `ReqLLM.ToolResult`; `Attachments.message/1` is the ONE normalizer.
- **Caps**: ≤ 4 attachments per message, each ≤ 15 MiB RAW bytes (`EvoGit.Attachments` attributes are the single core source), per task opt AND per tool output; malformed payloads raise a descriptive `ArgumentError`.
- **Site 1 — `:attachments` task opt (root-only)**: ROOT agent's FIRST user message only (`ContextBuilder.build_initial_messages/4`, gated on `parent_id == nil` AND non-empty; subagents never inherit); Genesis Mode A, Mode B both roots and the Evolve root receive it, Reflect never; validated by `RuntimeOpts` → `Attachments.validate/1`.
- **Site 2 — tool results (any agent, any turn)**: `Tools.execute/5` may return `String.t() | ToolOutput.t() | {:error, reason}` (`ToolOutput` = `%{text, attachments}`, `new/2`/`wrap/1`/`with_text/2`/`to_content_parts/1`). `agent/tool_dispatch.ex` is the SOLE **wrap boundary**: sanitize/truncate + hint appenders hit the TEXT component only (`OutputSanitizer`/`TruncationFeedback`/`DelegationHints` keep a binary contract), media is re-wrapped; error/timeout/crash paths stay plain strings. Detail: `agent/`.
- **Site 3 — injected user messages (mid-run, NO root gate)**: `AgentScheduler.send_user_message/2` / `RemoteAPI.send_agent_message/2` / `RemoteNode.send_agent_message/3` accept `String.t() | %{text:, attachments:}`; `Store.append_pending_user_message/2` stores shape-for-shape (legacy binary VERBATIM); `Runner.drain_and_inject_user_messages/1` materializes via `ContextBuilder.build_injected_message/2`. Detail: `agent_scheduler/`.
- **Invariants / limits**: a plain-string tool result and a legacy string pending message behave BYTE-IDENTICALLY to pre-media behavior (`%ReqLLM.Message{}` struct-equality regressions in `test/evo_git/agent/tool_output_pipeline_test.exs` + `tool_output_integration_test.exs`). ## Multi-Repo Read-Write Foreign Repos

Foreign repos may be **writable** — still ONE primary repo + one final report per task; foreign modifications are tracked but NEVER merged back by the task (the review page merges/rejects).

- **Data model** (`Core.ForeignRepo`): `writable: boolean()` (default `false`) + `base_sha: String.t() | nil` (`nil` = foreign HEAD); `new/*`/`normalize/1` handle STRING-keyed Codec maps; `ProjectConfig` accepts both; `-R <id>:<path>` stays READ-ONLY (TOML-only to mark writable) and Windows drive letters are NOT split on `:` (`CLI.Parser.split_foreign_repo_spec`).
- **Spawn gate** (`Subagents.validate_spatial_contract_for_spec/3,4`; 3-arity = root depth 0): read-only cross-repo spawns UNRESTRICTED at any depth; `:read_write` cross-repo spawns need `writable: true` (else `{:error, {:foreign_repo_read_only, msg}}`), are **root-only** (depth 0, else `{:error, {:foreign_repo_write_not_root, msg}}`) and **one per batch** (`spawn_validated_subagents/5` threads `writable_accepted`; 2nd+ → `{:error, {:foreign_repo_write_serialized, msg}}`); same-repo spawns INSIDE a foreign repo are UNRESTRICTED. `format_subagent_result/1` surfaces all three verbatim as `"Error: #{msg}"`; the role comes from id-matching `spec.foreign_repos` (Runner puts `Process.get(:foreign_repos)`), NEVER the path; unknown ids → read-only.
- **Tool gating**: `Tools.execute/5` chains `maybe_block_read_only_foreign_repo/5` after `maybe_block_repo_less/5` — blocks every `@write_tools` entry (incl. `run_git`); `Shared.validate_file_scope/3` rejects write targets inside one; `Tools.read_only_schemas/0` = read tools + Context write/edit + ShellTool + `WebFetch` + `Lsp` only when `Config.lsp_enabled?/0`; there is no `curl` tool.
- **Roots + report** (`Runtime.Helpers.merge_and_report/3,4`): writable repos get worktree roots like the primary; ONE branch name per task reused across all (`Git.create_branch(repo.root, branch_name, sha)`; failure logs + `branch_name: nil`). Report gains top-level **`repos: %{repo_id => %{commit_sha, branch_name}}`** (STRING keys): `"primary"` always, each writable repo that committed, read-only ABSENT; top-level `commit_sha`/`branch_name`/`result` stay the PRIMARY's. Source `Result.foreign_repo_commits`, rolled up by `Lifecycle.inject_foreign_repo_commits/2` + `store_sub_result/3` (child-wins), read via `AgentScheduler.get_foreign_repo_commits/1` (`%{}` on missing sched_meta).
- **Review + scoping**: each writable repo carries an `evogit-agent-*` branch at `repos[repo_id].commit_sha`; `Review.merge_branch/2,3` + `reject_branch` are per-repo-path; `maybe_init_repo/3` (required `primary?`) wipes `.genesis/workers` + `clean_orphaned_branches` ONLY for the primary, and `run_init_script` stays primary-only.
- **Persistent foreign worktree (read view)** at `<root>/.genesis/foreign_repos/<id>` (`ForeignRepo.worktree_path/1`), reset at task start (`ForeignWorktree.ensure_all/1`), advanced by `Agent.Runner.run/3` `try/after` → `sync_from_agent/0`; outside `.genesis/workers/`, never moves MAIN HEAD, kept at task end — detail: `agent_scheduler/`.
- **Validation + merge seeding**: `load_foreign_repos/2` validates up front (exists, is a git repo, non-nil `base_sha` resolves) → descriptive `ArgumentError`; `SubagentProcessing` returns `{:error, {call, 0, "Error: foreign repository path does not exist or is not a git repository: <path>"}}`; `resolve_foreign_repo_starting_commit/2` = `base_sha` else foreign HEAD; subagent phylo precedence = task `base_sha` → tracked `foreign_repo_commits` → foreign HEAD. `apply_merge_context/4` carries `:foreign_repos` and overrides each `base_sha` from the prev task's `repos[repo_id]["commit_sha"]`; `apply_resume_context/3` keeps `:foreign_repos` and overrides per-repo base_sha in BOTH branches; shared `TaskRegistry.PrevTaskRepos`. Detail: `task_registry/`.
- **Prompts**: `:read_write` foreign spawns are ROOT-ONLY + ONE-AT-A-TIME; static prompts + `PromptFragments.writable_foreign_repo_clause/0` are role-agnostic and tell NESTED agents to report upward, while each agent's role is stated in its FIRST-USER context by the pure `ContextBuilder.build_authority_section/1` (root signal `AgentState.parent_id == nil`; `""` for repo-less and single-repo tasks). Detail: `runtime/` + `agent/` + `core/`.

## Self-Reflective Agent (repo-less)

A **repo-less** Assistant with no repository or worktree uses tiered Elixir evaluation to inspect runtime state, control tasks and show transient guides.

- **Task type**: `:reflect` — `TaskExecutor.execute_task(:reflect, opts, task_id)` runs `Runtime.SelfReflective.run(opts ++ [task_id: task_id])`; codec atom `:reflect`, mode `"reflect"`; opts `objective`, optional `model_spec`/legacy `model_id`, `model_id_locked`, `source_root` and `task_id`, **NO `:path`** (the executor skips `RuntimeOpts.build_common_runtime_opts`, which `Keyword.fetch!`s `:path`); result `{:ok, %{result: <summary>, commit_sha: nil, branch_name: nil, tag: nil}}`.
- **Plumbing**: `spec.opts[:repo_less] = true`, `phylo_node` nil; `Dispatch.resolve_agent_repo_root/2` short-circuits to `resolve_repo_less_root/0` (`SelfReflectiveSource.reference_path/0` → `File.cwd!()` → `"[system]"`); the Runner skips `create_worktree_for_agent`, sets `Process.put(:repo_less, true)`, `commit_pending_in_worktree/0` no-ops; **write guard** `Tools.execute/5` blocks `@write_tools` when `Process.get(:repo_less)` and `available_tools/0` omits them.
- **Modules**: `Agents.SelfReflective` is the repo-less Assistant (`agent_type :read`, `delegation_level :low`, `subagent_modules []`) exposing source-reading tools (`read`, `rg`, `glob`, `list_dir`, context/history readers), `web_fetch`, config-gated `web_search` and tiered `elixir_eval`, but no shell, file writes or `run_command`.
Read raw implementation before calling an explicitly admitted real API; inspecting source never authorizes an unlisted function.
A reply with no tool calls ends the run; `Runtime.SelfReflective` owns source resolution and spec construction, and `SelfReflectiveSource` owns the managed source clone.
- **One `elixir_eval` tool**: read/write use Dune with explicit real module/function/arity grants so the Assistant can inspect source and call admitted task/detail/agent/config/status APIs directly, while existing projected Read/Write facades remain optional conveniences.
Write requires exact-code user approval and admits task lifecycle operations, runtime scheduler updates, persistent `Config.save_user_config/1` and explicit `AgentScheduler.RemoteAPI.reload_config/0`; saving replaces the whole config without automatic reload, so preserve unrelated settings with a read–modify–save and distinguish persisted settings from runtime overrides.
Sudo separately requires explicit approval for unrestricted native Elixir with full VM authority, not a security sandbox, and refusals never trigger automatic escalation.
Each call has fresh bindings, fail-closed Assistant-owner authorization and bounded execution/output; direct calls preserve actual return contracts and may expose sensitive/heavy data, but unlisted MFAs, wrong arities, arbitrary native APIs and the `CommandShell` registry remain unavailable in read/write.
Evaluator, capability, approval and cleanup details → `lib/evo_git/agent/tools/elixir_eval/CONTEXT.md`.
- **CLI + chat readiness**: `genesis reflect "<objective>"` accepts the shared provider/model/effort flags or legacy `-m`, with explicit choices locked and Auto left unlocked (`-f` reads a prompt file).
`:running → :completed/:failed/:cancelled` emits NO `:finalizing` broadcast; the root has `parent_id: nil` and a matching `task_id` (filter `list_agents/0`).
Live content is FETCH: watch `message_count` / `{:agents_updated, node}` then re-fetch `get_agent_history/1`; **history is wiped on completion** (`recycle_agent` deletes the ETS rows).
The persisted artifact is `task.result`, with no `resume_from`; tests include `reflect_tools_test.exs`, `self_reflective_source_test.exs`, `self_reflective_test.exs`, repo-less scheduler/tool-dispatch cases and `task_executor_reflect_test.exs`.

## LLM Concurrency & Slot Gating

LLM resource pools are keyed by immutable `provider_profile_id`, so every concrete model/effort selection in an account shares concurrency and exhaustion backoff, while distinct account profiles remain isolated.
Historical scheduler fields such as `model_concurrency` and `llm_backoff_until` retain their names but use account ids on the canonical path and legacy profile ids on compatibility paths.
`AgentScheduler.with_llm_slot/2` blocks in a purgeable `:infinity` call, capacity-zero requests enqueue, and `default_llm_max_concurrency` is a floor/fallback rather than a global cap, preserving explicit zero pauses.
Runtime updates preserve live holders/waiters/backoff, global pause gates pending grants, and resume/capacity changes sweep eligible waiters without evicting in-flight holders.
Rate-limit and insufficient-balance failures report growing account-shared backoff through `AgentScheduler.report_llm_error/3`; agents park in the slot queue rather than sleeping, preserving cancellation responsiveness.
`ReqLLMPool` sizes HTTP capacity from account concurrency once per account, never multiplying it by nested model/effort choices, and runtime reconciliation remains grow-only.
Slot maps, retry policy, reload/legacy behavior and pause contracts belong to `agent_scheduler/` and `agent/`; Finch sizing and peak-engine integration belong to `lib/evo_git/CONTEXT.md`.

## Peak/Off-Peak Hour Concurrency Scheduling

Provider accounts own `peak_concurrency`, `peak_hours`, `off_peak_days` and `timezone`, with `peak_concurrency = 0` a hard pause shared by all their models/efforts and exempt from the default-concurrency floor.
`EvoGit.PeakHours` remains the single source of truth for half-open/overnight/day-scoped windows, off-peak-day precedence, local/IANA wall clocks, validation and transition math.
`PeakHourEngine` prefers canonical provider profiles, falls back to legacy model profiles only when canonical accounts are absent, and applies one floored concurrency entry per account with explicit zero and peak exemptions preserved.
Account TOML/validation contracts belong to `config/`, engine/RPC integration to `lib/evo_git/CONTEXT.md`, and timer, queue and floor details to `agent_scheduler/`.

## Agent Loop Control Flow + Graceful Task Cancellation

**Loop injection point**: `Runner.loop/1` is the top of each turn (after `compress_if_needed`/`check_limit_warnings`, before `do_turn`'s LLM call); `AgentState.pending_user_messages` (`[String.t()]`) is the cross-process writable surface (written via `Store.append_pending_user_message/2`), drained by `drain_and_inject_user_messages/1` → turn-tagged user messages → `sync_context_to_ets/2`.
API chain: `EvoDash.NodeContext` → `RemoteNode.send_agent_message/3` → `RemoteAPI.send_agent_message/2` (guards `{:error, :scheduler_not_started}` when `:evogit_agent_state` is undefined) → `AgentScheduler.send_user_message/2` → `Store.append_pending_user_message/2`, returning `:ok | {:error, :not_found}`; ⚠️ RemoteNode's local path nests the inner error (`{:ok, {:error, :not_found}}`), so the dashboard falsely reports success for a missing agent. Every append/drain emits a `{:agent_updated, ..., [pending_user_messages: [...]]}` delta but nothing renders it. Detail: `agent/` + `agent_scheduler/`.

**Two cancellation actions** (node-aware via `RemoteNode.cancel_task/2` + `force_kill_task/2`):
- **Graceful cancel** (`TaskRegistry.cancel_task/1`): `:pending` → immediate `:cancelled`; `:running` → `:cancelling` + `AgentScheduler.begin_graceful_cancel/1` (`:evogit_cancelling_tasks` marker + per-agent cancel message via `Store.append_pending_user_message/2` (NOT `send_user_message` — self-call deadlock) + `AgentState.cancel_requested`). The Runner drains it right after user messages (`maybe_enter_cancel_grace/1`) and enters cancel-grace with a **3-turn budget** (`LoopState.grace_turns_remaining`; `maybe_recovery_auto_commit` first); final status persists `:cancelled` WITH result/usage/archive **preserved**. `:cancelling` is non-terminal + idempotent (`clear_finished_tasks` skips it, reconciliation → `:cancelled`) and blocks new root spawns (`run_agent` → `{:error, :cancelled}`).
- **Force kill** (`force_kill_task/1`): kills all agents + the wrapper and persists **`:failed`** with result nil'd, from `:running` and `:cancelling`; `:cancelled` means ONLY gracefully-cancelled tasks.
- **Dashboard**: Cancel button (`[:pending, :running]`) → warning modal → `confirm_cancel_task`; force kill in the card dropdown (`[:running, :cancelling]`, "Danger zone") → `confirm_force_kill_task`; `:cancelling` renders violet and is reviewable (ReviewLive treats `:cancelled` like `:completed`). Detail: `task_registry/` + `agent_scheduler/`.

## Update-Timing Safety

No restart/update machinery exists in `:evo_git` (zero `System.restart`/`:init.restart`/`:init.stop`, no signal handlers, no checkpointing on exit); graceful stop comes from `:evo_dash` (`DesktopQuit.default_stop/0`, SystemLive Stop — both `System.stop/0`), and the Rust shell NEVER sends SIGTERM (watchdog uses SIGKILL). `bin/<release> stop`/`restart` need `RELEASE_DISTRIBUTION != none` + a resolvable `RELEASE_NODE`, so the non-distributed desktop sidecar must be stopped from within. Pre-restart mechanism = **graceful cancel** (3-turn grace, NOT wall-clock bounded — each grace turn is a full LLM+tools cycle, so wait for a terminal status with a generous timeout, or force-kill).
Idle-detection API: `TaskRegistry.list_task_ids(statuses \ [])` / `list_tasks_summary(statuses \ [], since \ nil)` / `list_tasks_changed_since/1` / `get_task/1` (+ RemoteAPI/RemoteNode mirrors); in-flight set `[:running, :pending, :finalizing, :cancelling]`.
Task status lives ONLY in SQLite (`tasks.status`); scheduler ETS holds live-agent state and dies with the app. Lease: `@lease_duration` 120s, heartbeat every 60s renews `[:running, :pending, :cancelling]` (not `:finalizing`); one-shot `:lease_sweep` at `@sweep_after` 150s marks orphaned `:running` → `:failed` ONLY when the lease is invalid AND no live sched_meta agents (never reschedules). Startup reconciliation: `:finalizing` → `:failed`, `:cancelling` → `:cancelled` (result preserved), `:running` untouched. **No auto-resume** — resume is a NEW `:evolve` task via the Review page (`resume_from` → `ResumeContext`; `review_status: :continued` is a persisted marker only). Detail: `agent_scheduler/` + `task_registry/`.

## Backend Boot Profile (desktop sidecar readiness)

Boot work in `:evo_git` is CONSTANT-COST: nothing keyed to the release version or install path; no lockfile/`.genesis/` marker/cache verification/release-tree read at start.
Ordered `EvoGit.Application.start/2` work: (1) create the 4 ETS tables; (2) `Distribution.maybe_enable/0` (logs + returns `{:error, _}`, never raises); (3) `Calendar.put_time_zone_database(Tz.TimeZoneDatabase)`; (4) children in order: PubSub → Throttle → CommandApproval → RemoteConnection Registry/Supervisor → **`Store`** → TaskRegistry Registry → TaskRegistry → WorktreeManager → AgentGroupSupervisor (Task.Supervisor → **`EvoGit.CatalogWarmup`** → AgentScheduler) → PeakHourEngine → SystemSampler, plus SandboxProcessRegistry + SandboxSlice on Linux. `CatalogWarmup` sits IMMEDIATELY BEFORE the scheduler by design (it returns `:ignore`, so it is never a running child) so the LLM model catalog is already loaded when `AgentScheduler.init/1` first reads it.
The ONE potentially slow child is `Store`, whose `init/1` runs the migrations before any read/write (`Store.Boot.start_dynamic/2`); `TaskRegistry.init/1` then does a synchronous `Store.select_running_lease_info/1`; everything else is O(1). Per-migration cost: `store/`.
Catalog resolution can allocate a large transient heap on a fresh BEAM, so `EvoGit.CatalogWarmup` runs immediately before the scheduler and warms `Schema.effective_model_profiles/1`'s per-account default-model runtime projection in a throwaway process.
The scheduler then boots through `State.from_config/2` with the canonical selection snapshot and account-shared resource maps, reading the already-loaded catalog cheaply; boot allocation measurements and wiring belong to `lib/evo_git/agent_scheduler/CONTEXT.md` and `lib/evo_git/CONTEXT.md`.
**Boot-fatal paths** (a child EXIT ⇒ "Genesis backend unavailable"): an unwritable/missing data dir (`File.mkdir_p!` raises), a failed repo open (`{:stop, {:failed_to_open_sqlite, reason}}`), or ANY raise out of the migration run (baseline post-condition `Ecto.MigrationError`, bad `tasks` shape, `SQLITE_BUSY`, corrupt file) — uncaught in `init/1`; with `start_permanent: Mix.env() == :prod` a terminating permanent app takes the whole VM down.
`Store` opens with `journal_mode: :wal` + `default_transaction_mode: :immediate` + `busy_timeout: 30_000` (a locked `tasks.sqlite` stalls a statement up to ~30 s) and WAL needs `-wal`/`-shm` sidecars on a shared-memory-capable filesystem (a network/UNC data dir can fail the open). No boot-time self-exit exists in `:evo_git`.
**Observability**: the boot path emits no phase logs of its own — only Ecto.Migrator's lines (`Store.Boot` has ZERO Logger calls), `Config.resolve/0` warnings, `PeakHourEngine: starting — watched profiles: …` + `wakeup reason=:boot`/`next wakeup in` pair, and Linux `SandboxSlice` warnings.
**Boot lines CAN repeat inside ONE OS process**: a `Store` crash (`:one_for_one` child of `EvoGit.Supervisor`) re-runs `init/1` → the migration lines, and `System.restart/0` re-boots all applications INSIDE the running node (emulator not restarted) — its only caller is the dashboard System page (`system_live.ex`; remote variant `EvoDash.NodeContext.restart_remote/1`). `EvoGit.Supervisor`/`EvoGit.AgentGroupSupervisor` declare no restart intensities (OTP defaults 3/5s); exceeding them terminates the supervisor and, `evo_git` being `:permanent`, the node goes down — the Rust watchdog respawns a NEW OS process. The log handler appends (`type: :file` + rotation, no truncate-at-boot), so N boot sequences cannot distinguish in-place restarts from OS processes; `<data_dir>/logs/backend.log` is configured in the ROOT `config/runtime.exs` (rotating 10 MB × 5) and nothing in `:evo_git` writes/truncates/rotates/deletes under `<data_dir>/logs/`.
**No first-start-of-a-NEW-release-dir delta exists on the Elixir side** — per-BEAM one-time costs recur on EVERY boot. Port resolution / orphan prevention: root `./CONTEXT.md`.
### Boot memory profile (what a boot can actually allocate)
- The five app-owned ETS tables are created EMPTY in `EvoGit.Application.start/2` (`application.ex:20-62`); the only boot-time insert is ONE `{registry_name, store}` row in `:evogit_task_registry_stores` (`task_registry.ex:393`).
- No boot child loads task rows into its state: `TaskRegistry.init/1` reads only `select_running_lease_info/1` (id/status/lease_expires_at) and folds the list away (`task_registry.ex:413-446`), and `AgentScheduler.init/1` reads NO SQLite at all (`agent_scheduler.ex:526-658`).
- The SQLite page cache is per-connection and LAZY: `EvoGit.Repo.start_opts/0` sets `cache_size: -8_000` (8 MiB/connection, ~2048 × 4 KiB pages) × `Boot.default_pool_size/0` = 6, i.e. a ~48 MB STEADY-STATE ceiling but ~0 at boot (the boot leg touches only `sqlite_schema` + `schema_migrations`) → `store/` + `repo.ex`.
- The ONE eager multi-megabyte boot allocation is the LLMDB catalog, and it lands in a THROWAWAY process: `EvoGit.CatalogWarmup` (a `:ignore` child of `EvoGit.AgentGroupSupervisor` immediately before the scheduler) resolves the configured profiles in its own short-lived process → `Schema.llm_generation_params/1` → `model_metadata/1` → `ReqLLM.model/1` → `LLMDB.ensure_loaded!` decodes the 11.7 MB packaged snapshot (`deps/llm_db/priv/llm_db/snapshot.json`, ~10k models) into `:persistent_term` (`deps/llm_db/lib/llm_db/catalog.ex:91-95`); the decode's transient heap dies with that process, and the catalog itself is retained for the whole BEAM lifetime.
- That load requires the provider ATOM to exist already (`Schema.LLM.catalog_key/1` uses `String.to_existing_atom`, rescuing to nil), so the FIRST `llm_generation_params/1` call merely CREATES it via `LLMConstraints` → `provider_from_model/1` (`String.to_atom`) and a LATER call in the same warm-up run then loads the catalog — deterministic for any model written in the documented `"provider:model"` form, and skipped entirely when no model is configured (the warm-up is inert: seam installed or no profile carries a `model`) → `config/schema/CONTEXT.md`.
- Measured PROOF, same 4-profile config / isolated data dir / `[sandbox] mode = "disabled"` / `-mode embedded` (the release and `genesis start` path), sampled in-node from the running scheduler: WITH the warm-up, `EvoGit.AgentScheduler` reads **28.8 KB at t=0 (boot finished), 66.3 KB at t=3-30 s and 53.8 KB at t=90 s** (13.9k reductions at t=0; `:erlang.memory(:total)` ≈ 225 MB, processes ≈ 40 MB), and the endpoint is up ~2.1 s after the first boot log line. The SAME harness against the pre-warm-up build retained **94,804.2 KB (92.6 MB) at every sample out to t=90 s** (189.0M reductions; `:erlang.memory(:total)` ≈ 318 MB, processes ≈ 136 MB, settled RSS 492 MB vs 396 MB) — i.e. the scheduler's heap is now KB-scale in interactive AND embedded boots, and boot time is unchanged → `agent_scheduler/CONTEXT.md`.
- **Steady-state OS memory by launch method** (same 4-profile config, fresh isolated data dir, one `GET /` at t≈15-25 s): embedded release ≈ **RSS 395-396 MB / PSS ≈ 329 MB** from ~20 s on with boot peak **VmHWM ≈ 770 MB** (`:erlang.memory(:total)` ≈ 225 MB: processes 40, system 184, code 81; pre-warm-up v0.13.12 read RSS 465-492 MB / `:total` ≈ 296 MB, the ~92 MB delta being the scheduler's retained dead heap plus its carrier pages).
- **Interactive vs embedded dominates, NOT dev-vs-prod**: the SAME release booted interactive settles at RSS ≈ 177 MB / `:erlang.memory(:total)` ≈ 122 MB (code 27 MB), and a fresh compiled `mix phx.server` (interactive, with watchers) settles at RSS ≈ 200 MB / PSS ≈ 166 MB. The embedded gap (≈ +174 MB BEAM) is preloaded code 81 vs 29 MB (3523 modules vs ~981 loaded on demand), binaries 36 vs 12 MB, and carrier/arena pages ERTS never returns after the spike — the catalog load no longer contributes, because its heap dies with the warm-up process.
- **Boot PEAK is 0.6-0.9 GB RSS in every mode** (770 MB embedded release, 529 MB interactive release, 597 MB clean dev boot, 904 MB dev boot that also compiled 369 files), so any RSS sample taken in the first ~10 s reads far above the steady floor — a ">300 MB for the server" observation is usually the boot window or a mixed metric (OS RSS vs LiveDashboard/`:erlang.memory` ≈ 129 MB on the dev node).
- Runtime probe on a running node, no code change: the node name/cookie come from `[node] node_name`/`shortnames`/`cookie` (`genesis@127.0.0.1` longnames — NOT `~/.erlang.cookie`, NOT the release `releases/COOKIE`), so `elixir --name probe@127.0.0.1 --cookie <cookie> -e ':erpc.call(:"genesis@127.0.0.1", fn -> … end, [])'` runs arbitrary code remotely; read `:persistent_term.info/0` (`%{count, memory}`, cheap) and never `:persistent_term.get/0` (copies EVERY value and wedges the probe).
- ⚠️ Boot experiments must disable the sandbox (`[sandbox] mode = "disabled"` with an isolated `XDG_CONFIG_HOME` + `XDG_DATA_HOME`): `SandboxSlice.init/1` runs `systemctl --user stop evogit.slice`, and an agent shell itself runs INSIDE `evogit.slice` (`/proc/self/cgroup`), so booting the app from such a shell SIGTERMs its own BEAM at the end of boot (4× "SIGTERM received - shutting down"); `bin/<release> eval` starts no applications by itself — `Application.ensure_all_started/1` does, and it returns only after a full successful boot (`PeakHourEngine` config broadcasts arrive right after `AgentScheduler.init/1`); `eval` is INTERACTIVE, so to reproduce the real embedded boot by hand run `releases/<vsn>/elixir --erl "-mode embedded" --erl-config <root>/releases/<vsn>/sys --boot <root>/releases/<vsn>/start --boot-var RELEASE_LIB <root>/lib --vm-args <root>/releases/<vsn>/vm.args` with `RELEASE_ROOT`, `RELEASE_VSN`, `RELEASE_SYS_CONFIG=<root>/releases/<vsn>/sys` and `RELEASE_NAME=genesis_server` exported (`RELEASE_NAME` is the server-mode signal — without it `runtime.exs` raises on the missing `SECRET_KEY_BASE`; a `setsid`/background launch must also keep the process group out of `evogit.slice`).
- Migrations read blobs only on an UPGRADE: `000002` selects every legacy `id, opts` pair-array row in ONE result set (`priv/repo/migrations/20260815000002_data_normalization.exs:103`) and `000005` streams one legacy `result, archive_metadata` row at a time (`…000005_task_agent_archives.exs:437-456`); a current/fresh DB runs no migration body at all.
- Per-BEAM one-time and permanent: the migration `[{version, module}]` source is compiled once with `Code.compile_file/1` and memoized in `:persistent_term` (`store/boot.ex:354-380`) — a few hundred bytes plus ~0.1-0.3 MB of code area.
- Runtime (NOT boot) tens-of-MB growth lives in `:evogit_agent_state`: each value carries the agent's whole `context`, `:ets.delete_all_objects` appears nowhere in the app, and only `Lifecycle.delete_agent_state/1` removes a row → `agent_scheduler/CONTEXT.md`.
- Boot-time side effects that cost CPU/processes but no memory: `BackgroundJobs.init/1` fires an async `Sandbox.Background.sweep_stale_units/0` (systemctl) on Linux, and `SandboxSlice.init/1` runs `systemctl --user stop evogit.slice` + a 100 ms sleep before creating the slice.

## Known Issues

- **Whichever process first touches the LLMDB catalog on a fresh BEAM pays the whole load in ITS OWN heap — so at boot that process must be a throwaway one.** `:llm_db` loads `priv/llm_db/snapshot.json` (11,693,807 B, 239 providers, 10,100 models) lazily on the first query (`deps/llm_db/lib/llm_db/catalog.ex:107-132`, `:207-210`), and the load decodes the JSON, builds 3 full model lists + 5 indexes and canonicalises the whole catalog for a `term_to_binary` digest (`loader.ex:208-228`, `:546-566`, `:282-297`) — all in the caller's heap; `:persistent_term` READS never copy (ERTS `persistent_term.erl` docs), only the load allocates, so the retained MBs are dead garbage awaiting a fullsweep, NOT live state. `EvoGit.CatalogWarmup` therefore loads it in a short-lived process (see "Boot memory profile"); a LONG-lived process that happens to be first (a scheduler booted without the warm-up, e.g. after a warm-up timeout) is the one shape to avoid.
- Dispatch resolves concrete selections and populates effective `llm_model`, `llm_generation_params` and configured `llm_context_window` once at admission; ordinary turns and compression consume those fields rather than re-resolving provider defaults each turn.
Cost recomputation prices the effective model and resolves the selected account's current pricing schedule, while metadata/pricing reads reuse the warm catalog; consumer contracts belong to `agent/` and `agent/compression/`.
- **Interactive and embedded boots now agree on scheduler memory** (`-mode embedded` used to leave ~47 MB of the catalog's dead heap resident in `EvoGit.AgentScheduler` for the whole BEAM lifetime, because an embedded boot never fullsweeps and `init/1` is its last allocation-heavy work). With the warm-up owning the load, every boot samples 29-66 KB there; the remaining embedded/interactive delta is preloaded code + carrier pages, not dead heap.
- **Process/thread exhaustion inside containers breaks git forks (EAGAIN).** In rootless podman every process shares the host user's UID, so the kernel's per-UID `RLIMIT_NPROC` (`ulimit -u`) spans container + host processes (every OS thread counts); when hit, `fork()` fails with `EAGAIN` — git prints "cannot fork() ... Resource temporarily unavailable" (e.g. in `git worktree add`). `WorktreeManager` survives (persistent init marker + re-monitoring) but the run loses agents to crash-retry. Prevention: raise the HOST user's nproc limit (`/etc/security/limits.conf` or `systemctl --user set-property user.slice TasksMax=infinity`); or `--ulimit nproc=65536:65536 --pids-limit -1` (`pids_limit = -1` + `default_ulimits` in `~/.config/containers/containers.conf`); or delegate the pids controller (`/etc/systemd/system/user@.service.d/delegate.conf` → `[Service] Delegate=cpu cpuset io memory pids`); verify via `ulimit -u` / `/sys/fs/cgroup/pids.max`; or reduce concurrency (`[scheduler] default_llm_max_concurrency`, per-profile `concurrency`).

## Constraints

- Part of an **umbrella project** — deps, artifacts and lockfile at the repo root; Elixir ~> 1.18; **Git CLI only** (no libgit2); no source at root — all code under `./apps/`; subdirectories follow Elixir convention (`./lib/evo_git/<subdir>/` ↔ `EvoGit.<Subdir>`).
- All git operations go through `EvoGit.Adapters.Git` (or `Shared.commit_files/4` → `EvoGit.sandbox_run`); no direct `System.cmd("git", ...)` in domain modules (exception: GitEnv's config reads).
- `remote_api.ex` and `remote_node.ex` are intentionally long cohesive RPC wrappers — do NOT split them; add new RPC functions there (`defnode` macro from `EvoGit.RemoteNode.Defnode` for identity-unwrap wrappers; per-function-fallback wrappers stay hand-written).
- Agents are transient modules using the `EvoGit.Agent` behaviour; framework state lives in ETS; execution happens in **isolated git worktrees** managed by `AgentScheduler.WorktreeManager`, never on the main working copy; agents commit before delegating subagents (auto-commit fallback enforced by the scheduler).
- **Three-level configuration** (`EvoGit.Config`): built-in defaults → user config (`~/.config/genesis/config.toml`, XDG) → runtime overrides; **no default model or username is hardcoded**.
- **Slot discipline**: agent LLM calls acquire/release account-shared slots via `AgentScheduler`, binding immutable `provider_profile_id` independently of concrete `model_spec` and effective `llm_model`.
The canonical `[[llm.providers]]` account owns concurrency/peak/backoff and shared auth/endpoint defaults; nested model/effort inventory does not create additional pools.
Legacy `llm.models`/flat model configuration and `model_id` remain compatibility inputs, while locked children inherit the full canonical selection and lock.
Configuration/persistence details belong to `config/`, selection/pool semantics to `agent_scheduler/`, and effective request/compression/cost consumers to `agent/`.
- **Task-scoped naming**: worktree dirs `worker_T<task_number>_A<task_local_id>`, branches `evogit-agent-T<task_number>-A<task_local_id>`; `task_id` = 16-char hex GUID, `task_number` = short integer from a linear scan of `.genesis/workers/`, used only for naming.
- **Task persistence runs in `:evo_git`** — `Store` + `TaskRegistry` sit in the supervision tree, so the `genesis_server` daemon has full task history; a freshly-started Registry leaves orphaned `:running` rows to the lease sweep; `trim_recent_projects/1` is nil-safe (nil `last_opened_at` sorts LAST); test isolation pins `config :evo_git, :data_dir` to a UNIQUE per-run temp path in `config/test.exs`. Detail: `store/` + `task_registry/`.
- **Task Archive (opt-in)**: `--archive` → `runtime_opts` → `AgentSpec.opts` → `AgentState.archive`; each completing agent writes `refs/genesis/archive/T{task_id}-A{agent_id}-start`/`-final` + a usage git note + ONE `task_agent_archives` row STREAMING at completion (idempotent upsert on `(task_id, agent_id)`). No buffer, nothing in `%Result{}`/report; CRASH/FAILURE/ABORT writes NO row (usage LOST — a retry resets to `Usage.zero()`); Genesis Mode B shares one `task_id` → exactly 2 nil-parent rows; JSON round-trip caveats (string keys/timestamps; keys `input_cost`/`output_cost`/`total_cost`, never `cost`). Detail: `store/` + `agent_scheduler/`.
- **Distribution & releases** (EPMD-less via `-epmd_module Elixir.EvoGit.EpmdDist` + `-start_epmd false` in all `rel/vm.args.eex`; daemon on port 9000; releases `genesis`/`genesis_desktop`/`genesis_server` in the root `mix.exs`; prod-only `PORT`/`PHX_IP` → `[server] listen_port`/`listen_ip`, default 9999; zombie prevention via dynamic port + `EVOGIT_LIFETIME_PORT`): detail `lib/evo_git/CONTEXT.md` + root `./CONTEXT.md`.
- **SSH remote bootstrap** (remote commands are argv arrays, never quote-wrapped spawn strings — `run_ssh_command/4` `{:spawn_executable, ...}` + one argv element, wrapped by `sh_wrap/1` as `/bin/sh -c '<script>'` — no `/usr/bin/env`, no bash: stock NixOS lacks `/usr/bin/env` while `/bin/sh` is POSIX-mandated and is NixOS's `environment.binsh`; every remote script is POSIX sh and single-quote-free by construction, so fish/nushell/tcsh login shells pass the wrapper through untouched; override seam app env `:remote_shell`; the daemon itself is the `genesis_server` release and ALL of its lifecycle — systemd scope/unit, launchd plist, setsid fallback, readiness wait — is delegated to that release's `bin/genesis` CLI (`genesis remote start|stop|status|logs`), so Elixir only shells out `<launcher> remote status|stop|start --unit genesis-remote-<id>`; identity is verified from the node the CLI reports; NixOS patching happens only while the daemon is not running; best-effort `:copying_config`): detail `lib/evo_git/CONTEXT.md`.
- **Config caching** (mtime+size-validated `:persistent_term` cache for `user_config/0`/`credentials/0`; the ACTUAL cache is AgentScheduler state — `get_config/0` cached, `reload_config/0` re-reads disk; `save_user_config/1` does NOT auto-reload; `RemoteConnections` does NOT auto-create `remote_connections.toml`): detail `config/`.
- **Genesis Mode B** (`Genesis.run_new_codebase/4`): Phase 1 `Agents.Architect` → Phase 2 `Agents.Manager` (second root from the architect's final commit; "Genesis Implementation Mode" prompt). Detail: `runtime/`.
