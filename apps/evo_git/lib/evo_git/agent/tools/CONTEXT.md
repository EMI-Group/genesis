# EvoGit.Agent.Tools — Tool Definitions & Execution

## Intent
LLM tool definitions and implementations for EvoGit agents: each module declares a schema (`ReqLLM.tool/2`) and an `execute` function covering the filesystem, git, the web and system resources.
This node owns the schemas, the model-name/alias spine, the dispatch gate chain and the per-tool contracts; execution itself belongs to `../../tool_runtime/CONTEXT.md`.

## Routing Table
- `./skill/` → skill tool modules (SkillAdd, SkillEdit, SkillRemove, SkillEnable, SkillDisable, SkillList, SkillRead, SkillWhere) — detail `skill/CONTEXT.md`
- `./lsp/` → `EvoGit.Agent.Tools.Lsp.Protocol`, the PURE LSP wire codec (Content-Length framing, JSON-RPC encode, incremental `decode/1`, `file://` URIs, diagnostics/hover/definition normalization; no I/O, ports or processes) — detail `lsp/CONTEXT.md`
- `./elixir_eval/` → evaluator authorization, admitted MFAs, quotas, worker cleanup and rendering — detail `elixir_eval/CONTEXT.md`; the public wrapper/schema stays in `./elixir_eval.ex`
- `./boundary.ex` → `EvoGit.Agent.Tools.Boundary`, the ONE process-boundary guard (`run/2`, `run_string/1`, `call/3`) — § Boundary & failure shapes
- `./failure.ex` → `EvoGit.Agent.Tools.Failure`, the ONE failure renderer (`error/1,2`, `format_reason/1`)
- `../util/CONTEXT.md` → the PURE helpers this layer delegates to (`EvoGit.Util.Strings` truncation, `EvoGit.Util.Coerce`, `EvoGit.Util.Time`, `EvoGit.Util.Map`)
- Tool MODULES are siblings here and each file name spells its module's last segment (`make_dir.ex` → `MakeDir`, `file_read.ex` → `FileRead`); multi-tool `context.ex` (`Context`) and the adapters `genesis_tools.ex`/`genesis_source.ex` are the exceptions.

### Tool Schema Shape (`ReqLLM.tool/2`)

- `schema/0` everywhere; `WebSearch` also exposes `schema/1` (`schema/0` delegates with `[]`), and `Context` exposes `read_schema/0`, `write_schema/0`, `edit_schema/0`.
- `EvoGit.Agent.Tools.Context` is a FUNCTION-ONLY module — no `%EvoGit.Agent.Tools.Context{}` struct exists anywhere (`%Context{}` in `agent_scheduler/store.ex` is `ReqLLM.Context`, and `EvoGit.Core.ContextNode` is the spatial tree node).
- Every call uses the same four fields — `name:`, `description:`, `parameter_schema:`, `callback:` — and no tool uses the optional `strict:`/`provider_options:`; `callback` is always the no-op `fn _ -> {:ok, nil} end` because real execution goes through `execute`.
- `parameter_schema` is a STRING-keyed JSON-Schema map with `"type" => "object"`, `"properties"` and `"required"`; property vocabulary is `type` (`string`/`integer`/`boolean`/`array`; `object` only as the top-level type), `description`, `default`, `enum` (`make_dir` keep-file options, `lsp` actions and the `Context` `scope` params) and `items` (string arrays in `make_dir`, `git`, `ripgrep`, `file_create`); no tool declares `additionalProperties`.
- Only THREE builders produce config-dependent CONTENT at call time: `shell_tool.ex` (timeout text interpolating `max_timeout/0` + `@default_timeout`, and `generate_description/0`), `job_output.ex` (`BackgroundJobs.wait_default_ms()`/`wait_max_ms()`) and `web_search.ex` `schema/1` (provider-derived `search_depth`/`max_results`/`timeout`). The tool array is part of the LLM prompt PREFIX, so a mid-run `config.toml` or app-env change rewrites schema text and breaks prompt caching; every other `schema/0` interpolates module attributes only.

## Constraints
- **Unified `timeout` argument contract** — the canonical key is `timeout` (every tool that has one; `job_output` additionally accepts its own `timeout_ms`/`timeoutMs` wait-budget spellings, in that priority order, with `timeout` honoured between them); the value is an integer of MILLISECONDS, a float (truncated), or a numeric string with an optional `ms`/`s`/`m` unit (`"60000"`, `"90s"`, `"30m"`, `"1.5s"`), and an absent, non-positive or unparseable value means "no explicit timeout".
- Parsing lives ONLY in `EvoGit.Agent.Tools.Shared.fetch_duration_ms/2` / `get_duration_ms/3` (they coerce, never clamp, never raise; the whole value must parse, so `"60000abc"`/`"1h30m"` are unusable) — no tool re-implements it — and the per-call ceiling is `[:scheduler, :max_tool_timeout]` resolved at CALL time in every tool, never a duplicated literal.
- `web_fetch` deliberately keeps its OWN whole-request budget contract (`timeout` integer ms, 50..600_000, spanning all redirect hops) instead of the tool-wide rule.
- Result contract: `String.t() | %EvoGit.Agent.ToolOutput{} | {:error, reason}`; built-ins return strings, and media rides `%ToolOutput{}` through the `EvoGit.Agent.ToolDispatch` wrap boundary (`../CONTEXT.md` → "Multimodal Tool Outputs") while every guard path stays binary.
- Sandboxed tools run via `EvoGit.sandbox_run/4`; file tools use `File` directly.
- Every output passes `EvoGit.Agent.OutputSanitizer` (ensure_utf8 → ANSI strip → progress bars → truncation) plus a `TruncationFeedback` block; `[truncation]` keys: `tool_output_max_bytes` 131072 (ceiling), `tool_output_default_max_bytes` 16384 (high-output tools), `tool_output_truncate_size` 8192 (keep size) — a per-call `max_bytes` overrides the default but never the ceiling.
- Truncation keeps head+tail, cuts on UTF-8 boundaries, clamps the keep budget (head/tail never overlap; output between threshold and keep size survives whole) and reports the omitted byte count with "narrow the pattern/path or raise `max_bytes` (up to 131072)" plus one ⚠️ line.
- Batches split on `Tools.serial_tool?/1`: the file-mutating subset runs SEQUENTIALLY in the parent agent process, the rest in parallel (`Task.async_stream`, bounded by `max_tool_concurrency`); concurrent shell/git calls can still contend on git's `index.lock`.
- Write tools get 4 args (incl. `node_path`), read tools 3.
- `run_git`'s schema is commented out of `schemas/0`; agents use `bash` for git.
- New identity-named tool needs a module (`schema/0` + `execute`), a dispatcher clause and an explicit schema exposure site; an alias is only needed when the model-facing and dispatch names differ.
- `run_command` is refused by `Tools.execute/5`; user-defined custom tools dispatch through the `execute_tool/5` catch-all only, never in `schemas/0` or `read_only_schemas/0`, and are opt-in per agent `available_tools/0`.

## Execution Flow
1. `Tools.schemas/0` aggregates schemas into the agent's `available_tools/0` (with `web_search` gated on `[:tools] search_enabled` and `lsp` appended LAST by `maybe_append_lsp/1`).
2. `Tools.execute(tool_name, args, repo_path, repo_root, node_path)` refuses `run_command`, maps the args, then normalizes the model-facing name FIRST via `EvoGit.Agent.ToolNames.normalize/1`: `*_file`/`search_web` aliases map to internal keys and every shell spelling (`bash`/`shell`/`sh`/`execute_bash`/`bash_command`/`run_shell`/`shell_command`/`run_bash`/`run_powershell`, case-insensitive) maps to the compile-time `@shell_tool_name`; unknown names pass through.
3. The reserved `elixir_eval` route authorizes at the tool, then `maybe_block_repo_less/5` and `maybe_block_read_only_foreign_repo/5` run — normalization precedes both guards so aliases cannot bypass them.
4. Private `execute_tool/5` pattern-matches to the module's `execute`; write tools verify `Shared.validate_file_scope/4` (CONTEXT.md writers pass `format_context_scope_error/2`) before writing.
5. Sandboxed tools call `EvoGit.sandbox_run/4`.
6. Result: string | `{:error, reason}` (dispatcher renders `"Error: …"`) | `%ToolOutput{}`; an unknown name falls to the catch-all → custom tool (`EvoGit.CustomTools.execute/3`, `:unknown` continues) → dynamic skill → `"Error: Unknown tool '<name>'. Did you mean '<closest>'? Available tools: ..."`, where names come from `schemas/0` at runtime and the suggestion is the nearest `String.jaro_distance/2` ≥ 0.7 (`run_command` absent, `run_git` excluded). Custom tools must return a string (`{:error, "… returned a non-string value…"}` otherwise).

### Web Search Providers
- `WebSearch` supports `:tavily` (default), `:perplexity`, `:exa`, `:bing`, `:brave` and `:keenable` from `[:tools, :search, :provider]` (unknown/nil → `:tavily`); `EvoGit.Config.Schema.Definitions.search_providers/0` is the single source of truth.
- Pure, I/O-free adapters live in `EvoGit.Agent.Tools.WebSearchProviders`: `build_request/5` → `{:ok, %{method:, url:, headers:, body:}}`; `parse_response/2` → `{:ok, %{kind: :results, entries: [%{title, url, content}]}}` (Tavily/Exa/Bing/Brave/Keenable) or `{:ok, %{kind: :answer, text:, citations:}}` (Perplexity).
- Keenable is OPT-IN and the only keyless-capable provider: `KEENABLE_API_KEY` present → keyed POST (`X-API-Key`); absent/empty → the public `POST <base_url>/public` with `X-Keenable-Title: Genesis` and no key, so the missing-key failure is gated on `Definitions.search_provider_keyless?/1`.
- `WebSearch` owns schema/validation/API keys and the `Req` call through the call-time `:web_search_http_runner` seam; `do_web_search/4` is `@doc false` public for execute-level tests.
- `timeout` is coerced like the shell's and clamped to `[:scheduler, :max_tool_timeout]`; an absent/unusable argument falls back to the provider-config `:timeout`, then `@default_timeout` 30_000.
- `search_depth` is Tavily/Exa-only (Exa maps advanced→`type: "neural"`, basic→`"keyword"`); Perplexity ignores `max_results`/`search_depth`; Bing/Brave/Keenable honour only `max_results`.

### Web Fetch (`web_fetch`)
- READ-ONLY page reader (ONE GET → Markdown) in both schema lists, never a write tool, not serial, and NOT schema-gated.
- Params: `url` (required, absolute, http/https), `max_chars` (default 200_000, 100..2_000_000), `timeout` (default 30_000 ms, 50..600_000 — a WHOLE-request budget spanning every hop); retries disabled. The streamed body halts at `raw_cap = clamp(max_chars * 8, 512 KiB, 16 MiB)`.
- Rendering: `"Fetched <url> (HTTP <code>)\n\n<text>"` plus `[truncated: the response body exceeded the <N>-byte fetch limit]` or `[truncated: first N of ~M characters]`.
- HTML types (`text/html`, `application/xhtml+xml`, `application/xhtml`, `text/xhtml`) → Markdown via pure `HtmlToMarkdown` (relative `href`/`src` resolved against the FINAL url); JSON/XML/CSV/YAML/TOML/JS/GraphQL and `+json`/`+xml` verbatim; anything else → `"[binary content omitted: <label>]"`.
- Non-2xx → `Failure.error("<url> returned HTTP <code><reason phrase>")`; 301/302/303/307/308 are followed manually (`redirect: false`), at most 5 hops (the 6th errors), SAME host + scheme (port may change), relative `Location` via `URI.merge/2`; a timeout renders the CONFIGURED budget, never the measured per-hop remainder.
- The private-host gate is BEST EFFORT, explicitly not a security boundary: it resolves `:inet`/`:inet6` and refuses non-public addresses (IPv4 loopback/private/link-local incl. `169.254/16`, CGNAT, `0/8`, multicast; IPv6 loopback/unspecified/ULA/link-local/multicast and IPv4-mapped) plus `localhost`/`*.localhost`, but issues the request by NAME, so DNS rebinding and hostile relays are out of scope. Client is `Req` with a streaming `into:` callback; call-time test seam `:web_fetch_allow_private_hosts` (default `false`) skips the gate.

### Language Server (`lsp`)
- READ-ONLY code intelligence over ONE user-configured server (nothing bundled or left running); never a write tool, not serial, model-facing name equals the dispatch key.
- The schema is appended LAST to both schema lists by `maybe_append_lsp/1` only when `EvoGit.Config.lsp_enabled?/0` is true (`[lsp] enabled = true` + non-empty `command`) — absent by default, with the dispatch clause permanently registered.
- Params: `action` (required enum `diagnostics`/`hover`/`definition`), `path` (required, absolute or repo-relative, must resolve inside `repo_path`/`repo_root` via `EvoGit.Platform.path_under?/2`), `line`/`column` (1-based; required for hover/definition, ignored for diagnostics, converted to 0-based at the request boundary).
- Config `[lsp]`: `enabled`, `command`, `args`, `timeout`, `diagnostics_timeout`; the command resolves via `EvoGit.Executable.resolve/1` then `System.find_executable/1`. Not enabled or blank command → exactly `Error: no language server configured — set [lsp] command in config.toml`; malformed values normalize silently (non-map → `%{}`, non-list `args` → `[]`, bad timeouts → defaults).
- ONE server, hardcoded Elixir: `open_document/2` always sends `languageId: "elixir"` and `initialize/2` roots at `repo_root` — no per-language registry, defaults, extension mapping or root markers, so any readable UTF-8 file ≤ 2 MiB is analysed as Elixir.
- Per call: spawn on stdio → one handshake (`initialize` → `initialized` → `textDocument/didOpen`) → at most one request → teardown; request ids are fixed (1..4), and teardown always runs (`didClose` → `shutdown` → `exit` → SIGKILL by OS pid → drain → idempotent `close_port/1` → stderr removal).
- Spawn is a raw `Port.open({:spawn_executable, …})` (POSIX: a tiny `sh -c 'exec "$@" 2>"$err"'` trampoline) — NOT sandboxed and with no `{:cd, …}`, so the configured server runs with the BEAM user's full authority in the BEAM's own cwd; only the `[lsp] command` binary is ever spawned.
- Bounds: file ≤ 2 MiB (rejected before `didOpen`), 4 MiB frame buffer, 30 s total / 10 s diagnostics timeouts (configurable), 100 lines and 8 000 chars of output, 2 048-byte stderr; every `receive` is bounded.
- `diagnostics` collects `publishDiagnostics` until quiet for `settle_ms` (default 500) or budget expiry (`<path> — <N> diagnostic(s):` plus `<path>:<line>:<col> <severity> <message>` lines, `"No diagnostics for <path>."`, `"...[truncated at 100 diagnostics]"` past the cap); `hover` renders `Protocol.hover_text/1`; `definition` renders `<path>:<line>:<col>` per `Protocol.locations/1`.
- Gotchas: the dispatcher's generic 10 s timeout (`default_timeout_ms("lsp")` is `nil`) under-cuts the tool's 30 s default and skips teardown (stdin EOF); server→client requests are never answered, so such a server dies on timeout; a silent server renders `"No diagnostics for <path>."`; `lsp` reaches both schema lists only when enabled, `Agents.SelfReflective` never lists it, and it is a `@high_output_tools` member.
- Framing/URI/result helpers are the pure sibling `EvoGit.Agent.Tools.Lsp.Protocol` (`lsp/protocol.ex`) — detail `lsp/CONTEXT.md`; test seam `execute/4` accepts `:enabled`/`:command`/`:args`/`:timeout`/`:diagnostics_timeout`/`:settle_ms`, exercised by `EvoGit.FakeLspServer` (`test/support/fake_lsp_server.ex`, packed once per test module into an `escript`).

### Boundary & failure shapes
`EvoGit.Agent.Tools.Boundary` is the ONE guard for tool code that crosses a process boundary: a `GenServer.call` to a dead, restarting or timed-out `EvoGit.BackgroundJobs`/`EvoGit.TaskRegistry`/store exits the CALLER with `:noproc`/`:timeout`, which is an exit rather than a rescuable exception. Its moduledoc carries the single `rescue`/`catch` rationale.
- `Boundary.call/3` for an `{module, function, args}` GenServer read, `Boundary.run/2` when a CUSTOM error term must be preserved (e.g. `fn reason -> {:registry_unavailable, reason} end`), `Boundary.run_string/1` only when the failure value is the bare `"Error: …"` string; the wrapped function's own return passes through byte-identically.
- The guarded tools are `cancel_task`, `force_kill_task`, `delete_task`, `start_task`, `get_task`, `list_tasks`, `job_output`, `job_list`, `job_kill` and `system_info`; they carry NO local `try/rescue` around a GenServer/VCT/store call.
- A local guard survives only where the SEMANTIC is not an error value or the raise has no non-crashing variant, each with a justifying comment at that site: `job_output`'s graceful-cancel probe (a failure means "not cancelled") and `glob`'s `Path.wildcard/1` catch.
- **VCT reads are TOTAL and need no boundary**: `EvoGit.VCT.projects/1`/`workspaces/1` answer `[]` and `workspace_members/1` answers `{:error, :not_found}` when the server is absent or dead, so `ListProjects`, `ListWorkspaces` and `ShowWorkspace` call them DIRECTLY and keep every real result clause.
- Tool failure reasons render through `EvoGit.Agent.Tools.Failure.format_reason/1` (total: binary verbatim, exception struct via `Exception.message/1`, anything else `inspect/1`), and `Failure.error/1,2` builds the one `"Error: …"` shape; `test/evo_git/agent/tools/failure_test.exs` is the sole contract owner for `Failure` — do not duplicate its assertions elsewhere.
- `Shared` DELEGATES pure string work to `EvoGit.Util.Strings` (`truncate/2` keeps its public doc/spec and delegates), so one implementation sits at the bottom of the graph; the `:not_owner` prose speaks of READING the job and the `job_output` wording is canonical for read and kill.
- Handler error shapes: a VALIDATION/argument/not-found failure returns `{:error, message}` (propagated as a shell error) while a runtime DEGRADATION inside an otherwise successful call renders a readable line in the success string (an empty mount table is `"No projects found."` / `"No workspaces found."`).

### rg output conventions
`bare_args?/1` decides the shape: BARE args (`PATTERN [PATH ...]`) get `--line-number` + `--no-heading` injected and a 250-line cap with a narrowing footer; an EXPLICIT flag set (`-l`, `-c`, `--json`, `-A/-B/-C`, `-e`/`-f`) passes VERBATIM under the legacy `Command executed successfully.\nOutput:\n<raw>` envelope. Errors become prose with advisory tips (`build_hint/1`).

### String-replace semantics (`edit` / `edit_context`)
`new_string` is inserted VERBATIM (whitespace and newline state preserved) and matching is byte-exact after smart-quote normalization (`Shared.find_actual_string/2`), so CRLF files never match. Messages: `"Error: Found N matches of old_string in file. Set replace_all=true or provide more context."` and `"Error: old_string not found in file <display_path>"`.
`edit` delegates the whole file to `Shared.perform_string_replace/5`, while `edit_context` runs `Shared.find_actual_string/2` + `Shared.count_occurrences/2` + `Shared.apply_string_edit/4` on the SELECTED region only and writes back through `EvoGit.Core.ContextScope.splice/3` (`### Two-scope CONTEXT.md`).

### Two-scope CONTEXT.md (Shared / Local)
A CONTEXT.md may carry ONE divider line, the literal `<!-- genesis:local -->`; text before it is Shared (this node and all of its descendants) and text after it is Local (read only by agents assigned to that directory).
`EvoGit.Core.ContextScope` is the SINGLE implementation of the divider/split/splice logic (`marker/0`, `split/1`, `scope_content/2`, `splice/3`, `has_local?/1`, `parse_scope/1`) — the tool layer calls it and never re-implements it; the design record is `docs/context-scopes.md`.
`read_context` takes an optional `scope` (enum `all`/`shared`/`local`, default `all`): `all` returns the RAW file including the divider line, `shared`/`local` return just that region with the divider line excluded, and `local` on a file without a divider errors with the "has no Local section" remedy.
`edit_context` takes an optional `scope` (enum `shared`/`local`/`all`, default `shared`): matching, uniqueness counting and `replace_all` are restricted to the selected region.
`scope: "all"` matches across the RAW whole file, divider line included, so a whole-file edit can never silently drop the divider and an `old_string` spanning it still matches (`ContextScope.splice/3` returns the edited region verbatim for `:all`).
`shared`/`local` match only their own region (divider line excluded) and are spliced back, so the divider line and the other region survive byte-for-byte.
`write_context` takes no `scope` — it writes the FULL file, so the caller places the divider line itself when it wants a Local section.
`search_context` searches WHOLE CONTEXT.md files, so it sees BOTH scopes and has no scope filter.
Node-subtree enforcement is unchanged and still runs BEFORE any read or write: `edit_context`/`write_context` call `Shared.validate_file_scope/4`, and reads stay unrestricted.

### Per-Tool Path Handling (scope, sandbox, TMPDIR)
- Six tools scope-check via `Shared.validate_file_scope/4`: `write`, `edit`, `create_files`, `make_dir`, `write_context`, `edit_context`; the CONTEXT.md writers pass the target DIRECTORY plus `format_context_scope_error/2` and check BEFORE any filesystem change, so an out-of-node call changes nothing.
- No other tool scope-checks: `read`, `glob`, `list_dir`, `bash`, `rg`, `run_git`, `search_context`, `search_history`.
- Check order: (1) read-only foreign repo; (2) inside `repo_path` (anything outside the repo root, `/tmp/...` included, is rejected); (3) inside `node_path` (caller formatter, default `format_scope_error/2`); there is NO tmp-dir or arbitrary-path allowance, and a `nil` node path is ALLOW-ALL (kept only for direct/unit callers — the agent loop enforces a non-nil binary).
- Node ownership: `"./"` (root) owns the whole repo; any other node owns itself and its descendants. Both formatters are PUBLIC so callers and tests pin the teaching text.
- `Shared.expand_path/2` → `Platform.safe_expand/2` returns ABSOLUTE inputs unchanged (never anchored under `repo_path`), so `read`/`list_dir`/`glob`/`read_context` can read `/tmp/...` or `/etc/...` and `rg`/`search_context` pass args verbatim; it enforces NO containment (`Path.expand` semantics, UNC prefix preserved), so only `validate_file_scope/4` checks scope.
- Shell commands run through `EvoGit.Sandbox.run_with_partial/7` (the timeout variant); both it and `EvoGit.sandbox_run/4` use `EvoGit.Sandbox.backend()`. `bash` is the ONLY timed sandboxed call — `git`, `rg`, `search_context`, `search_history` and skill scripts use the UNTIMED `sandbox_run/4` (no timeout, no partial-output recovery, no `:execution_id`).
- Every shell path gets `TMPDIR = EvoGit.Sandbox.resolve_tmpdir/0`: sandboxed → backend injection (systemd `--setenv=TMPDIR`, bwrap `--setenv TMPDIR`, macOS `env:`); non-sandboxed/Windows → `TMPDIR`/`TMP`/`TEMP` via `Sandbox.Helpers.temp_env_vars/0`.
- `resolve_tmpdir/0` prefers the managed per-task dir installed on the calling process (`TaskTmpdir.current/0`) and returns it directly; otherwise it keeps `$TMPDIR` when it exists under `Platform.tmp_paths/0` (`/tmp`, `/var/tmp`; `System.tmp_dir!()` on Windows) and otherwise takes the first entry. It appears in exactly ONE tool module — `shared.ex` (the commit-message temp file, removed in `try/after`); no tool module uses `System.tmp_dir!/0`.
- Shell schema text: `$TMPDIR` (POSIX) / `$env:TEMP` (PowerShell), with "Always use $TMPDIR for temporary files, never /tmp." on POSIX.

### Write gating: role guards, write set, serial classification
- **Guard order (load-bearing)**: `Tools.execute/5` refuses `run_command`, maps args, normalizes the name through `ToolNames.normalize/1`, routes reserved `elixir_eval`, then runs `maybe_block_repo_less/5` and `maybe_block_read_only_foreign_repo/5` before `execute_tool/5`. Normalization MUST precede the guards: `run_bash`/`run_powershell` are write tools, so late normalization would let a repo-less or read-only-foreign-repo agent write via "Bash".
- Role resolution: `Process.get(:repo_less)` and `Process.get(:foreign_repos, [])` (set by `EvoGit.Agent.Session.Setup.install_process_context/3`, normalized via `EvoGit.Core.ForeignRepo.normalize/1`) matched by `:evogit_repo_id`, with a `ForeignRepo.resolve_path/2` path fallback because worktrees live under `<root>/.genesis/workers/...`.
- Role propagation: `EvoGit.ToolRuntime.Executor.execute_tool_task/4` installs `:repo_less`, `:foreign_repos` and `:evogit_repo_id` in EVERY spawned tool task from the batch's `%EvoGit.ToolRuntime.Request{}.role` (never from the caller's pd, which spawned tasks do not inherit), alongside `:evogit_agent_id`/`:evogit_task_id`/`:evogit_agent_pid`, `:repo_path`, `:genesis_repo_root`, the per-task tmpdir and `:evogit_execution_id` — so both gates and `validate_file_scope/4`'s foreign-repo arm enforce on the normal dispatch path.
- All three role sources are PROCESS-DICTIONARY keys carried by the runtime request rather than tool arguments, while repo/node paths reach the tools as ARGUMENTS (`repo_path`, `repo_root`, `node_path`); there is no `:node_path`/`:worktree_path` pd key anywhere.
- In a foreign repo whose `writable` is not literally `true`, every write tool (`write_tool?/1` = `@write_tools` OR `EvoGit.CustomTools.write_tool?/1`) is blocked with `"Error: this agent operates in a read-only foreign repository (<root>) — the <tool> tool is disabled. Writable foreign repos are the only foreign repos that accept modifications; read-only foreign repos are for investigation only."`, and `Shared.validate_file_scope/4` independently rejects a write target resolving into one (`"Path '...' is inside a read-only foreign repository ('<root>')…"`).
- `@write_tools` (17) = `create_files`, `write`/`write_file`, `edit`/`edit_file`, `bash`/`run_bash`/`run_powershell`, `make_dir`, `write_context`/`edit_context`, `run_git` (schema-less, blocked as defence-in-depth and absent from the SelfReflective list) and the five skill writers; every check normalizes its input first, and the model-facing spellings are listed as belt-and-braces.
- `serial_tool?/1` marks non-atomic read-modify-write callers that must never overlap in one batch (each would read the original bytes and only the last write would survive while all report success). It is derived by subtraction — `@serial_tools = @write_tools -- ["run_bash", "run_powershell", "run_git", "bash"]` — giving `create_files`, `write`/`write_file`, `edit`/`edit_file`, `make_dir`, `write_context`, `edit_context` and the five skill writers; a custom tool declaring itself a write tool IS serial (conservative), and `elixir_eval` plus the `genesis_*` task tools are serial at every tier independently of the file-write set.
- Everything else returns `false`: `read`, `read_context`, `glob`, `list_dir`, `rg`, `search_context`, `search_history`, `skill_list`, `skill_read`, `skill_where`, `web_fetch`, `lsp`, `run_command`, `web_search`, `genesis_source`, the job controls and unknown names. A background `bash` start is gated exactly like a write tool (`run_in_background` never bypasses the guards) while `bash` stays in `@write_tools` and out of `@serial_tools`.
- `read_only_schemas/0` = read tools + `Context` write/edit + `ShellTool` + `WebFetch` (always) + `Lsp` (gated): read-only agents must still update CONTEXT.md in their own repo and run tests, while writes inside read-only FOREIGN repos are blocked by the role gate. `job_output`/`job_list`/`job_kill` sit in BOTH schema lists and in NEITHER write list.
- Consumer: `EvoGit.ToolRuntime.Executor.execute_batch/2` runs the serial subset first, sequentially, in request order, in the calling agent process (`../../tool_runtime/CONTEXT.md`).

### Commit Semantics
**ONE helper: `Shared.commit_files/4,5`** (`(repo_path, repo_root, files, message) -> {:ok, output} | {:error, message}`; `/5` adds an `opts` keyword).
- It stages ONLY the passed paths (`EvoGit.sandbox_run(repo_path, "git", ["add" | paths], repo_root)`) — never `git add --all` — and commits with `git commit -F <tmpfile>` on the same sandbox path; the co-author trailer is appended only when `[:git, :co_authored_by_enabled]` is not `false`, and the message always rides a file, never `-m` argv.
- `{:ok, output}` is the concatenated add+commit output; `{:error, message}` is `"Error: git add failed (exit N): …"` / `"Error: git commit failed (exit N): …"`. An empty file list returns `{:ok, "No files to commit"}` with no git call, and git's exit-1 "nothing to commit" wordings (`@nothing_to_commit_markers`, locale-stable via `LC_ALL=C`) are graceful `{:ok, output}` no-ops.
- `opts` recognises `amend: true` (default `false`) and `amend_message_fun: (paths -> message)`; `/4` delegates to `/5` with `[]`.
- `amend: true` squashes into HEAD instead of creating a commit, and only when `files` holds EXACTLY ONE path (more than one always stays a plain commit), via `git commit --amend --only -F <tmpfile> -- <repo-relative path>` — `--only` keeps unrelated staged content out, and the relative path avoids MSYS2 backslash mangling.
- Amend is ATTEMPTED only when all four `amendable_context_head/3` checks pass: HEAD has exactly one parent (never a merge commit), HEAD's `diff-tree --name-only` paths are one or MORE and ALL of them CONTEXT.md paths, HEAD's subject starts with the literal `"Update CONTEXT.md for "`, and HEAD is PRIVATE to the current branch (`for-each-ref --contains HEAD` names exactly `git symbolic-ref HEAD`) — amending a commit still contained in a parent's branch, `main` or a remote-tracking ref would rewrite the base ContextMerge and the review flow depend on.
- Any failed check, git failure or unparsable output is a plain `:error` → the plain commit runs; a failed `--amend` also falls back and an identical-content amend is a git exit-0 no-op. `amend_message_fun` runs ONLY on the successful amend path with the FINAL path set (HEAD's changed paths ∪ the new repo-relative path, deduped and sorted), and only a non-empty binary return replaces the caller's message.
- `create_files` stages exactly the supplied paths (a new untracked ancestor directory, or a path tracked in a parent node, is not staged); `make_dir` stages only the keep-files it created (`keep_file: "none"` → no commit); the five skill writers use `Shared.maybe_commit_result/6` (schema `commit`, default true) and commit nothing for `:already_enabled_here`/`:already_enabled_above`/`:not_enabled` or errors (`skill/CONTEXT.md`). All three stay on plain `commit_files/4`: one commit per call, never squashed.
- `write_context`/`edit_context` are the ONLY amend opt-in: they stage their own CONTEXT.md, append `"\n\nCommitted:\n" <> output` on success (else the helper's message verbatim), honour `commit: false` (default true), and consecutive CONTEXT.md edits amend the previous auto context commit; the message is exactly `"Update CONTEXT.md for <dir>"` for a single-file union, and several files add a blank line, `Files in this commit:` and one `- <repo-relative path>` line per path in order.
- `write` and `edit` NEVER commit — their bytes land only via a later commit.
- Auto-commit fallback: `Dispatch.commit_pending_in_worktree/0` runs `git add --all` + `Git.commit(wt, "Agent: auto-commit fallback")`, short-circuiting on a clean worktree and warning (not raising) on git errors; `Runner.refresh_commit_sha/1` re-reads HEAD afterwards so a fallback-only commit still reaches `merge_and_report/4` as a reviewable `genesis/agent_*` branch. Trigger sites: `EvoGit.Agent.Session.Worker.run/3`'s `after` block (every exit except `:brutal_kill`/VM shutdown) and just before every subagent spawn; the grace variant `maybe_recovery_auto_commit/1` commits `"auto-commit: turn-limit recovery"` and there git errors DO propagate (deliberate).
- `repo_root` is the MAIN working copy and `repo_path` the agent worktree, both resolved ONCE in `ToolDispatch.batch_execute_tools/5` and passed to tools as ARGUMENTS; every tool read/write is rooted at `repo_path`. There is no per-turn commit — per-turn git activity is only the recorded `current_commit`.
- Loss windows (no commit lands): `:brutal_kill`, VM shutdown, worktree reclaim/destroy, and the primary-repo boot wipe of orphaned `evogit-agent-*` branches; only `refs/genesis/archive/T<task>-A<local>-start|-final` survive.

### Completion attribution (NOT a tool)
`EvoGit.Agent.Completion.complete/4` (reached only via `Completion.Builder.finalize/2`) writes the `refs/notes/evogit` note on the final commit and, additionally gated on the task opt `archive: true`, the `refs/genesis/archive/…` refs plus ONE `task_agent_archives` row written streaming through `TaskRegistry.put_task_archive/1`; repo-less agents write neither.
Nothing rides `%Result{}`/the task `result`, a persistence failure only logs, and a crash/failure/abort writes no archive row (usage lost).
Contracts: `../../../CONTEXT.md` ("Task Archive") + `../../store/CONTEXT.md`.

### User-Defined Custom Tools
- Modules in `<config_dir>/tools/` loaded by `EvoGit.CustomTools` (`../../custom_tools.ex`) dispatch through the `execute_tool/5` catch-all: an unknown name goes there first (a configured custom tool wins over a same-named dynamic skill; `:unknown` continues to the skill lookup, then the unknown-tool error; user-code failures return `"Error: " <> reason`).
- They obey the same write gates (`write_tool?/1`), so a write-classified custom tool is blocked for repo-less agents and inside read-only foreign repos; they are never in `schemas/0`/`read_only_schemas/0` and each agent opts in through `available_tools/0`.

### Configurable shell
- `EvoGit.Platform.shell/0` resolves the effective shell with `[tools] shell` overriding the platform default (`bash` on Linux/macOS, `powershell` on Windows); PowerShell executables (`powershell`/`pwsh`) get `-EncodedCommand`, everything else `["-c", command]`.
- The model-facing name is `bash` on EVERY platform while the internal dispatch key stays compile-time pinned (`run_bash` on POSIX, `run_powershell` on Windows), because dispatch clauses, `@write_tools` and tests pin it.
- A 💡 hint is appended when a command redundantly invokes a nested shell (`/bin/sh -c '...'`, `bash -c '...'`, a bare `/bin/sh`) per `detect_redundant_shell/2`; `/bin/bash script.sh` and `sh script.sh` are not flagged.

### Main-copy mutation hard block (`shell_tool.ex`)
`do_execute/5` returns an `"Error: ..."` string BEFORE executing when a command BOTH `cd`s into `repo_root` (`Platform.safe_expand`-resolved exactly) AND matches `@mutating_git_regex` `\bgit\s+(checkout|switch|reset|merge|pull)\b`.
- Purpose: `cd <foreign_root> && git checkout evogit-agent-…` from a worktree would move the MAIN copy's HEAD onto the branch pre-merge (empty review diff).
- Only the exact `repo_root` blocks; the agent's own worktree, other worktrees under `.genesis/workers/`, and mutating git without a cd-into-root never block.
- `@cd_regex` also matches relative targets (`./x`, `../x`, `../../../`, `foo`), expanding them against `repo_path`; `detect_cd_warnings/3`/`redundant_cd?/3` compare resolved targets and exclude descendants of the agent's own worktree. Platform-agnostic — PowerShell `cd`/`Set-Location` is out of scope.
- `repo_root` must be non-nil for shell tools (`Platform.safe_expand/1` accepts binaries only, so the `repo_root \\ nil` default raises a `FunctionClauseError` before any command runs); the agent loop always supplies it.

### Shell Tool — raw execution, NO allow-list
- `execute/3` resolves `command` then branches: `run_in_background` truthy → `start_background_job/3`, else `execute_foreground/4` → `EvoGit.Sandbox.run_with_partial/7` with the command VERBATIM.
- NO allow-list/deny-list/sanitization exists here — any command runs with the user's privileges; the sole pre-execution gate is `main_copy_mutation_error/3` (foreground AND background), and `detect_cd_warnings/3`/`detect_redundant_shell/2` are post-execution hints.
- Invocation: POSIX `["-c", command]`; PowerShell `EvoGit.Powershell.invoke_args/1` = `["-NoProfile", "-NonInteractive", "-ExecutionPolicy", "Bypass", "-EncodedCommand", base64(UTF-16LE("& { … } *>&1"))]`.
- On Windows the child is `powershell.exe` DIRECTLY (no `cmd.exe /c`): `Port.open({:spawn_executable, …})` plus `Helpers.wait_for_os_pid/1`; the unbounded `run/4` path uses `System.cmd/3`. Timeout tree-kill reaches DESCENDANTS only (`taskkill /PID <pid> /T /F`), never an ANCESTOR — while an unsanitized model command such as `taskkill /IM erl.exe /F` CAN kill the backend BEAM, which leaves only a sidecar exit.
- **Timeout contract**: the schema advertises `timeout` as milliseconds or a string with a unit (e.g. `90s`/`30m`), default `@default_timeout` 120_000 ms, maximum = the CONFIGURED `[:scheduler, :max_tool_timeout]` (30 min by default) rendered from `max_timeout/0` at schema-build time; `ShellTool.effective_timeout/1` coerces through `Shared.fetch_duration_ms/2`, clamps to `max_timeout/0` (resolved at CALL time), and falls back to `@default_timeout` for an unusable/non-positive value, so a non-integer never reaches `run_with_partial/7`.
- An omitted value resolves through `max(120_000, [:scheduler, :default_tool_timeout])` for platform shell spellings (with `default_timeout_ms/1` as a pure-max floor), an explicit usable value always wins, and all values clamp to `max_tool_timeout`; other tools use `[:scheduler, :default_tool_timeout]` (10 s), and the full wrapper contract (write/sudo approval floor) lives in `../CONTEXT.md`.
- `timeout` is FOREGROUND-only: background starts ignore it (`run_in_background` is read first), so a bad value can never reject a start.

### Background Jobs — `bash` `run_in_background` + `job_output` / `job_list` / `job_kill`
The backend is `EvoGit.BackgroundJobs` (`../../background_jobs.ex`, supervised singleton) which owns records, output capture and reaping; the three tools pass through (`../../background_jobs/CONTEXT.md`).
- `bash` param `run_in_background` (boolean, no `"default"` key): truthy → the same main-copy guard, then `start_job/1` with `command:`, `cwd: repo_path`, `repo_root:`, `label:` (first line trimmed to 60 chars), `owner_pid: BackgroundJobs.current_owner_pid()`, `agent_id: Process.get(:evogit_agent_id)` and `task_id: Process.get(:evogit_task_id)`; success returns ONE line `started background job <id> — read its output with job_output using job_id "<id>"` (quoted via `inspect/1`; a record without a usable binary id degrades to `started background job unknown`), failure is `Failure.error/1` prose, and `timeout` is ignored — the generated `bash` description states the same contract model-facing (no timeout on a start; collect a slow job with ONE long wait instead of short re-polls).
- Owner fence: `current_owner_pid/0` (`Process.get(:evogit_agent_pid)`) is the ONE resolution site, passed to `read/2`/`list/1`/`kill/3` only when non-nil. Job ids are per-registry monotonic (`bash-1`, `bash-2`, …), skipping any candidate still held by a record OR a tombstone, so `bash-<n>` is what the agent repeats and what `Sandbox.Background.unit_name/1` embeds.
- `job_output`'s `job_id` is REQUIRED by the schema; an omitted/blank/non-string one is a TOLERANCE path that resolves THIS agent's own jobs (`list(owner_pid: current_owner_pid())`): exactly one job is read as if its id had been passed (full `wait`/budget/`max_bytes` behaviour), zero or several are actionable `Error:` prose (the several case names every id with status and label, newest first, at most 10 then `… and N more`, never advancing a read cursor), and a nil owning pid keeps the explicit-id error. An INFERRED read appends ONE trailing `[note: no job_id given — read the only background job <id>; pass job_id explicitly next time]` line after the status line, any tombstone note and any `[wait: …]` marker; an explicit-id read is byte-identical to before.
- `job_output` returns the delta since the previous read, a newline, then `[status: <status>]` or `[status: <status>, <detail>]` (`detail` = `exit code: N`, `killed (<reason>)`, …); an empty delta renders `(no new output)`; `max_bytes` defaults to `[:truncation, :tool_output_default_max_bytes]`.
- TOMBSTONES: a record the retention policy evicted while this agent still owns it answers HONESTLY instead of vanishing — the registry returns a job-shaped tombstone carrying `evicted_reason` (atom) and `evicted_at`, and both tools detect it through the ONE shared predicate `EvoGit.BackgroundJobs.Retention.tombstone?/1` (never a locally re-implemented key test).
- A tombstone `job_output` read renders the surviving log tail, the byte-identical status line, then ONE note line `[note: this job's record aged out of retention (<reason>); finished with exit code N; its log is at <path>]`, placed BEFORE any `[wait: …]` marker and the inferred-id note; the `finished with exit code N; ` clause is dropped when the record has no `exit_code`, `<reason>` renders the `evicted_reason` atom via `Atom.to_string/1`, `<path>` is `output_path`, and a tombstone whose log file is gone renders the registry's own `Error:` prose (no second sentence invented here).
- `wait: true` polls `job/2` IN THE TOOL TASK (never in the registry) until the status is terminal (`not in [:running, :stopping]`), the owning agent is gracefully cancelled, or the budget expires; a timed-out wait returns the delta so far and leaves the job RUNNING. Cancellation is re-checked each iteration through the TOTAL `EvoGit.AgentScheduler.Store.cancel_requested?/1`, so a cancelled agent never sits out a long wait.
- Poll cadence backs off: first sleep `poll_interval_ms()` (call-time seam `:background_poll_interval_ms`, default 100 ms), then ×1.5 per poll capped at 3_000 ms (`JobOutput.next_poll_delay/2`; a 0 ms base is floored to 1). Each poll is a cheap state read: an OS status probe runs OFF the registry process in its own unlinked task behind a per-job cache (`BackgroundJobs.StatusProbe`, re-probed at most every `:background_probe_min_interval_ms`, default 250 ms). Expiry can overshoot by the current poll delay (≤ 3 s): a best-effort budget, not a wall-clock deadline.
- Budget keys are read IN ORDER from `"timeout_ms"`, `"timeout"` (the generic spelling the rest of the surface uses) and `"timeoutMs"` through `Shared.fetch_duration_ms/2` (integer, float `trunc`, or numeric string with optional `ms`/`s`/`m`); a key present with an unusable value falls through to the NEXT key, the result is clamped into `[0, BackgroundJobs.wait_max_ms()]`, and no usable value means the effective default `BackgroundJobs.wait_default_ms()` (120 s; seam `:background_wait_default_ms`).
- `wait_max_ms()` = the configured `[:scheduler, :max_tool_timeout]` minus `BackgroundJobs.dispatch_headroom_ms()` (25_000), floored at 1_000 → 1_775_000 ms (~29.6 min) by default (test seam `:background_wait_max_ms`, positive integers only), so ONE long wait covers a genuinely slow job. `job_output`'s DISPATCH ceiling adds that same headroom back, landing exactly on `max_tool_timeout` (1_800_000 ms) so an honoured budget is never cut off.
- Marker lines follow the byte-identical `[status: …]` line (and a tombstone note, when present) when `wait: true` read successfully: `[wait: finished after <elapsed_ms> ms, status: <status>]` for a terminal job, `[wait: aborted after <elapsed_ms> ms — cancellation requested, status: <status>]` for a graceful cancel, else `[wait: <budget_ms> ms budget expired, status: <status>]` for an explicit budget or `[wait: <budget_ms> ms budget expired, status: <status>; pass timeout_ms (or timeout) to wait up to <wait_max_ms> ms ("<human>")]` for the default one, where `<human>` renders the cap as `29m35s`/`1m`/`8s`. `wait: false` and `Error: …` replies carry no marker, and the marker is what makes a silently-defaulted budget diagnosable.
- `job_list` takes no params and emits one `<id> [bash] <status> — <label>` line per job, else `(no background jobs)`; an aged-out row keeps that line and gains ONE trailing marker ` (aged out of retention; log at <path>)` (the `; log at <path>` clause is dropped when the record carries no path), while a normal row stays byte-identical.
- `job_kill` takes an optional `reason` and returns `requested cancellation of job <id>`, or `job <id> had already finished [status: …, <detail>]` for a finished job (the `{:already_finished, job}` tuple, not an error); either reply marks the job announced (no completion notice for a job the agent itself killed), while a later `job_output` still returns the output produced before the kill.
- `JobOutput.status_line/1` (`@doc false` public) is the ONE status formatter, reused by `JobKill`.
- Completion notices: `Runner.inject_background_job_notices/1` claims this agent's terminal unannounced jobs at the turn top (after compression and the pending-message drain, before the cancel-grace check and the LLM call) and appends ONE `:user` `[NOTICE]` message from `BackgroundJobNotice.notice/1` — one `- \`id\` — status (detail) — label` line per job plus a `job_output`/`job_list` hint, never output. The claim is a PURE ETS read of `BackgroundJobs.NoticeMirror` (exactly-once via atomic `:ets.take/2`, no registry call or timeout) then ONE cast recording the `announced: true` marks; every announcing path removes the mirror row, a backend-failure `Error:` from `job_kill` stays unannounced, and the claim is skipped during a grace period.
- Compression re-injects jobs ONLY on the stage-2 summarising refresh (one `## Background Jobs` snapshot via `BackgroundJobNotice.section/1`, earlier snapshots dropped); stage 1 and message #1 carry none.
- State is per-agent-process and in-memory, fenced by the agent pid: it survives turns and compression, dies with the agent (owner `:DOWN` kills the job) and is LOST on registry restart (`:unit` jobs keep running unreachable until the next boot sweep).
- All failures return `Failure.error/1` prose (an unknown id and another agent's job both point at `job_list`); `{:error, :not_found}` now means ONLY an id the registry never issued, because a pruned record answers as a tombstone instead of disappearing. All three take `(args, repo_path, repo_root)`, ignore the paths, never raise, and never call `String.to_atom/1` on input.

### Windows MSYS2 argv quoting — commit message files
Every tools-node commit uses `git commit -F <tempfile>`, never `-m <message>` argv, because git-for-Windows re-tokenizes double-quoted elements (the co-author trailer contains `<>`), yielding "unknown switch `>`" / "too many arguments" under MSYS2.
- The temp file lives under `EvoGit.Sandbox.resolve_tmpdir()` (not `System.tmp_dir!()`, which may sit outside the macOS sandbox profile) and must be sandbox-readable, since the git calls go through the sandbox.
- Naming invariant: `genesis_git_commit_msg_<System.pid()>_<unique_integer>.txt`, generated only by `Shared.commit_message_file_path/0`. The per-task tmpdir is SHARED across agents and BEAMs, so a pid-less name could collide and one process's `after File.rm/1` would delete the other's `-F` file mid-commit; `System.pid/0` is ASCII digits and `_` keeps the mapping injective. Regression: `test/evo_git/agent/tools/commit_files_test.exs` "commit_message_file_path/0".
- On Windows the path is normalized `\` → `/` (MSYS2 mangles backslashes). `try/after` removes the temp file; a write failure surfaces as `"Error: could not write temporary commit message file: ..."`.
- Callers consume `{:ok, output}`/`{:error, message}`, and `write_context`/`edit_context` render `"\n\nCommitted:\n" <> output` or the message. The adapter (`EvoGit.Adapters.Git.commit/2`) keeps its own inline `-F` pattern with `System.tmp_dir!()` (correct for raw `System.cmd`, wrong for sandboxed reads), so the two stay separate while both generators carry the OS pid (`../../adapters/CONTEXT.md`).

### Audit: other git invocations in this node
- `Shared.commit_files/4,5` — SAFE (`["add" | paths]` plus a `-F` tempfile under `resolve_tmpdir()`); `write_context`/`edit_context` go through that same helper (amend path), so this node has NO `-m` argv commit instance.
- `SearchHistory.do_search` — SAFE: `["log", format, commit_id, "--max-count=N", …]` (refs/flags only), with the user pattern applied by Elixir `Regex` after the log is fetched.
- `Git.execute` (run_git) — LATENT: it would pass LLM `sanitized_args` verbatim to `EvoGit.sandbox_run/4` and `fetch_array_arg/2` validates shape only, so `["commit", "-m", "…"]` would hit the MSYS2 class; a re-enable must intercept `-m`/`-F`.

### Windows-Only Runtime Hazards
- `edit` cannot edit CRLF files: the read tools strip `\r` from displayed lines while `perform_string_replace`/`find_actual_string` match byte-exactly, so with `core.autocrlf=true` every edit fails with "old_string not found in file" (agents fall back to `write`/`bash`).
- PowerShell/pwsh off PATH still works: `EvoGit.Executable.resolve/1` returns the BARE name when nothing is bundled, so `Sandbox.None.resolve_executable/1` reaches its WINDIR/ProgramFiles known-location fallback. Any OTHER `[tools] shell` value (or any other missing executable) off PATH raises `:enoent`, while Unix degrades to exit 127 through `bash -c`.
- Tool-level raises are CONTAINED by the managed runtime (`ToolRuntime.Executor.execute_tool_task/4` wraps `Tools.execute/5` and reports `Error: Tool execution crashed: …`), so a raising tool never kills the agent loop — but unvalidated args are still fatal to that call rather than a readable validation error.
- Port hazards (indexed in `../../CONTEXT.md`): `lsp.ex` unwraps `Port.info(port, :os_pid)` and closes via the idempotent `Helpers.close_port/1`; `web_fetch` opens no port, and binary-env hazards are exclusive to `Sandbox.None`'s Windows `Port.open` clause.
- `describe_exit_code/1` applies Unix `>=128` signal semantics on Windows, the redundant-shell regexes are POSIX-only (cosmetic), and a drive-letter case mismatch (`C:` vs `c:`) in `validate_file_scope/4` makes an in-repo path look outside-repo.
- Test gap: every Windows branch (`Sandbox.None.run_windows/3`, `run_with_partial_windows/5`, `EvoGit.Powershell`) is unexercised on Linux dev/CI.

### Legacy command shell & Genesis task tools (outside agent dispatch)
`Tools.execute/5` refuses the legacy `run_command` tool for EVERY caller, answering exactly `Error: use elixir_eval exact-code approval path`; `EvoGit.CommandShell.execute/1,2` (`../../command_shell.ex`) and `EvoGit.Agent.Tools.RunCommand.execute/3` stay live APIs outside agent dispatch, exercised directly by tests.
- `EvoGit.CommandShell` is a compile-time literal registry (no `Code.eval_string`, no input-derived module/function names, no `String.to_atom/1` on input, whitelist-only dispatch) with guardrails `@max_command_length` 4_000 / `@max_tokens` 40 / `@max_token_length` 2_000; entries carry a `level:` (1 = safe read-only, 2 = needs user attention, 3 = real side effects) and levels 2/3 are approval-gated at `run_command/3` for direct callers via `EvoGit.CommandApproval.request/5` (fail closed).
- Handlers keep `execute/3` and are called as `apply(module, :execute, [string_keyed_args, nil, nil])` — no schema, no dispatch clause, no approval check of their own (direct calls bypass the shell policy entirely): `ListTasks`, `GetTask`, `StartTask`, `CancelTask`, `ForceKillTask`, `DeleteTask`, `SpawnInvestigator`, `GuideUser`, `ListProjects`, `ListWorkspaces`, `ShowWorkspace`, `SystemInfo`.
- Output contract: a binary → `{:ok, output}`; `{:error, binary}` → a propagated shell error; anything else → `{:error, "Unexpected handler output: …"}`. Task-control handlers and `SystemInfo` cross their boundary through `Boundary`; the VCT readers need none because VCT reads are total.
- Handlers use the LOCAL `EvoGit.TaskRegistry`, ignore both repository-path arguments and have no node selector (a remote-node switch does not retarget them); they poll no cancellation, install no timeout and roll back nothing, any nonblank id is accepted (including the caller's own), `DeleteTask` reports success without checking, and `ListTasks`/`GetTask` read unbounded (`GetTask` trims objective/result to 2,000 chars afterwards).
- `SpawnInvestigator` validates `path`/`objective` (exists/directory/`.git` checks, NO git subprocess), then runs the deterministic, strictly READ-ONLY `SpawnInvestigatorProbe.investigate/2` and answers single `Error:` strings.
- Workspace reads render VCT mount metadata only: `ListWorkspaces` one `<point> | name: <name> | members: <refs> | description: <…>` line per workspace (or `No workspaces found.`); `ShowWorkspace` a header plus one line per RESOLVED member and `MISSING:`/`NESTED:` lines, `{:error, message}` for a blank/unknown key, a project/reserved mount or an unusable point.
- Command syntax and per-command arg specs live in the `EvoGit.CommandShell` registry itself; adding a command means one handler `execute/3` plus ONE registry entry (including its `level:`).

### Assistant Elixir evaluator (`elixir_eval`)
`EvoGit.Agent.Tools.ElixirEval` (`elixir_eval.ex`) exposes `schema/0`, `execute/3`, persona-facing `help/0`, `authorized_assistant?/0` and `authorize/0,1`; it is dispatch-only (absent from BOTH shared schema sets), serial at EVERY tier regardless of the file-write set, and reachable only by the reflective assistant's own schema list.
- Wrapper argument contract: `code` required, nonblank valid UTF-8, ≤ 16_000 bytes (engine ceiling 16_384), passed byte-identically to approval and engine, fresh bindings per call; `tier` an explicit string enum `read` (default)/`write`/`sudo` (a refusal never escalates); `target_node` a STRING equal to `current`, `local` or the exact current node name (explicit nil, atoms and remote targets rejected); `timeout_ms` a positive integer, default 2_000 clamped to 5_000 and bounding only the inner engine (dispatch allows the separate approval window via the write/sudo floor, `../CONTEXT.md`); `max_output_bytes` default 16_384 clamped to 256..65_536 including errors and truncation markers.
- Write/sudo run only on exact-code approval through `EvoGit.CommandApproval.request_eval/5`, revalidate authority around execution and cannot roll back; config edits replace the WHOLE config.toml (read/modify/save the full map, then call `EvoGit.AgentScheduler.RemoteAPI.reload_config/0` explicitly).
- Authorization, admitted MFAs/tiers, Dune shims and facades, quotas, disclosure limits, cleanup and the operator recipe are owned by `elixir_eval/CONTEXT.md`.

### StartTask opt-forwarding surface (shell task-start data plane)
`StartTask.start_task` forwards ONLY `:objective` (positional 2, default `""`), `:path`, `:mode`, `:resume_from`, `:starting_commit` and `:model_id` (raw strings via `maybe_put`, nil/`""` dropped) — plus the same text under `:prompt`, the key the genesis executor reads, for `:genesis` only; undeclared `key=value` tokens fall through as positionals.
It calls the LOCAL `EvoGit.TaskRegistry.start_task/2` through `Boundary` (validates nothing) → `TaskExecutor.execute_task/3`, the entry point the dashboard also uses; any downstream raise happens inside the spawned executor task and persists the task `:failed`.
NOT forwarded even though `RuntimeOpts.build_common_runtime_opts/3` consumes them downstream: `:build_system`, `:archive`, `:agent` (so `mode=custom` evolve raises), `:foreign_repos`, `:node_path`, `:model_id_locked`, reflect `:source_root`, evolve `:merge_from`/`:merge_target` and the extract_skills PR-context keys.
Quirks: `mode` defaults to `"simple"` (a genesis start without `mode=new|existing` raises) and is `type: :string`, not an enum; `:path` is optional here but `fetch!`ed for genesis/evolve/extract_skills (reflect bypasses it); `model_id=` forwards without the lock flag, so a model-selection script can still override it; `reflect`/`extract_skills` ignore the extra keys and `extract_skills` requires `path=`; StartTask tests cover reflect only.

### Duplication & Naming Audit (tool modules)
- Cross-cutting helpers belong in `Shared` (its anti-duplication home) or, when layer-agnostic, `EvoGit.Util.*`; `Boundary` is the one process-boundary guard and `Failure` the one error renderer.
- Known leftovers: `run_command.ex`/`elixir_eval.ex` carry their own boundary instead of `Boundary`; `positive_integer`/`now_ms` wrappers duplicate `EvoGit.Util.Coerce.positive_integer/2` and `EvoGit.Util.Time.now_ms/0`.
- `web_fetch.ex`'s `truncate/2` is NOT a `Shared.truncate/2` duplicate (it returns `{text, truncated?}` and emits `[truncated: first N of ~M characters]`); keep both and rename the private one.
- No built-in tool behaviour exists (only user tools implement `CustomTools.Tool`), so the implicit `schema/0` + `execute/3` contract drifts: `execute/4` via `node_path \\ nil` (`file_create`/`file_write`/`file_edit`/`make_dir`) or with `opts` (`lsp.ex`, `genesis_source.ex`) or a leading `name` (`genesis_tools.ex`), per-kind `read_/write_/edit_schema/0` (`context.ex`), and `schema/1` taking ignored `_opts` beside `schema/0` (`web_search.ex`).
- `CancelTask`/`ForceKillTask`/`DeleteTask` each wrap `Shared.describe_error/2` in a private one-line `describe_error/1` supplying a literal; call `Shared.describe_error/2` directly.
