# EvoGit Agent Behaviour & Tools

## Intent
Contains the `EvoGit.Agent` behaviour module, its LLM tool definitions, data structs for agent state and results, and extracted helper modules for context compression and subagent processing. Each agent is a transient Elixir module that `use EvoGit.Agent` and provides a system prompt, optional tool overrides, and subagent delegation configuration. The `use` macro injects thin defaults and overridable callbacks; the actual agent loop logic lives in the shared `EvoGit.Agent.Runner` module (extracted from the macro).

**Note:** Agent type implementations (Manager, Executor, etc.) live in `../agents/`.

## Routing Table
- `./tools/` → LLM tool modules (17+ tools for file I/O, context, search, shell, etc.)
- `./runner.ex` → `EvoGit.Agent.Runner` — shared agent loop runner (run/3, do_run/2, loop/1, do_turn/1, effective_tools/1, trigger_recovery/2, enter_grace/3, maybe_enter_cancel_grace/1, etc.)
- `./subagent_schemas.ex` → `EvoGit.Agent.SubagentSchemas` — shared subagent tool/schema generation (tools/1, schemas/1), parameterized by agent_module
- `./context_compression.ex` → Context compression helper (compresses chat history when token threshold exceeded)
- `./subagent_processing.ex` → Subagent call processing (builds specs, spawns subagents, merges results)
- `./loop_state.ex` → `LoopState` struct — agent loop state threaded through every turn
- `./result.ex` → `Result` struct — structured output of a completed agent run
- `./output_sanitizer.ex` → Tool output sanitization (UTF-8 repair, ANSI stripping, progress bar removal, configurable truncation)

## API Surface

### Data Structs
| Struct | Purpose |
|---|---|
| `EvoGit.Agent.LoopState` | Agent loop state (enforced keys: `agent_id`, `agent_module`, `depth`, `node_path`, `context`; remaining fields have defaults). Threaded through every turn. |
| `EvoGit.Agent.Result` | Structured result of a completed run (`result`, `commit_sha`; optional `tag`, `branch`, `base_commit`, `repo_id`, `foreign_repo_commits`). `repo_id` identifies which repo the result belongs to (`"primary"` or a foreign repo string), populated from the process dictionary. `foreign_repo_commits` = `%{repo_id => latest commit SHA}` for work done in foreign repos (default `%{}`; the scheduler stream injects values, the runtime stream reads it for the per-repo report). Produced by `CompleteTask`. |

### Helper Modules
| Module | Purpose |
|---|---|
| `EvoGit.Agent.ContextCompression` | Compresses chat history when `total_tokens` exceeds threshold |
| `EvoGit.Agent.SubagentProcessing` | Spawns subagents, resolves cross-repo paths, merges results via octopus merge, formats results for LLM context. Foreign-repo subagent phylo nodes (`build_subagent_phylo_node/7`): starting-commit precedence = per-repo `base_sha` (task-level starting commit, non-nil wins) → tracked commit from the `foreign_repo_commits` map (previous subagent's latest commit in that foreign repo) → foreign repo HEAD; an unresolvable `base_sha` or a missing/non-git foreign repo root returns a descriptive `{:error, msg}` (surfaced as `{:error, {call, index, msg}}`) — never a MatchError crash |
| `EvoGit.Agent.TurnWarning` | Adaptive turn-budget warnings — 3 positional categories (beginning/end/critical) scaling with max_turns, plus a periodic middle reminder based on turns since last subagent delegation. `:beginning` delegation-strategy warning fires at ~25% of budget (min turn 6); `:middle` reminder fires every 15 turns (`:high`) / 45 turns (`:low`). Low-level agents (Executor, TaskScheduler, etc.) skip `:beginning` and have a 3x longer middle reminder interval |

### Tool Library (`EvoGit.Agent.Tools`)
| Component | Role |
|---|---|
| `tools.ex` | Central dispatch: `schemas/0` returns the STANDARD tool schemas (every `use EvoGit.Agent` coding agent's default `available_tools/0`), `execute/5` dispatches by name. Self-reflective/task-control tools are dispatch-registered ONLY — NOT in `schemas/0` (see Repo-less Agents) |
| Standard tools | `read_file`, `create_files`, `write_file`, `edit_file`, `make_dir`, `read_context`, `write_context`, `edit_context`, `run_bash`, `rg`, `glob`, `list_dir`, `search_web`, `search_context`, `search_history` |
| System Control tools | `list_tasks`, `get_task`, `start_task`, `cancel_task`, `force_kill_task`, `delete_task`, `guide_user` — task-registry read/control + user-guidance tools in `agent/tools/` (`EvoGit.Agent.Tools.ListTasks` etc.); dispatch-registered only, exposed via the SelfReflective agent's explicit `available_tools/0`, never in `Tools.schemas/0` |
| `subagent_investigator` | Placeholder tool (`EvoGit.Agent.Tools.SpawnInvestigator`) — dispatch-registered only (never in `Tools.schemas/0`; name collides with the real `SubagentSchemas` subagent tool); `execute/3` does NOT spawn — tells the agent to use its own read-only tools |
| `CompleteTask` | Special completion tool injected by `use` macro; returns `%Result{}` |

### Delegation Hinting

Two independent hinting mechanisms, both per-child-directory counter + fire-once:

- **Write-tool hint**: agent repeatedly *edits* files below its `node_path`; after the write-tool count per child dir exceeds `delegation_hint_threshold` (default 5, `[:scheduler, :delegation_hint_threshold]`), a nudge is appended to tool output suggesting a subagent for that child directory.
- **Read-tool hint**: a `:high`-level agent repeatedly reads/investigates a child dir (via `read_file`, `rg`, `glob`, `list_dir`); after the count (`read_delegation_hints`) exceeds `read_delegation_hint_threshold` (default 8, `[:scheduler, :read_delegation_hint_threshold]`), a nudge suggests `subagent_investigator`. `:low` agents are expected to read directly.
- Both hints show once per child dir (`hint_shown` flag); suppressed during merge-conflict resolution (`filter_child_paths_if_conflicts/2`). Implemented in `EvoGit.Agent.ToolDispatch` + `EvoGit.Agent.DelegationHints`: `batch_execute_tools/4`, `extract_child_paths/4` (target child dir from write-tool args), `maybe_append_delegation_hint/4`. Hints stored in `LoopState.delegation_hints`, threaded via process dictionary.

## Design Decisions

### Parallel standard tool call execution (bounded by scheduler tool slots)

Standard (non-subagent) tool calls in a batch execute **in parallel**, governed by the scheduler's tool-slot pool (`max_tool_concurrency`, default 2; `--tool-concurrency` CLI flag / `[scheduler] max_tool_concurrency` TOML). Subagent calls also run in parallel (`SubagentProcessing.process_subagent_calls`). `batch_execute_tools/4` uses `Task.async_stream`: `max_concurrency` = batch size (positive integers only — the scheduler, not a local cap, is the binding constraint), `ordered: true`, `timeout: :infinity` (per-tool timeout stays inside `execute_tool_with_timeout/7`, which wraps its own `Task.yield(task, tool_timeout) || Task.shutdown(task)` — an outer stream timeout would kill long-running tools). Tool-slot acquisition (`AgentScheduler.with_tool_slot/2`) happens per call inside `execute_tool_with_timeout/7`. Only raw tool execution runs in the parallel tasks; delegation hints are threaded in index order in the parent via `Enum.reduce` (`apply_tool_output_tracking/3`), keeping hint accumulation deterministic — same for the once-per-run redundant-cd warning (`:redundant_cd_warned` process-dict flag).

**Caveat — parallel committing tools:** `write_context`/`edit_context`/`make_dir` with `commit: true` run git add/commit in the same worktree; parallel execution may contend on git's `index.lock`. `max_tool_concurrency` (default 2) bounds this; lower it if contention appears.

### Grace Period & Graceful Cancellation (runner-side)

Two grace kinds, both entered via `Runner.enter_grace/3` (`runner.ex`, `@doc false`): (1) `maybe_recovery_auto_commit/1` FIRST (best-effort auto-commit of uncommitted work — for cancel this is "save the changes"), (2) optionally appends a recovery message, (3) sets `in_grace_period: true` + the `grace_turns_remaining` budget, then re-enters `loop/1`.

- **Turn-limit recovery** (`trigger_recovery/2`, call site `loop/1`: `"max turns (#{max_turns}) exceeded"`): budget **1** — one continue attempt → hard-stop. Appends the "exceeded the execution limit" warning (`message: :default`).
- **Cancel-grace** (`maybe_enter_cancel_grace/1`, called in `loop/1` immediately AFTER `drain_and_inject_user_messages/1`): when the ETS `cancel_requested` flag is set (scheduler-side graceful cancel), the flag is cleared and the agent enters grace with budget **3** and `message: nil` — NO extra recovery message (the cancel message was already injected via the `pending_user_messages` drain). Up to 3 turns to wrap up and call `complete_task`.
- **Budget semantics**: `LoopState.grace_turns_remaining` defaults to `0` (not in grace). Each turn ending WITHOUT `complete_task` decrements it via `consume_grace_turn/1` at the three call sites in `tool_dispatch.ex` (`handle_protocol_violation`, the `process_llm_response` `{:error, :protocol_violation}` branch, `continue_after_tools`). `grace_period_continue_failed?/1` (`agent.ex`): `in_grace_period: true, grace_turns_remaining: n` → `n <= 1` (counter 0 — the struct default — hard-stops); true → call sites return `{:error, :recovery_failed}`.
- **complete_task during grace**: `handle_complete_call`'s dirty-workspace check skip (`not state.in_grace_period and ...`) applies to BOTH kinds — completing with a dirty workspace is allowed during any grace period.
- **Turn counts**: cancel-grace 3 → 3→2, 2→1, 1 → hard-stop (3 grace turns). Turn-limit 1 → hard-stop on the first continue (1 grace turn). `trigger_turn_limit_recovery?/1` returns `false` during grace.

## Update-Timing Safety (in-flight state vs BEAM restart)

- **No turn-level wall-clock timeout.** A turn = LLM call(s) + tool executions + subagent waits, with NO overall cap. Per-piece bounds: per-LLM-attempt stream receive timeout 30s default (`:req_llm` `receive_timeout`/`stream_receive_timeout`, thinking models 300s via `thinking_timeout`) + pool checkout `stream_pool_timeout` 300s (runtime.exs) + ReqLLM inner retries (3× for 429/transport) + the outer `call_llm_with_retry` backoff (max_retries default 15, delays 0→60s cap ≈ 9 min worst-case); per-tool timeout `min(requested, max_tool_timeout)` with `default_tool_timeout` 10s / `max_tool_timeout` 30 min hard cap (definitions.ex:121-139); subagent waits unbounded (parent blocks). **Consequence: the 3-turn cancel-grace budget is bounded in TURNS, not wall-clock** — a slow LLM stretches a graceful cancel arbitrarily long. Hard stops: `max_turns` (default 128) and the grace budget.
- **Per-turn ETS checkpoint, in-memory only.** `context.messages` lives in the agent process heap (`%LoopState{context}`); a snapshot is written to ETS (`AgentState.context`) each turn at `batch_update_agent` (tool_dispatch.ex:389-394) and after compression/warnings (runner.ex:281-284) and the pending-message drain (runner.ex:260). Named ETS dies with the VM — **there is NO durable checkpoint of the conversation**; on BEAM restart the whole conversation is lost. The dashboard's `get_agent_history` reads this ETS snapshot.
- **Worktree wipe at next boot.** Uncommitted worktree changes survive the kill on disk, but `WorktreeManager.maybe_init_repo/1` (worktree_manager.ex:236-283) — on the FIRST `create_worktree_for_agent` request for a repo after restart — does `rm_rf .genesis/workers` → `Git.prune_worktrees` → `clean_orphaned_branches` (deletes all `evogit-agent-*` branches, worktree_manager.ex:376-390). Commits made only on an agent branch (never merged/archived) are destroyed at next boot's first worktree creation. Only commits protected by `refs/genesis/archive/T<task>-A<local>-start/-final` refs (written by `CompleteTask.complete/4` when `archive` is enabled AND the agent completed) survive.
- **`Runner.run/3`'s `after` block** (runner.ex:48-52) runs `Dispatch.commit_pending_in_worktree/0` ("Agent: auto-commit fallback", dispatch.ex:265-306) on ANY agent-process exit — normal completion, `{:error, :recovery_failed}` hard-stop, and crashes (raises). It does NOT run on `:brutal_kill` (force kill) or VM shutdown — a graceful-cancel hard-stop salvages the worktree via this after-block commit, a killed BEAM loses it.
- **Task status on restart**: orphaned `:running` tasks are untouched until lease expiry (`:lease_sweep` → `:failed` "Lease expired; owning instance no longer renewing"); orphaned `:finalizing`/`:cancelling` are reconciled at TaskRegistry init (`:failed` / `:cancelled` with "Runtime restarted during ..." results). See `task_registry/CONTEXT.md`.

## LLM Request Retry Mechanism (3 layers)

**Layer 1 — EvoGit outer loop (`call_llm_with_retry/5`, `tool_dispatch.ex:187-225`):** `retry with: exponential_backoff(1_000) |> randomize() |> cap(60_000) |> Stream.take(max_retries)` (tool_dispatch.ex:189-193) with `AgentScheduler.with_llm_slot(agent_id, fn -> ... end)` INSIDE the retry block — each attempt acquires the LLM slot for ONE `ReqLLM.stream_text` + `process_stream` and releases it (via `with_llm_slot`'s `after`) before the backoff sleep runs. Retry-library semantics (`deps/retry`): `delays_from/1` prepends `[0]`; `Enum.reduce_while` sleeps then runs the block per element; `{:ok, _, _}` halts, `{:error, _}` continues (`atoms: [:error]`). Effective delays: 0, ~1s, ~2s, ~4s, ~8s, ~16s, ~32s, then 60s×N, randomized ±10% (`randomize/1`, delay_streams.ex:101-111). **Total attempts = `max_retries + 1`**. `max_retries` = `agent_state.max_retries` (tool_dispatch.ex:102), set from scheduler `state.max_retries` at dispatch (`dispatch.ex:79`), config default **15** (`[scheduler] max_retries`, definitions.ex:63-71). **No error-type discrimination** — every `{:error, reason}` retries identically (429 == 5xx == timeout == connection error). After the stream is exhausted, `case` at tool_dispatch.ex:213-223 checks `EvoGit.Agent.TruncationFeedback.is_rate_limit_error?(reason)` (string-substring match on `inspect(reason)` for `"rate_limit"`/`"quota"`/`"429"`/`"resource_exhausted"`, truncation_feedback.ex:16-23) → `AgentScheduler.report_llm_error(agent_id, :rate_limit)`; then `{:error, reason}` propagates to `prompt_until_tools_or_limit/5` which **RAISES** `"LLM request failed after N retries"` (tool_dispatch.ex:177) → agent crash → scheduler crash-retry (`agent_max_retries`, default 3, lifecycle.ex:148-186). Retried agents get a fresh worktree + new turn; their next slot request is queued behind the backoff if one is active. A model with 0 LLM slots (peak hard-pause) does NOT raise: its slot request BLOCKS (queued in the scheduler — agent status `:blocked`) until capacity returns (peak exit → `update_config` → `grant_pending_on_resume` grants queued waiters) or a force-kill purge replies `{:error, :cancelled}` (raises in `with_llm_slot` → agent crash → scheduler crash-retry/cancel machinery). `rescue_only: []` stays because the remaining raise paths must propagate immediately, not be retried through exponential backoff.

**Layer 2 — ReqLLM inner retries (inside each `ReqLLM.stream_text/3`):** `ReqLLM.Streaming.Retry` (`deps/req_llm/lib/req_llm/streaming/retry.ex`, wired at `finch_client.ex:188`). `max_retries` default **3** (retry.ex:31; `finch_client.ex:238` — overridable via `[[llm.models]]` generation params `max_retries`). Only retried: (a) **HTTP 429** — delay = parsed `Retry-After` header (seconds→ms; missing/unparseable/zero → 1000ms; retry.ex:194-196, 211-245); (b) **transport errors before any body data** (`data_received?: false`) — `pool_not_available` → 250ms, `closed`/`timeout`/`econnrefused` → 0ms (retry.ex:86-92, 198-209; failure.ex:8). **5xx and other HTTP statuses are NOT retried at this layer** (`%ReqLLM.Error.API.Request{}`; retry.ex:76-108), and no retry once data has started streaming (avoids duplicating partial output). Inner retries use blocking `Process.sleep` (retry.ex:123-125). Non-streaming Req-based paths (e.g. `openai_codex`) use `ReqLLM.Step.Retry` (`step/retry.ex`) — same 429 Retry-After honoring, transient transport reasons → 0ms, `max_retries` default 3.

**Layer 3 — scheduler per-model backoff (fires only AFTER the outer loop exhausts):** `AgentScheduler.report_llm_error/2` (agent_scheduler.ex:286-289; handler 880-886) → `Slots.handle_report_llm_error(agent_id, :rate_limit, state)` (slots.ex:162-182): sets per-model `llm_backoff_until[model_id] = now + 60_000`, re-queues ALL waiting agents of that model with the backoff timestamp, schedules `:retry_llm_waiting` in 65s (slots.ex:179 → slots.ex:194-198 → `grant_pending_llm_slots`). New slot requests during backoff are queued (slots.ex:105-109). Non-`:rate_limit` reports are no-ops (slots.ex:184-186). Expired backoffs clear on any grant path (`maybe_clear_model_backoff/2`, slots.ex:492-508). **Scoped per model_id — NOT global** (a rate-limited model doesn't block other models).

**Slot acquired/released PER ATTEMPT — free during backoff sleeps:** `AgentScheduler.with_llm_slot/2` (agent_scheduler.ex:322-332) acquires via blocking `GenServer.call` (`request_llm_slot`, `timeout: :infinity`, agent_scheduler.ex:262-265) and releases via `after` → `release_llm_slot/1` cast (agent_scheduler.ex:277-280). Each attempt holds the slot only for its single `stream_text` + `process_stream`; the outer exponential-backoff sleep (and any inner Retry-After sleep) happens BETWEEN attempts while the slot is FREE. **Pause-scheduler implication:** a retrying agent's next attempt blocks at slot re-acquisition when `AgentScheduler.pause/0` is active (queued `:blocked`, granted on `resume/0`) — pause takes effect within one backoff delay. A raise inside the LLM call propagates immediately: `with_llm_slot`'s `after` releases the slot; the retry macro only retries `{:error, _}` tuples, never raises. `ContextCompression` also uses `with_llm_slot` (context_compression.ex:79-103) but WITHOUT the outer retry loop — single `stream_text` (inner 3-retry only).

## First Message Construction (objective → LLM) — single choke point

The objective (`AgentState.objective`, a plain `String.t()`) enters the conversation ONLY inside the first **user** message, built in `Runner.do_run/2` (`runner.ex:55-156`). Exact construction at `runner.ex:99-110`:

- `objective_body = if blank?(objective), do: "", else: to_string(objective)` (`runner.ex:110`)
- `combined_prompt` = `ContextBuilder.context_block(context_body)` (context tree + foreign-repos section + repo-notes section) joined with `ContextBuilder.objective_block(objective_body)` via `"\n\n---\n\n"` (`runner.ex:105-119`; wrappers at `context_builder.ex:74-85` emit `<context>...</context>` / `<objective>...</objective>`)
- **`runner.ex:121`**: `context = ReqLLM.Context.new([system(agent_module.system_prompt()), user(combined_prompt)])` — the ONLY place the objective is turned into an LLM message. The system message is `agent_module.system_prompt()` only; the objective is never a system message.

**Repo-notes section (git-submodules awareness)**: when the repo has git submodules, the `<context>` block includes a `## Git Submodules` note — the rendered markdown block in `AgentState.repo_notes` (set at root spec build by `EvoGit.Runtime.Helpers.load_repo_notes/2`, inherited by subagents), passed through `ContextBuilder.build_repo_notes_section/1` (`context_builder.ex`). It lists the gitlink paths, explains they arrive as empty placeholder dirs in agent worktrees, tells the agent to populate them with `git submodule update --init [--recursive]` (network required; shared clone in `.git/modules`), and warns never to delete the placeholder dirs, not to create filler files inside them, and not to commit inside submodules. When `repo_notes` is nil (no gitlinks or detection failed) the section renders `""` and the blank-filter drops it — prompts for repos without submodules stay noise-free.

The per-turn LLM call receives the whole `%ReqLLM.Context{}` by value — `ToolDispatch.do_turn/5` → `prompt_until_tools_or_limit(context, ...)` (`tool_dispatch.ex:131`) → `call_llm_with_retry(context, tools, llm_gen_opts, agent_id, max_retries)` (`tool_dispatch.ex:195`) → `ReqLLM.stream_text(current_model(), context, Keyword.merge([tools: tools], llm_gen_opts))` (`tool_dispatch.ex:204-208`). Messages are never re-assembled per call; all other construction sites (turn warnings `runner.ex:221,234`, pending-user-message drain `runner.ex:253`, grace/recovery messages `runner.ex:368,377` — which re-inject the objective text via `recovery_warning_message/2` at `runner.ex:414-435` — no-tool-call nudges `tool_dispatch.ex:246-260`, tool results, compression `context_compression.ex:74,87-90`) only APPEND. Context compression preserves `[system_msg, initial_user_msg | _rest]` verbatim (`context_compression.ex:69,90`), so anything injected into the first user message survives compression but permanently occupies the context window.

**File-attachment injection point**: `runner.ex:99-110`. Two viable shapes: (a) string-based — append converted text (e.g. PDF/DOCX extraction) as another block in `combined_prompt` (or a third `<attachment>` block) — works with every provider, no struct changes needed; (b) multimodal — replace `user(combined_prompt)` with `user([ContentPart.text(combined_prompt), ContentPart.file(data, filename, media_type)])` — ReqLLM supports this end-to-end (`ReqLLM.Context.user/1` accepts a part list, `context.ex:276-283`; `ContentPart.file/3` at `message/content_part.ex:78-79`; OpenAI-compatible encoder emits base64 data URIs for raw file data, `provider/defaults.ex:1055-1072`). NOTE: `objective` is strictly `String.t()` in `AgentSpec` (`agent_spec.ex:36`) and `AgentState` (`agent_state.ex:77`), written at `dispatch.ex:83` and passed as a plain spawn arg at `dispatch.ex:230` — carrying attachment metadata per-agent would require a NEW `AgentState` field (+ dispatch population, + `RemoteAPI`/codec awareness if it must cross distribution). Embedding attachment paths/text in the objective string itself requires no struct changes. No objective-size truncation exists anywhere (CLI `get_input/2` reads `-f file` verbatim, `cli.ex:136-152`); the only conversation-level limit is `[:llm, :compression_threshold_tokens]` (default 100_000, `config/schema/definitions.ex:152-160`).

## Constraints
- Every agent MUST `use EvoGit.Agent` and implement `system_prompt/0`.
- System prompts MUST NOT contain dynamic state, objectives, or context trees — those are injected as user prompts.
- Read-only agents (`agent_type: :read`) should restrict `available_tools/0` to read-only tools.
- The `complete_task` tool is always injected by the macro; agents need not include it.
- Tool schemas use `ReqLLM.tool/2` format.
- Agents commit before delegating subagents (enforced by auto-commit fallback in scheduler).
- Context compression and subagent processing are extracted to dedicated modules but invoked from the agent loop via callbacks.
- **LoopState discipline**: Agent loop state must always be a `%LoopState{}` struct. Update syntax preserves the struct type.
- **Result discipline**: Agent completion produces `%Result{}` structs. Consumers pattern-match on struct fields rather than using `Map.get/2`.

## Repo-Path Assumptions (agent-loop crash points on a missing repo)

The agent loop hard-assumes a real git worktree, set once by `Runner.setup_dispatch_context/1` (`runner.ex:158-211`): `Process.put(:repo_path, worktree_path)` (`runner.ex:179`), `:genesis_repo_root`, `:evogit_repo_id`, `:evogit_agent_id`, `:evogit_agent_depth`, `:evogit_started_at`, `:custom_agent_id` (from `spec.opts`). The same function UNCONDITIONALLY requests a fresh worktree via `WorktreeManager.create_worktree_for_agent/6` and RAISES `"Failed to create worktree..."` on `{:error, reason}` (`runner.ex:188-201`) — a repo-less agent type must branch here (the worktree-creation and `resolve_agent_repo_root` seams live on the scheduler side; see `../agent_scheduler/CONTEXT.md` → "Repo-path assumptions").

Within the agent loop, the following raise on nil/missing `:repo_path` (all `|| raise "repo_path not in process dictionary"` or git-error raises) — relevant to a future repo-less agent:
- `sync_and_get_current_commit/1` (`tool_dispatch.ex:68-85`) — `Git.rev_parse(repo_path)` raises on git failure; a missing repo/worktree directory (`{:error, {:enoent, _}}` from `Git.run/2`'s pre-check) raises a clear "Worktree vanished while agent was running (removed mid-run): ..." message (shared `raise_rev_parse_error/1` helper, same hardening as `sync_current_commit_after_tools/1`); all other error shapes raise `"Git rev_parse failed (#{code}): #{msg}"`. Called from `do_complete/2` (`tool_dispatch.ex:703`) — **so `complete_task` unavoidably crashes a repo-less agent at completion** — and from `sync_current_commit_after_tools/1` (`tool_dispatch.ex:50-65`), which runs after EVERY standard-tool batch (`process_standard_calls`, `tool_dispatch.ex:804`) and after subagent processing (`sync_commit_fn`).
- `batch_execute_tools/4` (`tool_dispatch.ex:812` `repo_path` raise; `process_standard_calls` `tool_dispatch.ex:793` raises on nil `:genesis_repo_root`) — any standard tool call requires BOTH keys present.
- `do_run/2` validates `Path.join(repo_path, node_path)` exists (`runner.ex:62-70`) → `{:error, :path_not_exist}` if not.
- `do_commit_pending/1` in `AgentScheduler.Dispatch.commit_pending_in_worktree/0` (scheduler side, dispatch.ex:271-312) is the ONE repo-dependent path that is already repo-less-safe: nil `:repo_path` → no-op `:ok`; non-git dir → `Git.status` returns `{:error, {128, _}}` → logged warning, returns `:ok`. Called from `Runner.run/3`'s `after` block (`runner.ex:51`) and `SubagentProcessing.process_subagent_calls/3` (`subagent_processing.ex:60`).
- `CompleteTask.complete/4` (`tools/complete_task.ex:128-190`): `%Result{}` construction sets `commit_sha` (enforced key), `branch` (derived from ETS `lookup_task_info/1` — repo-free, `{:error, :not_found}` → `{0, nil, 0}`), `repo_id` (`Process.get(:evogit_repo_id)`), `usage`; `tag/base_commit/agent_count/archive_records` stay nil. Git-note (`add_metadata_note`) and archive-ref writing (`write_archive_refs`) are both gated on `base_commit` (from `phylo_node`), so a repo-less agent with a nil phylo_node skips them naturally. The dirty-workspace check `CompleteTask.check_workspace_dirty/1` is tolerant (`_ -> {:clean, nil}` on git errors).

## Repo-less Agents

A repo-less agent runs WITHOUT a git worktree (chatbot-style). It is marked via `Process.get(:repo_less)` (set by the runner) and its `Process.get(:repo_path)` points at the real Genesis source root or a placeholder binary (not a worktree). Cardinal rule: **repo-less agents must never touch git or write files.**

- **Write guard**: `EvoGit.Agent.Tools.execute/5` (`tools.ex`) blocks all write tools for repo-less agents, returning `"Error: this agent has read-only access to the system — the <name> tool is disabled."`. The blocked set is the `@write_tools` module attribute (`create_files`, `write_file`, `edit_file`, `make_dir`, `write_context`, `edit_context`, `run_bash`, `run_powershell`, `run_git`, `curl`, `skill_add`, `skill_edit`, `skill_remove`, `skill_enable`, `skill_disable`). Both `execute/5` argument paths (map args and the JSON-string decode fallback) route through the shared `maybe_block_repo_less/5` helper, so there is no bypass. Chained AFTER the repo-less guard is the **foreign-repo role gate** `maybe_block_read_only_foreign_repo/5` (same `tools.ex`): it resolves the agent's repo role from the process dict (`:foreign_repos` — populated by `Runner.setup_dispatch_context/1` from `AgentSpec.foreign_repos` — via `:evogit_repo_id` id-match with a `ForeignRepo.resolve_path/2` root-path fallback) and blocks every `@write_tools` entry when the agent operates inside a foreign repo whose `writable` is not literally `true` (read-only foreign repos are for investigation only). `Shared.validate_file_scope/3` (`tools/shared.ex`) adds a path-level defense-in-depth check: a write target path that resolves to a read-only foreign repo is rejected before the scope check. `read_only_schemas/0` no longer includes `Curl.schema()` (no legitimate read-only role); it keeps `Context.write_schema`/`edit_schema` + `ShellTool` by design — read-only agents' write usage in read-only FOREIGN repos is blocked by the role gate, while CONTEXT.md updates and `mix test` in their own repo remain allowed.
- **System-control tools**: `list_tasks`, `get_task`, `start_task`, `cancel_task`, `force_kill_task`, `delete_task`, `guide_user` (and the `subagent_investigator` placeholder) live in `agent/tools/` (`EvoGit.Agent.Tools.ListTasks`, `GetTask`, `StartTask`, `CancelTask`, `ForceKillTask`, `DeleteTask`, `GuideUser`, `SpawnInvestigator`). They are **dispatch-registered only** (`execute_tool/5` in `tools.ex`) and exposed to agents via the SelfReflective agent's explicit `available_tools/0` list — they must NOT be added to `Tools.schemas/0`, which every `use EvoGit.Agent` coding agent receives by default (`SpawnInvestigator.schema()`'s name `subagent_investigator` collides with the `SubagentSchemas` subagent tool for any agent with an Investigator subagent → provider 400 "Tool names must be unique"). Regression-pinned by `tools_test.exs` (uniqueness + absence assertions).
