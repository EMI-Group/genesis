# EvoGit Agent Behaviour & Tools

## Intent
Contains the `EvoGit.Agent` behaviour module, its LLM tool definitions, data structs for agent state and results, and extracted helper modules for context compression and subagent processing. Each agent is a transient Elixir module that `use EvoGit.Agent` and provides a system prompt, optional tool overrides, and subagent delegation configuration. The `use` macro injects thin defaults and overridable callbacks; the actual agent loop logic lives in the shared `EvoGit.Agent.Runner` module (extracted from the macro).

**Note:** Agent type implementations (Manager, Executor, etc.) live in `../agents/`.

## Routing Table
- `./tools/` → LLM tool modules (17+ tools for file I/O, context, search, shell, etc.)
- `./runner.ex` → `EvoGit.Agent.Runner` — shared agent loop runner (run/3, do_run/2, loop/1, do_turn/1, effective_tools/1, trigger_recovery/2, enter_grace/3, maybe_enter_cancel_grace/1, etc.)
- `./subagent_schemas.ex` → `EvoGit.Agent.SubagentSchemas` — shared subagent tool/schema generation (tools/1, schemas/1) + the subagent-type → implementation-module resolver `subagent_module_for/2`, parameterized by agent_module
- `./context_compression.ex` → `EvoGit.Agent.ContextCompression` — the TWO-STAGE compression orchestrator behind `compress_if_needed/2` (window-relative trigger over the CONFIGURED `:llm_context_window` → hard-gated stage-1 tool-result prune → summarising checkpoint over the ORIGINAL context), called at the top of `./runner.ex`'s `loop/1`
- `./compression/` → the compression sub-modules the orchestrator composes — `Recency` (shared last-K-turns boundary), `ToolResultPruner` (stage 1, model-free), `Threshold` (window-relative trigger + stage-1 target), `SummaryPrompt` (the 8-section summary instruction + checkpoint delimiters), `Checkpoint` (stage 2 span replacement), `LlmRetry` (the bounded stage-2 slot-per-attempt retry loop) — detail in `compression/CONTEXT.md`
- `./completion_protocol.ex` → `EvoGit.Agent.CompletionProtocol` — pure turn classifier (`classify/1` → `{:tool_calls, calls} | {:text_reply, text} | :empty`) shared by the dispatcher and the empty-response nudge path; `report_text/1` reads the reply through `ReqLLM.Response.text/1` (so `:thinking` parts are never promoted to the report); TOTAL over any input — the `ReqLLM.Response`/`%ReqLLM.Message{}`/LIST-`:content` shape is checked BEFORE the ReqLLM accessors run, so a nil or missing message, `content: nil` or non-list content is `:empty` instead of a `Protocol.UndefinedError`/`FunctionClauseError`
- `./tool_invocation.ex` → `EvoGit.Agent.ToolInvocation` — pure per-call preparation at the dispatch boundary: the tolerant three-stage arguments parse (`arguments/1`, `arguments_map/1`, `invalid_arguments_result/1` — the call SHAPE is checked before any `ReqLLM.ToolCall.*` accessor, so a non-`%ReqLLM.ToolCall{}` value takes the "nothing recoverable" stage: `{:error, _}` / `%{}`) and the per-call timeout rule (`resolve_timeout/4`, `default_timeout/2`, `shell_tool?/1`)
- `./tool_names.ex` → `EvoGit.Agent.ToolNames` — the tool-NAME ALIAS SPINE (`normalize/1`, `model_name/1`, `shell_tool_name/0`, `matches_any?/2`): every accepted spelling maps onto the internal dispatch key, unknown names pass through unchanged, and the platform shell name is pinned at compile time (`run_powershell` on Windows, else `run_bash`)
- `./subagent_processing.ex` → Subagent call processing (builds specs, spawns subagents, collects mergeable children, merges them through `EvoGit.Agent.ContextMerge`, formats the note, deletes only merged children's branches) + foreign-repo spawn starting-commit resolution (see "Foreign-Repo Commit Propagation")
- `./context_merge.ex` → `EvoGit.Agent.ContextMerge` — ownership-aware merge engine for a parent's same-repo subagent commits (`merge_children/2,3` → `Report`, `format_note/2`, the pure ownership rules `file_node_path/1` / `ownership_strength/2` / `decide/3`) — see "Subagent Merge Conflict Resolution"
- Foreign-repo spawn starting commits & the stale-pointer hazard → this file ("Foreign-Repo Commit Propagation") + `../agent_scheduler/CONTEXT.md` (roll-up in `Subagents.store_sub_result/3,4`) + `../runtime/CONTEXT.md` (per-repo report branches)
- `./loop_state.ex` → `LoopState` struct — agent loop state threaded through every turn
- `./result.ex` → `Result` struct — structured output of a completed agent run
- `./tool_output.ex` → `EvoGit.Agent.ToolOutput` — structured TOOL output (text + optional multimodal attachments) and the wrap boundary that keeps the sanitizer/truncation/hints pipeline binary-only — detail in "Multimodal Tool Outputs (`EvoGit.Agent.ToolOutput`)"
- `./output_sanitizer.ex` → Tool output sanitization pipeline (ensure_utf8 → ANSI stripping → progress bar removal → truncation) + `./truncation_feedback.ex` (appended ⚠️ feedback block). Truncation thresholds (3-level config): `[:truncation, :tool_output_max_bytes]` = 131072 (128 KB global ceiling), `[:truncation, :tool_output_default_max_bytes]` = 16384 (16 KB for `@high_output_tools`, output_sanitizer.ex:55-77: the shell spellings `run_bash`/`bash`/`shell`/`run_powershell`, the file spellings `read_file`/`read`/`write_file`/`write`/`edit_file`/`edit`, and the search/network spellings `rg`/`grep`, `run_git`/`git`, `search_web`/`web_search`, `search_context`, `search_history` — BOTH spellings of every aligned name are listed deliberately so the per-tool cap applies whichever spelling the caller passes; bare shell-executable names (`powershell`/`pwsh`) are not tool names or accepted aliases and are absent), `[:truncation, :tool_output_truncate_size]` = 8192 (8 KB keep size); a per-call `max_bytes` tool arg overrides the default, capped at the global ceiling. Cuts are UTF-8-boundary-safe via `String.byte_slice/3` (Elixir 1.17+) with a defensive `EvoGit.UTF8.ensure_utf8/1` pass on the final assembled string; kept-budget clamping (`min(truncate_size, original_size)`) prevents head/tail overlap and negative omitted counts when output exceeds the threshold but is smaller than the keep size (whole content retained, nothing omitted). On truncation the LLM sees a short factual inline header (original size, effective max, kept first X + last X bytes, N bytes omitted, remediation "Narrow the pattern/path or raise max_bytes (up to 131072)") followed by head+tail content (+ omitted marker), then `TruncationFeedback.append_truncation_feedback/3` appends a single concise ⚠️ line (original/kept sizes + remediation). `truncation_info.truncated_size` = the retained CONTENT bytes (head+tail, excluding header/marker text); `truncation_info.original_size` = the pre-truncation byte size. The truncation call site (`ToolDispatch.sanitize_tool_result/3` → `sanitize_and_append_truncation_feedback/2`) runs `sanitize_and_truncate/3` then `append_truncation_feedback/3` on the TEXT component only (the wrap boundary — see "Multimodal Tool Outputs"); the sandbox helpers (`EvoGit.Sandbox.Helpers.truncate_output`) are a separate, lower-level truncation with their own wording.
- `./truncation_feedback.ex` → `EvoGit.Agent.TruncationFeedback` — the appended ⚠️ truncation-feedback block plus LLM-failure classification (`classify_model_exhaustion/1` → `:insufficient_balance | :rate_limit | nil`, helpers `is_insufficient_balance_error?/1` and `is_model_exhaustion_error?/1`)
- `./llm_retry_policy.ex` → `EvoGit.Agent.LlmRetryPolicy` — pure model-exhaustion retry-backoff schedule (15 delays, base 60s doubling, 8h cap, total 216,900,000 ms ≥ 2 days; app-env timing seams)
- `./llm_error.ex` → `EvoGit.Agent.LlmError` — pure fail-fast classification (`non_retryable?/1`) + self-diagnosing one-line messages (`format_failure/1,2`) for deterministic provider rejections (e.g. HTTP 400 code 1210) + the shared name rendering (`parameter_names/1`, `format_parameter_names/1`) used by the message tail and the request-path debug log — detail in "Fail-fast on a non-retryable provider rejection" below
- `./cost.ex` → `EvoGit.Agent.Cost` — self-computed LLM cost (raw token counts + the `llm_db` pricing catalog with an explicit peak/off_peak period resolved from the model profile's `EvoGit.PeakHours` config); ReqLLM's reported cost is NOT trusted — detail in "Helper Modules" + "Known Issues"
- `./background_job_notice.ex` → `EvoGit.Agent.BackgroundJobNotice` — pure renderers for the agent's background shell jobs: `section/1` (the `## Background Jobs` `<context>` sub-section) and `notice/1` (the combined `[NOTICE]` message for just-finished jobs); no IO, no config, total over malformed job maps

## API Surface

### Data Structs
| Struct | Purpose |
|---|---|
| `EvoGit.Agent.LoopState` | Agent loop state (enforced keys: `agent_id`, `agent_module`, `depth`, `node_path`, `context`; remaining fields have defaults). Threaded through every turn. |
| `EvoGit.Agent.Result` | Structured result of a completed run (`result`, `commit_sha`; optional `tag`, `branch`, `base_commit`, `repo_id`, `foreign_repo_commits`). `repo_id` identifies which repo the result belongs to (`"primary"` or a foreign repo string), populated from the process dictionary. `foreign_repo_commits` = `%{repo_id => latest commit SHA}` for work done in foreign repos (default `%{}`; the scheduler stream injects values, the runtime stream reads it for the per-repo report). Produced by the ONE shared completion builder `ToolDispatch.build_completion/2,3` (`tool_dispatch.ex:1125,1134`) on BOTH completion routes — an explicit `complete_task` call and an implicit completion (the model stopped calling tools and wrote usable text; see `EvoGit.Agent.CompletionProtocol`), so the two are indistinguishable downstream. |

### Helper Modules
| Module | Purpose |
|---|---|
| `EvoGit.Agent.ContextCompression` | The two-stage compression orchestrator behind the unchanged `compress_if_needed/2` entry point (`Runner.loop/1` calls it every iteration). The trigger is window-relative over the CONFIGURED window (`Compression.Threshold.for_model/2`, fed by `ToolDispatch.current_context_window/0` → `AgentState.llm_context_window`; profile `context_window`, default 200_000): `min(0.8·W, W − reserved − 65_536)` floored at `min(32_000, 0.9·W)` and capped at `0.9·W`, with `[:llm, :compression_threshold_tokens]` as an optional positive-integer OVERRIDE (`source: :config`). Stage 1 (`Compression.ToolResultPruner`) is model-free — old `:tool` text becomes head 4096 B + `[... tool result middle pruned ...]` + tail 1024 B and old media parts collapse into one placeholder — and it is adopted ONLY when it pruned something, the projection (`Threshold.project/3`) lands at or under `Threshold.pruning_target/2` (`[:llm, :tool_result_pruning_target_fraction]`, default 0.5 of the window, capped at the threshold) and the count really fell — otherwise the pruned list is DISCARDED, because pruning rewrites history and invalidates the provider prefix cache. `[:llm, :tool_result_pruning]` (default true) disables Stage 1 entirely. Stage 2 (`Compression.Checkpoint` + `Compression.SummaryPrompt`) always reads the ORIGINAL, un-pruned message list — a pruned request would be cheaper but would hide from the summariser exactly what the summary must preserve — and replaces only the span older than the last K turns (K = 4, `Compression.Recency.default_keep_recent_turns/0`) with ONE checkpoint message carrying an 8-section summary, keeping `[system, first_user]` BYTE-IDENTICAL and the recent tail VERBATIM. Every compression event resets `total_tokens` to 0, increments the compression count and APPENDS the runtime-context refresh message (`ContextBuilder.build_context_refresh_message/2`; omitted when the rendered block is blank) — message #1 is never rewritten, so the cached prefix survives. That refresh message re-injects the agent's LIVE background shell jobs: `refresh_messages/1` injects `EvoGit.BackgroundJobs.snapshot(owner_pid: self())` into the state map and `ContextBuilder.build_context_block/1` renders `EvoGit.Agent.BackgroundJobNotice.section/1` as a `## Background Jobs` sub-section (after quality guidance, before the clock), so a job started before the compaction is not lost; the Stage-2 `SummaryPrompt` additionally REQUIRES every still-running background job (exact job id, command/label, status) under `## Pending Jobs`. The stage-2 call runs through `Compression.LlmRetry` (bounded retries, `:compression_llm_max_attempts` default 3, slot per attempt); a NON-RETRYABLE provider rejection returns the terminal `{:error, {:llm_request_rejected, message}}` (propagated by `Runner.loop/1`), and every other failure class still raises. The archive `compression_threshold` (`CompleteTask.complete/4`'s `context_compression_threshold` field) is the SAME per-agent derived threshold (`Threshold.for_model(agent_state.llm_model, context_window: Map.get(agent_state, :llm_context_window)).threshold`). Detail: `compression/CONTEXT.md` |
| `EvoGit.Agent.CompletionProtocol` | Pure classifier of ONE LLM turn (`completion_protocol.ex`): `classify/1` → `{:tool_calls, calls}` when the response carries tool calls, `{:text_reply, text}` when it carries NONE and `report_text/1` finds usable text (that is an IMPLICIT COMPLETION, not a protocol failure), `:empty` when it carries no tool calls AND no usable text. `report_text/1` → `{:ok, text} | :empty` reads the reply through `ReqLLM.Response.text/1`, which selects `type: :text` parts only, so reasoning/thinking text is never promoted to the final report. Both functions are TOTAL over any input term: the response/message shape (and, for the text read, a LIST `:content`) is checked BEFORE the ReqLLM accessors run, so a nil or missing message, `content: nil` (only reachable via a hand-built `%ReqLLM.Message{}` — ReqLLM's own default is `[]`) or any non-list content yields `:empty` (tool calls still win in `classify/1`) instead of raising. `EvoGit.Agent.ToolDispatch` is the only consumer: `prompt_until_tools_or_limit/6` (`tool_dispatch.ex:298-340`) classifies every response, `do_turn/5` (`:232-268`) routes `{:text_reply, text}` to `process_llm_response/6` (which finishes the run through the shared `build_completion` path) and `:empty` to exactly ONE nudge (`@max_no_tool_call_nudges 1`, `:80`), after which it yields `{:error, :protocol_violation}` → `handle_protocol_violation/3` (`:612`). `complete_task` stays supported and OPTIONAL — the protocol never requires it |
| `EvoGit.Agent.ToolInvocation` | Pure per-call preparation at the dispatch boundary (`tool_invocation.ex`): (1) the TOLERANT three-stage arguments parse — `arguments/1` passes a decoded JSON object to the tool layer, passes a non-blank but UNPARSEABLE argument string through RAW (the `is_binary` clause of `Tools.execute/5`, tools.ex:244-261, answers with a self-correcting error string), and returns `{:error, reason}` when nothing is recoverable (`"the tool call carried no arguments"` / `"the arguments could not be decoded as JSON"`, tool_invocation.ex:159,166) — so a `nil` `args_map` never reaches `Tools.execute/5` (map/binary clauses only) and a malformed-arguments call is answered as a normal tool result instead of crashing the agent Task; `invalid_arguments_result/1` renders the caller's `"Error: invalid arguments: <reason>"` string (call sites `ToolDispatch.run_tool_call/3`, tool_dispatch.ex:1360-1382, and `handle_complete_call/3`, tool_dispatch.ex:1029-1046); `arguments_map/1` is the TOTAL `%{}` fallback for the map-only hint/telemetry helpers and returns `%{}` for a call that is not a `%ReqLLM.ToolCall{}` (same for `arguments/1` → `{:error, "the arguments could not be decoded as JSON"}`): the call SHAPE (`%ReqLLM.ToolCall{function: %{arguments: _}}`) is verified before any `ReqLLM.ToolCall.*` accessor runs, so a plain map / nil / RPC-decoded term takes the stage-3 path instead of raising `FunctionClauseError`. No JSON-Schema validation of arguments happens anywhere before dispatch (the declared parameter schema is prompt-only); a MISSING required argument is instead handled per tool by `EvoGit.Agent.Tools.Shared.fetch_string_arg/2` (tools/shared.ex:32-48 → `"Missing required argument '<key>'"`), so neither shape is fatal. (2) The per-call timeout rule — `resolve_timeout/4` uses an explicit positive integer `timeout` clamped by `max_tool_timeout`, otherwise `default_timeout/2`: the platform shell tool (`shell_tool?/1` — `bash`/`run_bash`/`run_powershell`/`pwsh`/`shell`/`sh`/… matched case-insensitively on the RAW name) with no explicit timeout gets at least `@shell_default_timeout_ms` 120_000, every other tool gets `[:scheduler, :default_tool_timeout]`, both clamped by `[:scheduler, :max_tool_timeout]` |
| `EvoGit.Agent.ToolNames` | The tool-name ALIAS SPINE (`tool_names.ex`, pure + TOTAL + case-insensitive): `normalize/1` maps every accepted spelling onto the INTERNAL dispatch key (`read`→`read_file`, `write`→`write_file`, `edit`→`edit_file`, shell aliases→the platform shell name, `grep`/`ripgrep`→`rg`, `websearch`/`web_search`→`search_web`, `task`/`subagent`→`subagent_manager`), `model_name/1` renders the model-facing spelling, `shell_tool_name/0` is the compile-time platform pin (`run_powershell` on Windows, else `run_bash`), and `matches_any?/2` powers `Tools.whitelist_match?/2` so an agents.toml `tools` whitelist written with either spelling resolves. Unknown names pass through unchanged (nothing is ever invented) — which is why an unknown tool call still reaches the `execute_tool/5` catch-all |
| `EvoGit.Agent.SubagentProcessing` | Spawns subagents, resolves cross-repo paths, merges same-repo results through `EvoGit.Agent.ContextMerge` (ownership-aware `CONTEXT.md` conflict resolution — see "Subagent Merge Conflict Resolution"), deletes only merged/auto-resolved children's branches, formats results for LLM context. Foreign-repo subagent phylo nodes (`build_subagent_phylo_node/8`, clause chosen by `same_repo?` = child repo id == the parent agent's repo id — a SAME-REPO child starts at the parent's live `parent_state.phylo_node.current_commit`; a CROSS-repo child uses starting-commit precedence = per-repo `base_sha` (task-level starting commit, non-nil wins) → tracked commit from the `foreign_repo_commits` map (previous subagent's latest commit in that foreign repo) → foreign repo HEAD); an unresolvable `base_sha` or a missing/non-git foreign repo root returns a descriptive `{:error, msg}` (surfaced as `{:error, {call, index, msg}}`) — never a MatchError crash. `format_subagent_result/1` surfaces foreign-repo spawn-gate rejection hints verbatim: `{:error, {:foreign_repo_read_only, msg}}`, `{:error, {:foreign_repo_write_not_root, msg}}` (write-capable spawn into a foreign repo by a nested agent — root-agent-only), and `{:error, {:foreign_repo_write_serialized, msg}}` (parallel writable-foreign-repo spawns in one batch — one-at-a-time) all render as `"Error: #{msg}"` |
| `EvoGit.Agent.TurnWarning` | Adaptive turn-budget warnings — 3 positional categories (beginning/end/critical) scaling with max_turns, plus a periodic middle reminder based on turns since last subagent delegation. `:beginning` delegation-strategy warning fires at ~25% of budget (min turn 6); `:middle` reminder fires every 15 turns (`:high`) / 45 turns (`:low`). Low-level agents (Executor, TaskScheduler, etc.) skip `:beginning` and have a 3x longer middle reminder interval. `:end` fires at ≤ `min(10, max(3, div(max_turns, 6)))` turns remaining (3-turn floor, 10-turn cap); `:critical` fires at ≤ `min(5, max(1, div(max_turns, 20)))` turns remaining (1-turn floor, 5-turn cap) — so the typical 128-turn subagent and 1000-turn root budgets both get a 10-turn `:end` / 5-turn `:critical` countdown, and the `:end` band always opens strictly before `:critical` for every budget (> 1) |
| `EvoGit.Agent.SubagentSchemas` | Shared subagent tool/schema machinery (tools/1, schemas/1, and `subagent_module_for/2` — the subagent-type → implementation-module resolver used by subagent spawning and subagent-call detection in tool_dispatch). Subagent tool/module resolution always goes through this schema machinery — the `EvoGit.Agent` behaviour injects NO default `subagent_tools/0` callback (the macro-injected default `available_tools/0` is `Tools.schemas() ++ SubagentSchemas.schemas(__MODULE__) ++ [CompleteTask.schema()]`) |
| `EvoGit.Agent.LlmError` | Pure, TOTAL fail-fast classifier + message formatter for deterministic provider rejections: `non_retryable?/1` (unwraps `{:error\|:exit\|:throw\|:shutdown\|:http_task_failed, reason}` tuples / `%ReqLLM.Error.API.Stream{cause:}` / nested `%ReqLLM.Error.API.Request{cause:}` / a plain map-or-keyword `:cause`, bounded at depth 5 so a cause cycle cannot hang, then classifies the `%ReqLLM.Error.API.Request{}`: `retryable == true` or status 408/409/425/429/500..599 → retryable, other integer 400..499 → non-retryable, `retryable == false` → non-retryable, no signal → retryable) and the one-line message formatter: `format_failure/1` (status + provider code + provider name + human message extracted defensively, atom- or string-keyed) and `format_failure/2` (`format_failure(reason, request_context)` — same line plus a self-diagnosing tail: `Request parameters sent: [max_tokens, temperature, tools].` built from `[params: <the exact keyword list handed to ReqLLM.stream_text/3>]` and `Check the model profile for model <spec> and remove parameters the provider does not support.` from `[model: <resolved model spec>]`; each part is omitted when absent, so `format_failure/1` — a delegate to `/2` with `[]` — is byte-identical to the pre-existing output; the tail is purely additive). `parameter_names/1` (the sorted, de-duplicated, single-line-sanitized NAMES of a request keyword list/map — values never read, `:tools` with an empty-list value contributes nothing because ReqLLM sends no such field, capped at 32 names with a `... N more` marker, total for EVERY input: a struct — a map without an `Enumerable` implementation — and any other non-keyword/non-map term yield `[]`) and `format_parameter_names/1` (`[a, b]`) are the ONE name-rendering site shared by the message tail and the request-path debug log. Anti-leak invariant: only parameter NAMES and the model spec are ever rendered — a map/struct model spec is reduced to its `:id`/`:model`/`:provider` identity fields, so an `:api_key`/`:base_url`/header can never reach a message. Model-exhaustion classification wins — a 402/429 is never non-retryable, however ReqLLM wrapped it (`non_retryable?/1` evaluates the precedence on the UNWRAPPED `%ReqLLM.Error.API.Request{}`, which is the only shape `TruncationFeedback`'s structural 402 check matches, and on the raw reason too). Detail: "Fail-fast on a non-retryable provider rejection" |
| `EvoGit.Agent.Cost` | Self-computed LLM cost — EvoGit does NOT trust ReqLLM's reported cost (see Known Issues). Pure + TOTAL (every public function is `try/rescue/catch`-wrapped and can never raise): `recompute(usage_map, model_spec, period) :: %{input_cost: float(), output_cost: float(), total_cost: float()} \| nil` prices the raw token counts against the `llm_db` catalog via `LLMDB.Pricing.components_for(model, %{pricing_period: period})` (model resolved through `ReqLLM.model/1`, accepting a `%LLMDB.Model{}` directly; a map spec whose resolution carries no pricing — e.g. a `base_url` profile — falls back to the `"provider:id"` catalog entry); only `kind: "token"` components with a positive `rate`/`per` (default `1_000_000`) and a recognizable meter/id are billed, skipping the model's `pricing.excluded_cost_components` (deepseek excludes `token.reasoning` — its completion tokens already include reasoning) plus derived-rate/modifier/conditional (`derives_from`/`multiplier`/`applies_to`/`rate_group`/non-`full_request` `charge_scope`) and non-token kinds; cost per component = `count / per * rate`; buckets by id prefix (`token.input*`/`token.cache*` → `input_cost`, `token.output*`/`token.reasoning*` → `output_cost`, mirroring ReqLLM's `meter_key/1` classification), `total_cost = input_cost + output_cost`, each rounded to 6 decimals; meter→token mapping: `input_tokens` → cache-MISS input (`max(input_tokens - cached_tokens - cache_creation_tokens, 0)` when `input_includes_cached`, else `input_tokens`), `output_tokens`/`cache_read_tokens` (`cached_tokens`)/`cache_write_tokens` (`cache_creation_tokens`)/`reasoning_tokens`, with an id-prefix fallback when the component carries no meter. `recompute_for_agent(usage_map, agent_id) :: costs() \| nil` fetches `%AgentState{llm_model, model_id}` via `EvoGit.AgentScheduler.get_agent_state/1` and picks the period with `period_for_model_id/1`. `apply_to_usage(%Usage{} = u, raw_usage_map, agent_id) :: %Usage{}` is THE shared wiring helper (used by `tool_dispatch.ex` + `context_compression.ex`): `nil` recompute → `u` unchanged (ReqLLM's values kept), otherwise only `input_cost`/`output_cost`/`total_cost` are overridden — the struct shape (8 fields) is untouched. Period resolution: `period_for_model_id(model_id)` (`"peak" \| "off_peak"`, default `"off_peak"`) looks the profile up in `EvoGit.AgentScheduler.get_config(:model_profiles)` (atom/string key + id tolerant) and delegates to the public, unit-testable `period_for_profile(profile)` — `PeakHours.validate_windows/1` → `{:ok, []}`/invalid → `"off_peak"`; off-peak days via `PeakHours.validate_days/1`; wall clock via `PeakHours.wall_clock_in(tz, utc_now)` (timezone key atom/string tolerant, `""`/nil → local clock) falling back to the local `now` on error; `PeakHours.in_peak?/3` decides (`false`/any error → `"off_peak"`). Clock seams read at call time: `:peak_hours_now_fun` / `:peak_hours_utc_now_fun` (same as `PeakHourEngine`) |

### Tool Library (`EvoGit.Agent.Tools`)
| Component | Role |
|---|---|
| `tools.ex` | Central dispatch: `schemas/0` returns the STANDARD tool schemas (every `use EvoGit.Agent` coding agent's default `available_tools/0`), `execute/5` dispatches by name. `run_command` — the self-reflective agent's single task-control shell tool — is dispatch-registered ONLY, never in `schemas/0` or `read_only_schemas/0` (scope/security; see Repo-less Agents) |

### Delegation Hinting

Two independent hinting mechanisms, both per-child-directory counter + fire-once:

- **Write-tool hint**: agent repeatedly *edits* files below its `node_path`; after the write-tool count per child dir exceeds `delegation_hint_threshold` (default 5, `[:scheduler, :delegation_hint_threshold]`), a nudge is appended to tool output suggesting a subagent for that child directory.
- **Read-tool hint**: a `:high`-level agent repeatedly reads/investigates a child dir (via `read`, `rg`, `glob`, `list_dir`); after the count (`read_delegation_hints`) exceeds `read_delegation_hint_threshold` (default 8, `[:scheduler, :read_delegation_hint_threshold]`), a nudge suggests `subagent_investigator`. `:low` agents are expected to read directly.
- Both hints show once per child dir (`hint_shown` flag); suppressed during merge-conflict resolution (`filter_child_paths_if_conflicts/2`). Implemented in `EvoGit.Agent.ToolDispatch` + `EvoGit.Agent.DelegationHints`: `batch_execute_tools/4`, `extract_child_paths/4` (target child dir from write-tool args), `maybe_append_delegation_hint/4`. Hints stored in `LoopState.delegation_hints`, threaded via process dictionary.

### Subagent Objective & File Handoff (no automatic path plumbing)

A parent hands work to a child ONLY through the spawn tool-call's `objective` STRING plus the child's own checkout — there is no side-channel carrying file handles, temp paths, or parent-worktree paths.

- **Objective is passed VERBATIM**: `build_subagent_specs/3` reads `objective = Map.get(args, "objective")` (`subagent_processing.ex:148`) and forwards it unchanged to `AgentSpec.new/5` (`:200`); `AgentSpec.new/5` stores it as-is (`agent_spec.ex:58-70`). No wrapping, path rewrite, sanitization, or cwd hint is added. The child sees it inside its `<objective>` block (`runner.ex:195-204`).
- **The `path` spawn ARG is a DIRECTORY node, not a file**: the schema requires a RELATIVE path for same-repo targets (`./src/auth`) and an ABSOLUTE path only for foreign repos (`subagent_schemas.ex:40-52`); a file path is silently redirected to its parent dir (`subagent_processing.ex:164-172`); non-absolute paths resolve to the parent's repo, absolute paths outside any known repo are rejected with a self-correct hint (`subagent_processing.ex:266-272`).
- **No `/tmp`/absolute-path objective plumbing exists** in this subtree — nothing writes a temp file and passes its path to a subagent. The only `/tmp` references here are unrelated (`delegation_hints.ex:93` comment; `shell_tool.ex:105` bash guidance; `spawn_investigator_probe.ex:353` keyword-scan comment). An LLM MAY put an absolute path in an objective (the schema invites "file paths", `subagent_schemas.ex:61`), but no code does this automatically and no rule forbids it in the objective text.
- **How a child learns its working dir / locates the parent's files**: the child gets a FRESH worktree at `spec.phylo_node.current_commit` (its process cwd == that worktree root; `shell_tool.ex:125`), so the schema tells the parent "Do NOT include worktree paths or `cd` commands in the objective" (`subagent_schemas.ex:59-60`). The child's `<context>` block renders ITS OWN node-path context tree relative to its worktree (`runner.ex:160-164`) — parent changes are visible only if COMMITTED before the spawn (parent commits first: `subagent_processing.ex:59-61`). Inherited spec opts are only `repo_id`, `foreign_repos`, `repo_notes`, `archive`, `model_id` (`subagent_processing.ex:200-206`) — never a path/file.
- **Absolute-path rules live on the tool ARG, not the objective**: write tools reject absolute file paths in `Shared.normalize_relpath/1` (`shared.ex:256-259`) and out-of-repo targets in `Shared.validate_file_scope/4`.
- **Cross-ref**: `SpawnInvestigator.spawn_investigator` (a `run_command` command handler, NOT the subagent spawn) takes an ABSOLUTE `path` + `objective`, but uses the objective only for keyword extraction (`spawn_investigator_probe.ex:352-368`). Writer-side prompt in a sibling node: `../agents/executor.ex:47` ("trust provided file paths/line numbers from the caller, do not re-investigate").

## Subagent Merge Conflict Resolution (`EvoGit.Agent.ContextMerge`)
A parent agent merges every SAME-REPO child commit into its own worktree; `CONTEXT.md` conflicts there are frequent and usually spurious, so the merge is ownership-aware (`context_merge.ex`, detail in this section).
- **Ownership strengths** (`ownership_strength/2`, pure, over a repo-relative `.../CONTEXT.md`): `3` = the node path IS the file's directory (the owner), `2` = a strict segment-wise ancestor of that directory (`./` is everybody's ancestor), `1` = unrelated — including a node BELOW the file's directory.
- **Fast path** (`merge_children/2,3`): ONE merge attempt — a plain `git merge` for a single child, `git merge_octopus` for several; a clean merge reports `:clean` (or `:no_changes` when HEAD did not move) and needs no conflict handling.
- **Sequential fallback**: a conflicting fast merge is aborted (`git merge --abort`) and the children are merged one at a time in SPAWN order, each `CONTEXT.md` conflict re-decided against the CURRENT "ours" candidates (the parent plus the children already merged).
- **"Ours" side**: the parent's own node path (option `:parent_node_path`, default `"./"`) PLUS every already-merged child that changed the same file; the highest-strength candidate decides.
- **`CONTEXT.md`-only auto-resolution** (`decide/3`): out of the child's own scope (strength `1`) → keep OURS and record the dropped edit with its truncated `git diff <base> <child_sha> -- <file>`; the child is a strictly deeper owner → keep THEIRS; shallower → keep OURS; EQUAL ownership ≥ 2 (two genuine owners) → unresolved.
- **Never auto-resolved**: any non-`CONTEXT.md` conflict and a same-ownership `CONTEXT.md` conflict — both abort that child's merge, end the pass at `:conflict`, and leave every remaining child `:not_attempted`.
- **Clean-worktree invariant**: every failure path aborts, so the worktree is always clean at a reported HEAD — nothing is ever left half-merged.
- **`Report`**: `status` (`:clean | :no_changes | :conflict | :error`), `starting_sha`, `head_sha` (short), `merge_output`, per-child `entries` (`index`, `commit_sha`, `branch`, `node_path`, `agent_module`, `agent_type`, `status` = `:merged | :auto_resolved | :conflict | :not_attempted`), `auto_resolutions` (`file`, `direction`, `child_node_path`, `reason`), `dropped_edits` (`file`, `child_node_path`, `diff`), `genuine_conflicts` (both node paths + both strengths) and `error` — a missing/invalid sha is reported per child, never guessed.
- **`format_note/2`** renders the parent's system note: `nil` for `:no_changes`; the `:conflict` note lists every child (index, node path, agent type, branch, full commit sha), each conflicting file with an ownership verdict per side, the dropped out-of-scope edits with their diffs, and explicit `git merge <sha>` next steps — plus branch handling.
- **Per-child attribution** (`SubagentProcessing.collect_mergeable_results/3`): children whose `spec.repo_id` equals the parent's repo id become merge participants in spawn order carrying index/commit sha/branch/node path/agent module/objective; cross-repo children are reported separately and never merged.
- **Branch preservation policy** (`SubagentProcessing.delete_merged_branches/2`): a branch is deleted ONLY for a `:merged`/`:auto_resolved` child; a `:conflict`/`:error` report preserves EVERY branch so the parent can merge one at a time.
- **Note composition** (`SubagentProcessing.build_merge_message/4`): a `:no_changes` report is silent, cross-repo activity alone yields the cross-repo note, otherwise `ContextMerge.format_note/2`.
## Design Decisions

### Foreign-repo subagent starting-commit chaining

Per-agent (not per-task) tracking, the `same_repo?` clause selection and `resolve_foreign_phylo_commit/4` precedence are detailed in "Foreign-Repo Commit Propagation" below, the same-repo merge and branch handling in "Subagent Merge Conflict Resolution" — do not duplicate here.

### Module sizes (cohesive-by-design)

`agent/tool_dispatch.ex` is ~1800 lines — the tool-dispatch orchestrator (`EvoGit.Agent.ToolDispatch`, extracted from the agent macro): per-turn LLM call with retry, tool-call routing (complete vs regular vs subagent; standard-tool batching through the write-gated `Tools.execute/5` dispatch), timeout management, the output sanitization/truncation-feedback call site (tool_dispatch.ex:995-1002), and subagent-spawn plumbing. Deliberately kept cohesive — do not split without a plan.

### Standard tool call execution — serial file-mutating phase + parallel rest (bounded by scheduler tool slots)

Standard (non-subagent) tool calls in one batch are PARTITIONED by `EvoGit.Agent.Tools.serial_tool?/1` — the single classification source of truth for tool semantics (see `agent/tools/CONTEXT.md`).
- **SERIAL group** = the file-mutating subset (`create_files`, `write`/`write_file`, `edit`/`edit_file`, `make_dir`, `write_context`, `edit_context`, `skill_add`, `skill_edit`, `skill_remove`, `skill_enable`, `skill_disable`, plus any user-defined custom tool that declares itself a write tool) — executed SEQUENTIALLY, one call at a time, in request order, in the PARENT agent process (`run_tool_call/3`). These tools do a NON-ATOMIC read-modify-write, so N concurrent calls targeting the same file would each read the ORIGINAL bytes and only the last write would survive — every other edit silently lost while still reporting success. File I/O is not a performance bottleneck, so serial execution of this subset is acceptable.
- **The serial phase runs FIRST**, deliberately: a mutation then always lands BEFORE any read or shell command of the same batch that could observe it, so `[write x.ex, bash "mix test"]` and `[edit x, read x]` behave as the model expects; the reverse order would let a same-batch read/exec observe stale bytes.
- **PARALLEL group** = everything else (the read-only tools `read`, `rg`, `glob`, `list_dir`, `read_context`, `search_context`, `search_history`, `skill_list`/`skill_read`/`skill_where`, the read-only network/language readers `web_fetch` + `lsp`, plus the shell/exec/network tools `bash` — internal key `run_bash`/`run_powershell` — `run_git`, `run_command`, `web_search`) — executed CONCURRENTLY via `Task.async_stream`, governed by the scheduler's tool-slot pool (`max_tool_concurrency`, default = detected CPU thread count, set via `[scheduler] max_tool_concurrency` TOML — no CLI flag).

Subagent calls also run in parallel (`SubagentProcessing.process_subagent_calls`) — the ENTIRE batch of subagent tool calls from one LLM response is passed in a single blocking `AgentScheduler.spawn_sub_agents/1` call and all specs are registered/dispatched together (`agent_scheduler/subagents.ex` `spawn_validated_subagents/5`, dispatched via `Enum.reduce(sub_ids, state, &Dispatch.try_dispatch/2)`). **Fan-out WIDTH has NO code cap**: there is no min/max on the number of subagent tool calls per response and no agent-count limit in the scheduler spawn path — the only code-level bounds are `max_depth` (recursion DEPTH), the ignored-path / spatial-contract validation, and the one-at-a-time writable-foreign-repo gate; execution is throttled only by the tool/LLM slot pools. Width is therefore at the LLM's discretion (prompt-driven), and the prompts explicitly invite wide parallelism (`agents/architect.ex` "there is no concurrency limit"; `agents/manager.ex` "Spawn subagents for ALL independent tasks simultaneously"). Turn caps bound TOTAL turns, not subagent count — one LLM response = one turn regardless of how many subagents it spawns. For the parallel group, `batch_execute_tools/4` uses `Task.async_stream`: `max_concurrency` = group size (positive integers only — the scheduler, not a local cap, is the binding constraint), `ordered: true`, `timeout: :infinity` (per-tool timeout stays inside `execute_tool_with_timeout/8`, which wraps its own `Task.yield(task, tool_timeout) || Task.shutdown(task)` — an outer stream timeout would kill long-running tools). Tool-slot acquisition (`AgentScheduler.with_tool_slot/2`) happens per call inside `execute_tool_with_timeout/8`, for BOTH groups. The two phases' result lists are concatenated and re-sorted by index BEFORE hint tracking, so the LLM receives results in request order; delegation hints and the once-per-run redundant-cd warning are threaded in index order in the parent via `Enum.reduce` (`apply_tool_output_tracking/3`), keeping hint accumulation deterministic (`:redundant_cd_warned` process-dict flag).

**Caveat — concurrent git tools:** the parallel group may still contain several git-touching shell calls (`run_git`, `bash` running a git command) that contend on git's `index.lock`. `max_tool_concurrency` (default = detected CPU thread count) bounds this; lower it if contention appears.

**No cap on subagent SPAWN COUNT (spawn-count is prompt-driven, not code-enforced).** Nothing in this directory limits how many subagent tool calls one LLM response may carry, or how many subagents may exist at once:
- `process_regular_tool_calls/3` (`tool_dispatch.ex:786-831`) `Enum.split_with`s the batch's subagent calls and passes the FULL list to `SubagentProcessing.process_subagent_calls/3` — no `Enum.take`/`Enum.slice`/batch limit anywhere in this directory (grep-verified).
- `SubagentProcessing.process_subagent_calls/3` (`subagent_processing.ex:50-110`) → `build_subagent_specs/3` (`:139` `Enum.map`) builds a spec for EVERY call, then one `AgentScheduler.spawn_sub_agents/2` call spawns them all; `split_valid_subagent_calls/1` only rejects calls missing `path` (per-call error feedback, not a count cap).
- `subagent_schemas.ex:29-77` emits ONE tool per declared subagent module with a SINGLE `path`+`objective` (+ optional `commit_id`) parameter — to spawn N subagents the model emits N tool calls; there is NO batch/multi-path schema.
- The only code-enforced recursion limit is DEPTH, not count: `[:scheduler] :max_agent_depth` (default 8, `config/schema/definitions.ex:76-85`), enforced by `runner.ex:636-652` `at_max_depth?/1` (drops subagent tool schemas once `depth >= max_depth`) and `agent_scheduler/subagents.ex:181-191` `validate_subagent_depth/3` (`subagent_depth > state.max_depth`). This bounds the DEPTH of each delegation *branch*, NOT the per-turn or task-wide subagent count.
- Running-subagent concurrency is throttled only by the shared LLM/tool slot pools; queued subagents are still registered and each holds its own worktree (no per-task subagent-count / batch-size / concurrency config key exists — the scheduler schema has no `max_subagents`/`max_children` key).
- **The parent BLOCKS for the whole batch** — `spawn_sub_agents/2` is a blocking `GenServer.call` with `timeout: :infinity` (`agent_scheduler.ex:101-109`; `subagent_processing.ex:63` passes no timeout), replying only when the LAST child returns. The parent agent process therefore stays ALIVE for the whole child subtree, holding its worktree (reclaimed only on `:DOWN`) but NOT an LLM slot (`with_llm_slot/2` wraps only the LLM call) and NOT a tool slot (standard tools released theirs earlier in the same batch). Within a batch, standard tool calls complete FIRST (`process_regular_tool_calls/3` runs `process_standard_calls` at `tool_dispatch.ex:797` before `process_subagent_calls` at `:800`) — sequential phases, not concurrent.
- Consequences for any future GLOBAL cap on agents/worktrees (deadlock surface, child-side mechanics incl. eager registration + worktree-before-LLM-slot): see `../agent_scheduler/CONTEXT.md` → "Subagent Spawn Fan-Out Bounds & Deadlock Surface".
So a "wide fan-out" (5-10 children per level) is bounded by DEPTH × turn budget (`max_turns`) and by prompt guidance — e.g. `agents/manager.ex` states "There is no limit on concurrency" and urges parallel batches — NOT by any spawn-count cap.

### Grace Period & Graceful Cancellation (runner-side)

Two grace kinds, both entered via `Runner.enter_grace/3` (`runner.ex`, `@doc false`): (1) `maybe_recovery_auto_commit/1` FIRST (best-effort auto-commit of uncommitted work — for cancel this is "save the changes"), (2) optionally appends a recovery message, (3) sets `in_grace_period: true` + the `grace_turns_remaining` budget, then re-enters `loop/1`.

- **Turn-limit recovery** (`trigger_recovery/2`, call site `loop/1`: `"max turns (#{max_turns}) exceeded"`): budget **1** — one continue attempt → hard-stop. Appends the "exceeded the execution limit" warning (`message: :default`).
- **Cancel-grace** (`maybe_enter_cancel_grace/1`, called in `loop/1` immediately AFTER `drain_and_inject_user_messages/1`): when the ETS `cancel_requested` flag is set (scheduler-side graceful cancel), the flag is cleared and the agent enters grace with budget **3** and `message: nil` — NO extra recovery message (the cancel message was already injected via the `pending_user_messages` drain). Up to 3 turns to wrap up and call `complete_task`.
- **Budget semantics**: `LoopState.grace_turns_remaining` defaults to `0` (not in grace). Each turn ending WITHOUT `complete_task` decrements it via `consume_grace_turn/1` at the three call sites in `tool_dispatch.ex` (`handle_protocol_violation`, the `process_llm_response` `{:error, :protocol_violation}` branch, `continue_after_tools`). `grace_period_continue_failed?/1` (`agent.ex`): `in_grace_period: true, grace_turns_remaining: n` → `n <= 1` (counter 0 — the struct default — hard-stops); true → call sites return `{:error, :recovery_failed}`.
- **complete_task during grace**: `handle_complete_call`'s dirty-workspace check skip (`not state.in_grace_period and ...`) applies to BOTH kinds — completing with a dirty workspace is allowed during any grace period.
- **Turn counts**: cancel-grace 3 → 3→2, 2→1, 1 → hard-stop (3 grace turns). Turn-limit 1 → hard-stop on the first continue (1 grace turn). `trigger_turn_limit_recovery?/1` returns `false` during grace.

### Lifecycle ordering — worktree allocation BEFORE the first LLM slot

The per-agent allocation order is FIXED and explains wide-tree worktree/IO bursts:

- `Runner.run/3` (runner.ex:41-71) calls `setup_dispatch_context/1` (runner.ex:285-415) FIRST; for non-repo-less agents this BLOCKS on `WorktreeManager.create_worktree_for_agent/6` (runner.ex:359-372; raises on `{:error, reason}`), and only afterwards runs `do_run/2` (runner.ex:50 → `do_run/2` at :131) → `loop/1` (runner.ex:493) → `ToolDispatch.do_turn/5` (tool_dispatch.ex:218) → `call_llm_with_retry/5` → `AgentScheduler.with_llm_slot/2` (tool_dispatch.ex:498). So the worktree is always allocated BEFORE any LLM slot is requested.
- **`ToolDispatch.current_model/0` / `current_generation_params/0` raise contract**: both resolve the calling process's agent state via `current_agent_id()` + `Store.get_agent_state/1`; a nil agent id (process not a scheduled agent) or a missing ETS row (agent purged/cancelled mid-call or scheduler restarted — e.g. while blocked in `with_llm_slot/2`) raises a DESCRIPTIVE `ArgumentError` naming the caller function + agent id (shared helper `fetch_current_agent_state!/1`), never a bare MatchError. The raise propagates — do not add default/nil fallbacks; pinned by regression tests in `tool_dispatch_retry_slot_test.exs`.
- Worktree creation is admission-bounded and concurrent across agents up to a cap: WorktreeManager offloads each create to an independent `Task.start` (worktree_manager.ex) and the caller WAITS INDEFINITELY (`GenServer.call(..., :infinity)`) — a slow worktree copy is waited for, never aborted; a GENUINE failure (a raise/throw/exit or a crashed command inside the create pipeline) still replies `{:error, reason}` promptly, so the agent fails directly instead of hanging. Create pipelines are admitted through a FIFO admission queue capped at `Application.get_env(:evo_git, :max_concurrent_worktree_creation, 4)` — at most 4 create pipelines run at once and extra requests queue (queuing only DELAYS the reply, never drops it). The scheduler never serializes creates (dispatch.ex:207-211); the scheduler's `queue` is the PAUSED-scheduler dispatch queue only (`Dispatch.process_queue`, drained on resume), not a worktree limiter. The cap bounds CREATE-pipeline concurrency only, never live worktrees/agents (detail: `agent_scheduler/CONTEXT.md`).
- Consequence: every dispatched agent — including every subagent in a fan-out batch, all registered+dispatched in one reduce (`Subagents.spawn_validated_subagents` → `Enum.reduce(sub_ids, state, &Dispatch.try_dispatch(&2, &1))`, subagents.ex:126) — allocates its worktree FIRST and only THEN queues for an LLM slot. A wide tree therefore performs a full worktree-creation burst even when most agents end up merely blocked on LLM slots.
- Subagent wait semantics: the parent BLOCKS in `AgentScheduler.spawn_sub_agents/2` (subagent_processing.ex:63) → `GenServer.call(__MODULE__, {:spawn_sub_agents, ...}, timeout \\ :infinity)` (agent_scheduler.ex:101-108) — no timeout; the scheduler holds `from` and replies via `GenServer.reply` when all subagents finish (`maybe_resume_parent/2` → `dispatch_ready_parent/3`, subagents.ex:441-483). The parent's status flips to `:waiting` (subagents.ex:48) but its worktree is NOT reclaimed while waiting (its process is alive; reclaimed only on process exit — subagents.ex:453-477). The parent holds NO LLM slot (released in `with_llm_slot`'s `after` right after the stream) and NO tool slot (subagent calls never enter `execute_tool_with_timeout/8`/`with_tool_slot/2`) during the wait.
- Spawn breadth is UNLIMITED: no per-call subagent cap exists in this subtree (`process_regular_tool_calls` partitions ALL subagent calls into one `process_subagent_calls/3`; no `Enum.take`/count clamp anywhere). Only DEPTH is capped: `state.max_depth` (default 8, `[:scheduler, :max_agent_depth]`, definitions.ex:76-85) checked in `Subagents.validate_subagent_depth/3` (subagents.ex:181-191) and used runner-side by `at_max_depth?/1` (runner.ex:649-652) to strip subagent tool schemas at max depth.

## Tool-Task Process Topology & the Process-Dictionary Seam (verified)

A tool body NEVER runs in the agent process: `run_tool_call/3` (tool_dispatch.ex:1360) → `execute_tool_with_timeout/8` (tool_dispatch.ex:1448) → `AgentScheduler.with_tool_slot/2` (agent_scheduler.ex:442 — blocking slot grant, then `fun.()` runs in the CALLER) → the tool body runs in a spawned `Task.async` (tool_dispatch.ex:1497). So `self()` inside `EvoGit.Agent.Tools.execute/5` is the TOOL-TASK pid, not the agent pid.

The two batch phases use the SAME `execute_tool_with_timeout/8`, but a DIFFERENT spawner — which changes the link target:
- SERIAL group (`Tools.serial_tool?/1`) — `Enum.map` directly in `batch_execute_tools/4` (tool_dispatch.ex:1288-1289), so `Task.async` is spawned BY THE AGENT PROCESS → the tool task is linked to the agent and `Process.get(:"$callers")` = `[agent_pid, …]`.

## Update-Timing Safety (in-flight state vs BEAM restart)

- **No turn-level wall-clock timeout.** A turn = LLM call(s) + tool executions + subagent waits, with NO overall cap. Per-piece bounds: per-LLM-attempt stream receive timeout 30s default (`:req_llm` `receive_timeout`/`stream_receive_timeout`, thinking models 300s via `thinking_timeout`) + pool checkout `stream_pool_timeout` 300s (runtime.exs) + ReqLLM inner retries (3× for 429/transport) + the outer `call_llm_with_retry` backoff (max_retries default 15, delays 0→60s cap ≈ 9 min worst-case); per-tool timeout `min(requested, max_tool_timeout)` with `default_tool_timeout` 10s / `max_tool_timeout` 30 min hard cap (definitions.ex:121-139); subagent waits unbounded (parent blocks). **Consequence: the 3-turn cancel-grace budget is bounded in TURNS, not wall-clock** — a slow LLM stretches a graceful cancel arbitrarily long. Hard stops: `max_turns` (config default 128, applies to subagents) / `max_turns_root` (config default 1000, root only — see `apps/evo_git/lib/evo_git/config/schema/definitions.ex` and `agent_scheduler/dispatch.ex` `resolve_max_turns/3`) and the grace budget.
- **Per-turn ETS checkpoint, in-memory only.** `context.messages` lives in the agent process heap (`%LoopState{context}`); a snapshot is written to ETS (`AgentState.context`) each turn at `batch_update_agent` (tool_dispatch.ex:389-394) and after compression/warnings (runner.ex:351-354) and the pending-message drain (runner.ex:330). Named ETS dies with the VM — **there is NO durable checkpoint of the conversation**; on BEAM restart the whole conversation is lost. The dashboard's `get_agent_history` reads this ETS snapshot.
- **Worktree wipe at next boot.** Uncommitted worktree changes survive the kill on disk, but `WorktreeManager.maybe_init_repo/1` (worktree_manager.ex:236-283) — on the FIRST `create_worktree_for_agent` request for a repo after restart — does `rm_rf .genesis/workers` → `Git.prune_worktrees` → `clean_orphaned_branches` (deletes all `evogit-agent-*` branches, worktree_manager.ex:376-390). Commits made only on an agent branch (never merged/archived) are destroyed at next boot's first worktree creation. Only commits protected by `refs/genesis/archive/T<task>-A<local>-start/-final` refs (written by `CompleteTask.complete/4` when `archive` is enabled AND the agent completed) survive.
- **`Runner.run/3`'s `after` block** (runner.ex:49-53) runs `Dispatch.commit_pending_in_worktree/0` ("Agent: auto-commit fallback", dispatch.ex:278-326) on ANY agent-process exit — normal completion, `{:error, :recovery_failed}` hard-stop, and crashes (raises) — and it runs BEFORE the run's value is handed back to the caller. It does NOT run on `:brutal_kill` (force kill) or VM shutdown — a graceful-cancel hard-stop salvages the worktree via this after-block commit, a killed BEAM loses it.
- **Post-fallback `commit_sha` refresh**: `Result.commit_sha` is captured EARLIER than the fallback, inside `do_complete/2` (tool_dispatch.ex:1105), so `run/3` passes the `try/after` value through the `@doc false` `Runner.refresh_commit_sha/1` (runner.ex:67-123, public solely so tests can call it against a real temp repo). Repo-less agents and every non-success shape (`{:error, _}` wrappers, nil, atoms, and any other tuple) are returned COMPLETELY unchanged — a successful result is never turned into a failure. A success shape carrying a commit sha gets the worktree HEAD re-read via `Git.rev_parse(Process.get(:repo_path))`: `%EvoGit.Agent.Result{}` (refreshed with a struct update, so the struct type is preserved), a plain map with a `:commit_sha` key, or either of those wrapped in `{:ok, inner}`. An unset/blank `:repo_path`, a missing/vanished worktree, a non-git directory, or a `{:error, _}` from git leaves the input unchanged — the function never raises. Re-reading the same sha (the normal `complete_task` path, where the fallback no-ops on a clean worktree) is a harmless fixed point; a nil `commit_sha` becoming the post-fallback HEAD is the fallback-only case. This is what keeps a fallback-only commit reviewable: `Runtime.Helpers.merge_and_report/3,4` compares `commit_sha` against the live repo HEAD and takes the no-changes path (`no_changes: true`, `branch_name: nil`) on a match or nil, so a stale pre-fallback sha would produce NO `genesis/agent_*` branch and the commit would die with the worktree on reclaim.
- **Terminal exit semantics (agent Task process)**: `Runner.run/3` returns `{:ok, %Result{}}` on `complete_task` (tool_dispatch.ex:489-490, do_complete at :820), `{:error, :recovery_failed}` when a grace budget is exhausted (tool_dispatch.ex:356 / :580-581), and `{:error, {:llm_request_rejected, message}}` on a non-retryable provider rejection (see "Fail-fast on a non-retryable provider rejection") — ALL plain return values, so the agent Task exits with reason `:normal` and the scheduler takes the recycle path (`Lifecycle.handle_agent_down/4` reason `:normal` → `recycle_agent/2`, lifecycle.ex:302-303). A returned `{:ok, %Result{}}` carries the POST-fallback worktree HEAD as `commit_sha` (refreshed by `refresh_commit_sha/1` after the `after` block ran); a returned `{:error, _}` is passed through completely untouched. Only a RAISE inside `do_run/2` (`"LLM request failed after N retries"` for the exhausted-transient path, tool_dispatch.ex:243 — the fail-fast rejection deliberately does NOT raise; worktree-vanished rev-parse raises tool_dispatch.ex:143-152; worktree-creation failure runner.ex:347) or a force-kill `Task.shutdown(task_ref, :brutal_kill)` (lifecycle.ex:66) is an ABNORMAL exit (→ `handle_agent_crash`). `Runner.run/3` calls `setup_dispatch_context/1` (runner.ex:42) BEFORE its `try`, so a worktree-creation raise skips the `after` commit fallback (runner.ex:51-53).
- **Task status on restart**: orphaned `:running` tasks are untouched until lease expiry (`:lease_sweep` → `:failed` "Lease expired; owning instance no longer renewing"); orphaned `:finalizing`/`:cancelling` are reconciled at TaskRegistry init (`:failed` / `:cancelled` with "Runtime restarted during ..." results). See `task_registry/CONTEXT.md`.

## LLM Request Retry Mechanism (3 layers)

**Layer 1 — EvoGit outer loop (`call_llm_with_retry/5`, `tool_dispatch.ex`):** a MANUAL recursive attempt loop — first attempt index 0, no initial sleep; total attempts = `max_retries + 1`.
`max_retries` = `agent_state.max_retries` (set from scheduler `state.max_retries` at dispatch, `dispatch.ex:79`), config default **15** (`[scheduler] max_retries`, definitions.ex:63-71).
Each attempt runs inside `AgentScheduler.with_llm_slot/2`, acquiring the LLM slot for ONE `ReqLLM.stream_text` + `process_stream` and releasing it (via `with_llm_slot`'s `after`) BEFORE any backoff wait — a retrying agent never holds its slot across the backoff.
Inside the slot block, a `Logger.warning` accompanies an `EvoGit.ReqLLMPool.excess_queuing_error?/1` check that calls `EvoGit.ReqLLMPool.bump_for_excess_queuing/2` on a Finch excess-queuing error.
On failure the loop classifies the error twice: `EvoGit.Agent.TruncationFeedback.classify_model_exhaustion/1` on the RAW reason → `:insufficient_balance | :rate_limit | nil`, and `EvoGit.Agent.LlmError.non_retryable?/1` (which unwraps the reason and evaluates the exhaustion precedence on the unwrapped `%ReqLLM.Error.API.Request{}`, so an HTTP 402 is never reported non-retryable) → boolean. The class check itself stays raw-reason-based: a wrapped 402 whose text carries no balance/quota phrase takes the ordinary transient retry path (NOT the long exhaustion backoff) — but never the fail-fast path.
`handle_llm_failure/7`'s `cond` reads the classes in this precedence order: model-exhaustion → non-retryable provider rejection → attempts exhausted → ordinary transient. **Model exhaustion always wins** (a 402 / 429 keeps its long scheduler-side backoff).
**Model-exhaustion (`class != nil`, attempts remain):** calls `AgentScheduler.report_llm_error(agent_id, class, EvoGit.Agent.LlmRetryPolicy.model_exhaustion_delay(attempt + 1))` and RECURSES IMMEDIATELY with NO agent-side sleep.
The multi-hour wait is realized by the scheduler's per-model backoff: the next attempt's `with_llm_slot/2` BLOCKS in the purgeable per-model backoff queue, unblocked by a force-kill or graceful-cancel purge (or granted when the backoff expires) — which is why the long wait is cancel-safe.
The agent keeps the same turn and context across attempts — no context loss.
**Ordinary transient errors (`class == nil`, attempts remain):** `:timer.sleep` of the short schedule — exponential base from the `:llm_retry_backoff_base_ms` app-env seam (default 1_000 ms), doubling, capped at 60_000 ms, with the same ±10% jitter.
The ordinary schedule is unchanged (not lengthened).
**Attempts exhausted (`attempt >= max_retries`):** if `class` is non-nil, `report_llm_error(agent_id, class, LlmRetryPolicy.model_exhaustion_delay(15))` seeds a fresh model-wide backoff for the crash-retry; then `{:error, reason}` propagates to `prompt_until_tools_or_limit/6` which **RAISES** `"LLM request failed after N retries"` → agent crash → scheduler crash-retry (`agent_max_retries`, default 3, lifecycle.ex:148-186).
Exceptions propagate IMMEDIATELY — the manual loop has no `rescue`, so raise paths are never retried.
Retried agents get a fresh worktree + new turn; their next slot request is queued behind the backoff if one is active.
A model with 0 LLM slots (peak hard-pause) does NOT raise: its slot request BLOCKS (queued in the scheduler — agent status `:blocked`) until capacity returns (peak exit → `update_config` → `grant_pending_on_resume` grants queued waiters) or a force-kill purge replies `{:error, :cancelled}` (raises in `with_llm_slot` → agent crash → scheduler crash-retry/cancel machinery).

**Fail-fast on a non-retryable provider rejection (`EvoGit.Agent.LlmError`):** a deterministic 4xx (e.g. HTTP 400 with Z.AI provider code 1210 "Invalid API parameter", reported by ReqLLM as `retryable: false`) can never succeed on a retry, so `handle_llm_failure/7` returns the terminal `{:error, {:llm_request_rejected, message}}` IMMEDIATELY after the first failed attempt: no sleep, no further attempt, no scheduler backoff, and it logs ONE `Logger.error` naming the agent + the message.
The message is **self-diagnosing**: `handle_llm_failure/7` builds it via `LlmError.format_failure(reason, params: ..., model: ...)`, so the persisted error names the request parameters Genesis SENT for that call (`Request parameters sent: [max_tokens, temperature, tools]` — NAMES only, sorted + de-duplicated, an empty `:tools` list excluded because ReqLLM sends no tools field then) and the model to check (`Check the model profile for model <spec> and remove parameters the provider does not support.`). Rationale: a provider code like 1210 names the KIND of problem but never the offending field, and the provider does not echo the request body back (`request_body: nil`), so without this tail the offending field is unidentifiable after the fact. The params come from the SAME `request_parameters(tools, llm_gen_opts)` value handed to `ReqLLM.stream_text/3` (`Keyword.merge([tools: tools], llm_gen_opts)`); the model from the private, deliberately TOTAL `ToolDispatch.diagnostic_model_spec/0` (a nil agent id / missing ETS row omits the model instead of raising — `current_model/0` would raise for a purged/cancelled agent, and a diagnostic annotation must never turn the graceful terminal tuple into a crash). Only parameter NAMES + the model spec are rendered: values (objective / tool-result content / credentials) are never inspected, and a map model spec is reduced to its `:id`/`:model`/`:provider` identity fields.
The same names are emitted once per attempt at `Logger.debug` (`ToolDispatch.log_request_parameters/2`, wording `"LLM request parameters sent: [...]"`) — a LAZY 0-arity message, so ordinary (retryable) failures are diagnosable too and the happy path pays nothing; nothing parameter-related is logged at info/error on the happy path. `EvoGit.Agent.ContextCompression.compression_llm_call/3`'s fail-fast branch passes its own `llm_gen_opts`/`llm_model` (the compression call sends no tools), so that path cannot raise either.
`prompt_until_tools_or_limit/6` has a dedicated arm passing that value through unchanged (the `raise "LLM request failed after N retries"` stays for every other `{:error, reason}`), and `ToolDispatch.do_turn/5` has a matching arm returning `{:error, terminal}` directly — deliberately NOT entering `handle_protocol_violation/5` or the grace path (grace turns / recovery cannot help a request that is rejected on every attempt).
The value then propagates out of `Runner.do_turn/1` → `Runner.loop/1` → `Runner.run/3` (which passes `{:error, _}` through `refresh_commit_sha/1` untouched) to the runtime and the task wrapper, so the task is persisted `:failed` with the actionable message in its structured `error` record — instead of a `RuntimeError` crash that the scheduler crash-retries, each crash-retry re-running the whole 15-attempt cycle.
The per-attempt failure log distinguishes the two: `retry_intent/1` appends `" (non-retryable — failing fast)."` instead of the `", retrying..."` used for every other class.
`format_subagent_result/1` (`subagent_processing.ex`) has a matching clause surfacing the message verbatim plus a "do not retry blindly — fix the model profile/request parameters or report to the user" hint, placed BEFORE the generic `{:error, reason}` catch-all (which would otherwise render it as an opaque `inspect/1`).

**Layer 2 — ReqLLM inner retries (inside each `ReqLLM.stream_text/3`):** `ReqLLM.Streaming.Retry` (`deps/req_llm/lib/req_llm/streaming/retry.ex`, wired at `finch_client.ex:251`). `max_retries` default **3** (retry.ex:31; `finch_client.ex:374` — overridable via `[[llm.models]]` generation params `max_retries`). Only retried: (a) **HTTP 429** — delay = parsed `Retry-After` header (seconds→ms; missing/unparseable/zero → 1000ms; retry.ex:194-196, 211-245); (b) **transport errors before any body data** (`data_received?: false`) — `pool_not_available` → 250ms, `closed`/`timeout`/`econnrefused` → 0ms (retry.ex:86-92, 198-209; failure.ex:5). **5xx and other HTTP statuses are NOT retried at this layer** (`%ReqLLM.Error.API.Request{}`; retry.ex:76-108), and no retry once data has started streaming (avoids duplicating partial output). Inner retries use blocking `Process.sleep` (retry.ex:123-125). Non-streaming Req-based paths (e.g. `openai_codex`) use `ReqLLM.Step.Retry` (`step/retry.ex`) — same 429 Retry-After honoring, transient transport reasons → 0ms, `max_retries` default 3.

**Layer 3 — scheduler per-model backoff:** `AgentScheduler.report_llm_error/3` (`agent_id, class, backoff_ms`) (agent_scheduler.ex) → `Slots.handle_report_llm_error(agent_id, class, backoff_ms, state)` (slots.ex): for both `:rate_limit` AND `:insufficient_balance` it sets per-model `llm_backoff_until[model_id] = now + backoff_ms`, re-queues ALL waiting agents of that model with the backoff timestamp, and schedules `:retry_llm_waiting` to fire once the backoff expires (slots.ex → `grant_pending_llm_slots`).
The `backoff_ms` is carried explicitly by the report — a short value for an ordinary transient rate-limit, a multi-hour value (`EvoGit.Agent.LlmRetryPolicy.model_exhaustion_delay/1`) for a model-exhaustion failure.
New slot requests during the backoff are queued (slots.ex).
A report with a nil/unknown class is a no-op (slots.ex).
Expired backoffs clear on any grant path (`maybe_clear_model_backoff/2`, slots.ex).
**Scoped per model_id — NOT global** (a backed-off model doesn't block other models).

**Slot acquired/released PER ATTEMPT — free during backoff sleeps:** `AgentScheduler.with_llm_slot/2` (agent_scheduler.ex:322-332) acquires via blocking `GenServer.call` (`request_llm_slot`, `timeout: :infinity`, agent_scheduler.ex:262-265) and releases via `after` → `release_llm_slot/1` cast (agent_scheduler.ex:277-280). Each attempt holds the slot only for its single `stream_text` + `process_stream`; the outer exponential-backoff sleep (and any inner Retry-After sleep) happens BETWEEN attempts while the slot is FREE. **Pause-scheduler implication:** a retrying agent's next attempt blocks at slot re-acquisition when `AgentScheduler.pause/0` is active (queued `:blocked`, granted on `resume/0`) — pause takes effect within one backoff delay. A raise inside the LLM call propagates immediately: `with_llm_slot`'s `after` releases the slot; the manual retry loop only recurses on `{:error, _}` tuples, never on raises. `ContextCompression` also uses `with_llm_slot` (context_compression.ex:79-103) but WITHOUT the outer retry loop — single `stream_text` (inner 3-retry only).

**Model-exhaustion retry policy — `EvoGit.Agent.LlmRetryPolicy`:** a pure module (no state, no I/O) holding the long model-exhaustion backoff schedule that Layer 1 reports to the scheduler.
`model_exhaustion_delays/0` is a 15-entry schedule — base 60 s, doubling, capped at 28_800_000 ms (8 h) — and `model_exhaustion_total_ms/0` = 216_900_000 ms (~60.25 h), which is `>= 172_800_000` (2 days).
Public API: `model_exhaustion_delays/0`, `model_exhaustion_delay/1` (1-based attempt index, clamped past the last entry), `model_exhaustion_total_ms/0`, `default_model_exhaustion_backoff_ms/0`.
Timing seams `:llm_model_exhaustion_backoff_base_ms` (default 60_000) and `:llm_model_exhaustion_backoff_cap_ms` (default 28_800_000) are read at call time.
Rationale: after a model-exhaustion error (e.g. DeepSeek HTTP 402 insufficient balance) the agent must wait long enough — ≥2 days total across 15 retries — for a human to top up, without any multi-hour agent-side sleep.

## First Message Construction (objective → LLM) — single choke point

The objective (`AgentState.objective`, a plain `String.t()`) enters the conversation ONLY inside the first **user** message, built in `Runner.do_run/2` (`runner.ex:131-276`). Exact construction: `combined_prompt` is assembled at `runner.ex:204-210`; the two initial messages are produced by the pure `ContextBuilder.build_initial_messages/4` at `runner.ex:218-224` (helper in `context_builder.ex`, directly unit-tested — see `agent/context_builder_test.exs`):

- `objective_body = if blank?(objective), do: "", else: to_string(objective)` (`runner.ex:201-202`)
- `combined_prompt` = `ContextBuilder.context_block(context_body)` (context tree + delegation-authority section + foreign-repos section + repo-notes section + quality-guidance section) joined with `ContextBuilder.objective_block(objective_body)` via `"\n\n---\n\n"` (`runner.ex:204-210`; wrappers at `context_builder.ex` — `context_block/1`/`objective_block/1` emit `<context>...</context>` / `<objective>...</objective>`)
- **`runner.ex:218-224`**: `ContextBuilder.build_initial_messages(system_prompt, combined_prompt, parent_id, attachments)` returns `[system, user]` (wrapped via `ReqLLM.Context.new/1` at `runner.ex:226`) — the ONLY place the objective is turned into an LLM message. The system message is `agent_module.system_prompt()` only; the objective is never a system message. No attachments (or non-root agent / repo-less) → the legacy plain-binary `user(combined_prompt)` fast path (byte-identical shape); a ROOT agent with attachments → `user([ContentPart.text(combined_prompt) | image/file parts…])` (multimodal — see below).

**Delegation-authority section**: built by `ContextBuilder.build_authority_section/1` (`context_builder.ex`, pure — takes `%{parent_id, repo_less, foreign_repos}`, never reads the process dictionary), present ONLY for non-repo-less agents whose task has non-primary foreign repos (else `""` and the blank-filter drops it — single-repo tasks stay token-neutral).
The section states the agent's role as **ROOT** (`AgentState.parent_id == nil` — exactly equivalent to `SchedMeta.depth == 0` by construction in `Dispatch.register_agent/7`) or **NESTED**, and pins the foreign-repo spawn rules for that role (root: writable foreign-repo `:read_write` spawns allowed one-at-a-time; nested: read-only foreign-repo spawns only, report writable needs back up the delegation chain).
The root signal at assembly is `agent_state.parent_id == nil` — never the process-dict depth (`Process.get(:evogit_agent_depth)` / `AgentScheduler.current_depth()`), which may not be populated yet in `do_run`.
Repo-less agents (self-reflective chat, `Process.get(:repo_less)`) never get the role statement; Genesis Mode B's two sequential depth-0 roots (Architect, then Manager) both have `parent_id` nil and both correctly get the ROOT statement — no special-casing.
The section is added in the runner-level `context_body` assembly ONLY — `ContextBuilder.build_dynamic_context/1` is untouched (tests pin its small-repo output length).

**Quality-guidance section**: built by `ContextBuilder.build_quality_guidance_section/1` (`context_builder.ex`, pure — takes `%{parent_id, repo_less, quality_level}`, never reads the process dictionary, `Map.get/3` so a partial map never raises), present ONLY for the task's ROOT agent.
It renders the per-task `:quality_level` guidance block via `EvoGit.QualityLevel.guidance/1` (`"fast"` → the FAST/speed block, `"high_quality"` → the HIGH QUALITY/correctness block).
The root signal at assembly is `agent_state.parent_id == nil` (exactly equivalent to `SchedMeta.depth == 0`, the same signal as the authority section); a NESTED agent (`parent_id` not nil) and a repo-less agent (`Process.get(:repo_less)`) both get `""` — subagents and the self-reflective chat are unaffected and their prompts stay byte-identical.
`"balanced"`/absent/unknown → `""` (`QualityLevel.guidance/1` is total), so the default case adds nothing and the blank-filter drops the section.
The value is surfaced from the spec opts via `Process.put(:quality_level, Keyword.get(spec.opts, :quality_level))` in `Runner.setup_dispatch_context/1` (alongside `:attachments`/`:custom_agent_id`); it reaches the root spec through `Runtime.Helpers.build_root_agent_spec/7` (`quality_level: Keyword.get(opts, :quality_level)`), which only the root spec builders call — subagent specs never carry the key.

**Repo-notes section (git-submodules awareness)**: when the repo has git submodules, the `<context>` block includes a `## Git Submodules` note — the rendered markdown block in `AgentState.repo_notes` (set at root spec build by `EvoGit.Runtime.Helpers.load_repo_notes/2`, inherited by subagents), passed through `ContextBuilder.build_repo_notes_section/1` (`context_builder.ex`). It lists the gitlink paths, explains they arrive as empty placeholder dirs in agent worktrees, tells the agent to populate them with `git submodule update --init [--recursive]` (network required; shared clone in `.git/modules`), and warns never to delete the placeholder dirs, not to create filler files inside them, and not to commit inside submodules. When `repo_notes` is nil (no gitlinks or detection failed) the section renders `""` and the blank-filter drops it — prompts for repos without submodules stay noise-free.

**Background-jobs section**: `ContextBuilder.build_context_block/1` renders `BackgroundJobNotice.section(Map.get(state, :background_jobs))` AFTER the quality-guidance section and BEFORE the clock line (the clock stays last).
It lists each of the agent's background shell jobs as `- `id` — status (detail) — label` plus a one-line orientation pointing at `job_output`/`job_list`; absent/`nil`/`[]` renders `""` (blank-filtered), so an agent with no jobs keeps a byte-identical `<context>` block.
Only the compression refresh injects the key (`ContextCompression.refresh_messages/1` → `EvoGit.BackgroundJobs.snapshot(owner_pid: self())`); message #1 is built once at run start and never rewritten, so it never carries jobs.
`BackgroundJobNotice.notice/1` renders the combined `[NOTICE]` message for just-finished jobs (header + one line per job + a `job_output`/`job_list` hint; `nil` for an empty list) for the agent loop to append.
Both renderers are total: label newlines fold to spaces, labels truncate at ~80 chars, the whole text caps at ~2000 chars, and a malformed/missing job key renders a placeholder instead of raising.

The per-turn LLM call receives the whole `%ReqLLM.Context{}` by value — `ToolDispatch.do_turn/5` → `prompt_until_tools_or_limit(context, ...)` (`tool_dispatch.ex:131`) → `call_llm_with_retry(context, tools, llm_gen_opts, agent_id, max_retries)` (`tool_dispatch.ex:195`) → `ReqLLM.stream_text(current_model(), context, Keyword.merge([tools: tools], llm_gen_opts))` (`tool_dispatch.ex:204-208`). Messages are never re-assembled per call; all other construction sites (turn warnings `runner.ex:291,304`, pending-user-message drain `runner.ex:323`, grace/recovery messages `runner.ex:438,447` — which re-inject the objective text via `recovery_warning_message/2` at `runner.ex:484-505` — no-tool-call nudges `tool_dispatch.ex:246-260`, tool results, compression `context_compression.ex:74,87-90`) only APPEND. Context compression re-injects `[system_msg, refreshed_first_user_msg, summary_msg]`: the `<objective>` block and any multimodal `:attachments` media parts are preserved byte-identically, but the `<context>` block is RE-READ from the agent's worktree on every compression (`ContextBuilder.refresh_first_user_message/2`, `context_compression.ex` `{:ok, response}` branch), so a long run's mid-run CONTEXT.md edits/creations are visible in the re-injected first message. Anything injected into the first user message survives compression but permanently occupies the context window — for multimodal `:attachments` this means the media parts (raw decoded bytes) are re-sent to the provider EVERY cycle after a compression, at full token/bandwidth cost.

**Multimodal content parts (`EvoGit.Attachments` — implemented)**: images/audio ride real req_llm content parts at THREE message-construction sites — the ROOT agent's FIRST user message, an injected user message, and a TOOL RESULT (`EvoGit.Agent.ToolOutput`). This paragraph covers the TASK-OPT path; `EvoGit.Attachments` (`../attachments.ex`) is the single source of truth for the wire contract and materialization. The `:attachments` task opt is a list of STRING-keyed maps `%{"type" => "image"|"audio", "name" => basename, "media_type" => IANA type, "data" => base64-encoded bytes}`; `RuntimeOpts.build_common_runtime_opts` validates it (`Attachments.validate/1`, spec-error style — malformed payloads fail task start with a descriptive `ArgumentError`; caps ≤4 per task and ≤15 MiB raw each) and `Helpers.build_root_agent_spec/7` forwards it into the root spec's `spec_opts` (omit-when-nil/[]). `Runner.setup_dispatch_context` surfaces the spec opt via `Process.put(:attachments, ...)` (`runner.ex:301`). **The task OPT itself is still ROOT-and-FIRST-message-only**: `ContextBuilder.build_initial_messages/4` gates on `parent_id == nil` AND a non-empty list — repo-less agents pass `nil` (a stray reflect key degrades to the plain-text path, never a crash) — then materializes base64 → raw bytes (`Base.decode64!/1`) as `image` → `ContentPart.image(raw, media_type)` and `audio` → `ContentPart.file(raw, name, media_type)` (audio rides a `:file` part — req_llm has no audio part type; `message/content_part.ex:69-79`), in stable input order, after a leading `ContentPart.text(combined_prompt)`. Base64 is mandatory in the opts layer (Store.Codec Jason-encodes whole opts; raw non-UTF-8 binaries abort Jason) — raw bytes exist only inside the LLM-message content parts. Subagents (non-nil `parent_id`) never inherit; resume/merge/auto-resolve follow-ups do not re-carry the key (fresh text objectives; the user can re-attach). Deliberately NO model-capability check (a provider erroring on the modality is the user's concern). The objective stays strictly `String.t()` in `AgentSpec`/`AgentState` — attachment bytes travel as a spec opt + base64 in persisted task opts, never in an `AgentState` field or the objective string. No objective-size truncation exists anywhere (CLI `get_input/2` reads `-f file` verbatim); the conversation-level limit is the window-relative compression trigger (configured profile `context_window`, default 200_000, with `[:llm, :compression_threshold_tokens]` as an optional explicit override — see `Compression.Threshold`). The any-step counterpart (media riding a TOOL RESULT instead of only the first user message) is `EvoGit.Agent.ToolOutput` — see "Multimodal Tool Outputs (`EvoGit.Agent.ToolOutput`)" below.

## Multimodal Tool Outputs (`EvoGit.Agent.ToolOutput`)

`%EvoGit.Agent.ToolOutput{text: String.t(), attachments: [EvoGit.Attachments.t()] | nil}` is the structured TOOL-RESULT type: the same media that ride the ROOT agent's first user message (`:attachments` task opt) can therefore ride a tool result at ANY step of a run. `attachments` holds the STRING-keyed base64 media maps of `EvoGit.Attachments` — raw non-UTF-8 bytes never ride the struct, so a `%ToolOutput{}` stays safe across a node/`:erpc` hop and an `EvoGit.Store.Codec` round trip.

- **Accessors (the ONLY sanctioned surface for the pipeline)**: `new/2` (validates the media via `EvoGit.Attachments.validate/1` at CONSTRUCTION — the same caps, ≤4 attachments and ≤15 MiB raw each — and stores them verbatim; `nil` and `[]` both mean "no media"), `wrap/1` (binary → `%ToolOutput{text: bin, attachments: nil}`; a `%ToolOutput{}` → itself, idempotent; `nil` → `nil`), `text/1`, `with_text/2` (replaces the text, PRESERVES the media — the post-sanitize seam), `media?/1`, `to_content_parts/1`.
- **All-text byte-identity**: `wrap("x") |> to_content_parts() == [ReqLLM.Message.ContentPart.text("x")]` — `to_content_parts/1` delegates to `EvoGit.Attachments.to_content_parts/2` with nil attachments, so an all-text tool output materializes exactly as today's plain-string path.
- **Wrap boundary invariant (pinned)**: `EvoGit.Agent.OutputSanitizer`, `EvoGit.Agent.TruncationFeedback` and `EvoGit.Agent.DelegationHints` keep their BINARY-ONLY contract (`sanitize_and_truncate/3`, `append_truncation_feedback/3`, `maybe_append_delegation_hint/4` take a string and return a string). The wrap/unwrap between binary and `%ToolOutput{}` happens ONLY inside `agent/tool_dispatch.ex`. No sanitizer ever sees or returns a `%ToolOutput{}`.
- **Pipeline (wired)**: `ToolDispatch.sanitize_tool_result/3` wraps a tool's raw return (`ToolOutput.wrap/1`), runs the BINARY-ONLY `OutputSanitizer.sanitize_and_truncate/3` → `TruncationFeedback.append_truncation_feedback/3` pipeline on the TEXT component only (`ToolOutput.text/1`), re-attaches the sanitized text (`ToolOutput.with_text/2`) and COLLAPSES an all-text output back to a plain binary (so it never becomes a struct). `ToolDispatch.apply_tool_output_tracking/3` (redundant-cd warning + write/read delegation hints) likewise unwraps the text before the string concatenations and re-attaches it with the media preserved. `ToolDispatch.run_tool_call/3` therefore yields `String.t() | %ToolOutput{} | nil`, and `ToolDispatch.assemble_tool_result/3` is the ONE message-construction site: a media-carrying output is materialized via `ToolOutput.to_content_parts/1` as a content-part LIST, while a plain binary (or a subagent result string) goes straight to `ReqLLM.Context.tool_result/3` — byte-identical to the legacy path. The tool-facing entry point is the enlarged `EvoGit.Agent.Tools.execute/5` return contract (`String.t() | %ToolOutput.t() | {:error, reason}`, see `tools/CONTEXT.md`); the guard/error paths stay binary.
- **Message normalization seam**: `EvoGit.Attachments.message/1` normalizes a legacy `String.t()` OR a `%{text:, attachments:}` map (atom- OR string-keyed) into the canonical `%{text: String.t(), attachments: [t()] | nil}`; `EvoGit.Attachments.validate_message!/1` validates that canonical map (descriptive `ArgumentError`, spec-error style). This is the ONE normalizer the pending-injected-user-message queue uses.
- **Pinned decisions**: (a) media stay base64 STRING maps — nothing non-UTF-8 may cross a node/Codec boundary; (b) materialization always produces a plain `[ReqLLM.Message.ContentPart.t()]` list, NEVER a `ReqLLM.ToolResult` (that struct stamps extra metadata and would break byte-identity); (c) the `:attachments` task-opt ROOT-only gate is UNCHANGED — the generalized capability enters via tool results and injected user messages, never by widening the task opt; (d) the `EvoGit.Attachments` caps apply PER TOOL OUTPUT as well as per task opt.

## Tool-Execution Crash Semantics (raises are CONTAINED in the tool task; escalation STOPS at the agent)

- Every tool call runs inside a **LINKED** `Task.async` in `ToolDispatch.execute_tool_with_timeout/8` (`tool_dispatch.ex:1448-1523`), hosted by the AGENT process itself in the serial (file-mutating) phase (`batch_execute_tools/4` at `tool_dispatch.ex:1238` calls `run_tool_call/3` — `:1360` — directly) and by a `Task.async_stream` worker in the parallel phase (`tool_dispatch.ex:1306-1320`; stream workers are themselves linked to the enumerating agent).
- A tool RAISE is CONTAINED one level up, in the tool task itself: `execute_tool_task/7` (`tool_dispatch.ex:1571-1622`) wraps `EvoGit.Agent.Tools.execute/5` in `try/rescue/catch` — a raise becomes `{:tool_crashed, Exception.format_banner(:error, exception)}`, a throw or any other exit becomes `{:tool_crashed, "<kind> <reason>"}`, and both reach the model as `"Error: Tool execution crashed: …"`. Only the `:normal`/`:shutdown`/`:kill`/`{:shutdown, _}` exit family is re-raised unchanged, so a legitimate task exit is never swallowed. The agent therefore SURVIVES a raising tool implementation and the model can self-correct on the next turn — which is also why `execute_tool_with_timeout/8`'s `{:exit, reason}` arm now only sees those re-raised exits (and `nil` = its own timeout shutdown).
- `EvoGit.Agent.Tools.execute/5` itself has NO try/rescue around a tool implementation (`tools.ex:218-249` — the `is_map`/`is_binary` clauses, with `execute_tool/5` clauses from `:458`) — containment lives exclusively in `execute_tool_task/7`, not in the tool layer.
- Timeout: a per-call WHOLE-CALL budget (not an idle timeout), resolved by the pure `EvoGit.Agent.ToolInvocation.resolve_timeout/4` (`tool_invocation.ex:103-112`): an explicit positive integer `timeout` arg clamped by `max_tool_timeout`; otherwise the platform shell tool gets at least `@shell_default_timeout_ms` 120_000 ms and every other tool gets `[:scheduler, :default_tool_timeout]` (default 10_000 ms), both clamped by `[:scheduler, :max_tool_timeout]` (default 1_800_000 ms hard cap) read via `DelegationHints.max_tool_timeout/0`. `apply_advertised_tool_timeout/3` (`tool_dispatch.ex:1542-1554`) then raises the budget to a tool's advertised default (`Tools.default_timeout_ms/1`, currently only the shell tool's 120 s) when no explicit `timeout` arg was supplied; level-2/3 `run_command` calls are floored to `CommandApproval.timeout() + @approval_execution_buffer` (30 s) and still capped (`tool_dispatch.ex:1462-1486`). The timeout path is link-safe because `Task.shutdown/2` unlinks before killing (Elixir `task.ex:1382-1390`).
- NO escalation to the app: the agent task is started with `Task.Supervisor.async_nolink(EvoGit.TaskSupervisor, ...)` (`agent_scheduler/dispatch.ex:225-231`) — monitor-only (no link to the scheduler) and a `:temporary` child (`task/supervisor.ex:610-619`); OTP's supervisor never counts a temporary child's exit toward restart intensity (`stdlib supervisor.erl:1441-1444` — the temporary clause never calls `add_restart/1`). The scheduler survives, crash-retries the agent (`agent_scheduler/lifecycle.ex:142-213`; `[:scheduler, :agent_max_retries]` default 3) and then fails the agent/task (`Lifecycle.handle_agent_down/4` reason ≠ `:normal`), and `TaskRegistry.handle_info({:DOWN, ...})` (`task_registry.ex:1513-1569`) is total (no raise).
- Diagnostic consequence: a tool failure is NEVER fatal to the agent (it arrives as a normal `"Error: …"` tool result), so an unexplained BEAM death or an agent crash should be looked for in the LLM-error paths (`## Known Issues (LLM-error exit shape)`), not in the tool layer. The only OS-process killing under `agent/` is `tools/lsp.ex`'s deliberate teardown of the EXTERNAL language-server child it spawned: `System.cmd("kill", ["-9", pid])` on Unix / `System.cmd("taskkill", ["/PID", pid, "/T", "/F"])` elsewhere (`lsp.ex:747-763`, with a `rescue _ -> :ok`), plus the port close and message drain through `EvoGit.Sandbox.Helpers.close_port/1` / `drain_port_messages/1` (`lsp.ex:728-729`). That kill is scoped to that reaped child — it never targets the agent process or the scheduler. No `Process.exit`, `System.stop`, `System.halt` or `:init.stop` exists anywhere under `agent/`.

## Known Issues (LLM-error exit shape)

Where an LLM error can become an ABNORMAL agent-Task exit (raise) instead of a returned `{:error, reason}` value:

- **Duplicate tool calls are dropped WITHIN one response only.** `ToolDispatch.dedupe_tool_calls/2` (tool_dispatch.ex:631-660) dedupes by `:id`, then by `{name, args_map}`, logs a warning and removes the extras (the response's `tool_calls` is rewritten to match). There is NO cross-turn detection of the same tool + arguments being re-issued, and NO cap on how many distinct tool calls one response may carry.
- `ToolDispatch.do_turn/5` (`tool_dispatch.ex:218-269`) matches the FOUR shapes `prompt_until_tools_or_limit/6` returns: `{:ok, response}`, `{:implicit_completion, response, text}` (→ `process_llm_response/6` with the model's own report text), `{:error, :protocol_violation}` (→ `handle_protocol_violation/3`) and the fail-fast terminal `{:error, {:llm_request_rejected, _}}` (passed through unchanged). Every OTHER `{:error, reason}` raises INSIDE `prompt_until_tools_or_limit/6` (`"LLM request failed after N retries"`, tool_dispatch.ex:352) rather than returning, so a `CaseClauseError` out of the agent Task can only appear if that return contract is widened without a matching clause here.
- `prompt_until_tools_or_limit/6` itself raises `"LLM request failed after N retries"` (`tool_dispatch.ex:352`) once `call_llm_with_retry/5` returns a terminal `{:error, reason}` — the exhaust-all-retries raise site.
- `ContextCompression.compress_if_needed/2` (`context_compression.ex`) makes ONE compression LLM call with NO retry and NO rescue.
  A NON-RETRYABLE provider rejection is the narrow fail-fast exception: it logs one `Logger.error` and returns the terminal `{:error, {:llm_request_rejected, message}}`, which `Runner.loop/1` propagates out of `Runner.run/3` unchanged (no crash-retry storm).
  Every OTHER LLM error there still raises a `MatchError` with zero retries burned (crash-retry + scheduler-backoff semantics unchanged).
- `AgentScheduler.with_llm_slot/2` (`agent_scheduler.ex:413-428`) raises only on a non-`:ok` slot reply; the only such reply is `{:error, :cancelled}` from a force-kill / graceful-cancel queue purge (`slots.ex:420,448,449`) — never from an LLM provider error. A 0-capacity model BLOCKS in the queue instead.
- The `use EvoGit.Agent`-generated `run/2` (`agent.ex:94-96`) is a bare delegation to `Runner.run/3` (no try/Task/spawn). `Runner.run/3`'s `try/after` helpers and `refresh_commit_sha/1` (`runner.ex:113`, fallback `other -> other`) never raise and pass non-success shapes through unchanged; `Runner.loop/1` (`runner.ex:478-499`) returns either `continue_loop/2`'s value (which returns `do_turn/5`'s value directly — no funneling of non-`:protocol_violation` errors into `trigger_recovery`) or the compression fail-fast terminal tuple unchanged.
- Provider 4xx (e.g. HTTP 400) arrives as a RETURNED `{:error, %ReqLLM.Error.API.Request{retryable: false}}`: req_llm classifies 400 as `:no_retry` (zero inner retries) and `ReqLLM.StreamResponse.process_stream/2` rescues/catches any stream raise into `{:error, _}`. There is NO try/rescue anywhere in `call_llm_with_retry/5` / `do_call_llm_with_retry/6` / `prompt_until_tools_or_limit/6` — raises propagate immediately and are never converted into retries.

## Constraints

- Every agent MUST `use EvoGit.Agent` and implement `system_prompt/0`.
- System prompts MUST NOT contain dynamic state, objectives, or context trees — those are injected as user prompts.
- Read-only agents (`agent_type: :read`) should restrict `available_tools/0` to read-only tools.
- The `complete_task` tool is always injected by the macro; agents need not include it.
- Tool schemas use `ReqLLM.tool/2` format.
- Agents commit before delegating subagents (enforced by auto-commit fallback in scheduler).
- Context compression and subagent processing are extracted to dedicated modules but invoked from the agent loop via callbacks.
- **LoopState discipline**: Agent loop state must always be a `%LoopState{}` struct. Update syntax preserves the struct type.
- **Result discipline**: Agent completion produces `%Result{}` structs. Consumers pattern-match on struct fields rather than using `Map.get/2`.

## Repo-Path Assumptions (agent-loop crash points on a missing repo)

The agent loop hard-assumes a real git worktree, set once by `Runner.setup_dispatch_context/1` (`runner.ex:228-281`): `Process.put(:repo_path, worktree_path)` (`runner.ex:249`), `:genesis_repo_root`, `:evogit_repo_id`, `:evogit_agent_id`, `:evogit_agent_depth`, `:evogit_started_at`, `:custom_agent_id` (from `spec.opts`). The same function UNCONDITIONALLY requests a fresh worktree via `WorktreeManager.create_worktree_for_agent/6` and RAISES `"Failed to create worktree..."` on `{:error, reason}` (`runner.ex:258-271`) — a repo-less agent type must branch here (the worktree-creation and `resolve_agent_repo_root` seams live on the scheduler side; see `../agent_scheduler/CONTEXT.md` → "Repo-path assumptions").

Within the agent loop, the following raise on nil/missing `:repo_path` (all `|| raise "repo_path not in process dictionary"` or git-error raises) unless marked repo-less-safe:
- `sync_current_commit_after_tools/1` (`tool_dispatch.ex:149-169`, `@doc false`) and its completion sibling `sync_and_get_current_commit/1` (`tool_dispatch.ex:172-195`) are BOTH repo-less-safe: `Process.get(:repo_less)` short-circuits them to `:ok` / a nil `commit_sha` before any git I/O, so `complete_task` (`do_complete/2`, `tool_dispatch.ex:1105-1112`) and the implicit-completion route (`build_completion/2`, `tool_dispatch.ex:1125-1128`) both finish a repo-less agent without touching git. For a repo-backed agent both raise: an unset `:repo_path` (`|| raise "repo_path not in process dictionary"`) and any `Git.rev_parse/1` failure through the shared `raise_rev_parse_error/1` helper — a missing repo/worktree directory (`{:error, {:enoent, _}}` from `Git.run/2`'s pre-check) raises a clear "Worktree vanished while agent was running (removed mid-run): ..." message, every other shape raises `"Git rev_parse failed (#{code}): #{msg}"`. `sync_current_commit_after_tools/1` runs after EVERY standard-tool batch (`process_standard_calls/2`, `tool_dispatch.ex:1232`) and after subagent processing (`sync_commit_fn`, `tool_dispatch.ex:1188`).
- `batch_execute_tools/4` (`tool_dispatch.ex:812` `repo_path` raise; `process_standard_calls` `tool_dispatch.ex:793` raises on nil `:genesis_repo_root`) — any standard tool call requires BOTH keys present.
- `do_run/2` validates `Path.join(repo_path, node_path)` exists (`runner.ex:132-140`) → `{:error, :path_not_exist}` if not.
- `do_commit_pending/1` in `AgentScheduler.Dispatch.commit_pending_in_worktree/0` (scheduler side, dispatch.ex:271-312) is the ONE repo-dependent path that is already repo-less-safe: nil `:repo_path` → no-op `:ok`; non-git dir → `Git.status` returns `{:error, {128, _}}` → logged warning, returns `:ok`. Called from `Runner.run/3`'s `after` block (`runner.ex:52`) and `SubagentProcessing.process_subagent_calls/3` (`subagent_processing.ex:60`).
- `CompleteTask.complete/4` (`tools/complete_task.ex:128-190`): `%Result{}` construction sets `commit_sha` (enforced key), `branch` (derived from ETS `lookup_task_info/1` — repo-free, `{:error, :not_found}` → `{0, nil, 0}`), `repo_id` (`Process.get(:evogit_repo_id)`), `usage`; `tag/base_commit/agent_count/archive_records` stay nil. Git-note (`add_metadata_note`) and archive-ref writing (`write_archive_refs`) are both gated on `base_commit` (from `phylo_node`), so a repo-less agent with a nil phylo_node skips them naturally. The dirty-workspace check `CompleteTask.check_workspace_dirty/1` is tolerant (`_ -> {:clean, nil}` on git errors).

## Repo-less Agents

A repo-less agent runs WITHOUT a git worktree (chatbot-style). It is marked via `Process.get(:repo_less)` (set by the runner) and its `Process.get(:repo_path)` points at the real Genesis source root or a placeholder binary (not a worktree). Cardinal rule: **repo-less agents must never touch git or write files.**

- **Write guard**: `EvoGit.Agent.Tools.execute/5` (`tools.ex`) blocks all write CALLS for repo-less agents, returning `"Error: this agent has read-only access to the system — the <name> tool is disabled."`. Both guards classify through the CALL-level `write_call?/2` (tools.ex:344) = `write_tool?/1` OR the shell tool called with a truthy `run_in_background` (lenient `background_start?/1`, tools.ex:368 — `true`/`"true"` only): starting a DETACHED job is a write capability (it can mutate anything a foreground command could and outlives the call) but it is an ARGUMENT of the shell tool, not a tool name, so it cannot live in the `@write_tools` set. That branch has its own message naming `bash`'s `run_in_background` mode (the shell tool is itself in `@write_tools`, so the narrow arm is matched FIRST in both `cond`s — otherwise it would be shadowed). `write_tool?/1` itself is unchanged (name-only: built-in `@write_tools` OR `EvoGit.CustomTools.write_tool?/1`, a user-defined tool loaded from `<config_dir>/tools/` whose `read_only?/0` is false/absent — custom write tools are gated exactly like built-in writers; unknown names are never write tools). Both `execute/5` argument paths (map args and the JSON-string decode fallback) route through the shared `maybe_block_repo_less/5` helper, so there is no bypass. ## Foreign-Repo Path Resolution (recognition sites)

A `%ForeignRepo{}` carries only `root` (absolute repo root) — there is NO worktree field. Each spawn gets a FRESH ephemeral worktree, currently laid out exactly like the primary's: `<repo_root>/.genesis/workers/worker_T<task>_A<local>` (scheduler-side, `agent_scheduler/dispatch.ex:198-203`). In ADDITION, every WRITABLE non-primary repo carries a PERSISTENT worktree at `<root>/.genesis/foreign_repos/<id>` (`ForeignRepo.worktree_path/1`; lifecycle owned by `EvoGit.AgentScheduler.ForeignWorktree` — see `agent_scheduler/CONTEXT.md`) that agents may address by absolute path to READ the repo's latest committed state. Path recognition uses `ForeignRepo.resolve/2`, which returns `{:ok, repo, base_dir, rel_path}` — for a WRITABLE repo it intercepts the `<root>/.genesis/foreign_repos/<id>` prefix BEFORE the generic `root` match, returning the worktree as `base_dir` with the node path taken relative to it; otherwise `base_dir` is `repo.root`. `resolve_path/2` delegates to it; `normalize_path/2` itself still prefix-matches `root` alone.

- **Spawn-arg → repo_id/base** — `subagent_processing.ex` `resolve_subagent_path/4`: absolute → `ForeignRepo.resolve(foreign_repos, raw_path)` → `{:ok, repo, base_dir, rel_path}` → returned as `{:ok, repo.id, base_dir, rel_path}` (base = the writable repo's persistent worktree when the path lies under it, else `repo.root`; node path relative to the base: `<wt>/src/foo` → `./src/foo`, never `./.genesis/foreign_repos/<id>/src/foo`); relative → parent repo id + parent `repo_path`. Absolute under NEITHER a foreign root NOR a writable worktree → fallback `foreign_repo_match_root/2` (prefix match against primary `repo_path`) → else descriptive error listing `Enum.map(foreign_repos, & &1.root)`.
- **Tool-layer write gate** — `tools.ex:302-330` `maybe_block_read_only_foreign_repo/5` resolves the agent's role by `:evogit_repo_id` id-match, falling back to `ForeignRepo.resolve_path(foreign_repos, Process.get(:repo_path))`; path-level scope check `tools/shared.ex:373-395`.
- **Scheduler repo-root resolution** — `agent_scheduler/dispatch.ex:542-558` `resolve_agent_repo_root_regular/2`: for `spec.repo_id != "primary"` it finds `spec.foreign_repos` by id and takes `.root` — `spec.phylo_node.repo` is IGNORED for foreign repos (the primary branch instead strips the worktree suffix via `Worktrees.repo_root_from_worktree/1`). Branch name `evogit-agent-T<task>-A<local>` (`agent_scheduler/worktrees.ex:44-45`). The persistent foreign worktree is a READ view only — a foreign agent's write/execution workspace remains its ephemeral `.genesis/workers/...` worktree, so this repo-root resolution is unaffected.
- **Prompt surface** — `context_builder.ex` `build_foreign_repos_section/1` renders `| :<id> | <path> | <desc> |`; for a WRITABLE repo the path cell shows BOTH the repo root AND its persistent worktree path (`<root> (worktree: <root>/.genesis/foreign_repos/<id>)`) plus a root-vs-worktree clarification sentence, while read-only repos keep today's root-only rendering (the output is unchanged when no writable repo exists). `subagent_schemas.ex:40-52` tells the LLM to use the ABSOLUTE foreign root.

## Foreign-Repo Commit Propagation (spawn-time resolution + staleness hazard)

Subagents NEVER get a live foreign-repo commit snapshot: the starting commit for a foreign target is resolved at SPAWN time from the task-level `foreign_repos` list plus the parent's scheduler-side roll-up map.

- **Advance authority — the write side lives in the scheduler, not here**: `agent/subagent_processing.ex` only ever READS the tracked map (`AgentScheduler.get_foreign_repo_commits(state.agent_id)` at `:419`) to seed spawns; it never records a foreign-repo commit. A subagent's `Result.foreign_repo_commits` is NOT populated here either (`CompleteTask` leaves the struct default `%{}`) — the scheduler injects it from the agent's own `SchedMeta` at completion (`Lifecycle.handle_task_result/3` → `inject_foreign_repo_commits/2`) before rolling it up into the parent. A foreign repo's tracked commit is advanced ONLY by a completing child that is ITSELF a writable agent running in that repo (its `spec.repo_id` is a task-level `writable: true` foreign repo AND its `agent_type() == :read_write`) — enforced in `agent_scheduler/subagents.ex` (`Subagents.store_sub_result/3,4`); a local/`"primary"` child or a read-only foreign probe never advances it.
- `AgentSpec.foreign_repos` is a struct FIELD (`agent_spec.ex:29`) that also rides inside `opts` (`agent_spec.ex:66`); the list is built ONCE per task by `Runtime.Helpers.build_root_agent_spec/7` (`runtime/helpers.ex:567-597`, after `load_foreign_repos/2` validation at `:306-346`) with the ORIGINAL per-repo `base_sha` (nil = HEAD, never resolved to a concrete sha at load time).
- Registration copies it verbatim into `%AgentState{}.foreign_repos` (`agent_scheduler/dispatch.ex:94`) — there is NO update path afterwards (only the change-detection field list, `agent_scheduler/store.ex:540`).
- `Runner.setup_dispatch_context/1` surfaces it twice: `Process.put(:foreign_repos, spec.foreign_repos || [])` (`runner.ex:290` — the role gate read by `tools.ex:248-276` and `tools/shared.ex:357-368`) and `LoopState.foreign_repos` (`runner.ex:256`).
- A child spec INHERITS the parent's list verbatim — `subagent_processing.ex:132` (`state.foreign_repos`) → `:190` (`foreign_repos: foreign_repos`) — so a child's `base_sha` is the frozen task-level value, never refreshed from completed foreign work.
- **The child spec's `repo_id` is derived from the spawn `path` form AND the parent's repo** (`resolve_subagent_path/4`, `subagent_processing.ex`): an ABSOLUTE path under a foreign repo root OR that writable repo's persistent worktree → that repo's id (`ForeignRepo.resolve/2`, which yields the worktree as the node base when the path lies under it); an ABSOLUTE path under the parent's own repo → the parent's repo id; a RELATIVE path → the PARENT's repo id (`parent_state.repo_id`, the SAME source the spawn gate reads) with the PARENT'S OWN worktree as target root. So a child a foreign-repo Manager delegates to by RELATIVE path carries the foreign `repo_id` and physically runs in the foreign repo (the relative branch never hardcodes `"primary"`). `build_subagent_specs/3` keys ContextNode.load AND the phylo-node clause on `same_repo? = target_repo_id == parent_repo_id`. Consequence for a writable foreign-repo parent B: a relative-path `:read_write` child is SAME-REPO (`spec.repo_id == parent_repo_id`), so `validate_spatial_contract_for_spec/4` takes the same-repo branch (UNRESTRICTED — the intended foreign-repo Manager internal-parallelism path), the child is authorized by `Subagents.writable_foreign_repo_agent?/1` (when its module is `:read_write` and the repo entry is `writable: true`), and it is merged into B's worktree. A foreign repo configured with the literal id `"primary"` is treated as the primary repo everywhere (`ForeignRepo.primary?/1`). An ABSOLUTE path remains the form for the ROOT's cross-repo delegation (the gate's root-agent-only + one-at-a-time rule for cross-repo `:read_write` spawns is unchanged), but is NOT required for a foreign-repo parent's own children.
- The child's phylo node for a foreign target is resolved by `resolve_foreign_phylo_commit/4` (`subagent_processing.ex:673-708`), precedence: (1) non-nil `base_sha` of that inherited entry (`:681-690`); (2) the PARENT's tracked map `AgentScheduler.get_foreign_repo_commits(parent_id)` fetched at spawn-batch time (`:419`, `agent_scheduler.ex:306-312`) (`:692-705`); (3) foreign HEAD (`:694-702`). Precedence (1) over (2) is pinned by `test/evo_git/agent/subagent_processing_test.exs:632-667`.
- A child's OWN `SchedMeta.foreign_repo_commits` starts EMPTY (`dispatch.ex:99-108`; `agent_scheduler/sched_meta.ex:57`) — the tracked map is NOT inherited, so a NESTED agent's foreign spawns can only see `base_sha` or foreign HEAD.
- The LLM `commit_id` arg is silently IGNORED for foreign targets (`subagent_processing.ex:620` binds `_commit_id`), even though the shared schema advertises it as "the commit SHA to spawn the subagent on" (`subagent_schemas.ex:65-70`); it is honored only for `"primary"` targets.
- The child's first-user context carries NO commit/branch info for foreign repos — only the id/root/description table (`context_builder.ex:32-52`) and the ROOT/NESTED authority line (`:71-86`); the worktree is created at `spec.phylo_node.current_commit` (`agent_scheduler/worktrees.ex:107,134`, phylo built at `:312-325`).
- Feedback loop: the parent's in-memory `foreign_repos` is NEVER updated — the only channels are the scheduler roll-up into the parent's `SchedMeta.foreign_repo_commits` (`agent_scheduler/subagents.ex` — `store_sub_result/3,4`) and the parent's textual cross-repo note `"  - <repo_id>: <sha>"` (`subagent_processing.ex:477-484`), which the LLM sees but cannot act on (no API to set a spawn's starting commit).
- STALENESS HAZARD (known issue, READ-SIDE): a non-nil task-level `base_sha` wins unconditionally in `resolve_foreign_phylo_commit/4`, masking all intra-task progress — every later foreign spawn (root OR nested) restarts there, and a NESTED agent's spawn (its own map starts empty, line above) falls back to foreign HEAD. The final per-repo report branch is created from the tracked map (`runtime/helpers.ex:148-160`, writable repos only) while the producing agent's own `evogit-agent-*` branch is deleted when its worktree is reclaimed (`agent_scheduler/worktree_manager.ex:280-298` → `:574-602`), so a spawn seeded from a stale commit can leave an advanced foreign commit unreachable from the reviewed/reported branch.

### Command-approval gate (run_command level-2/3, EvoGit.CommandApproval)

The command shell's security levels are enforced INSIDE the `run_command` tool call (`EvoGit.CommandShell.execute/1` — the `:chat` approval mode) — the tool task blocks until the user decides. (`CommandShell.execute/2` also supports `approval: :auto`, used by the CLI `run` subcommand, which bypasses the gate for all levels — the terminal user is the human authorizer.) Facts:

- **Levels**: `EvoGit.CommandShell.security_level/1` maps each command path to 1|2|3 (`"help"`/`"Help"` → 1; unknown/non-binary → 1). Level 1 executes immediately; levels 2 (`GuideUser.guide_user`) and 3 (`StartTask.start_task`, `CancelTask.cancel_task`, `ForceKillTask.force_kill_task`, `DeleteTask.delete_task`) do NOT run until the user approves. Parse/validation errors still surface BEFORE the gate (the args parse first).
- **Gate mechanics**: at the shell choke point (`EvoGit.CommandShell.run_command/3`), level ≥ 2 calls `EvoGit.CommandApproval.request(path, human_args, level, Process.get(:evogit_agent_id), Process.get(:evogit_task_id))` — a blocking `GenServer.call(:infinity)`. `:approved` → the handler runs; `:denied` → `{:error, "Action denied by the user: ..."}`; `:timeout` → `{:error, "The user did not confirm ... in time ..."}` — the handler NEVER runs on anything but `:approved` (fails closed, including when the approval service is not running).
- **Approval window**: bounded per request by app env `[:evo_git, :command_approval_timeout]` (default `120_000` ms), read at request time. When the window expires the caller is replied `:timeout` and a `{:approval_resolved, request_id, :timed_out}` broadcast goes out.
- **Task-lifecycle auto-deny**: `EvoGit.CommandApproval` subscribes to the `"tasks"` PubSub topic in init; a `{:task_updated, task_id, status, node}` with `node == node()` and `status in [:cancelling, :completed, :failed, :cancelled]` auto-resolves `:denied` every pending request carrying that `task_id` (a graceful Stop/cancel never stalls on an approval wait). Caller death (each waiting caller is monitored) cleans the request up and resolves it `:timed_out`.
- **PubSub contract** (topic `"approvals"`): `{:approval_requested, request}` where `request = %{request_id: "aprv-…", command, args, level, agent_id, task_id, node}` and `{:approval_resolved, request_id, decision}` (`:approve | :deny | :timed_out`). Every requested card eventually resolves (invariant: one requested → one resolved).
- **ToolDispatch timeout extension** (`execute_tool_with_timeout/8`): an approval-requiring `run_command` call is detected up front (`approval_window_tool_call?/2` peeks `CommandShell.security_level/1` of the first whitespace token) and gets a per-call timeout of `max(configured, EvoGit.CommandApproval.timeout() + @approval_execution_buffer 30_000)`, capped by the scheduler's `max_tool_timeout` (30 min) — otherwise the 10s default tool timeout would kill the task mid-wait. Level-1 `run_command` calls keep their exact current behavior.
- **Agent/task context**: spawned tool tasks do NOT inherit the caller's process dictionary, so `batch_execute_tools/4` resolves the owner identity ONCE per batch (`%{agent_id:, task_id:, agent_pid:}` — tool_dispatch.ex:1254-1258, with `agent_pid: self()`) and `execute_tool_task/7` puts `:evogit_agent_id`/`:evogit_task_id`/`:evogit_agent_pid` into EVERY tool task (the approval gate reads the first two; `EvoGit.BackgroundJobs` binds detached jobs to the third) AND unconditionally re-installs the per-task tmpdir via `EvoGit.TaskTmpdir.put_current/1` (the value is read once in `batch_execute_tools/4` via `TaskTmpdir.current/0` and threaded down through `run_tool_call/3` → `execute_tool_with_timeout/8`). Direct/test callers have neither key nor a tmpdir and the request registers with `nil` ids (still gated by request_id and its own task lifecycle).
- **RPC responders**: `EvoGit.AgentScheduler.RemoteAPI.respond_approval/2` (→ `EvoGit.CommandApproval.respond/2`; `{:error, :approval_not_started}` when the service is down) and `EvoGit.RemoteNode.respond_approval/3` (local direct call / remote `:erpc`).
- **Dispatch plumbing**: `run_command` is dispatch-registered ONLY in `tools.ex` — never in `schemas/0` or `read_only_schemas/0` (giving every coding agent task-control access would be a scope/security violation); the approval gate is defense-in-depth layered on top of the dispatch whitelist.

## Notes for Agents — Per-Task Scratch Space / TMPDIR Design Surface

The managed per-task tmpdir is IMPLEMENTED — `EvoGit.TaskTmpdir` (`../task_tmpdir.ex`) is the single source of truth for a task's scratch dir (`[tmp] mode` = `:system` → `<system tmp>/genesis/task_<id>`, `:custom` → `<[tmp] path>/genesis/task_<id>`, `:per_repo` → `<TASK's primary repo>/.genesis/tmp/task_<id>`, falling back to `:system` when the repo path is nil). The seam is threaded as follows (detail: `tools/CONTEXT.md` "Per-Tool Path Handling" + `sandbox/CONTEXT.md`):

- **Runner resolves + installs it** (`setup_dispatch_context/1`, runner.ex:360-391): prefers a parent-threaded `spec.opts[:task_tmpdir]`; otherwise computes `EvoGit.TaskTmpdir.ensure(meta.task_id, primary_repo_path)` where `primary_repo_path` is `Process.get(:genesis_repo_root)` (the agent's ORIGINAL repo root — for the root agent the task's primary repo) or `nil` for repo-less agents (so `:per_repo` falls back to `:system`; the Genesis source root must never receive a `.genesis/tmp` dir). It then calls `EvoGit.TaskTmpdir.put_current/1` unconditionally, so every agent of the task — including repo-less/reflect agents — has a per-task dir. `task_id` comes from `meta.task_id` (`%SchedMeta{}` populated at agent registration before `Runner.run`, `agent_scheduler/dispatch.ex:99-108`).
- **Subagent specs inherit it** (`SubagentProcessing.build_subagent_specs/3`): the parent's `EvoGit.TaskTmpdir.current/0` is read once and threaded into each child spec via `AgentSpec.new(..., task_tmpdir: task_tmpdir)` (the same spec-opts plumbing path as `:attachments`/`:custom_agent_id`), so the child Runner re-installs the SAME dir. This matters for `:per_repo` (the dir must stay rooted at the TASK's primary repo, not the child's foreign repo); for `:system`/`:custom` the threaded value is identical at every level. For `:system`/`:custom`, sharing is automatic anyway (the path depends only on `task_id`).
- **Tool tasks re-install it** (`ToolDispatch.batch_execute_tools/4` → `execute_tool_with_timeout/8`): spawned tool tasks do NOT inherit the caller's process dictionary, so `batch_execute_tools/4` reads `EvoGit.TaskTmpdir.current/0` once and threads it into each `Task.async` closure, which unconditionally calls `EvoGit.TaskTmpdir.put_current/1` before `Tools.execute/5`.

Facts relevant to further tmpdir work (detail: `tools/CONTEXT.md` "Per-Tool Path Handling" + `agents/CONTEXT.md` "Temp/Scratch Prompt Guidance" + `sandbox/CONTEXT.md`):

- **Tool path-scope is ASYMMETRIC.** SIX tools call `Shared.validate_file_scope/4`: the four file-CREATING writers (`file_write.ex`, `file_edit.ex`, `file_create.ex`, `make_dir.ex`) and the CONTEXT.md writers (`context.ex` `execute_write/4` / `execute_edit/4`, which scope-check the target DIRECTORY before `mkdir_p`/existence-check/read/replace/commit and pass `Shared.format_context_scope_error/2`); it rejects paths outside `repo_path` (this is what blocks `/tmp`) and outside `node_path`, plus read-only-foreign-repo paths. All READ/exec tools (`read`, `list_dir`, `glob`, `read_context`, `rg`, `search_context`, `bash`) accept arbitrary/absolute paths with NO tmp or root restriction — `EvoGit.Platform.safe_expand/2` returns an absolute input unchanged (`platform.ex:359-373`). Two read tools do NOT follow that pattern: `web_fetch` takes no filesystem path at all (only a URL), and `lsp`'s `path` must resolve INSIDE the agent's repo path (`tools/lsp.ex` validates the resolved target before touching the file), so it is not path-arbitrary.
- **`bash` (internal key `run_bash`/`run_powershell`) runs INSIDE the sandbox** via `EvoGit.Sandbox.run_with_partial/7` (`shell_tool.ex:285-317`), which injects `TMPDIR=<EvoGit.Sandbox.resolve_tmpdir()>` on Linux (`sandbox/linux.ex:196`) and macOS (`sandbox/macos.ex:465`); `resolve_tmpdir/0` (`sandbox.ex:164-169`) PREFERS `EvoGit.TaskTmpdir.current/0` (the managed per-task dir) when the calling process has one installed, and only falls back to the legacy constant (`$TMPDIR`/first tmp path — a host-wide `/tmp`) when no per-task dir is set. Since every agent process (and each spawned tool task) installs the per-task dir, a sandboxed agent sees its task's scratch dir.
- **The only existing LLM-visible tmp instruction** is the ShellTool schema text `shell_tool.ex:144`: "Always use $TMPDIR for temporary files, never /tmp." (POSIX; `$env:TEMP` on Windows, `:41`/`:101-106`). No system prompt, `PromptFragments`, or runtime prompt mentions temp/scratch space or cleanup anywhere (verified negative).
- **Runner finish point = the single teardown seam**: `Runner.run/3` (`runner.ex:41-65`) wraps `do_run/2` in `try/after`; the `after` block calls `EvoGit.AgentScheduler.Dispatch.commit_pending_in_worktree/0` on EVERY exit path (success `{:ok, %Result{}}`, `{:error, :recovery_failed}` grace exhaustion, `{:error, :path_not_exist}`, or a raise). It runs in the agent process, which is also the process WorktreeManager monitors for worktree reclaim. (The per-task tmpdir is CREATED earlier, in `setup_dispatch_context/1`; task-scoped reclaim is `EvoGit.TaskTmpdir.reclaim/2`.)
- **The fallback runs BEFORE the result is handed back, and the result's `commit_sha` is refreshed AFTERWARDS from the worktree HEAD**: `run/3` rebinds the `try/after` value and passes it through `refresh_commit_sha/1` (runner.ex:67-123), so a change that exists only as the auto-commit fallback's commit is reported with the NEW sha instead of the stale pre-fallback one. `merge_and_report/3,4` then sees a sha differing from the live repo HEAD and creates the `genesis/agent_*` branch, keeping the fallback-only change reviewable; a failure to re-read the HEAD (or a repo-less agent) leaves the result completely unchanged.

## Known Issues

- **`CompleteTask`'s metadata git note and archive refs lag the reported `commit_sha` on a fallback-only commit**: `CompleteTask.complete/4` writes its git note and its `refs/genesis/archive/T<task>-A<local>-start/-final` refs at the PRE-fallback sha at complete time, while `Runner.run/3` refreshes `Result.commit_sha` to the POST-fallback worktree HEAD afterwards — when the auto-commit fallback creates the only commit of the run, those refs (and the note) keep pointing at the earlier commit, so neither archive protection nor the note covers the commit the task reports.
- **LLM cost is recomputed by EvoGit itself — ReqLLM's reported cost is NOT trusted; token COUNTS stay accurate and still come from ReqLLM.**
  - `Usage.from_response_usage/1` copies `input_cost`/`output_cost`/`total_cost` verbatim from `ReqLLM.Response.usage/1`.
  - Both cost-producing call sites therefore override them through the ONE shared helper `EvoGit.Agent.Cost.apply_to_usage/3`: `tool_dispatch.ex` `update_turn_usage/2` (`Usage.from_response_usage(usage) |> Cost.apply_to_usage(usage, state.agent_id)`) and `context_compression.ex`'s `{:ok, response}` branch (which reads `ReqLLM.Response.usage(response)` ONCE into a local).
  - `EvoGit.Agent.Cost` recomputes the cost from the raw token counts + the `llm_db` pricing catalog, with an EXPLICIT peak/off_peak period resolved from the model profile's PeakHours config (`EvoGit.PeakHours` via `EvoGit.Agent.Cost.period_for_model_id/1` / `period_for_profile/1`).
  - When the recompute returns `nil` — unresolvable model spec, no applicable component, unexpected error — ReqLLM's reported values are KEPT, so the recompute can never fail a task.
  - Rationale (why ReqLLM's reported figures are not trusted): ReqLLM 1.28 prices a period-gated catalog only from a CALLER-supplied `pricing_context` (`%{pricing_period: "peak" | "off_peak"}`) — `ReqLLM.Billing.calculate/3` selects components through `LLMDB.Pricing.components_for/2`, which honors each component's `applies_when`, and leaves the request UNPRICED when a relevant condition stays unresolved. EvoGit never passes `pricing_context` to ReqLLM; it resolves the period itself from the model profile's PeakHours config and passes `%{pricing_period: period}` to `LLMDB.Pricing.components_for/2`.
  - EvoGit's scope is deliberately narrower than ReqLLM's: only `kind: "token"` components with a positive `rate`/`per` and a recognizable token meter/id are billed, minus the model's `pricing.excluded_cost_components` (deepseek excludes `token.reasoning` — its completion tokens already include reasoning), so `total_cost` is the TOKEN cost (`input_cost + output_cost`).
  - `LLMDB.Pricing.components_for/2` with an explicit `%{pricing_period: period}` context is the correct API (a known non-matching period is `:excluded`, not returned).
  - Module formula/period detail: `./cost.ex` + "Helper Modules" above.
  - Known limitations of the recompute: a pricing product gated behind a NON-time condition (e.g. a GLM coding-plan credit tariff) yields no applicable component, so those profiles keep the reported cost; tool/image/storage priced components are not billed, so `total_cost` is the TOKEN cost; and a `{provider, model}` TUPLE model spec makes `ReqLLM.model/1` raise inside its own validation-error builder, which `Cost`'s `safe/3` boundary catches → reported cost kept (a malformed spec is not a shape `EvoGit.Config` produces — it emits strings or maps).
- **Thinking/reasoning text lives in TWO places in a stored assistant message** — the core keeps thinking and response SEPARATE, but a naive consumer will see duplicates. Reasoning (thinking) models (e.g. `deepseek-v4-*`) stream `delta.reasoning_content` separately from `delta.content`; ReqLLM's default builder materializes the SAME thinking text BOTH as a `%ReqLLM.Message.ContentPart{type: :thinking, text: …}` inside `message.content` (after the `:text` part; `ReqLLM.Provider.Defaults.ResponseBuilder.build_standard_content_parts/2`) AND as the separate `message.reasoning_details` list. `ReqLLM.Response.text/1` filters to `type == :text`, so the response text is clean, but `message.content` still carries the `:thinking` part. The core stores the whole `%ReqLLM.Message{}` verbatim in `AgentState.context` and only compacts `reasoning_details` fragments (`compact_reasoning_details/1`, tool_dispatch.ex:859-899 — merges the `& &1.text` of a multi-fragment `reasoning_details` into ONE entry; it never touches `content`). `RemoteAPI.get_agent_history/1` therefore returns both. **Any consumer that joins `message.content` parts without a `type == :text` filter renders the thinking text as the response too** — on an agentic turn where a reasoning model emits no visible `:text` (only reasoning + tool calls) the join equals the thinking text EXACTLY. Detail + the offending display site: `apps/evo_dash` (`AgentsLive.message_to_history_entry/1`, `HomeLive.Messages.message_text/1`).
- **`reasoning_tokens` is not a `%Usage{}` field.** `EvoGit.Agent.Usage` (8 fields) has no reasoning bucket; `update_turn_usage/2` adds `Map.get(usage, :reasoning_tokens, 0)` into `state.total_tokens` (the compression trigger, tool_dispatch.ex:712), and `EvoGit.Agent.Cost` maps the `"reasoning_tokens"` meter / `token.reasoning*` id prefix to its `:reasoning` group billed into `output_cost` (cost.ex:100, 110, 476) — though DeepSeek's catalog `pricing.excluded_cost_components` excludes `token.reasoning` because its completion tokens already include reasoning.
