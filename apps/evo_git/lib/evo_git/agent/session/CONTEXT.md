# EvoGit Agent Session — `agent/session/`

## Intent

Holds the per-agent session process that owns `%EvoGit.Agent.State{}` for its whole life, plus the durable/per-process setup (worktree binding, process context, initial state).
The `:starting` phase runs the durable setup in ONE monitored task (the session pid stays the worktree owner), so a slow, queued or hung worktree create can never silence the session process itself.
`%EvoGit.Agent.State{}` is the ONE authoritative agent state; the process dictionary installed here is a DERIVED projection of it, never authoritative.
The exchange engine (`EvoGit.Agent.Exchange`) stays a pure function over the struct: the session spawns a short-lived WORKER task per exchange and never runs the turn loop inside its own process, so inspection/cancel/input stay answerable mid-run.
The session IS the one lifecycle for every agent: `EvoGit.AgentScheduler.Dispatch.do_try_dispatch/4` starts it under `EvoGit.Agent.Session.Supervisor` and `EvoGit.AgentScheduler` admits its ONE terminal `{:agent_session_result, …}`.
The session serves BOTH drivers: a `:oneshot` role ends at its first text reply, while an `:interactive` role YIELDS a text reply and parks in `:awaiting_input` until `start_input/3` resumes it on the SAME pid/worktree/context or `close/2` finalizes it; there is NO idle TTL.
The session also OWNS the push-only streaming contract — the watcher set, the monotonic `event_seq` and the coalescing batcher — so a live consumer is PUSHED deltas and never polls.
`../session.ex` is intentionally long and cohesive: the `gen_statem` lifecycle, authoritative state and stream sequence, and terminal ordering must remain together; `TerminalHandoff` extracts only direct fan-out, never lifecycle ownership.

## Assistant turn stop and project metadata

`Session.stop_current_turn/1` is non-terminal for interactive sessions: it retires only the exchange worker (a running tool batch first settles and checkpoints its complete results), keeps the session in `:awaiting_input`, emits the normal scheduler yield event and leaves the conversation resumable; nothing committed is rolled back, repeated stop while idle is harmless, and one-shot sessions refuse it.
`Session.Worker.boundary/2` serializes the `:llm`, `:tools` and `:checkpoint` gates through the session (drained input is retained before generation, the pre-tool gate never adopts unmatched tool calls, a checkpoint retains settled results before honouring a pending stop); outside session workers they are inert, and a retired worker's stale messages cannot terminate the parked session.
`Session.send_message_with_workspace/4` atomically updates project metadata and resumes an idle assistant in one serialized event; during a running exchange it accepts input only for the current normalized path/node, otherwise `{:error, :workspace_changed}` with the message never queued. `Session.update_assistant_workspace/2` accepts a normalized existing absolute directory or `nil` only while awaiting input, updating `spec.opts[:assistant_workspace]`, the dispatch spec and a small project-selection message; identity stays fixed, and SelfReflective context never loads project or launch-directory CONTEXT/skills.

**Seeded message order is exactly `[system, user]`, and this list IS what `history/2` returns**: message #1 is a `:system` message carrying `agent_module.system_prompt()` alone; message #2 is a `:user` message whose text is the `<context>` block joined to the `<objective>` block by `"\n\n---\n\n"` (blank sections dropped), so a plain-string objective becomes exactly `<objective>\n<objective>\n</objective>` (`ContextBuilder.build_initial_messages/4`). The system prompt is never prepended to or repeated inside the user message.
Message #2 is the session's ONE user-authored turn at start: `build_initial_state/3` calls `EvoGit.Agent.MessageMarker.mark_first_user_authored/1` AFTER turn-0 tagging, so it carries `metadata[:user_authored] => true` beside `:turn` + `:timestamp`; the `:system` message never carries it (`../CONTEXT.md` § User-Authored Message Marker).
The `<context>` block wraps `ContextNode.build_context(node_path, repo_path)` (the `# Context Tree` stages plus the location block) and a LAST `Current local time: <date> <HH:MM>[ (<IANA zone>)]` line. For a REPO-LESS session (`node_path: "./"`, `state.repo_path` = the resolved source root) message #2 embeds the SOURCE ROOT's `./CONTEXT.md` verbatim — truncated at `[:truncation, :context_max_bytes]` (64 KB) with a `... [Content Truncated] ...` marker — and the authority, foreign-repos, repo-notes, quality-guidance and background-jobs sections are all `""`.
The start path composes all of it INSIDE the ONE start task: `bind_worktree/2` (owner = the SESSION pid) → `ensure_tmpdir/1`; when that task replies the session reads the scheduler row, calls `build_initial_state/3` (whose worker later installs the process context) and publishes `status: :running`.
The only per-turn publication is the `:checkpoint` event → `Summary.publish/3` (summary fields only, never `context`); there is no per-turn ETS write-through, and live deltas travel on the separate push contract.

## Phases, Events and Commands (yield/finish split)

The `:gen_statem` uses `callback_mode: :handle_event_function` and its state name IS the phase: `:starting | :running | :awaiting_input | :cancelling | :finalizing | :done` (`data.phase` mirrors it for `inspect/2`).
Internal data is a plain map `%{state:, worker:, finalizer:, start_task:, start_timers:, last_yield_text:, notify_pid:, dispatch_ctx:, tmpdir:, result:, phase:, last_published_turn:, watchers:, event_seq:, batcher:, activity:}`: `notify_pid` is the normalized `{pid, tag} | nil` close sink; `start_task`/`start_timers` are cleared as soon as they reply, so a later `:DOWN`/timer is stale by construction; `watchers`, `event_seq`, `batcher` and `activity` are SESSION-authoritative and no worker copy may override them. Identity guards are the ONLY route to a transition: the worker ref delivers an outcome (`current_worker?/2`), the start ref finishes `:starting` (`current_start_ref?/2`), the finalizer handle delivers a finalization.

Transition table (as implemented):

| From | Event | To |
|---|---|---|
| `:starting` | internal `:start` | `:starting` (ONE monitored start task + two timers; the handler never blocks) |
| `:starting` | start task replies `{:ok, tmpdir}` and the state builds | `:running` (first worker started) |
| `:starting` | start failed (`:not_registered`, `:path_not_exist`, …) | `:finalizing` |
| `:starting` | create exceeded `:worktree_create_stall_timeout_ms` | `:finalizing` → `:done` with `{:error, {:worktree_create_stalled, ms}}` |
| `:starting` | start task `:DOWN`, `:normal`/`:shutdown` without a reply | `:finalizing` with `{:error, {:worktree_create_failed, {:down, reason}}}` |
| `:starting` | start task `:DOWN`, any other reason | stopped with that reason (scheduler crash/retry, unchanged) |
| `:running` | `{:exchange_finished, _worker, {:yield, state, text}}` (`mode == :interactive`) | `:awaiting_input` (no worker, idle TTL, poll or slot; a pending batch flush timer may briefly remain) |
| `:running` | `{:finish, …}` / `{:error, _}` / an unexpected outcome | `:finalizing` |
| `:running` | `{:cancel, :graceful}` | `:cancelling` (worker kept alive) |
| `:running` | `{:cancel, :force}` | stopped `:shutdown` (no result) |
| `:cancelling` | `{:yield, state, text}` (interactive cancel-grace) | `:finalizing` (finalizer, last yielded text) |
| `:cancelling` | `{:finish, …}` / `{:error, _}` | `:finalizing` |
| `:cancelling` | `{:cancel, :force}` | stopped `:shutdown` (no result) |
| `:awaiting_input` | `start_input/3` / `input/2` append ok | `:running` (NEW worker, same pid/context/worktree) |
| `:awaiting_input` | `close/2` or `{:cancel, :graceful}` | `:finalizing` (finalizer, `last_yield_text \|\| ""`), reply `:ok` immediately |
| `:awaiting_input` | `{:cancel, :force}` | stopped `:shutdown` (no result) |
| `:finalizing` | `{:session_finalized, pid, result}` (current finalizer) | `:done`, then `{:stop, :normal, …}` |
| `:finalizing` / `:done` | any command | `{:error, :finished}` |
| any of `:starting`/`:running`/`:cancelling`/`:awaiting_input` | `{:cancel, :force}` | stopped `:shutdown` |

Every read/streaming command (`:inspect`, `:history`, `:identity`, `:watching?`, `{:snapshot}`, `{:watch, _}`, `{:unwatch, _}`) replies WITHOUT changing the phase, so a watch can never perturb a run.

`init/1` returns `[{:next_event, :internal, :start}]`; that event starts ONE monitored `EvoGit.TaskSupervisor` task running `Setup.bind_worktree(ctx, session_pid)` + `Setup.ensure_tmpdir(ctx)` — the session pid is the create owner (reclamation is driven by the SESSION's `:DOWN`) and nothing in the task is rescued — plus two call-time timers from `:worktree_create_slow_warn_ms` (default 120_000, ONE warning) and `:worktree_create_stall_timeout_ms` (default 1_800_000, the terminal `{:error, {:worktree_create_stalled, ms}}`).
`:starting` is RESPONSIVE: every read answers (no state yet → `:error`/`[]`), `close/2` and a graceful cancel answer `{:error, {:bad_state, :starting}}`, `{:cancel, :force}` stops at once, and `{:watch, _}`/`{:snapshot}` serve `Stream.Snapshot.starting/2` (`phase: :starting`, `messages: []`, `turn: 0`, `status: nil`, live `activity`, the `event_seq` cut), which makes the start task's `:retry_wait` publishable. A missing scheduler row (`Store.get_agent_state/1` → `:error`) finalizes `{:error, :not_registered}`; `{:error, :path_not_exist}` goes straight to finalizing.
`:running`/`:cancelling` admit the SYNCHRONOUS `:gen_statem.call(…, :infinity)` gate `{:worker_boundary, worker_pid, phase, %State{}}` (`:llm | :tools | :checkpoint`) and `{:activity, worker_pid, event}` only from the current worker: `:tools` only records the boundary, `:llm` adopts the state and checkpoints durably ONLY when the conversation differs, and `:checkpoint` goes through `Session.adoptable?/2` (an advancing turn wins, an equal turn is a duplicate EXCEPT the ONE batch-completion checkpoint, stale ones do nothing) then publishes a COALESCED summary.
`:DOWN` arms, checked in this order: a dead WATCHER (`Watchers.watcher_ref?/3` for the ref that actually went down) removes only that watcher and stays in phase, so a consumer exit is never mistaken for a dead worker, start task or finalizer; a current FINALIZER down is logged and converted into `{:error, {:finalize_crashed, {:down, reason}}}` (never a crash); a current START task down with `:normal`/`:shutdown` (it died without a reply) finalizes `{:error, {:worktree_create_failed, {:down, reason}}}`, while any other start reason stops the session with it (an exception there is NEVER rescued, so scheduler crash/retry runs unchanged); once finalizing, a `:DOWN` is ignored; a non-`:normal`/`:shutdown` reason from the current worker is re-raised as `{:stop, reason, data}` (scheduler crash/retry); a `:normal`/`:shutdown` DOWN without a prior `{:exchange_finished, …}` stops `:normal`; anything from a stale worker/start task/finalizer is logged at `:debug` and ignored, as is the `async_nolink` `{ref, result}` reply.
`:cancelling` stays idempotent for `{:cancel, :graceful}`, and a late `{:start_input, …}` is rejected with `{:error, :finished}` because a cancelling run accepts only the engine's own grace turns.
`:finalizing` is terminal-only with a FIXED order: activity reset + delta flush, terminal watcher handoff, final summary, the result message ONCE, the durable completion marking (a cast), the `:notify` pid LAST, `:done`, then stop `:normal`.

## Interactive Idle Contract (`:awaiting_input`)

A yield is NOT a completion: `ToolDispatch.process_llm_response/7` commits pending worktree work and returns `{:yield, record_current_commit(state), text}` for `mode: :interactive`, so the engine hands back the conversation instead of finalizing it.
On that yield the session stores the yielded state with `phase: :awaiting_input`, records `last_yield_text`, clears the worker, calls `Store.clear_cancel_requested/1`, publishes summary `status: :awaiting_input`, sends `{:agent_session_yield, agent_id, self(), text}` to the scheduler, and calls the role callback `state.agent_module.on_yield(state)` as a PLAIN call (it must be cheap and side-effect-light; a raising callback is a role bug, deliberately not rescued).
The idle session has no worker process, idle TTL, poll or LLM/tool slot — slots are acquired and released INSIDE the worker, so an idle session cannot hold one. A pending yield/reset batch may briefly retain the single flush timer; that is delivery cleanup, not an idle timeout.
It keeps the transcript and the worktree: `history/2` still returns the full conversation, and the worktree is reclaimed exactly ONCE by the `WorktreeManager` monitor on the SESSION pid, only when the session stops (never at a yield; no explicit release call exists).
Resume is APPEND-ONLY: `start_input/3` applies `Input.resume_state/1` (rebase `exchange_turn_base` to the current turn, `phase: :running`, clear `cancel`/grace fields), appends through `Store.append_pending_user_message/2` (the next turn drains it into a user message), publishes `status: :running`, sends `{:agent_session_resumed, agent_id, self()}` and starts a NEW worker on the SAME session pid. The context tree is never rebuilt and `prompt_cache_key` is never reset, so the provider prefix cache survives. A failed append (`{:error, :not_found}`) answers `{:error, :finished}` and starts no worker. `:interrupt` in `:awaiting_input` is not a pre-emption — it RESUMES exactly like `:queue`.

## Durable State (per-agent persistence)
`EvoGit.Agent.Session.Persistence` is the ONE module knowing both `%EvoGit.Agent.State{}` and `EvoGit.AgentState`, and every function is total: a durable-state fault never crashes an agent run.
The hook is `publish_checkpoint/2`: inside its adoption branch it captures the PREVIOUSLY adopted state, adopts the worker's copy, then calls `Persistence.checkpoint(old_state, state)` — a list comparison plus ONE `EvoGit.AgentState.checkpoint/4` cast, with NO serialization in the session process (the baseline lives in its process dictionary).
The durable write shape is TWO tiers: `Persistence.initial_snapshot/1` is the run's ONE full-field row write (whole transcript plus every identity/run fact and `anchor_ref`) at session start, fresh and restored alike; every per-turn boundary writes ONLY the volatile projection (`EvoGit.AgentState.Record.volatile_field_specs/0`) plus the transcript.
A boundary that changed the message list issues ONE `checkpoint/4` (`:append` of the new tail when the previously adopted list is a prefix and `compression_count` did not move, else a `:rewrite`); one that moved only scalars issues `update_volatile/4` with the FULL volatile map (no chunk row, so `chunk_count` does not grow while `turn`/`usage`/`total_tokens`/`current_commit` advance); one that also established a new `anchor_ref` issues `checkpoint/4` with an EMPTY tail; one that changed NOTHING (the `unchanged?/6` fast path) writes nothing and runs no anchor task.
`pause_commit` and `result` stay outside BOTH paths — their writers are `EvoGit.AgentState.put_pause_commit/4` and `mark_done/5`, and the per-turn projections omit them. `persistent_state: false` is fully inert (no cast, encoding, database touch or pd write).
`initial_snapshot/1` is the run's FIRST durable write and happens at START, not at the first boundary: `finish_start/2` calls it ONCE after `Setup.build_initial_state/3` succeeded, so one row per RUNNING agent exists before the first exchange. It carries `status: "running"` (a resumed run RE-OPENS the `done` row it continues) and sets the append baseline to the full message count.
`%EvoGit.Agent.State{}` carries the DURABLE RUN FACTS beside the conversation: `branch`, `base_commit`, `spawn_turn`/`spawn_index` (`nil` for a ROOT), `redispatch` (the `EvoGit.AgentState.Redispatch` blob that rebuilds its `%EvoGit.AgentSpec{}`) and `anchor_ref`; they are persisted with every checkpoint and are what a resume cannot re-derive.
`EvoGit.Agent.Session.Durable` owns the tolerant transcript projection `messages/1` (a plain-map context and a `%ReqLLM.Context{}` alike) and the `valid_identity?/1,2` predicates shared by `persistence.ex` and `pause.ex`.
`EvoGit.Agent.Resume.restored_run?/1` is the durable-restore predicate — true for BOTH a crash retry and a pause resume — and `EvoGit.Agent.Resume.resume_kind/1` tells them apart. `resume_info` is the opposite: TRANSIENT bookkeeping of ONE dispatch (`restore_agent_state`, `restored`, `resume_kind`, `retries`, `retry_reason`, `worktree_resume_from`), built by `build_initial_state/3`, never persisted, consumed only by `EvoGit.Agent.Resume`.
The entry carries `owner: self()` (the session pid) and a small fixed fields map, so a store-reported continuity gap arrives as `{:agent_state_resync, task_id, agent_id}` in ANY phase and is answered with ONE full `:rewrite` (`Persistence.resync/1`) — never an append; a message for another/unset identity is logged and ignored.
`build_initial_state/3` restores a crashed run's conversation only when the dispatch ctx carries `restore_agent_state: true` (a CRASH RETRY or a pause resume of the SAME agent_id) AND `state.persistent_state` is on: the restored transcript is authoritative (it REPLACES the freshly rebuilt `[system, user]` pair) while identity/worktree/paths/model selection/phase stay fresh. A missing/corrupt/unavailable/`empty_state`/`identity_mismatch`/`no_identity` row logs ONE `:warning` naming the agent id and reason and keeps the fresh state (`restored: false` makes the resume notice say earlier turns are missing).
`Persistence.restore/3` OVERWRITES the conversation fields (`turn`, `usage`, `total_tokens`, `compression_count`, `prompt_cache_key`, `objective`, `pending_inputs`, `current_commit`, `pending_tool_batch`) because they are the stored run's progress; `current_commit` has no fresh counterpart (the worktree base travels as `worktree_resume_from`/`base_commit`). It also VERIFIES the row's `parent_id`/`depth` against the state it merges into and answers `{:error, :identity_mismatch}` on disagreement — an `agent_id` is unique only because the scheduler seeds its counter from the store, so this check stops an id collision from splicing one agent's transcript into another run. A restored `spawn_turn`, `spawn_index`, `branch`, `base_commit` or `redispatch` is recovered only where the fresh value is `nil`.
`Persistence.complete/1,2` runs from `finalize/1` ONLY and only AFTER the terminal result was delivered — never from `to_awaiting_input/3` (a parked interactive session is still resumable) and never on the force-cancel path; it is ONE cast to `EvoGit.AgentState.mark_done/5` (the finished run's JSON result plus `current_commit`), so the store can never delay, block or fail the terminal path. Then the row's fate is by ROLE: a ROOT's row is DELETED, a CHILD keeps its `done` row, which the parent's batch-clearing checkpoint deletes.
Checkpointing reaps those rows too: the checkpoint whose `pending_tool_batch` transitions to `nil` IS the batch boundary, and it calls `EvoGit.AgentState.delete_done_children/4` for the turn taken from `EvoGit.Agent.ToolBatch.normalize/1` on the OLD marker (a marker without an integer turn deletes nothing).
Git anchoring rides the same checkpoint: when the boundary ADVANCED `current_commit`, the session anchors that sha at `EvoGit.AgentState.Anchor.ref(task_id, agent_id)` (`refs/genesis/agent-state/…`, fire-and-forget unlinked task) and records `state.anchor_ref`, so commits survive worktree reclamation and branch cleanup; a repo-less run and a `persistent_state: false` task never anchor.
Checkpointing covers an in-flight tool batch at BOTH ends: `ToolDispatch.begin_tool_batch/4` fires the SAME `:checkpoint` seam immediately BEFORE the tools run (marker on `state.pending_tool_batch`, assistant `tool_calls` message tagged with the already-incremented turn) and `continue_after_tools/7` fires it again once every result is appended, at that SAME turn.
`Session.adoptable?/2` is the ONE adoption rule: a greater `turn` always wins, a lesser one never does, and at an EQUAL turn the batch-completion arm is the sole exception — the adopted state CARRIES the marker, the incoming one CLEARED it, and the transcript GREW. Tool RESULTS therefore stay turn-boundary granular while the MARKER is durable across the batch: a crash mid-batch resumes with the assistant message plus the marker, repaired after the retry in `EvoGit.Agent.Resume` — `../resume/CONTEXT.md`.
Checkpoints and the completion marking are CASTS; the ONE synchronous durable call in this node is `Pause`'s `EvoGit.AgentState.flush/1` barrier, whose `:ok | {:error, :timeout}` verdict alone decides whether a paused outcome may claim `durable: true`. `Persistence.restore/3` runs inside `finish_start/2` in the SESSION process, so its `AgentState.load/3` is a synchronous read there.

## Terminal Delivery Contract

`finalize/1` sends exactly ONE `{:agent_session_result, agent_id, self(), result}` to the dispatch context's `:scheduler` pid (`Dispatch.do_try_dispatch/4` sets it), falling back to `Process.whereis(EvoGit.AgentScheduler)` and skipped silently when neither exists, THEN hands the durable completion marking to `Persistence.complete/1` (one `mark_done/5` cast plus the root-row delete), then notifies the normalized `:notify` `{pid, tag}` sink (when present and alive) with `{:agent_session_closed, tag || agent_id, result}` — a bare notify pid normalizes to `{pid, nil}` — and THEN returns `{:stop, :normal, data}`.
The order is the contract: session-local work (activity reset, delta flush, terminal watcher handoff, final summary) and the terminal RESULT precede any durable bookkeeping, and the close notification comes LAST, so a slow, locked or dead agent-state store cannot delay the outcome. Sending BEFORE stopping exploits Erlang signal ordering: the result and `{:agent_session_closed, …}` (the caller-facing completion signal) always arrive before the monitor `:DOWN`, so no consumer observes a death without an outcome.
The session NEVER calls `GenServer.reply` on the dispatch-caller's `from` — the scheduler owns that reply (it injects `agent_count`/`foreign_repo_commits` and routes subagent results).
The completion side effects (`Completion.complete/4`: git note, archive refs, the streaming `task_agent_archives` row, `%Result{}`) run EXACTLY ONCE, inside whichever finalizer the FIRST terminal path started — a `:oneshot` finish inside the worker (`Completion.Builder.finalize/2`), an interactive session in `Finalize.start/4` from `close/2`, an idle `:graceful` cancel or a cancel-grace yield. `Completion.Builder.finalize/2` REQUIRES the installed process context and RAISES on a vanished worktree; the finalizer's `try/rescue/catch` converts any raise/exit into `{:error, {:finalize_crashed, reason}}`, so a finalization failure is a delivered error result, never a session crash.
A second `close/2` (or one on a still-finalizing session) answers `{:error, :finished}` (`{:error, :not_found}` once the pid is gone), and a graceful cancel while idle is IMMEDIATE: only the transcript needs saving (it is KEPT), so the finalizer runs with the last yielded text and the task registry maps that to `:cancelled` with the result preserved.
Outcome mapping is `Session.Outcome.classify/3`: `{:finish, state, result}` → terminal `{:ok, result}` (the worker already refreshed the sha), `{:error, reason}` → terminal `{:error, reason}` (delivered verbatim, never converted into a raise or success), an interactive yield → `:awaiting_input`, any unexpected shape → `{:error, {:unexpected_exchange_outcome, other}}` delivered LOUDLY (a one-shot yield, or a `{:finish, …}` while idle, is a contract violation, never silently dropped).
The final summary publishes `status: :done` for `{:ok, result}`, `:failed` for `{:error, _}`, plus `current_commit` from the built result when it carries one.
`EvoGit.AgentScheduler.handle_info({:agent_session_result, agent_id, session_pid, result}, state)` admits it only for an existing `SchedMeta` whose `session_pid` is `nil` (already recycled) or the sending pid, and delegates to `EvoGit.AgentScheduler.Lifecycle.handle_session_result/3`; a stale-session or missing-agent message is logged at `:debug` and ignored. `{:agent_session_yield, agent_id, session_pid, text}` and `{:agent_session_resumed, agent_id, session_pid}` are EMITTED here, consumed by the scheduler, and must never be treated as terminal.

## Terminal Watched-Inspector Handoff

`finalize/1` delivers exactly one direct handoff to each registered watcher pid after final state adoption, activity reset and delta flush, BEFORE final summary publication, scheduler result delivery and removal; there is none on an interactive yield, `terminate/3`, force cancellation or an abnormal worker-down path.
Only a nonempty watcher map and an owned `%State{}` allocate ONE shared `%EvoGit.Agent.Stream.Snapshot{}` (unwatched and state-less sessions allocate none): `phase: :done`, `status: :done | :failed` from the same decision as the final summary, retired activity, and `seq` = the post-flush `data.event_seq` without incrementing it. Success uses the final adopted state; `{:error, reason}` preserves the last accepted checkpoint transcript and never synthesizes assistant text from the error or partial activity.
`EvoGit.Agent.Session.TerminalHandoff.deliver/2` accepts the session-owned `%{watcher_pid => monitor_ref}` map and that snapshot, sends each pid `{:agent_stream_closed, agent_id, snapshot, snapshot.seq}` directly with `send/2` and returns `:ok`; remote pids need no local liveness probe and dead watchers need no retry. The snapshot never travels through PubSub (no persistence, retention, replay, acknowledgement or polling), and sending before other terminal notifications is session-side ordering only.

## Live Streaming (watchers, `event_seq`, coalesced deltas)

The session OWNS the push-only delta contract: the watcher set (`%{consumer_pid => monitor_ref}`), the monotonic `event_seq` and the coalescing `EvoGit.Agent.Stream.Batcher`.
`{:watch, consumer_pid}` REGISTERS the consumer with `Process.monitor/1` (works for a local or remote pid), flushes pending deltas AFTER registration and BEFORE taking the snapshot, and answers `{:ok, %EvoGit.Agent.Stream.Snapshot{}, seq}`, so a consumer starts coherent and is then PUSHED `{:agent_delta, agent_id, seq, events}` — it never polls.
`{:snapshot}` also flushes FIRST and is the ONLY resync: a bounded one-shot read, with deltas whose `seq` is `<=` the snapshot's dropped (`EvoGit.Agent.Stream.stale?/2`); there is no replay ring buffer and no cursor. Both replies carry the live session-owned activity, post-flush `seq` and LIVE gen_statem `phase`, never the state's boundary copies.
`Stream.Sink.emit/1` sends `{:delta, events}` from the exchange worker; the session buffers them for `Stream.Batcher.flush_interval_ms/0` (75 ms), and `Stream.Watchers.flush/4` is the ONE broadcast site — exactly ONE `{:agent_delta, agent_id, seq, events}` on the `"agent:<agent_id>"` `EvoGit.PubSub` topic per flush, with `event_seq` incremented by exactly one. A broadcast can never take the session down: an unavailable PubSub degrades to a dropped batch that a fresh snapshot repairs.
`event_seq` and `watchers` live in the session's data and stay authoritative: `publish_checkpoint/2` RE-STAMPS them onto every adopted worker state copy (`adopt_state/2`), so a checkpoint can never roll streaming state back.
Activity retirement and flushing are distinct: every handled exchange outcome resets activity before classification, while a successful resume, yield or finalizer startup may leave its public reset events pending for the batch timer; terminal delivery, current-worker down, force-cancel and best-effort `terminate/3` reset activity and flush, watch/snapshot flush pending deltas too, but a running graceful cancel preserves activity and the pending batch un-flushed.
At most ONE flush timer exists (`schedule_flush/1` schedules none for an empty buffer), a pending reset batch may keep it alive while idle or finalizing, and `:flush_deltas` is handled in EVERY phase.
ZERO WATCHERS gates only public delivery: `{:delta, …}` is dropped on arrival and activity's public events are not buffered (no batch, buffer, timer, `seq` consumption or broadcast), while live activity capture and chunk-level interrupts stay active.
`Sink.stream_opts/0` installs `ReqLLM.StreamResponse.process_stream/2` callbacks whenever a sink exists, independent of watcher count, and returns `[]` when none is installed; the delta vocabulary and `Stream.watch/1`/`register_watcher/2`/`snapshot/1`/`stale?/2`/`Sink` are specified in `../stream/CONTEXT.md`.

## `:interrupt` — a real chunk-level halt

`start_input(target, message, :interrupt)` on a `:running` session APPENDS the message through the settled transport (`EvoGit.AgentScheduler.Store.append_pending_user_message/2`) FIRST and THEN sends the current exchange worker `{:evogit_interrupt, ref}`, replying `:ok` — append-first is load-bearing, because the halt can end the turn before the caller gets the reply.
The worker's per-chunk `Sink` callback consumes that message exactly once (`Sink.interrupt_requested?/0`) and raises `%EvoGit.Agent.Stream.Interrupted{}`, which `ReqLLM.StreamResponse.process_stream/2` converts into `{:error, %Interrupted{}}` and `EvoGit.Agent.LLMPrompting.run_llm_attempt/4` turns into `{:interrupted, reason}` — never a failure warning, pool bump or retry. `EvoGit.Agent.ToolDispatch.do_turn/6` maps it to an EARLY turn end: no assistant message, no protocol violation and NO grace turn consumed; the loop re-enters at its top and drains the already-appended message for the next turn.
Chunk-level halt does not depend on watchers (`Worker.run/3` installs the sink), and the pending-message transport still delivers the message exactly once if the interrupt lands after the last chunk, so it is neither lost nor duplicated. A `{:evogit_interrupt, _ref}` arriving after the last chunk stays unread in that SHORT-LIVED worker's mailbox and dies with the process; the next exchange runs in a NEW worker (`Sink.install/2` sweeps the mailbox anyway), so one request can never abort two turns.

## Execution-Activity Projection Boundaries

`../session.ex` admits `{:worker_boundary, worker_pid, phase, %State{}}` and `{:activity, worker_pid, event}` only from the current worker in `:running` or `:cancelling`; a stale worker's boundary or activity never adopts state or publishes a summary.
An adopted checkpoint resets activity unless `activity.current_call.turn >= state.turn`, preserving a call already at or ahead of that boundary; a checkpoint still CARRYING the in-flight batch marker is the batch START and always preserves the tracked call. The installed streaming sink is removed before fallback commit or foreign-worktree sync, so neither checkpoint state nor activity/deltas describe that cleanup work.
The pre-LLM window is NAMED rather than idle: `ContextCompression.compress_if_needed/2` publishes `:compressing` once the threshold gate opens (spanning stage-1 pruning, the whole stage-2 summarising call and its slot wait/retries), `Exchange.continue_loop/3` publishes `:preparing` before the pending-input drain, the job notices and the prompt assembly, and `ToolDispatch.do_turn/6` orders the `start_turn` reset → `:preparing` → the synchronous `Worker.boundary(state, :llm)` call, so the boundary reset itself is the only `:idle` point of that stretch.
A crash retry waits `Application.get_env(:evo_git, :agent_retry_backoff_ms, 30_000) * retries` in the session's start task (`setup.ex`, repo-backed and repo-less alike) AFTER the worktree exists (30/60/90 s by default), and the wait is REPORTED as `{:phase, :retry_wait}` before it sleeps; `:starting` activity is accepted ONLY from the CURRENT start task (`current_start?/2`), so an attached consumer sees the real phase instead of a stale `:idle`.
The checkpoint gate is ON the turn path: the worker blocks on the synchronous call while the session classifies and casts (a NON-ALLOCATING `prefix?/2` walk) and anchors an advanced commit (`EvoGit.AgentState.Anchor.anchor/4`, one unlinked task); a boundary that learned NOTHING returns with no anchor and no cast.
Activity is a SESSION-DATA projection, separate from the worker-held `%State{}` and the checkpointed conversation; `history/2` stays the last checkpointed conversation, not the response in flight, and it is not a summary-table field (`Summary.publish/3` derives only its explicit fields).
The integration API is `Stream.Activity.new/0`, `Stream.Activity.apply/2` → `{activity, public_events}`, `Stream.Snapshot.from(state, activity: activity, ...)` and sink messages `{:activity, worker_pid, event}`; the value is exactly `%{phase: :idle | :llm_waiting | :llm | :llm_complete | :retry_wait | :tools | :compressing | :preparing, current_call: nil | %{id, turn, attempt, text, thinking}}`, with internal `start_call`, `call_phase`, `phase`, `chunk` and `reset` events interpreted by `Stream.Activity`. The session initializes `data.activity` via `Activity.new/0`, validates each message's current-worker identity, adopts `Activity.apply/2` and routes only its PUBLIC events through the watcher-gated batcher; reduction runs even with ZERO watchers, so a later watch/snapshot sees the live phase and accumulated text/thinking, and watch/snapshot replies pass `activity: data.activity` to `Snapshot.from/2`.

## Seams

`dispatch_ctx[:exchange_opts]` is a documented, DEFAULT-INERT seam: its keyword list is forwarded to every exchange worker (`[tmpdir: tmpdir] ++ exchange_opts`) so tests inject engine seams; production passes none and `:exchange_opts` never appears in a shipped configuration.
The `checkpoint:` opt handed to `Exchange.run/2` is LIVE: the engine calls it once per turn after the state advances, and the worker forwards each call SYNCHRONOUSLY through `Worker.boundary(state, :checkpoint)` → `:gen_statem.call(session, {:worker_boundary, self(), :checkpoint, state}, :infinity)`. Per-turn boundaries are SYNCHRONOUS `{:worker_boundary, worker_pid, :checkpoint | :llm | :tools, %State{}}` calls, and the ONE terminal message is `{:exchange_finished, self(), outcome}` beside the `{:delta, events}` stream. The `{:checkpoint, pid, state}` `:info` handler in `../session.ex` is a TEST-ONLY simulation seam, never a production message.
`EvoGit.Agent.Stream.Sink` is installed by the WORKER (two `Process.put/2` keys, uninstalled in the `after` block before the outcome is sent); `stream_opts/0` installs callbacks whenever the sink exists, independent of watcher count.
`dispatch_ctx[:scheduler]` and `dispatch_ctx[:notify]` are the two delivery addresses (see Terminal Delivery Contract); `dispatch_ctx[:session_mode]` is forwarded by `build_state/2` and consumed once by `Setup.build_initial_state/3` — the REAL context always carries the registration-resolved mode (`Dispatch.do_try_dispatch/4` puts `meta.mode` there, `:interactive` for `start_session/1`), the scheduler row's mirrored `mode` is only a fallback for a hand-built context and only when `:interactive` (`%AgentState{}` defaults it to `:oneshot`, which must never outrank a role `session_mode/0` callback), and an absent/`nil` value leaves the role callback in charge.

## Constraints

- Setup modules must not call `AgentScheduler` state/log APIs except the durable ones the dispatch path already used (`WorktreeManager`, `TaskTmpdir`); `build_initial_state/3` never reads the scheduler row or the process dictionary, and writes no ETS or pd.
- The installed process context must stay behaviour-identical: same keys, values, logs, retry wait (`:agent_retry_backoff_ms`, linear in the attempt) and the same repo-less cardinal rule (git is never touched, no worktree, no `.genesis/tmp` in the source root).
- Per-process keys are a projection only — never a source of truth for the exchange engine, which reads the struct.
- Every public read is TOTAL and non-polling: `inspect/2`/`history/2` are one-shot (`:gen_statem.call/3,4` wrapped in `try/catch :exit` for `:timeout`/`:noproc`/`:normal`, `Registry.lookup/2` guarded by `Process.whereis(EvoGit.Agent.Session.Registry)`), and following a live run is push-only (`{:agent_delta, agent_id, seq, events}`, with `{:watch, …}`/`{:snapshot}` for resync).
- `Summary.publish/3` never raises, never treats a missing row as an error (it no-ops), never builds a fresh `%AgentState{}` and never writes `context`; it guards `:ets.whereis(:evogit_agent_summary)`, skips a write when nothing but `last_activity_at` would change, and delegates persistence/broadcast to `EvoGit.AgentScheduler.Store.put_agent_state/2`. `Summary.select_all/0` uses `:ets.select/2` (never `:tab2list`), returning `[]` when the table is absent.
- `:awaiting_input` is a live agent status this module WRITES but does not own: `store/operations/lightweight.ex`'s `@live_statuses` and the task lease/heartbeat sets live outside this node, so treating an idle session as in-flight is their concern.
- A consumer that needs the TRANSCRIPT (`dashboard /help` chat, `/agents` history) goes through `Session.history/1` / `RemoteAPI.get_agent_history/1`; seeding the ETS row can only produce a SUMMARY, so a test needing real messages must start a live session (with `dispatch_ctx[:exchange_opts]` seams), never an `:evogit_agent_summary` row. A yield does NOT delete it.
- The session owns the worktree and the tmpdir; the worker owns nothing durable and installs the SESSION pid as `:evogit_agent_pid` (D7), so a worker death never orphans owner-bound state — the finalizer follows the same rule.
- An exception inside the worker or the START task is deliberately NOT caught: it becomes an abnormal `:DOWN` mapped onto the existing crash path, so the scheduler's crash retry restores the durable state (in-flight marker included) onto a fresh dispatch and `EvoGit.Agent.Resume` repairs the transcript there — never inside the dying process. The FINALIZER is the exception: it is monitored and its failure becomes an error result instead of a crash. This is why a crash in the MIDDLE of a tool batch is answerable: the worker is a short-lived supervised `Task` and the session never enters the tool loop.
- `:starting` performs NO I/O in the session process: the worktree request and scratch dir run in ONE monitored `EvoGit.TaskSupervisor` task whose create owner is the SESSION pid, and both diagnostic timers (`:worktree_create_slow_warn_ms`, `:worktree_create_stall_timeout_ms`) are read and validated (`> 0` integer, else the default) at call time.
- A start task must never outlive its session: the stall deadline, `{:cancel, :force}` and `terminate/3` all run `shutdown_start/1` (kill the task, cancel both timers), and only the CURRENT start ref may finish `:starting`.
- `EvoGit.Agent.Session.Registry` and `.Supervisor` are started by `EvoGit.Application` before `EvoGit.AgentScheduler`; every session is started by `Dispatch.do_try_dispatch/4`, a start failure is routed through the scheduler's crash/retry path, and `SchedMeta.session_pid`/`mode`/`phase` are only a best-effort mirror (`Session.inspect/2` is the live phase truth).
- `prompt_cache_key` is PROJECTED once by `EvoGit.Agent.Session` while assembling the state context and then lives on the owned `%State{}` for the whole session, so every exchange sends the same provider cache/routing identity and a resume never rotates it: `%AgentState{}` has no dedicated field, so a row field wins when present, else the registered value is read from `llm_generation_params[:provider_options][:prompt_cache_key]` with `:session_id` as fallback (`Config.Schema.LLM.with_cache_identity/3` appends both at registration); a provider with no cache identity keeps `nil`.
- Streaming state is SESSION-authoritative: `watchers`/`event_seq` live in the session's data and are re-stamped onto every adopted `%State{}` (`adopt_state/2`), `Watchers.flush/4` is the ONLY delta broadcast site, `Stream.Batcher` the ONLY coalescing buffer, and a watcher `:DOWN` is handled BEFORE the worker/finalizer arms (`Watchers.watcher_ref?/3`) so a consumer exit is never mistaken for a death.

`Session.Setup.bind_worktree/2` + `install_process_context/3` install these keys and seed the per-dir delegation counters; the table states who writes each key and who reads it.
| pd key | written | read / meaning |
|---|---|---|
| `:evogit_agent_id` | agent proc; EVERY tool task | `current_agent_id/0`, `CommandShell`, approval gate |
| `:evogit_task_id` | EVERY tool task | `CommandShell`, approval gate |
| `:evogit_agent_pid` | EVERY tool task (durable AGENT/session pid) | `BackgroundJobs.current_owner_pid/0` |
| `:evogit_agent_depth` | `session/setup.ex` | `AgentScheduler.current_depth/0` |
| `:evogit_started_at` | `session/setup.ex` | `Completion` — ISO-8601 |
| `:genesis_repo_root` | `session/setup.ex` (incl. repo-less override) | `ToolDispatch` — REAL repo root |
| `:evogit_repo_id` | `session/setup.ex` | `Tools.execute/5`, `Completion` — `"primary"` or a foreign id |
| `:foreign_repos` | `session/setup.ex` | `Tools`/`Tools.Shared` — `%ForeignRepo{}` list (write-role gate) |
| `:custom_agent_id` | `session/setup.ex` | `EvoGit.Agents.Custom` (root only) |
| `:attachments`, `:quality_level` | `session/setup.ex` | root media parts / quality level |
| `:repo_path`, `:repo_less` | `session/setup.ex` | agent worktree path / repo-less marker |
| `:evogit_task_tmpdir` | agent proc + tool task | `TaskTmpdir.current/0` |
| `:delegation_hints`, `:read_delegation_hints`, `:redundant_cd_warned` | exchange worker / tool_output_tracking | per-dir counters, once-per-run flag |
| `:conflict_files` | `ConflictState.refresh/1` (turn END) | `ConflictState.files/0`/`in_conflict?/0` — the ONE per-turn snapshot |

There are NO `:parent_id`, `:model_id` or `:depth` pd keys (they live on `%State{}` and the summary row), and the durable owner is `:evogit_agent_pid` (or `:ets.lookup(:evogit_sched_meta, agent_id)` → `%SchedMeta{session_pid: pid}`), never `$callers`; tool tasks inherit NO pd — the batch re-installs these keys per call (`../../tool_runtime/CONTEXT.md`).
