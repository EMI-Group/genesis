# Config — Unified Configuration Resolver

## Intent
`EvoGit.Config` — single source of truth for non-project configuration: merges built-in defaults with user config (`~/.config/genesis/config.toml`), loads API keys from `credentials.toml` into ReqLLM's key store, persists user config changes, and diagnoses configuration completeness.
Reads are served from ONE RAM snapshot per config directory (`EvoGit.Config.Cache`), refreshed only by a config-changed event raised by a save or by `EvoGit.Config.Watcher`'s file watch — never by a per-call file stat.

## Routing Table
- `./schema/` → config schema definitions (pure data: keys, types, defaults, validation) + provider/model generation-parameter extraction (`schema/CONTEXT.md`)
- `./schema/reasoning_effort.ex` → `EvoGit.Config.Schema.ReasoningEffort`: the ONE reasoning-effort ladder (`levels/0`, `options/0`, `allowed?/1`, `canonical/1`, `convert/1`), re-exported by `EvoGit.Config.Schema.LLM` as `reasoning_efforts/0` / `reasoning_effort_options/0` / `allowed?/1` / `canonical_reasoning_effort/1` / `convert_reasoning_effort/1`; every effort read, schema enum, selection rule and wire alias is built on it.
- `./keys.ex` → `EvoGit.Config.Keys`: the ONE tolerant key reader (`fetch/2`, `get/2,3` over atom- OR string-keyed maps, presence-based, never interning an atom) and the ONE recursive string-key transform (`stringify/2`, policies `:drop_nils` / `:model_tuples` / `:keyword_lists`); every tolerant read and string-key conversion in the config subtree delegates here.

## API Surface

### `EvoGit.Config`
| Function | Description |
|----------|-------------|
| `resolve/0` | Merged config map (defaults + user config) from the RAM snapshot — one `:persistent_term` lookup, no file I/O, no validation. Runtime overrides live in `AgentScheduler` state. |
| `resolve/1` | Value at an atom key or atom list from the same snapshot; a MISSING path answers the schema default (possibly `nil`), never an error. |
| `user_config/0` | Parsed `config.toml` from the snapshot, or `%{}` if absent/unparseable; zero `File.stat`/`File.read` per call. |
| `save_user_config/1` | Validates, then REPLACES `config.toml` through `persist_user_config/1` (creates the config dir) and raises `Watcher.notify_change/1`, so the snapshot refreshes synchronously. `:ok \| {:error, reason}` (`reason` = `[ValidationError]` or a filesystem term). |
| `save_credentials/1` | MERGES into `credentials.toml` with a SHALLOW per-key `Map.merge/2` (flat `ENV_VAR_NAME = "value"` table: same key replaced, unknown keys preserved, `nil`/`""` written rather than deleted); sets keys via `ReqLLM.put_key` BEFORE the write, then `Watcher.notify_change/1`. `:ok \| {:error, reason}` |
| `config_status/0` | `%{missing, warnings, ok?, validation_errors}`: `:llm_model` + `:api_key` (plus `:search_api_key` when search is enabled but unconfigured) checks; `resolved` and `validation_errors` come from ONE `Cache.get/0` snapshot value; the `:api_key` check is OAuth-aware; GitHub username is optional and NOT checked. |
| `credentials/0` | Credentials map from the snapshot; `ReqLLM.put_key` side effects run only on a snapshot BUILD, never on a hit. |
| `defaults/0` | `Schema.defaults/0` — a `deep_put` fold over every descriptor's `:default`; three values are CPU-thread-derived. |
| `list_settings/0` | `Settings.list_settings/0` → `Schema.all_schemas/0` |
| `show/0,1` / `update/1` | Settings facade (below). |
| `config_path/0` / `config_dir/0` / `credentials_path/0` | `config.toml` / `EvoGit.Platform.config_dir("genesis")` / `credentials.toml` |
| `api_key_present?/1` | `true` when any catalog credential key is in ReqLLM's key store or is a non-empty value in the given credentials map. |
| `tools_search_enabled?/0` | Provider-generic `[tools.search]` gate (see "Web Search Provider Config"). |
| `lsp_enabled?/0` | SINGLE gate for offering the `lsp` tool (see `[lsp]` below): `true` only when `[:lsp]` is a map whose `:enabled` is `true`/`"true"` AND `:command` is a non-blank binary; never raises. |
| `read_toml_file/2,3` / `ensure_trailing_newline/1` | `@doc false` shared helpers (see Constraints). |

### Settings facade (`EvoGit.Config` → `settings.ex`)

`list_settings/0` returns `Schema.all_schemas/0` unchanged: ordered descriptors with atom `key_path`, `type`, `default`, `validation`, `category`, `sub_category`, `description`.
`show/0` IS `resolve/0` (`EvoGit.Config.show/0` and `Settings.show/0` delegate): snapshot defaults + persisted config, never live scheduler overrides or the credentials map.
`show/1` accepts an atom, dotted string or nonempty atom/string list, returns the value directly (section maps and `nil` included), traverses existing keys by comparison without creating atoms, and answers `{:error, :invalid_path}` / `{:error, {:unknown_setting, remaining_path}}`.
`update/1` accepts a non-struct map of nested sections and/or dotted/list keys, resolves destinations against schema paths only, and rejects unknown paths (`{:error, {:unknown_setting, path}}`), malformed sections (`{:error, {:invalid_section, path}}`), malformed paths (`{:error, :invalid_path}`) and colliding aliases (`{:error, :colliding_patch_paths}`); a non-map patch is `{:error, :invalid_patch}`, an empty patch is `:ok`, and empty section maps are refused rather than treated as deletion.
Map-valued settings merge recursively; list-valued settings (including provider/model inventories) replace the whole value; indices and account ids are not patch paths; leaf payload keys normalize to strings.
An update starts from the snapshot's parsed USER map, overlays only requested leaves, preserves unrelated/unknown keys, validates exactly ONCE over `Schema.validate(Normalization.resolve(candidate))` and hands that USER-only data to `Config.persist_user_config/1` (no second pass; validation defaults and derived legacy mirrors are never persisted).
Validation failures return the schema's `{:error, [ValidationError]}` unchanged with no write; serialization/filesystem errors pass through.
No facade operation changes credentials, reloads the scheduler or applies runtime overrides, and its read-modify-save is non-atomic like `save_user_config/1`.
`normalization.ex` owns the shared default merge, safe existing-atom conversion, enum/model normalization and legacy migration for BOTH snapshot loading and candidate validation; serialization and credential handling stay in `config.ex`.

### `EvoGit.Config.ProviderPresets` (built-in schedule presets)
`provider_presets.ex` — machine-readable copies of peak/off-peak policies a vendor publishes unambiguously, so the dashboard's provider-profile editor can pre-fill an account's schedule in one click.
| Function | Description |
|----------|-------------|
| `all/0` | Every preset in display order |
| `ids/0` | The stable preset ids in display order |
| `get/1` | One preset by id; `nil` for an unknown id or a non-binary input |
| `for_provider/1` | Presets for one provider, by atom (`:deepseek`) or case-/separator-insensitive STRING (`"deepseek"`, `"ZAI-Coding-Plan"`); `[]` for nil or an unknown provider |
DATA ONLY: writes no config, touches no disk, starts no process, reads no clock, raises on nothing.
The envelope is `%{id, label, provider, schedule, note}`; `schedule` is STRING-keyed so it merges into a string-keyed canonical account over `concurrency`, `peak_concurrency`, `peak_hours`, `timezone`, `off_peak_days`, `off_peak_holidays`, carries only the keys its provider uses, and is valid input for `EvoGit.PeakHours.validate_windows/1`, `validate_days/1`, `validate_holidays/1`.
A published price/quota ratio is conservatively mapped onto slots (a rate that halves off-peak → `peak_concurrency` = half of `concurrency`) as an editable pre-fill, never a vendor-capacity claim.
Two presets ship: `deepseek-standard` (`:deepseek`, UTC weekday windows, CN holidays + weekends off-peak) and `zai-glm-coding-plan` (`:zai_coding_plan`, weekday 14:00-18:00 Singapore time); sources and the per-provider no-preset rationale live in the module's moduledoc and `docs/llm-profiles.md` §7.

### genesis.toml Structure
Three tables: `[worktree]` `script` (single fallback) with optional OS-specific variants as TOML dotted keys (`script.linux`/`script.macos`/`script.windows`; resolution `script.<current_os>` → `script` → `nil`), `[commands]` user shortcuts displayed in the dashboard and manually triggered (never auto-executed), and `[foreign_repos.<id>]` with `path` + `description` (+ `writable`/`base_sha`, see below).

### Foreign repos — schema & machine-binding gotchas
- **There is NO `[[repos]]`/repo-registry table in `config.toml`**: `Definitions.schemas/0` contains no repo/path key, so `Schema.validate/1` never validates a repository path and `Config.resolve/0` returns no repo list; the only repository configuration is per-repo `genesis.toml` `[foreign_repos.<id>]` (sibling `../project_config.ex`, deliberately NOT Ecto-validated) plus the per-task `:foreign_repos` opt.
- **Schema**: `path` REQUIRED (missing → entry dropped + a `Logger.warning`), `description` optional; the TOML table key IS the id; the key is `description`, NOT `name` (a `name` key is silently ignored), and there is no opt-in flag.
- **Committed to git**: `genesis.toml` is not git-ignored and Genesis Mode B auto-creates it, so absolute `[foreign_repos]` paths are committed and wrong on any other machine.
- **Path handling**: nothing validates absolute paths but they are semantically required — `ForeignRepo.new/3` only runs `EvoGit.Platform.safe_expand/1` (`~` → home, RELATIVE → the PROCESS CWD, no `$VAR` expansion) and nothing checks existence, so a missing path reaches the agent context and fails only at delegation (`build_subagent_phylo_node` matches `{:ok, foreign_head} = Git.rev_parse(...)`).
- **Task-opt merge**: `Runtime.Helpers.merge_foreign_repos/2` normalizes both lists and `Map.merge(toml_map, opt_map)` — the task opt wins per id and can OVERRIDE but never REMOVE a `genesis.toml` entry; the dashboard list lives only in socket assigns and `ResumeContext` does NOT carry `:foreign_repos` (only `MergeContext` does).

### Configuration Levels (priority low → high)
1. **Application defaults** — `Schema.defaults/0` (no model, no username). Three values are DYNAMIC from `EvoGit.Platform.cpu_threads/0` at `Definitions.schemas/0` runtime: `[:scheduler, :max_tool_concurrency]` (= CPU thread count) and both sandbox `:cpu_quota` strings (`"#{cores * 100}%"`), shared by display, reset-to-default and resolution.
2. **User config** — `~/.config/genesis/config.toml` (XDG), parsed with `TomlElixir.decode/1`.
3. **Runtime overrides** — `AgentScheduler` state via `handle_call({:update_config, opts})`; concurrency/retry/turn values are config.toml-only, and model selection is task-level in task opts, never a scheduler override.

### config.toml Structure
Key names by table (per-key types/defaults of all 112 descriptors — 19 under `[sandbox]` — and canonical `[[llm.providers]]` / legacy `[[llm.models]]` syntax with peak schedules: `schema/CONTEXT.md` + `docs/llm-profiles.md`):
- `[scheduler]` `default_llm_max_concurrency` (per-account fallback 3), `max_tool_concurrency` (default = CPU thread count), `agent_max_retries`, `max_agent_depth` (recursion DEPTH only), `max_retries` (LLM API), `max_turns` (SUB-agents), `max_turns_root` (ROOT only), `delegation_hint_threshold` / `read_delegation_hint_threshold` (0 disables), `max_tool_timeout`, `default_tool_timeout` (ms).
- `[llm]` `model` (`"provider:model"`, required only when no `[[llm.providers]]` exist), optional `compression_threshold_tokens`, `tool_result_pruning`, `tool_result_pruning_target_fraction`, `reasoning_effort`, `default_provider_profile`.
- `[user]` `github_username` (PR creation only, optional).
- `[sandbox]` `mode` (`"auto" | "enabled" | "disabled"`), `backend` (`"auto" | "systemd" | "bwrap"`), `write_paths` (nil = platform defaults; set incl. `[]` REPLACES them), plus `[sandbox.resources]` / `[sandbox.process]`.
- `[nix]` `enabled`, `flake_output` (cached dev env from a config-dir flake).
- `[appearance]` `accent_color` (GNOME/libadwaita palette: blue|teal|green|yellow|orange|red|pink|purple|brown|slate).
- `[data]` `dir`; `[tmp]` `mode` (`"system" | "custom" | "per_repo"`), `path`; `[lsp]` `enabled`, `command`, `args`, `timeout`, `diagnostics_timeout`.
- `[tools.search]` `enabled`, `provider`, per-provider sections (see "Web Search Provider Config").

**`[data] dir` relocates the whole runtime data dir** (`tasks.sqlite`, `agent_state.sqlite`, logs, caches, `genesis-source`); `Platform.data_dir/0` returns it, and an invalid value (nil/empty/non-binary/relative) logs a `Logger.warning` + falls back to the OS+env default — it NEVER raises.
Precedence: TaskRegistry `opts[:data_dir]` test seam → app env `config :evo_git, :data_dir` (read only by the Store child spec, `TaskRegistry.init/1` and `mix migrate.store`; set only in `config/test.exs`) → TOML `[data] dir` → XDG default; per-repo `.genesis` artifacts stay repo-root-fixed.
`Config.resolve()` runs in `config/runtime.exs` before any app starts and again in `Application.start/2` via `EvoGit.Distribution.maybe_enable/0`, so the Store child spec sees `[data] dir`; the config file's own location never depends on the data dir.

**`[tmp]` per-task managed tmpdir** `task_<id>`: `:system` (default) → `<system tmp>/genesis/task_<id>`; `:custom` → `<[tmp] path>/genesis/task_<id>` (empty/nil/non-absolute base falls back to system tmp); `:per_repo` → `<primary repo>/.genesis/tmp/task_<id>`.
`mode` is an `:atom` atomized by the `[:tmp]` clause of `Normalization.atomize_enum_values/1`, and the `[:tmp, :*]` keys carry `category: :data` (a new category would crash the dashboard's hardcoded Settings sidebar).

**`[lsp]`** — the tool (`agent/tools/lsp.ex`) speaks LSP over stdio to `command` (e.g. `lexical start`), one disposable process per call, and never installs a server.
Keys (all `category: :tools`): `enabled` (`:boolean`, `false`), `command` (`:string`, `nil`), `args` (`:list_of_strings`, `[]`), `timeout` (`:pos_integer` ms, `30_000`, the WHOLE-call budget), `diagnostics_timeout` (`:pos_integer` ms, `10_000`).
While `lsp_enabled?/0` is false the tool is NOT OFFERED AT ALL; once offered, an unconfigured call answers `Error: no language server configured — set [lsp] command in config.toml`.
Validation is warning-only at runtime (only `save_user_config/1` refuses a malformed value) and the gate plus the tool normalize defensively; the only consumers are `lsp_enabled?/0` and the tool (both `resolve([:lsp])`).

**`[[llm.providers]]` canonical inventory**: each STRING-keyed account carries `id`, `provider`, optional `name`, shared auth/endpoint/concurrency/peak/generation settings, ordered `models`, optional `default_model`/`reasoning_efforts`/`default_reasoning_effort`; `[llm] default_provider_profile` selects one by id (absent → first account/model, unknown → resolution error), and nested models accept a model id string or a map with `model` (`id` an alias) plus optional generation/context/effort overrides.
`Schema.provider_profiles/1`, `model_selections/1` and `resolve_selection/2` delegate to `Schema.ProviderProfiles`; exact maps, precedence and error shapes: `schema/CONTEXT.md`.

**Legacy `[[llm.models]]` fields** (accepted while providers are absent/empty): `id` + `model` required, `concurrency`, `context_window` (`200_000`), `auth_mode` + `oauth_file`, `peak_concurrency`, `peak_hours`, `timezone`, `off_peak_days`, `off_peak_holidays` (syntax: `docs/llm-profiles.md`).
- `auth_mode` (`"api_key"` default | `"oauth"`) is human/dashboard bookkeeping — the RUNTIME decision is `Schema.LLM.oauth_profile?/1`; validated by `EctoValidation.validate_auth_mode/2`, `oauth_file` by `validate_oauth_file/2` (absent → `<config_dir>/auth.json`; there is NO global `[llm] oauth_file` key).
- `context_window` is the compression window (stage-1 pruning target + derived threshold), never catalog metadata, read ONLY through `Schema.LLM.default_context_window/0`, `context_window/1` (invalid → warning + default, never raises) and `context_window_for/2`; `peak_concurrency` is NON-NEGATIVE (`0` = hard pause, never raised by the `default_llm_max_concurrency` floor).
- Peak window/day/timezone/holiday math is NEVER re-implemented here: `EvoGit.PeakHours.parse_window/1`, `validate_windows/1`, `validate_days/1`, `validate_timezone/2` (given `config_time_zone_database/0` explicitly, never the ambient `Calendar`, so a pre-boot snapshot validates identically) and `validate_holidays/1` own it. `peak_hours` takes `"HH:MM"` or integer minutes (one form per window), is half-open `[start, end)`, wraps when `start > end`, and disables on absent/`[]`/invalid; `off_peak_days` makes a whole day off-peak (every window suppressed, even `peak_concurrency: 0`) and WINS over window `days`; `off_peak_holidays` (today only `"CN"`) makes calendar non-working dates off-peak, 调休 make-up workdays counting as WORKING — both ACCOUNT-level only. `Schema.validate/1` reports at `[:llm, :models, <idx>, :peak_hours]` / `…, <window_idx>` (overlap at the later index) / `…, :off_peak_days` / `…, :off_peak_holidays`, and these fields plus `context_window` survive resolution untouched into `state.model_profiles` (`off_peak_holidays` via `ProviderProfiles.Normalize.@shared_keys`).
- `provider_options_for_model/1` returns `[store: false]` for a NATIVE OpenAI endpoint only (a model map with a non-nil `:base_url`/`:extra` is OpenAI-COMPATIBLE and gets `[]`); `store` is Responses-API-only, an explicit profile `provider_options` wins key-wise, and an undeclared key RAISES at request time (`zai` accepts `[:thinking]` only).
- Generation parameters are assembled at the ONE choke point `Schema.LLM.profile_generation_params/1` → `Schema.LLMConstraints.filter/3` (declarative Z.AI/GLM table + llm_db metadata); the dashboard persists none unless the user typed them, and this is the ONLY path here that reaches the LLMDB catalog (`model_metadata/1` uncached; a cold-BEAM first call loads it in the CALLING process — at boot `EvoGit.CatalogWarmup`'s throwaway process; `schema/CONTEXT.md` → "Model metadata seam"). Not every extracted key reaches the wire: the Z.AI family encodes neither `top_k` nor `reasoning_effort`, OpenAI chat-completions DOES emit `reasoning_effort`, and req_llm's unconditional `stream_options: %{include_usage: true}` is not suppressible from the config layer.

**`[sandbox] backend`**: `:atom`, default `:auto`, `[in: [:auto, :systemd, :bwrap]]`; `:auto` tries systemd-run → bwrap → no sandbox (macOS always sandbox-exec, bwrap is Linux-only), `:systemd` forces systemd-run, `:bwrap` forces bubblewrap (filesystem isolation only, falls back to no sandbox when unavailable). `[sandbox.resources]`/`[sandbox.process]` are systemd-only; strings are atomized by the `:sandbox` clause of `Normalization.atomize_enum_values/1`.
Mode/backend come from the CONFIG SNAPSHOT, never scheduler state (`resolve/0` excludes runtime overrides), so `AgentScheduler.update_config(sandbox_mode: …)` only changes the REPORTED value, while `sandbox_resources`/`sandbox_process_resources` DO apply live (Linux-only async `SandboxSlice.update_resources_async/1`). `get_config(:sandbox_backend)` reports `Platform.sandbox_backend/0`, NOT the configured backend.
There is NO app-env sandbox switch: no `.ex` reads `Application.get_env(:evo_git, :sandbox)`, so `put_env` there is a NO-OP.

**`[sandbox] write_paths`**: `:list_of_strings`, default `nil` — nil → platform defaults, set (incl. `[]`) → REPLACES the built-in list, malformed → validation error (never a crash). Consumed ONCE by `EvoGit.Sandbox.Spec.build/2`; structural paths (cwd, tmp, nix store, repo `.git`) are always appended and deny lists are unaffected (detail: `sandbox/CONTEXT.md`).

### credentials.toml Structure
A flat `ENV_VAR_NAME = "value"` table (`GOOGLE_API_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `ZAI_API_KEY`, `DEEPSEEK_API_KEY`, `GROQ_API_KEY`, `TAVILY_API_KEY`, …).
Keys load into ReqLLM's in-process key store on a snapshot build; one key matching the model provider is enough, and OAuth data never lives here.

## Adding a New Config Category / Schema (round-trip contract)

All schemas live in ONE flat list — `EvoGit.Config.Schema.Definitions.schemas/0` (NOT per-category modules); a schema is a plain map with 7 keys (`key_path`/`type`/`default`/`validation`/`category`/`sub_category`/`description`) — there is NO `%Schema{}` struct. `schemas_by_category/0` = `Enum.group_by(& &1.category)`; per-category order = definition order.
A NEW top-level category is additive for enumeration (append a map), `Schema.validate/1` (only checks defined keys; absent/nil pass; unknown keys are never rejected), `defaults/0` (derived from each `:default` via `deep_put`) and save-side serialization (`Keys.stringify/2` + `TomlElixir.encode` write any map; atom VALUES encode as quoted strings, nil values drop).
**The one non-additive gap is the READ/resolve path**: TOML has no atoms, and string enum values are atomized ONLY by `atomize_enum_values/1`, whose HARDCODED clauses cover `:sandbox` (`:mode`/`:backend`), `:git` (`:cow_worktree_creation`), `:llm` (model normalization + reasoning-effort canonicalization), `:tools` (search provider + per-provider `search_depth` via `search_providers/0`) and `[tmp]` (`:mode`). A NEW `:atom`-enum key needs a matching clause (or `:string` typing + atomization at the consumption point, like `[:llm, :reasoning_effort]`), else every snapshot build logs `must be an atom, got "blue"` and `config_status/0` reports it (non-fatal). The dashboard save path is unaffected: `SettingsUtils.parse_atom/2` (evo_dash) converts `:atom` form values against `validation[:in]` BEFORE `Schema.validate`.
Dashboard-side requirements for a new schema-driven category (evo_dash, not core): `category_display_name/1`, `category_icon/1`, `category_description/1` clauses in `EvoDashWeb.SettingsComponents.CategoryMetadata` (no catch-all — a missing clause is a FunctionClauseError) plus an entry in its `sort_categories/1` order list (missing = sorts last); `:agents`/`:remote_connections` are NOT core categories (the dashboard injects them as empty-schema pseudo-categories).

## Validation Path Typing
`Schema.key_path/0` describes atom-only schema descriptor paths; `Schema.ValidationError.key_path/0` describes error paths with atoms and non-negative list indexes (as emitted by composite profile validators) and is used by `Schema.ValidationError.t/0`.

## Validation Engine — Ecto-backed (architecture)

The validator beneath the DSL is **Ecto-backed, but Ecto is a VALIDATOR ONLY** — no `Ecto.Changeset` is ever built, `apply_changes` is never called, and the validated map passes through unchanged on `{:ok, config}` (unknown keys survive, model profiles stay plain maps).
- **`EctoTypes`** — eight nested strict `use Ecto.Type` modules (`PosInteger`, `NonNegInteger`, `Integer`, `String`, `ListOfStrings`, `Float`, `Atom`, `Boolean`), one per scalar DSL type, with `type_for/1`, `cast/2` and `valid?/2`. Strict oracles: no numeric-string coercion, `""` is meaningful, `:float` accepts int-or-float, `:atom` never casts strings.
- **`EctoValidation`** — `errors_for(key_path, type, validation, value) :: [%ValidationError{}]`, type errors FIRST then rule errors; all window/day/timezone/holiday math delegates to `EvoGit.PeakHours`; `provider_profile_shared_errors/2` covers `peak_concurrency`, `peak_hours`, `timezone`, `context_window`, `off_peak_days`, `off_peak_holidays`, `auth_mode` and `oauth_file` for BOTH canonical accounts and legacy profiles; `min`/`max`/`in` stay hand-written pure predicates (Ecto's `validate_number`/`validate_inclusion` are banned by design). Messages, `value`/`rule` terms, sub-path key_paths and error ordering are byte-pinned by the `schema_test.exs` / `config_test.exs` suites.
- **Delegation**: `Schema.validate/1` walks the map with `safe_get_in/2` and calls `EctoValidation.errors_for/4` per present value; scalars route through `EctoTypes.valid?/2`; `:model_spec`, `:model_profiles` and the optional profile fields recurse explicitly (multi-error, sub-path-aware).
- **Hand-written, and why**: Ecto has no TOML story and the pipeline runs on variable-depth maps with byte-pinned shapes, so the transform pipeline stays in `normalization.ex` (`deep_merge`, PRE-Ecto `atomize_enum_values` — which also writes every reasoning-effort site in the ONE ladder's canonical spelling — and `migrate_llm_models`), save serialization (`strip_flat_llm_fields`, `Keys.stringify/2`, `TomlElixir`) in `config.ex` (`persist_user_config/1`), and `Schema.defaults/0` as a hand-written `deep_put` (112 entries). `config.ex` calls `Schema.validate/1` exactly once per snapshot build, validate-first in `save_user_config/1`, and once over the normalized candidate in `Settings.update/1`.
- **Ecto quirks**: numeric strings fail number types; `""` is never stripped; unknown keys survive; no `Ecto.Enum`, so a surviving bad enum string surfaces as a TYPE error (`rule == :atom`); `cast(_, nil)` → `{:ok, nil}` (nil ≡ absent, and absent keys are skipped before `errors_for/4`); `EctoTypes.type_for/1` must return FULLY-QUALIFIED module atoms (`__MODULE__.PosInteger`) or runtime dispatch fails.
- **NOT Ecto-validated**: `LLMCatalog`, `VersionState`, `credentials.toml`, `ProjectConfig`/`genesis.toml` (lenient by design), `CustomAgents`/`agents.toml` (own CRUD validation), `RuntimeOpts` (raises `ArgumentError`). Only the `config.toml` DSL (112 `Definitions.schemas/0` entries, 14 LLM) is Ecto-validated.

## Direct API Admission and Persistence Boundaries
`EvoGit.Config` lives in `config.ex`; `Schema.all_schemas/0`, `schemas_by_category/0`, `defaults/0` and `validate/1` are real public APIs in `schema.ex`, and `Schema.effective_model_profiles/1` delegates to `Schema.LLM`.
The Assistant evaluator admits `Config.resolve/0,1`, `list_settings/0`, `show/0,1`, `user_config/0` and `config_path/0` in the read and write tiers through explicit exact-MFA lists (never namespace grants); only approved tier-2 write calls additionally admit `Config.update/1`, `save_user_config/1`, `AgentScheduler.RemoteAPI.reload_config/0` and `AgentScheduler.update_config/1` (contract: `../agent/tools/elixir_eval/CONTEXT.md`).
The model guards accidental self-corruption, not attackers: read/write stay Dune-interpreted and bounded, while separately approved sudo is unrestricted native evaluation, never an automatic escalation.
`resolve/0,1`, `show/0,1` and `user_config/0` return UNREDACTED data (node cookies, model `extra`/`provider_options`, endpoint credentials, arbitrary unknown TOML keys) and neither output caps nor error messages redact secrets; they cover defaults + user configuration, never live scheduler overrides.
`config_status/0` returns `missing`, `warnings`, `ok?` and `validation_errors`, loads credentials into ReqLLM and may lazily import OAuth credentials; `resolved` and `validation_errors` come from ONE `Cache.get/0` value (so the errors match that map), though its nested health reads are not transactionally isolated from an in-flight `Cache.reload/1`, and there is no process-dictionary error propagation — only a `Cache` store replaces the snapshot.
`:ok?` requires no missing critical settings AND an empty validation-error list; `missing`/`warnings` are presence/credential diagnostics without validation values or credentials.
Public visibility grants no evaluator access: `config_status/0`, `read_toml_file/2,3`, credential helpers and schema APIs stay unlisted; `read_toml_file/2,3` reads any supplied path despite `@doc false`, and `credential_key_to_reqllm_key/1` calls `String.to_atom/1` for arbitrary suffixed input.
`save_user_config/1` validates then REPLACES the whole config file (never a patch/merge), reloads the snapshot synchronously and performs no scheduler reload or PubSub `"config"` broadcast on its own behalf; saving a resolved map also materializes defaults.
`persist_user_config/1` is the UNVALIDATED half (mkdir_p → mirror stripping → `Keys.stringify/2` → TOML encode → plain `File.write/2` → `Watcher.notify_change/1`), `@doc false`, called ONLY by `save_user_config/1` and `Settings.update/1` after their own single validation pass; no atomic rename, lock, rollback or chmod, so both paths are non-atomic and can overwrite a concurrent writer.
Prefer approved `Config.update/1` for a targeted change; neither API applies scheduler runtime state, so after a successful `update/1` or `save_user_config/1` explicitly call `AgentScheduler.RemoteAPI.reload_config/0` and inspect its result (persistence success does not imply reload success; boot-only settings need a restart), while `AgentScheduler.update_config/1` stays a separate runtime-only mutation that a reload or restart can overwrite.
`Schema.validate/1` walks atom-keyed schema paths, skips missing/nil/non-map intermediates and preserves unknown keys, so string-keyed top-level maps and malformed intermediate sections can bypass validation; model-profile validation checks id/model, the atom-keyed provider-options container and optional peak/context/auth fields, but not per-profile concurrency or generation-parameter ranges.
`save_credentials/1` merges without schema validation, mutates ReqLLM's key store BEFORE the filesystem write, and does not clear previously loaded keys given empty/nil replacements; `credentials/0` returns raw secrets and mutates that store on a snapshot BUILD.
Schema validation is not authorization, and neither approval nor evaluation timeouts roll back committed side effects; leaf-specific OAuth assembly, atom creation and catalog side effects: `schema/CONTEXT.md`.

## Config Caching

`EvoGit.Config.Cache` holds ONE RAM-resident snapshot per config directory in `:persistent_term` under `{EvoGit.Config.Cache, dir}`, shaped `%{dir, user_config, credentials, resolved, validation_errors, generation, fingerprint}`.
- **Reads are pure term lookups**: `Cache.get/0` resolves the directory AT CALL TIME through `EvoGit.Config.config_dir/0` (so the per-process `:config_dir_fun` seam keeps working); a hit performs zero `File.stat`/`File.read`, no merge and no `Schema.validate/1`.
- **One build, then lookups**: a miss calls `EvoGit.Config.build_snapshot/1` once and stores the result with `generation: 1` and NO broadcast; `build_snapshot/1` is the ONLY reader of `config.toml`/`credentials.toml` and runs the whole pipeline once (`defaults() |> deep_merge(atomize_keys(user_config)) |> atomize_enum_values() |> migrate_llm_models()`, then `Schema.validate/1`), keeping the ReqLLM `put_key/1` side effects and one "Config validation error at …" warning per error.
- **Fingerprint-driven reload**: the snapshot fingerprints the raw bytes of both files (`:erlang.phash2({config_bytes, credentials_bytes})`), so `Cache.reload/0,1` rebuilds and compares — unchanged contents return the previous snapshot with no store, no generation bump and no broadcast; a change costs exactly ONE `:persistent_term.put` with `generation + 1`, followed by a best-effort `{:config_reloaded, node(), dir, generation}` on PubSub topic `"config"` (skipped when `EvoGit.PubSub` is not running, never raises into the caller).
- **ONE total reload helper**: `Cache.reload_safely/0,1` is the total variant and the ONLY place in the codebase that wraps a snapshot reload in rescue/catch logging (naming the directory), answering `:error`; `reload/0,1` stays RAW, and `Watcher`'s private `refresh/1` delegates to `reload_safely/1` and normalizes its answer to `:ok | :error`, so the boot prime, the debounced file event, the save event and the fallback share ONE reload implementation.
- **Freshness is event-driven, never polled**, from exactly two event sources — a successful save and a file event on the watched directory — that both converge on the watcher's single refresh handler.
- **Saves refresh synchronously through the watcher event**: `save_user_config/1` and `save_credentials/1` call `EvoGit.Config.Watcher.notify_change(dir)` after their successful write and before returning `:ok`, which runs the SAME refresh as a file event — or the `Cache.reload_safely/1` fallback when no watcher is registered — so the settings page, the Welcome setup and the Assistant `elixir_eval` write tier read fresh values immediately.
- **`EvoGit.Config.Watcher`** is a GenServer started after `Phoenix.PubSub` and before `EvoGit.AgentScheduler` (NOT started when `Mix.env() == :test`) that owns "config changed → refresh snapshot": it watches the config dir through the vendored `file_system` dep and debounces ONE ~150 ms coalesced refresh per burst of `config.toml`/`credentials.toml` create/modify/remove/rename events; its `handle_call({:config_changed, dir})` runs the same refresh for the save event (the explicit requested dir, even when it watches another) and replies the refresh VERDICT, which lets `notify_change/2` take its own guarded fallback when the refresh failed instead of reporting a save that never landed; an `agents.toml` event calls `EvoGit.CustomAgents.reload/0` instead.
- **Watcher degradation**: a backend that cannot start (no `inotifywait`/`inotify-tools`, watch limits, missing dir) logs ONE warning and the GenServer stays alive unwatched; a stopped worker logs one warning; saves plus explicit reloads still refresh. `notify_change/1,2` is total and bounded (a `nil`, unregistered, dead or slow watcher falls back to the same guarded refresh and still answers `:ok`); its `GenServer.call/3` guard is `catch :exit` ONLY, because a dead/restarting/slow watcher EXITS the caller rather than raising it, so a `rescue` arm would be dead code. The watcher is a convenience, never a requirement, and never crashes the application; its `dir:`/`name:` options (default the module name, `nil` = unnamed) exist so tests run isolated instances.
- **Explicit reload re-reads disk**: `AgentScheduler.RemoteAPI.reload_config/0` FORCES `Cache.reload()` before `Config.resolve()` + `update_config/1`, so an explicit (including remote/SSH-triggered) reload observes current disk content.
- **`read_toml_file/3` stays uncached** (`@doc false`): `project_config.ex` (`genesis.toml`), `remote_connections.ex` and `custom_agents.ex` (`agents.toml`) read through it and keep their own freshness rules.
- **Missing vs unparseable**: an absent/unreadable `config.toml`/`credentials.toml` silently yields `%{}`; a TOML decode failure logs one warning and also yields `%{}`.
- `config_status/0` takes BOTH `resolved` and `validation_errors` from ONE `Cache.get()` value; errors are recomputed only by the next build. `defaults/0` stays uncached (a cheap `deep_put` fold whose three CPU-thread-derived values read `Platform.cpu_threads/0` at call time).

**Snapshot vs scheduler state:**
- The runtime config agents use is the **`AgentScheduler` GenServer state**: `RemoteAPI.get_config/0` reads it, `reload_config/0` forces a snapshot reload and replaces it, and `get_config_status/0` reads the snapshot per call for truthful `:missing`/`:warnings`/`:ok?`.
- `save_user_config/1` refreshes the snapshot but does NOT apply scheduler runtime state — the dashboard (SettingsLive) calls `reload_remote_config` but ignores its return, so a reloadable setting can stay unapplied until an explicit reload.
- `RemoteConnections` does NOT auto-create an empty `remote_connections.toml` (unlike the config skeleton) — the file appears only when a target is saved.

## Boot-Time Resolve Cost & Retention

- `resolve/0,1` are `:persistent_term` lookups: the pipeline (defaults + atomized TOML merge → `atomize_enum_values` → `migrate_llm_models` → `Schema.validate/1` over all 112 schemas) runs ONCE per config directory per actual file change inside `build_snapshot/1`; no hot-path read pays for it and no read stats a file.
- `Watcher.init/1` primes the snapshot at boot through `refresh/1` → `Cache.reload_safely/1` (total, so a raising build cannot crash-loop the watcher) — a fingerprint-diffed no-op when `runtime.exs`'s early `resolve/0` already built it — before every CHILD that reads config; in test the watcher is absent, so the first `Cache.get/0` builds in the calling process.
- Retention: one snapshot per config dir lives in `:persistent_term` for the BEAM lifetime (parsed TOML maps, resolved map, validation errors — small); `AgentScheduler` independently keeps its selected fields (`model_profiles`, generation params, sandbox/scheduler scalars), and `PeakHourEngine.init`/`SystemSampler` read that state, never the disk.
- ⚠️ The DOMINANT boot cost is not config resolution: `AgentScheduler.init` → `Schema.LLM.llm_generation_params/1` → `model_metadata/1` → `ReqLLM.model/1` triggers LLMDB's LAZY packaged-catalog load (`priv/llm_db/snapshot.json`, ~11.7 MB, ~10,100 models), whose decoded table is retained in `:persistent_term` for the BEAM lifetime (tests: ~2.5 s). It fires whenever ANY profile carries a `model`; a model-less fresh install pays nothing. Config BEAM code is ~220 KB, lazily loaded, and no schema validation runs at compile time.

## Test Seam — per-process config dir (`:config_dir_fun`)

- `EvoGit.Platform.config_dir/1` consults the app-env seam `:evo_git, :config_dir_fun` at CALL time before XDG resolution; the seam accepts a zero-arity fun or `{m, f, a}` and the result must be a non-empty binary (garbage falls through, no `try/rescue`).
- It is **default-inert**: production never sets it, so production paths are byte-identical to the XDG/APPDATA/Library resolution; `test/test_helper.exs` installs `{EvoGit.TestSupport.ConfigDir, :resolve, []}` (from `test/support/config_dir.ex`).
- Helpers: `resolve/0` (own process dict → `$callers` pids on the local node → `nil`), `activate/1` (put in the calling process, e.g. `setup`), `isolate_module!/1` (`setup_all`; unique tmp dir + `on_exit` cleanup) and `isolate!/1` (`isolate_module!/1` + `activate/1`).
- `$callers` reaches `GenServer`/`Task`/`Supervisor` children started FROM the test process, NOT boot-time singletons (`AgentScheduler`, `TaskRegistry`, `Store`, `PeakHourEngine`) — a module reading config inside those must stay `async: false`.
- The snapshot is keyed by config DIRECTORY and resolved through the seam at CALL time, so a unique dir per test is snapshot-safe; `Cache.get(dir)` and `Cache.reload(dir: dir)` address an explicit dir, and `Cache.invalidate/0,1` erases a snapshot (the next `get` rebuilds at `generation: 1` and re-reads disk) — the seam for a test that changes files behind the cache's back.
- A test going through `save_user_config/1`/`save_credentials/1` needs no extra cache step (both reload synchronously); the watcher is not started in test, so no test need account for an asynchronous refresh unless it starts its own unnamed `EvoGit.Config.Watcher` (`name: nil`).

## LLM Shape and Normalization Boundaries
Canonical persisted inventory is `[[llm.providers]]`, selected by optional `[llm] default_provider_profile`; each account has one stable id, shared provider/auth/endpoint/concurrency/peak fields, generation defaults and an ordered `models` list whose nested maps may override generation/context/effort plus an ordered `reasoning_efforts` inventory. Canonical provider maps and all nested maps use STRING keys while the surrounding resolved config uses atom schema keys.
`default_model` plus optional `default_reasoning_effort` choose defaults without inventing an effort from inventory order.
`Normalization.atomize_enum_values/1` stringifies the whole providers subtree through `ProviderProfiles.Normalize.stringify/1` and canonicalizes its effort fields, preserving malformed entries for validation rather than dropping them; legacy `[[llm.models]]` and flat `[llm] model` stay accepted while no nonempty providers list exists.
`Schema.provider_profiles/1` exposes canonical string-keyed profiles and migrates legacy accounts one-for-one without combining equal provider/model/endpoint accounts or changing ids (the read projection never rewrites files); `Schema.model_selections/1` enumerates ordered model/effort inventory without credentials or metadata; `Schema.resolve_selection/2` (alias `resolve_model_spec/2`) resolves a nil/default, provider id or explicit provider/model/effort selection through `Schema.ProviderProfiles`.
Canonical providers are authoritative over stale legacy fields and resolution materializes no derived `llm.models`/flat mirrors; saving a config with nonempty providers strips legacy `models`, flat generation/model fields and flat auth/provider-options mirrors, leaving providers + default selector as the sole persisted inventory. Legacy model keys normalize via existing atoms only, with `@model_profile_extra_keys` pinning otherwise-unreferenced allowed atoms.
`Schema.validate/1` appends `ProviderProfileValidation.cross_field_errors/1` after descriptor validation: an explicit `llm.default_provider_profile` must match an id in a nonempty canonical providers list — absent/nil valid, an unknown id reports `%ValidationError{key_path: [:llm, :default_provider_profile], rule: {:in, configured_ids}}`, blank selectors report `:string` errors, non-string ones keep the descriptor's single type error, and the check reads raw atom-/string-keyed ids without hiding malformed-row errors.
`ProviderProfileValidation.default_model_errors/4` checks each account's raw `default_model` against its inventory: absent/nil and matching provider-qualified names pass, unknown names report `{:in, ids}`, blank/non-string values `:string` errors at `[:llm, :providers, index, :default_model]`. Runtime normalization may repair those and treats a global `false` selector as absent, but raw validation still rejects them, so `config_status/0` reports `ok?: false` even when another account supplies a model and credentials — the returned validation errors, not `missing == []`, are authoritative for that failure.
`Schema.effective_model_profiles/1` delegates to `Schema.LLM.effective_model_profiles/1` for scheduler boot, reload and catalog warm-up and never falls back to stale flat settings; presence/OAuth diagnostics use `Schema.model_profiles/1`'s runtime projection. A canonical API-key account's explicit `api_key_env_var` health check accepts a nonempty environment string first, then a nonempty `credentials/0` string under that exact name, with no catalog-key fallback and no borrowing another same-provider account's key; OAuth accounts never use this path.
The single effort ladder is `Schema.ReasoningEffort`: `levels/0` → `[:none, :minimal, :low, :medium, :high, :xhigh]`, `options/0` adds `:default` (send no effort at all), `allowed?/1` is the total acceptance predicate, `canonical/1` the total normalizer (`nil` for anything unrecognized) and `convert/1` its documented ECHO (unknown values return unchanged so validation can report them).
`max` is an accepted legacy ALIAS normalized to `xhigh` on read and NEVER an offered level: `Normalization.atomize_enum_values/1` canonicalizes every effort site (flat `[:llm, :reasoning_effort]`, each account's `reasoning_effort`/`default_reasoning_effort`/`reasoning_efforts[]` and every nested `models[*]` equivalent) and `ProviderProfiles.Normalize.string_effort/1` does the same when resolving a profile, while an UNKNOWN effort is left untouched so validation still reports it.
`[:llm, :reasoning_effort]` carries `validation: [in: <canonical option strings>]`, so `save_user_config/1` (which validates the RAW map it was handed) rejects a literal `"max"`/`" High "`, whereas the snapshot build and `Config.update/1` canonicalize first — `" High "` loads as `"high"`, a persisted `"max"` reads as `"xhigh"`. Detailed generation/auth/reasoning assembly, selection error contracts and compatibility traps: `schema/CONTEXT.md`.

## LLM Model Presence Decision (config_status `:llm_model` gate)

`config_status/0` reports `missing: [:llm_model]` plus "LLM model is not configured. Set [llm] model in config.toml." when NO profile carries a usable model: the predicate runs over `Schema.model_profiles(resolved)` and counts a `:model` that is a non-empty binary OR a valid map spec (non-empty map with non-nil `:provider` and non-empty binary `:id`) — nil, `""` and `%{}` all fail, so a custom-endpoint map model (kept a map whenever `base_url`/other override keys are present) passes.
**Validation asymmetry**: per-profile `:model` validation treats `nil` as an error but accepts ANY binary, so `""` passes `Schema.validate` yet fails this gate, yielding `validation_errors: []` plus `missing: [:llm_model]`; the flat `[:llm, :model]` spec is equally lax. This gate is the ONLY place empty strings are rejected, and a missing `:llm` section / `llm.models = []` / flat nil model produce NO validation error — the warning is the sole signal, by design.
**Legacy mirror rule (`migrate_llm_models/1`)**: with no canonical providers, flat `[llm] model` mirrors ONLY the FIRST legacy profile — a no/nil model there leaves the flat field nil even when later profiles carry valid models (so `resolve([:llm, :model])` is nil), a first-profile `""` mirrors as `""`, and canonical configs synthesize no flat mirror.
**Disk shape after save**: with a nonempty providers list `save_user_config/1` strips legacy `llm.models` and flat model/generation/auth/provider-options mirrors; legacy-only configs keep `[[llm.models]]` and lose flat generation/model fields only when that list is nonempty. `stringify_keys/1` drops nil values at every map level, so legacy nil-model profiles round-trip without a model key.

## OAuth / Subscription Auth
Subscription (OAuth) auth spends an existing ChatGPT/Claude login instead of a per-token API key; the ONLY credential store is the managed file (the profile's `oauth_file`, default `<config_dir>/auth.json`) — ReqLLM-native JSON keyed by provider OAuth id (`"openai-codex"` / `"anthropic"`), entries `type`/`access`/`refresh`/`expires`(ms)/`accountId` — and `credentials.toml` never carries OAuth data.
- **Path precedence** (`Schema.LLM.oauth_file_for/1`): `opts[:oauth_file]` → the profile's `oauth_file` → `EvoGit.Auth.default_oauth_file/0` (`<config_dir>/auth.json`, via `Platform.config_dir/1` so the `:config_dir_fun` seam applies); `~` is expanded and a broken managed-file read degrades to the default. There is NO global `[llm] oauth_file` config key.
- **Catalog auth metadata**: each `LLMCatalog` provider entry carries `auth_modes` (default `[:api_key]`), `oauth_source`, `provider_atoms` and `credential_key`; `:openai_codex` ("ChatGPT Subscription", `oauth_source: :chatgpt`) is OAuth-ONLY, `:anthropic` is `[:api_key, :oauth]` with `oauth_source: :claude_code`, every other provider is API-key only.
- **Which profiles are OAuth** (`Schema.LLM.oauth_profile?/1`): `auth_mode == :oauth` OR the provider is `oauth_only?` — so `model = "openai_codex:gpt-5.6-terra"` needs no `auth_mode`.
- **What reaches the request** (`profile_generation_params/1`): an OAuth profile gains `provider_options: [auth_mode: :oauth, oauth_file: <resolved>]`, overridden key-wise by explicit profile `provider_options` (three-level precedence: `schema/CONTEXT.md`).
- **Credentials**: Anthropic OAuth uses the lazy vendor import into its configured managed file; ChatGPT Subscription uses the protected Genesis SIWC registration identified by `siwc_account`, resolved at request time, and existing `openai_codex` identifiers continue through the SIWC adapter.
- **Env fallback**: `CLAUDE_CODE_OAUTH_TOKEN` (then `ANTHROPIC_OAUTH_TOKEN`) for `:anthropic` when no file credential exists — OAuth without refresh, never written to disk; `:openai_codex` has no env fallback.
- **`known_credential_keys/0` filter**: a provider entry contributes its `credential_key` only when `:api_key` is in its `auth_modes`, so an OAuth-only provider never makes `api_key_present?/1` report a key; variant keys stay unconditional.
- **Health (`config_status/0`)**: the `:api_key` check passes when `api_key_present?(credentials())`, an API-key account's exact custom `api_key_env_var` resolves from the environment or persisted credentials, OR a configured OAuth profile's credential resolves (`Schema.LLM.oauth_credential_status/1`, which imports first and degrades to "not configured" on a broken file). On failure WITH OAuth profiles, the warning names the OAuth providers, their `login_instructions/1` text and the per-profile managed file(s) from `oauth_file_for/1` ("Managed OAuth file: <path>", plural when profiles differ; `default_oauth_file/0` when none resolves); a config with no OAuth profile keeps the generic "No API key found. Add keys to credentials.toml or configure via the settings page." An OAuth profile reporting `{:error, {:managed_file_unwritable, reason}}` (login exists, managed copy cannot be written — read-only home, Nix sandbox) instead gets `EvoGit.Auth.managed_file_unwritable_remedy/2`'s actionable text and the misleading "run the vendor login" instructions are omitted.
- **Onboarding**: the dashboard Welcome setup and Settings → LLM editor ask an OAuth-capable provider for an auth mode ("API key" vs "Subscription (OAuth)"), skip the question for an OAuth-only provider, never prompt for an API key on the OAuth path, and save `auth_mode = "oauth"` (the API-key path writes none and clears a stale one); `credentials.toml` never carries OAuth data. `EvoGit.SystemCheck.do_llm_test/2` runs `ensure_profile_credentials/1` before its connection test and, for a `{:managed_file_unwritable, reason}` outcome, returns `{:error, "LLM connection test not run — <remedy>"}` WITHOUT issuing a request.

## Naming & Vocabulary (audit)

- **"Account" is spelled six ways**: the account id string is `profile["id"]` in `ProviderProfiles.provider_profiles/1`, `model_selections/1` and `resolve_selection/2` — the SAME value a task `model_spec` calls `provider_profile_id`; `[llm] default_provider_profile` is that id, `provider_profile` in a resolution result is the whole account MAP, and bare `profile` is a legacy `[[llm.models]]` entry or a model-selection row.
- **`model_spec` means two things**: in a resolution result it is the ReqLLM-ready qualified string/endpoint-override map (dispatch stores it as `llm_model`), while a task `model_spec` is the STRING-keyed identity (`provider_profile_id` + `model` + optional `reasoning_effort`).
- **`model_id` names a legacy profile/account id in `context_window_for/2`** but a model identifier in `LLMConstraints`' table lookup and `ProviderProfiles.Normalize`; `model_profiles` names both the raw legacy list and a resolved atom-keyed runtime projection (`Schema.LLM.model_profiles/1`; the schema TYPE `:model_profiles` is the former only); `id` carries three namespaces at once (account id, model id from that account's inventory, model id inside the ReqLLM spec) plus `LLMCatalog`'s own entry id.
- **`show/0` IS `resolve/0`** (both one-line delegations); `show/1` only adds path forms and `{:error, :invalid_path | {:unknown_setting, path}}`.
- **`save_*` is REPLACE in one function and MERGE in the other**: `save_user_config/1` validates then REPLACES the file through `persist_user_config/1`, while `save_credentials/1` shallowly merges; `Config.update/1` → `Settings.update/1` is the partial patch path.
- Both `canonical_providers?/1` implementations (public `Normalization`, private `LLM`) read through `Keys.get/2`'s presence semantics, so they agree.
- **Tolerant key reads have ONE home**: `Keys.fetch/2`/`get/2,3` (atom- OR string-keyed, presence-based, `String.to_existing_atom/1` inside its one justified rescue, never interning) — `Normalization.get_key/2` delegates, and `LLM`/`LLMConstraints`/`ProviderProfiles` read through it (`LLM.profile_field/2`, `EctoValidation.profile_field/2` and `LLMConstraints.fetch_key/2` do not exist); `Schema.safe_get_in/2` is the separate atom-only schema key-path walk, and `PeakHourEngine.profile_field/2` (sibling `agent_scheduler/`) plus `Settings.fetch_path/2` are the remaining hand-rolled readers outside this node.
- **Key stringification has ONE home**: `Keys.stringify/2` (policies `drop_nils:`/`model_tuples:`/`keyword_lists:`) serves the save-side conversion, the credentials map and `ProviderProfiles.Normalize.stringify/1`; `CustomAgents.stringify_keys/1` keeps its own copy in `custom_agents/`.
- **Atom-tolerant converters fail three ways**: `Normalization.safe_atomize/1` and `ProviderProfiles.existing_key/1` keep the string, `LLM.existing_atom_key/2` drops the pair to `nil`; `LLM.provider_from_model/1` resolves through its compile-time whitelist (`LLMCatalog.providers/0`) with a `String.to_existing_atom/1` fallback, so a provider atom absent from the VM has no catalog metadata (`catalog_key/1` → `nil`) and metadata/constraint filtering merely degrade — nothing raises.
- **`LLMCatalog` has two provider-lookup rules**: `find_provider/1` matches `provider_atoms` only, while private `resolve_entry/1` matches the entry `id` first — so `provider_models(:openai_compatible)` is `[]` while `requires_base_url?(:openai_compatible)` is `true`.
- `get_model_profile/2` and `default_model_profile/1` are `fetch_`-shaped under the wrong names (`{:ok, _} | {:error, :not_found}`, no non-map clause), unlike their total siblings; account validation is split over `ProviderProfileValidation.errors/2` + `.cross_field_errors/1`, `EctoValidation.provider_profile_shared_errors/2` (`@doc false`) and `Schema.validate/1`'s tail call, with `config/` and `config/schema/` aliasing each other both ways; `maybe_param/3` is public but internal-only (only `LLM.llm_generation_params/1`) and the keyword twin of private `maybe_put/3`.
- Intentional distinctions that MUST stay: legacy `[[llm.models]].id` ≡ canonical account `id` (one-for-one migration, `schema/provider_profiles_normalize.ex`); `model_spec` (selection identity) vs `llm_model` (ReqLLM-ready value); explicit `model_spec` vs unlocked `default_model_spec`; the `:openai` → `:openai_codex` auth-route rewrite.
- The schema subtree's own copies: `schema/CONTEXT.md` → `## Known Issues`.

## Constraints
- **No config key caps TOTAL agents / live worktrees / subagent spawn breadth.** `Definitions.schemas/0` has NO `max_agents`/`max_worktrees`/`max_subagents`/breadth key; `[:scheduler, :max_agent_depth]` (default 8) is the ONLY structural limit and bounds recursion DEPTH only (`Subagents.validate_subagent_depth/3`). `spawn_validated_subagents/5` spawns EVERY validated spec via `Dispatch.register_agent/7` — no queue, no spawn cap, each with a FRESH worktree. The ONLY bound is worktree CREATE-pipeline concurrency: `WorktreeManager`'s bounded FIFO admission queue capped at the app env `:max_concurrent_worktree_creation` (default 4 — NOT a config.toml schema key; detail: `agent_scheduler/CONTEXT.md`), which never limits live worktrees/agents. Slot pools gate LLM/tool CALLS; `State`'s `queue` is the resume FIFO for paused schedulers.
- `save_user_config/1` → `config.toml`; `save_credentials/1` → `credentials.toml`; both create the config dir if needed.
- Does NOT depend on `AgentScheduler` — runtime overrides are managed separately.
- **`Config.resolve/0` and `Schema.validate/1` never read model metadata or the LLMDB catalog** — pure map work (merge → atomize → migrate → validate); the ONLY catalog reach is `Schema.LLM.model_metadata/1` (`schema/CONTEXT.md` → "Model metadata seam"), so a memory/latency surprise attributed to config resolution is never catalog-related.
- Config dir follows XDG conventions via `EvoGit.Platform.os()`; all file reads use `case File.read/1` (non-crashing) with explicit `with`/`case` — no `try/rescue`.
- Reads go through `resolve/0,1` (the RAM snapshot); the only persisted writes are `save_user_config/1`, `save_credentials/1` and the partial `Config.update/1`, which delegate the actual write to `@doc false persist_user_config/1` / `save_credentials/1` and then refresh through `Watcher.notify_change/1`.
- **Model format**: `"provider:model"` string (preferred; resolves through LLMDB for cost tracking) OR map spec `%{provider: atom, id: string, base_url: string, extra: %{...}}` (ReqLLM-native). Map specs are normalized at resolve time (`normalize_model_map/1` inside `atomize_enum_values/1`): `:provider`+`:id` only → `"provider:id"`; with override keys they stay atomized maps. `[[llm.models]]` supports multiple endpoints per provider+model via per-profile `base_url`, and the provider atom determines the API key env var.
- `config_status/0` checks LLM model presence + at least one API key; GitHub username is **optional** (a missing username never appears in `:missing`/`:warnings` nor makes `:ok?` false).
- **Crash resilience (untrusted user config boundary)**: the `resolve/0` → `config_status/0` pipeline MUST NEVER raise on user content (incl. valid TOML with wrong value types, e.g. `llm = "string"`). `deep_merge/2` discards type-mismatched values (keeping defaults); `migrate_llm_models/1`, `atomize_enum_values/1`, `Schema.model_profiles/1` and `Schema.validate/1` guard non-map structures, and `Schema.validate/1` uses `safe_get_in` (not `get_in`) to avoid Access crashes. Bad config → `validation_errors`, never a crash — the user must always boot the app and reach the settings page.
- **Enum atomization gap for NEW top-level sections** — see "Adding a New Config Category" above; the `:string` workaround is UI-only, since the dashboard `SettingCard` renders `:string` as free text unless special-cased (`reasoning_effort` precedent).
- **Shared `@doc false` helpers (anti-duplication homes)**: `Schema.safe_get_in/2` — safe nested key-path lookup that NEVER raises on non-map intermediates (unlike `get_in`/Access); `EvoGit.Config.ensure_trailing_newline/1` — guarantees TOML content ends with a trailing newline before `File.write` (used by `save_credentials/1` and `version_state.ex`). Reuse rather than re-implement.

## Notes for Agents
The built-in defaults live in `EvoGit.Config.Schema.defaults/0` — a `deep_put` fold over every descriptor's `:default` — exposed as `EvoGit.Config.defaults/0`; there is NO `EvoGit.Config.Defaults` module.
`Schema.ReasoningEffort` is the ONE reasoning-effort ladder: `Normalization.atomize_enum_values/1`, `LLM`'s re-exports, `ProviderProfiles.Normalize.string_effort/1` and the wire alias table only consume its answer, so a new effort rule belongs there.
Tolerant key reads and key stringification belong to `EvoGit.Config.Keys`; a new caller delegates instead of re-implementing.
The `config.toml` write half is `@doc false Config.persist_user_config/1` (serialize → write → notify), called only by `save_user_config/1` (after validating) and `Settings.update/1` (after validating the normalized candidate).
