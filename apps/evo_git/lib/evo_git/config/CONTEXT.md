# Config — Unified Configuration Resolver

## Intent
`EvoGit.Config` — single source of truth for non-project configuration: merges built-in defaults with user config (`~/.config/genesis/config.toml`), loads API keys from `credentials.toml` into ReqLLM's key store, persists user config changes, and diagnoses configuration completeness.
Reads are served from ONE RAM snapshot per config directory (`EvoGit.Config.Cache`), refreshed only by a config-changed event raised by a save or by `EvoGit.Config.Watcher`'s file watch — never by a per-call file stat.

## Routing Table
- `./schema/` → config schema definitions (pure data: keys, types, defaults, validation) + provider/model generation-parameter extraction (`schema/CONTEXT.md`)
- `./schema/reasoning_effort.ex` → `EvoGit.Config.Schema.ReasoningEffort`: the ONE reasoning-effort ladder (`levels/0`, `options/0`, `allowed?/1`, `canonical/1`, `convert/1`), re-exported by `EvoGit.Config.Schema.LLM` as `reasoning_efforts/0` / `reasoning_effort_options/0` / `allowed?/1` / `canonical_reasoning_effort/1` / `convert_reasoning_effort/1`; every effort read, schema enum, selection rule and wire alias is built on it.
- `./keys.ex` → `EvoGit.Config.Keys`: the ONE tolerant key reader (`fetch/2`, `get/2,3` over atom- OR string-keyed maps, presence-based, never interning an atom) and the ONE recursive string-key transform (`stringify/2`, policies `:drop_nils` / `:model_tuples` / `:keyword_lists`); every tolerant read and string-key conversion in the config subtree delegates here.

## API Surface

### `EvoGit.Config`
- `resolve/0` — the merged map (defaults + user config) from the RAM snapshot: one `:persistent_term` lookup, no file I/O, no validation. Runtime overrides live in `AgentScheduler` state.
- `resolve/1` — the value at an atom key or atom list from the same snapshot; a MISSING path answers the schema default (possibly `nil`), never an error.
- `user_config/0` — the parsed `config.toml` from the snapshot (`%{}` if absent/unparseable); zero `File.stat`/`File.read` per call.
- `save_user_config/1` — validates, then REPLACES `config.toml` through `persist_user_config/1` (creating the config dir) and raises `Watcher.notify_change/1` so the snapshot refreshes synchronously: `:ok | {:error, reason}` (`reason` = `[ValidationError]` or a filesystem term).
- `save_credentials/1` — a SHALLOW per-key `Map.merge/2` into the flat `ENV_VAR_NAME = "value"` table (unknown keys preserved, `nil`/`""` written not deleted); `ReqLLM.put_key` runs BEFORE the write, then `Watcher.notify_change/1`: `:ok | {:error, reason}`.
- `config_status/0` — `%{missing, warnings, ok?, validation_errors}` (see "LLM Model Presence Decision" + "Direct API Admission"): `:llm_model` + `:api_key` (plus `:search_api_key` when search is enabled but unconfigured) checks, OAuth-aware; `resolved` and `validation_errors` come from ONE `Cache.get/0`; GitHub username is optional and NOT checked.
- `credentials/0` — the credentials map from the snapshot; `ReqLLM.put_key` side effects run only on a snapshot BUILD, never on a hit.
- `defaults/0` — `Schema.defaults/0`, a `deep_put` fold over every descriptor's `:default`; three values are CPU-thread-derived.
- `list_settings/0` — `Settings.list_settings/0` → `Schema.all_schemas/0`; `show/0,1` / `update/1` — the Settings facade (below).
- `config_path/0` / `config_dir/0` / `credentials_path/0` — `config.toml` / `EvoGit.Platform.config_dir("genesis")` / `credentials.toml`.
- `api_key_present?/1` — `true` when any catalog credential key is in ReqLLM's key store or is a non-empty value in the given credentials map.
- `tools_search_enabled?/0` — the provider-generic `[tools.search]` gate ("Web Search Provider Config").
- `lsp_enabled?/0` — the SINGLE gate for offering the `lsp` tool (`[lsp]` below): `true` only when `[:lsp]` is a map whose `:enabled` is `true`/`"true"` AND `:command` is a non-blank binary; never raises.
- `read_toml_file/2,3` / `ensure_trailing_newline/1` — `@doc false` shared helpers (see Constraints).

### Settings facade (`EvoGit.Config` → `settings.ex`)

`list_settings/0` returns `Schema.all_schemas/0` unchanged: ordered descriptors with atom `key_path`, `type`, `default`, `validation`, `category`, `sub_category`, `description`.
`show/0` IS `resolve/0` (`EvoGit.Config.show/0` and `Settings.show/0` delegate): snapshot defaults + persisted config, never live scheduler overrides or the credentials map.
`show/1` accepts an atom, dotted string or nonempty atom/string list, returns the value directly (section maps and `nil` included), traverses existing keys by comparison without creating atoms, and answers `{:error, :invalid_path}` / `{:error, {:unknown_setting, remaining_path}}`.
`update/1` accepts a non-struct map of nested sections and/or dotted/list keys, resolves destinations against schema paths only, and rejects unknown paths (`{:error, {:unknown_setting, path}}`), malformed sections (`{:error, {:invalid_section, path}}`), malformed paths (`{:error, :invalid_path}`) and colliding aliases (`{:error, :colliding_patch_paths}`); a non-map patch is `{:error, :invalid_patch}`, an empty patch is `:ok`, and empty section maps are refused rather than treated as deletion.
Map-valued settings merge recursively; list-valued settings (including provider/model inventories) replace the whole value; indices and account ids are not patch paths; leaf payload keys normalize to strings.
An update starts from the snapshot's parsed USER map, overlays only requested leaves, preserves unrelated/unknown keys, validates exactly ONCE over `Schema.validate(Normalization.resolve(candidate))` and hands that USER-only data to `Config.persist_user_config/1` (no second pass; validation defaults and derived legacy mirrors are never persisted).
Validation failures return the schema's `{:error, [ValidationError]}` unchanged with no write; serialization/filesystem errors pass through.
No facade operation changes credentials, reloads the scheduler or applies runtime overrides, and its read-modify-save is non-atomic like `save_user_config/1`.
`normalization.ex` owns the shared default merge, safe existing-atom conversion, enum/model normalization and legacy migration for BOTH snapshot loading and candidate validation; serialization and credential handling stay in `config.ex`.

### `EvoGit.Config.LLMCatalog` (provider/model shortcuts)
- Discovery: `providers/0` (Anthropic, OpenAI, ChatGPT Subscription/Codex, Google, DeepSeek, Alibaba, Z.ai, MiniMax, Moonshot AI, xAI, OpenRouter, OpenAI-Compatible), `provider_models/1`, `find_provider/1` (matches `provider_atoms`), `unknown_provider_help/0` (llmdb.xyz + ReqLLM docs links).
- Resolution: `resolve_model/2` → `"provider:model"` (backward-compat); `resolve_runtime_spec/3` (`:base_url`/`:variant`/`:extra`) → the CANONICAL `%{provider: atom, id: string}` ReqLLM `runtime_spec()` (+ optional `base_url`/`extra`), NOT a task `model_spec` — `resolve_model_spec/3` is its documented compatibility alias; `requires_base_url?/1` is `true` for `:openai_compatible` (default `false`).
- Auth: `auth_modes/1` (`[:api_key] | [:api_key, :oauth] | [:oauth]`, default `[:api_key]` for an unknown/API-key-only provider), `oauth_source/1` (`:chatgpt` for `:openai_codex`, `:claude_code` for `:anthropic`, else `nil`), `oauth_only?/1` (`:api_key` NOT in `auth_modes/1`), `supports_oauth?/1`.
- `known_credential_keys/0`: all unique credential key names — an entry contributes its `credential_key` ONLY when `:api_key` is in its `auth_modes` (so OAuth-only `:openai_codex` never makes `api_key_present?/1` report a key); VARIANT keys are unconditional.
**Model lists are derived data**: ChatGPT registrations supply the available model IDs/display names; other providers use shortcuts derived from the vendored LLMDB snapshot (`deps/llm_db/priv/llm_db/snapshot.json`).

### `EvoGit.Config.ProviderPresets` (built-in schedule presets)
`provider_presets.ex` — machine-readable copies of peak/off-peak policies a vendor publishes unambiguously, so the dashboard's provider-profile editor pre-fills an account's schedule in one click.
DATA ONLY: writes no config, touches no disk, starts no process, reads no clock, raises on nothing.
- `all/0` / `ids/0` (every preset / stable ids in display order), `get/1` (one preset by id; `nil` for an unknown id or non-binary input), `for_provider/1` (by atom `:deepseek` or case-/separator-insensitive STRING `"deepseek"`/`"ZAI-Coding-Plan"`; `[]` for nil or unknown).
- Envelope `%{id, label, provider, schedule, note}`; `schedule` is STRING-keyed so it merges into a string-keyed canonical account over `concurrency`, `peak_concurrency`, `peak_hours`, `timezone`, `off_peak_days`, `off_peak_holidays`, carries only the keys its provider uses, and is valid input for `EvoGit.PeakHours.validate_windows/1`, `validate_days/1` and `validate_holidays/1`. A published price/quota ratio maps conservatively onto slots (a rate that halves off-peak → `peak_concurrency` = half of `concurrency`) as an editable pre-fill, never a vendor-capacity claim.
- Two ship: `deepseek-standard` (`:deepseek`, UTC weekday windows, CN holidays + weekends off-peak) and `zai-glm-coding-plan` (`:zai_coding_plan`, weekday 14:00-18:00 Singapore time); sources and per-provider no-preset rationale: the module's moduledoc + `docs/llm-profiles.md` §7.

### `EvoGit.Config.VersionState` (upgrade detection)
Tracks the last-seen Genesis version in `version_state.toml` (config dir); `get_version/0` defaults to `"0.8.0"` when the file is absent/unparseable/a key is missing.
`current_version/0` reads `Application.spec(:evo_git, :vsn) |> to_string()`; `save_version/1` persists a version string (`save_version/0` persists `current_version/0`) answering `:ok | {:error, reason}`; `upgraded?/0` is recorded ≠ current; `record_current_version/0` persists `current_version/0` (call after showing the update log).

### `EvoGit.Platform` (cross-platform utilities)
`os/0` (`:linux` / `:macos` / `:windows` / `:unknown`); `config_dir/1` / `data_dir/1`; `shell/0` (honors `[tools] shell`; defaults `"bash"` on Linux/macOS, `"powershell"` on Windows); `shell_args/1` (`["-c", cmd]` or PowerShell `-EncodedCommand` args via `EvoGit.Powershell`); `systemd_available?/0` (Linux + systemd) / `nix_available?/0` (`nix` on PATH, Linux and macOS).

### `EvoGit.ProjectConfig` (per-repo genesis.toml)
`read/1` (parse `genesis.toml` from the repo root); `worktree_script/1,2` (init script for the current/given OS, with variant resolution); `write_worktree_script/2` (writes/merges `[worktree].script`, preserving existing sections/keys); `commands/1` (user dev-command shortcuts); `foreign_repos/1` (`ForeignRepo` structs).

### genesis.toml Structure
Three tables: `[worktree]` `script` (single fallback) with optional OS-specific variants as TOML dotted keys (`script.linux`/`script.macos`/`script.windows`; resolution `script.<current_os>` → `script` → `nil`), `[commands]` user shortcuts displayed in the dashboard and manually triggered (never auto-executed), and `[foreign_repos.<id>]` with `path` + `description` (+ `writable`/`base_sha`, see below).

### Foreign repos — schema & machine-binding gotchas
- **There is NO `[[repos]]`/repo-registry table in `config.toml`**: `Definitions.schemas/0` contains no repo/path key, so `Schema.validate/1` never validates a repository path and `Config.resolve/0` returns no repo list; the only repository configuration is per-repo `genesis.toml` `[foreign_repos.<id>]` (sibling `../project_config.ex`, deliberately NOT Ecto-validated) plus the per-task `:foreign_repos` opt.
- **Schema**: `path` REQUIRED (missing → entry dropped + a `Logger.warning`), `description` optional; the TOML table key IS the id; the key is `description`, NOT `name` (a `name` key is silently ignored), and there is no opt-in flag.
- **Committed to git**: `genesis.toml` is not git-ignored and Genesis Mode B auto-creates it, so absolute `[foreign_repos]` paths are committed and wrong on any other machine.
- **Path handling**: nothing validates absolute paths but they are semantically required — `ForeignRepo.new/3` only runs `EvoGit.Platform.safe_expand/1` (`~` → home, RELATIVE → the PROCESS CWD, no `$VAR` expansion) and nothing checks existence, so a missing path reaches the agent context and fails only at delegation (`build_subagent_phylo_node` matches `{:ok, foreign_head} = Git.rev_parse(...)`).
- **Task-opt merge**: `Runtime.Helpers.merge_foreign_repos/2` normalizes both lists and `Map.merge(toml_map, opt_map)` — the task opt wins per id and can OVERRIDE but never REMOVE a `genesis.toml` entry; the dashboard list lives only in socket assigns and `ResumeContext` does NOT carry `:foreign_repos` (only `MergeContext` does).

### Configuration Levels (priority low → high)
1. **Application defaults** — `Schema.defaults/0` (no model, no username); three values are DYNAMIC from `EvoGit.Platform.cpu_threads/0` (the tool cap = CPU thread count, both sandbox `:cpu_quota` strings `"#{cores * 100}%"`), shared by display, reset-to-default and resolution.
2. **User config** — `~/.config/genesis/config.toml` (XDG), parsed with `TomlElixir.decode/1`.
3. **Runtime overrides** — `AgentScheduler` state via `handle_call({:update_config, opts})`; concurrency/retry/turn values are config.toml-only, and model selection is task-level in task opts, never a scheduler override.

### config.toml Structure
Per-key types/defaults of all 112 descriptors (19 under `[sandbox]`) and canonical `[[llm.providers]]` / legacy `[[llm.models]]` syntax: `schema/CONTEXT.md` + `docs/llm-profiles.md`. Keys by table:
- `[scheduler]` `default_llm_max_concurrency` (per-account fallback 3), `max_tool_concurrency`, `agent_max_retries`, `max_agent_depth` (DEPTH only), `max_retries`, `max_turns` (sub-agents) / `max_turns_root` (root), `delegation_hint_threshold` / `read_delegation_hint_threshold` (0 disables), `max_tool_timeout` / `default_tool_timeout` (ms).
- `[llm]` `model` (`"provider:model"`), `compression_threshold_tokens`, `tool_result_pruning`, `tool_result_pruning_target_fraction`, `reasoning_effort`, `default_provider_profile`; `[user]` `github_username`; `[nix]` `enabled`/`flake_output`; `[appearance]` `accent_color`; `[sandbox]` `mode`/`backend`/`write_paths`; `[data]` `dir`; `[tmp]` `mode`/`path`; `[lsp]` `enabled`/`command`/`args`/`timeout`/`diagnostics_timeout`; `[tools.search]` `enabled`/`provider` + per-provider sections.

**`[data] dir`** relocates the whole runtime data dir (`tasks.sqlite`, `agent_state.sqlite`, logs, caches, `genesis-source`); `Platform.data_dir/0` returns it, and an invalid value (nil/empty/non-binary/relative) logs a `Logger.warning` + falls back to the OS+env default, never raising.
Precedence: TaskRegistry `opts[:data_dir]` test seam → app env `config :evo_git, :data_dir` (read only by the Store child spec, `TaskRegistry.init/1` and `mix migrate.store`; set only in `config/test.exs`) → TOML `[data] dir` → XDG default; per-repo `.genesis` artifacts stay repo-root-fixed, and `Config.resolve()` runs in `config/runtime.exs` + again in `Application.start/2` (via `EvoGit.Distribution.maybe_enable/0`) so the Store child spec sees it.
**`[tmp]`** per-task tmpdir `task_<id>`: `:system` (default) → `<system tmp>/genesis/task_<id>`, `:custom` → `<[tmp] path>/genesis/task_<id>` (empty/nil/non-absolute base falls back to system tmp), `:per_repo` → `<primary repo>/.genesis/tmp/task_<id>`; `mode` is an `:atom` atomized by the `[:tmp]` clause of `Normalization.atomize_enum_values/1`, and `[:tmp, :*]` keys carry `category: :data` (a new category would crash the dashboard's hardcoded Settings sidebar).
**`[lsp]`** — the `lsp` tool speaks LSP over stdio to `command` (`lexical start`), one disposable process per call, never installing a server; keys (all `category: :tools`): `enabled` (`false`), `command` (`nil`), `args` (`[]`), `timeout` (`30_000` ms whole-call budget), `diagnostics_timeout` (`10_000` ms). While `lsp_enabled?/0` is false the tool is NOT OFFERED AT ALL; once offered, an unconfigured call answers `Error: no language server configured — set [lsp] command in config.toml`; validation is warning-only at runtime (only `save_user_config/1` refuses).
**`[[llm.providers]]`** — each STRING-keyed account carries `id`, `provider`, optional `name`, shared auth/endpoint/concurrency/peak/generation settings, ordered `models` and optional `default_model`/`reasoning_efforts`/`default_reasoning_effort`; `[llm] default_provider_profile` selects one by id (absent → first account/model, unknown → resolution error), and a nested model is a model id string or a map with `model` (`id` an alias) plus optional generation/context/effort overrides (`Schema.provider_profiles/1`, `model_selections/1`, `resolve_selection/2` → `Schema.ProviderProfiles`; exact maps/precedence/errors: `schema/CONTEXT.md`).

**Legacy `[[llm.models]]`** (accepted while providers are absent/empty): `id` + `model` required, `concurrency`, `context_window` (`200_000`), `auth_mode` + `oauth_file`, `peak_concurrency`, `peak_hours`, `timezone`, `off_peak_days`, `off_peak_holidays` (syntax: `docs/llm-profiles.md`).
- `auth_mode` (`"api_key"` | `"oauth"`) is bookkeeping — the RUNTIME decision is `Schema.LLM.oauth_profile?/1`; `EctoValidation.validate_auth_mode/2` / `validate_oauth_file/2` validate them (absent `oauth_file` → `<config_dir>/auth.json`; NO global `[llm] oauth_file`).
- `context_window` is the compression window (stage-1 pruning target + derived threshold), never catalog metadata, read ONLY through `Schema.LLM.default_context_window/0`, `context_window/1` (invalid → warning + default, never raises) and `context_window_for/2`; `peak_concurrency` is NON-NEGATIVE (`0` = hard pause, never raised by the `default_llm_max_concurrency` floor).
- Peak windows/days/timezone/holidays, their parsers and their `%ValidationError{}` key paths live in `EvoGit.PeakHours` + `Schema.validate/1` (`schema/CONTEXT.md`); the load-bearing rules here: `off_peak_days` WINS over a window's `days`, `off_peak_holidays` (today only `"CN"`) treats 调休 make-up days as WORKING, both are ACCOUNT-level only and reach `state.model_profiles` untouched (`off_peak_holidays` via `ProviderProfiles.Normalize.@shared_keys`), and zone math always receives `config_time_zone_database/0` explicitly, never the ambient `Calendar`.
- `provider_options_for_model/1` returns `[store: false]` for a NATIVE OpenAI endpoint only (non-nil `:base_url`/`:extra` = OpenAI-COMPATIBLE → `[]`); `store` is Responses-API-only, an explicit profile `provider_options` wins key-wise, and an undeclared key RAISES at request time (`zai` accepts `[:thinking]` only). Generation parameters assemble at ONE choke point, `Schema.LLM.profile_generation_params/1` → `Schema.LLMConstraints.filter/3` (Z.AI/GLM table + llm_db metadata) — the ONLY path here reaching the LLMDB catalog (`model_metadata/1` uncached; at boot `EvoGit.CatalogWarmup` pays the cold load) — the Z.AI family encodes neither `top_k` nor `reasoning_effort` (OpenAI chat-completions DOES), and req_llm's unconditional `stream_options: %{include_usage: true}` is not suppressible here.

**`[sandbox] backend`**: `:atom`, default `:auto`, `[in: [:auto, :systemd, :bwrap]]` — `:auto` tries systemd-run → bwrap → no sandbox (macOS always sandbox-exec, bwrap Linux-only), `:systemd` forces systemd-run, `:bwrap` forces bubblewrap (filesystem isolation only, no sandbox when unavailable); `[sandbox.resources]`/`[sandbox.process]` are systemd-only and strings atomize via the `:sandbox` clause of `Normalization.atomize_enum_values/1`. Mode/backend come from the CONFIG SNAPSHOT, never scheduler state (`resolve/0` excludes runtime overrides), so `AgentScheduler.update_config(sandbox_mode: …)` only changes the REPORTED value while `sandbox_resources`/`sandbox_process_resources` DO apply live (Linux-only async `SandboxSlice.update_resources_async/1`); `get_config(:sandbox_backend)` reports `Platform.sandbox_backend/0`, and there is NO app-env sandbox switch (no `.ex` reads `Application.get_env(:evo_git, :sandbox)`).
**`[sandbox] write_paths`**: `:list_of_strings`, default `nil` — nil → platform defaults, set (incl. `[]`) → REPLACES the built-in list, malformed → validation error (never a crash); consumed ONCE by `EvoGit.Sandbox.Spec.build/2`, structural paths (cwd, tmp, nix store, repo `.git`) always appended, deny lists unaffected (`sandbox/CONTEXT.md`).

### credentials.toml Structure
A flat `ENV_VAR_NAME = "value"` table (`GOOGLE_API_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `ZAI_API_KEY`, `DEEPSEEK_API_KEY`, `GROQ_API_KEY`, `TAVILY_API_KEY`, …).
Keys load into ReqLLM's in-process key store on a snapshot build; one key matching the model provider is enough, and OAuth data never lives here.

## Adding a New Config Category / Schema (round-trip contract)

All schemas live in ONE flat list — `EvoGit.Config.Schema.Definitions.schemas/0` (NOT per-category modules); a schema is a plain map with 7 keys (`key_path`/`type`/`default`/`validation`/`category`/`sub_category`/`description`) — there is NO `%Schema{}` struct. `schemas_by_category/0` = `Enum.group_by(& &1.category)`; per-category order = definition order.
A NEW top-level category is additive for enumeration (append a map), `Schema.validate/1` (only checks defined keys; absent/nil pass; unknown keys are never rejected), `defaults/0` (derived from each `:default` via `deep_put`) and save-side serialization (`Keys.stringify/2` + `TomlElixir.encode` write any map; atom VALUES encode as quoted strings, nil values drop).
**The one non-additive gap is the READ/resolve path**: TOML has no atoms, and string enum values are atomized ONLY by `atomize_enum_values/1`, whose HARDCODED clauses cover `:sandbox` (`:mode`/`:backend`), `:git` (`:cow_worktree_creation`), `:llm` (model normalization + reasoning-effort canonicalization), `:tools` (search provider + per-provider `search_depth` via `search_providers/0`) and `[tmp]` (`:mode`). A NEW `:atom`-enum key needs a matching clause (or `:string` typing + atomization at the consumption point, like `[:llm, :reasoning_effort]`), else every snapshot build logs `must be an atom, got "blue"` and `config_status/0` reports it (non-fatal). The dashboard save path is unaffected: `SettingsUtils.parse_atom/2` (evo_dash) converts `:atom` form values against `validation[:in]` BEFORE `Schema.validate`.
Dashboard-side requirements for a new schema-driven category (evo_dash, not core): `category_display_name/1`, `category_icon/1`, `category_description/1` clauses in `EvoDashWeb.SettingsComponents.CategoryMetadata` (no catch-all — a missing clause is a FunctionClauseError) plus an entry in its `sort_categories/1` order list (missing = sorts last); `:agents`/`:remote_connections` are NOT core categories (the dashboard injects them as empty-schema pseudo-categories).

## Validation Path Typing
`Schema.key_path/0` describes atom-only schema descriptor paths; `Schema.ValidationError.key_path/0` describes error paths with atoms and non-negative list indexes (as emitted by composite profile validators) and is used by `Schema.ValidationError.t/0`.

## Validation Engine — Ecto-backed (architecture)

The validator beneath the DSL is **Ecto-backed, but Ecto is a VALIDATOR ONLY** — no `Ecto.Changeset` is ever built, `apply_changes` is never called, and the validated map passes through unchanged on `{:ok, config}` (unknown keys survive, model profiles stay plain maps).
- **`EctoTypes`** — eight nested strict `use Ecto.Type` modules (`PosInteger`, `NonNegInteger`, `Integer`, `String`, `ListOfStrings`, `Float`, `Atom`, `Boolean`), one per scalar DSL type, with `type_for/1`, `cast/2` and `valid?/2`; strict oracles (no numeric-string coercion, `""` meaningful, `:float` accepts int-or-float, `:atom` never casts strings) that must return FULLY-QUALIFIED module atoms (`__MODULE__.PosInteger`) or runtime dispatch fails.
- **`EctoValidation`** — `errors_for(key_path, type, validation, value) :: [%ValidationError{}]`, type errors FIRST then rule errors; all window/day/timezone/holiday math delegates to `EvoGit.PeakHours`; `provider_profile_shared_errors/2` covers `peak_concurrency`, `peak_hours`, `timezone`, `context_window`, `off_peak_days`, `off_peak_holidays`, `auth_mode` and `oauth_file` for BOTH canonical accounts and legacy profiles; `min`/`max`/`in` stay hand-written pure predicates (Ecto's `validate_number`/`validate_inclusion` are banned by design). Messages, `value`/`rule` terms, sub-path key_paths and error ordering are byte-pinned by `schema_test.exs` / `config_test.exs`.
- **Delegation**: `Schema.validate/1` walks the map with `safe_get_in/2` and calls `errors_for/4` per present value; scalars route through `EctoTypes.valid?/2`; `:model_spec`, `:model_profiles` and the optional profile fields recurse explicitly (multi-error, sub-path-aware).
- **Hand-written, and why**: Ecto has no TOML story and the pipeline runs on variable-depth, byte-pinned shapes, so `normalization.ex` keeps the transforms (`deep_merge`, PRE-Ecto `atomize_enum_values` — which also writes every reasoning-effort site in the ONE ladder's canonical spelling — and `migrate_llm_models`), `config.ex` keeps save serialization (`strip_flat_llm_fields`, `Keys.stringify/2`, `TomlElixir` inside `persist_user_config/1`), and `Schema.defaults/0` stays a `deep_put` fold (112 entries). `Schema.validate/1` runs once per snapshot build, validate-first in `save_user_config/1`, and once over the normalized candidate in `Settings.update/1`.
- **Ecto quirks**: numeric strings fail number types; `""` is never stripped; unknown keys survive; no `Ecto.Enum`, so a surviving bad enum string surfaces as a TYPE error (`rule == :atom`); `cast(_, nil)` → `{:ok, nil}` (nil ≡ absent, and absent keys are skipped before `errors_for/4`).
- **NOT Ecto-validated**: `LLMCatalog`, `VersionState`, `credentials.toml`, `ProjectConfig`/`genesis.toml` (lenient by design), `CustomAgents`/`agents.toml` (own CRUD validation), `RuntimeOpts` (raises `ArgumentError`). Only the `config.toml` DSL (112 `Definitions.schemas/0` entries, 14 LLM) is Ecto-validated.

## Direct API Admission and Persistence Boundaries
`EvoGit.Config` lives in `config.ex`; `Schema.all_schemas/0`, `schemas_by_category/0`, `defaults/0` and `validate/1` are real public APIs in `schema.ex`, and `Schema.effective_model_profiles/1` delegates to `Schema.LLM`.
The Assistant evaluator admits `Config.resolve/0,1`, `list_settings/0`, `show/0,1`, `user_config/0` and `config_path/0` in the read and write tiers through explicit exact-MFA lists (never namespace grants); only approved tier-2 write calls additionally admit `Config.update/1`, `save_user_config/1`, `AgentScheduler.RemoteAPI.reload_config/0` and `AgentScheduler.update_config/1` (contract: `../agent/tools/elixir_eval/CONTEXT.md`).
The model guards accidental self-corruption, not attackers: read/write stay Dune-interpreted and bounded, separately approved sudo is unrestricted native evaluation with no escalation path, and neither approval nor evaluation timeouts roll back committed side effects.
`resolve/0,1`, `show/0,1` and `user_config/0` return UNREDACTED data (node cookies, model `extra`/`provider_options`, endpoint credentials, arbitrary unknown TOML keys) and cover defaults + user configuration, never live scheduler overrides; `credentials/0` returns raw secrets and mutates the ReqLLM key store on a snapshot BUILD, and no output cap or error message redacts anything.
`config_status/0` returns `missing`, `warnings`, `ok?` and `validation_errors` from ONE `Cache.get/0` value, loads credentials into ReqLLM and may lazily import OAuth credentials; its nested health reads are not transactionally isolated from an in-flight `Cache.reload/1`, only a `Cache` store replaces the snapshot, and `:ok?` requires no missing critical settings AND an empty validation-error list.
Public visibility grants no evaluator access: `config_status/0`, `read_toml_file/2,3`, credential helpers and schema APIs stay unlisted — `read_toml_file/2,3` reads any supplied path despite `@doc false`, and `credential_key_to_reqllm_key/1` calls `String.to_atom/1` for arbitrary suffixed input.
`save_user_config/1` validates then REPLACES the whole file (never a patch/merge), reloads the snapshot synchronously and performs no scheduler reload or PubSub `"config"` broadcast on its own behalf; saving a resolved map materializes defaults. `@doc false persist_user_config/1` is the UNVALIDATED half (mkdir_p → mirror stripping → `Keys.stringify/2` → TOML encode → plain `File.write/2` → `Watcher.notify_change/1`), called ONLY by `save_user_config/1` and `Settings.update/1` after their own single validation pass; no atomic rename, lock, rollback or chmod, so both paths are non-atomic and can overwrite a concurrent writer.
Prefer approved `Config.update/1` for a targeted change, then explicitly call `AgentScheduler.RemoteAPI.reload_config/0` and inspect its result (persistence ≠ reload; boot-only settings need a restart); `AgentScheduler.update_config/1` stays a runtime-only mutation a reload or restart can overwrite.
`Schema.validate/1` walks atom-keyed schema paths, skips missing/nil/non-map intermediates and preserves unknown keys, so string-keyed top-level maps and malformed intermediate sections bypass validation; model-profile validation checks id/model, the atom-keyed provider-options container and optional peak/context/auth fields, but not per-profile concurrency or generation-parameter ranges. `save_credentials/1` merges without schema validation, mutates the ReqLLM key store BEFORE the filesystem write, and does not clear previously loaded keys on empty/nil replacements. Leaf-specific OAuth assembly, atom creation and catalog side effects: `schema/CONTEXT.md`.

## Config Caching

`EvoGit.Config.Cache` holds ONE RAM-resident snapshot per config directory in `:persistent_term` under `{EvoGit.Config.Cache, dir}`, shaped `%{dir, user_config, credentials, resolved, validation_errors, generation, fingerprint}`.
- **Reads are pure term lookups**: `Cache.get/0` resolves the directory AT CALL TIME through `EvoGit.Config.config_dir/0` (so the per-process `:config_dir_fun` seam keeps working); a hit performs zero `File.stat`/`File.read`, no merge and no `Schema.validate/1`.
- **One build, then lookups**: a miss calls `EvoGit.Config.build_snapshot/1` once and stores the result with `generation: 1` and NO broadcast; `build_snapshot/1` is the ONLY reader of `config.toml`/`credentials.toml` and runs the whole pipeline once (`defaults() |> deep_merge(atomize_keys(user_config)) |> atomize_enum_values() |> migrate_llm_models()`, then `Schema.validate/1`), keeping the ReqLLM `put_key/1` side effects and one "Config validation error at …" warning per error; an absent/unreadable file silently yields `%{}`, a TOML decode failure logs one warning and also yields `%{}`.
- **Fingerprint-driven reload**: the snapshot fingerprints the raw bytes of both files (`:erlang.phash2({config_bytes, credentials_bytes})`), so `Cache.reload/0,1` rebuilds and compares — unchanged contents return the previous snapshot with no store, no generation bump and no broadcast; a change costs exactly ONE `:persistent_term.put` with `generation + 1` plus a best-effort `{:config_reloaded, node(), dir, generation}` on PubSub topic `"config"` (skipped when `EvoGit.PubSub` is not running, never raised into the caller).
- **ONE total reload helper**: `Cache.reload_safely/0,1` is the total variant and the ONLY place in the codebase that wraps a snapshot reload in rescue/catch logging (naming the directory), answering `:error`; `reload/0,1` stays RAW, and `Watcher`'s private `refresh/1` delegates to `reload_safely/1` and normalizes its answer to `:ok | :error`, so the boot prime, the debounced file event, the save event and the fallback share ONE reload implementation.
- **Freshness is event-driven, never polled**: exactly two event sources — a successful save and a file event on the watched directory — converge on that single refresh handler, so `save_user_config/1` and `save_credentials/1` call `EvoGit.Config.Watcher.notify_change(dir)` after their successful write and before returning `:ok` and the settings page, the Welcome setup and the Assistant `elixir_eval` write tier read fresh values immediately (the `Cache.reload_safely/1` fallback covers no registered watcher).
- **`EvoGit.Config.Watcher`** is a GenServer started after `Phoenix.PubSub` and before `EvoGit.AgentScheduler` (NOT started when `Mix.env() == :test`): it watches the config dir through the vendored `file_system` dep, debounces ONE ~150 ms coalesced refresh per burst of `config.toml`/`credentials.toml` create/modify/remove/rename events, answers the save event's `handle_call({:config_changed, dir})` (the explicit requested dir, even when it watches another) with the refresh VERDICT so `notify_change/2` can take its own guarded fallback instead of reporting a save that never landed, and calls `EvoGit.CustomAgents.reload/0` for an `agents.toml` event.
- **Watcher degradation**: an unstartable backend (no `inotifywait`/`inotify-tools`, watch limits, missing dir) logs ONE warning and the GenServer stays alive unwatched (a stopped worker logs one), while saves and explicit reloads still refresh. `notify_change/1,2` is total and bounded — a `nil`, unregistered, dead or slow watcher falls back to the same guarded refresh and still answers `:ok` — and its `GenServer.call/3` guard is `catch :exit` ONLY, because a dead/restarting/slow watcher EXITS the caller rather than raising it, so a `rescue` arm would be dead code. The watcher is a convenience, never a requirement, and its `dir:`/`name:` options (default the module name, `nil` = unnamed) let tests run isolated instances.
- **Explicit reload re-reads disk**: `AgentScheduler.RemoteAPI.reload_config/0` FORCES `Cache.reload()` before `Config.resolve()` + `update_config/1`, so an explicit (including remote/SSH-triggered) reload observes current disk content; `read_toml_file/3` stays uncached (`@doc false`) for `project_config.ex` (`genesis.toml`), `remote_connections.ex` and `custom_agents.ex` (`agents.toml`), which keep their own freshness rules.
- `config_status/0` takes BOTH `resolved` and `validation_errors` from ONE `Cache.get()` value; errors are recomputed only by the next build. `defaults/0` stays uncached (a cheap `deep_put` fold whose three CPU-thread-derived values read `Platform.cpu_threads/0` at call time).
- **Boot prime & retention**: `Watcher.init/1` primes the snapshot at boot through `refresh/1` → `Cache.reload_safely/1` (total, so a raising build cannot crash-loop the watcher), a fingerprint-diffed no-op when `runtime.exs`'s early `resolve/0` already built it; in test the watcher is absent, so the first `Cache.get/0` builds in the calling process, and ONE snapshot per config dir lives in `:persistent_term` for the BEAM lifetime.
- ⚠️ The DOMINANT boot cost is not config resolution: `AgentScheduler.init` → `Schema.LLM.llm_generation_params/1` → `model_metadata/1` → `ReqLLM.model/1` triggers LLMDB's LAZY packaged-catalog load (`priv/llm_db/snapshot.json`, ~11.7 MB, ~10,100 models) retained in `:persistent_term`, and fires whenever ANY profile carries a `model` (a model-less fresh install pays nothing); config BEAM code is ~220 KB and no schema validation runs at compile time.

**Snapshot vs scheduler state:** the runtime config agents use is the `AgentScheduler` GenServer state (`RemoteAPI.get_config/0` reads it, `reload_config/0` forces a snapshot reload and replaces it, `get_config_status/0` reads the snapshot per call for truthful `:missing`/`:warnings`/`:ok?`); `save_user_config/1` refreshes the snapshot but does NOT apply scheduler runtime state (SettingsLive calls `reload_remote_config` but ignores its return, so a reloadable setting can stay unapplied until an explicit reload), and `RemoteConnections` does NOT auto-create an empty `remote_connections.toml` (the file appears only when a target is saved).

## Test Seam — per-process config dir (`:config_dir_fun`)

- `EvoGit.Platform.config_dir/1` consults the app-env seam `:evo_git, :config_dir_fun` at CALL time before XDG resolution; it accepts a zero-arity fun or `{m, f, a}` and the result must be a non-empty binary (garbage falls through, no `try/rescue`), and it is **default-inert**, so production paths are byte-identical to the XDG/APPDATA/Library resolution; `test/test_helper.exs` installs `{EvoGit.TestSupport.ConfigDir, :resolve, []}` (`test/support/config_dir.ex`).

The watcher is not started in test, so nothing asynchronous needs accounting for unless a test starts its own unnamed `EvoGit.Config.Watcher` (`name: nil`).

## LLM Shape and Normalization Boundaries
Canonical persisted inventory is `[[llm.providers]]`, selected by optional `[llm] default_provider_profile`: each account has one stable id, shared provider/auth/endpoint/concurrency/peak fields, generation defaults, an ordered `models` list whose nested maps may override generation/context/effort, and an ordered `reasoning_efforts` inventory; canonical maps are STRING-keyed while the surrounding resolved config uses atom schema keys, and `default_model` + optional `default_reasoning_effort` choose defaults without inventing an effort from inventory order.
`Normalization.atomize_enum_values/1` stringifies the whole providers subtree through `ProviderProfiles.Normalize.stringify/1` and canonicalizes its effort fields, preserving malformed entries for validation rather than dropping them; legacy `[[llm.models]]` and flat `[llm] model` stay accepted while no nonempty providers list exists.
`Schema.provider_profiles/1` exposes canonical string-keyed profiles and migrates legacy accounts one-for-one without combining equal provider/model/endpoint accounts or changing ids (the read projection never rewrites files); `Schema.model_selections/1` enumerates ordered model/effort inventory without credentials or metadata; `Schema.resolve_selection/2` (alias `resolve_model_spec/2`) resolves a nil/default, provider id or explicit provider/model/effort selection through `Schema.ProviderProfiles`; canonical providers outrank stale legacy fields, resolution materializes no derived `llm.models`/flat mirrors, saving with nonempty providers strips legacy `models`, flat generation/model fields and flat auth/provider-options mirrors, and legacy model keys normalize via existing atoms only with `@model_profile_extra_keys` pinning otherwise-unreferenced allowed atoms.
`Schema.validate/1` appends `ProviderProfileValidation.cross_field_errors/1`: `llm.default_provider_profile` must match an id in a nonempty canonical list (absent/nil valid, unknown id → `%ValidationError{key_path: [:llm, :default_provider_profile], rule: {:in, configured_ids}}`, blank `:string`, non-string the descriptor's type error), and `ProviderProfileValidation.default_model_errors/4` checks each raw `default_model` against its inventory (absent/nil and provider-qualified matches pass, unknown `{:in, ids}`, blank/non-string `:string` at `[:llm, :providers, index, :default_model]`); runtime normalization may repair those and treats a global `false` selector as absent, but raw validation still rejects them — so `config_status/0` reports `ok?: false` even when another account supplies a model, and those validation errors, not `missing == []`, are authoritative.
`Schema.effective_model_profiles/1` delegates to `Schema.LLM.effective_model_profiles/1` for scheduler boot, reload and catalog warm-up and never falls back to stale flat settings; presence/OAuth diagnostics use `Schema.model_profiles/1`'s runtime projection, and a canonical API-key account's explicit `api_key_env_var` check accepts a nonempty env string first, then a nonempty `credentials/0` string under that exact name — no catalog-key fallback, no borrowing a sibling account's key, never on the OAuth path.
The single effort ladder is `Schema.ReasoningEffort`: `levels/0` → `[:none, :minimal, :low, :medium, :high, :xhigh]`, `options/0` adds `:default` (send no effort), `allowed?/1` is the total acceptance predicate, `canonical/1` the total normalizer (`nil` when unrecognized) and `convert/1` its documented ECHO (unknown values unchanged so validation can report them). `max` is an accepted legacy ALIAS normalized to `xhigh` on read and NEVER an offered level: `Normalization.atomize_enum_values/1` canonicalizes every effort site (flat `[:llm, :reasoning_effort]`, each account's `reasoning_effort`/`default_reasoning_effort`/`reasoning_efforts[]` and every nested `models[*]` equivalent) and `ProviderProfiles.Normalize.string_effort/1` does the same when resolving a profile, while an UNKNOWN effort is left untouched. `[:llm, :reasoning_effort]` carries `validation: [in: <canonical option strings>]`, so `save_user_config/1` (validating the RAW map) rejects a literal `"max"`/`" High "` whereas the snapshot build and `Config.update/1` canonicalize first (`" High "` loads as `"high"`, a persisted `"max"` reads as `"xhigh"`). Generation/auth/reasoning assembly, selection error contracts and compatibility traps: `schema/CONTEXT.md`.

## LLM Model Presence Decision (config_status `:llm_model` gate)

`config_status/0` reports `missing: [:llm_model]` plus "LLM model is not configured. Set [llm] model in config.toml." when NO profile carries a usable model: the predicate runs over `Schema.model_profiles(resolved)` and counts a `:model` that is a non-empty binary OR a valid map spec (non-empty map with non-nil `:provider` and non-empty binary `:id`) — nil, `""` and `%{}` all fail, so a custom-endpoint map model (kept a map whenever `base_url`/other override keys are present) passes.
**Validation asymmetry**: per-profile `:model` validation treats `nil` as an error but accepts ANY binary, so `""` passes `Schema.validate` yet fails this gate, yielding `validation_errors: []` plus `missing: [:llm_model]`; the flat `[:llm, :model]` spec is equally lax. This gate is the ONLY place empty strings are rejected, and a missing `:llm` section / `llm.models = []` / flat nil model produce NO validation error — the warning is the sole signal, by design.
**Legacy mirror & disk shape**: with no canonical providers, `migrate_llm_models/1` mirrors flat `[llm] model` ONLY from the FIRST legacy profile — a nil model there leaves the flat field nil even when later profiles carry valid models (so `resolve([:llm, :model])` is nil), a first-profile `""` mirrors as `""`, and canonical configs synthesize no flat mirror.
`save_user_config/1` with a nonempty providers list strips legacy `llm.models` and the flat model/generation/auth/provider-options mirrors, while a legacy-only config keeps `[[llm.models]]` and loses flat generation/model fields only when that list is nonempty; `stringify_keys/1` drops nil values at every map level, so legacy nil-model profiles round-trip without a model key.

## OAuth / Subscription Auth
Subscription (OAuth) auth spends an existing ChatGPT/Claude login instead of a per-token API key; the ONLY credential store is the managed file — the profile's `oauth_file` (default `<config_dir>/auth.json`), ReqLLM-native JSON keyed by provider OAuth id (`"openai-codex"` / `"anthropic"`) with `type`/`access`/`refresh`/`expires`(ms)/`accountId` — and `credentials.toml` never carries OAuth data.
- **Path precedence** (`Schema.LLM.oauth_file_for/1`): `opts[:oauth_file]` → the profile's `oauth_file` → `EvoGit.Auth.default_oauth_file/0` (`<config_dir>/auth.json`, via `Platform.config_dir/1` so the `:config_dir_fun` seam applies); `~` is expanded, a broken managed-file read degrades to the default, and there is NO global `[llm] oauth_file` key.
- **Catalog metadata**: each `LLMCatalog` entry carries `auth_modes` (default `[:api_key]`), `oauth_source`, `provider_atoms` and `credential_key`; `:openai_codex` ("ChatGPT Subscription", `oauth_source: :chatgpt`) is OAuth-ONLY, `:anthropic` is `[:api_key, :oauth]` with `oauth_source: :claude_code`, every other provider is API-key only.
- **Which profiles are OAuth** (`Schema.LLM.oauth_profile?/1`): `auth_mode == :oauth` OR the provider is `oauth_only?/1` — so `model = "openai_codex:gpt-5.6-terra"` needs no `auth_mode`.
- **What reaches the request** (`profile_generation_params/1`): an OAuth profile gains `provider_options: [auth_mode: :oauth, oauth_file: <resolved>]`, overridden key-wise by explicit profile `provider_options` (three-level precedence: `schema/CONTEXT.md`).
- **Credentials**: Anthropic OAuth lazily imports the vendor login into its configured managed file; ChatGPT Subscription uses the protected Genesis SIWC registration identified by `siwc_account`, resolved at request time (existing `openai_codex` identifiers continue through the SIWC adapter).
- **Env fallback**: `CLAUDE_CODE_OAUTH_TOKEN` (then `ANTHROPIC_OAUTH_TOKEN`) for `:anthropic` when no file credential exists — OAuth without refresh, never written to disk; `:openai_codex` has no env fallback.
- **`known_credential_keys/0` filter**: an entry contributes its `credential_key` only when `:api_key` is in its `auth_modes`, so an OAuth-only provider never makes `api_key_present?/1` report a key; variant keys stay unconditional.
- **Health (`config_status/0`)**: the `:api_key` check passes when `api_key_present?(credentials())`, an API-key account's exact custom `api_key_env_var` resolves from the environment or persisted credentials, OR a configured OAuth profile's credential resolves (`Schema.LLM.oauth_credential_status/1`, which imports first and degrades to "not configured" on a broken file). With OAuth profiles the failure warning names the OAuth providers, their `login_instructions/1` text and the per-profile file(s) from `oauth_file_for/1` ("Managed OAuth file: <path>", plural when profiles differ; `default_oauth_file/0` when none resolves); without one it keeps "No API key found. Add keys to credentials.toml or configure via the settings page." A profile reporting `{:error, {:managed_file_unwritable, reason}}` (login exists, managed copy unwritable — read-only home, Nix sandbox) instead gets `EvoGit.Auth.managed_file_unwritable_remedy/2`'s actionable text and omits the misleading vendor-login instructions.
- **Onboarding**: the dashboard Welcome setup and Settings → LLM editor ask an OAuth-capable provider for an auth mode ("API key" vs "Subscription (OAuth)"), skip the question for an OAuth-only provider, never prompt for an API key on the OAuth path, and save `auth_mode = "oauth"` (the API-key path writes none and clears a stale one). `EvoGit.SystemCheck.do_llm_test/2` runs `ensure_profile_credentials/1` before its connection test and, on `{:managed_file_unwritable, reason}`, returns `{:error, "LLM connection test not run — <remedy>"}` WITHOUT issuing a request.

## Naming & Vocabulary (audit)

- **"Account" is spelled six ways**: the account id string is `profile["id"]` in `ProviderProfiles.provider_profiles/1`, `model_selections/1` and `resolve_selection/2` — the SAME value a task `model_spec` calls `provider_profile_id`; `[llm] default_provider_profile` is that id, `provider_profile` in a resolution result is the whole account MAP, and bare `profile` is a legacy `[[llm.models]]` entry or a model-selection row.
- **`model_spec` means two things**: a resolution result's ReqLLM-ready qualified string/endpoint-override map (dispatch stores it as `llm_model`) vs a task `model_spec` STRING-keyed identity (`provider_profile_id` + `model` + optional `reasoning_effort`).
- **`model_id` names a legacy profile/account id in `context_window_for/2`** but a model identifier in `LLMConstraints` and `ProviderProfiles.Normalize`; `model_profiles` names the raw legacy list AND a resolved atom-keyed runtime projection (`Schema.LLM.model_profiles/1`; the schema TYPE `:model_profiles` is the former only); `id` carries three namespaces (account id, inventory model id, model id inside the ReqLLM spec) plus `LLMCatalog`'s entry id.
- **`show/0` IS `resolve/0`** and `show/1` only adds path forms + `{:error, :invalid_path | {:unknown_setting, path}}`; **`save_*` is REPLACE in one function and MERGE in the other** (`save_user_config/1` replaces via `persist_user_config/1`, `save_credentials/1` shallowly merges, `Config.update/1` → `Settings.update/1` patches partially); both `canonical_providers?/1` implementations (public `Normalization`, private `LLM`) read through `Keys.get/2` presence semantics and agree.

## Constraints
- **No config key caps TOTAL agents / live worktrees / subagent spawn breadth.** `Definitions.schemas/0` has NO `max_agents`/`max_worktrees`/`max_subagents`/breadth key; `[:scheduler, :max_agent_depth]` (default 8) is the ONLY structural limit and bounds recursion DEPTH only (`Subagents.validate_subagent_depth/3`). `spawn_validated_subagents/5` spawns EVERY validated spec via `Dispatch.register_agent/7` — no queue, no spawn cap, each with a FRESH worktree. The ONLY bound is worktree CREATE-pipeline concurrency: `WorktreeManager`'s bounded FIFO admission queue capped at the app env `:max_concurrent_worktree_creation` (default 4 — NOT a config.toml schema key; detail: `agent_scheduler/CONTEXT.md`), which never limits live worktrees/agents. Slot pools gate LLM/tool CALLS; `State`'s `queue` is the resume FIFO for paused schedulers.
- Does NOT depend on `AgentScheduler` — runtime overrides are managed separately.
- **`Config.resolve/0` and `Schema.validate/1` never read model metadata or the LLMDB catalog** — pure map work (merge → atomize → migrate → validate); the ONLY catalog reach is `Schema.LLM.model_metadata/1` (`schema/CONTEXT.md` → "Model metadata seam"), so a memory/latency surprise attributed to config resolution is never catalog-related.
- Config dir follows XDG conventions via `EvoGit.Platform.os()`; all file reads use `case File.read/1` (non-crashing) with explicit `with`/`case` — no `try/rescue`.
- Reads go through the RAM snapshot; the only persisted writes are `save_user_config/1`, `save_credentials/1` and the partial `Config.update/1`, all refreshing through `Watcher.notify_change/1`.
- **Model format**: `"provider:model"` string (preferred; resolves through LLMDB for cost tracking) OR map spec `%{provider: atom, id: string, base_url: string, extra: %{...}}` (ReqLLM-native). Map specs are normalized at resolve time (`normalize_model_map/1` inside `atomize_enum_values/1`): `:provider`+`:id` only → `"provider:id"`; with override keys they stay atomized maps. `[[llm.models]]` supports multiple endpoints per provider+model via per-profile `base_url`, and the provider atom determines the API key env var.
- `config_status/0` checks LLM model presence + at least one API key; GitHub username is **optional** (a missing username never appears in `:missing`/`:warnings` nor makes `:ok?` false).
- **Crash resilience (untrusted user config boundary)**: the `resolve/0` → `config_status/0` pipeline MUST NEVER raise on user content (incl. valid TOML with wrong value types, e.g. `llm = "string"`). `deep_merge/2` discards type-mismatched values (keeping defaults); `migrate_llm_models/1`, `atomize_enum_values/1`, `Schema.model_profiles/1` and `Schema.validate/1` guard non-map structures, and `Schema.validate/1` uses `safe_get_in` (not `get_in`) to avoid Access crashes. Bad config → `validation_errors`, never a crash — the user must always boot the app and reach the settings page.
- **Shared `@doc false` helpers (anti-duplication homes)**: `Schema.safe_get_in/2` — safe nested key-path lookup that NEVER raises on non-map intermediates (unlike `get_in`/Access); `EvoGit.Config.ensure_trailing_newline/1` — guarantees TOML content ends with a trailing newline before `File.write` (used by `save_credentials/1` and `version_state.ex`). Reuse rather than re-implement.

## Notes for Agents
The built-in defaults live in `EvoGit.Config.Schema.defaults/0` — a `deep_put` fold over every descriptor's `:default` — exposed as `EvoGit.Config.defaults/0`; there is NO `EvoGit.Config.Defaults` module.
Routing homes: the ONE reasoning-effort ladder is `Schema.ReasoningEffort`; tolerant key reads and key stringification are `EvoGit.Config.Keys`; the `config.toml` write half is `@doc false Config.persist_user_config/1` (called only by `save_user_config/1` and `Settings.update/1`).
