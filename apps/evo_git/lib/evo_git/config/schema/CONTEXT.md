# Config Schema

## Intent
Configuration schema definitions — pure data describing every config key, its type, default, and validation rules — plus the provider/model-aware extraction of LLM generation parameters from model profiles.

## Routing Table
None — leaf directory.

## API Surface

### `EvoGit.Config.Schema.Definitions`
Returns all config key schemas as a flat list of maps. Each schema: `key_path` (dotted atom path, e.g. `:scheduler.agent_workers`), `type`, `default`, `validation`, `category`, `sub_category`, `description`. Covers scheduler, sandbox, git, truncation, and more.
The five `[lsp]` keys (`:enabled`, `:command`, `:args`, `:timeout`, `:diagnostics_timeout`) describe the `lsp` tool's configuration; the `lsp` tool is offered to agents only while `EvoGit.Config.lsp_enabled?/0` is true (`[:lsp, :enabled] = true` plus a non-empty `[:lsp, :command]`), so the default `enabled = false` keeps it out of every agent's tool list.
`[:llm, :oauth_file]` (a `:string`, default `nil`) is the GLOBAL managed-OAuth-file override — `nil` means `<config_dir>/auth.json` — and the `[:llm, :models]` description documents the per-profile `auth_mode` / `oauth_file` keys.

### `EvoGit.Config.Schema.LLM`
Extracts LLM generation parameters from config/model profiles. `llm_generation_params/1` accepts a model profile map or a resolved config map and returns a keyword list suitable for `ReqLLM`.

`profile_generation_params/1` is the **single choke point** for every parameter consumer (scheduler state, dispatch, agent state, and both the legacy-flat and explicit-profile path — the legacy path builds a profile via `build_legacy_default_profile/1` which is then read through this same function). It assembles `temperature, max_tokens, reasoning_effort, top_p, top_k, frequency_penalty, presence_penalty` plus `provider_options`, then pipes the result through `EvoGit.Config.Schema.LLMConstraints.filter/3` exactly once. Provider-aware filtering must NOT be duplicated at the other parameter-assembly sites.

`provider_from_model/1` derives the provider atom from the three supported spec shapes — string `"provider:id"`, map `%{provider: ..., id: ...}`, tuple `{provider, opts}` — and `nil` for anything unrecognized.

`context_window/1` resolves a profile's context window (tokens): the optional `context_window` profile key (atom- or string-keyed) when it is a positive integer, else `default_context_window/0` (`200_000`) — an invalid value logs a `Logger.warning` and falls back, never raises.
`context_window_for/2` (`config` map, `model_id`) reuses `get_model_profile/2` and returns the same value, defaulting on `{:error, :not_found}`.
Context-compression consumers use this ONE resolver instead of model-catalog metadata.

`provider_options_for_model/1` returns the OpenAI-only default (`[store: false]`, from `default_provider_options/0`) **only for a genuine NATIVE OpenAI endpoint**: provider `:openai` AND no custom endpoint override. A model spec MAP carrying a non-nil `:base_url` or `:extra` is an OpenAI-**compatible** third-party endpoint (the dashboard's "OpenAI-Compatible API" catalog entry maps to provider `:openai` with a custom `base_url`) and gets `[]` — such endpoints do not implement the OpenAI Responses-API `store` option. The check is a presence check, so even an empty `extra` map counts as an override.
For an OAuth-ONLY provider (`EvoGit.Config.LLMCatalog.oauth_only?/1` — today `:openai_codex`) it returns the OAuth defaults (`[auth_mode: :oauth, oauth_file: <resolved>]`, from `oauth_provider_options/1`) instead. `:openai_codex` is a DISTINCT provider atom upstream of the OpenAI driver, so it is NEVER given `store: false`: that field exists only in the native OpenAI provider schema and a provider-undeclared `provider_options` key raises at request time.

**`provider_options` precedence is THREE levels**: a profile's explicit `provider_options` (map or keyword list) is a PARTIAL override whose own keys win, over the profile-derived OAuth defaults (empty for an API-key profile), over model-derived options from `provider_options_for_model/1`. The merge is key-wise (`merge_options/2`: override keys win, defaults fill the gaps), so an explicit `oauth_file:` inside the override is honoured while the surviving OAuth default `auth_mode: :oauth` stays; an EMPTY result omits the `:provider_options` key entirely (`maybe_provider_options/2`). A profile that sets `provider_options` REPLACES the model-derived branch wholesale (it is not consulted), so a user override never silently inherits `store: false`.
**OAuth auto-detection** (`oauth_profile?/1`): a profile is OAuth when its `auth_mode` normalizes to `:oauth` (`"oauth"` or `:oauth`) OR its model's provider is OAuth-only — so `model = "openai_codex:gpt-5.6-terra"` means subscription auth with no `auth_mode` at all; anything else (including absent) is the API-key default.
The vendor-CLI credential import runs at ASSEMBLY time inside the OAuth branch only (`oauth_provider_options/1`), so an api_key profile stays allocation-identical and never touches `auth.json`.
Public OAuth helpers: `ensure_profile_credentials/1` (profile → `:ok | {:error, reason}`) and `oauth_credential_status/1` (profile → `{:ok, %{expires: ms | nil, account_id: String.t() | nil}} | {:error, :no_credentials | :invalid_credentials | :expired_credentials} | {:error, {:managed_file_unwritable, posix_reason}}`) — both resolve the provider from the profile's `:model`, the managed file via the profile's `oauth_file` → `[llm] oauth_file` → `<config_dir>/auth.json` (`EvoGit.Auth.oauth_file/1`), both are fault-isolated, and both accept a bare `%{model: model}` spec. `oauth_credential_status/1` imports first and threads a write-side import failure into `EvoGit.Auth.credential_status/2` as its `managed_file_error:` opt, so "the login exists but the managed copy cannot be written" is `{:error, {:managed_file_unwritable, posix_reason}}` rather than `:no_credentials` (`managed_file_error/1` extracts it from `ensure_credentials/1`).
`oauth_file_for/1` (public) returns the resolved managed OAuth path for a profile — the ONE way callers render that path in a message.
`build_legacy_default_profile/1` threads the flat `[llm] auth_mode` into the synthesized `"default"` profile (a flat `[llm] oauth_file` reaches it through `EvoGit.Auth.oauth_file/1`'s own fallback), so an OAuth subscription configured flat-style hits the same choke point without a `[[llm.models]]` table.
Login/credential lookup normalizes `:openai` to `:openai_codex` via `EvoGit.Auth.normalize_provider/1`; the REQUEST always uses the real provider atom from the model spec.

### `EvoGit.Config.Schema.LLMConstraints`
The declarative, pure, never-raising filter for the generation-parameter keyword list. Holds two constraint sources:

1. **`@constraint_tables`** — one map per provider/model family, each carrying its own `:provenance` code comment (the documented source every rule comes from). Seeded with `:zai_glm` (Z.AI GLM Chat-Completions API reference): `:unsupported_params` = `top_k`/`frequency_penalty`/`presence_penalty` (not documented by Z.AI); `:max_temperature` = `1.0` (Z.AI documents `[0.0, 1.0]` while Genesis allows up to 2.0); `:reasoning_effort` = full OpenAI set, with `by_model` overriding GLM-5.3 / GLM-5.3-FLASH to `low|high|max` only; `:thinking_disable_unsupported` records that GLM-5.3 rejects `thinking.type = "disabled"` (informational — Genesis never emits a `thinking` parameter, which is only reachable through the user `provider_options` override). Adding a provider = adding one table map.
2. **Model metadata** — `%{limits: map(), capabilities: map()}`: `limits.output` bounds `max_tokens`; `capabilities.reasoning.enabled` gates `reasoning_effort`; `capabilities.tools.enabled` gates `tools`/`tool_choice`.

Public API: `filter(params, model, metadata)` (guard-clause safe for non-list/non-keyword input, preserves keyword ORDER of survivors, never raises), `constraints_for(model)` (matching table entries), `normalize_metadata/1` (`@doc false`; collapses a metadata map or raw catalog-like struct to the documented contract, `nil` when unusable — shared with `LLM.model_metadata/1`).

**Model matching** is provider-atom based (`:zai`/`:zai_coder`/`:zai_coding_plan`) OR model-id based (case-insensitive `glm` substring, which also covers OpenRouter-style ids such as `z-ai/glm-5.3-flash` served under a non-Z.AI provider atom). The heuristic and its limits are documented in the table entry: GLM weights served under an id without `glm` are not matched, and an unrelated id containing `glm` is matched conservatively.

**Degradation contract**: a violation is always resolved by OMITTING the parameter (never clamped, never mapped — no documented value mapping exists for the affected families) plus a `Logger.warning` naming the parameter, the model and the reason. A `nil`/empty metadata map, an unknown or unparseable model spec, or a model the catalog does not know leaves the parameter list **byte-identical** — nothing is dropped merely because metadata is missing. Unknown providers/models are left completely untouched.

### Model metadata seam (`LLM.model_metadata/1`, app env `:llm_model_metadata_fun`)
`LLM.model_metadata/1` (`@doc false` public, returns `%{limits: map(), capabilities: map()} | nil`) reads the app-env seam `:llm_model_metadata_fun` — a 1-arity fun over the model spec, read AT CALL TIME — and falls back to a real ReqLLM model-catalog lookup (`ReqLLM.model/1`, already a declared dependency) when unset. The lookup is deliberately NON-raising (`rescue` + `catch` → `Logger.warning` + `nil`), so it degrades to "no metadata" (table rules still apply) rather than breaking a boot or a spawn.
**The catalog fallback DOES load the catalog, in the CALLING process**: `catalog_lookup/2` → `ReqLLM.model/1` → `LLMDB.Spec.resolve/2` → `LLMDB.Catalog.resolve_model/2` → `Catalog.ensure_loaded!/0` (`deps/llm_db/lib/llm_db/catalog.ex:107-132`); on the first model lookup of a BEAM that means the whole `LLMDB` snapshot load (`Jason.decode` of `deps/llm_db/priv/llm_db/snapshot.json`, ~11.7 MB / 239 providers / 10,100 models, a canonicalizing digest over the whole catalog, and the `models_by_key`/`aliases_by_key`/`providers_by_id`/`__llm_db_resolutions_by_model_id__`/`__llm_db_model_id_prefixes__`/… indexes) plus a `:persistent_term.put` — seconds of CPU and tens of MB of transient heap in the process that happens to call first.
After the first load the term is READ with `:persistent_term.get(:llm_db_store, nil)` (`catalog.ex:64`), which does NOT copy it into the reader's heap (OTP `persistent_term.erl`: a copy + global GC happens only on `put`/`erase`).
There is NO cache or memoization in front of `model_metadata/1` (no ETS, `:persistent_term` or process-dictionary entry) — every call re-runs the resolve against the loaded catalog.
Callers (all of them): boot — `EvoGit.CatalogWarmup.warm_up/1` (a throwaway process started immediately before `AgentScheduler`, so it takes the cold-catalog load with it when it dies), then `AgentScheduler.init/1` (`agent_scheduler.ex:577-581`) and `State.from_model_profiles/2` (`agent_scheduler/state.ex:182`) against the now-warm catalog; per agent spawn — `Dispatch.resolve_model_for_agent/2` (`agent_scheduler/dispatch.ex:357`); per compression check — `Agent.Compression.Threshold.output_limit/1` (`agent/compression/threshold.ex:240`).
**Keep it cheap** — it runs per agent spawn (and per profile read / per-turn compression check), and whichever process calls it FIRST on a cold BEAM carries the whole snapshot load in its own heap: at boot that must be `EvoGit.CatalogWarmup`'s short-lived process, never a long-lived one (an embedded BEAM does not fullsweep it away — measured: 92.6 MB retained by the scheduler before the warm-up existed, 28.8-66.3 KB after; see `../agent_scheduler/CONTEXT.md`); cache per-model `%{limits, capabilities}` (ETS/`:persistent_term`) instead of re-resolving.

Tests inject stub metadata through the seam, so no catalog is needed.

## Assistant Evaluation / Configuration Boundaries
The evaluator's explicit MFA/tier lists, not namespace grants or an API's public visibility, determine admission; the authoritative policy and full inventory live in `../../agent/tools/elixir_eval/CONTEXT.md`.
`EvoGit.Config.resolve/0,1` are admitted direct reads in read/write tiers, while `EvoGit.Config.save_user_config/1`, `EvoGit.AgentScheduler.RemoteAPI.reload_config/0` and `EvoGit.AgentScheduler.update_config/1` are admitted only in write tier.
Write tier requires exact-code tier-2 manual approval; unrestricted native sudo requires its separate explicit approval and is not a security sandbox, and denied operations never auto-escalate.
These boundaries guard against accidental Assistant self-corruption, not a malicious attacker with unrestricted sudo authority.
Direct reads retain actual nested values, potentially including secrets, and are neither facade projections nor secret-safe; output caps are not redaction.
`Config.resolve/0,1` reads normalized defaults plus user configuration, not live scheduler overrides; direct `AgentScheduler.update_config/1` changes runtime settings without persisting them.
`Config.save_user_config/1` replaces the whole file rather than patching and does not automatically reload the scheduler.
For persistent changes, resolve the full configuration, update only intended keys and save the full map in the same approved evaluation, then explicitly call `RemoteAPI.reload_config/0` after save success and inspect its result.
This preserves unrelated keys but materializes resolved defaults, and read-modify-save is not atomic, so avoid concurrent edits; boot-only settings still require restart.
Schema/defaults APIs and this node's `Definitions`, `LLM` and `LLMConstraints` functions remain unlisted, not implicitly admitted through Config reads or writes.
`Definitions` describes metadata without user values, whereas `LLM` helpers can return unredacted supplied profiles, create provider atoms, import OAuth credentials or load catalog metadata, and constraint filtering can log model specs containing secrets.
`context_window_for/2` can raise on a non-map model-list entry through `get_model_profile/2`; schema validation and helper purity claims are not evaluator authorization or redaction guarantees.

## Constraints
- `Definitions` describes defaults without reading user configuration, but `LLM` is not a pure read boundary: OAuth option assembly/status can import credentials into a caller-selected managed file, metadata resolution can load the catalog, and provider parsing can create atoms.
- Schema definitions are the single source of truth for all config keys.
- The parameter filter never raises on user config and never guesses: a constraint is only applied where there is documented provenance or actual model metadata.

## Notes for Agents
- **`Definitions.schemas/0` yields 105 entries** = 74 hand-written schema maps (57 in the first list, 17 in the post-`search_provider_schema_maps()` list) + 31 generated search-provider maps (5 providers × 6 keys + Perplexity's extra `:model`).
- **Per-category counts at HEAD** (mechanically verifiable with `rg -o 'category: :[a-z_]+' definitions.ex` minus the `sub_category:` lines, plus the 31 generated maps): scheduler 11, llm 13, user 1, sandbox 19 (sub_category `:resources` 4 / `:process` 4 / `:linux` 8), truncation 4, task_history 2, nix 2, git 2, server 2, node 6, appearance 1, data 3, **tools 39** (3 hand-written top-level `[:tools, …]` maps: `:shell`, `:search, :enabled`, `:search, :provider`; 5 `[lsp]` maps; 31 generated `[:tools, :search, <provider>, …]` maps).
- **Count pins in `test/evo_git/config/schema_test.exs`**: `"has exactly 105 schemas"` (`assert length(Schema.all_schemas()) == 105`), `assert length(grouped[:llm]) == 13` and `assert length(grouped[:tools]) == 39` in the per-category test — these ARE the HEAD totals. Any new schema entry must update the TOTAL pin and its own category pin (105 + N, its category + N); leaving a pin behind keeps the suite red.
- **No key caps total agents/worktrees and there is no `max_llm_max_concurrency` key** — the only per-model LLM cap is `[[llm.models]].concurrency` (resolved default 3 via `AgentScheduler.State.from_model_profiles/2`'s `Map.get(profile, :concurrency, 3)`), with `[:scheduler, :default_llm_max_concurrency]` (3) as the floor/fallback.
- **A model profile has NO retry or timeout fields**: the accepted per-profile keys are `id`, `model`, `concurrency`, `context_window`, `auth_mode` (`"api_key"` | `"oauth"`, default `"api_key"`), `oauth_file` (per-profile managed-credential path), the 7 generation params (`temperature`, `max_tokens`, `reasoning_effort`, `top_p`, `top_k`, `frequency_penalty`, `presence_penalty`), `provider_options`, and the 4 peak fields (`peak_concurrency`, `peak_hours`, `timezone`, `off_peak_days`) — nothing else is validated nor extracted. Retries are global (`[:scheduler, :max_retries]` 15, `[:scheduler, :agent_max_retries]` 3).
- **LLM HTTP timeouts are NOT config.toml schema keys**: `receive_timeout` 600_000, `metadata_timeout` 600_000 and `thinking_timeout` 1_000_000 live in the ReqLLM application env in the root `config/config.exs` (`config :req_llm, ...`), so they are not user-editable via the settings page or `[[llm.models]]`.
- **`EctoValidation.validate_model_profile/2` is lax about `:model`**: `nil` is an error but ANY binary (including `""`) passes; the `config_status` has_model gate is the only place an empty-string model is rejected.
- **`profile_generation_params/1` reads ATOM keys only** and emits scalar generation keys ONLY for non-nil values (`llm.ex:543–558`), so a minimal profile (`id`/`model`/`concurrency`) adds no scalar generation overrides but may still emit native-OpenAI or OAuth provider defaults (`llm.ex:700–713`).
A STRING-keyed profile yields `[]`; `llm_generation_params/1` also dispatches only on ATOM keys `:id`/`:llm` (`llm.ex:75–90`).
Profiles reaching this code are atom-keyed because `EvoGit.Config` normalizes them (`normalize_profile_keys/1`); the dashboard writes no generation params unless the user typed them.
- Scheduler concurrency schemas both require `:pos_integer` with `[min: 1]`; `default_llm_max_concurrency` defaults to 3 and `max_tool_concurrency` defaults dynamically to `EvoGit.Platform.cpu_threads()` (`definitions.ex:36–64`).
The `llm.models` schema defaults to `[]`, and its description documents per-profile concurrency default 3 (`definitions.ex:275–283`); the actual profile validator and TOML normalization/migration live in the parent config node.
`LLM.build_legacy_default_profile/1` synthesizes an atom-keyed `"default"` profile with concurrency from the atom-keyed scheduler section (fallback 3), plus non-nil flat generation fields and auth_mode (`llm.ex:257–276`).
- **`provider_options_for_model/1` is native-OpenAI or OAuth-only by design** (`[store: false]` for a native `:openai` endpoint, the OAuth defaults for an OAuth-only provider such as `:openai_codex`, `[]` otherwise — see the `API Surface` entry above for what makes an endpoint non-native) and must NEVER emit `store: false` for `:openai_codex`: that field exists only in the native OpenAI provider schema, and a provider-undeclared `provider_options` key raises at request time. Passing `provider_options: [store: false]` to ANY other non-OpenAI provider raises the same way — req_llm validates `provider_options` against the provider schema (`zai`/`zai_coder`/`zai_coding_plan` accept `[:thinking]` only → `NimbleOptions.ValidationError: unknown options [:store]`). Verified against the vendored `deps/req_llm` (`zai`/`zai_coder`/`zai_coding_plan` `provider_schema/0` accepts only `:thinking`, and `provider_options` is validated against it in `ReqLLM.Provider.Options.process!/4`).
- **Not every extraction key reaches the wire.** `top_k` and `reasoning_effort` are accepted ReqLLM generation options but are not encoded by the Z.AI family (`ReqLLM.Providers.Zai.Shared.add_basic_options/2` emits only `temperature`, `top_p`, `frequency_penalty`, `presence_penalty`, `user`, `seed`, `stop`); `reasoning_effort` is telemetry-only. `temperature`/`top_p`/`frequency_penalty`/`presence_penalty` DO reach the body when non-nil. This module can therefore not "leak" provider-unsupported parameter names of its own — except via an explicit profile `provider_options` map, which is passed through verbatim (`maybe_provider_options/2`).
- `definitions.ex` is ~810 lines — legitimate (comprehensive data table of all config keys); do not split it.
- In `definitions.ex`, the search-provider schemas (`[:tools, :search, <provider>, ...]`) are NOT hand-written literals — they are generated from the data-driven `@search_provider_defs` list (one `%{name:, label:, credential_key:, base_url:, optional model:}` map per search provider: `:tavily`/`:perplexity`/`:exa`/`:bing`/`:brave`), each entry expanded by `search_provider_schema_maps/1` into the repeated per-key schema maps (33 search schema maps in `schemas/0` in total incl. the fixed `:enabled`/`:provider`). Adding or extending a search provider means editing that list, not hand-writing repeated provider maps. `@search_providers`/`search_providers/0` remains the source of truth for the provider-ID list used by the `:provider` schema `in:` validation.
- `EvoGit.Config.Schema` (validate + defaults + typespecs) lives in the PARENT node file `../schema.ex`; the validation ENGINE (former `type_errors/3`/`rule_errors/3` privates) now lives in the parent node's `../ecto_validation.ex` (`EctoValidation.errors_for/4`) with scalar type decisions routed through the strict custom Ecto types in `../ecto_types.ex` (`EctoTypes`). Definitions here, the engine there and the `@type schema_type` union in `schema.ex` must stay in sync. **Adding a new validation type requires three touch points** (see the "Validation Engine — Ecto-backed" section of the parent `../CONTEXT.md`): (1) a definition entry here, (2) a new nested strict `use Ecto.Type` module in `ecto_types.ex` + a `type_for/1` clause (returning the fully-qualified `__MODULE__.X` atom) + a `@type scalar_type` union entry, and (3) a `type_errors/2,3`-style clause in `ecto_validation.ex` plus the `@type schema_type` union entry in `schema.ex`. `min`/`max`/`in` rules need no type-module — they are pure predicates in `EctoValidation.rule_errors/3`.
- `llm_constraints.ex` deliberately does NOT depend on any catalog being loadable: the Z.AI/GLM table rules must stay effective with zero metadata. Do not move table rules behind a metadata check.
