# Config Schema

## Intent
Configuration schema definitions — pure data describing every config key, its type, default, and validation rules — plus the provider/model-aware extraction of LLM generation parameters from model profiles.

## Routing Table
None — leaf directory.

## API Surface

### `EvoGit.Config.Schema.Definitions`
Returns all config key schemas as a flat list of maps. Each schema: `key_path` (dotted atom path, e.g. `:scheduler.agent_workers`), `type`, `default`, `validation`, `category`, `sub_category`, `description`. Covers scheduler, sandbox, git, truncation, and more.
The five `[lsp]` keys (`:enabled`, `:command`, `:args`, `:timeout`, `:diagnostics_timeout`) describe the `lsp` tool's configuration; the `lsp` tool is offered to agents only while `EvoGit.Config.lsp_enabled?/0` is true (`[:lsp, :enabled] = true` plus a non-empty `[:lsp, :command]`), so the default `enabled = false` keeps it out of every agent's tool list.
There is NO global `[llm] oauth_file` config key — the managed OAuth credential file is a per-profile setting, and the `[:llm, :models]` description documents those `auth_mode` / `oauth_file` keys (absent `oauth_file` means `<config_dir>/auth.json`).

### `EvoGit.Config.Schema.LLM`
Extracts LLM generation parameters from config/model profiles. `llm_generation_params/1` accepts a model profile map or a resolved config map and returns a keyword list suitable for `ReqLLM`.

`profile_generation_params/1` is the **single choke point** for every parameter consumer (scheduler state, dispatch, agent state, and both the legacy-flat and explicit-profile path — the legacy path builds a profile via `build_legacy_default_profile/1` which is then read through this same function). It assembles `temperature, max_tokens, reasoning_effort, top_p, top_k, frequency_penalty, presence_penalty` plus `provider_options`, then pipes the result through `EvoGit.Config.Schema.LLMConstraints.filter/3` exactly once. Provider-aware filtering must NOT be duplicated at the other parameter-assembly sites.
The returned keyword list holds a scalar generation key ONLY when the profile value is non-nil (`maybe_param/3`), a NESTED `provider_options:` keyword list when non-empty (`auth_mode: :oauth` + `oauth_file:` for OAuth profiles, `store: false` for a native OpenAI endpoint), and — appended AFTER the constraint filter — a top-level `api_key:` only for a NON-OAuth profile carrying a nonempty `api_key_env_var` (`""` when the named env/credential is missing, so ReqLLM rejects instead of borrowing another account's key).
`base_url`/`extra` and `api_key_env_var` themselves NEVER appear in the generation params: endpoint overrides ride the ReqLLM-ready `model_spec` (the model input), and provider-wide API keys reach ReqLLM out of band through its key store (`Config.credentials/0` → `ReqLLM.put_key/2`).
Nothing per-request (request id, `user`) is added in the extraction layer or at the `ReqLLM.stream_text/3` call site, which only merges `tools:` over these params; the ONE cache/routing identity is attached separately by `with_cache_identity/3` at agent registration.

`provider_from_model/1` derives the provider atom from the three supported spec shapes — string `"provider:id"`, map `%{provider: ..., id: ...}`, tuple `{provider, opts}` — and `nil` for anything unrecognized.

`context_window/1` resolves a profile's context window (tokens): the optional `context_window` profile key (atom- or string-keyed) when it is a positive integer, else `default_context_window/0` (`200_000`) — an invalid value logs a `Logger.warning` and falls back, never raises.
`with_cache_identity/3` (`params`, `conversation_id`, `model`) attaches a stable per-conversation prompt-cache/routing identity to request params and is the ONLY place EvoGit adds one.
It is provider-gated to `:openai_codex` (adds `prompt_cache_key` AND `session_id`, the latter also emitting the `session-id` header) and `:openai` (adds `prompt_cache_key` only — `session_id` is not in that provider schema), returning every other provider's params byte-identically because an undeclared `provider_options` key is a hard request-time validation error.
The key is derived deterministically from `conversation_id` and stays stable for that conversation: the readable `genesis-<conversation_id>` form when it is ASCII and fits 64 characters, otherwise `genesis-` plus url-base64 SHA-256, so the key is always ASCII and bounded.
Explicit user configuration wins: an existing `provider_options[:prompt_cache_key]` (or, for `:openai_codex`, an explicit `:session_id`, which already implies the cache key) leaves params untouched, and an append EXTENDS the existing `provider_options` list rather than replacing it, so `auth_mode: :oauth` / `oauth_file:` survive.
The reason is routing-keyed provider prefix cache: OpenAI caches a request prefix only under a cache/routing identity, ReqLLM invents none when the caller omits one, and Genesis's own prompt prefix is already byte-stable across turns — so without this identity every turn misses the cache.
`context_window_for/2` (`config` map, `model_id`) reuses `get_model_profile/2` and returns the same value, defaulting on `{:error, :not_found}`.
Context-compression consumers use this ONE resolver instead of model-catalog metadata.

`provider_options_for_model/1` returns the OpenAI-only default (`[store: false]`, from `default_provider_options/0`) **only for a genuine NATIVE OpenAI endpoint**: provider `:openai` AND no custom endpoint override. A model spec MAP carrying a non-nil `:base_url` or `:extra` is an OpenAI-**compatible** third-party endpoint (the dashboard's "OpenAI-Compatible API" catalog entry maps to provider `:openai` with a custom `base_url`) and gets `[]` — such endpoints do not implement the OpenAI Responses-API `store` option. The check is a presence check, so even an empty `extra` map counts as an override.
For an OAuth-ONLY provider (`EvoGit.Config.LLMCatalog.oauth_only?/1` — today `:openai_codex`) it returns the OAuth defaults (`[auth_mode: :oauth, oauth_file: <resolved>]`, from `oauth_provider_options/1`) instead. `:openai_codex` is a DISTINCT provider atom upstream of the OpenAI driver, so it is NEVER given `store: false`: that field exists only in the native OpenAI provider schema and a provider-undeclared `provider_options` key raises at request time.

**`provider_options` precedence is THREE levels**: a profile's explicit `provider_options` (map or keyword list) is a PARTIAL override whose own keys win, over the profile-derived OAuth defaults (empty for an API-key profile), over model-derived options from `provider_options_for_model/1`. The merge is key-wise (`merge_options/2`: override keys win, defaults fill the gaps), so an explicit `oauth_file:` inside the override is honoured while the surviving OAuth default `auth_mode: :oauth` stays; an EMPTY result omits the `:provider_options` key entirely (`maybe_provider_options/2`). A profile that sets `provider_options` REPLACES the model-derived branch wholesale (it is not consulted), so a user override never silently inherits `store: false`.
**OAuth auto-detection** (`oauth_profile?/1`): a profile is OAuth when its `auth_mode` normalizes to `:oauth` (`"oauth"` or `:oauth`) OR its model's provider is OAuth-only — so `model = "openai_codex:gpt-5.6-terra"` means subscription auth with no `auth_mode` at all; anything else (including absent) is the API-key default.
The vendor-CLI credential import runs at ASSEMBLY time inside the OAuth branch only (`oauth_provider_options/1`), so an api_key profile stays allocation-identical and never touches `auth.json`.
Public OAuth helpers: `ensure_profile_credentials/1` (profile → `:ok | {:error, reason}`) and `oauth_credential_status/1` (profile → `{:ok, %{expires: ms | nil, account_id: String.t() | nil}} | {:error, :no_credentials | :invalid_credentials | :expired_credentials} | {:error, {:managed_file_unwritable, posix_reason}}`) — both resolve the provider from the profile's `:model`, the managed file via `oauth_file_for/1` (the profile's `oauth_file` → `<config_dir>/auth.json`), both are fault-isolated, and both accept a bare `%{model: model}` spec. `oauth_credential_status/1` imports first and threads a write-side import failure into `EvoGit.Auth.credential_status/2` as its `managed_file_error:` opt, so "the login exists but the managed copy cannot be written" is `{:error, {:managed_file_unwritable, posix_reason}}` rather than `:no_credentials` (`managed_file_error/1` extracts it from `ensure_credentials/1`).
`oauth_file_for/1` (public) returns the resolved managed OAuth path for a profile — the ONE way callers render that path in a message.
`build_legacy_default_profile/1` threads the flat `[llm] auth_mode` into the synthesized `"default"` profile — and only `auth_mode`, so that profile's managed file is the default `<config_dir>/auth.json` — so an OAuth subscription configured flat-style hits the same choke point without a `[[llm.models]]` table.
Login/credential lookup normalizes `:openai` to `:openai_codex` via `EvoGit.Auth.normalize_provider/1`; the REQUEST always uses the real provider atom from the model spec.

### `EvoGit.Config.Schema.LLMConstraints`
The declarative, pure, never-raising filter for the generation-parameter keyword list. Holds two constraint sources:

1. **`@constraint_tables`** — one map per provider/model family, each carrying its own `:provenance` code comment (the documented source every rule comes from). Seeded with `:zai_glm` (Z.AI GLM Chat-Completions API reference): `:unsupported_params` = `top_k`/`frequency_penalty`/`presence_penalty` (not documented by Z.AI); `:max_temperature` = `1.0` (Z.AI documents `[0.0, 1.0]` while Genesis allows up to 2.0); `:reasoning_effort` = full OpenAI set, with `by_model` overriding GLM-5.3 / GLM-5.3-FLASH to `low|high|max` only; `:thinking_disable_unsupported` records that GLM-5.3 rejects `thinking.type = "disabled"` (informational — Genesis never emits a `thinking` parameter, which is only reachable through the user `provider_options` override). Adding a provider = adding one table map.
2. **Model metadata** — `%{limits: map(), capabilities: map()}`: `limits.output` bounds `max_tokens`; `capabilities.reasoning.enabled` gates `reasoning_effort`; `capabilities.tools.enabled` gates `tools`/`tool_choice`.

Public API: `filter(params, model, metadata)` (guard-clause safe for non-list/non-keyword input, preserves keyword ORDER of survivors, never raises), `constraints_for(model)` (matching table entries), `normalize_metadata/1` (`@doc false`; collapses a metadata map or raw catalog-like struct to the documented contract, `nil` when unusable — shared with `LLM.model_metadata/1`).

**Model matching** is provider-atom based (`:zai`/`:zai_coder`/`:zai_coding_plan`) OR model-id based (case-insensitive `glm` substring, which also covers OpenRouter-style ids such as `z-ai/glm-5.3-flash` served under a non-Z.AI provider atom). The heuristic and its limits are documented in the table entry: GLM weights served under an id without `glm` are not matched, and an unrelated id containing `glm` is matched conservatively.

**Degradation contract**: a violation is always resolved by OMITTING the parameter (never clamped, never mapped — no documented value mapping exists for the affected families) plus a `Logger.warning` naming the parameter, the model and the reason. A `nil`/empty metadata map, an unknown or unparseable model spec, or a model the catalog does not know leaves the parameter list **byte-identical** — nothing is dropped merely because metadata is missing. Unknown providers/models are left completely untouched.

### Model metadata seam (`LLM.model_metadata/1`, app env `:llm_model_metadata_fun`)
`LLM.model_metadata/1` (`@doc false` public, returns `%{limits: map(), capabilities: map()} | nil`) reads the app-env seam `:llm_model_metadata_fun` — a 1-arity fun over the model spec, read AT CALL TIME — and falls back to a real ReqLLM model-catalog lookup (`ReqLLM.model/1`, already a declared dependency) when unset. The lookup is deliberately NON-raising (`rescue` + `catch` → `Logger.warning` + `nil`), so it degrades to "no metadata" (table rules still apply) rather than breaking a boot or a spawn.
**The catalog fallback DOES load the catalog, in the CALLING process**: `catalog_lookup/2` → `ReqLLM.model/1` → `LLMDB.Spec.resolve/2` → `LLMDB.Catalog.resolve_model/2` → `Catalog.ensure_loaded!/0` (`deps/llm_db/lib/llm_db/catalog.ex:107-132`); on the first model lookup of a BEAM that means the whole `LLMDB` snapshot load (`Jason.decode` of `deps/llm_db/priv/llm_db/snapshot.json`, ~11.7 MB / 239 providers / 10,100 models, a canonicalizing digest over the whole catalog, and the `models_by_key`/`aliases_by_key`/`providers_by_id`/`__llm_db_resolutions_by_model_id__`/`__llm_db_model_id_prefixes__`/… indexes) plus a `:persistent_term.put` — seconds of CPU and tens of MB of transient heap in the process that happens to call first.
After the first load the term is READ with `:persistent_term.get(:llm_db_store, nil)` (`catalog.ex:64`), which does NOT copy it into the reader's heap (OTP `persistent_term.erl`: a copy + global GC happens only on `put`/`erase`).
There is NO cache or memoization in front of `model_metadata/1` (no ETS, `:persistent_term` or process-dictionary entry) — every call re-runs the resolve against the loaded catalog.
Callers (all of them): boot — `EvoGit.CatalogWarmup.warm_up/1` (a throwaway process started immediately before `AgentScheduler`, so it takes the cold-catalog load with it when it dies), then `AgentScheduler.init/1` (`agent_scheduler.ex:577-581`) and `State.from_model_profiles/2` (`agent_scheduler/state.ex:182`) against the now-warm catalog; per agent spawn — `Dispatch.resolve_model_for_agent/2` (`agent_scheduler/dispatch.ex:357`); per compression check — `Agent.Compression.Threshold.output_limit/1` (`agent/compression/threshold.ex:240`).
**Keep it cheap** — it runs per agent spawn (and per profile read / per-turn compression check), and whichever process calls it FIRST on a cold BEAM carries the whole snapshot load in its own heap: at boot that must be `EvoGit.CatalogWarmup`'s short-lived process, never a long-lived one (an embedded BEAM does not fullsweep it away — measured: 92.6 MB retained by the scheduler before the warm-up existed, 28.8-66.3 KB after; see `../agent_scheduler/CONTEXT.md`); cache per-model `%{limits, capabilities}` (ETS/`:persistent_term`) instead of re-resolving.

Tests inject stub metadata through the seam, so no catalog is needed.

## Assistant Evaluation / Configuration Boundaries
The evaluator's explicit MFA/tier lists, not namespace grants or an API's public visibility, determine admission; the authoritative policy and full inventory live in `../../agent/tools/elixir_eval/CONTEXT.md`.
`EvoGit.Config.resolve/0,1` are admitted direct reads in read/write tiers, while `EvoGit.Config.save_user_config/1`, `EvoGit.AgentScheduler.RemoteAPI.reload_config/0` and `EvoGit.AgentScheduler.update_config/1` are admitted only in write tier.
Write tier requires exact-code tier-2 manual approval; unrestricted native sudo requires its separate explicit approval and is not a security sandbox, and denied operations never auto-escalate.
These boundaries guard against accidental Assistant self-corruption, not a malicious attacker with unrestricted sudo authority.
Direct reads retain actual nested values, potentially including secrets, and are neither facade projections nor secret-safe; output caps are not redaction.
`Config.resolve/0,1` reads normalized defaults plus user configuration, not live scheduler overrides; direct `AgentScheduler.update_config/1` changes runtime settings without persisting them.
`Config.save_user_config/1` replaces the whole file rather than patching and does not automatically reload the scheduler.
For persistent changes, resolve the full configuration, update only intended keys and save the full map in the same approved evaluation, then explicitly call `RemoteAPI.reload_config/0` after save success and inspect its result.
This preserves unrelated keys but materializes resolved defaults, and read-modify-save is not atomic, so avoid concurrent edits; boot-only settings still require restart.
Schema/defaults APIs and this node's `Definitions`, `LLM` and `LLMConstraints` functions remain unlisted, not implicitly admitted through Config reads or writes.
`Definitions` describes metadata without user values, whereas `LLM` helpers can return unredacted supplied profiles, create provider atoms, import OAuth credentials or load catalog metadata, and constraint filtering can log model specs containing secrets.
`context_window_for/2` defaults on an unknown id and skips malformed legacy entries through `get_model_profile/2`; schema helper access is not evaluator authorization or a redaction guarantee.

## Reasoning Selection and Resolution Gotchas
`LLM.default_model_profile/1` honors `llm.default_provider_profile` for canonical and legacy profiles, selecting the first profile only when the selector is absent and returning `{:error, :not_found}` for an invalid explicit selector.
`get_model_profile/2` skips malformed legacy entries, returns the first matching legacy id, and reads canonical accounts through the provider resolver's duplicate/default-model/effort checks.
The legacy `LLM` API gives each model profile one optional scalar `reasoning_effort`; ordered provider/model effort inventories and default selection are handled separately by `ProviderProfiles`.
The flat reasoning schema is a string with nil default and no membership validation (`definitions.ex:225–234`), and generation assembly omits nil instead of inventing a model default (`llm.ex:541–557,729–731`).
`LLM.convert_reasoning_effort/1` converts none/minimal/low/medium/high/xhigh/default strings to atoms but leaves every other value unchanged, including the documented GLM-5.3 value `"max"` (`llm.ex:737–746`).
`LLMConstraints` normalizes effort only for comparisons and preserves the original surviving wire value, so accepting `"max"` in the GLM allowlist does not convert it to `:max` (`llm_constraints.ex:283–326`).
A nonempty metadata capabilities map that omits reasoning, or lacks explicit `reasoning.enabled == true`, removes a configured effort, whereas nil metadata and empty capabilities leave it alone (`llm_constraints.ex:357–373`).
The constraint table's `reasoning_effort.default` is an allowed-values fallback for unmatched model ids, not a default effort injected into requests (`llm_constraints.ex:101–105,207–239`).

## Canonical Provider Profiles (`ProviderProfiles`)
`EvoGit.Config.Schema.ProviderProfiles` exposes `provider_profiles/1`, `model_selections/1`, and `resolve_model_spec/2` independently of the legacy `LLM` entry points.
`ProviderProfiles.Normalize` owns recursive string-key normalization and one-for-one legacy migration, while `ProviderProfiles` owns enumeration, default selection and runtime resolution.
`provider_profiles(config)` accepts atom- or string-keyed config and returns canonical STRING-keyed maps from `llm.providers`, falling back to legacy `llm.models` or flat `llm.model` only when the provider list is absent or empty.
Every legacy profile keeps its own exact id and account boundary, even when another profile has the same provider/model/endpoint, and a model-less flat config returns no provider profiles.
Provider maps carry `id`, optional `name`, `provider` (string), normalized `auth_mode`, `concurrency` (default 3), shared peak fields, optional `api_key_env_var`/`base_url`/`oauth_file`, generation defaults, ordered `reasoning_efforts`, optional `default_reasoning_effort`, `default_model` and nested `models`.
Nested model strings become maps with a `model` key, maps accept `model` or input alias `id`, and model maps can override generation parameters, context window, effort inventory and effort default.
Canonical `default_model` is a selector, not an implicit model declaration: `Normalize.canonical_profile/1` normalizes missing `models` to `[]` exactly like explicit `models: []`, without synthesizing a singleton from `default_model` (`provider_profiles_normalize.ex:52–62`).
Both shapes enumerate no model selections and fail runtime resolution with `{:model_not_found, profile_id, default_model}` when a nonempty default is supplied (`provider_profiles.ex:38–41,119–132`), so valid single-model fixtures must include `models: [default_model]` or the equivalent model map.
Only legacy migration synthesizes a singleton inventory from its legacy `model` field (`provider_profiles_normalize.ex:136–155`); the empty-inventory no-restriction rule refers to reasoning efforts, not models.
`Normalize.put_default_model/2` selects the first normalized model when `default_model` is nil, empty-string or non-string, not merely absent; a nonempty string is preserved (same-provider qualification removed) and an unknown or whitespace-only string fails runtime lookup.
`ProviderProfiles.find_profile/3` uses `spec.provider_profile_id || llm.default_provider_profile || first_profile_id`, so nil and boolean false fall through, but empty strings, whitespace strings and other non-string selectors remain explicit ids and normally return `{:provider_profile_not_found, value}`.
Canonical `LLM.default_model_profile/1` inherits that false-selector fallback, whereas its legacy branch rejects non-string selectors; validation must reject malformed values separately rather than treating successful resolution as proof of valid configuration.
`model_selections(config)` returns ordered atom-keyed maps with exactly `provider_profile_id`, `profile_name` (name or id), `provider` (string), `model` (unqualified id), `reasoning_efforts`, `default_reasoning_effort` and `context_window`.
The inventory preserves effort order and removes duplicates; a model inventory replaces the provider inventory, an explicit empty inventory imposes no restriction, and no effort default is invented from the first inventory entry.
`resolve_model_spec(config, spec)` accepts nil, a provider/legacy id string, or an atom-/string-keyed map with `provider_profile_id`, optional `model` and optional `reasoning_effort`.
A nonempty string candidate is always an EXACT provider-profile id, not an encoded selection or qualified model selector; there is no colon-splitting or `id:provider:model` alias matching at this boundary.
A legacy id containing colons is preserved verbatim by migration and therefore resolves only as that exact profile id; explicit model selection belongs in the map's `model` field, which strips only the selected provider's exact prefix.
Empty-string candidates fail with `:invalid_model_spec`, while a map with no provider id uses `llm.default_provider_profile` or the first profile and a nil candidate follows the same default path.
Resolution precedence is provider defaults, then model overrides, then explicit task effort, and the provider default selector is `llm.default_provider_profile`.
Success is `{:ok, resolved}` with all selection fields plus `reasoning_effort`, canonical `provider_profile`, atom-keyed legacy-compatible `runtime_profile`, ReqLLM `model_spec`, shared concurrency/peak keys and `generation_params`.
Selection `model` stays an unqualified id, whereas `model_spec` and `runtime_profile.model` are the actual qualified string or custom-endpoint ReqLLM map.
Only the ACCOUNT-level `base_url`/`extra` reach `model_spec` (`reqllm_model/2` reads them off the profile, `provider_profiles.ex:208–221`); a nested canonical model map's `base_url`/`extra` is in neither `Normalize.generation_keys/0` nor `inherit/2`, so it is silently ignored.
Effort values are compared WITHOUT case folding (`Normalize.string_effort/1` only rejects nil/empty, `provider_profiles_normalize.ex:212–214`), so `"HIGH"` against a configured `["high"]` inventory fails as `{:unsupported_reasoning_effort, "HIGH", ["high"]}`.
For dashboard/task picker persistence, reconstruct `%{"provider_profile_id" => resolved.provider_profile_id, "model" => resolved.model}` and add `"reasoning_effort" => resolved.reasoning_effort` only when non-nil, rather than persisting `resolved.model_spec` (`provider_profiles.ex:53–62,135–144,208–220`).
The resolved outer map is atom-keyed, its `provider_profile` is recursively string-keyed, and its top-level `reasoning_effort` is the selected normalized string or nil, independent of later ReqLLM generation-parameter conversion/filtering (`provider_profiles.ex:171–200`, `llm.ex:628–644`).
An omitted or nil input effort selects the configured default, so nil cannot explicitly suppress a configured effort default (`provider_profiles.ex:171–175`).
Runtime generation uses `LLM.profile_generation_params/1` for OAuth import, provider-option precedence, constraint filtering and optional `api_key_env_var` resolution for API-key profiles only.
Resolved generation parameters may therefore contain secrets and must not be treated as a dashboard projection.
Enumeration does not import OAuth credentials or read model metadata, but resolution can do both through the existing LLM choke point.
Errors are `:invalid_config`, `:invalid_model_spec`, `{:provider_profile_not_found, id}`, `{:duplicate_provider_profile_id, id}`, `{:model_not_found, profile_id, model}`, `{:duplicate_model, profile_id, model}`, `{:invalid_reasoning_effort, value}` or `{:unsupported_reasoning_effort, effort, allowed}`.
`ProviderProfiles.resolve_runtime_profile/2` shares selection and inheritance with `resolve_model_spec/2` but returns only the runtime profile without generation assembly, OAuth import, environment-key reads or catalog metadata reads.
`LLM.model_profiles/1` projects a non-empty `llm.providers` list into one atom-keyed legacy-compatible runtime profile per provider account using that account's default model and effort, preserving provider order and account ids.
Invalid canonical selections are logged and omitted, and canonical presence suppresses legacy fallback even when all canonical entries are invalid.
`LLM.default_model_profile/1` uses the canonical default selector directly, and `LLM.effective_model_profiles/1` preserves the model-less flat fallback only when canonical providers are absent or empty.
Legacy `llm.models` profiles remain unchanged, and the flat profile builder never calls ProviderProfiles, preventing recursive normalization.
Runtime profiles retain `api_key_env_var`; `LLM.profile_generation_params/1` is the single assembly boundary for resolving account-specific keys on API-key profiles, with OAuth profiles always excluded.
For a nonempty configured `api_key_env_var`, a nonempty environment value wins, followed by a nonempty `EvoGit.Config.credentials()` value under that exact string key, without consulting provider/catalog credential names.
If neither source has a nonempty binary value, assembly emits `api_key: ""`, which ReqLLM rejects instead of falling back to provider-wide credentials, preserving isolation between accounts using the same provider.
Profiles without a nonempty custom key name retain the existing provider-default lookup behavior.
`Definitions` describes `llm.providers` as `:provider_profiles` with default `[]` and `llm.default_provider_profile` as an optional `:string` with default nil, alongside the legacy schema entries.
Parent-owned `../schema.ex`, `../provider_profile_validation.ex` and `../config.ex` own schema delegation, canonical composite/cross-field validation and config persistence; verify those files rather than inferring validation from these lenient normalization helpers.
Permanent regression tests belong in the parent-owned test tree and must cover canonical round trips, separate same-provider legacy accounts, defaults/ordering/effort overrides, custom endpoints, OAuth/API-key isolation, constraints, duplicate/unknown selectors and malformed or empty inputs.

## Health-Check Selection and Credential Boundaries
`Definitions` declares `[:llm, :default_provider_profile]` as an optional string with nil default and no descriptor-level membership rule; canonical selector membership and blank-value errors belong to the parent validator rather than this descriptor.
`LLM.model_profiles/1` resolves each canonical account by its explicit id, so a valid account still appears in that projection even when the configured default selector names a missing account.
An account whose nonempty-string `default_model` is unknown is omitted from `LLM.model_profiles/1`, while other valid accounts remain visible; `model_selections/1` still enumerates that account's model inventory because it never resolves defaults.
An any-model/any-credential presence check over that projection cannot establish that the configured default selection is valid.
`Config.config_status/0` snapshots schema validation errors from its initial resolve and requires both no missing critical settings and an empty validation-error snapshot for `ok?: true`, so invalid default selectors remain unhealthy even when another account has a usable model and credentials.
`LLM.effective_model_profiles/1` returns `[]` rather than legacy/flat fallback when a nonempty canonical providers list yields no valid runtime profiles, even if legacy fields still contain usable models.
`ProviderProfiles.resolve_runtime_profile(config, nil)` checks default account/model/effort selection without assembling generation parameters, importing OAuth credentials, reading API-key values or loading catalog metadata; `LLM.default_model_profile/1` wraps its failures as `{:error, :not_found}`.
Do not use `resolve_model_spec/2` solely to inspect health because its successful result contains the complete canonical profile, runtime profile and potentially secret-bearing generation parameters, and its assembly can import OAuth files and load the catalog.
`LLM.oauth_credential_status/1` intentionally imports credentials before checking them and preserves managed-file write failures through `managed_file_error`, but its managed-file path comes from the top-level profile `oauth_file`, whereas request assembly permits an explicit `provider_options.oauth_file` override.
OAuth health and actual request files can differ when that override is supplied.
Avoid embedding inspected validation values or whole resolved profiles in health warning text because custom endpoints, provider options and arbitrary malformed fields may contain secrets.

## Constraints
- `Definitions` describes defaults without reading user configuration, but `LLM` is not a pure read boundary: OAuth option assembly/status can import credentials into a caller-selected managed file, metadata resolution can load the catalog, and provider parsing can create atoms.
- Schema definitions are the single source of truth for all config keys.
- The parameter filter never raises on user config and never guesses: a constraint is only applied where there is documented provenance or actual model metadata.

## Notes for Agents
- **`Definitions.schemas/0` yields 106 entries** = 75 hand-written schema maps (58 in the first list, 17 in the post-`search_provider_schema_maps()` list) + 31 generated search-provider maps (5 providers × 6 keys + Perplexity's extra `:model`).
- **Per-category counts**: scheduler 11, llm 14, user 1, sandbox 19 (sub_category `:resources` 4 / `:process` 4 / `:linux` 8), truncation 4, task_history 2, nix 2, git 2, server 2, node 6, appearance 1, data 3, **tools 39** (3 hand-written top-level `[:tools, …]` maps: `:shell`, `:search, :enabled`, `:search, :provider`; 5 `[lsp]` maps; 31 generated `[:tools, :search, <provider>, …]` maps).
- **No key caps total agents/worktrees and there is no `max_llm_max_concurrency` key** — canonical `[[llm.providers]]` accounts own shared `concurrency` and peak/off-peak capacity across all nested models and reasoning efforts, while legacy `[[llm.models]].concurrency` remains a compatibility input.
`[:scheduler, :default_llm_max_concurrency]` (default 3) is the floor/fallback, preserving explicit zero-capacity pauses.
- **Canonical account and nested model fields** are documented in "Canonical Provider Profiles (`ProviderProfiles`)" above: accounts own shared auth, endpoint, capacity and generation defaults, while nested models may override generation/context/effort settings.
Legacy `[[llm.models]]` compatibility profiles retain `id`, `model`, `concurrency`, `context_window`, `auth_mode`, `oauth_file`, scalar generation parameters, `provider_options` and peak schedule fields; this legacy shape is not the canonical account schema.
Retries remain global (`[:scheduler, :max_retries]` 15, `[:scheduler, :agent_max_retries]` 3), not per-account or per-model settings.
- **LLM HTTP timeouts are NOT config.toml schema keys**: `receive_timeout` 600_000, `metadata_timeout` 600_000 and `thinking_timeout` 1_000_000 live in the ReqLLM application env in the root `config/config.exs` (`config :req_llm, ...`), so they are not user-editable via the settings page or `[[llm.models]]`.
- **`EctoValidation.validate_model_profile/2` is lax about `:model`**: `nil` is an error but ANY binary (including `""`) passes; the `config_status` has_model gate is the only place an empty-string model is rejected.
- **`profile_generation_params/1` reads ATOM keys only** and emits scalar generation keys ONLY for non-nil values (`llm.ex:543–558`), so a minimal profile (`id`/`model`/`concurrency`) adds no scalar generation overrides but may still emit native-OpenAI or OAuth provider defaults (`llm.ex:700–713`).
A STRING-keyed profile yields `[]`; `llm_generation_params/1` also dispatches only on ATOM keys `:id`/`:llm` (`llm.ex:75–90`).
Profiles reaching this code are atom-keyed because `EvoGit.Config` normalizes them (`normalize_profile_keys/1`); the dashboard writes no generation params unless the user typed them.
- Scheduler concurrency schemas both require `:pos_integer` with `[min: 1]`; `default_llm_max_concurrency` defaults to 3 and `max_tool_concurrency` defaults dynamically to `EvoGit.Platform.cpu_threads()` (`definitions.ex:36–64`).
The `llm.models` schema defaults to `[]`, and its description documents per-profile concurrency default 3 (`definitions.ex:275–283`); the actual profile validator and TOML normalization/migration live in the parent config node.
`LLM.build_legacy_default_profile/1` synthesizes an atom-keyed `"default"` profile with concurrency from the atom-keyed scheduler section (fallback 3), plus non-nil flat generation fields and auth_mode (`llm.ex:257–276`).
- **`provider_options_for_model/1` is native-OpenAI or OAuth-only by design** (`[store: false]` for a native `:openai` endpoint, the OAuth defaults for an OAuth-only provider such as `:openai_codex`, `[]` otherwise — see the `API Surface` entry above for what makes an endpoint non-native) and must NEVER emit `store: false` for `:openai_codex`: that field exists only in the native OpenAI provider schema, and a provider-undeclared `provider_options` key raises at request time. Passing `provider_options: [store: false]` to ANY other non-OpenAI provider raises the same way — req_llm validates `provider_options` against the provider schema (`zai`/`zai_coder`/`zai_coding_plan` accept `[:thinking]` only → `NimbleOptions.ValidationError: unknown options [:store]`). Verified against the vendored `deps/req_llm` (`zai`/`zai_coder`/`zai_coding_plan` `provider_schema/0` accepts only `:thinking`, and `provider_options` is validated against it in `ReqLLM.Provider.Options.process!/4`).
- **Not every extraction key reaches the wire.** `top_k` and `reasoning_effort` are accepted ReqLLM generation options but are not encoded by the Z.AI family (`ReqLLM.Providers.Zai.Shared.add_basic_options/2` emits only `temperature`, `top_p`, `frequency_penalty`, `presence_penalty`, `user`, `seed`, `stop`); `reasoning_effort` is telemetry-only. `temperature`/`top_p`/`frequency_penalty`/`presence_penalty` DO reach the body when non-nil. This module can therefore not "leak" provider-unsupported parameter names of its own — except via an explicit profile `provider_options` map, which is passed through verbatim (`maybe_provider_options/2`).
- `definitions.ex` is a comprehensive data table of config keys; do not split it.
- In `definitions.ex`, the search-provider schemas (`[:tools, :search, <provider>, ...]`) are NOT hand-written literals — they are generated from the data-driven `@search_provider_defs` list (one `%{name:, label:, credential_key:, base_url:, optional model:}` map per search provider: `:tavily`/`:perplexity`/`:exa`/`:bing`/`:brave`), each entry expanded by `search_provider_schema_maps/1` into the repeated per-key schema maps (33 search schema maps in `schemas/0` in total incl. the fixed `:enabled`/`:provider`). Adding or extending a search provider means editing that list, not hand-writing repeated provider maps. `@search_providers`/`search_providers/0` remains the source of truth for the provider-ID list used by the `:provider` schema `in:` validation.
- `EvoGit.Config.Schema` (validate + defaults + typespecs) lives in the PARENT node file `../schema.ex`; the validation ENGINE (former `type_errors/3`/`rule_errors/3` privates) now lives in the parent node's `../ecto_validation.ex` (`EctoValidation.errors_for/4`) with scalar type decisions routed through the strict custom Ecto types in `../ecto_types.ex` (`EctoTypes`). Definitions here, the engine there and the `@type schema_type` union in `schema.ex` must stay in sync. **Adding a new validation type requires three touch points** (see the "Validation Engine — Ecto-backed" section of the parent `../CONTEXT.md`): (1) a definition entry here, (2) a new nested strict `use Ecto.Type` module in `ecto_types.ex` + a `type_for/1` clause (returning the fully-qualified `__MODULE__.X` atom) + a `@type scalar_type` union entry, and (3) a `type_errors/2,3`-style clause in `ecto_validation.ex` plus the `@type schema_type` union entry in `schema.ex`. `min`/`max`/`in` rules need no type-module — they are pure predicates in `EctoValidation.rule_errors/3`.
- `llm_constraints.ex` deliberately does NOT depend on any catalog being loadable: the Z.AI/GLM table rules must stay effective with zero metadata. Do not move table rules behind a metadata check.
