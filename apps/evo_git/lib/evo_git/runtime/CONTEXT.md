# Runtime

## Intent
Implements the two-phase execution engine of EvoGit: **Genesis** (initial codebase creation or analysis of an existing codebase) and **Evolution** (iterative modification loop). A shared `PullRequest` module handles post-phase PR creation. There is no centralized `EvoGit.Runtime.Prompts` module — prompts live in agent `system_prompt/0` callbacks and inline strings.

## Routing Table

None — leaf directory (modules: `runtime.ex` (parent dir `../runtime.ex`), `helpers.ex`, `genesis.ex`, `evolution.ex`, `pull_request.ex`, `worktree_init_script.ex`, `skill_extraction.ex`, `self_reflective.ex`).

### `Genesis.run/2` — Steps

1. Parse opts: `repo_path` (default `File.cwd!()`), `foreign_repos` (loaded + validated via `Helpers.load_foreign_repos/2` — no separate AgentScheduler registration; the validated list is threaded through AgentSpec opts `foreign_repos:` by `build_phase_spec/6`).
2. `Runtime.ensure_repo/1` (`git init` if needed); HEAD via `Helpers.resolve_starting_commit/2` (nil → `PhyloGraphNode.current_head/1`).
3. Detect mode via `new_codebase?/1` (files beyond `.git`, `README.md`, `.genesis`, `.gitignore`).
4. Mode B only: read `build_system` opt (CLI `--build-system`), `WorktreeInitScript.scripts_for/1` → write `script.linux`/`script.macos`/`script.windows` to `genesis.toml` via `ProjectConfig.write_worktree_script/2`. Skipped when no build system or `:none`.
5. Dispatch: **Mode A (Existing)** → `ContextExtractor` (read-only, recursive CONTEXT.md tree extraction). **Mode B (New)** → `Architect` (read-write, 3-phase: architecture & design → implementation delegation → review & accountability) + second root `Manager` for implementation.
6. `AgentSpec.new(context_node, phylo_node, agent_module, objective)` → `AgentScheduler.run_agent/1` (blocks until complete).
7. Post-processing `merge_and_report/3`: base SHA vs the agent-reported final SHA — `agent_output.commit_sha`, the POST-fallback worktree HEAD, so a change committed ONLY by the agent-exit auto-commit fallback still counts as "changed"; changed → `genesis/agent_<hex>` branch at the agent commit (reviewable/mergeable on the dashboard review page); unchanged → `no_changes: true`.

### `Evolution.run/2` — Steps

1. Parse opts: `repo_path`, `mode`, `node_path` (default `"./"`), `foreign_repos`.
2. `mode_atom/1` (`@doc false` test wrapper): nil/absent, `:simple`, `"simple"` → `:simple`; `:custom`/`"custom"` → `:custom`; ANY other value → warning + `:simple` fallback.
3. Custom mode requires an `agent:` opt — nil/empty raises `ArgumentError` ("custom mode requires an agent id; pass agent: <id> (defined in agents.toml)") BEFORE repo/git I/O; unknown ids raise in `Helpers.resolve_root_agent/2`.
4. Register foreign repos; ensure repo + HEAD (same as Genesis).
5. `validate_node_path/2`: path relative, dir exists, contains `CONTEXT.md` (root `"./"` always passes).
6. Dispatch: `:simple` → `Manager` agent (plans, delegates to Executor/TaskScheduler/Investigator subagents); `:custom` → `EvoGit.Agents.Custom` root bound to the `agent:` id. Both modes share one private flow `run_mode/7` (evolution.ex:93) parameterized by the resolved root-agent module/opts — the spec itself is assembled by `Helpers.build_root_agent_spec/7`.
7. Post-processing: same `merge_and_report/4` pattern (base SHA vs `agent_output.commit_sha` — the POST-fallback worktree HEAD).

### `starting_commit` Opt — Evolution Only (Genesis Ignores It)

`TaskRegistry.RuntimeOpts.build_common_runtime_opts/3` (`task_registry/runtime_opts.ex:32-37`) passes `:starting_commit` into runtime opts for BOTH `:genesis` and `:evolve`; the CLI passes it for evolve (`cli.ex:89`, `--starting-commit`, `cli/parser.ex:34`). **Only `Evolution.run/2` reads it** (`evolution.ex:24,33`) — `Genesis.run/2` has no `starting_commit` clause and always resolves HEAD, so a genesis `:starting_commit` is silently ignored. Resolution goes through **`Helpers.resolve_starting_commit/2`** (`helpers.ex`, the single choke point — `resolve_foreign_repo_starting_commit/2` delegates to it): `nil` → current HEAD via `PhyloGraphNode.current_head/1`; a ref (commit SHA / branch name / lightweight + annotated tag) → `Git.rev_parse` with the `^{commit}` peel suffix, so a valid annotated tag resolves to its peeled COMMIT sha (all downstream consumers — worktree add, phylo node, merge_and_report, resume contexts — work on real commit SHAs) and a ref pointing at a non-commit object (tree/blob) is rejected. A non-existent ref, a non-commit object, or an unborn-HEAD repo yields the structured `{:error, {:invalid_starting_commit, ref, repo_path, git_output}}` — NEVER the raw git `{:error, {code, output}}` tuple — which the genesis/evolution phase else-arms turn into a human-readable `{:error, message}` (via the shared `Helpers.format_invalid_starting_commit_error/3`) persisted as the failed-task result. Valid refs, resume (`ResumeContext`), merge-auto-resolve (`MergeContext`) and genesis Mode B architect restarts are unaffected — they pass real prior commit SHAs.

**Path to the agent**: resolved SHA → `PhyloGraphNode.new(repo_path, current_sha)` (`phylo_graph_node.ex:23-24`; both `base_commit`/`current_commit` = SHA) → `AgentSpec.phylo_node` → `AgentScheduler.run_agent/1` (`agent_scheduler.ex:593-641`) → worktree created AT that commit: `Worktrees.create_worktree/6` (`worktrees.ex:96-137`) uses `spec.phylo_node.current_commit` for `CowWorktree.create_worktree`/`Git.add_worktree`; `assign_and_prepare_worktree/2` (`worktrees.ex:233-259`) rebuilds the worktree-bound phylo node (repo = worktree path) into ETS. The SHA is NOT injected into prompt text — the agent learns its starting point from the worktree contents (`base_commit`/`current_commit` live only in ETS; described abstractly in Manager's `system_prompt/0`, `agents/manager.ex:51`).

### Genesis Mode B Second Root

The second root (`Manager`) spawns only in Mode B after a successful Architect run (`run_implementation_phase/8` called at `genesis.ex:105-114`, defined at `genesis.ex:123-209`). No condition on repo non-emptiness or `starting_commit != base` — Mode B is gated only by `resolve_mode/2` (`genesis.ex:252-268`: explicit `:mode` opt or `Helpers.new_codebase?/1`, `helpers.ex:198-206`). The Manager's phylo node starts at the architect's final commit (`architect_output.commit_sha || base_sha`, `genesis.ex:134`). Both roots share one `task_id` (`genesis.ex:67-71`); the scheduler's cancel guard (run_agent handler, `agent_scheduler.ex:664-712`, cancel check at `:673-678`) refuses the second root when the task is cancelling. On implementation-phase failure the architect's output is merged as partial success (`genesis.ex:200-208`). **Mode-B forwards multi-modal `:attachments` to the phase-2 Manager**: `run_implementation_phase` passes the shared runtime `opts` (which carry the validated `:attachments` list) verbatim into `build_phase_spec` (`genesis.ex:161-162`) → `Helpers.build_root_agent_spec` (`genesis.ex:217-231` def `build_phase_spec`, root-agent call at `:222-230`), so the implementing root can reference the attached media exactly like the phase-1 Architect — no per-phase stripping or extra plumbing (product intent: both sequential roots of a Mode-B task may use the initial attachments).

### Prompt / Objective Assembly — No Cross-Agent File Hand-Off

Runtime phases never pass file locations between agents — hand-off is text + a commit SHA only:

- `:objective` reaches the root agent's FIRST user message **verbatim**: the runtime passes it as the 4th positional arg to `AgentSpec.new/5` (`agent_spec.ex:58-69`) → `AgentSpec.objective` → scheduler → Runner wraps it in `<objective>…</objective>` (`agent/runner.ex:125-134`, `agent/context_builder.ex:132-134`). Only blank→"" normalization — no truncation/reformatting. Any absolute path inside an objective comes from the CALLER (CLI/dashboard/parent objective string), not from prompt assembly.
- **Genesis Mode B (Architect → phase-2 Manager) hand-off is TEXT ONLY** (`genesis.ex:123-162`): `impl_objective` interpolates the ORIGINAL `objective` plus `architect_output.result` (the architect's report STRING); the Manager starts from `architect_commit = architect_output.commit_sha || base_sha` (a SHA). No scratch/artifact file is written by the architect or read by the Manager.
- This directory embeds NO absolute filesystem path into any prompt/objective. The only interpolations are the objective text, the architect report string, commit SHAs (`skill_extraction.ex:71-72` `git diff <base_sha> <commit_sha>`), and RELATIVE gitlink paths (`helpers.ex` `render_repo_notes/1`). No `/tmp`/`$TMPDIR` scratch-file instruction exists here.
- Absolute paths DO reach prompts, but from the AGENT layer, not the runtime: non-primary foreign-repo ROOT paths via `ContextBuilder.build_foreign_repos_section/1` (`agent/context_builder.ex:44,50`) and the agent's own worktree path via `ContextNode.build_context/2`'s `location_info` block (`core/context_node.ex:213-219`). Detail: `agent/CONTEXT.md` + `core/CONTEXT.md`.
- `PullRequest.generate_title_with_llm/3` (`pull_request.ex:134-141`) embeds `objective` + a 2000-char slice of the agent result into a PR-TITLE prompt — a post-phase utility, not an agent hand-off.

### `merge_and_report` Never Merges — `Task.resolve_conflict/3` Is Dead Code

`merge_and_report/4` (`helpers.ex:11-84`) only `rev_parse`s HEAD + `Git.create_branch(repo_path, branch_name, final_sha)` — for the primary repo AND each WRITABLE foreign repo that produced commits (same branch name across repos; `Git.create_branch(foreign_root, branch_name, sha)` per repo — NEVER merged into any default branch).
`final_sha` is `agent_output.commit_sha`: the POST-fallback worktree HEAD, because the Runner's `after` auto-commit fallback (`EvoGit.AgentScheduler.Dispatch.commit_pending_in_worktree/0`) runs BEFORE the agent result is returned and the runner then re-reads the worktree HEAD.
A change committed ONLY by that fallback therefore still differs from the repo root's live HEAD and produces a real `genesis/agent_<hex>` branch — reviewable/mergeable on the dashboard review page — instead of `no_changes: true` / `branch_name: nil` (those outcomes apply only when the POST-fallback `final_sha` equals the repo root HEAD).
The agent commit is NOT merged into any target branch; PR creation is not done here. No conflict path in the phases. `EvoGit.Task.resolve_conflict/3` (`task.ex:115-190`) is dead code (no caller anywhere in `apps/`, rg-verified): it git-merges `incoming_sha` into `phylo_node.current_commit` and, on `{:error, {:conflict, _}}`, spawns one `Manager` per conflicted file with an inline conflict-resolution prompt (`task.ex:157-165`), then commits. Real branch merging with conflict reporting lives in `EvoGit.Review.merge_branch/2,3` (dashboard Review flow → `{:conflict, details}`).

### Per-Repo Branches & the `repos` Report Key

`merge_and_report/4` (3-arity `merge_and_report/3` delegates with `foreign_repos: []`) reports the PRIMARY repo exactly as before (top-level keys `commit_sha`, `result`, `tag`, `branch_name`, `pr_url`, `pr_title`, `usage`, `agent_count`, `archive_records`, plus `no_changes: true` when applicable — all PRIMARY-repo values, backward compat) and adds a NEW top-level `repos` key consumed by the dashboard review workstream:

- **Shape**: `repos` is a map `repo_id (String) => %{commit_sha: String.t(), branch_name: String.t() | nil}` — plain maps only, no structs inside (must survive JSON). Repo-id KEYS are strings (`ForeignRepo.primary_id()` = `"primary"`, foreign `repo.id` values); the INNER keys are ATOMS in memory (`helpers.ex:124,171,179` — `%{commit_sha:, branch_name:}`) and become strings only after the Codec/JSON round trip. The `"primary"` entry is ALWAYS present (commit_sha = the top-level `commit_sha`, branch_name = the primary branch or nil when no changes/no primary branch). Each WRITABLE foreign repo that got a branch created appears under its string repo id. READ-ONLY foreign repos produce NO entries.
- **One branch name per task**: `generate_branch_name(phase)` is called ONCE and the resulting `genesis/agent_<hex>` name is REUSED for the primary AND every writable foreign repo with commits → uniform dashboard merge/reject broadcast (one branch name across repos). In the no-changes / rev_parse-error paths the primary keeps `branch_name: nil` but foreign branches are still created (branch name generated only when foreign commits exist).
- **Per-repo data source**: `result.foreign_repo_commits` — a map `repo_id => latest commit SHA in that repo`; it IS a field of `%EvoGit.Agent.Result{}` (`agent/result.ex:31,44,73`, default `%{}`) and is still read defensively via `Map.get(result, :foreign_repo_commits, %{})` (Mode B merges two results with `Map.put`, yielding a plain map). Entries are looked up against the `foreign_repos` list (4th arg); only `writable: true` repos WITH a binary tracked SHA are processed (`helpers.ex:152-153`); unknown/read-only/sha-less ids → no entry; branch-creation failure → `Logger.error` + entry kept with `branch_name: nil` (same tolerance as the primary path). Genesis Mode B merges the Architect + Manager `foreign_repo_commits` maps before reporting (`genesis.ex:190-196`).
- **Codec round trip**: `repos` is NOT in `EvoGit.Store.Codec.@result_data_fields` (`codec.ex:61`), so after `encode_result`/`decode_result` the top-level key stays the STRING `"repos"` and its inner maps are string-keyed (Jason stringifies atom keys). Consumers must read `Map.get(decoded, "repos")` with string keys.
- **Per-repo starting commits**: `resolve_foreign_repo_starting_commit(entry, repo_root)` → `{:ok, sha}` — delegates to `resolve_starting_commit/2` with `entry.base_sha`: a set `base_sha` resolves via the `^{commit}` peel (guaranteed resolvable by `load_foreign_repos/2` up-front validation), a `nil` `base_sha` resolves the foreign repo's HEAD via `PhyloGraphNode.current_head/1`; a non-resolving `base_sha` or an unborn foreign HEAD yields the structured `{:error, {:invalid_starting_commit, ref, repo_root, git_output}}` (no raw git error passthrough).
- **Up-front validation in `load_foreign_repos/2`**: after merging TOML + CLI repos, EVERY entry is validated (spec-error style, no `try/rescue`, runs in the task process before any agent spawns): the path must exist AND be a git repo (`Git.rev_parse(root)` succeeds) and a non-nil `base_sha` must resolve (`Git.rev_parse(root, base_sha)`). On failure raises `ArgumentError` naming the repo id, the path, and the problem — e.g. `"Foreign repo '<id>' at '<root>' is not a valid git repository: <inspect(reason)>"` / `"...: base_sha '<sha>' does not resolve in the repository (<inspect(reason)>)"`. `merge_foreign_repos/2` (resume/review paths) stays lenient (no validation).

### Known Issue — CompleteTask Note & Archive Refs Lag the Reported `commit_sha` (Fallback-Only Commit)

`EvoGit.Agent.Tools.CompleteTask.complete/4` writes its git note (`refs/notes/evogit`, `add_metadata_note/3`) and — when `archive` is enabled — its archive refs (`refs/genesis/archive/T<task>-A<local>-start` at `base_commit`, `-final` at the SHA it was handed; `agent/tools/complete_task.ex:284-341`) at COMPLETE time, from the pre-fallback `commit_sha` that `do_complete/2` resolves via `sync_and_get_current_commit/1` (`agent/tool_dispatch.ex:845-847`).
For a commit produced ONLY by the agent-exit auto-commit fallback those refs therefore point at the PRE-fallback SHA, lagging the `commit_sha` `merge_and_report/4` reports (the POST-fallback worktree HEAD) by one commit.
This is acceptable: the change itself is reviewable/mergeable via the `genesis/agent_<hex>` branch `merge_and_report/4` creates — only the note and archive-ref metadata can reference the pre-fallback commit.

### Known Issue — Foreign-Repo Starting-Commit Staleness & Report Last-Writer-Wins

Every foreign-repo spawn resolves its starting commit with the precedence: task-level `repo_entry.base_sha` (when non-nil) → the SPAWNING agent's OWN `foreign_repo_commits` map → the foreign repo's HEAD (`EvoGit.Agent.SubagentProcessing.resolve_foreign_phylo_commit/4`, `agent/subagent_processing.ex:673-708`).
The tracked-commit map is read from the spawning agent's own SchedMeta row (`agent/subagent_processing.ex:419` → `AgentScheduler.get_foreign_repo_commits/1`, `agent_scheduler.ex:307-312`), so it is **per-agent**: a DIFFERENT agent (another subtree, or Genesis Mode B's second root) sees `%{}` and falls back to `base_sha` / foreign HEAD — an OLD commit.
A non-nil task-level `base_sha` wins UNCONDITIONALLY (`agent/subagent_processing.ex:681`), so even the SAME agent's later foreign spawns start from the fixed `base_sha` and never from a previously tracked advanced commit.
Writable foreign spawns are gated ROOT-ONLY (`parent.depth == 0`) + one-per-batch (`agent_scheduler/subagents.ex:270-280`, depth plumbing `:166`/`:171`, root depth 0 at `agent_scheduler.ex:688-697`) — a nested or sibling agent CANNOT write into a foreign repo (`{:error, {:foreign_repo_write_not_root, msg}}`), so the literal "sibling branches over the advanced commit" topology is blocked by the gate.
Reachable stale-start paths are therefore: (a) Genesis Mode B's TWO sequential roots (architect + manager, both depth 0, independent maps) — `genesis.ex:190-196` merges the two `foreign_repo_commits` maps MANAGER-WINS, so the created `genesis/agent_<hex>` branch carries only the manager's lineage; (b) any task whose foreign entry has an explicit `base_sha`; (c) a write-capable Manager spawned INTO the foreign repo and its CROSS-repo children in a DIFFERENT repo — such a child starts at `base_sha`/that repo's tracked commit/HEAD rather than the parent's own commit (`subagent_processing.ex`, `build_subagent_phylo_node/8` foreign clause), and the parent's own `commit_sha` then OVERWRITES the tracked sha for that repo id (`subagents.ex`, `roll_up_foreign_repo_commits/3`). The Manager's OWN same-repo children (relative-path, or absolute back into the parent's repo) DO inherit the parent's live `current_commit` and ARE merged into its worktree (`collect_mergeable_results/3` merges when `spec.repo_id == parent_repo_id`).
The report takes exactly ONE sha per repo id (`Map.get(commits, repo.id)`, `helpers.ex:148-160`; fallback sha-recorded roll-up `subagents.ex:386-424`), so when two foreign commits exist for the same repo id the LAST writer wins and an earlier lineage is absent from the branch.
That earlier commit survives only as a dangling object: each agent's per-agent branch `evogit-agent-T<task>-A<local>` (`agent_scheduler/worktrees.ex:44-45`, minted from a per-task counter at `agent_scheduler/dispatch.ex:54-58`) is DELETED on agent exit for PRIMARY AND FOREIGN repos (`agent_scheduler/worktree_manager.ex:289` → `destroy_worktree/3` `:574-582`).
**No branch clobber is possible**: `Git.create_branch/3` is non-force (`git branch <name> <sha>`, `adapters/git.ex:664-667`) — an existing same-named ref fails with `{:error, {128, ...}}` and is never reset — and the task branch name is a fresh random `genesis/agent_<hex>` per `merge_and_report` call (`helpers.ex:193-196`); nothing in the runtime does `update-ref`/`branch -f`/`reset` on a `genesis/agent_*` branch.
Branch-creation failure is tolerated SILENTLY: the foreign entry keeps its `commit_sha` but gets `branch_name: nil` (`helpers.ex:173-179`, primary `:65-73`), which makes the dashboard merge/reject unavailable for that repo (`EvoGit.Review.merge_branch/3` → `{:error, :no_branch}`).
`PullRequest.try_create/4` contains no merge path — it only pushes a branch and opens a PR, and is not called by the runtime phases at all (callers: `EvoGit.Review.create_github_pr`).

### `PullRequest.try_create/4` — Steps

1. `Git.gh_available?/0` check.
2. `Git.has_origin_remote?/1`; if none, `Git.create_origin_remote/1`.
3. Base branch from `Git.origin_default_branch/1`.
4. `generate_title/2` — optional LLM (ReqLLM streaming) ≤8-word title, falls back to branch name.
5. `format_body/2` — header `## 🤖 Auto-generated by EvoGit` + agent result.
6. `Git.push_branch/2` → `Git.create_pull_request/5`.
7. Returns PR URL on success, `nil` on any failure (never raises).

## Constraints

- Both phases: ensure repo → create phylo node → load context node → build spec → run agent → handle result.
- Agent changes go to **isolated branches** (`genesis/agent_<hex>`), never the working tree. PR creation is optional (requires `gh` CLI).
- `merge_and_report/3` is shared via `EvoGit.Runtime.Helpers` — `Helpers.merge_and_report(repo_path, agent_output, phase)` where phase is `"genesis"` or `"evolve"`.
- No centralized `prompts.ex` — all prompt text lives in agent modules' `system_prompt/0` callbacks or inline in `EvoGit.Task`.
- PR creation is best-effort and never fails the phase — all PR errors are logged and return `nil`.
- Evolution `node_path` validation requires a `CONTEXT.md` at the target directory (except root).

### Task Lifecycle Boundary — Entry Opts, Finalization Report, Disk Ownership

The runtime phases are pure executors run by `TaskRegistry.TaskExecutor` inside a spawned `Task.Supervisor` process (task_executor.ex:29-117); they own NO task-level scratch/directory lifecycle. Every directory on disk belongs either to the repo (`repo_path`) or to the AgentScheduler's WorktreeManager.

- **Entry points**: `Genesis.run(objective, opts \\ [])` (genesis.ex:17), `Evolution.run(objective, opts \\ [])` (evolution.ex:11), `SelfReflective.run/1,2` (self_reflective.ex:39,43), `SkillExtraction.run(opts \\ [])` (skill_extraction.ex:12). `/runtime` has no `Prompts` module (no `prompts.ex`).
- **Genesis/Evolve opts** are built by `TaskRegistry.RuntimeOpts.build_common_runtime_opts/3` (runtime_opts.ex:16-76): `repo_path:` = `Keyword.fetch!(opts, :path)` (ABSOLUTE, resolved pre-enqueue), `mode:` atom, `task_id:`, plus put-if-present `node_path`/`starting_commit`/`foreign_repos`/`archive`/`model_id`/`agent`/`model_id_locked?`/`build_system`/`attachments`. Genesis ignores `:starting_commit` (it is read only by Evolution, evolution.ex:24,33). `SelfReflective.run/2` gets the RAW task opts + `task_id:` (task_executor.ex:116 — deliberately no `build_common_runtime_opts`, which would `KeyError` without `:path`). SkillExtraction gets `[repo_path, task_id] + pr-context keys` (task_executor.ex:83-103).
- **Return shapes**: Genesis/Evolution/SkillExtraction → `{:ok, report_map}` on success, else `{:error, reason}` (`{:error, message}` for an invalid starting commit; `{:error, {:invalid_node_path, msg}}` for evolution). SelfReflective → `{:ok, %{result:, commit_sha: nil, branch_name: nil, tag: nil}}` | `{:error, reason}` — it NEVER calls `merge_and_report`. TaskRegistry maps any non-`{:ok, _}` to `:failed`.
- **Finalization report**: produced by `Helpers.merge_and_report/3,4` → private `report_map/5` (helpers.ex:103-129) = `%{commit_sha, result, tag, branch_name, pr_url: nil, pr_title: nil, usage, agent_count, archive_records, repos: %{...}}` (+ `no_changes: true` when the POST-fallback `final_sha` == the repo root HEAD SHA). `repos` maps every STRING repo id (`"primary"` always present) to `%{commit_sha, branch_name}`. `pr_url`/`pr_title` are ALWAYS nil here — PR creation is `PullRequest.try_create/4`, called only from `EvoGit.Review`, never by the phases.
- **`notify_finalizing/1`** (helpers.ex:183-191; `nil` → `:ok`) is called IMMEDIATELY BEFORE `merge_and_report/4` at every success site: genesis.ex:53 (Mode A), genesis.ex:168 (Mode B implementation success), genesis.ex:206 (Mode B partial-success error arm), evolution.ex:114, skill_extraction.ex:31. Mode B reads its shared `task_id` at genesis.ex:67-71 (generating a random one when absent); Mode A / Evolution read `Keyword.get(opts, :task_id)` only at those call sites. No `:finalizing` broadcast on the reflect path.
- **Disk ownership** — the phases create NO task scratch dirs and never touch `EvoGit.Platform.data_dir/0` or system tmp (zero `data_dir`/`System.tmp_dir` references under `runtime/`). The only filesystem writes are: (a) `Runtime.ensure_repo/1` (runtime.ex:15-39) creating the repo dir + `.git` + a `/.genesis` `.gitignore` when `<repo>/.git` is absent; (b) `ProjectConfig.write_worktree_script/2` writing `genesis.toml` INSIDE the repo (genesis.ex:90,243); (c) `Git.create_branch/3` creating refs inside the repo's `.git` (helpers.ex:57 primary; helpers.ex:165 per writable foreign repo). `usage`/`archive_records` are produced by the AGENTS (scheduler/tools) and merely passed through here. Agent worktrees are created/reclaimed ENTIRELY by the AgentScheduler (`WorktreeManager.create_worktree_for_agent/6` + `:DOWN` reclaim) — the runtime hands over only `repo_path` via `PhyloGraphNode.new(repo_path, sha)` / `ContextNode.load/2` (genesis.ex:217-231, evolution.ex:96-99) and never sees a worktree path.

### Task Status & Event Emission (Dashboard Contract)

`EvoGit.TaskRegistry` (started by `EvoGit.Application`) tracks task status via TWO mechanisms:

1. **PubSub topic `"tasks"`**: the ONLY runtime-phase emitter is `Helpers.notify_finalizing/1` (`helpers.ex:183-191`; `notify_finalizing(nil)` = `:ok` no-op at `helpers.ex:183`), broadcasting `{:task_updated, task_id, :finalizing, node()}` immediately after `AgentScheduler.run_agent/1` returns, BEFORE `merge_and_report/4`. Callers: `genesis.ex:53` (Mode A success), `genesis.ex:168` (Mode B implementation success), `genesis.ex:206` (Mode B implementation ERROR arm — partial-success, architect result merged/reported), `evolution.ex:114`, `skill_extraction.ex:31`. No `task_id` → no-op (defensive — every task entry point goes through `TaskExecutor.execute_task/3`, which always passes one; the CLI/dashboard/shell no longer call the phases directly); the phases' own `Keyword.get(opts, :task_id)` reads (e.g. `genesis.ex:67-71` generating one when absent) keep direct API calls working. No `:failed`/`:completed`/`:running` is EVER broadcast on `"tasks"` from the runtime phase modules — the full status set (`:running`, `:cancelling`, `:completed`, `:failed`, `:cancelled`, `:finalizing`, plus `nil` for review-status/review-metadata mutations and `{:task_deleted, task_id, node()}` for deletions) is emitted by `EvoGit.TaskRegistry` (see `lib/evo_git/task_registry/CONTEXT.md`). `AgentScheduler.PubSub` uses different topics/shapes: `"agents"` → `{:agent_registered|:agent_updated|:agent_removed, ..., node}` + `{:agents_updated, node}`; `"scheduler_config"` → `{:scheduler_config_updated, node}`.
2. **Task monitor exit** (`Task.Supervisor.async_nolink` in `EvoGit.TaskRegistry`): any non-`{:ok, _}` runtime-process result (incl. `{:error, _}`) maps to `:failed`.

**Finalizing window** (between the `:finalizing` broadcast and the phase return) contains ONLY: the broadcast, (Mode B success) in-memory `Usage.add`/result merging (`genesis.ex:166-191`), and `merge_and_report/4`'s git calls — the broadcast itself is a plain fire-and-forget `Phoenix.PubSub.broadcast/3` (async cast — returns `:ok` immediately, never waits for subscribers, cannot block the wrapper), so a long dwell at status `:finalizing` is ENTIRELY the subsequent in-process work (Mode B in-memory assembly + the no-timeout git ops below), never the broadcast — `Git.rev_parse` (call at helpers.ex:44; def git.ex:309-311, plain `git rev-parse HEAD` — no `--verify`) + `Git.create_branch` per repo with commits (primary call helpers.ex:57, foreign call helpers.ex:167; def git.ex:664-667; primary + writable foreign repos), all via `Git.run/2` (git.ex:64-71) → raw `System.cmd` (git.ex:78-84) with **NO timeout (`:infinity`)** — they can block indefinitely on a slow filesystem (e.g. NFS-mounted home on a remote daemon). **Per-step visibility logging**: `merge_and_report/4` brackets every blocking git op in the window with `Logger.info` lines — `"<Phase>: Finalizing repo '<path>': resolving HEAD"` before `Git.rev_parse` (helpers.ex:42; the call itself at :44), `"<Phase>: Creating branch '<name>' at <sha7>"` before the primary `Git.create_branch` (helpers.ex:53, the existing `"<Phase>: Created branch ..."` at helpers.ex:59-61 fires right after it succeeds), and `"Creating branch '<name>' in foreign repo '<id>' at '<root>'"` / `"Created branch ... in foreign repo ... at <sha7>"` around each writable foreign-repo `Git.create_branch` (`create_foreign_branch/3`, helpers.ex:162-171). A hung op leaves the last-issued log line naming the exact step that is stuck. The git adapter itself (git.ex) has ZERO `Logger` usage by design (merge_and_report-level logs are the requirement — adapters/ is deliberately untouched); git timeouts are deliberately out of scope. `merge_and_report/4` NEVER raises and ALWAYS returns `{:ok, map}`: branch-creation/`rev_parse` failure → success maps with `branch_name: nil` (helpers.ex:65-72, 88-96); `no_changes: true` when the POST-fallback `final_sha` equals the repo root HEAD SHA (helpers.ex:74-85). It does NOT create PRs (`pr_url`/`pr_title` always `nil` at helpers.ex:115-116; PR creation is `PullRequest.try_create/4`, called only from `EvoGit.Review` `create_github_pr` review.ex:488). Worktree cleanup is NOT in the window: `WorktreeManager` reclaims + destroys via its process monitor on agent exit (`:DOWN` — `File.rm_rf` → `Git.prune_worktrees` → `Git.delete_branch`), asynchronous, never blocks the finalizing path (`Lifecycle.recycle_agent/2` before `run_agent/1` replies performs no worktree I/O).

**Critical implication**: every runtime entry point (`Genesis.run/2`, `Evolution.run/2`, `SkillExtraction.run/1`) returns whatever `AgentScheduler.run_agent/1` returns on the `error` arm — `{:error, _}` propagates to the dashboard, which marks the task `:failed`. The scheduler replies `{:error, _}` in two cases: top-level agent permanently failed (crashed `agent_max_retries` times) → `{:error, :agent_max_retries_exceeded}` (lifecycle.ex:238); top-level agent cancelled → `{:error, :cancelled}` (lifecycle.ex:72). Graceful `{:error, :recovery_failed}` / `{:error, :path_not_exist}` also map to `:failed` (exit the Task `:normal` but non-`{:ok, _}`). See `agent_scheduler/lifecycle.ex` + the `:DOWN` handler (`agent_scheduler.ex:826`) for the full crash→retry→permanent-failure cascade.

### ETS Table Ownership & Crash Resilience

- The three scheduler ETS tables (`:evogit_agent_state`, `:evogit_sched_meta`, `:evogit_archive_records`) are created in `EvoGit.Application.start/2` (`application.ex:20-22`) via the idempotent `ensure_ets_table/2`, owned by the long-lived application process; `AgentScheduler.init/1` only warns if a table is missing. Tables survive an `AgentScheduler` crash/restart.
- `EvoGit.AgentGroupSupervisor` is `strategy: :one_for_all` over `EvoGit.TaskSupervisor` + `EvoGit.AgentScheduler` — a scheduler crash kills/restarts the TaskSupervisor, tearing down ALL running agent Tasks (no orphaned agents). Agent Tasks are spawned via `Task.Supervisor.async_nolink/4` (monitored by the scheduler, NOT linked to the wrapper).
- `merge_and_report/3` is failure-tolerant: `with`/graceful `else` clauses, always `{:ok, _}` — failure → `branch_name: nil`, the agent's committed work remains valid.
- Foreign repos are loaded + validated up front (`Helpers.load_foreign_repos/2`, `helpers.ex:306-311`) and carried on the root AgentSpec via the `foreign_repos:` opt (`build_root_agent_spec/7`, `helpers.ex:518`) — the scheduler derives each agent's repo role from that list; there is no `AgentScheduler.register_foreign_repo` step in the phases.

## Agent Spawning & Coordination

### How Agents Are Spawned

Both phases build an `AgentSpec` and call `AgentScheduler.run_agent/1` (synchronous GenServer call blocking until the agent completes):

```
AgentSpec.new(context_node, phylo_node, agent_module, objective, opts)
|> AgentScheduler.run_agent()
```

The scheduler: 1) assigns a unique `task_id` (GUID), `task_number` (short integer), `agent_id` (`T<task_number>_A<task_local_id>`); 2) computes the worktree path (`worker_T<task_number>_A<task_local_id>`) into sched_meta — **no worktree I/O here**; 3) stores initial state in `:evogit_agent_state` (agent-owned) + `:evogit_sched_meta` (scheduler-owned); 4) spawns a Task running the agent loop; 5) inside the Task, `Runner.setup_dispatch_context/1` requests a FRESH worktree from `WorktreeManager.create_worktree_for_agent/6` (1-hour call; lazy per-repo init + the create pipeline — `git clean`/checkout/init script — offloaded inside WorktreeManager); 6) on `complete_task`/crash/cancel → WorktreeManager reclaims the worktree via its `:DOWN` process monitor, scheduler replies to caller.

### Root-Agent Spec Builder (`Helpers.build_root_agent_spec/7`)

`EvoGit.Runtime.Helpers.build_root_agent_spec/7` (`helpers.ex:484-493`) is the shared builder producing the root-agent `{agent_module, opts}` spec for evolution (simple AND custom modes) and genesis phase specs — resolving the default/custom root module and threading the custom-agent id + `model_id_locked` opts into the spec. New code constructing a root-agent spec should reuse it instead of hand-assembling specs at call sites.

### Agent Hierarchy by Phase

- **Genesis Mode A (Existing)**: `ContextExtractor` root → recursive `subagent_context_extractor` children (one per child dir).
- **Genesis Mode B (New)**: `Architect` root (architecture phase; optional `subagent_genesis_planner` for large-scale planning, `subagent_executor` for design artifacts — CONTEXT.md/init commands/directories/API stubs, recursive `subagent_architect` + `subagent_executor` per child dir, `subagent_manager` for implementation delegation) → then `Manager` root (implementation phase, second root agent, same `task_id`) → `subagent_executor`/`subagent_manager` subtrees. Mode B spawns TWO sequential root agents sharing a `task_id`.
- **Evolution Simple Mode**: `Manager` (target node) → `subagent_task_scheduler` (complex objectives — execution sequence), `subagent_investigator` (codebase exploration), `subagent_executor` (code changes), `subagent_manager` (child-node delegation).
- **Evolution Custom Mode**: `EvoGit.Agents.Custom` root (resolved from agents.toml via the `agent:` opt) → subagent modules declared in the custom agent definition. Custom agents are ROOT-only; the module resolves its definition (system prompt, tools, subagents, max_turns, model_id) at run time from `agents.toml` via the process-dictionary `:custom_agent_id` bridge.

### Subagent Spawning Mechanics

`AgentScheduler.spawn_sub_agents/2` (from within the agent process): validates depth ≤ `max_agent_depth`; checks the parent's path isn't git-ignored; marks parent `:waiting` (parent Task blocked; its worktree stays alive — reclaim only on process exit via WorktreeManager's `:DOWN` monitor); dispatches each subagent with its own fresh worktree + incremented task-local ID; blocks until all subagents complete, returns results in order.

## Phase Transitions

No automatic transition between Genesis and Evolution — they are dispatched as independent task commands (each CLI/dashboard/shell invocation enqueues its own task):

```bash
# Genesis — must be called first to bootstrap the Context Tree
evogit genesis "Create a web app" --mode new

# Evolution — called after Genesis (or on any existing codebase)
evogit evolve "Fix the login bug" --mode simple
```

`EvoGit.Runtime` has no combined entry point; each phase is invoked by `TaskExecutor.execute_task/3` (the task data plane — CLI/dashboard/shell all enqueue via `TaskRegistry.start_task/2`):
- `execute_task(:genesis, opts, task_id)` → `Genesis.run/2`
- `execute_task(:evolve, opts, task_id)` → `Evolution.run/2`

## Known Issues — repo_path Resolution vs. BEAM cwd (dashboard Windows path bug)

- **UNC / network-share repo roots are UNSUPPORTED for worktree-based tasks** (`\\server\share\...`, `\\wsl.localhost\...`, `\\wsl$\...` — and the forward-slash `//server/share/...` form). git-for-Windows (incl. the bundled MinGit on the desktop, `executable.ex:30`) is broken/limited for `git worktree add` on UNC roots: MSYS2 normalizes `\\server\share` ↔ `//server/share` inconsistently across the worktree metadata files (`.git` pointer + `.git/worktrees/<n>/gitdir`), so path-form comparison fails → "outside repository"/worktree-not-detected errors (git-for-windows#1320/#439, JetBrains WI-84410, fork TrackerWin#2829). Genesis creates worktrees INSIDE the repo root (`dispatch.ex:207-212` → `worktrees.ex:94-135`), so a UNC root puts all worktree I/O on the share. Even if `worktree add` succeeds, Elixir-side form-sensitive code breaks: `ensure_linked_worktree/2`'s `Path.expand` prefix check (`worktrees.ex:347-370`) and the literal `"/.genesis/workers/"` splits (`dispatch.ex:557`, `worktree_manager.ex:569`) assume forward-slash-normalized paths. **Guard (implemented)**: `EvoGit.Platform.unc_path?/1` detects the UNC share shape (`^//[^/]+/[^/]+` after separator normalization — distinct from `unc?/1`, which flags ANY double-separator marker; bare `//foo` with no share is NOT flagged) and `EvoGit.Runtime.Helpers.validate_repo_path!/1` raises an `ArgumentError` — naming the offending path, the git-for-Windows worktree-metadata limitation, and the workarounds — at task start, BEFORE any git/worktree I/O. The check runs from `Runtime.ensure_repo/1` (`runtime.ex:14`, before the `File.dir?` check, covering genesis/evolution/skill_extraction since all three call it with the `safe_expand`'d path) and from `Helpers.validate_foreign_repo!/1` (`helpers.ex:269`, before `Git.rev_parse`) so foreign repos with UNC roots fail early with the same diagnostic. Workarounds named in the message: clone/move the repo to a local drive, `subst X: \\server\share\proj` on Windows, or run inside WSL at the native Linux path.
- All three `run/2` entry points resolve a possibly-relative/name-only `:repo_path` against the **BEAM process cwd**: `genesis.ex:20`, `evolution.ex:20`, `skill_extraction.ex:13` — `repo_path = Keyword.get(opts, :repo_path, File.cwd!()) |> EvoGit.Platform.safe_expand()` (a UNC-preserving `Path.expand`).
- The desktop Tauri sidecar spawns the release launcher with **no `current_dir` set** (`desktop/src-tauri/src/sidecar.rs:147-152`) → BEAM cwd inherited from the Tauri process (typically the app install/data dir; Windows: `%LOCALAPPDATA%\genesis-desktop`). `"Test"` → `c:/Users/<user>/AppData/Local/genesis-desktop/Test`. `Runtime.ensure_repo/1` (`runtime.ex:14-32`) **silently `File.mkdir_p!`s + git-inits** a missing repo dir — a name-only path creates a stray repo under the app dir instead of erroring.
- The string "Directory does not exist: <path>" in evo_git is produced ONLY by `Helpers.validate_node_path/2` (`helpers.ex:136`), called from `evolution.ex:35` (evolve tasks with a `:node_path` opt); it prints the raw `node_path` (repo-relative sub-path), NOT the joined `abs_path`. The first branch (`helpers.ex:126-129`) rejects absolute node_paths ("Node path must be relative..."), so on a Windows host the reported full-path string comes from dashboard-side flash messages that print the raw submitted path: `apps/evo_dash/lib/evo_dash_web/live/projects_live/project_flow.ex` `open_project/2`/`select_project/2`; `projects_live.ex` `handle_palette_key/3` (`"Enter"` in `:menu` mode). The dashboard reduces a picked absolute path to its basename only in the JS File System Access API fallback (`apps/evo_dash/assets/js/app.js:171` — `fillInput(handle.name)`), after which `Path.expand/1` (`project_flow.ex:33,98,130`) resolves the bare name against the BEAM cwd.
- **No absolute-ness/existence validation of `:path`/`:repo_path` exists between the dashboard and the runtime**: `TaskRegistry.start_task/2` (`task_registry.ex:51-54`) → `RuntimeOpts.build_common_runtime_opts` (`runtime_opts.ex:17` — `Keyword.fetch!(opts, :path)`, verbatim) → runtime. Only existence checks: `Adapters.Git.run/2` pre-check `File.dir?(cd)` → `{:error, {:enoent, "Repository path does not exist: #{cd}"}}` (`adapters/git.ex:45`) and `validate_node_path/2` (node sub-paths only). `TaskRegistry.add_recent_project/2` (`task_registry.ex:481-494`) stores the path verbatim — no expansion, no validation.
- **Fix direction**: validate/expand the project path at the task boundary (TaskRegistry or RuntimeOpts) and reject non-absolute paths; the dashboard's `ProjectFlow` already expands before registering recents, so the runtime should do the same (and/or `Runtime.ensure_repo/1` should require an absolute path).

The value is the managed PER-TASK directory (`EvoGit.TaskTmpdir`, `<tmp>/genesis/task_<id>`) — the runner resolves it and installs it via `put_current/1`, and tool dispatch re-installs it inside each spawned tool task; the sandbox layer only forwards it. Detail: `../sandbox/CONTEXT.md` → "Temporary Directory Handling" + root `./CONTEXT.md` (`EvoGit.TaskTmpdir`).
- The ONLY agent-visible prompt text in the whole app that mentions temp files is the ShellTool tool description: `../agent/tools/shell_tool.ex:101-106` (POSIX suffix `", never /tmp."`) and `:144` — `"- Always use #{tmp_var()} for temporary files..."` with `tmp_var/0` = `$TMPDIR` on POSIX, `$env:TEMP` on PowerShell (`:41`). Detail: `../agent/tools/CONTEXT.md`.
- `../agent/tools/context.ex:313-318` uses `EvoGit.Sandbox.resolve_tmpdir/0` for the `git commit -F <tmpfile>` commit-message file (framework-internal use, not agent guidance).
