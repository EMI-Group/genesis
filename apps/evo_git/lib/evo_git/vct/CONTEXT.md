# VCT — Virtual Context Tree primitives
## Intent
The Virtual Context Tree (VCT) is a pure namespace layered over local OS paths: a mount binds a canonical `vct:///…` point to an absolute OS path.
It is NOT a filesystem — no directory is ever created for a point, a mount's OS path is never required to exist, and no symlink, bind mount, junction, FUSE mount or on-disk layout change is ever produced.
The mount table is ordinary relational store state (`vct_mounts` in `tasks.sqlite`); the only files the VCT owns are the OPTIONAL global context `<data_dir>/vct/CONTEXT.md` and its local git repository.
A project list is a persistent, CAPPED list of PROJECT mounts (oldest evicted), not a "recently opened" history.
A **workspace** is the one grouping layer over projects: a mount with `kind: "workspace"`, point `vct:///workspaces/<slug>`, NO OS path (`path: nil`), an ORDERED `members` list and an optional `description`.
Workspaces are nested exactly ONE level deep: a member is a project (by point) or an OS path, never another workspace, so a workspace can never contain a workspace and no cycle is representable.
VCT URLs are INTERNAL metadata: nothing renders a `vct:///` URL (or an OS path) as a CONTEXT.md file path in a prompt, and agent execution keeps one concrete repo worktree — a workspace is never an execution path.
The supervised store and its client API live one level up in `EvoGit.VCT` (`../vct.ex`), which delegates to the internal siblings in this directory (`call.ex`, `mounts.ex`, `workspaces.ex`, `global_context.ex`); consumers are `EvoGit.AgentScheduler.RemoteAPI`/`EvoGit.RemoteNode` (`projects/0`, `mount_project/2`, `forget_project/1`, `workspaces/0`, `create_workspace/3`, `workspace_members/1`, `workspaces_for/1`), the `ListProjects.list_projects` command, and prompt rendering in `EvoGit.Core.ContextNode`.
Workspaces are seeded and inspected outside the dashboard with `mix vct.workspace list|create|show` (`../../mix/tasks/vct.workspace.ex`; `create` goes through `create_workspace/3`, never by writing rows), interface: `../../mix/tasks/CONTEXT.md`.
Project mountpoints live under `vct:///projects/<name>`, workspace mountpoints under `vct:///workspaces/<name>`; everything else is a RESERVED (system) mount: `vct:///`, `vct:///projects`, `vct:///workspaces` and any other top-level namespace such as `vct:///genesis-source` (the runtime source checkout).
Reserved mounts are real mounts for resolution but are never listed as projects, never forgotten and never evicted by the cap; hosts declare them at boot through the `:system_mounts` init option (see `EvoGit.SelfReflectiveSource`), while `EvoGit.VCT.Table` only owns the rules.

- `EvoGit.VCT.Path.canonical/1` (total) and `canonical!/1` (raising) are the ONE canonicaliser: `Mount.new/3` and `Table.ensure_mount/4`/`upsert_workspace/6` go through them, and no other module re-implements point canonicalisation.
- A **member ref** is a STRING-KEYED map `%{"point" => "vct:///…" | nil, "path" => "/abs/path" | nil}` with at least one non-nil value; order in `members` is significant and duplicates are not collapsed.
- Member EXISTENCE is never required at creation: a member may be an unmounted OS path, or a mount whose recorded OS path is missing; resolution reports what is missing.
- `Mount.normalize_members/1` is the strict creation validator (`{:error, {:member_is_workspace, point}}` for a workspace point, `{:error, {:invalid_member, ref}}` for an unparseable point or a non-absolute path, `{:error, :invalid_members}` for a non-list) and `new/3` raises through it.
- `Mount.from_map/1` is the LENIENT loader: it preserves members AS STORED (a workspace ref or an unusable ref survives, only non-map elements are dropped) so a persisted row is never lost — resolution (`Table.member_mount/2`) owns the diagnosis (`:nested` / `:missing`).
- `Table.project_mount?/1` / `Table.workspace_point?/1` / `Table.reserved?/1` are the ONE definition of the mount split: a point is a PROJECT mount iff it has at least two segments and the first is `"projects"`, a WORKSPACE mount iff it has at least two segments and the first is `"workspaces"`, and RESERVED iff it is parseable and neither.
- Both project/workspace predicates accept a canonical point string or a `%Path{}` and are TOTAL: an unparseable/non-path input is neither (`false`, never a raise), so callers can tell "reserved" from "not a point at all".
- `Table.project_mounts/1` / `Table.workspace_mounts/1` filter a mount list to one kind, preserving order — the only list-facing filters callers use.
- `Table.enforce_cap/2` caps PROJECT mounts only: reserved AND workspace mounts are always retained and never count against the cap, surviving project mounts keep their original list positions, and a non-positive/non-integer cap leaves the list untouched.
- `Table.upsert_workspace/6` (`{:ok, mounts, mount}` | `{:error, :invalid_point | :invalid_mounts | member errors}`) is the PURE workspace rule: the row at the point is REPLACED IN PLACE (same list position) or appended, with `kind: "workspace"`, `path: nil`, the supplied name/members/description and `last_opened_at: now`; it never applies the cap.
- `Table.member_mount/2` (`{:ok, mount} | :missing | :nested`) resolves a member POINT-FIRST and only falls back to the exact normalized OS path when the point did not resolve; a resolved workspace is `:nested` and is never expanded.
- `Table.member_refs/1` (`{[valid_ref], [invalid_ref]}`) is the ONE documented member policy: normalise each element INDIVIDUALLY with `Mount.member/1`, keep every resolvable member (stored order, normalised) and report the unusable ones (stored order, STORED form), `{[], []}` for a non-list — so one bad ref never hides its siblings.
- `Table.workspaces_containing/3` returns the workspaces whose members match a project point, match a project OS path, or resolve to that point; membership follows `member_refs/1`'s policy (the usable members only) and `nil` inputs simply never match.
- `Table.ensure_mount/4` (`{:ok, mounts, mount, changed?}` | `{:error, :invalid_point | :invalid_path | :invalid_mounts}`) is the POINT-first, PURE rule for reserved mounts: no clock and no filesystem probe, so `last_opened_at` is never refreshed and a repeated ensure never churns a timestamp.
  Same point + same normalized OS path → the existing mount UNCHANGED (`changed? = false`, no rename); same point + different path → RE-POINT (new path, supplied name only when non-blank, point and `last_opened_at` kept, a row mounting that path elsewhere removed); no row at the point but the path mounted elsewhere → MOVE that row to the point (path, name and `last_opened_at` preserved, supplied name winning when non-blank); otherwise INSERT with `last_opened_at: nil`.
  Points stay unique and an OS path never has two rows; a workspace point is refused (`{:error, :invalid_point}`) because a workspace is never a system mount.
- `Table.register/4` stays the USER-facing open rule (it refreshes `last_opened_at`, dedupes/portability re-points and always targets a `vct:///projects/<name>` point) — do not use it for system mounts or workspaces.
- `find_by_os_path/2` and `mount_for_path/2` SKIP mounts with a nil `path`, so a workspace never owns an OS path and can never crash a path lookup.
`EvoGit.VCT` (`../vct.ex`) is the single supervised store over these primitives:
- **Internals**: the facade keeps the state, the public API and the `handle_call/3` clauses (thin dispatchers); the helpers are the sibling INTERNAL modules `EvoGit.VCT.Call` (transport + the one best-effort broadcast), `EvoGit.VCT.Mounts` (mount-table load/validate/list/resolve/remove and the persist-plus-broadcast funnel), `EvoGit.VCT.Workspaces` (workspace resolution and entry builders) and `EvoGit.VCT.GlobalContext` (global context file + lazy git repository) — no consumer needs any of them.
- **State**: `%{name, data_dir, vct_dir, store, pubsub, mounts}` — `mounts` is an in-memory READ CACHE of the `vct_mounts` table, loaded at `init/1` from `EvoGit.Store.list_vct_mounts/1` through the `:store` init opt (default `EvoGit.Store`); an invalid persisted row is dropped with a warning and a store fault loads `[]` instead of crashing boot.
- **Writes**: every mutation computes the new list, persists the WHOLE table with `EvoGit.Store.save_vct_mounts/2`, and only then replaces the cached list — so memory and the database can never disagree, and a failed persist (`{:error, :disk_full}`, `{:error, :store_unavailable}`) leaves both untouched and is returned to the caller.
- Client reads are TOTAL: a LIST or SCALAR read answers its empty shape (`[]`, `nil`, `""`), while a read whose return type is an ERROR UNION (`resolve/1`, `workspace_members/1`, `workspace_entries/2`) answers `{:error, :vct_unavailable}` exactly like a mutation — a VCT fault can never crash a caller (e.g. a boot race from `EvoGit.Core.ContextNode`), and `{:error, :not_found}` therefore means ONE thing: no such row.
- `server/0` resolves the instance at CALL time from the `:evogit_vct_server` process-dictionary key (set by `init/1` for self-calls), else the registered singleton `__MODULE__`; `start_link/1` takes `:name`, `:data_dir` (default `EvoGit.Platform.data_dir/0`), `:store`, `:pubsub` and `:system_mounts`.
- Client functions: `mount/2` (`path` + `:name` → `{:ok, mount}` | `{:error, reason}`), `ensure_mount/3` (`point` + `path` + `:name` → `{:ok, mount}` | `{:error, reason}`), `projects/1`, `search/2`, `forget/1`, `resolve/1`, `mount_for_path/1`, `vct_path_for/2`, `vct_paths_for/2`, `max_projects/0`, `global_context_path/0`, `global_context/0`, `put_global_context/1`, and the workspace surface `create_workspace/3`, `workspaces/1`, `workspace_members/1`, `workspace_entries/1,2`, `workspaces_for/1`, `workspace_point?/1`.
- **Batched reads** — `workspace_entries(opts \\ [])` answers EVERY workspace with its members ALREADY resolved in ONE `GenServer.call`: `[%{workspace: mount, members: [member_entry], missing: [member_ref], nested: [member_ref]}]`, the same roster order and `:limit` rule as `workspaces/1`, and `[]` on a dead/absent server.
  A `member_entry` is the FLAT `%{point: point, name: String.t(), path: String.t() | nil}` map, so a roster screen never has to fetch each workspace separately.
  `workspace_entries(key, opts)` is the single-workspace form and answers `{:ok, entry}` | `{:error, :not_found | :not_a_workspace | :invalid_point | :vct_unavailable}` with exactly `workspace_members/1`'s acceptance and error rules (its `opts` exists for call-site symmetry; no option is defined).
  `vct_paths_for(repo_root, relative_paths)` maps a WHOLE list of relative paths through the ONE containing-mount lookup: it returns exactly `length(relative_paths)` entries in INPUT order (`nil` = the repo is unmounted or that path escapes the mount), degrades on a dead/absent server to one `nil` per input path, and never shortens the list.
- `mount/2` requires an ABSOLUTE OS path (`{:error, :relative_path}` / `:invalid_path` otherwise) and never requires it to exist; registering the SAME path again is idempotent (refreshes `last_opened_at`, keeps the point, updates `name` only for a non-blank name), and a new path matching the name/point basename of a mount whose recorded path is GONE re-points that mount instead of adding a second one.
- `ensure_mount/3` requires a valid point (`{:error, :invalid_point}` otherwise, canonicalized before use) and the same path rules, and NEVER requires the path to exist; it applies `Table.ensure_mount/4` then `Table.enforce_cap/2` and persists/broadcasts ONLY when the merge actually changed something — a no-op replies `{:ok, mount}` with no store write, no broadcast and no `last_opened_at` change.
- `create_workspace(name, members, opts \\ [])` requires a non-blank binary name (`{:error, :invalid_name}` otherwise), derives the point from the SANITISED name (`vct:///workspaces/<Table.point_segment(name)>` — separators and control characters folded, NOT a slugifier; the display name stays free text), takes `opts[:description]`, and is an IDEMPOTENT UPSERT by point: re-creating the same name REPLACES members/description/name and refreshes `last_opened_at` (the seed path and the dashboard both use it).
  Member validation errors are propagated verbatim (`{:member_is_workspace, point}`, `{:invalid_member, ref}`, `:invalid_members`), and the cap is never applied — workspaces are UNCAPPED.
- `workspaces/1` lists WORKSPACE mounts newest first, with the same `:limit` rule as `projects/1`.
- `workspace_members/1` accepts a `vct:///workspaces/<name>` point, a `%Path{}` or a BARE workspace name (its point segment or display name) and answers `{:ok, %{workspace: mount, members: [mount], missing: [ref], nested: [ref]}}`, `{:error, :not_found}`, `{:error, :not_a_workspace}` (an existing non-workspace mount) or `{:error, :invalid_point}`; members resolve in stored order, a member reporting to nothing is reported with its STORED ref under `missing`, and a member ref that RESOLVES to a workspace point is reported under `nested` and never expanded — that split is POINT-based (`Table.member_mount/2` → `Table.workspace_point?/1`), not `kind`-based.
- `workspaces_for/1` accepts a project point, a bare project name or an absolute OS path and returns the containing workspaces newest first (`[]` when none or the input is garbage); membership matches a member point, a member path or a member that resolves to that project.
- `workspace_point?/1` is the TOTAL, PROCESS-FREE delegate to `Table.workspace_point?/1` — it works with no VCT started and never raises, which is what the task-admission execution guard relies on.
- `projects/1` and `search/2` list PROJECT mounts only unless `:include_workspaces` is `true`, which MERGES workspace mounts in and sorts by the same recency rule; without the option the lists are unchanged.
- `resolve/1`, `mount_for_path/1` and `vct_path_for/2` operate over EVERY mount, so a reserved mount resolves and answers for the paths underneath it (e.g. `vct_path_for(<genesis-source path>, "./src") == "vct:///genesis-source/src"`), while a workspace only ever resolves by POINT and never owns an OS path.
- `forget/1` refuses a RESERVED point with `{:error, :reserved_point}` — both when the key is a reserved point string (row or no row) and when an OS-path key matches a reserved mount — and accepts a project mount, a WORKSPACE point and a BARE workspace name (its point segment or display name) with `:ok` / `{:error, :not_found}` / `{:error, :invalid_point}`.
- `:system_mounts` (list of maps or keyword lists with `:point`, `:path`, optional `:name`; default `[]`) is merged at `init/1` with `Table.ensure_mount/4` IN BOOT ORDER, so boot is idempotent and a malformed entry is skipped with a `Logger.warning` (boot never fails); the merged table is persisted only when it changed, a successful change broadcasts exactly ONE `{:vct_updated, node()}`, a persist failure logs a warning and reverts the cache to the LOADED table, and an instance without the option behaves exactly as before.
- **Cap**: `max_projects/0` is 100, overridable through the app env `:vct_max_projects` (a non-positive or non-integer value falls back to the default); a registration that would exceed it EVICTS the oldest PROJECT mounts (`Table.enforce_cap/2`, `nil` `last_opened_at` = oldest), so the table stays newest-first and bounded while reserved AND workspace mounts are never evicted or counted.
- `<data_dir>/vct/` is the ONLY directory the VCT creates; a mount point is never materialized.
- The GLOBAL context is `<data_dir>/vct/CONTEXT.md`: `global_context/0` returns its contents (`""` when absent/unreadable) and `put_global_context/1` writes it verbatim, then — only for non-blank content — lazily `git init`s that directory, writes a `.gitignore` (`*.tmp`, `*.tmp.*`), stages and commits as `Update global context` (a clean tree commits nothing; git failures are logged and never lose the file); `init/1` runs the SAME best-effort sync at boot when the file already exists and is non-blank, idempotently and without ever failing boot.
- **Exactly ONE broadcast per successful mutation**: `{:vct_updated, node()}` on `"vct"`, published on the instance's `:pubsub` init option (default `EvoGit.PubSub`, so production is unchanged); a successful `put_global_context/1` and a CHANGED `:system_mounts` boot merge broadcast the same message; broadcasts are best-effort (`rescue`/`catch` → `:ok`).
- A test that asserts `"vct"` messages MUST start an isolated `Phoenix.PubSub` instance, pass it as `pubsub:` and subscribe to THAT instance — never to `EvoGit.PubSub` — otherwise a concurrently running case's broadcast is indistinguishable and `refute_receive` windows flake.
## Constraints
- No filesystem side effects except ONE `File.exists?/1` probe in `EvoGit.VCT.Table.register/4` — the portability re-point rule (a mount whose recorded OS path is gone is re-pointed instead of duplicated); `ensure_mount/4` never probes the filesystem.
- No new dependencies; the mount table is relational store state, so this directory holds no file/JSON persistence of its own (member JSON encoding lives in the store layer).
- `EvoGit.VCT.Table` never touches a process, a data dir, the store or PubSub, so it stays unit-testable in isolation.
- Mount points are unique within a table (`unique_point/2`); OS paths compare separator-insensitively so Windows `\` paths work, and one OS path is never mounted at two points.
- A mount's `point` is STABLE for a stable OS path (idempotent registration never renames the point); a workspace's point is STABLE for a stable name (re-creating upserts the same point).
- The project/workspace/reserved split lives ONLY in `Table.project_mount?/1`, `Table.workspace_point?/1` and `Table.reserved?/1` — never re-implement a namespace test at a call site, and never read `kind` for identity (`Mount.workspace?/1` is the mount-shaped delegate of `workspace_point?/1`; `kind` is a storage-class label only).
- The ONE canonicaliser is `EvoGit.VCT.Path.canonical/1` (`canonical!/1` where the input has already been validated) — do not add another private point parser or normaliser.
- The cap protects reserved AND workspace mounts: any code filtering or evicting a mount list must go through `project_mounts/1` / `workspace_mounts/1` / `enforce_cap/2` rather than a raw length or take.
- Workspaces are ONE level deep by construction: a workspace member may not be a workspace point, so nesting and cycles are unrepresentable, and a workspace is never expanded into its members by any VCT API.
- A workspace has no OS path and no worktree, so it is NEVER an execution path: `EvoGit.TaskRegistry.RuntimeOpts.admit_task_path/1` refuses `vct:///workspaces/…` with `{:error, :workspace_not_executable}` (and any other `vct:` point with `:vct_point_not_executable`) at task admission, and `build_common_runtime_opts/3` raises `ArgumentError` for a direct caller.
- Isolated instances use a unique `:name` + `:data_dir` + `:store` (an isolated `EvoGit.Store` owning its own database), so a test's mounts never reach the app-global table.
## Known Issues
- Every mount read is ONE `GenServer.call` into this process with a hardcoded 30 s timeout and no ETS read path, so a per-item caller pays one call per item; the batched forms (`workspace_entries/1`, `vct_paths_for/2`) collapse such a fan-out into ONE call, while `EvoGit.Core.ContextNode.load/3` still issues one `vct_path_for/2` per node of the context chain.
- Every mutation persists the WHOLE table (`Store.save_vct_mounts/2` = `delete_all` + `insert_all`) inside one immediate transaction, so a mutation is O(table size) — near the 100-project cap that is ~100 rewritten rows per project open — and workspaces are uncapped, so the table (and each write) has no upper bound.
- `put_global_context/1` runs its git init/add/status/commit synchronously inside this server (and `Table.register/4` stats candidate paths), so an unrelated mount read queues behind it for up to the 30 s call timeout.
- `EvoGit.VCT.Mount.git?/1` and `EvoGit.VCT.Table.workspace_mount?/1` are redundant spellings with no production caller, retained only because the test suite pins them; the project/workspace/reserved split is defined by `Table.project_mount?/1` / `workspace_point?/1` / `reserved?/1` alone.
