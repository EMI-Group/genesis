# Agent Scheduler Data Structures and Helper Modules

## Intent

Structs + helpers behind the `EvoGit.AgentScheduler` GenServer: `%AgentState{}` rows in ETS `:evogit_agent_summary` (ONE writer: the agent process), cross-process control data in `:evogit_agent_inbox` + `:evogit_agent_control` (`ControlPlane`), `%SchedMeta{}` rows in `:evogit_sched_meta` (scheduler-exclusive).
All four tables are created/owned by `EvoGit.Application`, never the scheduler — no heir, they must outlive a scheduler crash (which kills `EvoGit.TaskSupervisor`, i.e. every in-flight exchange worker, and through them all agent sessions, via the `:one_for_all` `AgentGroupSupervisor`; `%State{}` resets, tables keep stale rows).
Helpers are pure over `State.t()` except the GenServers (`WorktreeManager`, `PubSub.Throttle`).

## Routing Table

Leaf directory: `model_selection.ex` (schema/dispatch adapter), `state.ex`, `agent_state.ex`, `control_plane.ex`, `sched_meta.ex`, `slots.ex`, `store.ex`, `worktrees.ex`, `worktree_manager.ex`, `worktree_retry.ex`, `foreign_worktree.ex`, `dispatch.ex`, `subagents.ex`, `lifecycle.ex`, `pubsub.ex`, `throttle.ex`, `remote_api.ex`; hub `../agent_scheduler.ex`.

### Project-mount surface (Virtual Context Tree)
`RemoteAPI.projects/0` (`EvoGit.VCT.projects/1`) returns the PROJECT mounts only as `[%EvoGit.VCT.Mount{}]` newest first (a reserved/system mount such as `vct:///genesis-source` is never listed), empty when nothing is mounted or the VCT is down; `mount_project(path, name)` (`EvoGit.VCT.mount/2`) returns `{:ok, mount} | {:error, :relative_path | :store_unavailable | :vct_unavailable}`; `forget_project(key)` (`EvoGit.VCT.forget/1`) returns `:ok | {:error, :not_found} | {:error, :invalid_point} | {:error, :reserved_point}` and accepts either a VCT point or an OS path.
`RemoteNode` mirrors them as `projects(node)`, `mount_project(node, path, name)` and `forget_project(node, key)`: the local node calls `RemoteAPI` directly, a remote node goes through `call_remote/4`, and a failed transport degrades to `[]` for the list while mount/forget return the wrapper's `{:error, {kind, reason}}` so the caller can report it.
Every mount mutation on the target node emits its ONE `{:vct_updated, node}` broadcast; these RPCs add no notification of their own.

## Direct-Eval / Assistant API Safety

`RemoteAPI` is a mixed read/write RPC facade, not an authorization boundary; Assistant evaluation admits exact module/function/arity tuples, never namespace grants or `get_*`/`list_*` name patterns.
The authoritative full admission registry and facade contracts belong to `../agent/tools/elixir_eval/CONTEXT.md`; this node's admitted direct reads are `EvoGit.AgentScheduler.RemoteAPI.list_agents/0`, `EvoGit.AgentScheduler.get_config/1`, `EvoGit.AgentScheduler.paused?/0` and `EvoGit.AgentScheduler.get_llm_slot_status/0` in both read and write tiers.
Write tier additionally admits `EvoGit.AgentScheduler.update_config/1`, `EvoGit.AgentScheduler.pause/0`, `EvoGit.AgentScheduler.resume/0` and `EvoGit.AgentScheduler.RemoteAPI.reload_config/0`; unlisted MFAs and wrong arities remain denied.
Tier-2 write requires exact-code human approval and remains Dune-interpreted with exact-MFA admission; separately approved sudo is unrestricted native evaluation with full VM authority, not an expanded write allowlist or a security sandbox.
These guardrails target accidental self-corruption, not containment of a malicious attacker, and refusal never automatically escalates tiers.
Direct calls invoke the actual public APIs with unchanged arguments and actual return values under broker authorization/lifecycle checks and evaluation quotas/limits; compatible convenience facades retain their separate projections, validators and shorter deadlines.
Direct `get_config/1` preserves arbitrary key semantics, nested values and nil for unknown keys; actual direct reads are not projected or secret-safe, and output truncation is not redaction.
`RemoteAPI.get_agent_state/1` returns the native `%AgentState{}` with ONLY `context` set to nil (the field is not removed), leaving `llm_generation_params`, foreign-repo metadata and multimodal pending messages untouched, while `get_agent_history/1` exposes full native message content, so neither is a redacted assistant-safe projection.
`RemoteAPI.list_agents/0` returns an unordered, unpaged bare list of 28-key atom-keyed summaries per SchedMeta row, joining two separately copied whole ETS tables and computing compression thresholds; its metadata includes arbitrary objective text, repo/worktree paths and native module atoms rather than an Assistant-specific bounded projection.
Each summary has `id, task_local_id, repo_id, status, depth, parent_id, usage, total_tokens, compression_count, message_count, objective, result, agent_module, started_at, model_id, provider_profile_id, model_spec, llm_model, repo_root, context_path, worktree, current_commit, base_commit, task_id, task_number, retries, compression_threshold, context_window`, with `result` and `started_at` always nil and `usage` a native `%Usage{}`.
Missing sched-meta table returns `[]`, but a missing agent-state table still yields fallback summaries for existing metadata; the two-table join is not an atomic snapshot, and absent agent-state rows get zero usage/token/message counters plus nil model/repo/task-local identifiers.
RemoteAPI wrappers install no deadlines or exit containment of their own, and ETS whereis→lookup/tab2list checks have a table-deletion race; `get_agent_history/1` accepts only nil or `%ReqLLM.Context{}` context shapes and raises on other stored shapes.
`State.from_model_profiles/1,2` retains incoming profile maps verbatim as `model_profiles` and accepts a raw `:llm_generation_params` override, so neither field is a redacted inspection surface; only convenience facades project explicit safe keys, not admitted direct configuration reads.
`RemoteAPI.get_config/0` delegates directly to scheduler config with no redaction here, and `get_config_status/0` delegates to `Config.config_status/0`, whose credential/import behavior must be audited at the config/auth boundary before treating it as inert.
`RemoteAPI.list_custom_agents/0` calls `CustomAgents.ModelSelector.status/0` and `custom_tools_status/0` calls the custom-tools loader, so their read-like names do not guarantee absence of compilation or user-code loading.
`RemoteAPI` control wrappers (`start_task`, `cancel_task`, `force_kill_task`, `send_agent_message`, config/custom-agent saves, review mutations and `respond_approval`) do not ask for approval themselves, and exposing `respond_approval/2` to an assistant would let it answer the human approval gate.
`Store.get_task_info/1` returns `{:ok, task_id, task_number, task_local_id}` and `SchedMeta.session_pid` identifies the live agent session process, but raw metadata/state reads are internal and unredacted rather than safe user-facing capabilities.
`Lifecycle.cancel_agent/2` is an internal destructive state-transformer requiring the scheduler to remove refs first, not a stand-alone public cancellation API; killing an agent process externally can trigger crash retry instead of cancelling its task.

## Reload and runtime-update contracts
`RemoteAPI.reload_config/0` calls `Config.resolve/0`, `build_reload_opts/1`, then `AgentScheduler.update_config/1`, with no local validation, exception containment, file write or transaction.
`RemoteAPI.build_reload_opts/1` requires only an outer map and expects atom-keyed scheduler/sandbox maps; it emits `ModelSelection.config_opts/1`'s model options (legacy `Schema.effective_model_profiles/1` shape or canonical selection inventory plus account profiles/snapshot), plus scheduler `default_llm_max_concurrency`, `max_tool_concurrency`, `agent_max_retries`, `max_depth` (from `max_agent_depth`), `max_retries`, `max_turns`, `max_turns_root`, and sandbox `sandbox_mode`, `sandbox_resources`, `sandbox_process_resources` (from `mode`, `resources`, `process`), dropping only nil values.
`RemoteAPI.save_user_config/1` persists via `Config.save_user_config/1`, then calls reload but discards a returned reload error and returns `:ok`; a reload raise/exit still escapes, and the saved file has no rollback.
`RemoteAPI.save_credentials/1` delegates only to `Config.save_credentials/1`, with no scheduler reload.
`State.do_update_config/2` consumes the reload keys plus `llm_model`, `llm_generation_params`, `model_concurrency` and `model_concurrency_skip_floor`, ignores unknown keyword keys, and provides no type/range/schema validation of its own.
The state helper assigns explicitly present nil values, requires a genuine profile-list/map shape for profile rebuilding, and treats every truthy `model_concurrency_skip_floor` value as bypass permission; admitted direct `AgentScheduler.update_config/1` retains this actual option contract without facade validation.
The compatible `Write.update_scheduler_config/1` facade separately validates its narrow key/value contract, and standalone pause/resume use the scheduler's dedicated transitions rather than an `update_config` substitute.
Profile replacement keeps live holder/waiter/backoff/last-granted maps and non-LLM state, but rebuilds profile concurrency/default generation parameters; direct `llm_model` assignment alone does not rewrite `model_profiles` despite the nearby backward-compatibility comment.
`State.do_update_config/2` logs ONE `Logger.warning` inside that profile branch, before the `ModelSelection.update_opts/2` call, when `ModelSelection.legacy_replacement?/1` holds while a canonical snapshot is installed (`provider_profiles != []` or `model_selection_config != nil`), naming the consequence (`explicit model_spec selections will no longer resolve` → `:model_spec_schema_unavailable`) and the `ModelSelection.config_opts/1` / `RemoteAPI.build_reload_opts/1` remedy; the reply stays `:ok` and the diagnostic changes no state or return value.
Every state update sweeps available slots and broadcasts scheduler-config changes, while Linux sandbox-resource map changes enqueue an asynchronous slice update, so `:ok` is not confirmation of operating-system resource application.
These state-helper operations do not persist files or mutate existing agents' ETS configuration snapshots, and runtime changes are not durable across scheduler reinitialization.
Persistence is separately admitted through `EvoGit.Config.resolve/0,1` (read and write tiers) and `EvoGit.Config.save_user_config/1` (approved write tier), owned by the config node rather than this scheduler node.
Resolve reads defaults plus user configuration, not live scheduler runtime overrides; save validates and replaces the whole config.toml, invalidates its read cache and does not automatically reload the scheduler.
For persistent edits, resolve the full map, update only intended fields and save the full map while preserving other keys in the same approved evaluation; saving resolved configuration materializes defaults, and read-modify-save is not atomic with concurrent writers.
After a successful save, explicitly call admitted `RemoteAPI.reload_config/0` and inspect its actual result; save success is not reload success, committed effects have no automatic rollback, and boot-only settings still require restart.
`RemoteAPI.save_user_config/1` is not admitted, despite its save-and-reload convenience behavior described above.
The public `AgentScheduler.update_config/1` wrapper and hub-level rejection/reconciliation are owned by the parent directory and must be checked there separately from this helper contract.

## Throttled PubSub

- The `:agent_registered` `summary` has EXACTLY `status, depth, parent_id, task_id, task_number, objective` — NOT `message_count`/`agent_module` (only `list_agents/0` has those); `message_count` arrives via `:agent_updated` deltas.

## Agent identity: parent_id & depth (root ⇔ parent_id nil ⇔ depth 0)

- `register_agent/7` is the only writer: ROOT (`handle_call({:run_agent, spec}, ...)` → nil/0) and NESTED (`parent_id`, `parent.depth + 1`). Depth is never derived by walking a parent chain.
- Depth reaches the agent as `dispatch_ctx` `depth: meta.depth` → Runner `Keyword.fetch!(ctx, :depth)` → `LoopState.depth` + `Process.put(:evogit_agent_depth, depth)`; crash-retry resets preserve identity (`phylo_node: nil, context: nil`). The writable-foreign-repo root check is `parent_depth == 0` (threaded through `validate_single_subagent/5` → `validate_spatial_contract_for_spec/4`; the `/3` form hardcodes `0`).
- Root-only custom-agent `max_turns`: `if is_nil(parent_id)`; subagents use `state.max_turns`.
- A repo-less `:reflect` ROOT is registered with `parent_id: nil, depth: 0` (`agent_scheduler.ex:682`), so it gets `state.max_turns_root` (default 1000), not 128.
- `Dispatch.resolve_max_turns/3` NEVER reads `spec.opts[:max_turns]` (and `RuntimeOpts` has no such key): the only per-agent turn-cap sources are a root custom-agent definition's positive-integer `max_turns` and the scheduler's `max_turns`/`max_turns_root` (set at boot from `[scheduler]`, changed at runtime only by `AgentScheduler.update_config/1` for future registrations).

## Task Spawn & Starting-Commit Flow (run_agent)

`spec.phylo_node.current_commit` arrives pre-resolved (`%PhyloGraphNode{repo, base_commit, current_commit}`).
Upstream `Runtime.Helpers.resolve_starting_commit/2`: nil → `PhyloGraphNode.current_head/1` (unborn HEAD = structured error), a ref → `Git.rev_parse(repo_path, ref <> "^{commit}")`; failure → `{:error, {:invalid_starting_commit, ref, repo_path, git_output}}`. Sources: CLI `--starting-commit`; resume (`commit_sha`); Genesis Mode B (`architect_output.commit_sha || base_sha`).

`run_agent/2` (both clauses reply `{:error, :llm_not_configured}`): `task_id` from `spec.opts[:task_id]` (else random hex) → refuse `{:error, :cancelled}` while in the `:evogit_cancelling_tasks` marker → guarded `reset_task_archives/1` (`EvoGit.Store.delete_task_archives/1`) → `resolve_agent_repo_root/2` + `next_task_number/1` → `register_agent/7` (`phylo_node: nil`, `task_local_id` from 1) → paused ? queue : `try_dispatch/2`.
**Registration is STATELESS per call — a `run_agent/2` call never reuses an agent id or prior row**: `handle_call({:run_agent, spec}, ...)` (`agent_scheduler.ex:656-701`) allocates a fresh id from `state.next_agent_id` (`dispatch.ex:59-60,145`; seeded `1` at `init/1`, `agent_scheduler.ex:613`), a fresh per-task `task_local_id` (`dispatch.ex:63-68`), and INSERTs both rows (`Store.put_agent_state` `dispatch.ex:98-119`, `Store.put_sched_meta` `dispatch.ex:122-131`); no code path looks up a row by `task_id` or `objective` (the only task_id-keyed scans are `agent_ids_for_task/1` for cancel/kill, `agent_scheduler.ex:1140-1144`), and the insert never reads/merges the existing row's fields — an id reused after a scheduler-only restart is OVERWRITTEN, not resumed.
`AgentSpec.opts` keys consumed on this path are exactly `:task_id` (grouping + `reset_task_archives/1`), `:model_spec`, `:model_id_locked`, `:default_model_spec`, `:archive`, plus `:repo_less`, `:custom_agent_id`, `:attachments`, `:quality_level` in `Runner.setup_dispatch_context/1` (`runner.ex:299-327`); this subtree contains NO `:history`/`:messages`/`:chat`/`:conversation`/`:session`/`:resume_from`/`:multi_turn` option.
The initial `[system, user]` conversation is built FRESH in the agent's session start event (`agent/session/setup.ex` `build_initial_state/3`, the one-shot `Runner` path doing the same in `runner.ex:224-234` → `ContextBuilder.build_initial_messages/4`) and only THEN written to ETS `context` (`update_agent_context/2`/`Summary.publish/3`); `do_register_agent/8` never writes `:context` (struct default nil) and crash-retry clears it (`lifecycle.ex:160-163`).
Reuse within ONE run exists only as re-dispatch of the SAME id: crash retry (`lifecycle.ex:148-180`, resets `phylo_node`/`context`) and a WAITING parent resumed by `Subagents.dispatch_ready_parent/3` (`subagents.ex:522`).
`try_dispatch/2` computes `worktree_path = <repo_root>/.genesis/workers/worker_T#{task_number}_A#{task_local_id}` (`dispatch.ex`), stores it in SchedMeta BEFORE starting anything (so `cancel_agent` finds it), adds `scheduler: self()` to `dispatch_ctx`, starts the agent's session with `DynamicSupervisor.start_child(EvoGit.Agent.Session.Supervisor, {EvoGit.Agent.Session, dispatch_ctx})`, then `Process.monitor(pid)` + `ref_to_agent` + `status: :running`/`session_pid`/`phase: :starting`. An `{:error, {:already_started, pid}}` (stale registry entry) is tracked like a fresh start; any other start failure is logged and routed through `Lifecycle.handle_agent_crash/3` as `{:session_start_failed, reason}` (meta stays `:pending`, bounded retry, parent/root replied an error at permanent failure). No git/worktree work here.
`setup_dispatch_context/1` requests the worktree; `create_worktree/6` checks out `current_commit` via `EvoGit.Adapters.CowWorktree.create_worktree/5` (fallback `Git.add_worktree`), then `assign_and_prepare_worktree/3` writes the worktree-bound phylo_node (`repo: wt`) into ETS — the nil → live transition; the agent advances it via `ToolDispatch.sync_current_commit_after_tools/1` → `AgentScheduler.update_phylo_node/2`.
Subagent phylo nodes (`build_subagent_phylo_node/6`): explicit `commit_id` validated by `Git.rev_parse`, else the parent's `current_commit`; cross-repo uses tracked `foreign_repo_commits` or foreign HEAD.
**Repo root resolution**: per-agent ETS `AgentState.repo_root` first, then `Process.get(:genesis_repo_root)` (set by `Runner.setup_dispatch_context/1`, `agent/runner.ex:302,342`; read via `current_repo_root/0`) — no global `state.repo_root`; repo-init tracking lives in `WorktreeManager`, running = `map_size(state.ref_to_agent)`.

## Subagent Spawn Fan-Out Bounds & Deadlock Surface

- **Spawn is a blocking batch**: `spawn_sub_agents/2` is a `GenServer.call` with `timeout \\ :infinity`; the parent blocks until ALL subagents complete; the scheduler GenServer is NOT blocked.
- **Batch size UNBOUNDED**: one reduce over the subagent tool calls of ONE LLM response; `SubagentSchemas.schemas/1` has `path`/`objective`/`commit_id` only (no `maxItems`). Gates: `max_agent_depth`, `:path_ignored`, the spatial contract, one-writable-foreign-repo-per-batch, `{:error, :scheduler_paused}`, `:llm_not_configured`.
- **Registration is EAGER at accept** (`:pending` → `:running` + immediate spawn; `state.queue` exists only while paused) and the **worktree is created EAGERLY at child start** (`setup_dispatch_context/1` before `loop/1`), so a child HOLDS a worktree while blocked on an LLM slot; a WAITING parent keeps its live worktree too (reclaim `:DOWN`-only) and holds NO slot, so capping LIVE worktrees/agents with queueing can deadlock, whereas the implemented cap bounds CREATE-pipeline concurrency and cannot.
- **`max_depth`** — `[:scheduler, :max_agent_depth]`, `:pos_integer`, default `8`, `[min: 1]`; `validate_subagent_depth` → `{:error, :max_depth_exceeded}`; Runner `at_max_depth?/1`. Bounds DEPTH only.
- **Defensive ETS lookups**: `Store.get_sched_meta/1`/`get_agent_state/1` return `{:ok, x} | :error`, so four sites degrade when a parent is reaped mid-spawn — `spawn_validated_subagents/5` (replies `[{:error, :parent_recycled}]` per spec, bails BEFORE the `:waiting` mutation), `store_sub_result/3,4` (→ `:ok`), `maybe_resume_parent/2`, `dispatch_ready_parent/3` (still replies/resets meta, logs `"unknown"`). Covered by `subagents_test.exs` + `pubsub_test.exs`.

## Agent-facing submodule awareness (repo_notes)

`AgentSpec.repo_notes` carries the ALREADY-RENDERED git-submodules note, rendered ONCE at root spec build by `Runtime.Helpers.load_repo_notes/2` (`Git.ls_tree_gitlinks/2`; nil when none/fails) → `AgentState.repo_notes` → `LoopState.repo_notes` → `ContextBuilder.build_repo_notes_section/1`. Subagents inherit the rendered TEXT (no re-detection) — a foreign-repo subagent still carries the PRIMARY's note.

## Repo-Nil Tolerance & Repo-Less Agent Plumbing

The repo-less self-reflective agent (`EvoGit.Agents.SelfReflective`, `spec.opts[:repo_less] = true`) runs on this plumbing; nothing here runs git or creates worktrees for it.
**Nil-tolerant:** `phylo_node` defaults nil, written nil at registration + crash-retry reset (a transient nil is NORMAL); `repo_root` defaults nil, `resolve_agent_repo_root/2` returns nil for a foreign id missing from `spec.foreign_repos`;
Foreign roots are already ABSOLUTE (`EvoGit.Core.ForeignRepo.new/3` applies `Platform.safe_expand/1`, and every `normalize/1` path goes through `new/3`), so `resolve_agent_repo_root_regular/2` never expands a path, and a foreign-repo agent's ephemeral worktree lands under `<foreign_root>/.genesis/workers/worker_T<n>_A<m>` exactly like a primary one (the repo entry is matched by `spec.repo_id`, never by path); `Store.get_agent_state/1` returns the FULL `%AgentState{}` (only the RPC projection `RemoteAPI.get_agent_state/1` nils `:context`); `commit_pending_in_worktree/0` short-circuits on `Process.get(:repo_less)`; skill loading guards `repo_root && is_binary(repo_root)`; `build_agent_summary/3` nil-guards via `safe_phylo_commit/2`/`safe_context_path/1`.

The worktree skip lives ENTIRELY in `Runner.setup_dispatch_context/1` (the `if repo_less` branch, `agent/runner.ex:329-350`); `WorktreeManager.create_worktree_for_agent/6` (`worktree_manager.ex:122`) has no repo-less branch and is simply never called for such agents.

Nothing in the runtime calls `File.cd!`/`:file.set_cwd`; an agent process keeps the BEAM's launch cwd and every path is passed explicitly (`repo_path`/`repo_root` as tool roots, `cd:` on subprocess spawns).

## Provider/account selections and resource pools

`ModelSelection.config_opts/1` and `State.from_config/2` share the schema snapshot used by reload and dispatch.
When `Schema.provider_profiles/1`, `model_selections/1` and `resolve_model_spec/2` are available, options carry canonical string-keyed `provider_profiles` and `model_selection_config` for resolution without re-reading disk.
A nonempty atom- or string-keyed `llm.providers` inventory supplies canonical selections in the historical `model_profiles` field, while legacy populated, flat and empty configurations preserve `Schema.effective_model_profiles/1` exactly.
A legacy configuration without any normalized provider account emits only legacy `model_profiles` options, clearing any previous account snapshot on reload and preserving its model-less default profile and boot path rather than raising during schema resolution.
Without that schema API, legacy model profiles and scripts retain their existing behavior, while explicit model_spec fails closed rather than silently using a different model.
`State.from_model_profiles/2` accepts the same three configuration keys as options and initializes resource maps from unique provider ids when provider profiles are supplied.
`model_concurrency`, `llm_holders`, `llm_waiting`, `llm_backoff_until` and `llm_last_granted` keep their historical field names but use provider/account ids in the new configuration path.
`Slots.resolve_model_id/2` likewise keeps its historical name but returns the immutable dispatch-assigned provider id, with legacy-id-to-pool mapping only for old ETS rows lacking that field.
Distinct model or reasoning selections on one provider profile therefore share capacity and backoff, whereas separately configured provider/account profiles remain isolated.
The default-concurrency floor and PeakHourEngine skip-floor contract operate on those provider keys and preserve explicit zero-capacity pauses.
The floor is applied at BOOT, not only on runtime overrides: `State.from_config/2` always injects the resolved `[:scheduler] :default_llm_max_concurrency` (schema default 3), so an account `concurrency` BELOW that default is raised to it by `from_model_profiles/2` (explicit `0` survives); only a lowered scheduler default, or a raw `from_model_profiles/2` call without the key, keeps a lower account value.
Provider-profile reloads preserve live holder/waiter/backoff/last-granted maps and stale resource pools exactly as legacy reloads do.
`ModelSelection.update_opts/2` distinguishes a legacy `model_profiles`-only replacement from a canonical selection inventory by provider identity (`provider_profile_id`, directly or inside `model_spec`), delegating that classification to the public `ModelSelection.legacy_replacement?/1` predicate while itself staying pure.
Legacy-only replacements clear `provider_profiles` and `model_selection_config` together, restoring the legacy resolver and script-returned model ids rather than resolving new ids against stale boot accounts; an empty replacement also clears the snapshot, and that clearing is the intended behavior for a genuine legacy configuration.
Any runtime push that REPLACES model profiles for a canonical `[[llm.providers]]` configuration MUST also carry `provider_profiles` and `model_selection_config`, built by `ModelSelection.config_opts/1` or `RemoteAPI.build_reload_opts/1`; a bare `model_profiles`-only push clears the canonical resolution snapshot, so every explicit `model_spec` then fails with `:model_spec_schema_unavailable`.
Canonical selection-only inventories retain the account/config snapshot, configured defaults and shared account pools, while explicitly supplied `provider_profiles` or `model_selection_config` keys take precedence over legacy classification.
`Dispatch.resolve_selection/5` resolves an explicit STRING map from `AgentSpec.model_spec` or `spec.opts[:model_spec]` first, rejecting malformed or invalid explicit selections without fallback.
Otherwise priority is locked legacy id → script selection → `spec.opts[:default_model_spec]` → legacy `spec.model_id` (or the custom definition's legacy id) → configured default.
`opts[:default_model_spec]` is a separate canonical custom-definition fallback, never an explicit task selection or lock; runtime consumers must omit this key when no canonical definition default exists.
Its value uses string keys `provider_profile_id`, `model` (both nonblank strings) and optional `reasoning_effort`, and is validated through `ModelSelection.resolve_explicit/2` and the schema only when selected.
A present nil/malformed fallback returns `:invalid_model_spec`, an unavailable schema snapshot returns `:model_spec_schema_unavailable`, and provider/model/effort errors propagate unchanged before registration mutates ETS or counters.
Scripts still run and override this fallback; nil/error script results use it, invalid canonical script selections fail closed, and unknown legacy script ids retain their configured-default fallback.
`CustomAgents.ModelSelector` atom-keyed account/model/effort map returns use `ModelSelection.resolve/2` and `Schema.resolve_model_spec/2`, never legacy id lookup or unknown-id fallback; schema errors propagate and a state without a resolution snapshot returns `:model_spec_schema_unavailable` rather than crashing or silently changing models.
Locked inherited parent selections and explicit task selections bypass the script, and a locked legacy parent clears both the child's model_spec field and compatibility opts entry so the inherited legacy id and lock override any child canonical selection.
`Schema.resolve_model_spec/2` returns top-level `provider_profile_id`, unqualified `model`, `reasoning_effort`, `runtime_profile` and `generation_params`; its `model_spec` is the ReqLLM-ready qualified string or custom-endpoint map, NEVER the canonical task selection.
`ModelSelection` constructs the canonical STRING-keyed task selection from the top-level provider/model/effort fields, copies the ReqLLM identifier into `llm_model`, takes `generation_params` verbatim and reads the configured context window from `runtime_profile` rather than catalog metadata.
`llm_model` is therefore either a bare `"provider:model"` string or, for an account with a non-nil account-level `base_url`/`extra`, a map (`%{provider:, id:, base_url:, extra:}`) — endpoint config rides the MODEL INPUT, never the generation params, while credentials ride `llm_generation_params` (resolved top-level `:api_key` only for a non-OAuth custom `api_key_env_var`; OAuth path/`auth_mode` inside `:provider_options`).
Nothing in this node adds a per-request value (session/request id, prompt-cache key, timestamp, random or unique integer) to the selection, generation params or model input.
Legacy-id/default requests retain the resolved provider id as `model_id`, while explicit selection maps have no legacy alias (`model_id: nil`).
`State.from_config/2` and schema-backed `from_model_profiles/2` seed defaults with a nil schema request, honoring configured default provider/model/effort instead of enumeration order, and `default_pool_id/1`/`default_model_id/1` honor the configured provider without assembling generation parameters.
Only an unknown legacy string id falls back to the configured default; invalid models/efforts or duplicate provider/model definitions propagate their schema error before counters or ETS rows can change.
`AgentState` stores the canonical model_spec, runtime model/params/context window, legacy model_id, provider_profile_id and model_id_locked independently.
Registration attaches a per-AGENT-RUN prompt-cache identity: `do_register_agent/8` passes `selection.llm_generation_params` through `EvoGit.Config.Schema.LLM.with_cache_identity/3` with the scope `"genesis-#{task_id}-#{agent_id}"` (or `"genesis-agent-#{agent_id}"` without a task id), so every turn, retry and compression call of ONE agent shares a single provider cache routing key while distinct agents/subagents get distinct keys.
The identity is provider-gated inside the helper (`:openai`/`:openai_codex` only), so non-OpenAI generation params are persisted byte-identically.
`register_agent/7` returns `{integer_agent_id, state}` or `{:error, reason}` and resolves before any counter or ETS mutation.
Subagent registration handles errors per child and inherits a locked parent's entire model_spec and lock before selection; legacy locked parents retain id/lock inheritance.
The parent hub owns boot wiring through `State.from_config/2`, root registration error propagation, exposing the new config fields and any provider-oriented peak-engine/RPC integration outside this node.
Scheduler regression tests belong at `apps/evo_git/test/evo_git/agent_scheduler/model_selection_regression_test.exs`, owned by the parent test tree; tests must never be placed under `lib/` to work around node scope.

## Slot Management (Slots module)

Two independent pools of agent-ID `MapSet`s; capacity = `capacity - map_size(holders)` — leaks impossible, `release_agent_slots/2` removes the holder from both sets.

| Pool | State keys | Capacity | Backoff |
|---|---|---|---|
| LLM | `llm_holders`, `llm_waiting`, `llm_backoff_until`, `llm_last_granted` | **per-model** `model_concurrency[model_id]` (profile `concurrency`, default 3); fallback `default_llm_max_concurrency` (3) via `State.concurrency_for/2` | **per-model** on `:rate_limit` AND `:insufficient_balance` (HTTP 402) — caller duration (default 60 s, clamped to `@max_timer_ms`), self-rescheduling sweep; one model never blocks others |
| Tool | `tool_holders`, `tool_waiting` | `max_tool_concurrency` (default `EvoGit.Platform.cpu_threads/0`) | None |

`handle_request_llm_slot/3`, `handle_request_tool_slot/3`; `handle_release_llm_slot/2`, `handle_release_tool_slot/2` (`handle_cast`); `release_agent_slots/2` (`:DOWN`: both sets, queue purge, grant); `purge_agents_from_queues/2` (replies `{:error, :cancelled}`); `grant_pending_on_resume/1` (also at the END of every config update, so 0→N grants queued waiters). Sync ops return `{:reply, :ok, state, status_updates}`/`{:noreply, state, status_updates}`, async releases `{state, status_updates}`; `status_updates` = `{agent_id, :blocked | :running}` written to ETS SchedMeta.
`default_llm_max_concurrency` is a DEFAULT per-LLM concurrency, NOT a global cap: `State.concurrency_for/2` prefers `model_concurrency[model_id]`, else the default; the map is filled only at config-load time (`State.from_model_profiles/2` at `init/1`, the `:model_profiles` update branch, or `update_config(model_concurrency: map)`), legacy config yielding `model_concurrency["default"]`. **A runtime override is a FLOOR**: `State.apply_default_llm_concurrency_override/2` sets the default AND raises every entry to `max(c, N)` (explicit `0` stays `0`), while a profile concurrency above the default still wins.

### Slot-Pool Sizing & Concurrency (state.ex + slots.ex — do not regress)

- **Config updates preserve live LLM pools**: the `:model_profiles` branch merges existing `llm_holders`/`llm_waiting`/`llm_backoff_until`/`llm_last_granted` OVER the fresh `from_model_profiles/2` maps, then `prune_empty_pools/1`.
- **Stale-model pools are swept**: `State.all_model_ids/1` = UNION of the keys of `model_concurrency`, `llm_holders`, `llm_waiting`, `llm_backoff_until`, so absent/unknown ids are still swept by `grant_pending_llm_slots`, `release_agent_slots`'s LLM cleanup and `purge_llm_waiting_queues`.
- **LLM release scans all pools**: `handle_release_llm_slot/2` iterates `all_model_ids` (an ETS model lookup picks the wrong pool once the row is gone), removes the agent from every holder set, then grants.
- **`maybe_update_model_concurrency/2`** replaces the map then re-applies the active floor, preserving explicit `0` entries, UNLESS `:model_concurrency_skip_floor` is truthy, in which case it stores the map verbatim; the PeakHourEngine owns its own floor/exemptions and uses that bypass to preserve its fixed point.
`handle_call({:update_config, opts}, ...)` → `reconcile_pool_after_update` reconciles the ReqLLM Finch pool.
- **Global pause gates EVERY pending grant** at `grant_llm_from_queue/2` and `grant_tool_from_queue/1`, so holder release, agent-death cleanup, config/floor changes and expired-backoff retry sweeps cannot reply to queued callers while `state.paused` is true.
Holder cleanup, waiter cancellation and expired-backoff clearing still run while paused; queues remain intact until resume, which applies the current account capacity, peak-zero and backoff rules.
- **`:sandbox_resources` changes (Linux) are FIRE-AND-FORGET** via `EvoGit.SandboxSlice.update_resources_async/1` (a synchronous `systemctl` update blocked every scheduler caller and crashed `SystemSampler` on its `:get_config` timeout).
- **0-capacity slots enqueue and block (peak hard pause)**: `concurrency_for/2` may return `0`; `handle_request_llm_slot/3` has no pre-check → stores `{agent_id, from, nil}` and replies `{:noreply, state, [{agent_id, :blocked}]}`; `grant_llm_from_queue/2` at 0 leaves the queue untouched; a 0→N transition grants automatically; in-flight holders are never evicted; `with_llm_slot/2` never raises.
- **Diagnostics (logging only)**: `model_concurrency updated — old=... new=... skip_floor=...` (pre-update vs post-floor); `LLM slot grant sweep (resume) — model=... capacity=... waiting_before=... granted=... waiting_after=...` (info when `granted > 0` or `capacity == 0 and waiting_before > 0`; `capacity=5 waiting_before=3 granted=0` = queued-waiter-never-granted). `handle_retry_llm_waiting/1` self-reschedules while any model sits in future backoff (max across `all_model_ids/1` + epsilon read at CALL time from `:llm_backoff_sweep_epsilon_ms`, fallback `@default_sweep_epsilon_ms` 1000 ms, in BOTH timer sites — shrinkable in tests).

### LLM-model resolution gotchas (scheduler state vs config file)

- **Boot/reload share `ModelSelection.config_opts/1`** — legacy `model_profiles` preserves `Schema.effective_model_profiles/1` (including one model-less `"default"` profile when unconfigured), while a canonical nonempty `llm.providers` configuration uses the canonical selection inventory and schema-configured default, never stale flat keys.
`EvoGit.CatalogWarmup` uses `Schema.effective_model_profiles/1`'s per-account runtime projection rather than the scheduler's canonical inventory, so it remains provider-compatible without changing the scheduler's public legacy profile shape.
- **Runtime `:model_profiles` updates have NO flat fallback**: `llm_model` comes from `Map.get(first_profile, :model)` only, so nil/absent silently sets `state.llm_model = nil` and the update is ACCEPTED (nil-rejection checks only an explicit `:llm_model => nil` OPTS key). Reload paths never push `:llm_model`.
- **Dispatch selection**: `resolve_selection/5` resolves a task `model_spec` first and never falls back on its errors; otherwise `effective_model_id/5` applies lock → script → canonical definition fallback → legacy/custom id → configured default priority.
Canonical definition fallbacks use `ModelSelection.resolve_explicit/2`; scripts and legacy/default requests resolve through `ModelSelection` when a schema snapshot exists.
Legacy fixtures with no `model_selection_config` retain `resolve_model_for_agent/2` (unknown id → warn + first profile; nil id → first profile), with model = `Map.get(profile, :model, state.llm_model)` (fallback only when the key is ABSENT).
- **Slot-side resolution reads ONLY `:evogit_agent_summary`** (`:evogit_sched_meta` only by `Store.depth_of/1`): `Slots.resolve_model_id/2` prefers immutable `Store.get_provider_profile_id/1`, maps old rows' legacy model ids through `State.pool_id/2`, and uses `State.default_pool_id/1` for missing bindings — no separate default pool or capacity bypass.
- **`get_llm_slot_status/0` is keyed by resource-pool id**: provider/account ids for schema-backed state, legacy model-profile ids for legacy fixtures; `{id, %{used: holders, waiting: queue_len, capacity: concurrency_for}}` ranges over `State.all_model_ids/1`, including configured idle pools and live/stale pool entries.
- **`run_agent` rejection clauses**: (a) `%State{model_profiles: []}` — reachable only via `update_config(model_profiles: [])` (tests use this, `test/evo_git/runtime/evolution_test.exs`); (b) `llm_model: nil` with `model_profiles == nil` — effectively DEAD. Both reply `{:error, :llm_not_configured}`.
- **No file-watching**: config changes ONLY via `update_config/1` (dashboard save → reload_config; evo_dash ConfigIO; `PeakHourEngine`); `get_config` serves in-memory values while `Config.resolve()`/`config_status()` are file-fresh.
- **Selection and resource identity are separate**: `AgentState.model_id` retains the optional legacy selection id, `model_spec` is the full canonical string-keyed selection, and immutable `provider_profile_id` keys shared provider/account capacity and backoff independently of concrete request model or reasoning effort.
- `Dispatch.register_agent/7` applies `ModelSelection.inherit/2` at the scheduler boundary, so a locked parent's entire canonical selection and lock override child-supplied picks before scripts or legacy ids are considered.
- `RemoteAPI.list_agents/0` summaries expose `model_id`, `provider_profile_id`, `model_spec` and `llm_model`, allowing consumers to distinguish configured aliases, resource pools and concrete requests.

## Worktree Lifecycle (WorktreeManager + Worktrees)

**Fresh per agent run** — no pool, no reuse across retries.

1. **Lazy per-repo init** on the FIRST create for a repo: rm_rf `.genesis/workers` → `git worktree prune` → orphaned `evogit-agent-*` cleanup → mkdir_p (never from the scheduler). Gated on the **persistent marker** `:evogit_worktree_repos` (app-owned ETS, read via `:ets.whereis` — missing = "uninitialized"): **present** (manager-only restart) → wipe skipped, only `mkdir_p_retry/2`; **absent** (first request or genuine BEAM restart) → full wipe, then the marker is recorded. **PRIMARY-ONLY destructive steps** when `primary?` (from `spec.repo_id` via `EvoGit.Core.ForeignRepo.primary?/1`); foreign repos get only prune + mkdir_p + marker. `mkdir_p_retry` raises `File.Error` on exhaustion — safe because the marker is written before the first worktree exists.
2. **Request path**: `create_worktree_for_agent/6` (`:infinity`) offloads to a MONITORED Task (`run_create/6`) replying exactly once — result, or `{:error, reason}` when the create fun raises/throws/exits (`report_create_failure/3`) or the task dies silently (`create_monitors` `:DOWN` net, `handle_create_task_down/4`) — plus the `{:create_finished, agent_id}` permit-release cast.
3. **Create pipeline** (`prepare_new_worktree/5`): destroy leftover dir/branch (rm_rf failure escalates) → CoW create via `EvoGit.Adapters.CowWorktree.create_worktree` (fallback `EvoGit.Adapters.Git.add_worktree`, the uniform `{:ok, v} | {:error, {tag, output}}` adapter; failure → `{:error, {:worktree_create_failed, msg}}`) → `assign_and_prepare_worktree/3` → `run_init_script/3` (genesis.toml `[worktree]` script, primary only; env `SOURCE_REPO_PATH`/`SOURCE_WORKTREE_PATH`/`TARGET_WORKTREE_PATH`; Windows via `Platform.shell_args/1` → PowerShell `-EncodedCommand`, `EvoGit.Powershell`).
4. **Monitor-based reclaim**: `:DOWN` for ANY reason (including after a successful completion) → `destroy_worktree/3` in FOUR ordered steps (`worktree_manager.ex:699-731`): `BackgroundJobs.reap_under(worktree_path)` under `safe_reap/1` (a detached job whose cwd is inside the dir would hold it open) → `rm_rf_retry/2` → only AFTER the dir is gone `Git.prune_worktrees(repo_root)` → `delete_branch_tolerant(repo_root, branch_name)`; rm_rf failure logs ERROR and skips prune + branch delete. A failed CREATE-path rm_rf returns `{:error, {:worktree_create_failed, msg}}` and also SKIPS prune — a dir surviving WITH its `.git` file + registration is safe, while a partially-removed dir that is pruned becomes a PLAIN unregistered dir (the leak precondition). Idempotent; `recycle_agent/2`, `cancel_agent/2` and permanent failure never delete worktrees; after a manager-only restart `rebuild_monitors/1` re-monitors live agents from `:evogit_sched_meta` + `:evogit_agent_summary`, skipping missing/stale rows.
   Reclaim is keyed ONLY by the agent process monitor — the manager never removes a worktree on task completion, and `:evogit_sched_meta`/`:evogit_agent_summary` rows are deleted by the scheduler (`Lifecycle.recycle_agent/2`), not here.

### Repo-root derivation from a worktree path (only source: a literal string split)

`Worktrees.repo_root_from_worktree/1` (`worktrees.ex:33-38`) is `String.split(path, "/.genesis/workers/", parts: 2)`; a path with no such suffix is returned UNCHANGED (`[_] -> worktree_path`), so it is only correct for the primary per-agent worktree layout — the persistent foreign read view (`<root>/.genesis/foreign_repos/<id>`) and any mount outside `workers/` must NOT be passed through it.
It has exactly TWO callers: `Dispatch.resolve_agent_repo_root_regular/2` (`dispatch.ex:681`, primary branch) and `WorktreeManager.rebuild_monitor/3`'s fallback when `AgentState.repo_root` is nil (`worktree_manager.ex:828`). Both run on `Path.join/Path.expand`-normalized forward-slash paths only (see the Windows note below).
`task_number` is computed ONCE per task from the ROOT agent's repo root (`agent_scheduler.ex:678-679` → `Dispatch.next_task_number/1`, a `File.ls` scan of `<repo_root>/.genesis/workers` for `worker_T<n>_` maxima — `1` when the dir is missing, `dispatch.ex:164-190`) and every subagent inherits the SAME number (`subagents.ex:93` passes `parent.task_number`). Since each mounted repo owns its own `.genesis/workers`, the `worker_T<n>_A<m>` dir names and the `evogit-agent-T<n>-A<m>` branch names REPEAT across repos — they are unique per repo only, never task-globally.

### Worktree Allocation & I/O Concurrency Model (creation admission-bounded; deletion serialized)

**Creation is admission-bounded**: `accept_request/8` registers each request `:queued` on the FIFO `admission_queue`; `admit_next/1` starts requests while `creating_count < max_concurrent_creation/0` (app env `:max_concurrent_worktree_creation`, default 4, read at ADMISSION time), flipping each to `:creating` and spawning an independent `Task.start`; a permit lasts one pipeline and is released by the `{:create_finished, agent_id}` cast (from `try/after`). Agent entries carry `status: :queued | :creating | :live`. **Caps CREATE-pipeline concurrency, NOT live worktrees/agents**; the rest is per-`agent_id` serialization plus synchronous deletion inside `handle_info({:DOWN, ...})`.

### WorktreeRetry — transient filesystem failure retries

Transient set: `:eacces`, `:eperm`, `:eexist`, `:enotempty`, `:ebusy`, `:again`, `:eintr`; `:enoent` deliberately absent — "not found" means the goal is met (`rm_rf_retry/2` → `{:ok, []}`). Retryable: 2-/3-tuple fs errors, git `{:error, {tag, output}}` and binary error shapes — EXCEPT repo-gone outputs (`repo_gone_output?/1`).
Delays: `delay_stream/1` precedence is an explicit `:delays` opt → the CALL-TIME app-env seam `Application.get_env(:evo_git, :worktree_retry_delays)` (test-only) → the production default `exponential_backoff(50, 2) |> cap(200) |> take(3)` = `[50, 100, 200]` (a leading `0` "first attempt now" delay is always prepended, so 4 attempts).

## Persistent Foreign-Repo Worktrees (ForeignWorktree)

`ForeignWorktree` owns the PERSISTENT worktree of every WRITABLE non-primary foreign repo at `<root>/.genesis/foreign_repos/<id>` (`ForeignRepo.worktree_path/1`) — a stable READ view of the latest committed state, addressable by absolute path (`ForeignRepo.resolve/2`, `ContextBuilder.build_foreign_repos_section/1`); it lives OUTSIDE `.genesis/workers/`, so the primary-only wipe and `destroy_worktree/3`/`destroy_leftovers/3` never touch it, the MAIN HEAD never moves, and it is NOT torn down at task end. A foreign agent's WRITE workspace remains its ephemeral worktree.
API: `start_commit/1` (`base_sha` else repo HEAD), `ensure/2` (idempotent create-or-reset; non-writable → no-op; create = `mkdir_p_retry` → `Git.add_worktree(root, wt, sha)` detached, no branch → prune + one retry; update = `Git.checkout(wt, sha)` with `Git.reset_hard/2` fallback), `ensure_all/1` (best-effort, never raises), `sync_from_agent/0`, `worktree_path/1`.

**Hooks**: `Runtime.Helpers.load_foreign_repos/2` calls `ensure_all/1` after validating (before any spawn — `runtime/helpers.ex:317`); `Agent.Runner.run/3`'s `try/after` calls `sync_from_agent/0` right after `commit_pending_in_worktree/0` on EVERY exit path (`agent/runner.ex:56-62`), advancing the agent's OWN repo worktree (id-matched via `Process.get(:evogit_repo_id)`) to `Process.get(:repo_path)`'s HEAD — no-op for primary/repo-less agents, last-writer-wins. NOT torn down at task end (reused/reset by the next task).
`ensure_all/1` filters to `writable == true and not ForeignRepo.primary?(repo.id)` (`foreign_worktree.ex:102`), so a repo entry whose id is literally `"primary"` is never provisioned, and `sync_from_agent/0` only advances `writable` entries (`foreign_worktree.ex:240`).

## Session-Owned Agent Lifecycle (re-keyed from the agent Task)
Every agent is ONE `EvoGit.Agent.Session` started by `Dispatch.do_try_dispatch/4` under `EvoGit.Agent.Session.Supervisor`; there is no per-agent `%Task{}`, and `ref_to_agent` keys on the SESSION monitor ref.
`SchedMeta.session_pid`/`mode`/`phase` are a BEST-EFFORT mirror only — the AUTHORITATIVE live phase is `EvoGit.Agent.Session.inspect/2`.
The ONE terminal delivery is `{:agent_session_result, agent_id, session_pid, result}`, sent BEFORE the session stops; `AgentScheduler.handle_info/2` admits it only when the agent's `SchedMeta.session_pid` is `nil` (already recycled) or equals the sender, and otherwise logs at `:debug` and ignores it (stale session or unknown agent).
A session START failure is routed through `Lifecycle.handle_agent_crash/3` as `{:session_start_failed, reason}`, so it is retried up to `agent_max_retries` and the parent/root is replied an error at permanent failure — never silently dropped.
Force cancel uses `EvoGit.Agent.Session.cancel(pid, :force)` with a bounded wait plus a `Process.exit(pid, :kill)` fallback, and a `nil` `session_pid` (registered but never dispatched) is a no-op.
Worktree create/reclaim is keyed on the session pid (`Setup.bind_worktree/2` passes `self()`), so a WorktreeManager-only restart re-monitors `SchedMeta.session_pid`.

## Agent Lifecycle (Lifecycle module)

1. `recycle_agent/2` — deletes ONLY the two ETS rows (`delete_agent_state` + `delete_sched_meta`, which also drops the `SchedMeta.session_pid`/`phase` mirror; it writes `phase: :done` first) on normal completion (no worktree I/O; a `case` guard tolerates an already-gone entry), invoked ONLY from the scheduler's session-monitor `:DOWN` (`handle_agent_down/4`, `reason == :normal or meta.result_sent`), i.e. AFTER `handle_session_result/3` replied. `ref_to_agent` was popped earlier by `handle_agent_down/4`, `task_agent_counts` is dropped by `handle_session_result/3` (root) or the permanent-crash path, and the `:evogit_cancelling_tasks` marker belongs to `TaskRegistry.clear_cancelling_marker/1` — none of them are Lifecycle's.
   Consequence: `AgentState.context` (the conversation) lives ONLY in the deleted row, so an agent's transcript is unrecoverable once it is recycled (archives persist `result`/usage/settings, never messages). `cancel_agent/2` is the other path: `EvoGit.Agent.Session.cancel(meta.session_pid, :force)` (a BOUNDED call; anything but `:ok` — e.g. a session stuck in `:starting` — falls back to `Process.exit(pid, :kill)`, and a `nil` pid is a no-op) → manager `:DOWN` reclaim, replies to blocked callers, deletes ETS entries.
2. `handle_agent_crash/3` — crash-RETRY policy, ONLY from `handle_agent_down/4` when `reason != :normal AND meta.result_sent == false` (an abnormal exit AFTER delivery is a RECYCLE). `do_handle_agent_crash/4` logs `"Retry #{meta.retries}/#{state.agent_max_retries}"` BEFORE incrementing (first crash logs `Retry 0/3`), then either RETRIES (bump `retries`, `:pending`, `session_pid: nil`, `phase: nil`, reset `phylo_node`/`context`, re-dispatch via `try_dispatch/2`) or PERMANENTLY FAILS (subagent → `store_sub_result(parent_id, agent_id, {:error, :agent_max_retries_exceeded})` + `maybe_resume_parent/2`; root → `GenServer.reply(meta.from, {:error, :agent_max_retries_exceeded})`; both then `process_queue/1`). Neither deletes worktrees.
3. Limit `state.agent_max_retries` (default 3, `non_neg_integer` min 0 — `[:scheduler, :agent_max_retries]`); lifetime = `1 + agent_max_retries` attempts; the wait lives in the Runner (`setup_dispatch_context/1` runs `Process.sleep(30_000 * retries)` AFTER creating the fresh worktree).
4. Exit-shape contract: a RETURNED value (`{:error, {:llm_request_rejected, msg}}`, `{:error, :recovery_failed}`) arrives as the session's ONE `{:agent_session_result, agent_id, session_pid, result}` BEFORE that session's `:DOWN`; `handle_session_result/3` sets `result_sent: true` and replies `meta.from` VERBATIM for any non-`{:ok, %Result{}}` result — crash-retry applies ONLY to a RAISE before delivery. After `result_sent` it injects `SchedMeta.foreign_repo_commits` via `inject_foreign_repo_commits/2` (`Map.put`, NOT struct update — the field is added by the agent stream in parallel) BEFORE the parent/root split.

## Foreign-Repo Writable Spawn Gate & Per-Repo Commit Roll-up

Writable foreign repos (`EvoGit.Core.ForeignRepo.writable`, default `false`) let `:read_write` agents work in foreign repos.

- **Spawn gate order** (cross-repo `:read_write`): target writable (from `spec.foreign_repos`, never the path)? else `{:foreign_repo_read_only, msg}` → spawner ROOT (`parent.depth == 0`)? else `{:foreign_repo_write_not_root, msg}` → only accepted writable foreign spec in the batch? else `{:foreign_repo_write_serialized, msg}`.
- **Subtree roll-up is authority-gated** (`store_sub_result/3,4`): ONLY a child that is ITSELF a writable agent in its own foreign repo may advance `SchedMeta.foreign_repo_commits` — `repo_id` a binary `!= "primary"`, `agent_module.agent_type() == :read_write`, task-level `spec.foreign_repos` entry `writable: true`; it rolls up its result's subtree map child-wins via `Map.merge`, then records its OWN `commit_sha` via `Map.put`. A LOCAL/PRIMARY or READ-ONLY child (even a probe whose `commit_sha` is its starting commit) leaves the map EXACTLY as-is.
- **Injection + getter**: the `Map.put` happens BEFORE the parent/root split, so the ROOT's result carries what the runtime reads for the per-repo report; `AgentScheduler.get_foreign_repo_commits/1` returns the SPAWNING agent's OWN map (`%{}` when missing), consumed by `agent/subagent_processing.ex` to seed the next subagent phylo-node starts (`resolve_foreign_phylo_commit/4`, precedence task-level `base_sha` → tracked sha → foreign HEAD).

## Control Plane (the one-writer rule for `:evogit_agent_summary`)

**The agent process is the ONLY writer of its own `:evogit_agent_summary` row.** Nothing else may read-modify-write it (a whole-struct write from another process races the agent's context writes and loses updates, messages and flags). Every cross-process control datum therefore lives in `ControlPlane`'s two APP-GLOBAL `:public` named tables — created in `application.ex` beside the scheduler tables so they survive scheduler restarts, and never purged by the scheduler:

| Table | Type | Object |
|---|---|---|
| `:evogit_agent_inbox` | `:bag`, `read_concurrency` + `write_concurrency` | `{agent_id, {seq, message}}`, `seq = System.unique_integer([:monotonic, :positive])` (the scheduler serializes appends, so seq order == append order) |
| `:evogit_agent_control` | `:set`, `read_concurrency` | `{agent_id, cancel_requested, compression_count}` (3-tuple, counters positionally addressable) |

One atomic primitive per operation, never a read-modify-write: `append_message/2` = one `:ets.insert/2` (gated on the `:evogit_agent_summary` row existing, else `{:error, :not_found}` — NOT on the inbox row); `drain_messages/1` = `:ets.take/2` (one BIF that removes AND returns every object for the key, so a concurrent append is either fully drained or fully left for the next drain — never lost, never duplicated) + `Enum.sort_by/2` on `seq`; `pending_messages/1` = `:ets.lookup/2` + the same sort (a peek, never a take); `set_cancel/2` = `:ets.insert_new/2` (idempotent `{id, nil, 0}` row) + `:ets.update_element(table, id, {2, value})`; `increment_compression_count/1` = `:ets.update_counter(table, id, {3, 1}, {id, nil, 0})` → `{:ok, new_count}`; `delete/1` removes both rows (`Store.delete_agent_state/1` calls it, so a recycled agent leaks nothing).
Every read is TOTAL (`:ets.whereis/1` guard → the documented default) and every write degrades to `{:error, :not_found}`; the control plane never raises.
**The projection rule**: `Store.get_agent_state/1` overlays `cancel_requested`, `compression_count` and `pending_user_messages` (from `pending_messages/1`) onto the row it read, so every consumer — Runner, dashboard, `RemoteAPI.list_agents/0`, `elixir_eval` authorization, tests — keeps reading LIVE values although the row no longer stores them.
Consequently `Store.put_agent_state/2` and `Store.batch_update_agent/2` RESET those three fields to their struct defaults before `:ets.insert`, so a projected struct can never be written back (that would resurrect drained messages and stale flags).

## Pending User-Message Queue (shape tolerance + the `Attachments.message/1` seam)

The `:evogit_agent_inbox` table is the ONE external injection queue (drained by the Runner at the top of each turn), projected onto `AgentState.pending_user_messages` for readers. Two shapes: **legacy plain `String.t()`** stored/drained VERBATIM (byte-identical end-to-end; pinned by `lifecycle_test.exs`'s `String.contains?(&1, "being cancelled")` assertions) and the **canonical multimodal message** `%{text: String.t(), attachments: [map] | nil}`, where any atom-/string-keyed `%{text:, attachments:}` map is CANONICALIZED through **`EvoGit.Attachments.message/1`** before storing. `Attachments.validate_message!/1` enforces caps (`Attachments.validate/1`) and raises a descriptive `ArgumentError` — never swallowed, nothing queued. Attachments are base64 STRING maps only.
Write: `Store.append_pending_user_message/2` (guard `is_binary or is_map`; private `canonical_pending_message/1`, then `ControlPlane.append_message/2`); read: `Store.drain_pending_user_messages/1` → `ControlPlane.drain_messages/1`, which returns the queue in seq order (`[]` for an absent agent). Callers: graceful cancel appends the binary `cancel_message/0`; `RemoteAPI.send_agent_message/2` → `AgentScheduler.send_user_message/2` accepts both shapes; both ride the `:agent_updated` `pending_user_messages` delta verbatim.
Delivery is best-effort and status-blind: the append checks ONLY that an `:evogit_agent_summary` row exists, so a message sent after the agent's final turn but before its `:DOWN` recycle returns `:ok` and is NEVER read (the run already returned), and once `recycle_agent/2` has deleted the row (and `ControlPlane.delete/1` both control rows) every later send answers `{:error, :not_found}` — an agent cannot be messaged back to life, because its session_pid is gone with the ETS row.

## Graceful Cancellation (cancel_requested + `:evogit_cancelling_tasks` marker)

**`AgentState.cancel_requested`** (LIVE value in `:evogit_agent_control`, projected onto the struct) — `boolean() | nil`, default nil; set by the scheduler, checked/cleared by the runner at the top of each turn, which then enters cancel-grace (save work → reply with the summary as plain text; no tool call is required — a reply with no tool calls is the ONE completion route). Store helpers: `set_cancel_requested/1,/2`, `cancel_requested?/1` (`false` when missing), `clear_cancel_requested/1` — all delegating to `ControlPlane.set_cancel/2` / `cancel_requested?/1` (an atomic single-element update; the agent's row is untouched).
**Delta-broadcast asymmetry**: `@agent_state_tracked_fields` alone produce `:agent_updated` deltas from `put_agent_state`'s struct diff — but `:pending_user_messages` and `:compression_count` can never diff there (their row fields are reset to the struct defaults on every write), so the Store helpers emit those deltas THEMSELVES: `append_pending_user_message/2` carries the whole new queue, `drain_pending_user_messages/1` carries `[]`, `increment_compression_count/1` carries the new count; `:cancel_requested` emits NO delta (only the throttled `{:agents_updated, node}` — keep it that way); `batch_update_agent/2` broadcasts the caller kwlist verbatim minus `:context`, so **any new dashboard-visible per-agent flag must go through `batch_update_agent(agent_id, flag: value)` or be added to `@agent_state_tracked_fields`**.

**`begin_graceful_cancel/1`**: (1) registers `task_id` in the `:evogit_cancelling_tasks` marker — a public `:set` ETS table created in `application.ex` and owned by the application process (survives scheduler restarts); (2) scans `SchedMeta.task_id` and per live agent appends the cancel message via **`Store.append_pending_user_message/2`** (NOT `send_user_message/2`, a self-call deadlock) + `Store.set_cancel_requested/1`, then drives the agent's SESSION with `EvoGit.Agent.Session.cancel(session_pid, :graceful)` and mirrors `phase: :cancelling` into sched_meta (best-effort: a `nil`/unreachable session is left to the pending-message drain); (3) purges the task's agents from the LLM/tool waiting queues via **`Slots.purge_agents_from_queues/2`**, replying `{:error, :cancelled}` to each blocked `from`.
Exact `cancel_message/0` text: *"The task is being cancelled by the user. Please immediately save your work: commit any uncommitted changes, then reply with a summary of what was accomplished as plain text — a reply with no tool calls ends the run and its text IS the report, so no tool call is required. You are in a grace period: finish now."*
**`clear_cancelling_task/1`** — idempotent delete, called by TaskRegistry's guarded `clear_cancelling_marker/1` at terminal transitions; **`cancelling_task?/1`** (public, `@doc false`) is the SHARED nil-safe read (missing table = not cancelling).
**Guards**: `run_agent` replies `{:error, :cancelled}` WITHOUT dispatch while the task is in the marker (blocks Genesis Mode B's second root, which shares the `task_id`); a NEW-agent registration guard gives agents registered meanwhile (subagent spawns, crash-retries, late queued agents) the cancel message + `cancel_requested`.
**`force_kill_task_agents/1`** — brutal reverse-depth `:brutal_kill` cascade (remove refs, purge queues, release slots, `Lifecycle.cancel_agent/2` deepest-first), called by `TaskRegistry.force_kill_task/1`. **RPC**: `RemoteAPI.cancel_task/1` + `force_kill_task/1`, `RemoteNode.cancel_task/2` + `force_kill_task/2` (local-direct when `node == node()`).

## Shutdown & Restart Safety

- **No `terminate/2` in the scheduler ecosystem** (`AgentScheduler`, `Slots`, `State`, `Store`, `WorktreeManager`; the app's only one is `TaskRegistry.terminate/2`) — cleanup is purely monitor-driven. On app stop `EvoGit.Supervisor` terminates children in reverse: `AgentGroupSupervisor` FIRST, whose `one_for_all` kills `EvoGit.TaskSupervisor` (every exchange worker) + `AgentScheduler`, so all agent sessions die with their workers, and WorktreeManager dies before processing queued `:DOWN`s — so `.genesis/workers/worker_T<n>_A<m>/` dirs and `evogit-agent-T<n>-A<m>` branches REMAIN on disk after any BEAM/app stop.
- **Next-start cleanup is the lazy per-repo init** on the FIRST create per repo (`rm_rf_retry` → `Git.prune_worktrees` → `clean_orphaned_branches/1` → `mkdir_p_retry`), ONLY when the marker `:evogit_worktree_repos` is ABSENT and ONLY for the PRIMARY repo; nothing is cleaned at boot without a create request.
- **Task rows survive in SQLite**: `TaskRegistry.init/1` reconciles orphaned `:finalizing` → `:failed` and `:cancelling` → `:cancelled` at boot; `:running` rows fall to the one-shot `:lease_sweep` (150 s after init; `@lease_duration 120`, `@heartbeat_interval 60_000`, `@sweep_after (@lease_duration + 30) * 1000`) → `:failed` ("Lease expired; owning instance no longer renewing"). In-flight agent ETS state (`context`, `pending_user_messages`, `cancel_requested`) is LOST on BEAM death.
- **Slot pools are memory-only**: the restarted `%State{}` has empty pools (holders cannot leak), blocked waiters (`GenServer.call` `:infinity`) exit with the scheduler, and there is no explicit shutdown gate — only `state.paused` plus per-model capacity/backoff. The `:evogit_cancelling_tasks` marker survives scheduler restarts, not app restarts.

## Worktree Safety — Main-Copy HEAD Protection (foreign repos)

The foreign repo's MAIN working copy must never have its HEAD moved pre-merge; a main HEAD on `evogit-agent-T<task>-A<agent>` yields an EMPTY review diff.

- **`Git.clean`/`Git.checkout` are only safe in a REGISTERED linked worktree — `assign_and_prepare_worktree/3` GUARDS this** via `ensure_linked_worktree/2`: `wt/.git` must be a FILE with `"gitdir: <path>"` whose `<path>` (after `EvoGit.Platform.safe_expand/2`) lies under `<repo_root>/.git/worktrees/`; `repo_root` is the explicit param from `prepare_new_worktree/5` (from `resolve_agent_repo_root/2` — NOT `spec.phylo_node.repo`, which for subagents is the PARENT's worktree). Failure → `{:error, {:worktree_prepare_failed, :not_a_linked_worktree}}`, NO git run. `rev-parse --git-common-dir` is unusable: it reports `<repo_root>/.git` for a real worktree AND for a plain dir inside the repo tree, while the repo ROOT has a `.git` DIRECTORY — all indistinguishable.
- **`delete_branch_tolerant/2` RECOVERS git's "cannot delete branch used by worktree"** (both wordings, via `branch_in_worktree?/1`): the stale registration is dropped by `WorktreeRetry.retry_on_transient(fn -> Git.prune_worktrees(repo_root) end)`, then the delete retries ONCE; a branch live in a worktree survives → `{:error, output}` (never force-deleted). Crash-retry interleavings fail safely: a stale `:DOWN` destroy can delete a fresh branch, so `git checkout` errors and main HEAD stays put.
- **LLM cd-escape into the repo root is HARD-BLOCKED at the tool layer**: `do_execute/5` (`agent/tools/shell_tool.ex`) calls `main_copy_mutation_error/3` first — if ANY resolved cd target equals `Path.expand(repo_root)` AND the command matches `@mutating_git_regex` `\bgit\s+(checkout|switch|reset|merge|pull)\b`, it returns an error string and NOTHING executes (`@cd_regex` covers absolute, dot-relative and plain relative targets; `cd_targets/2` resolves via `EvoGit.Platform.safe_expand/2`). `detect_cd_warnings/3` stays warning-only, so prompts still forbid checkout/switch/reset against the repo root.

## Multi-Repo Identity: a flat `[%ForeignRepo{}]` list, NO mount/workspace layer

The scheduler's entire multi-repo vocabulary is a flat list plus a string `repo_id` — any design that introduces mounts/virtual-tree grouping has no existing representation to hook into.

- `%EvoGit.Core.ForeignRepo{}` is `[:id, :root, :description, writable: false, base_sha: nil]` (`core/foreign_repo.ex:27`) — no parent, no mount point, no ordering; `"primary"` is the only special id.
- `AgentSpec.repo_id` / `AgentState.repo_id` default `"primary"` (`agent_spec.ex:28`, `agent_state.ex:69`); `AgentState.foreign_repos` (default `[]`, `agent_state.ex:71`) is the task-level list copied in at registration (`dispatch.ex:117`) and inherited verbatim — no update path.
- Root resolution is a LOOKUP over that list, never a tree walk: `resolve_agent_repo_root_regular/2` strips `"/.genesis/workers/"` for `"primary"`, else `Enum.find(fn repo -> repo.id == spec.repo_id end) |> %ForeignRepo{root: root}` (`dispatch.ex:676-690`).
- A foreign repo's per-agent worktree and branch reuse the PRIMARY conventions under that repo's own root (`dispatch.ex:229-236`, `worktrees.ex:44-45`) — paths are `<root>/.genesis/workers/worker_T<n>_A<m>` and `evogit-agent-T<n>-A<m>` for every repo, so two repos never share a namespace and nothing records which task touched which mount.
- `ContextNode` DOES carry `repo_id` (`core/context_node.ex:18`, `load/3` at `:101-107`; cross-repo subagent specs are built with it at `agent/subagent_processing.ex:186-192`), but the context READ drops it: `ContextNode.build_context/2` (`context_node.ex:162`) calls the 2-arity `hierarchy_nodes/2`, which tags every node `repo_id: "primary"` (`:117`, `:94`) and resolves against the `repo_path` argument (the agent's OWN worktree, `runner.ex:141-143,196`). So a foreign agent reads ITS repo's CONTEXT.md chain correctly by path alone, while node identity is effectively `path` — nothing cross-repo is keyed by `{repo_id, path}`.
- Consequence: `ContextMerge` (CONTEXT.md conflict ownership) and `Shared.validate_file_scope/4` are repo-agnostic — ownership/scope compares relative node paths only, and the sole repo-aware file gate is the read-only-foreign-repo check via `ForeignRepo.resolve_path/2` (`agent/tools/shared.ex:446-520`).

## Windows-Only Runtime Risks

Windows-only failure modes here; NONE is test-covered (the suite runs on Linux/macOS).

- **`run_init_script/3` spawns a BARE executable name**: `System.cmd(shell, extra_args ++ Platform.shell_args(cmd), cd: repo_root, stderr_to_stdout: true)`; without a shebang `shell` = `Platform.shell()` = `"powershell"`, resolved via `:os.find_executable/1` → `ErlangError :enoent` on a miss (OTP's win32 resolver hardcodes `[".exe", ".com", ".cmd", ".bat"]`, never PATHEXT, and tries cwd LAST; built-in `WorktreeInitScript` windows variants carry NO shebang). Elsewhere the class IS guarded (`EvoGit.Sandbox.None.resolve_executable/1`, `Git.gh_available?/0`); `worktrees.ex` is not.
- **Create-path raises fail safely**: `run_init_script/3` sits in `prepare_new_worktree/5`'s `with` BODY with no `try`/rescue, so a raise reaches `WorktreeManager.run_create/6`, which catches it (`rescue`/`catch :throw,:exit`) into `{:error, {:worktree_create_failed, "worktree create raised: ..."}}` while `after` still fires `{:create_finished, agent_id}`; the create Task is MONITORED too, so a death bypassing the catch replies an error and releases the permit (`handle_create_task_down/4`).
- **No POSIX-only process handling**: no `:os.cmd`, `System.cmd("kill", ...)`, `os_pid`, negative-pgid kill, `chmod` or `sh -c` here — kills are `Task.shutdown/2` + monitor reclaim, and git resolves through `EvoGit.Executable.resolve/1` (bundled-MinGit fallback). A create stuck in a blocking syscall holds its permit until `{:create_finished, agent_id}`, so queued callers WAIT.
- **Windows path normalization is load-bearing and HOLDS — do not "fix" it**: `Path.join/2` emits `/` and `Path.expand/2` normalizes `\` → `/`, so `repo_root_from_worktree/1`'s split on `"/.genesis/workers/"` and the `safe_expand` comparison work only via those stdlib behaviours; a raw backslash path fails to strip → `:not_a_linked_worktree` (fail-safe). `branch_name/2` has no character illegal in a Windows ref.

## AgentScheduler GenServer Hub (`agent_scheduler.ex`)

~1130 lines — agent lifecycle, per-model LLM/tool slot pools, config state + updates, cancellation markers, startup reconciliation; sub-logic lives in `agent_scheduler/`.
**Lazy config-read rule (do not regress)**: single-key config reads inside the scheduler MUST use the lazy private `config_value/2`, never an eagerly built full config map — `config_map/1` evaluates `Platform.sandbox_backend()` and `Sandbox.capabilities()` on every call, which deterministically regressed the system_sampler tests. `config_map/1` is used ONLY for the full `:get_config` reply; `@config_keys` (16 keys) enumerates the fields.
**Boot cost of `init/1` is O(#model profiles) for LIVE STATE and KB-scale for HEAP**: `agent_scheduler.ex:520-655` only `:ets.whereis`-warns about the two app-owned tables, calls `Config.resolve()`/`Config.credentials()` (TOML read + merge + validate), resolves `Schema.effective_model_profiles/1`, builds empty per-model pools via `State.from_model_profiles/2`, and runs one best-effort `ReqLLMPool.reconcile/1` no-op — no SQLite query, no `.genesis/workers` scan, no PubSub subscribe, no timer.
**The llm_db catalog load happens BEFORE this process starts, in `EvoGit.CatalogWarmup`'s throwaway process** (a `:ignore` child of `AgentGroupSupervisor` immediately before the scheduler): `State.from_model_profiles/1` (`agent_scheduler/state.ex:182`) and the `default_params` seed (`agent_scheduler.ex:577-581`) → `Schema.LLM.llm_generation_params/1` → `model_metadata/1` → `ReqLLM.model/1` → `LLMDB.Spec.resolve/2` → `Catalog.resolve_model/2` → `Catalog.ensure_loaded!/0`, so the FIRST such call in the boot path now runs in a process that exits immediately afterwards; the read + `Jason.decode` of `deps/llm_db/priv/llm_db/snapshot.json` (~11.7 MB, ~8.7k models), the index builds and the canonicalizing digest (tens of MB of transient heap) die with it, and the durable store lands in `:persistent_term` (`:llm_db_store`). `init/1` therefore only performs WARM lookups: they re-resolve against the published catalog but never copy it (see `../config/schema/CONTEXT.md`).
A SCHEDULER RESTART does not re-pay the load either (the catalog stays in `:persistent_term`); it would only pay it if the warm-up had been skipped AND the catalog were cold — never both in a boot where a model is configured.
The live `%State{}` is KB-scale (`model_profiles` = the few configured profiles, empty slot pools; measured 2007 B / 375 words with 4 profiles), and the scheduler's heap stays KB-scale in EVERY boot mode: measured in-node on a `-mode embedded` `genesis_server` boot (4 profiles, `[sandbox] mode = "disabled"`, isolated data dir) it reads **28.8 KB at boot-finished, 66.3 KB at t=3-30 s, 53.8 KB at t=90 s** with 13.9k reductions at t=0. The SAME harness against the pre-warm-up build read **94,804.2 KB (92.6 MB) at every sample through t=90 s** (189.0M reductions, `:erlang.memory(:total)` ≈ 318 MB vs 225 MB, settled RSS 492 MB vs 396 MB): an embedded BEAM never fullswept the load's dead heap, and `init/1` (its last allocation-heavy work) never GC'd again → the whole reason the warm-up exists.
Control: a config with ZERO configured models does no catalog work at all — the warm-up is inert (its gate is the `:llm_model_metadata_fun` seam or a profile list with no `model`), `init/1` resolves no metadata, and `:persistent_term` never holds a catalog.
`Slots`, `Store`, `PubSub` and `RemoteAPI` are PLAIN modules (no GenServer/init/ETS/timer/`:pg`); the only process besides the scheduler is `PubSub.Throttle`, whose state is a single timer ref (`throttle.ex:24-33`).
`task_local_counters` is NEVER pruned (`task_agent_counts` is, at `lifecycle.ex:208,250`), so one ~100-byte entry per task_id accumulates for the scheduler's lifetime.
Nothing purges `:evogit_agent_summary` (`:ets.delete_all_objects` appears nowhere in `:evo_git`) and `init/1` resets `next_agent_id: 1`, so a scheduler-only crash leaves dead agents' rows — each carrying its full `context` — until the ids are reused.
`RemoteAPI.list_agents/0` walks EVERY `:evogit_sched_meta` row and reads that agent's state individually through `Store.get_agent_state/1` (`remote_api.ex`), so the roster reports the PROJECTED `compression_count` while no whole-table copy of all live agent contexts is built.
Remaining fix direction (NOT the boot issue, which `EvoGit.CatalogWarmup` resolved): cache per-model `%{limits, capabilities}` instead of re-resolving per spawn/compression check.

## Task-Scoped Resource Inventory (per-task on-disk artifacts + teardown hooks)

- **The ONLY on-disk artifact this subtree creates is the worktree**: `<repo_root>/.genesis/workers/worker_T<task_number>_A<task_local_id>` + branch `evogit-agent-T<task_number>-A<task_local_id>` (`.genesis` git-ignored). **`task_number` is DERIVED FROM DIRECTORY NAMES, not `task_id`**: `Dispatch.next_task_number/1` scans `.genesis/workers/worker_T*` → max+1 per ROOT spawn.
- **The worktree dir is removed in EXACTLY one function**: `destroy_worktree/3` → `rm_rf_retry` (then prune, then branch delete); callers are the `:DOWN` `:live` branch and the `:create_finished` `pending_cleanup` branch. Extra CREATE-path removals: `Worktrees.destroy_leftovers/3`, `Git.remove_leftover_worktree_dir/1`.
- **Background jobs rooted under a worktree are REAPED first** (`destroy_worktree/3` via the defensive `safe_reap/1`): `EvoGit.BackgroundJobs.reap_under(worktree_path)` runs IMMEDIATELY BEFORE `rm_rf_retry`; a dead/timed-out registry degrades to a logged no-op (`rescue` + `catch :exit` → `:ok`).
- **Reclaim follows AGENT PROCESS DEATH, never task completion**; `recycle_agent/2`/`cancel_agent/2`/`handle_agent_crash/3` do ETS deletes only; the `:finalizing`/merge path never touches worktrees.
- **The managed per-task scratch dir is NOT scheduler-owned**: `EvoGit.TaskTmpdir` (`../task_tmpdir.ex`) is created and reclaimed by `EvoGit.TaskRegistry` (`TaskExecutor.ensure_task_tmpdir/2`); `:per_repo` places it at `<primary repo>/.genesis/tmp/task_<id>`, and an app crash orphans it.
- **Cancel teardown touches NO disk** (marker insert + pending message + `purge_agents_from_queues/2`; force kill adds the brutal kills) and **archive state is persisted per agent, never buffered in RAM**. This subtree writes NOTHING under `EvoGit.Platform.data_dir/0`.

## Known Issues

- **A create pipeline that hangs FOREVER holds one admission permit, and its blocked caller is not cancellable by timeout**: `create_worktree_for_agent/6` waits `:infinity` while the create runs in an unlinked `Task.start` nothing kills, so a create stuck in a blocking syscall (wedged NFS, anti-virus holding the tree) neither fails nor returns; `creating_count` only decrements on the `{:create_finished, agent_id}` cast, so four such creates saturate the default cap of 4 and `admission_queue` starves silently (no stall detection or logging). Escapes: force-kill / graceful-cancel the task (its monitor moves the `:creating` registration to `pending_cleanup`, but the create task and its permit survive); restart `WorktreeManager` (resets `creating_count`); restart the BEAM (orphans the stuck worktrees).

## Constraints

- Data structs are plain data with no behaviour/callbacks; `Slots`, `Worktrees`, `Dispatch`, `Subagents`, `Lifecycle`, `State` are pure functions over `State.t()`. GenServer state must always be `%State{}` (struct update, not `Map.put/3`).
- `AgentState` is shared (scheduler + agent processes); `SchedMeta` is scheduler-exclusive.
- The scheduler process NEVER calls git, does blocking filesystem I/O, or calls ANY worktree function — git work happens in the agent's exchange worker (and the session for its worktree create), and ALL worktree filesystem operations (rm_rf, mkdir_p, prune_worktrees, delete_branch) belong to `WorktreeManager`. The only worktree call is the session's `Setup.bind_worktree/2` → `create_worktree_for_agent/6` (`:infinity`, the SESSION pid is the monitored owner, exactly one reply, `:DOWN` reclaim).
- Slot availability is derived from holder MapSets, never a counter. `SchedMeta.session_pid` stores the agent's `EvoGit.Agent.Session` pid (cancelled through `EvoGit.Agent.Session.cancel/2`); `ref_to_agent` keys on the session monitor ref.
- `case`/`with` guards on ETS lookups only where a genuine race can make the entry absent (`recycle_agent`, `try_dispatch`, `cancel_agent`).

### Task archive persistence (`task_agent_archives`)

A RELATIONAL table — one row per agent per task, keyed `{task_id, agent_id}`, idempotent upsert (crash-retry double-writes safe).
**The ONLY producer is `EvoGit.Agent.Completion.complete/4`** (called by `EvoGit.Agent.ToolDispatch.build_completion/2,3` when a tool-free reply ends the run) via its private `write_archive_refs/7`, which writes the `refs/genesis/archive/T{task_id}-A{task_local_id}-start`/`-final` git refs AND calls `EvoGit.TaskRegistry.put_task_archive/1` (→ `EvoGit.Store.put_task_archive/2`) at agent completion — no ETS archive buffer, no archive field in `%Result{}`, no end-of-task collection (`Lifecycle.handle_session_result/3` persists the root result unchanged; `run_agent` only resets a task's leftover rows via the guarded `EvoGit.Store.delete_task_archives/1`).
`usage` is a PLAIN MAP of the 9 canonical token/cost keys plus the derived `cache_hit_rate` (NEVER a `cost` key), rows round-trip STRING-keyed (`EvoGit.Agent.Usage.from_archive_map/1` is the consumer reader), and a crash/failure/abort writes NO row.

## Per-message timestamp metadata convention

Every message in an agent's session memory (`%ReqLLM.Message{}` list in `%ReqLLM.Context{}.messages`, held in `AgentState.context`) carries `metadata[:timestamp]` — **Unix seconds** (`System.system_time(:second)`), an atom-keyed integer like `:turn`, stamped at message-CREATION time in agent code, never in the Store.
**Single choke point — `ContextBuilder.tag_message_turn/2`** (`agent/context_builder.ex`): every message the loop produces passes through it; it sets BOTH `metadata[:turn]` and `metadata[:timestamp]`, idempotent via `Map.put_new`. `ContextBuilder.tag_message_timestamp/1` stamps just the timestamp (nudge + compression-summary sites); creation-site inventory in `agent/CONTEXT.md`.
**`Store` is a dumb pass-through** (`batch_update_agent/2` writes fields verbatim into ETS, only the broadcast kwlist transformed; `update_agent_context/2` delegates) and **no read-back exists** — the dashboard reads `msg.metadata[:timestamp]` from `RemoteAPI.get_agent_history/1`. An integer is timezone-agnostic (`DateTime` deliberately avoided) and **the dashboard interprets it as Unix SECONDS** (`EvoDashWeb.Helpers.format_history_timestamp/1`) — do NOT change granularity without updating evo_dash.
