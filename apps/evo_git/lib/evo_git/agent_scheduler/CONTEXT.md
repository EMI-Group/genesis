# Agent Scheduler Data Structures and Helper Modules

## Intent

Contains data structs and extracted helper modules used internally by `EvoGit.AgentScheduler` GenServer. The data structs back two ETS tables (`:evogit_agent_state` and `:evogit_sched_meta`) tracking agent execution state and scheduling metadata. Helper modules encapsulate slot management, worktree lifecycle, agent dispatching, subagent management, and agent lifecycle logic.

## Routing Table

None — leaf directory (modules: `state.ex`, `agent_state.ex`, `sched_meta.ex`, `slots.ex`, `store.ex`, `worktrees.ex`, `worktree_manager.ex`, `worktree_retry.ex`, `dispatch.ex`, `subagents.ex`, `lifecycle.ex`, `pubsub.ex`, `throttle.ex`, `remote_api.ex`).

## Throttled PubSub (PubSub module + throttle.ex)

`EvoGit.AgentScheduler.PubSub` provides the throttled `{:agents_updated, node}` bulk broadcast plus enriched delta broadcasts (`{:agent_registered, agent_id, summary, node}` / `{:agent_updated, agent_id, changed_fields, node}` / `{:agent_removed, agent_id, node}`). Every broadcast carries a trailing `node` element — the emitting BEAM node — added by the helpers themselves. The throttle is **supervised**:

- `EvoGit.AgentScheduler.PubSub.Throttle` (throttle.ex — a small GenServer) is a **standard child of the application supervision tree**: declared in `EvoGit.Application`'s `children` (application.ex) immediately after `{Phoenix.PubSub, name: EvoGit.PubSub}`, it runs under `EvoGit.Supervisor` (one_for_one) with the default `:permanent` restart — a crash restarts it instead of silently degrading to unthrottled broadcasts forever.
- `broadcast_agents_updated/0` casts `:schedule` to the Throttle (coalesces rapid calls into one flush `@throttle_ms` = 200ms after the last schedule). When `Process.whereis(EvoGit.AgentScheduler.PubSub.Throttle)` is nil (tests, supervisor restart window, contexts where the app isn't started), broadcasts fall back to **immediate dispatch**.
- If the Throttle exhausts the supervisor's max_restarts, `EvoGit.Supervisor` dies and takes the app down — standard OTP; the 200ms timer loop is not a realistic crash source.

## Defensive ETS lookups in Subagents

`Store.get_sched_meta/1` / `Store.get_agent_state/1` return `{:ok, x} | :error`. Four sites in `subagents.ex` use `case`-guarded lookups with graceful fallbacks (log warning + safe return) instead of bare `{:ok, x} = Store.get_*(id)` matches — a missing ETS entry (e.g. a parent's entries reaped by `cancel_agent/2` while a subagent spawn/result is in flight) never crashes the scheduler GenServer with a `MatchError`:

1. `spawn_validated_subagents/5` — missing parent agent_state → replies `[{:error, :parent_recycled}]` per spec to the blocked `from`, spawns nothing, returns `{:noreply, state}` (bails BEFORE the `:waiting` status mutation).
2. `store_sub_result/3` — missing parent sched_meta → `:ok` (result dropped; parent is gone).
3. `maybe_resume_parent/2` — missing parent sched_meta → state unchanged.
4. `dispatch_ready_parent/3` — missing agent_state (only needed for the resume log's commit SHA) → still replies/resets meta, logs `"unknown"` SHA.

Normal-path behavior is identical for all four sites. Error paths are covered by `./apps/evo_git/test/evo_git/agent_scheduler/subagents_test.exs` (e.g. the `:parent_recycled` reply) and the Throttle by `pubsub_test.exs`.

## Task Spawn & Starting-Commit Flow (run_agent)

The **starting commit is NOT decided in this directory** — it arrives pre-resolved as `spec.phylo_node.current_commit` (a `%PhyloGraphNode{repo, base_commit, current_commit}` built by the runtime phase). Upstream resolution: `Runtime.Evolution.run/2` (`runtime/evolution.ex:23`) and `Runtime.Genesis` (`runtime/genesis.ex:23`) call `Runtime.Helpers.resolve_starting_commit/2` (`runtime/helpers.ex:167-180`): nil → `PhyloGraphNode.current_head/1` (HEAD); a ref → `Git.rev_parse/2`. Sources of the ref: CLI evolve `-s/--start-commit` (`cli.ex:89`, `cli/parser.ex:34`) and task resume (`TaskRegistry.ResumeContext.apply_resume_context/3`, `task_registry/resume_context.ex:43-54` — sets `:starting_commit` to the previous task's `commit_sha`). Genesis Mode B's second root starts from `architect_output.commit_sha || base_sha` (`runtime/genesis.ex:143-144`).

Spawn flow: `AgentScheduler.run_agent/2` (`agent_scheduler.ex:80-82`) → `handle_call({:run_agent, spec}, ...)` (`agent_scheduler.ex:593-641`): derives `task_id` from `spec.opts[:task_id]` (else random hex, :595), refuses `{:error, :cancelled}` when the task is in the `:evogit_cancelling_tasks` marker (blocks Genesis Mode B's second root during cancel, :602-607), resets per-task archive (`Lifecycle.clear_archive_records`, :612), resolves repo root (`Dispatch.resolve_agent_repo_root/2`, dispatch.ex:367-386), computes `task_number = Dispatch.next_task_number/1` (scans `.genesis/workers/worker_T*`, dispatch.ex:133-159), then `Dispatch.register_agent/7` (dispatch.ex:39-117: `id = state.next_agent_id`; `task_local_id` from `state.task_local_counters` starting at 1; writes `%AgentState{}` with `phylo_node: nil` + `%SchedMeta{}` carrying the full original `spec`). Paused → queued; else `Dispatch.try_dispatch/2` (dispatch.ex:176-247): computes `worktree_path = <repo_root>/.genesis/workers/worker_T#{task_number}_A#{task_local_id}`, stores it in SchedMeta BEFORE spawning, then `Task.Supervisor.async_nolink(EvoGit.TaskSupervisor, spec.agent_module, :run, [spec.objective, dispatch_ctx])` (:225-231); the agent's Runner requests the fresh worktree from `WorktreeManager.create_worktree_for_agent/6` (runner.ex:182-189).

**Checkout to the starting commit** happens in `Worktrees.create_worktree/6` (worktrees.ex:96-137): `commit_sha = spec.phylo_node.current_commit` is passed to `EvoGit.Adapters.CowWorktree.create_worktree/6` (or fallback `Git.add_worktree(repo_root, worktree_path, commit_sha, branch_name)`), then `assign_and_prepare_worktree/2` (worktrees.ex:233-259) runs `Git.clean` + `Git.checkout(wt, branch_name)` and writes the worktree-bound phylo_node (`repo: wt`, `base_commit: spec.phylo_node.base_commit`, `current_commit: commit_sha`) into AgentState ETS — this is where `AgentState.phylo_node` transitions from nil to the live node. During the run the agent advances it via `ToolDispatch.sync_current_commit_after_tools/1` / `sync_and_get_current_commit/1` (agent/tool_dispatch.ex:50-84) → `AgentScheduler.update_phylo_node/2` (agent_scheduler.ex:226-230). Subagent phylo nodes: `build_subagent_phylo_node/6` (agent/subagent_processing.ex:569-601) — explicit `commit_id` validated via `Git.rev_parse`, else parent's `current_commit`; cross-repo uses tracked `foreign_repo_commits` or foreign HEAD (:603-614).

**No reuse / no resume-checkout special-casing in the scheduler layer**: `prepare_new_worktree/5` always destroys leftovers (dir, branch) and creates fresh (worktrees.ex:61, 139-170) — a branch that already has commits is deleted first, then re-created from the spec's starting commit. The only exception is `Subagents.dispatch_ready_parent/3` (subagents.ex:355-390): a waiting parent keeps its LIVE worktree (no new checkout). A resumed TASK's "existing commits" are handled entirely upstream by setting `:starting_commit` in opts (see `task_registry/resume_context.ex`).

| Module | Description |
|---|---|

| `EvoGit.AgentScheduler.AgentState` | Live agent state in `:evogit_agent_state` ETS — context_node, phylo_node, objective, repo_id |
| `EvoGit.AgentScheduler.SchedMeta` | Scheduler-private metadata in `:evogit_sched_meta` ETS — status, depth, worktree, subagent tracking |
| `EvoGit.AgentScheduler.Slots` | Pure-function LLM/tool slot management using holder MapSets with FIFO queuing and rate-limit backoff |
| `EvoGit.AgentScheduler.Worktrees` | Pure helper functions for the worktree create pipeline (no own state): `workers_dir/1`, `assign_and_prepare_worktree/2` (git clean + checkout agent branch + bind `phylo_node.repo = worktree` in ETS), `run_init_script/3` (genesis.toml `[worktree]` script; env `SOURCE_REPO_PATH`/`SOURCE_WORKTREE_PATH`/`TARGET_WORKTREE_PATH`), `prepare_new_worktree/5` (the full fresh-create pipeline: destroy leftover dir/branch via `destroy_leftovers/3` — same retried `WorktreeRetry` helpers, never raises (runs in the offloaded create task) → CoW create via `EvoGit.Adapters.CowWorktree.create_worktree` with `Git.add_worktree` fallback → assign_and_prepare → init script for primary repo only), `branch_name/2` (single source of truth: `"evogit-agent-T#{task_number}-A#{task_local_id}"`), `delete_branch_tolerant/2` (treats "branch not found" AND repo-gone outputs — "Repository path does not exist" / "not a git repository" via `WorktreeRetry.repo_gone_output?/1` — as `:ok`: a vanished repo implies the branch is gone with it, so the goal is already met; eliminates spurious warnings when stale `:DOWN` cleanup races a repo teardown). No fast/slow path — every agent run gets a FRESH worktree. |
| `EvoGit.AgentScheduler.WorktreeManager` | Stateful GenServer owning the entire worktree lifecycle (supervised in `EvoGit.Application`, same name). Lazy per-repo initialization (`maybe_init_repo/2`: rm_rf workers dir → `Git.prune_worktrees` → orphaned `evogit-agent-*` branch cleanup → mkdir_p) runs on the FIRST create request for a repo — never from the scheduler. All init steps go through `WorktreeRetry`: `rm_rf_retry` for the workers-dir rm_rf (log-and-continue on exhaustion — a leftover dir is harmless, the following mkdir_p is then a no-op), `retry_on_transient` around `Git.prune_worktrees`, and `mkdir_p_retry` that raises `File.Error` exactly like `File.mkdir_p!` on exhaustion (loud create-failure semantics). Request API: `create_worktree_for_agent(agent_id, repo_root, worktree_path, spec, meta, agent_pid)` — a `GenServer.call` with a named 1-hour timeout (`@worktree_call_timeout` 3_600_000), called by the agent Runner. The handler offloads the blocking create I/O to a spawned `Task` (reply via `GenServer.reply/2` + `{:create_finished, agent_id}` cast — same pattern as TaskRegistry `:list_tasks`), so the loop stays responsive for `:DOWN` handling. Per-agent serialization: a second create request for an agent whose create is still in flight is stashed in `pending_requests` and started when the previous create finishes (retry-after-crash-during-setup race); agents that die while their create is in flight are tracked in `pending_cleanup` and cleaned up when the create task finishes. `Process.monitor(agent_pid)` per agent; on `:DOWN` for ANY reason (normal exit, crash, cancel kill) the worktree is reclaimed + destroyed (`destroy_worktree/3`): `File.rm_rf(worktree_path)` → `Git.prune_worktrees(repo_root)` → `Git.delete_branch(repo_root, branch_name)` (this order — git refuses to delete a branch checked out in another worktree), each step through `WorktreeRetry` (retried rm_rf/prune/delete-branch; never raises — log-and-continue after exhaustion; cleanup order preserved). Idempotent; the GenServer never crashes on agent exits. Kept: `workers_dir/1`, `start_link/1`. |
| `EvoGit.AgentScheduler.WorktreeRetry` | Pure retry helpers for transient filesystem failures in the worktree lifecycle (Windows file locking, anti-virus scans) — single shared implementation, no duplicated loops (worktree_retry.ex). `rm_rf_retry/2` → `{:ok, files} \| {:error, reason, file}` — retries `File.rm_rf/1` on transient reasons; `:enoent` normalized to `{:ok, []}` (dir already gone = success); non-transient fails fast. `mkdir_p_retry/2` → `:ok \| {:error, reason}` — same policy for `File.mkdir_p/1` (2-tuple error shape); caller decides loud-vs-tolerate. `retry_on_transient/2` — generic wrapper: success shapes (`:ok`, `{:ok, _}`) halt immediately; retryable = transient POSIX reasons (`:eacces`, `:eperm`, `:eexist`, `:enotempty`, `:ebusy`, `:again`, `:eintr`) in 2-/3-tuple fs error shapes, git adapter `{:error, {tag, output}}` tuples, and binary error shapes — EXCEPT repo-gone outputs ("Repository path does not exist" / "not a git repository", `repo_gone_output?/1`) which fail fast (repo isn't coming back; for delete ops the goal is already met). Policy: 4 total attempts (first immediate — a `0` delay is prepended), exponential backoff 50ms → 100ms → 200ms via `Retry.DelayStreams` (the `retry` hex lib; `opts[:delays]` overridable for hermetic tests — `[0,0,0]`/`[]` never sleep). Never raises on its own; exceptions from the wrapped fun propagate (fail fast). |
| `EvoGit.AgentScheduler.Dispatch` | Agent registration, dispatching, agent-process git commit, repo root resolution, queue processing |
| `EvoGit.AgentScheduler.Subagents` | Subagent validation/spawning, spatial contract checks, result tracking, parent resumption |
| `EvoGit.AgentScheduler.Lifecycle` | Agent recycling (cleanup) and crash handling (retry logic, permanent failure) |
| `EvoGit.AgentScheduler.PubSub` | Centralized broadcast helpers — throttled `{:agents_updated, node}` (via `Throttle` GenServer supervised under `EvoGit.Supervisor`, see "Throttled PubSub" below) plus enriched delta broadcasts `{:agent_registered, agent_id, summary, node}` / `{:agent_updated, agent_id, changed_fields, node}` / `{:agent_removed, agent_id, node}`, and the config broadcast `{:scheduler_config_updated, node}` — every broadcast carries a trailing `node` element (the emitting BEAM node) computed inside the helpers. Agent-state broadcast kwlists have the heavy `:context` field stripped, with `message_count` added when a context is present; ETS writes stay verbatim (see `EvoGit.AgentScheduler.Store`) |
| `EvoGit.AgentScheduler.PubSub.Throttle` | GenServer (throttle.ex) — coalesces `:schedule` casts into one flush broadcast 200ms after the last schedule; supervised child of `EvoGit.Supervisor` (`:permanent` restart), declared in `EvoGit.Application`'s children after `Phoenix.PubSub` |

### Slot Management (Slots module)

Two independent slot pools tracked as `MapSet`s of agent IDs. Available capacity is derived: `capacity - map_size(holders)`. This makes slot leaks impossible by construction — when an agent dies, `release_agent_slots/2` removes it from both holder sets, restoring the slot automatically.

| Pool | State Keys | Capacity | Backoff |
|------|-----------|----------|---------|
| LLM slots | `llm_holders`, `llm_waiting`, `llm_backoff_until` | **per-model** `model_concurrency[model_id]` (from `[[llm.models]]` profile `concurrency`, default 3); fallback `default_llm_max_concurrency` (3) for unknown model_ids via `State.concurrency_for/2` | **per-model** 60s cooldown on `:rate_limit` errors (NOT global — one model's rate limit doesn't block others) |
| Tool slots | `tool_holders`, `tool_waiting` | `max_tool_concurrency` (2) | None |

### `scheduler.default_llm_max_concurrency` precedence

`scheduler.default_llm_max_concurrency` is **not dead config, but its live effect is narrow** — it is the **default per-LLM concurrency**, NOT a global cap:
- **Effective LLM limit for an agent = `model_concurrency[model_id]` if present, else `state.default_llm_max_concurrency`** (`State.concurrency_for/2`, state.ex:205-207). Both slot enforcers read it: `Slots.do_handle_request_llm_slot/4` (slots.ex:103) and `Slots.grant_llm_from_queue/2` (slots.ex:399).
- `model_concurrency` is populated at config-load time ONLY by `State.from_model_profiles/2` (state.ex:146-151) from `[[llm.models]]` profile `concurrency` fields (default 3), at two places: `AgentScheduler.init/1` (agent_scheduler.ex:419) and `State.do_update_config`'s `:model_profiles` branch (state.ex:299-301) — the `reload_config` path (`RemoteAPI.build_reload_opts`, remote_api.ex:192-222). At RUNTIME it can additionally be replaced wholesale via `update_config(model_concurrency: map)` (the dynamic wall-clock engine path — see "Slot-Pool Sizing & Concurrency").
- **Legacy (no `[[llm.models]]`) path**: `scheduler.default_llm_max_concurrency` IS live — it becomes the synthesized "default" profile's `concurrency` via `Schema.LLM.build_legacy_default_profile/1` (schema/llm.ex:123), then flows into `model_concurrency["default"]`. This happens at config-load time (init or reload), NOT at runtime.
- **When `[[llm.models]]` profiles exist**: each profile's own `concurrency` wins for its pool; `scheduler.default_llm_max_concurrency` does NOT cap or override it — it only remains as (a) the fallback for agents whose `model_id` is not in `model_concurrency` (state.ex:206) and (b) the value surfaced in `get_config/0` as `default_llm_max_concurrency` (agent_scheduler.ex:656).
- **CLI `-c`/`--concurrency` runtime override (floor semantics)**: `CLI.Parser.configure_scheduler/1` maps `-c` → `update_config(default_llm_max_concurrency: N)` (parser.ex:67) → `State.do_update_config`'s dedicated `maybe_apply_default_llm_concurrency` step → `State.apply_default_llm_concurrency_override/2`, which sets `state.default_llm_max_concurrency = N` AND raises every `model_concurrency` entry to `max(c, N)`. Raising the default thus takes effect immediately for ALL live pools — with `[[llm.models]]` profiles (each pool's capacity is floored; an explicit profile concurrency above the default still wins and is never lowered) AND without profiles (the synthesized "default" pool's capacity is raised directly). The floor applies to runtime `update_config` only — at init the file semantics remain "profile wins". (`--tool-concurrency` → `update_config(max_tool_concurrency: N)` also takes effect — tool slots read `state.max_tool_concurrency` directly, slots.ex:219.) The TOML-file path (`scheduler.default_llm_max_concurrency` + reload) works as described above.

Key functions:
- `handle_request_llm_slot/3`, `handle_request_tool_slot/3` — Grant if capacity available, else enqueue
- `handle_release_llm_slot/2`, `handle_release_tool_slot/2` — Remove from holder set, grant pending. Called via `handle_cast` (fire-and-forget); return `{state, status_updates}`.
- `release_agent_slots/2` — Called on agent death (`:DOWN` handler): removes from both holder sets, purges from queues, grants pending slots
- `purge_agents_from_queues/2` — Removes agents from waiting queues, replies `{:error, :cancelled}` to each
- `grant_pending_on_resume/1` — Grants all available slots when resuming from pause; also runs at the END of every config update (state.ex), so a 0→N capacity increase (peak exit) grants queued 0-capacity waiters automatically

Slot functions return `{:reply, :ok, state, status_updates}` or `{:noreply, state, status_updates}` for synchronous operations, and `{state, status_updates}` for asynchronous release operations (`handle_cast`). The `status_updates` list contains `{agent_id, :blocked | :running}` tuples applied to ETS SchedMeta for dashboard visibility.

### Slot-Pool Sizing & Concurrency

Four coordinated behaviors in `state.ex` + `slots.ex` keep slot pools correct (do not regress):

- **Config updates preserve live LLM pools**: `State.do_update_config/2`'s `:model_profiles` branch calls `from_model_profiles(profiles, opts)` (opts pass-through so a `:default_llm_max_concurrency` override in the same update is honored instead of being clobbered by the first profile's concurrency) and merges the existing state's `llm_holders`/`llm_waiting`/`llm_backoff_until`/`llm_last_granted` maps OVER the fresh ones (existing entries win for ids present in both; brand-new profile ids keep fresh empty entries; stale pool ids keep live entries), then `prune_empty_pools/1` drops entries with empty values (empty MapSet / empty queue / nil backoff / empty last_granted — safe because all accessors default gracefully). The trailing `Slots.grant_pending_on_resume(state)` (state.ex:399) grants under the new capacity after the merge. Queued waiters' `GenServer.from`s survive the update (agents never block forever with capacity free) and live holders stay counted (no over-grant beyond capacity).
- **Stale-model pools are visible to all sweeps**: `State.all_model_ids/1` returns the UNION of keys of `model_concurrency`, `llm_holders`, `llm_waiting`, `llm_backoff_until` — pools for model_ids absent from `model_concurrency` (agents whose ETS `model_id` became stale after a profiles update removed their profile; agents requesting a model not in profiles) are swept by `grant_pending_llm_slots` (both Enum.reduce sweeps), `release_agent_slots`'s LLM cleanup, and `purge_llm_waiting_queues`, so queued stale-model waiters get granted and dead holders in stale pools get released. Capacity for a stale pool = `concurrency_for`'s fallback (`default_llm_max_concurrency`). All call sites are inside this node (slots.ex Enum.reduce sweeps).
- **LLM slot release scans all pools**: `Slots.handle_release_llm_slot/2` scans ALL pool ids (`State.all_model_ids`) rather than resolving the model via ETS at cast-processing time (which picks the wrong pool when the ETS entry is gone — stale `model_id` after a profiles update), deletes the agent from every pool's holder set (idempotent — an agent holds at most one LLM slot), cleans `llm_last_granted` for the pool it was removed from (mirroring `release_agent_slots`), then runs the existing `grant_pending_llm_slots` sweep.
- **`default_llm_max_concurrency` override is a floor**: a dedicated pipeline step (`maybe_apply_default_llm_concurrency/2` → public `State.apply_default_llm_concurrency_override/2`) sets the default AND applies a FLOOR to every `model_concurrency` entry (`max(c, N)`; explicit `0` entries — the peak hard-pause sentinel — stay `0`) — raising the default never lowers an explicit profile concurrency; applies whether or not `:model_profiles` is in the same update (CLI `-c` and the dashboard default-concurrency slider raise the effective capacity of ALL live pools immediately, with AND without `[[llm.models]]` profiles).
- **Dynamic `:model_concurrency` override (wall-clock engine path)**: `State.do_update_config/2`'s pipeline has a dedicated `maybe_update_model_concurrency/2` step (private, state.ex) that replaces `state.model_concurrency` with the given `%{model_id => non_neg_integer()}` map — the runtime entry point for `EvoGit.PeakHourEngine`, which raises/lowers per-model LLM concurrency when the wall clock enters/leaves daily peak windows. After replacement it re-applies the active floor via `apply_default_llm_concurrency_override(state, state.default_llm_max_concurrency)`: an engine update with values below an active CLI `-c` / runtime `default_llm_max_concurrency` NEVER silently drops the floor (the floor is a LOWER BOUND on all entries; explicit values above it win) — **EXCEPT explicit `0` entries (the peak hard-pause sentinel), which are never floored up**; the engine applies the identical rule (`effective 0 → 0`), so the fixed point holds end-to-end. It is independent of `from_model_profiles/2` (which keeps reading the base `concurrency` field only — config loading stays wall-clock agnostic; the engine owns dynamic overrides). Capacity changes take effect immediately via the END-of-update `Slots.grant_pending_on_resume(state)` sweep, which runs for EVERY update (including `:model_concurrency` replacements) — a capacity increase grants queued LLM waiters automatically, no separate sweep call exists. The `AgentScheduler` handler (`handle_call({:update_config, opts}, ...)` → `reconcile_pool_after_update`) already reconciles the ReqLLM Finch pool from the new `model_concurrency`/`default_llm_max_concurrency` — untouched.
- **0-capacity LLM slots enqueue and block (peak hard pause)**: `concurrency_for/2` may legitimately return `0` (the engine emits `{model_id, 0}` during peak windows for `peak_concurrency = 0` profiles). A slot request for a 0-capacity model now ENQUEUES exactly like the paused-scheduler case — `Slots.handle_request_llm_slot/3` has no 0-capacity pre-check, so flow falls through to the paused branch (or, when not paused, `do_handle_request_llm_slot/4`'s full-queue branch, since `MapSet.size(holders) < 0` is false), storing `{agent_id, from, nil}` and replying `{:noreply, state, [{agent_id, :blocked}]}` — the agent blocks until capacity returns. `Slots.grant_llm_from_queue/2` at capacity 0 is a no-op that KEEPS the waiting queue untouched (`{state, []}` — no replies, no drain, no status updates): waiters stay queued, and a 0→N transition (peak exit → `update_config(model_concurrency: %{...})` → end-of-update `Slots.grant_pending_on_resume/1` sweep → this function's normal grant branch) grants them automatically. In-flight holders are never evicted (their call completes and releases normally; at 0 the release sweep is a no-op). `AgentScheduler.with_llm_slot/2` does not raise on zero capacity — agents wait. Graceful cancel unblocks blocked agents of the cancelling task: `begin_graceful_cancel/1` purges their entries from the LLM/tool waiting queues via `Slots.purge_agents_from_queues/2`, replying `{:error, :cancelled}` → the blocked `with_llm_slot` raises → crash-retry → the agent enters cancel-grace at its next loop top (reads `cancel_requested`, saves work, calls `complete_task`). Force-kill's `{:error, :cancelled}` purge path is unchanged and capacity-independent.

### Running Count

There is no `running_count` field. The running count is always derived as `map_size(state.ref_to_agent)`. Every agent lifecycle transition (dispatch, completion, crash) pops or puts from `ref_to_agent`, keeping the count authoritative at all times.

### Multi-Task Repo Root Resolution

The scheduler supports multiple concurrent tasks targeting different repos. Repo root resolution follows this priority:

1. **Per-agent ETS** (`AgentState.repo_root`) — set at registration via `Dispatch.resolve_agent_repo_root/2`, derived from spec data. Used by `Lifecycle` for agent cleanup/retry paths.
2. **Process dictionary** (`Process.get(:genesis_repo_root)`) — set at dispatch time in `try_dispatch/2`. Preferred by `current_repo_root/0` for runtime lookups.

There is no global `state.repo_root` fallback — repo root resolution is always per-agent. Repo-init tracking lives in `WorktreeManager` (lazy per-repo init on first create request); `%State{}` does not carry `initialized` / `initialized_repos` fields.

`resolve_agent_repo_root/2` in Dispatch is self-contained for primary repos (strips worktree suffix from `spec.phylo_node.repo`). For foreign repos, it looks up the repo root from the agent's own `spec.foreign_repos` list by `spec.repo_id` — foreign repos are carried per-agent, not stored in global scheduler state.

### Worktree Lifecycle (WorktreeManager + Worktrees modules)

Worktrees are **created fresh per agent run** — there is NO pool and NO persistent-worktree reuse across retries (no fast/slow path, no `File.exists?` reuse branch, no `newly_created` flag). The entire lifecycle is owned by the `WorktreeManager` GenServer:

1. **Lazy per-repo init** — on the FIRST `create_worktree_for_agent/6` request for a repo, WorktreeManager executes the repo init (rm_rf `.genesis/workers` → `git worktree prune` → orphaned `evogit-agent-*` branch cleanup → mkdir_p). Never called from the scheduler.
2. **Runner requests a fresh worktree** — `EvoGit.Agent.Runner.setup_dispatch_context/1` calls `WorktreeManager.create_worktree_for_agent(agent_id, repo_root, worktree_path, spec, meta, self())` with the named 1-hour timeout. The handler offloads the blocking create I/O to a spawned `Task` (reply via `GenServer.reply/2`, `{:create_finished, agent_id}` cast on completion) so the loop stays responsive for `:DOWN` handling. On `{:error, ...}` the Runner raises → the agent Task crashes → scheduler crash-retry → fresh worktree.
3. **Create pipeline** (`Worktrees.prepare_new_worktree/5`, running inside the create task): destroy leftover dir/branch → CoW create via `EvoGit.Adapters.CowWorktree.create_worktree` (fallback `Git.add_worktree`; failure → `{:error, {:worktree_create_failed, msg}}`) → `assign_and_prepare_worktree/2` (git clean + checkout agent branch + bind `phylo_node.repo = worktree` in ETS) → `run_init_script/3` (genesis.toml `[worktree]` script, primary repo only; env `SOURCE_REPO_PATH`/`SOURCE_WORKTREE_PATH`/`TARGET_WORKTREE_PATH`; Windows scripts run via `Platform.shell_args/1` → PowerShell `-EncodedCommand` — single source of truth: `EvoGit.Powershell` in lib/evo_git/powershell.ex; the script is base64-encoded so no command-line quoting/parsing issues, output forced UTF-8). Branch name comes from `Worktrees.branch_name/2` — `"evogit-agent-T#{task_number}-A#{task_local_id}"`.
4. **Monitor-based reclaim** — WorktreeManager `Process.monitor`s each agent; on `:DOWN` for ANY reason (normal exit, crash, cancel kill) it destroys the worktree (`destroy_worktree/3`): `File.rm_rf(worktree_path)` → `Git.prune_worktrees(repo_root)` → `Git.delete_branch(repo_root, branch_name)` (this order — git refuses to delete a branch checked out in another worktree). All destroy steps go through `WorktreeRetry` with the modest budget (4 attempts, ≤350ms sleep per op) because `destroy_worktree/3` runs in the WorktreeManager GenServer process. Idempotent; the GenServer never crashes on agent exits. `recycle_agent/2`, `cancel_agent/2` (`Task.shutdown(:brutal_kill)` fires the monitor) and the `handle_agent_crash/3` permanent-failure path never call worktree deletion — cleanup is entirely monitor-driven.
5. **Per-agent serialization** — a second create request for an agent whose create is still in flight is stashed in `pending_requests` and started when the previous create finishes (retry-after-crash-during-setup race); agents that die while their create is in flight are tracked in `pending_cleanup` and cleaned up when the create task finishes.

All blocking filesystem operations (rm_rf, prune_worktrees, delete_branch, mkdir_p) run inside `WorktreeManager` (create I/O offloaded to a spawned Task); the scheduler never touches worktree I/O.

### WorktreeRetry — transient filesystem failure retries (worktree_retry.ex)

`EvoGit.AgentScheduler.WorktreeRetry` is the single shared implementation of all retry logic for the worktree lifecycle (no duplicated loops). Purpose: Windows file lockers and anti-virus scanners transiently fail file operations with `:eacces`/`:eperm`/`:eexist` (and friends) — a single immediate failure is usually a false alarm, and the operation succeeds on retry.

**Design — `Enum.reduce_while` over `Retry.DelayStreams` instead of the `retry` macro:** the macro's `atoms:` predicate cannot express the mixed return-shape classification required here (`{:error, reason, file}` 3-tuples, `{:error, reason}` 2-tuples, git `{:error, {tag, output}}` tuples, and bare binary error tuples are each classified differently), and its default `rescue_only: [RuntimeError]` would retry raised exceptions that must fail fast. Failures in this lifecycle arrive as error tuples, never exceptions — exceptions from the wrapped fun propagate immediately (equivalent to `rescue_only: []`).

**Transient-reason set rationale:** `:eacces`, `:eperm`, `:eexist`, `:enotempty`, `:ebusy`, `:again`, `:eintr` — the reasons Windows lockers/AV scanners surface. `:enoent` is deliberately absent: "not found" means the goal is already met (`rm_rf_retry/2` normalizes `{:error, :enoent, file}` to `{:ok, []}`). Git repo-gone outputs ("Repository path does not exist" / "not a git repository", `repo_gone_output?/1`) also fail fast — the repo is not coming back within the retry window, and for delete operations the goal is already met. The moduledoc in `worktree_retry.ex` is the authoritative detail.

### Agent Dispatching (Dispatch module)

Handles the mechanics of registering and dispatching agents:

1. `register_agent/6` — Assigns agent IDs, computes task-local IDs, resolves event sink inheritance, writes both ETS tables
2. `try_dispatch/2` — Scheduling-only dispatch (no worktree I/O). Uses a `with` guard to bail cleanly if ETS entries are missing (genuine race). Computes the worktree path (`Worktrees.branch_name/2` + workers dir) and stores it in sched_meta **before** spawning the task (so `cancel_agent` can find the worktree), spawns the task immediately via the 4-arity `Task.Supervisor.async_nolink/4` **named-function** form (`spec.agent_module, :run, [spec.objective, dispatch_ctx]`), updates `ref_to_agent`. **NO git commands, worktree creation, or init scripts run here** — the scheduler never does blocking I/O and never calls any worktree function (not even init). The named-function form (instead of an anonymous fn) means the spawned process shows up as a meaningful `module.run/2` in process inspection (observer/Process.info).
   - **Worktree creation happens in the agent Task**: `EvoGit.Agent.Runner.setup_dispatch_context/1` (inside `run/2`, the single true entry point for an agent, before the agent loop) calls `WorktreeManager.create_worktree_for_agent(..., self())` with the 1-hour timeout. The create pipeline (`Worktrees.prepare_new_worktree/5` — destroy leftovers → CoW create → assign_and_prepare → init script; lazy per-repo init on first request) runs offloaded inside WorktreeManager, concurrently across subagents. The CoW optimization copies unchanged files from a source working tree (parent's worktree for subagents, repo root for top-level) using `cp --reflink=auto` (Linux) or `cp -c` (macOS), avoiding full git object extraction. Controlled by `[:git, :cow_worktree_creation]` config (`:auto` default). `spawn_validated_subagents`' `Enum.reduce` over `try_dispatch` spawns all tasks immediately.
3. `commit_pending_in_worktree/0` — Best-effort git commit of pending changes, designed to run in the **agent process** (not the scheduler). Uses `Process.get(:repo_path)` for the worktree path. Handles all git adapter error tuples (`{:ok, _}`, `{:error, _}`, `{:conflict, _}`) explicitly via a `with` block rather than a broad `try/rescue`, so failures are logged but never crash. Called via `try/after` in the agent's `run/2` (the dispatch entry point) after the agent loop. **The scheduler process NEVER calls git directly.**
4. `resolve_agent_repo_root/2` — Resolves repo root from spec (primary vs foreign repo)
5. `dispatch_queued_agents/1` — Drains queue dispatching agents (used after resume)
6. `process_queue/1` — Processes queue with ready-parent detection (delegates to Subagents)

### Repo-path assumptions (relevant to any repo-less / no-worktree agent design)

The whole scheduler dispatch path assumes every agent spec carries a real repo. Facts verified at dispatch.ex / worktrees.ex / worktree_manager.ex / runner.ex:

- **`commit_pending_in_worktree/0` is fully safe on missing/non-git paths** (dispatch.ex:271-312): `Process.get(:repo_path)` nil → skips entirely, returns `:ok`. Non-nil but missing path → `Git.run/2`'s `File.dir?` guard returns `{:error, {:enoent, ...}}` (git.ex:64-66). Bare non-git dir → `git status --porcelain` exits 128 → `{:error, {128, "fatal: not a git repository..."}}` (git.ex:89-95). Both fall into the `with`'s `else error -> Logger.warning(...)` arm → `:ok`. Never raises (only environment-level raises possible: `Executable.resolve("git")` / `System.tmp_dir!` in `Git.commit/2`'s temp-file path). Call sites: `Runner.run/3` `try/after` (runner.ex:48-52 — cannot mask a `do_run` exception) and `SubagentProcessing.process_subagent_calls` (subagent_processing.ex:60, inline before `spawn_sub_agents`).
- **Nil `repo_root` / `phylo_node.repo` CRASHES the scheduler GenServer** (no graceful path exists):
  1. `resolve_agent_repo_root/2` (dispatch.ex:508-528): primary branch does `String.split(spec.phylo_node.repo, "/.genesis/workers/", parts: 2)` — a nil `phylo_node.repo` (`PhyloGraphNode` has `defstruct [:repo, :base_commit, :current_commit]`, repo defaults nil) raises `FunctionClauseError`. Called at registration (dispatch.ex:69), `run_agent` handler (agent_scheduler.ex:629), and `try_dispatch` (dispatch.ex:204).
  2. `do_try_dispatch` (dispatch.ex:206-211): `worktree_path = Path.join([agent_repo_root, ".genesis/workers", "worker_T#{..}_A#{..}"])` — nil root raises `ArgumentError` (Path.join requires binaries). `worktree_path` is therefore NEVER nil in the dispatch_ctx when the ctx is built; a nil root crashes before the ctx exists.
  3. `WorktreeManager.maybe_init_repo/2` → `Worktrees.workers_dir/1` (`Path.join(repo_root, ".genesis/workers")`, worktrees.ex:26) — nil root raises `ArgumentError` inside the WorktreeManager GenServer.
  4. `Runner.setup_dispatch_context/1` (runner.ex:158-211) UNCONDITIONALLY calls `WorktreeManager.create_worktree_for_agent(agent_id, repo_root, worktree_path, spec, meta, self())` and raises `"Failed to create worktree..."` on `{:error, reason}` (runner.ex:188-201) — the agent Task crashes → scheduler crash-retry. `Process.put(:repo_path, worktree_path)` at runner.ex:179 is what `commit_pending_in_worktree` reads.
- **`dispatch_ctx` keys** (dispatch.ex:220-229): `[agent_id:, depth:, repo_root:, repo_id:, worktree_path:, retries:, spec:, meta:]` — all `Keyword.fetch!`'d in `setup_dispatch_context` (runner.ex:159-166); `meta` is the full `%SchedMeta{}` (status `:pending | :running | :waiting | :ready | :blocked`). `SchedMeta.worktree` defaults to nil (sched_meta.ex:48) and is set in `do_try_dispatch` BEFORE the task spawn.
- **Child AgentState gets `repo_id` + `repo_root` only — no worktree_path field** (dispatch.ex:79-95): `phylo_node` starts nil and is bound to the worktree later by `Worktrees.assign_and_prepare_worktree/2`. Each subagent gets its OWN fresh worker dir under the repo root (computed in `do_try_dispatch`), never the parent's path.
- **Subagent validation never checks repo existence** (`validate_single_subagent/5`, subagents.ex:130-144): only depth, `ContextNode.is_ignored?`, and the spatial contract (which reads `spec.context_node.path` — nil context_node would raise via `.path` access). A spec with a nil/phantom repo passes validation and crashes later in dispatch/worktree creation.

Handles subagent validation, spawning, and result collection:

1. `spawn_validated_subagents/5` — Validates all specs, registers valid ones, replies immediately if all invalid. The parent agent commits its pending changes BEFORE calling `spawn_sub_agents` (done in the agent process via `Dispatch.commit_pending_in_worktree/0`), so the scheduler does not perform git operations.
2. `validate_single_subagent/5` — Per-spec validation chain (depth, ignored, spatial)
3. `validate_subagent_depth/3`, `validate_subagent_not_ignored/1` — Individual validation checks
4. `validate_spatial_contract_for_spec/3`, `validate_spawn_spatiality/4` — Spatial contract enforcement
5. `store_sub_result/3` — Stores subagent result at correct index in parent's results map. Also tracks foreign repo commit SHAs in `SchedMeta.foreign_repo_commits` — when a foreign-repo subagent completes successfully, its `commit_sha` is recorded under the `repo_id` key so subsequent subagents targeting the same foreign repo start from that commit instead of HEAD.
6. `maybe_resume_parent/2` — Checks if all subagents done, resumes parent if so
7. `dispatch_ready_parent/3` — Replies to parent's GenServer.call with ordered results
8. `build_ordered_results/2` — Builds final results list in original spec order

### Agent Lifecycle (Lifecycle module)

Handles agent completion and crash recovery:

1. `recycle_agent/2` — Deletes both ETS entries on normal completion. Uses `with` guard to return state unchanged if ETS entry is already gone (genuine race between `:DOWN` completion and another cleanup path). Resolves `repo_root` from the agent's own `AgentState` ETS entry (not global state). No worktree deletion — cleanup is monitor-driven (WorktreeManager `:DOWN` handler).
2. `cancel_agent/2` — Kills the agent's Task process via `Task.shutdown(meta.task_ref, :brutal_kill)`. The `task_ref` field stores a full `%Task{}` struct (not a bare reference), enabling proper shutdown. The kill fires the WorktreeManager `:DOWN` monitor → worktree reclaim. Replies to blocked callers, deletes ETS entries. Uses `case` to skip ETS deletion if agent_state is missing.
3. `handle_agent_crash/3` — Retry logic (re-dispatch — the retried agent gets a FRESH worktree from WorktreeManager; crash-retry never reuses a worktree) or permanent failure (ETS cleanup, notify parent/reply error). Both paths resolve `repo_root` from per-agent ETS state; neither calls worktree deletion — cleanup is monitor-driven.

## Graceful Cancellation (cancel_requested + `:evogit_cancelling_tasks` marker)

**`AgentState.cancel_requested`** (`agent_state.ex:27,63,88`) — `boolean() | nil`, default `nil`. Set by the scheduler when the task is being gracefully cancelled; the runner checks/clears it at the top of each turn and enters cancel-grace (save work → `complete_task`). `EvoGit.AgentScheduler.Store` helpers (`store.ex:199-255`): `set_cancel_requested/1` (sets `true`) and `/2` (arbitrary `boolean() | nil`), `cancel_requested?/1` (boolean getter — `false` when the state is missing or the flag is nil/false), `clear_cancel_requested/1` (sets back to `nil`). All return `:ok | {:error, :not_found}` except the getter.

**`AgentScheduler.begin_graceful_cancel/1`** (public `agent_scheduler.ex:400-402`, handler `:700-731`):
1. Registers `task_id` in the `:evogit_cancelling_tasks` marker — a public `:set` ETS table created in `application.ex:22-27` (owned by the application process, survives scheduler restarts).
2. Scans `SchedMeta.task_id` (same pattern as `force_kill_task_agents`), and for each live agent appends the cancel message via **`Store.append_pending_user_message/2`** (NOT `send_user_message` — that's a `GenServer.call` to the scheduler itself, which would self-call deadlock) + `Store.set_cancel_requested/1`.
3. Purges the task's agents from the LLM/tool waiting queues via **`Slots.purge_agents_from_queues/2`**, replying `{:error, :cancelled}` to each blocked `from` — an agent blocked on a zero-capacity (peak-paused) or saturated pool unblocks immediately; the raised error propagates → crash-retry → the agent enters cancel-grace at its next loop top.
4. Exact message text in `cancel_message/0` (`agent_scheduler.ex:375-383`): *"The task is being cancelled by the user. Please immediately save your work: commit any uncommitted changes, then call complete_task with a summary of what was accomplished. You are in a grace period and must call complete_task now."*

**`AgentScheduler.clear_cancelling_task/1`** (public `:412-414`, handler `:734-741`) — deletes the task from the marker, idempotent (defensive against a missing table). Called by TaskRegistry's guarded `clear_cancelling_marker/1` at terminal transitions.

**`run_agent` guard** (`agent_scheduler.ex:568-578`) — replies `{:error, :cancelled}` WITHOUT dispatch when the task is in the marker. This blocks Genesis Mode B's second sequential root agent (which shares the first root's `task_id`) from spawning after the first root completes during a cancel.

**New-agent registration guard** in `Dispatch.register_agent` (`dispatch.ex:103-113`) — agents registered while their task is in the marker (subagent spawns, crash-retries, queued agents starting late) immediately get the cancel message + `cancel_requested` flag, so they enter grace at their first loop top.

**`AgentScheduler.force_kill_task_agents/1`** (public `agent_scheduler.ex:367-369`, handler `:615-697`) — the brutal reverse-depth `:brutal_kill` cascade (removes refs from `ref_to_agent` first, purges queues, releases slots, `Lifecycle.cancel_agent` deepest-first), called by `TaskRegistry.force_kill_task/1`.

**RPC:** `RemoteAPI.cancel_task/1` (graceful — delegates to `TaskRegistry.cancel_task/1`, `remote_api.ex:374-377`) + `RemoteAPI.force_kill_task/1` (`:389-392`); `RemoteNode.cancel_task/2` + `RemoteNode.force_kill_task/2` (`remote_node.ex:449-483` — local-direct when `node == node()`, else `:erpc` routing).

## Shutdown & Restart Safety (update-safety investigation)

Facts relevant to restarting the BEAM (e.g. a desktop auto-update) while agent tasks are in flight:

- **No `terminate/2` anywhere in the scheduler ecosystem** — `AgentScheduler`, `Slots`, `State`, `Store`, and `WorktreeManager` have no terminate callbacks (the only `terminate` in the app is `TaskRegistry.terminate/2` → `:ok` no-op). **Worktree cleanup is purely monitor-driven**: `WorktreeManager.handle_info({:DOWN, ...})` (worktree_manager.ex:198-229) destroys the worktree when the AGENT process dies. When the app/BEAM stops, `EvoGit.Supervisor` terminates children in reverse order — `AgentGroupSupervisor` (application.ex:63, last child) goes FIRST, its `one_for_all` (agent_group_supervisor.ex:25) kills `EvoGit.TaskSupervisor` (all agent Tasks, brutal-killed per Task.Supervisor's default `shutdown: :brutal_kill`) + `AgentScheduler`; then WorktreeManager is terminated before it can process the queued `:DOWN`s. **Result: `.genesis/workers/worker_T<n>_A<m>/` dirs and `evogit-agent-T<n>-A<m>` branches remain on disk after any BEAM/app stop.**
- **Next-start cleanup is the lazy per-repo init** (`maybe_init_repo/2`, worktree_manager.ex:236-283, runs on the FIRST `create_worktree_for_agent` per repo): (1) `rm_rf_retry(worker_base)` deletes the whole `.genesis/workers/` dir (log-and-continue on failure — the following `mkdir_p_retry` is then a no-op), (2) `Git.prune_worktrees(repo_root)` prunes the worktree registry, (3) `clean_orphaned_branches/1` (worktree_manager.ex:379-395) deletes every `evogit-agent-*` branch, (4) `mkdir_p_retry` (raises `File.Error` on exhaustion). No cleanup happens at boot without a create request.
- **Task rows survive in SQLite**; `TaskRegistry.init/1` (task_registry.ex:252-289) reconciles orphaned `:finalizing` → `:failed` and `:cancelling` → `:cancelled` synchronously at boot; `:running` rows are left to the one-shot `:lease_sweep` (task_registry.ex:1354-1394, scheduled 150s after init; `@lease_duration 120`/`@heartbeat_interval 60_000`/`@sweep_after (@lease_duration + 30) * 1000` at task_registry.ex:37-42), which marks `:running` + expired lease + no live agents → `:failed` ("Lease expired; owning instance no longer renewing"). In-flight agent ETS state (`AgentState.context`, `pending_user_messages`, `cancel_requested`) is LOST on BEAM death — ETS tables are owned by the application process.
- **Slot pools are memory-only** (`%State{}`: `llm_holders`, `llm_waiting`, `llm_backoff_until`, `llm_last_granted`, `tool_holders`, `tool_waiting` — state.ex:79-88). On scheduler restart the new `%State{}` is fresh (empty pools from `from_model_profiles`, state.ex:194-196) — capacity-derived holder sets can't leak. Blocked slot waiters (`GenServer.call(:infinity)`, agent_scheduler.ex:263-265, 296-298) exit with the scheduler; no explicit "shutting down" gate exists — the only slot gating is `state.paused` (slots.ex:89-93, 214-216) and per-model capacity/backoff.
- **Graceful-cancel marker `:evogit_cancelling_tasks`** is ETS owned by the application process — it survives scheduler restarts but NOT app restarts; on boot the marker is empty (any task that was `:cancelling` is reconciled to `:cancelled` by TaskRegistry.init as above).

## Constraints

- Data structs are plain data with no behaviour or callbacks.
- `Slots`, `Worktrees`, `Dispatch`, `Subagents`, and `Lifecycle` are pure-function modules operating on `State.t()`; they don't maintain their own state.
- `AgentState` is shared (scheduler + agent processes); `SchedMeta` is scheduler-exclusive.
- Both ETS tables are created by **`EvoGit.Application`** (the application process), NOT by the `AgentScheduler` GenServer (see `application.ex:13-15`). This is deliberate: the tables have **no heir**, so ownership must outlive a scheduler crash. Because they are owned by the long-lived application process, the tables **SURVIVE an `AgentScheduler` restart** — stale `SchedMeta` entries from the crashed instance remain. (Restart semantics: `AgentGroupSupervisor` is `strategy: :one_for_all`, so a scheduler crash also kills `EvoGit.TaskSupervisor` and all running agent Tasks. The GenServer `%State{}` is reset fresh on restart, but the ETS tables persist.)
- GenServer state must always be `%State{}`; use struct update syntax, not `Map.put/3`.
- The scheduler process NEVER calls git, does blocking filesystem I/O, or calls ANY worktree function (not even init) — all git operations (auto-commit, sync) happen in the agent (Task) process, and ALL worktree filesystem operations (rm_rf, mkdir_p, prune_worktrees, delete_branch) are owned by the `WorktreeManager` GenServer. The only worktree call is Runner → `WorktreeManager.create_worktree_for_agent/6` (named 1-hour timeout; create I/O offloaded to a spawned Task; reclaim via `:DOWN` monitor).
- Slot availability is derived from holder MapSets, never stored as a counter — this eliminates leak/deadlock bugs by construction.
- `SchedMeta.task_ref` stores a `%Task{}` struct (for `Task.shutdown/2`), NOT a bare reference. The `ref_to_agent` map still keys on `task.ref` (the monitor reference).
- `case`/`with` guards on ETS lookups are used ONLY where a genuine race can cause the entry to be absent (recycle_agent, try_dispatch, cancel_agent). Not used defensively everywhere.
- Cross-module calls: `Dispatch.process_queue/1` calls `Subagents.dispatch_ready_parent/3` for ready parents. `Lifecycle.handle_agent_crash/3` calls `Dispatch.try_dispatch/2`, `Dispatch.process_queue/1`, `Subagents.store_sub_result/3`, and `Subagents.maybe_resume_parent/2`.
- **Task archive table**: `:evogit_archive_records` is a **`:set` keyed by `{task_id, agent_id}`** (at most one record per agent per task — `EvoGit.AgentScheduler.Store.put_archive_record/3` writes are idempotent, so crash-retry double-writes are safe). Records are written at agent exit, consumed (collected into `Result.archive_records`) **AND** cleared at successful root completion in `Lifecycle.handle_task_result/3`, and reset defensively at task start in the `run_agent` call.

### Per-message timestamp metadata convention
Every message in an agent's session memory (the `%ReqLLM.Message{}` list inside `%ReqLLM.Context{}.messages`, held in `AgentState.context` / `:evogit_agent_state` ETS) carries `metadata[:timestamp]` — **Unix seconds** (`System.system_time(:second)`), an atom-keyed integer consistent with the existing `:turn` metadata convention. Timestamps are stamped **at message-CREATION time in the agent code** — never in the Store.

**Single choke point — `ContextBuilder.tag_message_turn/2` (agent/context_builder.ex)**: every message produced by the agent loop passes through it, and it sets BOTH `metadata[:turn]` AND `metadata[:timestamp]` in one place. Idempotent via `Map.put_new` — an already-stamped message keeps its original `:turn` and `:timestamp`. `ContextBuilder.tag_message_timestamp/1` stamps just the timestamp (used at the nudge and compression-summary append sites). The agent subtree owns all stamping; see `apps/evo_git/lib/evo_git/agent/CONTEXT.md` for the full inventory of creation sites.

**`Store` is a dumb pass-through.** `batch_update_agent/2` (store.ex) writes the fields verbatim into ETS; only the broadcast kwlist is stripped (`:context` removed, `message_count` added when a context is updated). `update_agent_context/2` delegates to `batch_update_agent` — same path. Both return `:ok`. **No read-back exists anywhere** — data flows one way: agent → ETS/pubsub → frontend. The dashboard reads `msg.metadata[:timestamp]` (Unix seconds) directly from `RemoteAPI.get_agent_history/1` (raw structs, unchanged).

`DateTime` was deliberately avoided (struct — heavier, and Jason-encodes to ISO-8601 strings elsewhere in the codebase); an integer is timezone-agnostic and trivial for the dashboard to convert to local display time. **The dashboard interprets integer timestamps as Unix SECONDS** (`EvoDashWeb.Helpers.format_history_timestamp/1`) — do NOT switch granularity without updating evo_dash. Second-granularity means messages produced within the same second share a stamp — acceptable by design. Compression (`context_compression.ex:85-86`) rebuilds context as `[system, initial_user, summary]` — the fresh summary is stamped via `tag_message_timestamp/1` at creation (history collapse is by design, not a bug).design, not a bug).
