# Agent Scheduler Data Structures and Helper Modules

## Intent

Contains data structs and extracted helper modules used internally by `EvoGit.AgentScheduler` GenServer. The data structs back two ETS tables (`:evogit_agent_state` and `:evogit_sched_meta`) tracking agent execution state and scheduling metadata. Helper modules encapsulate slot management, worktree lifecycle, agent dispatching, subagent management, and agent lifecycle logic.

## Routing Table

None — leaf directory (modules: `state.ex`, `agent_state.ex`, `sched_meta.ex`, `slots.ex`, `store.ex`, `worktrees.ex`, `worktree_manager.ex`, `worktree_retry.ex`, `dispatch.ex`, `subagents.ex`, `lifecycle.ex`, `pubsub.ex`, `throttle.ex`, `remote_api.ex`).

## Throttled PubSub (PubSub + throttle.ex)

- `EvoGit.AgentScheduler.PubSub` — throttled `{:agents_updated, node}` bulk broadcast plus delta broadcasts `{:agent_registered, agent_id, summary, node}` / `{:agent_updated, agent_id, changed_fields, node}` / `{:agent_removed, agent_id, node}`. Every broadcast carries a trailing `node` element (the emitting BEAM node), added by the helpers themselves.
- **Registered-summary key set** (`store.ex:67-74`): the `:agent_registered` `summary` map has EXACTLY `status, depth, parent_id, task_id, task_number, objective` — it does NOT include `message_count` or `agent_module` (those live only in the `list_agents/0` RPC summary, `RemoteAPI.build_agent_summary/3`, remote_api.ex:1009-1078 — a different shape, 20 keys). Dashboard code must not dot-access `summary.message_count` on registration events (KeyError). `message_count` arrives only via `:agent_updated` deltas (prepended as `[message_count: n]` when a context is written — `store.ex:143-149, 420-430`).
- `EvoGit.AgentScheduler.PubSub.Throttle` (throttle.ex) — small GenServer, standard child of the application supervision tree: declared in `EvoGit.Application`'s `children` immediately after `{Phoenix.PubSub, name: EvoGit.PubSub}`, runs under `EvoGit.Supervisor` (one_for_one, default `:permanent` restart) — a crash restarts it instead of silently degrading to unthrottled broadcasts forever.
- `broadcast_agents_updated/0` casts `:schedule` to the Throttle (coalesces rapid calls into one flush `@throttle_ms` = 200ms after the last schedule). When `Process.whereis(EvoGit.AgentScheduler.PubSub.Throttle)` is nil (tests, supervisor restart window), broadcasts fall back to **immediate dispatch**. If the Throttle exhausts the supervisor's max_restarts, `EvoGit.Supervisor` dies and takes the app down — standard OTP.

## Defensive ETS lookups in Subagents

`Store.get_sched_meta/1` / `Store.get_agent_state/1` return `{:ok, x} | :error`. Four sites in `subagents.ex` use `case`-guarded lookups with graceful fallbacks (log warning + safe return) instead of bare `{:ok, x} = Store.get_*(id)` matches — a missing ETS entry (e.g. a parent's entries reaped by `cancel_agent/2` while a subagent spawn/result is in flight) never crashes the scheduler GenServer with a `MatchError`:

1. `spawn_validated_subagents/5` — missing parent agent_state → replies `[{:error, :parent_recycled}]` per spec to the blocked `from`, spawns nothing, returns `{:noreply, state}` (bails BEFORE the `:waiting` status mutation).
2. `store_sub_result/3` — missing parent sched_meta → `:ok` (result dropped; parent gone).
3. `maybe_resume_parent/2` — missing parent sched_meta → state unchanged.
4. `dispatch_ready_parent/3` — missing agent_state (only needed for the resume log's commit SHA) → still replies/resets meta, logs `"unknown"` SHA.

Normal-path behavior is identical for all four sites. Error paths are covered by `./apps/evo_git/test/evo_git/agent_scheduler/subagents_test.exs` (e.g. the `:parent_recycled` reply) and the Throttle by `pubsub_test.exs`.

## Task Spawn & Starting-Commit Flow (run_agent)

The **starting commit is NOT decided in this directory** — it arrives pre-resolved as `spec.phylo_node.current_commit` (a `%PhyloGraphNode{repo, base_commit, current_commit}` built by the runtime phase). Upstream resolution: `Runtime.Evolution.run/2` (`runtime/evolution.ex:23`) and `Runtime.Genesis` (`runtime/genesis.ex:23`) call `Runtime.Helpers.resolve_starting_commit/2` (`runtime/helpers.ex:167-180`): nil → `PhyloGraphNode.current_head/1` (HEAD); a ref → `Git.rev_parse/2`. Ref sources: CLI evolve `-s/--start-commit` (`cli.ex:89`, `cli/parser.ex:34`); task resume (`TaskRegistry.ResumeContext.apply_resume_context/3`, `task_registry/resume_context.ex:43-54` — sets `:starting_commit` to the previous task's `commit_sha`); Genesis Mode B's second root starts from `architect_output.commit_sha || base_sha` (`runtime/genesis.ex:143-144`).

Spawn flow: `AgentScheduler.run_agent/2` (`agent_scheduler.ex:80-82`) → `handle_call({:run_agent, spec}, ...)` (`agent_scheduler.ex:593-641`): derives `task_id` from `spec.opts[:task_id]` (else random hex, :595); refuses `{:error, :cancelled}` when the task is in the `:evogit_cancelling_tasks` marker (blocks Genesis Mode B's second root during cancel, :602-607); resets per-task archive (`Lifecycle.clear_archive_records`, :612); resolves repo root (`Dispatch.resolve_agent_repo_root/2`, dispatch.ex:367-386); computes `task_number = Dispatch.next_task_number/1` (scans `.genesis/workers/worker_T*`, dispatch.ex:133-159); then `Dispatch.register_agent/7` (dispatch.ex:39-117: `id = state.next_agent_id`; `task_local_id` from `state.task_local_counters` starting at 1; writes `%AgentState{}` with `phylo_node: nil` + `%SchedMeta{}` carrying the full original `spec`). Paused → queued; else `Dispatch.try_dispatch/2` (dispatch.ex:176-247): computes `worktree_path = <repo_root>/.genesis/workers/worker_T#{task_number}_A#{task_local_id}`, stores it in SchedMeta BEFORE spawning, then `Task.Supervisor.async_nolink(EvoGit.TaskSupervisor, spec.agent_module, :run, [spec.objective, dispatch_ctx])` (:225-231); the agent's Runner requests the fresh worktree from `WorktreeManager.create_worktree_for_agent/6` (runner.ex:182-189).

**Checkout to the starting commit** happens in `Worktrees.create_worktree/6` (worktrees.ex:94-135): `commit_sha = spec.phylo_node.current_commit` goes to `EvoGit.Adapters.CowWorktree.create_worktree/6` (or fallback `Git.add_worktree(repo_root, worktree_path, commit_sha, branch_name)`), then `assign_and_prepare_worktree/3` (worktrees.ex:295-345) — after the registered-linked-worktree guard (`ensure_linked_worktree/2`, worktrees.ex:347-388: asserts `wt/.git` is a FILE with `gitdir: <path>` under `<repo_root>/.git/worktrees/`; refuses `{:error, {:worktree_prepare_failed, :not_a_linked_worktree}}` WITHOUT running git against a plain dir — see "Worktree Safety" below) — runs `Git.clean` + `Git.checkout(wt, branch_name)` and writes the worktree-bound phylo_node (`repo: wt`, `base_commit: spec.phylo_node.base_commit`, `current_commit: commit_sha`) into AgentState ETS — this is where `AgentState.phylo_node` transitions from nil to the live node. During the run the agent advances it via `ToolDispatch.sync_current_commit_after_tools/1` / `sync_and_get_current_commit/1` (agent/tool_dispatch.ex:50-84) → `AgentScheduler.update_phylo_node/2` (agent_scheduler.ex:226-230). Subagent phylo nodes: `build_subagent_phylo_node/6` (agent/subagent_processing.ex:569-601) — explicit `commit_id` validated via `Git.rev_parse`, else parent's `current_commit`; cross-repo uses tracked `foreign_repo_commits` or foreign HEAD (:603-614). Both creation paths (CoW and `Git.add_worktree` fallback) handle gitlink/submodule entries like `git worktree add`: submodule dirs arrive in worktrees as **empty placeholders** (never CoW-copied — `Git.ls_tree_names/2` excludes gitlinks); `Git.clean/1` (`git clean -fd`) neither deletes the tracked placeholder dirs nor fails; populate via `git submodule update --init`.

**No reuse / no resume-checkout special-casing in the scheduler layer**: `prepare_new_worktree/5` always destroys leftovers (dir, branch) and creates fresh (worktrees.ex:61, 139-170) — a branch that already has commits is deleted first, then re-created from the spec's starting commit. The only exception is `Subagents.dispatch_ready_parent/3` (subagents.ex:355-390): a waiting parent keeps its LIVE worktree (no new checkout). A resumed TASK's "existing commits" are handled entirely upstream by setting `:starting_commit` in opts (see `task_registry/resume_context.ex`).

## Agent-facing submodule awareness (repo_notes)

`AgentSpec.repo_notes` (`String.t() | nil`) carries the **already-rendered** git-submodules note block — rendered ONCE at root spec build by `EvoGit.Runtime.Helpers.load_repo_notes/2` (calls `Git.ls_tree_gitlinks/2`; nil when the repo has no gitlinks or detection fails — graceful degradation, no `try/rescue`). Registration copies it into `AgentState.repo_notes` (`Dispatch.register_agent/7`, dispatch.ex:95, alongside `foreign_repos:`); the Runner copies it into `LoopState.repo_notes` (runner.ex:152) and renders it into the agent's `<context>` block via `ContextBuilder.build_repo_notes_section/1` (blank when nil — dropped by the blank-filter, so repos without submodules get no noise). **Subagents inherit the rendered text** — `SubagentProcessing.build_subagent_specs/3` reads `state.repo_notes` (subagent_processing.ex:131) and passes `repo_notes:` to the subagent `AgentSpec.new(...)` (no re-detection; a foreign-repo subagent still carries the PRIMARY repo's note). Detection happens at the primary-repo root specs only: `Runtime.Evolution.run_resolved_root_agent/7` (evolution.ex:118) and `Runtime.Genesis` Mode A / Mode B architect / Mode B implementation roots (genesis.ex:49, 114, 192) — Mode B's second root detects against the architect's final commit tree (`architect_output.commit_sha || base_sha`).

## Repo-Nil Tolerance & Repo-Less Agent Plumbing

Facts about which scheduler paths tolerate `nil` repo/worktree fields and which hard-dereference them. The repo-less self-reflective agent (`EvoGit.Agents.SelfReflective`, `spec.opts[:repo_less] = true`; phylo_node nil, repo root = Genesis source root or `"[system]"`) runs on this plumbing — nothing in this subtree runs git or creates worktrees for repo-less agents.

**Nil-tolerant:**
- `AgentState.phylo_node` defaults nil (agent_state.ex:44), written nil at registration (dispatch.ex:81) and on crash-retry reset (lifecycle.ex:162) — a transient nil phylo_node in ETS is the NORMAL state.
- `AgentState.repo_root` defaults nil (agent_state.ex:60); `Dispatch.resolve_agent_repo_root/2` returns nil when a foreign repo id is missing from `spec.foreign_repos` (dispatch.ex:525).
- `RemoteAPI.get_agent_state/1` (remote_api.ex:125-130) only drops `:context`; `get_agent_history/1` (remote_api.ex:102-113) reads only `state.context`.
- `Dispatch.commit_pending_in_worktree/0` is repo-less-safe: `Process.get(:repo_less)` → immediate `:ok` (never git-commits the Genesis source root); otherwise `if wt = Process.get(:repo_path)` → `:ok` when unset.
- Runner skill loading guards nil repo_root (`if repo_root && is_binary(repo_root)`, runner.ex:119).
- `RemoteAPI.build_agent_summary/3` nil-guards `phylo.current_commit`/`phylo.base_commit`/`context_node.path` (`safe_phylo_commit/2`/`safe_context_path/1`): repo-less agents emit `current_commit: nil`/`base_commit: nil` instead of crashing the dashboard's `list_agents` RPC.
- `Subagents.dispatch_ready_parent/3` logs `"unknown"` commit for a repo-less parent (nil phylo_node) instead of raising KeyError.

**Hard-dereferences (crash on nil — repo-less agents must guard/avoid):**
- `Dispatch.resolve_agent_repo_root/2` primary branch: `String.split(spec.phylo_node.repo, "/.genesis/workers/", parts: 2)` — nil `spec.phylo_node` → FunctionClauseError for NORMAL agents; repo-less agents short-circuit to a binary BEFORE touching `spec.phylo_node`. Called from `register_agent` (dispatch.ex:69) and `do_try_dispatch` (dispatch.ex:204 — the latter runs in the scheduler GenServer process, so a crash takes the scheduler down).
- `Dispatch.do_try_dispatch`: `worktree_path = Path.join([agent_repo_root, ".genesis/workers", ...])` — nil root raises ArgumentError; repo-less agents get a binary from `resolve_agent_repo_root/2`. Their `worktree_path` is synthetic (stored in SchedMeta for cancel lookup, NEVER created on disk — the Runner skips `create_worktree_for_agent`).
- `WorktreeManager.maybe_init_repo/2` → `Worktrees.workers_dir/1` (`Path.join(repo_root, ".genesis/workers")`, worktrees.ex:26) — nil root raises ArgumentError inside the WorktreeManager GenServer.
- `Runner.setup_dispatch_context/1` (runner.ex:158-211) UNCONDITIONALLY calls `WorktreeManager.create_worktree_for_agent(agent_id, repo_root, worktree_path, spec, meta, self())` and raises `"Failed to create worktree..."` on `{:error, reason}` (runner.ex:188-201) — the agent Task crashes → scheduler crash-retry. `Process.put(:repo_path, worktree_path)` (runner.ex:179) is what `commit_pending_in_worktree` reads. `Runner.do_run/2` also requires `Process.get(:repo_path)` (`Path.join(repo_path, node_path)` + `File.exists?` validation, runner.ex:62-70).
- `Worktrees.assign_and_prepare_worktree/3` (worktrees.ex:295-345): bare matches `{:ok, meta} = Store.get_sched_meta(agent_id)` / `{:ok, %AgentState{}}`, reads `spec.phylo_node.current_commit`, FIRST runs the registered-linked-worktree guard `ensure_linked_worktree/2` (worktrees.ex:347-388 — `.git`-file check, see "Worktree Safety"; refuses `{:error, {:worktree_prepare_failed, :not_a_linked_worktree}}` without running git), then runs `Git.clean`+`Git.checkout`, then writes the worktree-bound phylo_node (`repo: wt`) into AgentState. `Worktrees.branch_name/2` (worktrees.ex:31-33) is repo-agnostic — only used for branch naming.
- `SchedMeta` (sched_meta.ex:39-58) carries `worktree` (nil default, set at dispatch), `task_number`, `spec` (full `%AgentSpec{}` incl. phylo_node/repo_id/foreign_repos), `foreign_repo_commits`; no `repo_root` field. `Slots` has NO repo-specific state (pure per-model_id LLM/tool pools).
- `commit_pending_in_worktree/0` is fully safe on missing/non-git paths (dispatch.ex:271-312): nil `:repo_path` → skips, `:ok`; missing path → `Git.run/2`'s `File.dir?` guard returns `{:error, {:enoent, ...}}` (git.ex:64-66); bare non-git dir → `git status --porcelain` exits 128 → `{:error, {128, "fatal: not a git repository..."}}` (git.ex:89-95); both fall into the `with`'s `else error -> Logger.warning(...)` arm → `:ok`. Never raises. Call sites: `Runner.run/3` `try/after` (runner.ex:48-52 — cannot mask a `do_run` exception) and `SubagentProcessing.process_subagent_calls` (subagent_processing.ex:60, inline before `spawn_sub_agents`).
- `dispatch_ctx` keys (dispatch.ex): `[agent_id:, depth:, repo_root:, repo_id:, worktree_path:, retries:, spec:, meta:]` — all `Keyword.fetch!`'d in `setup_dispatch_context` (runner.ex:159-166); `meta` = full `%SchedMeta{}` (status `:pending | :running | :waiting | :ready | :blocked`). Repo-less agents additionally carry `repo_less: true` + `repo_less_repo_path: <resolved root>`. `SchedMeta.worktree` defaults nil (sched_meta.ex:48), set in `do_try_dispatch` BEFORE the task spawn.
- Child AgentState gets `repo_id` + `repo_root` only — no worktree_path field (dispatch.ex:79-95): `phylo_node` starts nil, bound to the worktree later by `Worktrees.assign_and_prepare_worktree/3`. Each subagent gets its OWN fresh worker dir under the repo root (computed in `do_try_dispatch`), never the parent's path.
- Subagent validation never checks repo existence (`validate_single_subagent/5`, subagents.ex:130-144): only depth, `ContextNode.is_ignored?`, and the spatial contract (which reads `spec.context_node.path` — nil context_node would raise via `.path` access). A nil/phantom-repo spec passes validation and crashes later in dispatch/worktree creation.

**Repo-less plumbing specifics:**
- `Dispatch.resolve_agent_repo_root/2` resolves repo-less roots FIRST via the SHARED chain `EvoGit.SelfReflectiveSource.reference_path/0` (`:self_reflective_source_root` app env → `GENESIS_SOURCE_ROOT` env var → valid managed clone at `<data_dir>/genesis-source`), terminal fallback `File.cwd!()` (dev = the genesis repo) → `"[system]"`. `EvoGit.Runtime.SelfReflective.source_root/0` delegates to the same `reference_path/0` (with `File.cwd!()` fallback) so both always agree.
- `Dispatch.do_try_dispatch` appends `repo_less: true` + `repo_less_repo_path: <resolved root>` to the dispatch_ctx (the Runner uses `repo_less_repo_path` as its `Process.get(:repo_path)` and SKIPS `create_worktree_for_agent`).
- `Dispatch.commit_pending_in_worktree/0` no-ops for repo-less agents (guarded on `Process.get(:repo_less)`) — never `git add/commit` against the real Genesis source root.
- Runner-side (outside this subtree, `agent/`): `Runner.setup_dispatch_context/1` skips `create_worktree_for_agent` and sets `:repo_path` from `repo_less_repo_path`; `ToolDispatch.sync_current_commit_after_tools` is skipped (no commits to track).

|---|---|
| `EvoGit.AgentScheduler.State` | GenServer state struct — configuration, agent lifecycle queues, slot holder sets |
| `EvoGit.AgentScheduler.AgentState` | Live agent state in `:evogit_agent_state` ETS — context_node, phylo_node, objective, repo_id, foreign_repos, `repo_notes` (already-rendered git-submodules note block, `String.t() \| nil`; set at registration from `spec.repo_notes`, rendered into the agent's `<context>` block, inherited by subagents via LoopState — see "Agent-facing submodule awareness") |
| `EvoGit.AgentScheduler.SchedMeta` | Scheduler-private metadata in `:evogit_sched_meta` ETS — status, depth, worktree, subagent tracking |
| `EvoGit.AgentScheduler.Slots` | Pure-function LLM/tool slot management using holder MapSets with FIFO queuing and rate-limit backoff |
| `EvoGit.AgentScheduler.Worktrees` | Pure helper functions for the worktree create pipeline (no own state): `workers_dir/1`, `assign_and_prepare_worktree/3` (registered-linked-worktree guard via `ensure_linked_worktree/2` — `.git`-file check against `<repo_root>/.git/worktrees/`, refuses `{:error, {:worktree_prepare_failed, :not_a_linked_worktree}}` without running git — then git clean + checkout agent branch + bind `phylo_node.repo = worktree` in ETS; `repo_root` is an explicit param, resolved by `Dispatch.resolve_agent_repo_root/2`, NOT `spec.phylo_node.repo` which for subagents is the parent's worktree path), `run_init_script/3` (genesis.toml `[worktree]` script; env `SOURCE_REPO_PATH`/`SOURCE_WORKTREE_PATH`/`TARGET_WORKTREE_PATH`), `prepare_new_worktree/5` (fresh-create pipeline: destroy leftover dir/branch via `destroy_leftovers/3` — rm_rf failure ESCALATES to `{:error, {:worktree_create_failed, msg}}` and skips the prune (dir+registration consistency, see "Worktree Safety"); same retried `WorktreeRetry` helpers, never raises (runs in the offloaded create task) → CoW create via `EvoGit.Adapters.CowWorktree.create_worktree` with `Git.add_worktree` fallback → assign_and_prepare → init script for primary repo only), `branch_name/2` (single source of truth: `"evogit-agent-T#{task_number}-A#{task_local_id}"`), `delete_branch_tolerant/2` ("branch not found" AND repo-gone outputs — "Repository path does not exist" / "not a git repository" via `WorktreeRetry.repo_gone_output?/1` — treated as `:ok`: a vanished repo implies the branch is gone with it; "used by worktree at" / "checked out at" is RECOVERABLE — prune stale registrations + retry once, see "Worktree Safety"). No fast/slow path — every agent run gets a FRESH worktree. |
| `EvoGit.AgentScheduler.WorktreeManager` | Stateful GenServer owning the entire worktree lifecycle (supervised in `EvoGit.Application`, same name). Lazy per-repo initialization (`maybe_init_repo/2`) on the FIRST create request for a repo — never from the scheduler — gated on a **persistent per-repo marker** in the app-owned ETS table `:evogit_worktree_repos` (created in `EvoGit.Application.start/2`, same pattern as `:evogit_cancelling_tasks`; read/written defensively via `:ets.whereis` — a missing table means "uninitialized"). **Marker present** (WorktreeManager-only restart) → destructive wipe SKIPPED (no rm_rf, no orphaned `evogit-agent-*` cleanup, no prune), only the workers dir ensured via `WorktreeRetry.mkdir_p_retry/2` — live agents' worktrees preserved. **Marker absent** (first request, or genuine BEAM restart with no live agents) → full wipe (rm_rf workers dir → `Git.prune_worktrees` → orphaned branch cleanup → mkdir_p) then marker recorded (`repo_root` => init timestamp) — **the destructive steps (rm_rf + orphaned `evogit-agent-*` branch cleanup) run for the PRIMARY repo only**: `maybe_init_repo/3` takes a `primary?` flag derived at the call sites from `spec.repo_id` (`EvoGit.Core.ForeignRepo.primary?/1`); foreign repos (possibly writable per-task, holding real task branches) get only the non-destructive prune + workers-dir ensure + init marker. All init steps via `WorktreeRetry` (`rm_rf_retry` log-and-continue on exhaustion; `retry_on_transient` around prune; `mkdir_p_retry` raises `File.Error` on exhaustion — safe because the marker is written before the first worktree exists). Request API: `create_worktree_for_agent(agent_id, repo_root, worktree_path, spec, meta, agent_pid)` — `GenServer.call` with named 1-hour timeout (`@worktree_call_timeout` 3_600_000), called by the agent Runner; handler offloads blocking create I/O to a spawned `Task` (reply via `GenServer.reply/2` + `{:create_finished, agent_id}` cast), so the loop stays responsive for `:DOWN` handling. Per-agent serialization: a second create request for an in-flight agent is stashed in `pending_requests`, started when the previous finishes; agents dying mid-create tracked in `pending_cleanup`, cleaned up when the create task finishes. `Process.monitor(agent_pid)` per agent; on `:DOWN` for ANY reason (normal exit, crash, cancel kill) the worktree is reclaimed + destroyed (`destroy_worktree/3`): `File.rm_rf(worktree_path)` → only AFTER the dir is gone `Git.prune_worktrees(repo_root)` → `Worktrees.delete_branch_tolerant(repo_root, branch_name)` (this order — git refuses to delete a branch checked out in another worktree; the tolerant delete recovers stale "used by worktree at" registrations). On rm_rf failure it logs at ERROR and skips BOTH prune and branch delete — a dir that survives rm_rf WITH its `.git` file + registration stays a safe registered worktree; pruning it would create the plain-unregistered-dir leak precondition (see "Worktree Safety"). Each step through `WorktreeRetry` (never raises — idempotent; the GenServer never crashes on agent exits). **Crash-restart re-monitoring**: one_for_one child of `EvoGit.Supervisor` — a crash restarts IT without killing the running agent Tasks (which keep running in their live worktrees); `init/1` calls `rebuild_monitors/1` to re-monitor live agents from `:evogit_sched_meta` rows (`worktree`, `task_ref.pid`, `task_number`) + `:evogit_agent_state` rows (`repo_root`, `task_local_id`); missing/stale rows skipped, never crashes init. Kept: `workers_dir/1`, `start_link/1`. |
| `EvoGit.AgentScheduler.WorktreeRetry` | Pure retry helpers for transient filesystem failures in the worktree lifecycle (Windows file locking, anti-virus scans) — single shared implementation (worktree_retry.ex). `rm_rf_retry/2` → `{:ok, files} \| {:error, reason, file}` — retries `File.rm_rf/1` on transient reasons; `:enoent` normalized to `{:ok, []}` (dir already gone = success); non-transient fails fast. `mkdir_p_retry/2` → `:ok \| {:error, reason}`. `retry_on_transient/2` — generic wrapper: success shapes (`:ok`, `{:ok, _}`) halt immediately; retryable = transient POSIX reasons (`:eacces`, `:eperm`, `:eexist`, `:enotempty`, `:ebusy`, `:again`, `:eintr`) in 2-/3-tuple fs error shapes, git `{:error, {tag, output}}` tuples, and binary error shapes — EXCEPT repo-gone outputs ("Repository path does not exist" / "not a git repository", `repo_gone_output?/1`) which fail fast. Policy: 4 total attempts (first immediate — a `0` delay is prepended), exponential backoff 50ms → 100ms → 200ms via `Retry.DelayStreams` (the `retry` hex lib; `opts[:delays]` overridable for hermetic tests — `[0,0,0]`/`[]` never sleep). Design: `Enum.reduce_while` over `Retry.DelayStreams` — the `retry` macro's `atoms:` predicate cannot express the mixed return-shape classification and its default `rescue_only: [RuntimeError]` would retry exceptions that must fail fast. Never raises on its own; exceptions from the wrapped fun propagate (fail fast). |
| `EvoGit.AgentScheduler.Dispatch` | Agent registration, dispatching, agent-process git commit, repo root resolution, queue processing |
| `EvoGit.AgentScheduler.Subagents` | Subagent validation/spawning, spatial contract checks, result tracking, parent resumption |
| `EvoGit.AgentScheduler.Lifecycle` | Agent recycling (cleanup) and crash handling (retry logic, permanent failure) |
| `EvoGit.AgentScheduler.PubSub` | Centralized broadcast helpers — throttled `{:agents_updated, node}` (via `Throttle` GenServer supervised under `EvoGit.Supervisor`, see "Throttled PubSub") plus delta broadcasts `{:agent_registered, agent_id, summary, node}` / `{:agent_updated, agent_id, changed_fields, node}` / `{:agent_removed, agent_id, node}`, and config broadcast `{:scheduler_config_updated, node}` — every broadcast carries a trailing `node` element computed inside the helpers. Agent-state broadcast kwlists have the heavy `:context` field stripped, with `message_count` added when a context is present; ETS writes stay verbatim (see `EvoGit.AgentScheduler.Store`) |
| `EvoGit.AgentScheduler.PubSub.Throttle` | GenServer (throttle.ex) — coalesces `:schedule` casts into one flush broadcast 200ms after the last schedule; supervised child of `EvoGit.Supervisor` (`:permanent` restart), declared in `EvoGit.Application`'s children after `Phoenix.PubSub` |

### Slot Management (Slots module)

Two independent slot pools tracked as `MapSet`s of agent IDs. Available capacity is derived: `capacity - map_size(holders)` — slot leaks impossible by construction: when an agent dies, `release_agent_slots/2` removes it from both holder sets, restoring the slot automatically.

| Pool | State Keys | Capacity | Backoff |
|------|-----------|----------|---------|
| LLM slots | `llm_holders`, `llm_waiting`, `llm_backoff_until` | **per-model** `model_concurrency[model_id]` (from `[[llm.models]]` profile `concurrency`, default 3); fallback `default_llm_max_concurrency` (3) for unknown model_ids via `State.concurrency_for/2` | **per-model** 60s cooldown on `:rate_limit` errors (NOT global — one model's rate limit doesn't block others) |
| Tool slots | `tool_holders`, `tool_waiting` | `max_tool_concurrency` (2) | None |

Key functions: `handle_request_llm_slot/3`, `handle_request_tool_slot/3` (grant if capacity available, else enqueue); `handle_release_llm_slot/2`, `handle_release_tool_slot/2` (remove from holder set, grant pending — called via `handle_cast`, fire-and-forget; return `{state, status_updates}`); `release_agent_slots/2` (on agent death `:DOWN`: removes from both holder sets, purges queues, grants pending); `purge_agents_from_queues/2` (removes agents from waiting queues, replies `{:error, :cancelled}` to each); `grant_pending_on_resume/1` (grants all available slots when resuming from pause; also runs at the END of every config update (state.ex), so a 0→N capacity increase (peak exit) grants queued 0-capacity waiters automatically).

Slot functions return `{:reply, :ok, state, status_updates}` or `{:noreply, state, status_updates}` for synchronous operations, and `{state, status_updates}` for asynchronous releases (`handle_cast`). `status_updates` contains `{agent_id, :blocked | :running}` tuples applied to ETS SchedMeta for dashboard visibility.

### `scheduler.default_llm_max_concurrency` precedence

`scheduler.default_llm_max_concurrency` is the **default per-LLM concurrency**, NOT a global cap:
- **Effective LLM limit for an agent = `model_concurrency[model_id]` if present, else `state.default_llm_max_concurrency`** (`State.concurrency_for/2`, state.ex:205-207). Both slot enforcers read it: `Slots.do_handle_request_llm_slot/4` (slots.ex:103) and `Slots.grant_llm_from_queue/2` (slots.ex:399).
- `model_concurrency` is populated at config-load time ONLY by `State.from_model_profiles/2` (state.ex:146-151) from `[[llm.models]]` profile `concurrency` fields (default 3), at `AgentScheduler.init/1` (agent_scheduler.ex:419) and `State.do_update_config`'s `:model_profiles` branch (state.ex:299-301) — the `reload_config` path (`RemoteAPI.build_reload_opts`, remote_api.ex:192-222). At RUNTIME it can additionally be replaced wholesale via `update_config(model_concurrency: map)` (the dynamic wall-clock engine path — see "Slot-Pool Sizing & Concurrency").
- **Legacy (no `[[llm.models]]`) path**: `scheduler.default_llm_max_concurrency` is live — it becomes the synthesized "default" profile's `concurrency` via `Schema.LLM.build_legacy_default_profile/1` (schema/llm.ex:123), then flows into `model_concurrency["default"]`. Config-load time only (init or reload), NOT runtime.
- **When `[[llm.models]]` profiles exist**: each profile's own `concurrency` wins for its pool; `scheduler.default_llm_max_concurrency` does NOT cap or override it — it remains only as (a) the fallback for agents whose `model_id` is not in `model_concurrency` (state.ex:206) and (b) the value surfaced in `get_config/0` as `default_llm_max_concurrency` (agent_scheduler.ex:656).
- **CLI `-c`/`--concurrency` runtime override (floor semantics)**: `CLI.Parser.configure_scheduler/1` maps `-c` → `update_config(default_llm_max_concurrency: N)` (parser.ex:67) → `State.do_update_config`'s `maybe_apply_default_llm_concurrency` step → `State.apply_default_llm_concurrency_override/2`, which sets `state.default_llm_max_concurrency = N` AND raises every `model_concurrency` entry to `max(c, N)`. Raising the default takes effect immediately for ALL live pools — with AND without `[[llm.models]]` profiles (an explicit profile concurrency above the default still wins and is never lowered). The floor applies to runtime `update_config` only — at init the file semantics remain "profile wins". (`--tool-concurrency` → `update_config(max_tool_concurrency: N)` also takes effect — tool slots read `state.max_tool_concurrency` directly, slots.ex:219.)

### Slot-Pool Sizing & Concurrency

Coordinated behaviors in `state.ex` + `slots.ex` (do not regress):

- **Config updates preserve live LLM pools**: `State.do_update_config/2`'s `:model_profiles` branch calls `from_model_profiles(profiles, opts)` (opts pass-through so a `:default_llm_max_concurrency` override in the same update is honored) and merges the existing `llm_holders`/`llm_waiting`/`llm_backoff_until`/`llm_last_granted` maps OVER the fresh ones (existing entries win; new profile ids keep fresh empty entries; stale pool ids keep live entries), then `prune_empty_pools/1` drops empty-value entries. Trailing `Slots.grant_pending_on_resume(state)` (state.ex:399) grants under the new capacity. Queued waiters' `GenServer.from`s survive the update; live holders stay counted (no over-grant beyond capacity).
- **Stale-model pools are visible to all sweeps**: `State.all_model_ids/1` returns the UNION of keys of `model_concurrency`, `llm_holders`, `llm_waiting`, `llm_backoff_until` — pools for model_ids absent from `model_concurrency` (stale ETS `model_id` after a profiles update; unknown models) are swept by `grant_pending_llm_slots` (both Enum.reduce sweeps), `release_agent_slots`'s LLM cleanup, and `purge_llm_waiting_queues`. Capacity for a stale pool = `concurrency_for`'s fallback (`default_llm_max_concurrency`).
- **LLM slot release scans all pools**: `Slots.handle_release_llm_slot/2` scans ALL pool ids (`State.all_model_ids`) rather than resolving the model via ETS at cast-processing time (which picks the wrong pool when the ETS entry is gone), deletes the agent from every pool's holder set (idempotent — an agent holds at most one LLM slot), cleans `llm_last_granted` for the pool it was removed from, then runs `grant_pending_llm_slots`.
- **`default_llm_max_concurrency` override is a floor**: `maybe_apply_default_llm_concurrency/2` → public `State.apply_default_llm_concurrency_override/2` sets the default AND applies a FLOOR to every `model_concurrency` entry (`max(c, N)`; explicit `0` entries — the peak hard-pause sentinel — stay `0`); applies whether or not `:model_profiles` is in the same update (CLI `-c` and the dashboard default-concurrency slider raise the effective capacity of ALL live pools immediately).
- **Dynamic `:model_concurrency` override (wall-clock engine path)**: `State.do_update_config/2`'s `maybe_update_model_concurrency/2` step (private, state.ex) replaces `state.model_concurrency` with the given `%{model_id => non_neg_integer()}` map — the runtime entry point for `EvoGit.PeakHourEngine`. After replacement it re-applies the floor via `apply_default_llm_concurrency_override(state, state.default_llm_max_concurrency)` — an engine update below an active floor NEVER drops it (the floor is a LOWER BOUND), **EXCEPT explicit `0` entries (the peak hard-pause sentinel), which are never floored up**; the engine applies the identical rule (`effective 0 → 0`), so the fixed point holds end-to-end. Independent of `from_model_profiles/2` (config loading stays wall-clock agnostic; the engine owns dynamic overrides). Capacity changes take effect immediately via the END-of-update `Slots.grant_pending_on_resume(state)` sweep (runs for EVERY update). The `AgentScheduler` handler (`handle_call({:update_config, opts}, ...)` → `reconcile_pool_after_update`) reconciles the ReqLLM Finch pool from the new `model_concurrency`/`default_llm_max_concurrency`.
- **0-capacity LLM slots enqueue and block (peak hard pause)**: `concurrency_for/2` may legitimately return `0` (the engine emits `{model_id, 0}` during peak windows for `peak_concurrency = 0` profiles). A slot request for a 0-capacity model enqueues exactly like the paused-scheduler case — `Slots.handle_request_llm_slot/3` has no 0-capacity pre-check, so flow falls through to the paused branch (or `do_handle_request_llm_slot/4`'s full-queue branch), storing `{agent_id, from, nil}` and replying `{:noreply, state, [{agent_id, :blocked}]}` — the agent blocks until capacity returns. `Slots.grant_llm_from_queue/2` at capacity 0 is a no-op that KEEPS the waiting queue untouched (`{state, []}` — no replies, no drain, no status updates): waiters stay queued, and a 0→N transition (peak exit → `update_config(model_concurrency: %{...})` → end-of-update `grant_pending_on_resume/1` sweep → normal grant branch) grants them automatically. In-flight holders are never evicted (at 0 the release sweep is a no-op). `AgentScheduler.with_llm_slot/2` does not raise on zero capacity — agents wait. Graceful cancel unblocks blocked agents of the cancelling task: `begin_graceful_cancel/1` purges their LLM/tool waiting-queue entries via `Slots.purge_agents_from_queues/2`, replying `{:error, :cancelled}` → the blocked `with_llm_slot` raises → crash-retry → the agent enters cancel-grace at its next loop top (reads `cancel_requested`, saves work, calls `complete_task`). Force-kill's `{:error, :cancelled}` purge path is unchanged and capacity-independent.

### Peak/Off-Peak Slot Diagnostics (logging)

Diagnostic logging for the blocked-after-peak-exit case lives on the SLOT side here (`slots.ex`) plus the scheduler's `model_concurrency` update (`agent_scheduler.ex`); the engine-side wakeup/decision logging is documented in `../CONTEXT.md` ("Peak/Off-Peak Diagnostics"). Read the slot-side lines in this order:

1. **`AgentScheduler: model_concurrency updated — old=... new=... skip_floor=... default_llm_max_concurrency=...`** (info, `agent_scheduler.ex` `log_model_concurrency_update/3` in `handle_call({:update_config, opts}, ...)`) — every `:model_concurrency` update logs the pre-update map vs the POST-application map (post-floor / verbatim for `model_concurrency_skip_floor: true`). `old=%{"m" => 0} new=%{"m" => 5}` ⇒ capacity WAS restored by the engine; `old==new` ⇒ the update was a no-op (or the engine never applied).
2. **`AgentScheduler: LLM slot grant sweep (resume) — model=... capacity=... waiting_before=... granted=... waiting_after=...`** (info when `granted > 0` or `capacity == 0 and waiting_before > 0`, else debug; `slots.ex` `grant_pending_on_resume/1`) — the end-of-update sweep that grants queued 0-capacity waiters. `capacity=5 waiting_before=3 granted=0 waiting_after=3` is the **"applied but queued waiter never granted"** symptom. `grant_pending_llm_slots/1` returns a per-model sweep tuple `{model_id, capacity, waiting_before, granted, waiting_after}` (third return element) to feed this log; the other three callers (`handle_release_llm_slot/2`, `handle_retry_llm_waiting/1`, `release_agent_slots/2`) discard it.
3. **Debug per-agent events** (`slots.ex`): `LLM slot request ENQUEUED — agent=... model=... capacity=0 (peak pause)` at the 0-capacity enqueue point in `do_handle_request_llm_slot/4`; `granted LLM slot — agent=... model=...` at each queue grant in `grant_llm_from_queue/2` (right after `GenServer.reply(from, :ok)`); `purged N LLM waiter(s) for model ... — agent(s) [...]` in `purge_llm_waiting_queues/2` when a cancel/force-kill purge removes queued waiters (the "rejected" counterpart of the sweep's granted/remaining counts).

Logging-only: no behavior, timing, floor, fixed-point, or slot semantics changed; `grant_pending_llm_slots/1`'s return shape grew a third element purely to carry sweep stats.

### Running Count

No `running_count` field — always derived as `map_size(state.ref_to_agent)`. Every agent lifecycle transition (dispatch, completion, crash) pops or puts from `ref_to_agent`, keeping the count authoritative.

### Multi-Task Repo Root Resolution

The scheduler supports multiple concurrent tasks targeting different repos. Repo root resolution priority:
1. **Per-agent ETS** (`AgentState.repo_root`) — set at registration via `Dispatch.resolve_agent_repo_root/2`, derived from spec data. Used by `Lifecycle` for agent cleanup/retry paths.
2. **Process dictionary** (`Process.get(:genesis_repo_root)`) — set at dispatch time in `try_dispatch/2`. Preferred by `current_repo_root/0` for runtime lookups.

No global `state.repo_root` fallback — always per-agent. Repo-init tracking lives in `WorktreeManager` (lazy per-repo init on first create request); `%State{}` does not carry `initialized`/`initialized_repos` fields.

`resolve_agent_repo_root/2` in Dispatch is self-contained for primary repos (strips worktree suffix from `spec.phylo_node.repo`). For foreign repos it looks up the repo root from the agent's own `spec.foreign_repos` list by `spec.repo_id` — foreign repos are carried per-agent, not in global scheduler state.

### Worktree Lifecycle (WorktreeManager + Worktrees)

Worktrees are **created fresh per agent run** — NO pool, NO persistent-worktree reuse across retries (no fast/slow path, no `File.exists?` reuse branch, no `newly_created` flag). The entire lifecycle is owned by the `WorktreeManager` GenServer:

1. **Lazy per-repo init** — on the FIRST `create_worktree_for_agent/6` request for a repo: rm_rf `.genesis/workers` → `git worktree prune` → orphaned `evogit-agent-*` branch cleanup → mkdir_p. Never called from the scheduler. The destructive wipe is gated on the **persistent per-repo marker** `:evogit_worktree_repos` (app-owned ETS): marker present (WorktreeManager-only restart) → wipe skipped, only the workers dir ensured; marker absent (first request, or BEAM restart with all agents dead) → full wipe + marker recorded. **PRIMARY-ONLY destructive steps**: the rm_rf workers-base wipe and the orphaned-`evogit-agent-*`-branch cleanup run only when `primary?` (derived from `spec.repo_id` via `ForeignRepo.primary?/1` at the two handle_call call sites); foreign repos — which may be writable per-task and carry real `evogit-agent-*` task branches — get only the non-destructive `Git.prune_worktrees` + workers-dir ensure + init marker. (See the WorktreeManager row.)
2. **Runner requests a fresh worktree** — `EvoGit.Agent.Runner.setup_dispatch_context/1` calls `WorktreeManager.create_worktree_for_agent(agent_id, repo_root, worktree_path, spec, meta, self())` with the named 1-hour timeout; the handler offloads the blocking create I/O to a spawned `Task` (reply via `GenServer.reply/2`, `{:create_finished, agent_id}` cast on completion) so the loop stays responsive for `:DOWN` handling. On `{:error, ...}` the Runner raises → agent Task crashes → scheduler crash-retry → fresh worktree.
3. **Create pipeline** (`Worktrees.prepare_new_worktree/5`, inside the create task): destroy leftover dir/branch (rm_rf failure escalates — see "Worktree Safety") → CoW create via `EvoGit.Adapters.CowWorktree.create_worktree` (fallback `Git.add_worktree`; failure → `{:error, {:worktree_create_failed, msg}}`) → `assign_and_prepare_worktree/3` (registered-linked-worktree guard, then git clean + checkout agent branch + bind `phylo_node.repo = worktree` in ETS; `repo_root` passed explicitly) → `run_init_script/3` (genesis.toml `[worktree]` script, primary repo only; env `SOURCE_REPO_PATH`/`SOURCE_WORKTREE_PATH`/`TARGET_WORKTREE_PATH`; Windows scripts run via `Platform.shell_args/1` → PowerShell `-EncodedCommand` — single source of truth: `EvoGit.Powershell`; base64-encoded so no command-line quoting issues, output forced UTF-8). Branch name from `Worktrees.branch_name/2` — `"evogit-agent-T#{task_number}-A#{task_local_id}"`.
4. **Monitor-based reclaim** — WorktreeManager `Process.monitor`s each agent; on `:DOWN` for ANY reason (normal exit, crash, cancel kill) it destroys the worktree (`destroy_worktree/3`): `File.rm_rf(worktree_path)` → only AFTER the dir is gone `Git.prune_worktrees(repo_root)` → `Worktrees.delete_branch_tolerant(repo_root, branch_name)` (this order — git refuses to delete a branch checked out in another worktree; on rm_rf failure it logs at ERROR and skips both prune and branch delete — see "Worktree Safety"). All destroy steps via `WorktreeRetry` with a modest budget (4 attempts, ≤350ms sleep per op) because `destroy_worktree/3` runs in the WorktreeManager GenServer process. Idempotent; the GenServer never crashes on agent exits. `recycle_agent/2`, `cancel_agent/2` (`Task.shutdown(:brutal_kill)` fires the monitor) and the `handle_agent_crash/3` permanent-failure path never call worktree deletion — cleanup is entirely monitor-driven. After a WorktreeManager-only restart, `init/1` calls `rebuild_monitors/1` to re-monitor live agents from scheduler ETS rows (see the WorktreeManager row) so `:DOWN`-driven cleanup keeps working for worktrees that predate the crash.
5. **Per-agent serialization** — a second create request for an agent whose create is still in flight is stashed in `pending_requests`, started when the previous create finishes (retry-after-crash-during-setup race); agents that die while their create is in flight are tracked in `pending_cleanup`, cleaned up when the create task finishes.

All blocking filesystem operations (rm_rf, prune_worktrees, delete_branch, mkdir_p) run inside `WorktreeManager` (create I/O offloaded to a spawned Task); the scheduler never touches worktree I/O.

### WorktreeRetry — transient filesystem failure retries

`EvoGit.AgentScheduler.WorktreeRetry` is the single shared implementation of all retry logic for the worktree lifecycle. Purpose: Windows file lockers and anti-virus scanners transiently fail file operations with `:eacces`/`:eperm`/`:eexist` (and friends) — a single immediate failure is usually a false alarm; the operation succeeds on retry. (API details in the API Surface table above.) Transient-reason set: `:eacces`, `:eperm`, `:eexist`, `:enotempty`, `:ebusy`, `:again`, `:eintr`. `:enoent` deliberately absent: "not found" means the goal is already met (`rm_rf_retry/2` normalizes `{:error, :enoent, file}` to `{:ok, []}`). Git repo-gone outputs ("Repository path does not exist" / "not a git repository", `repo_gone_output?/1`) also fail fast. The moduledoc in `worktree_retry.ex` is the authoritative detail.

### Agent Dispatching (Dispatch module)

1. `register_agent/6` — Assigns agent IDs, computes task-local IDs, resolves event sink inheritance, writes both ETS tables.
2. `try_dispatch/2` — Scheduling-only dispatch (no worktree I/O). `with` guard bails cleanly if ETS entries are missing (genuine race). Computes the worktree path (`Worktrees.branch_name/2` + workers dir) and stores it in sched_meta **before** spawning (so `cancel_agent` can find the worktree), spawns the task immediately via the 4-arity `Task.Supervisor.async_nolink/4` **named-function** form (`spec.agent_module, :run, [spec.objective, dispatch_ctx]`), updates `ref_to_agent`. **NO git commands, worktree creation, or init scripts run here** — the scheduler never does blocking I/O and never calls any worktree function (not even init). The named-function form makes the spawned process show up as a meaningful `module.run/2` in process inspection.
   - **Worktree creation happens in the agent Task**: `EvoGit.Agent.Runner.setup_dispatch_context/1` (inside `run/2`, the single true entry point for an agent, before the agent loop) calls `WorktreeManager.create_worktree_for_agent(..., self())` with the 1-hour timeout. The create pipeline (`Worktrees.prepare_new_worktree/5` — destroy leftovers → CoW create → assign_and_prepare → init script; lazy per-repo init on first request) runs offloaded inside WorktreeManager, concurrently across subagents. The CoW optimization copies unchanged files from a source working tree (parent's worktree for subagents, repo root for top-level) using `cp --reflink=auto` (Linux) or `cp -c` (macOS), avoiding full git object extraction. Controlled by `[:git, :cow_worktree_creation]` config (`:auto` default). `spawn_validated_subagents`' `Enum.reduce` over `try_dispatch` spawns all tasks immediately.
3. `commit_pending_in_worktree/0` — Best-effort git commit of pending changes, runs in the **agent process** (not the scheduler). Uses `Process.get(:repo_path)` for the worktree path. Handles all git adapter error tuples (`{:ok, _}`, `{:error, _}`, `{:conflict, _}`) explicitly via a `with` block (not a broad `try/rescue`), so failures are logged but never crash. Called via `try/after` in the agent's `run/2` after the agent loop. **The scheduler process NEVER calls git directly.**
4. `resolve_agent_repo_root/2` — Resolves repo root from spec (primary vs foreign repo).
5. `dispatch_queued_agents/1` — Drains queue dispatching agents (used after resume).
6. `process_queue/1` — Processes queue with ready-parent detection (delegates to Subagents).

### Subagent Management (Subagents module)

1. `spawn_validated_subagents/5` — Validates all specs, registers valid ones, replies immediately if all invalid. The parent agent commits its pending changes BEFORE calling `spawn_sub_agents` (done in the agent process via `Dispatch.commit_pending_in_worktree/0`), so the scheduler performs no git operations.
2. `validate_single_subagent/5` — Per-spec validation chain (depth, ignored, spatial).
3. `validate_subagent_depth/3`, `validate_subagent_not_ignored/1` — Individual validation checks.
4. `validate_spatial_contract_for_spec/3,4` (4-arity takes the parent's `depth`; the 3-arity treats the parent as ROOT/depth 0 — backward-compatible entry), `validate_spawn_spatiality/4` — Spatial contract enforcement. Cross-repo delegation: `:read` agents are always allowed in foreign repos at ANY depth (unrestricted); `:read_write` agents are allowed ONLY into foreign repos whose TASK-LEVEL entry (resolved from `spec.foreign_repos` — never the path alone) is `%{writable: true}`, AND only from a ROOT parent (`parent.depth == 0`); unknown repo ids and listed-but-read-only repos are blocked with `{:error, {:foreign_repo_read_only, msg}}`; a non-root parent targeting a writable foreign repo is blocked with `{:error, {:foreign_repo_write_not_root, msg}}`. The messages teach the model: read-only unrestricted; writable = root-only + one-at-a-time; nested agents report needed foreign-repo changes back up to the root. Same-repo spawns WITHIN a foreign repo (`spec.repo_id == parent repo_id`) are unrestricted — the foreign-repo Manager's own internal parallelism is never gated. One-per-batch serialization of accepted writable foreign spawns is enforced by the caller `spawn_validated_subagents/5` (2nd+ accepted writable foreign spec in one batch → `{:error, {:foreign_repo_write_serialized, msg}}`).
5. `store_sub_result/3` — Stores subagent result at correct index in parent's results map; tracks foreign repo commit SHAs in `SchedMeta.foreign_repo_commits` — when a foreign-repo subagent completes successfully, its `commit_sha` is recorded under the `repo_id` key so subsequent subagents targeting the same foreign repo start from that commit instead of HEAD. **Subtree roll-up**: for ANY `{:ok, %Result{}}` result it also merges the subagent result's own `foreign_repo_commits` map (`Map.get(res, :foreign_repo_commits, %{})` — the field is injected by `Lifecycle.inject_foreign_repo_commits/2` at completion, may be absent) via `Map.merge(parent.foreign_repo_commits, child_frc)` — child entries win — so multi-level agent trees accumulate per-repo commits at the root; the direct-commit recording runs on top of the rolled map.
6. `maybe_resume_parent/2` — Checks if all subagents done, resumes parent if so.
7. `dispatch_ready_parent/3` — Replies to parent's GenServer.call with ordered results.
8. `build_ordered_results/2` — Builds final results list in original spec order.

### Agent Lifecycle (Lifecycle module)

1. `recycle_agent/2` — Deletes both ETS entries on normal completion. `with` guard returns state unchanged if the ETS entry is already gone (genuine race between `:DOWN` completion and another cleanup path). Resolves `repo_root` from the agent's own `AgentState` ETS entry (not global state). No worktree deletion — cleanup is monitor-driven (WorktreeManager `:DOWN` handler).
2. `cancel_agent/2` — Kills the agent's Task process via `Task.shutdown(meta.task_ref, :brutal_kill)`. `task_ref` stores a full `%Task{}` struct (not a bare reference), enabling proper shutdown. The kill fires the WorktreeManager `:DOWN` monitor → worktree reclaim. Replies to blocked callers, deletes ETS entries. `case` skips ETS deletion if agent_state is missing.
3. `handle_agent_crash/3` — Retry logic (re-dispatch — the retried agent gets a FRESH worktree from WorktreeManager; crash-retry never reuses a worktree) or permanent failure (ETS cleanup, notify parent/reply error). Both paths resolve `repo_root` from per-agent ETS state; neither calls worktree deletion — cleanup is monitor-driven.
4. `handle_task_result/3` — after marking `result_sent`, injects the agent's own `SchedMeta.foreign_repo_commits` into its result via `inject_foreign_repo_commits/2` (`{:ok, %Result{}}` → `Map.put(res, :foreign_repo_commits, commits)` — Map.put, NOT struct update, because the Result field is being added by the agent stream in parallel; non-Result tuples pass through) BEFORE the parent/root split, so the subagent path (`Subagents.store_sub_result` roll-up) and the root reply both carry it.

## Foreign-Repo Writable Spawn Gate & Per-Repo Commit Roll-up

Writable foreign repos (`EvoGit.Core.ForeignRepo.writable`, default `false`) enable `:read_write` agents to work in foreign repos. Scheduler-side support (SchedMeta collection/injection):

- **Spawn gate** (`Subagents.validate_spatial_contract_for_spec/3,4` — depth-aware 4-arity; backward-compatible 3-arity treats the parent as ROOT; one-per-batch serialization enforced by `spawn_validated_subagents/5`): read-only CROSS-repo spawns (`:read` agent type) into ANY foreign repo at ANY depth are UNRESTRICTED. Write-capable cross-repo spawns (`:read_write` agent type) are allowed ONLY when (1) the target repo's task-level entry — resolved from `spec.foreign_repos` (the task-level list carried into every subagent spec by `build_subagent_specs/3`), NEVER from the path — is `%{writable: true}`, (2) the spawning parent is the ROOT agent (`parent.depth == 0`), and (3) it is the only accepted writable foreign spec in the spawn batch. Check order (cross-repo `:read_write` only): target writable? else `{:error, {:foreign_repo_read_only, msg}}` (unchanged — explains foreign repos may be writable per-task, changes go to `evogit-agent-*` branches tracked by the task and never merged back; suggests `subagent_investigator`/`subagent_task_scheduler` or reporting back) → parent root? else `{:error, {:foreign_repo_write_not_root, msg}}` → one-per-batch? else `{:error, {:foreign_repo_write_serialized, msg}}` (the 2nd+ accepted writable foreign spec in one `spawn_validated_subagents/5` batch — a "writable foreign subagent already accepted" flag is threaded through the reduce; one-per-batch == one-at-a-time because the parent blocks until all batch subagents complete). **Same-repo spawns WITHIN a foreign repo are unrestricted** (`spec.repo_id == parent repo_id` — how the foreign-repo Manager does its own internal parallelism); only CROSS-repo `:read_write` spawns are gated. Same-repo `validate_spawn_spatiality/4` unchanged. Error messages teach the model: read-only unrestricted; writable = root-only + one-at-a-time; the foreign-repo Manager owns its own parallelism (it knows that repo and can serialize/merge its own work); nested agents report needed foreign-repo changes back up to the root (child agents were never supposed to edit foreign repos; parallel writes create merge conflicts the spawning agent cannot resolve — the sandbox restricts write access to the agent's LOCAL path, not the foreign repo path).
- **Subtree roll-up** (`Subagents.store_sub_result/3`): for ANY `{:ok, %Result{}}` subagent result, the parent's `SchedMeta.foreign_repo_commits` is `Map.merge`d with the result's own `foreign_repo_commits` map (read via `Map.get(res, :foreign_repo_commits, %{})` — the field is injected by Lifecycle at completion and may be absent) — child entries win (fresher subtree view) — then the existing direct-commit recording (`Map.put(map, repo_id, sha)` for binary sha + non-nil non-`"primary"` repo_id) runs on top. Multi-level agent trees accumulate per-repo commits at the ROOT's SchedMeta.
- **Result injection** (`Lifecycle.handle_task_result/3` + `inject_foreign_repo_commits/2`): after `result_sent` is set, `meta.foreign_repo_commits` is injected into the `{:ok, %Result{}}` tuple BEFORE the parent/root split, so both the subagent path (roll-up above) and the ROOT's replied result carry the full map — the runtime stream reads `result.foreign_repo_commits` at root completion to build the per-repo report. **Cross-stream note**: the `%Result{}` field `foreign_repo_commits` is introduced by the agent/ stream in parallel — until it lands, injection uses `Map.put(res, :foreign_repo_commits, commits)` and reads use `Map.get(res, :foreign_repo_commits, %{})` (struct-update would raise KeyError on the absent field); behavior is identical once the field exists.
- **Getter** (`AgentScheduler.get_foreign_repo_commits/1`, module at `../agent_scheduler.ex`): returns the agent's SchedMeta `foreign_repo_commits` map; consumed by `agent/subagent_processing.ex:403` to seed subsequent subagent phylo-node starting commits (`build_subagent_specs/3` `foreign_repo_commits` arg).
- **WorktreeManager scoping**: the destructive per-repo init (rm_rf workers base + orphaned-`evogit-agent-*`-branch cleanup) runs for the PRIMARY repo only (`maybe_init_repo/3` `primary?` flag from `spec.repo_id`); foreign repos keep only the non-destructive prune + workers-dir ensure + init marker — their `evogit-agent-*` branches carry real task work and must survive. `Worktrees.run_init_script/3` is already primary-gated; `prepare_new_worktree/5`'s `destroy_leftovers` (own dir + own branch only) is safe for foreign repos.

## Graceful Cancellation (cancel_requested + `:evogit_cancelling_tasks` marker)

**`AgentState.cancel_requested`** (`agent_state.ex:27,63,88`) — `boolean() | nil`, default `nil`. Set by the scheduler when the task is being gracefully cancelled; the runner checks/clears it at the top of each turn and enters cancel-grace (save work → `complete_task`). `EvoGit.AgentScheduler.Store` helpers (`store.ex:199-255`): `set_cancel_requested/1` (sets `true`) and `/2` (arbitrary `boolean() | nil`), `cancel_requested?/1` (boolean getter — `false` when the state is missing or the flag is nil/false), `clear_cancel_requested/1` (sets back to `nil`). All return `:ok | {:error, :not_found}` except the getter.

**`AgentScheduler.begin_graceful_cancel/1`** (public `agent_scheduler.ex:400-402`, handler `:700-731`):
1. Registers `task_id` in the `:evogit_cancelling_tasks` marker — a public `:set` ETS table created in `application.ex:22-27` (owned by the application process, survives scheduler restarts).
2. Scans `SchedMeta.task_id` (same pattern as `force_kill_task_agents`); for each live agent appends the cancel message via **`Store.append_pending_user_message/2`** (NOT `send_user_message` — that's a `GenServer.call` to the scheduler itself, which would self-call deadlock) + `Store.set_cancel_requested/1`.
3. Purges the task's agents from the LLM/tool waiting queues via **`Slots.purge_agents_from_queues/2`**, replying `{:error, :cancelled}` to each blocked `from` — an agent blocked on a zero-capacity (peak-paused) or saturated pool unblocks immediately; the raised error propagates → crash-retry → the agent enters cancel-grace at its next loop top.
4. Exact message text in `cancel_message/0` (`agent_scheduler.ex:375-383`): *"The task is being cancelled by the user. Please immediately save your work: commit any uncommitted changes, then call complete_task with a summary of what was accomplished. You are in a grace period and must call complete_task now."*

**`AgentScheduler.clear_cancelling_task/1`** (public `:412-414`, handler `:734-741`) — deletes the task from the marker, idempotent (defensive against a missing table). Called by TaskRegistry's guarded `clear_cancelling_marker/1` at terminal transitions.

**`run_agent` guard** (`agent_scheduler.ex:568-578`) — replies `{:error, :cancelled}` WITHOUT dispatch when the task is in the marker. Blocks Genesis Mode B's second sequential root agent (which shares the first root's `task_id`) from spawning after the first root completes during a cancel.

**New-agent registration guard** in `Dispatch.register_agent` (`dispatch.ex:103-113`) — agents registered while their task is in the marker (subagent spawns, crash-retries, queued agents starting late) immediately get the cancel message + `cancel_requested` flag, so they enter grace at their first loop top.

**`AgentScheduler.force_kill_task_agents/1`** (public `agent_scheduler.ex:367-369`, handler `:615-697`) — the brutal reverse-depth `:brutal_kill` cascade (removes refs from `ref_to_agent` first, purges queues, releases slots, `Lifecycle.cancel_agent` deepest-first), called by `TaskRegistry.force_kill_task/1`.

**RPC:** `RemoteAPI.cancel_task/1` (graceful — delegates to `TaskRegistry.cancel_task/1`, `remote_api.ex:374-377`) + `RemoteAPI.force_kill_task/1` (`:389-392`); `RemoteNode.cancel_task/2` + `RemoteNode.force_kill_task/2` (`remote_node.ex:449-483` — local-direct when `node == node()`, else `:erpc` routing).

## Shutdown & Restart Safety

Facts relevant to restarting the BEAM (e.g. a desktop auto-update) while agent tasks are in flight:

- **No `terminate/2` anywhere in the scheduler ecosystem** — `AgentScheduler`, `Slots`, `State`, `Store`, and `WorktreeManager` have none (the only `terminate` in the app is `TaskRegistry.terminate/2` → `:ok` no-op). **Worktree cleanup is purely monitor-driven**: `WorktreeManager.handle_info({:DOWN, ...})` (worktree_manager.ex:216-247) destroys the worktree when the AGENT process dies. When the app/BEAM stops, `EvoGit.Supervisor` terminates children in reverse order — `AgentGroupSupervisor` (application.ex:63, last child) goes FIRST, its `one_for_all` (agent_group_supervisor.ex:25) kills `EvoGit.TaskSupervisor` (all agent Tasks, brutal-killed per Task.Supervisor's default `shutdown: :brutal_kill`) + `AgentScheduler`; then WorktreeManager is terminated before it can process the queued `:DOWN`s. **Result: `.genesis/workers/worker_T<n>_A<m>/` dirs and `evogit-agent-T<n>-A<m>` branches remain on disk after any BEAM/app stop.**
- **Next-start cleanup is the lazy per-repo init** (`maybe_init_repo/3`, worktree_manager.ex:268-322, on the FIRST `create_worktree_for_agent` per repo): (1) `rm_rf_retry(worker_base)` deletes the whole `.genesis/workers/` dir (log-and-continue on failure — the following `mkdir_p_retry` is then a no-op), (2) `Git.prune_worktrees(repo_root)` prunes the worktree registry, (3) `clean_orphaned_branches/1` (worktree_manager.ex:456-472) deletes every `evogit-agent-*` branch, (4) `mkdir_p_retry` (raises `File.Error` on exhaustion). No cleanup at boot without a create request. **This full wipe runs ONLY when the persistent per-repo marker `:evogit_worktree_repos` is absent** — i.e. a genuine BEAM/app restart (all agents dead) or the first-ever create for a repo — AND **only for the PRIMARY repo** (steps 1 + 3 are gated on the `primary?` flag from `spec.repo_id`; foreign repos skip them to preserve real task branches). On a **WorktreeManager-only restart** (one_for_one child of `EvoGit.Supervisor`; agent Tasks keep running in their live worktrees) the marker survives → wipe skipped, only `mkdir_p` runs — a manager-only restart never re-wipes live worktrees. The marker is app-owned ETS (dies with the app), written before the first worktree exists, so "marker absent ⇒ no live worktrees for this repo" always holds.
- **Task rows survive in SQLite**; `TaskRegistry.init/1` (task_registry.ex:252-289) reconciles orphaned `:finalizing` → `:failed` and `:cancelling` → `:cancelled` synchronously at boot; `:running` rows are left to the one-shot `:lease_sweep` (task_registry.ex:1354-1394, scheduled 150s after init; `@lease_duration 120`/`@heartbeat_interval 60_000`/`@sweep_after (@lease_duration + 30) * 1000` at task_registry.ex:37-42), which marks `:running` + expired lease + no live agents → `:failed` ("Lease expired; owning instance no longer renewing"). In-flight agent ETS state (`AgentState.context`, `pending_user_messages`, `cancel_requested`) is LOST on BEAM death — ETS tables are owned by the application process.
- **Slot pools are memory-only** (`%State{}`: `llm_holders`, `llm_waiting`, `llm_backoff_until`, `llm_last_granted`, `tool_holders`, `tool_waiting` — state.ex:79-88). On scheduler restart the new `%State{}` is fresh (empty pools from `from_model_profiles`, state.ex:194-196) — capacity-derived holder sets can't leak. Blocked slot waiters (`GenServer.call(:infinity)`, agent_scheduler.ex:263-265, 296-298) exit with the scheduler; no explicit "shutting down" gate — the only slot gating is `state.paused` (slots.ex:89-93, 214-216) and per-model capacity/backoff.
- **Graceful-cancel marker `:evogit_cancelling_tasks`** is ETS owned by the application process — survives scheduler restarts but NOT app restarts; on boot the marker is empty (any `:cancelling` task is reconciled to `:cancelled` by TaskRegistry.init as above).

## Worktree Safety — Main-Copy HEAD Protection (foreign repos)

The foreign repo's MAIN working copy (repo root, not a `.genesis/workers/` worktree) must never have its HEAD moved by the framework pre-merge. Empirically verified on git 2.54.0 (Aug 2026 investigation of an intermittent bug where the foreign main HEAD landed on `evogit-agent-T<task>-A<agent>` and the review diff went EMPTY):

- **`git worktree add -b <branch> <path-inside-main> <sha>` never moves the main HEAD** (non-mutating w.r.t. the main copy); neither do `Git.create_branch/3` (`git branch <name> <sha>`) or CoW's `--no-checkout` + `git checkout <sha> -- .` (path-limited). The full CoW lifecycle (create → clean+checkout branch in WT → agent commit → destroy rm_rf+prune+branch -D → `git branch genesis/agent_*` → `merge-base`/`merge-tree` review reads) leaves the foreign main on its original branch with a clean tree.
- **`Git.clean`/`Git.checkout` are only safe in a REGISTERED linked worktree — and `assign_and_prepare_worktree/3` now GUARDS this** (worktrees.ex, `ensure_linked_worktree/2`): before running `Git.clean(wt)`/`Git.checkout(wt, branch_name)` it asserts `wt` is a registered linked worktree of the agent's repo. A registered linked worktree ALWAYS has a `.git` FILE whose content is `"gitdir: <path>"`, where `<path>` (after `EvoGit.Platform.safe_expand/2` — a UNC-preserving `Path.expand` — relative to the worktree, per git's own rule) lies under `<repo_root>/.git/worktrees/`. The repo root for the check is the `repo_root` param threaded from `prepare_new_worktree/5` (resolved by `Dispatch.resolve_agent_repo_root/2` — NOT `spec.phylo_node.repo`, which for subagents is the PARENT'S worktree path, not the root). On failure it returns `{:error, {:worktree_prepare_failed, :not_a_linked_worktree}}` WITHOUT running any git — no clean, no checkout, no rev-parse (a plain `File.read`/`Path` check only), so the main copy can never be touched. **Why the `.git`-file check and NOT `git -C wt rev-parse --git-common-dir`**: from a PLAIN dir inside the repo tree (the dangerous broken-registration state) git walks UP and returns `<repo_root>/.git` — identical to a real worktree's common dir — so a rev-parse check would PASS for exactly the dangerous state. The repo ROOT itself has a `.git` DIRECTORY (not a file) and a plain dir has no `.git` file at all — both fail the check. The guard failure propagates through `prepare_new_worktree/5`'s existing `{:error, {:worktree_prepare_failed, _}}` else clause → the agent's Runner raises → scheduler crash-retry (the retry's fresh create cleans the path first).
- **Leftover-dir removal now ESCALATES** (`destroy_leftovers/3` in `prepare_new_worktree/5`, and `WorktreeManager.destroy_worktree/3`): a failed `rm_rf_retry` after retries is no longer warn-and-continue. `destroy_leftovers/3` returns `{:error, {:worktree_create_failed, msg}}` (propagated through `prepare_new_worktree/5`'s existing else clause — the retried agent crash-retries) and **skips the `Git.prune_worktrees` for that path**: a dir that survives rm_rf WITH its `.git` file + registration is a SAFE registered worktree, but a partially-removed dir that is then pruned becomes a PLAIN unregistered dir — the leak precondition. The dir+registration pair is kept consistent so a later create/cleanup can rm_rf it properly. `destroy_worktree/3` (runs in the WorktreeManager GenServer — must never crash) likewise logs at ERROR level and skips both prune and branch delete on rm_rf failure.
- **`delete_branch_tolerant/2` (worktrees.ex:188-245) RECOVERS git's "cannot delete branch 'X' used by worktree at '<path>'"** (and the older "checked out at" wording — matched robustly via `branch_in_worktree?/1`, verified 2.54.0): the registration may be STALE (worktree dir already removed without a matching prune), so it runs `WorktreeRetry.retry_on_transient(fn -> Git.prune_worktrees(repo_root) end)` to drop stale registrations, then retries the delete ONCE with the same tolerant logic. A branch genuinely checked out in a LIVE worktree survives the prune and the retry still fails — `{:error, output}` (correct: a live checked-out branch is never force-deleted). Existing "branch not found" / repo-gone tolerance unchanged.
- **On git 2.54.0 the scheduler's own crash-retry interleavings FAIL SAFELY**: a stale `:DOWN` destroy racing a retry's fresh create deletes the new worktree's branch, so the retry's `git checkout` errors ("pathspec did not match") and main HEAD stays put (the run crashes and retries instead). The dangerous plain-dir+live-branch state is not reachable through scheduler code alone on 2.54.0 — but the `:not_a_linked_worktree` guard + destroy-leftovers escalation make it structurally unreachable regardless of git version (older git had `git worktree add`/prune corner-case bugs; Windows partial rm_rf can leave a plain dir).
- **LLM cd-escape into the repo root is HARD-BLOCKED at the tool layer**: `do_execute/5` (shell_tool.ex:243-248) first calls `main_copy_mutation_error/3` (shell_tool.ex:258-265) — if ANY resolved cd target equals `Path.expand(repo_root)` AND the command matches the mutating-git regex `\bgit\s+(checkout|switch|reset|merge|pull)\b` (`@mutating_git_regex`, shell_tool.ex:34), it returns an error string ("Error: This command changes directory into the repository's MAIN working copy ... and runs a mutating git command ... blocked ...") and NOTHING executes. Relative cd escapes are caught too: `@cd_regex` (shell_tool.ex:30) matches absolute paths, dot-relative escapes (`..`, `../..`, ...) and plain relative targets, and `cd_targets/2` (shell_tool.ex:534-540) resolves each target via `EvoGit.Platform.safe_expand(target, repo_path)` (the worktree cwd) before the comparison — so the attack shape `cd <foreign_root> && git checkout evogit-agent-*` from inside a writable-foreign-repo worktree resolves to the repo root and is blocked. `detect_cd_warnings/3` (shell_tool.ex:400) remains warning-only for cds that stay inside the worktree or cross between worktrees (no root+mutating-git combo). The block is tool-layer defense — `run_bash`/`run_git`/`run_powershell`/`curl` are in `@write_tools` (tools.ex:47-63) → ALLOWED for writable foreign repos (the read-only gate `maybe_block_read_only_foreign_repo/5`, tools.ex:221-243, only blocks `writable != true`), and the sandbox does not prevent the mutation: under bwrap the foreign repo's common `.git` dir is in the writable binds (bwrap.ex:425-429), and a same-tree checkout (HEAD/index-only) succeeds even with the working tree read-only; under systemd-run the whole filesystem stays writable (only `ReadWritePaths` additions, no `ReadOnlyPaths=/`); `:none` backend unrestricted. Residual risk is defense-in-depth: the block is string-pattern based — an agent that reaches the main copy through a command shape other than `cd`-into-root + `git checkout/switch/reset/merge/pull` could still move the main HEAD, so the prompts still tell agents never to run checkout/switch/reset against the repo root (manager/executor system prompts).

## Constraints

- Data structs are plain data with no behaviour or callbacks.
- `Slots`, `Worktrees`, `Dispatch`, `Subagents`, and `Lifecycle` are pure-function modules operating on `State.t()`; they don't maintain their own state.
- `AgentState` is shared (scheduler + agent processes); `SchedMeta` is scheduler-exclusive.
- Both ETS tables are created by **`EvoGit.Application`** (the application process), NOT by the `AgentScheduler` GenServer (see `application.ex:13-15`). Deliberate: the tables have **no heir**, so ownership must outlive a scheduler crash. Because they are owned by the long-lived application process, they **SURVIVE an `AgentScheduler` restart** — stale `SchedMeta` entries from the crashed instance remain. (Restart semantics: `AgentGroupSupervisor` is `strategy: :one_for_all`, so a scheduler crash also kills `EvoGit.TaskSupervisor` and all running agent Tasks. The GenServer `%State{}` is reset fresh on restart, but the ETS tables persist.)
- GenServer state must always be `%State{}`; use struct update syntax, not `Map.put/3`.
- The scheduler process NEVER calls git, does blocking filesystem I/O, or calls ANY worktree function (not even init) — all git operations (auto-commit, sync) happen in the agent (Task) process, and ALL worktree filesystem operations (rm_rf, mkdir_p, prune_worktrees, delete_branch) are owned by the `WorktreeManager` GenServer. The only worktree call is Runner → `WorktreeManager.create_worktree_for_agent/6` (named 1-hour timeout; create I/O offloaded to a spawned Task; reclaim via `:DOWN` monitor).
- Slot availability is derived from holder MapSets, never stored as a counter — this eliminates leak/deadlock bugs by construction.
- `SchedMeta.task_ref` stores a `%Task{}` struct (for `Task.shutdown/2`), NOT a bare reference. The `ref_to_agent` map still keys on `task.ref` (the monitor reference).
- `case`/`with` guards on ETS lookups are used ONLY where a genuine race can cause the entry to be absent (recycle_agent, try_dispatch, cancel_agent). Not used defensively everywhere.
- Cross-module calls: `Dispatch.process_queue/1` calls `Subagents.dispatch_ready_parent/3` for ready parents. `Lifecycle.handle_agent_crash/3` calls `Dispatch.try_dispatch/2`, `Dispatch.process_queue/1`, `Subagents.store_sub_result/3`, and `Subagents.maybe_resume_parent/2`.
- **Task archive table**: `:evogit_archive_records` is a **`:set` keyed by `{task_id, agent_id}`** (at most one record per agent per task — `EvoGit.AgentScheduler.Store.put_archive_record/3` writes are idempotent, so crash-retry double-writes are safe). Records are written at agent exit, consumed (collected into `Result.archive_records`) **AND** cleared at successful root completion in `Lifecycle.handle_task_result/3`, and reset defensively at task start in the `run_agent` call. **Archive record shape** (plain map): core fields `agent_id`, `parent_id`, `depth`, `objective`, `result` (ALWAYS a binary string), `base_commit`, `final_commit`, `archive_ref_start`/`archive_ref_final`, `branch_name`, `usage` (PLAIN MAP — `input`/`output`/`total_tokens`, costs, `cached_tokens`, `cache_hit_rate`; NOT a `%Usage{}` struct), `compression_count`, `repo_path`/`repo_id`/`repo_root`, `started_at`/`completed_at` (`%DateTime{}`); plus `:llm_settings` (model, model_id, context_compression_threshold, generation params), `:agent_settings` (`max_turns`, `max_retries`, `max_agent_depth`), and `:foreign_repos` (`%{id, root, description}` maps). **Only writer is `CompleteTask.complete/4`** (writes `refs/genesis/archive/T{task_id}-A{agent_id}-start`/`-final` git refs + a usage git note); a CRASH/FAILURE/ABORT writes NO record (crashed agents are ABSENT from `archive_records`, usage LOST — retry resets to `Usage.zero()`). **JSON round-trip caveats**: decoded records are STRING-keyed maps with STRING timestamps (Jason encodes `%DateTime{}` as ISO strings; inner maps not re-atomized) — consumers must handle string keys (per-agent tiles reading atom keys render 0; the cost tile reads `:cost` but core writes `total_cost`).

### Per-message timestamp metadata convention

Every message in an agent's session memory (the `%ReqLLM.Message{}` list inside `%ReqLLM.Context{}.messages`, held in `AgentState.context` / `:evogit_agent_state` ETS) carries `metadata[:timestamp]` — **Unix seconds** (`System.system_time(:second)`), an atom-keyed integer consistent with the existing `:turn` metadata convention. Timestamps are stamped **at message-CREATION time in the agent code** — never in the Store.

**Single choke point — `ContextBuilder.tag_message_turn/2` (agent/context_builder.ex)**: every message produced by the agent loop passes through it, and it sets BOTH `metadata[:turn]` AND `metadata[:timestamp]` in one place. Idempotent via `Map.put_new` — an already-stamped message keeps its original `:turn` and `:timestamp`. `ContextBuilder.tag_message_timestamp/1` stamps just the timestamp (used at the nudge and compression-summary append sites). The agent subtree owns all stamping; see `apps/evo_git/lib/evo_git/agent/CONTEXT.md` for the full inventory of creation sites.

**`Store` is a dumb pass-through.** `batch_update_agent/2` (store.ex) writes the fields verbatim into ETS; only the broadcast kwlist is stripped (`:context` removed, `message_count` added when a context is updated). `update_agent_context/2` delegates to `batch_update_agent` — same path. Both return `:ok`. **No read-back exists anywhere** — data flows one way: agent → ETS/pubsub → frontend. The dashboard reads `msg.metadata[:timestamp]` (Unix seconds) directly from `RemoteAPI.get_agent_history/1` (raw structs, unchanged).

`DateTime` was deliberately avoided (struct — heavier, and Jason-encodes to ISO-8601 strings elsewhere in the codebase); an integer is timezone-agnostic and trivial for the dashboard to convert to local display time. **The dashboard interprets integer timestamps as Unix SECONDS** (`EvoDashWeb.Helpers.format_history_timestamp/1`) — do NOT switch granularity without updating evo_dash. Second-granularity means messages produced within the same second share a stamp — acceptable by design. Compression (`context_compression.ex:85-86`) rebuilds context as `[system, initial_user, summary]` — the fresh summary is stamped via `tag_message_timestamp/1` at creation (history collapse is by design, not a bug).
