# EvoGit.Store — Ecto/SQLite Persistence Layer

## Intent

The task and VCT-mount persistence layer of `:evo_git`, so the headless `genesis_server` daemon carries full task history.
`EvoGit.Store` (`../store.ex`) is a THIN GenServer facade over a pure-Operations Ecto layer; the on-disk bytes are owned exclusively by `EvoGit.Store.Codec` (the wire oracle).
The public client API — names, arities, defaults, 30 s `@call_timeout`, return shapes — is a frozen contract extended ADD-ONLY; `lib/evo_git/task_registry.ex` and the `evo_dash` RPC surface call it untouched.

## Architecture (facade → Operations → Repo → schemas → Types → Codec)

`EvoGit.Store` (facade) → `Store.Operations.*` (repo pid FIRST arg) → `Store.RepoScope.with_repo/2` → `EvoGit.Repo.*` + `Ecto.Query` on an unnamed dynamic instance (XqliteEcto3) → `Schemas.TaskRow`/`TaskAgentArchiveRow`/`VctMountRow` (typed, WRITE) or `TaskRowRaw` (raw, READ) → `Store.Types.*` (Ecto.Type, THIN delegation) → `Store.Codec` (the single encode/decode oracle).
- **Facade (`store.ex`)** owns only: the client API, one-line-per-handler `handle_call` dispatch, the read offload (`offload/5`), the WRITE offload (`offload_write/3` → `Writer.submit/3`), the disk-full choke point (`write_call/2`, executed in the writer), the `__repo_pid__/1` + `__writer__/1` test seams and `init/1`/`terminate/2`. No SQL lives here.
- **Writer (`writer.ex`)** — `EvoGit.Store.Writer`, LINKED to the store: writes stay strictly serialized in ARRIVAL order, replies arrive only AFTER the commit (read-after-write), and a failing statement kills the writer and — over the link — the store with the operation's own reason.
- **Operations** (`./operations/`) own every `EvoGit.Repo.*` + `Ecto.Query` call (see the Operations table); each public function takes the repo PID first and runs its body inside `RepoScope.with_repo/2`, so a call targets THAT store's instance regardless of the caller (offloaded read worker included).
- **Wire format**: the typed schemas dump/load through `Types.*`, which delegate verbatim to `Codec`.

## Dynamic-Repo Design

- **Per-store UNNAMED instances**: `init/1` boots via `Boot.start_dynamic(data_dir, pool_size: <opt>)` an UNNAMED (`name: nil`) `EvoGit.Repo`, so many same-named `EvoGit.Store` GenServers (test isolation, multi-store) each own their own DB. `state = %{repo: pid, name: name, data_dir: path, writer: pid, offloads: %{}}` (`:data_dir` is the SQLite FILE path, parent `mkdir_p`'d; `:offloads` maps each in-flight read worker's monitor ref to `%{pid, from, op, degraded, timer}`).
- **PID addressing via the process dictionary**: unnamed instances are addressed BY PID through `EvoGit.Repo.put_dynamic_repo/1` / `get_dynamic_repo/0`; a process with no binding addresses the canonical named instance. `RepoScope.with_repo(pid, fun)` binds for `fun`'s duration and ALWAYS restores the previous binding (raise/throw/exit safe, nesting composes).
- **Pool size — `Boot.default_pool_size/0` = 6**, overridable per store via `start_link(pool_size: n)` (non-positive/non-integer raises `ArgumentError`). One connection belongs to the writer, so 6 gives five concurrent readers.
- **Connection tuning lives in `EvoGit.Repo.start_opts/0`**, passed as START OPTS by `Boot.start_dynamic/2` and by `mix store.maintenance`: `timeout: 60_000`, `queue_target: 500`, `queue_interval: 5_000`, `cache_size: -8_000` (8 MiB page cache per connection), `temp_store: :memory`.
- **`EvoGit.Repo.config/0` does NOT report the effective tuning** — it re-runs `init/2` without the start opts and shows Ecto's defaults (`timeout: 15_000`, `pool_size: 10`); `start_opts/0` holds the effective values, while `defaults/0` keeps only keys Ecto does not override (`journal_mode: :wal`, `synchronous: :normal`, `busy_timeout: 30_000`, fallback `pool_size: 2`, `default_transaction_mode: :immediate`, `ownership_timeout: 30_000`).
- **Test seam**: `__repo_pid__/1` (`@doc false`) exposes the facade's dynamic repo instance — the sanctioned way for tests to reach the store's own connection (e.g. `XqliteEcto3.with_xqlite/2`).

## Boot & Migrations

`init/1` → `Boot.start_dynamic(data_dir, pool_size: <opt>)` runs the migrations in `../../priv/repo/migrations/` BEFORE any read/write (`Ecto.Migrator.run(repo, Boot.migration_source(), :up, all: true)` — a no-op on a current DB), so an existing user DB upgrades automatically on first start.
`start_dynamic/2` opens at `pool_size: 1`, migrates (plus one best-effort `PRAGMA optimize`), then — for `pool_size > 1` — releases that instance and reopens at the requested size (`reopen_pool/3`), so every pooled connection sees an already-migrated file (SQLite caches a connection's schema, so a pre-migration connection could answer `PRAGMA index_list/…` with an EMPTY list). A `pool_size: 1` store keeps the boot instance (`store_disk_full_test.exs` pins it — its `PRAGMA query_only` arm is CONNECTION-scoped).
A repo-OPEN failure stops with `{:stop, {:failed_to_open_sqlite, reason}}`; a MIGRATION raise (e.g. the baseline post-condition rejecting a non-canonical `tasks` shape) propagates out of `init/1` and crashes the Store child (supervisor restart, then app-boot failure).
A migration that could not take its lock is NEVER a successful boot: `with_migration_lock/1` is the ONE lock-taking point and normalizes `:global.trans/2`'s bare `:aborted` answer to `{:error, :migration_lock_unavailable}`; `reject_lock_unavailable/1` then raises ONE `RuntimeError` (text from `@migration_lock_unavailable`) out of `Boot.run_migrations/1` (whose success contract stays the `[integer()]` version list `mix migrate.store` pins), and `start_dynamic/2` STOPS the half-started boot repo and answers `{:error, :migration_lock_unavailable}` instead of handing back a pid for a schema-less database.
`EvoGit.Store.init/1` turns that case into the DISTINCT stop reason `{:store_migration_failed, :migration_lock_unavailable}`, so a migration fault can never be read as `{:failed_to_open_sqlite, reason}`.
The lock FUNCTION is a default-inert call-time seam — `Application.get_env(:evo_git, :store_boot_lock_fun, &:global.trans/2)` read at the `with_migration_lock/1` call site, the ONLY way to reach the `:aborted` arm because OTP 29's `:global.trans/2` retries until granted.
`terminate/2` reaps in-flight read workers, drains the writer and calls `Boot.stop(repo)` inside a justified try/rescue (terminate must never raise).

### Boot blocking profile and memory footprint

The repo open and the migration run are SYNCHRONOUS inside `init/1` (boot repo → migrator → `PRAGMA optimize` → reopen the pool → start the writer), so the supervisor's child start BLOCKS until it returns — and so does `EvoDashWeb.Endpoint`'s Bandit bind: **Store boot precedes the HTTP listener** (desktop budget: `desktop/src-tauri/CONTEXT.md` → "Backend Readiness Budgets & Launch Diagnostics").
Only versions absent from `schema_migrations` run, so a release shipping no new migration is a pure no-op, and `Ecto.Migrator` runs each migration AND its version stamp in ONE transaction (atomic under a SIGKILL).
A DB locked by another process can stall a boot connection up to `busy_timeout: 30_000`, in the CALLING process (no VM thread parked) — no sleeps exist on the store/application boot path.
Nothing is rehydrated into a long-lived process at boot (`init/1` keeps only its state map); the ONE boot read is `TaskRegistry.init/1`'s `select_running_lease_info` (`id`/`status`/`lease_expires_at` for `WHERE status IN ('running','awaiting_input','finalizing','cancelling')`, reduced to `{id, status}` pairs), empty with no tasks running.
`@cache_size -8_000` (8 MiB) is PER-CONNECTION SQLite NATIVE memory, so 6 × 8 MiB ≈ 47 MiB is a lazily-filled CAP visible only in OS RSS — never in `Process.info(pid, :memory)`; the only environment inputs are `:data_dir` and the two call-time seams (`:store_boot_optimize_fun`, `:store_boot_lock_fun`).

### Migration ledger (versions 1–9 and 11)

Every migration is `up/0` only, self-contained (a shipped migration must keep working after application modules are refactored), and runs every statement through `repo().query!/3`, never `Ecto.Migration.execute/1` (whose string commands queue until `flush/0`, so an in-body probe would see pre-migration state); frozen shipped source files are never rewritten.
Each post-condition asserts the migration's own physical shape through `PRAGMA table_info`/`PRAGMA index_info`/`EXPLAIN QUERY PLAN`, so an `IF NOT EXISTS` can never silently keep a same-named object of a different shape; each `.exs` moduledoc carries that migration's own rationale and exclusions.

### Migration versions & ordering

The migration versions are 1..9 plus 11, CONTIGUOUS, and shipped ledger identities and frozen source files are never rewritten.
Version 10 is RETIRED and must never be reused; boot has no physical-schema reconciliation for an already-stamped ledger.
`HistoricalSources.run/1` only rejects reserved preservation remnants and then runs pending versions, so a ledger containing versions 1–9 and 11 with a missing `session_mode`, `pause_kind` or the workspace `vct_mounts` shape stays inconsistent after a successful no-op run.
Repair that offline: preserve the ledger and existing payloads and fix only verified physical gaps, because deleting ledger rows to replay migrations re-enables the destructive legacy archive/project transformations (migrations 5 and 7 keep their normal fan-out and capped project import).
The reserved marker table `__genesis_historical_sources`, column `tasks.__genesis_preserved_archive_metadata` or table `__genesis_preserved_projects` fails boot before any migration runs, regardless of the ledger; those remnants need explicit inspection and recovery, which boot never guesses.
Each migration keeps its own transaction/version-stamp atomicity, but the whole upgrade is not one transaction, and no concurrent external migrator or old binary may touch the database during an upgrade.

### Migration source & concurrent-boot serialization

`Boot.migration_source/0` returns a PRE-LOADED, ASCENDING `[{version, module}]` source — never the migrations DIRECTORY: it enumerates `Ecto.Migrator.migrations_path(@repo)` + `Path.wildcard("*.exs")` (via `Application.app_dir/2`, so every per-store instance reads the same directory), parses each `"NNN_name.exs"` basename like `Ecto.Migrator.extract_migration_info/1`, compiles it with `Code.compile_file/1` and picks the module exporting `__migration__/0` (none → `Ecto.MigrationError`).
The source is memoized in `:persistent_term`, so the `.exs` files compile at most ONCE per BEAM (a directory source would redefine the module and log `redefining module` on every run).
`Boot.run_migrations/1` wraps the run and that compile in `:global.trans({{:evo_git_store_migrations, self()}, fun})` — a cluster-safe PRODUCTION lock (no test-side wrapper), since compiling the same module is not concurrency-safe and boots are not exclusive; the per-process pdict save/restore stays OUTSIDE the lock.

### `mix migrate.store` / `mix store.maintenance`

`Mix.Tasks.Migrate.Store` boots a private unnamed dynamic repo on the target DB (default `<data_dir>/tasks.sqlite`), runs `Boot.run_migrations/1` (the exact boot call), reports applied versions and stops the instance — normally a NO-OP, for manual verification of interrupted upgrades.
`mix store.maintenance [--data-dir PATH] [--vacuum] [--no-optimize]` boots a private `pool_size: 1` unnamed dynamic repo (never starting `:evo_git`), optionally switches `PRAGMA auto_vacuum = INCREMENTAL` (the header change takes effect only after the `VACUUM` the same flag runs), `VACUUM`s, and prints file size plus `page_size`/`page_count`/`freelist_count`/`auto_vacuum` before and after (`--optimize` ON by default); `VACUUM` never runs at boot.

## API Surface

### `EvoGit.Store` (`../store.ex`) — facade

Public API (all `GenServer.call`, 30 s timeout; `store \\ __MODULE__`): `put_task`, `get_task` (full `%TaskInfo{}` incl. `result`/`logs`), `get_task_lite`, `put_task_archive`, `list_task_archives/3`, `get_agent_archive/3`, `delete_task_archives/2`, `delete_task`, `delete_tasks`, `clear_tasks`, `safe_select_paginated_tasks`, `select_tasks_page`, `update_lease_expires_at` (never bumps `updated_at`), `renew_leases/3` (batched `[String.t()]`-id lease renewal, `:ok | {:error, :disk_full}`, never bumps `updated_at`), `update_task_columns` (ALWAYS bumps `updated_at`), `get_task_status`, `select_task_statuses/2`, `select_tasks_restart_info/2`, `select_task_update_info`, `select_task_paths`, `select_finished_task_ids`, `select_task_ids`, `select_running_lease_info`, `select_cleanup_info/1,3`, `select_tasks_summary/3,4` and `select_tasks_summary_by_path/4,5` (both take a trailing `opts \\ []` carrying the add-only `:limit`, passed through the GenServer message), `select_tasks_changed_since/1`, the VCT mount table (`list_vct_mounts` — STRING-keyed `%{"point", "path", "name", "kind", "last_opened_at", "members", "description"}` entries newest-first, `"path"` nil and `"members"` `[]` for a workspace mount, `[]` on a failed read; `save_vct_mounts` — transactional diff accepting atom- or string-keyed maps, `:ok | {:error, :disk_full}`), safety (`safe_select_all_tasks`, `size`), and the `__repo_pid__/1` / `__writer__/1` seams; per-read defaults and limits live in the Operations table below.
`start_link(data_dir:, name: \\ __MODULE__, pool_size: nil)`.
- **Batched lease renewal (the heartbeat design rule)**: ONE heartbeat tick costs ONE status read (`select_task_statuses/2` → `%{id => atom() | {:unknown, raw}}` of PRESENT rows only, `%{}` for an empty id list) plus ONE `renew_leases/3` `UPDATE … WHERE id IN (…)` (`:ok` no-op on an empty id list) — never a statement pair per live task, and neither bumps `updated_at`.
- **`select_tasks_restart_info/2`** → `[%{id, status, type, opts, pause_kind, project_path}]` for PRESENT ids, ONE query over the raw wire twin decoded row-by-row inside `Decoding.decode_skipping_bad/4`, so ONE corrupt `opts` row is skipped+logged instead of failing the batch; `[]` on an empty id list and as the degraded value.
- `select_task_update_info/2` carries EXACTLY `:status, :opts, :finished_at, :lease_expires_at, :project_path` (5 keys; `opts` stays because `TaskRegistry` reads `opts[:path]`, while `project_path` lets a status-transition caller skip the `opts` decode).
The facade declares `@type store :: GenServer.server()`, `@type write_result :: :ok | {:error, :disk_full | :store_unavailable}` and `@type read_degradation`, and carries an `@spec` on every public function.
`put_task/2`'s spec includes `{:error, :invalid_task_struct}`, the documented answer for a non-`%TaskInfo{}` argument (never a raise).
`select_all_tasks/1`, `count_tasks/1` and `select_task_logs/2` do NOT exist at any layer; `safe_select_all_tasks/1` (skip-and-log, the only full-table task read) is the survivor.

The LIGHTWEIGHT read API is ADD-ONLY (per-function shapes in `./operations/CONTEXT.md`):
- `select_tasks_page/2` → `%{rows: [18-key summary map], total: non_neg_integer}`; `get_task_lite/2` → a FULL-detail `%TaskInfo{} | nil` (same `Codec.decode_raw_row/1`, 20 of the 21 physical columns, omitting only store-internal `updated_at`), so lite is NOT a bounded or blob-light inspection API.
- The page omits `result/logs/usage` but retains whole unredacted `opts/error`, so a row-count bound is not a payload-byte bound.
- `TaskRegistry.list_tasks_page/0,1`, `get_task_lite/1` and `get_task/1` return these real API values, including through `elixir_eval`; there is no evaluator-facade substitution or secret-safe payload contract.

The PER-AGENT ARCHIVE API (`task_agent_archives`, see "Per-Agent Archive"):
- `put_task_archive/2` → `:ok` | `{:error, :disk_full}` | `{:error, :missing_task_id | :missing_agent_id | :invalid_entry}` before any write (WRITE offload).
- `list_task_archives/3` → `%{entries: [STRING-KEYED map], total: non_neg_integer | nil}` in `depth, agent_id` order, limit default 100 clamped 1..1000 and offset ≥ 0 (past the end = EMPTY page); three projection opt-ins, each key ABSENT (never `nil`) when off: `:include_results` (default `false`), `:include_settings` (default `false` — the three export-only JSON columns the CSV/JSON export requests) and `:include_total` (default `true`; `false` skips the `count(*)` and answers `total: nil`); `"usage"` is NEVER withheld and a lean entry is a strict SUBSET of `get/3`'s full row (READ offload).
- `get_agent_archive/3` → the FULL entry map (result included) or `nil` (READ offload); `delete_task_archives/2` → `:ok`, also for a task with no rows (WRITE offload).
The shared filter builder `Operations.Filters` (`where_filters/2` + the clamps) backs BOTH `safe_select_paginated_tasks/2` and `Operations.Pages`, so the two paged reads can never match different rows; the clamps are ONE parameterized `clamp_limit/2` (`default:`, `max:`, `non_positive:`) behind `clamp_limit/1`, `clamp_page_limit/1` and `clamp_offset/1`, which `Operations.Archives.list/3` also uses.

**Search contract**: the ONE runtime `fragment/1` LIKEs `id`, `opts`, `project_path`, `branch_name` only — `result` is deliberately NOT searched (a full-blob scan), so a phrase only in a task's final response text never matches and an `opts` hit needs its exact JSON text spelling.

## Storage Model — plain JSON text columns
`result`, `logs`, `opts`, `usage` and `error` are plain UTF-8 JSON TEXT — exactly what the encoder produced, no compression layer and no prefix tag — so a stored value is uniformly readable by plain SQL (`json_valid`, `json_extract`, `LIKE`); `opts` being a plain object lets search `LIKE` its raw text and SQL paths use `json_extract(opts, '$.path')`.
Decode strictness is unchanged: `decode_result/1` is strictly canonical while `decode_logs/1` → `[]` and `decode_error/1` → `nil` keep callers safe.

## Task repo/commit identity — where each field lives

Only these identity fields are real `tasks` columns: `project_path` (the repo ROOT, denormalized from `opts[:path]`), `base_sha` (the REVIEW base, written only by `TaskRegistry.set_review_metadata/3` — NOT the runtime starting commit), `commit_sha` (the primary repo's final commit), `branch_name` (denormalized from the primary's `{:ok, %{branch_name: _}}` result) and `model_id`.
The runtime starting commit exists ONLY in the JSON `opts` key `:starting_commit`; `:path`, `:mode`, `:node_path`, `:resume_from`, `:merge_from`, `:merge_target` and `:foreign_repos` are opts-only too, and `:merge_from`/`:merge_target` decode STRING-keyed while `:path`/`:starting_commit`/`:resume_from`/`:foreign_repos` decode atom-keyed.
There is NO column for a worktree path, a task number or a parent task id: `task_number` is naming-only (a `.genesis/workers/` scan) and an archive's `parent_id` is the spawn-tree PARENT AGENT id, never a task id.
Per-repo identity for a finished task lives only in the `result` JSON: `result["repos"] = %{repo_id => %{"commit_sha", "branch_name"}}` inside the canonical `{"__result_tag__":"ok","data":{…}}` envelope (`"repos"` is NOT in `@result_data_fields`, so it stays a STRING key holding string-keyed nested maps).

## Per-Agent Archive (`task_agent_archives`)

The archived conversation is a RELATIONAL table, one row per `(task_id, agent_id)` — not a JSON blob on the task row; migration 5 creates the table, composite key and index.

- There is NO `messages`/`transcript`/`conversation` column anywhere in the table or its schema: the ONLY conversation artifact archived is the final `result` TEXT (the live transcript is never persisted), so a forensic tool-call question must be answered from the live agent or a tool's own side artifacts.
- **23 columns**, in order: `task_id` (TEXT PK), `agent_id` (INTEGER PK), `parent_id`, `depth` (INTEGER NOT NULL DEFAULT 0), `agent_type`, `context_node_path`, `objective`, `result`, `base_commit`, `final_commit`, `branch_name`, `archive_ref_start`, `archive_ref_final`, `repo_id` (TEXT — a repo ID STRING such as `"primary"`, never an index), `repo_root`, `repo_path`, `usage`, `llm_settings`, `agent_settings`, `foreign_repos`, `compression_count` (INTEGER NOT NULL DEFAULT 0), `started_at`, `completed_at` (ISO-8601 TEXT as-is).
- **Schema module** (`Schemas.TaskAgentArchiveRow`): `@primary_key false`, `primary_key: true` on `task_id`/`agent_id`, plain `:string`/`:integer` fields elsewhere, NO `timestamps()`.
- **Wire format** (`Types.ArchiveColumns.*`): `ArchiveUsageJson`, `ArchiveLlmSettingsJson`, `ArchiveAgentSettingsJson`, `ArchiveForeignReposJson` are PLAIN Jason — `Jason.encode/1` on dump (`nil` ⇔ SQL NULL, never the string `"null"`) and `Jason.decode/1` on load (corrupt/non-JSON text loads as `nil`, so one unreadable column never fails a read); deliberately NOT the Codec — no `%EvoGit.Agent.Usage{}` struct, no magic prefixes. `ArchiveColumns.dump_json/1` recursively normalizes keyword lists, lists of 2-tuples and tuples into string-keyed JSON objects before encoding (Jason has no Tuple encoder), and genuinely unencodable terms (pids, refs, functions) still return `:error`.
- **Entry maps**: STRING-KEYED with the same 23 keys (minus `"result"` unless the read includes results), produced by ONE row → entry translation in `Operations.Archives`; writers accept atom- OR string-keyed maps (an atom key wins when both exist).
- **Write / lifecycle**: `put/2` is `ON CONFLICT (task_id, agent_id) DO UPDATE` over the FULL 23-column row — replace semantics (a re-put NULLs what the entry omits) and idempotent. The row is written STREAMING at AGENT COMPLETION by `EvoGit.Agent.Completion`'s private `write_archive_refs/7` → `EvoGit.TaskRegistry.put_task_archive/1` → `EvoGit.Store.put_task_archive/2` (no in-memory buffer, nothing in a task's `result`), and a task start clears leftover rows for that task id (the scheduler's guarded `delete_task_archives/1`), so one run owns exactly one canonical archive set.
- **Deletes**: `Operations.Archives.delete_by_task/2` backs `delete_task_archives/2`; `delete_by_tasks/2` (500-id chunks) and `delete_all/1` are the bulk primitives the task deletes call — `Operations.Tasks.delete_task/2`, `delete_tasks/2` and `clear_tasks/1` delete their archive rows in the SAME `:immediate` transaction as the task `delete_all`, so the cascade can never be split by a crash or disk-full.
- **Fault isolation + tests**: every read/write uses the facade offload/`write_call` path (degraded `%{entries: [], total: 0}` / `nil`; writes `:ok` / `{:error, :disk_full}` / crash); `../test/evo_git/store/operations/archives_test.exs` pins each column's round trip (`repo_id` an integer-shaped input stored as decimal TEXT), nil-JSON/timestamp preservation, idempotent replaces, both key spellings, ordering, limit/offset + total and the 100/1/1000 clamps.

## Disk-Full Handling

**Contract:** disk-full-class write errors — `SQLITE_FULL` (13), `SQLITE_IOERR` (10), `SQLITE_READONLY` (8) — become `{:error, :disk_full}` at the write boundary instead of crashing the GenServer (a full disk is transient, unlike a corrupt DB): reads keep working and writes can be retried. Every other write error re-raises and crashes the GenServer.

- **Where**: `write_call/2` wraps `put_task`, `delete_task`, `delete_tasks`, `clear_tasks`, `update_lease_expires_at`, `update_task_columns`, `put_task_archive`, `delete_task_archives` and `save_vct_mounts`; its closure runs in the writer, so the adapter raise and the conversion both happen where the write runs. `put_task`/`put_task_archive` also return `{:error, :missing_task_id | :missing_task_status | :missing_agent_id}`-style validation tuples before any write.
- **Classification** (`Errors.disk_full_exception?/1`): the `XqliteEcto3` adapter RAISES `%XqliteEcto3.Error{message, statement, type, details}`; matched are `type: :sqlite_failure` with `details.code` in 8/10/13, `type: :read_only_database`, and a message-text fallback (downcased, containing "database or disk is full"). Trigger `RAISE`s are NOT matched (`SQLITE_CONSTRAINT_TRIGGER` 19 → constraint shape → crash).
- **Caller degradation** (TaskRegistry + Cleanup): a failing `start_task` put logs and continues in-memory; `force_kill_task`/`cancel_task` (pending)/`clear_finished_tasks` return `{:error, :disk_full}`; casts (review-status/metadata, heartbeat) fire-and-forget; terminal-status writes log while in-memory cleanup still runs. Full table: `task_registry/CONTEXT.md`.

## Read Fault Isolation & Write Offload

**Every READ goes through `offload(from, state, op_name, degraded_value, fun)`** — one failure-isolated `spawn_monitor` worker per read (UNLINKED, tracked in `state.offloads`) that runs the query AND the decode and replies via `GenServer.reply/2`, so large decoded terms live and die on the worker's heap: a raise/exit/kill arrives as `:DOWN`, a spawn failure converts identically, and a worker wedged past the **25 s internal deadline** (`@offload_timeout`, below the caller's 30 s `@call_timeout`) is killed and answered with the degraded value — each logged at `:error` with the operation name + reason.
`run_offload/2` is the justified centralized-boundary `try/catch`: a query/decode failure becomes the `:shutdown`-class exit `{:shutdown, {:offload_failed, kind, reason, stacktrace}}`, so NO OTP crash report appears beside the facade's own line (`format_offload_reason/1` → `Exception.format/3`).
Reads NEVER raise/exit/return `{:error, _}` — they return the empty value of their own shape (`nil` single-row incl. `get_agent_archive/3`, `[]` list, `{[], 0}` `safe_select_paginated_tasks`, `%{rows: [], total: 0}` `select_tasks_page`, `%{entries: [], total: 0}` `list_task_archives/3`, `0` counts/`size`), passed EXPLICITLY per call site so handlers cannot drift; the full table is `store.ex`'s moduledoc ("Read degradation policy") and `terminate/2` reaps any running worker.

**Writer offload (writes)** — each write handler forwards its operation closure plus the ORIGINAL caller's `from` to `EvoGit.Store.Writer` and replies `{:noreply, state}` immediately, so a slow write cannot stall the facade mailbox while reads, counts and the 60 s lease heartbeat are served; the writer replies only after the commit, in strict arrival order.

**Caller-side containment (`EvoGit.TaskRegistry.StoreGuard`)** — the registry wraps every SYNCHRONOUS store call in `StoreGuard.read(op, degraded, fun)` / `StoreGuard.write(op, fun)`, catching `:exit`/raise/throw, logging at `:error` and degrading: reads to their documented empty value, writes to `{:error, :store_unavailable}` (handled exactly like `{:error, :disk_full}`), so a Store crash — or an absent store at `TaskRegistry.init/1` — never kills the registry.

**Not offloaded**: the two test seams `__repo_pid__/1` / `__writer__/1`; everything else that reads a DB column goes through `offload/5`.

## Read-path profile & index inventory
**Query plans**: `select_task_ids` → `SEARCH … USING COVERING INDEX idx_tasks_status_updated_at_id`; the page statement → `USE TEMP B-TREE FOR ORDER BY` (`count(*) OVER ()` must see every matching row); `select_tasks_summary*` with the add-only `:limit` → `idx_tasks_updated_at`; the archive roster / per-task `count(*)` / `DELETE … WHERE task_id = ?` → `task_agent_archives_task_depth_idx`.
**What dominates reads**: the per-row `opts` JSON decode of a summary row, the legacy full-row page's `Codec.decode_task/1` of every blob column, and `select_tasks_summary` with `[]` (all statuses — a full table scan).
**Index inventory (6 `idx_tasks_*` + 1 archive index)**: `idx_tasks_updated_at`, `idx_tasks_started_at`, `idx_tasks_status_started_at` `(status, started_at)`, `idx_tasks_project_path_started_at` `(project_path, started_at)`, `idx_tasks_status_updated_at_id` `(status, updated_at, id)` and `idx_tasks_finished_at_id` `(finished_at, id)`, plus `task_agent_archives_task_depth_idx` on `(task_id, depth, agent_id)`.
Four redundant index shapes are never created and are DROPPED by migration 6 on an adopted legacy DB (see the ledger row); the prune is a WAL/page-churn win, not a space win.
**Maintenance**: `PRAGMA optimize` once per boot after the migrations (boot connection, best-effort, seam `:store_boot_optimize_fun`) and hourly via `EvoGit.Store.Maintenance` (best-effort, never raises when the store is restarting/absent), so `sqlite_stat1` tracks schema and data; `VACUUM` is never automatic.

## Summary Projection Contract (18 keys)

`select_tasks_summary` / `select_tasks_summary_by_path` / `select_tasks_changed_since` / `select_tasks_page` return plain maps with EXACTLY `id, status, review_status, started_at, finished_at, type, project_path, opts, branch_name, model_id, agent_count, base_sha, commit_sha, lease_expires_at, updated_at, error, session_mode, pause_kind` (the 18th key is `:clean | :dirty | nil` via `Codec.decode_pause_kind/1`).
`session_mode` is decoded through `Codec.decode_session_mode/1`, so it is ALWAYS `"oneshot"` or `"interactive"` (a NULL cell reads as `"oneshot"`, so a UI filter needs no null branch); `result` is never selected/decoded (the heaviest per-row blob), `error` is the lenient 16th key decoded unconditionally via `Codec.decode_error/1`, `updated_at` is the RAW fixed-precision ISO string, and undecodable rows are skipped + `Logger.warning`'d.
`select_tasks_summary/3,4` and `select_tasks_summary_by_path/4,5` take an ADD-ONLY `:limit`: a positive integer applies `ORDER BY updated_at DESC` and `LIMIT min(n, 1_000)` (served by `idx_tasks_updated_at`), while absent/nil/non-integer/non-positive keeps the unchanged unordered, unbounded query; `select_tasks_changed_since/1` stays unordered and unbounded, and `select_tasks_page` adds `ORDER BY started_at DESC` plus the clamped LIMIT/OFFSET.
**Count/page agreement (`Summaries.where_renderable/1`)**: `where_renderable/1` (`opts IS NULL OR (json_valid(opts) AND json_type(opts) = 'object')`) is applied ONCE to the single `count(*) OVER ()` page statement, so `total` counts exactly the rows the page can yield — the exact SQL twin of the Elixir skip rule (`decode_skipping_bad/1` skips a row only when `Codec.decode_opts/1` raises, and that raises for every non-object JSON value while accepting SQL NULL).

## Constraints

- **Codec is the wire oracle**: `Types.*` and the Operations must DELEGATE, never re-implement, encode/decode logic — the `types_test.exs` oracle-equivalence tests pin byte-identity so drift fails loudly.
- **No `?N` SQL in runtime store code**: all runtime access is `EvoGit.Repo.*` + `Ecto.Query`; raw SQL is restricted to migrations and the boot-only `HistoricalSources` interrupted-preservation guard (read-only schema probes). The ONE runtime `fragment/1` is `Filters`' 4-column OR-LIKE search (`id`/`opts`/`project_path`/`branch_name` LIKE ? ESCAPE ?), with the escape char pinned as a PARAMETER (a SQL literal `'\'` is doubled by the adapter and rejected by SQLite).
- **Crash philosophy**: no blanket try/rescue on the write path — a failed write raises out of the `EvoGit.Repo.*` call and crashes the process running it (the writer), then the store. Deliberate boundaries: `write_call/2`, the failure-isolated read worker, the writer LINKED to the store, the per-row skip-and-log decode boundaries and `TaskRegistry.StoreGuard`; the only justified try/rescue / try-catch are `terminate/2`, `write_call/2`, `start_offload_worker/2` and `run_offload/2`.
- **Writes go through the TYPED schemas** (or `Codec.encode_*` directly); the raw twins are read-projection only, and `update_task_columns/3` addresses EXACTLY `TaskRow.__schema__(:fields)` (`validate_update_column!/1` → `ArgumentError` on an unknown name), so a new column becomes writable by adding the field to `TaskRow`/`TaskRowRaw`.
- The 21-column `tasks` table has NO generic `metadata` column: extra per-task state that must survive a restart rides `opts` (free-form JSON object — an unregistered key decodes STRING-keyed, an atom value round-trips as its string) or `error` (`encode_error/1` stringifies ANY key, `decode_error/1` keeps unknown keys as strings), or needs a new column plus a migration; `result`/`usage`/`logs` are not free-form.
- **Atom safety**: closed whitelists (`@known_atoms`, `@known_opt_keys`) — never `String.to_atom` on DB-sourced strings; unknown values stay strings or decode to nil, and the whitelists must track the valid status/review_status/type atoms — `:awaiting_input` is a NON-TERMINAL status (a waiting interactive session), so it belongs to the lease set and is deliberately absent from every "finished" set. Statuses additionally have a TOTAL decoder, `Codec.decode_status/1` (`nil` for absent | known atom | `{:unknown, raw}` + `Logger.warning`), and `store_invariants_test.exs` pins the whitelists against the persisted set.
- **Quarantine-free design**: no recovery tables, no per-start repair — undecodable rows are skipped + logged; the only startup integrity check is lease reconciliation (`select_running_lease_info` in `TaskRegistry.init/1`).
- **`store.ex` stays cohesive** — do not split the facade without a plan; new handlers dispatch to an Operations module in one line.

## Fixed-precision timestamps & canonical encodings (Codec wire rules)

- `encode_datetime/1` emits the constant 24-char fixed-ms ISO form (`%Y-%m-%dT%H:%M:%S.SSSZ` via `DateTime.truncate(:millisecond)`) — lexicographically sortable in SQLite, which makes SQL-side `ORDER BY started_at DESC` and `updated_at > ?` string comparisons correct; legacy variable-precision rows are rewritten by migration 2 at boot.
- **Result tuples** round-trip via the `__result_tag__` JSON discriminator (`ok`/`error`/`exit`/`string`); plain strings always become the `"string"` form, so every `result` is valid JSON. `decode_result/1` is STRICTLY canonical — nil plus the 4 tagged forms only; raw strings, untagged JSON, invalid JSON and JSON null raise `ArgumentError`.
- **Opts** encode as a JSON OBJECT with string keys; `decode_opts/1` atomizes ONLY `@atomized_opt_keys` (`path mode prompt objective foreign_repos node_path starting_commit archive task_id repo_path concurrency tool_concurrency resume_from attachments quality_level model_spec persistent_state`), every other key stays a string, non-object JSON raises, and a non-Jason-encodable opt value falls back to the 4 essential keys only.
- **Canonical task selection** restores the outer `:model_spec` atom for keyword consumers while the nested identity map's `provider_profile_id`, `model` and optional `reasoning_effort` keys stay strings; registering `:model_spec` changes DECODING only — admission owns projecting identity without resolved generation parameters, provider profiles or credentials.
- **Persisted opt keys are TWO sets**: `@atomized_opt_keys` decode ATOM-keyed for `evo_git`'s `Keyword.get(opts, :key)` callers, while `@string_opt_keys` (`model_id model_id_locked agent build_system merge_from merge_target session_mode`) decode STRING-keyed ON PURPOSE because the dashboard reads them by string key and no `evo_git` code reads them from a decoded row; `:persistent_state` is atomized (consumers use `Keyword.get/2`), a boolean whose absence means the core default `true`. `Codec.known_opt_keys/0` returns the UNION (the registry the invariant test pins) and `known_atomized_opt_keys/0` the atomized subset — promoting a key between sets changes the cross-app contract and requires updating the dashboard lookups in the SAME change.
- **`:foreign_repos` values** round-trip as STRING-keyed maps — normalize via `EvoGit.Core.ForeignRepo.normalize/1` before dot-access; the result `repos` map is deliberately NOT atomized by `decode_result` (read via `Map.get(decoded, "repos")`).
- **`error` payloads**: `decode_error/1` is lenient by design (nil/invalid/non-object → nil), whitelisted keys atomized and closed-set values restored to atoms; the single producer is `TaskRegistry.Diagnostics.failure_error/3,4`.
- **`review_status`** is ONE flat task-level column (`:open | :merged | :rejected | :continued | :ignored | :no_changes` via the shared whitelist) and no per-repo review state exists anywhere — writes go through `update_task_columns(store, id, review_status: atom)`.
- **`updated_at`** is store-internal bookkeeping — NOT in `Codec.task_columns/0`/`%TaskInfo{}`; written by `put_task` and every `update_task_columns`, never by the lease heartbeat or a migration's maintenance rewrite.

## Known Issues

- **`task_agent_archives.repo_path` is a TRANSIENT per-agent WORKTREE path, not a repo root**: the producer passes `Process.get(:repo_path)`, which the Runner sets to the agent's `worker_T<n>_A<m>` worktree dir (destroyed when the agent exits), while `repo_root` is the real root (worktree suffix stripped by `Dispatch.resolve_agent_repo_root/2`); an archive row's `repo_path` must never be used to read files.
- **`tasks.id` is a NULLABLE TEXT primary key**: `PRAGMA table_info` reports `notnull = 0` (SQLite only implies NOT NULL for INTEGER primary keys), so the DDL allows a NULL id that every read would then miss. Only hand-edited/adopted rows can produce one — `Codec.validate_task/1` and `Operations.Archives.validate_entry/1` reject a missing id before any write. `vct_mounts.point` is NOT NULL.
- **`put_task/2` rewrites the whole row by design** (ONE `on_conflict: :replace_all` upsert over the complete 20-key row, so a single status change re-writes every column and all six index entries; `update_task_columns/3` exists to avoid that), and the same `%EvoGit.Agent.Usage{}` is stored TWICE per task (a result's `data.usage` plus the `usage` column — two decodes in `get_task/2`, two encodes in `put_task/2`; the summary/page projections select neither).
- **The one-time data migrations cost O(rows)**: migration 5 decodes each archived task's array on a cold page cache and migration 2 rewrites every legacy opts/status form — the slowest boots in the product, inside the desktop shell's 90 s backend-readiness budget; freed pages return only via `mix store.maintenance --vacuum`.
- **Several facade reads have no `apps/` caller**: `safe_select_paginated_tasks/2` (reachable only through the frozen `list_tasks_paginated/1`/`list_tasks_by_path/1` RPC wrappers), `safe_select_all_tasks/1`, `clear_tasks/1` and `size/1`; the dashboard reads `select_tasks_page/2` + `get_task_lite/2`.
- **Test-only shims**: `Store.Errors.disk_full_error?/1` (the legacy NIF-tuple classifier) and `put_task/2`'s `{:error, :invalid_task_struct}` clause have no production caller; both are test-pinned.
- Runtime project operations use only `vct_mounts`, which `EvoGit.VCT` owns end to end; migration 7 imports the newest 100 legacy projects and drops the legacy `projects` table.
- **A status value missing from `Codec.@known_atoms` is TOTALLED**: `Codec.decode_status/1` answers `{:unknown, raw}` + a `Logger.warning` (`nil` for absent), so `get_task_status/2` distinguishes "no such row" from "unknown status", while `get_task/2` maps it to `:pending` and the summary projections report `status: nil`; the lease classifiers stay CONSERVATIVE (`lease_renewable?/1` → `true`, `leaked?/3` → `false`) so the heartbeat keeps renewing — pinned by `store_invariants_test.exs`.
- **A multi-megabyte `result` row is decoded IN FULL by `get_task/2`** (`Codec.validate_task/1` checks only `id`/`status`); `select_tasks_page/2` avoids result/logs/usage but still decodes whole opts (incl. base64 attachments) and error without byte limits, and `get_task_lite/2` reads every heavy payload.
- **No single-column index on `type`/`review_status`, and `:search` is unindexable**: `review_status: "pending"` is the composite `status = 'completed' AND review_status IS NULL AND branch_name IS NOT NULL` served by `(status, started_at)`, an exact `review_status` filter rides `idx_tasks_started_at`, and the OR-LIKE forces a full `SCAN tasks` (no paginated query filters `type` — the dashboard drops `:reflect` rows CLIENT-side); an `opts` hit needs its exact JSON text spelling.
- **Store boot failure is fatal, not degraded**: `init/1`'s `File.mkdir_p!/1` raises on an unwritable `[data] dir` and a failed `Xqlite.open/2` stops with `{:stop, {:failed_to_open_sqlite, reason}}`, so a bad data dir crash-loops the application instead of falling back; a Windows UNC `[data] dir` is ACCEPTED by `Platform.data_dir/0` (`absolute_path?/1`) yet unusable, because `journal_mode: :wal` needs `-shm`/`-wal` files a network filesystem does not provide.
