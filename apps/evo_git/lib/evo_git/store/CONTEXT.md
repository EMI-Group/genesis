# EvoGit.Store — Ecto/SQLite Persistence Layer

## Intent

The task/project persistence layer of `:evo_git` (so the headless `genesis_remote` daemon has full task history). `EvoGit.Store` (`../store.ex`) is a THIN GenServer facade over a pure-Operations Ecto layer; the on-disk bytes are owned exclusively by `EvoGit.Store.Codec` (the wire oracle). The public client API — names, arities, defaults, 30s `@call_timeout`, return shapes — is a frozen contract extended ADD-ONLY; `lib/evo_git/task_registry.ex` and the `evo_dash` RPC surface call it untouched.

## Architecture (facade → Operations → Repo → schemas → Types → Codec)

```
EvoGit.Store (GenServer facade, store.ex)
  └─ EvoGit.Store.Operations.* (pure modules; repo pid FIRST arg)
       └─ EvoGit.Store.RepoScope.with_repo(pid, fun)   — scoped dynamic-repo binding
            └─ EvoGit.Repo.* + Ecto.Query              — unnamed dynamic instance (XqliteEcto3)
                 └─ Schemas.TaskRow/ProjectRow (typed, WRITE) / TaskRowRaw/ProjectRowRaw (raw, READ)
                      └─ EvoGit.Store.Types.*           — Ecto.Type, THIN delegation
                           └─ EvoGit.Store.Codec        — the single encode/decode oracle
```

- **Facade (`store.ex`)** owns ONLY: the client API, the one-line-per-handler `handle_call` dispatch, the failure-isolated read offload (`offload/5`), the WRITE offload (every write handler forwards its operation to the store's dedicated `EvoGit.Store.Writer` via `offload_write/3`/`offload_raw_write/3` and replies `{:noreply, state}` immediately — the writer runs the operation and `GenServer.reply/2`s the ORIGINAL caller after it commits), the disk-full write choke point (`write_call/2`), the `__repo_pid__/1` + `__writer__/1` test seams, and `init/1`/`terminate/2` (boot/stop the dynamic repo, start/drain the writer, reap read workers). No SQL lives here.
- **Writer (`writer.ex`)** is the per-store dedicated writer process (`EvoGit.Store.Writer`, LINKED to the store) that makes the write offload safe: writes stay strictly serialized in ARRIVAL order (facade FIFO forward → single writer), the reply still arrives only AFTER the commit (read-after-write), every Operation binds the dynamic repo itself in the writer's process (`RepoScope.with_repo/2`), and a failing statement kills the writer and — over the link — the store with the operation's own reason (the disk-full conversion stays `write_call/2`, whose closure runs in the writer). Writes are serialized here, so the connection pool is purely a READ-parallelism knob.
- **Operations** (`./operations/`) own every `EvoGit.Repo.*` + `Ecto.Query` call: `Tasks` (write/core/pagination/narrow reads), `Lightweight` (id/lease/cleanup projections), `Summaries` (16-key summary projections), `Pages` (the LIGHTWEIGHT read API — summary page + task-lite), `Archives` (the relational per-agent archive in `task_agent_archives`), `Filters` (the ONE shared pagination WHERE builder + limit/offset clamps), `Projects` (project CRUD + its own disk-full rescue), `Safety` (safe selects + `size`). Every public function takes the repo PID first and runs its whole body inside `RepoScope.with_repo/2`, so calls target THAT store's instance regardless of the calling process (the offloaded read worker included).
- **Wire format**: the typed schemas dump/load through `Types.*`, which delegate verbatim to `Codec` — stored bytes are byte-identical to what the Codec defines, never re-implemented.

## Dynamic-Repo Design

- **Per-store UNNAMED instances**: `init/1` boots the repo via `EvoGit.Store.Boot.start_dynamic(data_dir, pool_size: <opt>)` — an UNNAMED (`name: nil`) `EvoGit.Repo` instance. No name ⇒ no global collision ⇒ many same-named `EvoGit.Store` GenServers (test isolation, multi-store) each own their own DB. `state = %{repo: pid, name: name, data_dir: path, writer: pid, offloads: %{}}` (`:data_dir` is the SQLite FILE path; its parent dir is `mkdir_p`'d; `:writer` is the store's dedicated `EvoGit.Store.Writer`; `:offloads` tracks in-flight read workers by monitor ref).
- **PID addressing via the process dictionary**: unnamed instances are addressed BY PID through `EvoGit.Repo.put_dynamic_repo/1` / `get_dynamic_repo/0`; a process that never set the binding transparently addresses the canonical named instance. `RepoScope.with_repo(pid, fun)` binds for `fun`'s duration and ALWAYS restores the previous binding (raise/throw/exit safe; nesting composes — the inner restores the outer's).
- **Pool size — `EvoGit.Store.Boot.default_pool_size/0` (6) by default**: each store's unnamed dynamic repo opens that many connections, overridable per store via `EvoGit.Store.start_link(pool_size: n)` → `init/1` → `Boot.start_dynamic/2`'s validated `:pool_size` (a non-positive / non-integer value raises `ArgumentError`). One connection is the writer's, so 6 gives five concurrent readers beside it; a dashboard page mount issues several concurrent reads (paginated list + summary + changed-since + project count, plus a review-page diff read), and a cold read must not stall every other reader.
- **Connection tuning lives in `EvoGit.Repo.start_opts/0`**, passed as START OPTS by `Boot.start_dynamic/2` (every per-store dynamic instance) and by `mix store.maintenance`: `timeout: 60_000` (the DBConnection per-statement/checkout budget), `queue_target: 500`, `queue_interval: 5_000`, `cache_size: -8_000` (8 MiB SQLite page cache PER connection → ~47 MiB at pool 6), `temp_store: :memory`.
- **Trap for future readers**: `EvoGit.Repo.config/0` does NOT show the effective tuning — it re-runs `init/2` without the start opts and therefore reports Ecto's `@defaults` (`timeout: 15_000`, `pool_size: 10`). The effective values are `start_opts/0`'s, merged as start opts by `Boot.start_dynamic/2`; `defaults/0` keeps only keys Ecto's `@defaults` does not override (`journal_mode: :wal`, `synchronous: :normal`, `busy_timeout: 30_000`, a fallback `pool_size: 2`, `default_transaction_mode: :immediate`, `ownership_timeout: 30_000`).
- **Migrations run on a single-connection BOOT instance**: `Boot.start_dynamic/2` opens the pool at `pool_size: 1`, runs the migrations (and one best-effort `PRAGMA optimize`), then — for a requested `pool_size > 1` — releases that instance and reopens at the requested size (`reopen_pool/3`), so every pooled connection is created against an already-migrated file. Reason: SQLite loads a connection's schema LAZILY and answers `PRAGMA index_list/…` from its cached (possibly empty) schema WITHOUT triggering a load, so a pre-migration connection would report an EMPTY index list non-deterministically in a multi-connection pool; a `pool_size: 1` store keeps the boot instance (and `test/evo_git/store_disk_full_test.exs` pins `pool_size: 1` because its `PRAGMA query_only` arm is CONNECTION-scoped).
- **Test seam**: `EvoGit.Store.__repo_pid__/1` (`@doc false`) exposes the facade's dynamic repo instance — the sanctioned way for tests to reach the store's own connection (e.g. `XqliteEcto3.with_xqlite/2`).

## Boot & Migrations

`init/1` → `Boot.start_dynamic(data_dir, pool_size: <opt>)` runs the Ecto migrations in `../../priv/repo/migrations/` BEFORE any read/write (`Ecto.Migrator.run(repo, Boot.migration_source(), :up, all: true)` — a no-op on a current DB), so an existing user DB upgrades automatically on first start; a manual `mix migrate.store` is never required to boot. Boot failure → `{:stop, {:failed_to_open_sqlite, reason}}` (historical stop tuple) — that tuple covers ONLY the repo-OPEN path (`start_dynamic/2`'s `{:error, reason}` from `EvoGit.Repo.start_link/1`); a MIGRATION raise (e.g. the baseline post-condition rejecting a non-canonical `tasks` shape) propagates out of `init/1` and crashes the Store child (supervisor restart, then app-boot failure) instead of stopping with that tuple. `terminate/2` → reaps in-flight read workers, drains the writer, `Boot.stop(repo)` inside the module's justified try/rescue (GenServer terminate must never raise).

### Boot blocking profile (startup latency)

`Boot.start_dynamic/2` and the migration run are SYNCHRONOUS inside `EvoGit.Store.init/1` (single-connection boot repo → `Ecto.Migrator.run(repo, migration_source(), :up, all: true)` → `PRAGMA optimize` → `Boot.stop(boot)` → reopen the pool at the requested size → `Store.Writer.start_link`) — there is NO `handle_continue`/Task/async deferral, so the supervisor's child start BLOCKS until it returns.
That blocks `EvoGit.Application.start/2`, and therefore — via the OTP application-dependency order (`evo_dash`'s `.app` lists `evo_git` as a start-time dep) — also blocks `EvoDashWeb.Endpoint`'s Bandit listener bind: **Store boot precedes the HTTP listener**, so nothing in evo_dash serves HTTP until evo_git's supervision tree is fully started, and a slow first-boot migration directly delays HTTP readiness (the desktop shell probes that endpoint against a fixed budget).
**Migration timing is version-stamped, not per-boot** (`Boot.migrate_synchronized!/0` → `Ecto.Migrator.run(@repo, source, :up, all: true)`): only migrations whose filename version is NOT already in `schema_migrations` run, so an app-version bump that ships no new migration file is a pure no-op — `Ecto.Migrator` still runs `ensure_schema_migrations_table!` (metadata-only) + reads the applied versions and logs one `Migrations already up` line.
O(rows) WHEN they run: migration 2 (`data_normalization`) is entirely full-table scans/rewrites over `tasks`/`projects` (timestamp normalize ×3, result canonicalize ×2, a per-row Elixir opts rewrite, `branch_name`/`updated_at` backfills), and every `CREATE INDEX` scans the table it indexes (the 6 single-column baseline indexes in migration 1, the 2 composites in migration 3, the 2 covering indexes in migration 5).
O(rows) for a database that still holds legacy values, ONCE: migration 6 (`unpack_abandoned_compressed_rows`) inflates every prefix-tagged compressed text value it finds, and migration 8 (`move_archives_to_table`) decodes each task's legacy archive array, writes one row per archived agent and then drops that column.
O(1)/schema-only: the 3 `CREATE TABLE IF NOT EXISTS` (20-column `tasks` — its legacy archive column is dropped again by migration 8, leaving the 19 live columns —, 3-column `projects`, 23-column `task_agent_archives`) + 6 nullable `ALTER TABLE ADD COLUMN` (no default → no SQLite table rewrite) + the quarantine `DROP TABLE IF EXISTS` + the one-column `ALTER TABLE tasks DROP COLUMN` for the legacy archive column (guarded by a `PRAGMA table_info` probe) + the `PRAGMA table_info`/`index_info` post-conditions.
A fresh DB pays no scan cost (0 rows); a pre-Ecto legacy DB pays the migration-2/3/5 index builds and the migration-6/8 rewrites ONCE and every later boot pays only the `schema_migrations` check.
The migration `.exs` SOURCE is `Code.compile_file`'d once per BEAM (`:persistent_term` memo `{EvoGit.Store.Boot, :migration_source}`) — on EVERY boot, whether or not anything is pending.
`Ecto.Migrator` runs each migration AND its version stamp inside ONE transaction (`XqliteEcto3.supports_ddl_transaction?` is `true`), so a migration interrupted by a SIGKILL rolls back atomically and re-runs in full on the next boot — never a half-applied-but-stamped DB.
A DB locked by another process can stall a boot connection up to `busy_timeout: 30_000` (`../repo.ex`); there are NO `Process.sleep`/`:timer.sleep` calls anywhere on the store/application boot path.
Desktop impact: a boot slow enough to overrun the shell's readiness/navigation budgets surfaces as the shell's "Genesis backend unavailable" retry page while the backend is still booting — see `desktop/src-tauri/CONTEXT.md` → "Backend Readiness Budgets & Launch Diagnostics".

### Migration 1 — `20260815000001_baseline_adoption`

Baseline schema ADOPTION: works on a fresh DB (tables via `CREATE TABLE IF NOT EXISTS` — 20-column `tasks`, 3-column `projects`) AND adopts ANY pre-Ecto legacy DB (no `schema_migrations` table ⇒ migrator sees version 0 ⇒ this migration runs):

- per-column NULLABLE `ALTER TABLE tasks ADD COLUMN` for the six columns a legacy table may lack (`lease_expires_at, model_id, project_path, branch_name, error, updated_at`), THEN the 6 baseline indexes (`CREATE INDEX IF NOT EXISTS` — `idx_tasks_updated_at` references a column the ALTERs may have just added).
- Post-condition: `tasks` carries EXACTLY the 20 canonical columns (names/types/notnull/pk). Physical order is canonical (fresh creates, 15/17-col prefix adoptions) OR the ACCEPTED adopted tail `…, branch_name, updated_at, error` — SQLite ALTERs can only APPEND, and the real v0.9.0–v0.12.5 table already ended in `updated_at`, so the appended `error` lands after it. Column order is functionally irrelevant in SQLite (every query in this system is name-based).
- Every statement runs via `repo().query!/3` (NOT `Ecto.Migration.execute/1` — string commands are queued until `flush/0`, so an in-body `PRAGMA table_info` probe would see the pre-migration state). `up/0` only — rolling back an adoption would drop user data.

### Migration 2 — `20260815000002_data_normalization`

Idempotent DATA rewrites (every guard leaves normalized rows alone):

- **Timestamps**: `strftime('%Y-%m-%dT%H:%M:%fZ', col)` where `col NOT GLOB '*.[0-9][0-9][0-9]Z' AND julianday(col) IS NOT NULL` — for `tasks.started_at`, `tasks.finished_at`, `projects.last_opened_at` (NOT `tasks.updated_at`: only backfilled, never re-formatted). Unparseable/NULL rows skipped.
- **Results**: JSON literal `null` text → SQL NULL; every other untagged value (raw non-JSON strings AND untagged JSON objects/arrays/scalars) wrapped verbatim as `{"__result_tag__":"string","value":…}` via `json_object`. Already-tagged rows untouched.
- **Opts**: legacy positional `[key, value]` pair arrays → JSON objects, rewritten in ELIXIR (Jason) so JSON booleans survive (never `json_group_object`, which collapses them to SQLite integers); malformed rows left untouched.
- **Backfills**: `branch_name` ← `json_extract(result, '$.data.branch_name')` only where NULL AND the result tag is `ok`; `updated_at` ← `COALESCE(finished_at, started_at, now)` where NULL (runs AFTER timestamp normalization). Drops the DETS-era `tasks_quarantine`/`projects_quarantine` tables.

### Migration 3 — `20260815000003_composite_indexes`

Additive DDL only (no table rebuild, no data rewrite; `up/0` only). Creates the two composite `(equality column, started_at)` indexes that make the paginated read index-served: `idx_tasks_status_started_at` on `(status, started_at)` and `idx_tasks_project_path_started_at` on `(project_path, started_at)`. Post-condition: `PRAGMA index_info(<name>)` must report EXACTLY the declared columns in order (`IF NOT EXISTS` alone would silently keep a same-named index of a different shape). Deliberately NOT added: `(status, project_path, started_at)` (never chosen over the two, and it cannot serve a status-only query — incomparable middle column), `type`/`review_status`/`branch_name` (no paginated query leads with them), and no `ANALYZE` at build time (the planner picks both composites with no statistics; boot runs `PRAGMA optimize` instead). Full rationale + measurements: the migration's moduledoc.

### Migration 5 — `20260815000005_covering_indexes`

Additive DDL only, two covering indexes: `idx_tasks_status_updated_at_id` on `(status, updated_at, id)` and `idx_tasks_finished_at_id` on `(finished_at, id)`. `idx_tasks_status_updated_at_id` makes `select_task_ids/2` FULLY COVERING (`status` leads a seek per `IN` value; `updated_at`/`id` ride in the index entry, so no table access, no blob pages, no row decode) and likewise turns the `select_task_ids([])` and `select_finished_task_ids/1` full scans into covering-index scans. `idx_tasks_finished_at_id` serves both `select_cleanup_info/1,3` legs: the age cutoff becomes a covering seek and the count trim's `ORDER BY finished_at DESC` is index-served (no temp B-tree, no per-row lookup for the `OFFSET`-skipped rows). Post-condition: `PRAGMA index_info` must report exactly the declared columns in order. NOT added: `(status, lease_expires_at, id)` (lease reads are tiny), `type`/`review_status`/`branch_name` (no id-oriented read leads with them). Rationale + measurements: the migration's moduledoc.

### Migration 6 — `20260815000006_unpack_abandoned_compressed_rows`

One-shot REPAIR (idempotent, `up/0` only) for databases written by the retired compression iteration: it inflates every value still stored as a tagged `Base64(zlib(json))` envelope back into the plain JSON text it was made from — for `result`, `logs` and the legacy archive column independently (the archive column is unpacked BEFORE migration 8 decodes it). Per column: sweep the ids whose value starts with the tag (`substr(col, 1, 3)`), read ONE value at a time (a `result` can be tens of MiB, `timeout: 600_000` per statement), and `UPDATE` exactly that one column of that one row — never `updated_at`. The base64/zlib helpers live LOCALLY in the migration and no `EvoGit.Store.Codec` function is involved, so the format can never be resurrected as a live writer. Lenient: a payload that fails to decode/inflate is left EXACTLY as it was and logged (`Logger.warning`, task id + column, never the payload), excluded from the post-condition. Post-condition: no value in those columns starts with the prefix.

### Migration 7 — `20260815000007_create_task_agent_archives`

Additive DDL only (`up/0` only, no table rebuild, no data rewrite): creates the RELATIONAL per-agent archive — `task_agent_archives` with `PRIMARY KEY (task_id, agent_id)` (the composite key is what makes a re-put an idempotent REPLACE) — plus `task_agent_archives_task_depth_idx` on `(task_id, depth, agent_id)`. `task_id`/`agent_id` are `NOT NULL`; `depth` and `compression_count` are `NOT NULL DEFAULT 0`; `parent_id` is `INTEGER` while `repo_id` is `TEXT` (a repo ID STRING — `"primary"` or a foreign repo id — NEVER an index, so a migrated row can never hit an `cannot load "primary" as type :integer` failure); `usage`/`llm_settings`/`agent_settings`/`foreign_repos` are plain JSON `TEXT`; `started_at`/`completed_at` are ISO-8601 `TEXT` stored as-is. Post-conditions: `PRAGMA table_info` must report exactly the 23 declared columns in order and `PRAGMA index_info` exactly the declared index columns (`IF NOT EXISTS` alone would silently keep a same-named object of a different shape). Verified with `EXPLAIN QUERY PLAN`: the roster read (`WHERE task_id = ? ORDER BY depth, agent_id LIMIT/OFFSET`) and the per-task `count(*)` are both `SEARCH … USING COVERING INDEX task_agent_archives_task_depth_idx (task_id=?)` with no temp B-tree, and the `DELETE … WHERE task_id = ?` uses the same index prefix. Rationale + full column table: the migration's moduledoc.

### Migration 8 — `20260815000008_move_archives_to_table`

Fans the legacy archive JSON array out of the task row into the relational archive and then DROPs that column. Per task row with a non-empty archive: decode the array LENIENTLY (`Jason.decode/1` — a corrupt or non-list value is logged with the task id and SKIPPED, so one unreadable archive never wedges an upgrade), `INSERT OR REPLACE` exactly ONE `task_agent_archives` row per record (`task_id` from the task row, `agent_id` from the record, `depth`/`compression_count` defaulting to 0, the four JSON columns re-encoded with `Jason.encode!` — plain JSON, SQL NULL for a missing value; `repo_id` is copied VERBATIM, never cast, because it is a repo ID STRING and its column is `TEXT`), strip the duplicated archive list from `result` ONLY when that key is present (a result without it stays byte-identical), then NULL that task's archive column. At the end the column is dropped (`ALTER TABLE tasks DROP COLUMN`, guarded by a `PRAGMA table_info` probe) — no index or constraint references the column, so it is an O(1) schema-header edit. `updated_at` is NEVER touched. Idempotent/resumable: the composite-PK upsert cannot duplicate an agent and each step converges on a re-run.

### Migration versions & ordering

The shipped versions are 1, 2, 3, 5, 6, 7 and 8 — version 4 (the abandoned oversized-row compression rewrite) no longer ships, so a FRESH database never carries its `schema_migrations` row while an upgraded one may still list it (harmless: the version is simply already applied).
Migration 6 MUST stay ABOVE migration 5: an index build WALKS the table, and on rows still carrying compressed blobs the `updated_at`/`id` columns sit physically after the overflow chains, so the walk crawls those pages.
Give any future index migration a version ABOVE `20260815000008`.

### Migration source & concurrent-boot serialization

The migrator is fed a PRE-LOADED source — `Boot.migration_source/0` returns `[{version, module}]` ascending by version — never the migrations DIRECTORY: `migration_source/0` enumerates `Ecto.Migrator.migrations_path(@repo)` + `Path.wildcard("*.exs")` (resolved through `Application.app_dir/2`, so every per-store instance reads the same directory), parses each `"NNN_name.exs"` basename like `Ecto.Migrator.extract_migration_info/1`, compiles it with `Code.compile_file/1`, and picks the module exporting `__migration__/0` (mirroring `load_migration!/1` + `migration?/1`; none → `Ecto.MigrationError`).
The source is memoized in `:persistent_term` under `{EvoGit.Store.Boot, :migration_source}`, so the `.exs` files are compiled at most ONCE per BEAM — a directory source would make `load_migration!/1` `Code.compile_file/1` every pending file on every run, redefining an already-loaded module and printing a `redefining module` warning per boot.
`Boot.run_migrations/1` wraps the run (and the one-time compile) in `:global.trans({{:evo_git_store_migrations, self()}, fun})` — a cluster-safe PRODUCTION lock (no test-side wrapper), because `Code.compile_file/1` of the same module is not concurrency-safe and boots are not exclusive; the lock id is ONE global constant (the protected resource is the shared source modules) and the `self()` LockRequesterId makes it actually exclude; the per-process pdict save/restore stays OUTSIDE the lock.

### `mix migrate.store`

`Mix.Tasks.Migrate.Store` (`lib/mix/tasks/migrate.store.ex`) is a thin wrapper: boots a private unnamed dynamic repo on the target DB (default `<data_dir>/tasks.sqlite`), runs `Boot.run_migrations/1` (the exact call boot uses), reports applied versions, stops the instance. Never starts `:evo_git`. Normally a NO-OP — exists for manual verification / interrupted upgrades.

### `mix store.maintenance`

`Mix.Tasks.Store.Maintenance` (`lib/mix/tasks/store.maintenance.ex`): `mix store.maintenance [--data-dir PATH] [--vacuum] [--no-optimize]` reclaims disk space on demand. It boots a private `pool_size: 1` unnamed dynamic repo on the target `tasks.sqlite` (never starts `:evo_git`), optionally switches `PRAGMA auto_vacuum = INCREMENTAL` (the header change only takes effect after the `VACUUM` the same flag then runs), `VACUUM`s, and prints the main file size plus `page_size` / `page_count` / `freelist_count` / `auto_vacuum` before and after with a one-line reclaimed summary (`--optimize` is ON by default; `--no-optimize` disables it). `VACUUM` is NEVER automatic and never runs at boot.

## API Surface

### `EvoGit.Store` (`../store.ex`) — facade

Public API (all `GenServer.call`, 30s timeout; `store \\ __MODULE__`): `put_task`, `get_task` (full `%TaskInfo{}` incl. `result`/`logs`), `get_task_lite` (the same struct from a decode-identical column projection), `put_task_archive`, `list_task_archives/3`, `get_agent_archive/3`, `delete_task_archives/2`, `delete_task`, `delete_tasks` (500-id chunked), `clear_tasks`, `select_all_tasks`, `count_tasks`, `safe_select_paginated_tasks` (filters `status`/`project_path`/`review_status`/`search`, clamped limit 50/offset 0), `select_tasks_page` (same filters + page-clamp refetch, but 16-key summary rows + `total`, limit default 25/max 50), `update_lease_expires_at` (never bumps `updated_at`), `update_task_columns` (ALWAYS bumps `updated_at`), `get_task_status`, `select_task_logs`, `select_task_update_info`, `select_task_paths`, `select_finished_task_ids`, `select_task_ids`, `select_running_lease_info`, `select_cleanup_info/1,3`, `select_tasks_summary/3`, `select_tasks_summary_by_path/4`, `select_tasks_changed_since/1`, project CRUD (`put_project`, `get_project`, `delete_project`, `select_all_projects`, `count_projects`), safety (`safe_select_all_tasks`, `safe_select_all_projects`, `size`), `__repo_pid__/1`, `__writer__/1`. Plus `start_link(data_dir:, name: \\ __MODULE__, pool_size: nil)`.

The LIGHTWEIGHT read API is ADD-ONLY (every pre-existing name/arity/default/timeout/shape untouched):

- `select_tasks_page(store \\ __MODULE__, opts)` → `%{rows: [16-key summary map], total: non_neg_integer}`; `opts` accepts `status:`, `project_path:`, `review_status:`, `search:`, `limit:` (clamped ≤ 50, default 25), `offset:` (≥ 0), applies the same last-page refetch as `safe_select_paginated_tasks/2`, and never selects `result`/`logs`/`usage`.
- `get_task_lite(store \\ __MODULE__, task_id)` → `%EvoGit.TaskInfo{} | nil`; field-identical to `get_task/2` (the same `Codec.decode_task/1` over an 18-column projection), so it differs only in what a caller must pay for, not in shape.

The PER-AGENT ARCHIVE API (`task_agent_archives`, see "Per-Agent Archive" below):

- `put_task_archive(store \\ __MODULE__, entry)` → `:ok` (`{:error, :disk_full}`, or `{:error, :missing_task_id | :missing_agent_id | :invalid_entry}` before any write). Entry maps may be ATOM- or STRING-keyed; missing values default (`depth` 0, `compression_count` 0, rest `nil`); idempotent on `(task_id, agent_id)` — a re-put REPLACES the row. WRITE offload (the `Store.Writer`).
- `list_task_archives(store \\ __MODULE__, task_id, opts \\ [])` → `%{entries: [string-keyed map], total: non_neg_integer}`, `ORDER BY depth ASC, agent_id ASC`; `:limit` default 100 clamped to 1..1000, `:offset` ≥ 0 (an offset past the end yields an EMPTY page — no last-page refetch here), `:include_results` default `false` means the `result` column is NOT SELECTED and the `"result"` key is ABSENT from every entry (not `nil`, not `""`). `total` counts every row of the task regardless of the page. READ offload.
- `get_agent_archive(store \\ __MODULE__, task_id, agent_id)` → the FULL entry map (result included) or `nil`. READ offload — the lazy detail read paired with the roster page.
- `delete_task_archives(store \\ __MODULE__, task_id)` → `:ok` (also for a task with no rows). WRITE offload.

The shared filter builder lives in `EvoGit.Store.Operations.Filters` (`where_filters/2` + the limit/offset clamps) and is used by BOTH `safe_select_paginated_tasks/2` and `EvoGit.Store.Operations.Pages`, so the two paged reads can never match different rows.

**Search contract**: the ONE runtime `fragment/1` LIKEs `id`, `opts`, `project_path`, `branch_name` only — `result` is deliberately NOT searched (a full-blob scan). Consequence: a phrase that exists ONLY inside a task's final response text never matches; phrases in the objective (`opts`), the id, the project path and the branch name still do.

## Storage Model — plain JSON text columns

`result`, `logs`, `opts`, `usage` and `error` are stored as plain UTF-8 JSON TEXT, exactly what the encoder produced.
There is NO compression layer and no prefix-tagged payload anywhere: a stored value is uniformly readable as JSON by plain SQL (`json_valid`, `json_extract`, `LIKE`), and a `result`/`logs` write is the bytes Jason emitted.
`opts` is a plain JSON object for the same reason: task search is a SQL `LIKE` over its raw text and several SQL paths read it as JSON (`json_extract(opts, '$.path')`).
Decode strictness is unchanged: `decode_result/1` raises `ArgumentError` on anything but the 4 tagged forms, while the lenient `decode_logs/1` → `[]` and `decode_error/1` → `nil` keep their callers safe.
`Types.*` stay thin delegations, so the Codec remains the single wire oracle.

## Per-Agent Archive (`task_agent_archives`)

The archived conversation is a RELATIONAL table, one row per `(task_id, agent_id)` — not a JSON blob on the task row. The table, its composite key and its index are created by migration 7 (`20260815000007_create_task_agent_archives`, see "Boot & Migrations").

- **Schema** (`EvoGit.Store.Schemas.TaskAgentArchiveRow`): `@primary_key false` + `primary_key: true` on `task_id` (`:string`) and `agent_id` (`:integer`) → the composite PK the table declares. Every other column is a plain `:string`/`:integer` field except the four JSON columns (the integers are `parent_id`, `depth` and `compression_count`; `repo_id` is `:string` — a repo ID such as `"primary"`, never an index); NO `timestamps()` (`started_at`/`completed_at` are the archive's own ISO-8601 strings, kept as TEXT so a read returns exactly the bytes written).
- **Wire format** (`EvoGit.Store.Types.ArchiveColumns.*`): `ArchiveUsageJson`, `ArchiveLlmSettingsJson`, `ArchiveAgentSettingsJson`, `ArchiveForeignReposJson` are PLAIN Jason — `Jason.encode/1` on dump (`nil`/map/list; `nil` ⇔ SQL NULL, never the string `"null"`) and `Jason.decode/1` on load, where corrupt/non-JSON text loads as `nil` (one unreadable column never fails an archive read). Deliberately NOT the Codec: no `EvoGit.Agent.Usage{}` struct, no magic prefixes — the archive records data, and the columns stay readable to plain SQL (`json_extract`).
- **Entry maps**: STRING-KEYED, produced by ONE row → entry translation in `Operations.Archives`: `"task_id"`, `"agent_id"`, `"parent_id"`, `"depth"`, `"agent_type"`, `"context_node_path"`, `"objective"`, `"result"` (only when the read includes results), `"base_commit"`, `"final_commit"`, `"branch_name"`, `"archive_ref_start"`, `"archive_ref_final"`, `"repo_id"` (a repo ID STRING — `"primary"` or a foreign repo id), `"repo_root"`, `"repo_path"`, `"usage"`, `"llm_settings"`, `"agent_settings"`, `"foreign_repos"`, `"compression_count"`, `"started_at"`, `"completed_at"`. Writers accept atom- OR string-keyed maps (an atom key wins when both are present), so a read-modify-write round trip needs no reshaping.
- **Read split** (the reason the table exists): the dashboard pages the roster with `list_task_archives/3` (`:include_results` default false ⇒ `result` is never SELECTED, so the key is absent from the entries) and lazily fetches the opened agent's conversation with `get_agent_archive/3` — one agent's result is never paid for by the whole task's archive.
- **Write**: `put/2` is `ON CONFLICT (task_id, agent_id) DO UPDATE` over the FULL 23-column row (replace semantics — a re-put NULLs/resets what the entry omits — and idempotent, so a retried or crash-recovered write can never duplicate an agent).
- **Producer / lifecycle**: the row is written STREAMING, at AGENT COMPLETION, by `EvoGit.Agent.Tools.CompleteTask.write_archive_refs/7` → `EvoGit.TaskRegistry.put_task_archive/1` → `EvoGit.Store.put_task_archive/2` — there is no in-memory buffer, no collection at task end and no archive anywhere in a task's `result`.
  A task start clears any leftover rows for that task id (`AgentScheduler`'s guarded `EvoGit.Store.delete_task_archives/1`), so one task run owns exactly one canonical archive set.
- **Deletes**: `Operations.Archives.delete_by_task/2` backs `delete_task_archives/2`, `delete_by_tasks/2` (500-id chunks) and `delete_all/1` are the bulk primitives.
- **Fault isolation**: every read and write goes through the same facade offload/`write_call` path as the task reads (degraded `%{entries: [], total: 0}` / `nil`; writes `:ok` / `{:error, :disk_full}` / crash).
- **Tests**: `../test/evo_git/store/operations/archives_test.exs` pins the round trip of every column (incl. `repo_id` as the repo ID STRING `"primary"`/`"cowboy"` — an integer-shaped input is stored as its decimal TEXT, a non-string/non-integer one is rejected), nil-JSON/timestamp preservation, idempotent replaces, both key spellings, the depth-then-agent ordering, limit/offset + total, the 100/1/1000 clamps, the absent `"result"` key, and the deletes (operations AND facade).

## Disk-Full Handling

**Contract:** disk-full-class write errors — `SQLITE_FULL` (13), `SQLITE_IOERR` (10), `SQLITE_READONLY` (8) — are converted at the write boundary to `{:error, :disk_full}` instead of crashing the GenServer. Reads keep working; writes can be retried (a full disk is transient, unlike a corrupt DB). Every other write error re-raises and crashes the GenServer; the supervisor restarts it with a fresh repo instance.

- **Where**: the facade's `write_call/2` choke point wraps `put_task`, `delete_task`, `delete_tasks`, `clear_tasks`, `update_lease_expires_at`, `update_task_columns`, `delete_project`, `put_task_archive`, `delete_task_archives` — its closure is handed to the writer process, so the adapter's raise and the `{:error, :disk_full}` conversion both happen where the write runs. `Operations.Projects.put_project` protects itself (returns the tuple directly — never double-wrapped). `put_task`/`put_project` also return `{:error, :missing_task_id | :missing_task_status | :invalid_project_struct}`-style validation tuples before any write.
- **Classification** (`Errors.disk_full_exception?/1`): the `XqliteEcto3` adapter RAISES `%XqliteEcto3.Error{message, statement, type, details}` — matched are `type: :sqlite_failure` with `details.code` in 8/10/13, `type: :read_only_database`, and a message-text fallback (details/top-level message, downcased, containing "database or disk is full"). Trigger `RAISE`s are NOT matched (SQLite reports them as `SQLITE_CONSTRAINT_TRIGGER` code 19 → constraint-violation shape → crash, never a misclassification).
- **Caller degradation** (TaskRegistry + Cleanup): `start_task` put → log + continue in-memory; `force_kill_task`/`cancel_task` pending/`clear_finished_tasks` → `{:error, :disk_full}`; casts (`append_log`, review-status/metadata, heartbeat) → fire-and-forget log; terminal-status writes → log, in-memory cleanup still runs. Full table: `task_registry/CONTEXT.md`.

## Read Fault Isolation & Write Offload

**Every READ is dispatched through `offload(from, state, op_name, degraded_value, fun)`** — one failure-isolated worker per read, `spawn_monitor` (UNLINKED, tracked in `state.offloads`) running the query AND the decode and replying via `GenServer.reply/2`. Large decoded terms are allocated and discarded on the worker's heap, and nothing inside an offloaded read can propagate to the facade: a raise/exit/kill arrives as a `:DOWN` message, a worker-spawn failure is converted identically, and a worker wedged past the **25 s internal deadline** (`@offload_timeout`, below the caller's 30 s `@call_timeout`) is killed and answered with the degraded value. On any of those the facade logs at `:error` with the operation name + reason (exception + stacktrace, exit reason, or `:timeout`) — a degraded read is observable and attributable, never silent. The FULL policy table lives in `store.ex`'s moduledoc ("Read degradation policy"); in one line: reads NEVER raise/exit/return `{:error, _}` — they return the empty value of their own shape (`nil` for single-row reads incl. `get_agent_archive/3`, `[]` for list reads, `{[], 0}` for `safe_select_paginated_tasks`, `%{rows: [], total: 0}` for `select_tasks_page`, `%{entries: [], total: 0}` for `list_task_archives/3`, `0` for counts/`size`). The degraded value is passed EXPLICITLY at each call site, so the table and the handlers cannot drift. `terminate/2` reaps any still-running worker (kills it, cancels its timer), so a terminating store leaves no orphaned worker.

**Writer offload (writes)** — every write handler forwards its operation closure + the ORIGINAL caller's `from` to the store's dedicated `EvoGit.Store.Writer` and replies `{:noreply, state}` immediately, so a slow write (a multi-megabyte `put_task`, a chunked cleanup burst) no longer stalls the facade's mailbox — reads, counts and the 60 s lease heartbeat keep being served. The writer runs the operation and `GenServer.reply/2`s the caller AFTER it commits (read-after-write), preserving strict arrival-order serialization. `put_task`/`put_task_archive`/`delete_task`/`delete_tasks`/`delete_task_archives`/`clear_tasks`/`update_lease_expires_at`/`update_task_columns`/`delete_project` go through `offload_write/3`; `put_project` through `offload_raw_write/3` (unwrapped — `Operations.Projects` owns its own disk-full rescue). The writer is LINKED to the store, so a raising statement kills the writer and (over the link) the store with the operation's own reason; the disk-full choke point (`write_call/2`) runs INSIDE the writer. Writes keep their contract (`:ok` / `{:error, :disk_full}` / crash for other write faults) — a genuine write fault may still restart the store.

**Caller-side containment (`EvoGit.TaskRegistry.StoreGuard`)** — the registry wraps every SYNCHRONOUS store call in `StoreGuard.read(op, degraded, fun)` / `StoreGuard.write(op, fun)`, catching `:exit`/raise/throw, logging at `:error`, and degrading: reads to their documented empty value, writes to `{:error, :store_unavailable}`, which every call site handles EXACTLY like `{:error, :disk_full}`. A Store crash (or an absent store at `TaskRegistry.init/1`) therefore no longer kills the registry — disk-full behaviour is unchanged.

**Not offloaded**: the two test seams `__repo_pid__/1` / `__writer__/1` (plain `GenServer.reply`), because they touch no repo. Everything else that reads a DB column goes through `offload/5`.

## Read-path profile & index inventory

**Query plans**: `select_task_ids` → `SEARCH … USING COVERING INDEX idx_tasks_status_updated_at_id`; the page `COUNT(*)` → a covering-index scan; the page SELECT → `idx_tasks_started_at` index-ordered with NO temp B-tree but NOT covering (one table lookup per row for the 16-key projection); the archive roster read (`WHERE task_id = ? ORDER BY depth, agent_id LIMIT/OFFSET`) and its per-task `count(*)` → `SEARCH … USING COVERING INDEX task_agent_archives_task_depth_idx (task_id=?)`, and the archive `DELETE … WHERE task_id = ?` uses the same index prefix.

**What dominates reads**: the per-row `opts` JSON decode of a summary row and, for the legacy full-row page, `Codec.decode_task/1` of every blob column; a `get_task/2` on a row with a huge `result` pays the full decode; `:search`'s OR-LIKE defeats every index (a full `SCAN tasks` for BOTH statements); `select_tasks_summary/2` with `[]` (all statuses) is a full table scan.

**Index inventory (10 named `idx_tasks_*` indexes + 1 archive index)**: the baseline six — `status`, `finished_at`, `lease_expires_at`, `project_path`, `updated_at`, `started_at` — plus the two composites from migration 3 (`(status, started_at)`, `(project_path, started_at)`) plus the two covering indexes from migration 5 (`(status, updated_at, id)`, `(finished_at, id)`), plus `task_agent_archives_task_depth_idx` on `(task_id, depth, agent_id)`. NOTHING on `type`, `review_status`, or `branch_name` (no paginated query leads with them, and no id-oriented read needs them); no `(status, project_path, started_at)` (the planner reads the combined shape off the path composite).

**Maintenance**: `PRAGMA optimize` runs once per boot after the migrations (on the boot connection, best-effort, seam `:store_boot_optimize_fun`) and hourly via `EvoGit.Store.Maintenance` (supervised right after `EvoGit.Store`, best-effort, never raises when the store is restarting/absent), so `sqlite_stat1` tracks the schema/data over a database's life. `VACUUM` is never automatic — `mix store.maintenance --vacuum` is the only way to return freed pages to the OS.

## Summary Projection Contract (16 keys)

`select_tasks_summary` / `select_tasks_summary_by_path` / `select_tasks_changed_since` / `select_tasks_page` return plain maps with EXACTLY: `id, status, review_status, started_at, finished_at, type, project_path, opts, branch_name, model_id, agent_count, base_sha, commit_sha, lease_expires_at, updated_at, error`. `result` is deliberately never selected/decoded (heaviest per-row blob); `error` is the lenient 16th key (`Codec.decode_error/1` — `nil` for non-failed rows, never a crash); `updated_at` is the RAW fixed-precision ISO string. Undecodable rows (raising `opts` decode) are skipped + `Logger.warning`'d. The three `select_tasks_summary*` reads have no ORDER BY / LIMIT — consumers sort client-side; `select_tasks_page` adds `ORDER BY started_at DESC` + the clamped LIMIT/OFFSET.

## Constraints

- **Codec is the wire oracle**: `Types.*` and the Operations must DELEGATE, never re-implement, encode/decode logic — the `types_test.exs` oracle-equivalence tests pin byte-identity so drift fails loudly.
- **No `?N` SQL in store code**: all runtime access is `EvoGit.Repo.*` + `Ecto.Query`. Raw SQL exists ONLY inside the seven migrations (via `repo().query!/3`, where in-body `PRAGMA` probing requires immediate execution). The ONE runtime `fragment/1` is `Operations.Filters`' 4-column OR-LIKE search filter (`id`/`opts`/`project_path`/`branch_name` LIKE ? ESCAPE ?) — LIKE-escaping cannot be expressed in Ecto.Query syntax; the escape char is pinned as a PARAMETER (a SQL literal `'\'` is doubled by the adapter and rejected by SQLite).
- **Crash philosophy**: no blanket try/rescue on the write path — a failed write statement raises out of the `EvoGit.Repo.*` call and crashes the process running it (the writer), and then the store. Deliberate boundaries: (1) the disk-full choke point (`write_call/2`, executed inside the writer); (2) the failure-isolated read worker (a read fault is observed as `:DOWN`/deadline and degraded, never re-raised); (3) the Writer LINKED to the store (a write raise kills the writer and — over the link — the store with the operation's own reason); (4) the per-row skip-and-log decode boundary inside the Operations (safe selects, summaries, paginated); (5) `TaskRegistry.StoreGuard` at every synchronous registry→store call. Justified try/rescue: `terminate/2`, `write_call/2`, `start_offload_worker/2` only.
- **A READ never takes down the store or its callers**: reads degrade to their own empty shape (see "Read Fault Isolation"), and the registry's `StoreGuard` catches the remaining store-process failures, so a slow/raising read can no longer kill both GenServers.
- **Writes through the TYPED schemas** (or `Codec.encode_*` directly); the raw twins are read-projection only.
- **Atom safety**: closed whitelists (`@known_atoms`, `@known_opt_keys`) — never `String.to_atom` on DB-sourced strings; unknown values stay strings / decode to nil.
- **Known-atom whitelists must stay in sync** with the application's valid status/review_status/type atoms.
- **Quarantine-free design**: no recovery tables, no per-start repair — undecodable rows are skipped + logged; SQLite WAL mode does not corrupt rows. The only startup integrity check is lease reconciliation (`select_running_lease_info` in `TaskRegistry.init/1`).
- **`store.ex` stays cohesive** — do not split the facade without a plan; new handlers dispatch to an Operations module in one line.

## Fixed-precision timestamps & canonical encodings (Codec wire rules)

- `encode_datetime/1` emits the constant 24-char fixed-ms ISO form (`%Y-%m-%dT%H:%M:%S.SSSZ` via `DateTime.truncate(:millisecond)`) — lexicographically sortable in SQLite, which is what makes SQL-side `ORDER BY started_at DESC` and `updated_at > ?` string comparisons correct. Legacy variable-precision rows are rewritten by the data-normalization migration at boot.
- **Result tuples** round-trip via the `__result_tag__` JSON discriminator (`ok`/`error`/`exit`/`string`); plain strings are always JSON-wrapped as the `"string"`-tag form so every `result` value is valid JSON. `decode_result/1` is STRICTLY canonical — nil + the 4 tagged forms only; raw strings, untagged JSON, invalid JSON, JSON null raise `ArgumentError`. Pre-canonical rows are rewritten at boot by the data-normalization migration.
- **Opts** encode as a JSON OBJECT with string keys (JSON-path addressable); `decode_opts/1` atomizes ONLY `@known_opt_keys` (`path mode prompt objective foreign_repos node_path starting_commit archive task_id repo_path concurrency tool_concurrency resume_from attachments quality_level`) — every other key stays a string. Non-object JSON raises. Legacy positional pair-array rows are rewritten at boot. Silent-drop risk: a non-Jason-encodable opt value falls back to the 4 essential keys ONLY.
- **`:foreign_repos` values** round-trip as STRING-keyed maps — normalize via `EvoGit.Core.ForeignRepo.normalize/1` before dot-access. The result `repos` map is deliberately NOT atomized by `decode_result` (read via `Map.get(decoded, "repos")`).
- **`error` payloads**: `decode_error/1` is lenient by design (nil/invalid/non-object → nil); known keys atomized via whitelist, closed-set values restored to atoms. Single producer: `TaskRegistry.Diagnostics.failure_error/3,4`.
- **`review_status`** is ONE flat task-level column (`:open | :merged | :rejected | :continued | :ignored | :no_changes` via the shared whitelist); no per-repo review state exists anywhere — writes go through the generic `update_task_columns(store, id, review_status: atom)`.
- **`updated_at`** is store-internal bookkeeping — deliberately NOT in `Codec.task_columns/0`/`%TaskInfo{}`; written by `put_task` and every `update_task_columns`, never by the lease heartbeat, and never by a migration's maintenance rewrite (migration 4 touches only the two blob columns).

## Known Issues

- **The one-time data migrations cost O(rows)**: migration 6 reads and rewrites every legacy oversized value and migration 8 decodes each archived task's array, on a cold page cache. Both stay within the desktop shell's 90 s backend-readiness budget but are the slowest boots in the product; freed pages are only reclaimed by a manual `mix store.maintenance --vacuum`.
- **A task's archive rows outlive a task-row delete**: `delete_task`/`delete_tasks`/`clear_tasks` touch `tasks` only, so clearing archive data is a separate `delete_task_archives/2` (or `Operations.Archives.delete_by_tasks/2`/`delete_all/1`) call.
- **The lightweight page SELECT is index-ordered but NOT covering**: one table lookup per row for the 16-key projection (fine at dashboard page sizes, but it does touch table pages, so a cold cache pays for them).
- **`select_tasks_summary/2` with `[]` (all statuses) is a full table scan** — inherent to "every row", not index-fixable.
- **`evo_dash` still calls the legacy full-row page read** (`safe_select_paginated_tasks/2`) — wiring it to `select_tasks_page/2` + `get_task_lite/2` is a later round. One dashboard test (`apps/evo_dash/test/evo_dash_web/live/tasks_live_test.exs`, "search_tasks handler filters tasks by agent response message") still searches result text and must flip with that round.
- **A multi-megabyte `result` row is decoded IN FULL by `get_task/2`**: nothing bounds the decoded in-memory term, and `Codec.validate_task/1` checks only `id`/`status`, so a huge `result` is accepted and read whole (one `Repo.one/1` fetch, one `Jason.decode`, then the `decode_result_data/1` map rebuild). Use `select_tasks_page/2` / `get_task_lite/2` when the blobs are not needed, and the paged archive reads when one agent's conversation is what the caller wants.
- **No single-column index on `type`/`review_status`; the `:search` filter is unindexable**: no paginated query filters on `type` (the dashboard drops `:reflect` rows CLIENT-side), and the `review_status: "pending"` shape is the composite `status = 'completed' AND review_status IS NULL AND branch_name IS NOT NULL` — no leading equality column for an index, already served by `(status, started_at)`; an exact `review_status = <value>` filter rides `idx_tasks_started_at` with early exit. The `:search` OR-LIKE forces a full `SCAN tasks` for BOTH statements — inherent to a 4-column OR-LIKE, not fixable by an index.
- **Search hits depend on JSON text representation**: the OR-LIKE runs over `id`/`opts`/`project_path`/`branch_name`, so `opts` hits depend on its JSON key/string spelling (e.g. underscores escaped) — a match requires the JSON text to contain the value verbatim, and `result` is never searched.
- **A data dir on a network/UNC path is accepted but unusable (Windows)**: `EvoGit.Platform.data_dir/0`'s `[data] dir` override validation (`absolute_path?/1`) accepts `\\server\share\...`, yet `Store.init/1` opens with `journal_mode: :wal` — SQLite's WAL needs the `-shm`/`-wal` shared-memory files, which network filesystems do not provide, so the open can fail and `init/1` returns `{:stop, {:failed_to_open_sqlite, reason}}` → the app never boots cleanly.
- **Store boot failure is fatal, not degraded**: `init/1` calls `File.mkdir_p!(dir)` (bang → raises on an unwritable `[data] dir`) and `{:stop, ...}` on a failed `Xqlite.open/2`, so a bad/unwritable/UNC data dir crash-loops the application instead of falling back to a default location.
