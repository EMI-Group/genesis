# EvoGit Core Library — `lib/evo_git/`

## Intent
Core source of the `:evo_git` OTP application: the Agent system (LLM-powered tool-calling loops), AgentScheduler (GenServer for scheduling, ETS state, slot management — worktree lifecycle owned by `AgentScheduler.WorktreeManager`), Core domain types (ContextNode, PhyloGraphNode, ForeignRepo), Git adapter, and Runtime phases (Genesis, Evolution). Supports multi-repo operation — foreign repos configured via `genesis.toml` or CLI flags enable cross-repo subagent spawning into isolated worktrees.

## Routing Table
- `./agent/` → Agent behaviour, tool library, context compression, subagent processing
- `./agents/` → Agent implementations (Manager, Executor, TaskScheduler, Investigator, Architect, ContextExtractor, SkillExtractor, GenesisPlanner)
- `./agent_scheduler/` → AgentState, SchedMeta, Slots, Worktrees, WorktreeManager — ETS schemas, helpers, worktree lifecycle
- `./core/` → ContextNode, PhyloGraphNode, ForeignRepo data structures
- `./adapters/` → Git CLI adapter — all git operations go through this module
- `./runtime/` → Genesis, Evolution, PR helpers, Skill Extraction
- `./config/` → Unified 3-level configuration resolver (defaults → user TOML → runtime overrides), schema definitions, LLM catalog, platform detection, project config
- `./sandbox/` → Multi-platform sandbox backends (Linux systemd-run, Linux bwrap, macOS sandbox-exec, passthrough)
- `./skills/` → Dynamic skill tools system — YAML-frontmatter markdown skills as LLM-callable tools
- `./store/` → SQLite persistence codec — pure serialization for `EvoGit.Store`
- `./task_registry/` → TaskRegistry support modules — Cleanup, Diagnostics, Lease, ResumeContext, RuntimeOpts, TaskExecutor

### SSH Remote Bootstrap — Auto-Download Flow
`EvoGit.RemoteConnection.bootstrap/1` does not require a local tarball. Sources in priority order: (1) `local_binary_path` set + exists → `scp` upload; (2) set-but-missing → `Logger.warning` + fall back to auto-download (VS Code semantics); (3) absent → auto-download. Auto-download stages: `:probing_platform` (uses target's optional `platform` field, else one `uname -s && uname -m` SSH call) → `:downloading` (remote `curl -fL`, with a remote `wget -O` fallback when curl is missing or fails) → `:downloading_locally` (fallback: local curl into `<data_dir>/remote_binaries/<platform>_<version>.tar.xz` cache + `scp`) → then the existing `:extracting` → `:setting_permissions` → `:copying_config` → `:generating_cookie` → `:patching_binaries` → `:starting_daemon`. The probed/overridden OS is threaded through so `:detecting_os` is skipped on the auto path (still broadcast on the local-tarball path). On NixOS remotes, bootstrap patches the extracted glibc release **on the fly**: after `:generating_cookie`, one SSH round trip runs `EvoGit.RemoteBootstrap.nixos_detect_command/0` (`test -d /etc/nixos` or `ID=nixos` in `/etc/os-release`); when NixOS is detected (Linux + daemon not already running — a live daemon is never patched) the `:patching_binaries` stage runs `nixos_patch_script/1` — a single remote shell script that `nix-build`s `patchelf`/`bintools`/`stdenv.cc.cc.lib`/`openssl` from `<nixpkgs>` (GC-rooted under `<release>/.nixos-patch`, so re-bootstraps are instant) and rewrites every ELF binary's interpreter/RPATH to the Nix store paths. Non-NixOS/macOS remotes skip the stage entirely; failures surface as `{:error, {:nixos_patch_failed, details}}`. Stage atoms: `:probing_platform | :downloading | :downloading_locally` (evo_dash `settings_live.ex` needs UI labels for these three).
**Error tuples** (for tests): probe → `{:error, {:probe_failed, {:exit_status, n} | :timeout | {:unexpected_output, out}}}` or `{:error, :unsupported_platform}`; download → `{:error, {:download_failed, {:exit_status, n} | :timeout | {:local, detail} | {:local_scp, detail}}}`; platform override → `{:error, {:invalid_platform, p}}` / `{:error, :unsupported_platform}` (e.g. `windows_x64` — daemon launcher only supports Linux/macOS). `download_url/1` returns `{:ok, url, version}`; version is always `"latest"` (deterministic, no API query) and keys the local cache.
**Notes**: `remote_connection.ex` is ~1300 lines (over the ~1000 baseline) — all pure logic lives in `remote_bootstrap.ex`; the remaining length is the ssh/scp/curl/wget orchestration, stage broadcasting, and state transitions that the module-boundary design deliberately keeps in `RemoteConnection`. `@bootstrap_call_timeout_ms` is 900s (download can be slow); `@download_timeout_ms` is 300s.

### Remote Bootstrap Asset Format

The SSH remote-bootstrap release asset is a **`.tar.xz`** archive: `genesis_remote_<platform>.tar.xz` (asset name, download URL, local cache path, and remote temp file all use `.tar.xz`). This is coordinated with `.github/workflows/build-desktop.yml`, which uploads `genesis_remote_<os>_<arch>.tar.xz` per platform (linux_x64 / linux_arm64 / darwin_arm64 / windows_x64). Extraction uses `tar -xJf` — the remote host needs xz-capable tar (works on all Linux distros with xz-utils, and macOS bsdtar supports xz natively). There is intentionally NO gz fallback: if xz extraction fails it should fail loudly.

### SQLite Store — SQL-Lowering Refactor

- **No row-recovery/quarantine machinery**: SQLite WAL mode does not corrupt rows, so there is no recovery-table repair routine or `mix` recovery task. `safe_select_all_tasks/1`, `safe_select_all_projects/1`, `safe_select_paginated_tasks/2` skip undecodable rows with a `Logger.warning` ("Store: skipping undecodable row in ...").
- **NO auto-migration at startup**: `Store.init/1` runs ONLY `Schema.create_tables/1` (fresh DBs get the full schema). `Schema.migrate_schema/1` + `Schema.normalize_timestamps/1` are NOT called at init — existing DBs are upgraded by the manual **`mix migrate.store`** task (`apps/evo_git/lib/mix/tasks/migrate.store.ex`): it applies schema migrations (adds the `updated_at` column to `tasks`, etc.) and normalizes legacy timestamp formats. The `Schema` functions remain available for the mix task and tests.
- **`updated_at` write semantics**: `tasks.updated_at` is store-internal bookkeeping — NOT in `Codec.@task_columns`/`%TaskInfo{}`. `put_task` writes it via the 19-column INSERT (`Codec.encode_datetime(DateTime.utc_now())`); `update_task_columns` automatically appends `{:updated_at, DateTime.utc_now()}` (encoded via `Queries.encode_column_value/2`). `update_lease_expires_at` does NOT bump `updated_at` — the 60s heartbeat must not mark tasks dirty. Rows with NULL `updated_at` (legacy DBs before `mix migrate.store`) never match changed-since queries.
- **Extended summary API**: `EvoGit.Store.select_tasks_summary(store \\ __MODULE__, statuses \\ [], since \\ nil)` and `select_tasks_summary_by_path(store \\ __MODULE__, project_path, statuses \\ [], since \\ nil)` — `statuses` is a list of status atoms, `[]` = all statuses; `since` is an optional fixed-precision ISO-8601 string that pushes `AND updated_at > ?N` into SQL (nil = no filter). The SELECT projection includes scalar columns `branch_name, model_id, agent_count, base_sha, commit_sha, lease_expires_at` plus `updated_at` (raw fixed-precision ISO string, NOT decoded — heavy columns logs/usage/archive_metadata stay out). **Summary map keys (15)**: id, status, review_status, started_at, finished_at, type, project_path, opts, branch_name, model_id, agent_count, base_sha, commit_sha, lease_expires_at, updated_at. (`result` is deliberately NOT in the projection — no summary consumer reads it; the dashboard's review button uses the denormalized `branch_name` column, and `result`'s JSON blob is the heaviest per-row decode.) Pass-throughs: `TaskRegistry.list_tasks_summary(statuses \\ [], since \\ nil)` + `list_tasks_summary_by_path(path, statuses \\ [], since \\ nil)`, `AgentScheduler.RemoteAPI.list_tasks_summary/1` + `list_tasks_summary_by_path/2` (no-arg forms kept for old RPC callers), `EvoGit.RemoteNode.list_tasks_summary/2` + `list_tasks_summary_by_path/3` over `:erpc`. **⚠️ `since` is NOT exposed through RemoteAPI/RemoteNode** — the RPC layers only accept `statuses`; remote callers needing a time filter must use `list_tasks_changed_since` (which accepts no statuses). Only the local `TaskRegistry`/`Store` calls can combine statuses + since.
- **Changed-since API (polling)**: `Store.select_tasks_changed_since(store \\ __MODULE__, since_iso)` returns summary-shaped maps (same 15-key projection incl. `updated_at`) for rows with `updated_at > since_iso` (fixed-precision string comparison — no heavy columns). Chain: `TaskRegistry.list_tasks_changed_since/1` → `AgentScheduler.RemoteAPI.list_tasks_changed_since/1` → `EvoGit.RemoteNode.list_tasks_changed_since/2` (over `:erpc`; `[]` on RPC failure).
- **Summary-handler offload**: `TaskRegistry`'s `:list_tasks_summary` / `:list_tasks_summary_by_path` / `:list_tasks_changed_since` handlers (task_registry.ex:416-458) use the `Task.start` + `GenServer.reply` offload pattern (same as `:list_tasks`/`:list_tasks_paginated`/`:list_tasks_by_path` at task_registry.ex:285-310, 374-391) — large decoded terms are allocated/discarded on a short-lived Task process's heap, not the TaskRegistry GenServer's.
- **Store-side decode offload**: the Store's own heavy full-decode handlers also offload — `select_all_tasks`, `safe_select_all_tasks`, `safe_select_paginated_tasks`, `select_tasks_summary`, `select_tasks_summary_by_path`, and `select_tasks_changed_since` run the query AND the decode on a short-lived LINKED `Task.start` replying via `GenServer.reply/2` (`{:noreply, state}` immediately), so decoded terms are allocated/discarded on the Task heap, not the Store GenServer's. Cross-process xqlite use is safe (the connection is mutex-guarded in the NIF — no owner constraint; verified in deps/xqlite connection.rs). The link preserves the exact crash-on-decode-raise behavior; the skip-and-log boundary (`decode_skipping_bad`) and `_ -> []` query-failure arms run inside the Task; the caller's 30s `@call_timeout` is unchanged. Bodies live in `do_*` private helpers. Single-row/tiny handlers (`get_task`, `select_task_logs`/`update_info`, id-only projections, counts, projects ≤10 rows) stay synchronous.
- **Disk-full write handling**: SQLite disk-full-class write errors (`SQLITE_FULL` 13, `SQLITE_IOERR` 10, `SQLITE_READONLY` 8) are detected at the write boundary by the pure classifier `EvoGit.Store.Errors.disk_full_error?/1` (matches `{:sqlite_failure, code, _, _}` with code 8/10/13, `{:read_only_database, _, _}`, plus the canonical "database or disk is full" message fallback) and converted to `{:error, :disk_full}` by the shared private `execute_write/4` — the GenServer survives, reads keep working, writes can be retried; every other write error raises an identical MatchError (crash + supervisor restart). All 8 write functions (`put_task`, `delete_task`, `delete_tasks`, `clear_tasks`, `update_lease_expires_at`, `update_task_columns`, `put_project`, `delete_project`) return `{:error, :disk_full}` on the disk-full class (success shapes unchanged). TaskRegistry + Cleanup degrade gracefully at all 14 write call sites (log+continue for casts/heartbeat/log-loss; `{:error, :disk_full}` from `force_kill_task`/`cancel_task`/`clear_finished_tasks`; in-memory terminal cleanup always runs). Full contract + xqlite error shapes + testability findings in `store/CONTEXT.md` → "Disk-Full Handling".
- **Minimal id/status/updated_at projection**: `Store.select_task_ids(store \\ __MODULE__, statuses \\ [])` — SELECT of ONLY `id, status, updated_at` (no JSON blob decode; `updated_at` returned RAW as the stored fixed-precision ISO string, never decoded). Status filter pushed into SQL via `build_status_where/1` (`[]` = all rows); `_ -> []` on query failure. Chain: `TaskRegistry.list_task_ids/1` (synchronous handler — tiny projection, deliberately NOT offloaded) → `AgentScheduler.RemoteAPI.list_task_ids/1` (direct delegation) → `RemoteNode.list_task_ids/2` (local-vs-`:erpc`, `[]` on failure). Purpose: dashboard task-changed tracking without decoding the heavy `result` blob.
- **Narrow-read Store functions**: `select_task_logs(store \\ __MODULE__, task_id)` (SELECT logs, decoded list or nil) and `select_task_update_info(store \\ __MODULE__, task_id)` (SELECT status, opts, finished_at, lease_expires_at → map or nil). TaskRegistry hot paths (`append_log`, `set_review_status`, `set_review_metadata`, `handle_update_status`/`update_task_status_with_caller`, `cancel_task`, `resolve_recheck_task`) use these narrow reads + `update_task_columns` instead of full `task_get` decodes.
- **Cleanup pushdown**: `Store.select_cleanup_info(store \\ __MODULE__, cutoff_iso, max_tasks)` returns the ids to delete with BOTH filters in SQL: age cutoff (`finished_at IS NOT NULL AND finished_at < ?cutoff` — ALL age-expired rows, no count trim) and count trim (`finished_at >= ?cutoff ORDER BY finished_at DESC LIMIT -1 OFFSET ?max_tasks` — keeps the NEWEST `max_tasks` among non-age-expired finished rows). String comparison is safe on the fixed-precision 24-char ISO format. `TaskRegistry.Cleanup.cleanup_expired_tasks/1` consumes it (reads only ids; semantics unchanged — verified by `cleanup_test.exs`/`persistence_test.exs`). The `select_cleanup_info/0,1` variants (returning `%{id, finished_at}` maps) remain for backward compat (tests pin them).
- **`resolve_recheck_task/3`** persists `branch_name` (extracted from `{:ok, %{branch_name: _}}` results, mirroring `handle_update_status/6`; only written when non-nil so it never clobbers). `Lease.lookup_sched_meta_result/1` is used by `resolve_recheck_task/3`. `trim_recent_projects` is nil-safe (`sort_projects_by_recency/1` sorts nil `last_opened_at` LAST).
- **Lease/cleanup queries**: `select_running_lease_info` queries `status IN ('running','finalizing')`.
- **Batched delete**: `delete_tasks` uses chunked `DELETE ... WHERE id IN (...)` (~500 ids/chunk) — all-or-nothing per chunk.

## Known Issues

- **Startup reconciliation of orphaned `:finalizing` tasks** (detailed in `./task_registry/CONTEXT.md` "Restart Recovery & Status Transitions"): `EvoGit.TaskRegistry.init/1` (`task_registry.ex:159-220`) performs **startup reconciliation** for orphaned `:finalizing` tasks — after Store startup (timestamp normalization does not run at init — it happens via the manual `mix migrate.store` task), it queries `EvoGit.Store.select_running_lease_info/1` (lightweight id+status+lease_expires_at, SQL-filtered to `status IN ('running','finalizing')`), filters `status == :finalizing`, and synchronously marks each `:failed` via the shared `handle_update_status/6` (`:506`) with result `"Runtime restarted during task finalization"` and `caller_info = {:startup_reconcile, :finalizing}`. This covers the crash window where slow git calls in `merge_and_report/3` hang while the task sits at `:finalizing` and the app dies before the terminal write. `:running` tasks are deliberately untouched — the one-shot `:lease_sweep` (`:896-947`) handles orphaned `:running` owners after the lease duration (it respects lease validity for the legitimate multi-VM case). Remaining caveats: `:heartbeat` renews leases only for `:running`/`:pending`; `:periodic_cleanup` deletes only rows with `finished_at != nil`; the `{:recheck_task, _}` handler (`:971-990`) is unreachable (nothing schedules the first recheck). In-process resolution still requires the wrapper process to finish (→ `:completed`/`:failed`) or crash (→ `:DOWN` → `:failed` only if no active sched_meta agents) — lease expiry plays NO role in resolving `:finalizing`.

## Windows PowerShell Invocation — `-EncodedCommand`

**Why `-EncodedCommand` (do not re-investigate):** `powershell.exe -Command <script>` spawned from Erlang is broken by construction. PowerShell does NOT parse `-Command` via standard Windows argv rules — it re-joins the raw command line and re-parses it as PowerShell code, so quotes/escapes inserted by Erlang's spawn (Port.open/System.cmd arg quoting) get mangled. When the script arg is lost, PowerShell falls back to INTERACTIVE mode; with closed/EOF stdin it exits 0 with NO output. Secondary issue: PS 5.1 writes piped output using `[Console]::OutputEncoding` (OEM/UTF-16 code page) — `EvoGit.UTF8.ensure_utf8/1` treats a UTF-16LE BOM as invalid UTF-8 and would return an empty valid prefix.

**Invocation (robust by construction — Linux CI can only compile-check Windows code):**
- Spawn `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -EncodedCommand <b64>` where b64 = base64(UTF-16LE of `& { [Console]::OutputEncoding = [System.Text.Encoding]::UTF8; <script> } *>&1`). `-EncodedCommand` eliminates ALL command-line quoting/parsing; the OutputEncoding line forces UTF-8 output; `*>&1` merges all streams incl. Write-Host/information. No `<` / input redirection anywhere.
- All pure logic lives in `EvoGit.Powershell` (lib/evo_git/powershell.ex), applied at: `Platform.shell_args/1` Windows clause (fixes ShellTool `run_powershell` AND `Worktrees.run_init_script/3` — both consume `Platform.shell_args`); `EvoGit.Sandbox.None` `run_windows/3` + `run_with_partial_windows/5` (defense-in-depth `transform_args/2` for any caller still passing `["-Command", cmd]`; `decode_output/1` on collected output — BOM-aware, idempotent).
- `transform_args/2` matches ONLY powershell/pwsh (any case, incl. `C:\...\powershell.exe` paths — backslash-normalized before `Path.basename`) with the exact 2-element `["-Command", cmd]` shape → already-encoded args and bash/git invocations pass through untouched (no double transform).

**Tests:** `apps/evo_git/test/evo_git/powershell_test.exs` (26 pure-module tests: `powershell_executable?/1`, `wrap_script/1`, `encode_command/1`, `invoke_args/1`, `transform_args/2`, `decode_output/1` — Linux-runnable, `async: true`). The `shell_args/1` test in `apps/evo_git/test/evo_git_test.exs` branches on `Platform.os()` (`:windows` → `EvoGit.Powershell.invoke_args/1`, else `["-c", cmd]`).

## Constraints
- All git operations must go through `EvoGit.Adapters.Git` — no direct `System.cmd("git", ...)` outside adapters.
- Agents are transient modules using `EvoGit.Agent` behaviour; persistent state lives in ETS.
- System prompts MUST NOT contain dynamic state, objectives, or context trees.
- Worktrees are created FRESH per agent run (no pool, no reuse across retries); the `WorktreeManager` GenServer owns lazy per-repo init, creation (via `Worktrees.prepare_new_worktree/5`), and monitor-driven reclaim/destruction.
- Agents commit before delegating subagents (auto-commit fallback enforced by scheduler).
- Tool outputs truncated at 128KB; agent loop has 30-min LLM budget with graduated warnings.
- Cross-repo subagents commit to their foreign repo's worktree — changes are NOT merged into the primary repo.
- 3-level configuration: `EvoGit.Config` merges defaults → user TOML → runtime overrides.

## First User Prompt Assembly
The `run/1` callback (injected by `use EvoGit.Agent`) assembles the agent's first user message as two distinct, XML-delimited blocks separated by a markdown horizontal rule, so the LLM can cleanly distinguish environment from objective:

```
<context>
{context_tree}

{foreign_repos_section}  ← omitted when blank
</context>

---

<objective>
{objective}  ← entire block omitted when there is no objective
</objective>
```

- **`build_dynamic_context/1`** and **`build_foreign_repos_section/1`** produce the section bodies (unchanged by framing); only how the sections are delimited relative to each other is structured.
- Blank sections (e.g. no foreign repos, or no objective) are dropped entirely — no dangling rules, empty headers, or empty XML blocks are ever emitted. The `---` delimiter appears only between two non-blank blocks.

## ReqLLM Finch Pool Reconciliation (`EvoGit.ReqLLMPool`)

`lib/evo_git/req_llm_pool.ex` — dynamic runtime reconciliation of the ReqLLM Finch HTTP pool (`ReqLLM.Finch`), fixing the user-facing "Finch was unable to provide a connection within the timeout due to excess queuing" RuntimeError (deps/finch/lib/finch/http1/pool.ex:81-90) that occurs when runtime concurrency changes outgrow the boot-time pool size.

**Public API:** `desired_count(total)` → `max(total + 2, 8)` (single source of truth — `config/runtime.exs` delegates to it); `error_target_count(total)` → `max(ceil(total * 1.5), 8)`; `effective_concurrency(model_concurrency_map, default)` → `max(sum of map values, default)` for non-empty maps, falls back to `default` for empty/nil; `reconcile(total, finch \\ ReqLLM.Finch)` → grow pools to `desired_count`; `bump_for_excess_queuing(model_concurrency_map, default, finch \\ ReqLLM.Finch)` → grow pools to the 1.5x target; `excess_queuing_error?(reason)` → matcher for the Finch error (bare `%RuntimeError{message}` with "excess queuing", `%ReqLLM.Error.API.Stream{reason, cause}` inspecting to it, or inspect-fallback like `TruncationFeedback.is_rate_limit_error?/1`).

**Grow-only semantics (MANDATORY):** `Finch.set_pool_count/3` grows by `Supervisor.start_child`-ing new pool processes (safe) but shrinks by `terminate_child` (kills in-flight streams) — `EvoGit.ReqLLMPool` NEVER shrinks (`max(current, desired)` per origin). All public functions never raise; `{:error, :not_found}` (no materialized origins) is a graceful no-op.

**Enumeration & the `start_pool_metrics?` requirement (CRITICAL):** pools are materialized LAZILY per origin on first request. `Finch.get_pool_status(finch, :default)` returns `{:ok, %{%Finch.Pool{} => [%Finch.HTTP1.PoolMetrics{}, ...]}}` (list length = current pool-process count; keys are `%Finch.Pool{}` structs directly usable by `set_pool_count/3`) — but ONLY for pools whose config has `start_pool_metrics?: true` (deps/finch finch.ex:98-102 default `false`; pool/manager.ex:216 `track_default? = pool_config.start_pool_metrics? and not Map.has_key?(config.pools, pool)`). Without the flag, `get_pool_status(:default)` always returns `{:error, :not_found}` → reconciliation is a **silent no-op**. `config/runtime.exs` uses the full `finch:` override form (`config :req_llm, finch: [name: ReqLLM.Finch, pools: %{default: [protocols: [:http1], size: 2, count: stream_pool_count, start_pool_metrics?: true]}]`, runtime.exs:66-78), so production `ReqLLM.Finch` DOES have the flag and `get_pool_status(:default)` enumerates every lazily-materialized origin. Per-origin capacity = `count × 2` concurrent HTTP/1 streams. Shard selection across pool processes is **RoundRobin** via ReqLLM's top-level `stream_pool_strategy` config key (`{Finch.Pool.Strategy.RoundRobin, round_robin}` — an `:atomics` ref created at config-eval time in runtime.exs; read per request as the `pool_strategy` opt at call time, streaming/finch_client.ex:426-428 — NOT a pool-template key, NimbleOptions would raise). `stream_pool_timeout: 300_000` stays top-level (Finch checkout/pool-queue wait, read at CALL time via `Application.fetch_env(:req_llm, :stream_pool_timeout)`, streaming/finch_client.ex:299-305). Tests use their own Finch with the flag set, so they pass regardless.

**Two triggers (both wired):**
1. **Config change** — `AgentScheduler.handle_call({:update_config, opts}, ...)` (`agent_scheduler.ex:641-654`): the `{:reply, :ok, new_state}` path (via private `reconcile_pool_after_update/1`) computes `effective_concurrency(new_state.model_concurrency, new_state.default_llm_max_concurrency)` and calls `reconcile/2`. Covers ALL config-change routes (RemoteAPI.reload_config, save_user_config, evo_dash ConfigIO). The `{:error, "llm_model cannot be nil"}` path never reconciles. `State.do_update_config/2` (state.ex, pure) is untouched — it always returns `{:reply, :ok, state}` (state.ex:376), so the single-clause helper is total. Boot safety: `init/1` also reconciles after building `%State{}` (no-op at boot — pools lazy; must never crash init).
2. **Excess-queuing error** — `ToolDispatch.call_llm_with_retry/5` (`tool_dispatch.ex:204-218`): in the `retry with` loop's inner-`with` `{:error, reason}` branch (between retries, so the bump executes BEFORE the next retry attempt), `if EvoGit.ReqLLMPool.excess_queuing_error?(reason), do: EvoGit.ReqLLMPool.bump_for_excess_queuing(AgentScheduler.get_config(:model_concurrency), AgentScheduler.get_config(:default_llm_max_concurrency))`. No `report_llm_error` for this — the bump IS the fix; existing retry/rate-limit semantics unchanged. `AgentScheduler.get_config/1` from the agent process is safe (pure state reads, no slot contention).

**Tests:** `test/evo_git/req_llm_pool_test.exs` (16 tests, `async: false`) — pure-function tests + real-tiny-Finch grow/grow-only/`:not_found`-grace tests (test Finch started with `start_pool_metrics?: true`, `pools: %{default: [size: 1, count: 2]}`; origin materialized via a request to a closed port, `http://127.0.0.1:1/`, which still materializes the pool). ## Per-Origin Pool Semantics & Sizing Rationale

**Q: Does Finch build a pool per endpoint, or do all endpoints share one pool? → Per-origin (scheme://host:port), all from the single `:default` template.**

- **Pool identity = `{scheme, host, port, tag}`** — `Finch.Pool.to_name/1` (deps/finch/lib/finch/pool.ex:143); path prefixes (e.g. `/v1`) are NOT part of the key. Request dispatch derives the pool from the request: `Finch.get_pool/3` builds `Finch.Pool.from_name({scheme, host, port, tag})` (deps/finch/lib/finch.ex:1017-1020) → `Pool.Manager.get_pool` (manager.ex:96-99) → on Registry miss, lazy `maybe_start_pool`/`start_pool` (manager.ex:130-140, 214-230) → `pool_config(config, pool) = Map.get(config.pools, pool, default_pool_config)` (manager.ex:232-236). ReqLLM's pools map contains ONLY `:default` (req_llm application.ex:101-109; the runtime.exs `finch:` override pops `:default` at finch.ex:374), so **every origin materializes lazily on first request from the same `:default` template** — one pool supervisor + `count` NimblePool shards per distinct origin.
- **`Finch.get_pool_status(finch, :default)` = per-origin enumeration** (finch.ex:1082-1099): `Pool.Manager.get_default_pools` → `Registry.lookup(registry, :default)` (manager.ex:181-184) → `%{%Finch.Pool{} => [per-shard metrics]}` (map key = origin; list length = that origin's current shard count). Requires `start_pool_metrics?: true` (manager.ex:216 `track_default?`; pool/supervisor.ex:17-19) — set via the `finch:` override form (see above).
- **`Finch.set_pool_count(finch, pool_id, count)` is per-origin** (finch.ex:1202-1205): `resolve_pool` → `Pool.Manager.set_pool_count` (manager.ex:201-210) → `get_pool_supervisor` (unique Registry keyed by `{scheme,host,port,tag}`, manager.ex:144-161) → `Finch.Pool.Supervisor.set_count` (supervisor.ex:29-55: grow = `start_child`, shrink = `terminate_child`). **Only the addressed origin's pool changes.** `{:error, :not_found}` until that origin has been materialized by at least one request (finch.ex:1194-1195 doc) — this is why boot-time `reconcile` is a graceful no-op and why `ReqLLMPool.grow_pools_to` must key `set_pool_count` by the `%Finch.Pool{}` structs returned by `get_pool_status/2` (req_llm_pool.ex:204).
- **ReqLLM never selects a pool explicitly per request.** `Retry.stream` passes only `[:pool_timeout, :receive_timeout, :request_timeout, :pool_strategy]` to `Finch.stream/5` (retry.ex:33-34; finch_client.ex:230-242). There is no `:pool` request option in Finch's API at all — the pool is always derived from the request's scheme/host/port (finch.ex:1017-1020). ReqLLM never sets `pool_tag` (the only `pool_tag` references in deps/req_llm are reads in finch_client.ex:392-399 used only for HTTP/2 body-size validation), so every request uses tag `:default`.

**How many origins does EvoGit produce?** One per distinct base_url host among the `[[llm.models]]` profiles (path prefixes ignored). Profile `model` is a string `"provider:model"` (origin = provider's ReqLLM default host, e.g. openai → `api.openai.com:443`, anthropic → `api.anthropic.com:443`, ollama → `localhost:11434`) or a map `%{provider:, id:, base_url:}` (schema.ex:323/374; llm_catalog.ex:335-338 — per-profile `base_url` supported). Multiple profiles sharing a host share ONE pool (e.g. several OpenAI models → one `api.openai.com` pool). Typical configs: 1-4 origins.

**Sizing correctness — SUM formula `max(total + 2, 8)` applied uniformly per origin:**
- Per-origin capacity = `count` × `size` (= `count` × 2 here, size=2) concurrent HTTP/1 streams; `size` is a LAZY upper bound, not a reservation (finch.ex:55-68; http1/pool.ex:33 `lazy: true` — connections open on first checkout).
- **Slot-gated demand on origin O = D(O) = Σ concurrency of profiles targeting O ≤ total = Σ all profile concurrencies.** Since the pool for O is sized to `total + 2 ≥ D(O) + 2`, the SUM-based uniform formula **never under-provisions slot-gated demand**: summing is the provably sufficient upper bound (equality when all profiles share one origin). The `+2` covers the two non-slot-gated auxiliary call sites (system_check.ex:344, pull_request.ex:153).
- **Over-provisioning (the real cost of summing):** N single-profile origins each get `total+2` shards instead of `c_i+2` (waste `total − c_i` shards per origin; e.g. 5 single-profile origins at c=3 → 12 wasted × 5 = 60 idle NimblePool processes). **Practically harmless**: shards are cheap lightweight processes and connections open lazily (no sockets until checkout); Finch's own docs recommend the lowest `count` that meets needs but err in the safe (raise) direction (finch.ex:36-41). The 1.5× error bump (`error_target_count`) over-provisions similarly — also harmless.
- **Error path cannot identify the failing origin**: `%ReqLLM.Error.API.Stream{}` carries only `[:reason, :cause]` (req_llm error.ex:313-323) and the Finch RuntimeError message is static (http1/pool.ex:81-90 — no host/port). The origin is recoverable only at the call site (the agent knows `current_model()`), but `bump_for_excess_queuing/3` (tool_dispatch.ex:210-214) doesn't pass it — so the bump is necessarily uniform today.

**Design decision — the uniform SUM formula is kept.** It is provably sufficient for slot-gated demand; over-provisioning is cheap (lazy connections); and a per-origin resolver would require mirroring ReqLLM's ~35-entry provider `default_base_url` table (plus region templates for google_vertex/amazon_bedrock, empty default for azure, unknown `-m` providers) — fragile and version-coupled, for no correctness gain. `effective_concurrency/2` applies the `max(sum, default)` rule (unknown model ids are gated by `default_llm_max_concurrency` via `State.concurrency_for/2`, state.ex:206-208), and `desired_count/1` is the single source of truth for the boot formula (`config/runtime.exs` delegates to it, preserving the empty-profiles fallback to `default_llm_max_concurrency`). If per-origin refinement is ever wanted, design: per-origin count = `max(Σ concurrency of profiles with that origin + 2, 8)`; uniform boot count = max over origins of that (≤ total+2); unmapped/materialized origins fall back to the max per-origin load; plumbing requires passing the failing model id through `call_llm_with_retry` → `bump_for_excess_queuing` to target the right origin.
