# EvoGit Core Library — `lib/evo_git/`

## Intent
Core source of the `:evo_git` OTP application: the Agent system (LLM-powered tool-calling loops), AgentScheduler (GenServer for scheduling, ETS state, slot management — worktree lifecycle owned by `AgentScheduler.WorktreeManager`), Core domain types (ContextNode, PhyloGraphNode, ForeignRepo), Git adapter, and Runtime phases (Genesis, Evolution). Supports multi-repo operation — foreign repos configured via `genesis.toml` or CLI flags enable cross-repo subagent spawning into isolated worktrees.

## Routing Table
- `./agent/` → Agent behaviour, tool library, context compression, subagent processing, LLM error classification + retry/backoff policy
- `./agents/` → Agent implementations (Manager, Executor, TaskScheduler, Investigator, Architect, ContextExtractor, SkillExtractor, GenesisPlanner)
- `./agent_scheduler/` → AgentState, SchedMeta, Slots, Worktrees, WorktreeManager — ETS schemas, helpers, worktree lifecycle
- `./core/` → ContextNode, PhyloGraphNode, ForeignRepo data structures
- `./adapters/` → Git CLI adapter — all git operations go through this module
- `./runtime/` → Genesis, Evolution, PR helpers, Skill Extraction
- `./config/` → Unified 3-level configuration resolver (defaults → user TOML → runtime overrides), schema definitions, LLM catalog, platform detection, project config
- `./cli/` → CLI argument parsing (`EvoGit.CLI.Parser`), interactive setup wizard (`EvoGit.CLI.Setup`)
- `./custom_agents/` → `EvoGit.CustomAgents` store + `ModelSelector` (agents.toml + per-agent model-selection script)
- `./custom_tools/` → `EvoGit.CustomTools` + `EvoGit.CustomTools.Tool` behaviour — user-defined custom tools loaded from `<config_dir>/tools/` (`.ex`/`.exs`/`.beam`); detail in `custom_tools/CONTEXT.md`
- `./sandbox/` → Multi-platform sandbox backends (Linux systemd-run, Linux bwrap, macOS sandbox-exec, passthrough)
- **Background / detached job execution** (an agent starts a long-running command that must outlive the tool call) → `./background_jobs.ex` (`EvoGit.BackgroundJobs` registry: ids, output cursors, owner-pid lifetime) + `./sandbox/` (`EvoGit.Sandbox.Background`: detached spawn/kill/status, the boot sweep) + `./agent/tools/` (`bash`'s `run_in_background` + the `job_output`/`job_list`/`job_kill` tools)
- `./skills/` → Dynamic skill tools system — YAML-frontmatter markdown skills as LLM-callable tools
- `./store/` → Ecto persistence layer — Operations modules, Boot/migrations, RepoScope, schemas, Ecto.Types, Codec (the wire oracle), Errors, Writer — detail in `store/CONTEXT.md`
- `./task_registry/` → TaskRegistry support modules — Cleanup, Diagnostics, Lease, ResumeContext, RuntimeOpts, TaskExecutor
- **Owner identity from inside a tool call** (a tool task's fresh process dictionary; the ONE key it inherits, `$callers`, `SchedMeta.task_ref.pid`, `AgentScheduler.task_id_for_agent/1`) → detail: `./agent/CONTEXT.md` ("Tool-task owner identity") + `./agent_scheduler/CONTEXT.md` (ETS row shapes) + `./task_registry/CONTEXT.md` ("Task Lifecycle & Terminal-Write Sites")
- Supervised per-resource registry that must die with its OWNER process (`Process.monitor` in the registry, `:DOWN` = teardown) — pattern precedent: `EvoGit.SandboxProcessRegistry` (`sandbox_process_registry.ex`, GenServer state map, NO ETS, no name seam) + `EvoGit.TaskRegistry.server/0` (the `Process.get(:evogit_task_registry_server) || __MODULE__` test-isolation seam)
- **Supervision tree**: built INLINE in `EvoGit.Application.start/2` (`application.ex:84-132`) — there is **no `lib/evo_git/supervisor.ex`** module; `EvoGit.Supervisor` is only the root supervisor's registered NAME, and the nested agent group is `EvoGit.AgentGroupSupervisor` (`one_for_all`: `Task.Supervisor` named `EvoGit.TaskSupervisor` + `EvoGit.AgentScheduler`)

### SSH Remote Bootstrap — Auto-Download Flow
`EvoGit.RemoteConnection.bootstrap/1` does not require a local tarball (the `bootstrap/2` arity adds the `:on_running` opt — see safeguards). Sources in priority order: (1) `local_binary_path` set + exists → `scp` upload; (2) set-but-missing → `Logger.warning` + auto-download fallback (VS Code semantics); (3) absent → auto-download. A **silent pre-flight** runs before ANY staging on both paths: the daemon OS is resolved up front (target's optional `platform` field, else one `uname -s && uname -m` SSH call) and the running-daemon check fires (see safeguards). Stages — auto-download: `:probing_platform` → `:downloading` (remote `curl -fL`, remote `wget -O` fallback) → `:downloading_locally` (local curl into `<data_dir>/remote_binaries/<platform>_<version>.tar.xz` + `scp`) → `:extracting` → `:setting_permissions` → `:copying_config` → `:generating_cookie` → `:patching_binaries` → `:starting_daemon`; local-tarball: `:probing_platform` → `:uploading` → `:extracting` → ... same tail. The pre-flight-resolved OS is threaded through both paths — `:detecting_os` no longer exists as a stage. On NixOS remotes, bootstrap patches the extracted glibc release on the fly: after `:generating_cookie`, one SSH round trip runs `EvoGit.RemoteBootstrap.nixos_detect_command/0` (`test -d /etc/nixos` or `ID=nixos` in `/etc/os-release`); when NixOS is detected (Linux + daemon not already running — a live daemon is never patched) the `:patching_binaries` stage runs `nixos_patch_script/1` — one remote shell script `nix-build`ing `patchelf`/`bintools`/`stdenv.cc.cc.lib`/`openssl.out`/`zlib`/`ncurses`/`pcre2.out` from `<nixpkgs>` (GC-rooted under `<release>/.nixos-patch`; re-bootstraps instant), then patches each ELF binary three ways — interpreter + rpath for dynamic executables, rpath-only for shared libraries (NEEDED-deps probe via the built bintools readelf), skip truly static binaries. Non-NixOS/macOS remotes skip the stage; failures surface as `{:error, {:nixos_patch_failed, details}}`. Stage atoms `:probing_platform | :downloading | :downloading_locally | :stopping_daemon` (evo_dash `settings_live.ex` needs UI labels for these).

**Error tuples** (for tests): probe → `{:error, {:probe_failed, {:exit_status, n} | :timeout | {:unexpected_output, out}}}` or `{:error, :unsupported_platform}`; download → `{:error, {:download_failed, {:exit_status, n} | :timeout | {:local, detail} | {:local_scp, detail}}}`; platform override → `{:error, {:invalid_platform, p}}` / `{:error, :unsupported_platform}` (e.g. `windows_x64` — daemon launcher only supports Linux/macOS). `download_url/1` → `{:ok, url, "latest"}` (deterministic, keys the local cache).

**Notes**: `remote_connection.ex` is ~1880 lines — all pure logic lives in `remote_bootstrap.ex` (incl. `parse_unit_environment/1`, the unit-environment parser used by daemon-identity verification); the rest is ssh/scp/curl/wget orchestration + stage broadcasting + state transitions deliberately kept in `RemoteConnection`. `@bootstrap_call_timeout_ms` 900s, `@download_timeout_ms` 300s.

**Bootstrap/release safeguards**:
- Remote ssh commands are argv arrays, never quote-wrapped spawn strings: `run_ssh_command/3` uses `{:spawn_executable, ...}` + `{:args, [target, remote_cmd]}` (one argv element). `{:spawn, String}` with a quote-wrapped command breaks Windows bootstrap (CRT consumes only double quotes → single quotes reach remote bash as ONE command name → fails at `:extracting`) and the double-quote swap breaks Unix (spawn strings go through `/bin/sh -c` → local `$`-expansion). OpenSSH re-joins argv with single spaces so the command is preserved verbatim.
- **A running daemon is NEVER killed without explicit permission**: `bootstrap/2` takes `:on_running` ∈ `:refuse` (default) | `:restart`. The silent pre-flight (see flow above) resolves the daemon OS then checks `daemon_running?/3` BEFORE any staging: not running → normal flow; running + `:refuse` → `{:error, {:daemon_running, details}}` (details is a String naming the unit and the `on_running: :restart` escape hatch) with NO staging, NO kill, NO broadcast and the GenServer state untouched — the dashboard shows a permission dialog from this tuple; running + `:restart` → broadcasts the `:stopping_daemon` stage, stops the daemon (`systemctl --user stop genesis-remote-<id>` / `launchctl unload ~/Library/LaunchAgents/com.genesis.remote.<id>.plist`; a failed stop is non-fatal, the start surfaces real failures), then proceeds with the normal flow (a fresh daemon with the current contract). `maybe_start_daemon/6` + `verify_daemon_identity/4` remain as the RACE safety net for a daemon that appears between the pre-flight and the launch point — fail-loud on identity mismatch, never auto-kill.
- Every remote command is wrapped `/usr/bin/env bash -c '<escaped>'` via `EvoGit.RemoteBootstrap.bash_wrap/1` (embedded single quotes escaped `'\''`) — login-shell independent (required for NixOS hosts whose login shell is fish).
- `systemctl --user reset-failed` is run before launching the daemon (clears failed-unit state so a prior crash does not block launch).
- After launch, `verify_daemon_healthy/2` polls daemon readiness (3 retries × 1s).
- The `:copying_config` stage is a best-effort scp of the LOCAL config.toml + credentials.toml to the remote (`copy_config_to_remote/2`, remote_connection.ex:1000). Failure is non-fatal, and files that ALREADY EXIST on the remote are NEVER overwritten: per file, the local side probes `ssh <target> 'test -f <remote_file> && echo yes || echo no'` (`remote_file_exists?/2`, remote_connection.ex:1033) and skips the scp when the file is present — the skip decision is made LOCALLY, by the machine running bootstrap (not by the remote daemon). Only when the remote file is absent does the stage upload; for config.toml it uploads a locally-staged textual variant whose `[appearance] accent_color` is set to a deterministic-per-target palette color that differs from the local node's effective accent (`remote_accent_for/2` + `rewrite_config_accent/2`, remote_connection.ex:1157/1183; so the remote node is visually distinguishable in the dashboard), strictly best-effort with any failure falling back to scp'ing the unmodified local file. The target directory mirrors the remote daemon's `EvoGit.Platform.config_dir/1`: Linux/other `~/.config/genesis`, Darwin `~/Library/Application Support/genesis` (`remote_config_dir/1`, remote_connection.ex:1024; NOTE: the Darwin path contains a space and is neither shell-quoted in the `test -f` probe nor in the raw-string `scp` at remote_connection.ex:1130 — config copy to Darwin remotes is unreliable there). Behavior pinned by tests: `remote_connection_test.exs:1285` "existing remote config.toml is never overwritten by bootstrap" + `:1315` "fresh remote without config.toml receives an accent variant differing from the local accent".
- EPMD module for outbound distribution connects is `EvoGit.EpmdDist`, ensured via the idempotent `Distribution.ensure_epmd_module/0` (`@doc false`, `Application.put_env(:kernel, :epmd_module, EvoGit.EpmdDist)`): called at the top of the connect worker's `establish_tunnel_and_node/1` AND from `enable_for_remote/1`'s already-distributed branch; `enable_for_connection/0` also uses it before `:net_kernel.start/1` (the `-epmd_module` vm.args flag covers the release boot path). `net_kernel:epmd_module/0` reads the kernel env PER connection attempt (inet_tcp_dist fam_setup — not cached at net_kernel init), so flipping it after boot takes effect for the next outbound `Node.connect`. The BOOT path (`maybe_enable/0` → `enable_distribution/1`, config `[node] enabled=true`) deliberately does NOT set it: the local node registers with the REAL epmd daemon for inbound discovery; only outbound tunnel connects need EpmdDist's persistent-term registry (fed by `EpmdDist.register_target/2` right before `Node.connect`).
- Supervision order: `RemoteConnection.Registry` (unique, keyed by target id) + `RemoteConnection.Supervisor` (DynamicSupervisor, `restart: :transient`) start before the agent group; task persistence (`Store`/`TaskRegistry`) is supervised so the headless daemon has full task history.
- Distribution is NOT started at boot by default (`[node] enabled` unset/false) — enabled on-demand by `RemoteConnection`, or at boot via `Distribution.maybe_enable/0` when config `[node] enabled=true`; the remote daemon starts distributed at boot on port 9000 via `rel/vm.args.eex` (`-epmd_module Elixir.EvoGit.EpmdDist` + `-start_epmd false`).
- **Boot-time distribution is skipped in the test env**: `EvoGit.Application.start/2` gates the `Distribution.maybe_enable/0` call behind a compile-time `@mix_env != :test` attribute (same pattern as `sandbox/linux.ex`). Without it, a developer's real `~/.config/genesis/config.toml` (`[node] enabled = true`) makes the test BEAM attempt to start `:net_kernel`/EPMD and print `[warning] Failed to enable distribution: ... :nodistribution` at app boot — BEFORE `ExUnit.start/1`, so `capture_log: true` cannot catch it and no test-side redirect (XDG) can prevent it. The gate is inert outside tests (`:prod`/`:dev` ≠ `:test`); the gate lives at the CALL SITE, so `maybe_enable/0` stays fully functional/testable and its `distribution_test.exs` test remains meaningful. Tests needing distribution start it on demand via `enable_for_remote/1`.
- Release definitions live in the umbrella ROOT `mix.exs` (`genesis`/`genesis_desktop`/`genesis_remote`) — no `apps/evo_git/rel/` overlays; endpoint bind resolved in `config/runtime.exs` prod-only from `PORT`/`PHX_IP` → config.toml `[server] listen_port`/`listen_ip` (default 9999); orphaned-backend zombie prevention via dynamic port + `EVOGIT_LIFETIME_PORT` TCP pipe (see root `./CONTEXT.md`).

### Known Issues — Remote Daemon Cookie / Connect Failures (`node_connect_failed`)

- **Stale-daemon identity is caught at bootstrap** (`{:error, {:daemon_identity_mismatch, details}}`): the daemon's distribution identity (node name + cookie) is fixed at LAUNCH time (`--setenv=RELEASE_NODE`/`--setenv=RELEASE_COOKIE` on the transient systemd-run unit, or the launchd plist `EnvironmentVariables`), so a daemon launched by an older bootstrap — or started manually — keeps its stale cookie forever. `maybe_start_daemon/6` verifies an ALREADY-RUNNING daemon's launch identity via `verify_daemon_identity/4` (one SSH round trip: Linux `systemctl --user show <unit> -p Environment --value` parsed by `EvoGit.RemoteBootstrap.parse_unit_environment/1`; Darwin reads the deployed plist and string-contains the expected `RELEASE_NODE`/`RELEASE_COOKIE`; unknown OS → `:ok`) against the current contract (expected node = `remote_node_name(target)`, expected cookie = the `cookie` arg from `ensure_cookie!`, remote_connection.ex:1712) and FAILS LOUDLY. Missing keys, differing values, empty output (stale daemon, no env) and `:timeout` are all mismatches; `details` states found vs expected + exact remediation. The check now fires only as a RACE safety net — bootstrap's pre-flight decides the running-daemon policy BEFORE any staging (refuse by default, or `on_running: :restart`), so a stale daemon is never verified-and-left-running by a re-bootstrap. The safe replacement path is `bootstrap(target_id, on_running: :restart)` (broadcasts `:stopping_daemon`, stops the old daemon, starts a fresh one with the current contract; a plain `restart` re-runs the old unit Environment and does NOT help). Manual fallback: `systemctl --user stop genesis-remote-<id>` (Linux) / `launchctl unload ~/Library/LaunchAgents/com.genesis.remote.<id>.plist` (macOS), then re-run bootstrap. The cookie is per-MACHINE (persisted in each machine's config.toml) — bootstrapping from machine A and connecting from machine B cannot match unless B relaunches the daemon.
- **`Distribution.enable_for_connection/1` reads the config `[node] cookie`** (distribution.ex): reads `EvoGit.Config.resolve()[:node][:cookie]` — the SAME source the connect worker's `establish_tunnel_and_node/1` uses — and sets it after `:net_kernel.start` succeeds (nil/empty → skip + debug log, masked by `establish_tunnel_and_node`'s own `Node.set_cookie` before `Node.connect`). The RemoteConnections target schema has NO `:cookie` field.
- **`dist_port` ≠ 9000 never works**: the remote daemon is hard-pinned to port 9000 (`rel/genesis_remote/vm.args.eex:8`, `rel/vm.args.eex:17` — `-kernel inet_dist_listen_min 9000 inet_dist_listen_max 9000`); no code reads a `GENESIS_REMOTE_DIST_PORT` env var. The tunnel forwards to `Map.get(target, :dist_port) || 9000` (remote_connection.ex:427, schema default 9000); a target's `dist_port` edited to anything else forwards to a dead remote port and connect fails with the same error shape (`wait_for_tunnel` still passes — `ssh -L` accepts local connections even when the remote forward target is dead).
- **Outbound name resolution for tunnel connects on a boot-distributed local node**: when the local node is already distributed at connect time (config `[node] enabled=true` via `Distribution.maybe_enable/0`, or `-sname`/`-name`), the kernel `epmd_module` defaults to `erl_epmd` — an outbound `Node.connect` to a tunnel-registered name would ask the REAL epmd daemon for a port it never registered (`:noport` → connect `false` → `{:error, {:node_connect_failed, ...}}` with NO daemon-journal entry: the handshake never starts). The connect path prevents this: the connect worker's `establish_tunnel_and_node/1` and `enable_for_remote/1`'s already-distributed branch call `Distribution.ensure_epmd_module/0` so `port_please` resolves through EpmdDist's registry. Do NOT move the `epmd_module` set into the boot path — the local node must keep registering with the real epmd daemon for inbound discovery; outbound-only resolution is the design.

### Remote Bootstrap Asset Format

The SSH remote-bootstrap release asset is a **`.tar.xz`** archive: `genesis_remote_<platform>.tar.xz` (asset name, download URL, local cache path, remote temp file). Coordinated with `.github/workflows/build-desktop.yml`, which uploads `genesis_remote_<os>_<arch>.tar.xz` per platform (linux_x64 / linux_arm64 / darwin_arm64 / windows_x64). Extraction uses `tar -xJf` — needs xz-capable tar (all Linux distros with xz-utils; macOS bsdtar supports xz natively). No gz fallback — xz failure fails loudly. On NixOS hosts the glibc-linked tarball runs via on-the-fly patchelf patching during bootstrap (`nixos_patch_script/1`, `:patching_binaries` stage) — no new asset variants.

### SSH Tunnel Readiness (connect-path invariant)

The async connect worker's `establish_tunnel_and_node/1` must NOT call `Node.connect/1` before the SSH tunnel's local forwarded port accepts TCP connections.
An `ssh -L <local_port>:127.0.0.1:<dist_port> -N <target>` forward can take >1.5s to start listening; a too-early `Node.connect` fails instantly with econnrefused → `{:error, {:node_connect_failed, ...}}` with NO remote-side log entry (no remote daemon-journal entry ⇒ LOCAL-side failure — tunnel not ready, dead local forward target (`dist_port` ≠ 9000: the daemon is hard-pinned to 9000), or outbound name resolution — see the epmd_module bullet under "Known Issues" above; a cookie mismatch is the one failure that ALWAYS leaves a daemon-journal "Invalid challenge reply").
The connect path polls local-port readiness via `wait_for_tunnel/4` (`@tunnel_poll_interval_ms` 100ms, `@tunnel_wait_timeout_ms` 10s budget), failing fast when the ssh Port dies (draining its output into the error).
`wait_for_tunnel/4` is `@doc false` public solely for tests (`test/evo_git/remote_connection_test.exs`).

### Connect path (async, event-driven — non-blocking)

`connect/1` (`remote_connection.ex:285-290`) is NON-BLOCKING: it replies `{:ok, :connecting}` (or `{:ok, :connected}` when already connected) as soon as the connect is initiated and returns control to the caller immediately — there is no 25s `@connect_call_timeout_ms` call anymore (default 5s `GenServer.call`).
The blocking I/O — distribution auto-enable, `find_free_port`, the ssh spawn, `wait_for_tunnel/4`, `EpmdDist.register_target/2`, `Node.connect/1` — runs in a MONITORED + LINKED worker (`Task.start_link` from `handle_call(:connect, ...)` `:425-437`) so the manager stays responsive (`status/1`/`connected?/1`/`disconnect/1`/`list_connections/0`) for the whole connect; a busy 25s connect can no longer queue concurrent callers.
The GenServer remains the SINGLE owner of phase state: the worker never mutates state or broadcasts — it reports back via the internal message protocol `{:connect_result, worker_pid, {:ok, %{port:, local_port:, node_name:}}} | {:connect_result, worker_pid, {:error, message}}`, and every phase transition + broadcast happens in the `handle_info` `{:connect_result, ...}` / `:DOWN` handlers (`:521-568`).
On success the worker transfers the tunnel `Port` to the GenServer (`Port.connect/2`) BEFORE sending its result, so the tunnel survives the worker's exit; the manager records the port, arms the heartbeat and broadcasts `:connected`.
On failure the worker already closed its port; the manager stores the message as `last_error` and broadcasts `:error`.
A `:DOWN` for the current worker with no result having arrived means a crash → `:error` broadcast ("connect worker crashed: ...").
Lifecycle broadcasts on PubSub `"remote_connections"` use the unchanged shape `{:remote_connection_status, target.id, status_map}` — NO trailing node element (exception to the general node-carrying event contract; subscribed by `EvoDashWeb.LiveHooks.NodeAware`): `:connecting` on connect start (fired in `handle_call(:connect)` before the worker spawn — previously never broadcast), `:connected` on success, `:error` with `last_error` populated on EVERY failure arm (distribution failed / no free port / tunnel not ready / ssh exited / node connect failed / worker crash — all through the `fail_connect/2` choke point), `:disconnected` when `disconnect/1` aborts an in-flight connect.
Duplicate connects are idempotent: `handle_call(:connect, ...)` has a guard clause `when phase in [:connecting, :connected]` → prompt `{:ok, phase}` ack, NO second tunnel spawned, no state clobbering; a fresh connect retry from `:error`/`:disconnected` starts a new worker.
The ssh argv (`build_tunnel_command/2`, remote_connection.ex:2011-2028) carries `-o ConnectTimeout=8` (`@ssh_connect_timeout_ms` 8s, kept under the 10s `@tunnel_wait_timeout_ms` budget) so an unreachable/dead host fails inside the budget instead of hanging on the OS TCP timeout.
`disconnect/1` during `:connecting` (dedicated `handle_call(:disconnect, ...)` phase clause `:453-469`) kills the worker (`Process.exit(pid, :kill)` — the worker owns the tunnel port until success, so killing it closes the ssh), clears the worker bookkeeping, then runs the normal `cleanup/1` teardown → terminal `:disconnected` broadcast + `{:stop, :normal, ...}` (child spec `restart: :transient` → the manager is NOT restarted); if the worker already transferred the port, the manager's own termination closes it.
No app-env/clock test seams exist in remote_connection.ex (zero `Application.get_env`/`System.get_env` reads); tests fake the `ssh` executable on PATH (`with_fake_ssh_immediate_exit`/`with_fake_ssh_connect`, `remote_connection_test.exs`) and assert the prompt reply + broadcast lifecycle.
The dashboard consumes this contract through `EvoDash.NodeContext.connect/1` (apps/evo_dash, stateless passthrough to `EvoGit.RemoteConnection.connect/1`) — its callers must NOT block on it: connect initiation is always wrapped in a `EvoDash.TaskSupervisor` task from LiveView events (shared helper `EvoDashWeb.LiveHooks.NodeAware.initiate_remote_connect/2`), navigation happens optimistically, and terminal UI state (`:connected` / `:error` with `last_error` / `:disconnected`) arrives via the `"remote_connections"` PubSub broadcasts through `NodeAware.handle_connection_status/2`.

## Windows-Only Runtime Hazards (audit index)

Code that is latently Windows-broken because the Windows branch is unreachable on Linux/macOS dev+CI (`Platform.windows?()` gates) — each item is a raise/degradation, not a compile error.
Per-subsystem detail lives in the child CONTEXT.md files; this is the cross-cutting index.

- **`Port.open` `{:env, ...}` requires CHARLISTS** while `System.cmd/3` normalizes binaries itself (`validate_env/1` → `String.to_charlist/1`) — the ONE raw-port env site is `EvoGit.Sandbox.None`'s Windows clause (detail: `./sandbox/CONTEXT.md`); `bwrap`/`remote_connection` ports pass no `:env` at all.
- **`Port.info(port, :os_pid)` returns the TUPLE `{:os_pid, pid}` (never a bare integer) and `Port.close/1` RAISES `ArgumentError` on an already-closed port** (verified on this box, Elixir 1.20/OTP 29) — raw `Port.open/2` is NOT interchangeable with `System.cmd/3`; `Sandbox.Helpers.wait_for_os_pid/2` unwraps the tuple and every timeout path closes through the shared idempotent `Helpers.close_port/1`, so the Windows `taskkill /T /F` tree kill and bwrap's process-group kill do fire (detail: `./sandbox/CONTEXT.md`).
- **Tool-level raises are FATAL, not degraded**: `Agent.ToolDispatch.execute_tool_with_timeout/8` wraps each tool in a LINKED `Task.async` (verified: a raise kills the caller, `Task.yield/2` never returns), so its `{:exit, reason}` arm is dead code for raises — an unresolved executable or a wrong-typed arg (e.g. `timeout` as a string) crashes the agent instead of yielding an `Error: ...` string (detail: `./agent/tools/CONTEXT.md`).
- **`EvoGit.GitEnv` exports `GIT_EDITOR` as an UNQUOTED path** (`git_env.ex:80` + `derive_windows_true_exe/0`) — git hands the editor to `sh -c`, so the normal `C:\Program Files\Git\usr\bin\true.exe` is split at the space and every git operation that would open an editor aborts (detail: `./adapters/CONTEXT.md`).
- **`EvoGit.RemoteConnection`'s `run_cmd/2` spawn-string commands interpolate LOCAL paths unquoted** (`remote_connection.ex:1035` `"curl -fL -o #{cache_file} #{url}"`, `:1149`/`:1322`/`:1887` `"scp #{local_path} ..."`) where those paths come from `Platform.data_dir()`/`System.tmp_dir!()` — on Windows `C:\Users\<First Last>\AppData\...` splits at the space because `Port.open({:spawn, _})` is ONE command-line string re-parsed by the child, not argv (the argv-safe form already exists in `run_ssh_command/3`).
- **Those three `Port.open` sites pass no `:hide`** (`remote_connection.ex:704,1971,2001`) — on Windows each spawn may open a console window (Elixir's `System.cmd/3` always adds `:hide`).
- **`SystemCheck.check_tool/1` (`system_check.ex:289-291`)** passes `Executable.resolve/1`'s output straight to `System.cmd/3`, so a genuinely missing tool raises `ErlangError :enoent` (surfaced as a check error via the centralized rescue) instead of an "unavailable" result — `Executable.resolve/1` itself never returns a non-existent absolute path.
- **`EvoGit.Skills.Executor`'s Windows branch resolves bash only via `System.find_executable("bash")`** — MinGit (the vendored git under `<priv>/vendor/windows-x64/mingit/`) ships its POSIX shell as `sh`, NOT `bash.exe` (per Git for Windows' MinGit docs `/usr/bin/bash` is deliberately absent), and MinGit's directories are not on PATH in a desktop install, so bash skills degrade to the "install Git for Windows" error unless the user's own Git for Windows bash is on PATH (detail: `./skills/CONTEXT.md`).

## Executable Resolution (`EvoGit.Executable`)

`EvoGit.Executable.resolve/1` implements the system-first, bundled-fallback contract: a name found on the system PATH is returned UNCHANGED, so `System.cmd/3`'s own PATH/PATHEXT search runs; only when it is absent from PATH is a bundled candidate under `priv/vendor/<platform>/` considered. The bundled candidate is returned ONLY when it exists as a regular file — otherwise `resolve/1` returns the ORIGINAL name unchanged, so PATH search, `System.find_executable/1`, and the Windows known-location fallback (`EvoGit.Sandbox.None.resolve_windows_executable/1`: WINDIR/ProgramFiles PowerShell/pwsh) still apply and `System.cmd/3` behaves exactly like a plain `System.cmd(name, args, ...)`. `resolve/1` never returns a non-existent absolute path.

Pure `@doc false` helpers make this testable without a real Windows vendor layout: `candidates/3` (`name, vendor_dir, os_type` → candidate path list: Windows `git` → `<vendor>/mingit/cmd/git.exe`, other Windows names → `<vendor>/<name>.exe`, elsewhere → `<vendor>/<name>`) and `bundled_path/3` (first EXISTING candidate, else `nil`). Only the `git` MinGit layout and the plain `<name>`/`<name>.exe` vendor files are candidates — `resolve/1` never resolves a bundled bash (a bundled MinGit shell is not put on PATH and is not resolved through this module; see `./skills/CONTEXT.md`). Tests: `apps/evo_git/test/evo_git/executable_test.exs`.

## Review / RemoteNode Return-Shape Contract (remote-SSH payload analysis)

`EvoGit.RemoteNode` review wrappers return the **verbatim underlying value** of the `EvoGit.Review` function (local → `AgentScheduler.RemoteAPI` direct, remote → `:erpc` via `call_remote/4`); the ONLY added shape is `{:error, {kind, reason}}` on RPC failure (node down/timeout/remote raise). Arity note: RemoteNode functions are Review arity + 1 (leading `node` arg). **`defnode` convention (durable)**: new identity-unwrap RPC wrapper functions in `remote_node.ex` are declared via the `defnode` macro from `EvoGit.RemoteNode.Defnode` — `defnode EvoGit.AgentScheduler.RemoteAPI.some_fun(args)` — which generates the local-direct / `call_remote` identity-unwrap wrapper. Only functions whose remote branch is EXACTLY the plain `{:ok, r} -> r; {:error, e} -> {:error, e}` shape are macro-eligible; functions with per-function RPC failure fallbacks (`[]`/`%{}`/`nil`/`false`/`{:error, :rpc_failed}`, nested-error asymmetries) stay hand-written. `remote_node.ex` is ~1150 lines (post-condensation). **Every review/task wrapper is `defnode`-generated (no per-function fallbacks)** — none hardcodes the primary repo path; each takes an explicit `repo_path` argument from the caller (`set_review_status/3`, `set_review_metadata/4`, `get_file_content/4`, `list_commits/3`, `load_review_data/3`, `load_review_metadata/3`, `load_file_diff/5,6`, `load_review_metadata_from_shas/4`, `list_commits_from_shas/4`, `load_commit_files/3`, `load_commit_file_diff/4`, `merge_branch/3,4`, `check_merge/4`, `default_merge_target/2`, `list_branches/2`, `reject_branch/3`, `create_github_pr/5`, `github_upstream/2`, `list_github_issues/3`, `github_issue_markdown/3`, `branch_exists?/3`, `list_commit_graph/4`). Timeout for ALL of them is the shared `call_remote/4` → `rpc_timeout/0` (`Application.get_env(:evo_git, :remote_rpc_timeout, 30_000)`, read at CALL time). Struct shapes:

- **`%EvoGit.Review.FileInfo{}`** (review.ex:12-26): 8 fields — `:path` (String), `:status` (`"added" | "deleted" | "modified"`), `:additions`/`:deletions` (integers), `:diff` (String | nil), `:language` (highlight.js name, always populated), `full_new_content: nil`, `full_old_content: nil` — the `full_*` fields are NEVER populated by Review; the caller (evo_dash via `get_file_content/3`) fills them for whole-file highlighting.
- **`%EvoGit.Review.CommitInfo{}`** (review.ex:28-31): 6 fields — `:sha`, `:short_sha`, `:message` (subject line, `%s`), `:author_name`, `:author_email`, `:date` (`%DateTime{}` parsed from `%aI`, raw String fallback on parse failure).
- **Metadata maps** (`load_review_metadata/2`, `load_review_metadata_from_shas/3`, `load_commit_files/2`) share ONE shape: `{:ok, %{commit_sha: String, base_sha: String, diff_stat: String (git diff --numstat raw output), diff: nil, files: [%FileInfo{}] (diff: nil), changed_files_count: int, total_additions: int, total_deletions: int}}` | `{:error, {tag, output}}`. `load_review_data/2` is the payload-heavy variant: top-level `diff` = FULL combined `git diff`, each `FileInfo.diff` = `"diff --git " <> section`; NOT called anywhere in `apps/evo_dash` (only the `NodeContext` passthrough at node_context.ex:703; the review page uses metadata + lazy `load_file_diff`). `load_commit_files/2` diffs against `commit_sha~1`.
- **Diffs**: `load_file_diff/4,5` and `load_commit_file_diff/3` → `{:ok, diff_string}` | `{:error, {tag, output}}` (`:context` opt: int | `:all` → `-U999999` | nil = git default 3 lines). `get_file_content/3` → `{:ok, full_file_content}` | `{:error, {tag, output}}`.
- **Commits**: `list_commits/2` and `list_commits_from_shas/3` → ALWAYS `{:ok, [%CommitInfo{}]}` (empty list on git errors — the `{:error, _}` in the RemoteNode spec only occurs via RPC failure).
- **Commit graph** (`CommitGraph.for_ranges/3` → `RemoteAPI.list_commit_graph/3` → `RemoteNode.list_commit_graph/4`): ALWAYS `{:ok, %{commits: [commit], refs: %{sha => [ref_name]}}}` (never raises — bad ranges degrade to `[]`, a failed ref listing to `%{}`). Each `commit` is an atom-keyed MAP with the seven keys `:sha, :short_sha, :message, :author_name, :author_email, :date, :parents` (not a struct): `:date` is a `%DateTime{}` or `nil`, `:parents` a list of full SHAs (`[]` for a root commit). `refs` maps each returned commit SHA to its short branch/tag names.
- **Task-scoped commit graph** (`EvoGit.TaskCommitGraph.for_task/4` → `RemoteAPI.list_task_commit_graph/4` → `RemoteNode.list_task_commit_graph/5`, arity 5 = node + `task_id` + `repo_path` + `live_tips` + `opts`): the durable, WHOLE-TASK variant that keeps a recycled agent's history visible. `resolve_refs/1` (pure) / `resolve/1` (reads `TaskRegistry.get_task/1`, total — a corrupt row / dead registry degrades to `%{base_sha: nil, tips: [], project_path: nil}`) gather durable tips from the task row: `commit_sha`, `branch_name`, and every `result["repos"][repo_id]["commit_sha"|"branch_name"]` (the persisted `result` is the DECODED result — an `{:ok, data}` tuple — plus a bare data map is accepted; STRING/atom keys both handled; blanks/dupes dropped). ## Windows PowerShell Invocation — `-EncodedCommand`

**Why `-EncodedCommand`:** `powershell.exe -Command <script>` spawned from Erlang is broken by construction — PowerShell re-joins the raw command line and re-parses it as PowerShell code, so Erlang spawn quoting gets mangled; a lost script arg falls back to INTERACTIVE mode, exiting 0 with NO output on closed/EOF stdin. Secondary: PS 5.1 writes piped output via `[Console]::OutputEncoding` (OEM/UTF-16) — `EvoGit.UTF8.ensure_utf8/1` treats a UTF-16LE BOM as invalid UTF-8.

**Invocation:** spawn `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -EncodedCommand <b64>` where b64 = base64(UTF-16LE of `& { [Console]::OutputEncoding = [System.Text.Encoding]::UTF8; <script> } *>&1`). `-EncodedCommand` eliminates ALL command-line quoting/parsing; the OutputEncoding line forces UTF-8 output; `*>&1` merges all streams incl. Write-Host/information. No `<`/input redirection.

All pure logic lives in `EvoGit.Powershell` (lib/evo_git/powershell.ex), applied at: `Platform.shell_args/1` PowerShell clause (chosen from the effective shell — fixes ShellTool `run_powershell` AND `Worktrees.run_init_script/3` — both consume `Platform.shell_args`); `EvoGit.Sandbox.None` `run_windows/3` + `run_with_partial_windows/5` (defense-in-depth `transform_args/2` for any caller still passing `["-Command", cmd]`; `decode_output/1` on collected output — BOM-aware, idempotent). `transform_args/2` matches ONLY powershell/pwsh (any case, incl. `C:\...\powershell.exe` paths — backslash-normalized before `Path.basename`) with the exact 2-element `["-Command", cmd]` shape; already-encoded args and bash/git invocations pass through untouched (no double transform).

**Tests:** `apps/evo_git/test/evo_git/powershell_test.exs` (26 pure-module tests: `powershell_executable?/1`, `wrap_script/1`, `encode_command/1`, `invoke_args/1`, `transform_args/2`, `decode_output/1` — Linux-runnable, `async: true`). The `shell_args/1` test in `apps/evo_git/test/evo_git_test.exs` branches on `Platform.os()` (`:windows` → `EvoGit.Powershell.invoke_args/1`, else `["-c", cmd]`).

## Constraints
- All git operations must go through `EvoGit.Adapters.Git` — no direct `System.cmd("git", ...)` outside adapters.
- Agents are transient modules using `EvoGit.Agent` behaviour; persistent state lives in ETS.
- System prompts MUST NOT contain dynamic state, objectives, or context trees.
- Worktrees are created FRESH per agent run (no pool, no reuse across retries); the `WorktreeManager` GenServer owns lazy per-repo init, creation (via `Worktrees.prepare_new_worktree/5`), and monitor-driven reclaim/destruction.
- Agents commit before delegating subagents (auto-commit fallback enforced by scheduler).
- Tool outputs truncated at 128KB; agent loop has 30-min LLM budget with graduated warnings.
- Cross-repo subagents commit to their foreign repo's worktree — changes are NOT merged into the primary repo.
- 3-level configuration: `EvoGit.Config` merges defaults → user TOML → runtime overrides.

## Managed Per-Task Tmpdir & Reclaim Lifecycle (`EvoGit.TaskTmpdir`)

All agents of one task share ONE scratch directory (`task_<id>` under a node-local managed root), replacing the former behaviour where every BEAM wrote into the shared host `/tmp` (no isolation, no sweep). A per-task (not per-agent) scope is required because agents legitimately hand temp files to **sibling** agents via raw paths. The managed root (`managed_root/1`) is the ONE directory the module owns — `reclaim/2` NEVER deletes anything outside it and NEVER deletes the root itself.

**Sandbox TMPDIR seam**: `EvoGit.Sandbox.resolve_tmpdir/0` prefers `EvoGit.TaskTmpdir.current/0` when set, so every sandbox backend injects `TMPDIR=<task dir>` (and the runtime's own temp files target the per-task directory instead of the shared host tmp). The runner resolves the path once and calls `put_current/1`; the tool-dispatch layer reads `current/0` and re-installs it inside each spawned tool task — those tasks do NOT inherit the caller's process dictionary, so the value is threaded explicitly.

**Reclaim lifecycle** (owner: `EvoGit.TaskRegistry`; every reclaim is node-local — the managed root is per-BEAM, never shared across nodes). Reclaim is **event-driven ONLY** — there is NO boot reaper and NO periodic sweep:
- **Terminal transition** — `handle_update_status/6` is the dominant choke point (the wrapper result, the stuck-`:finalizing` watchdog, and startup reconciliation all flow through it) and reclaims on every terminal status. The direct terminal writes that BYPASS it carry their own reclaim call: `force_kill_task` (`:failed`), cancel of a `:pending` task (`:cancelled`), the `:lease_sweep` (`:failed`), and `resolve_recheck_task/3` on its successful terminal write.

A `task_<id>` dir orphaned by a full-runtime crash (no terminal status ever written) is NOT reaped automatically — it now requires manual cleanup. `TaskTmpdir.reclaim/2` never raises, so a reclaim can never crash the registry.

## First User Prompt Assembly
The `run/1` callback (injected by `use EvoGit.Agent`) assembles the agent's first user message as two XML-delimited blocks separated by a `---` rule — `<context>` (context_tree + `{authority_section}` + `{foreign_repos_section}` + `{repo_notes_section}`, each omitted when blank), then `<objective>` (`{objective}`, omitted when there is no objective).
Section bodies are produced by **`build_dynamic_context/1`**, **`build_authority_section/1`** (delegation-authority role line), **`build_foreign_repos_section/1`** and **`build_repo_notes_section/1`**.
Blank sections are dropped entirely — no dangling rules, empty headers, or empty XML blocks; `---` appears only between two non-blank blocks.
**Delegation-authority section** (`ContextBuilder.build_authority_section/1`, wired in `Runner.do_run/2` only — never inside `build_dynamic_context/1`): authoritatively states whether THIS agent is the **ROOT agent** (`AgentState.parent_id == nil` ⇔ `SchedMeta` depth 0 — exact by construction in `Dispatch.register_agent/7`; never the process-dict depth, which may not be populated at assembly time) or a **NESTED agent**, plus the foreign-repo spawn authority that role carries (ROOT may spawn write-capable `:read_write` foreign-repo subagents one at a time; NESTED may not and reports needed foreign-repo changes up to its parent).
Returns `""` for repo-less agents (the self-reflective chat persona must not read a task-role statement) and for tasks with no non-primary foreign repos (single-repo prompts stay token-neutral; mirrors `build_foreign_repos_section/1`'s empty-string convention, so the blank-filter drops it).
Static system prompts are role-agnostic by design and point to this dynamic statement ("Your first-user context states whether you are the ROOT or a NESTED agent...") — system prompts must NOT contain dynamic state, and only the first user message (built with the live `%AgentState{}` in hand) can truthfully state the agent's own role.

## Injected User Messages (mid-run, multimodal)

The ONLY external message-injection point is the drain at the TOP of `Runner.loop/1`: **`Runner.drain_and_inject_user_messages/1`** (public `@doc false` so it can be driven directly from tests — same convention as `refresh_commit_sha/1`/`maybe_enter_cancel_grace/1`; called only from `loop/1` in production) drains `AgentScheduler.Store.drain_pending_user_messages/1` and appends each drained message through the pure **`ContextBuilder.build_injected_message/2`**, turn-tagged, then syncs the context to ETS.

- **Entry points** (message = a legacy plain `String.t()` OR a `%{text:, attachments:}` map carrying images/audio): `EvoGit.AgentScheduler.send_user_message/2` (guard widened to binary OR map) → scheduler GenServer → the pending queue append; and `EvoGit.RemoteNode.send_agent_message/3` (node-first: local → `RemoteAPI.send_agent_message/2` directly, remote → `:erpc`). `EvoGit.Attachments.message/1` is the ONE normalizer and canonicalization happens in the QUEUE (Phase 2B owns that append + the `pending_user_messages` type widening); the injection entry points pass the message through verbatim.
- **Materialization** (`build_injected_message(message, turn)`): a legacy binary or a map whose attachments are `nil`/`[]` → `ReqLLM.Context.user(text)` (byte-identical to the legacy injection path); a map carrying attachments → `ReqLLM.Context.user(Attachments.to_content_parts(text, attachments))` = `[ContentPart.text(text) | image/file parts…]`. `turn` integer → turn-tagged via `tag_message_turn/2` (+ creation timestamp); `nil` → the raw untagged message. Malformed message maps raise a descriptive `ArgumentError` (spec-error style).
- **NO root gate** on injected messages: an agent at ANY depth may receive media this way. The root-only gate stays on the `:attachments` TASK OPT (the initial user message only — `build_initial_messages/4`).

## ReqLLM Finch Pool Reconciliation (`EvoGit.ReqLLMPool`)

`lib/evo_git/req_llm_pool.ex` — dynamic runtime reconciliation of the ReqLLM Finch HTTP pool (`ReqLLM.Finch`), fixing the "Finch was unable to provide a connection within the timeout due to excess queuing" RuntimeError (deps/finch/lib/finch/http1/pool.ex:81-90) that occurs when runtime concurrency outgrows the boot-time pool size.

**Public API:** `desired_count(total)` → `max(total + 2, 8)` (single source of truth — `config/runtime.exs` delegates to it); `error_target_count(total)` → `max(ceil(total * 1.5), 8)`; `effective_concurrency(model_concurrency_map, default)` → `max(sum of map values, default)` for non-empty maps, falls back to `default` for empty/nil; `reconcile(total, finch \\ ReqLLM.Finch)` → grow pools to `desired_count`; `bump_for_excess_queuing(model_concurrency_map, default, finch \\ ReqLLM.Finch)` → grow pools to the 1.5x target; `excess_queuing_error?(reason)` → matcher for the Finch error (bare `%RuntimeError{message}` with "excess queuing", `%ReqLLM.Error.API.Stream{reason, cause}` inspecting to it, or inspect-fallback like `TruncationFeedback.is_rate_limit_error?/1`).

**Grow-only semantics (MANDATORY):** `Finch.set_pool_count/3` grows by `Supervisor.start_child`-ing new pool processes (safe) but shrinks by `terminate_child` (kills in-flight streams) — `EvoGit.ReqLLMPool` NEVER shrinks (`max(current, desired)` per origin). All public functions never raise; `{:error, :not_found}` (no materialized origins) is a graceful no-op.

**Enumeration & the `start_pool_metrics?` requirement (CRITICAL):** pools are materialized LAZILY per origin on first request. `Finch.get_pool_status(finch, :default)` returns `{:ok, %{%Finch.Pool{} => [%Finch.HTTP1.PoolMetrics{}, ...]}}` — but ONLY for pools whose config has `start_pool_metrics?: true` (deps/finch finch.ex:98-102 default `false`; pool/manager.ex:216 `track_default? = pool_config.start_pool_metrics? and not Map.has_key?(config.pools, pool)`). Without the flag, `get_pool_status(:default)` always returns `{:error, :not_found}` → reconciliation is a **silent no-op**. `config/runtime.exs` uses the full `finch:` override form (`config :req_llm, finch: [name: ReqLLM.Finch, pools: %{default: [protocols: [:http1], size: 2, count: stream_pool_count, start_pool_metrics?: true]}]`, runtime.exs:66-78), production `ReqLLM.Finch` has the flag. Per-origin capacity = `count × 2` concurrent HTTP/1 streams. Shard selection across pool processes is **RoundRobin** via ReqLLM's top-level `stream_pool_strategy` config key (`{Finch.Pool.Strategy.RoundRobin, round_robin}` — an `:atomics` ref created at config-eval time in runtime.exs; read per request as the `pool_strategy` opt at call time, streaming/finch_client.ex:426-428 — NOT a pool-template key, NimbleOptions would raise). `stream_pool_timeout: 300_000` stays top-level (Finch checkout/pool-queue wait, read at CALL time via `Application.fetch_env(:req_llm, :stream_pool_timeout)`, streaming/finch_client.ex:299-305). Tests use their own Finch with the flag set.

**Two triggers (both wired):**
1. **Config change** — `AgentScheduler.handle_call({:update_config, opts}, ...)` (agent_scheduler.ex:849-858): the `{:reply, :ok, new_state}` path (via private `reconcile_pool_after_update/1`, agent_scheduler.ex:979-988) computes `effective_concurrency(new_state.model_concurrency, new_state.default_llm_max_concurrency)` and calls `reconcile/2`. Covers ALL config-change routes (RemoteAPI.reload_config, save_user_config, evo_dash ConfigIO). The `{:error, "llm_model cannot be nil"}` path never reconciles. `State.do_update_config/2` (state.ex:313-425, pure) always returns `{:reply, :ok, state}` → single-clause helper total.
2. **Excess-queuing error** — `ToolDispatch.run_llm_attempt/4` (tool_dispatch.ex): inside the per-attempt `AgentScheduler.with_llm_slot/2` body, the inner `with`'s `{:error, reason}` branch runs `if EvoGit.ReqLLMPool.excess_queuing_error?(reason), do: EvoGit.ReqLLMPool.bump_for_excess_queuing(AgentScheduler.get_config(:model_concurrency), AgentScheduler.get_config(:default_llm_max_concurrency))`. No `report_llm_error` for this — the bump IS the fix. `AgentScheduler.get_config/1` from the agent process is safe (pure state reads, no slot contention).

**Tests:** `test/evo_git/req_llm_pool_test.exs` (16 tests, `async: false`) — pure-function tests + real-tiny-Finch grow/grow-only/`:not_found`-grace tests (test Finch started with `start_pool_metrics?: true`, `pools: %{default: [size: 1, count: 2]}`; origin materialized via a request to a closed port, `http://127.0.0.1:1/`). Scheduler smoke test in `test/evo_git/agent_scheduler/agent_scheduler_test.exs` (update_config → :ok, no crash; model_concurrency keys are STRINGS, `%{"default" => 3}`).

## Per-Origin Pool Semantics & Sizing Rationale

**Per-origin (scheme://host:port) pools, all from the single `:default` template.**

- **Pool identity = `{scheme, host, port, tag}`** — `Finch.Pool.to_name/1` (deps/finch/lib/finch/pool.ex:143); path prefixes (e.g. `/v1`) are NOT part of the key. Request dispatch: `Finch.get_pool/3` → `Finch.Pool.from_name(...)` (finch.ex:1036-1044) → `Pool.Manager.get_pool` (manager.ex:96-99) → lazy `maybe_start_pool`/`start_pool` on Registry miss (manager.ex:130-140, 214-230) → `pool_config(config, pool) = Map.get(config.pools, pool, default_pool_config)` (manager.ex:232-236). ReqLLM's pools map contains ONLY `:default` (req_llm application.ex:101-109; the runtime.exs `finch:` override pops `:default` at finch.ex:374) — every origin materializes lazily from the same `:default` template: one pool supervisor + `count` NimblePool shards per distinct origin.
- **`Finch.get_pool_status(finch, :default)` = per-origin enumeration** (finch.ex:1082-1099): `Pool.Manager.get_default_pools` → `Registry.lookup(registry, :default)` (manager.ex:181-184) → `%{%Finch.Pool{} => [per-shard metrics]}` (map key = origin; list length = that origin's shard count). Requires `start_pool_metrics?: true` (manager.ex:216; pool/supervisor.ex:17-19).
- **`Finch.set_pool_count(finch, pool_id, count)` is per-origin** (finch.ex:1202-1205): `resolve_pool` → `Pool.Manager.set_pool_count` (manager.ex:201-210) → unique Registry keyed `{scheme,host,port,tag}` (manager.ex:144-161) → `Finch.Pool.Supervisor.set_count` (supervisor.ex:29-55: grow = `start_child`, shrink = `terminate_child`). **Only the addressed origin's pool changes.** `{:error, :not_found}` until that origin has been materialized by at least one request (finch.ex:1194-1195) — why boot-time `reconcile` is a graceful no-op and `ReqLLMPool.grow_pools_to` keys `set_pool_count` by the `%Finch.Pool{}` structs from `get_pool_status/2` (req_llm_pool.ex:204).
- **ReqLLM never selects a pool explicitly per request.** `Retry.stream` passes only `[:pool_timeout, :receive_timeout, :request_timeout, :pool_strategy]` to `Finch.stream/5` (retry.ex:33-34; finch_client.ex:251-258). There is no `:pool` request option in Finch — the pool is always derived from the request's scheme/host/port (finch.ex:1036-1044). ReqLLM rewrites the request's `pool_tag` — to `{:req_llm, tag, hash}` of the connection-pool options — only when `req_http_options[:connect_options]` is set (finch_client.ex:289-291), and `request_pool/1` (finch_client.ex:532-537) derives the pool from scheme/host/port plus that tag; EvoGit never sets connect options, so every request uses tag `:default`.

**How many origins does EvoGit produce?** One per distinct base_url host among the `[[llm.models]]` profiles (path prefixes ignored). Profile `model` is a string `"provider:model"` (origin = provider's ReqLLM default host: openai → `api.openai.com:443`, anthropic → `api.anthropic.com:443`, ollama → `localhost:11434`) or a map `%{provider:, id:, base_url:}` (schema.ex:323/374; llm_catalog.ex:335-338 — per-profile `base_url` supported). Multiple profiles sharing a host share ONE pool. Typical configs: 1-4 origins.

**Sizing correctness — SUM formula `max(total + 2, 8)` applied uniformly per origin:**
- Per-origin capacity = `count` × `size` (= `count` × 2 here, size=2) concurrent HTTP/1 streams; `size` is a LAZY upper bound, not a reservation (finch.ex:55-68; http1/pool.ex:33 `lazy: true` — connections open on first checkout).
- **Slot-gated demand on origin O = D(O) = Σ concurrency of profiles targeting O ≤ total = Σ all profile concurrencies.** Since the pool for O is sized to `total + 2 ≥ D(O) + 2`, the SUM-based uniform formula **never under-provisions slot-gated demand**: summing is the provably sufficient upper bound (equality when all profiles share one origin). The `+2` covers the two non-slot-gated auxiliary call sites (system_check.ex:344, pull_request.ex:153).
- **Over-provisioning (the real cost of summing):** N single-profile origins each get `total+2` shards instead of `c_i+2` (waste `total − c_i` shards per origin). **Practically harmless**: shards are cheap, connections lazy (no sockets until checkout); Finch's docs recommend the lowest `count` that meets needs, erring safe (finch.ex:36-41). The 1.5× error bump (`error_target_count`) over-provisions similarly — also harmless.
- **Error path cannot identify the failing origin**: `%ReqLLM.Error.API.Stream{}` carries only `[:reason, :cause]` (req_llm error.ex:313-323) and the Finch RuntimeError message is static (http1/pool.ex:81-90 — no host/port). The origin is recoverable only at the call site (the agent knows `current_model()`), but `bump_for_excess_queuing/3` (tool_dispatch.ex:210-214) doesn't pass it — so the bump is necessarily uniform today.

**Design decision — the uniform SUM formula is kept.** It is provably sufficient for slot-gated demand; over-provisioning is cheap (lazy connections); and a per-origin resolver would require mirroring ReqLLM's ~35-entry provider `default_base_url` table (plus region templates for google_vertex/amazon_bedrock, empty default for azure, unknown `-m` providers) — fragile and version-coupled, for no correctness gain. `effective_concurrency/2` applies the `max(sum, default)` rule (unknown model ids are gated by `default_llm_max_concurrency` via `State.concurrency_for/2`, state.ex:206-208), and `desired_count/1` is the single source of truth for the boot formula (`config/runtime.exs` delegates to it, preserving the empty-profiles fallback to `default_llm_max_concurrency`). If per-origin refinement is ever wanted: per-origin count = `max(Σ concurrency of profiles with that origin + 2, 8)`; uniform boot count = max over origins of that (≤ total+2); unmapped/materialized origins fall back to the max per-origin load; plumbing requires passing the failing model id through `call_llm_with_retry` → `bump_for_excess_queuing` to target the right origin.

## SystemSampler — System Topic Sampling (`EvoGit.SystemSampler`)

`apps/evo_git/lib/evo_git/system_sampler.ex` — a supervised GenServer (child of `EvoGit.Application`, runs on EVERY node incl. the headless `genesis_remote` daemon) sampling scheduler status every 3s and broadcasting on `EvoGit.PubSub` topic `"system"`, so the dashboard (local AND remote) renders charts from pushes instead of polling.

- **Event contract**: `{:system_sample, node, seq, sample}` every tick — `node` = `node()` (sampling is LOCAL-only, no RPC), `seq` = monotonically increasing integer per sampler instance. Sample map keys EXACTLY (no extras): `llm_slots, llm_used, llm_waiting, tool_used, tool_waiting, llm_capacity, tool_capacity, agents_total, agents_running, agents_blocked, agents_waiting, agents_pending, scheduler_alive`. `llm_slots` = `%{model_id => %{used, waiting, capacity}}` — REAL per-model LLM slot occupancy (holder count / queue length / effective capacity), read live per tick via a BOUNDED 2s scheduler `GenServer.call` (`:get_llm_slot_status`, seam `:system_sampler_llm_slots_fun` — see the busy-scheduler bullet below); `%{}` when the scheduler is down or that tick's bounded call fails.
- **Tick**: `Process.send_after(self(), :sample_tick, interval)` self-message; interval = `Application.get_env(:evo_git, :system_sample_interval_ms, 3000)`, read ONCE at init (tests set it high, e.g. 86_400_000, and drive ticks synchronously via `EvoGit.SystemSampler.tick/0` — a `GenServer.call` — or by sending `:sample_tick` directly); the tick is rescheduled BEFORE sampling so a slow step never breaks cadence.
- **Local-only sampling**: per tick the sampler reads the local `:evogit_sched_meta` ETS table directly (same guarded `:ets.whereis` pattern as RemoteAPI's private `read_table/1`) and counts `meta.status` — the status source `RemoteAPI.build_agent_summary/3` uses for the summary `:status` field; `status_counts/1` reproduces the `total/running/blocked/waiting/pending/ready` grouping (unknown statuses → `:unknown` bucket). Proxy semantics: the aggregated `llm_used`/`llm_waiting` keys and both tool keys keep `:running` = slot-use proxy, `:blocked` = waiting signal (backward compat). REAL per-model LLM slot holders ARE now observable — via the scheduler GenServer read `EvoGit.AgentScheduler.get_llm_slot_status/0` (per model: `used` = true holder `MapSet.size`, `waiting` = true `:queue.len`, `capacity` = `State.concurrency_for/2` effective capacity incl. peak-pause `0`), fetched live per tick into the sample's `llm_slots` key. The read lives on the AgentScheduler GenServer itself, NOT `RemoteAPI` (that surface stays intentionally ETS-pure).
- **Capacity totals & the 10-tick config cache**: `llm_capacity` = Σ per-profile `concurrency`, `tool_capacity` = `max_tool_concurrency`. Source: a direct BOUNDED scheduler `GenServer.call` for `:get_config` — 2s timeout through `safe_scheduler_call/1`, default fetch = the sampler's own `config_fetch/0` (test seam `:system_sampler_config_fun`), deliberately NOT `RemoteAPI.get_config/0` (its implicit 5000 ms timeout is exactly the crash this module must not inherit) — the RESOLVED config map incl. runtime overrides (dashboard saves / `RemoteAPI.reload_config` / `PeakHourEngine` applies via `AgentScheduler.update_config/1` — never the CLI, which makes no scheduler overrides); `Config.resolve/0` would re-read disk and MISS runtime overrides — the GenServer call is the cheapest in-process resolved-config read. Cached in sampler state (`config_cache: {totals, tick}`), refreshed on the `rem(tick, 10) != 1` rule — tick 1 always loads; an unloaded cache refetches on any tick until the first attempt succeeds OR fails (a failure stores the `{:failed_at, tick}` marker, deferring retries to the refresh cadence). The refetch is additionally gated on `Process.whereis(EvoGit.AgentScheduler) != nil` (no `GenServer.call` into a dead process); a dead process keeps the last-known totals.
- **Busy-scheduler degradation (a live-but-wedged scheduler must not crash the sampler)**: both scheduler reads run through `safe_scheduler_call/1` — an explicit `@scheduler_call_timeout_ms` 2s bound (deliberately < the 3s tick cadence, so a wedged scheduler costs at most ONE degraded sample) plus `catch :exit` (the call timeout, the whereis→call `:noproc` race, or a mid-call server crash) — the module's single justified cross-GenServer try/catch, mirroring `PeakHourEngine.safe_get_config/2`. Production crash history: a wedged systemd user bus stalled the scheduler ~7s inside a config update; the sampler's uncaught default-5000ms call timed out and crash-looped it. A config-refresh failure KEEPS the last cached totals (never nils the cache); with no cache yet the `{:failed_at, tick}` marker defers the retry to the regular 10-tick cadence (no per-tick hammering) and `cached_totals/1` maps the marker to the zero fallback — the sample still broadcasts with the exact 13-key shape. An `llm_slots` fetch failure broadcasts `llm_slots: %{}` for that tick. Failures log a RATE-LIMITED clear `Logger.warning` (`warn_rate_limited/4` — at most once per 10 ticks per failure kind; last-warn ticks live in state). Recovery is automatic on the next successful tick. Test seams (read per call): `:system_sampler_config_fun`, `:system_sampler_llm_slots_fun`.
- **Dead-scheduler branch**: when `scheduler_alive?/0` is false (`Process.whereis(EvoGit.AgentScheduler) != nil or :ets.info(:evogit_sched_meta) != :undefined` — same liveness gate as the dashboard's `scheduler_alive?/1`) the sample has zero counts, zero capacities AND `llm_slots: %{}` with `scheduler_alive: false`; zero capacities are NEVER cached (caching them would suppress the refresh for 10 ticks after the scheduler returns). Broadcasts continue.
- **Ring buffer**: last 60 samples in state (`push/3`, oldest dropped). `get_recent_samples/0` → `{:ok, samples}` | `{:error, :not_found}` (guarded by `Process.whereis(__MODULE__)` — converts the `:noproc` exit into a returned error, per the no-try/rescue policy).
- **RPC surface**: `RemoteAPI.get_recent_system_samples/0` (remote_api.ex:75) checks `Process.whereis(EvoGit.SystemSampler)`: not running → `{:error, :sampler_down}`; running → delegates to `get_recent_samples/0` → `{:ok, samples}` (or `{:error, :not_found}` in the whereis→call race). `RemoteNode.get_recent_system_samples/1` (remote_node.ex:94-114, FINAL) routes local → RemoteAPI direct / remote → `:erpc` and passes the three shapes through verbatim.

## SandboxSlice — Bounded systemctl Slice Updates (`EvoGit.SandboxSlice`)

`apps/evo_git/lib/evo_git/sandbox_slice.ex` — owns the live `evogit.slice` resource-limit property writes (`systemctl --user set-property evogit.slice CPUWeight=… MemoryMax=… TasksMax=…`) for systemd-run sandboxing; started in `EvoGit.Application` on Linux whenever the systemd backend is selected (all real-execution paths gate on `@mix_env == :test` first — disabled path in tests).
- **Every systemctl invocation is time-bounded**: `run_systemctl_bounded/4` (`@doc false`, public for tests) runs the command in a separate unlinked MONITORED process with a hard `@systemctl_timeout_ms` 5000ms bound (app-env seam `:sandbox_slice_systemctl_timeout_ms`, read per call); on timeout the runner process is killed — closing its OS ports terminates the client-side subprocess (safe for set-property: a single DBus invocation, idempotent last-write-wins, no partial-limit corruption) — and `{:error, :timeout}` is returned; a raising runner returns `{:error, {:runner_crashed, reason}}`. Runner seam: `:sandbox_slice_systemctl_fun` (default `EvoGit.Sandbox.Helpers.system_cmd/2`).
- **Two client entry points**: `update_resources/1` (synchronous 10s `GenServer.call`, kept for direct callers, now internally bounded) and `update_resources_async/1` (fire-and-forget `GenServer.cast`, `:ok` even when the GenServer is not running; the `handle_cast` stores the resources and applies them only while `state.slice_active`, logging its own success/failure).
- **Scheduler integration**: `AgentScheduler`'s config-update path propagates `:sandbox_resources` via `update_resources_async/1` — the scheduler NEVER blocks on slice work (a synchronous update stalled the scheduler ~7s on a wedged systemd user bus in production; design note: `agent_scheduler/CONTEXT.md`).
- The slice itself is created at SandboxSlice init and by `ensure_slice` before every sandboxed run (`sandbox/linux.ex`); property updates only ever write absolute limits on an already-active slice — never create or stop it.

## Peak/Off-Peak Diagnostics (diagnosing a task that stays blocked after peak exit)

Scenario: a profile has `concurrency: 5`, `peak_concurrency: 0` (hard pause) and peak windows (e.g. 09:00–12:00 + 14:00–18:00); a task launched in-window blocks (0 LLM slots → request enqueues, agent `:blocked`), and after 18:00 it stays blocked. The logging below (all `Logger`, all in the `PeakHourEngine` / `AgentScheduler` prefix style) makes the four failure classes distinguishable: **engine never woke** / **woke but didn't apply** / **applied but waiter never granted** / **waiter granted but agent stuck elsewhere**. Read the log lines in this order:

1. **`PeakHourEngine: wakeup reason=... now=... utc_now=... scheduler_up=...`** (info, `peak_hour_engine.ex` `run_check/2` — every check). `reason` = `:boot | :timer | :broadcast | :manual` (threaded into `run_check` for logging ONLY — no timing/floor/fixed-point impact). Missing 18:00 `:timer` wakeup ⇒ engine never woke (dead timer / wrong transition math).
2. **`PeakHourEngine: decision=applying|unchanged effective=... current=...`** (info, `run_check/2`). `unchanged` right after 18:00 with `effective=%{"m" => 5} current=%{"m" => 5}` ⇒ engine woke but computed nothing new (map already 5 — look at the *previous* apply). `applying` with `effective=%{"m" => 0}` ⇒ the engine thinks it is still in peak — clock/window/timezone bug, check the wakeup clocks.
3. **`PeakHourEngine: next wakeup in <ms>ms ... transitions=[{id, tz, wall_transition}]`** (info, `log_next_wakeup/4`) — per-profile next in-peak transition wall-clock times; a "next_transition returned 09:00 tomorrow instead of 18:00 today" is visible here. The 6h safety-net fallback is explicitly flagged when no transition was computable.
4. **`AgentScheduler: model_concurrency updated — old=... new=... skip_floor=... default_llm_max_concurrency=...`** (info, `agent_scheduler.ex` `log_model_concurrency_update/3`) — fires on every `update_config(model_concurrency:)` incl. the engine's apply; shows the POST-application (post-floor / verbatim-for-skip_floor) map. `old=%{"m" => 0} new=%{"m" => 0}` right after 18:00 ⇒ the apply never happened (see 2); `new=%{"m" => 5}` ⇒ capacity WAS restored.
5. **`AgentScheduler: LLM slot grant sweep (resume) — model=... capacity=... waiting_before=... granted=... waiting_after=...`** (info on meaningful events, `slots.ex` `grant_pending_on_resume/1`; debug on empty no-op sweeps) — per-model sweep on every config update / resume. `capacity=5 granted=0 waiting_after=N>0` is exactly **"applied but queued waiter never granted"** (queue survived the sweep). `granted=N` ⇒ the sweep unblocked N waiters (per-agent `granted LLM slot` lines are `debug`).
6. **`PeakHourEngine: starting — watched profiles: ...`** (info, `init/1` `log_boot_profiles/0`) — boot-time per-profile summary (id, concurrency, peak_concurrency, peak_hours, timezone) so a misconfigured profile is visible immediately.

Debug-level per-agent events (`slots.ex`): `LLM slot request ENQUEUED — agent=... model=... capacity=0 (peak pause)` at the 0-capacity enqueue point (`do_handle_request_llm_slot/4`), `granted LLM slot — agent=... model=...` at each queue grant (`grant_llm_from_queue/2`), and `purged N LLM waiter(s) for model ...` at each cancel/force-kill purge (`purge_llm_waiting_queues/2`, the "rejected" counterpart). `PeakHourEngine: scheduling 6h safety-net wakeup` (info) marks the no-profiles / scheduler-down path.

Logging-only by design: `EvoGit.PeakHours` (the pure module) is untouched — all logging lives at the engine/scheduler call sites; no behavior, timing, floor, fixed-point, or slot semantics changed. Tests pin the fixed-point invariant (no "applied model concurrency" log on no-op re-checks) in `peak_hour_engine_test.exs`.
