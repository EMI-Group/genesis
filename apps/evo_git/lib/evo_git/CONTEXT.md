# EvoGit Core Library — `lib/evo_git/`

## Intent
Core source of the `:evo_git` OTP application: the Agent system (LLM-powered tool-calling loops), AgentScheduler (GenServer for scheduling, ETS state, slot management — worktree lifecycle owned by `AgentScheduler.WorktreeManager`), Core domain types (ContextNode, PhyloGraphNode, ForeignRepo), Git adapter, and Runtime phases (Genesis, Evolution). Supports multi-repo operation — foreign repos configured via `genesis.toml` or CLI flags enable cross-repo subagent spawning into isolated worktrees.

## Routing Table
- `./agent/` → Agent behaviour, tool library, context compression, subagent processing, LLM error classification + retry/backoff policy, tool-name alias spine (`tool_names.ex`), completion protocol (`completion_protocol.ex`)
- `./agents/` → Agent implementations (Manager, Executor, TaskScheduler, Investigator, Architect, ContextExtractor, SkillExtractor, GenesisPlanner)
- `./agent_scheduler/` → AgentState, SchedMeta, Slots, Worktrees, WorktreeManager — ETS schemas, helpers, worktree lifecycle
- `./core/` → ContextNode, PhyloGraphNode, ForeignRepo data structures
- `./adapters/` → Git CLI adapter — all git operations go through this module
- `./runtime/` → Genesis, Evolution, PR helpers, Skill Extraction
- `./config/` → Unified 3-level configuration resolver (defaults → user TOML → runtime overrides), schema definitions, LLM catalog, platform detection, project config
- `./cli/` → CLI argument parsing (`EvoGit.CLI.Parser`), interactive setup wizard (`EvoGit.CLI.Setup`)
- `./custom_agents/` → `EvoGit.CustomAgents` store + `ModelSelector` (agents.toml + per-agent model-selection script)
- `./custom_tools/` → `EvoGit.CustomTools` + `EvoGit.CustomTools.Tool` behaviour — user-defined custom tools loaded from `<config_dir>/tools/` (`.ex`/`.exs`/`.beam`); detail in `custom_tools/CONTEXT.md`
- `./sandbox/` → Multi-platform sandbox backends (Linux systemd-run, Linux bwrap, macOS sandbox-exec, passthrough)
- **Background / detached job execution** (an agent starts a long-running command that must outlive the tool call) → `./background_jobs.ex` (`EvoGit.BackgroundJobs` registry: ids, output cursors, owner-pid lifetime) + `./sandbox/` (`EvoGit.Sandbox.Background`: detached spawn/kill/status, the boot sweep) + `./agent/tools/` (`bash`'s `run_in_background` + the `job_output`/`job_list`/`job_kill` tools)
- `./skills/` → Dynamic skill tools system — YAML-frontmatter markdown skills as LLM-callable tools
- `./store/` → Ecto persistence layer — Operations modules, Boot/migrations, RepoScope, schemas, Ecto.Types, Codec (the wire oracle), Errors, Writer — detail in `store/CONTEXT.md`
- `./task_registry/` → TaskRegistry support modules — Cleanup, Diagnostics, Lease, ResumeContext, RuntimeOpts, TaskExecutor
- **Owner identity from inside a tool call** (a tool task's fresh process dictionary; the ONE key it inherits, `$callers`, `SchedMeta.task_ref.pid`, `AgentScheduler.task_id_for_agent/1`) → detail: `./agent/CONTEXT.md` ("Tool-task owner identity") + `./agent_scheduler/CONTEXT.md` (ETS row shapes) + `./task_registry/CONTEXT.md` ("Task Lifecycle & Terminal-Write Sites")
- Supervised per-resource registry that must die with its OWNER process (`Process.monitor` in the registry, `:DOWN` = teardown) — pattern precedent: `EvoGit.SandboxProcessRegistry` (`sandbox_process_registry.ex`, GenServer state map, NO ETS, no name seam) + `EvoGit.TaskRegistry.server/0` (the `Process.get(:evogit_task_registry_server) || __MODULE__` test-isolation seam)
- **Supervision tree**: built INLINE in `EvoGit.Application.start/2` (`application.ex`) — there is **no `lib/evo_git/supervisor.ex`** module; `EvoGit.Supervisor` is only the root supervisor's registered NAME, and the nested agent group is `EvoGit.AgentGroupSupervisor` (`one_for_all`: `Task.Supervisor` named `EvoGit.TaskSupervisor` + `EvoGit.AgentScheduler`)

### SSH Remote (RemoteBootstrap / RemoteConnection)

`EvoGit.RemoteBootstrap` is pure platform/asset/download logic (no I/O): `parse_uname/2`, `parse_platform/1`, `daemon_os/1`, `asset_name/1` (always `genesis_remote_<platform>.tar.xz`, never suffixed), `download_url/1` (deterministic `https://genesis.evox.group/dl/genesis_remote_<platform>.tar.xz` → `{:ok, url, "latest"}` — a Cloudflare-worker "smart download" URL proxying the GitHub release asset; no API query, no asset matching), `cache_path/2`, `bash_wrap/1`, `nixos_detect_command/0`, `nixos_patch_script/1`, `parse_unit_environment/1`.

`EvoGit.RemoteConnection` owns bootstrap + connect. Bootstrap sources in priority order: `local_binary_path` set + exists → `scp` upload; set-but-missing → warning + auto-download; absent → auto-download (remote `curl -fL`, remote `wget -O` fallback, local curl + `scp`). A silent pre-flight resolves the daemon OS (target `platform`, else one `uname -s && uname -m`) and applies the running-daemon policy BEFORE any staging.
Stage atoms (evo_dash `settings_live.ex` needs UI labels): `:probing_platform | :downloading | :downloading_locally | :stopping_daemon | :uploading | :extracting | :setting_permissions | :copying_config | :generating_cookie | :patching_binaries | :starting_daemon`.
NixOS remotes (Linux, no daemon already running) get the `:patching_binaries` stage: `nixos_patch_script/1` builds `patchelf`/`bintools`/`stdenv.cc.lib`/`openssl`/`zlib`/`ncurses`/`pcre2` from `<nixpkgs>` (GC-rooted under `<release>/.nixos-patch`) and patches each ELF binary three ways — interpreter + rpath for dynamic executables, rpath-only for shared libraries (NEEDED-deps probe), skip truly static binaries.

Error tuples (tests pin these): probe → `{:error, {:probe_failed, {:exit_status, n} | :timeout | {:unexpected_output, out}}}` | `{:error, :unsupported_platform}`; download → `{:error, {:download_failed, {:exit_status, n} | :timeout | {:local, detail} | {:local_scp, detail}}}`; platform override → `{:error, {:invalid_platform, p}}` / `{:error, :unsupported_platform}` (`windows_x64` is not a valid daemon target). Timeouts: bootstrap 900s, download 300s.

Safeguards:
- Remote commands are ARGV arrays, never quote-wrapped spawn strings: `run_ssh_command/3` uses `{:spawn_executable, …}` + `{:args, [target, remote_cmd]}` — a quote-wrapped `{:spawn, String}` breaks Windows (the CRT consumes only double quotes) and Unix (spawn strings go through `/bin/sh -c`, so local `$` expands).
- **A running daemon is never killed without permission**: `bootstrap/2`'s `:on_running` ∈ `:refuse` (default) | `:restart`. Refuse → `{:error, {:daemon_running, details}}` with NO staging, NO kill, NO broadcast and state untouched (the dashboard renders a permission dialog from this tuple); restart → `:stopping_daemon` broadcast + stop (a failed stop is non-fatal), then the normal flow. `verify_daemon_identity/4` stays as the RACE safety net for a daemon appearing between pre-flight and launch — fail loud on an identity mismatch, never auto-kill.
- Every remote command is `bash_wrap/1`ed (`/usr/bin/env bash -c '…'`, embedded single quotes escaped) — login-shell independent (required on NixOS hosts whose login shell is fish).
- `systemctl --user reset-failed` runs before launch; `verify_daemon_healthy/2` polls readiness afterwards (3 retries × 1s).
- `:copying_config` is best-effort and NEVER overwrites an existing remote config.toml / credentials.toml (per file the bootstrapping machine probes `ssh <target> 'test -f <remote_file>'` and skips the scp when present). When config.toml is absent it uploads an accent-rewritten variant (deterministic per-target color differing from the local node's accent) so nodes stay visually distinguishable, falling back to the unmodified file on failure. The target dir mirrors the remote `EvoGit.Platform.config_dir/1` (Linux `~/.config/genesis`, Darwin `~/Library/Application Support/genesis` — the space in the Darwin path is unquoted in the probe/scp, so config copy to Darwin remotes is unreliable).
- `Distribution.ensure_epmd_module/0` (idempotent flip of `:epmd_module` to `EvoGit.EpmdDist`) runs in the connect worker's `establish_tunnel_and_node/1` and in `enable_for_remote/1`'s already-distributed branch; the BOOT path deliberately does NOT set it — inbound discovery keeps the real epmd daemon, outbound-only resolution is the design.
- Supervision: `RemoteConnection.Registry` (keyed by target id) + `RemoteConnection.Supervisor` (`restart: :transient`) start before the agent group; `Store`/`TaskRegistry` are supervised so the headless daemon has full task history.
- Distribution is off by default — enabled on demand by `RemoteConnection`, or at boot via `Distribution.maybe_enable/0` when `[node] enabled = true`; the daemon itself starts distributed on port 9000 via `rel/vm.args.eex`. Boot-time enabling is skipped in the test env (`@mix_env != :test` gate at the CALL SITE — otherwise a developer's real config would start `:net_kernel`/EPMD before `ExUnit.start/1`, invisible to `capture_log` and unpreventable by XDG redirects); tests needing distribution use `enable_for_remote/1`.
- Asset format: `genesis_remote_<platform>.tar.xz`, extracted with `tar -xJf` (no gz fallback — xz failure fails loudly); CI uploads one per platform (linux_x64 / linux_arm64 / darwin_arm64 / windows_x64), and the NixOS patchelf path means no extra asset variants.
- Release definitions live in the umbrella ROOT `mix.exs` (`genesis`/`genesis_desktop`/`genesis_remote`); endpoint bind + `EVOGIT_LIFETIME_PORT` zombie prevention: root `./CONTEXT.md`.

#### Connect path (async, event-driven — non-blocking)

`connect/1` replies `{:ok, :connecting}` (or `{:ok, :connected}`) immediately (default 5s `GenServer.call`); the blocking I/O — distribution auto-enable, `find_free_port`, the ssh spawn, `wait_for_tunnel/4`, `EpmdDist.register_target/2`, `Node.connect/1` — runs in a monitored + linked worker, so the manager stays responsive (`status/1`/`connected?/1`/`disconnect/1`/`list_connections/0`).
The GenServer is the SINGLE owner of phase state: the worker never mutates state or broadcasts — it reports `{:connect_result, worker_pid, {:ok, %{port:, local_port:, node_name:}}} | {:connect_result, worker_pid, {:error, message}}`, and all transitions happen in the `{:connect_result, …}` / `:DOWN` handlers. On success the worker transfers the tunnel `Port` to the GenServer (`Port.connect/2`) BEFORE reporting, so the tunnel survives the worker's exit; a `:DOWN` with no result means a crash → `:error` ("connect worker crashed: …").
Broadcasts on PubSub `"remote_connections"`: `{:remote_connection_status, target.id, status_map}` — NO trailing node element (exception to the node-carrying contract; consumed by `EvoDashWeb.LiveHooks.NodeAware`): `:connecting` on start, `:connected`, `:error` with `last_error` on EVERY failure arm (all through the `fail_connect/2` choke point), `:disconnected` when `disconnect/1` aborts an in-flight connect. Duplicate connects are idempotent; a retry from `:error`/`:disconnected` starts a new worker. The ssh argv carries `-o ConnectTimeout=8` (under the 10s tunnel budget). `disconnect/1` during `:connecting` kills the worker (it owns the port until success), then runs the normal `cleanup/1` teardown → terminal `:disconnected` + `{:stop, :normal, …}` (`restart: :transient` → not restarted). No app-env/clock seams exist in `remote_connection.ex`; tests fake the `ssh` executable on PATH. Dashboard consumers must NOT block on `connect/1` — initiation is wrapped in an `EvoDash.TaskSupervisor` task (`NodeAware.initiate_remote_connect/2`), navigation is optimistic, and terminal state arrives via the broadcasts (`NodeAware.handle_connection_status/2`).

#### SSH tunnel readiness (connect-path invariant)

`establish_tunnel_and_node/1` must NOT call `Node.connect/1` before the tunnel's local forwarded port accepts TCP connections — `ssh -L <local_port>:127.0.0.1:<dist_port> -N <target>` can take >1.5s to start listening, and a too-early `Node.connect` fails instantly with econnrefused → `{:error, {:node_connect_failed, …}}` with NO remote-side log entry.
`wait_for_tunnel/4` polls the local port (100ms interval, 10s budget) and fails fast when the ssh Port dies (draining its output into the error); it is `@doc false` public solely for tests.

#### Known connect failures (`node_connect_failed`)

- **Stale-daemon identity** → `{:error, {:daemon_identity_mismatch, details}}`: the daemon's node name + cookie are fixed at LAUNCH time (systemd-run unit `Environment`, or the launchd plist `EnvironmentVariables`), so an old or manually-started daemon keeps a stale identity forever. The pre-flight decides the running-daemon policy before staging and `verify_daemon_identity/4` is the race safety net (Linux: `parse_unit_environment/1` over `systemctl show -p Environment`; Darwin: the deployed plist; unknown OS → `:ok`) — missing keys, differing values, empty output and `:timeout` are all mismatches, `details` stating found vs expected plus remediation. Replacement path: `bootstrap(target_id, on_running: :restart)` (a plain `systemctl restart` re-runs the old unit env and does NOT help). The cookie is per-MACHINE — machine A bootstrapping and machine B connecting cannot match unless B relaunches the daemon.
- **`dist_port` ≠ 9000 never works**: the daemon is hard-pinned to 9000 (`rel/*/vm.args.eex`); the tunnel forwards to `Map.get(target, :dist_port) || 9000`, and any other value forwards to a dead remote port (`wait_for_tunnel/4` still passes — `ssh -L` accepts local connections to a dead forward target).
- **Outbound name resolution on a boot-distributed local node**: with `epmd_module` left at `erl_epmd`, an outbound `Node.connect` to a tunnel-registered name asks the real epmd daemon for a port it never registered (`:noport` → `false` → `{:error, {:node_connect_failed, …}}` with NO daemon-journal entry — the handshake never starts). Hence `ensure_epmd_module/0` on both connect paths.

### SQLite Store — Ecto Persistence Layer

`EvoGit.Store` is a GenServer facade over `Store.Operations.*` on an Ecto/`xqlite_ecto3` dynamic repo; five Ecto migrations run at EVERY boot in a fixed order (baseline adoption → data normalization → composite indexes → compress oversized rows → covering indexes; migration 4 must precede 5, legacy user DBs self-heal with no manual steps) and `mix migrate.store` is a thin `Ecto.Migrator` report wrapper over the same run.
Every read is dispatched to a failure-isolated unlinked worker with a 25 s deadline and degrades to its own empty shape (reads never raise/exit/`{:error, _}`), while `EvoGit.TaskRegistry.StoreGuard` gives the registry the same containment (`{:error, :store_unavailable}` on writes, handled like `{:error, :disk_full}`).
Summary reads return the 16-key projection (`result` never selected/decoded), `tasks.updated_at` is store-internal bookkeeping (the heartbeat never bumps it, undecodable rows are skipped with a `Logger.warning`), and disk-full-class write errors surface as `{:error, :disk_full}` at the `write_call/2` choke point while every other write error re-raises.

- **⚠️ `since` is NOT exposed through RemoteAPI/RemoteNode** (they accept only `statuses`) — remote time-filtered callers must use `list_tasks_changed_since`.
- **Lightweight reads**: `select_tasks_page/2` (16-key summary rows + `total`), `get_task_lite/2` (no archive decode) and `get_task_archive/2` are the non-blob read path; the search `fragment/1` LIKEs `id`/`opts`/`project_path`/`branch_name` only, never `result`.
- **Storage model**: `Store.Codec` compresses oversized `result`/`archive_metadata`/`logs` as `"z1:" <> Base64(zlib)` and `ArchiveDedup` keeps exactly one archive copy per row; `mix store.maintenance [--vacuum]` is the only way to reclaim freed pages.

Detail: `./store/CONTEXT.md` (schemas, operations, read fault isolation + write offload, compression/dedup storage model, indexes, migrations, maintenance).

## Windows-Only Runtime Hazards (audit index)

Code that is latently Windows-broken because the Windows branch is unreachable on Linux/macOS dev+CI (`Platform.windows?()` gates) — each item is a raise/degradation, not a compile error.
Per-subsystem detail lives in the child CONTEXT.md files; this is the cross-cutting index.

- **`Port.open` `{:env, ...}` requires CHARLISTS** while `System.cmd/3` normalizes binaries itself (`validate_env/1` → `String.to_charlist/1`) — the ONE raw-port env site is `EvoGit.Sandbox.None`'s Windows clause (detail: `./sandbox/CONTEXT.md`); `bwrap`/`remote_connection` ports pass no `:env` at all.
- **`Port.info(port, :os_pid)` returns the TUPLE `{:os_pid, pid}` (never a bare integer) and `Port.close/1` RAISES `ArgumentError` on an already-closed port** — raw `Port.open/2` is NOT interchangeable with `System.cmd/3`; `Sandbox.Helpers.wait_for_os_pid/2` unwraps the tuple and every timeout path closes through the shared idempotent `Helpers.close_port/1`, so the Windows `taskkill /T /F` tree kill and bwrap's process-group kill do fire (detail: `./sandbox/CONTEXT.md`).
- **Tool-level raises are CONTAINED, not fatal**: `Agent.ToolDispatch.execute_tool_with_timeout/7` wraps each tool call in a spawned, linked `Task.async` and the task body (`execute_tool_task/7`) has its own `try/rescue/catch` — a RAISING tool implementation (wrong-typed argument, unresolved executable, buggy custom tool) is converted into the normal tool-result string `Error: Tool execution crashed: …` that the model can self-correct from on the next turn. Only the `:normal` / `:shutdown` / `:kill` / `{:shutdown, _}` exit family is re-raised unchanged, reaching the caller's `{:exit, reason}` arm as `Error: Tool execution crashed: …` (a `nil` yield is the timeout arm). Detail: `./agent/tools/CONTEXT.md`.
- **`EvoGit.GitEnv` exports `GIT_EDITOR` as an UNQUOTED path** (from `derive_windows_true_exe/0`) — git hands the editor to `sh -c`, so the normal `C:\Program Files\Git\usr\bin\true.exe` is split at the space and every git operation that would open an editor aborts (detail: `./adapters/CONTEXT.md`).
- **`EvoGit.RemoteConnection`'s `run_cmd/2` spawn-string commands interpolate LOCAL paths unquoted** (`"curl -fL -o #{cache_file} #{url}"`, `"scp #{local_path} …"`) where those paths come from `Platform.data_dir()`/`System.tmp_dir!()` — on Windows `C:\Users\<First Last>\AppData\...` splits at the space because `Port.open({:spawn, _})` is ONE command-line string re-parsed by the child, not argv (the argv-safe form already exists in `run_ssh_command/3`).
- **Those three `Port.open` sites pass no `:hide`** — on Windows each spawn may open a console window (Elixir's `System.cmd/3` always adds `:hide`).
- **`SystemCheck.check_tool/1`** passes `Executable.resolve/1`'s output straight to `System.cmd/3`, so a genuinely missing tool raises `ErlangError :enoent` (surfaced as a check error via the centralized rescue) instead of an "unavailable" result — `Executable.resolve/1` itself never returns a non-existent absolute path.
- **`EvoGit.Skills.Executor`'s Windows branch resolves bash only via `System.find_executable("bash")`** — MinGit (the vendored git under `<priv>/vendor/windows-x64/mingit/`) ships its POSIX shell as `sh`, NOT `bash.exe`, and MinGit's directories are not on PATH in a desktop install, so bash skills degrade to the "install Git for Windows" error unless the user's own Git for Windows bash is on PATH (detail: `./skills/CONTEXT.md`).

## Executable Resolution (`EvoGit.Executable`)

`EvoGit.Executable.resolve/1` implements the system-first, bundled-fallback contract: a name found on the system PATH is returned UNCHANGED, so `System.cmd/3`'s own PATH/PATHEXT search runs; only when it is absent from PATH is a bundled candidate under `priv/vendor/<platform>/` considered, and only when that candidate exists as a regular file. Otherwise `resolve/1` returns the ORIGINAL name unchanged, so PATH search, `System.find_executable/1` and the Windows known-location fallback (`EvoGit.Sandbox.None.resolve_windows_executable/1`: WINDIR/ProgramFiles PowerShell/pwsh) still apply. `resolve/1` never returns a non-existent absolute path.

Pure `@doc false` helpers make this testable without a real Windows vendor layout: `candidates/3` (Windows `git` → `<vendor>/mingit/cmd/git.exe`, other Windows names → `<vendor>/<name>.exe`, elsewhere → `<vendor>/<name>`) and `bundled_path/3` (first EXISTING candidate, else `nil`). `resolve/1` never resolves a bundled bash (a bundled MinGit shell is not put on PATH; see `./skills/CONTEXT.md`). Tests: `apps/evo_git/test/evo_git/executable_test.exs`.

## Review / RemoteNode Return-Shape Contract (remote-SSH payload analysis)

`EvoGit.RemoteNode` review wrappers return the **verbatim underlying value** of the `EvoGit.Review` function (local → `RemoteAPI` direct, remote → `:erpc` via `call_remote/4`); the ONLY added shape is `{:error, {kind, reason}}` on RPC failure. Arity is Review + 1 (leading `node`), and ALL of them time out through `call_remote/4` → `rpc_timeout/0` (`Application.get_env(:evo_git, :remote_rpc_timeout, 30_000)`, read at CALL time). **`defnode` convention (durable)**: identity-unwrap wrappers are declared `defnode EvoGit.AgentScheduler.RemoteAPI.some_fun(args)` via the `defnode` macro (`EvoGit.RemoteNode.Defnode`), which generates the local-direct / `call_remote` pair; only functions whose remote branch is EXACTLY `{:ok, r} -> r; {:error, e} -> {:error, e}` are macro-eligible — per-function failure fallbacks (`[]`/`%{}`/`nil`/`false`/`{:error, :rpc_failed}`, nested-error asymmetries) stay hand-written. **Every review/task wrapper is `defnode`-generated (no per-function fallbacks)** and takes an explicit `repo_path` from the caller (see the `@spec`s in `remote_node.ex`). Struct shapes:

- **`%EvoGit.Review.FileInfo{}`**: 8 fields — `:path`, `:status` (`"added" | "deleted" | "modified"`), `:additions`/`:deletions`, `:diff` (String | nil), `:language` (highlight.js name, always populated), `full_new_content: nil`, `full_old_content: nil` — the `full_*` fields are NEVER populated by Review; the caller (evo_dash via `get_file_content/4`) fills them for whole-file highlighting.
- **`%EvoGit.Review.CommitInfo{}`**: 6 fields — `:sha`, `:short_sha`, `:message` (subject line, `%s`), `:author_name`, `:author_email`, `:date` (`%DateTime{}` from `%aI`, raw String fallback on parse failure).
- **Metadata maps** (`load_review_metadata/2`, `load_review_metadata_from_shas/3`, `load_commit_files/2` — the last diffs against `commit_sha~1`) share ONE shape: `{:ok, %{commit_sha, base_sha, diff_stat (git diff --numstat raw output), diff: nil, files: [%FileInfo{}] (diff: nil), changed_files_count, total_additions, total_deletions}}` | `{:error, {tag, output}}`. `load_review_data/2` is the payload-heavy variant (top-level `diff` = FULL combined `git diff`, each `FileInfo.diff` = `"diff --git " <> section`), NOT called anywhere in `apps/evo_dash` — the review page uses metadata + lazy `load_file_diff`.
- **Diffs**: `load_file_diff/4,5` and `load_commit_file_diff/3` → `{:ok, diff_string}` | `{:error, {tag, output}}` (`:context` opt: int | `:all` → `-U999999` | nil = git default 3 lines). `get_file_content/3` → `{:ok, full_file_content}` | `{:error, {tag, output}}`.
- **Commits**: `list_commits/2` and `list_commits_from_shas/3` → ALWAYS `{:ok, [%CommitInfo{}]}` (empty list on git errors — the `{:error, _}` in the RemoteNode spec only occurs via RPC failure).
- **Commit graph** (`CommitGraph.for_ranges/3` → `RemoteAPI.list_commit_graph/3` → `RemoteNode.list_commit_graph/4`): ALWAYS `{:ok, %{commits: [commit], refs: %{sha => [ref_name]}}}` (never raises — bad ranges degrade to `[]`, a failed ref listing to `%{}`). Each `commit` is an atom-keyed MAP with the seven keys `:sha, :short_sha, :message, :author_name, :author_email, :date, :parents` (not a struct): `:date` is a `%DateTime{}` or `nil`, `:parents` a list of full SHAs (`[]` for a root commit). `refs` maps each returned commit SHA to its short branch/tag names.
- **Task-scoped commit graph** (`EvoGit.TaskCommitGraph.for_task/4` → `RemoteAPI.list_task_commit_graph/4` → `RemoteNode.list_task_commit_graph/5` — node + `task_id` + `repo_path` + `live_tips` + `opts`): the durable WHOLE-TASK variant that keeps a recycled agent's history visible. `resolve_refs/1` (pure) / `resolve/1` (reads `TaskRegistry.get_task/1`; total — a corrupt row or dead registry degrades to `%{base_sha: nil, tips: [], project_path: nil}`) gather durable tips from the task row: `commit_sha`, `branch_name`, and every `result["repos"][repo_id]["commit_sha"|"branch_name"]` (the persisted `result` is the DECODED `{:ok, data}` tuple plus a bare data map; STRING/atom keys handled, blanks/dupes dropped). Base per `repo_path`, first non-blank wins: `opts[:base_sha]` → repo-aware task base (`refs.base_sha` when `repo_path == refs.project_path`, else the `:base_sha` of a matching `opts[:foreign_repos]` entry, via `Core.ForeignRepo.normalize/1`) → merge-base fallback (`Git.merge_base(repo_path, "HEAD", ref)` on the first resolvable ref among `refs.tips ++ live_tips`) → `nil`. Tips = `refs.tips ++ normalize(live_tips)`. `CommitGraph.for_task/4` = `for_ranges/3`'s 2-key shape PLUS `truncated: boolean` (any tip range cut at `opts[:limit]`, detected via a `limit + 1` fetch, carried verbatim through `RemoteAPI`/`RemoteNode`/`:erpc`). Durable task refs survive `Lifecycle.recycle_agent/2`, which deletes the agent's ETS rows AND its `evogit-agent-*` branch.
- **Mutating ops (nil/blank-branch guarded)**: `merge_branch/2,3` → `{:ok, merged_sha}` | `{:conflict, details}` (trimmed git merge stderr from `Git.run` exit-1) | `{:error, {code, output}}` | `{:error, {:switch_back_failed, reason}}` (restore-after-merge failure); `reject_branch/2` → `:ok` | `{:error, {code, output}}`. These AND `check_merge/3` return `{:error, :no_branch}` for a nil OR blank (`String.trim(x) == ""`) branch/ref — one shared Review-layer guard (`valid_branch_name?/1`), so the `is_binary`-guarded `EvoGit.Adapters.Git` functions never see nil (a multi-repo task's no-change repo carries `branch_name: nil`); for `merge_branch/3` that is EITHER `branch_name` OR `target_branch` (`merge_branch/2` has no target arg; `check_merge/3` guards both). `create_github_pr/4` → `{pr_url, pr_title}` | `{nil, nil}` (never raises; delegates to `EvoGit.Runtime.PullRequest.try_create`). `list_branches/1` → `{:ok, [names]}` | `{:error, {tag, output}}` (`git for-each-ref`). `branch_exists?/2` → bare boolean.
- **`check_merge/3`**: `{:ok, :clean}` (identical SHAs short-circuit) | `{:ok, {:conflict, files}}` (files = conflicted path strings; 40-hex OID lines dropped by shape, `conflicted_file_paths/1`) | `{:error, {:merge_failed, output}}` (exit-1 with no file lines) | `{:error, {code, output}}` / `{:error, {:conflict, output}}` (rev_parse failures) | `{:error, :no_branch}` (nil/blank `branch_or_sha` OR `target_branch`). Non-mutating: `git merge-tree --write-tree --name-only --no-messages` — no worktree/index/ref changes, nothing under `.genesis/`.
- **`set_review_status` / `set_review_metadata` do NOT live in `EvoGit.Review`** — they live in `EvoGit.TaskRegistry` (GenServer **casts** → `:ok` immediately). RemoteNode routes (both `defnode` identity-unwrap): `set_review_status/3` → `RemoteAPI.set_review_status/2` → `TaskRegistry.set_review_status/2`; `set_review_metadata/4` → `RemoteAPI.set_review_metadata/3` → `TaskRegistry.set_review_metadata/3`.
- **Review status is TASK-LEVEL only — there is NO per-repo merged/rejected/review state anywhere** (evo_git). `set_review_status/2` persists exactly ONE column: `tasks.review_status` (TEXT); `set_review_metadata/3` persists `tasks.base_sha` + `tasks.commit_sha`. Both go through `Store.update_task_columns/3` (auto-bumps store-internal `updated_at`), gated by a `Store.get_task_status/2` existence check — a missing row is a silent no-op (`:ok`). Allowed `review_status` (Codec whitelist): `:open, :merged, :rejected, :continued, :ignored, :no_changes` (unknown/corrupt → nil). Both broadcast one `"tasks"` message `{:task_updated, task_id, nil, node()}` — even for a nil-row no-op; the status element is intentionally `nil` (review mutations don't change task status).
- **`RemoteNode.start_task/3`** → `RemoteAPI.start_task/2` → `TaskRegistry.start_task/2` (GenServer.call) → `{:ok, %TaskInfo{}}` (19 fields incl. in-memory-only `ref`) | `{:error, :cancelled}` (already-cancelled/cancelling id) | `{:error, :disk_full}`-class handled in-memory. `RemoteNode.get_task/2` → bare `%TaskInfo{} | nil` (nil on RPC failure AND missing task).
- **`custom_tools_status/1`** → `RemoteAPI.custom_tools_status/0` → `EvoGit.CustomTools.status/0` (per-node `<config_dir>/tools/`): local/remote success → the status map `%{ok: [%{name, file, module, read_only?: boolean}], errors: [%{file, reason}]}` verbatim, remote RPC failure → `{:error, {kind, reason}}` (deliberately NOT swallowed into an empty map). `defnode`-eligible — `status/0` never raises and never returns `{:error, _}`.

**⚠️ Known spec mismatch — `default_merge_target`**: `Review.default_merge_target/1` returns `{:ok, String.t()}` | `{:error, :no_branch_found}`, but the `@spec`s in `RemoteAPI`, `RemoteNode` and `NodeContext` all claim `String.t() | {:error, term()}` — the `{:ok, _}` wrapper is missing from the specs. The runtime value is the wrapped tuple; `ReviewLive` correctly pattern-matches `{:ok, name}`. Do NOT trust the specs when doing payload analysis.

## Windows PowerShell Invocation — `-EncodedCommand`

**Why `-EncodedCommand`:** `powershell.exe -Command <script>` spawned from Erlang is broken by construction — PowerShell re-joins the raw command line and re-parses it as PowerShell code, so Erlang spawn quoting gets mangled; a lost script arg falls back to INTERACTIVE mode, exiting 0 with NO output on closed/EOF stdin. Secondary: PS 5.1 writes piped output via `[Console]::OutputEncoding` (OEM/UTF-16) — `EvoGit.UTF8.ensure_utf8/1` treats a UTF-16LE BOM as invalid UTF-8.

**Invocation:** spawn `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -EncodedCommand <b64>` where b64 = base64(UTF-16LE of `& { [Console]::OutputEncoding = [System.Text.Encoding]::UTF8; <script> } *>&1`). `-EncodedCommand` eliminates ALL command-line quoting/parsing; the OutputEncoding line forces UTF-8 output; `*>&1` merges all streams incl. Write-Host/information. No `<`/input redirection.

Applied at: `Platform.shell_args/1`'s PowerShell clause (covers the shell tool and `Worktrees.run_init_script/3`) and `EvoGit.Sandbox.None` `run_windows/3` + `run_with_partial_windows/5` (defense-in-depth `transform_args/2` + `decode_output/1`). `transform_args/2` matches ONLY powershell/pwsh (any case, backslash-normalized before `Path.basename`) with the exact 2-element `["-Command", cmd]` shape; already-encoded args and bash/git invocations pass through untouched (no double transform). Tests: `test/evo_git/powershell_test.exs` + the `shell_args/1` test in `test/evo_git_test.exs`.

## Constraints
- All git operations must go through `EvoGit.Adapters.Git` — no direct `System.cmd("git", ...)` outside adapters.
- Agents are transient modules using `EvoGit.Agent` behaviour; persistent state lives in ETS.
- System prompts MUST NOT contain dynamic state, objectives, or context trees.
- Worktrees are created FRESH per agent run (no pool, no reuse across retries); the `WorktreeManager` GenServer owns lazy per-repo init, creation (via `Worktrees.prepare_new_worktree/5`), and monitor-driven reclaim/destruction.
- Agents commit before delegating subagents (auto-commit fallback enforced by scheduler).
- Tool outputs are truncated at the `[:truncation, :tool_output_max_bytes]` global ceiling (default 128 KB) and every tool timeout is clamped by `[:scheduler, :max_tool_timeout]` (default 30 min); turn limits produce adaptive turn-limit warnings (`EvoGit.Agent.TurnWarning`, threaded through `LoopState.last_warned_level`).
- Cross-repo subagents commit to their foreign repo's worktree — changes are NOT merged into the primary repo.
- 3-level configuration: `EvoGit.Config` merges defaults → user TOML → runtime overrides.

## Managed Per-Task Tmpdir & Reclaim Lifecycle (`EvoGit.TaskTmpdir`)

All agents of one task share ONE scratch directory (`task_<id>` under a node-local managed root) instead of the shared host `/tmp` (no isolation, no sweep). A per-task (not per-agent) scope is required because agents legitimately hand temp files to **sibling** agents via raw paths. The managed root (`managed_root/1`) is the ONE directory the module owns — `reclaim/2` NEVER deletes anything outside it and NEVER deletes the root itself.

**Sandbox TMPDIR seam**: `EvoGit.Sandbox.resolve_tmpdir/0` prefers `EvoGit.TaskTmpdir.current/0` when set, so every sandbox backend injects `TMPDIR=<task dir>`. The runner resolves the path once and calls `put_current/1`; the tool-dispatch layer reads `current/0` and re-installs it inside each spawned tool task — those tasks do NOT inherit the caller's process dictionary, so the value is threaded explicitly.

**Reclaim lifecycle** (owner: `EvoGit.TaskRegistry`; every reclaim is node-local — the managed root is per-BEAM). Reclaim is **event-driven ONLY** — there is NO boot reaper and NO periodic sweep:
- **Terminal transition** — `handle_update_status/6` is the dominant choke point (the wrapper result, the stuck-`:finalizing` watchdog and startup reconciliation all flow through it) and reclaims on every terminal status. The direct terminal writes that BYPASS it carry their own reclaim call: `force_kill_task` (`:failed`), cancel of a `:pending` task (`:cancelled`), the `:lease_sweep` (`:failed`), and `resolve_recheck_task/3` on its successful terminal write.

A `task_<id>` dir orphaned by a full-runtime crash (no terminal status ever written) is NOT reaped automatically — it requires manual cleanup. `TaskTmpdir.reclaim/2` never raises, so a reclaim can never crash the registry.

## First User Prompt Assembly
The `run/1` callback (injected by `use EvoGit.Agent`) assembles the agent's first user message as two XML-delimited blocks separated by a `---` rule — `<context>` (context_tree + `{authority_section}` + `{foreign_repos_section}` + `{repo_notes_section}`, each omitted when blank), then `<objective>` (`{objective}`, omitted when there is no objective).
Section bodies are produced by **`build_dynamic_context/1`**, **`build_authority_section/1`** (delegation-authority role line), **`build_foreign_repos_section/1`** and **`build_repo_notes_section/1`**.
Blank sections are dropped entirely — no dangling rules, empty headers, or empty XML blocks; `---` appears only between two non-blank blocks.
**Delegation-authority section** (`ContextBuilder.build_authority_section/1`, wired in `Runner.do_run/2` only — never inside `build_dynamic_context/1`): authoritatively states whether THIS agent is the **ROOT agent** (`AgentState.parent_id == nil` ⇔ `SchedMeta` depth 0 — exact by construction in `Dispatch.register_agent/7`; never the process-dict depth, which may not be populated at assembly time) or a **NESTED agent**, plus the foreign-repo spawn authority that role carries (ROOT may spawn write-capable `:read_write` foreign-repo subagents one at a time; NESTED may not and reports needed foreign-repo changes up to its parent).
Returns `""` for repo-less agents (the self-reflective chat persona must not read a task-role statement) and for tasks with no non-primary foreign repos (single-repo prompts stay token-neutral; mirrors `build_foreign_repos_section/1`'s empty-string convention, so the blank-filter drops it).
Static system prompts are role-agnostic by design and point to this dynamic statement — system prompts must NOT contain dynamic state, and only the first user message (built with the live `%AgentState{}` in hand) can truthfully state the agent's own role.
`ContextBuilder.build_quality_guidance_section/1` adds the ROOT agent's `EvoGit.QualityLevel` block the same way (Runner `<context>` assembly, gated on `parent_id == nil`; subagents AND repo-less/reflect agents get `""`), reached via `Runtime.Helpers.build_root_agent_spec/7` → `AgentSpec.opts` + the Runner process dict.

## Injected User Messages (mid-run, multimodal)

The ONLY external message-injection point is the drain at the TOP of `Runner.loop/1`: **`Runner.drain_and_inject_user_messages/1`** (public `@doc false` so tests can drive it directly — same convention as `refresh_commit_sha/1`/`maybe_enter_cancel_grace/1`; called only from `loop/1` in production) drains `AgentScheduler.Store.drain_pending_user_messages/1` and appends each drained message through the pure **`ContextBuilder.build_injected_message/2`**, turn-tagged, then syncs the context to ETS.

- **Entry points** (message = a legacy plain `String.t()` OR a `%{text:, attachments:}` map carrying images/audio): `EvoGit.AgentScheduler.send_user_message/2` (guard widened to binary OR map) → scheduler GenServer → the pending queue append; and `EvoGit.RemoteNode.send_agent_message/3` (node-first: local → `RemoteAPI.send_agent_message/2` directly, remote → `:erpc`). `EvoGit.Attachments.message/1` is the ONE normalizer and canonicalization happens in the QUEUE; the injection entry points pass the message through verbatim.
- **Materialization** (`build_injected_message(message, turn)`): a legacy binary or a map whose attachments are `nil`/`[]` → `ReqLLM.Context.user(text)` (byte-identical to the plain-text injection path); a map carrying attachments → `ReqLLM.Context.user(Attachments.to_content_parts(text, attachments))` = `[ContentPart.text(text) | image/file parts…]`. `turn` integer → turn-tagged via `tag_message_turn/2` (+ creation timestamp); `nil` → the raw untagged message. Malformed message maps raise a descriptive `ArgumentError` (spec-error style).
- **NO root gate** on injected messages: an agent at ANY depth may receive media this way. The root-only gate stays on the `:attachments` TASK OPT (the initial user message only — `build_initial_messages/4`).
- **There is NO per-turn runtime-context block** — `ContextBuilder.build_context_block/1` runs only at run start (`Runner.do_run/2`) and on a compression refresh (`ContextCompression` → `build_context_refresh_message/2`). The top-of-turn machinery (`Runner.loop/1` → `continue_loop/1`) appends messages (turn warnings, drained injections, background-job `[NOTICE]` messages) but never re-renders `<context>`, so any per-turn notice must be an APPENDED message, not a context section.
- **The drain is a non-atomic read-modify-write of the whole `%AgentState{}`** (`AgentScheduler.Store.drain_pending_user_messages/1`: `get_agent_state` → `put_agent_state(%{state | pending_user_messages: []})`, full-struct write). Appends are serialized against EACH OTHER only by routing through the AgentScheduler GenServer (`send_user_message/2`); an append landing between the drain's read and write is silently LOST, as is a concurrent `set_cancel_requested/1`. A notice whose loss is unacceptable must be re-derivable (pulled from its source at the turn top) rather than queue-only.

## Background Job Completion Notices (`announced`)

Every job record carries `announced` — `false` at start and never reset once set.
`snapshot/1` (`owner_pid:` defaults to `current_owner_pid/0`) is the per-turn read: a pure state snapshot of one owner's jobs, newest first (started_at desc, id tie-break), capped at 20 — no backend reconciliation, no output-file I/O, no cursor advance.
`claim_finished_notices/1` is the exactly-once completion feed: ONE GenServer call selects that owner's terminal (`:completed | :killed | :failed`) unannounced jobs, marks them `announced: true` and returns `{:ok, jobs}` newest first, so a second call can never return the same job.
Both answer their empty shapes without raising when the registry is down or the owner is unknown (`[]` / `{:ok, []}`).
`read/2` and `list/1` mark every TERMINAL job they return as announced (the status was already reported to the caller), while a `:running` job is never marked.
**Consumer side (the agent loop)**: `Runner.inject_background_job_notices/1` (called in `continue_loop/2` right after the pending-user-message drain, before the cancel-grace check and the LLM call) makes ONE `claim_finished_notices(owner_pid: self())` call that claims ALL of that owner's terminal unannounced jobs and appends exactly ONE turn-tagged `:user` message rendered by `EvoGit.Agent.BackgroundJobNotice.notice/1` (`[NOTICE] N background shell job(s) finished:` + `- `id` — status (detail) — label` per job + a `job_output`/`job_list` hint), syncing the context to ETS so the dashboard shows it; the notice is notification-only — it NEVER includes job output — and the claim is exactly-once, so polling with `job_output`/`job_list` never produces a duplicate.
The claim is SKIPPED during a grace period (cancel / turn-limit wrap-up), leaving the job unannounced for the next non-grace turn; an unreachable registry already yields `{:ok, []}`, so no rescue is needed.
**Compression contract**: the runtime-context refresh message is appended on every compression event, but the live job snapshot rides ONLY the summarising (stage-2) path — `ContextCompression.refresh_messages/2` injects `snapshot(owner_pid: self())` when its `include_background_jobs?` flag is true and `ContextBuilder.build_context_block/1` renders the `## Background Jobs` sub-section; every summarising outcome drops earlier job-carrying refresh messages (`drop_stale_background_job_refreshes/1`) before appending the new one, so exactly ONE current section survives; the stage-1 prune-only path injects no jobs snapshot and performs no background-job cleanup; and the summariser does NOT list job ids/statuses under `## Pending Jobs` (background shell jobs are tracked by the runtime and re-injected there).

## ReqLLM Finch Pool (`EvoGit.ReqLLMPool`)

`req_llm_pool.ex` — dynamic, GROW-ONLY runtime reconciliation of ReqLLM's Finch HTTP pool (`ReqLLM.Finch`), fixing the "Finch was unable to provide a connection within the timeout due to excess queuing" RuntimeError that occurs when runtime concurrency outgrows the boot-time pool size.

**Public API:** `desired_count(total)` → `max(total + 2, 8)` (single source of truth — `config/runtime.exs` delegates to it); `error_target_count(total)` → `max(ceil(total * 1.5), 8)`; `effective_concurrency(model_concurrency_map, default)` → `max(sum of map values, default)`, `default` for empty/nil; `reconcile(total, finch \\ ReqLLM.Finch)`; `bump_for_excess_queuing(model_concurrency_map, default, finch \\ ReqLLM.Finch)`; `excess_queuing_error?(reason)` → matches a bare `%RuntimeError{message}`, `%ReqLLM.Error.API.Stream{reason, cause}`, or an inspect fallback.

**Grow-only semantics (MANDATORY):** `Finch.set_pool_count/3` grows by starting new pool processes (safe) but shrinks by terminating them (kills in-flight streams), so `ReqLLMPool` NEVER shrinks (`max(current, desired)` per origin). All public functions never raise; `{:error, :not_found}` (no materialized origins) is a graceful no-op.

**Enumeration & the `start_pool_metrics?` requirement (CRITICAL):** pools materialize LAZILY per origin on first request. `Finch.get_pool_status(finch, :default)` → `{:ok, %{%Finch.Pool{} => [per-shard metrics]}}` (map key = origin, list length = shard count) but ONLY for pools configured `start_pool_metrics?: true`; without the flag it always returns `{:error, :not_found}` and reconciliation is a **silent no-op** — hence `config/runtime.exs` uses the full `finch:` override form with the flag set (plus top-level `stream_pool_timeout` and the RoundRobin `stream_pool_strategy`, both read at CALL time; per-origin capacity = `count × 2` HTTP/1 streams, `size` a LAZY bound). Config detail: root `./CONTEXT.md`.

**Per-origin semantics (the sizing rationale):** pool identity is `{scheme, host, port, tag}` — path prefixes are NOT part of the key (`:default` tag because EvoGit sets no connect options and no `pool_tag`), so profiles sharing a host share ONE pool. Applying the `max(total + 2, 8)` SUM formula uniformly per origin is the provably sufficient upper bound — a single origin's demand `D(O) ≤ total` — with the `+2` covering the two non-slot-gated auxiliary call sites (system_check, pull_request); shards are cheap and connections lazy. The error path cannot identify the failing origin (`%ReqLLM.Error.API.Stream{}` carries only `:reason`/`:cause`; Finch's RuntimeError message is static), so the bump is necessarily uniform. Root `./CONTEXT.md` carries the sizing summary — never inline the formula elsewhere.

**Two triggers (both wired):**
1. **Config change** — `AgentScheduler.handle_call({:update_config, opts}, …)`'s `{:reply, :ok, new_state}` path (private `reconcile_pool_after_update/1`) calls `reconcile(effective_concurrency(new_state.model_concurrency, new_state.default_llm_max_concurrency))`, covering ALL config-change routes (`RemoteAPI.reload_config`, `save_user_config`, evo_dash ConfigIO); the `{:error, "llm_model cannot be nil"}` path never reconciles, so the helper is single-clause and total.
2. **Excess-queuing error** — `ToolDispatch.run_llm_attempt/4`: inside the per-attempt `with_llm_slot/2` body, the inner `with`'s `{:error, reason}` branch calls `bump_for_excess_queuing/3` when `excess_queuing_error?(reason)`. No `report_llm_error` — the bump IS the fix; `AgentScheduler.get_config/1` from the agent process is safe (pure state reads).

**Tests:** `test/evo_git/req_llm_pool_test.exs` (pure functions + real tiny-Finch grow / grow-only / `:not_found`-grace tests; the test Finch sets `start_pool_metrics?: true`) plus a scheduler smoke test in `agent_scheduler_test.exs` (`model_concurrency` keys are STRINGS, e.g. `%{"default" => 3}`).

## SystemSampler — System Topic Sampling (`EvoGit.SystemSampler`)

`system_sampler.ex` — a supervised GenServer (child of `EvoGit.Application`, running on EVERY node incl. the headless `genesis_remote` daemon) sampling scheduler status every 3s and broadcasting on `EvoGit.PubSub` topic `"system"`, so the dashboard (local AND remote) renders charts from pushes instead of polling.

- **Event contract**: `{:system_sample, node, seq, sample}` every tick — `node` = `node()` (sampling is LOCAL-only, no RPC), `seq` monotonic per sampler instance. Sample keys EXACTLY (no extras): `llm_slots, llm_used, llm_waiting, tool_used, tool_waiting, llm_capacity, tool_capacity, agents_total, agents_running, agents_blocked, agents_waiting, agents_pending, scheduler_alive`. `llm_slots` = `%{model_id => %{used, waiting, capacity}}` — REAL per-model LLM slot occupancy (holders / queue length / effective capacity incl. peak-pause `0`), read live per tick from `AgentScheduler.get_llm_slot_status/0` (`RemoteAPI` stays intentionally ETS-pure); `%{}` when the scheduler is down or that tick's bounded call fails.
- **Tick**: `Process.send_after(self(), :sample_tick, interval)`; interval = `Application.get_env(:evo_git, :system_sample_interval_ms, 3000)`, read ONCE at init (tests set it high and drive ticks via `EvoGit.SystemSampler.tick/0` or a raw `:sample_tick`); rescheduled BEFORE sampling so a slow step never breaks cadence.
- **Local-only sampling**: per tick the sampler reads the local `:evogit_sched_meta` ETS table (guarded `:ets.whereis`) and counts `meta.status`; the aggregated `llm_used`/`llm_waiting` keys and both tool keys keep `:running` = slot-use proxy, `:blocked` = waiting signal (backward compat).
- **Capacity totals & the 10-tick config cache**: `llm_capacity` = Σ per-profile `concurrency`, `tool_capacity` = `max_tool_concurrency`, from a direct BOUNDED scheduler call for `:get_config` (2s via `safe_scheduler_call/1`, seam `:system_sampler_config_fun`) — deliberately NOT `RemoteAPI.get_config/0` (its implicit 5000 ms timeout is exactly the crash this module must not inherit) and NOT `Config.resolve/0` (re-reads disk, MISSES runtime overrides). Cached as `config_cache: {totals, tick}`, refreshed on the `rem(tick, 10) != 1` rule — tick 1 always loads; an unloaded cache refetches every tick until an attempt succeeds or fails.
- **Busy-scheduler degradation (a live-but-wedged scheduler must not crash the sampler)**: both scheduler reads go through `safe_scheduler_call/1` — an explicit 2s bound (deliberately < the 3s tick cadence, so a wedged scheduler costs at most ONE degraded sample) plus `catch :exit` (call timeout, the whereis→call `:noproc` race, a mid-call crash) — the module's single justified cross-GenServer try/catch. A config-refresh failure KEEPS the last cached totals (zero fallback when none yet) so the sample still broadcasts the exact 13-key shape; an `llm_slots` failure broadcasts `llm_slots: %{}`. Failures log a rate-limited `Logger.warning`; recovery is automatic.
- **Dead-scheduler branch**: when `scheduler_alive?/0` is false the sample has zero counts, zero capacities AND `llm_slots: %{}` with `scheduler_alive: false`; zero capacities are NEVER cached (that would suppress the refresh for 10 ticks after the scheduler returns). Broadcasts continue.
- **Ring buffer**: last 60 samples in state. `get_recent_samples/0` → `{:ok, samples}` | `{:error, :not_found}` (guarded by `Process.whereis(__MODULE__)` — converts the `:noproc` exit into a returned error).
- **RPC surface**: `RemoteAPI.get_recent_system_samples/0` → `{:error, :sampler_down}` when the sampler is not running, else the delegate result; `RemoteNode.get_recent_system_samples/1` routes local → RemoteAPI direct / remote → `:erpc`, passing all three shapes verbatim.

## SandboxSlice — Bounded systemctl Slice Updates (`EvoGit.SandboxSlice`)

`sandbox_slice.ex` — owns the live `evogit.slice` resource-limit property writes (`systemctl --user set-property evogit.slice CPUWeight=… MemoryMax=… TasksMax=…`) for systemd-run sandboxing; started in `EvoGit.Application` on Linux whenever the systemd backend is selected (all real-execution paths gate on `@mix_env == :test` first — disabled path in tests).
- **Every systemctl invocation is time-bounded**: `run_systemctl_bounded/4` (`@doc false`, public for tests) runs the command in a separate unlinked MONITORED process with a hard `@systemctl_timeout_ms` 5000ms bound (app-env seam `:sandbox_slice_systemctl_timeout_ms`, read per call); on timeout the runner process is killed — closing its OS ports terminates the client-side subprocess (safe for set-property: a single DBus invocation, idempotent last-write-wins, no partial-limit corruption) — and `{:error, :timeout}` is returned; a raising runner returns `{:error, {:runner_crashed, reason}}`. Runner seam: `:sandbox_slice_systemctl_fun` (default `EvoGit.Sandbox.Helpers.system_cmd/2`).
- **Two client entry points**: `update_resources/1` (synchronous 10s `GenServer.call`, kept for direct callers, now internally bounded) and `update_resources_async/1` (fire-and-forget `GenServer.cast`, `:ok` even when the GenServer is not running; the `handle_cast` stores the resources and applies them only while `state.slice_active`, logging its own success/failure).
- **Scheduler integration**: `AgentScheduler`'s config-update path propagates `:sandbox_resources` via `update_resources_async/1` — the scheduler NEVER blocks on slice work (a synchronous update stalled the scheduler ~7s on a wedged systemd user bus; design note: `agent_scheduler/CONTEXT.md`).
- The slice is created at SandboxSlice init and by `ensure_slice` before every sandboxed run (`sandbox/linux.ex`); property updates only ever write absolute limits on an already-active slice — never create or stop it.

## Peak/Off-Peak Diagnostics (diagnosing a task that stays blocked after peak exit)

Scenario: a profile with `concurrency: 5`, `peak_concurrency: 0` (hard pause) and peak windows; a task launched in-window blocks (0 LLM slots → request enqueues, agent `:blocked`) and stays blocked afterwards. The log lines below separate the four failure classes — **engine never woke** / **woke but didn't apply** / **applied but waiter never granted** / **waiter granted but agent stuck elsewhere**. Read in this order:

1. **`PeakHourEngine: wakeup reason=… now=… utc_now=… scheduler_up=…`** (info, every check). `reason` = `:boot | :timer | :broadcast | :manual` (threaded in for logging ONLY — no timing/floor/fixed-point impact). A missing post-window `:timer` wakeup means the engine never woke (dead timer / wrong transition math).
2. **`PeakHourEngine: decision=applying|unchanged effective=… current=…`** (info). `unchanged` with the post-window map already equal to `current` means it woke but computed nothing new (look at the *previous* apply); `applying` with `effective=%{"m" => 0}` means it still believes it is in peak — clock/window/timezone bug.
3. **`PeakHourEngine: next wakeup in <ms>ms … transitions=[{id, tz, wall_transition}]`** (info) — per-profile next transition wall-clock times ("tomorrow instead of today" is visible here); the 6h safety-net fallback is flagged explicitly when none was computable.
4. **`AgentScheduler: model_concurrency updated — old=… new=… skip_floor=… default_llm_max_concurrency=…`** (info) — every `update_config(model_concurrency:)` incl. the engine's apply, showing the POST-application (post-floor / verbatim-for-skip_floor) map. `old` equal to `new` after the window means the apply never happened (see 2).
5. **`AgentScheduler: LLM slot grant sweep (resume) — model=… capacity=… waiting_before=… granted=… waiting_after=…`** (info on meaningful events, debug on empty no-op sweeps) — per-model sweep on every config update / resume. `capacity=N granted=0 waiting_after>0` is exactly **"applied but queued waiter never granted"**; `granted=N` means N waiters were unblocked.
6. **`PeakHourEngine: starting — watched profiles: …`** (info, `init/1`) — boot-time per-profile summary (id, concurrency, peak_concurrency, peak_hours, timezone) so a misconfigured profile is visible immediately.

Debug-level per-agent events (`slots.ex`): `LLM slot request ENQUEUED — agent=… model=… capacity=0 (peak pause)` at the 0-capacity enqueue point, `granted LLM slot — agent=… model=…` at each queue grant, and `purged N LLM waiter(s) for model …` at each cancel/force-kill purge. `PeakHourEngine: scheduling 6h safety-net wakeup` (info) marks the no-profiles / scheduler-down path.

Logging-only: `EvoGit.PeakHours` (pure) and every engine/scheduler log site imply no behavior, timing, floor or fixed-point change; `peak_hour_engine_test.exs` pins the fixed-point invariant (no "applied model concurrency" log on no-op re-checks). Detail: `./agent_scheduler/CONTEXT.md`.
