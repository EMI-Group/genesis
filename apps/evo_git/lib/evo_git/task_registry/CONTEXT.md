# TaskRegistry Support Modules

## Intent

Support modules extracted from `EvoGit.TaskRegistry` GenServer to keep the main module focused. These are pure-function or ETS-only modules — none maintain their own GenServer state. They were migrated from `evo_dash` to `evo_git` as part of the domain persistence layer migration.

## Routing Table

None — leaf directory (all modules at this level).

## API Surface

| Module | File | Purpose |
|--------|------|---------|
| `EvoGit.TaskRegistry.Cleanup` | `cleanup.ex` | Expires finished tasks by configurable age (14d default) and count (100 default). SQL-pushdown cleanup: `cleanup_expired_tasks/1` reads only task ids via `Store.select_cleanup_info/3` (age cutoff + count trim in SQL), deletes via `delete_tasks/2`. |
| `EvoGit.TaskRegistry.Diagnostics` | `diagnostics.ex` | Failed-transition diagnostic logging with greppable prefix (`"TaskRegistry: FAILED_TRANSITION"`) and captured stacktraces. Pure Logger/Process.info functions — no GenServer state dependency. |
| `EvoGit.TaskRegistry.Lease` | `lease.ex` | Lease validity checks and `:evogit_sched_meta` ETS helpers: `sched_meta_has_active_agents?/1` (cross-VM liveness detection), `lease_valid?/1` (expiry check), `best_effort_result/1` (result lookup). All ETS access guarded by `:ets.info/1` (non-crashing). |
| `EvoGit.TaskRegistry.MergeContext` | `merge_context.ex` | Merge-conflict-resolution context builder: `apply_merge_context/4` (opts → opts; strips `:merge_from`/`:merge_target`, loads the previous task, overrides `:starting_commit` with its end commit, carries over `:foreign_repos`, prepends the context block to the objective) and `build_merge_context_block/2` (task id, shas, branch, merge target, goal, hints). Fallback: nil previous task → stripped opts unchanged. |
| `EvoGit.TaskRegistry.RuntimeOpts` | `runtime_opts.ex` | Keyword-list builder for `EvoGit.Runtime.*` modules. Threads mode atoms, `model_id`, `build_system`, `archive`, `foreign_repos`, `starting_commit`, `node_path` into runtime opts. |
| `EvoGit.TaskRegistry.ResumeContext` | `resume_context.ex` | Assembles a "Previous Task Context" block (commits, objective, result summary) prepended to the objective when an evolve task resumes from a prior task. Sets `:starting_commit` from the prior task's `commit_sha`. |
| `EvoGit.TaskRegistry.TaskExecutor` | `task_executor.ex` | Execution entry points: `:genesis` → `Runtime.Genesis.run`, `:evolve` → `Runtime.Evolution.run`, `:extract_skills` → `Runtime.SkillExtraction.run`. Runs in spawned processes under `Task.Supervisor`, registers tasks in `ProcessRegistry`. |

## Constraints

- All modules are pure functions or ETS-only — no GenServer state, no I/O (aside from `Cleanup` which calls `EvoGit.Store` for deletion).
- `Lease` module: all ETS access uses `:ets.info/1` first (returns `:undefined` for missing tables), avoiding `try/rescue`.
- `Diagnostics`: logging only — never modifies state or raises.
- `TaskExecutor`: runs OUTSIDE the GenServer process (under `Task.Supervisor`).
- `RuntimeOpts` and `ResumeContext`: pure builders — no side effects.

## Restart Recovery & Status Transitions

**Startup reconciliation of orphaned `:finalizing` and `:cancelling` tasks.** `TaskRegistry.init/1` (`task_registry.ex:252-289`) reconciles orphaned non-terminal tasks directly: it runs the lightweight query `EvoGit.Store.select_running_lease_info/1` (id+status+lease_expires_at, SQL-filtered to `status IN ('running','finalizing','cancelling')`), filters Elixir-side, and for each `:finalizing` or `:cancelling` row synchronously calls the shared `handle_update_status/6` with `{:startup_reconcile, ...}` caller info — `:finalizing` → `:failed` with result `"Runtime restarted during task finalization"`, `:cancelling` → `:cancelled` with `"Runtime restarted during task cancellation"`. The handler performs the narrow `select_task_update_info/1` read (status/opts/finished_at/lease_expires_at — no full struct decode), the stale-guard (`:finalizing`/`:cancelling` are non-terminal so the transitions pass), `Diagnostics.log_failed_transition`, finished_at/lease_expires_at handling, the `{:tasks_updated}` broadcast, and task_refs cleanup. The writes are SYNCHRONOUS in init (NOT via the async `update_task_status/4` cast, which would race callers). This covers the crash window where slow git calls in `merge_and_report/3` hang while the task sits at `:finalizing` (or a graceful cancel is interrupted) and the app dies before the terminal write. Other properties:
- `state.task_refs` is in-memory only — after restart it's empty, so the `{ref, result}` handler and `{:DOWN, ...}` handler can never fire for pre-restart tasks (hence the init reconciliation above).
- `:heartbeat` renews leases only for owned tasks with `status in [:running, :pending, :cancelling]` — never `:finalizing`.
- `:lease_sweep` (one-shot, fires `@sweep_after` = 150s after init) filters `status == :running and id not in owned_ids and not Lease.lease_valid?(lease)` — **`:finalizing` is excluded by design**: init already handled it, and `:running` stays the sweep's job (it respects lease validity for the legitimate multi-VM case).
- `:periodic_cleanup` → `Cleanup.cleanup_expired_tasks/1` only deletes tasks with `finished_at != nil` (that filter lives in SQL inside `select_cleanup_info/3`); `:finalizing` tasks have `finished_at == nil` (set only for terminal transitions) → never deleted.
- `{:recheck_task, task_id}` would resolve a `:finalizing` task (its guard only excludes terminal statuses), but **nothing schedules the first recheck** — only self-rescheduling — so the handler is unreachable in practice.

**Resolution paths for a `:finalizing` task:** (a) **at startup** — init reconciliation marks it `:failed` (above); (b) explicit user action — `clear_finished_tasks` uses `select_finished_task_ids` (SQL `status NOT IN ('running','pending','cancelling')` — **`SELECT` includes `:finalizing`**) and DELETEs them, or `delete_task`; (c) in-process only: wrapper completion → `{ref, result}` (`{:ok,_}`→`:completed`, error/exit→`:failed`), wrapper crash → `:DOWN` (`:normal`→`:completed`, abnormal→`:failed` only if `Lease.sched_meta_has_active_agents?` is false), or the public `update_task_status/4` cast (stale-guard blocks terminal→terminal changes except to `:completed`). `cancel_task` does not work from `:finalizing` — it returns `{:error, :not_running}` for it (graceful cancel works from `:pending` and `:running`). **Lease expiry plays NO role in resolving `:finalizing`** — a stuck-but-alive `:finalizing` wrapper just stops getting lease renewals (heartbeat skips it) and stays `:finalizing` until the wrapper process finishes/dies or the runtime restarts.

**Unreachable code:** `Lease.lookup_sched_meta_result/1` is used only by `resolve_recheck_task/3` (task_registry.ex:988), whose `{:recheck_task, _}` handler is never triggered (nothing schedules the first recheck).

**Cleanup semantics:** `Cleanup.cleanup_expired_tasks/1` never changes status — it only DELETEs, with age cutoff (`finished_at < cutoff`) and count trim (`max_tasks` newest kept) both pushed down to SQL via `Store.select_cleanup_info/3`; `config` defaults `max_tasks: 100, max_age_days: 14` (`cleanup.ex:13`).

**Lease mechanics:** `@lease_duration 120` s, `@heartbeat_interval 60_000` ms, `@sweep_after (@lease_duration + 30) * 1000` ms (`task_registry.ex:37-42`). Lease set at start, renewed by heartbeat via `Store.update_lease_expires_at`. The one-shot `:lease_sweep` marks expired `:running` foreign tasks `:failed` only when `sched_meta_has_active_agents?` is false, then runs cleanup + broadcasts.

**TaskExecutor structure:** `start_task` (handle_call `:start_task`, task_registry.ex:312-360) does `Task.Supervisor.async_nolink(EvoGit.TaskSupervisor, TaskExecutor, :execute_task, [task_type, opts, task_id])`. The wrapper process IS the executor — `TaskExecutor.execute_task/3` (`task_executor.ex:20-71`) registers itself in `EvoGit.TaskRegistry.ProcessRegistry` and calls the runtime phase directly (Genesis.run, Evolution.run, SkillExtraction.run). **The wrapper never writes statuses** — TaskRegistry's GenServer performs all writes from `{ref, result}` / `:DOWN` / PubSub `{:task_status, ...}` / `update_status` casts; `handle_update_status` writes via `EvoGit.Store.update_task_columns` and deletes terminal tasks from `task_refs`.

## Graceful Cancellation & Force Kill

**Task status `:cancelling`** — the graceful-cancel state, deliberately **NON-terminal**: the `task_refs` entry stays, `finished_at` stays nil, and the lease stays valid (the heartbeat renews it). Touched in:
- `Store.Codec.@known_atoms` (`store/codec.ex:217-219`) — `:cancelling` is a whitelisted status atom; the `task_info.ex:31` typespec includes it.
- `Store.select_finished_task_ids` (`store.ex:634`) — SQL `status NOT IN ('running','pending','cancelling')`, so `clear_finished_tasks` never deletes an in-flight cancelling task; `:finalizing` still counts as finished (cleanup target).
- `Store.select_running_lease_info` (`store.ex:682`) — SQL `status IN ('running','finalizing','cancelling')`, so startup reconciliation can resolve orphaned cancelling tasks.
- **Startup reconciliation** (task_registry.ex:252-289) — `:cancelling` → `:cancelled` ("Runtime restarted during task cancellation") alongside `:finalizing` → `:failed`, both via synchronous `handle_update_status/6` with `{:startup_reconcile, ...}` caller info (a runtime that died mid-cancel must not leave a task `:cancelling` forever).
- **Heartbeat lease renewal** (`task_registry.ex:1316-1346`) — `[:running, :pending, :cancelling]`, so a long graceful cancel keeps its lease while the wrapper is still alive.
- **`{:task_status, :finalizing}` handler** (task_registry.ex:1105-1120) — a `:cancelling` task ignores phase-finalization broadcasts (keeps the more informative `:cancelling`; the final mapping happens at result time).
- **`handle_update_status/6` final-result force-mapping** (task_registry.ex:841-850) — stored `:cancelling` + incoming `:completed | :failed` → persisted `:cancelled`; result/usage/archive flow through untouched (never nil'd), so the agent's final summary is preserved.

**`TaskRegistry.cancel_task/1` is GRACEFUL** (public `:92-94`, handler `:486-544`):
- `:pending` → immediate `:cancelled` write (finished_at set, lease cleared); the `start_task` guard refuses already-`:cancelled`/`:cancelling` tasks with `{:error, :cancelled}` (`:312-319`).
- `:running` → `handle_update_status(..., :cancelling, ...)` (broadcasts `{:tasks_updated}`; non-terminal so finished_at/lease/task_refs stay) then `AgentScheduler.begin_graceful_cancel(task_id)` (cross-GenServer call, catch `:exit` guarded — a down scheduler leaves the task `:cancelling` for force_kill or restart reconciliation).
- `:cancelling` → `:ok` idempotent (does NOT re-send the cancel message — agents already hold it).
- terminal (`:completed`/`:failed`/`:cancelled`) or `:finalizing` → `{:error, :not_running}`; missing → `{:error, :not_found}`.

**`TaskRegistry.force_kill_task/1`** (public `:111-113`, handler `:402-454`) — the brutal cancellation path: status gate `:running | :cancelling` (escalation path for a hung graceful cancel) → `AgentScheduler.force_kill_task_agents(pid)` (reverse-depth `:brutal_kill` cascade, catch `:exit`) + `Task.shutdown(ref, :brutal_kill)` + direct terminal write (`:failed`, finished_at set, lease nil, result nil — a force-killed task is persisted as `:failed`, never `:cancelled`; `:cancelled` means ONLY graceful cancel) + `clear_cancelling_marker(task_id)`.

**Marker cleanup** — `clear_cancelling_marker/1`: prefers `AgentScheduler.clear_cancelling_task/1` (serialized GenServer, can't race `begin_graceful_cancel`), falls back to a direct `:ets.delete(:evogit_cancelling_tasks, task_id)` when the scheduler is down (TaskRegistry starts BEFORE the AgentScheduler in the supervision tree, e.g. during startup reconciliation). Called from every terminal transition (`handle_update_status/6`, the `{:task_status, ...}` handler, and force_kill).

## SQL-Lowering Analysis

**Cleanup (`cleanup.ex`):**
- `cleanup_expired_tasks/1` (cleanup.ex:31) reads only task **ids** via `EvoGit.Store.select_cleanup_info/3`: the age cutoff (`AND finished_at < ?cutoff`) and over-limit keys (`ORDER BY finished_at DESC LIMIT -1 OFFSET ?max_tasks`) are both pushed down to SQL. No row decode and no Elixir-side sort/filter remain; deletion goes through `delete_tasks/2`.
- **ISO-8601 lexicographic caveat**: `finished_at` is stored as an ISO-8601 string, and SQLite string comparison is only order-correct for consistently-formatted values. The pushdown relies on the fixed-precision 24-char format emitted by `EvoGit.Store.Codec.encode_datetime/1` (`DateTime.truncate(:millisecond)`) for the cutoff; legacy formats are normalized by the manual `mix migrate.store` task (documented in store/CONTEXT.md).
- `delete_tasks` (store.ex:527-550) uses chunked `DELETE FROM tasks WHERE id IN (...)` (~500 ids/chunk, all-or-nothing per chunk).

**`select_running_lease_info`** (store.ex:682) queries `WHERE status IN ('running','finalizing','cancelling')` (SQL pushdown cuts decoded rows); callers still filter Elixir-side afterwards: init reconcile `status == :finalizing`/`:cancelling` (task_registry.ex:263-289) and lease_sweep `status == :running`. The `id not in owned_ids` (in-memory task_refs) and lease-expiry-vs-wall-clock parts must stay Elixir-side.

**ResumeContext** (`resume_context.ex:24`) → `TaskRegistry.get_task` → `Store.get_task/2` decodes the FULL 18-column row (including heavy JSON blobs logs/result/usage/archive_metadata) when only `base_sha` (`resume_context.ex:44`), `opts` and `result` are used. A lightweight variant (mirroring `select_tasks_summary`) would avoid the heavy decodes — low priority: single-row point lookup on an infrequent resume-from path.

**No Store access at all:** `lease.ex` (ETS-only; `sched_meta_has_active_agents?/1` at lease.ex:17-29 does a full `:ets.tab2list` scan — could be `:ets.select`, but that's ETS not SQL), `diagnostics.ex` (pure Logger/Process.info), `runtime_opts.ex` (pure builder; only `Application.ensure_all_started(:evo_git)`), `task_executor.ex` (no Store calls; reaches Store only transitively via ResumeContext).

**Full inventory of `EvoGit.Store.` (SQLite) callers in `apps/evo_git/lib`:** only `task_registry.ex` (main GenServer — ~28 call sites) and `task_registry/cleanup.ex` (`select_cleanup_info/3` + `delete_tasks/2`). **No other module** in evo_git or evo_dash calls the SQLite Store directly — `agent_scheduler/*` `Store.` references are `EvoGit.AgentScheduler.Store` (the ETS store, a DIFFERENT module).

**Related Elixir-side sorting outside this node** (task_registry.ex, for completeness): `trim_recent_projects` (task_registry.ex:649-663) + `sort_projects_by_recency` (`:668-675`) fully decode all projects (`safe_select_all_projects`) and sort in Elixir — SQL `ORDER BY last_opened_at DESC` + `LIMIT` would apply, with the same ISO-8601 ordering caveat.

## Known Issues

- **⚠️ Memory scales with `tasks.sqlite` size — the summary-query path (NOT init).** `TaskRegistry.init/1` and the GenServer's retained state (`task_refs` = running tasks only) are clean — no full-table load at startup. The O(N) memory mechanism (N = DB rows) is the **dashboard-driven summary-query path**:
  1. `Store.select_tasks_summary*` / `select_tasks_changed_since` decode every matching row's `opts` JSON. (`result` is deliberately NOT in the 15-column summary projection, so the heavy `Codec.decode_result` — which parses the full result blob embedding `archive_records` + usage — never runs in the summary path.)
  2. `TaskRegistry`'s `:list_tasks_summary` / `:list_tasks_summary_by_path` / `:list_tasks_changed_since` handlers (task_registry.ex:587-624) run the Store call on a `Task.start` + `GenServer.reply` process, and the Store's own summary handlers (store.ex:843-878) do the same — no large decoded terms are retained on either GenServer heap (the linked Task preserves the crash-on-decode-raise behavior).
  3. The dashboard re-fetches the sidebar summaries on every task-status broadcast (300 ms trailing-edge debounce via `NodeAware.debounce_task_reload/1` → `:node_aware_reload_tasks` → `NodeAware.reload_tasks/1` → `load_running_and_pending_tasks/1` — a statuses-filtered summary, NOT a full scan) and every ProjectsLive session retains the summary maps (15-key, `result` dropped; `opts` remains) in socket assigns (`:running_tasks`, `:pending_tasks`) for its whole lifetime (see apps/evo_dash/lib/CONTEXT.md "Memory Profile").
  Net effect: retained BEAM memory ≈ O(rows × opts-blob size) — correlates with `tasks.sqlite` size (`periodic_cleanup` caps finished rows at `max_tasks: 100` but each row can be multi-MB). Remaining cost drivers: the `:completed` inclusion in `assign_running_and_pending_tasks/1` (review candidates need completed rows — a `since` window would bound it), the per-row `opts` decode, and dashboard assign retention. Nothing loads the DB into memory at boot.

## Store SQLite Optimization

- **Row-recovery machinery**: undecodable rows are SKIPPED with a `Logger.warning` ("Store: skipping undecodable row in ...") — there are no recovery tables, no per-start repair routine, and no manual `mix` recovery task. Design rationale: SQLite WAL mode does not corrupt rows. Applies to `safe_select_all_tasks/1`, `safe_select_all_projects/1`, `safe_select_paginated_tasks/2` and the summary reads (`select_tasks_summary` / `select_tasks_summary_by_path` / `select_tasks_changed_since`).
- **Schema upgrades**: `Store.init/1` runs ONLY `Schema.create_tables/1` (fresh DBs get the full schema). Existing DBs are upgraded by the manual **`mix migrate.store`** task (`Mix.Tasks.Migrate.Store`), which applies schema migrations (adds the `updated_at` column to `tasks`, etc.) and normalizes legacy timestamp formats. The task is standalone — it never starts the `:evo_git` application.
- **Extended summary API**: `EvoGit.Store.select_tasks_summary(store \\ __MODULE__, statuses \\ [], since \\ nil)` / `select_tasks_summary_by_path(store \\ __MODULE__, project_path, statuses \\ [], since \\ nil)` — `statuses` is a list of status atoms, `[]` = all statuses (SQL pushdown); `since` is an optional fixed-precision ISO-8601 string that pushes `AND updated_at > ?N` into SQL (nil = no filter). The SELECT projection includes scalar columns `branch_name, model_id, agent_count, base_sha, commit_sha, lease_expires_at` plus `updated_at` (raw fixed-precision ISO string, NOT decoded — heavy columns logs/usage/archive_metadata and `result` stay out). Summary map keys (15): id, status, review_status, started_at, finished_at, type, project_path, opts, branch_name, model_id, agent_count, base_sha, commit_sha, lease_expires_at, updated_at. Pass-throughs: `TaskRegistry.list_tasks_summary(statuses \\ [], since \\ nil)` + `list_tasks_summary_by_path(path, statuses \\ [], since \\ nil)`; `AgentScheduler.RemoteAPI.list_tasks_summary/1` + `list_tasks_summary_by_path/2` (no-arg forms kept for old RPC callers); `EvoGit.RemoteNode.list_tasks_summary/2` + `list_tasks_summary_by_path/3` over `:erpc`. **⚠️ `since` is NOT exposed through RemoteAPI/RemoteNode** — the RPC layers only accept `statuses`; remote callers needing a time filter must use `list_tasks_changed_since` (which accepts no statuses). Only the local `TaskRegistry`/`Store` calls can combine statuses + since.
- **Changed-since API (polling)**: `Store.select_tasks_changed_since(store \\ __MODULE__, since_iso)` returns summary-shaped maps (same 15-key projection incl. `updated_at`) for rows with `updated_at > since_iso` (fixed-precision string comparison — no heavy columns). Chain: `TaskRegistry.list_tasks_changed_since/1` → `AgentScheduler.RemoteAPI.list_tasks_changed_since/1` → `EvoGit.RemoteNode.list_tasks_changed_since/2` (over `:erpc`; `[]` on RPC failure).
- **Summary-handler offload**: `TaskRegistry`'s `:list_tasks_summary` / `:list_tasks_summary_by_path` / `:list_tasks_changed_since` handlers (task_registry.ex:587-624) use the `Task.start` + `GenServer.reply` offload pattern (same as `:list_tasks` / `:list_tasks_paginated` / `:list_tasks_by_path`) — large decoded terms are allocated/discarded on a short-lived Task process's heap, not the TaskRegistry GenServer's. The Store's own heavy full-decode handlers (`select_all_tasks`, `safe_select_all_tasks`, `safe_select_paginated_tasks`, `select_tasks_summary`, `select_tasks_summary_by_path`, `select_tasks_changed_since`) run the query AND the decode on a short-lived LINKED `Task.start` replying via `GenServer.reply/2`, so decoded terms are allocated/discarded on the Task heap, not the Store GenServer's; the link preserves the crash-on-decode-raise behavior, and the skip-and-log boundary (`decode_skipping_bad`) plus `_ -> []` query-failure arms run inside the Task. Single-row/tiny handlers (`get_task`, `select_task_logs` / `update_info`, id-only projections, counts, projects ≤10 rows) stay synchronous.
- **Disk-full write handling**: SQLite disk-full-class write errors (`SQLITE_FULL` 13, `SQLITE_IOERR` 10, `SQLITE_READONLY` 8) are detected at the write boundary by the pure classifier `EvoGit.Store.Errors.disk_full_error?/1` (matches `{:sqlite_failure, code, _, _}` with code 8/10/13, `{:read_only_database, _, _}`, plus the canonical "database or disk is full" message fallback) and converted to `{:error, :disk_full}` by the shared private `execute_write/4` — the GenServer survives, reads keep working, writes can be retried; every other write error raises (crash + supervisor restart behavior). All 8 write functions (`put_task`, `delete_task`, `delete_tasks`, `clear_tasks`, `update_lease_expires_at`, `update_task_columns`, `put_project`, `delete_project`) return `{:error, :disk_full}` on the disk-full class (success shapes unchanged). TaskRegistry + Cleanup degrade gracefully at all 14 write call sites (log+continue for casts/heartbeat/log-loss; `{:error, :disk_full}` from `force_kill_task` / `cancel_task` / `clear_finished_tasks`; in-memory terminal cleanup always runs). Full contract + xqlite error shapes in `store/CONTEXT.md` → "Disk-Full Handling".
- **Narrow-read Store functions**: `select_task_logs(store \\ __MODULE__, task_id)` (SELECT logs, decoded list or nil) and `select_task_update_info(store \\ __MODULE__, task_id)` (SELECT status, opts, finished_at, lease_expires_at → map or nil). TaskRegistry hot paths — `append_log`, `set_review_status`, `set_review_metadata`, `handle_update_status` / `update_task_status_with_caller`, `cancel_task`, `resolve_recheck_task` — use these narrow reads + `update_task_columns` instead of full `task_get` decodes.

## Merge-Conflict-Resolution Flow (MergeContext / TaskExecutor)

- **Only trigger point**: `TaskExecutor.execute_task(:evolve, opts, task_id)` (task_executor.ex:28-62) runs a merge-context step BEFORE the `resume_from` handling: when `opts[:merge_from]` is a non-empty binary (trimmed), it calls `MergeContext.apply_merge_context(opts, task_id, trimmed_merge_from, opts[:merge_target])` and reassigns `opts`; otherwise opts pass through unchanged. The rest of the flow (resume handling, `RuntimeOpts.build_common_runtime_opts`) then runs on the transformed opts — merge keys are already stripped, and `resume_from` is not passed in this flow.
- **`apply_merge_context(opts, _task_id, merge_from, merge_target)`** (merge_context.ex): strips `:merge_from`/`:merge_target` FIRST (never leak into runtime opts) → `prev_task = EvoGit.TaskRegistry.get_task(merge_from)` (full `%TaskInfo{}` decode). **prev_task nil** → stripped opts returned unchanged. **prev_task found** → `:starting_commit` overridden with `prev_task.commit_sha` when it's a non-empty binary (caller's own value preserved otherwise) → `:foreign_repos` carried over from `prev_task.opts` when present/non-nil → `:objective` = `build_merge_context_block(prev_task, merge_target) <> "\n\n" <> old_objective`. Pure opts-transforming function (keyword in, keyword out — no RuntimeOpts call; returns opts, NOT a `{objective, runtime_opts}` tuple like ResumeContext).
- **`build_merge_context_block(%TaskInfo{}, merge_target)`** (merge_context.ex): returns a "Merge Conflict Resolution Context" string delimited by `--- Merge Conflict Resolution Context ---` / `--- End Merge Conflict Resolution Context ---`. Contents: `Previous task id: <id>`; `Base sha: <base_sha>` (omitted when nil/empty) and `End (commit) sha: <commit_sha>` (omitted when nil/empty — block is still emitted with the other fields when neither is available); `Task branch name: <branch_name || "unknown">`; `Merge target branch: <merge_target || "unknown">`; a `Goal:` paragraph (merge the target branch into the worktree via `git merge <target>`, resolve ALL conflicts by combining both sides, commit, then continue developing until coherent); a `Hints:` section with 3 bullet points (commit conflict resolutions before delegating follow-up work — subagents spawn at clean checkouts so uncommitted changes are invisible; inspect `git log/diff <base>..<end_sha>` for the task's own changes and `git log/diff <base>..<target>` for the target side since the base — ranges interpolated from the shas when available, placeholder fallbacks otherwise; incremental milestone merges OR rough-resolve-then-develop-on-top as fallback strategies). Fallback clause `build_merge_context_block(_, _), do: ""` for non-struct input.

## Resume-From Flow (ResumeContext / TaskExecutor / RuntimeOpts)

- **Only trigger point**: `TaskExecutor.execute_task(:evolve, opts, task_id)` (task_executor.ex:27-41) calls `ResumeContext.apply_resume_context/3` when `opts[:resume_from]` is a non-empty binary after `String.trim/1`. Non-resume evolve tasks build `{objective, runtime_opts}` directly (`objective = Keyword.get(opts, :objective, "")`).
- **`apply_resume_context(opts, task_id, resume_from_id)`** (resume_context.ex:20-60): strips `:resume_from` (never leaks into runtime opts) → `prev_task = EvoGit.TaskRegistry.get_task(resume_from_id)` (FULL 18-column row decode — known inefficiency, low priority). **prev_task nil** → original objective (`Keyword.get(opts, :objective, "")`), `build_common_runtime_opts` with opts unchanged (a caller-provided `:starting_commit` still flows through). **prev_task found** → `context_block = build_resume_context_block/1`; objective becomes `context_block <> "\n\n" <> objective` only when the block is non-empty; `:starting_commit` is **overridden** with `prev_task.commit_sha` when it's a non-empty binary (a caller-provided starting_commit is silently dropped in that case), otherwise the caller's own value (if any) passes through — then `build_common_runtime_opts(opts_with_commit, task_id, :evolve)`.
- **Context block exact format** (resume_context.ex:67-133): `"--- Previous Task Context ---\n" <> Enum.join(parts, "\n\n") <> "\n--- End Previous Task Context ---"` — empty string when `parts == []`. Parts are joined with **blank lines** (sections never run together). Part 1 (single line): `"Previous task commits: #{base_sha}..#{commit_sha}"` (both non-empty; falls back to just `commit_sha` when base_sha empty/nil; omitted when commit_sha empty). Part 2 (multi-line, delimited): `"Previous task objective:\n<<<BEGIN OBJECTIVE>>>\n#{old_objective}\n<<<END OBJECTIVE>>>"` (objective from `prev_task.opts` keyword `:objective` || `:prompt`, only when list and non-empty). Part 3 (multi-line, delimited): `"Previous task result:\n<<<BEGIN RESULT>>>\n#{summary}\n<<<END RESULT>>>"` (summary omitted when `extract_result_summary/1` returns nil or `""`). The `<<<BEGIN ...>>>`/`<<<END ...>>>` markers wrap arbitrary (possibly multi-line) content so the agent can never confuse a label with its content or the content with the outer fence; the triple-angle-bracket all-caps form is chosen so no plausible agent-generated text collides with it. `extract_result_summary/1` (resume_context.ex:135-142): `{:ok, %{result: s}}` binary → passthrough, atom → `to_string/1`; `{:error, reason}` → `"Error: #{inspect(reason)}"`; `{:exit, reason}` → `"Exited: #{inspect(reason)}"`; anything else → nil (part omitted).
- **SHA provenance**: `prev_task.commit_sha` is populated at task completion by the `{ref, result}` handler extracting `{:ok, %{commit_sha: sha}}` from the runtime result (task_registry.ex:1226-1230; the runtime merge result carries `commit_sha: final_sha || base_sha`, runtime/helpers.ex:70). `prev_task.base_sha` is set ONLY by the review flow (`set_review_metadata/3` cast, task_registry.ex:792-801) — so for a never-reviewed task the commits_line is just the commit_sha.
- **`RuntimeOpts.build_common_runtime_opts(opts, task_id, task_type)`** (runtime_opts.ex:16-74) returns `{nil, runtime_opts}` (first element always nil). `:path` is REQUIRED (`Keyword.fetch!` — crashes without it); `mode` defaults to `"simple"`; base keys `[repo_path, mode: mode_atom(task_type, mode), task_id]`; conditionally appended only-if-truthy: `node_path`, `starting_commit`, `foreign_repos`, `archive`, `model_id` (non-nil and ≠ ""), `build_system`. **No default for `:starting_commit`** — when absent the runtime resolves HEAD itself (`Runtime.Helpers.resolve_starting_commit(repo_path, nil)` → `PhyloGraphNode.current_head/1`, runtime/helpers.ex:167-169); when present it must `git rev-parse` cleanly or evolution fails (helpers.ex:171-179). Mode atoms: genesis `"new"`/`"existing"`, evolve `"simple"`/`"custom"` — anything else raises `ArgumentError` (runtime_opts.ex:98-114); **genesis mode `"custom"` raises a SPECIFIC error** (`"custom mode is evolve-only; use an evolve task with mode \"custom\""`, runtime_opts.ex:110-111) instead of the generic invalid-mode raise, covering the dashboard string-mode path where a genesis task receives `mode: "custom"`. No concurrency key is built here.
