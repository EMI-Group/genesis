# TaskRegistry Support Modules

## Intent

Support modules extracted from `EvoGit.TaskRegistry` GenServer to keep the main module focused. Pure-function or ETS-only modules — none maintain their own GenServer state.

## Routing Table

None — leaf directory (all modules at this level).

## Process-Scoped Isolation Seam

`EvoGit.TaskRegistry.server/0` (task_registry.ex) resolves the registry name for the CURRENT process.
It returns the value stored under the `:evogit_task_registry_server` process dictionary key when present, otherwise the default registered name `__MODULE__`.
Every client function (`start_task/2`, `get_task/1`, `list_tasks/0`, `list_tasks_paginated/1`, `cancel_task/1`, `force_kill_task/1`, `update_task_status/4`, `update_task_log/2`, `set_review_status/2`, `set_review_metadata/3`, `list_tasks_by_path/1`, `list_tasks_summary/2`, `list_task_ids/1`, `list_tasks_summary_by_path/3`, `list_tasks_changed_since/1`, `get_unique_paths/0`, `delete_task/1`, `clear_finished_tasks/0`, `add_recent_project/2`, `list_recent_projects/0`, `remove_recent_project/1`) routes its `GenServer.call`/`GenServer.cast` through `server()`, read at CALL time and never cached.
`EvoGit.Store` needs no equivalent seam: every Store client function already takes an explicit `store` argument as its first parameter (default `__MODULE__`), and `start_link/1` already honours a custom `:name` (its `child_spec/1` forwards the same opts, though its child-spec `id` remains `__MODULE__`, so supervising multiple instances requires an explicit `id:` override).
An isolated instance is started with `EvoGit.TaskRegistry.start_link(name: <unique_atom>, task_store: <isolated_store_name>, data_dir: <tmp_dir>)` alongside a matching `EvoGit.Store.start_link(name: <isolated_store_name>, data_dir: <tmp_dir>)`; the app-global singletons are never started or stopped.
The registry captures its own registered name (`Keyword.get(opts, :name, __MODULE__)`) into its GenServer state and sets it under the `:evogit_task_registry_server` process dictionary key in `init/1`, then passes it as the 4th argument of the wrapper spawn, so `EvoGit.TaskRegistry.TaskExecutor.execute_task/4` sets the wrapper's process dictionary and in-wrapper callbacks (`MergeContext`/`ResumeContext` → `EvoGit.TaskRegistry.get_task/1`) resolve back to the SAME instance.
Setting the key in the registry's OWN process means its in-process self-casts (`update_task_status_with_caller/4` / `update_task_status/2` from the `{ref, result}` and `:DOWN` handlers) resolve `server/0` to THIS instance rather than the global singleton.
When `:evogit_task_registry_server` is unset in the calling process every seam read resolves to `__MODULE__`, so production behavior is byte-for-byte unchanged.
Callers that run in processes NOT descending from the task wrapper do not inherit the key and always target the default `__MODULE__` — the self-reflective `agent/tools/*` command handlers, `cli.ex`, `agent_scheduler/remote_api.ex`, and all evo_dash callers — so a test-side workstream must keep the suites that exercise them serialized against the global singleton.

## Constraints

- **Task-type atom whitelist in the SQLite Codec**: `EvoGit.TaskRegistry.start_task/2` is TYPE-AGNOSTIC — any atom passes to `TaskExecutor.execute_task/3` (the 3-arity form of `execute_task/4`'s `server \\ __MODULE__` default), which dispatches through the private `do_execute_task/3` clauses — one per type (`:genesis`, `:evolve`, `:extract_skills`, `:reflect`) and NO catch-all (unknown type raises `FunctionClauseError` in the spawned task → task `:failed`). The persisted `type` column round-trips `EvoGit.Store.Codec` whose `@known_atoms` whitelist (store/codec.ex:217-222) holds `genesis evolve extract_skills reflect` — `decode_atom` returns `nil` for non-whitelisted strings, so a NEW task type MUST be added to `@known_atoms` (and comment at codec.ex:206) or its tasks load back with `type: nil`. `TaskInfo.type` typespec (task_info.ex:29) is `atom() | nil`.
- **`:reflect` is repo-less**: `execute_task(:reflect, opts, task_id)` routes to `EvoGit.Runtime.SelfReflective.run(opts ++ [task_id: task_id])` WITHOUT `RuntimeOpts.build_common_runtime_opts` — that builder does `Keyword.fetch!(opts, :path)` → `KeyError` (reflect opts carry `:objective`, optional `:model_id`/`:source_root`, no `:path`). Runtime returns `{:ok, %{result: ..., commit_sha: nil, branch_name: nil, tag: nil}}`; TaskInfo rows persist `commit_sha`/`branch_name`/`project_path` nil.
- All modules are pure functions or ETS-only — no GenServer state, no I/O (except `Cleanup` → `EvoGit.Store` deletion, and `TaskExecutor` → `EvoGit.TaskTmpdir.ensure/2` per-task tmpdir creation).
- **Cleanup/reaping in the registry is SQLite-row-only — NO disk or `.genesis/` reaping.** Every startup/periodic reaping hook (init reconciliation :302-331, one-shot `:lease_sweep` :1566-1638, `Cleanup.cleanup_expired_tasks/1`, 5-min `:periodic_cleanup` :1643-1647, `clear_finished_tasks` :661-689, `delete_task` :780-795) only reads/deletes `tasks.sqlite` rows and clears the in-memory `task_refs` entry + the `:evogit_cancelling_tasks` ETS marker. None touches agent worktrees, `.genesis/workers`, or per-agent ETS rows — worktree reclamation is owned by `EvoGit.AgentScheduler.WorktreeManager` (monitor-driven `:DOWN` reclaim), outside this subtree.
- `Lease`: all ETS access uses `:ets.info/1` first (returns `:undefined` for missing tables), no `try/rescue`.
- `Diagnostics`: pure Logger/Process.info functions + the `failure_error/3,4` payload builder — never modifies state or raises; TaskRegistry persists the payload it builds into the `error` column.
- `TaskExecutor`: runs OUTSIDE the GenServer process (under `Task.Supervisor`).
- `RuntimeOpts` and `ResumeContext`: pure builders — no side effects.
- **`task_registry.ex` stays long by design**: the main `EvoGit.TaskRegistry` GenServer at `lib/evo_git/task_registry.ex` (~1577 lines) is the task-lifecycle state machine — status transitions, lease/heartbeat, graceful cancel + force kill, startup reconciliation, review-status handlers — deliberately kept cohesive as one module (same policy as the long `remote_api.ex`/`remote_node.ex` RPC wrappers); the reusable pure/ETS logic extracted out of it lives in this `task_registry/` directory.

## Per-Task Tmpdir Lifecycle

Each task owns ONE managed scratch directory shared by all of its agents (`EvoGit.TaskTmpdir` at `lib/evo_git/task_tmpdir.ex` — a PARENT-node file, read-only from this directory). Mode is `[tmp] mode` ∈ `:system` (`<system tmp>/genesis/task_<id>`, default), `:custom` (`<[tmp] path>/genesis/task_<id>`), `:per_repo` (`<task's primary repo>/.genesis/tmp/task_<id>`); a nil primary repo path (repo-less/`:reflect`) falls back to the system mode. Creation + reclamation both route through this module — nothing under `task_registry/` reaps tmpdirs directly except by calling it.

- **Create trigger (this directory)**: `EvoGit.TaskRegistry.TaskExecutor.execute_task/4` — the single entry point for ALL four task types — calls `ensure_task_tmpdir/2` (private) right after installing the `:evogit_task_registry_server` process-dictionary seam and BEFORE `do_execute_task/3` dispatches, so the dir exists before any agent can spawn a tool (genesis / evolve / extract_skills / reflect alike). `ensure_task_tmpdir/2` calls `EvoGit.TaskTmpdir.ensure(task_id, Keyword.get(opts, :path))`, discards the returned path, and returns `:ok`. `opts[:path]` is the task's PRIMARY repo (`Keyword.get/3`, never `Keyword.fetch!` — a nil/missing `:path` must not crash the wrapper and correctly falls back to system mode). `EvoGit.TaskTmpdir.ensure/2` is idempotent and NEVER raises (a filesystem failure is logged and the path is still returned), so there is no try/rescue.
- **Reclaim triggers (parent `lib/evo_git/task_registry.ex`)**: reclaim is **event-driven ONLY** — a task's `task_<id>` dir is removed by `EvoGit.TaskTmpdir.reclaim/2` (per-task) when that task reaches a terminal status: (1) the terminal reclaim in `handle_update_status/6` plus (2) the direct terminal write sites that bypass it — `force_kill_task/1`, `cancel_task/1`'s `:pending` arm, `:lease_sweep`, and `resolve_recheck_task/3`. There is NO boot reaper and NO periodic sweep. `reclaim/2` never deletes anything outside the managed root and never deletes the root itself; it is best-effort and never raises. The terminal reclaim in `handle_update_status/6` (task_registry.ex:1000-1009) is reached for EVERY final status in `[:completed, :failed, :cancelled]` — it reads the FINAL (post force-map) status, so a graceful-cancelled task that completes still reclaims; `:cancelling`/`:finalizing` are non-terminal and never reclaim.
- **Reclaim is event-driven only — there is NO age-based tmpdir GC**: `Cleanup.cleanup_expired_tasks/1` deletes SQLite task ROWS, never directories. Consequences/gotchas: (a) every terminal write now carries an explicit reclaim hook — `resolve_recheck_task/3` included — so no terminal transition skips reclamation; (b) a `task_<id>` dir orphaned by a full-runtime CRASH (no terminal status ever written) is NEVER reaped automatically in ANY mode — it requires manual cleanup; (c) `[tmp] mode` is re-resolved by `EvoGit.TaskTmpdir.mode/0` at RECLAIM time (never stored per task), so changing the mode mid-flight aims the terminal reclaim at a different root and can orphan the dir created under the old mode.

## Failed-Task Error Persistence (`TaskInfo.error`)

Every path that transitions a task to `:failed` records a structured error payload, persisted in the dedicated `error` column (JSON TEXT) and decoded onto `TaskInfo.error` (`map() | nil`) — visible in BOTH the full-decode paths (`Store.get_task/1`, `list_tasks_paginated/1` via `Codec.decode_task/1`) AND the 16-key summary projection (`error` decoded via the lenient `Codec.decode_error/1`; nil for non-failed rows — no heavy result decode). Payload shape is a fixed 4-key map with ATOM keys after decode: `%{kind: atom, source: atom, message: String.t(), stacktrace: [String.t()] | nil}`. Closed-set atoms: `kind` ∈ `:error | :exit | :down | :force_kill | :timeout | :restart | :lease_expired | :recheck`; `source` ∈ `:result_handler | :down_handler | :force_kill_task | :finalizing_watchdog | :startup_reconcile | :lease_sweep | :recheck_resolve`. Single producer = the pure `Diagnostics.failure_error(kind, source, message, stacktrace \\ nil)` builder (diagnostics.ex). Decode is lenient (nil / invalid JSON / non-object → nil — a corrupt cell can never break a row read). Graceful-cancel `:cancelled` is NOT a failure: no error is ever recorded there. In `handle_update_status/6` the `error:` opt is appended to `update_cols` ONLY when the FINAL persisted status is `:failed` (checked after the force-map that rewrites a stored `:cancelling` row + terminal status to `:cancelled`), so a force-mapped `:cancelled` row never carries an error even if a caller passed one.

Per-path mapping (what each failure site stores):
- **(a) wrapper result error/exit** (`handle_info({ref, result}, state)`, result-mapping case): `{:error, reason}` → kind `:error`, message `"Task failed: #{inspect(reason)}"`; `{:exit, reason}` → kind `:exit`, message `"Task exited: ..."`; unknown-shape → kind `:error`; source always `:result_handler`; stacktrace = last 8 frames via the private `stacktrace_lines/0` (captures via `Diagnostics.capture_stacktrace/8` + `format_stacktrace_frame/1`). Error rides the `update_task_status_with_caller(..., [error: error])` opts → the self-cast → `handle_update_status/6`.
- **(b) wrapper abnormal `:DOWN`** (persisted `:failed` only when `Lease.sched_meta_has_active_agents?/1` is false): kind `:down`, source `:down_handler`, message = the same `"Task process exited: #{inspect(reason)}"` string written as `result`, stacktrace captured.
- **(c) stuck-`:finalizing` grace watchdog** (`resolve_finalizing_watchdog/3`): kind `:timeout`, source `:finalizing_watchdog`, message = the same `"Finalization did not complete within N minutes"` string written as `result`, stacktrace nil.
- **(d) force kill** (`force_kill_task/1`'s direct `Store.update_task_columns` write): kind `:force_kill`, source `:force_kill_task`, message `"Task force-killed by user"`, stacktrace nil — written in the SAME update as the status flip; `result` stays nil (review/partial-success semantics unchanged), the error records the reason.
- **(e) startup reconciliation** (`TaskRegistry.init/1`, `:finalizing` → `:failed`): kind `:restart`, source `:startup_reconcile`, message = `"Runtime restarted during task finalization"` (same string as `result`), stacktrace nil.
- **(lease sweep)**: kind `:lease_expired`, source `:lease_sweep`, message = `"Lease expired; owning instance no longer renewing"` (same as `result`), set on the full-struct `%TaskInfo{error: ...}` before `Store.put_task`.

## Restart Recovery & Status Transitions

**Startup reconciliation of orphaned `:finalizing` / `:cancelling` tasks.** `TaskRegistry.init/1` (task_registry.ex:266-293) runs `EvoGit.Store.select_running_lease_info/1` (id+status+lease_expires_at, SQL-filtered `status IN ('running','finalizing','cancelling')`); for each `:finalizing`/`:cancelling` row it synchronously calls `handle_update_status/6` with `{:startup_reconcile, ...}` caller info: `:finalizing` → `:failed` (result `"Runtime restarted during task finalization"`), `:cancelling` → `:cancelled` (`"Runtime restarted during task cancellation"`). The handler narrow-reads `select_task_update_info/1` (status/opts/finished_at/lease_expires_at — no full struct decode), applies the stale-guard (both non-terminal → transitions pass), logs via `Diagnostics.log_failed_transition`, handles finished_at/lease, broadcasts `{:task_updated, task_id, status, node()}` (status = persisted status after the write; node = `node()`), cleans task_refs. Writes are SYNCHRONOUS in init (NOT the async `update_task_status/4` cast — would race callers). Covers the crash window where slow git calls in `merge_and_report/3` hang at `:finalizing` (or a graceful cancel is interrupted) and the app dies before the terminal write. Other properties:
- `state.task_refs` is in-memory only — empty after restart, so `{ref, result}` / `{:DOWN, ...}` handlers never fire for pre-restart tasks.
- `:heartbeat` renews leases only for owned tasks with `status in [:running, :pending, :cancelling]` — never `:finalizing`.
- `:lease_sweep` (one-shot, `@sweep_after` = 150s after init) filters `status == :running and id not in owned_ids and not Lease.lease_valid?(lease)` — `:finalizing` excluded by design (init handled it); `:running` respects lease validity for the multi-VM case.
- `:periodic_cleanup` → `Cleanup.cleanup_expired_tasks/1` deletes only tasks with `finished_at != nil` (SQL filter inside `select_cleanup_info/3`); `:finalizing` has `finished_at == nil` (set only for terminal transitions) → never deleted.
- **The stuck-`:finalizing` grace watchdog now schedules `{:recheck_task, task_id}`** — a one-shot `Process.send_after` from the local-node `:finalizing` PubSub handler's successful-persist arm (see "Stuck-`:finalizing` Grace Watchdog" below).

**Resolution paths for `:finalizing`:** (a) startup — init reconciliation marks it `:failed`; (b) explicit user action — `clear_finished_tasks` uses `select_finished_task_ids` (SQL `status NOT IN ('running','pending','cancelling')` — includes `:finalizing`) and DELETEs them, or `delete_task`; (c) in-process — wrapper completion → `{ref, result}` (`{:ok,_}`→`:completed`, error/exit→`:failed`), wrapper crash → `:DOWN` (`:normal`→`:completed`, abnormal→`:failed` only if `Lease.sched_meta_has_active_agents?` is false), or public `update_task_status/4` cast (stale-guard blocks terminal→terminal except →`:completed`). `cancel_task` from `:finalizing` → `{:error, :not_running}` (graceful cancel works from `:pending`/`:running`); (d) in-process — the stuck-`:finalizing` grace watchdog resolves a task still `:finalizing` past the grace window to `:failed` (see below). **Lease expiry plays NO role in resolving `:finalizing`** — a stuck wrapper stops getting renewals (heartbeat skips it); the in-process watchdog (not lease expiry) bounds how long a task can sit at `:finalizing` while the BEAM is alive.

**Stuck-`:finalizing` grace watchdog (in-process resolution for the alive-but-blocked wrapper).** When the local-node `:finalizing` PubSub handler (task_registry.ex:1245-1298) SUCCESSFULLY persists the `:finalizing` status (`EvoGit.Store.put_task` `:ok` arm only — never the disk-full path), it schedules a ONE-SHOT watchdog timer via `schedule_finalizing_watchdog/1` (helper at 1155): `Process.send_after(self(), {:recheck_task, task_id}, delay)` — reusing the existing recheck message shape; `delay = trunc(minutes * 60_000)` (always an integer; `Process.send_after` rejects floats; 0 = fires immediately). Grace minutes come from the app-env seam `Application.get_env(:evo_git, :finalizing_watchdog_grace_minutes)`, read at schedule time by `finalizing_watchdog_grace/0` (1131) — the FIRST configurable TaskRegistry lifecycle interval (declared in `config/config.exs` = 60 — matching the code fallback `@finalizing_watchdog_default_minutes` — and `config/test.exs` = 1): `false` → DISABLED (no timer scheduled; zero behavioral change); unset/nil → default **60** minutes; numeric ≥ 0 → that many minutes (0 = immediate; floats tolerated); any other → 60 (defensive). When the timer fires while the task is STILL `:finalizing`, the recheck handler `handle_info({:recheck_task, task_id}, state)` (1546) takes its dedicated `%TaskInfo{status: :finalizing}` arm (1556-1561, between the unchanged terminal-status clause and the unchanged generic clause) → `resolve_finalizing_watchdog/3` (helper at 1182): re-reads the minutes for the message (`finalizing_watchdog_result_minutes/0`, 1144 — a mid-flight env change is reflected; `:disabled` at fire time falls back to the default) and resolves the task to `:failed` with result `"Finalization did not complete within N minutes"` via the shared `handle_update_status/6` (812) with `caller_info {:finalizing_watchdog, task_id}` — mirroring the startup-reconcile `{:startup_reconcile, :finalizing}` style: Diagnostics failed-transition logging, finished_at set, lease cleared, `{:task_updated, task_id, :failed, node()}` broadcast only on a successful write, `clear_cancelling_marker`, task_refs deletion. It does NOT check `Lease.sched_meta_has_active_agents?` and does NOT 30s-reschedule — the wrapper is alive-but-blocked; the grace expiry resolves the task regardless of scheduler/agent state (nothing killed, no git timeouts added; residual sched_meta/agent state deliberately untouched, mirroring startup reconciliation). Timers are per-boot — a restart mid-grace is covered by the startup-reconcile block (a task still `:finalizing` at init resolves via `{:startup_reconcile, :finalizing}`). **Pinned late-wrapper-result semantics**: after the watchdog resolves to `:failed` the wrapper is STILL alive (blocked, e.g. in slow NFS git I/O); when it eventually returns/exits, the `{ref, result}` (1308-1355) and `{:DOWN, ...}` (1358-1406) handlers are complete NO-OPS — `task_id_for_ref/2` (1000) returns nil because `handle_update_status/6`'s terminal branch deleted the task_refs entry, so both handlers skip their write bodies (no DB write — the row stays `:failed` with the watchdog result + finished_at preserved, never clobbered), and the `{ref, result}` handler's unconditional `Process.demonitor(ref, [:flush])` clears the monitor plus any queued `:DOWN`. Nothing re-adds the task to task_refs; residual sched_meta/agent state is left untouched (test-pinned in persistence_test.exs).

**`resolve_recheck_task/3` and the 30s live-agent reschedule remain effectively unreachable:** `Lease.lookup_sched_meta_result/1` (lease.ex:42-60) is used only by `resolve_recheck_task/3` (task_registry.ex:1038), reached only from the recheck handler's generic arm for non-terminal, non-`:finalizing` rows — the watchdog schedules rechecks only for `:finalizing` rows (which take the dedicated arm, never the generic one), and nothing schedules a first recheck for `:running` rows, so the generic arm is still never entered in production.

**Cleanup semantics:** `Cleanup.cleanup_expired_tasks/1` never changes status — only DELETEs, with age cutoff (`finished_at < cutoff`) and count trim (`max_tasks` newest kept) both pushed into SQL via `Store.select_cleanup_info/3`; config defaults `max_tasks: 100, max_age_days: 14` (cleanup.ex:13).

**Lease mechanics:** `@lease_duration 120` s, `@heartbeat_interval 60_000` ms, `@sweep_after (@lease_duration + 30) * 1000` ms (task_registry.ex:37-42). Lease set at start, renewed by heartbeat via `Store.update_lease_expires_at`. One-shot `:lease_sweep` marks expired `:running` foreign tasks `:failed` only when `sched_meta_has_active_agents?` is false, then runs cleanup + broadcasts.

**TaskExecutor structure:** `start_task` (handle_call `:start_task`, task_registry.ex:312-365) does `Task.Supervisor.async_nolink(EvoGit.TaskSupervisor, TaskExecutor, :execute_task, [task_type, opts, task_id])`. The wrapper process IS the executor — `TaskExecutor.execute_task/3` (task_executor.ex:21-104, whole file = 123 lines) has FOUR clauses, NO catch-all: `:genesis` (:21-26 → `Runtime.Genesis.run(prompt, runtime_opts)`), `:evolve` (:28-63 → merge-context step, then resume-context-or-plain, then `Runtime.Evolution.run(objective, runtime_opts)`), `:extract_skills` (:65-93 → `Runtime.SkillExtraction.run(runtime_opts)`), `:reflect` (:95-104 → `Runtime.SelfReflective.run(opts ++ [task_id: task_id])` — deliberately bypasses `RuntimeOpts.build_common_runtime_opts`, whose `Keyword.fetch!(opts, :path)` at runtime_opts.ex:17 would KeyError). Unknown type → FunctionClauseError in the spawned task → `{ref, {:exit, ...}}` → `:failed`. Every clause FIRST calls `register_task_process/1` (:112-114, `Registry.register(EvoGit.TaskRegistry.ProcessRegistry, task_id, :task)`); the runtime-phase call is the LAST expression — a plain SYNCHRONOUS direct call (no spawn/Task wrapper, no try/rescue/catch) and the module has ZERO `Logger`/`IO` calls (the executor is silent; all task-level logging lives in TaskRegistry's result handlers). **The wrapper never writes statuses** — TaskRegistry's GenServer performs all writes from `{ref, result}` (task_registry.ex:1317-1377) / `:DOWN` (:1380-1437) / PubSub `{:task_updated, id, :finalizing, node}` (:1245-1298) / `update_status` casts. **Stuck-`:finalizing` consequence**: the `:finalizing` broadcast fires from INSIDE the runtime phase — `Runtime.Helpers.notify_finalizing/1` (runtime/helpers.ex:171-179) is called right after `AgentScheduler.run_agent` returns and BEFORE `merge_and_report/4` (e.g. evolution.ex:109-110) — so a blocked `merge_and_report` blocks the wrapper process while status stays `:finalizing`; `task_id` reaches the runtime via `build_common_runtime_opts`' base key `task_id:` (runtime_opts.ex:25). While the wrapper is blocked: `{ref, result}`/`:DOWN` never fire, heartbeat/lease-sweep/periodic-cleanup all skip `:finalizing`, `cancel_task` → `{:error, :not_running}`, and force_kill's status gate is `[:running, :cancelling]` (task_registry.ex:399) — in-process resolution via the stuck-`:finalizing` grace watchdog (see "Restart Recovery & Status Transitions"), else wrapper finish/death, `clear_finished_tasks` deletion, or restart reconciliation.

## Graceful Cancellation & Force Kill

**Task status `:cancelling`** — the graceful-cancel state, deliberately **NON-terminal**: `task_refs` entry stays, `finished_at` stays nil, lease stays valid (heartbeat renews it). Touched in:
- `Store.Codec.@known_atoms` (store/codec.ex:217-219) — whitelisted status atom; `task_info.ex:31` typespec includes it.
- `Store.select_finished_task_ids` (store.ex:634) — SQL `status NOT IN ('running','pending','cancelling')`, so `clear_finished_tasks` never deletes an in-flight cancelling task; `:finalizing` still counts as finished (cleanup target).
- `Store.select_running_lease_info` (store.ex:682) — SQL `status IN ('running','finalizing','cancelling')`, so startup reconciliation can resolve orphaned cancelling tasks.
- Startup reconciliation (task_registry.ex:266-293) — `:cancelling` → `:cancelled` alongside `:finalizing` → `:failed`, both synchronous `handle_update_status/6` with `{:startup_reconcile, ...}`.
- Heartbeat lease renewal (task_registry.ex:1316-1346) — `[:running, :pending, :cancelling]`, so a long graceful cancel keeps its lease while the wrapper is alive.
- **`{:task_updated, id, :finalizing, node}` handler** (task_registry.ex:1245-1298) — matches ONLY the `:finalizing` status (other statuses are persisted locally by TaskRegistry itself, not reprocessed here), node-filter guard `when node == node()` + explicit no-op clause for other nodes (a remote node's finalizing broadcast must never persist into the local store — task ids are per-node, cross-node collisions corrupt rows). A `:cancelling` task ignores phase-finalization broadcasts (keeps the more informative `:cancelling`; final mapping at result time). On a SUCCESSFUL persist (`EvoGit.Store.put_task` `:ok` arm — never the disk-full path) it schedules the ONE-SHOT stuck-`:finalizing` grace watchdog timer (see "Restart Recovery & Status Transitions" → "Stuck-`:finalizing` Grace Watchdog").
- **`handle_update_status/6` final-result force-mapping** (task_registry.ex:858-867) — stored `:cancelling` + incoming `:completed | :failed` → persisted `:cancelled`; result/usage/archive flow through untouched (never nil'd), so the agent's final summary is preserved.

**`TaskRegistry.cancel_task/1` is GRACEFUL** (public `:92-94`, handler `:486-561`):
- `:pending` → immediate `:cancelled` write (finished_at set, lease cleared) + `{:task_updated, task_id, :cancelled, node()}` broadcast (only on the successful write); `start_task` guard refuses already-`:cancelled`/`:cancelling` ids with `{:error, :cancelled}` (`:312-319`).
- `:running` → `handle_update_status(..., :cancelling, ...)` — broadcasts `{:task_updated, task_id, :cancelling, node()}` (the ONLY broadcast for this arm — cancel/1 itself adds none; non-terminal so finished_at/lease/task_refs stay) then `AgentScheduler.begin_graceful_cancel(task_id)` (cross-GenServer call, catch `:exit` guarded — a down scheduler leaves the task `:cancelling` for force_kill or restart reconciliation).
- `:cancelling` → `:ok` idempotent (does NOT re-send the cancel message — agents already hold it).
- terminal (`:completed`/`:failed`/`:cancelled`) or `:finalizing` → `{:error, :not_running}`; missing → `{:error, :not_found}`.

**`TaskRegistry.force_kill_task/1`** (public `:111-113`, handler `:402-454`): status gate `:running | :cancelling` (escalation for a hung graceful cancel) → `AgentScheduler.force_kill_task_agents(pid)` (reverse-depth `:brutal_kill` cascade, catch `:exit`) + `Task.shutdown(ref, :brutal_kill)` + direct terminal write (`:failed`, finished_at set, lease nil, result nil — a force-killed task persists as `:failed`, never `:cancelled`; `:cancelled` means ONLY graceful cancel) + `clear_cancelling_marker(task_id)`.

**Marker cleanup** — `clear_cancelling_marker/1`: prefers `AgentScheduler.clear_cancelling_task/1` (serialized GenServer, can't race `begin_graceful_cancel`), falls back to direct `:ets.delete(:evogit_cancelling_tasks, task_id)` when the scheduler is down (TaskRegistry starts BEFORE AgentScheduler in the supervision tree, e.g. during startup reconciliation). Called from every terminal transition (`handle_update_status/6`, the `{:task_updated, id, :finalizing, node}` handler, and force_kill).

## PubSub Broadcast Contract (topic "tasks") — ordering vs persist

- **Default ordering is persist-then-broadcast (safe for listeners).** The single status-transition choke point `handle_update_status/6` writes via `Store.update_task_columns` FIRST (task_registry.ex:893) and broadcasts `{:task_updated, task_id, status, node()}` ONLY in the `:ok` arm (:899-905, gated on `status != task_status`) — a missing row, a stale-guard skip, or a disk-full write never broadcasts, so any listener that re-fetches on the event sees the NEW persisted row.
- Every other write+broadcast pair keeps the same ordering: `start_task` (put_task :352 → broadcast :366-370), `force_kill_task` (update_task_columns :441 → broadcast :476), cancel's `:pending` arm (:493-497 → :499-503), recheck resolution (:1099 → :1101-1105), `:lease_sweep` (put_task :1519 → :1547-1549), `clear_finished_tasks` (:623 → :630-632), `delete_task` (:737 → :741). Review-status/metadata casts broadcast `nil` status AFTER the write (:775, :804). Startup reconciliation + the stuck-`:finalizing` watchdog resolve via `handle_update_status/6` (safe ordering inherited).
- **The ONLY broadcast that precedes its persist is `:finalizing`**: `Runtime.Helpers.notify_finalizing/1` (runtime/helpers.ex:185-191) fires `{:task_updated, task_id, :finalizing, node()}` from INSIDE the wrapper process, and the local TaskRegistry's handler (:1254) persists it afterward; if that handler's `put_task` hits disk-full (:1292), subscribers were told `:finalizing` while the row stays `:running` (self-heals at the terminal broadcast). Reflect tasks never emit `:finalizing` at all (`SelfReflective.run` skips `notify_finalizing` — transitions are `:running → :completed/:failed/:cancelled`).
- **Terminal-transition sequences end-to-end**: completed = wrapper sends `{ref, result}` → handler :1317 maps to `:completed`/`:failed`/`:exit` → cast `update_task_status_with_caller` (:1357) → `handle_update_status/6` force-maps `:cancelling`+terminal → `:cancelled` with result preserved (:836-838) → persist then broadcast. Abnormal wrapper death = `{:DOWN, ...}` (:1380): `:normal` → `update_task_status(:completed)` (:1389); other reasons → `:failed` ONLY when `Lease.sched_meta_has_active_agents?` is false (:1401-1424), else the row stays `:running` (no broadcast — task continues via scheduler).

## Task Lifecycle & Terminal-Write Sites (teardown-hook map)

- **Start**: `TaskRegistry.start_task/2` (task_registry.ex:77-80) mints `task_id` via `TaskExecutor.generate_id/0` (task_executor.ex:132-134), then `handle_call({:start_task, ...})` (:354-412) spawns the wrapper (`Task.Supervisor.async_nolink(EvoGit.TaskSupervisor, TaskExecutor, :execute_task, [task_type, opts, task_id, state.server_name])`, :364-370), persists `%TaskInfo{status: :running, opts: opts (RAW, verbatim), ...}` (:372-399), records the in-memory `task_refs` entry (:402) and broadcasts `:running` (:404-408). TaskRegistry itself creates NO on-disk state; the task's repo path is `opts[:path]` and foreign repos are `opts[:foreign_repos]`.
- **Run**: the wrapper process IS `TaskExecutor.execute_task/4` (task_executor.ex:29-32) → `do_execute_task/3` per type (`:genesis` :34, `:evolve` :41, `:extract_skills` :78, `:reflect` :108) → `EvoGit.Runtime.*.run/2`. The wrapper runs the WHOLE lifecycle synchronously (incl. the finalize phase `Runtime.Helpers.merge_and_report/4`) and returns; it NEVER writes statuses — every write is done by the TaskRegistry GenServer.
- **Finalize**: `Runtime.Helpers.notify_finalizing/1` (runtime/helpers.ex:183-191) broadcasts `{:task_updated, id, :finalizing, node()}` from inside the wrapper before `merge_and_report` (genesis.ex:53/168/206, evolution.ex:114, skill_extraction.ex:31); the local handler (:1323-1376) persists it. Reflect tasks never emit `:finalizing`.
- **DOMINANT terminal choke point = `handle_update_status/6` (:856-998)**: its terminal branch (:981-989) is where the existing in-memory teardown runs — `clear_cancelling_marker/1` + `task_refs` deletion. Reached via casts from: wrapper result (`handle_info({ref, result})` :1386-1461 → `update_task_status_with_caller` :1440), wrapper `:DOWN` `:normal` (:1473) and abnormal (:1504), startup reconcile (:309 / :319), stuck-`:finalizing` watchdog (:1263).
- **Terminal transitions that BYPASS the choke point (direct `Store` writes)**: `force_kill_task/1` handler (write :479-490, `:failed`, broadcast :520), `cancel_task/1` `:pending` arm (write :537-541, `:cancelled`, broadcast :543), `resolve_recheck_task/3` (:1161-1167, effectively unreachable in production), `:lease_sweep` (:1605-1618 write via `put_task`, broadcast :1634, `:failed`). There is therefore NO single teardown choke point; the per-task tmpdir reclaim hook consequently fires from `handle_update_status/6`'s terminal branch PLUS these four direct sites (see "Per-Task Tmpdir Lifecycle" above).
- **Per-task on-disk artifact**: besides the SQLite rows, each task owns a managed tmpdir (`EvoGit.TaskTmpdir`, "Per-Task Tmpdir Lifecycle" above) — created by the wrapper, reclaimed by the registry. `Cleanup.cleanup_expired_tasks/1` (cleanup.ex:32-55) still only DELETEs finished task ROWS by age/count, called from `clear_finished_tasks` (:669), `:lease_sweep` (:1628) and `:periodic_cleanup` (:1644). Archive records are memory-only ETS + in-repo git refs/notes (see agent_scheduler/CONTEXT.md).
- **Boot-time reconciliation**: `init/1` startup reconciliation (:302-331) enumerates orphaned `:running`/`:finalizing`/`:cancelling` rows via `Store.select_running_lease_info/1`. Additionally the first primary-repo spawn after boot wipes `<repo>/.genesis/workers` (agent_scheduler WorktreeManager, see agent_scheduler/CONTEXT.md).
- **Worktree / scheduler-side artifacts** (per-AGENT, monitor-reclaimed, never task-scoped): see `agent_scheduler/CONTEXT.md` "Task-Scoped Resource Inventory". Runtime phases write nothing outside the repo: see `runtime/CONTEXT.md` "Task Lifecycle Boundary".

## SQL-Lowering Analysis

- **Cleanup**: `cleanup_expired_tasks/1` (cleanup.ex:31) reads only task ids via `Store.select_cleanup_info/3` — age cutoff (`AND finished_at < ?cutoff`) and over-limit keys (`ORDER BY finished_at DESC LIMIT -1 OFFSET ?max_tasks`) pushed into SQL; deletion via `delete_tasks/2` (store.ex:527-550, chunked ~500 ids/chunk, all-or-nothing per chunk). No row decode / Elixir-side sort/filter remains.
- **ISO-8601 lexicographic caveat**: `finished_at` is stored as an ISO-8601 string; SQLite string comparison is only order-correct for consistently-formatted values. Pushdown relies on the fixed-precision 24-char format from `EvoGit.Store.Codec.encode_datetime/1` (`DateTime.truncate(:millisecond)`); non-conforming formats need the manual `mix migrate.store` task (store/CONTEXT.md).
- **`select_running_lease_info`** (store.ex:682) SQL-filters `status IN ('running','finalizing','cancelling')` (cuts decoded rows); callers still filter Elixir-side: init reconcile `status == :finalizing`/`:cancelling` (task_registry.ex:266-293), lease_sweep `status == :running`. `id not in owned_ids` (in-memory task_refs) + lease-expiry-vs-wall-clock stay Elixir-side.
- **ResumeContext** (resume_context.ex:24) → `TaskRegistry.get_task` → `Store.get_task/2` decodes the FULL 18-column row (heavy JSON blobs logs/result/usage/archive_metadata) when only `base_sha` (resume_context.ex:44), `opts`, `result` are used. A `select_tasks_summary`-style lightweight variant would avoid the heavy decodes — low priority (infrequent single-row resume path).
- **No Store access**: `lease.ex` (ETS-only; `sched_meta_has_active_agents?/1` at lease.ex:17-29 does a full `:ets.tab2list` scan — could be `:ets.select`, but ETS not SQL), `diagnostics.ex` (pure Logger/Process.info), `runtime_opts.ex` (pure builder; only `Application.ensure_all_started(:evo_git)`), `task_executor.ex` (reaches Store only transitively via ResumeContext).
- **Full inventory of `EvoGit.Store.` (SQLite) callers in `apps/evo_git/lib`**: only `task_registry.ex` (main GenServer, ~28 call sites) and `task_registry/cleanup.ex` (`select_cleanup_info/3` + `delete_tasks/2`). No other module in evo_git or evo_dash calls the SQLite Store directly — `agent_scheduler/*` `Store.` references are `EvoGit.AgentScheduler.Store` (the ETS store, a DIFFERENT module).
- **Elixir-side sorting** (task_registry.ex): `trim_recent_projects` (task_registry.ex:649-663) + `sort_projects_by_recency` (`:668-675`) fully decode all projects (`safe_select_all_projects`) and sort in Elixir — SQL `ORDER BY last_opened_at DESC` + `LIMIT` would apply (same ISO-8601 ordering caveat).

## Known Issues

- **The `:finalizing` PubSub handler's ignore-list deliberately omits `:failed`** (task_registry.ex:1259): `if task.status in [:completed, :cancelled, :cancelling]` — `:failed` is the one terminal status NOT in the list, and the omission is DELIBERATE recovery semantics (pinned by persistence_test.exs "recovery before completion" — the ignore-list must NOT gain `:failed`): recovering a persisted-`:failed` row to `:finalizing` on a stale broadcast is intended. The in-code comment's "tasks already terminal" wording is loose — it covers exactly the three listed statuses, not all terminal ones. Practically the recovery only fires on a stale in-flight broadcast: the wrapper process sends the `:finalizing` broadcast (via `Runtime.Helpers.notify_finalizing/1`) before it completes and sends `{ref, result}`, and BEAM per-sender message ordering applies; a cross-node broadcast is dropped by the node guard.
- **`force_kill_task/1` broadcasts `{:task_updated, task_id, :failed, node()}` UNCONDITIONALLY** (task_registry.ex:472) — even when the reply is `{:error, :not_running}` / `{:error, :not_found}` / `{:error, :disk_full}` (no persisted change). Local TaskRegistry subscribers only act on `:finalizing` broadcasts (unaffected), but dashboard/other subscribers see a spurious `:failed` for a task whose row was not changed.
- **Disk-full at a terminal write can leave a row `:finalizing` with NO in-process retry.** `handle_update_status/6`'s `{:error, :disk_full}` arm (task_registry.ex:909-918) only logs a warning; the in-memory terminal cleanup (clear_cancelling_marker + `task_refs` deletion, :920-928) runs UNCONDITIONALLY after the case, but the persisted row keeps its OLD status and no broadcast fires. Nothing re-attempts the write: the stuck-`:finalizing` watchdog is ONE-SHOT and never rescheduled (`resolve_finalizing_watchdog/3` :1182-1195), heartbeat renews only `[:running, :pending, :cancelling]` (:1423), `:lease_sweep` filters `status == :running` (:1462-1466), `:periodic_cleanup` only deletes rows with `finished_at != nil`, and once the task_refs entry is gone the wrapper's late `{ref, result}` cannot be persisted — it now logs a `Logger.warning` ("received task result for unknown ref ... (registry restarted?); result dropped", :1363-1372) instead of failing silently. Wedge combination: row at `:finalizing` (watchdog scheduled) → watchdog fires but its `:failed` write hits disk-full (timer consumed) → row stays `:finalizing` until explicit `clear_finished_tasks`/`delete_task` or a TaskRegistry restart whose init reconcile (:270-278) maps it to `:failed` with "Runtime restarted during task finalization".
- **The wrapper→terminal window is now LOGGED (was fully silent) — a wedge still needs the watchdog.** The completion success path between the wrapper's last runtime log ("Created branch ...", runtime/helpers.ex:59-61) and the terminal SQLite write/broadcast used to be zero-Logger. It now leaves a trail at every step: `handle_info({ref, result})` logs `"TaskRegistry: Task <id> wrapper returned — persisting terminal status <status>"` right before the terminal cast (:1353-1355; the `:completed` arm is no longer silent — Logger previously existed only on the `{:error,...}`/`{:exit,...}`/other-shape arms), and `handle_update_status/6`'s `:ok` arm (:894-916) logs `"TaskRegistry: Task <id> terminal status persisted: <status>"` for every terminal write (wrapper result, watchdog resolution, startup reconcile). So an operator now sees an info line at BOTH ends of the window; the residual gap is only the in-flight duration itself (no per-phase progress logs inside `merge_and_report`). A task wedged at `:finalizing` without the watchdog still has no in-process RESOLUTION until the 60-min watchdog `Logger.warning` (:1186-1189) — the logging is forensic, not curative. Post-restart lost results also leave a warning trail: a `{ref, result}` or `{:DOWN, ...}` arriving after a TaskRegistry restart (task_refs cleared in-memory, :250-254) finds `task_id_for_ref` nil → the new `else` arms log `"received task result for unknown ref ... (registry restarted?); result dropped"` (:1363-1372) / `"received :DOWN for unknown ref ... ignoring"` (:1426-1434) — the unconditional `Process.demonitor(ref, [:flush])` still runs. The row is then resolvable by the watchdog, reconcile-at-restart, or manual cleanup (now with a log saying why no terminal write happened).
- **⚠️ Memory scales with `tasks.sqlite` size — the summary-query path (NOT init).** `TaskRegistry.init/1` + retained state (`task_refs` = running tasks only) are clean — no full-table load at startup. The O(N) mechanism (N = rows) is the dashboard-driven summary-query path:
  1. `Store.select_tasks_summary*` / `select_tasks_changed_since` decode every matching row's `opts` JSON. (`result` is deliberately NOT in the 15-column summary projection, so the heavy `Codec.decode_result` — which parses the full result blob embedding `archive_records` + usage — never runs in the summary path.)
  2. `TaskRegistry`'s `:list_tasks_summary` / `:list_tasks_summary_by_path` / `:list_tasks_changed_since` handlers (task_registry.ex:587-624) run the Store call on a `Task.start` + `GenServer.reply` process, and the Store's own summary handlers (store.ex:843-878) do the same — no large decoded terms retained on either GenServer heap (the linked Task preserves the crash-on-decode-raise behavior).
  3. The dashboard re-fetches sidebar summaries on every task-status broadcast (300 ms trailing-edge debounce via `NodeAware.debounce_task_reload/1` → `:node_aware_reload_tasks` → `NodeAware.reload_tasks/1` → `load_running_and_pending_tasks/1` — a statuses-filtered summary, NOT a full scan) and every ProjectsLive session retains the summary maps (15-key, `result` dropped; `opts` remains) in socket assigns (`:running_tasks`, `:pending_tasks`) for its whole lifetime (see apps/evo_dash/lib/CONTEXT.md "Memory Profile").
  Net effect: retained BEAM memory ≈ O(rows × opts-blob size) — correlates with `tasks.sqlite` size (`periodic_cleanup` caps finished rows at `max_tasks: 100` but each row can be multi-MB). Cost drivers: `:completed` inclusion in `assign_running_and_pending_tasks/1` (review candidates need completed rows — a `since` window would bound it), per-row `opts` decode, dashboard assign retention. Nothing loads the DB into memory at boot.
- **Derived foreign-repo `base_sha` is a FROZEN snapshot that is never re-validated against git.** `PrevTaskRepos.apply_starting_commits/2` (prev_task_repos.ex:84-94) reads `prev_task.result`'s `repos[repo_id]["commit_sha"]` — a value persisted ONCE at the previous task's terminal write (`result` is written only by `handle_update_status/6`, task_registry.ex:930-945; never rewritten afterwards — review metadata touches only the primary-scoped `base_sha`/`commit_sha` columns, task_registry.ex:824-849). Nothing re-reads the foreign repo's branch tip and nothing checks ancestry. A follow-up (resume / merge-auto-resolve) derived from an OLDER task in a lineage therefore starts that foreign repo at the older commit when a LATER task advanced the same repo — the recorded sha is then merely an ancestor (only existence is validated, via `Runtime.Helpers.validate_foreign_repo_base_sha!` helpers.ex:334-340). A recorded sha that no longer resolves (deleted + gc'd) raises a descriptive `ArgumentError` at task start instead. Recording is skipped when the foreign-repo subagent's result is not `{:ok, %Result{}}` AND for any child that is not itself a writable `:read_write` agent running in that foreign repo (`Subagents.store_sub_result/3,4`, subagents.ex:417-441) — work committed by a failed subagent is not recorded, and a local/primary or read-only child never advances a foreign repo's tracked commit.
- **Resume block vs runtime mismatch**: the `Writable foreign repos: id@<base_sha|HEAD>` line in the "Previous Task Context" block is rendered from the PREVIOUS task's own `opts[:foreign_repos]` (resume_context.ex:131-147), NOT from the overridden per-repo starting commits actually threaded into runtime opts — the two can disagree. `MergeContext` avoids this by passing its 3-arity block builder the actual carried repos (merge_context.ex:78-79, 112-113, 173).

## Store SQLite Optimization

- **Row-recovery**: undecodable rows are SKIPPED + `Logger.warning` ("Store: skipping undecodable row in ...") — no recovery tables, no per-start repair, no manual `mix` recovery task (SQLite WAL mode does not corrupt rows). Applies to `safe_select_all_tasks/1`, `safe_select_all_projects/1`, `safe_select_paginated_tasks/2` and the summary reads (`select_tasks_summary` / `select_tasks_summary_by_path` / `select_tasks_changed_since`).
- **Schema upgrades**: `Store.init/1` auto-migrates at boot — it boots the store's UNNAMED dynamic `EvoGit.Repo` via `EvoGit.Store.Boot.start_dynamic/1`, which runs the two Ecto migrations in `priv/repo/migrations/` (`20260815000001_baseline_adoption` — idempotent legacy-shape adoption: NULLABLE column adds + 6 indexes; `20260815000002_data_normalization` — fixed-ms timestamp rewrites, canonical `result`/`opts` rewrites incl. positional pair-array opts, `branch_name`/`updated_at` backfills, DETS-era quarantine drops) before any read/write, so an upgraded app boots against an older DB. The manual **`mix migrate.store`** task (`Mix.Tasks.Migrate.Store`) is a thin wrapper over the same `Boot.run_migrations/1` (never starts the `:evo_git` application) — normally a no-op. Detail: `store/CONTEXT.md`.
- **Extended summary API**: `EvoGit.Store.select_tasks_summary(store \\ __MODULE__, statuses \\ [], since \\ nil)` / `select_tasks_summary_by_path(store \\ __MODULE__, project_path, statuses \\ [], since \\ nil)` — `statuses` list of status atoms (`[]` = all, SQL pushdown); `since` optional fixed-precision ISO-8601 string → `AND updated_at > ?N` (nil = no filter). Projection includes scalar columns `branch_name, model_id, agent_count, base_sha, commit_sha, lease_expires_at` + `updated_at` (raw fixed-precision ISO string, NOT decoded — heavy columns logs/usage/archive_metadata and `result` stay out). Summary map keys (15): id, status, review_status, started_at, finished_at, type, project_path, opts, branch_name, model_id, agent_count, base_sha, commit_sha, lease_expires_at, updated_at. Pass-throughs: `TaskRegistry.list_tasks_summary/1,2` + `list_tasks_summary_by_path/2,3`; `AgentScheduler.RemoteAPI.list_tasks_summary/1` + `list_tasks_summary_by_path/2` (no-arg forms kept for RPC callers); `EvoGit.RemoteNode.list_tasks_summary/2` + `list_tasks_summary_by_path/3` over `:erpc`. **⚠️ `since` is NOT exposed through RemoteAPI/RemoteNode** — the RPC layers only accept `statuses`; remote callers needing a time filter must use `list_tasks_changed_since` (which accepts no statuses). Only local `TaskRegistry`/`Store` calls combine statuses + since.
- **Changed-since API**: `Store.select_tasks_changed_since(store \\ __MODULE__, since_iso)` returns summary-shaped maps (same 15-key projection incl. `updated_at`) for rows with `updated_at > since_iso` (fixed-precision string comparison — no heavy columns). Chain: `TaskRegistry.list_tasks_changed_since/1` → `AgentScheduler.RemoteAPI.list_tasks_changed_since/1` → `EvoGit.RemoteNode.list_tasks_changed_since/2` (over `:erpc`; `[]` on RPC failure).
- **Summary-handler offload**: `TaskRegistry`'s `:list_tasks_summary` / `:list_tasks_summary_by_path` / `:list_tasks_changed_since` handlers (task_registry.ex:587-624) + the Store's heavy full-decode handlers (`select_all_tasks`, `safe_select_all_tasks`, `safe_select_paginated_tasks`, `select_tasks_summary`, `select_tasks_summary_by_path`, `select_tasks_changed_since`) run the query AND the decode on a short-lived LINKED `Task.start` replying via `GenServer.reply/2` — decoded terms live on the Task heap, not the GenServer's; the link preserves the crash-on-decode-raise behavior; the skip-and-log boundary (`decode_skipping_bad`) + `_ -> []` query-failure arms run inside the Task. Single-row/tiny handlers (`get_task`, `select_task_logs`/`update_info`, id-only projections, counts, projects ≤10 rows) stay synchronous.
- **Disk-full write handling**: SQLite disk-full-class write errors (`SQLITE_FULL` 13, `SQLITE_IOERR` 10, `SQLITE_READONLY` 8) — RAISED by the `XqliteEcto3` adapter as `%XqliteEcto3.Error{}` and detected at the write boundary by pure classifier `EvoGit.Store.Errors.disk_full_exception?/1` (code-based matches, `type: :read_only_database`, plus the canonical "database or disk is full" message fallback; the sibling `disk_full_error?/1` classifies the legacy xqlite NIF tuple shapes) → converted to `{:error, :disk_full}` by the Store facade's `write_call/2` choke point (and inside `Operations.Projects.put_project`) — the GenServer survives, reads keep working, writes retryable; every other write error re-raises (crash + supervisor restart). All 8 write functions (`put_task`, `delete_task`, `delete_tasks`, `clear_tasks`, `update_lease_expires_at`, `update_task_columns`, `put_project`, `delete_project`) return `{:error, :disk_full}` on the disk-full class (success shapes unchanged). TaskRegistry + Cleanup degrade gracefully at all 14 write call sites (log+continue for casts/heartbeat/log-loss; `{:error, :disk_full}` from `force_kill_task`/`cancel_task`/`clear_finished_tasks`; in-memory terminal cleanup always runs). Full contract + adapter error shapes in `store/CONTEXT.md` → "Disk-Full Handling".
- **Narrow-read Store functions**: `select_task_logs(store \\ __MODULE__, task_id)` (SELECT logs, decoded list or nil) and `select_task_update_info(store \\ __MODULE__, task_id)` (SELECT status, opts, finished_at, lease_expires_at → map or nil). TaskRegistry hot paths — `append_log`, `set_review_status`, `set_review_metadata`, `handle_update_status`/`update_task_status_with_caller`, `cancel_task`, `resolve_recheck_task` — use these narrow reads + `update_task_columns` instead of full `task_get` decodes.

## Merge-Conflict-Resolution Flow (MergeContext / TaskExecutor)

- **Only trigger point**: `TaskExecutor.execute_task(:evolve, opts, task_id)` (task_executor.ex:28-62) runs a merge-context step BEFORE the `resume_from` handling: when `opts[:merge_from]` is a non-empty binary (trimmed), it calls `MergeContext.apply_merge_context(opts, task_id, trimmed_merge_from, opts[:merge_target])` and reassigns `opts`; otherwise opts pass through unchanged. The rest of the flow (resume handling, `RuntimeOpts.build_common_runtime_opts`) runs on the transformed opts — merge keys already stripped, `resume_from` not passed in this flow.
- **`apply_merge_context(opts, _task_id, merge_from, merge_target)`** (merge_context.ex): strips `:merge_from`/`:merge_target` FIRST (never leak into runtime opts) → `prev_task = EvoGit.TaskRegistry.get_task(merge_from)` (full `%TaskInfo{}` decode). **prev_task nil** → stripped opts unchanged. **prev_task found** → `:starting_commit` overridden with `prev_task.commit_sha` when a non-empty binary (caller's value preserved otherwise) → `:foreign_repos` carried over from `prev_task.opts` when present/non-nil — each entry normalized via `EvoGit.Core.ForeignRepo.normalize/1`, unparseable dropped (persisted opts round-trip the Codec JSON as STRING-keyed maps; raw carry-over crashed downstream `Runtime.Helpers.merge_foreign_repos/2` dot-access with `KeyError`), then **per-repo starting commits**: each carried repo's `base_sha` is overridden from the previous task's result `repos[repo_id]["commit_sha"]` via `PrevTaskRepos.apply_starting_commits/2` (defensive string-key reads; repos absent from prev `repos` — read-only/no-changes — keep their base_sha; legacy tasks without `repos` are a no-op) → `:objective` = `build_merge_context_block(prev_task, merge_target, carried_repos) <> "\n\n" <> old_objective` (the 3-arity so the block shows the ACTUAL starting commits). Pure opts-transforming function (keyword in/out — no RuntimeOpts call; returns opts, NOT a `{objective, runtime_opts}` tuple like ResumeContext).
- **`build_merge_context_block(%TaskInfo{}, merge_target)` / `(prev_task, merge_target, foreign_repos)`** (merge_context.ex): returns a "Merge Conflict Resolution Context" string delimited by `--- Merge Conflict Resolution Context ---` / `--- End Merge Conflict Resolution Context ---`. Contents: `Previous task id:`; `Base sha:` (omitted when nil/empty) and `End (commit) sha:` (omitted when nil/empty — block still emitted with the other fields when neither is available); `Task branch name: <branch_name || "unknown">`; `Merge target branch: <merge_target || "unknown">`; a `Goal:` paragraph (merge the target branch into the worktree via `git merge <target>`, resolve ALL conflicts by combining both sides, commit, then continue developing until coherent); a `Writable foreign repos: <id>@<base_sha|HEAD>, ...` line (ONLY when ≥1 writable repo, from normalized structs — 3-arity takes explicit normalized repos; the 2-arity derives them from `prev_task.opts[:foreign_repos]`); a `Hints:` section with 3 bullet points (commit conflict resolutions before delegating follow-up work — subagents spawn at clean checkouts so uncommitted changes are invisible; inspect `git log/diff <base>..<end_sha>` for the task's own changes and `git log/diff <base>..<target>` for the target side since the base — ranges interpolated from the shas when available, placeholder fallbacks otherwise; incremental milestone merges OR rough-resolve-then-develop-on-top as fallback strategies). Fallback clauses `build_merge_context_block(_, _), do: ""` / `(_, _, _), do: ""` for non-struct input.

## Resume-From Flow (ResumeContext / TaskExecutor / RuntimeOpts)

- **Only trigger point**: `TaskExecutor.execute_task(:evolve, opts, task_id)` (task_executor.ex:27-41) calls `ResumeContext.apply_resume_context/3` when `opts[:resume_from]` is a non-empty binary after `String.trim/1`. Non-resume evolve tasks build `{objective, runtime_opts}` directly (`objective = Keyword.get(opts, :objective, "")`).
- **`apply_resume_context(opts, task_id, resume_from_id)`** (resume_context.ex:20-91): strips `:resume_from` (never leaks into runtime opts) → `prev_task = EvoGit.TaskRegistry.get_task(resume_from_id)` (FULL 18-column row decode — known inefficiency, low priority). Caller-supplied `:foreign_repos` are **normalized to `%ForeignRepo{}` structs** (entries may be string-keyed maps from a Codec JSON round trip — `ForeignRepo.normalize/1`, unparseable dropped) and each repo's `base_sha` is **overridden from the previous task's result `repos[repo_id]["commit_sha"]`** via `PrevTaskRepos.apply_starting_commits/2` (string-keyed, defensive; repos absent from prev `repos` keep their base_sha; legacy tasks without `repos` are a no-op); the `:foreign_repos` key is only (re)added when the normalized list is non-empty (no key when the caller has none). **prev_task nil** → original objective (`Keyword.get(opts, :objective, "")`), `build_common_runtime_opts` with the caller's own repos (still normalized). **prev_task found** → `context_block = build_resume_context_block/1`; objective becomes `context_block <> "\n\n" <> objective` only when the block is non-empty; `:starting_commit` **overridden** with `prev_task.commit_sha` when a non-empty binary (a caller-provided starting_commit is silently dropped in that case), otherwise the caller's own value (if any) passes through — then `build_common_runtime_opts(opts_with_commit, task_id, :evolve)`. **⚠️ Foreign repos are NOT inherited from `prev_task.opts` on resume**: `apply_resume_context` never reads `prev_task.opts[:foreign_repos]` — only caller-supplied `:foreign_repos` in the NEW task's opts flow through `build_common_runtime_opts`. `MergeContext` (merge-conflict flow) is the ONLY cross-task foreign-repo inheritance path.
- **Context block exact format** (resume_context.ex:93-169): `"--- Previous Task Context ---\n" <> Enum.join(parts, "\n\n") <> "\n--- End Previous Task Context ---"` — empty string when `parts == []`. Parts are joined with **blank lines** (sections never run together). Part 1 (single line): `"Previous task commits: #{base_sha}..#{commit_sha}"` (both non-empty; falls back to just `commit_sha` when base_sha empty/nil; omitted when commit_sha empty). Part 2 (single line, only when ≥1 writable foreign repo in `prev_task.opts[:foreign_repos]`): `"Writable foreign repos: <id>@<base_sha|HEAD>, ..."` (repos normalized first; NOT delimited, like the commits part). Part 3 (multi-line, delimited): `"Previous task objective:\n<<<BEGIN OBJECTIVE>>>\n#{old_objective}\n<<<END OBJECTIVE>>>"` (objective from `prev_task.opts` keyword `:objective` || `:prompt`, only when list and non-empty). Part 4 (multi-line, delimited): `"Previous task result:\n<<<BEGIN RESULT>>>\n#{summary}\n<<<END RESULT>>>"` (summary omitted when `extract_result_summary/1` returns nil or `""`). The `<<<BEGIN ...>>>`/`<<<END ...>>>` markers wrap arbitrary (possibly multi-line) content so the agent can never confuse a label with its content or the content with the outer fence; the triple-angle-bracket all-caps form is chosen so no plausible agent-generated text collides with it. `extract_result_summary/1` (resume_context.ex:135-142): `{:ok, %{result: s}}` binary → passthrough, atom → `to_string/1`; `{:error, reason}` → `"Error: #{inspect(reason)}"`; `{:exit, reason}` → `"Exited: #{inspect(reason)}"`; anything else → nil (part omitted).
- **SHA provenance**: `prev_task.commit_sha` is populated at task completion by the `{ref, result}` handler extracting `{:ok, %{commit_sha: sha}}` from the runtime result (task_registry.ex:1226-1230; the runtime merge result carries `commit_sha: final_sha || base_sha`, runtime/helpers.ex:70). `prev_task.base_sha` is set ONLY by the review flow (`set_review_metadata/3` cast, task_registry.ex:792-801) — so a never-reviewed task's commits_line is just the commit_sha.
- **`RuntimeOpts.build_common_runtime_opts(opts, task_id, task_type)`** (runtime_opts.ex:16-74) returns `{nil, runtime_opts}` (first element always nil). `:path` is REQUIRED (`Keyword.fetch!` — crashes without it); `mode` defaults to `"simple"`; base keys `[repo_path, mode: mode_atom(task_type, mode), task_id]`; conditionally appended only-if-truthy: `node_path`, `starting_commit`, `foreign_repos`, `archive`, `model_id` (non-nil and ≠ `""`), `build_system`, `attachments` (multi-modal objective media — validated UNCONDITIONALLY via `EvoGit.Attachments.validate/1` at the top of the builder (nil/`[]` → `:ok`; malformed payloads raise a descriptive `ArgumentError` at task start, spec-error style like mode validation), put only when non-nil AND non-`[]` via the `value not in [nil, []]` predicate; STRING-keyed base64 maps — detail: `EvoGit.Attachments`) — the chain is built by the internal `put_if/4` (appends `key => value` only when the optional key's predicate passes; default predicate = plain truthiness of the value) and `put_if_true/3` (flag keys such as `model_id_locked` → `key => true`, never the value, when truthy) helpers (runtime_opts.ex:71-80). **Truthiness nuance**: the `if foreign_repos` guard (runtime_opts.ex:43) is Elixir truthiness — only `nil`/`false` drop; an EMPTY `[]` list IS truthy and passes through into runtime opts (harmless: `Runtime.Helpers.load_foreign_repos/2` merges it with genesis.toml defaults). Same semantics in the `:extract_skills` passthrough (task_executor.ex:84-90). **No default for `:starting_commit`** — when absent the runtime resolves HEAD itself (`Runtime.Helpers.resolve_starting_commit(repo_path, nil)` → `PhyloGraphNode.current_head/1`, runtime/helpers.ex:167-169); when present it must `git rev-parse` cleanly or evolution fails (helpers.ex:171-179). Mode atoms: genesis `"new"`/`"existing"`, evolve `"simple"`/`"custom"` — anything else raises `ArgumentError` (runtime_opts.ex:98-114); **genesis mode `"custom"` raises a SPECIFIC error** (`"custom mode is evolve-only; use an evolve task with mode \"custom\""`, runtime_opts.ex:110-111) instead of the generic invalid-mode raise, covering the dashboard string-mode path where a genesis task receives `mode: "custom"`. No concurrency key is built here.
- **Task start (no `create_task` exists anywhere in evo_git/evo_dash)**: `TaskRegistry.start_task(task_type, opts)` (task_registry.ex:51-54) → generates id via `TaskExecutor.generate_id/0` → `handle_call({:start_task, task_id, task_type, opts}, ...)` (task_registry.ex:312-365): guard refuses `:cancelled`/`:cancelling` ids with `{:error, :cancelled}` → `Task.Supervisor.async_nolink(EvoGit.TaskSupervisor, TaskExecutor, :execute_task, [task_type, opts, task_id])` → persists `%TaskInfo{status: :running, opts: opts (RAW — no defaults applied in TaskRegistry), started_at, logs: [], result: nil, lease_expires_at: now + 120s, model_id: opts[:model_id]}` (ref nulled for persistence; disk-full → warning, in-memory only) → `task_refs` updated, `{:task_updated, task_id, :running, node()}` broadcast, reply `{:ok, task}`. All opts defaults live in the CALLERS, NOT in TaskRegistry (raw opts persisted as given): the DASHBOARD (`ProjectsLive.handle_event("task_submit", ...)`, projects_live.ex:997-1082: `path` required, `mode` always passed, `:prompt` for genesis / `:objective` for evolve, plus conditional `build_system`/`node_path`/`starting_commit`/`foreign_repos`/`archive`/`model_id`/`resume_from`) and the CLI (`cli.ex` — genesis/evolve/reflect are thin clients enqueueing via this same `start_task/2`: ABSOLUTE `:path`, STRING `:mode`, `:prompt`/`:objective`, put-if-present `:build_system`/`:node_path`/`:starting_commit`/`:agent`/`:archive`, always `:foreign_repos`, `-m` → `model_id` + `model_id_locked: true`); the remaining defaults (`:prompt`/`:objective` fall back to `""`, mode falls back to `"simple"`) live in TaskExecutor/RuntimeOpts. Remote path: `RemoteAPI.start_task/2` → `TaskRegistry.start_task/2` (remote_api.ex:498-499) via `RemoteNode.start_task/2` (remote_node.ex:1178) / `NodeContext.start_task/3` (node_context.ex:516-518) — the shell's `StartTask.start_task` command handler and the CLI both call the local `TaskRegistry.start_task/2` directly.
- **Adjacent**: `resolve_recheck_task/3` (task_registry.ex:1034-1106) recovers a task whose wrapper process died before replying — best-effort result lookup via `Lease.lookup_sched_meta_result/1` (lease.ex:42-60, top-level agent's first `sub_agent_results` value), falls back to `:completed`; shares the `{:ok, %{branch_name: _}}` extraction with `handle_update_status/6`.
