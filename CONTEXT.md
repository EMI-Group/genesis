# EvoGit — Root

## Intent

EvoGit is an evolutionary software development framework built in Elixir. It models a codebase as a hierarchical **Context Tree** (Spatial Dimension) and evolves it through a DAG of Git commits (Temporal Dimension). AI agents recursively build and optimize software, guided by spatial contracts in per-directory CONTEXT.md files.

This is an **Elixir umbrella project** with two child applications:

| App | Directory | Purpose |
|-----|-----------|---------|
| `:evo_git` | `./apps/evo_git/` | Core runtime — agent execution, Git interactions, CLI |
| `:evo_dash` | `./apps/evo_dash/` | Phoenix LiveView dashboard — real-time visualization and task management |

The full design specification is documented across the CONTEXT.md tree.

## Routing Table

- `./apps/evo_git/` → Core runtime (agents, scheduler, git adapter, runtime phases)
- `./apps/evo_dash/` → Web dashboard (LiveView pages, components, task registry)
- `./config/` → Environment-based Elixir configuration
- `./rel/` → Mix release overlays (`rel/genesis/`, `rel/genesis_remote/` — vm.args + env scripts per release; distribution config for SSH remote dev)
- `./desktop/` → Tauri desktop shell (native WebView wrapper, sidecar lifecycle management)
- `./nix/` → NixOS build support (vendor bundling helper for local desktop builds)
- `./.github/workflows/` → CI/CD pipelines (desktop app build on release)

### CLI Interface

```bash
# Setup — guided LLM configuration wizard
mix run -e 'EvoGit.CLI.main(System.argv())' -- setup

# Genesis — create a codebase from a prompt
mix run -e 'EvoGit.CLI.main(System.argv())' -- genesis "<prompt>" [-f file] [-c concurrency] [-p path] [-R <id:>path]

# Evolution — modify an existing codebase
mix run -e 'EvoGit.CLI.main(System.argv())' -- evolve "<objective>" [-p path] [-R <id:>path]
```

Flags: `-c` / `--concurrency` for LLM slots, `--tool-concurrency` for tool slots, `-R <id:>path` for foreign repos (repeatable).

## Constraints

- Umbrella structure: all deps, build artifacts, lockfile at root (`./deps/`, `./_build/`, `mix.lock`)
- Elixir ~> 1.18 required
- Git CLI only — no libgit2 bindings
- No source code at root — all code under `./apps/`
- Agents commit before delegating subagents (auto-commit fallback enforced)
- Genesis stores its runtime artifacts (agent worktrees, state) under a `.genesis/` directory at each repo root. This directory must be git-ignored everywhere (root `.gitignore` and the `.gitignore` that Genesis auto-writes into new repos).
- LLM-generated code runs under platform-appropriate sandboxing (systemd-run on Linux, bwrap/bubblewrap on Linux without systemd — e.g. Docker — filesystem isolation only, sandbox-exec on macOS, direct on Windows); backend preference configurable via `[sandbox] backend = "auto" | "systemd" | "bwrap"` (`auto` tries systemd-run first, then bwrap, then no sandbox)
- No hardcoded model or username — users configure via `~/.config/genesis/config.toml`
- User config follows XDG conventions

## Architecture Summary

EvoGit has two OTP applications under an umbrella:

- **`:evo_git`** (Core Runtime): AgentScheduler GenServer managing worktree pools, LLM/tool slot management with global backoff, agent implementations (Manager, Executor, Investigator, etc.), Git adapter, and two-phase execution (Genesis → Evolution). Uses a 3-level configuration system: built-in defaults → user TOML config → session-level runtime overrides.
- **`:evo_dash`** (Web Dashboard): Phoenix LiveView interface with project-based task management, agent tree inspector, runtime settings panel, and in-browser config editor. Uses Bandit adapter, Tailwind CSS 4 + DaisyUI, SQLite-based persistence (xqlite).

Key design: spatial context tree for routing, phylogenetic graph for temporal evolution, transient agents in isolated worktrees, multi-repo support via absolute path resolution, slot-based concurrency with LLM rate-limit backoff, multi-platform sandboxing (systemd-run on Linux, bwrap/bubblewrap filesystem isolation on Linux without systemd, sandbox-exec on macOS), and a dynamic skills system.

The web dashboard (`:evo_dash`) is internationalized with Gettext — all user-facing strings in LiveViews, components, helpers, and templates are wrapped with `gettext/1,2`. When a string's meaning needs anchoring for the release-time AI translator (ambiguous short labels, domain jargon, etc.), write a **Chinese comment** next to the `gettext` call explaining the intended meaning — that is the ONLY i18n-related work expected during development.

### Runtime Data Directory (`tasks.sqlite`)

The SQLite task database (`tasks.sqlite`) lives in the platform data directory, resolved at runtime by `EvoGit.Platform.data_dir/0` (`apps/evo_git/lib/evo_git/platform.ex:106-132`) — NOT via Tauri's `path_resolver`/`app_data_dir`. The Tauri sidecar passes no data-dir env vars (only `PORT`, `PHX_IP`, `PHX_SERVER`, `SECRET_KEY_BASE`, `RELEASE_DISTRIBUTION`, `EVOGIT_DESKTOP`; `desktop/src-tauri/src/sidecar.rs:44-55`) — the Elixir backend decides the path itself:

- **macOS**: `~/Library/Application Support/genesis/tasks.sqlite`
- **Linux**: `$XDG_DATA_HOME/genesis/tasks.sqlite` (default `~/.local/share/genesis/tasks.sqlite`)
- **Windows**: `%APPDATA%\genesis\tasks.sqlite` (default `~\genesis\tasks.sqlite` if APPDATA unset)

Path is computed in `EvoGit.Application.start/2` (`apps/evo_git/lib/evo_git/application.ex:36-38`): `Path.join(Application.get_env(:evo_git, :data_dir, EvoGit.Platform.data_dir()), "tasks.sqlite")`, passed to `EvoGit.Store`, which `mkdir_p!`s the parent dir and opens with SQLite WAL mode (`store.ex:328-332`; WAL sidecars `tasks.sqlite-wal`/`-shm` sit beside it). `EvoGit.TaskRegistry.init/1` mirrors the same resolution (`task_registry.ex:151-161`). **Override**: set the application env `config :evo_git, :data_dir` (only `config/test.exs:29` does this); there is NO dedicated env var and NO TOML config key (`EvoGit.Config` schema has no data-dir option). Indirect env influence only: `HOME` (macOS), `XDG_DATA_HOME` (Linux), `APPDATA` (Windows). The desktop log file uses the same dir (`<data_dir>/logs/backend.log`, `config/runtime.exs:121`), and the `genesis_remote` daemon uses the same resolution on its host (macOS remote: `~/Library/Application Support/genesis/tasks.sqlite`).

### Task Cancellation Model (graceful cancel vs force kill)

Task cancellation has **two distinct actions** (both node-aware via the RemoteNode RPC chain):

- **Graceful cancel** — `EvoGit.TaskRegistry.cancel_task/1` (also `RemoteAPI.cancel_task/1`, `RemoteNode.cancel_task/2`, `EvoDash.NodeContext.cancel_task/2`): sets the task to the **`:cancelling`** status, then via `AgentScheduler.begin_graceful_cancel/1` sends each running agent a user message (same `pending_user_messages` channel as `send_user_message`) telling it to save work and call `complete_task`, and sets a new `AgentState.cancel_requested` ETS flag. `Runner.loop/1` drains the flag right after user messages (`maybe_enter_cancel_grace/1`) and enters the turn-limit grace machinery with a **3-turn budget** (`LoopState.grace_turns_remaining`; turn-limit recovery keeps its exact 1-turn behavior). The wrapper is NOT killed — the phase finishes normally, and the final-status mapping in TaskRegistry force-persists `:cancelled` (preserving result/archive/usage) when the task is `:cancelling`. `:pending` tasks cancel immediately to `:cancelled` (and `start_task` refuses already-cancelled/cancelling ids); `:cancelling` is idempotent. New root spawns are blocked for cancelling tasks (`run_agent` replies `{:error, :cancelled}` — Genesis Mode B's second root won't start); new-agent registration for a cancelling task gets the flag immediately (dispatch.ex:103-113). Escalation: `force_kill_task/1` also works from `:cancelling`.
- **Force kill** — `EvoGit.TaskRegistry.force_kill_task/1` (same for RemoteAPI/RemoteNode/NodeContext): kills all agents + the wrapper, persists **`:failed`** with result nil'd. `:cancelled` means ONLY gracefully-cancelled tasks. Works from `:running` and `:cancelling`. **Dashboard consequence**: a force-killed task renders as Failed (no result, no review); a gracefully cancelled task persists `:cancelled` WITH result/archive preserved and is reviewable on the Tasks page exactly like a completed task — the Review button on the task card (`task_card_components.ex` `show_review_button?/1`) matches `:cancelled` (branch result and `no_changes: true` variants), and ReviewLive's `is_no_changes` treats `:cancelled` like `:completed` so merge/reject/ignore/resume work. Sidebar active-task semantics: `:cancelled` is not an active status, `:cancelling` counts as active.

**`:cancelling` status plumbing** (non-terminal): codec `@known_atoms` (store/codec.ex), TaskInfo typespec, `select_finished_task_ids` excludes it (clear_finished_tasks won't delete in-flight cancels), `select_running_lease_info` includes it, heartbeat renews its lease, startup reconciliation maps orphaned `:cancelling` → `:cancelled` (mirrors `:finalizing` → `:failed`), the `{:task_status, :finalizing}` handler does NOT clobber it.

**Dashboard UI** (`apps/evo_dash`, Tasks page): visible **Cancel** button (`[:pending, :running]`) → `open_cancel_modal` → custom warning modal ("agents will be informed to save changes and exit; intermediate results will be saved") → `confirm_cancel_task`. **Force kill** lives in the task card's three-dot dropdown (`[:running, :cancelling]`, "Danger zone" divider) → `open_force_kill_modal` → warning modal ("ALL progress will be completely lost") → `confirm_force_kill_task`. Modal state = `confirm_cancel_task_id`/`confirm_force_kill_task_id` assigns in TasksLive (seeded nil, mutually exclusive, cleared on node switch). `:cancelling` renders as violet badge/label/accent/tint, appears in the sidebar active-tasks lists (node_aware `@active_statuses` + running partition) and the Tasks page status filter. `ProjectsLive.handle_event("cancel_task", ...)` (calls `TaskRegistry.cancel_task/1` directly = graceful) is currently triggerless (sidebar has no cancel button) — harmless. See `apps/evo_git/CONTEXT.md` + `apps/evo_dash/CONTEXT.md` for full details.

### Merge Conflict Check & Auto-Resolution (Review Page)

The review page now checks merge cleanliness asynchronously (GitHub-style) and offers agent-driven auto-resolution:

- **Async merge check**: on review page load (and when the merge-target selector changes), `ReviewLive` spawns a supervised Task (`EvoDash.TaskSupervisor`, same self-message pattern as SettingsLive's LLM test) calling `EvoDash.NodeContext.check_merge/4` → `EvoGit.RemoteNode.check_merge/4` (node-aware, `:erpc` on remote) → `EvoGit.Review.check_merge/3` — a **non-mutating dry-run**: resolves both refs (identical SHAs → `:clean`, already merged), then runs `git merge-tree --write-tree --name-only --no-messages <branch_sha> <target_sha>` — a real merge computed entirely in memory (requires git ≥ 2.38, the version that added `--name-only`/`--no-messages`). No worktree is ever created, nothing is added under `<repo>/.genesis/`, and index/HEAD/refs are untouched — there is nothing to clean up. Exit 0 → `:clean`; exit 1 → `{:conflict, files}` (stdout = conflicted-tree OID line followed by one conflicted file path per line; OID line dropped by shape); exit 128 → error. Returns `{:ok, :clean} | {:ok, {:conflict, files}} | {:error, reason}`.
- **UI** (`ReviewComponents.Actions.action_buttons/1` + `ReviewLive.MergeCheck` support module): merge-status block above the Merge button — checking → clean (green) → conflict (amber, conflicted-file list + **Auto-resolve conflict** button with phx-confirm) → error (renders nothing, falls back to old behavior). Existing manual Merge button + conflict flash remain as fallback.
- **Auto-resolve** (counts as resumed): marks the original task `review_status: :continued` (same as the resume flow), then starts a new `:evolve` task via `NodeContext.start_task/3` with opts `[path:, mode: "simple", objective:, starting_commit:, merge_from: <task_id>, merge_target: <branch>]`. `TaskExecutor.execute_task(:evolve)` routes `merge_from` to `EvoGit.TaskRegistry.MergeContext.apply_merge_context/4` which strips the merge keys, loads the previous task, overrides `starting_commit` with prev `commit_sha`, carries over prev `foreign_repos`, and prepends a context block (task id, base/end SHAs, branch name, target, goal, and hints: commit resolutions before delegating because subagents always spawn at clean checkouts; inspect `git log/diff base..end` and `base..target` to understand both sides; for hard conflicts use incremental milestone merges or rough-fix-then-continue). The merge agent runs `git merge <target>` in its worktree, resolves conflicts, and commits; `merge_and_report` then produces a reviewable `genesis/agent_*` branch whose merge into the target is clean.
- **Test seam**: `Application.get_env(:evo_dash, :merge_check_runner)` overrides the async check function in tests (default `&EvoDash.NodeContext.check_merge/4`); the spawned task rescues exceptions and reports `{:error, :check_failed}` so the status can never wedge at `:checking`.

### Native Directory Picker (wx backend)

The dashboard's directory picker (Browse buttons on the project/new-project/foreign-repo pickers) is implemented **on the Elixir backend with Erlang's `:wx` module** (`wxDirDialog`), NOT via Tauri. Flow: the JS `DirectoryPicker` hook pushes `"directory_pick"` → `ProjectsLive` checks the current node is local → `EvoDash.DirectoryPicker` (a GenServer in `apps/evo_dash`, serializes wx dialog usage) runs the modal dialog → result pushed back to the client as `"picker_result:<picker_id>"`. wx picks are absolute paths and auto-submit the project/new-project forms; Tauri's `pick_directory` Rust command + `tauri-plugin-dialog` are not used (unstable: Windows invoke fails after picking, macOS NSOpenPanel never presents). When wx is unavailable (headless server, remote node, OTP built without wx) the hook shows the manual-entry fallback. Because `wx` is not a dependency of any umbrella app, it must be listed explicitly in the `applications:` list of the `genesis` and `genesis_desktop` releases in `./mix.exs` (`wx: :load`) — `genesis_remote` intentionally stays wx-free. The `directory_picked` LiveView event is dead code (superseded by the `picker_result` push). **CI note**: the desktop release's wx NIFs link against wxWidgets 3.2 sonames, so AppImage bundling requires the wx 3.2 runtime (without it linuxdeploy fails with `failed to run linuxdeploy`). The Linux runners are **ubuntu-24.04** (x64) / **ubuntu-24.04-arm**, where wxWidgets 3.2.4 ships in the default Ubuntu repos — the x64-gated CI step plain-apt-installs `libwxbase3.2-1t64 libwxgtk3.2-1t64 libwxgtk-gl3.2-1t64 libwxgtk-webview3.2-1t64 libglu1-mesa` (no PPA). ### ReqLLM Finch Connection Pool (LLM HTTP concurrency)

- **Boot-time sizing** (`config/runtime.exs:23-72`): pool `count = EvoGit.ReqLLMPool.desired_count(total_concurrency)` — the `max(total + 2, 8)` formula lives ONLY in `desired_count/1` (single source of truth shared with runtime reconciliation; do NOT inline it in runtime.exs). `total_concurrency` = `max(sum of per-profile concurrency, scheduler.default_llm_max_concurrency)` from `EvoGit.Config.resolve()` (per-profile `concurrency` defaults to 3); falls back to `scheduler.default_llm_max_concurrency` alone when no `[[llm.models]]` profiles exist. Configured via the full `finch:` override form — `finch: [name: ReqLLM.Finch, pools: %{default: [protocols: [:http1], size: 2, count: stream_pool_count, start_pool_metrics?: true]}]` — with `stream_pool_timeout: 300_000` and `stream_pool_strategy: {Finch.Pool.Strategy.RoundRobin, round_robin}` kept top-level (both read at CALL time; the strategy is forwarded as the per-request `pool_strategy` opt — there is NO `strategy:` key in the pool template, NimbleOptions raises on unknown keys at boot; `round_robin = Finch.Pool.Strategy.RoundRobin.new()` is an `:atomics` ref created at config-eval time, `config/runtime.exs:99`). The `start_pool_metrics?: true` flag is REQUIRED for `Finch.get_pool_status(ReqLLM.Finch, :default)` to enumerate origins (see runtime reconciliation below). Evaluated before `:req_llm` starts, in ALL releases (genesis, genesis_desktop, genesis_remote — releases run runtime.exs at boot; the desktop/remote flags in runtime.exs never touch the pool; NO desktop-specific pool override exists anywhere in `desktop/`, `rel/`, `config/`, or app code).
- **Semantics — pools are PER ORIGIN**: ReqLLM starts ONE Finch named `ReqLLM.Finch` (`deps/req_llm/lib/req_llm/application.ex:43,83`) with a single `:default` pool config (`application.ex:101-109`) that is a TEMPLATE for every origin. Finch materializes a separate pool per origin `{scheme, host, port, tag}` (`Finch.Pool.to_name/1`, deps/finch/lib/finch/pool.ex:143; lazy `maybe_start_pool`, pool/manager.ex:130-140,214-236) — path prefixes like `/v1` are NOT part of the key, and there is NO explicit `:pool` request option in Finch (deps/finch/lib/finch.ex:1017-1020); ReqLLM never sets a pool tag, so every request uses its origin's lazily-created pool from the `:default` template. Per origin: `count` pool processes (NimblePool) × `size` connections each (deps/finch/lib/finch/pool/supervisor.ex:4,22; http1/pool.ex:32-39) — pool capacity = `count × 2` concurrent HTTP/1 streams per origin (size: 2, connections open lazily), NOT global. Shard selection is RoundRobin (finch 0.23's default when no strategy is given is random, `Enum.random`, manager.ex:124; RoundRobin spreads requests across shards via a shared `:atomics` counter, `rem(idx-1, length(entries))` per call — shards added later by `set_pool_count` are included automatically). **Sum-based sizing is the provably safe upper bound**: any single origin's demand = Σ concurrency of the profiles targeting that origin ≤ total concurrency, so sizing every origin at `desired_count(total)` never under-provisions; over-provisioning (N origins × total shards) is harmless (NimblePool shards are cheap; HTTP/1 connections open lazily on checkout, http1/pool.ex:33). Per-origin precision was considered and REJECTED: mapping profiles→origins would require mirroring ReqLLM's ~35-entry provider `default_base_url` table (plus region templates), and the excess-queuing error path is origin-blind (`%ReqLLM.Error.API.Stream{}` carries only `[:reason, :cause]` — no URL field). `count`/`size`/`protocols` are read ONCE at app startup (`application.ex:111-127`); `stream_pool_timeout` (`finch_client.ex:299-305`, becomes Finch's `pool_timeout` checkout/queue wait) and `stream_pool_strategy` (`finch_client.ex:426-428`, becomes the per-request `pool_strategy` opt) are read at CALL time. On checkout timeout, HTTP/1 pool raises the RuntimeError "Finch was unable to provide a connection within the timeout due to excess queuing" (deps/finch/lib/finch/http1/pool.ex:81-90). ReqLLM classifies `:pool_not_available` as retryable (250ms backoff, retry.ex:199-201); EvoGit's `call_llm_with_retry` adds exponential backoff + logs "LLM request failed, retrying..." (`apps/evo_git/lib/evo_git/agent/tool_dispatch.ex:187-224`).
- **Runtime reconciliation (`EvoGit.ReqLLMPool`, `apps/evo_git/lib/evo_git/req_llm_pool.ex`)**: the pool is sized at boot, and runtime concurrency changes AFTER boot (dashboard model-profile save → `AgentScheduler.update_config(:model_profiles)`; `RemoteAPI.reload_config`; per-task `-m` model ids) resize the Finch pool dynamically, **grow-only**. Two triggers: (1) **config change** — `AgentScheduler.handle_call({:update_config, opts}, ...)` (`agent_scheduler.ex:641-654`, helper `reconcile_pool_after_update/1`) reconciles to `desired_count(total)` after any successful config update, where `total = effective_concurrency(model_concurrency, default)` = **`max(sum(model_concurrency), default_llm_max_concurrency)`** — the default bucket is included because unknown model ids share an independent `default_llm_max_concurrency` slot pool (`State.concurrency_for/2`, state.ex:206-208; `Slots` per-model holder MapSets); boot `init/1` also reconciles as a no-op safety (pools are lazy). (2) **excess-queuing error** — `ToolDispatch.call_llm_with_retry/5` (`tool_dispatch.ex:204-218`) detects Finch's "excess queuing" RuntimeError between retries via `EvoGit.ReqLLMPool.excess_queuing_error?/1` and calls `bump_for_excess_queuing/3` to grow pools to `max(ceil(effective * 1.5), 8)` using the same effective-concurrency computation. Grow-only: `Finch.set_pool_count/3` (deps/finch/lib/finch.ex:1202; pool/supervisor.ex:29-55) grows by `start_child`-ing new pools (safe) but shrinks by `terminate_child` (kills in-flight streams) — the module NEVER shrinks (`max(current, desired)`). Pools are keyed per origin and materialized LAZILY on first request, so `set_pool_count` returns `{:error, :not_found}` until an origin is used; `reconcile`/`bump` no-op gracefully on `{:error, :not_found}` and never raise. CLI `-c`/`--concurrency` sets `state.default_llm_max_concurrency`; via the `max(sum, default)` formula it raises the pool size when it exceeds the profile sum (see `apps/evo_git/CONTEXT.md`). **Slot pools**: a runtime `default_llm_max_concurrency` override ALSO raises the scheduler's live per-model LLM slot pools immediately (floor semantics via `State.apply_default_llm_concurrency_override/2` — never lowers explicit profile concurrencies), and queued waiters are granted as capacity frees — see `apps/evo_git/lib/evo_git/agent_scheduler/CONTEXT.md` and `apps/evo_git/CONTEXT.md` for the slot-pool deadlock/wipe analysis. Non-slot-gated `stream_text` calls exist at `system_check.ex:344` and `runtime/pull_request.ex:153` only (the "+2 buffer" comment naming "context compression, evolution synthesis" is stale — context compression IS slot-gated; no synthesis module exists).
- **`start_pool_metrics?`**: `Finch.get_pool_status(ReqLLM.Finch, :default)` only reports pools whose config has `start_pool_metrics?: true` (deps/finch finch.ex:98-102; pool/manager.ex:216 — `track_default?`); the flag defaults to `false`, and ReqLLM's `get_default_pools/0` (deps/req_llm/lib/req_llm/application.ex:101-108) hardcodes `protocols/size/count` only. `config/runtime.exs` uses the `finch:` override form with `start_pool_metrics?: true` in the `:default` pool (the `:default` entry is popped into `default_pool_config` by `Finch.start_link`, so every lazily-materialized origin inherits the flag and `track_default?` becomes true). Without it, reconciliation on `ReqLLM.Finch` is a silent no-op (tests use their own Finch with the flag set, so they pass regardless). `stream_pool_timeout: 300_000` stays top-level (read at CALL time via `Application.fetch_env(:req_llm, :stream_pool_timeout)`, streaming/finch_client.ex:300 — not part of the pool config), as does `stream_pool_strategy: {Finch.Pool.Strategy.RoundRobin, round_robin}` (read at CALL time, finch_client.ex:426-428). The sizing formula `max(total_concurrency + 2, 8)` (per-origin capacity is 2× it, size: 2).

### SSH Remote Development

Genesis supports a VSCode Remote-SSH-like workflow: a lightweight headless daemon runs on a remote server, and the local Phoenix dashboard controls it over an SSH tunnel via Erlang distribution.

**Architecture:**
- **Remote daemon** (`genesis_remote` release): a standard `mix release` `evo_git`-only build (no Phoenix/Tauri), bundled with `include_erts`. Distributed as a tarball that is SCP'd to the remote host and extracted. Launched via `systemd-run --user` (Linux) or `launchctl` with a launchd plist (macOS) as an independent daemon — survives dashboard disconnection. Uses a custom EPMD module (`EvoGit.EpmdDist`) for EPMD-less distribution on a pinned port (default 9000) via `rel/vm.args.eex` (`-epmd_module Elixir.EvoGit.EpmdDist`).
- **Local dashboard**: connects to the remote daemon by (1) establishing an SSH port-forwarding tunnel (`ssh -L <local_port>:127.0.0.1:<remote_port> -N`), then (2) auto-enabling local distribution on-demand via `EvoGit.Distribution.enable_for_remote/1`, then (3) `Node.connect/1` over the tunnel. The custom `EvoGit.EpmdDist` module resolves the remote node's port from a `:persistent_term` registry populated by `EpmdDist.register_target/2` at connect time — no external `epmd` process needed. The `EvoGit.RemoteConnection` GenServer manages this lifecycle.
- **Data access**: the dashboard reads remote agent state/config via `:erpc.call/5` to `EvoGit.AgentScheduler.RemoteAPI` on the remote node (`:erpc` transfers native BEAM terms — atoms, structs, maps — directly, so the API returns native structs like `%ReqLLM.Message{}`, `%Usage{}`, `%AgentState{}` without any serialization). PubSub uses the existing PG2 adapter backed by `:pg`, which is cluster-aware — broadcasts on the remote node's `EvoGit.PubSub` propagate to the local dashboard.
- **Bootstrap vs Connect**: deliberately separate. **Bootstrap** (`EvoGit.RemoteConnection.bootstrap/1`) SCPs the local release tarball to the remote host via CLI `scp`, extracts it via `ssh tar -xJf`, sets the launcher executable via `ssh chmod +x`, detects the remote OS, and launches it as a daemon (`systemd-run --user` on Linux, `launchctl` + launchd plist on macOS) — first-time setup. **Connect** (`EvoGit.RemoteConnection.connect/1`) assumes the daemon is already running and only establishes the tunnel + distribution link. All SSH operations use CLI `ssh`/`scp` via `Port.open` — no Erlang `:ssh`/`:ssh_sftp` modules. **Remote ssh commands must be argv arrays, never quote-wrapped spawn strings**: they go through `EvoGit.RemoteConnection.run_ssh_command/3` (`{:spawn_executable, ...}` + `{:args, [target, remote_cmd]}`, one argv element, no quotes) — `{:spawn, String}` with a quote-wrapped remote command breaks Windows bootstrap (CRT consumes only double quotes, so single quotes reach remote bash and become ONE command name → fails at `:extracting`), and the double-quote swap breaks Unix (spawn strings go through `/bin/sh -c` → local `$`-expansion). OpenSSH re-joins argv with single spaces so the command is preserved verbatim. SSH port, identity file, and other options are handled by the user's `~/.ssh/config`; the target stores only an `ssh_target` string (e.g. `gpu-server` or `user@host`).

**Dashboard UX:**
- Node indicator/selector next to the brand logo in the navbar — shows green dot "Local" or blue dot + target name when remote.
- All navigation links carry `?node=<target_id>` when viewing a remote node.
- Connection management on Settings page (`/settings?category=remote_connections`): add/edit/delete SSH targets (ssh_target, local_binary_path, dist_port, remote_path), bootstrap remote daemon, connect/disconnect.
- When viewing a remote node: Agents page shows remote agents via RPC, Settings is read-only, System controls are disabled (restart/stop), config banner shows remote config status.
- SSH targets are persisted and remembered across sessions.

**Design constraint — multiple remote connections:** Each SSH target gets a **unique per-target node name** (`genesis_remote_<id>@127.0.0.1`, derived from the target's slugified `id`) and a per-target systemd unit (`genesis-remote-<id>`) / launchd plist label (`com.genesis.remote.<id>`). This enables **multiple simultaneous remote connections** — each target connects to a distinct BEAM node name, so `Node.connect` can address multiple hosts. The SSH tunnel uses a dynamically-assigned local port (via `find_free_port/0`) that forwards to the remote daemon's fixed port 9000. The custom `EvoGit.EpmdDist` module maps each per-target node name to its tunnel's local port via `:persistent_term` so the VM's `port_please/2` callback resolves it correctly without an external EPMD process. The remote daemon's `RELEASE_NODE` is set per-target at launch time via `--setenv=RELEASE_NODE` (systemd-run) or an `EnvironmentVariables` dict (launchd plist), and `rel/genesis_remote/env.sh.eex` respects an existing `RELEASE_NODE` env var (`export RELEASE_NODE="${RELEASE_NODE:-...}"`).

**Remote asset download**: `EvoGit.RemoteBootstrap.download_url/1` is deterministic and network-free, always returning the direct `https://genesis.evox.group/dl/genesis_remote_<platform>.tar.xz` URL — a Cloudflare worker "smart download" endpoint that auto-detects whether the user is in mainland China and proxies the GitHub release asset through the Cloudflare network when needed (`curl -fL`/`wget` follow redirects). **glibc is the default and ONLY published Linux variant — asset names are NEVER suffixed** (the musl build is disabled for now, so the `_glibc` suffix, the libc-probe machinery, and `effective_libc`/`detect_libc`/`probe_libc` were all removed from `EvoGit.RemoteBootstrap` / `EvoGit.RemoteConnection`; if musl is ever revived, the suffix logic must be reintroduced deliberately). The `version` in `{:ok, url, version}` is always `"latest"` (keys the local download cache). CI uploads unversioned names (`genesis_remote_<os>_<arch>.tar.xz` — build-desktop.yml; Linux tarballs come from the dedicated `build-linux-remote` job on ubuntu-22.04, darwin/windows from their platform jobs), so no asset matching is needed. **Do NOT reintroduce asset listing/matching or any suffix check** — the desktop (`genesis_desktop_*_*.tar.gz`) and remote (`genesis_remote_*_*.tar.xz`) tarballs share the `_<os>_<arch>` suffix shape, so a bare suffix match would select the wrong asset, and the API call is unnecessary. **Format**: the remote asset is `.tar.xz` (`genesis_remote_<platform>.tar.xz`, created with `tar -cJf` in CI, downloaded/extracted with `tar -xJf` on the remote host); the desktop portable archive is `.tar.gz`. All runner OSes and remote hosts (Linux/macOS) have xz-capable tar, so no fallback exists — xz failure fails loudly.

### Desktop App Build Pipeline

The project includes a GitHub Actions workflow (`.github/workflows/build-desktop.yml`) that automatically builds native desktop app installers on every GitHub release. Each platform builds its own native Elixir release (with `include_erts`) and then packages it with Tauri — no cross-compilation or third-party wrapper is used.

- **Trigger**: Release published (including pre-releases) or manual `workflow_dispatch`
- **Build process**: Each platform job runs `mix release genesis_desktop` (native, `include_erts` bundles the host ERTS into the release directory) → copies the release directory to `desktop/src-tauri/resources/genesis-backend/` → `tauri build` produces native installers (the Tauri CLI is installed from the npm package `@tauri-apps/cli` — prebuilt binaries for all platforms including linux-arm64-gnu; see `.github/workflows/CONTEXT.md` for why npm rather than cargo-binstall). The headless `genesis_remote` release is also built and uploaded as a `.tar.xz` tarball (xz-compressed for smaller remote-bootstrap downloads) alongside the desktop installers.
- **Release configuration**: Three standard mix releases are defined in `mix.exs`: `genesis_desktop` (full, bundled as Tauri resource), `genesis_remote` (headless `evo_git`-only, bakes `config: [evo_git: [remote_release: true]]` so the runtime detects remote-daemon mode and enables EPMD-less distribution via `rel/genesis_remote/vm.args.eex`), and the base `genesis`. The remote release excludes `evo_dash` entirely.
- **Job structure**: Five job groups, each on a native runner for its target platform: `build-linux` (desktop only, ubuntu-24.04), `build-linux-remote` (dedicated glibc `genesis_remote` tarball on ubuntu-22.04 — the default Linux remote asset), `build-macos-arm64`, `build-windows-x64`, and `publish-release`.
- **macOS**: Builds ARM64 (`macos-15`) → `.dmg` / `.app` bundles
- **Linux (glibc) desktop**: Builds x86_64 (`ubuntu-24.04`) and ARM64 (`ubuntu-24.04-arm`) → `.deb` / `.rpm` / AppImage / `.tar.gz` portable archive (AppImage excluded on ARM64 — `appimagetool`/`linuxdeploy` are x86_64-only). Flatpak is not built — Tauri v2 has no native Flatpak bundle target (documented in the workflow).
- **Linux remote (glibc, default)**: the dedicated `build-linux-remote` job builds `genesis_remote` ONLY (no desktop, no Tauri, no Rust) on `ubuntu-22.04` (x64) and `ubuntu-22.04-arm` — the older glibc (2.35 vs 24.04's 2.39) gives the daemon a wider host-compatibility range → `genesis_remote_linux_x64.tar.xz` / `genesis_remote_linux_arm64.tar.xz` (NO suffix — glibc is the default and only published Linux variant). The **musl build is disabled for now** (too costly; it was an Alpine-container x64-only job that bundled `libgcc_s.so.1` into `lib/runtime/` for the precompiled Rust NIF `.so` files; arm64 was never supported because GitHub Actions JavaScript actions don't run in Alpine containers on ARM64 runners — revival notes in `.github/workflows/CONTEXT.md`).
- **Windows**: Builds x86_64 (`windows-2022`) → `.msi` / `.exe` (NSIS) installers.
- **Caching**: Mix deps (`deps/`), Mix build (`_build/`), and Rust target (`Swatinem/rust-cache@v2`) are cached per platform/target to speed up CI. The Tauri CLI (npm `@tauri-apps/cli`, cached under `~/tauri-cli` on POSIX / `%APPDATA%\npm` on Windows) is also cached.
- **ARM runner ImageOS fix**: GitHub-hosted ARM partner runners (`ubuntu-24.04-arm`, `ubuntu-22.04-arm`) report `ImageOS` values that `erlef/setup-beam` does not recognize. The workflow sets `ImageOS` to the base value (`ubuntu24` / `ubuntu22`) via `$GITHUB_ENV` before the setup-beam step for each ARM64 target.
- **Toolchains**: CI requires Elixir/OTP and Rust (Tauri) on all platforms; Linux also needs system packages (webkit2gtk, libayatana-appindicator3-dev for system tray, libdbus-1-dev for tray-icon crate, etc.)
- **Vendor binaries**: ripgrep and git (or MinGit on Windows) are bundled into `apps/evo_git/priv/vendor/{platform}/` for each target
- **Version pinning**: CI pins the BEAM toolchain via explicit `OTP_VERSION` / `ELIXIR_VERSION` env vars in the workflows (OTP 29, Elixir 1.20.3)

The Tauri Rust shell (`desktop/src-tauri/src/sidecar.rs`) spawns the release launcher script (`bin/genesis_desktop start`) as a child process and handles backend lifecycle with the correct env vars.

### Auto-Update / Push-Update (design analysis — NOT yet implemented)

A full design analysis lives in `docs/auto-update.md`. Recommended direction (decided, pending implementation):

- **Per-platform, convention-respecting**: macOS → in-app updater via `tauri-plugin-updater` (pipeline already signs/notarizes; only the DMG is stapled, `.app.zip` is not); Windows → `tauri-plugin-updater` with **NSIS only** (`installMode: "passive"`; MSI excluded — known updater bugs; no Authenticode signing exists yet); **Linux → package-manager-first**: deb/rpm channels get an apt/dnf repo + in-app "update via your package manager" notification, NO self-install; only the **AppImage** (x64) channel self-updates; portable `.tar.gz` → download link only. Remote daemons (`genesis_remote`): current flow overwrites files under a running daemon — needs stop→swap→start (deferred).
- **Update timing — two-phase model**: Phase 1 check/download/signature-verify is safe anytime (background); Phase 2 apply (stop backend → install → relaunch) is **gated on task idle** (`TaskRegistry.list_task_ids([:running, :pending, :cancelling, :finalizing]) == []`). Busy → defer or "Apply & gracefully stop tasks" (reuses graceful-cancel: 3-turn grace, worktree git-commit at grace entry, results preserved; grace is NOT wall-clock bounded — LLM retries ~9min, tool cap 30min → generous timeout + `force_kill_task/1` fallback with explicit user warning). A new **`:interrupted`** task status is recommended (codec `@known_atoms` + ~10 hardcoded status lists; schema has no constraints). Backend must stop from inside the BEAM (`System.stop/0` — `bin/genesis_desktop stop` is broken under `RELEASE_DISTRIBUTION=none`); Rust watchdog needs a new update-intent state (currently exit-code-0 = intentional app exit).
- **Blocker checklist** (in order): minisign keypair + CI secrets, manifest/signature generation in `publish-release` (static JSON per platform, GitHub Releases hosting first, genesis.evox.group Cloudflare worker later), Windows Authenticode cert, macOS `.app.zip` stapling, Linux apt/dnf repo + GPG. No `tauri-plugin-updater` dependency or updater config exists anywhere today. See the doc for the phased plan and open questions.
- **Updater choice (decided, follow-up analysis — docs §1.1, §10, §11):** official `tauri-plugin-updater` v2 everywhere — NOT a custom updater, NOT Sparkle (macOS-only third-party plugin + appcast feed; our UX is a dashboard component, not a native panel). Rust `check_update`/`install_update` commands wrapping `UpdaterExt`, invoked from dashboard JS via the existing `window.__TAURI__.core.invoke` pattern (no npm — asset pipeline has no package.json; `withGlobalTauri: true`). Requires `bundle.createUpdaterArtifacts: true` — tauri build then emits updater payloads + minisign `.sig` files; **CI's macOS `ditto` `.app.zip` staging (build-desktop.yml L593-595) must become a `.app.tar.gz` of the notarized + stapled app** (the zip stays as a distribution artifact only). **CI changes**: `TAURI_SIGNING_PRIVATE_KEY`/`TAURI_SIGNING_PRIVATE_KEY_PASSWORD` secrets (`tauri signer generate` once; pubkey embedded in `tauri.conf.json` `plugins.updater.pubkey`), `latest.json` manifest generation in `publish-release` between staging (L745-750) and upload (L752-757) — version = release tag (strip `v`), per-platform `{url, signature}` (signature = full `.sig` file content); platforms = darwin-aarch64 app.tar.gz, linux-x86_64 AppImage tar.gz, windows-x86_64 NSIS exe; MSI/deb/rpm/dmg/portable-tar.gz/`genesis_remote` tarballs excluded; feed = `releases/latest/download/latest.json`. **UX (decided): Check Update card on the System page** (`SystemLive`, System Control section ~L81-114, async pattern L765/809) with states checking/up-to-date/available/ready/error + a notification dot (amber = available, blue `animate-ping` = downloaded & verified) on the System sidebar item (`sidebar_nav_link/1`, layouts.ex L391-414); background check (startup + manual "Check now" + ~6h) with **auto-download** (download+verify is inert); apply is manual-click only, gated on task idle (`TaskRegistry.list_task_ids([:running, :pending, :cancelling, :finalizing]) == []`) with Defer / "Apply & gracefully stop tasks" / user-warned force fallback; apply sequence mirrors `begin_quit` (JS `invoke("begin_update")` sets Rust update-intent flag → backend `System.stop/0` from inside the BEAM → watchdog runs installer → relaunch). Desktop gating: `Application.get_env(:evo_dash, :desktop_release, false)` or `EVOGIT_DESKTOP=1` + local node.

### NixOS Local Build

For building and testing the desktop app on NixOS, a `flake.nix` is provided at the repository root:

```bash
# Enter the development shell with all native dependencies (Erlang/OTP 29,
# Elixir 1.20, Rust, webkitgtk-4.1, etc.)
nix develop

# Then follow the build steps printed by the shell hook:
#   1. mix deps.get && mix assets.setup && mix assets.deploy
#   2. cargo install tauri-cli --version "^2.0"   (first time only)
#   3. ./nix/bundle-vendor.sh                      (vendor binaries)
#   4. MIX_ENV=prod mix release genesis_desktop      (standard release)
#   5. cp -a _build/prod/rel/genesis_desktop desktop/src-tauri/resources/genesis-backend
#   6. cd desktop/src-tauri && cargo tauri build    (native desktop app)
```

`nix build .#desktop` produces a working store app: the Tauri binary resolves the backend release via `sidecar_path::resolve_launcher` (checks `<exe_dir>/resources/genesis-backend/bin/genesis_desktop` first — `genesis-desktop.nix` symlinks the release there), the wrapper puts the full GTK/WebKit/tray runtime stack on `LD_LIBRARY_PATH`, and `genesis.nix` bakes a deterministic `releases/COOKIE` (`removeCookie = false`, otherwise nixpkgs' mixRelease postFixup deletes it and the launcher dies with `cat: .../COOKIE: No such file or directory`). The GUI needs a writable `XDG_RUNTIME_DIR` for the tray icon. Details in `desktop/CONTEXT.md` → Known Issues.

**Known issue — tauri-build resource check:** tauri-build 2.x validates at compile time (relative to the crate dir) that every path in `tauri.conf.json`'s `bundle.resources` exists — `resources/genesis-backend` must be present when `build.rs` runs or the build fails with `resource path 'resources/genesis-backend' doesn't exist`. The flake source is the bare git tree (no placeholder dir), so `genesis-desktop.nix` symlinks the Mix release into the unpacked crate source in a `preBuild` hook (`ln -s ${genesisRelease} resources/genesis-backend`). Keep this hook when restructuring the derivation; dev flows (`cargo tauri build` with a cargo-installed CLI) and CI (`tauri build` via the npm-installed CLI) must still copy the release into `desktop/src-tauri/resources/genesis-backend` before building, as documented in `desktop/CONTEXT.md`.

**Design decision — no cargoHash, version from VERSION:** The flake avoids all manual hash/version maintenance on code updates:
- `genesis-desktop.nix` uses `cargoLock.lockFile = ./desktop/src-tauri/Cargo.lock` (NOT `cargoHash`) — nixpkgs `buildRustPackage` derives the vendored-deps store path purely from the lock file (each crate fetched by the checksum already in Cargo.lock), so updating Cargo.lock never requires touching the derivation. There are no git deps, so no `cargoLock.outputHashes` is needed; if git deps are ever added, they MUST be declared there. Do NOT use `cargoHash`/`lib.fakeHash` — the lock-file-derived approach is the only supported way.
- Both `genesis.nix` and `genesis-desktop.nix` derive `version = lib.trim (lib.fileContents ./VERSION)` from the repo-root `VERSION` file instead of a hardcoded string — never bump the version in the Nix files by hand (a stale hardcode would misalign `postInstall`'s `evo_git-<version>` vendor path and the baked COOKIE with the actual mix release app dir).
- **Remaining manual hash:** `mixFodDeps.hash` in `genesis.nix` must still be updated when `mix.lock` changes (nixpkgs `fetchMixDeps` has no lock-derived equivalent) — this is the only flake hash that needs manual maintenance.

### Research Notes: PDF/DOCX → Plain Text Extraction (for LLM objective prompts)

Research (Aug 2026) for feeding `.pdf`/`.docx` file contents into LLM objectives. **Status: plain-text, `.docx`, AND `.pdf` are IMPLEMENTED — but the conversion utility is a FRONTEND feature and lives in `EvoDash.AttachedFile` (`apps/evo_dash/lib/evo_dash/attached_file.ex`), with `ex_pdf` declared as a plain Hex dep of `:evo_dash` (ex_pdf 1.0.7 — plus ex_pdf_core/ex_pdf_read/ex_pdf_components — pure BEAM, zero runtime deps, no release `applications:` changes needed; the umbrella mix.lock already covers it, so the existing `genesis.nix` mixFodDeps hash remains valid)**. `.txt`/any text read verbatim; `.docx` extracted with OTP `:zip` + regex; `.pdf` extracted to Markdown via the pure-BEAM `ex_pdf` reader — each page becomes a `## Page N` heading with a visible conversion note (basename + extraction-artifact caveat) prepended so LLM agents don't mistake artifacts for broken text; password-protected PDFs → `{:invalid, ...}`; scanned/image-only PDFs → `{:empty, ...}` (no OCR). **The core `:evo_git` stays clean by design**: `EvoGit.PromptFile` (`apps/evo_git/lib/evo_git/prompt_file.ex`, CLI `get_input/2` at `cli.ex:136-154`) reads plain text only and rejects non-UTF-8 binaries/PDFs/DOCX with `{:error, {:not_text, ext}}` — core users bring their own read/convert script, and the `genesis_remote` release (evo_git only) deliberately ships no ex_pdf (in the remote-SSH architecture files are read on the local node running the frontend, not on the remote server). The objective stays a plain `String.t()` end-to-end (AgentSpec/AgentState/TaskInfo `opts`); conversion happens only at the dashboard's objective-editor attach flow: a "+" button on the objective box (`TaskFormComponents.task_form/1`) opens a native file dialog (`EvoDash.DirectoryPicker` `:file` kind — native tools + wx `wxFileDialog` fallback) and appends the `EvoDash.AttachedFile.read/1`-converted content (Markdown for PDFs, text for txt/docx) into the objective — see `apps/evo_dash/CONTEXT.md`. Findings:

- **No existing deps**: no XML/zip/PDF/archive hex packages in `mix.lock` (63 entries). Precompiled-Rust-NIF precedent exists: `lumis`, `mdex`, `html5ever` (rustler_precompiled, pre-fetched in `genesis.nix`).
- **OTP built-ins**: `:zip` module is in `:stdlib` (always present in releases — verified). `:xmerl` is a separate OTP app and is **NOT** in a default mix release (verified empirically: only kernel/stdlib/compiler/elixir/logger/sasl + the app) — would need `xmerl: :load` added to all 3 release `applications:` lists in `./mix.exs` (same pattern as `wx`). `:zlib` also in stdlib.
- **DOCX (zero-dependency, recommended)**: docx = ZIP of XML; main text in `word/document.xml` as `<w:t>` runs. Verified end-to-end with OTP only: `:zip.extract(binary, [:memory])` → `re:run(xml, ~r{<w:t[^>]*>([^<]*)</w:t>}, [global, {capture, all_but_first, binary}])`. Gotchas: XML entities (`&amp;` etc.) need unescaping; `xml:space="preserve"` attrs; `w:instrText` field codes leak in; headers/footers/footnotes/comments are separate files (`word/header*.xml`, `word/footnotes.xml`, ...) not in document.xml. `re:find` crashes this OTP 29.0.4 Nix build — use `re:run`. Hex docx readers are dead (`docx` 2022, `docxelixir` 2017); `redlines` (active, sweet_xml-based) validates the same approach in production.
- **Pure-BEAM PDF**: `ex_pdf` (MIT, fork of `pdf`; writer-only original — no extraction) adds `ex_pdf_read`: `Pdf.Reader.open/read`, `shape: :text` → per-page strings; handles xref recovery, no OCR. Young (v1.0.7, Jul 2026, ~2 stars, single maintainer). `native_elixir_pdf_utilities` (MIT, pure-BEAM tokenizer/merger/extractor; requires Elixir ~> 1.19; ~1yr old, 6 stars). Both extract only embedded text; quality on complex CMaps/ligatures unproven vs poppler.
- **NIFs**: `pdf_elixide` (Rustler + `rustler_precompiled`; wraps pdf_oxide; MIT) — precompiled for ALL 5 vendor platforms incl. windows-msvc/gnu; high-quality output (text w/ geometry, Markdown/HTML, table detection); pre-1.0 with issue tracker disabled (API instability risk). `pdfium` (gmile, MIT, NIF wrapping Google PDFium, precompiled darwin/linux ONLY — no Windows → disqualifying for this project). No `mupdf`/`pdf2text`/`pagetop`/`pdf_text` packages on hex (don't exist; `mllp` is an HL7 protocol lib — unrelated). `pdf_extractor` wraps Python pdfplumber — rejected (Python runtime dep). `ex_pdf_poppler` — abandoned README template.
- **External binaries**: `pdftotext` (poppler) is the quality benchmark (`-layout` flag). Vendoring feasibility per platform: Windows — `oschwartz10612/poppler-windows` GitHub releases (pdftotext.exe + DLLs, active; MinGit-style); Linux — apt `poppler-utils` on ubuntu-24.04 runners (deb/rpm: declare runtime dep; AppImage/portable: bundle via linuxdeploy ldd scanning); macOS — no official binaries; brew bottle + `install_name_tool` dylib surgery (fiddly) or skip vendoring on macOS. MuPDF `mutool` — Artifex now ships only source + Windows binaries (no recent mac/linux prebuilts); AGPL (project is AGPL-3.0 so license OK, but no binaries). `pandoc` reads docx but NOT pdf. `antiword`/`catdoc` = legacy `.doc` only. `textutil` (macOS built-in) does docx/rtf/html→txt but NOT pdf. `libreoffice --headless` does both but is heavy/slow (multi-second startup) — not per-file suitable.
- **Tauri/Rust side** (assessed, not recommended): `lopdf` has no real text extraction; `pdf-extract` (MIT) spotty maintenance; `docx-rs` immature; would not serve CLI/`genesis_remote` — Elixir-side solution preferred.
- **ReqLLM-native file attachment** (alternative to text conversion — investigated Aug 2026, NOT implemented): the vendored `req_llm` 1.20.0 (published hex, not a fork) already has a `:file` content-part type (`ReqLLM.Message.ContentPart.file(data, filename, media_type)` = inline binary; `file_id/1` / `owned_file_id/3` = provider-owned refs, `ReqLLM.ProviderFileReference`). Native support matrix: **PDF** ✅ OpenAI Responses API (inline base64 `input_file`, client-validated mimes `@responses_api_mimes` = images + `application/pdf`, `openai.ex:137`), **Gemini** ✅ any media type inline (`google.ex:2736-2746`; server accepts pdf/docx/txt/csv/xlsx/pptx, ~20 MB inline limit), **Anthropic** ✅ base64 `document` block (server accepts only `application/pdf` for documents — docx → HTTP 400), **OpenRouter** ✅ native PDF file block (`openrouter.ex:586-611`). **DOCX**: only Gemini works end-to-end (OpenAI client-side validation blocks docx; Anthropic server rejects). **Silent-failure gotcha**: providers WITHOUT `:file` handling (DeepSeek, Alibaba/Qwen, Moonshot, Z.ai, MiniMax, vllm, ollama, ...) do NOT raise — binary data is silently mis-encoded as an `image_url` data-URI (`provider/defaults.ex:1055-1072`) and the server 400s or returns garbage; OpenAI Chat API and xAI raise client-side ("images only"). EvoGit uses plain-text parts everywhere today; the LLM call path is `ReqLLM.stream_text` (`tool_dispatch.ex:204`). Injection point for native attachments would be `Runner.do_run/2` `runner.ex:99-110` (the single place the objective becomes a user message) but carrying binary data per-agent would need a new AgentState field (dispatch/RemoteAPI/codec plumbing) and provider gating — assessed as NOT "straightforward and clean", hence not implemented.
- **Recommended shape** (tier 2 EXECUTED): tiered — (1) zero-dep `:zip`+regex DOCX extractor — **DONE** (`EvoDash.AttachedFile`, frontend only); (2) pure-BEAM PDF via `ex_pdf` — **DONE** (`EvoDash.AttachedFile`, frontend only — deliberately NOT in `genesis_remote`); (3) optional `pdftotext` upgrade path via `EvoGit.Executable.resolve("pdftotext")` (system-first, vendored fallback — extend `bundled_path/1` beyond git/rg) for higher-quality layout when available — remains OPTIONAL/future; (4) ReqLLM-native PDF attachment for file-capable providers with a text-extraction fallback for the rest — NOT implemented (see the provider-matrix findings above).
