# EvoGit — Root

## Intent

EvoGit is an evolutionary software development framework built in Elixir.
It models a codebase as a hierarchical **Context Tree** (Spatial Dimension) and evolves it through a DAG of Git commits (Temporal Dimension); AI agents recursively build and optimize software, guided by spatial contracts in per-directory CONTEXT.md files.
This is an **Elixir umbrella project** with two child applications:

| App | Directory | Purpose |
|-----|-----------|---------|
| `:evo_git` | `./apps/evo_git/` | Core runtime — agent execution, Git interactions |
| `:evo_dash` | `./apps/evo_dash/` | Phoenix LiveView dashboard — real-time visualization and task management |

The full design specification is documented across the CONTEXT.md tree.

## Routing Table

- `./apps/evo_git/` → Core runtime (agents, scheduler, git adapter, runtime phases)
- **Config freshness (RAM snapshot + event-driven reload)** — `EvoGit.Config.resolve/0,1`, `user_config/0`, `credentials/0` and `config_status/0` read ONE `:persistent_term` snapshot per config directory (`EvoGit.Config.Cache`, built by `EvoGit.Config.build_snapshot/1`: parse both TOML files → defaults merge → validate ONCE), so a read is a term lookup with zero `File.stat`/`File.read`; freshness comes from exactly two event SOURCES converging on ONE reload handler in `EvoGit.Config.Watcher` (`refresh/1` → `Cache.reload_safely/1`, the only rescue/catch-guarded reload; `Cache.reload/0,1` stays raw): the already-vendored `file_system` watch of the config dir (debounced ~150 ms on `config.toml`/`credentials.toml`, `agents.toml` → `CustomAgents.reload/0`; production-only, skipped in `:test`, degrades to one warning when the backend is unavailable) and the synchronous `Watcher.notify_change(dir)` event raised by `save_user_config/1`/`save_credentials/1` (the `/settings` save event — a bounded `GenServer.call`, total with an inline guarded fallback when no watcher is registered/dead/slow, so a save always returns with fresh RAM config); a content-fingerprint change stores once and broadcasts `{:config_reloaded, node, dir, generation}` on the `"config"` topic, and `RemoteAPI.reload_config/0` still forces a disk re-read before applying scheduler settings → `./apps/evo_git/` (`config/cache.ex`, `config/watcher.ex`, `config/config.ex`, `application.ex`) + `./config/`
- **Agent runtime — one session process, two drivers (implemented)** — every agent (one-shot or interactive) is ONE supervised `EvoGit.Agent.Session` (`gen_statem`, `:temporary`, registered by `agent_id`) owning the single `%EvoGit.Agent.State{}`; the loop is a library run in ONE short-lived task per exchange (`EvoGit.Agent.Exchange.run/2` + `Agent.Turn` via `Agent.Session.Worker`) checkpointing state per turn, so inspect/input/cancel/close stay answerable mid-run.
  `:evogit_agent_summary` is a summary-only read model (no context, pending messages or cancel flag); `EvoGit.AgentScheduler.ControlPlane` owns the atomic `:evogit_agent_inbox` + `:evogit_agent_control` tables the `AgentScheduler.Store` helpers delegate to.
  `{:yield}` parks an interactive root in the non-terminal `:awaiting_input` status (persisted `session_mode`), `{:finish}` keeps `AgentScheduler.run_agent/2` blocking `{:ok, %Result{}}`, close is explicit (`start_session/1`, `send_session_message/3`, `close_session/1`, `await_close/1`; no idle TTL), completion runs once, `prompt_cache_key` is minted at registration, and streaming is push-only (`EvoGit.Agent.Stream`: `watch/1` subscribes the caller to the `"agent:<id>"` topic and registers it in the session's monitored watcher set, the `map_size(watchers) > 0` gate is evaluated per LLM attempt, deltas are ~75 ms coalesced `{:agent_delta, agent_id, seq, events}`, and snapshot + `seq` is the only resync).
  Lifecycle ownership is re-keyed on the session pid (worktree leased/released once, background jobs, `ProcessManager`, `SchedMeta.session_pid`), `EvoGit.Runtime.Assistant` is the interactive phase, and durability (P5) is deferred — sessions are in-memory, so a BEAM restart fails them and reclaims their worktree; rationale: `./docs/agent-runtime-refactor.md`, contracts: `agent/session/CONTEXT.md` + `agent/stream/CONTEXT.md`.
- Managed process & tool-execution platform — `EvoGit.ProcessManager` owns every agent-held execution (foreground vs background, one terminal fact, audited control), `EvoGit.ToolRuntime` owns the tool batch, and `/processes` is the inspector → `./apps/evo_git/` (`process_manager/`, `tool_runtime/`, `sandbox/`, `background_jobs.ex`) + `./apps/evo_dash/` (`live/processes_live/`, `components/process_components.ex`); details: `process_manager/CONTEXT.md` + `tool_runtime/CONTEXT.md` + `docs/process-management.md` + §Managed Process below.
- Virtual Context Tree (VCT) — an internal namespace, NOT a filesystem: `vct:///projects/<name>` mounts bind a point to an absolute OS path as metadata only (no directory created, the path may be missing) in SQLite `vct_mounts`, the project list is capped at `VCT.max_projects/0` with oldest eviction, and RESERVED/system mounts (outside `vct:///projects/…`, first `vct:///genesis-source`) resolve but are never listed, evicted or forgotten; `%ContextNode{}` carries `path` + `vct_path` while task execution, `foreign_repos` and prompt paths stay unchanged → `./apps/evo_git/` (`vct.ex`, `vct/`, `core/context_node.ex`) + `./apps/evo_dash/` (`components/project_components.ex`) — details: `vct/CONTEXT.md` + `core/CONTEXT.md` + `docs/virtual-tree.md`.

### Task data plane

Objectives are submitted and observed through the dashboard task form, the Genesis Assistant, and the MCP endpoint (`docs/agent-mcp.md`).
Every path — `NodeContext.start_task` (dashboard) through `EvoGit.TaskRegistry.start_task/2` → TaskExecutor → runtime phases — uses the same data-plane key contract: `:path` is absolute before enqueue, `:mode` is a STRING, and `RuntimeOpts` raises on atoms.
Task-level options are `path`, `mode`, `starting_commit` (evolve), `node_path`, `archive`, `foreign_repos` (read-only), and `attachments` (the root agent's first message); objectives come from the task form or MCP, not a prompt file.
Custom-agent mode is the option pair `mode: "custom"` plus `:agent` (custom agent id).
Canonical selection is `provider_profile_id` + `model` + optional `reasoning_effort`, validated with the schema and enqueued as `model_spec: spec, model_id_locked: true`; Auto omits both keys.
Canonical nonempty `llm.providers` takes precedence over legacy `llm.models` / flat config; old model profiles normalize one-for-one into separate accounts.
Configured defaults are `[llm] default_provider_profile` (else first account), account `default_model` (else first nested model), then model-over-account reasoning defaults; effort-list order never implies a default.
Config is persistent in config.toml and is never changed by task submission.
`EvoGit.CommandShell` is only the `run_command` agent tool's literal command registry.
Details: `apps/evo_git/CONTEXT.md` + `apps/evo_git/lib/evo_git/CONTEXT.md`.

### Custom Agents & Custom Task Mode

Users define custom agents declaratively in `<config_dir>/agents.toml` (pure TOML: `name`, `description`, `prompt` system prompt, `agent_type` read/read_write, `delegation_level`, `model_id`, `max_turns`, `tools`, `subagents`; ids auto-derived from slugified names).
An optional `[model_selection] script` is a short user Elixir body evaluated per agent spawn (an `agent` map in scope: `agent_type`, `custom_agent_id`, `depth`, `parent_id`, `task_id`, `objective`; last expression = provider-profile/account id selecting its defaults, `nil`/`""`/`false` → default) via `EvoGit.CustomAgents` / `EvoGit.Agents.Custom` / `EvoGit.CustomAgents.ModelSelector` (compile-once stat-validated cache, never raises user-code errors).
Custom-agent `model_id` remains the legacy-named account-ID default, distinct from a task's concrete `model_spec`.
Model priority per spawn: explicit canonical task selection (including inherited locked selection) → locked legacy ID → script → canonical definition/inherited `default_model_spec` → legacy spec/custom-definition ID → configured default.
A locked canonical selection propagates the entire account/model/effort identity to children and overrides child choices; invalid canonical selections fail closed, while unknown legacy script IDs retain configured-default fallback.

**Custom tools** — users add LLM-callable tools by dropping Elixir source (`.ex`/`.exs`) or compiled BEAM (`.beam`) into `<config_dir>/tools/`: each file implements the `EvoGit.CustomTools.Tool` behaviour (`schema/0`, `execute/2`, optional `read_only?/0` defaulting to `false` → WRITE).
They load lazily + cached by file fingerprint, are opt-in via a custom agent's `tools` whitelist (an absent `tools` yields only the built-in set), and dispatch through the SAME tool-dispatch + write-gating path as built-ins; dashboard Settings → Agents shows a "Custom Tools" panel alongside the custom-agents list editor + model-selection script editor.
Detail: `apps/evo_git/lib/evo_git/custom_tools/CONTEXT.md` + `apps/evo_git/lib/evo_git/custom_agents/CONTEXT.md` + `apps/evo_dash/CONTEXT.md`.

**Custom task mode** (entry point for custom root agents): a 4th dashboard task mode **"Custom Agent"** (combined-mode string `"custom_agent"`) maps to `{:evolve, mode: "custom", agent: <custom_agent_id>}` — task type stays `:evolve`, mode opt value `"custom"` (a STRING from every entry point; RuntimeOpts normalizes); `EvoGit.Runtime.Evolution.run/2` routes `"custom"` to a custom-root path with evolve semantics (reviewable `merge_and_report`), and a missing/empty `:agent` raises a descriptive ArgumentError before any repo I/O.
Custom task mode is the dashboard's **"Custom Agent"** mode or the MCP equivalent (mode `"custom"` plus a root agent select); custom agents are root-only this version (not spawnable as subagents), `delegation_level` default `:low`; the task form has an Agent select plus provider/model/reasoning selection with an explicit "Auto (by rules)" provider option.
Details: `apps/evo_git/CONTEXT.md` + `apps/evo_dash/CONTEXT.md`.
## Constraints

- Umbrella structure: all deps, build artifacts, lockfile at root (`./deps/`, `./_build/`, `mix.lock`)
- Elixir ~> 1.18 required
- Git CLI only — no libgit2 bindings
- No source code at root — all code under `./apps/`
- Agents commit before delegating subagents (auto-commit fallback enforced)
- Genesis stores its runtime artifacts (agent worktrees, state) under a `.genesis/` directory at each repo root; that directory must be git-ignored everywhere (root `.gitignore` and the `.gitignore` Genesis auto-writes into new repos)
- LLM-generated code runs under platform-appropriate sandboxing (systemd-run on Linux, bwrap/bubblewrap on Linux without systemd — e.g. Docker — filesystem isolation only, sandbox-exec on macOS, direct on Windows); backend preference via `[sandbox] backend = "auto" | "systemd" | "bwrap"` (`auto` tries systemd-run first, then bwrap, then no sandbox). The bwrap backend runtime-probes its environment (`EvoGit.Sandbox.Bwrap.capability/0`; override via app env `:bwrap_capability`): in rootless podman containers (container root without CAP_SYS_ADMIN) it runs `:degraded` — `--unshare-pid` dropped (the kernel blocks fresh-procfs-in-nested-pid-ns), filesystem isolation retained; an environment where even the degraded shape fails is `:unusable` and `:auto` falls back to no sandbox. **Windows currently has NO sandbox** (`EvoGit.Sandbox.None`, `enabled?/0` hardcoded `false`, direct `System.cmd`), and the macOS profile is allow-most-read with plain string-interpolated paths; the policy itself lives ONCE in `EvoGit.Sandbox.Spec.build/2`, the spec every Unix renderer consumes, and `EvoGit.Sandbox.backend_reason/0` plus the once-per-BEAM `warn_if_unisolated/0` make a no-isolation host (Windows) visible instead of silent; the target design — one `EvoGit.Sandbox.Spec` consumed by per-OS renderers, a small standalone Rust helper (`genesis-sandbox.exe` → Windows **MXC**/PSEC, modelled on OpenAI Codex) and a hardened Seatbelt profile built from `-D` parameters with writable-root/ancestor anchors — plus its P0–P4 plan, non-goals, gotchas and test strategy live in `./docs/platform-sandbox.md` (read it before adding a backend or changing the policy spec; resource governance/OOM is a separate workstream there). Details: `apps/evo_git/lib/evo_git/sandbox/CONTEXT.md`
- No hardcoded model or username — users configure via `~/.config/genesis/config.toml`
- SQLite stack (`xqlite` + its Ecto adapter) moves as ONE unit: `{:xqlite, "~> 0.16.0"}` in `apps/evo_git/mix.exs` paired with the `xqlite_ecto3` git `ref:` pin (each adapter revision requires exactly one xqlite minor series — `~> 0.16.0` since ref `8f2e632`), because a bulk `mix deps.update --all` that moves only one of them fails resolution or ships a half-migrated driver.

## Architecture Summary

EvoGit has two OTP applications under an umbrella:

- **`:evo_git`** (Core Runtime): AgentScheduler GenServer managing worktree pools, LLM/tool slot management with global backoff, agent implementations, Git adapter, and two-phase execution (Genesis → Evolution); 3-level configuration (built-in defaults → user TOML config → session-level runtime overrides).
- **`:evo_dash`** (Web Dashboard): Phoenix LiveView interface with project-based task management, agent tree inspector, runtime settings panel and an in-browser config editor (Bandit, Tailwind CSS 4 + DaisyUI, SQLite via Ecto / `xqlite_ecto3`).

Key design: spatial context tree for routing, phylogenetic graph for temporal evolution, transient agents in isolated worktrees, multi-repo support via absolute path resolution, slot-based concurrency with LLM rate-limit backoff, multi-platform sandboxing, and a dynamic skills system.

### Test Runtime & Parallelism Policy

Code integrity matters, and so does the test suite's runtime: a slow suite taxes every future change, so **test speed is part of test quality and an unnecessary `async: false` module is a defect**, not a style choice.
ExUnit runs ALL `async: true` modules concurrently and THEN drains the `async: false` ones one at a time — so only work removed from that serial tail, or made cheaper, shortens a suite.
**New tests default to `async: true`.** A module may be `async: false` only when it mutates BEAM-global state another concurrently running module can observe (a process-wide env var, an app-env key, `:persistent_term`, a global ETS table or singleton GenServer, a shared PubSub topic it asserts on), and it then carries an in-file comment naming the exact forcing global; the suite's `test/CONTEXT.md` lists the sync modules and their reasons.
**ExUnit parallelises across MODULES, never within one** — splitting an oversized suite into several async modules is the lever.
Buy speed with the established patterns, never by weakening an assertion: default-inert call-time seams (`Application.get_env(:evo_git, key, production_default)` read at the call site; `EvoGit.Platform.config_dir/1`'s `:config_dir_fun`), per-process overrides resolved via `Process.get`/`$callers`, uniquely-named isolated Store/TaskRegistry instances instead of the app-global pair, and event-driven/bounded-poll waits instead of fixed `Process.sleep`; removing a redundant or over-blocking test is allowed when it buys real parallelization and a fixture may be simplified for speed, but a surviving assertion keeps its full strength and the documented "pins that must not be weakened" stay pinned.
Judge a change by the TOTAL wall clock of the app's suite, not by the sync figure alone (a sync→async move that shifts work into an already-saturated async cohort is a regression and gets reverted); the host is shared, so absolute timings swing several-fold under load — compare a same-session A/B and repeat runs before concluding anything.
Per-suite rules, the measured cost profile and the remaining sync inventory: `apps/evo_git/test/CONTEXT.md` and `apps/evo_dash/test/CONTEXT.md`.

### Runtime Data Directory (`tasks.sqlite`)

The SQLite task database lives in the platform data directory resolved by `EvoGit.Platform.data_dir/0` (`apps/evo_git/lib/evo_git/platform.ex`) — NOT via Tauri's `path_resolver`: macOS `~/Library/Application Support/genesis/tasks.sqlite`, Linux `$XDG_DATA_HOME/genesis/tasks.sqlite`, Windows `%APPDATA%\genesis\tasks.sqlite` (WAL mode, sidecars beside it).
`EvoGit.Application.start/2` passes it to `EvoGit.Store`; `EvoGit.TaskRegistry.init/1` mirrors the same resolution.
Overrides, highest → lowest: the app env `config :evo_git, :data_dir` (only `config/test.exs` sets it, so test isolation outranks file config) → the config.toml `[data] dir` key (absolute or `~`-relative; invalid → `Logger.warning` + fallback; boot-time only) → the platform default; an override relocates the WHOLE data dir coherently (sqlite + sidecars, `mix migrate.store`, logs, caches, `genesis-source`) while per-repo `.genesis/` artifacts stay repo-root-fixed.
Desktop logs are `<data_dir>/logs/backend.log` and `shell.log`; headless boots log to stdout (journald, or `<data_dir>/server.log` on launchd/pidfile backends).
Persistence runs on Ecto 3.x via `xqlite_ecto3` (`EvoGit.Repo`, dynamic-repo capable) and `EvoGit.Store.Boot.run_migrations/1` migrates `priv/repo/migrations/` BEFORE any read/write.
`EvoGit.Store` is a thin GenServer facade over `store/operations/` + `store/schemas/` + `store/types/`; reads use 6 WAL readers, writes serialize through `EvoGit.Store.Writer`, and every read runs on a failure-isolated offload worker answering its documented degraded value — a slow read can never kill `EvoGit.Store` or `EvoGit.TaskRegistry`.
Migration `000001` is the ONE schema-creating step and every later one is a probe-guarded no-op on a fresh DB; a shipped version number is an identity that is never renumbered.

### Desktop Backend Port & Orphan Prevention (dynamic port)

The `genesis_desktop` backend port is **never fixed**: the Rust shell resolves it once at startup (`resolve_backend_port`) — an explicitly-set `PORT` is honored **only while that port is free** (bind probe), else a random free ephemeral port is picked, so a stale `PORT=9999` from a zombie cannot wedge the app; that port drives the sidecar env, readiness probe, watchdog URLs and WebView URL.
Shell-generated client URLs use the literal loopback IPv4 `127.0.0.1` (never `localhost`), because the endpoint binds IPv4 loopback only while macOS/Windows resolve `localhost` through `::1` first (the "browser works, Tauri window cannot connect" bug).
Boot and crash recovery share ONE latch-gated navigation driver (6 × 10s) on a dedicated bootstrap thread (not the Tauri `setup` hook); `dashboard_loaded` is set only by a genuine `PageLoadEvent::Finished` for the backend URL, and a Genesis loading page is held for the whole readiness wait (90s first boot, 30s per watchdog restart).
**Quit** (tray Quit / Cmd+Q) waits for dashboard confirmation only when the backend is healthy AND the dashboard is loaded; otherwise it kills and exits immediately.
**Orphan prevention (TCP lifetime pipe — zero polling)**: the shell binds `TcpListener` on `127.0.0.1:0` and passes `EVOGIT_LIFETIME_PORT`; `EvoDash.DesktopLifetime` blocks on `:gen_tcp.recv(sock, 0, :infinity)` and stops the BEAM only on a GENUINE peer close (`{:error, :closed}` → `System.stop(0)`), and the Rust hold thread likewise ends only on a real peer EOF — a spurious close would self-stop with exit 0, so both retry transient errors boundedly.
Port/navigation/latch diagnostics go to `<data_dir>/logs/shell.log`.
Details: `desktop/CONTEXT.md` + `desktop/src-tauri/CONTEXT.md` + `apps/evo_dash/CONTEXT.md`.
### Task Cancellation Model (graceful cancel vs force kill)

Task cancellation has **two distinct actions** (both node-aware via the RemoteNode RPC chain).
**Graceful cancel** — `EvoGit.TaskRegistry.cancel_task/1` (also RemoteAPI/RemoteNode/NodeContext) sets the task to **`:cancelling`** and sends each running agent session `{:cancel, :graceful}`, so the session enters `:cancelling`, appends a save-work user message through the pending-message transport and records the cancel flag in `EvoGit.AgentScheduler.ControlPlane` (never a whole-struct ETS read-modify-write); the wrapper is NOT killed — the phase finishes normally (3-turn grace budget), the final-status mapping force-persists **`:cancelled`** with result/usage preserved, and the task stays reviewable.
`:pending` cancels immediately; `:cancelling` is idempotent; new root spawns are blocked while cancelling; escalation via `force_kill_task/1` works from `:cancelling`.
**Force kill** — `TaskRegistry.force_kill_task/1` kills all agents, the in-flight exchange worker and the session, persisting **`:failed`** with result nil'd (from `:running` or `:cancelling`); `:cancelled` therefore means ONLY gracefully-cancelled tasks.
Dashboard UI: a visible **Cancel** button (`[:pending, :running, :awaiting_input]`, warning modal) and **force kill** in the card's three-dot dropdown (`[:running, :awaiting_input, :cancelling]`); `:cancelling` renders violet and appears in sidebar active lists.
Details: `apps/evo_git/CONTEXT.md` + `apps/evo_dash/CONTEXT.md`.
### Genesis Assistant (repo-less)

Genesis Assistant at `/assistant` (sidebar **Assistant**, `EvoDashWeb.HomeLive`) is a general-purpose Genesis operator: it understands the system — context tree, task lifecycle, agents, scheduler, models/config, dashboard — and helps the user control it (inspecting and driving tasks, pausing/resuming the scheduler, changing runtime or persisted configuration).
`GET /help` remains a 302 redirect to `/assistant` (query string preserved), so older links keep working.
`/assistant` runs ONE long-lived interactive agent session per conversation, addressed `/assistant?session=<agent_id>` (the agent id IS the chat id, so one worktree and prompt-cache identity per conversation), each user message delivered through `AgentScheduler.send_session_message/3` and live text/thinking/tool deltas applied via `HomeLive.Watch` + `HomeLive.Delta` (dropping `seq <= snapshot.seq`); the conversation list (idle/running/ended) lives in the app-layout sidebar directly under **Active Tasks**, and the one-shot `:reflect` task remains the fallback.
It speaks as Genesis in the first person, answers in the user's language, and its prompt teaches the role, the capability inventory and copy-ready operator recipes over the exact admitted MFAs.
Source reading is a core benefit: source/context/history tools let it discover real API contracts instead of relying on fixed command facades; its source tree is the reserved VCT mount `vct:///genesis-source` (bound to the managed `<data_dir>/genesis-source` clone), and `EvoGit.SelfReflectiveSource.reference_path/0` resolves the app-env override → `GENESIS_SOURCE_ROOT` → that mount when it holds a valid checkout → the managed clone, so re-pointing the mount points it at a different tree.
`EvoGit.Runtime.Assistant` is the interactive phase (build the repo-less spec, `start_session/1`, `await_close/2` for the session's lifetime, then `merge_and_report` once); `EvoGit.Agents.SelfReflective` + `EvoGit.Runtime.SelfReflective` remain the one-shot repo-less `:reflect` path (mode `"reflect"`, NO `:path`) with no worktree, git operations or subagent spawning.
Its single evaluation tool is `elixir_eval`, with fresh bindings and three authority tiers: **read** (Dune, read-only MFA whitelist, no approval) and **write** (Dune, known writes only, approval of the exact code) admit real APIs with their actual contracts — projected facades are optional conveniences, unlisted MFAs or wrong arities stay unavailable; **sudo** is unrestricted ordinary Elixir in the live VM, not a sandbox or OS root, and needs its own warning and explicit approval because it can affect processes, files and configuration without rollback.
Read/write refusals never imply escalation to sudo, and `CommandShell` is only the `run_command` tool's literal command registry, not an Assistant tool.
Chat replies retain task status, streaming and collapsible thought process; the transcript is a display projection, not raw history — only user-authored turns (`EvoGit.Agent.MessageMarker`'s `metadata[:user_authored]`, with a `<objective>` unwrap) and one assistant bubble per reply, ordered per message, so the persona prompt, `<context>` block and injected notices never surface; a streaming turn keeps ONE bubble across tool calls and a silent finish reconciles once from history; chat state restores through `EvoDash.ChatHistory`, guides stay transient UI pushes, and the chat keeps a layout-stable column: approvals surface as a fixed-height strip above the composer plus a single-request modal dialog (exact-code write grants vs prominently warned sudo), a new request also raises a browser notification while the window is hidden or unfocused, and the transcript is stick-to-bottom with no animated scrolling.
Pending requests are recovered from the core on remount.
User guide: [Genesis Assistant](docs/genesis-assistant.md); contracts: `apps/evo_git/CONTEXT.md`, `apps/evo_git/lib/evo_git/agent/tools/elixir_eval/CONTEXT.md`, `apps/evo_dash/CONTEXT.md`, `apps/evo_dash/lib/evo_dash_web/live/home_live/CONTEXT.md`.
### Merge Conflict Check & Auto-Resolution (Review Page)

The review page checks merge cleanliness **asynchronously** and offers agent-driven auto-resolution.
**Async merge check**: on review load (and on merge-target change) `ReviewLive` spawns a supervised task calling `EvoDash.NodeContext.check_merge/4` → `EvoGit.Review.check_merge/3` — a **non-mutating dry-run** that resolves both refs (identical SHAs → `:clean`) and runs `git merge-tree --write-tree --name-only --no-messages <branch> <target>` (git ≥ 2.38): no worktree, nothing under `.genesis/`, refs untouched; exit 0 → `:clean`, exit 1 → `{:conflict, files}`, exit 128 → error.
**UI**: a merge-status block above the Merge button — checking → clean (green) → conflict (amber, file list + **Auto-resolve conflict** with phx-confirm) → error (renders nothing).
**Default merge target** (selector preselection and the per-repo/merge-all fallback): `EvoGit.Review.default_merge_target/1` — the branch HEAD is on (detached HEAD skipped), else the first existing of `main`/`master`/`dev`/`prod`, else the first local branch; mirrored by all three RPC layers.
**Auto-resolve** (counts as resumed): marks the original task `review_status: :continued` and starts a new `:evolve` task with `[path:, mode: "simple", objective:, starting_commit:, merge_from: <task_id>, merge_target: <branch>]`; `EvoGit.TaskRegistry.MergeContext.apply_merge_context/4` strips the merge keys, loads the previous task, overrides `starting_commit` with its `commit_sha`, carries over `foreign_repos` and prepends a resolution-hints block (inspect `git log/diff base..end` and `base..target`; incremental milestone merges for hard conflicts), producing a reviewable `genesis/agent_*` branch whose merge is clean.
**Test seam**: `Application.get_env(:evo_dash, :merge_check_runner)`; exceptions rescue to `{:error, :check_failed}`.
Details: `apps/evo_git/CONTEXT.md` + `apps/evo_dash/CONTEXT.md`.

### ReqLLM Finch Connection Pool (LLM HTTP concurrency)

The ReqLLM Finch pool is **sized at boot** (`config/runtime.exs`): `count = EvoGit.ReqLLMPool.desired_count(total_concurrency)`, where the `max(total + 2, 8)` formula lives ONLY in `desired_count/1` (single source of truth — do NOT inline it) and `total_concurrency = max(Σ account-keyed concurrency, scheduler.default_llm_max_concurrency)` from `EvoGit.Config.resolve()`, counting each account once (its models and reasoning efforts share it).
**Pools are PER ORIGIN** — Finch materializes one pool per origin from the `:default` template (`size: 2`, lazily), so capacity = `count × 2` concurrent HTTP/1 streams per origin, NOT global; sum-based sizing is the provably safe upper bound.
**Runtime reconciliation is grow-only** (`EvoGit.ReqLLMPool`): resized on config changes and on Finch "excess queuing" errors (`max(ceil(effective * 1.5), 8)`), never shrunk (`Finch.set_pool_count` kills in-flight streams on shrink); it requires `start_pool_metrics?: true` (else `get_pool_status/2` enumerates no origins and reconciliation is a silent no-op) and tolerates lazy pools (`{:error, :not_found}` until an origin is used).
A runtime `default_llm_max_concurrency` override ALSO raises the scheduler's live per-account LLM slot pools (floor semantics; explicit account and in-peak limits stay authoritative).
Details: `config/CONTEXT.md` (full option table) + `apps/evo_git/CONTEXT.md` + `apps/evo_git/lib/evo_git/agent_scheduler/CONTEXT.md`.
### Peak/Off-Peak Hour Concurrency Scheduling (provider accounts)

Each `[[llm.providers]]` account may declare optional `peak_concurrency` (**`0` = hard pause**; every explicit in-peak value is exempt from the `default_llm_max_concurrency` floor), `peak_hours` (half-open `%{start: "HH:MM", end: "HH:MM"}` windows, `start > end` = overnight wrap, optionally scoped by `days` — `"mon".."sun"` and/or `"weekdays"`/`"weekends"`), `off_peak_days` (off-peak the ENTIRE day: normal `concurrency` 24/7, every window and `peak_concurrency` suppressed, wins over window `days`) and `timezone` (IANA, DST-aware; absent/blank → server local wall clock, never UTC).
Models and reasoning efforts within an account share these limits; distinct account IDs keep separate slot and exhaustion-backoff pools.
`EvoGit.PeakHours` is the **pure** single source of truth for parsing/validation and runtime math (`in_peak?/2,3`, `next_transition/2,3` — midnight day-boundary flips ARE transitions, `effective_concurrency/2,3`, `wall_clock_in/2`); the config schema delegates to it — do NOT re-implement window logic (needs `Calendar.put_time_zone_database(Tz.TimeZoneDatabase)` at boot).
`EvoGit.PeakHourEngine` (supervised after the scheduler) flips scheduler concurrency on start/timer/`"scheduler_config"` PubSub, one entry per account ID (`max(effective, default)` floor, zero stays zero); 0-capacity ENQUEUES slot requests instead of failing fast (granted on resume by `Slots.grant_pending_on_resume/1`; in-flight holders never evicted); clock seams `:peak_hours_now_fun`/`:peak_hours_utc_now_fun`.
Dashboard: Settings → provider-profile editor edits shared account schedules (absent/empty peak fields serialize as absent).
Details: `apps/evo_git/CONTEXT.md` (wake triggers, +100ms transition epsilon, 6h safety-net cap) + `apps/evo_git/lib/evo_git/agent_scheduler/CONTEXT.md` + `apps/evo_dash` settings CONTEXT.md.
### Managed Process & Tool-Execution Platform

Tool-call execution is owned by a managed platform, not by the agent loop.
`EvoGit.ToolRuntime.execute_batch/2` takes a `%Request{}` (agent/task identity, repo paths, role context, `max_timeout`) plus the model's indexed tool calls, partitions them on the serial-vs-parallel rule, acquires tool slots, runs each call in a supervised task with timeout/containment/output sanitization, and returns results in the unchanged `{index, tool_call_id, name, output}` shape; `EvoGit.Agent.ToolDispatch.batch_execute_tools/4,5` stays a thin delegator.
`EvoGit.ProcessManager` (supervised registry, every function total and `server:`-injectable) tracks each execution as an `%Execution{}` (identity, target, owner, backend/runtime, status, OS handle, exit/reason, stats, control log) with `track/attach/finish`, `list/get`, `sample/sample_all`, `signal/pause/resume/kill` (reason + actor recorded), `prune`, and PubSub topic `"processes"`; the field set is `process_manager/CONTEXT.md`'s.
`runtime` is the call's ORIGIN (`:foreground` = blocked on it, `:background` = an `EvoGit.BackgroundJobs` job); `backend` is how it is anchored — `:builtin` ran inside the BEAM (no OS identity, never sampled, control answers `{:error, :no_os_process}`), the sandbox values mean an external process.
Every terminal record carries ONE terminal-fact pair — `exit_code` (integer only for an external process that genuinely exited) plus `reason` (`:exited`, `:timeout`, `:invalid_arguments`, `:owner_died`, `{:killed_by, actor}`, `{:crashed, detail}`, `:no_os_process`) — mapped to `:completed`/`:failed`/`:killed`; an operator kill is authoritative over a racing natural exit.
Control is platform-independent behind `EvoGit.ProcessManager.Control` (systemd units, POSIX process groups, Windows `tasklist`/`taskkill` with pause/resume honestly `{:error, :unsupported}`); stats normalize to `%{cpu_time_ms, cpu_percent, memory_bytes, rss_bytes, pids, sampled_at}`, and owner death best-effort-kills and fails the execution.
The registry is node-local and in-memory (never stored, archived or aggregated; lost on restart), keeping terminal records for `:process_finished_retention_ms` (default 300 s) / newest `:process_finished_max_records` (200) while live records are never pruned.
The dashboard `/processes` page (plus a compact per-agent section in `/agents`) lists live and recent executions asynchronously and streams `"processes"` pushes with no polling; a `:builtin` row renders `—` for Target/Uptime/CPU/Memory with no control cluster, and every terminate/kill needs a non-empty reason.
Details: `apps/evo_git/lib/evo_git/process_manager/CONTEXT.md`, `apps/evo_git/lib/evo_git/tool_runtime/CONTEXT.md`, `apps/evo_dash/lib/evo_dash_web/live/processes_live/CONTEXT.md`, `docs/process-management.md`.
### SSH Remote Development

A VSCode Remote-SSH-like workflow: the local Phoenix dashboard controls a remote host's **single `genesis_server` instance** over an SSH tunnel via Erlang distribution.
The remote side is the ordinary dashboard server (HTTP always on) and no second process or unit exists: distribution is toggled **at runtime inside that same BEAM**, so a host that already ran `genesis start` never ends up with two instances and never restarts to become a remote target.
**Runtime toggle**: `bin/genesis remote start|stop|status|logs` drives distribution on the existing server through `EvoGit.DaemonControl` (atomic 0600 control request + `SIGHUP`, matching `SEQ` acknowledgement, durable intent restored at boot); `remote stop` detaches distribution only, `genesis stop` stops the server.
`EvoGit.RemoteConnection` delegates service control to the release CLI, never builds service-manager commands itself, and verifies the reported live distribution identity rather than trusting stale state files.
**Distribution**: `EvoGit.EpmdDist` is EPMD-less; `EvoGit.Distribution.pin_dist_port/1` pins the port at runtime enable, and the local dashboard auto-enables distribution and connects through an SSH loopback port-forward owned by `EvoGit.RemoteConnection`.
**Data access**: `:erpc.call/5` to `EvoGit.AgentScheduler.RemoteAPI` (native BEAM terms, no serialization); PubSub uses the cluster-aware `:pg` adapter.
**Dashboard RPC UX**: ALL node-aware data loads run OUTSIDE the LiveView process via `EvoDash.TaskSupervisor` + self-message + stale-guards — **no LiveView ever blocks on a cross-node `:erpc` call, and there is NO periodic polling anywhere** (push-based PubSub; per-page consumers: `apps/evo_dash/lib/evo_dash_web/live/CONTEXT.md`).
**Bootstrap vs Connect**: bootstrap installs the release, copies config, mints credentials and starts the server through the release CLI; connect only establishes the tunnel and distribution link.
SSH/SCP use CLI ports (not Erlang `:ssh`), remote commands are argv arrays, and `EvoGit.RemoteBootstrap.sh_wrap/1` uses `/bin/sh -c '<script>'` with single-quote-free POSIX inner scripts so non-POSIX login shells pass through; remote failures must retain useful stderr.
Connections target different hosts, one distribution identity per host (`genesis_remote_<id>@127.0.0.1`), and tunnel readiness is checked before `Node.connect/1`.
**Remote assets**: `EvoGit.RemoteBootstrap.download_url/1` deterministically returns `https://genesis.evox.group/dl/genesis_server_<platform>.tar.xz` (no network discovery); only glibc Linux variants are published.
Details: `apps/evo_git/CONTEXT.md` + `apps/evo_dash/lib/evo_dash/CONTEXT.md` + `rel/CONTEXT.md`.
### Desktop App Build Pipeline

`.github/workflows/build-desktop.yml` builds native desktop installers on every release (version tag `v*` or manual dispatch) and creates the release itself: all platform builds finish first, then `publish-release` creates a **draft** release with every artifact attached and flips it public as its FINAL step, so `releases/latest` never points at a release whose assets are still uploading.
Each platform job runs `mix release genesis_desktop` (native, `include_erts`) → copies the release dir to `desktop/src-tauri/resources/genesis-backend/` → `tauri build`; the headless `genesis_server` release is also built and uploaded as `.tar.xz` (linux x64/arm64, darwin arm64) — that tarball is both the headless dashboard server AND the SSH remote target.
**Five job groups** on native runners: `build-linux` (ubuntu-24.04 x64/arm64 → `.deb`/`.rpm`/AppImage/`.tar.gz`), `build-linux-server` (glibc `genesis_server` on ubuntu-22.04, musl disabled), `build-macos-arm64`, `build-windows-x64` (`.msi`/NSIS) and `publish-release`; toolchains are pinned via `OTP_VERSION`/`ELIXIR_VERSION` and the Tauri CLI comes from npm.

### Headless Server (CLI + install script)

Genesis also ships as a **headless server**: the `genesis_server` release runs BOTH apps under plain http (no Tauri shell, no `wx`), driven by the `genesis` CLI (`rel/overlays/bin/genesis` → `bin/genesis`).
CLI: bare `genesis` / `genesis serve [--ip A] [--port P]` runs in the foreground; `genesis start` daemonizes it (`systemd-run --user --unit=genesis-server`, launchd `com.genesis.server`, or setsid/nohup + pidfile) and waits for health; plus `status`, `logs [-f]`, `stop`, `restart`, `url`, `version`, `help`. Defaults are `127.0.0.1:9999`; service state lives in `<data dir>/server.env`.
`genesis update` (alias `upgrade`) self-updates in place: reads `latest.json`'s `server` map (or a pinned tag), refuses while the instance reports active tasks unless `--force`, downloads and sha256-verifies the tarball BEFORE stopping the service, extracts to a staged sibling, then stops → swaps atomically → restarts with the saved ip/port → verifies `/health` and rolls back on failure; a lock at `<data dir>/update.lock` serializes updates. `--check` reports only (`--json` one line; exit `10` = update available), plus `--version TAG`, `--wait N`, `--no-linger`, and `GENESIS_DOWNLOAD_BASE`/`GENESIS_DOWNLOAD_FALLBACK_BASE`.
`genesis remote …` toggles distribution on that SAME instance (see "SSH Remote Development").
On the Linux `systemd` backend `start` checks `loginctl` lingering and offers `loginctl enable-linger <user>` (TTY only, default yes; `GENESIS_LINGER=ask|yes|no`, `--no-linger`; every outcome is warn-only).
**Server mode** is baked (`server_release: true`) or forced by `EVOGIT_SERVER=1`: the endpoint binds `PHX_IP` (default `127.0.0.1`) and `PORT` (default `9999`), the URL host is `PHX_HOST` else the bind address, plain http with `check_origin: false`, `SECRET_KEY_BASE` from env or a persisted `<data dir>/secret_key_base`, logs to stdout/journald.
Installer: `curl -LsSf https://genesis.evox.group/dl/install.sh | sh` installs into `~/.local/share/genesis/server` and symlinks `~/.local/bin/genesis`; assets are `genesis_server_linux_x64.tar.xz`, `_linux_arm64`, `_darwin_arm64` — Windows headless is NOT supported in v1.
Details: `rel/CONTEXT.md` + `config/CONTEXT.md` + `scripts/CONTEXT.md` + `apps/evo_dash/CONTEXT.md` + `.github/workflows/CONTEXT.md` + `docs/server-update.md`.
### Auto-Update / Push-Update (tauri-plugin-updater v2 — implemented)

Desktop auto-update (design record: `docs/auto-update.md`) uses the official `tauri-plugin-updater` v2 in the Rust shell, **two-phase**: check/download/verify anytime, **apply is manual-click only and gated on task idle**.
Feed = static `latest.json` via the **genesis.evox.group `/dl/` Cloudflare proxy** (mainland-China reachable; payload `url`s and inline `.sig` ride the proxied manifest), with GitHub Releases as the upstream target; artifacts use the unversioned `/dl/<asset>` form only (tag-scoped routes ship from an external worker after a manual deploy).
**Rust shell**: `bundle.createUpdaterArtifacts: true`, `plugins.updater` endpoints, and the commands `check_update` (`up_to_date|available|not_configured|not_available|error`), `download_update` and `begin_update` (sets the watchdog update intent; on backend exit 0 the watchdog installs the staged payload and relaunches).
**Dashboard**: `EvoDash.UpdateStatus` hub (topic `"updates"`), a global on-mount hook + JS bridge (checks ~30s after startup then ~6h, auto-downloads after a successful check, sidebar dot on System), and `SystemLive`'s "Software Update" card.
**Apply**: "Restart & Update" → idle gate `list_task_ids([:running, :pending, :cancelling, :finalizing]) == []` (node-aware); busy → Defer / "Apply & gracefully stop tasks" (results preserved as `:cancelled`) / user-warned `force_kill_task/1`; then `begin_update` → `System.stop/0`. Desktop mode + local node only; Linux non-AppImage installs are **notify-only**.
**Headless self-update uses NO plugin** (`docs/server-update.md`): the release CLI owns the same shape — `genesis update --check` (exit `10`) then `genesis update`; deferred items (Windows Authenticode, Linux apt/dnf repos + GPG, dashboard-initiated/remote-node server updates, staged rollout) and activation state are tracked in `docs/auto-update.md`.
Details: `desktop/src-tauri/CONTEXT.md` + `.github/workflows/CONTEXT.md` + `apps/evo_dash/CONTEXT.md` + `docs/server-update.md`.
