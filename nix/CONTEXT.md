# Nix — NixOS Build Support

## Intent

Nix build support for Genesis. The primary entry points are the flake at the repository root (`flake.nix`) and the two derivations it calls. Users can build the CLI app or the Tauri desktop app directly with `nix build`/`nix run`.

## Routing Table

- None — leaf directory (two scripts: `bundle-vendor.sh`, `desktop-smoke.sh`).

## API Surface

| File | Purpose |
|------|---------|
| `bundle-vendor.sh` | Downloads ripgrep and copies system git into `apps/evo_git/priv/vendor/<platform>/`, replicating the "Bundle vendor binaries" step from `.github/workflows/build-desktop.yml`. Auto-detects x86_64/aarch64 Linux targets. |
| `desktop-smoke.sh` | Release-time desktop start-up smoke test — boots the packaged Tauri app in `--headless` mode and asserts the dashboard is served, then shuts it down. Run via `nix run .#desktop-smoke`; the flake wrapper exports `GENESIS_DESKTOP_APP` and provides `curl`/`coreutils`/`grep`/`procps`. |

## Desktop Smoke Test

`desktop-smoke.sh` proves the REAL packaged desktop app starts: the Tauri shell runs in its `--headless` mode (`desktop/src-tauri/src/main.rs` `run_headless()`), resolves the bundled release through `sidecar_path::resolve_launcher` (the same resolution the GUI path uses), starts the BEAM and serves the dashboard over HTTP on `127.0.0.1:$PORT`.
Nothing else boots the packaged artifact, which is why a release could ship `+t 80000` in `vm.args`, exhaust the atom table, and fail to start on ALL platforms with a silent, zero-log boot failure while every test stayed green.
Run it manually at release time: `nix run .#desktop-smoke` (it is also `packages.desktop-smoke`; that exposure exists only so the app's program path resolves).
It is deliberately NOT a flake `checks` entry and never wired into CI — it builds the entire desktop app and boots a real BEAM, so it must stay an explicit release-manager action.
Assertions, in order (each failure prints a single `[smoke] FAIL:` line): package layout (`$GENESIS_DESKTOP_APP/lib/genesis-desktop/resources/genesis-backend/bin/genesis_desktop` exists — catches drift between `genesis-desktop.nix` and the script); the packaged `releases/*/vm.args` carries NO `+t`/`+P` process/atom cap (the atom-table regression guard, and it names the historical `+t 80000` failure); a FINAL HTTP 200 **reached by following redirects** (`curl --location`) from `http://127.0.0.1:$PORT/` within 180s, whose body contains `<html` — the dashboard's root `/` answers `302` (to `/projects`, or `/welcome` on a fresh data dir), so a probe that does not follow the redirect chain can never see the 200 (the chain is followed rather than hitting a hard-coded path, so the probe survives routing changes; the `[smoke]` success line prints the final URL it landed on); non-empty `$XDG_DATA_HOME/genesis/logs/{shell,backend}.log` free of boot-failure markers (`atom table`, `no more index entries`, `failed to start`, `CRASH`); SIGTERM shutdown, port closed, and no leftover release process (`pgrep -f` on the release path, ancestors excluded — never a broad `beam.smp` match).
The port probe (`port_taken`) and the post-shutdown "port closed" check deliberately do NOT follow redirects — they only assert that something answers on the socket, so any HTTP status (including the `/` → `/projects` 302) proves liveness.
Reading a failure: the `[smoke] FAIL:` line names the assertion, and the 40-line tails of the headless stdout plus both data-dir logs are printed above it — an EMPTY `backend.log` is itself the atom-table signature, `PORT ... already in use` in the headless output means the probed port was taken (just re-run), a readiness timeout that shows `GET / ... Sent 302` is a redirect NOT being followed (the probe must keep `--location`), and a readiness timeout with no logs means the release never reached the BEAM.
The run is isolated (temp `HOME`, `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, `XDG_RUNTIME_DIR`), so it never touches the developer's `tasks.sqlite` or `config.toml`.

## Constraints

- **One BEAM package set for everything.** `flake.nix` extends the `packagesWith erlang_29` set to Elixir 1.20 (`(pkgs.beam.packagesWith pkgs.beam.interpreters.erlang_29).extend (final: prev: { elixir = final.elixir_1_20; })`) and derives `erlang` + `elixir` from that single binding, so the release builds (`packages.default`, `packages.desktop`) and `devShells.default` all run OTP 29 + Elixir 1.20 (matching CI's `ELIXIR_VERSION`). Never rely on the set default: `packagesWith erlang_29` defaults to Elixir 1.18, which cannot compile the app — `apps/evo_git/lib/evo_git/config/schema/llm_constraints.ex` reads a module attribute holding compiled `%Regex{}` values inside a function body, and < 1.20 refuses to escape the pattern's `#Reference<>` ("cannot inject attribute @constraint_tables into function/macro because cannot escape"). Keep the override on the shared `beamPkgs`, not per-output, or the release build and the dev shell drift apart again.
- The Nix expressions (`flake.nix`, `genesis.nix`, `genesis-desktop.nix`) live at the repository ROOT, not here.

- **No `cargoHash` maintenance**: `genesis-desktop.nix` vendors Rust deps via `cargoLock.lockFile = ./desktop/src-tauri/Cargo.lock` — the vendor store path derives from the lock file, so updating Cargo.lock never requires a hash edit. Only git deps would need `cargoLock.outputHashes`. Both derivations read `version` from the repo-root `VERSION` file (`lib.fileContents ./VERSION`) — never hardcode it. The flake hashes that still need manual updates live in `genesis.nix`: `mixFodDeps.hash` (when `mix.lock` or the prod-visible dependency set changes) and the per-target `precompiled_nifs` hashes (when a NIF package version changes).
- Refreshing `mixFodDeps.hash` after a `mix deps.update --all` does NOT require a full `nix build`: set `hash = lib.fakeHash;`, then locate and realize only the dependency FOD — `nix eval --raw .#default.drvPath` → `nix-store -q --references <drv> | grep -i mix-deps` → `nix-store --realise <fod.drv>` — whose hash-mismatch error prints the correct `sha256-...` value, and whose exit 0 after pasting it in verifies the new hash. Realizing is the only authority: `mix deps.get` resolves `mix.lock` against the `mix.exs` constraints inside the FOD build, so a hash observed at an earlier lock/constraint state does not necessarily realize against the current tree.
- **The `mixFodDeps` pin covers the PROD-VISIBLE dependency set, not just `mix.lock`.**
  `fetchMixDeps` builds its fixed-output derivation with `MIX_ENV=prod mix deps.get --only prod`, so moving an EXISTING dep out of `only: [:dev, :test]` into prod (e.g. `{:file_system, "~> 1.1"}` moved for `apps/evo_git/lib/evo_git/config/watcher.ex`) changes the FOD's contents and its required hash while `mix.lock` stays byte-identical.
  Recompute the hash for ANY prod-scope change in a `mix.exs`, not only for `mix deps.get`/`mix deps.update`.
  A stale hash is NOT reported as a hash mismatch on a machine that already has the old content-addressed output: fixed-output derivations are keyed by the DECLARED hash, so the old tree is silently reused and the failure only surfaces later as `** (Mix) Could not find application :file_system` (or whichever dep moved) during app compilation, which reads like a source bug rather than a pin bug.
  Recipe: set `hash = lib.fakeHash;`, run `nix build .#default --no-link` and copy the `got: sha256-…` value from the mismatch error, then re-pin and build again; use `nix build .#default --rebuild` when a silent stale reuse is suspected, since the ordinary build reports a cached path as success.
  `genesis.nix`'s `postConfigure` preflight (`mix deps` + a grep for Mix 1.20's `the dependency is not available` line, which still exits 0 — the exit status alone never catches this) now fails the build fast with this recipe instead of letting the cryptic `Could not find application` error through.
- `precompiled_nifs` holds one entry per Rustler NIF package — a `prefix` (`libmdex_native_nif-v0.3.0-nif-2.15`), a `urlPrefix` (the GitHub release download URL) and `hashes`, a map keyed by Rust target triple (`x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`, `x86_64-apple-darwin`, `aarch64-apple-darwin`). `nifAssets` resolves each entry for `stdenv.hostPlatform` into the `{ name, file }` pairs that the `preConfigure` hook copies into `$RUSTLER_PRECOMPILED_GLOBAL_CACHE_PATH`: `name` must reproduce the real release asset filename or `rustler_precompiled` misses the cache and tries to download inside the (network-less) build sandbox. A `rustTarget` with no pinned hash fails evaluation with an explicit `throw` instead of silently fetching a foreign asset.
- Only mdex_native's plain, unsuffixed asset per target is pinned: it is the variant selected when `:syntax_highlighter` is unset and `:use_legacy_artifacts` keeps its `false` default, while upstream also publishes `--lumis`/`--syntect`/`--legacy_cpu`-suffixed variants that must never be reintroduced (a mismatched variant name silently misses the seeded cache and the network-less sandbox then fails the build).
- Every NIF asset hash is **platform-specific** — the same version+ABI ships different bytes per target triple — so refreshing `precompiled_nifs` is a per-release-asset job, not a per-version one: download each target's asset (e.g. `https://github.com/leandrocp/mdex_native/releases/download/v<version>/<prefix>-<rustTarget>.so.tar.gz`) and hash it with `nix hash file --sri <file>` (flat SHA-256, which is what `fetchurl` verifies). Reuse the same realize-the-FOD check for each entry: `nix eval --raw .#default.drvPath` → `nix-store -q --references <drv> | grep '\.so\.tar\.gz'` → `nix-store --realise <fod.drv>` per FOD (exit 0 proves the pin).
- Never guess a `precompiled_nifs` asset name or its ABI suffix: both the library prefix (`libmdex_native_nif` vs `libxqlitenif`) and the ABI suffix (`nif-2.15` for mdex_native, `nif-2.17` for xqlite, tracking the OTP ABI each package was built against) are per-package, and the version comes from `mix.lock`. Read the real asset names off the GitHub release listing for that version (the hex package's unpacked `priv/native/*.so`, or its bundled checksum file — `checksum-Elixir.MDExNative.Native.exs` for mdex_native, `checksum-Erlang.<Module>.exs` elsewhere — lists the same names and their per-asset digests) and update `prefix` + `urlPrefix` + `hashes` together on a bump.
- `mixFodDeps` covers Hex deps only, so a NIF bump needs BOTH the `mixFodDeps.hash` refresh AND the `precompiled_nifs` entry update; verify each separately with `nix-store --realise <fod.drv>` on the drvs referenced by `nix eval --raw .#default.drvPath` (`.#desktop.drvPath` must evaluate too). A green `nix build .#default` is the end-to-end proof of both — the build sandbox has no network, so it also proves the seeded cache still satisfies `rustler_precompiled` at the new version.
- Scripts in this directory are designed to run inside the `nix develop` shell where `curl`, `git`, and `rg` are available.
- `bundle-vendor.sh` is only needed for the manual `nix develop` → `mix release` workflow. The `nix build` path handles vendor binaries via the derivation's `postInstall` hook.
- `bundle-vendor.sh` and CI's `Bundle vendor binaries` step stay in parity on ripgrep `15.2.0` (musl target on Linux for a static binary) and both copy the host `git` binary; unlike CI, the script does NOT verify a `sha256`, so a corrupted download is copied silently.
- `desktop-smoke.sh` is wrapped by `writeShellApplication`, which runs `shellcheck` at build time — the script must stay shellcheck-clean (and it relies on the wrapper's `set -o errexit -o nounset -o pipefail`).
- Keep the smoke test out of `checks` and out of CI, and never make `desktop-smoke.sh` build anything: it consumes `$GENESIS_DESKTOP_APP` (an already-built `packages.desktop`) only.

## EGL / Mesa

- The desktop package and the dev shell MUST resolve EGL from the flake's OWN `pkgs.mesa` via `__EGL_VENDOR_LIBRARY_DIRS=${mesa}/share/glvnd/egl_vendor.d` (the app wrapper uses `--set-default`, the shell exports it).
- `libglvnd` has the vendor dirs `/run/opengl-driver/share/glvnd/egl_vendor.d:/etc/glvnd/egl_vendor.d:/usr/share/glvnd/egl_vendor.d` compiled in, so the HOST's mesa is tried first.
- A host mesa built against a NEWER glibc than the flake's pin fails `dlopen(libEGL_mesa.so.0)` with `version 'GLIBC_2.43' not found`, leaving glvnd with no usable EGL vendor.
- `eglGetDisplay` then returns `EGL_NO_DISPLAY` and WebKitWebProcess aborts with `Could not create default EGL display: EGL_BAD_PARAMETER`.
- The symptom is a blank / never-loading WebView while the BEAM backend still serves HTTP 200, so it looks like a frontend bug rather than a graphics one.
- Bundling mesa costs roughly 1 GiB of closure (`libgallium` + `llvm`); `mesa.override` trimming would drop the binary-cache hits, so it is deliberately NOT done.
- `/run/opengl-driver` exists only on NixOS, so the override also keeps the package correct on non-NixOS hosts, where the flake's mesa is the only vendor dir available.
- Do NOT set `EGL_PLATFORM` or any WebKit workaround env var: the vendor-dir override is the fix, and the tested alternatives did not help.
- `WEBKIT_DISABLE_DMABUF_RENDERER=1` (dev shell) stays a separate, unrelated compositor workaround.
- The override REPLACES the host vendor dirs, so a proprietary-NVIDIA EGL vendor under `/run/opengl-driver` is not consulted; such hosts fall back to the bundled mesa (llvmpipe software rendering) and can re-enable their vendor with an explicit `__EGL_VENDOR_LIBRARY_DIRS` (the app wrapper uses `--set-default` so an operator override wins).
- `nix/desktop-smoke.sh` runs the shell in its `--headless` mode, which creates NO WebView, so it cannot catch a WebView/EGL regression like this one; the window-free way to check the GUI path is to run the packaged app against a headless compositor (`XDG_RUNTIME_DIR=<writable tmp> weston --backend=headless-backend.so --socket=wl-test`, then `WAYLAND_DISPLAY=wl-test <pkg>/bin/genesis-desktop` with `DISPLAY` unset) and assert ZERO `Could not create default EGL display` lines plus the `[desktop] webview loaded the dashboard` log line.

## Rust Binaries & New Native Payloads

- The dev shell (`flake.nix` `devShells.default`) provides `cargo`/`rustc`/`rustfmt`/`clippy`; `nix/` itself contains no build logic.
- The ONLY Rust build in Nix is `tauriBinary = rustPlatform.buildRustPackage` in `../genesis-desktop.nix`, with `src = src + "/desktop/src-tauri"` and `cargoLock.lockFile = ./desktop/src-tauri/Cargo.lock`.
- `desktop/src-tauri` is the only in-repo Rust crate (`**/Cargo.toml` elsewhere are vendored `deps/` NIF crates).
- A NEW standalone crate is built by its own `rustPlatform.buildRustPackage` (`src = src + "/<crate-dir>"`, `cargoLock.lockFile = ./<crate-dir>/Cargo.lock`, no `cargoHash`) and must be imported into `flake.nix` (or passed as an argument to `genesis.nix`/`genesis-desktop.nix`).
- The vendor destination is `$out/lib/evo_git-${version}/priv/vendor/${vendorPlatform}` (`genesis.nix` `postInstall`), shared by BOTH `mixReleaseName` variants, so a payload copied there reaches the runtime through `Application.app_dir(:evo_git, "priv/vendor/<platform>")`.
- `EvoGit.Executable.resolve/1` maps a bare name to `priv/vendor/<platform>/<name>` (`<name>.exe` on Windows; `git` → `mingit/cmd/git.exe`), so that directory is the drop-in spot for any new bundled external binary — system PATH still wins.
- `packages.default` builds the `genesis` release only; the headless `genesis_server` release is CI-built and has NO flake package, so a new bundled binary also needs the `Bundle vendor binaries`-style step in `.github/workflows/build-desktop.yml`.
- Tauri-side payloads ride `bundle.resources = ["resources/genesis-backend"]`; there is NO `externalBin`/sidecar declaration, so a binary that must sit beside the Tauri exe has to be reachable under the `resources/genesis-backend/…` symlink (populate it inside the release) rather than added to `externalBin`.
- Gotcha: the `postBuild` `chmod -R u+w` in `genesis-desktop.nix` hardcodes `target/x86_64-unknown-linux-gnu/release/resources`; aarch64 relies on the non-fatal `target/release/resources` fallback, so a new resource under a non-x86_64 layout needs that fallback to hold.
