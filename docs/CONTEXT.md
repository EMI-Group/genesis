# ./docs — Design Records & Reference Documentation

## Intent
Long-form design records, reference documentation and short user-facing guides for Genesis: rationale, verified external facts, and implementation details too granular for the CONTEXT.md tree.

## API Surface
- `agent-runtime-refactor.md` — design record + phased plan (P0–P6) for the **implemented** agent-runtime refactor (P0–P4 core + P6 dashboard; P5 durability deliberately deferred): ONE supervised `EvoGit.Agent.Session` (`gen_statem`) per agent — one-shot and interactive alike — owning the single copy of `%EvoGit.Agent.State{}` (the ETS context mirror collapses to the summary-only `:evogit_agent_summary` read model), a per-exchange worker `Task` running the loop so the owner stays responsive, a `:yield`/`:finish` split that lets ONE engine serve both today's one-shot agents and interactive sessions (`:awaiting_input` task status), consumer-gated PUSH-ONLY `EvoGit.Agent.Stream` deltas (one `watch/1` call = snapshot + monotonic `seq` + registration in the session-owned watcher set, coalesced broadcasts on the `EvoGit.PubSub` `"agent:<id>"` topic, no callbacks and no broadcast with zero watchers, no polling/cursor path, gaps repaired by a fresh snapshot), a worktree kept for the session's whole life and reclaimed exactly once when it ends (no idle TTL, no suspend, explicit close instead), lifecycle re-keying onto the session pid, the invariants to pin with tests, and durability as deferred with the seams that keep it additive.
- `genesis-assistant.md` — user guide (not a design record): the dashboard **Assistant** (`/assistant`; `/help` 302-redirects there) as a general-purpose Genesis operator — reading the Genesis source through the `vct:///genesis-source` system mount (re-pointable, `GENESIS_SOURCE_ROOT` override), CONTEXT.md/git-history reading, `elixir_eval` read/write/sudo tiers with exact-code approvals, task control, the guide overlay, and runtime versus saved configuration.
- `auto-update.md` — full design record for the desktop auto-update / push-update system (tauri-plugin-updater v2): two-phase check/download/apply model, the genesis.evox.group `/dl/` update feed, CI signing, platform matrix, and remaining blockers.
- `server-update.md` — design record AND user guide for the headless `genesis_server` self-update: why the release shell CLI (not the desktop plugin) performs it, the shared `latest.json` `server` map + published `.sha256`, the `genesis update`/`upgrade` flags, exit codes and output lines, the `/server/status` idle gate, the staged stop→swap→start→`/health`→rollback flow, and the deferred dashboard/remote-node orchestration.
- `experiments.md` — results/reference document: the per-regime experimental results (formation, continuation, redevelopment, Terminal-Bench) and their figures, moved out of the top-level README; figures live under `images/experiments/`.
- `harness-alignment.md` — comparison record: Genesis agent runtime (tools, result conventions, role prompts, compression, loop, delegation) vs the DeepSeek Harness (`dsh`), with a tiered proposal list for aligning our environment with the harness newer DeepSeek models are trained on. Carries the verified `dsh` facts (tool names/caps/footers, prompt-slot table, compaction thresholds, subagent limits) so future agents do not re-investigate `/home/bill/Source/deepseek-harness`.
- `llm-profiles.md` — user guide: canonical provider accounts and nested concrete-model inventories, reasoning defaults versus explicit effort selection, dashboard setup, shared capacity and schedules, credentials, and legacy configuration compatibility.
- `llm-oauth.md` — user guide: ChatGPT/Codex or Claude Pro-Max subscription authentication through vendor CLI login, managed `auth.json` import, canonical provider-profile examples, setup paths, and troubleshooting.
- `process-management.md` — design record of the managed process & tool-execution platform: `EvoGit.ProcessManager`'s `%Execution{}` lifecycle, normalized OS handles and their control backends (systemd unit / POSIX pid+pgid / Windows pid), stats sampling and CPU-percent derivation, the `"processes"` PubSub contract, `EvoGit.ToolRuntime`'s batch responsibilities, the `/processes` inspector (the only dashboard surface, with its `?agent_id=`/`?task_id=` filters), an extension guide, and the known limitations (untested systemd control path, no Windows pause/resume/signal).
- `virtual-tree.md` — design record of the **implemented, deliberately minimal** Virtual Context Tree (VCT): an internal `vct:///…` namespace with a DB-backed, capped mount registry (`vct_mounts` in the task store, 100 projects by default, oldest evicted), the optional global context level (`<data_dir>/vct/CONTEXT.md`, rendered as `global/CONTEXT.md`), `ContextNode.vct_path`, and the first reserved system mount `vct:///genesis-source` (Genesis's own source checkout: boot-seeded via `EvoGit.SelfReflectiveSource.system_mounts/0`, re-ensured with `VCT.ensure_mount/3`, resolvable but excluded from `projects/1`/`search/2`, never evicted, `{:error, :reserved_point}` on forget); never materialized on the filesystem — explicitly NOT symlink farms, bind mounts, FUSE, junctions, per-mount worktrees or any filesystem-layout change (tasks still run in one concrete repo worktree with unchanged `foreign_repos`); closes with the deferred future extension (remote `vct://<host>/…`, global-context UI, further capability/system mounts as git mounts, nested mounts, materialization explicitly rejected).
- `images/` — figures referenced by the design records and reference documents (`images/experiments/` for the experimental plots), plus the promo-film poster `promo-poster.jpg`.
- `images/readme/` — original README diagrams in the website palette: light/dark recursive-agent Git-history AVIF recordings (29.2 seconds, 30 FPS, 1440 x 960) with matching reduced-motion/static PNG fallbacks, and a three-layer architecture SVG. The README uses a centered 720px picture with theme and reduced-motion sources. Legacy recursive-work SVG/GIF assets remain available; their editable sources, render/encode scripts and all asset notes live alongside the files.

## Constraints

- README curation/update instructions live in `readme-evidence.md`; `readme-evidence.json` selects exactly three projects and result fields, and `readme-evidence.snapshot.json` stores minimal published data for deterministic offline generation.
- These are design records, not CONTEXT.md nodes: they may carry rationale and sequencing that CONTEXT.md deliberately must not.
- Keep external-fact claims accurate (Cloudflare worker behaviour, GitHub release redirect chains, CI mechanics) — other agents cite these instead of re-investigating.
- The desktop updater (`tauri-plugin-updater`) and the headless server updater (`genesis update`) share ONE `latest.json`: `platforms` is the desktop half and `server` the headless-tarball half, so a manifest change has to keep both consumers working and a server-only release must still publish the file.
- The tag-scoped `/dl/<tag>/<asset>` worker form is only live after a manual `pnpm deploy` in `genesis-doc`; the unversioned `/dl/<asset>` form is what shipped consumers use, and pinned server installs may fall back to GitHub.
- Design records describe the CURRENT design; edit them in place as the design changes rather than appending change history.
- The numbers in `experiments.md` mirror the published Genesis paper — keep them verbatim; they are observed system-level results, not normalized benchmarks.
